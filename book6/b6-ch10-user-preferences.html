Chapter 10: User Preference Storage for Personalized AI

Personalization is what separates a generic AI assistant from one that users actually want to come back to. When your application remembers that a user prefers concise responses, works primarily in Python, operates in the Pacific timezone, and gets frustrated by overly formal language, every interaction improves. This chapter covers how to design and implement a complete user preference system for AI applications — one that goes beyond a simple key-value store to capture explicit settings, inferred behavioral signals, semantic preferences expressed as vectors, and the machinery to make all of it available at inference time without destroying your latency budget.

---

The Anatomy of AI User Preferences

User preferences in AI applications are not a single thing. They exist at multiple layers, each contributing differently to how your model behaves.

Explicit preferences are settings the user consciously sets: "Respond in Spanish," "Keep answers under 200 words," "Don't use markdown formatting." These are discrete, structured, and easy to act on. They belong in typed columns with strict constraints.

Implicit preferences are inferred from behavior: a user who consistently upvotes short answers probably wants brevity even if they never said so. A user who rephrases questions about code into more specific forms after getting broad answers is signaling they want precision. These are statistical signals extracted from interaction logs.

Semantic preferences are the most interesting for AI systems. They capture concepts that don't reduce cleanly to a flag or a number. "This user likes analogies from physics" or "prefers examples from the financial domain" are preferences that live in embedding space and can be retrieved by similarity against incoming queries.

Session-level context is temporary preference — what the user needs right now, in this conversation, based on what they've said in the last ten turns. This is your conversation history feeding into in-context personalization.

The reason PostgreSQL handles this well is that it speaks all four of these languages natively. JSONB handles arbitrary structured settings. Numeric aggregations and window functions extract implicit signals from logs. pgvector stores semantic preference embeddings. And foreign keys tie all of it to a single users table that your security policies can anchor to.

A Redis-backed cache layer gives you sub-millisecond preference retrieval so that adding personalization doesn't add perceptible latency to inference calls.

graph TD
    A[Explicit: typed columns, user-set] --> E[Assembled system prompt addendum]
    B[Implicit: aggregated from interaction logs] --> E
    C[Semantic: pgvector, retrieved by query similarity] --> E
    D[Session: last N turns in this conversation] --> E
    E --> LLM[LLM call with personalized params]

*Four independent sources feed one assembled context — each stored and retrieved the way its data shape actually calls for.*

---

Schema Design: Layered Preference Storage

The schema needs to support all four preference types without collapsing them into an unmanageable blob. Here is a production-ready design:

-- Core user table (referenced by all preference tables)
CREATE TABLE users (
    user_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    external_id     TEXT UNIQUE NOT NULL,          -- maps to your auth provider
    email           TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_active_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    is_active       BOOLEAN NOT NULL DEFAULT true
);

-- Explicit preferences: typed, constrained, version-tracked
CREATE TABLE user_explicit_preferences (
    preference_id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id             UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    response_language   TEXT NOT NULL DEFAULT 'en',
    response_length     TEXT NOT NULL DEFAULT 'medium'
                            CHECK (response_length IN ('brief', 'medium', 'detailed')),
    tone                TEXT NOT NULL DEFAULT 'neutral'
                            CHECK (tone IN ('formal', 'neutral', 'casual')),
    code_language       TEXT,                      -- preferred programming language
    use_markdown        BOOLEAN NOT NULL DEFAULT true,
    max_response_tokens INTEGER CHECK (max_response_tokens BETWEEN 50 AND 8000),
    domain_focus        TEXT[],                    -- e.g. ARRAY['finance', 'healthcare']
    avoid_topics        TEXT[],                    -- topics to steer clear of
    custom_instructions TEXT,                      -- free-form system prompt addendum
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    version             INTEGER NOT NULL DEFAULT 1,
    UNIQUE (user_id)
);

-- Implicit preferences: aggregated signals from interaction logs
CREATE TABLE user_implicit_preferences (
    user_id                 UUID PRIMARY KEY REFERENCES users(user_id) ON DELETE CASCADE,
    avg_preferred_length    FLOAT,                 -- rolling average of upvoted response lengths
    topic_affinity          JSONB NOT NULL DEFAULT '{}',  -- topic → engagement score
    format_affinity         JSONB NOT NULL DEFAULT '{}',  -- format → satisfaction signal
    query_complexity_avg    FLOAT,                 -- average complexity of user queries
    preferred_response_time TEXT,                  -- 'quick' or 'thorough' inferred
    last_computed_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    sample_size             INTEGER NOT NULL DEFAULT 0
);

-- Semantic preferences: preference concepts stored as embeddings
CREATE TABLE user_semantic_preferences (
    pref_embedding_id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id             UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    preference_text     TEXT NOT NULL,             -- human-readable description of the preference
    embedding           VECTOR(1536) NOT NULL,     -- OpenAI text-embedding-3-small or similar
    category            TEXT NOT NULL,             -- 'style', 'domain', 'format', 'persona'
    weight              FLOAT NOT NULL DEFAULT 1.0 CHECK (weight BETWEEN 0.0 AND 5.0),
    source              TEXT NOT NULL DEFAULT 'inferred'
                            CHECK (source IN ('explicit', 'inferred', 'admin')),
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at          TIMESTAMPTZ                -- null means permanent
);

CREATE INDEX ON user_semantic_preferences USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
CREATE INDEX ON user_semantic_preferences (user_id, category);

-- Preference audit log: every change to explicit preferences is tracked
CREATE TABLE user_preference_audit (
    audit_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    changed_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    changed_by      TEXT NOT NULL,                 -- 'user', 'system', 'admin'
    field_name      TEXT NOT NULL,
    old_value       TEXT,
    new_value       TEXT,
    session_id      TEXT
);

CREATE INDEX ON user_preference_audit (user_id, changed_at DESC);

-- Row-level security so users can only read their own preferences
ALTER TABLE user_explicit_preferences ENABLE ROW LEVEL SECURITY;
ALTER TABLE user_semantic_preferences ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_own_explicit_prefs ON user_explicit_preferences
    FOR ALL
    USING (user_id = current_setting('app.current_user_id')::UUID);

CREATE POLICY user_own_semantic_prefs ON user_semantic_preferences
    FOR ALL
    USING (user_id = current_setting('app.current_user_id')::UUID);

The separation into four tables is deliberate. Explicit preferences are updated infrequently and queried on every request — they deserve tight typing and a simple unique index. Implicit preferences are computed asynchronously and can be slightly stale; the last_computed_at column lets you decide when to refresh them. Semantic preferences grow over time as the system learns more about a user, so they get their own HNSW index for fast similarity queries.

Capturing and Updating Preferences

You need three update paths: user-initiated changes through an API, system-inferred updates from interaction signals, and the audit trail that connects them.

Start with the FastAPI endpoints for explicit preference management:

# preferences_api.py
from fastapi import FastAPI, Depends, HTTPException, Header
from pydantic import BaseModel, Field
from typing import Optional, List
import asyncpg
import redis.asyncio as aioredis
import json
import uuid
from datetime import datetime

app = FastAPI()

# Connection pool and Redis cache
DB_DSN = "postgresql://appuser:secret@localhost/aiapp"
REDIS_URL = "redis://localhost:6379/0"

# Pydantic models
class ExplicitPreferenceUpdate(BaseModel):
    response_language: Optional[str] = None
    response_length: Optional[str] = Field(None, pattern="^(brief|medium|detailed)$")
    tone: Optional[str] = Field(None, pattern="^(formal|neutral|casual)$")
    code_language: Optional[str] = None
    use_markdown: Optional[bool] = None
    max_response_tokens: Optional[int] = Field(None, ge=50, le=8000)
    domain_focus: Optional[List[str]] = None
    avoid_topics: Optional[List[str]] = None
    custom_instructions: Optional[str] = None

class PreferenceResponse(BaseModel):
    user_id: str
    response_language: str
    response_length: str
    tone: str
    code_language: Optional[str]
    use_markdown: bool
    max_response_tokens: Optional[int]
    domain_focus: Optional[List[str]]
    avoid_topics: Optional[List[str]]
    custom_instructions: Optional[str]
    updated_at: datetime
    version: int

async def get_db():
    conn = await asyncpg.connect(DB_DSN)
    try:
        yield conn
    finally:
        await conn.close()

async def get_redis():
    r = await aioredis.from_url(REDIS_URL, decode_responses=True)
    try:
        yield r
    finally:
        await r.aclose()

async def resolve_user_id(x_user_id: str = Header(...)) -> str:
    """In production this would validate a JWT and extract user_id."""
    return x_user_id

@app.get("/preferences/{user_id}", response_model=PreferenceResponse)
async def get_preferences(
    user_id: str,
    db=Depends(get_db),
    redis=Depends(get_redis),
    current_user: str = Depends(resolve_user_id)
):
    if current_user != user_id:
        raise HTTPException(status_code=403, detail="Access denied")

    # Check cache first
    cache_key = f"prefs:explicit:{user_id}"
    cached = await redis.get(cache_key)
    if cached:
        return PreferenceResponse(**json.loads(cached))

    row = await db.fetchrow(
        """
        SELECT ep.*, u.user_id::text
        FROM user_explicit_preferences ep
        JOIN users u ON u.user_id = ep.user_id
        WHERE ep.user_id = $1
        """,
        uuid.UUID(user_id)
    )
    if not row:
        raise HTTPException(status_code=404, detail="Preferences not found")

    prefs = dict(row)
    prefs["user_id"] = str(prefs["user_id"])
    # Cache for 5 minutes
    await redis.setex(cache_key, 300, json.dumps(prefs, default=str))
    return PreferenceResponse(**prefs)

@app.patch("/preferences/{user_id}")
async def update_preferences(
    user_id: str,
    update: ExplicitPreferenceUpdate,
    db=Depends(get_db),
    redis=Depends(get_redis),
    current_user: str = Depends(resolve_user_id)
):
    if current_user != user_id:
        raise HTTPException(status_code=403, detail="Access denied")

    uid = uuid.UUID(user_id)
    changes = update.model_dump(exclude_none=True)
    if not changes:
        raise HTTPException(status_code=400, detail="No fields to update")

    # Build the audit records and perform the update atomically
    async with db.transaction():
        # Fetch current state for audit
        current = await db.fetchrow(
            "SELECT * FROM user_explicit_preferences WHERE user_id = $1", uid
        )
        if not current:
            raise HTTPException(status_code=404, detail="User preferences not found")

        # Record each changed field in audit log
        audit_records = []
        for field, new_val in changes.items():
            old_val = current[field]
            if old_val != new_val:
                audit_records.append((uid, "user", field, str(old_val), str(new_val)))

        if audit_records:
            await db.executemany(
                """
                INSERT INTO user_preference_audit
                    (user_id, changed_by, field_name, old_value, new_value)
                VALUES ($1, $2, $3, $4, $5)
                """,
                audit_records
            )

        # Dynamic UPDATE — only set fields that were provided
        set_clauses = ", ".join(
            f"{field} = ${i+2}" for i, field in enumerate(changes.keys())
        )
        values = list(changes.values())
        await db.execute(
            f"""
            UPDATE user_explicit_preferences
            SET {set_clauses},
                updated_at = now(),
                version = version + 1
            WHERE user_id = $1
            """,
            uid, *values
        )

    # Invalidate cache
    await redis.delete(f"prefs:explicit:{user_id}")

    # Notify other services via pg_notify
    await db.execute(
        "SELECT pg_notify('preference_updates', $1)",
        json.dumps({"user_id": user_id, "changed_fields": list(changes.keys())})
    )

    return {"status": "updated", "changed_fields": list(changes.keys())}

Now the Celery worker that processes interaction signals and updates implicit preferences asynchronously:

# tasks/preference_inference.py
from celery import Celery
import asyncpg
import asyncio
import json
from anthropic import Anthropic

celery_app = Celery("preference_inference", broker="redis://localhost:6379/1")
anthropic_client = Anthropic()

DB_DSN = "postgresql://appuser:secret@localhost/aiapp"

@celery_app.task(name="infer_preferences_from_interaction")
def infer_preferences_from_interaction(interaction_payload: dict):
    """
    Called after each AI interaction with feedback signals.
    interaction_payload contains: user_id, query, response, rating,
    response_length_chars, topics_detected, format_used
    """
    asyncio.get_event_loop().run_until_complete(
        _async_infer(interaction_payload)
    )

async def _async_infer(payload: dict):
    conn = await asyncpg.connect(DB_DSN)
    try:
        user_id = payload["user_id"]
        rating = payload.get("rating")         # 1-5 or None
        thumbs_up = payload.get("thumbs_up")   # True/False/None
        response_length = payload.get("response_length_chars", 0)
        topics = payload.get("topics_detected", [])

        # Pull recent interaction stats for this user (last 50 interactions)
        stats = await conn.fetchrow(
            """
            SELECT
                COUNT(*) as total,
                AVG(response_length_chars) FILTER (WHERE rating >= 4) as avg_good_length,
                AVG(response_length_chars) FILTER (WHERE thumbs_up = true) as avg_liked_length
            FROM interaction_logs
            WHERE user_id = $1
              AND created_at > now() - interval '30 days'
            """,
            user_id
        )

        # Update topic affinity scores using a simple exponential moving average
        existing = await conn.fetchrow(
            "SELECT topic_affinity, sample_size FROM user_implicit_preferences WHERE user_id = $1",
            user_id
        )

        topic_affinity = json.loads(existing["topic_affinity"]) if existing else {}
        alpha = 0.1  # EMA decay factor

        if thumbs_up is True or (rating and rating >= 4):
            for topic in topics:
                current_score = topic_affinity.get(topic, 0.5)
                topic_affinity[topic] = current_score + alpha * (1.0 - current_score)
        elif thumbs_up is False or (rating and rating <= 2):
            for topic in topics:
                current_score = topic_affinity.get(topic, 0.5)
                topic_affinity[topic] = current_score - alpha * current_score

        # Upsert implicit preferences
        await conn.execute(
            """
            INSERT INTO user_implicit_preferences
                (user_id, avg_preferred_length, topic_affinity, sample_size, last_computed_at)
            VALUES ($1, $2, $3::jsonb, 1, now())
            ON CONFLICT (user_id) DO UPDATE SET
                avg_preferred_length = CASE
                    WHEN $2 IS NOT NULL
                    THEN 0.9 * COALESCE(user_implicit_preferences.avg_preferred_length, $2) + 0.1 * $2
                    ELSE user_implicit_preferences.avg_preferred_length
                END,
                topic_affinity = $3::jsonb,
                sample_size = user_implicit_preferences.sample_size + 1,
                last_computed_at = now()
            """,
            user_id,
            float(response_length) if (thumbs_up or (rating and rating >= 4)) else None,
            json.dumps(topic_affinity)
        )

        # If we have enough data and a strong positive signal, generate a semantic preference
        if thumbs_up is True and stats["total"] >= 10:
            await _maybe_create_semantic_preference(conn, payload)

    finally:
        await conn.close()

async def _maybe_create_semantic_preference(conn, payload: dict):
    """
    Ask Claude to synthesize a semantic preference description from the interaction,
    then store it as a vector.
    """
    from openai import AsyncOpenAI
    oai = AsyncOpenAI()

    prompt = f"""
    A user gave positive feedback on this AI response. 
    Query: {payload.get('query', '')[:500]}
    Response excerpt: {payload.get('response', '')[:500]}
    Topics detected: {', '.join(payload.get('topics_detected', []))}
    Format used: {payload.get('format_used', 'prose')}

    In one sentence, describe what this user seems to prefer about AI responses.
    Be specific. Do not hedge. Return only the sentence.
    """

    message = anthropic_client.messages.create(
        model="claude-opus-4-5",
        max_tokens=100,
        messages=[{"role": "user", "content": prompt}]
    )
    preference_text = message.content[0].text.strip()

    # Embed the preference description
    embedding_response = await oai.embeddings.create(
        model="text-embedding-3-small",
        input=preference_text
    )
    embedding = embedding_response.data[0].embedding

    await conn.execute(
        """
        INSERT INTO user_semantic_preferences
            (user_id, preference_text, embedding, category, source)
        VALUES ($1, $2, $3::vector, 'inferred', 'inferred')
        ON CONFLICT DO NOTHING
        """,
        payload["user_id"],
        preference_text,
        embedding
    )

---

Injecting Preferences at Inference Time

Stored preferences are worthless if they don't reach the model. The challenge is assembling a complete preference context cheaply on every request. You need all four preference layers — explicit settings, implicit signals, semantically relevant preferences, and conversation history — combined into a coherent system prompt addendum.

# preference_context.py
from openai import AsyncOpenAI
from anthropic import Anthropic
import asyncpg
import redis.asyncio as aioredis
import json
import uuid
from typing import Optional

oai_client = AsyncOpenAI()
anthropic_client = Anthropic()

async def build_preference_context(
    user_id: str,
    current_query: str,
    db: asyncpg.Connection,
    redis: aioredis.Redis,
    top_k_semantic: int = 3
) -> dict:
    """
    Returns a dict with:
      - system_addendum: text to append to the system prompt
      - model_params: dict of inference params derived from preferences
      - preference_summary: structured dict for logging
    """

    # Try cache for explicit + implicit (fast path)
    cache_key = f"prefs:combined:{user_id}"
    cached = await redis.get(cache_key)
    if cached:
        base_context = json.loads(cached)
    else:
        rows = await db.fetch(
            """
            SELECT
                ep.response_language,
                ep.response_length,
                ep.tone,
                ep.code_language,
                ep.use_markdown,
                ep.max_response_tokens,
                ep.domain_focus,
                ep.avoid_topics,
                ep.custom_instructions,
                ip.avg_preferred_length,
                ip.topic_affinity,
                ip.preferred_response_time
            FROM user_explicit_preferences ep
            LEFT JOIN user_implicit_preferences ip USING (user_id)
            WHERE ep.user_id = $1
            """,
            uuid.UUID(user_id)
        )

        if not rows:
            return _default_context()

        row = dict(rows[0])
        base_context = {
            "explicit": {
                "language": row["response_language"],
                "length": row["response_length"],
                "tone": row["tone"],
                "code_language": row["code_language"],
                "use_markdown": row["use_markdown"],
                "max_tokens": row["max_response_tokens"],
                "domain_focus": row["domain_focus"] or [],
                "avoid_topics": row["avoid_topics"] or [],
                "custom_instructions": row["custom_instructions"] or ""
            },
            "implicit": {
                "avg_preferred_length": row["avg_preferred_length"],
                "topic_affinity": row["topic_affinity"] or {},
                "preferred_response_time": row["preferred_response_time"]
            }
        }
        # Cache for 2 minutes — explicit prefs don't change often
        await redis.setex(cache_key, 120, json.dumps(base_context, default=str))

    # Semantic preferences require a query embedding — always fresh
    semantic_prefs = await _fetch_relevant_semantic_prefs(
        db, user_id, current_query, top_k_semantic
    )

    return _assemble_context(base_context, semantic_prefs)

async def _fetch_relevant_semantic_prefs(
    db: asyncpg.Connection,
    user_id: str,
    query: str,
    top_k: int
) -> list[str]:
    """Find semantic preferences most relevant to this specific query."""
    embedding_response = await oai_client.embeddings.create(
        model="text-embedding-3-small",
        input=query
    )
    query_embedding = embedding_response.data[0].embedding

    rows = await db.fetch(
        """
        SELECT preference_text, weight,
               1 - (embedding <=> $1::vector) AS similarity
        FROM user_semantic_preferences
        WHERE user_id = $2
          AND (expires_at IS NULL OR expires_at > now())
          AND 1 - (embedding <=> $1::vector) > 0.7
        ORDER BY embedding <=> $1::vector
        LIMIT $3
        """,
        query_embedding,
        uuid.UUID(user_id),
        top_k
    )
    return [row["preference_text"] for row in rows]

def _assemble_context(base_context: dict, semantic_prefs: list[str]) -> dict:
    explicit = base_context["explicit"]
    implicit = base_context["implicit"]

    # Build system prompt addendum
    parts = []

    # Language
    if explicit["language"] and explicit["language"] != "en":
        parts.append(f"Respond in {explicit['language']}.")

    # Tone
    tone_map = {
        "formal": "Use a formal, professional tone.",
        "casual": "Use a conversational, casual tone.",
        "neutral": ""
    }
    if tone_map.get(explicit["tone"]):
        parts.append(tone_map[explicit["tone"]])

    # Length guidance — explicit wins, implicit refines
    length_instructions = {
        "brief": "Keep responses concise and to the point.",
        "medium": "Provide balanced responses — neither too brief nor exhaustive.",
        "detailed": "Provide thorough, comprehensive responses."
    }
    if explicit["length"] in length_instructions:
        parts.append(length_instructions[explicit["length"]])

    if implicit.get("avg_preferred_length"):
        avg = implicit["avg_preferred_length"]
        if avg < 500:
            parts.append("This user historically prefers shorter responses.")
        elif avg > 2000:
            parts.append("This user historically engages well with longer, detailed responses.")

    # Formatting
    if not explicit["use_markdown"]:
        parts.append("Do not use markdown formatting. Respond in plain text.")

    # Code language preference
    if explicit.get("code_language"):
        parts.append(f"When showing code examples, default to {explicit['code_language']} unless the user specifies otherwise.")

    # Domain focus
    if explicit["domain_focus"]:
        domains = ", ".join(explicit["domain_focus"])
        parts.append(f"When examples or analogies are helpful, draw from these domains: {domains}.")

    # Topics to avoid
    if explicit["avoid_topics"]:
        avoided = ", ".join(explicit["avoid_topics"])
        parts.append(f"Avoid discussing the following topics: {avoided}.")

    # Semantic preferences (most specific — listed last so they carry weight)
    if semantic_prefs:
        parts.append("Additional style notes inferred from this user's history:")
        for pref in semantic_prefs:
            parts.append(f"  - {pref}")

    # Custom instructions go last and verbatim
    if explicit["custom_instructions"]:
        parts.append(explicit["custom_instructions"])

    system_addendum = "\n".join(p for p in parts if p)

    # Model params derived from preferences
    model_params = {}
    if explicit.get("max_tokens"):
        model_params["max_tokens"] = explicit["max_tokens"]
    elif explicit["length"] == "brief":
        model_params["max_tokens"] = 512
    elif explicit["length"] == "detailed":
        model_params["max_tokens"] = 4096
    else:
        model_params["max_tokens"] = 1500

    return {
        "system_addendum": system_addendum,
        "model_params": model_params,
        "preference_summary": {
            "explicit": explicit,
            "implicit": implicit,
            "semantic_pref_count": len(semantic_prefs)
        }
    }

def _default_context() -> dict:
    return {
        "system_addendum": "",
        "model_params": {"max_tokens": 1500},
        "preference_summary": {}
    }

Now wire this into an actual inference call so you can see the full request lifecycle:

# inference_endpoint.py
from fastapi import FastAPI, Depends, Header, HTTPException
from pydantic import BaseModel
from anthropic import Anthropic
import asyncpg
import redis.asyncio as aioredis
from preference_context import build_preference_context

app = FastAPI()
anthropic_client = Anthropic()

BASE_SYSTEM_PROMPT = """You are a helpful AI assistant. You answer questions accurately 
and adapt your communication style to suit the user."""

class ChatRequest(BaseModel):
    query: str
    conversation_history: list[dict] = []   # list of {role, content} dicts

@app.post("/chat")
async def chat(
    request: ChatRequest,
    db=Depends(get_db),
    redis=Depends(get_redis),
    current_user: str = Depends(resolve_user_id)
):
    # Build personalized context
    pref_context = await build_preference_context(
        user_id=current_user,
        current_query=request.query,
        db=db,
        redis=redis
    )

    # Compose full system prompt
    system_prompt = BASE_SYSTEM_PROMPT
    if pref_context["system_addendum"]:
        system_prompt += "\n\n--- User Preferences ---\n" + pref_context["system_addendum"]

    # Assemble messages
    messages = request.conversation_history + [
        {"role": "user", "content": request.query}
    ]

    # Call Claude with personalized params
    model_params = pref_context["model_params"]
    response = anthropic_client.messages.create(
        model="claude-opus-4-5",
        max_tokens=model_params.get("max_tokens", 1500),
        system=system_prompt,
        messages=messages
    )

    response_text = response.content[0].text

    # Fire-and-forget: enqueue interaction for preference inference
    from tasks.preference_inference import infer_preferences_from_interaction
    infer_preferences_from_interaction.delay({
        "user_id": current_user,
        "query": request.query,
        "response": response_text,
        "response_length_chars": len(response_text),
        "format_used": "markdown" if pref_context["preference_summary"].get(
            "explicit", {}).get("use_markdown") else "plain"
        # rating and thumbs_up come from a separate feedback endpoint
    })

    return {
        "response": response_text,
        "personalization_applied": bool(pref_context["system_addendum"]),
        "pref_summary": pref_context["preference_summary"]
    }

The SQL Server Equivalent

For teams running on SQL Server, the schema maps cleanly with a few syntax adjustments. The main difference is that SQL Server uses NVARCHAR for Unicode text, BIT for booleans, and does not have a native array type — you use comma-separated strings or a separate child table instead. Vector storage requires pgvector's equivalent, which on SQL Server means either Azure SQL's native vector preview feature or a serialized VARBINARY with application-side distance computation.

-- SQL Server equivalent schema
CREATE TABLE users (
    user_id         UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    external_id     NVARCHAR(255) NOT NULL UNIQUE,
    email           NVARCHAR(320),
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    last_active_at  DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    is_active       BIT NOT NULL DEFAULT 1
);

CREATE TABLE user_explicit_preferences (
    preference_id       UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id             UNIQUEIDENTIFIER NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    response_language   NVARCHAR(10) NOT NULL DEFAULT 'en',
    response_length     NVARCHAR(20) NOT NULL DEFAULT 'medium'
                            CHECK (response_length IN ('brief', 'medium', 'detailed')),
    tone                NVARCHAR(20) NOT NULL DEFAULT 'neutral'
                            CHECK (tone IN ('formal', 'neutral', 'casual')),
    code_language       NVARCHAR(50),
    use_markdown        BIT NOT NULL DEFAULT 1,
    max_response_tokens INT CHECK (max_response_tokens BETWEEN 50 AND 8000),
    -- Arrays become comma-separated strings or child tables in SQL Server
    domain_focus        NVARCHAR(1000),            -- comma-separated
    avoid_topics        NVARCHAR(1000),            -- comma-separated
    custom_instructions NVARCHAR(MAX),
    updated_at          DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    version             INT NOT NULL DEFAULT 1,
    CONSTRAINT uq_user_explicit_prefs UNIQUE (user_id)
);

CREATE TABLE user_implicit_preferences (
    user_id                 UNIQUEIDENTIFIER PRIMARY KEY REFERENCES users(user_id) ON DELETE CASCADE,
    avg_preferred_length    FLOAT,

    format_affinity         NVARCHAR(MAX),

);

-- For semantic preferences in Azure SQL with vector preview:
CREATE TABLE user_semantic_preferences (
    pref_embedding_id   UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id             UNIQUEIDENTIFIER NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,

    embedding           VECTOR(1536),

    source              NVARCHAR(20) NOT NULL DEFAULT 'inferred'

);

    audit_id        UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),

    changed_by      NVARCHAR(20) NOT NULL,
    field_name      NVARCHAR(100) NOT NULL,

    session_id      NVARCHAR(255)
);

    ON user_preference_audit (user_id, changed_at DESC);

The similarity search for semantic preferences in Azure SQL uses VECTOR_DISTANCE:

-- Azure SQL semantic preference retrieval
DECLARE @query_embedding VECTOR(1536) = CAST(@embedding_json AS VECTOR(1536));

SELECT TOP 3
    preference_text,
    weight,
    VECTOR_DISTANCE('cosine', embedding, @query_embedding) AS distance
FROM user_semantic_preferences
WHERE user_id = @user_id
  AND (expires_at IS NULL OR expires_at > SYSDATETIMEOFFSET())
  AND VECTOR_DISTANCE('cosine', embedding, @query_embedding) < 0.3
ORDER BY VECTOR_DISTANCE('cosine', embedding, @query_embedding);

On non-Azure SQL Server deployments without the vector preview, store embeddings as VARBINARY(MAX) and perform the cosine similarity computation in application code after fetching candidates filtered by category or recency — not ideal at scale, but workable for smaller user bases.

Preference Versioning and Drift Detection

User preferences are not static. People's needs evolve, and a preference inferred six months ago might actually conflict with current behavior. You need two things: a way to know when inferred preferences have gone stale, and a way to detect when explicit preferences are no longer reflected in actual interaction patterns — a sign the user set them and forgot.

-- PostgreSQL: find users whose inferred preferences conflict with explicit settings
WITH recent_satisfaction AS (
    SELECT
        il.user_id,
        AVG(il.rating) FILTER (WHERE ep.response_length = 'brief'
                                AND il.response_length_chars > 1500) AS long_response_satisfaction_when_brief_set,
        AVG(il.rating) FILTER (WHERE ep.response_length = 'detailed'
                                AND il.response_length_chars < 400) AS short_response_satisfaction_when_detailed_set,
        COUNT(*) AS interaction_count
    FROM interaction_logs il
    JOIN user_explicit_preferences ep ON ep.user_id = il.user_id
    WHERE il.created_at > now() - interval '14 days'
    GROUP BY il.user_id
)
SELECT
    user_id,
    long_response_satisfaction_when_brief_set,
    short_response_satisfaction_when_detailed_set,
    interaction_count,
    CASE
        WHEN long_response_satisfaction_when_brief_set > 3.5 THEN 'user_set_brief_but_prefers_long'
        WHEN short_response_satisfaction_when_detailed_set > 3.5 THEN 'user_set_detailed_but_prefers_short'
        ELSE 'consistent'
    END AS preference_drift_signal
FROM recent_satisfaction
WHERE interaction_count >= 5
  AND (
    long_response_satisfaction_when_brief_set > 3.5
    OR short_response_satisfaction_when_detailed_set > 3.5
  );

When drift is detected, the right response is not to silently override the explicit preference — the user set it deliberately. Instead, surface it as a nudge: "We noticed you've been getting great results with more detailed responses lately. Would you like to update your preference?" This keeps the user in control while the system stays honest about what it observes.

For semantic preferences, staleness is handled by the expires_at column. Preferences generated from interactions older than a configurable window get a shorter TTL:

-- Expire semantic preferences derived from old interactions
UPDATE user_semantic_preferences
SET expires_at = now() + interval '7 days'
WHERE source = 'inferred'
  AND created_at < now() - interval '60 days'
  AND expires_at IS NULL;

Run this as a nightly maintenance job. The HNSW index automatically skips expired rows once you add the expires_at filter to your query predicate.

Preference Inheritance and Defaults

Not every user will configure preferences before their first session. A new user with no preference record should still get a reasonable experience. You have two options: application-level defaults (handled in _default_context() above) and database-level defaults with a synthetic "global default" row.

The pattern that works best at scale is a tiered fallback:

-- PostgreSQL: preference resolution with org-level and global fallback
CREATE TABLE org_default_preferences (
    org_id              UUID NOT NULL,
    response_language   TEXT NOT NULL DEFAULT 'en',
    response_length     TEXT NOT NULL DEFAULT 'medium',
    tone                TEXT NOT NULL DEFAULT 'neutral',
    use_markdown        BOOLEAN NOT NULL DEFAULT true,
    custom_instructions TEXT,
    PRIMARY KEY (org_id)
);

-- View that resolves preferences with fallback chain
CREATE VIEW resolved_user_preferences AS
SELECT
    u.user_id,
    u.external_id,
    COALESCE(ep.response_language, od.response_language, 'en') AS response_language,
    COALESCE(ep.response_length, od.response_length, 'medium') AS response_length,
    COALESCE(ep.tone, od.tone, 'neutral') AS tone,
    COALESCE(ep.use_markdown, od.use_markdown, true) AS use_markdown,
    COALESCE(ep.custom_instructions, od.custom_instructions) AS custom_instructions,
    COALESCE(ep.max_response_tokens, 1500) AS max_response_tokens,
    ep.code_language,
    ep.domain_focus,
    ep.avoid_topics
FROM users u
LEFT JOIN user_explicit_preferences ep ON ep.user_id = u.user_id
LEFT JOIN org_default_preferences od ON od.org_id = u.org_id;

This view means your application code never has to handle null preferences explicitly — the fallback chain is expressed once in the database and reused everywhere.

Latency Profile and Optimization

Every preference layer adds latency, but the layers are not equal contributors. An indexed lookup of explicit and implicit preferences is a single-digit-millisecond query, and a Redis cache hit for that same data is faster still — both are effectively free next to a network round trip. The HNSW similarity search over semantic preferences is also fast once the query is embedded. The step that dominates the whole preference-injection path is the embedding API call itself: a network round trip to an external embedding provider, which is one to two orders of magnitude slower than everything else in this pipeline combined. Measure this in your own environment rather than assuming a fixed number — provider latency, region, and payload size all move it — but plan your optimization effort around the embedding call, because that is where nearly all of the addressable latency lives.

If that latency is unacceptable for your use case, you have three options:

Option 1: Cache the query embedding. If the user sends the same or very similar query repeatedly (common in iterative workflows), a short-lived Redis cache keyed on a hash of the query text avoids repeated embedding API calls.

Option 2: Pre-compute top-N semantic preferences on session start. When the user opens a session, pre-fetch and cache their top-10 semantic preferences without filtering by query relevance. At inference time, do a local cosine similarity computation against those 10 vectors in Python — nanoseconds versus milliseconds. This trades some relevance precision for dramatically lower per-request latency.

Option 3: Skip semantic preferences for low-stakes queries. If your query classifier identifies a query as factual or closed-ended (e.g., "What is the capital of France?"), skip semantic preference retrieval entirely. Personalization matters most for open-ended, stylistic, or advice-seeking queries.

The pre-computation approach with application-side cosine similarity looks like this:

# Session initialization: pre-load semantic preferences into session cache
async def preload_session_preferences(user_id: str, session_id: str, db, redis):
    rows = await db.fetch(
        """
        SELECT preference_text, embedding::text, weight
        FROM user_semantic_preferences
        WHERE user_id = $1
          AND (expires_at IS NULL OR expires_at > now())
        ORDER BY weight DESC, created_at DESC
        LIMIT 10
        """,
        uuid.UUID(user_id)
    )

    session_prefs = [
        {
            "text": row["preference_text"],
            "embedding": json.loads(row["embedding"]),  # parse vector back to list
            "weight": row["weight"]
        }
        for row in rows
    ]

    session_key = f"session:prefs:{session_id}"
    await redis.setex(session_key, 3600, json.dumps(session_prefs))  # 1-hour TTL

def cosine_similarity(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = sum(x ** 2 for x in a) ** 0.5
    norm_b = sum(x ** 2 for x in b) ** 0.5
    return dot / (norm_a * norm_b + 1e-9)

async def get_relevant_prefs_from_session_cache(
    session_id: str,
    query_embedding: list[float],
    redis: aioredis.Redis,
    threshold: float = 0.7
) -> list[str]:
    session_key = f"session:prefs:{session_id}"
    raw = await redis.get(session_key)
    if not raw:
        return []

    session_prefs = json.loads(raw)
    scored = [
        (cosine_similarity(query_embedding, p["embedding"]), p["text"])
        for p in session_prefs
    ]
    scored.sort(reverse=True)
    return [text for score, text in scored if score >= threshold][:3]

This hybrid approach — database HNSW for full-corpus searches, application-side computation for session-scoped retrieval — gives you the best of both worlds without sacrificing correctness on long-lived sessions.

Key Takeaways

  • → **Four-layer preference architecture** — explicit settings, implicit behavioral signals, semantic embeddings, and session context — covers the full spectrum of what it means to personalize an AI interaction. Conflating them into a single blob loses precision; separating them into typed tables keeps each layer maintainable and queryable.
  • → **Redis caching for explicit and implicit preferences** brings per-request preference retrieval overhead down to sub-millisecond range. Cache invalidation on write is straightforward because explicit preferences change rarely and are always updated through a known API surface.
  • → **Semantic preferences stored as pgvector embeddings** allow the system to retrieve the most contextually relevant style or domain preferences for a given query rather than injecting all of them unconditionally. The HNSW index keeps retrieval fast even as a user's preference history grows.
  • → **Preference drift detection** — comparing explicit settings against actual satisfaction signals from interaction logs — ensures the system can surface useful nudges to users whose declared preferences no longer reflect what they actually respond well to, without silently overriding their choices.
  • → **Latency optimization requires a tiered strategy**: cache explicit and implicit preferences aggressively, pre-load session-scoped semantic preferences at session start for application-side cosine similarity, and skip semantic retrieval entirely for queries where stylistic personalization adds little value. The semantic embedding API call is the dominant cost and must be managed deliberately.
