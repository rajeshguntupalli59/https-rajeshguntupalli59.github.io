Chapter 3 of 40 The Cloud Database Engineer

Chapter 3: Cloud Database Landscape: AWS, Azure, GCP Side-by-Side

Every cloud provider sells you the same promise: managed databases that eliminate the undifferentiated heavy lifting of patching, backups, and hardware provisioning. The reality is that AWS, Azure, and GCP have taken fundamentally different architectural philosophies to reach that promise, and those differences shape every decision you make — from instance sizing to failover behavior to how you debug a slow query at 2 a.m. This chapter builds the mental map you need before writing a single line of Terraform or clicking a single console button. You will see how each platform organizes its database services, where their managed offerings genuinely replace on-prem work, and where the seams show.

---

3.1 The Service Taxonomy: What Each Cloud Actually Offers

Before comparing specifics, you need to understand the organizational logic of each platform. They do not map cleanly onto each other, and conflating them causes real architectural mistakes.

AWS Database Services

AWS built its database portfolio as a collection of purpose-built, largely independent services. For relational workloads, the primary offerings are:

  • → **Amazon RDS**: The foundational managed relational service. Supports MySQL, PostgreSQL, MariaDB, Oracle, and SQL Server. You pick an engine, pick an instance class, and AWS handles patching, backups, and failover. RDS is the closest thing to "take your on-prem database and move it to a managed host."
  • → **Amazon Aurora**: AWS's rewritten storage layer, available in MySQL-compatible and PostgreSQL-compatible variants. Aurora separates compute from storage in a way standard RDS does not. The storage layer automatically grows in 10 GB increments up to 128 TB, replicates across three Availability Zones at the storage level, and allows up to 15 read replicas without the replication lag penalty you see on standard RDS. Aurora is not just "faster RDS" — it is a different internal architecture.
  • → **Aurora Serverless v2**: Compute that scales in Aurora Capacity Units (ACUs), with a floor as low as 0.5 ACU and a ceiling that AWS has raised more than once (check current documentation for the exact maximum), with sub-second scaling response. One ACU is approximately 2 GB of memory with proportional CPU. Useful for variable workloads, but the cold-start behavior when scaling from near-zero can surprise you in production.
  • → **RDS Proxy**: A fully managed connection pooler that sits in front of RDS or Aurora. It maintains a warm pool of connections to the database and presents a single endpoint to your application. Relevant when you have Lambda functions or containers generating thousands of short-lived connections.

    • Azure Database Services

    Azure organizes its relational offerings around the concept of deployment models — how much of the infrastructure stack you control:

  • → **Azure SQL Database**: A fully managed PaaS service built on SQL Server. No OS access, no SQL Server Agent (limited version available), but a high published availability SLA (the exact figure varies by tier and zone redundancy — check current Microsoft documentation) and automatic tuning available. The purchasing model adds complexity: you choose between DTU-based pricing (a bundled compute/IO unit AWS has no equivalent for) and vCore-based pricing (which maps more cleanly to familiar instance sizing).
  • → **Azure SQL Managed Instance**: The "nearly full SQL Server" option. You get SQL Agent, cross-database queries, linked servers, and CLR — features that disappear in Azure SQL Database. The tradeoff is a longer provisioning time (up to four hours for some operations) and a higher cost floor.
  • → **Azure Database for PostgreSQL / MySQL**: Managed open-source database services, analogous to RDS PostgreSQL/MySQL. The Flexible Server deployment model is the current recommended path; the older Single Server model is being retired.
  • → **Azure SQL Hyperscale**: A distributed storage architecture for Azure SQL Database that allows databases up to 100 TB. The page server architecture separates compute from storage and enables near-instant database restores regardless of database size — a restore of a 10 TB database takes roughly the same time as restoring a 10 GB database.
  • → **Elastic Pools**: A resource-sharing model where multiple databases share a pool of DTUs or vCores. This is Azure's answer to database consolidation — comparable to running multiple schemas on one PostgreSQL instance, but with more granular resource governance.

    • Google Cloud Database Services

    GCP's philosophy leans toward horizontal scale and global distribution more heavily than the other two:

  • → **Cloud SQL**: The managed MySQL, PostgreSQL, and SQL Server service. Functionally similar to RDS — it handles patching, backups, and HA failover. Storage scales automatically up to 64 TB. Cloud SQL HA uses a standby instance in a different zone with synchronous replication, promoted automatically on failure.
  • → **AlloyDB for PostgreSQL**: Google's reengineered PostgreSQL-compatible service, analogous to how Aurora relates to RDS. AlloyDB separates log processing from storage, uses a distributed storage layer with columnar caching, and claims 4x faster transactional throughput than standard Cloud SQL PostgreSQL. AlloyDB also integrates the Vertex AI embedding generation directly within the database, which becomes relevant in Book 4 of this series.
  • → **Cloud Spanner**: A globally distributed, horizontally scalable relational database with external consistency (a stronger guarantee than serializable isolation). Spanner is in a category of its own — it uses TrueTime to order transactions across geographic regions. The SQL dialect is ANSI-compatible but not identical to PostgreSQL or SQL Server. Spanner is not a drop-in replacement for anything; it requires application-level rethinking.
  • → **BigQuery**: Analytical, serverless, columnar. Not covered in this book except where it intersects with operational database exports.
  • → **Firestore / Bigtable**: NoSQL services outside the scope of this book.

    • The practical implication of this taxonomy: when a product manager says "we're going multi-cloud," you are not mapping AWS RDS to Azure SQL Database to Cloud SQL as equivalent services. Each has architectural behaviors that will affect your SLA, your cost model, and your operational runbooks differently.

    3.2 Compute and Storage Architecture: What Changes Under the Hood

    As an on-prem DBA, you have a mental model of "database server": CPU, RAM, disks, and a file system you can inspect with ls. That model breaks in specific ways on each cloud platform. Understanding what breaks — and what remains — determines how you approach performance tuning and capacity planning.

    AWS RDS: EBS-Based Single Instance

    Standard RDS runs a single database process on an EC2-backed instance. Storage is Amazon EBS (Elastic Block Store). The key operational parameters:

  • → **gp3 storage**: General purpose SSD, baseline 3,000 IOPS up to 16,000 IOPS, throughput up to 1,000 MiB/s. You configure IOPS and throughput independently. For most OLTP workloads under 16,000 IOPS, gp3 is the right choice and costs less than provisioned IOPS.
  • → **io1/io2 storage**: Provisioned IOPS SSD, up to 256,000 IOPS for io2 Block Express. You pay per IOPS-month provisioned, so overprovisioning is expensive. Rule of thumb: if your peak IOPS demand exceeds 16,000 sustainably, move to io2.
  • → **Storage autoscaling**: You can enable autoscaling with a maximum threshold. RDS will expand storage automatically but will never shrink it. A common gotcha: a runaway job fills the disk, autoscaling kicks in, and you end up paying for 10 TB of storage you no longer need because you cannot scale down.
  • → **Instance classes**: RDS uses the `db.` prefix on EC2 instance families. The `db.r7g` family (Graviton3, memory-optimized) is the current sweet spot for most PostgreSQL workloads — a `db.r7g.4xlarge` gives you 16 vCPUs and 128 GB RAM. SQL Server workloads requiring Windows licensing have fewer Graviton options and typically run on `db.m7i` or `db.r7i`.

    • Aurora: Shared Distributed Storage

    Aurora's storage layer is the architectural departure that matters most. The Aurora storage is a distributed volume that spans six storage nodes across three AZs. Your Aurora cluster's "writer" instance does not write to local disk — it writes log records to the distributed storage layer, which handles redo application independently of the compute layer. This means:

  • → Failover to a reader within the same region promotes without storage copy, typically completing in under 30 seconds. Aurora Global Database's managed planned failover across regions is slower — AWS documents it as typically under a minute — since it involves cross-region coordination that a same-region reader promotion does not.
  • → Read replicas share the same storage volume. There is no binary log replication lag in the traditional sense — replicas apply the cache invalidation messages from the storage layer. Replica lag on a lightly loaded Aurora cluster is typically 10–20 milliseconds, not the 100ms–several seconds you may have seen on RDS read replicas under write pressure.
  • → You cannot SSH to the storage nodes. You cannot run `iostat` on the underlying storage. You lose the low-level observability you had on-prem and gain instead Aurora-specific CloudWatch metrics like `AuroraReplicaLag` and `VolumeWriteIOPs`.

    • Azure SQL: DTUs vs. vCores

    The DTU (Database Transaction Unit) purchasing model is Azure's attempt to simplify capacity selection by bundling CPU, memory, and IO into a single unit. The problem is that DTUs are opaque — a DTU is defined relative to performance on a specific Microsoft benchmark, not to hardware specs. You cannot predict whether a workload that runs on 8 CPU cores and 64 GB RAM on-prem will fit in 500 DTUs without testing.

    The vCore model is more familiar. An 8-vCore General Purpose Azure SQL Database gives you 8 vCores and 40.8 GB memory. The Business Critical tier adds local SSD storage and a built-in readable secondary replica included in the cost. For new deployments, prefer vCore unless the workload is small and predictable enough that DTU bundles save money.

    Azure SQL Hyperscale's page server architecture is the most aggressive storage separation on the market. Page servers store the database pages, log service writes the transaction log, and the compute replica only caches the pages it needs. A 50 TB Hyperscale database restores in minutes because restore means redirecting pointers to a new snapshot, not copying bytes.

    GCP Cloud SQL: Zonal with Optional HA

    Cloud SQL instances run on GCP Compute Engine VMs with Persistent Disk (PD) storage. A standard Cloud SQL PostgreSQL instance is single-zone; if that zone fails, your database is unavailable until it recovers. Enabling High Availability provisions a standby instance in a different zone with synchronous replication through a regional Persistent Disk. Failover is automatic but takes 60–120 seconds in practice — significantly slower than Aurora's sub-30-second failover.

    Storage on Cloud SQL scales automatically up to 64 TB for PostgreSQL, but like RDS, it does not scale down. The --storage-auto-increase-limit flag lets you cap automatic growth.

    AlloyDB uses a disaggregated storage design similar to Aurora but adds a columnar storage layer that caches frequently accessed data in a columnar format on the compute node. The practical effect: analytical queries that would require a separate OLAP system in traditional deployments can run acceptably on AlloyDB without a full scan of row-based storage.

    3.3 Networking: VPCs, Private Link, and the End of pg_hba.conf

    On-prem, you controlled database access through a combination of network topology (firewall rules, VLANs) and database-level access control (pg_hba.conf for PostgreSQL, logins/users for SQL Server). Cloud managed services extend and complicate this with additional abstraction layers. Getting networking wrong in cloud databases does not just cause connection failures — it creates security vulnerabilities and unexpected egress costs.

    AWS VPC and RDS

    Every RDS and Aurora instance lives inside a VPC subnet. You define which subnets the instance can use via a DB Subnet Group, which must span at least two AZs. Security Groups control inbound access — they are stateful firewall rules at the instance level.

    The critical operational point: RDS instances in private subnets cannot be reached from the internet by default. To connect from your workstation, you need either a bastion host, AWS Systems Manager Session Manager tunneling, or a VPN/Direct Connect. This is the right posture for production, but it surprises engineers used to opening a pgAdmin connection directly to a server.

    # Create a DB Subnet Group spanning three AZs
aws rds create-db-subnet-group \
  --db-subnet-group-name prod-postgres-subnets \
  --db-subnet-group-description "Production PostgreSQL subnets across 3 AZs" \
  --subnet-ids subnet-0a1b2c3d4e5f00001 subnet-0a1b2c3d4e5f00002 subnet-0a1b2c3d4e5f00003 \
  --region us-east-1

# Create Security Group allowing PostgreSQL access only from application subnet
aws ec2 create-security-group \
  --group-name rds-postgres-sg \
  --description "RDS PostgreSQL access from app tier" \
  --vpc-id vpc-0a1b2c3d4e5f00001

aws ec2 authorize-security-group-ingress \
  --group-id sg-0a1b2c3d4e5f12345 \
  --protocol tcp \
  --port 5432 \
  --source-group sg-0a1b2c3d4e5f67890  # app tier security group

    RDS Proxy and Connection Management

    If you have ever tuned max_connections in PostgreSQL and dealt with the "too many connections" error under load, RDS Proxy addresses exactly this problem for managed services. Lambda functions are the primary driver — each Lambda invocation can open its own database connection, and a spike to 1,000 concurrent invocations means 1,000 simultaneous connections, which will overwhelm a db.r6g.large long before you'd want to rely on raw connection count (check the instance's default max_connections for the actual ceiling, and note that performance degrades well before that ceiling is hit).

    RDS Proxy maintains a persistent connection pool to the database and multiplexes application connections against it. The proxy endpoint replaces your database endpoint in the application connection string. The proxy also integrates with AWS Secrets Manager and IAM for authentication, so your application never handles a plaintext database password.

    # Create RDS Proxy for Aurora PostgreSQL cluster
aws rds create-db-proxy \
  --db-proxy-name prod-aurora-proxy \
  --engine-family POSTGRESQL \
  --auth '[{
    "AuthScheme": "SECRETS",
    "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:prod/aurora/pgcreds",
    "IAMAuth": "REQUIRED"
  }]' \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0a1b2c3d4e5f00001 subnet-0a1b2c3d4e5f00002 \
  --vpc-security-group-ids sg-0a1b2c3d4e5f12345 \
  --require-tls

    Azure Private Link and Service Endpoints

    Azure SQL Database has a public endpoint by default (in older deployments). For production, you want a Private Endpoint — an Azure Private Link resource that assigns a private IP from your VNet to the Azure SQL logical server. Once a private endpoint exists, you can deny all public access via the firewall.

    The Azure SQL firewall is conceptually similar to pg_hba.conf in that it operates at the server level before the database authentication step. But unlike pg_hba.conf where you write IP ranges directly into a config file, the Azure SQL firewall rules are API-managed objects attached to the logical server.

    # Create Azure SQL Private Endpoint
az network private-endpoint create \
  --name prod-sql-private-endpoint \
  --resource-group prod-rg \
  --vnet-name prod-vnet \
  --subnet prod-db-subnet \
  --private-connection-resource-id \
    "/subscriptions/12345678-abcd-1234-abcd-123456789012/resourceGroups/prod-rg/providers/Microsoft.Sql/servers/prod-sql-server" \
  --group-id sqlServer \
  --connection-name prod-sql-pe-connection

# Disable public network access after private endpoint is confirmed active
az sql server update \
  --name prod-sql-server \
  --resource-group prod-rg \
  --enable-public-network false

    GCP VPC and Cloud SQL Authorized Networks

    Cloud SQL can use two connectivity models: Authorized Networks (an IP allowlist — the simplest but least secure approach, similar to pg_hba.conf host-based entries) and Private Service Access (a VPC peering-based model that gives Cloud SQL a private IP in your VPC).

    The recommended production approach uses Private Service Access combined with the Cloud SQL Auth Proxy, a sidecar process that handles IAM authentication and TLS tunneling without requiring direct IP allowlisting. The proxy runs alongside your application and presents a local socket that your application connects to as if it were a local PostgreSQL instance.

    # Assign private IP to Cloud SQL instance
gcloud sql instances patch prod-postgres \
  --network=projects/my-project/global/networks/prod-vpc \
  --no-assign-ip \
  --project my-project

# Run Cloud SQL Auth Proxy (typically as a sidecar in Kubernetes)
# Download: https://cloud.google.com/sql/docs/postgres/sql-proxy
./cloud-sql-proxy \
  --address 127.0.0.1 \
  --port 5432 \
  my-project:us-central1:prod-postgres &

    The Cloud SQL Auth Proxy is analogous to AWS RDS Proxy in that it handles authentication abstraction, but it does not provide connection pooling. For pooling with Cloud SQL, you run PgBouncer or pgpool-II separately — either as a sidecar or as a dedicated VM.

    3.4 Authentication and Access Control: IAM Is the New pg_hba.conf

    The phrase "IAM is the new pg_hba.conf" captures the conceptual shift without being entirely accurate. IAM controls which entities can perform management-plane operations (create instances, modify parameter groups, take snapshots). Database-level authentication — which users can log in to the database itself — remains a separate concern on every cloud platform, but IAM is increasingly integrated into that layer too.

    AWS IAM Database Authentication

    RDS and Aurora support IAM database authentication for MySQL and PostgreSQL. Instead of password-based login, an IAM entity (user or role) generates a short-lived authentication token using the AWS SDK. The token is valid for 15 minutes. On the database side, the user is created with the rds_iam authentication plugin enabled. The workflow:

    1. Application assumes an IAM role.

    2. Application calls generate_db_auth_token to get a 15-minute token.

    3. Application connects using the token as the password.

    4. RDS validates the token against IAM.

    import boto3
import psycopg2

def get_iam_auth_token(hostname, port, username, region):
    client = boto3.client('rds', region_name=region)
    token = client.generate_db_auth_token(
        DBHostname=hostname,
        Port=port,
        DBUsername=username,
        Region=region
    )
    return token

def connect_rds_iam():
    hostname = "prod-aurora.cluster-xyz.us-east-1.rds.amazonaws.com"
    port = 5432
    username = "app_service_user"
    region = "us-east-1"
    database = "appdb"
    
    token = get_iam_auth_token(hostname, port, username, region)
    
    # SSL is required for IAM auth
    conn = psycopg2.connect(
        host=hostname,
        port=port,
        database=database,
        user=username,
        password=token,
        sslmode="require"
    )
    return conn

    The database user still needs to exist as a PostgreSQL role — IAM auth does not bypass PostgreSQL's internal user system. The integration point is the authentication method: the password field carries the IAM token, and RDS validates it before PostgreSQL processes the login.

    Azure SQL: Azure Active Directory Integration

    Azure SQL supports both SQL authentication (username/password stored in the database) and Azure Active Directory authentication. AAD authentication is the recommended path for production because it enables conditional access policies, MFA for human users, and managed identity authentication for applications.

    An Azure Managed Identity — a service principal automatically managed by Azure for a VM, App Service, or container — can authenticate to Azure SQL without any credentials in the application configuration. This is functionally equivalent to the IAM role-based RDS authentication above:

    # Enable AAD admin for Azure SQL Server
az sql server ad-admin create \
  --server prod-sql-server \
  --resource-group prod-rg \
  --display-name "DBA-Team-AAD-Group" \
  --object-id "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"

# Create contained database user for a Managed Identity
# Run this SQL as the AAD admin inside the target database
    -- Create database user for App Service Managed Identity
-- Run as AAD admin inside the target database
CREATE USER [prod-app-service] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [prod-app-service];
ALTER ROLE db_datawriter ADD MEMBER [prod-app-service];

-- Verify AAD users
SELECT name, type_desc, authentication_type_desc
FROM sys.database_principals
WHERE type IN ('E', 'X');  -- E = external user, X = external group

    GCP Cloud IAM and Cloud SQL

    Cloud SQL integrates with GCP IAM through a feature called Cloud SQL IAM database authentication for PostgreSQL. A Cloud IAM user or service account is mapped to a PostgreSQL role using a login trigger. The user authenticates with an OAuth2 access token rather than a password. The role name in the database matches the email address of the IAM identity (truncated to 63 characters, which can cause collisions you need to test for in advance).

    The conceptual alignment: in pg_hba.conf, you would write an ident or peer line to map OS users to database roles. Cloud SQL IAM auth does the same thing, replacing OS identity with GCP IAM identity.

    Always Encrypted (Azure SQL)

    Azure SQL offers Always Encrypted — a client-side encryption mechanism where encryption and decryption happen in the application layer, never in the database engine. The database server stores ciphertext and cannot read the plaintext values, even with administrative access. This is a fundamentally different threat model than TDE (Transparent Data Encryption), which only encrypts at-rest storage and is transparent to anyone with database access.

    Always Encrypted requires application-level changes: the connection string must include the column encryption setting, and the client driver handles the cryptographic operations using keys stored in Azure Key Vault, Windows Certificate Store, or other supported keystores. The operational tradeoff: you cannot filter on encrypted columns with inequality operators (a search for salaries between $50,000 and $100,000 on an encrypted column requires decrypting all rows client-side). Always Encrypted with Randomized Encryption supports no server-side filtering at all; Deterministic Encryption supports equality comparisons only.

    3.5 High Availability and Disaster Recovery: Comparing the Failover Mechanics

    HA is where managed services diverge most sharply from on-prem setups, and where the "managed" abstraction creates the most operational surprises. You need to understand what each platform does automatically, what you still configure, and what the failure scenarios look like.

    AWS RDS Multi-AZ

    Standard RDS Multi-AZ maintains a synchronous standby replica in a second AZ. The standby is not readable — it is purely a failover target. Failover happens automatically when RDS detects instance failure, AZ outage, or network partitioning. The DNS endpoint for the instance is updated to point to the promoted standby. Expected failover time: 60–120 seconds. Applications that cache DNS or use long connection timeouts may not recover within this window without explicit reconnect logic.

    RDS Multi-AZ DB Cluster (a newer feature, not to be confused with Aurora) provides two readable standby instances in separate AZs with a stated failover time under 35 seconds. It uses semi-synchronous replication — different from Aurora's storage-level replication. Choose this over standard Multi-AZ when you need the read capacity of the standbys and can tolerate the additional cost.

    Aurora Global Database

    Aurora Global Database extends the Aurora cluster across AWS Regions for disaster recovery and global read distribution. The primary Region hosts the writer and up to 15 readers. Secondary Regions each receive the storage log stream from the primary with typical replication lag under 1 second (the actual observed lag varies by workload and region distance — confirm against your own replication latency metrics before committing to an RPO based on vendor documentation).

    Failover to a secondary Region — called a managed planned failover — promotes the secondary Region to primary. The process detects that the secondary has caught up to the primary, then redirects writes. For disaster scenarios where the primary Region is unavailable, you perform an unplanned detach and promote, which may lose the transactions that had not yet replicated. The RPO in a true regional outage is therefore bounded by that replication lag, not zero.

    # Initiate managed planned failover for Aurora Global Database
# (use when primary region is healthy — for maintenance or DR testing)
aws rds failover-global-cluster \
  --global-cluster-identifier prod-global-aurora \
  --target-db-cluster-identifier \
    arn:aws:rds:eu-west-1:123456789012:cluster:prod-aurora-eu-secondary \
  --region us-east-1

# For unplanned failover when primary region is unreachable:
# First, remove the secondary from the global cluster (detach)
aws rds remove-from-global-cluster \
  --db-cluster-identifier \
    arn:aws:rds:eu-west-1:123456789012:cluster:prod-aurora-eu-secondary \
  --global-cluster-identifier prod-global-aurora \
  --region eu-west-1

# The secondary is now an independent cluster — promote it
# (it is already writable once detached; update your application endpoint)

    Azure SQL Business Critical and Geo-Replication

    Azure SQL Business Critical tier automatically provisions an Always On availability group across nodes within a single region. You get a built-in readable secondary at no additional replica cost, with failover typically completing in under 30 seconds. This is the closest Azure analog to Aurora's standard HA.

    For cross-region DR, Azure SQL offers two mechanisms:

  • → **Active Geo-Replication**: Creates up to four readable secondary databases in other regions. Failover is manual or application-triggered. Secondary databases are readable, making them useful for read offloading in addition to DR.
  • → **Auto-Failover Groups**: A layer above Active Geo-Replication that provides a single listener endpoint (a DNS alias) which automatically redirects to the current primary. On failover, the endpoint updates transparently. You configure the failover policy — automatic or manual — and the grace period before automatic failover triggers.
    • # Create Auto-Failover Group between two Azure SQL logical servers
az sql failover-group create \
  --name prod-fog \
  --partner-server prod-sql-server-dr \
  --resource-group prod-rg \
  --server prod-sql-server \
  --failover-policy Automatic \
  --grace-period 1 \
  --add-db prod-database-1 prod-database-2

# Check replication health
az sql failover-group show \
  --name prod-fog \
  --resource-group prod-rg \
  --server prod-sql-server \
  --query "{role:replicationRole, state:replicationState, partnerServer:partnerServers[0].id}"

# Manual failover to secondary (for DR testing or planned maintenance)
az sql failover-group set-primary \
  --name prod-fog \
  --resource-group prod-rg \
  --server prod-sql-server-dr

    One subtle operational point with Auto-Failover Groups: the read-write listener always points to the current primary, and the read-only listener always points to the current secondary. If your application uses a single connection string for both reads and writes, it will work after failover. If your application uses separate connection strings for the read-only replica, verify those strings use the read-only listener endpoint (.secondary.database.windows.net) rather than the secondary server's direct hostname — the direct hostname stops being the secondary after failover.

    GCP Cloud SQL HA and Cross-Region Replicas

    Cloud SQL HA uses a primary instance and a standby instance in separate zones within the same region, connected by a shared regional Persistent Disk. When the primary fails, the standby mounts the disk and resumes. Because the disk is regional (synchronously replicated across zones), no data is lost — the RPO is zero for zone failures. The RTO is approximately 60–120 seconds, including time to detect the failure and complete the promotion.

    For cross-region DR, Cloud SQL uses Cross-Region Read Replicas. These are asynchronous replicas in a different region. Unlike Aurora Global Database, these replicas cannot be promoted with a single API call that preserves the global endpoint — promoting a cross-region replica to a standalone instance requires updating your application's connection string manually or through automation you build yourself.

    # Create cross-region read replica for DR
gcloud sql instances create prod-postgres-dr \
  --master-instance-name=prod-postgres \
  --region=us-west1 \
  --database-version=POSTGRES_15 \
  --tier=db-custom-8-32768 \
  --availability-type=REGIONAL \
  --project=my-project

# Check replication lag on cross-region replica
gcloud sql instances describe prod-postgres-dr \
  --project=my-project \
  --format="value(replicaConfiguration.replicationLagMaxSeconds)"

# Promote replica to standalone (DR failover — point of no return)
gcloud sql instances promote-replica prod-postgres-dr \
  --project=my-project

    AlloyDB introduces a different HA model. AlloyDB clusters are regional by default, and the read pool instances within a region can absorb traffic during a primary failure while a new primary is provisioned from the distributed storage layer — similar to how Aurora promotes a reader. AlloyDB cross-region DR currently relies on backups or third-party replication tools, though Google continues to extend AlloyDB's capabilities.

    3.6 Backup and Point-in-Time Recovery: What "Managed" Actually Means

    On-prem, you owned the backup strategy: take a base backup with pg_basebackup or SQL Server backup to disk, ship transaction logs to a secondary location, test restores quarterly (or, regrettably, never). Cloud managed services automate the base backup and log archiving, but they do not automate the testing, and the restore mechanics differ in ways that catch DBAs off guard.

    AWS RDS and Aurora Backups

    RDS automated backups capture a daily snapshot and stream transaction logs (PostgreSQL WAL, MySQL binary logs) to S3 throughout the day. Point-in-time recovery allows restoration to any second within the backup retention window (1–35 days, configurable). PITR always restores to a new instance — you cannot restore in-place over the existing instance. This is the correct behavior from a safety perspective but means your DR runbook must account for updating application connection strings after restore.

    Aurora backups are stored in S3 in the Aurora storage subsystem — not as traditional filesystem snapshots. This is what enables the fast restore behavior: Aurora restores by making the backup's storage blocks available to a new compute instance, then replaying only the WAL records since the last backup as the instance warms up. The practical result is that Aurora PITR to a large database is significantly faster than RDS PITR to the same effective dataset size.

    # Restore Aurora cluster to a specific point in time
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier prod-aurora-restored-20241115 \
  --source-db-cluster-identifier prod-aurora \
  --restore-to-time "2024-11-15T03:45:00Z" \
  --vpc-security-group-ids sg-0a1b2c3d4e5f12345 \
  --db-subnet-group-name prod-postgres-subnets \
  --region us-east-1

# After cluster restore, create a writer instance in the restored cluster
aws rds create-db-instance \
  --db-instance-identifier prod-aurora-restored-writer \
  --db-cluster-identifier prod-aurora-restored-20241115 \
  --db-instance-class db.r7g.2xlarge \
  --engine aurora-postgresql \
  --region us-east-1

    Manual snapshots exist outside the automated backup retention window. If you need to preserve the state of a database before a major schema migration, take a manual snapshot. Manual snapshots persist until explicitly deleted — they do not expire with the automated backup window.

    Azure SQL Backup

    Azure SQL Database performs automated full backups weekly, differential backups every 12–24 hours, and transaction log backups every 5–12 minutes. The retention period for PITR is 1–35 days on most tiers. Hyperscale uses a different mechanism — snapshots stored on Azure Blob Storage — which is why Hyperscale restores are fast regardless of database size.

    The PITR restore in Azure SQL creates a new database on the same logical server (or a different server in the same region). You cannot restore over an existing database.

    # Restore Azure SQL Database to point in time
az sql db restore \
  --dest-name prod-database-restored-20241115 \
  --edition GeneralPurpose \
  --service-objective GP_Gen5_8 \
  --name prod-database-1 \
  --resource-group prod-rg \
  --server prod-sql-server \
  --time "2024-11-15T03:45:00Z"

# Check restore progress
az sql db show \
  --name prod-database-restored-20241115 \
  --resource-group prod-rg \
  --server prod-sql-server \
  --query "{status:status, createMode:createMode}"

    Long-term retention (LTR) in Azure SQL allows you to keep full backups for up to 10 years — useful for compliance scenarios where you need to restore data from two years ago to answer a legal hold. LTR backups are stored in geo-redundant Azure Blob Storage and count against your storage costs separately.

    GCP Cloud SQL and AlloyDB Backups

    Cloud SQL automated backups take daily snapshots and retain transaction logs for PITR within the retention window (up to 7 days by default, configurable up to 35 days for PostgreSQL 14+). PITR restores to a new instance, consistent with the behavior on AWS and Azure.

    # List available backups for a Cloud SQL instance
gcloud sql backups list \
  --instance=prod-postgres \
  --project=my-project \
  --limit=10

# Restore to point in time — creates a new instance
gcloud sql instances clone prod-postgres prod-postgres-pitr-20241115 \
  --point-in-time="2024-11-15T03:45:00.000Z" \
  --project=my-project

# Export a specific database to GCS for long-term retention
gcloud sql export sql prod-postgres \
  gs://my-backup-bucket/exports/prod-postgres-20241115.sql.gz \
  --database=appdb \
  --project=my-project

    AlloyDB automated backups operate similarly, but AlloyDB's distributed storage layer makes the backup process non-blocking — backup I/O does not contend with production workload I/O in the same way it can on single-instance Cloud SQL.

    A discipline that every DBA should build, regardless of cloud platform: schedule regular restore tests. AWS, Azure, and GCP all automate the backup creation, but none of them verify that the backup is restorable and that the restored database is consistent. Monthly restore tests to a non-production environment, with a validation query that checks row counts against known good values, should be part of every production runbook. The managed service handles the mechanics; the verification remains your responsibility.

    3.7 Performance Monitoring: What You Get, What You Have to Build

    On-prem, a PostgreSQL DBA reaches for pg_stat_activity, pg_stat_bgwriter, pg_locks, and the slow query log. A SQL Server DBA reaches for DMVs, SQL Server Profiler (or Extended Events), and the Query Store. Cloud platforms wrap these native tools with additional abstraction layers and, in some cases, surface insights that would take significant tooling to produce on-prem.

    AWS Performance Insights

    Performance Insights is AWS's answer to the question "why is my database slow right now?" It exposes the database's active session data — the same information underlying pg_stat_activity — through a time-series visualization of Average Active Sessions (AAS) broken down by wait event, SQL statement, host, user, and database.

    The key metric is the DB Load line: the number of sessions actively executing or waiting at any given second. When DB Load exceeds the number of vCPUs on your instance, you have more demand than supply — the database is CPU-bound or has a wait bottleneck worth investigating. Performance Insights retains 7 days of data on the free tier and up to 2 years with the paid tier.

    # Retrieve Performance Insights metrics via CLI
aws pi get-resource-metrics \
  --service-type RDS \
  --identifier db-ABCDEFGHIJKLMNOPQRSTUVWXYZ \
  --metric-queries '[
    {
      "Metric": "db.load.avg",
      "GroupBy": {
        "Group": "db.wait_event",
        "Dimensions": ["db.wait_event.name", "db.wait_event.type"],
        "Limit": 5
      }
    }
  ]' \
  --start-time "2024-11-15T00:00:00Z" \
  --end-time "2024-11-15T01:00:00Z" \
  --period-in-seconds 60 \
  --region us-east-1

    Enhanced Monitoring is a separate feature that captures OS-level metrics (CPU steal, file system I/O, process list) from the host at intervals as low as 1 second. This is the closest cloud-managed equivalent to running top, iostat, and vmstat on the database host. Enhanced Monitoring data flows to CloudWatch Logs, not CloudWatch Metrics, so querying it programmatically requires Log Insights queries rather than standard GetMetricData calls.

    Azure Query Performance Insight and Query Store

    Azure SQL Database automatically enables Query Store, the SQL Server feature that captures query execution statistics and plan history. Query Store data is queryable through the standard DMVs:

    -- Top 10 queries by total CPU time over the last 24 hours (Azure SQL / SQL Server)
SELECT TOP 10
    qsq.query_id,
    qsqt.query_sql_text,
    SUM(qsrs.avg_cpu_time * qsrs.count_executions) AS total_cpu_time_us,
    SUM(qsrs.count_executions) AS total_executions,
    MAX(qsrs.last_execution_time) AS last_execution
FROM sys.query_store_query qsq
JOIN sys.query_store_query_text qsqt ON qsq.query_text_id = qsqt.query_text_id
JOIN sys.query_store_plan qsp ON qsq.query_id = qsp.query_id
JOIN sys.query_store_runtime_stats qsrs ON qsp.plan_id = qsrs.plan_id
JOIN sys.query_store_runtime_stats_interval qsrsi
    ON qsrs.runtime_stats_interval_id = qsrsi.runtime_stats_interval_id
WHERE qsrsi.start_time >= DATEADD(HOUR, -24, GETUTCDATE())
GROUP BY qsq.query_id, qsqt.query_sql_text
ORDER BY total_cpu_time_us DESC;

-- Identify queries with plan regressions (new plan is slower than historical best)
SELECT
    qsq.query_id,
    qsqt.query_sql_text,
    rsp.plan_id AS regressed_plan_id,
    rsp.avg_duration AS regressed_avg_duration_us,
    bsp.plan_id AS best_plan_id,
    bsp.avg_duration AS best_avg_duration_us
FROM sys.dm_db_tuning_recommendations tr
CROSS APPLY OPENJSON(tr.details, '$.queryId') WITH (query_id INT '$') qid
JOIN sys.query_store_query qsq ON qsq.query_id = qid.query_id
JOIN sys.query_store_query_text qsqt ON qsq.query_text_id = qsqt.query_text_id
CROSS APPLY OPENJSON(tr.details, '$.regressedPlanId') WITH (plan_id BIGINT '$') rpid
CROSS APPLY OPENJSON(tr.details, '$.recommendedPlanId') WITH (plan_id BIGINT '$') bpid
JOIN sys.query_store_plan rsp ON rsp.plan_id = rpid.plan_id
JOIN sys.query_store_plan bsp ON bsp.plan_id = bpid.plan_id
WHERE tr.reason = N'PlanChange'
  AND tr.state = 1;  -- Active recommendation

    Query Performance Insight in the Azure portal is a GUI layer over Query Store that highlights the top CPU-consuming and long-running queries. It is useful for initial triage but limited for deep investigation — experienced DBAs will drop into the DMVs directly.

    Azure SQL also offers Automatic Tuning, which can automatically create missing indexes and force the last known good query plan when a regression is detected. Automatic index creation is worth enabling in non-production environments to surface index recommendations, but treat it carefully in production: automatically created indexes consume storage and write overhead, and the automated decision logic may not account for your maintenance windows or storage constraints.

    GCP Cloud SQL Insights and AlloyDB

    Query Insights for Cloud SQL provides a sampling-based view of query activity — similar conceptually to Performance Insights but built around the PostgreSQL pg_stat_statements extension and sampling of active queries. It surfaces the top queries by execution count, mean latency, and rows processed.

    For PostgreSQL, the underlying native tooling remains accessible through standard catalog queries:

    -- Top queries by total execution time in PostgreSQL (Cloud SQL, AlloyDB, RDS, Aurora)
-- Requires pg_stat_statements extension
SELECT
    substring(query, 1, 80) AS query_snippet,
    calls,
    round(total_exec_time::numeric, 2) AS total_exec_time_ms,
    round(mean_exec_time::numeric, 4) AS mean_exec_time_ms,
    round((100.0 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 2) AS pct_total
FROM pg_stat_statements
WHERE query NOT LIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC
LIMIT 20;

-- Identify high lock wait activity
SELECT
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
  AND state != 'idle'
ORDER BY duration DESC;

    The SQL Server equivalent for lock wait analysis uses DMVs:

    -- Active lock waits in SQL Server / Azure SQL
SELECT
    r.session_id,
    r.blocking_session_id,
    r.wait_type,
    r.wait_time / 1000.0 AS wait_time_seconds,
    r.status,
    substring(st.text, (r.statement_start_offset / 2) + 1,
        CASE r.statement_end_offset
            WHEN -1 THEN datalength(st.text)
            ELSE (r.statement_end_offset - r.statement_start_offset) / 2
        END) AS statement_text,
    db_name(r.database_id) AS database_name
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
WHERE r.blocking_session_id > 0
   OR r.wait_type LIKE 'LCK%'
ORDER BY r.wait_time DESC;

    AlloyDB for PostgreSQL surfaces standard pg_stat_* views plus AlloyDB-specific metrics for its columnar cache. The google_columnar_cache schema provides insight into which tables and columns are cached in the columnar store and the cache hit rate — useful for understanding whether analytical queries are benefiting from the columnar acceleration layer.

    3.8 The Operational Cost Model: Thinking in Cloud Units

    The final mental model shift in this chapter is economic. On-prem, you amortize hardware costs over three to five years and pay for licenses, DBA headcount, and data center costs. In the cloud, you pay for every resource-hour consumed. This changes how you make sizing decisions, how you think about idle capacity, and how you evaluate feature tradeoffs.

    AWS RDS Pricing Dimensions

    An Aurora PostgreSQL deployment has multiple cost components:

  • → **Instance hours**: Charged per second for the time each compute instance (writer and readers) runs. Reserved Instances (1-year or 3-year commitments) reduce the effective hourly rate substantially for stable workloads.
  • → **Aurora I/O**: For Aurora Standard, each million read and write I/O operations to the storage layer is charged separately. I/O costs can dominate total spend for write-heavy OLTP workloads. **Aurora I/O-Optimized** is a pricing tier that eliminates the per-I/O charge in exchange for a higher instance and storage base rate. At roughly 25% or more of your Aurora cost coming from I/O charges, the I/O-Optimized tier becomes worth evaluating.
  • → **Storage**: Charged per GB-month for the Aurora storage volume, which grows automatically and never shrinks. Data you deleted six months ago still occupies storage until Aurora's background reclamation completes.
  • → **Backup storage**: Automated backups within the retention window are included. Storage beyond the database size is charged per GB-month.
  • → **Data transfer**: Intra-region data transfer between RDS and EC2 in the same AZ is free. Cross-AZ data transfer (which happens when your application is in AZ-a and your Aurora reader endpoint resolves to AZ-b) is charged per GB. Using the Aurora cluster endpoint reader with AZ affinity routing reduces this cost.

    • Azure SQL Pricing Dimensions

    Azure SQL vCore pricing separates compute and storage:

  • → **vCores**: Charged per vCore-hour. The Serverless compute tier bills per vCore-second when active and a flat rate per GB-hour when paused — useful for development databases that are idle overnight.
  • → **Storage**: Charged per GB-month for the allocated storage. General Purpose tier uses remote storage; Business Critical tier uses local SSD included in the compute pricing.
  • → **Backup storage**: Locally redundant backup storage up to the database size is included. Geo-redundant backup storage is charged extra.
  • → **Elastic Pools**: Share a vCore or DTU allocation across multiple databases. If you have 20 databases where peak activity is staggered, pooling can cut compute costs compared to provisioning each database independently.

    • The Azure Hybrid Benefit allows you to apply existing on-premises SQL Server licenses with active Software Assurance to reduce the Azure SQL compute cost. For organizations migrating from on-prem SQL Server, this can make a significant difference in total cost — verify the current discount percentages with Microsoft's licensing terms, as they are updated periodically.

    GCP Cloud SQL Pricing Dimensions

    Cloud SQL pricing includes:

  • → **Instance type**: Charged per vCPU and GB of RAM per hour. Custom machine types allow precise sizing — you are not locked into predefined instance families.
  • → **Storage**: Charged per GB-month for SSD or HDD persistent disk.
  • → **High Availability**: Enabling HA doubles the compute cost (you pay for the standby instance).
  • → **Read replicas**: Charged at the same rate as the primary instance per replica.
  • → **Egress**: Data transferred out of GCP to the internet is charged per GB. Data transferred within the same region between Cloud SQL and Cloud Run or GKE is typically free.

    • The persistent-disk storage model on Cloud SQL means that provisioned storage counts against your bill whether you use it or not. If you provision 2 TB and use 200 GB, you pay for 2 TB. Monitor storage utilization and adjust provisioning accordingly — or enable storage autoscaling with a reasonable cap.

    Right-sizing in Practice

    The most common cost optimization mistake for cloud databases is running on the same instance size chosen during initial provisioning without revisiting it. The right workflow:

    1. Enable Performance Insights (AWS), Query Performance Insight (Azure), or Query Insights (GCP).

    2. After two to four weeks of representative traffic, look at the sustained CPU utilization and memory pressure metrics.

    3. If average CPU stays below 20% and you never see memory pressure, consider sizing down one instance tier.

    4. If you see sustained CPU above 60–70%, investigate query tuning before scaling up — you may be paying for compute to execute inefficient queries.

    5. Use Reserved Instances (AWS) or Committed Use Discounts (GCP) for your baseline capacity once you have a stable sizing baseline. Paying on-demand rates for a production database running continuously is one of the most visible and correctable cloud cost inefficiencies.

    ---

    Key Takeaways

  • → **The three cloud platforms are not equivalent at the service layer.** Aurora's distributed storage model, Azure SQL's DTU vs. vCore models, and Cloud SQL's zonal-vs-regional HA have real architectural consequences that affect failover time, replica behavior, and storage costs — mapping them as interchangeable is an architectural mistake.
  • → **Networking has become a first-class database configuration concern.** Private endpoints, VPC peering, Security Groups, and connection proxies (RDS Proxy, Cloud SQL Auth Proxy) replace the IP-based rules of pg_hba.conf and require deliberate architecture decisions before your first production deployment.
  • → **IAM integration reduces credential sprawl but does not eliminate database-level access control.** IAM tokens, Azure Managed Identity, and GCP service account authentication control who can connect, but PostgreSQL roles and SQL Server logins still govern what they can do inside the database — both layers must be managed.
  • → **HA failover times and RPO characteristics differ substantially across platforms.** Aurora's sub-30-second failover from shared storage contrasts with Cloud SQL's 60–120 second zone failover and Azure SQL Business Critical's Always On behavior. Design application reconnect logic and SLA commitments around the actual failover mechanics of your chosen platform, not a generic "managed = highly available" assumption.
  • → **Backup automation covers creation, not validation.** Every managed database service handles scheduled backups automatically, but restore testing remains a manual operational responsibility. Monthly restore drills to a non-production environment are the only reliable way to know that your backup retention window represents actual recoverability.
