Chapter 15: Query-Time Retrieval: Writing Efficient Vector Queries

Vector search is only as good as the queries that drive it. Embedding documents into PostgreSQL is the straightforward part — you run text through an embedding model, store the resulting float array, and call it done. The hard part is writing queries that return relevant results fast enough for real users, at real scale, without burning your GPU budget or melting your database under load. This chapter covers the full mechanics of query-time retrieval: how distance operators work and when to choose each one, how to write vector queries that compose cleanly with relational filters, how to tune index behavior at query time, and how to build the retrieval layer of a production RAG system that your database will actually survive serving.

---

15.1 Distance Operators and When Each One Matters

pgvector exposes three distance operators, and choosing the wrong one for your embedding model is one of the most common mistakes teams make when moving from prototype to production.

Cosine distance (<=>) measures the angle between two vectors, ignoring magnitude. Most modern embedding models — OpenAI's text-embedding-3-small, text-embedding-3-large, Anthropic's embeddings via Voyage, Cohere's embed-v3 — produce L2-normalized vectors. For normalized vectors, cosine similarity and dot product similarity are mathematically equivalent: they produce the same ranking. But the operator you choose still matters because the index type that backs it changes performance characteristics.

L2 distance (<->) measures Euclidean distance in embedding space. Use this when your model produces unnormalized embeddings or when you're working with embeddings that carry magnitude information you want to preserve — for example, some fine-tuned models where magnitude encodes confidence or frequency.

Negative inner product (<#>) computes the dot product and negates it so that higher similarity means lower operator output (fitting PostgreSQL's ascending sort convention). For normalized vectors, <#> and <=> rank identically, but <#> is slightly faster because it skips the normalization step.

The practical rule: check your model's documentation. If it says to use cosine similarity (essentially every major API embedding model does), use <=>. If your embeddings are not normalized and you want magnitude-sensitive ranking, use <->. The following schema demonstrates how to make the operator choice visible and testable:

-- Schema: embedding store with operator-aware retrieval functions
CREATE TABLE document_chunks (
    id              BIGSERIAL PRIMARY KEY,
    document_id     BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    chunk_index     INTEGER NOT NULL,
    content         TEXT NOT NULL,
    token_count     INTEGER NOT NULL,
    embedding       VECTOR(1536),           -- OpenAI text-embedding-3-small
    embedding_model VARCHAR(64) NOT NULL DEFAULT 'text-embedding-3-small',
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE(document_id, chunk_index)
);

-- IVFFlat index for cosine distance (the right choice for OpenAI embeddings)
CREATE INDEX idx_chunks_embedding_cosine
    ON document_chunks
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

-- HNSW index for cosine distance — better recall, higher build cost
CREATE INDEX idx_chunks_embedding_hnsw
    ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Basic cosine similarity search
-- Returns top-k chunks nearest to a query embedding
CREATE OR REPLACE FUNCTION search_chunks(
    query_embedding  VECTOR(1536),
    top_k            INTEGER DEFAULT 10,
    similarity_threshold FLOAT DEFAULT 0.7
)
RETURNS TABLE (
    id              BIGINT,
    document_id     BIGINT,
    content         TEXT,
    metadata        JSONB,
    similarity      FLOAT
)
LANGUAGE sql STABLE PARALLEL SAFE AS $$
    SELECT
        dc.id,
        dc.document_id,
        dc.content,
        dc.metadata,
        1 - (dc.embedding <=> query_embedding) AS similarity
    FROM document_chunks dc
    WHERE dc.embedding IS NOT NULL
      AND 1 - (dc.embedding <=> query_embedding) >= similarity_threshold
    ORDER BY dc.embedding <=> query_embedding
    LIMIT top_k;
$$;

Notice that the WHERE clause uses a similarity threshold expressed as 1 - distance >= threshold. This is important: a cosine distance of 0.0 means identical vectors (similarity 1.0), and a distance of 2.0 means perfectly opposite (similarity -1.0). Most semantic search applications want results with similarity above 0.7 for meaningful matches. Setting similarity_threshold = 0.0 disables filtering and returns the nearest neighbors regardless of how far they are — sometimes appropriate when your corpus is small and you always want _something_.

The distance operators also have different EXPLAIN plan characteristics. Run EXPLAIN ANALYZE against your retrieval queries during development:

-- Inspect the execution plan for a vector search
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    id,
    content,
    1 - (embedding <=> '[0.1, 0.2, ...]'::VECTOR(1536)) AS similarity
FROM document_chunks
ORDER BY embedding <=> '[0.1, 0.2, ...]'::VECTOR(1536)
LIMIT 10;

When an index is active, you'll see Index Scan using idx_chunks_embedding_hnsw in the plan. When the query planner falls back to a sequential scan — because the table is too small, statistics are stale, or the query shape doesn't match the index — you'll see Seq Scan with a much higher actual rows count. Both are correct behavior at different scales; the important thing is knowing which you're getting.

15.2 Hybrid Search: Combining Vector and Relational Filters

Pure vector search returns the semantically nearest chunks, but production RAG systems almost always have additional constraints. A user asks about Q3 expenses — you want semantically relevant chunks _and_ chunks from financial documents created after a certain date. A multi-tenant SaaS system needs to limit search to chunks belonging to the current tenant. A chatbot for a software product needs to filter by product version.

These are relational constraints, and they're exactly what PostgreSQL does better than any dedicated vector store. The pattern is called pre-filtering (apply relational filters before vector ranking) versus post-filtering (vector rank first, then filter). Pre-filtering is almost always preferable for correctness; post-filtering can miss relevant results if your top-k window is smaller than the filtered result set.

-- Full schema for multi-tenant document corpus
CREATE TABLE tenants (
    id          BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    slug        VARCHAR(64) UNIQUE NOT NULL,
    plan        VARCHAR(32) NOT NULL DEFAULT 'free'
);

CREATE TABLE documents (
    id              BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    tenant_id       BIGINT NOT NULL REFERENCES tenants(id),
    title           TEXT NOT NULL,
    source_url      TEXT,
    doc_type        VARCHAR(64) NOT NULL,   -- 'policy', 'report', 'manual', etc.
    published_at    TIMESTAMPTZ,
    tags            TEXT[] NOT NULL DEFAULT '{}',
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_documents_tenant ON documents(tenant_id);
CREATE INDEX idx_documents_type_tenant ON documents(doc_type, tenant_id);
CREATE INDEX idx_documents_tags ON documents USING gin(tags);

-- Hybrid search function: relational filters + vector similarity
-- This is the workhorse function for a production RAG retrieval layer
CREATE OR REPLACE FUNCTION hybrid_search(
    p_query_embedding   VECTOR(1536),
    p_tenant_id         BIGINT,
    p_doc_types         TEXT[]      DEFAULT NULL,
    p_tags              TEXT[]      DEFAULT NULL,
    p_published_after   TIMESTAMPTZ DEFAULT NULL,
    p_top_k             INTEGER     DEFAULT 10,
    p_min_similarity    FLOAT       DEFAULT 0.65
)
RETURNS TABLE (
    chunk_id        BIGINT,
    document_id     BIGINT,
    doc_type        VARCHAR(64),
    title           TEXT,
    content         TEXT,
    metadata        JSONB,
    published_at    TIMESTAMPTZ,
    similarity      FLOAT,
    rank_position   BIGINT
)
LANGUAGE sql STABLE PARALLEL SAFE AS $$
    SELECT
        dc.id                                            AS chunk_id,
        d.id                                             AS document_id,
        d.doc_type,
        d.title,
        dc.content,
        dc.metadata,
        d.published_at,
        1 - (dc.embedding <=> p_query_embedding)         AS similarity,
        ROW_NUMBER() OVER (
            ORDER BY dc.embedding <=> p_query_embedding
        )                                                AS rank_position
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.tenant_id = p_tenant_id
      AND d.is_active = TRUE
      AND dc.embedding IS NOT NULL
      AND 1 - (dc.embedding <=> p_query_embedding) >= p_min_similarity
      AND (p_doc_types IS NULL OR d.doc_type = ANY(p_doc_types))
      AND (p_tags IS NULL      OR d.tags && p_tags)
      AND (p_published_after IS NULL OR d.published_at >= p_published_after)
    ORDER BY dc.embedding <=> p_query_embedding
    LIMIT p_top_k;
$$;

The && operator on the tags array means "arrays overlap" — the GIN index on documents.tags makes this fast. Combining a GIN index for the tag filter with an HNSW index for the vector sort produces an efficient plan where PostgreSQL applies the cheap relational filters first, then ranks the survivors by vector distance.

For scenarios where you also need full-text ranking alongside vector ranking — the full "hybrid" in hybrid search — you can combine tsvector BM25 scoring with cosine similarity using Reciprocal Rank Fusion (RRF):

-- Reciprocal Rank Fusion: blend full-text and vector rankings
-- RRF score = 1/(k + rank) summed across retrieval methods
-- k=60 is standard; lower k amplifies differences at the top
WITH vector_results AS (
    SELECT
        dc.id,
        dc.content,
        dc.document_id,
        ROW_NUMBER() OVER (ORDER BY dc.embedding <=> '[...]'::VECTOR(1536)) AS vector_rank
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.tenant_id = 42
      AND d.is_active = TRUE
    ORDER BY dc.embedding <=> '[...]'::VECTOR(1536)
    LIMIT 50   -- candidate pool, wider than final top_k
),
fulltext_results AS (
    SELECT
        dc.id,
        dc.content,
        dc.document_id,
        ROW_NUMBER() OVER (
            ORDER BY ts_rank_cd(
                to_tsvector('english', dc.content),
                websearch_to_tsquery('english', 'quarterly revenue forecast')
            ) DESC
        ) AS text_rank
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.tenant_id = 42
      AND d.is_active = TRUE
      AND to_tsvector('english', dc.content)
          @@ websearch_to_tsquery('english', 'quarterly revenue forecast')
    LIMIT 50
),
rrf_scores AS (
    SELECT
        COALESCE(v.id, f.id)              AS chunk_id,
        COALESCE(v.content, f.content)    AS content,
        COALESCE(v.document_id, f.document_id) AS document_id,
        COALESCE(1.0 / (60 + v.vector_rank), 0)  +
        COALESCE(1.0 / (60 + f.text_rank), 0)    AS rrf_score
    FROM vector_results v
    FULL OUTER JOIN fulltext_results f ON v.id = f.id
)
SELECT chunk_id, content, document_id, rrf_score
FROM rrf_scores
ORDER BY rrf_score DESC
LIMIT 10;

RRF is model-agnostic and works well across domains without tuning weights. The 60 constant is a smoothing factor that prevents very high-ranked results in one list from completely dominating the final score when they don't appear in the other list.

15.3 Index Tuning at Query Time

Index configuration is set at CREATE time, but several behaviors can be adjusted per-session or per-query, which is valuable when you need different speed/recall trade-offs for different workloads.

For HNSW indexes, the hnsw.ef_search parameter controls how many candidates the graph search explores. Higher values improve recall at the cost of latency. The default is 40:

-- Tune HNSW recall per session
-- High-recall mode for offline batch processing or evaluation runs
SET hnsw.ef_search = 200;

-- Low-latency mode for real-time chat (default is fine here)
SET hnsw.ef_search = 40;

-- Verify what the planner will use
SHOW hnsw.ef_search;

-- Per-transaction override (won't persist after COMMIT)
BEGIN;
SET LOCAL hnsw.ef_search = 100;
SELECT * FROM search_chunks('[...]'::VECTOR(1536), 20);
COMMIT;

For IVFFlat indexes, the analogous parameter is ivfflat.probes — the number of lists to search. More probes means higher recall but slower queries:

-- IVFFlat probe tuning
-- Rule of thumb: probes = sqrt(lists) for balanced speed/recall
-- With lists=100, probes=10 is baseline; probes=20 is higher recall
SET ivfflat.probes = 10;   -- fast, ~85-90% recall
SET ivfflat.probes = 20;   -- slower, ~95% recall
SET ivfflat.probes = 100;  -- full scan, 100% recall (defeats the index purpose)

-- Check whether queries are actually using your index
-- If the planner chooses sequential scan over small result sets, that's correct
SELECT relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'document_chunks';

The planner switches between index scan and sequential scan based on statistics and the enable_indexscan GUC. If you're seeing sequential scans on a large table and you know your HNSW index should be used, run ANALYZE document_chunks to refresh statistics. If that doesn't fix it, check whether your query includes any functions that prevent index usage:

-- This CAN use the vector index (operator directly on indexed column)
SELECT id FROM document_chunks
ORDER BY embedding <=> query_embedding
LIMIT 10;

-- This CANNOT use the vector index (function wrapping the column)
-- Don't do this
SELECT id FROM document_chunks
ORDER BY vector_distance(embedding, query_embedding)
LIMIT 10;

Partial indexes are another underused tool. If 90% of your searches target active, non-deleted chunks, a partial index on that subset is smaller, faster to build, and produces better plans:

-- Partial HNSW index: only active chunks with populated embeddings
-- Dramatically faster for the 99% case
CREATE INDEX idx_chunks_active_hnsw
    ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE embedding IS NOT NULL
      AND is_deleted = FALSE;

-- The query must match the partial index condition exactly
-- to get the index scan
SELECT id, content, 1 - (embedding <=> '[...]'::VECTOR) AS sim
FROM document_chunks
WHERE embedding IS NOT NULL
  AND is_deleted = FALSE
ORDER BY embedding <=> '[...]'::VECTOR
LIMIT 10;

15.4 Building the Retrieval Layer in Python

The query logic above needs to be called from your application. The retrieval layer is the bridge between an LLM request (user question → embedding → SQL → retrieved context → LLM prompt → answer) and PostgreSQL. Here's a production-grade retrieval client using asyncpg, OpenAI for embeddings, and the hybrid_search function defined earlier:

# retrieval/client.py
# Production retrieval layer: embedding + hybrid search + result formatting

import asyncio
import hashlib
import json
import time
from dataclasses import dataclass, field
from typing import Optional

import asyncpg
import redis.asyncio as redis
from openai import AsyncOpenAI

@dataclass
class RetrievedChunk:
    chunk_id: int
    document_id: int
    doc_type: str
    title: str
    content: str
    metadata: dict
    published_at: Optional[str]
    similarity: float
    rank_position: int

@dataclass
class RetrievalConfig:
    top_k: int = 10
    min_similarity: float = 0.65
    doc_types: Optional[list[str]] = None
    tags: Optional[list[str]] = None
    published_after: Optional[str] = None
    use_hybrid: bool = True
    cache_ttl_seconds: int = 300


class RetrievalClient:
    """
    Query-time retrieval client for PostgreSQL vector search.

    Responsibilities:
    - Embed the user query using the same model used at ingestion time
    - Cache embeddings to avoid redundant API calls
    - Execute hybrid_search via asyncpg
    - Return structured chunks ready for prompt assembly
    """

    EMBEDDING_MODEL = "text-embedding-3-small"
    EMBEDDING_DIMS = 1536

    def __init__(
        self,
        pg_pool: asyncpg.Pool,
        redis_client: redis.Redis,
        openai_client: AsyncOpenAI,
    ):
        self._pool = pg_pool
        self._redis = redis_client
        self._openai = openai_client

    async def embed_query(self, text: str) -> list[float]:
        """
        Embed a query string, using Redis to cache results.
        Cache key is a hash of model + text so cache is model-version-safe.
        """
        cache_key = "emb:" + hashlib.sha256(
            f"{self.EMBEDDING_MODEL}:{text}".encode()
        ).hexdigest()

        cached = await self._redis.get(cache_key)
        if cached:
            return json.loads(cached)

        response = await self._openai.embeddings.create(
            input=text,
            model=self.EMBEDDING_MODEL,
        )
        embedding = response.data[0].embedding

        # Cache for 1 hour — query embeddings are deterministic
        await self._redis.setex(cache_key, 3600, json.dumps(embedding))
        return embedding

    def _embedding_to_pg(self, embedding: list[float]) -> str:
        """Format a Python list as a pgvector literal."""
        return "[" + ",".join(str(x) for x in embedding) + "]"

    async def retrieve(
        self,
        query: str,
        tenant_id: int,
        config: Optional[RetrievalConfig] = None,
    ) -> list[RetrievedChunk]:
        """
        Main retrieval entrypoint.
        Embeds query, runs hybrid_search, returns structured results.
        """
        if config is None:
            config = RetrievalConfig()

        t0 = time.monotonic()
        embedding = await self.embed_query(query)
        embed_ms = (time.monotonic() - t0) * 1000

        embedding_literal = self._embedding_to_pg(embedding)

        t1 = time.monotonic()
        async with self._pool.acquire() as conn:
            rows = await conn.fetch(
                """
                SELECT
                    chunk_id, document_id, doc_type, title,
                    content, metadata, published_at,
                    similarity, rank_position
                FROM hybrid_search(
                    $1::VECTOR,   -- query embedding
                    $2,           -- tenant_id
                    $3,           -- doc_types filter
                    $4,           -- tags filter
                    $5,           -- published_after filter
                    $6,           -- top_k
                    $7            -- min_similarity
                )
                """,
                embedding_literal,
                tenant_id,
                config.doc_types,
                config.tags,
                config.published_after,
                config.top_k,
                config.min_similarity,
            )
        query_ms = (time.monotonic() - t1) * 1000

        chunks = [
            RetrievedChunk(
                chunk_id=row["chunk_id"],
                document_id=row["document_id"],
                doc_type=row["doc_type"],
                title=row["title"],
                content=row["content"],
                metadata=dict(row["metadata"]) if row["metadata"] else {},
                published_at=str(row["published_at"]) if row["published_at"] else None,
                similarity=float(row["similarity"]),
                rank_position=int(row["rank_position"]),
            )
            for row in rows
        ]

        # Structured log for query latency observability
        print(json.dumps({
            "event": "retrieval_complete",
            "tenant_id": tenant_id,
            "query_preview": query[:80],
            "embed_ms": round(embed_ms, 1),
            "query_ms": round(query_ms, 1),
            "results_count": len(chunks),
            "top_similarity": chunks[0].similarity if chunks else None,
        }))

        return chunks

    def format_context_for_prompt(
        self,
        chunks: list[RetrievedChunk],
        max_chars: int = 12000,
    ) -> str:
        """
        Format retrieved chunks into a context block for LLM prompts.
        Respects a character budget to avoid overflowing context windows.
        """
        sections = []
        total_chars = 0

        for chunk in chunks:
            header = (
                f"[Source: {chunk.title} | Type: {chunk.doc_type} "
                f"| Relevance: {chunk.similarity:.2f}]"
            )
            body = chunk.content.strip()
            section = f"{header}\n{body}"
            section_chars = len(section)

            if total_chars + section_chars > max_chars:
                break

            sections.append(section)
            total_chars += section_chars

        return "\n\n---\n\n".join(sections)


# Factory: build the client with connection pools
async def create_retrieval_client(
    postgres_dsn: str,
    redis_url: str,
    openai_api_key: str,
) -> RetrievalClient:
    pg_pool = await asyncpg.create_pool(
        dsn=postgres_dsn,
        min_size=5,
        max_size=20,
        command_timeout=30,
    )
    redis_client = redis.from_url(redis_url, decode_responses=True)
    openai_client = AsyncOpenAI(api_key=openai_api_key)

    return RetrievalClient(pg_pool, redis_client, openai_client)

The end-to-end shape of a single retrieval call — from incoming query to LLM-ready context — looks like this:

graph TD
    A[User query] --> B[embed_query]
    B --> C{Redis cache hit?}
    C -->|yes| E[Cached embedding]
    C -->|no| D[OpenAI embeddings API]
    D --> F[Cache in Redis]
    F --> E
    E --> G[hybrid_search SQL function]
    G --> H[(document_chunks + documents)]
    H --> I[Ranked chunks]
    I --> J[format_context_for_prompt]
    J --> K[LLM completion]

*Retrieval client flow: the embedding step is cached, the SQL function does the relational-plus-vector ranking, and only the survivors are formatted into the LLM prompt.*

15.5 Plugging Retrieval into a FastAPI RAG Endpoint

The retrieval client needs to live inside a request/response lifecycle. Here's a complete FastAPI endpoint that wires together the retrieval layer, LLM call, and response streaming, using the client built in 15.4:

# api/rag_endpoint.py
# FastAPI RAG endpoint: retrieval + LLM prompt assembly + streaming response

import json
import os
from contextlib import asynccontextmanager
from typing import AsyncIterator, Optional

from fastapi import Depends, FastAPI, Header, HTTPException, Request
from fastapi.responses import StreamingResponse
from openai import AsyncOpenAI
from pydantic import BaseModel, Field

from retrieval.client import (
    RetrievalClient,
    RetrievalConfig,
    create_retrieval_client,
)


# ---------------------------------------------------------------------------
# App lifecycle: create shared pools once at startup
# ---------------------------------------------------------------------------

retrieval_client: Optional[RetrievalClient] = None


@asynccontextmanager
async def lifespan(app: FastAPI):
    global retrieval_client
    retrieval_client = await create_retrieval_client(
        postgres_dsn=os.environ["POSTGRES_DSN"],
        redis_url=os.environ["REDIS_URL"],
        openai_api_key=os.environ["OPENAI_API_KEY"],
    )
    yield
    # Cleanup on shutdown (asyncpg pool closes gracefully)
    if retrieval_client:
        await retrieval_client._pool.close()


app = FastAPI(title="RAG API", lifespan=lifespan)


# ---------------------------------------------------------------------------
# Request / response models
# ---------------------------------------------------------------------------

class RAGRequest(BaseModel):
    query: str = Field(..., min_length=1, max_length=2000)
    doc_types: Optional[list[str]] = None
    tags: Optional[list[str]] = None
    published_after: Optional[str] = None
    top_k: int = Field(default=8, ge=1, le=50)
    min_similarity: float = Field(default=0.65, ge=0.0, le=1.0)
    stream: bool = False


class RAGSource(BaseModel):
    chunk_id: int
    document_id: int
    title: str
    doc_type: str
    similarity: float
    rank_position: int


class RAGResponse(BaseModel):
    answer: str
    sources: list[RAGSource]
    embed_cached: bool
    chunks_retrieved: int


# ---------------------------------------------------------------------------
# Tenant resolution (simplified — replace with your auth middleware)
# ---------------------------------------------------------------------------

async def get_tenant_id(x_tenant_id: str = Header(...)) -> int:
    try:
        return int(x_tenant_id)
    except ValueError:
        raise HTTPException(status_code=400, detail="X-Tenant-Id must be an integer")


# ---------------------------------------------------------------------------
# System prompt builder
# ---------------------------------------------------------------------------

SYSTEM_PROMPT_TEMPLATE = """You are a helpful assistant answering questions \
based on the provided document excerpts.

Rules:
- Answer only from the provided context. Do not use prior knowledge.
- If the context does not contain enough information to answer, say so explicitly.
- Cite sources by title when you reference specific information.
- Be concise and accurate.

Context:
{context}
"""


def build_messages(query: str, context: str) -> list[dict]:
    return [
        {
            "role": "system",
            "content": SYSTEM_PROMPT_TEMPLATE.format(context=context),
        },
        {
            "role": "user",
            "content": query,
        },
    ]


# ---------------------------------------------------------------------------
# Non-streaming RAG handler
# ---------------------------------------------------------------------------

@app.post("/rag/query", response_model=RAGResponse)
async def rag_query(
    body: RAGRequest,
    tenant_id: int = Depends(get_tenant_id),
):
    config = RetrievalConfig(
        top_k=body.top_k,
        min_similarity=body.min_similarity,
        doc_types=body.doc_types,
        tags=body.tags,
        published_after=body.published_after,
    )

    chunks = await retrieval_client.retrieve(body.query, tenant_id, config)

    if not chunks:
        return RAGResponse(
            answer=(
                "I could not find any relevant documents for your query. "
                "Try rephrasing or broadening your search filters."
            ),
            sources=[],
            embed_cached=False,
            chunks_retrieved=0,
        )

    context = retrieval_client.format_context_for_prompt(chunks, max_chars=12000)
    messages = build_messages(body.query, context)

    openai_client = AsyncOpenAI(api_key=os.environ["OPENAI_API_KEY"])
    completion = await openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
        temperature=0.2,
        max_tokens=1024,
    )

    answer = completion.choices[0].message.content or ""

    sources = [
        RAGSource(
            chunk_id=c.chunk_id,
            document_id=c.document_id,
            title=c.title,
            doc_type=c.doc_type,
            similarity=c.similarity,
            rank_position=c.rank_position,
        )
        for c in chunks
    ]

    return RAGResponse(
        answer=answer,
        sources=sources,
        embed_cached=False,   # wire up cache-hit tracking if needed
        chunks_retrieved=len(chunks),
    )


# ---------------------------------------------------------------------------
# Streaming RAG handler — sends answer tokens as SSE, then sources as JSON
# ---------------------------------------------------------------------------

@app.post("/rag/stream")
async def rag_stream(
    body: RAGRequest,
    tenant_id: int = Depends(get_tenant_id),
):
    config = RetrievalConfig(
        top_k=body.top_k,
        min_similarity=body.min_similarity,
        doc_types=body.doc_types,
        tags=body.tags,
        published_after=body.published_after,
    )

    chunks = await retrieval_client.retrieve(body.query, tenant_id, config)

    async def event_stream() -> AsyncIterator[str]:
        if not chunks:
            yield "data: " + json.dumps({
                "type": "error",
                "message": "No relevant documents found.",
            }) + "\n\n"
            return

        # Send source metadata immediately so the client can render citations
        # before the LLM has finished generating
        sources_payload = [
            {
                "chunk_id": c.chunk_id,
                "document_id": c.document_id,
                "title": c.title,
                "doc_type": c.doc_type,
                "similarity": c.similarity,
                "rank_position": c.rank_position,
            }
            for c in chunks
        ]
        yield "data: " + json.dumps({
            "type": "sources",
            "sources": sources_payload,
        }) + "\n\n"

        context = retrieval_client.format_context_for_prompt(
            chunks, max_chars=12000
        )
        messages = build_messages(body.query, context)

        openai_client = AsyncOpenAI(api_key=os.environ["OPENAI_API_KEY"])
        stream = await openai_client.chat.completions.create(
            model="gpt-4o-mini",
            messages=messages,
            temperature=0.2,
            max_tokens=1024,
            stream=True,
        )

        async for chunk in stream:
            delta = chunk.choices[0].delta.content
            if delta:
                yield "data: " + json.dumps({
                    "type": "token",
                    "content": delta,
                }) + "\n\n"

        yield "data: " + json.dumps({"type": "done"}) + "\n\n"

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",   # disable nginx buffering for SSE
        },
    )

The streaming endpoint separates source metadata from answer tokens in the SSE stream. Clients receive type: sources first (so citations can appear in the UI immediately), then type: token events as the LLM generates, then type: done to signal completion. This pattern avoids the common mistake of waiting for the full LLM response before returning anything to the user.

15.6 Pagination and Cursor-Based Result Retrieval

Vector search with LIMIT is not paginated — running the same query twice with LIMIT 10 OFFSET 10 is not safe for vector search because approximate indexes do not guarantee stable ordering between executions. The result set at positions 11–20 may not be the "next 10 most similar" items; it depends on the execution path through the graph or inverted file.

For the rare cases where you need pagination over vector results, the correct approach is to fetch a larger candidate pool upfront, store it server-side, and paginate over that stable set:

-- Server-side cursor pagination over vector results
-- Step 1: Materialize a retrieval session (run once per user query)
CREATE TABLE retrieval_sessions (
    session_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       BIGINT NOT NULL,
    query_text      TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ NOT NULL
        DEFAULT NOW() + INTERVAL '10 minutes'
);

CREATE TABLE retrieval_session_results (
    session_id      UUID NOT NULL REFERENCES retrieval_sessions(session_id)
                        ON DELETE CASCADE,
    rank_position   INTEGER NOT NULL,
    chunk_id        BIGINT NOT NULL,
    similarity      FLOAT NOT NULL,
    PRIMARY KEY (session_id, rank_position)
);

-- Step 2: Populate a session with top-100 candidates
CREATE OR REPLACE FUNCTION create_retrieval_session(
    p_tenant_id         BIGINT,
    p_query_embedding   VECTOR(1536),
    p_query_text        TEXT,
    p_candidate_pool    INTEGER DEFAULT 100
)
RETURNS UUID
LANGUAGE plpgsql AS $$
DECLARE
    v_session_id UUID;
BEGIN
    INSERT INTO retrieval_sessions(tenant_id, query_text)
    VALUES (p_tenant_id, p_query_text)
    RETURNING session_id INTO v_session_id;

    INSERT INTO retrieval_session_results(session_id, rank_position, chunk_id, similarity)
    SELECT
        v_session_id,
        ROW_NUMBER() OVER (ORDER BY dc.embedding <=> p_query_embedding),
        dc.id,
        1 - (dc.embedding <=> p_query_embedding)
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.tenant_id = p_tenant_id
      AND d.is_active = TRUE
      AND dc.embedding IS NOT NULL
    ORDER BY dc.embedding <=> p_query_embedding
    LIMIT p_candidate_pool;

    RETURN v_session_id;
END;
$$;

-- Step 3: Stable paginated fetch from the materialized session
CREATE OR REPLACE FUNCTION fetch_session_page(
    p_session_id    UUID,
    p_page          INTEGER DEFAULT 1,
    p_page_size     INTEGER DEFAULT 10
)
RETURNS TABLE (
    rank_position   INTEGER,
    chunk_id        BIGINT,
    content         TEXT,
    title           TEXT,
    similarity      FLOAT
)
LANGUAGE sql STABLE AS $$
    SELECT
        rsr.rank_position,
        rsr.chunk_id,
        dc.content,
        d.title,
        rsr.similarity
    FROM retrieval_session_results rsr
    JOIN document_chunks dc ON dc.id = rsr.chunk_id
    JOIN documents d ON d.id = dc.document_id
    WHERE rsr.session_id = p_session_id
      AND rsr.rank_position BETWEEN
            (p_page - 1) * p_page_size + 1
        AND p_page * p_page_size
    ORDER BY rsr.rank_position;
$$;

In practice, most RAG applications never need pagination — they retrieve 5–20 chunks and feed them all to the LLM. The session pattern above is useful for search-UI applications where users browse results and expect stable pages, not for the inner loop of an LLM pipeline.

15.7 SQL Server Companion: Vector Search with Azure SQL and Fabric

SQL Server introduced native vector support in Azure SQL Database and SQL Server 2025, using the VECTOR data type and the VECTOR_DISTANCE function. The pattern is similar to pgvector but with different syntax and index mechanics.

-- Azure SQL / SQL Server 2025: vector search schema
CREATE TABLE document_chunks (
    id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    document_id     BIGINT NOT NULL,
    chunk_index     INT NOT NULL,
    content         NVARCHAR(MAX) NOT NULL,
    token_count     INT NOT NULL,
    embedding       VECTOR(1536),          -- native VECTOR type
    embedding_model VARCHAR(64) NOT NULL DEFAULT 'text-embedding-3-small',
    metadata        NVARCHAR(MAX) NOT NULL DEFAULT '{}',  -- JSON as NVARCHAR
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    UNIQUE (document_id, chunk_index)
);

-- Vector index (DiskANN-based in Azure SQL)
CREATE VECTOR INDEX idx_chunks_embedding
    ON document_chunks (embedding)
    WITH (metric = 'cosine');

-- Basic similarity search using VECTOR_DISTANCE
-- Lower distance = more similar (same convention as pgvector operators)
SELECT TOP 10
    id,
    content,
    1 - VECTOR_DISTANCE('cosine', embedding, CAST(@query_embedding AS VECTOR(1536)))
        AS similarity
FROM document_chunks
WHERE embedding IS NOT NULL
ORDER BY VECTOR_DISTANCE('cosine', embedding, CAST(@query_embedding AS VECTOR(1536)));

-- Hybrid search: relational filter + vector distance
DECLARE @tenant_id BIGINT = 42;
DECLARE @query_vec VECTOR(1536) = CAST(@query_embedding_json AS VECTOR(1536));
DECLARE @min_sim FLOAT = 0.65;
DECLARE @top_k INT = 10;

SELECT TOP (@top_k)
    dc.id                 AS chunk_id,
    d.id                  AS document_id,
    d.doc_type,
    d.title,
    dc.content,
    1 - VECTOR_DISTANCE('cosine', dc.embedding, @query_vec) AS similarity
FROM document_chunks dc
JOIN documents d ON dc.document_id = d.id
WHERE d.tenant_id = @tenant_id
  AND d.is_active = 1
  AND dc.embedding IS NOT NULL
  AND 1 - VECTOR_DISTANCE('cosine', dc.embedding, @query_vec) >= @min_sim
ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vec);

The key differences from pgvector are:

  • → **`VECTOR_DISTANCE(metric, col, value)`** is a function rather than an infix operator. You must specify the metric (`'cosine'`, `'euclidean'`, `'dot'`) as an explicit argument.
  • → **Vector indexes** in Azure SQL use DiskANN under the hood (a Microsoft Research graph-based ANN algorithm comparable to HNSW). You create them with `CREATE VECTOR INDEX` rather than `USING hnsw` or `USING ivfflat`.
  • → **Casting** from JSON string to `VECTOR` uses `CAST(... AS VECTOR(1536))`, where the input is a JSON array string like `'[0.1, 0.2, ...]'`.
  • → **`TOP` instead of `LIMIT`** follows standard T-SQL convention; `TOP (@variable)` allows parameterized limits.

    • Reciprocal Rank Fusion in T-SQL follows the same logic as the PostgreSQL version but uses CTEs with T-SQL syntax:

    -- RRF hybrid search in T-SQL (Azure SQL / SQL Server 2025)
DECLARE @query_vec   VECTOR(1536) = CAST(@embedding_json AS VECTOR(1536));
DECLARE @query_text  NVARCHAR(1000) = N'quarterly revenue forecast';
DECLARE @tenant_id   BIGINT = 42;
DECLARE @k           FLOAT = 60.0;

WITH vector_results AS (
    SELECT TOP 50
        dc.id,
        ROW_NUMBER() OVER (
            ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vec)
        ) AS vector_rank
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    WHERE d.tenant_id = @tenant_id
      AND d.is_active = 1
      AND dc.embedding IS NOT NULL
    ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vec)
),
fulltext_results AS (
    SELECT TOP 50
        dc.id,
        ROW_NUMBER() OVER (
            ORDER BY ft.[RANK] DESC
        ) AS text_rank
    FROM document_chunks dc
    JOIN documents d ON dc.document_id = d.id
    JOIN CONTAINSTABLE(document_chunks, content,
         @query_text) AS ft ON dc.id = ft.[KEY]
    WHERE d.tenant_id = @tenant_id
      AND d.is_active = 1
    ORDER BY ft.[RANK] DESC
),
rrf_scores AS (
    SELECT
        COALESCE(v.id, f.id) AS chunk_id,
        ISNULL(1.0 / (@k + v.vector_rank), 0) +
        ISNULL(1.0 / (@k + f.text_rank), 0)    AS rrf_score
    FROM vector_results v
    FULL OUTER JOIN fulltext_results f ON v.id = f.id
)
SELECT TOP 10
    rs.chunk_id,
    dc.content,
    dc.document_id,
    rs.rrf_score
FROM rrf_scores rs
JOIN document_chunks dc ON dc.id = rs.chunk_id
ORDER BY rs.rrf_score DESC;

    Note that SQL Server full-text search uses CONTAINSTABLE for ranked results rather than ts_rank_cd / @@. The [RANK] column from CONTAINSTABLE is SQL Server's term-frequency–based score on a 0–1000 scale, which you convert to a per-row rank for RRF using ROW_NUMBER().

    15.8 Observability: Measuring Retrieval Quality

    Retrieval quality is separate from LLM answer quality, and you need to measure both independently. The retrieval layer can fail in ways the LLM partially masks: if the wrong chunks are retrieved, the LLM may hallucinate, hedge, or answer a slightly different question. Catching this requires offline evaluation, not just watching whether users are satisfied.

    The standard offline metric is recall@k: for a set of labeled query-document pairs, what fraction of the ground-truth relevant documents appear in the top-k retrieved results? Build a small evaluation harness that runs against your production PostgreSQL instance:

    # eval/retrieval_eval.py
# Offline recall@k evaluation for the retrieval layer

import asyncio
import json
from dataclasses import dataclass
from pathlib import Path

from retrieval.client import RetrievalClient, RetrievalConfig


@dataclass
class EvalCase:
    query: str
    tenant_id: int
    relevant_chunk_ids: list[int]    # ground truth
    relevant_document_ids: list[int] # document-level ground truth


def load_eval_set(path: str) -> list[EvalCase]:
    """
    Load evaluation cases from a JSON file.
    Format:
    [
      {
        "query": "What is the refund policy?",
        "tenant_id": 1,
        "relevant_chunk_ids": [101, 102],
        "relevant_document_ids": [5]
      },
      ...
    ]
    """
    cases = []
    for item in json.loads(Path(path).read_text()):
        cases.append(EvalCase(**item))
    return cases


async def evaluate_recall(
    client: RetrievalClient,
    eval_cases: list[EvalCase],
    k_values: list[int] = (1, 3, 5, 10),
    min_similarity: float = 0.0,   # disable threshold for eval to see full ranking
) -> dict:
    results = {f"recall@{k}": [] for k in k_values}
    results["mrr"] = []   # mean reciprocal rank

    for case in eval_cases:
        config = RetrievalConfig(
            top_k=max(k_values),
            min_similarity=min_similarity,
        )
        chunks = await client.retrieve(case.query, case.tenant_id, config)
        retrieved_chunk_ids = [c.chunk_id for c in chunks]

        # recall@k: fraction of relevant chunks found in top k
        for k in k_values:
            top_k_ids = set(retrieved_chunk_ids[:k])
            relevant = set(case.relevant_chunk_ids)
            recall = len(top_k_ids & relevant) / len(relevant) if relevant else 0.0
            results[f"recall@{k}"].append(recall)

        # mean reciprocal rank: 1/rank of first relevant result
        rr = 0.0
        for rank, chunk_id in enumerate(retrieved_chunk_ids, start=1):
            if chunk_id in case.relevant_chunk_ids:
                rr = 1.0 / rank
                break
        results["mrr"].append(rr)

    # Aggregate
    summary = {}
    for metric, values in results.items():
        summary[metric] = round(sum(values) / len(values), 4) if values else 0.0

    return summary


async def main():
    import os
    from retrieval.client import create_retrieval_client

    client = await create_retrieval_client(
        postgres_dsn=os.environ["POSTGRES_DSN"],
        redis_url=os.environ["REDIS_URL"],
        openai_api_key=os.environ["OPENAI_API_KEY"],
    )

    eval_cases = load_eval_set("eval/cases.json")
    summary = await evaluate_recall(client, eval_cases)

    print(json.dumps(summary, indent=2))
    # Example output:
    # {
    #   "recall@1": 0.61,
    #   "recall@3": 0.78,
    #   "recall@5": 0.84,
    #   "recall@10": 0.91,
    #   "mrr": 0.69
    # }


if __name__ == "__main__":
    asyncio.run(main())

    Run this evaluation suite on a schedule (nightly, or after any schema or index change) and track the numbers over time. A drop in recall@5 after a schema migration or embedding model upgrade is a signal to investigate before it affects users in production.

    In addition to offline recall metrics, instrument your live retrieval with per-query observability stored back into PostgreSQL:

    -- Retrieval observability: log per-query metrics
CREATE TABLE retrieval_logs (
    id              BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    tenant_id       BIGINT NOT NULL,
    session_id      UUID,
    query_hash      CHAR(64) NOT NULL,  -- SHA-256 of query text
    query_preview   TEXT NOT NULL,      -- first 120 chars, safe to log
    top_k_requested INTEGER NOT NULL,
    results_count   INTEGER NOT NULL,
    top_similarity  FLOAT,
    min_similarity  FLOAT,
    embed_ms        FLOAT,
    query_ms        FLOAT,
    doc_types       TEXT[],
    tags_filter     TEXT[],
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_retrieval_logs_tenant_time
    ON retrieval_logs(tenant_id, created_at DESC);

CREATE INDEX idx_retrieval_logs_zero_results
    ON retrieval_logs(tenant_id, created_at DESC)
    WHERE results_count = 0;

    The partial index on results_count = 0 makes it cheap to query "what searches returned nothing?" — a high-value signal for identifying gaps in your corpus or overly aggressive similarity thresholds.

    Key Takeaways

  • → **Match the distance operator to your embedding model.** Most API-served embedding models produce L2-normalized vectors and are designed for cosine similarity; use `<=>` in pgvector and `VECTOR_DISTANCE('cosine', ...)` in Azure SQL. Using L2 distance on normalized vectors produces correct rankings but wastes compute and can mislead index configuration.
  • → **Pre-filter with relational predicates, not post-filter.** Applying `tenant_id`, `doc_type`, date range, and tag filters inside the `WHERE` clause before the vector ranking produces correct results at lower cost. Post-filtering after a vector scan risks missing relevant results when your top-k window is small.
  • → **Tune `ef_search` and `ivfflat.probes` per workload, not per table.** Real-time user-facing queries need low-latency settings; offline batch evaluation or RAG pipeline evaluation runs can trade latency for recall using `SET hnsw.ef_search = 200` within a session, without affecting other connections.
  • → **RRF hybrid search outperforms either vector or full-text ranking alone for keyword-heavy queries.** Combining pgvector cosine distance ranking with PostgreSQL full-text `ts_rank_cd` using Reciprocal Rank Fusion improves result quality on queries containing proper nouns, version numbers, or technical abbreviations that embedding models may not distinguish well.
  • → **Measure retrieval quality independently from LLM answer quality.** An LLM can sometimes produce plausible-sounding answers even when given partially wrong context, masking retrieval failures. Build and run a recall@k evaluation harness against labeled query-document pairs on a regular cadence so that index changes, model upgrades, or schema migrations don't silently degrade retrieval before users notice.
