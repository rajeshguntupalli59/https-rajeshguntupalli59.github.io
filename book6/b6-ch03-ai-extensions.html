Chapter 3: PostgreSQL Extensions That Enable AI: pgvector, pg_ai, pgml

PostgreSQL's extension architecture is one of its most underappreciated features — the ability to bolt new data types, operators, index strategies, and procedural languages directly into the engine without forking the codebase. For AI application builders, this means you don't need to bolt a separate vector database onto the side of your stack and then spend engineering cycles keeping it synchronized with your relational data. You can store embeddings next to the records they describe, run semantic search inside transactions, and call external ML models directly from SQL. This chapter covers the three extensions that matter most for production AI work: pgvector for embedding storage and similarity search, pg_ai for direct LLM integration from SQL, and pgml (PostgresML) for in-database model training and inference. By the end, you'll have working schema patterns, query strategies, and production-ready configurations for each.

---

3.1 pgvector: Embedding Storage and Similarity Search at the Relational Layer

pgvector is the extension that makes PostgreSQL a serious vector database. It adds a native vector data type, two ANN index types (IVFFlat and HNSW) — plus exact nearest-neighbor search via a plain sequential scan when no index is present — and a suite of distance operators that the query planner understands natively. The key insight is that embeddings live *with* their source data, not in a separate system.

#### Installing and Configuring pgvector

cd pgvector

sudo make install

# On macOS with Homebrew

# With Docker — use the official pgvector image
docker run -d \

  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=aiapp \

psql -U postgres -d aiapp -c "SELECT * FROM pg_extension WHERE extname = 'vector';"

#### Schema Design: Embedding Tables That Actually Work

The worst mistake teams make is creating a single generic embeddings table with a foreign key pointing everywhere. That design leads to unbounded scans and makes it impossible to enforce referential integrity meaningfully. Instead, co-locate embeddings with the data they represent, and use separate embedding tables only when you need to store multiple embedding models for the same content.

-- Enable required extensions
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;  -- for hybrid search

-- Core content table: product knowledge base
CREATE TABLE knowledge_articles (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    title           TEXT NOT NULL,
    body            TEXT NOT NULL,
    metadata        JSONB NOT NULL DEFAULT '{}',
    source_url      TEXT,
    published_at    TIMESTAMPTZ,
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    is_active       BOOLEAN NOT NULL DEFAULT true
);

-- Embedding table co-located with articles
-- Separate table allows multiple models per article
CREATE TABLE knowledge_article_embeddings (
    id              BIGSERIAL PRIMARY KEY,
    article_id      BIGINT NOT NULL REFERENCES knowledge_articles(id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,  -- denormalized for RLS performance
    model_name      TEXT NOT NULL,  -- 'text-embedding-3-small', 'text-embedding-3-large', etc.
    model_version   TEXT NOT NULL DEFAULT 'v1',
    embedding       vector(1536),   -- OpenAI text-embedding-3-small dimension
    chunk_index     INT NOT NULL DEFAULT 0,  -- for chunked documents
    chunk_text      TEXT NOT NULL,           -- store the chunk for retrieval
    token_count     INT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (article_id, model_name, model_version, chunk_index)
);

-- HNSW index: best for high-QPS production workloads
-- Build this after initial bulk load for speed
CREATE INDEX idx_article_embeddings_hnsw
    ON knowledge_article_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- IVFFlat index: better for very large datasets (10M+ vectors)
-- Requires knowing approximate row count at index creation time
-- CREATE INDEX idx_article_embeddings_ivfflat
--     ON knowledge_article_embeddings
--     USING ivfflat (embedding vector_cosine_ops)
--     WITH (lists = 100);  -- sqrt(row_count) is a good starting point

-- Supporting indexes for filtered similarity search
CREATE INDEX idx_article_embeddings_tenant
    ON knowledge_article_embeddings (tenant_id, model_name);

CREATE INDEX idx_article_embeddings_article
    ON knowledge_article_embeddings (article_id);

-- Full-text search index for hybrid search
CREATE INDEX idx_articles_fts
    ON knowledge_articles
    USING gin (to_tsvector('english', title || ' ' || body));

-- GIN index for metadata queries
CREATE INDEX idx_articles_metadata
    ON knowledge_articles USING gin (metadata);

-- Row-Level Security for multi-tenant isolation
ALTER TABLE knowledge_articles ENABLE ROW LEVEL SECURITY;
ALTER TABLE knowledge_article_embeddings ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_articles
    ON knowledge_articles
    USING (tenant_id = current_setting('app.tenant_id')::UUID);

CREATE POLICY tenant_isolation_embeddings
    ON knowledge_article_embeddings
    USING (tenant_id = current_setting('app.tenant_id')::UUID);

#### Similarity Search Patterns

pgvector supports three distance operators: <-> (L2/Euclidean), <#> (inner product — use negative for max similarity), and <=> (cosine distance). For normalized embeddings from OpenAI and Anthropic models, cosine distance is the right default.

-- Pure vector similarity search with tenant isolation
-- This is your baseline RAG retrieval query
SELECT
    kae.chunk_text,
    ka.title,
    ka.metadata,
    ka.source_url,
    1 - (kae.embedding <=> $1::vector) AS cosine_similarity
FROM knowledge_article_embeddings kae
JOIN knowledge_articles ka ON ka.id = kae.article_id
WHERE kae.tenant_id = $2::UUID
  AND kae.model_name = 'text-embedding-3-small'
  AND ka.is_active = true
  AND 1 - (kae.embedding <=> $1::vector) > 0.75  -- similarity threshold
ORDER BY kae.embedding <=> $1::vector
LIMIT 10;

-- Hybrid search: combine vector similarity with full-text ranking
-- This dramatically improves recall for keyword-heavy queries
WITH semantic_results AS (
    SELECT
        kae.article_id,
        kae.chunk_text,
        kae.chunk_index,
        1 - (kae.embedding <=> $1::vector) AS semantic_score
    FROM knowledge_article_embeddings kae
    WHERE kae.tenant_id = $3::UUID
      AND kae.model_name = 'text-embedding-3-small'
    ORDER BY kae.embedding <=> $1::vector
    LIMIT 50
),
fts_results AS (
    SELECT
        ka.id AS article_id,
        ts_rank_cd(
            to_tsvector('english', ka.title || ' ' || ka.body),
            plainto_tsquery('english', $2)
        ) AS fts_score
    FROM knowledge_articles ka
    WHERE ka.tenant_id = $3::UUID
      AND ka.is_active = true
      AND to_tsvector('english', ka.title || ' ' || ka.body)
          @@ plainto_tsquery('english', $2)
)
SELECT
    sr.chunk_text,
    ka.title,
    ka.source_url,
    ka.metadata,
    sr.semantic_score,
    COALESCE(fr.fts_score, 0) AS fts_score,
    -- Reciprocal Rank Fusion scoring
    (0.7 * sr.semantic_score + 0.3 * COALESCE(fr.fts_score, 0)) AS combined_score
FROM semantic_results sr
JOIN knowledge_articles ka ON ka.id = sr.article_id
LEFT JOIN fts_results fr ON fr.article_id = sr.article_id
ORDER BY combined_score DESC
LIMIT 10;

-- Metadata-filtered similarity search
-- The JSONB filter runs before the ANN scan via the planner
SELECT
    kae.chunk_text,
    ka.title,
    ka.metadata->>'category' AS category,
    1 - (kae.embedding <=> $1::vector) AS similarity
FROM knowledge_article_embeddings kae
JOIN knowledge_articles ka ON ka.id = kae.article_id
WHERE kae.tenant_id = $2::UUID
  AND kae.model_name = 'text-embedding-3-small'
  AND ka.metadata->>'category' = $3
  AND ka.metadata->>'language' = $4
  AND ka.published_at >= NOW() - INTERVAL '90 days'
ORDER BY kae.embedding <=> $1::vector
LIMIT 5;

-- Check that the HNSW index is being used
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT chunk_text, 1 - (embedding <=> '[0.1, 0.2, ...]'::vector) AS similarity
FROM knowledge_article_embeddings
WHERE tenant_id = 'some-uuid'::UUID
  AND model_name = 'text-embedding-3-small'
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;
-- Look for: "Index Scan using idx_article_embeddings_hnsw"
-- If you see Seq Scan, your WHERE clause is filtering too aggressively
-- for the planner to use the index — consider partial indexes per tenant

#### Tuning HNSW for Production

-- HNSW parameters control the accuracy/speed tradeoff
-- ef_search: higher = more accurate, slower. Default 40. Range: 10–500
SET hnsw.ef_search = 100;

-- For a session dedicated to high-accuracy retrieval:
SET hnsw.ef_search = 200;

-- For low-latency applications where approximate is fine:
SET hnsw.ef_search = 40;

-- Monitor index build progress (PostgreSQL 16+)
SELECT phase, blocks_done, blocks_total,
       round(100.0 * blocks_done / NULLIF(blocks_total, 0), 1) AS pct
FROM pg_stat_progress_create_index
WHERE relid = 'knowledge_article_embeddings'::regclass;

-- Measure actual recall quality against exact search
WITH exact AS (
    SELECT id, embedding <=> '[...]'::vector AS dist
    FROM knowledge_article_embeddings
    ORDER BY dist LIMIT 10
),
approx AS (
    SELECT id, embedding <=> '[...]'::vector AS dist
    FROM knowledge_article_embeddings
    ORDER BY dist LIMIT 10
)
SELECT
    COUNT(*) FILTER (WHERE e.id IN (SELECT id FROM approx)) AS recall_at_10
FROM exact e;

3.2 Embedding Generation: Connecting PostgreSQL to LLM APIs

The schema is ready. Now the question is how embeddings get created and stored. For production workloads, there are two patterns: synchronous generation at write time (for small volumes or interactive use cases), and async batch generation via Celery workers (for bulk ingestion and re-embedding when you change models).

# embedding_service.py
# Handles both OpenAI and Anthropic embeddings with automatic retry

import asyncio
import hashlib
import json
from typing import Optional
import asyncpg
import openai
import anthropic
import tiktoken
from tenacity import retry, stop_after_attempt, wait_exponential

# OpenAI client
oai_client = openai.AsyncOpenAI()

# Optional: Voyage AI client. Anthropic recommends Voyage AI as a
# third-party embeddings provider — Claude chat models do not expose
# an embeddings endpoint of their own, so a separate embedding model
# is required regardless of which LLM generates the final answer.
import voyageai
voyage_client = voyageai.AsyncClient()

CHUNK_SIZE = 512    # tokens per chunk
CHUNK_OVERLAP = 64  # token overlap between chunks

def chunk_text(text: str, model: str = "text-embedding-3-small") -> list[str]:
    """Split text into overlapping chunks respecting token boundaries."""
    enc = tiktoken.encoding_for_model(model)
    tokens = enc.encode(text)
    
    chunks = []
    start = 0
    while start < len(tokens):
        end = min(start + CHUNK_SIZE, len(tokens))
        chunk_tokens = tokens[start:end]
        chunks.append(enc.decode(chunk_tokens))
        if end == len(tokens):
            break
        start += CHUNK_SIZE - CHUNK_OVERLAP
    
    return chunks


@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10)
)
async def get_openai_embeddings(texts: list[str]) -> list[list[float]]:
    """Batch embed texts using OpenAI. Returns list of embedding vectors."""
    response = await oai_client.embeddings.create(
        model="text-embedding-3-small",
        input=texts,
        dimensions=1536
    )
    return [item.embedding for item in sorted(response.data, key=lambda x: x.index)]


async def embed_and_store_article(
    pool: asyncpg.Pool,
    article_id: int,
    tenant_id: str,
    title: str,
    body: str,
    model_name: str = "text-embedding-3-small"
) -> int:
    """
    Chunk an article, generate embeddings, and store them.
    Returns the number of chunks stored.
    
    This function is idempotent — running it twice replaces existing embeddings.
    """
    full_text = f"{title}\n\n{body}"
    chunks = chunk_text(full_text, model=model_name)
    
    if not chunks:
        return 0
    
    # Generate embeddings in a single API call (batch is much cheaper)
    embeddings = await get_openai_embeddings(chunks)
    
    enc = tiktoken.encoding_for_model(model_name)
    
    async with pool.acquire() as conn:
        # Use a transaction: either all chunks are stored or none
        async with conn.transaction():
            # Delete existing embeddings for this article + model
            await conn.execute(
                """
                DELETE FROM knowledge_article_embeddings
                WHERE article_id = $1 AND model_name = $2
                """,
                article_id, model_name
            )
            
            # Insert new chunks and embeddings
            await conn.executemany(
                """
                INSERT INTO knowledge_article_embeddings
                    (article_id, tenant_id, model_name, chunk_index, 
                     chunk_text, embedding, token_count)
                VALUES ($1, $2, $3, $4, $5, $6::vector, $7)
                """,
                [
                    (
                        article_id,
                        tenant_id,
                        model_name,
                        idx,
                        chunk,
                        json.dumps(embedding),  # asyncpg expects JSON for vector
                        len(enc.encode(chunk))
                    )
                    for idx, (chunk, embedding) in enumerate(zip(chunks, embeddings))
                ]
            )
    
    return len(chunks)


async def semantic_search(
    pool: asyncpg.Pool,
    query: str,
    tenant_id: str,
    limit: int = 5,
    similarity_threshold: float = 0.70,
    metadata_filter: Optional[dict] = None
) -> list[dict]:
    """
    Run semantic search over the knowledge base.
    Returns chunks with their source article metadata.
    """
    # Embed the query — single vector, not batched
    query_embedding = await get_openai_embeddings([query])
    embedding_vector = query_embedding[0]
    
    async with pool.acquire() as conn:
        # Set the tenant context for RLS
        await conn.execute(
            "SELECT set_config('app.tenant_id', $1, true)", tenant_id
        )
        
        if metadata_filter:
            rows = await conn.fetch(
                """
                SELECT
                    kae.chunk_text,
                    ka.title,
                    ka.source_url,
                    ka.metadata,
                    ka.published_at,
                    1 - (kae.embedding <=> $1::vector) AS similarity
                FROM knowledge_article_embeddings kae
                JOIN knowledge_articles ka ON ka.id = kae.article_id
                WHERE kae.tenant_id = $2::UUID
                  AND kae.model_name = 'text-embedding-3-small'
                  AND ka.is_active = true
                  AND ka.metadata @> $3::jsonb
                  AND 1 - (kae.embedding <=> $1::vector) > $4
                ORDER BY kae.embedding <=> $1::vector
                LIMIT $5
                """,
                json.dumps(embedding_vector),
                tenant_id,
                json.dumps(metadata_filter),
                similarity_threshold,
                limit
            )
        else:
            rows = await conn.fetch(
                """
                SELECT
                    kae.chunk_text,
                    ka.title,
                    ka.source_url,
                    ka.metadata,
                    ka.published_at,
                    1 - (kae.embedding <=> $1::vector) AS similarity
                FROM knowledge_article_embeddings kae
                JOIN knowledge_articles ka ON ka.id = kae.article_id
                WHERE kae.tenant_id = $2::UUID
                  AND kae.model_name = 'text-embedding-3-small'
                  AND ka.is_active = true
                  AND 1 - (kae.embedding <=> $1::vector) > $3
                ORDER BY kae.embedding <=> $1::vector
                LIMIT $4
                """,
                json.dumps(embedding_vector),
                tenant_id,
                similarity_threshold,
                limit
            )
        
        return [dict(row) for row in rows]

#### Async Batch Ingestion with Celery

# tasks/embedding_tasks.py
# Celery workers for bulk re-embedding when you upgrade models

from celery import Celery
import asyncpg
import asyncio
import logging
from embedding_service import embed_and_store_article

logger = logging.getLogger(__name__)

app = Celery(
    'embedding_tasks',
    broker='redis://localhost:6379/0',
    backend='redis://localhost:6379/1'
)

app.conf.update(
    task_serializer='json',
    result_serializer='json',
    accept_content=['json'],
    task_acks_late=True,           # Only ack after successful completion
    worker_prefetch_multiplier=1,  # One task at a time per worker (embedding is slow)
    task_reject_on_worker_lost=True,
)

DB_URL = "postgresql://aiapp:secret@localhost:5432/aiapp"


@app.task(bind=True, max_retries=3, default_retry_delay=30)
def embed_article_task(self, article_id: int, tenant_id: str):
    """Embed a single article. Called after insert/update."""
    async def _run():
        pool = await asyncpg.create_pool(DB_URL, min_size=1, max_size=3)
        try:
            # Fetch the article content
            async with pool.acquire() as conn:
                row = await conn.fetchrow(
                    "SELECT title, body FROM knowledge_articles WHERE id = $1",
                    article_id
                )
            
            if not row:
                logger.warning(f"Article {article_id} not found, skipping.")
                return
            
            chunks_stored = await embed_and_store_article(
                pool=pool,
                article_id=article_id,
                tenant_id=tenant_id,
                title=row['title'],
                body=row['body']
            )
            logger.info(f"Stored {chunks_stored} chunks for article {article_id}")
        finally:
            await pool.close()
    
    try:
        asyncio.run(_run())
    except Exception as exc:
        logger.error(f"Embedding task failed for article {article_id}: {exc}")
        raise self.retry(exc=exc)


@app.task
def bulk_reembed_tenant(tenant_id: str, model_name: str = "text-embedding-3-small"):
    """
    Re-embed all articles for a tenant — used when upgrading embedding models.
    Spawns individual tasks with rate limiting.
    """
    async def _get_article_ids():
        pool = await asyncpg.create_pool(DB_URL)
        async with pool.acquire() as conn:
            rows = await conn.fetch(
                "SELECT id FROM knowledge_articles WHERE tenant_id = $1 AND is_active = true",
                tenant_id
            )
        await pool.close()
        return [row['id'] for row in rows]
    
    article_ids = asyncio.run(_get_article_ids())
    logger.info(f"Re-embedding {len(article_ids)} articles for tenant {tenant_id}")
    
    # Dispatch individual tasks — Celery handles parallelism
    for article_id in article_ids:
        embed_article_task.apply_async(
            args=[article_id, tenant_id],
            countdown=0,
            retry=True
        )

3.3 pg_notify and Trigger-Based Embedding Pipelines

Polling for new content to embed is wasteful. PostgreSQL's LISTEN/NOTIFY mechanism gives you an event-driven approach: a trigger fires when content changes, publishes a notification, and your worker picks it up. This is how you build a real-time embedding pipeline without Kafka.

-- Trigger function: fires on INSERT/UPDATE to knowledge_articles
-- Sends a NOTIFY with article metadata as JSON payload
CREATE OR REPLACE FUNCTION notify_article_changed()
RETURNS TRIGGER AS $$
DECLARE
    payload JSONB;
BEGIN
    -- Only notify if the content actually changed (skip metadata-only updates)
    IF TG_OP = 'UPDATE' AND NEW.body = OLD.body AND NEW.title = OLD.title THEN
        RETURN NEW;
    END IF;
    
    payload = jsonb_build_object(
        'event',      TG_OP,
        'article_id', NEW.id,
        'tenant_id',  NEW.tenant_id::TEXT,
        'table',      TG_TABLE_NAME,
        'timestamp',  extract(epoch FROM now())
    );
    
    -- Channel name: 'article_embeddings'
    -- Payload size limit is 8000 bytes — keep it small (just IDs)
    PERFORM pg_notify('article_embeddings', payload::TEXT);
    
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach trigger to the articles table
CREATE TRIGGER trg_article_embedding_notify
    AFTER INSERT OR UPDATE ON knowledge_articles
    FOR EACH ROW
    EXECUTE FUNCTION notify_article_changed();

-- Soft-delete also needs to trigger cleanup
CREATE OR REPLACE FUNCTION notify_article_deleted()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.is_active = false AND OLD.is_active = true THEN
        PERFORM pg_notify(
            'article_embeddings',
            jsonb_build_object(
                'event',      'DELETE',
                'article_id', NEW.id,
                'tenant_id',  NEW.tenant_id::TEXT,
                'table',      TG_TABLE_NAME,
                'timestamp',  extract(epoch FROM now())
            )::TEXT
        );
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_article_soft_delete_notify
    AFTER UPDATE OF is_active ON knowledge_articles
    FOR EACH ROW
    EXECUTE FUNCTION notify_article_deleted();
# listeners/embedding_listener.py
# Async LISTEN loop — runs as a long-lived process alongside your app

import asyncio
import json
import logging
import signal
from typing import Optional
import asyncpg
from tasks.embedding_tasks import embed_article_task

logger = logging.getLogger(__name__)

DB_URL = "postgresql://aiapp:secret@localhost:5432/aiapp"


class EmbeddingPipelineListener:
    """
    Listens on the 'article_embeddings' NOTIFY channel and dispatches
    Celery tasks for changed articles.

    Design decisions:
    - Uses a single dedicated connection for LISTEN (not from the pool).
    - Reconnects automatically on connection loss.
    - Deduplicates rapid-fire notifications with a small in-memory buffer.
    """

    def __init__(self, channel: str = "article_embeddings"):
        self.channel = channel
        self.conn: Optional[asyncpg.Connection] = None
        self._running = False
        self._pending: set[int] = set()   # dedup buffer
        self._flush_interval = 2.0         # seconds between batch flushes

    async def connect(self):
        self.conn = await asyncpg.connect(DB_URL)
        await self.conn.add_listener(self.channel, self._handle_notification)
        logger.info(f"Listening on channel '{self.channel}'")

    async def disconnect(self):
        if self.conn:
            await self.conn.remove_listener(self.channel, self._handle_notification)
            await self.conn.close()
            self.conn = None

    def _handle_notification(self, connection, pid, channel, payload):
        """Called synchronously by asyncpg when a NOTIFY arrives."""
        try:
            data = json.loads(payload)
            event = data.get("event")
            article_id = data.get("article_id")
            tenant_id = data.get("tenant_id")

            if event in ("INSERT", "UPDATE"):
                self._pending.add((article_id, tenant_id))
            elif event == "DELETE":
                # Remove from pending if it was waiting; no embed needed
                self._pending.discard((article_id, tenant_id))
                logger.info(f"Article {article_id} soft-deleted; skipping embed")
        except (json.JSONDecodeError, KeyError) as e:
            logger.error(f"Malformed notification payload: {payload!r} — {e}")

    async def _flush_pending(self):
        """Dispatch Celery tasks for all pending articles."""
        if not self._pending:
            return
        
        to_process = list(self._pending)
        self._pending.clear()

        for article_id, tenant_id in to_process:
            embed_article_task.apply_async(
                args=[article_id, tenant_id],
                countdown=0
            )
            logger.info(f"Dispatched embed task for article {article_id}")

    async def run(self):
        """Main loop: maintain connection and flush pending notifications."""
        self._running = True
        
        while self._running:
            try:
                await self.connect()
                while self._running:
                    # asyncpg fires the callback in the background;
                    # we just need to keep the event loop alive and flush periodically
                    await asyncio.sleep(self._flush_interval)
                    await self._flush_pending()
            except (asyncpg.PostgresConnectionError, OSError) as e:
                logger.warning(f"Connection lost: {e} — reconnecting in 5s")
                await self.disconnect()
                await asyncio.sleep(5)
            except asyncio.CancelledError:
                break

        await self.disconnect()
        logger.info("Embedding pipeline listener shut down cleanly")

    def stop(self):
        self._running = False


async def main():
    listener = EmbeddingPipelineListener()

    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):
        loop.add_signal_handler(sig, listener.stop)

    await listener.run()


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    asyncio.run(main())

This listener process costs very little: it holds one idle connection and wakes every two seconds. Deploy it as a systemd service or a Kubernetes sidecar alongside your application.

graph LR
    A[INSERT/UPDATE knowledge_articles] --> B[Trigger: notify_article_changed]
    B --> C["pg_notify('article_embeddings', payload)"]
    C --> D[EmbeddingPipelineListener LISTEN]
    D --> E[Dedup buffer, flushed every ~2s]
    E --> F[Celery task: embed_article_task]
    F --> G[OpenAI embeddings API]
    G --> H[UPDATE knowledge_article_embeddings]

*A commit-triggered notification replaces polling: nothing runs until a row actually changes.*

3.4 pg_ai: Direct LLM Calls from SQL

pg_ai is a newer extension that embeds HTTP calls to LLM APIs (OpenAI, Anthropic, Ollama) directly into PostgreSQL functions. The idea is compelling: classification, summarization, and extraction become SQL operations you can compose with joins, CTEs, and triggers.

> When to use pg_ai vs. application-layer calls: pg_ai is excellent for offline batch enrichment — classifying rows, generating summaries on ingest, running nightly jobs. It is *not* a good choice for interactive request paths because each LLM call blocks a backend process and holds a database connection. Use application-layer async calls for anything user-facing.

  AND t.created_at >= NOW() - INTERVAL '1 hour';

#### Building an Automated Enrichment Pipeline with pg_ai

The real power comes from combining pg_ai with PostgreSQL's procedural capabilities — using it inside functions called by scheduled jobs or triggers.

-- Add enrichment columns to the articles table
ALTER TABLE knowledge_articles
    ADD COLUMN IF NOT EXISTS ai_summary      TEXT,
    ADD COLUMN IF NOT EXISTS ai_tags         TEXT[],
    ADD COLUMN IF NOT EXISTS ai_enriched_at  TIMESTAMPTZ;

-- Enrichment function: summarize + extract tags in one LLM call
CREATE OR REPLACE FUNCTION enrich_article(p_article_id BIGINT)
RETURNS VOID AS $$
DECLARE
    v_title      TEXT;
    v_body       TEXT;
    v_api_key    TEXT;
    v_response   JSONB;
    v_summary    TEXT;
    v_tags       TEXT[];
BEGIN
    -- Fetch content
    SELECT title, body INTO v_title, v_body
    FROM knowledge_articles
    WHERE id = p_article_id AND is_active = true;
    
    IF NOT FOUND THEN
        RAISE WARNING 'enrich_article: article % not found', p_article_id;
        RETURN;
    END IF;
    
    -- Fetch API key
    SELECT key_value INTO v_api_key
    FROM ai_secrets WHERE key_name = 'openai_api_key';
    
    -- Single LLM call: extract both summary and tags
    v_response := (
        ai.openai_chat_complete(
            model    => 'gpt-4o-mini',
            messages => ARRAY[
                ai.openai_chat_message('system',
                    'You are a knowledge base curator. Given an article, return a JSON object with: '
                    '"summary" (2-3 sentence summary), '
                    '"tags" (array of 3-7 lowercase keyword tags). '
                    'Return only valid JSON.'),
                ai.openai_chat_message('user',
                    'Title: ' || v_title || E'\n\nBody:\n' || LEFT(v_body, 3000))
            ],
            api_key => v_api_key
        ) ->> 'content'
    )::JSONB;
    
    v_summary := v_response->>'summary';
    
    -- Parse tags array from JSON
    SELECT array_agg(tag)
    INTO v_tags
    FROM jsonb_array_elements_text(v_response->'tags') AS tag;
    
    -- Update the article
    UPDATE knowledge_articles
    SET
        ai_summary     = v_summary,
        ai_tags        = v_tags,
        ai_enriched_at = NOW()
    WHERE id = p_article_id;

EXCEPTION WHEN OTHERS THEN
    RAISE WARNING 'enrich_article failed for article %: %', p_article_id, SQLERRM;
END;
$$ LANGUAGE plpgsql;

-- Scheduled batch enrichment: called by pg_cron or an external scheduler
CREATE OR REPLACE FUNCTION batch_enrich_articles(p_batch_size INT DEFAULT 20)
RETURNS INT AS $$
DECLARE
    v_count INT := 0;
    v_id    BIGINT;
BEGIN
    FOR v_id IN
        SELECT id
        FROM knowledge_articles
        WHERE ai_enriched_at IS NULL
          AND is_active = true
        ORDER BY created_at DESC
        LIMIT p_batch_size
    LOOP
        PERFORM enrich_article(v_id);
        v_count := v_count + 1;
    END LOOP;
    
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

#### A Note on pg_ai and SQL Server

For readers working in SQL Server environments, Microsoft's equivalent pathway is Azure SQL's external language runtimes and the sp_invoke_external_endpoint stored procedure (available in Azure SQL Managed Instance) or Extensibility Framework scripts via sp_execute_external_script. The functional pattern is the same — calling an HTTP endpoint from T-SQL — but the ergonomics differ significantly. Azure OpenAI Service integration is natively supported through Azure SQL's managed identity, which eliminates the credential-management problem. A comparable enrichment query in T-SQL looks like this:

-- SQL Server / Azure SQL: classify a support ticket via Azure OpenAI
-- Requires: Azure SQL Managed Instance, outbound network access enabled,
-- and a DATABASE SCOPED CREDENTIAL for the Azure OpenAI endpoint.

DECLARE @endpoint   NVARCHAR(MAX) = 
    'https://YOUR_RESOURCE.openai.azure.com/openai/deployments/gpt-4o-mini/chat/completions?api-version=2024-02-01';

DECLARE @payload    NVARCHAR(MAX) = N'{
  "messages": [
    {"role": "system", "content": "Classify the ticket as BILLING, TECHNICAL, ACCOUNT, FEATURE_REQUEST, or OTHER. Return only the category name."},
    {"role": "user",   "content": "Subject: Cannot login\n\nI have been locked out of my account for two days."}
  ],
  "max_tokens": 10
}';

DECLARE @response   NVARCHAR(MAX);

EXEC sp_invoke_external_endpoint
    @url        = @endpoint,
    @payload    = @payload,
    @credential = 'AzureOpenAICredential',
    @response   = @response OUTPUT;

SELECT JSON_VALUE(@response, '$.choices[0].message.content') AS ai_category;

The PostgreSQL pg_ai approach is more composable — you can use it inline in SELECT/UPDATE statements — whereas the SQL Server approach requires procedural T-SQL blocks. For batch enrichment at scale in Azure SQL, the recommended pattern is Azure Data Factory or a Fabric notebook pipeline rather than looping stored procedures.

3.5 pgml (PostgresML): In-Database Model Training and Inference

PostgresML takes a different approach from pg_ai. Where pg_ai makes HTTP calls to external APIs, pgml loads models *into the database process itself* — either trained inside PostgreSQL via scikit-learn and XGBoost bindings, or loaded from HuggingFace for transformer-based inference. This eliminates the network hop entirely.

#### Training a Classification Model Inside PostgreSQL

pgml's pgml.train() function takes a SQL query as its training dataset. The model lives in the pgml.models table and is callable via pgml.predict().

-- First, prepare a labeled training table
-- In a real project this comes from human-labeled historical data
CREATE TABLE support_ticket_labels AS
SELECT
    id,
    -- Feature engineering: extract numeric/categorical features
    length(body)                                           AS body_length,
    array_length(string_to_array(body, ' '), 1)           AS word_count,
    CASE WHEN body ~* '(invoice|charge|payment|refund|billing)'
         THEN 1 ELSE 0 END                                 AS has_billing_keyword,
    CASE WHEN body ~* '(error|crash|bug|broken|not working|fails)'
         THEN 1 ELSE 0 END                                 AS has_tech_keyword,
    CASE WHEN body ~* '(account|login|password|access|locked)'
         THEN 1 ELSE 0 END                                 AS has_account_keyword,
    ai_category                                            AS label  -- ground truth
FROM support_tickets
WHERE ai_category IS NOT NULL   -- labeled rows only
  AND ai_category != 'OTHER';   -- exclude ambiguous class for this demo

-- Train a gradient boosted classifier with pgml
-- pgml.train() returns a snapshot ID you can use to track model versions
SELECT pgml.train(
    project_name    => 'support_ticket_classifier',
    task            => 'classification',
    relation_name   => 'support_ticket_labels',
    y_column_name   => 'label',
    algorithm       => 'xgboost',
    hyperparams     => '{
        "n_estimators": 200,
        "max_depth": 6,
        "learning_rate": 0.1,
        "subsample": 0.8,
        "eval_metric": "mlogloss"
    }'::JSONB
);

-- Check model performance metrics
SELECT
    p.project_name,
    m.algorithm,
    m.status,
    s.metrics->>'f1'        AS f1_score,
    s.metrics->>'accuracy'  AS accuracy,
    s.created_at
FROM pgml.models m
JOIN pgml.projects p ON p.id = m.project_id
JOIN pgml.snapshots s ON s.id = m.snapshot_id
WHERE p.project_name = 'support_ticket_classifier'
ORDER BY s.created_at DESC
LIMIT 5;

-- Deploy the best model for production use
-- pgml.deploy() sets the active model for a project
SELECT pgml.deploy(
    project_name => 'support_ticket_classifier',
    strategy     => 'best_score',   -- picks highest F1 automatically
    algorithm    => 'xgboost'
);

-- Run inference: classify new tickets in SQL
SELECT
    t.id,
    t.subject,
    pgml.predict(
        project_name => 'support_ticket_classifier',
        features     => ARRAY[
            length(t.body)::FLOAT,
            array_length(string_to_array(t.body, ' '), 1)::FLOAT,
            CASE WHEN t.body ~* '(invoice|charge|payment|refund|billing)' THEN 1.0 ELSE 0.0 END,
            CASE WHEN t.body ~* '(error|crash|bug|broken|not working|fails)' THEN 1.0 ELSE 0.0 END,
            CASE WHEN t.body ~* '(account|login|password|access|locked)' THEN 1.0 ELSE 0.0 END
        ]
    ) AS predicted_category
FROM support_tickets t
WHERE t.ai_category IS NULL
LIMIT 100;

#### HuggingFace Transformer Inference with pgml

For tasks that need transformer-quality results without external API calls — on-premises deployments, sensitive data, low-latency requirements — pgml can load HuggingFace models directly:

-- Download and cache a sentence-transformer model for embedding generation
-- The model is stored on disk and loaded into shared memory on first use
SELECT pgml.load_dataset('pgml/review_classification');  -- example dataset

-- Generate embeddings using a locally-hosted sentence transformer
-- This replaces the OpenAI API call entirely — useful for air-gapped environments
SELECT
    id,
    title,
    pgml.embed(
        transformer => 'intfloat/e5-small-v2',   -- compact, fast model
        text        => title || ' ' || body,
        kwargs      => '{"normalize": true}'::JSONB
    ) AS local_embedding
FROM knowledge_articles
WHERE id = 42;

-- Zero-shot classification without API dependency
SELECT
    id,
    subject,
    pgml.transform(
        task        => '{
            "task": "zero-shot-classification",
            "model": "facebook/bart-large-mnli"
        }'::JSONB,
        inputs      => ARRAY[subject || ' ' || body],
        args        => '{
            "candidate_labels": ["billing", "technical", "account", "feature request"]
        }'::JSONB
    ) AS classification_result
FROM support_tickets
WHERE id = 101;

-- Sentiment analysis using a fine-tuned model
SELECT
    id,
    body,
    pgml.transform(
        task   => '{"task": "text-classification", "model": "distilbert-base-uncased-finetuned-sst-2-english"}'::JSONB,
        inputs => ARRAY[LEFT(body, 512)]  -- truncate to model max length
    )->0->>'label' AS sentiment,
    (pgml.transform(
        task   => '{"task": "text-classification", "model": "distilbert-base-uncased-finetuned-sst-2-english"}'::JSONB,
        inputs => ARRAY[LEFT(body, 512)]
    )->0->>'score')::FLOAT AS confidence
FROM support_tickets
WHERE id = 101;

#### pgml vs. pg_ai: Choosing the Right Tool

Both extensions solve the problem of AI inference from SQL, but they occupy different positions in the tradeoff space:

| Dimension | pgml | pg_ai |

|---|---|---|

| Inference location | Inside the PostgreSQL process | External API (HTTP) |

| Latency | Microseconds to low milliseconds | Network-bound (50–500ms typical) |

| Model variety | HuggingFace ecosystem + sklearn/XGBoost | Any LLM API (OpenAI, Anthropic, Ollama) |

| Frontier model access | No (open-weight models only) | Yes (GPT-4o, Claude 3.5, etc.) |

| Operational complexity | High (GPU/memory on DB host) | Low (stateless HTTP) |

| Data privacy | Data never leaves the database host | Data sent to external API |

| Training support | Yes (sklearn, XGBoost, LightGBM) | No |

| Best for | Embedding generation, classical ML, privacy-sensitive workloads | Enrichment, classification, summarization using frontier models |

A common production architecture uses both: pgml for high-volume, latency-sensitive embedding generation (replacing OpenAI API calls for embeddings), and pg_ai for occasional enrichment tasks that benefit from frontier model reasoning quality.

3.6 Putting It Together: A Complete RAG Pipeline on PostgreSQL

This section assembles the pieces into a production RAG pipeline. The architecture is: trigger-based embedding on ingest → HNSW similarity search → context assembly → LLM answer generation in the application layer.

-- Complete schema: ready for production RAG
-- Run this as a migration

BEGIN;

CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- Tenants
CREATE TABLE IF NOT EXISTS tenants (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name         TEXT NOT NULL,
    plan         TEXT NOT NULL DEFAULT 'free',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Knowledge base articles
CREATE TABLE IF NOT EXISTS knowledge_articles (
    id           BIGSERIAL PRIMARY KEY,
    tenant_id    UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    title        TEXT NOT NULL,
    body         TEXT NOT NULL,
    metadata     JSONB NOT NULL DEFAULT '{}',
    source_url   TEXT,
    ai_summary   TEXT,
    ai_tags      TEXT[],
    ai_enriched_at TIMESTAMPTZ,
    published_at TIMESTAMPTZ,
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_active    BOOLEAN NOT NULL DEFAULT TRUE
);

-- Embeddings
CREATE TABLE IF NOT EXISTS knowledge_article_embeddings (
    id            BIGSERIAL PRIMARY KEY,
    article_id    BIGINT NOT NULL REFERENCES knowledge_articles(id) ON DELETE CASCADE,
    tenant_id     UUID NOT NULL,
    model_name    TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    model_version TEXT NOT NULL DEFAULT 'v1',
    chunk_index   INT NOT NULL DEFAULT 0,
    chunk_text    TEXT NOT NULL,
    embedding     vector(1536),
    token_count   INT,

);

CREATE TABLE IF NOT EXISTS conversations (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,

CREATE TABLE IF NOT EXISTS conversation_messages (
    id              BIGSERIAL PRIMARY KEY,
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system')),
    content         TEXT NOT NULL,
    sources         JSONB,   -- array of article IDs used as context
    token_count     INT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Indexes
CREATE INDEX IF NOT EXISTS idx_kae_hnsw
    ON knowledge_article_embeddings
    USING hnsw (embedding vector_cosine_ops)

    ON knowledge_article_embeddings (tenant_id, model_name);

    USING (tenant_id = current_setting('app.tenant_id')::UUID);

        conversation_id IN (

-- Notify trigger
CREATE OR REPLACE FUNCTION notify_article_changed()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'UPDATE' AND NEW.body = OLD.body AND NEW.title = OLD.title THEN
        RETURN NEW;
    END IF;
    PERFORM pg_notify('article_embeddings',
        jsonb_build_object(
            'event',      TG_OP,
            'article_id', NEW.id,
            'tenant_id',  NEW.tenant_id::TEXT
        )::TEXT
    );
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_article_embedding_notify ON knowledge_articles;
CREATE TRIGGER trg_article_embedding_notify
    AFTER INSERT OR UPDATE ON knowledge_articles
    FOR EACH ROW EXECUTE FUNCTION notify_article_changed();

# rag_pipeline.py
# Complete RAG pipeline: retrieval + answer generation

import asyncio
import json
import uuid
from typing import Optional
import asyncpg
import openai

oai_client = openai.AsyncOpenAI()

SYSTEM_PROMPT = """You are a helpful support assistant. Answer the user's question 
using only the provided context. If the context does not contain enough information 
to answer the question, say so clearly. Do not make up information.

When you use information from a specific source, cite it naturally in your response."""


async def rag_answer(
    pool: asyncpg.Pool,
    tenant_id: str,
    user_id: str,
    question: str,
    conversation_id: Optional[str] = None,
    top_k: int = 5,
    similarity_threshold: float = 0.70
) -> dict:
    """
    Full RAG pipeline:
    1. Embed the question
    2. Retrieve relevant chunks
    3. Load conversation history
    4. Generate answer with citations
    5. Persist conversation turn

    Returns: {"answer": str, "sources": list, "conversation_id": str}
    """

    # Step 1: Embed the question
    embed_response = await oai_client.embeddings.create(
        model="text-embedding-3-small",
        input=[question],
        dimensions=1536
    )
    query_vector = embed_response.data[0].embedding

    async with pool.acquire() as conn:
        # Set tenant context for RLS
        await conn.execute(
            "SELECT set_config('app.tenant_id', $1, true)", tenant_id
        )

        # Step 2: Retrieve relevant chunks (hybrid search)
        chunks = await conn.fetch(
            """
            WITH semantic AS (
                SELECT
                    kae.chunk_text,
                    kae.article_id,
                    ka.title,
                    ka.source_url,
                    ka.metadata,
                    1 - (kae.embedding <=> $1::vector) AS semantic_score
                FROM knowledge_article_embeddings kae
                JOIN knowledge_articles ka ON ka.id = kae.article_id
                WHERE kae.tenant_id = $2::UUID
                  AND kae.model_name = 'text-embedding-3-small'
                  AND ka.is_active = true
                  AND 1 - (kae.embedding <=> $1::vector) > $3
                ORDER BY kae.embedding <=> $1::vector
                LIMIT $4
            )
            SELECT
                chunk_text,
                article_id,
                title,
                source_url,
                metadata,
                semantic_score
            FROM semantic
            ORDER BY semantic_score DESC
            """,
            json.dumps(query_vector),
            tenant_id,
            similarity_threshold,
            top_k
        )

        # Step 3: Load or create conversation
        if conversation_id:
            history = await conn.fetch(
                """
                SELECT role, content
                FROM conversation_messages
                WHERE conversation_id = $1
                ORDER BY created_at
                LIMIT 20
                """,
                uuid.UUID(conversation_id)
            )
        else:
            # Create a new conversation
            conv_row = await conn.fetchrow(
                """
                INSERT INTO conversations (tenant_id, user_id)
                VALUES ($1::UUID, $2)
                RETURNING id
                """,
                tenant_id, user_id
            )
            conversation_id = str(conv_row['id'])
            history = []

    # Step 4: Assemble context and build message list
    context_parts = []
    sources = []
    seen_articles = set()

    for chunk in chunks:
        context_parts.append(
            f"[Source: {chunk['title']}]\n{chunk['chunk_text']}"
        )
        if chunk['article_id'] not in seen_articles:
            sources.append({
                "article_id": chunk['article_id'],
                "title": chunk['title'],
                "source_url": chunk['source_url'],
                "score": round(chunk['semantic_score'], 4)
            })
            seen_articles.add(chunk['article_id'])

    context_block = "\n\n---\n\n".join(context_parts) if context_parts else \
        "No relevant documents found in the knowledge base."

    messages = [{"role": "system", "content": SYSTEM_PROMPT}]

    # Include conversation history for multi-turn coherence
    for msg in history:
        messages.append({"role": msg['role'], "content": msg['content']})

    # Inject retrieved context into the final user message
    messages.append({
        "role": "user",
        "content": (
            f"Context from knowledge base:\n\n{context_block}"
            f"\n\n---\n\nQuestion: {question}"
        )
    })

    # Step 5: Generate the answer
    completion = await oai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
        temperature=0.2,
        max_tokens=800
    )
    answer = completion.choices[0].message.content
    total_tokens = completion.usage.total_tokens

    # Step 6: Persist the conversation turn
    async with pool.acquire() as conn:
        await conn.execute(
            "SELECT set_config('app.tenant_id', $1, true)", tenant_id
        )
        await conn.executemany(
            """
            INSERT INTO conversation_messages
                (conversation_id, role, content, sources, token_count)
            VALUES ($1, $2, $3, $4, $5)
            """,
            [
                (
                    uuid.UUID(conversation_id), 'user',
                    question, None, None
                ),
                (
                    uuid.UUID(conversation_id), 'assistant',
                    answer, json.dumps(sources), total_tokens
                ),
            ]
        )

        # Update conversation activity timestamp
        await conn.execute(
            """
            UPDATE conversations
            SET last_activity = NOW()
            WHERE id = $1
            """,
            uuid.UUID(conversation_id)
        )

    return {
        "answer": answer,
        "sources": sources,
        "conversation_id": conversation_id,
        "tokens_used": total_tokens,
        "chunks_retrieved": len(chunks)
    }

3.7 Observability and Performance Monitoring

Production RAG systems need observability at the database layer, not just at the application layer. PostgreSQL gives you what you need natively.

-- Enable pg_stat_statements to track query performance
-- Add to postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 slowest queries involving vector similarity
SELECT
    LEFT(query, 100)             AS query_snippet,
    calls,
    round(mean_exec_time::NUMERIC, 2)  AS mean_ms,
    round(total_exec_time::NUMERIC, 2) AS total_ms,
    round(stddev_exec_time::NUMERIC, 2) AS stddev_ms,
    rows / NULLIF(calls, 0)     AS avg_rows
FROM pg_stat_statements
WHERE query ILIKE '%<=>%'   -- cosine distance operator
   OR query ILIKE '%<->%'   -- L2 distance operator
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Monitor HNSW index usage vs. sequential scans
SELECT
    schemaname,
    relname                         AS table_name,
    indexrelname                    AS index_name,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    seq_scan,
    seq_tup_read
FROM pg_stat_user_indexes psi
JOIN pg_stat_user_tables pst USING (relid)
WHERE indexrelname LIKE '%hnsw%'
   OR indexrelname LIKE '%ivfflat%';

-- Connection pool health
SELECT
    state,
    wait_event_type,
    wait_event,
    COUNT(*) AS connections
FROM pg_stat_activity
WHERE datname = current_database()
GROUP BY state, wait_event_type, wait_event
ORDER BY connections DESC;

-- Embedding table bloat check (important for high-churn datasets)
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
    last_vacuum,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE relname LIKE '%embedding%'
ORDER BY n_dead_tup DESC;

-- Trigger VACUUM ANALYZE on the embeddings table if dead_pct is high
-- VACUUM ANALYZE knowledge_article_embeddings;

-- Track RAG query latencies at the application level
-- Store these in a dedicated table for dashboard queries
CREATE TABLE IF NOT EXISTS rag_query_log (
    id                BIGSERIAL PRIMARY KEY,
    tenant_id         UUID NOT NULL,
    conversation_id   UUID,
    query_text        TEXT NOT NULL,
    chunks_retrieved  INT,
    similarity_scores FLOAT[],
    llm_model         TEXT NOT NULL,
    tokens_used       INT,
    latency_embed_ms  INT,     -- time to embed the query
    latency_search_ms INT,     -- time for vector search
    latency_llm_ms    INT,     -- time for LLM response
    latency_total_ms  INT,     -- end-to-end
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_rag_log_tenant_created
    ON rag_query_log (tenant_id, created_at DESC);

-- Query latency percentiles — use for SLO tracking
SELECT
    date_trunc('hour', created_at)                         AS hour,
    COUNT(*)                                               AS queries,
    round(percentile_cont(0.50) WITHIN GROUP
        (ORDER BY latency_total_ms)::NUMERIC, 0)           AS p50_ms,
    round(percentile_cont(0.95) WITHIN GROUP
        (ORDER BY latency_total_ms)::NUMERIC, 0)           AS p95_ms,
    round(percentile_cont(0.99) WITHIN GROUP
        (ORDER BY latency_total_ms)::NUMERIC, 0)           AS p99_ms,
    round(AVG(chunks_retrieved)::NUMERIC, 1)               AS avg_chunks,
    round(AVG(tokens_used)::NUMERIC, 0)                    AS avg_tokens
FROM rag_query_log
WHERE created_at >= NOW() - INTERVAL '24 hours'
  AND tenant_id = 'your-tenant-uuid'::UUID
GROUP BY hour
ORDER BY hour;

3.8 Common Pitfalls and How to Avoid Them

Pitfall 1: The HNSW index isn't being used

The most common cause is an overly restrictive WHERE clause. When the planner estimates that the filter will return a small fraction of rows, it switches to a sequential scan. Two fixes: (a) create partial indexes per tenant to reduce cardinality, or (b) use SET enable_seqscan = off temporarily to confirm the issue, then rebuild the query plan around the index.

-- Partial index per tenant: helps planner choose the HNSW index
CREATE INDEX idx_kae_hnsw_tenant_a
    ON knowledge_article_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE tenant_id = 'tenant-uuid-here'::UUID
      AND model_name = 'text-embedding-3-small';

Pitfall 2: Embedding dimensions don't match the index

If you switch embedding models (e.g., from 1536-dimensional OpenAI embeddings to 768-dimensional ones), the vector column dimension must change. This requires dropping the column, recreating it with the new dimension, and rebuilding the index. Plan model migrations carefully — they require a backfill of all existing content.

-- Add a new column for the larger model; don't alter the existing one
-- This avoids a full table rewrite and allows gradual migration
ALTER TABLE knowledge_article_embeddings
    ADD COLUMN embedding_large vector(3072);  -- text-embedding-3-large

-- After backfill, build a second HNSW index
CREATE INDEX idx_kae_hnsw_large
    ON knowledge_article_embeddings
    USING hnsw (embedding_large vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

Pitfall 3: pg_ai blocking connections under load

Each pg_ai call holds a PostgreSQL backend connection open for the duration of the LLM API call. A single slow OpenAI request can block a connection for several seconds. Under concurrent load this exhausts the connection pool. Mitigate this by running pg_ai enrichment through a dedicated connection pool with aggressive timeouts, or by moving enrichment entirely to the application layer with async HTTP clients.

-- Set statement_timeout for pg_ai-heavy sessions
-- Prevents runaway LLM calls from holding connections indefinitely
SET statement_timeout = '30s';

-- Or set at the role level for the enrichment service account
ALTER ROLE enrichment_worker SET statement_timeout = '30s';

Pitfall 4: Similarity threshold too high or too low

A threshold of 0.9 sounds safe but will miss relevant results when query phrasing differs from document phrasing. A threshold of 0.5 lets in too much noise. The right value depends on your embedding model and content domain. Calibrate by running offline evaluation: embed 50–100 representative queries, retrieve with no threshold, and manually label which results are relevant. Plot precision-recall curves across threshold values and pick the point that meets your quality bar.

Pitfall 5: Not chunking long documents

Embedding a 10,000-word article as a single vector produces a representation that is too diluted to match specific queries. A query about a detail in paragraph 47 will score poorly against a vector representing the entire article. Always chunk, and store the chunk text alongside the embedding so you can return the exact passage.

Key Takeaways

  • → **pgvector co-locates embeddings with relational data**, eliminating synchronization overhead and enabling transactionally consistent semantic search. Use HNSW indexes for high-QPS production workloads and IVFFlat for datasets exceeding tens of millions of vectors.
  • → **Hybrid search — combining pgvector cosine similarity with PostgreSQL full-text search — outperforms pure vector search** for keyword-rich or domain-specific queries. The Reciprocal Rank Fusion scoring pattern is a practical starting point for weighting the two signals.
  • → **pg_ai is best suited for offline batch enrichment** (classification, summarization, tag extraction) where you want LLM capabilities expressed as SQL. It is not appropriate for synchronous user-facing paths because each call holds a database backend connection open for the duration of the API request.
  • → **pgml trades operational complexity for latency and data privacy**: transformer inference runs inside the PostgreSQL process, eliminating the network round-trip and keeping data on-premise — at the cost of requiring GPU or high-memory compute on the database host.
  • → **Observability belongs in the database layer**: tracking vector index usage, embedding table bloat, and per-query latency percentiles in `pg_stat_statements` and a dedicated query log table gives you the signal you need to tune retrieval quality and catch regressions before users do.
