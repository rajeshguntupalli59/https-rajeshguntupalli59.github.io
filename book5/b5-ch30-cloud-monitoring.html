Chapter 30: Monitoring Cloud Databases: CloudWatch, Azure Monitor, Cloud Logging

Cloud-managed databases remove your access to the operating system, which means the monitoring stack you built around top, iostat, pg_stat_activity, and custom Nagios checks no longer has a foundation to stand on. The platform now owns the infrastructure layer, and you must rebuild your observability posture using the native tooling each cloud provider offers. This chapter walks through CloudWatch for AWS RDS and Aurora, Azure Monitor for Azure SQL and Elastic Pools, and Cloud Logging and Cloud Monitoring for Google Cloud SQL and AlloyDB. For each platform, you will learn how to configure metrics collection, set meaningful alert thresholds grounded in production experience, build dashboards that surface what matters, and avoid the most common instrumentation gaps that cause DBAs to miss incidents until users are already calling.

---

30.1 What You Lost and What You Gained: Monitoring Philosophy for Managed Databases

On-premises PostgreSQL and SQL Server gave you unrestricted access. You could run sar -u 1 10 to sample CPU across ten seconds, attach perf to the Postgres process, read /proc/meminfo for exact memory pressure, and correlate all of it with pg_stat_bgwriter in the same terminal session. The trade-off for managed databases is real: you cannot SSH into an RDS instance, you cannot inspect /var/log/postgresql/ directly, and you cannot run top on the underlying host.

What you gain in exchange is a pre-wired telemetry pipeline. CloudWatch, Azure Monitor, and Google Cloud Monitoring collect dozens of metrics automatically from the moment the instance starts, with no agent installation, no scrape configuration, and no storage management for the metric data itself. The platform also exposes metrics that would have been difficult or impossible to capture yourself — RDS Enhanced Monitoring samples OS-level statistics at one-second intervals using an agent that runs inside the managed environment, which is more granular than most self-managed deployments bother to configure.

The mental model shift is this: you are moving from pull-based, CLI-driven observation to push-based, subscription-driven alerting. Instead of checking the server, you define what matters and let the platform tell you when thresholds are crossed. This demands that you know your thresholds before an incident, not during one.

The four signal categories you must cover on any cloud database platform:

| Signal | Managed equivalent | What it replaces |

|--------|-------------------|-----------------|

| CPU and OS resource | CloudWatch, Azure Metrics, Cloud Monitoring | top, vmstat, sar |

| Storage and I/O | Platform metrics + Performance Insights | iostat, df, storage vendor tools |

| Query-level performance | Performance Insights, Query Store, Query Insights | pg_stat_statements, Profiler traces |

| Replication and HA state | Platform events, replica lag metrics | pg_stat_replication, AlwaysOn DMVs |

A note on metric resolution and cost. All three platforms charge for high-resolution metrics and extended retention beyond a free tier — CloudWatch bills per metric beyond an initial free allotment, Azure Monitor bills on ingested log volume, and Cloud Monitoring bills per custom metric beyond a free byte threshold. Check current pricing for your account before enabling maximum-resolution monitoring across a large fleet; the bill scales directly with instance count and metric cardinality.

30.2 CloudWatch: Monitoring AWS RDS and Aurora in Production

CloudWatch is the primary observability surface for RDS and Aurora. It collects standard metrics at one-minute intervals automatically, and at ten-second intervals when Enhanced Monitoring is enabled on the instance. Performance Insights sits alongside CloudWatch and provides query-level attribution. Understanding which tool answers which question saves considerable time during incidents.

Standard RDS CloudWatch metrics and their production thresholds:

| Metric | Namespace | Healthy range (general guidance) |

|--------|-----------|----------------------------------|

| CPUUtilization | AWS/RDS | Sustained < 75%; alert at 85% for 5 min |

| FreeStorageSpace | AWS/RDS | Alert when < 10% of allocated storage |

| DatabaseConnections | AWS/RDS | Alert at 80% of max_connections |

| ReadLatency / WriteLatency | AWS/RDS | Alert > 20 ms for OLTP workloads |

| ReplicaLag | AWS/RDS | Alert > 30 seconds for read replicas |

| AuroraReplicaLag | AWS/RDS | Alert > 100 ms for Aurora replicas |

| Deadlocks | AWS/RDS | Alert on any sustained increase |

| FreeableMemory | AWS/RDS | Alert when < 256 MB on db.r6g.large |

ReplicaLag for standard RDS read replicas is a physical replication metric measured in seconds. Aurora's AuroraReplicaLag is fundamentally different — it measures how far behind an Aurora replica is in applying redo log pages to its local buffer cache from the shared storage layer, and it is usually measured in single-digit milliseconds. Do not apply the same alert threshold to both.

Enabling Enhanced Monitoring and Performance Insights via AWS CLI:

# Enable Enhanced Monitoring (1-second granularity) and Performance Insights
# on an existing RDS instance. The monitoring role must exist first.

# Step 1: Create the Enhanced Monitoring IAM role if it doesn't exist
aws iam create-role \
  --role-name rds-monitoring-role \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": { "Service": "monitoring.rds.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }]
  }'

aws iam attach-role-policy \
  --role-name rds-monitoring-role \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonRDSEnhancedMonitoringRole

# Step 2: Modify the instance to enable both features
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --monitoring-interval 1 \
  --monitoring-role-arn arn:aws:iam::123456789012:role/rds-monitoring-role \
  --enable-performance-insights \
  --performance-insights-retention-period 731 \
  --performance-insights-kms-key-id alias/aws/rds \
  --apply-immediately

# Step 3: Verify the configuration
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].{
    MonitoringInterval: MonitoringInterval,
    PIEnabled: PerformanceInsightsEnabled,
    PIRetention: PerformanceInsightsRetentionPeriod
  }'

Performance Insights retention of 731 days (two years) is the maximum. The default is 7 days free; anything beyond that is billed per vCPU-hour of retained history, and the cost scales with both instance size and how far back you extend the window. For a large multi-vCPU instance, two-year retention is a meaningful recurring line item — check current Performance Insights pricing and budget for it explicitly before enabling extended retention fleet-wide.

Creating a CloudWatch alarm for connection saturation:

# Alert when DatabaseConnections exceeds 80% of max_connections.
# The default max_connections value is derived from instance memory and
# varies by instance class — always verify the actual value from your
# Parameter Group before calculating this threshold; do not assume a
# stock number.

aws cloudwatch put-metric-alarm \
  --alarm-name "rds-prod-postgres-01-connection-saturation" \
  --alarm-description "RDS connections above 80% of max_connections" \
  --metric-name DatabaseConnections \
  --namespace AWS/RDS \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-01 \
  --statistic Average \
  --period 60 \
  --evaluation-periods 3 \
  --threshold "${CONNECTION_ALARM_THRESHOLD}" \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:prod-db-alerts \
  --ok-actions arn:aws:sns:us-east-1:123456789012:prod-db-alerts \
  --treat-missing-data notBreaching

# Retrieve current max_connections from the parameter group
aws rds describe-db-parameters \
  --db-parameter-group-name prod-postgres15-params \
  --query 'Parameters[?ParameterName==`max_connections`].{Name:ParameterName,Value:ParameterValue}'

One gotcha with DatabaseConnections: RDS Parameter Groups compute max_connections dynamically based on instance memory by default (LEAST({DBInstanceClassMemory/9531392}, 5000)). When you resize an instance, max_connections changes silently. If you hardcode alarm thresholds, they become wrong after a resize. Build automation to recalculate thresholds whenever an instance class changes, or use a CloudWatch metric math expression that accounts for the dynamic value.

Querying Performance Insights for top wait events using Python:

import boto3
from datetime import datetime, timedelta, timezone

def get_top_waits(db_instance_id: str, region: str = "us-east-1", minutes: int = 60):
    """
    Retrieve top wait events from Performance Insights for the last N minutes.
    Equivalent to querying pg_stat_activity for wait_event_type in PostgreSQL.
    """
    pi = boto3.client("pi", region_name=region)
    rds = boto3.client("rds", region_name=region)

    # PI requires the DbiResourceId, not the instance identifier
    response = rds.describe_db_instances(DBInstanceIdentifier=db_instance_id)
    resource_id = response["DBInstances"][0]["DbiResourceId"]

    end_time = datetime.now(timezone.utc)
    start_time = end_time - timedelta(minutes=minutes)

    response = pi.get_resource_metrics(
        ServiceType="RDS",
        Identifier=resource_id,
        StartTime=start_time,
        EndTime=end_time,
        PeriodInSeconds=60,
        MetricQueries=[
            {
                "Metric": "db.load.avg",
                "GroupBy": {
                    "Group": "db.wait_event",
                    "Dimensions": ["db.wait_event.name", "db.wait_event.type"],
                    "Limit": 10,
                },
            }
        ],
    )

    print(f"\nTop wait events for {db_instance_id} (last {minutes} minutes):\n")
    print(f"{'Wait Event':<45} {'Type':<20} {'Avg DB Load':>12}")
    print("-" * 80)

    for result in response.get("MetricList", []):
        for key_dim in result.get("DataPoints", []):
            pass  # We want the grouped keys

    # The grouped response structure differs — use Keys endpoint
    keys_response = pi.get_resource_metadata(
        ServiceType="RDS",
        Identifier=resource_id,
    )

    # Simpler approach: get dimension keys directly
    dim_response = pi.describe_dimension_keys(
        ServiceType="RDS",
        Identifier=resource_id,
        StartTime=start_time,
        EndTime=end_time,
        PeriodInSeconds=3600,
        Metric="db.load.avg",
        GroupBy={
            "Group": "db.wait_event",
            "Dimensions": ["db.wait_event.name", "db.wait_event.type"],
            "Limit": 10,
        },
    )

    for key in dim_response.get("Keys", []):
        wait_name = key["Dimensions"].get("db.wait_event.name", "unknown")
        wait_type = key["Dimensions"].get("db.wait_event.type", "unknown")
        avg_load = key.get("Total", 0)
        print(f"{wait_name:<45} {wait_type:<20} {avg_load:>12.4f}")

    return dim_response

if __name__ == "__main__":
    results = get_top_waits("prod-postgres-01", region="us-east-1", minutes=60)

The output maps directly to what you would see in pg_stat_activity.wait_event and wait_event_type. If LWLock:buffer_mapping appears at the top, your buffer pool is under pressure. If IO:DataFileRead dominates, your working set exceeds buffer pool capacity. The interpretation is identical to on-premises; only the collection mechanism differs.

Aurora-specific metrics worth explicit attention:

Aurora exposes metrics standard RDS does not. AuroraVolumeBytesLeftTotal tracks remaining capacity in the Aurora cluster volume. The cluster volume grows in 10 GB increments and supports up to 128 TB, but it does not shrink automatically. BufferCacheHitRatio for Aurora should stay above 99.9% for OLTP; if it drops below 99%, you are seeing genuine I/O latency against the distributed storage layer. CommitLatency and DDLLatency are Aurora-specific metrics that have no direct CloudWatch equivalent in standard RDS.

30.3 Azure Monitor: Metrics, Diagnostics, and Log Analytics for Azure SQL

Azure Monitor is a unified observability platform that covers Azure SQL Database, Managed Instances, and Elastic Pools through two distinct systems: Metrics (pre-aggregated, 93-day retention, low cost) and Diagnostic Logs (raw records streamed to a Log Analytics Workspace, Storage Account, or Event Hub, with cost proportional to data volume).

The equivalent of CloudWatch Enhanced Monitoring is the Intelligent Performance blade in the Azure portal, which surfaces Query Store data through the Query Performance Insight interface. The equivalent of Performance Insights is the sys.dm_exec_query_stats and sys.query_store_* views in Azure SQL, which remain accessible because Azure SQL gives you T-SQL access to DMVs — a significant advantage over RDS if you come from a SQL Server background.

Core Azure SQL metrics and alert thresholds:

| Metric name | Alert threshold (OLTP) | Notes |

|-------------|------------------------|-------|

| cpu_percent | > 80% for 5 minutes | Based on DTU or vCore allocation |

| storage_percent | > 85% | Alert well before 100% — autogrow is not automatic |

| connection_failed | > 10 per minute | Indicates authentication or firewall issues |

| deadlock | Any increase > baseline | Query Store records the deadlock graph |

| dtu_consumption_percent | > 85% | DTU model only — consider vCore if consistently high |

| workers_percent | > 80% | Maximum worker threads; hitting 100% causes errors |

| log_write_percent | > 90% | Indicates log I/O becoming a bottleneck |

Configuring Diagnostic Settings to stream metrics to Log Analytics:

# Prerequisites: Log Analytics Workspace already created
# Retrieve the workspace resource ID
WORKSPACE_ID=$(az monitor log-analytics workspace show \
  --resource-group prod-rg \
  --workspace-name prod-db-logs \
  --query id \
  --output tsv)

# Get the Azure SQL Database resource ID
DB_RESOURCE_ID=$(az sql db show \
  --resource-group prod-rg \
  --server prod-sql-server-01 \
  --name prod-appdb \
  --query id \
  --output tsv)

# Enable all diagnostic categories to Log Analytics
# SQLInsights includes query-level data from Query Store
# AutomaticTuning includes index recommendation events
# QueryStoreRuntimeStatistics is the most valuable for query troubleshooting
az monitor diagnostic-settings create \
  --name "prod-appdb-diagnostics" \
  --resource "$DB_RESOURCE_ID" \
  --workspace "$WORKSPACE_ID" \
  --logs '[
    {"category": "SQLInsights", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "AutomaticTuning", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "QueryStoreRuntimeStatistics", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "QueryStoreWaitStatistics", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "Errors", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "DatabaseWaitStatistics", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "Deadlocks", "enabled": true, "retentionPolicy": {"enabled": false}},
    {"category": "Blocks", "enabled": true, "retentionPolicy": {"enabled": false}}
  ]' \
  --metrics '[
    {"category": "Basic", "enabled": true},
    {"category": "InstanceAndAppAdvanced", "enabled": true}
  ]'

# Verify the diagnostic setting
az monitor diagnostic-settings list \
  --resource "$DB_RESOURCE_ID" \
  --query '[].{Name:name, Workspace:workspaceId}' \
  --output table

There is a meaningful delay between enabling Diagnostic Settings and data appearing in Log Analytics — typically 5 to 15 minutes. Do not assume the feature is broken if the workspace shows no data immediately after configuration. Also note that enabling diagnostic settings on an Elastic Pool is separate from enabling them on each database within the pool. The pool-level settings cover pool resource metrics (eDTUs, storage); per-database settings cover query-level telemetry.

Querying Log Analytics with KQL for wait statistics:

# Run a KQL query against the Log Analytics Workspace to find top wait types
# over the last 24 hours — equivalent to querying sys.dm_os_wait_stats
# on an on-premises SQL Server instance

az monitor log-analytics query \
  --workspace "$WORKSPACE_ID" \
  --analytics-query '
AzureDiagnostics
| where ResourceType == "DATABASES"
| where Category == "DatabaseWaitStatistics"
| where TimeGenerated > ago(24h)
| where Resource == "PROD-APPDB"
| summarize
    TotalWaitTime_ms = sum(delta_wait_time_ms_d),
    AvgWaitTime_ms = avg(delta_wait_time_ms_d),
    SampleCount = count()
    by wait_type_s
| sort by TotalWaitTime_ms desc
| take 15
| project
    WaitType = wait_type_s,
    TotalWait_Seconds = round(TotalWaitTime_ms / 1000.0, 1),
    AvgWait_ms = round(AvgWaitTime_ms, 2),
    Samples = SampleCount
' \
  --timespan P1D \
  --output table

# Find the top 10 CPU-consuming queries from Query Store via Log Analytics
az monitor log-analytics query \
  --workspace "$WORKSPACE_ID" \
  --analytics-query '
AzureDiagnostics
| where Category == "QueryStoreRuntimeStatistics"
| where TimeGenerated > ago(6h)
| where Resource == "PROD-APPDB"
| summarize
    TotalCPU_ms = sum(cpu_time_d),
    TotalDuration_ms = sum(duration_d),
    ExecutionCount = sum(count_executions_d),
    AvgLogicalReads = avg(avg_logical_io_reads_d)
    by query_hash_s, query_id_d
| sort by TotalCPU_ms desc
| take 10
| project
    QueryID = query_id_d,
    QueryHash = query_hash_s,
    TotalCPU_seconds = round(TotalCPU_ms / 1000000.0, 2),
    Executions = ExecutionCount,
    AvgLogicalReads = round(AvgLogicalReads, 0)
' \
  --output table

The KQL query against QueryStoreRuntimeStatistics maps directly to sys.query_store_runtime_stats joined with sys.query_store_plan and sys.query_store_query in on-premises SQL Server. If you have built Query Store dashboards on-premises, the transition to KQL is largely a syntax change rather than a conceptual one. The query_hash_s field lets you correlate across databases or time windows even when query IDs differ.

Creating a metric alert for Elastic Pool DTU consumption:

# Alert when Elastic Pool eDTU consumption exceeds 85% for 10 minutes
POOL_RESOURCE_ID=$(az sql elastic-pool show \
  --resource-group prod-rg \
  --server prod-sql-server-01 \
  --name prod-elastic-pool-01 \
  --query id \
  --output tsv)

ACTION_GROUP_ID=$(az monitor action-group show \
  --resource-group prod-rg \
  --name prod-db-oncall \
  --query id \
  --output tsv)

az monitor metrics alert create \
  --name "elastic-pool-dtu-saturation" \
  --resource-group prod-rg \
  --scopes "$POOL_RESOURCE_ID" \
  --condition "avg dtu_consumption_percent > 85" \
  --window-size 10m \
  --evaluation-frequency 5m \
  --severity 2 \
  --description "Elastic Pool eDTU consumption above 85% — consider scaling or workload redistribution" \
  --action "$ACTION_GROUP_ID"

One alert configuration mistake that appears frequently: setting the evaluation frequency equal to the window size. If your window is 10 minutes and you evaluate every 10 minutes, a spike that occurs in the last two minutes of a window will not fire an alert until the next evaluation cycle — potentially 18 minutes after the spike began. Use an evaluation frequency of 5 minutes or less when the window size is 10 minutes.

30.4 Google Cloud Monitoring and Cloud Logging for Cloud SQL and AlloyDB

Google Cloud Monitoring (formerly Stackdriver) collects Cloud SQL and AlloyDB metrics automatically with no configuration required. The metrics are available in the cloudsql.googleapis.com and alloydb.googleapis.com namespaces. Cloud Logging captures database flags, slow query logs, and general logs as structured log entries that can be queried with the Logs Explorer or exported to BigQuery for long-term analysis.

The model is similar to Azure Monitor: there is a metrics layer (low cost, pre-aggregated, 6-week default retention in Cloud Monitoring) and a logging layer (structured logs in Cloud Logging, charged per GB ingested beyond the free 50 GB per project per month, with 30-day default retention).

Critical Cloud SQL metrics:

| Metric | Full path | Alert threshold |

|--------|-----------|----------------|

| CPU utilization | cloudsql.googleapis.com/database/cpu/utilization | > 0.80 for 5 min |

| Disk utilization | cloudsql.googleapis.com/database/disk/utilization | > 0.85 |

| Memory utilization | cloudsql.googleapis.com/database/memory/utilization | > 0.90 |

| Active connections | cloudsql.googleapis.com/database/postgresql/num_backends | > 80% of max_connections |

| Replica lag (seconds) | cloudsql.googleapis.com/database/replication/replica_lag | > 30 seconds |

| Deadlock count | cloudsql.googleapis.com/database/postgresql/deadlock_count | Any non-zero trend |

| Transaction ID utilization | cloudsql.googleapis.com/database/postgresql/transaction_id_utilization | > 0.70 |

transaction_id_utilization is specific to PostgreSQL and has no equivalent in SQL Server monitoring. It measures the fraction of the 2^31 transaction ID space that has been consumed since the last VACUUM FREEZE cycle. On-premises DBAs who ran autovacuum aggressively often never encountered transaction ID wraparound; in Cloud SQL, autovacuum still runs, but understanding this metric is important because a Cloud SQL instance under heavy write load can approach the wraparound limit if autovacuum is tuned too conservatively. Alert at 70% utilization and treat 80% as an emergency requiring manual VACUUM FREEZE intervention.

Enabling the PostgreSQL slow query log and Cloud Logging export using gcloud:

# Enable the slow query log for a Cloud SQL PostgreSQL instance.
# log_min_duration_statement is set in milliseconds.
# Setting it to 1000 logs any query taking longer than 1 second.

gcloud sql instances patch prod-cloudsql-pg01 \
  --database-flags \
    log_min_duration_statement=1000,\
    log_checkpoints=on,\
    log_connections=off,\
    log_disconnections=off,\
    log_lock_waits=on,\
    log_temp_files=10240,\
    log_autovacuum_min_duration=500

# Verify the flags were applied
gcloud sql instances describe prod-cloudsql-pg01 \
  --format="value(settings.databaseFlags)"

# Cloud SQL logs flow automatically to Cloud Logging.
# Create a log sink to export slow query logs to BigQuery for long-term analysis.
# The filter captures log entries from the postgres database log.
gcloud logging sinks create prod-cloudsql-slowquery-bq \
  bigquery.googleapis.com/projects/prod-project/datasets/db_monitoring \
  --log-filter='
    resource.type="cloudsql_database"
    resource.labels.database_id="prod-project:prod-cloudsql-pg01"
    log_id("cloudsql.googleapis.com/postgres.log")
    textPayload=~"duration:"
  ' \
  --use-partitioned-tables

# Grant the sink service account write access to the BigQuery dataset
SINK_SA=$(gcloud logging sinks describe prod-cloudsql-slowquery-bq \
  --format="value(writerIdentity)")

bq add-iam-policy-binding \
  --member="$SINK_SA" \
  --role="roles/bigquery.dataEditor" \
  prod-project:db_monitoring

After the sink is in place, slow query logs accumulate in the db_monitoring dataset partitioned by date. This allows long-term trend analysis — comparing this week's p99 query latency against the same period last month — that would be impractical inside Cloud Logging's 30-day default retention window.

Querying Cloud SQL slow query logs in BigQuery:

-- BigQuery SQL: Find the top 20 slowest queries from the Cloud SQL PostgreSQL
-- slow query log over the last 7 days, grouped by normalized query pattern.
-- The textPayload field contains the raw log line from PostgreSQL.

SELECT
  REGEXP_EXTRACT(textPayload, r'duration: ([0-9.]+) ms') AS duration_ms_str,
  CAST(REGEXP_EXTRACT(textPayload, r'duration: ([0-9.]+) ms') AS FLOAT64) AS duration_ms,
  -- Normalize the statement by removing literal values (basic normalization)
  REGEXP_REPLACE(
    REGEXP_EXTRACT(textPayload, r'statement: (.+)$'),
    r"'[^']*'|[0-9]+",
    '?'
  ) AS normalized_query,
  textPayload AS raw_log,
  timestamp
FROM
  `prod-project.db_monitoring.prod-project_prod-cloudsql-pg01_*`
WHERE
  _TABLE_SUFFIX >= FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY))
  AND textPayload LIKE '%duration:%'
ORDER BY
  duration_ms DESC
LIMIT 20;

-- Aggregate by normalized pattern to find the highest cumulative load
SELECT
  REGEXP_REPLACE(
    REGEXP_EXTRACT(textPayload, r'statement: (.+)$'),
    r"'[^']*'|[0-9]+",
    '?'
  ) AS normalized_query,
  COUNT(*) AS execution_count,
  ROUND(AVG(CAST(REGEXP_EXTRACT(textPayload, r'duration: ([0-9.]+) ms') AS FLOAT64)), 2) AS avg_duration_ms,
  ROUND(MAX(CAST(REGEXP_EXTRACT(textPayload, r'duration: ([0-9.]+) ms') AS FLOAT64)), 2) AS max_duration_ms,
  ROUND(SUM(CAST(REGEXP_EXTRACT(textPayload, r'duration: ([0-9.]+) ms') AS FLOAT64)) / 1000.0, 1) AS total_cpu_seconds
FROM
  `prod-project.db_monitoring.prod-project_prod-cloudsql-pg01_*`
WHERE
  _TABLE_SUFFIX >= FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY))
  AND textPayload LIKE '%duration:%'
GROUP BY
  normalized_query
HAVING
  execution_count > 10
ORDER BY
  total_cpu_seconds DESC
LIMIT 25;

The regex-based normalization above is a reasonable first pass, but it does not handle all cases — dollar-quoted strings, array literals, and multi-line queries will not normalize cleanly. For production use, consider using the pg_stat_statements extension in Cloud SQL, which PostgreSQL normalizes internally, and exporting its contents periodically to BigQuery using a scheduled job or a Dataflow pipeline.

AlloyDB-specific monitoring considerations:

AlloyDB exposes metrics in the alloydb.googleapis.com namespace and shares the same Cloud Monitoring and Cloud Logging infrastructure as Cloud SQL. The key metrics that are specific to AlloyDB's columnar engine and distributed storage architecture include:

  • → `alloydb.googleapis.com/database/memory/columnar_engine_fill_ratio` — the fraction of the columnar engine cache that is occupied. If this consistently approaches 1.0, the columnar engine is evicting data before it can be used effectively.
  • → `alloydb.googleapis.com/database/replication/log_archive_lag_seconds` — the lag in archiving WAL to AlloyDB's distributed storage. Unlike standard PostgreSQL replication lag, this measures the pipeline between the primary's WAL writer and the durable storage layer, not the replica application lag.
  • → `alloydb.googleapis.com/database/postgresql/num_backends` — shared with the Cloud SQL metric name for consistency, but the threshold context differs. AlloyDB's connection pooling architecture through AlloyDB Auth Proxy or PgBouncer affects how this number relates to application concurrency.

    • For AlloyDB, enabling the columnar engine requires setting the google_columnar_engine.enabled database flag and then explicitly marking tables for columnar storage or letting the auto-columnarization feature select candidates. Monitoring columnar_engine_fill_ratio without first verifying that the engine is actually enabled for your workload is a common instrumentation mistake.

    30.5 Building Effective Dashboards Across All Three Platforms

    A monitoring system that generates alerts but has no dashboard is a fire alarm with no sprinkler system. Alerts tell you something is wrong; dashboards tell you why, in what context, and how it compares to recent history. Every production cloud database environment should have at minimum two dashboard tiers: a fleet overview dashboard visible to anyone on-call, and a per-instance deep-dive dashboard used during active troubleshooting.

    Fleet overview dashboard — what to include:

    The fleet overview should answer the question "which of my databases is sick right now?" in under 30 seconds. Design for this use case explicitly:

  • → One row per database instance, with CPU, memory, connections, storage, and replication lag displayed as colored status indicators (green/yellow/red) rather than raw numbers.
  • → An alert count widget showing open alarms grouped by severity.
  • → A timeline of alert state changes over the last 24 hours — this lets on-call engineers see whether a current alert is a new event or something that has been flapping.
  • → Storage growth trend over 7 days, not current utilization — current utilization at 72% is a different situation depending on whether it was 60% last week or 71% yesterday.

    • Per-instance deep-dive dashboard — structure by signal type:

    30.6 Alerting Strategy: Avoiding Alert Fatigue Without Missing Real Incidents

    Every DBA who has operated a cloud database for more than a few months has experienced alert fatigue — a state where the volume of alerts is high enough that engineers begin to ignore them, which is worse than having no alerts at all. The root cause is almost always over-alerting on symptoms rather than on actionable signals.

    The three tests for a well-designed alert:

    1. Actionability test: When this alert fires at 3 a.m., is there a specific action an on-call engineer can take within 15 minutes that will resolve or mitigate the condition? If the answer is "they need to wait for business hours to investigate," the alert severity should be at most a warning, not a page.

    2. Specificity test: Does the alert condition uniquely identify a real problem, or does it fire frequently for transient conditions that resolve themselves? CPU at 85% for 60 seconds might be a routine batch job; CPU at 85% for 5 continuous minutes is more likely to be an actual problem.

    3. Freshness test: Has this alert been reviewed in the last 90 days? Thresholds that were correct when set often become wrong as workloads evolve, instances are resized, or application behavior changes.

    graph TD
    A[Metric crosses threshold] --> B{Actionable within
    15 minutes?}
    B -->|No| C[Downgrade to warning
    or dashboard-only]
    B -->|Yes| D{Fires only on

    *The three tests applied as a gate before an alert is allowed to page anyone.*

    Alert tiering for production databases:

    | Tier | Criteria | Response expectation |

    |------|----------|---------------------|

    | P1 — Page immediately | Database unavailable, replica lag > 5 minutes, storage > 95%, workers at 100% | Wake on-call engineer immediately |

    | P2 — Page within 30 min | CPU > 85% for 10 min, connections > 90% of max, storage > 90%, deadlock rate spike | On-call responds before next check cycle |

    | P3 — Ticket during business hours | CPU > 75% for 30 min, storage growth rate anomaly, slow query count increase | Engineer reviews within next business day |

    | P4 — Dashboard annotation | Configuration drift, index recommendation events, autovacuum duration spikes | Visible but does not generate a notification |

    Multi-step alert suppression during maintenance windows:

    All three platforms support alert suppression or maintenance window configuration, but the mechanisms differ:

  • → **CloudWatch**: Use CloudWatch Alarms in `ALARM` state with an SNS topic that has a subscription filter. During maintenance, disable the SNS subscription rather than the alarm. This preserves alarm state history.
  • → **Azure Monitor**: Use Action Groups with webhooks and Logic Apps to implement time-based suppression, or use the built-in **Alert suppression rules** (now called **Action rules**) which can suppress by resource, resource group, or tag during a defined time window.
  • → **Cloud Monitoring**: Use **Alerting Policy** snoozes, which can be created programmatically via the Cloud Monitoring API and scoped to a specific policy or resource.
    • # Google Cloud Monitoring: Create a snooze for maintenance window
# This suppresses the TXID wraparound alert during a planned VACUUM FREEZE operation

POLICY_NAME=$(gcloud alpha monitoring policies list \
  --project=prod-project \
  --filter="displayName:'Cloud SQL PostgreSQL - Transaction ID Wraparound Warning'" \
  --format="value(name)")

  "displayName": "Planned VACUUM FREEZE maintenance snooze",
  "interval": {

  },

    The storage runaway alert pattern: One alert that every cloud DBA should implement but frequently omits is not a threshold alert but a rate-of-change alert. Disk at 80% is concerning; disk growing at 5 GB per hour when it was growing at 200 MB per hour yesterday is an emergency — a runaway batch job, a missing partition pruning condition, or an accidental cross join is generating data at an anomalous rate. All three platforms support rate-of-change alerting through metric math (CloudWatch), dynamic thresholds (Azure Monitor Metric Alerts), and absent data plus threshold combination (Cloud Monitoring).

    # CloudWatch metric math alert for storage growth rate
# RATE() computes the per-second rate of change of the metric
# Multiply by 3600 to convert to GB per hour

aws cloudwatch put-metric-alarm \
  --alarm-name "rds-prod-postgres-01-storage-growth-anomaly" \
  --alarm-description "Storage shrinking faster than 1 GB/hour (FreeStorageSpace decreasing rapidly)" \
  --metrics '[
    {
      "Id": "m1",
      "MetricStat": {
        "Metric": {
          "Namespace": "AWS/RDS",
          "MetricName": "FreeStorageSpace",
          "Dimensions": [{"Name": "DBInstanceIdentifier", "Value": "prod-postgres-01"}]
        },
        "Period": 300,
        "Stat": "Minimum"
      },
      "ReturnData": false
    },
    {
      "Id": "growth_rate",
      "Expression": "RATE(m1) * 3600 / -1073741824",
      "Label": "Storage consumption GB/hour",
      "ReturnData": true
    }
  ]' \
  --comparison-operator GreaterThanThreshold \
  --threshold 1.0 \
  --evaluation-periods 2 \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:prod-db-alerts \
  --treat-missing-data notBreaching

    The RATE() function returns the per-second change; the sign is negative when free space is shrinking (consumption is growing), so we multiply by -1 to make the threshold comparison intuitive. If free storage is decreasing by more than 1 GB per hour for two consecutive 5-minute periods, the alarm fires.

    30.7 Common Instrumentation Gaps and How to Close Them

    After reviewing how monitoring is configured across a range of production cloud database environments, a set of instrumentation gaps appears consistently. These are conditions that the platform does not alert on by default, that engineers assume are covered when they are not.

    Gap 1: Missing connection pool exhaustion detection

    CloudWatch's DatabaseConnections metric counts connections at the RDS level. If you use PgBouncer, RDS Proxy, or a connection pool in front of RDS, the application-side pool can be exhausted while RDS shows a healthy connection count. You need application-side metrics (PgBouncer's SHOW POOLS output, RDS Proxy's DatabaseConnectionRequests and QueryRequests metrics in CloudWatch) to detect pool starvation. RDS Proxy specifically surfaces ClientConnections, DatabaseConnections, QueryRequests, and ClientConnectionsClosed as distinct metrics.

    # CloudWatch alarm for RDS Proxy client connection saturation
# RDS Proxy max client connections depend on instance class and max_connections
aws cloudwatch put-metric-alarm \
  --alarm-name "rds-proxy-prod-client-saturation" \
  --metric-name ClientConnections \
  --namespace AWS/RDS \
  --dimensions Name=ProxyName,Value=prod-rds-proxy \
  --statistic Maximum \
  --period 60 \
  --evaluation-periods 3 \
  --threshold 900 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:prod-db-alerts

    Gap 2: Autovacuum and dead tuple accumulation (PostgreSQL on all platforms)

    Neither CloudWatch, Azure Monitor, nor Cloud Monitoring alerts on dead tuple accumulation by default. A table with millions of dead tuples causes index bloat, query plan degradation, and eventually transaction ID wraparound risk. You must push this data from pg_stat_user_tables to your monitoring system manually.

    # Python script to push pg_stat_user_tables dead tuple metrics to CloudWatch.
# Run this as a scheduled Lambda function every 5 minutes on RDS PostgreSQL,
# or as a Cloud Run job for Cloud SQL.

import boto3
import psycopg2
from datetime import datetime, timezone
import os

def push_dead_tuple_metrics():
    conn = psycopg2.connect(
        host=os.environ["DB_HOST"],
        dbname=os.environ["DB_NAME"],
        user=os.environ["DB_USER"],
        password=os.environ["DB_PASSWORD"],
        sslmode="require"
    )
    cw = boto3.client("cloudwatch", region_name="us-east-1")
    db_instance = os.environ["DB_INSTANCE_ID"]

    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                schemaname,
                relname,
                n_dead_tup,
                n_live_tup,
                CASE WHEN (n_live_tup + n_dead_tup) > 0
                     THEN ROUND(n_dead_tup::numeric / (n_live_tup + n_dead_tup) * 100, 2)
                     ELSE 0
                END AS dead_ratio_pct,
                last_autovacuum,
                last_autoanalyze
            FROM pg_stat_user_tables
            WHERE n_dead_tup > 10000
            ORDER BY n_dead_tup DESC
            LIMIT 20
        """)
        rows = cur.fetchall()

    metric_data = []
    now = datetime.now(timezone.utc)

    for schema, table, dead, live, dead_pct, last_vac, last_analyze in rows:
        table_name = f"{schema}.{table}"
        metric_data.extend([
            {
                "MetricName": "DeadTuples",
                "Dimensions": [
                    {"Name": "DBInstanceIdentifier", "Value": db_instance},
                    {"Name": "TableName", "Value": table_name}
                ],
                "Timestamp": now,
                "Value": float(dead),
                "Unit": "Count"
            },
            {
                "MetricName": "DeadTupleRatioPct",
                "Dimensions": [
                    {"Name": "DBInstanceIdentifier", "Value": db_instance},
                    {"Name": "TableName", "Value": table_name}
                ],
                "Timestamp": now,
                "Value": float(dead_pct),
                "Unit": "Percent"
            }
        ])

    # CloudWatch PutMetricData accepts max 20 metrics per call
    for i in range(0, len(metric_data), 20):
        cw.put_metric_data(
            Namespace="CustomRDS/PostgreSQL",
            MetricData=metric_data[i:i+20]
        )

    conn.close()
    print(f"Pushed {len(metric_data)} dead tuple metrics to CloudWatch.")

if __name__ == "__main__":
    push_dead_tuple_metrics()

    After this runs, create CloudWatch alarms on CustomRDS/PostgreSQL/DeadTupleRatioPct > 20 filtered by table name to catch tables where autovacuum is not keeping up. The same pattern applies on Azure SQL (using sys.dm_db_index_physical_stats for fragmentation) and on Cloud SQL (using the same pg_stat_user_tables query with metrics pushed to Cloud Monitoring custom metrics).

    Gap 3: Long-running transaction detection

    Long-running transactions block autovacuum, hold locks, and inflate FreeableMemory consumption through WAL retention. None of the three platforms alert on long-running transactions by default.

    -- Query to push to a monitoring system.
-- Works on both RDS PostgreSQL and Cloud SQL PostgreSQL.
-- Returns sessions with open transactions older than 5 minutes.

-- PostgreSQL version
SELECT
    pid,
    usename AS username,
    application_name,
    client_addr,
    EXTRACT(EPOCH FROM (now() - xact_start))::INT AS xact_age_seconds,
    state,
    LEFT(query, 200) AS current_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND state != 'idle'
  AND now() - xact_start > INTERVAL '5 minutes'
ORDER BY xact_age_seconds DESC;

-- SQL Server equivalent (Azure SQL)
SELECT
    s.session_id,
    s.login_name,
    s.program_name,
    s.client_interface_name,
    DATEDIFF(SECOND, t.transaction_begin_time, GETUTCDATE()) AS xact_age_seconds,
    r.status AS session_status,
    LEFT(st.text, 200) AS current_query
FROM sys.dm_tran_active_transactions t
JOIN sys.dm_exec_sessions s ON t.transaction_id = s.transaction_id
LEFT JOIN sys.dm_exec_requests r ON s.session_id = r.session_id
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) st
WHERE DATEDIFF(SECOND, t.transaction_begin_time, GETUTCDATE()) > 300
  AND s.session_id != @@SPID
ORDER BY xact_age_seconds DESC;

    Push the row count from the PostgreSQL version as a custom metric. Alert when any transaction has been open for more than 30 minutes — at that point, it is almost never intentional and is very likely to be causing collateral damage to other queries waiting on locks.

    Gap 4: Logical replication slot lag

    Logical replication slots in PostgreSQL retain WAL indefinitely if a consumer stops consuming. This causes storage to grow unboundedly and is not reflected in the standard FreeStorageSpace metric until the situation is already severe. On RDS PostgreSQL, logical replication slots are used by AWS DMS, Debezium, and pglogical consumers. Monitor pg_replication_slots directly.

    -- PostgreSQL: Check logical replication slot lag
-- Works on RDS PostgreSQL, Cloud SQL PostgreSQL, and AlloyDB
SELECT
    slot_name,
    plugin,
    slot_type,
    active,
    active_pid,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal_size,
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS retained_wal_bytes,
    confirmed_flush_lsn
FROM pg_replication_slots
WHERE slot_type = 'logical'
ORDER BY retained_wal_bytes DESC;

    If retained_wal_bytes exceeds your available storage headroom, the instance will eventually run out of space. Alert when any logical slot retains more than 5 GB of WAL. On RDS, you can set the max_slot_wal_keep_size parameter (available in PostgreSQL 13+) to cap WAL retention per slot, but doing so means a lagging consumer will have its slot invalidated — a trade-off you must manage at the application level.

    Gap 5: Backup window overlap with production load

    Automated backups on RDS and Cloud SQL cause brief I/O elevation during the backup window. On heavily loaded instances, this can push I/O latency above alert thresholds, generating pages that resolve themselves once the backup completes. The fix is not to raise the alert threshold — it is to annotate the dashboard with the backup window and ensure the backup window is scheduled during the lowest-traffic period. Both RDS and Cloud SQL allow the backup window to be configured.

    # RDS: Move the backup window to 02:00-03:00 UTC (lowest traffic window)
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --preferred-backup-window "02:00-03:00" \
  --preferred-maintenance-window "sun:03:30-sun:04:30" \
  --apply-immediately

# Cloud SQL: Move the backup window start time
gcloud sql instances patch prod-cloudsql-pg01 \
  --backup-start-time 02:00

    Separate the backup window from the maintenance window by at least 30 minutes to prevent overlap between backup I/O and any parameter or minor version updates.

    30.8 Integrating Cloud Database Monitoring with Existing Observability Stacks

    Most engineering organizations already have a Prometheus/Grafana stack, a Datadog deployment, or a Splunk environment before they migrate databases to the cloud. Bridging cloud-native metrics into these existing systems is preferable to maintaining parallel alert configurations in two places.

    Exporting CloudWatch metrics to Prometheus:

    The yet-another-cloudwatch-exporter (YACE) project is the most widely deployed solution for pulling CloudWatch metrics into Prometheus. Deploy it as a Kubernetes Deployment or an ECS task in the same VPC as your RDS instances.

    Azure Monitor to Prometheus using the Azure Monitor Metrics Exporter:

    Azure provides a managed Prometheus offering through Azure Monitor managed service for Prometheus, available when using Azure Kubernetes Service. For non-AKS environments, the azure-metrics-exporter project provides similar functionality to YACE.

    Google Cloud Monitoring to Prometheus:

    The stackdriver_exporter (now maintained as part of the prometheus-community Helm charts) scrapes Cloud Monitoring metrics and exposes them in Prometheus format. The configuration maps cloudsql.googleapis.com/database/cpu/utilization to stackdriver_cloudsql_database_cpu_utilization in Prometheus.

    Sending cloud database alerts to PagerDuty via SNS (AWS example):

  --protocol https \
  --notification-endpoint "$PAGERDUTY_ENDPOINT"

# After subscribing, PagerDuty sends a confirmation URL.
# CloudWatch SNS messages include the alarm name, state, and metric values,
# which PagerDuty maps to incident fields automatically.

# Verify the subscription is confirmed
aws sns list-subscriptions-by-topic \
  --topic-arn arn:aws:sns:us-east-1:123456789012:prod-db-alerts \
  --query 'Subscriptions[].{Protocol:Protocol, Endpoint:Endpoint, Status:SubscriptionArn}'

    When integrating with PagerDuty, Opsgenie, or VictorOps, pay attention to the deduplication key. CloudWatch sends both ALARM and OK state change notifications. Your incident management tool should close incidents automatically when it receives the OK notification. Configure this deduplication explicitly — the default behavior differs by integration and by the incident tool's version.

    Key Takeaways

  • → **The monitoring mental model shift is from pull to push.** Cloud-managed databases remove your direct access to the OS and log files, but replace it with pre-wired telemetry pipelines. Your job is to define thresholds and subscriptions before incidents occur, not to react to them with ad-hoc CLI commands during an outage.
  • → **Platform-specific layers serve different purposes.** CloudWatch Metrics, Azure Monitor Metrics, and Cloud Monitoring handle pre-aggregated, low-cost, high-availability signal collection. CloudWatch Logs Insights, Log Analytics (KQL), and Cloud Logging with BigQuery export handle raw query-level and event-level forensics. Use each layer for what it is designed for — routing everything into logs is expensive; keeping everything in metrics loses detail.
  • → **Several critical signals require custom instrumentation.** Dead tuple accumulation, long-running transactions, logical replication slot lag, and connection pool saturation at the proxy layer are not covered by any platform's default alerting. These gaps are responsible for a disproportionate share of production incidents that seem surprising because engineers assumed the platform would have flagged the condition.
  • → **Alert design determines whether your monitoring system is an asset or a liability.** Apply the three tests — actionability, specificity, and freshness — to every alert rule. Tier alerts into P1 through P4 based on what response they require. Rate-of-change alerts for storage catch runaway data growth events far earlier than simple threshold alerts on current utilization.
  • → **Cloud-native monitoring integrates with existing observability stacks through well-supported exporters.** YACE for CloudWatch-to-Prometheus, the azure-metrics-exporter for Azure Monitor, and the stackdriver-exporter for Cloud Monitoring all allow you to surface cloud database metrics in Grafana dashboards and Prometheus alerting rules alongside your application and infrastructure metrics, preserving a single pane of glass without duplicating alert logic across two systems.
