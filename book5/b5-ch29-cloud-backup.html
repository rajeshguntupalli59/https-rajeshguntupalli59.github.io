Chapter 29: Backup and Restore in Cloud: Automated Snapshots vs Manual

Cloud-managed databases don't eliminate the need for backup strategy — they redistribute the responsibility. The platforms handle the mechanics of snapshot creation and storage, but the decisions about retention windows, cross-region durability, point-in-time recovery granularity, and restore validation remain squarely in your hands. This chapter walks through how AWS RDS, Aurora, Azure SQL, and Google Cloud SQL implement backup systems, where automated snapshots fall short of what on-premises DBAs are accustomed to controlling, and how to build a production-grade backup posture that accounts for the gaps. You will also see the restore side in detail, because backup systems that have never been tested are guesses, not strategies.

---

29.1 How Automated Snapshots Work Under the Hood

When you ran backups on-premises, you controlled everything: backup agent, target storage, compression, parallelism, verification jobs. In cloud-managed RDS, the platform takes daily automated snapshots during a configurable maintenance window and retains transaction logs for point-in-time recovery (PITR). Understanding what actually happens during these operations — not just what the console tells you — changes how you design around them.

RDS Automated Snapshots

RDS snapshots are storage-volume snapshots backed by EBS. For single-AZ instances, the snapshot process briefly suspends I/O — typically for a few seconds on modern instances, but measurable. For Multi-AZ deployments, the snapshot is taken from the standby replica, which eliminates the I/O pause on the primary. This is the same reason you should always run production workloads as Multi-AZ, not just for failover, but for backup behavior.

The retention window accepts values from 0 to 35 days. Setting it to 0 disables automated snapshots entirely — and also disables PITR, because transaction log uploads to S3 depend on automated snapshots being enabled. A common misconfiguration is setting retention to 1 day to save costs on a "non-critical" system, then discovering that PITR only reaches back 24 hours when a logic error surfaces three days later.

Transaction logs are uploaded to S3 every five minutes. This gives you a recovery point objective (RPO) of approximately five minutes for PITR restores. You cannot restore to an arbitrary second — you restore to a specific UTC timestamp and RDS selects the nearest log position.

Aurora Automated Backups

Aurora's backup model differs architecturally. Because Aurora stores data in a distributed storage layer (six copies across three AZs), snapshots are not EBS volume captures — they are metadata pointers into the shared storage. This means Aurora snapshots are nearly instantaneous and impose no I/O impact regardless of whether you're using a Multi-AZ writer or not. Snapshot creation time is measured in seconds even for multi-terabyte clusters.

Aurora's PITR window covers the same 1–35 day range, and because Aurora streams changes continuously into its storage layer rather than uploading transaction logs in five-minute batches, its restorable window trails the current time more tightly than standard RDS in practice.

Azure SQL Automated Backups

Azure SQL Database takes full backups weekly, differential backups every 12 hours, and transaction log backups every 5–12 minutes. These are stored in geo-redundant storage (GRS) by default, giving you cross-region durability without additional configuration. The retention window for Point-in-Time Restore (PITR) ranges from 1 to 35 days on General Purpose and Business Critical tiers; the Hyperscale tier handles backup differently and warrants its own treatment below.

One difference from RDS that catches on-premises DBAs: in Azure SQL, you cannot directly access backup files. You restore to a new database — you cannot restore over an existing database in-place. This forces a rename-and-swap procedure that has implications for connection strings and dependent jobs.

Cloud SQL Automated Backups

Cloud SQL stores automated backups in the same region as the instance by default. Cross-region backup storage requires explicit configuration via backup export or cross-region replicas. Cloud SQL's PITR uses binary log retention for MySQL-compatible instances and WAL archiving for PostgreSQL-compatible instances, with a configurable retention window from 1 to 7 days — shorter than AWS or Azure. If you need more than 7 days of PITR coverage on Cloud SQL PostgreSQL, you are responsible for shipping WAL files to Cloud Storage manually using pg_basebackup exports or the pg_receivewal utility.

29.2 Configuring Automated Backup Windows and Retention

The defaults are rarely appropriate for production. Every platform gives you the ability to adjust backup windows, retention periods, and storage locations, but the configuration paths differ.

RDS Backup Configuration via AWS CLI

# Create an RDS PostgreSQL instance with backup configured for production
aws rds create-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --db-instance-class db.r6g.2xlarge \
  --engine postgres \
  --engine-version 15.4 \
  --master-username dbadmin \
  --master-user-password "${DB_MASTER_PASS}" \
  --allocated-storage 500 \
  --storage-type gp3 \
  --multi-az \
  --backup-retention-period 14 \
  --preferred-backup-window "02:00-03:00" \
  --preferred-maintenance-window "sun:04:00-sun:05:00" \
  --deletion-protection \
  --no-publicly-accessible \
  --db-subnet-group-name prod-db-subnet-group \
  --vpc-security-group-ids sg-0abc123def456789 \
  --tags Key=Environment,Value=Production Key=Owner,Value=DBA-Team

# Modify an existing instance's backup retention (takes effect immediately)
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --backup-retention-period 21 \
  --apply-immediately

The --preferred-backup-window uses UTC. Set it outside your peak transaction period. If you don't specify it, AWS assigns a random window — and randomly assigned maintenance windows have a habit of landing during business hours in some time zones.

RDS Cross-Region Backup Replication

Automated snapshots do not replicate cross-region by default. You must enable cross-region automated backup replication separately:

# Enable cross-region automated backup replication
# Source: us-east-1, Destination: us-west-2
aws rds start-export-task \
  --export-task-identifier backup-export-$(date +%Y%m%d) \
  --source-arn arn:aws:rds:us-east-1:123456789012:snapshot:rds:prod-postgres-01-2024-01-15 \
  --s3-bucket-name prod-db-backups-dr \
  --s3-prefix postgres-exports/ \
  --iam-role-arn arn:aws:iam::123456789012:role/RDSExportRole \
  --kms-key-id arn:aws:kms:us-west-2:123456789012:key/mrk-abcdef1234567890

# Enable cross-region backup copy for all future automated snapshots
aws rds enable-cross-region-automated-backups \
  --source-db-instance-identifier prod-postgres-01 \
  --backup-retention-period 7 \
  --s3-export-path s3://prod-db-backups-dr/cross-region/ \
  --destination-region us-west-2

Note: cross-region backup replication for RDS is a separate feature from cross-region read replicas. The replicated backups are usable independently of the source instance — if your primary region fails, you can restore from the replicated backups in the DR region without access to the source.

Azure SQL Backup Configuration

# Check current backup policy on an Azure SQL Database
az sql db show \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name proddb \
  --query "{name:name, shortTermRetention:requestedServiceObjectiveName}" \
  --output table

# Configure short-term backup retention (PITR window)
az sql db str-policy set \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name proddb \
  --retention-days 21

# Configure long-term retention (LTR) policy
# Weekly: keep 12 weeks, Monthly: keep 12 months, Yearly: keep 5 years
az sql db ltr-policy set \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name proddb \
  --weekly-retention P12W \
  --monthly-retention P12M \
  --yearly-retention P5Y \
  --week-of-year 1

# List available LTR backups
az sql db ltr-backup list \
  --location eastus \
  --server prod-sql-server \
  --database proddb \
  --output table

The LTR (Long-Term Retention) policy in Azure SQL maps to what on-premises DBAs implemented with backup-to-tape or offsite archive policies. Azure stores LTR backups in geo-redundant storage and they survive even if you delete the database or server — a meaningful difference from RDS where manual snapshots are deleted if you delete the instance unless you explicitly retain them.

Cloud SQL Backup Configuration

# Create a Cloud SQL PostgreSQL instance with backup configured
gcloud sql instances create prod-postgres-01 \
  --database-version=POSTGRES_15 \
  --tier=db-custom-8-32768 \
  --region=us-central1 \
  --availability-type=REGIONAL \
  --backup-start-time=03:00 \
  --enable-bin-log \
  --retained-backups-count=14 \
  --retained-transaction-log-days=7 \
  --storage-type=SSD \
  --storage-size=500GB \
  --storage-auto-increase \
  --deletion-protection \
  --no-assign-ip \
  --network=projects/myproject/global/networks/prod-vpc

# Verify backup configuration
gcloud sql instances describe prod-postgres-01 \
  --format="json(settings.backupConfiguration)"

The --retained-transaction-log-days cap of 7 on Cloud SQL is the most significant constraint compared to RDS or Azure SQL. If your organization requires 14 or 30 days of PITR, Cloud SQL PostgreSQL cannot satisfy it natively, and you must supplement with exported logical backups.

29.3 Manual Snapshots and On-Demand Backups

Automated snapshots cover the daily cadence. Manual snapshots address the scenarios automated backups were not designed for: pre-migration checkpoints, pre-schema-change captures, compliance archiving, and cross-account copies for DR testing.

When Manual Snapshots Matter

On-premises DBAs took pre-change backups before every major schema migration. In cloud managed databases, that discipline translates directly to manual snapshots. Unlike automated snapshots — which are deleted when their retention window expires or when the instance is deleted (unless explicitly protected) — manual snapshots persist until you explicitly delete them. This makes them appropriate for compliance retention.

# Create a manual RDS snapshot before a schema migration
aws rds create-db-snapshot \
  --db-instance-identifier prod-postgres-01 \
  --db-snapshot-identifier prod-postgres-01-pre-migration-v2-$(date +%Y%m%d%H%M) \
  --tags Key=Purpose,Value=pre-migration Key=Schema,Value=v2 Key=Retention,Value=90days

# Check snapshot status
aws rds describe-db-snapshots \
  --db-snapshot-identifier prod-postgres-01-pre-migration-v2-20240115-1430 \
  --query "DBSnapshots[0].{Status:Status,Progress:PercentProgress,Size:AllocatedStorage}" \
  --output table

# Copy a manual snapshot to another region for DR validation
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier arn:aws:rds:us-east-1:123456789012:snapshot:prod-postgres-01-pre-migration-v2-20240115-1430 \
  --target-db-snapshot-identifier prod-postgres-01-pre-migration-v2-dr-copy \
  --kms-key-id arn:aws:kms:us-west-2:123456789012:key/mrk-abcdef1234567890 \
  --source-region us-east-1 \
  --region us-west-2

# Share a snapshot with another AWS account (for DR account access)
aws rds modify-db-snapshot-attribute \
  --db-snapshot-identifier prod-postgres-01-pre-migration-v2-20240115-1430 \
  --attribute-name restore \
  --values-to-add 987654321098  # DR account ID

Cloud SQL On-Demand Backups

# Create an on-demand backup before a maintenance operation
gcloud sql backups create \
  --instance=prod-postgres-01 \
  --description="Pre-major-version-upgrade backup $(date +%Y%m%d)"

# List all backups (automated and on-demand)
gcloud sql backups list \
  --instance=prod-postgres-01 \
  --filter="type=ON_DEMAND" \
  --format="table(id, windowStartTime, status, diskEncryptionConfiguration.kmsKeyName)"

# Export a logical backup to Cloud Storage (supplements snapshot-based backup)
gcloud sql export sql prod-postgres-01 \
  gs://prod-db-exports/postgres/prod-postgres-01-$(date +%Y%m%d).sql.gz \
  --database=appdb \
  --offload

The --offload flag on Cloud SQL exports runs the export from a serverless export process rather than the instance itself, reducing impact on production. Without it, the export operation uses instance CPU and creates transient I/O load.

Aurora Manual Snapshots and Export to S3

Aurora adds a capability that standard RDS does not have in the same form: you can export a snapshot to S3 as Parquet files organized by table, making the data queryable by Athena without restoring the full database. This is useful for compliance audits and forensic queries on point-in-time data.

# Export Aurora snapshot to S3 as Parquet (for Athena querying)
aws rds start-export-task \
  --export-task-identifier audit-export-20240115 \
  --source-arn arn:aws:rds:us-east-1:123456789012:cluster-snapshot:aurora-prod-cluster-2024-01-15 \
  --s3-bucket-name prod-audit-exports \
  --s3-prefix aurora-exports/2024-01-15/ \
  --iam-role-arn arn:aws:iam::123456789012:role/RDSExportRole \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/mrk-export-key \
  --export-only "appdb.orders" "appdb.customers"  # Export only specific tables

# Monitor export progress
aws rds describe-export-tasks \
  --export-task-identifier audit-export-20240115 \
  --query "ExportTasks[0].{Status:Status,PercentProgress:PercentProgress,TotalExtractedDataInGB:TotalExtractedDataInGB}"

29.4 Point-in-Time Recovery: Configuration and Execution

PITR is where backup strategy meets recovery strategy. The mechanics differ substantially across platforms, and the gotchas matter more here than anywhere else.

RDS PITR Restore

PITR on RDS always creates a new DB instance — it does not restore in place. This is a fundamental difference from on-premises PostgreSQL where you recover into the existing data directory. The new instance inherits the parameter group, security group, and subnet group from the original, but you must manually update application connection strings or your DNS CNAME to point to the new instance.

# Restore RDS to a specific point in time
# Note: this creates a NEW instance, not an in-place restore
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-postgres-01 \
  --target-db-instance-identifier prod-postgres-01-restored-20240115T0230 \
  --restore-time 2024-01-15T02:30:00Z \
  --db-instance-class db.r6g.2xlarge \
  --multi-az \
  --no-publicly-accessible \
  --db-subnet-group-name prod-db-subnet-group \
  --vpc-security-group-ids sg-0abc123def456789 \
  --tags Key=Purpose,Value=PITR-restore Key=RestoreTime,Value=2024-01-15T02:30:00Z

# Check restore status
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01-restored-20240115T0230 \
  --query "DBInstances[0].{Status:DBInstanceStatus,Endpoint:Endpoint.Address,Port:Endpoint.Port}"

# After validation, modify DNS to point to restored instance
# (or promote to replace the original — must be done outside AWS)

Determining the Correct Restore Timestamp

This is where the DBA skill matters. Identifying the exact timestamp before a problematic event requires querying application logs, CloudWatch Logs Insights, or PostgreSQL log files. A script to correlate an error event with the appropriate restore target:

import boto3
from datetime import datetime, timedelta, timezone

def find_pitr_restore_window(instance_id: str, event_timestamp: datetime) -> dict:
    """
    Given an incident timestamp, identify the earliest and latest
    usable PITR restore points around that event.
    """
    rds = boto3.client('rds', region_name='us-east-1')
    
    # Get instance details to check backup retention and earliest restore time
    response = rds.describe_db_instances(DBInstanceIdentifier=instance_id)
    instance = response['DBInstances'][0]
    
    earliest_restore = instance.get('LatestRestorableTime')
    # Note: AWS SDK returns LatestRestorableTime but you need both ends
    
    # Check automated snapshots to find earliest available point
    snapshots = rds.describe_db_snapshots(
        DBInstanceIdentifier=instance_id,
        SnapshotType='automated',
        Filters=[
            {'Name': 'snapshot-create-time',
             'Values': ['2024-01-01T00:00:00Z']}  # Adjust range
        ]
    )
    
    snapshot_times = sorted([
        s['SnapshotCreateTime'] 
        for s in snapshots['DBSnapshots']
        if s['Status'] == 'available'
    ])
    
    # Recommended restore point: 5 minutes before the event
    recommended_restore = event_timestamp - timedelta(minutes=5)
    
    result = {
        'incident_time': event_timestamp.isoformat(),
        'recommended_restore_target': recommended_restore.isoformat(),
        'earliest_available_snapshot': snapshot_times[0].isoformat() if snapshot_times else None,
        'latest_restorable_time': earliest_restore.isoformat() if earliest_restore else None,
        'pitr_feasible': (
            snapshot_times[0] <= recommended_restore <= earliest_restore
            if snapshot_times and earliest_restore else False
        )
    }
    
    return result


# Example usage
incident_time = datetime(2024, 1, 15, 2, 47, 0, tzinfo=timezone.utc)
window = find_pitr_restore_window('prod-postgres-01', incident_time)

print(f"Incident occurred at: {window['incident_time']}")
print(f"Recommended restore to: {window['recommended_restore_target']}")
print(f"PITR feasible: {window['pitr_feasible']}")

Azure SQL PITR

# Restore Azure SQL Database to a point in time
# Creates a new database — cannot restore in place
az sql db restore \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name proddb \
  --dest-name proddb-restored-20240115 \
  --time "2024-01-15T02:30:00" \
  --edition GeneralPurpose \
  --service-objective GP_Gen5_8 \
  --backup-storage-redundancy Geo

# Monitor restore status
az sql db show \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name proddb-restored-20240115 \
  --query "{status:status, createTime:createTime}" \
  --output table

# After validation: rename original (if replacing), then rename restored
# Azure SQL supports database rename via ALTER DATABASE
# Connect to master and run:
# ALTER DATABASE [proddb] MODIFY NAME = [proddb-old-20240115];
# ALTER DATABASE [proddb-restored-20240115] MODIFY NAME = [proddb];

The rename approach in Azure SQL is your equivalent of the on-premises "restore over the original" workflow. It requires brief downtime during the rename operation, and active connections must be terminated. Azure SQL does not allow renaming a database with active connections — you must set it to single-user mode first via the portal or SSMS, or terminate connections via sys.dm_exec_sessions.

Cloud SQL PITR

# Restore Cloud SQL instance to a point in time
# PITR on Cloud SQL creates a clone of the instance
gcloud sql instances clone prod-postgres-01 prod-postgres-01-pitr-restore \
  --point-in-time="2024-01-15T02:30:00.000Z"

# Check clone status
gcloud sql instances describe prod-postgres-01-pitr-restore \
  --format="value(state)"

# After validation, if replacing the original:
# 1. Rename original (Cloud SQL doesn't support rename directly)
# 2. Update application connection strings or Cloud SQL proxy config
# 3. Delete original once validated

# List available transaction logs to verify PITR window
gcloud sql instances describe prod-postgres-01 \
  --format="json(settings.backupConfiguration.transactionLogRetentionDays,\
settings.backupConfiguration.backupRetentionSettings)"

One detail that trips up Cloud SQL users: PITR clone operations require that binary logging (for MySQL) or WAL archiving (for PostgreSQL) was enabled before the target timestamp. If you enable PITR on an existing instance today, you cannot restore to a timestamp from yesterday. The continuous log chain only begins from when the feature was activated.

29.5 Cross-Region and Cross-Account Backup Strategies

The backup sitting in the same region as your database is not a disaster recovery backup — it is a convenience restore mechanism. A region-level outage takes down both your database and your same-region backups simultaneously. Production posture requires cross-region backup copies, and for organizations with strict data segregation requirements, cross-account copies.

RDS Cross-Region Snapshot Automation

Automating cross-region snapshot copies requires either AWS Backup, a Lambda function triggered by snapshot events, or an EventBridge rule. The native enable-cross-region-automated-backups CLI command shown earlier is the simplest path, but AWS Backup gives you a unified policy view across services.

# Terraform: AWS Backup plan with cross-region copy for RDS
resource "aws_backup_plan" "rds_backup_plan" {
  name = "prod-rds-backup-plan"

  rule {
    rule_name         = "daily-backup-14day-retention"
    target_vault_name = aws_backup_vault.primary.name
    schedule          = "cron(0 3 * * ? *)"  # Daily at 3 AM UTC
    
    start_window      = 60   # minutes
    completion_window = 180  # minutes
    
    lifecycle {
      delete_after = 14
    }

    copy_action {
      destination_vault_arn = aws_backup_vault.dr_region.arn
      
      lifecycle {
        delete_after = 7  # Keep 7 days in DR region
      }
    }
  }

  rule {
    rule_name         = "weekly-backup-90day-retention"
    target_vault_name = aws_backup_vault.primary.name
    schedule          = "cron(0 4 ? * SUN *)"  # Weekly on Sunday at 4 AM UTC
    
    lifecycle {
      delete_after = 90
    }

    copy_action {
      destination_vault_arn = aws_backup_vault.dr_region.arn

      lifecycle {
        delete_after = 90
      }
    }
  }

  advanced_backup_setting {
    backup_options = {
      WindowsVSS = "disabled"
    }
    resource_type = "RDS"
  }
}

resource "aws_backup_vault" "primary" {
  name        = "prod-rds-backup-vault"
  kms_key_arn = aws_kms_key.backup_key.arn

  tags = {
    Environment = "Production"
  }
}

resource "aws_backup_vault" "dr_region" {
  provider    = aws.us_west_2
  name        = "prod-rds-backup-vault-dr"
  kms_key_arn = aws_kms_key.backup_key_dr.arn
}

resource "aws_backup_selection" "rds_selection" {
  name         = "prod-rds-instances"
  plan_id      = aws_backup_plan.rds_backup_plan.id
  iam_role_arn = aws_iam_role.backup_role.arn

  resources = [
    "arn:aws:rds:*:*:db:prod-*",
    "arn:aws:rds:*:*:cluster:aurora-prod-*"
  ]

  # Tag-based selection as alternative to ARN list
  selection_tag {
    type  = "STRINGEQUALS"
    key   = "BackupPolicy"
    value = "14-day-retention"
  }
}

resource "aws_backup_vault_policy" "primary_vault_policy" {
  backup_vault_name = aws_backup_vault.primary.name

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Deny"
        Principal = { AWS = "*" }
        Action = [
          "backup:DeleteBackupVault",
          "backup:DeleteRecoveryPoint",
          "backup:UpdateRecoveryPointLifecycle"
        ]
        Resource = "*"
        Condition = {
          StringNotLike = {
            "aws:PrincipalArn" = [
              "arn:aws:iam::${data.aws_caller_identity.current.account_id}:role/BackupAdminRole"
            ]
          }
        }
      }
    ]
  })
}

The vault policy above implements a critical control: it prevents deletion of recovery points by anyone except the designated BackupAdminRole. This protects against ransomware scenarios where an attacker gains broad IAM access and attempts to destroy backups before encrypting data.

Cross-Account Backup Copies

For organizations that run separate AWS accounts for production and DR, copying snapshots across account boundaries requires both accounts to cooperate:

# In source account: share the snapshot
aws rds modify-db-snapshot-attribute \
  --db-snapshot-identifier prod-postgres-01-2024-01-15-03-00 \
  --attribute-name restore \
  --values-to-add 987654321098  # DR account ID

# In destination account: copy the shared snapshot
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier \
    arn:aws:rds:us-east-1:123456789012:snapshot:prod-postgres-01-2024-01-15-03-00 \
  --target-db-snapshot-identifier prod-postgres-01-2024-01-15-cross-account-copy \
  --kms-key-id arn:aws:kms:us-east-1:987654321098:key/mrk-dr-account-key \
  --source-region us-east-1 \
  --copy-tags \
  --region us-east-1

# Verify the copy in destination account
aws rds describe-db-snapshots \
  --db-snapshot-identifier prod-postgres-01-2024-01-15-cross-account-copy \
  --query "DBSnapshots[0].{Status:Status,Encrypted:Encrypted,KmsKeyId:KmsKeyId}" \
  --output table

A note on KMS keys and cross-account copies: you cannot copy a snapshot encrypted with a source-account KMS key into a destination account without re-encrypting it with a key that the destination account controls. The --kms-key-id in the destination-account copy command must reference a key in the destination account. This is a deliberate design — it prevents a compromised source account from planting inaccessible encrypted snapshots in the DR account.

Azure SQL Geo-Restore

Azure SQL's default GRS backup storage gives you geo-restore capability without explicit cross-region configuration. However, the restore target must be in a paired region:

# Geo-restore to the paired region (e.g., East US → West US)
az sql db geo-backup restore \
  --resource-group dr-rg \
  --server dr-sql-server \
  --name proddb-geo-restored \
  --geo-backup-name proddb \
  --source-server-name prod-sql-server \
  --source-resource-group prod-rg \
  --edition GeneralPurpose \
  --service-objective GP_Gen5_8

# Note: geo-restore uses the most recent geo-redundant backup
# available — you cannot specify a point in time for geo-restore.
# If you need PITR in the DR region, you need active geo-replication,
# not just geo-restore from backup.

This distinction between geo-restore and geo-replication is important for RPO calculations. Geo-restore gives you the most recent backup, which may be hours old. Active geo-replication gives you near-zero RPO with the ability to failover with seconds of lag. For workloads requiring low RPO in a DR scenario, backup alone is insufficient.

29.6 Restore Testing and Validation Frameworks

A backup system that has never been tested is an assumption. The volume of data people have lost because they assumed backups were working — and discovered otherwise during an actual incident — makes restore testing one of the most important recurring operational practices a DBA team can establish.

What to Test, Not Just Whether It Restores

Many teams verify that a restore completes without error and stop there. That confirms the backup file is intact. It does not confirm:

  • → Schema consistency (all objects present, all constraints valid)
  • → Data completeness (row counts match expected ranges)
  • → Application connectivity (connection pools, service accounts, certificate trust)
  • → Performance characteristics (indexes are present, statistics are current)
  • → Dependent service configuration (secrets rotation, application config pointing to restored instance)

    • A restore validation script needs to cover all of these:

    import psycopg2
import boto3
import json
import time
from datetime import datetime, timezone
from typing import Optional

class RestoreValidator:
    """
    Validates a restored RDS PostgreSQL instance against a production
    baseline. Run this after every scheduled restore test.
    """
    
    def __init__(
        self,
        restored_endpoint: str,
        prod_endpoint: str,
        port: int,
        database: str,
        username: str,
        password: str
    ):
        self.restored_endpoint = restored_endpoint
        self.prod_endpoint = prod_endpoint
        self.port = port
        self.database = database
        self.credentials = {
            'user': username,
            'password': password,
            'database': database,
            'port': port,
            'connect_timeout': 10
        }
        self.results = []

    def _connect(self, host: str):
        return psycopg2.connect(host=host, **self.credentials)

    def _record(self, check: str, passed: bool, detail: str):
        self.results.append({
            'check': check,
            'passed': passed,
            'detail': detail,
            'timestamp': datetime.now(timezone.utc).isoformat()
        })
        status = "PASS" if passed else "FAIL"
        print(f"[{status}] {check}: {detail}")

    def check_connectivity(self) -> bool:
        """Verify the restored instance accepts connections."""
        try:
            conn = self._connect(self.restored_endpoint)
            conn.close()
            self._record("connectivity", True, f"Connected to {self.restored_endpoint}")
            return True
        except Exception as e:
            self._record("connectivity", False, str(e))
            return False

    def check_schema_completeness(self) -> bool:
        """
        Compare table count and object counts between production
        and restored instance.
        """
        schema_query = """
            SELECT 
                schemaname,
                COUNT(*) FILTER (WHERE relkind = 'r') AS tables,
                COUNT(*) FILTER (WHERE relkind = 'i') AS indexes,
                COUNT(*) FILTER (WHERE relkind = 'S') AS sequences,
                COUNT(*) FILTER (WHERE relkind = 'v') AS views
            FROM pg_catalog.pg_class c
            JOIN pg_catalog.pg_namespace n ON n.oid = c.relnamespace
            WHERE schemaname NOT IN ('pg_catalog', 'information_schema', 'pg_toast')
            GROUP BY schemaname
            ORDER BY schemaname;
        """
        
        try:
            prod_conn = self._connect(self.prod_endpoint)
            rest_conn = self._connect(self.restored_endpoint)
            
            with prod_conn.cursor() as cur:
                cur.execute(schema_query)
                prod_schema = {row[0]: row[1:] for row in cur.fetchall()}
            
            with rest_conn.cursor() as cur:
                cur.execute(schema_query)
                rest_schema = {row[0]: row[1:] for row in cur.fetchall()}
            
            prod_conn.close()
            rest_conn.close()
            
            mismatches = []
            for schema, prod_counts in prod_schema.items():
                rest_counts = rest_schema.get(schema)
                if rest_counts is None:
                    mismatches.append(f"Schema '{schema}' missing from restore")
                elif prod_counts != rest_counts:
                    mismatches.append(
                        f"Schema '{schema}': prod={prod_counts}, "
                        f"restored={rest_counts}"
                    )
            
            if mismatches:
                self._record("schema_completeness", False, "; ".join(mismatches))
                return False
            else:
                self._record(
                    "schema_completeness", True,
                    f"Schema matches across {len(prod_schema)} schemas"
                )
                return True
                
        except Exception as e:
            self._record("schema_completeness", False, str(e))
            return False

    def check_row_count_variance(
        self,
        tables: list[tuple[str, str]],
        max_variance_pct: float = 5.0
    ) -> bool:
        """
        Check that row counts on key tables in the restore are within
        an acceptable variance of production counts.
        
        tables: list of (schema, table) tuples to check
        max_variance_pct: maximum acceptable difference in row counts
        """
        all_passed = True
        
        try:
            prod_conn = self._connect(self.prod_endpoint)
            rest_conn = self._connect(self.restored_endpoint)
            
            for schema, table in tables:
                count_query = f"SELECT COUNT(*) FROM {schema}.{table}"
                
                with prod_conn.cursor() as cur:
                    cur.execute(count_query)
                    prod_count = cur.fetchone()[0]
                
                with rest_conn.cursor() as cur:
                    cur.execute(count_query)
                    rest_count = cur.fetchone()[0]
                
                if prod_count == 0:
                    variance_pct = 0.0 if rest_count == 0 else 100.0
                else:
                    variance_pct = abs(prod_count - rest_count) / prod_count * 100
                
                passed = variance_pct <= max_variance_pct
                all_passed = all_passed and passed
                self._record(
                    f"row_count_{schema}_{table}",
                    passed,
                    f"prod={prod_count:,}, restored={rest_count:,}, "
                    f"variance={variance_pct:.2f}%"
                )
            
            prod_conn.close()
            rest_conn.close()
            
        except Exception as e:
            self._record("row_count_variance", False, str(e))
            all_passed = False
        
        return all_passed

    def check_constraint_validity(self) -> bool:
        """
        Verify no invalid constraints exist on the restored instance.
        Invalid constraints indicate partial restores or corruption.
        """
        constraint_query = """
            SELECT 
                conrelid::regclass AS table_name,
                conname AS constraint_name,
                contype AS constraint_type,
                convalidated AS is_valid
            FROM pg_constraint
            WHERE NOT convalidated
              AND contype IN ('f', 'c')
            ORDER BY table_name, constraint_name;
        """
        
        try:
            conn = self._connect(self.restored_endpoint)
            with conn.cursor() as cur:
                cur.execute(constraint_query)
                invalid = cur.fetchall()
            conn.close()
            
            if invalid:
                detail = ", ".join(
                    f"{row[0]}.{row[1]}({row[2]})" for row in invalid
                )
                self._record(
                    "constraint_validity", False,
                    f"{len(invalid)} invalid constraints: {detail}"
                )
                return False
            else:
                self._record(
                    "constraint_validity", True,
                    "All constraints valid"
                )
                return True
                
        except Exception as e:
            self._record("constraint_validity", False, str(e))
            return False

    def check_statistics_freshness(self) -> bool:
        """
        Verify autovacuum/analyze has run on key tables, or explicitly
        run ANALYZE on the restored instance.
        """
        stats_query = """
            SELECT 
                schemaname,
                tablename,
                last_analyze,
                last_autoanalyze,
                n_live_tup
            FROM pg_stat_user_tables
            WHERE n_live_tup > 10000
              AND last_analyze IS NULL
              AND last_autoanalyze IS NULL
            ORDER BY n_live_tup DESC
            LIMIT 10;
        """
        
        try:
            conn = self._connect(self.restored_endpoint)
            with conn.cursor() as cur:
                cur.execute(stats_query)
                stale_tables = cur.fetchall()
            
            if stale_tables:
                # Run ANALYZE on tables with stale stats
                for row in stale_tables:
                    with conn.cursor() as cur:
                        cur.execute(
                            f"ANALYZE {row[0]}.{row[1]}"
                        )
                    conn.commit()
                self._record(
                    "statistics_freshness", True,
                    f"Ran ANALYZE on {len(stale_tables)} tables with stale stats"
                )
            else:
                self._record(
                    "statistics_freshness", True,
                    "Table statistics are current"
                )
            
            conn.close()
            return True
            
        except Exception as e:
            self._record("statistics_freshness", False, str(e))
            return False

    def generate_report(self, output_path: Optional[str] = None) -> dict:
        """Generate a validation report for audit and alerting."""
        total = len(self.results)
        passed = sum(1 for r in self.results if r['passed'])
        failed = total - passed
        
        report = {
            'validation_run': datetime.now(timezone.utc).isoformat(),
            'restored_endpoint': self.restored_endpoint,
            'summary': {
                'total_checks': total,
                'passed': passed,
                'failed': failed,
                'overall_status': 'PASS' if failed == 0 else 'FAIL'
            },
            'checks': self.results
        }
        
        if output_path:
            with open(output_path, 'w') as f:
                json.dump(report, f, indent=2)
        
        return report


# Example usage in a scheduled restore test pipeline
def run_restore_validation(restored_endpoint: str):
    import os
    
    validator = RestoreValidator(
        restored_endpoint=restored_endpoint,
        prod_endpoint=os.environ['PROD_DB_ENDPOINT'],
        port=5432,
        database='appdb',
        username=os.environ['DB_VALIDATION_USER'],
        password=os.environ['DB_VALIDATION_PASS']
    )
    
    # Run all checks
    validator.check_connectivity()
    validator.check_schema_completeness()
    validator.check_row_count_variance([
        ('public', 'orders'),
        ('public', 'customers'),
        ('public', 'products'),
        ('audit', 'change_log')
    ])
    validator.check_constraint_validity()
    validator.check_statistics_freshness()
    
    report = validator.generate_report('/tmp/restore-validation-report.json')
    
    if report['summary']['overall_status'] == 'FAIL':
        # Alert via SNS or PagerDuty
        sns = boto3.client('sns')
        sns.publish(
            TopicArn=os.environ['OPS_ALERT_TOPIC'],
            Subject='RESTORE VALIDATION FAILED',
            Message=json.dumps(report['summary'], indent=2)
        )
        raise SystemExit(1)
    
    return report

    Scheduling Regular Restore Tests

    An automated restore test should run at least monthly for production databases — weekly for high-criticality systems. The test pipeline should:

    1. Trigger a PITR or snapshot restore to an isolated VPC subnet

    2. Run the validation framework above

    3. Compare results against the previous test baseline

    4. Terminate the restored instance to avoid ongoing compute cost

    5. Log results to a compliance-accessible audit store

    graph TD
    A[Trigger PITR restore
    to isolated subnet] --> B[Wait for instance
    status: available]
    B --> C[Run validation checks:
    schema, row counts, constraints]
    C --> D{All checks pass?}
    D -->|Yes| E[Log report to
    audit store]
    D -->|No| F[Alert on-call via
    SNS/PagerDuty]
    E --> G[Delete restored
    test instance]
    F --> G

    *Scheduled restore test pipeline: validation runs before cleanup, and failures alert regardless of whether cleanup proceeds.*

    # EventBridge-triggered Lambda or Step Function for monthly restore test
# Sample shell pipeline for CloudWatch Events / Step Functions:

#!/bin/bash
set -euo pipefail

INSTANCE_ID="prod-postgres-01"
RESTORE_ID="restore-test-$(date +%Y%m%d%H%M)"
RESTORE_TIME=$(date -u -d '2 hours ago' +%Y-%m-%dT%H:%M:%SZ)
SUBNET_GROUP="restore-test-isolated-subnet"
SECURITY_GROUP="sg-restore-test-isolated"

echo "Starting restore test: ${RESTORE_ID}"

# Step 1: Trigger PITR restore
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier "${INSTANCE_ID}" \
  --target-db-instance-identifier "${RESTORE_ID}" \
  --restore-time "${RESTORE_TIME}" \
  --db-instance-class db.r6g.xlarge \
  --no-multi-az \
  --no-publicly-accessible \
  --db-subnet-group-name "${SUBNET_GROUP}" \
  --vpc-security-group-ids "${SECURITY_GROUP}"

# Step 2: Wait for available status (poll with backoff)
echo "Waiting for restored instance to become available..."
for i in $(seq 1 60); do
  STATUS=$(aws rds describe-db-instances \
    --db-instance-identifier "${RESTORE_ID}" \
    --query "DBInstances[0].DBInstanceStatus" \
    --output text)
  echo "  Status: ${STATUS} (attempt ${i}/60)"
  if [ "${STATUS}" = "available" ]; then
    break
  fi
  sleep 60
done

if [ "${STATUS}" != "available" ]; then
  echo "ERROR: Instance did not become available within 60 minutes"
  exit 1
fi

# Step 3: Get endpoint
ENDPOINT=$(aws rds describe-db-instances \
  --db-instance-identifier "${RESTORE_ID}" \
  --query "DBInstances[0].Endpoint.Address" \
  --output text)

# Step 4: Run validation
python3 /opt/restore-validator/validate.py \
  --endpoint "${ENDPOINT}" \
  --report-path "/tmp/restore-test-${RESTORE_ID}.json"

# Step 5: Tag result and upload report
aws s3 cp "/tmp/restore-test-${RESTORE_ID}.json" \
  "s3://prod-audit-logs/restore-tests/$(date +%Y/%m)/restore-test-${RESTORE_ID}.json"

# Step 6: Cleanup — delete the test instance
echo "Deleting restore test instance: ${RESTORE_ID}"
aws rds delete-db-instance \
  --db-instance-identifier "${RESTORE_ID}" \
  --skip-final-snapshot \
  --delete-automated-backups

echo "Restore test complete."

    29.7 Logical Backups as a Supplement to Snapshots

    Snapshot-based backups restore the entire instance. Sometimes you need to restore a single table, a single schema, or a specific subset of rows — and snapshot restores are not designed for that. Logical backups using pg_dump, mysqldump, or BACPAC files fill this gap.

    29.8 Backup Encryption, Access Control, and Compliance

    Backups represent the same data as your production database, which means they require the same classification and access controls. A common gap in cloud database security reviews is discovering that backups are encrypted at rest but accessible to a broad set of IAM principals, or that the encryption key is not under BYOK (bring your own key) control.

    RDS Backup Encryption

    RDS snapshots inherit the encryption status of the source instance. An unencrypted RDS instance produces unencrypted snapshots. You cannot encrypt a snapshot in place — you must copy it and specify a KMS key during the copy. The production enforcement practice is to ensure all RDS instances are created with encryption enabled using a customer-managed KMS key (CMK), not the AWS-managed aws/rds key.

    # Encrypt an unencrypted snapshot by copying with a CMK
# (migrate a legacy unencrypted instance's snapshot to encrypted)
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier prod-postgres-legacy-snapshot-20240115 \
  --target-db-snapshot-identifier prod-postgres-legacy-encrypted-20240115 \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/mrk-abcdef1234567890 \
  --copy-tags \
  --region us-east-1

# Verify encryption status
aws rds describe-db-snapshots \
  --db-snapshot-identifier prod-postgres-legacy-encrypted-20240115 \
  --query "DBSnapshots[0].{Encrypted:Encrypted,KmsKeyId:KmsKeyId}" \
  --output table

    Compliance Reporting: Verifying Backup Coverage

    For audits and compliance reviews (SOC 2, PCI-DSS, HIPAA), you need to demonstrate that all production databases have backup retention meeting the policy requirement. A cross-platform compliance check:

    import boto3
import json
from datetime import datetime, timezone

def audit_rds_backup_compliance(
    region: str,
    min_retention_days: int = 14
) -> list[dict]:
    """
    Returns a list of RDS and Aurora instances that do not meet
    minimum backup retention requirements.
    """
    rds = boto3.client('rds', region_name=region)
    non_compliant = []

    # Check RDS instances
    paginator = rds.get_paginator('describe_db_instances')
    for page in paginator.paginate():
        for instance in page['DBInstances']:
            retention = instance.get('BackupRetentionPeriod', 0)
            tags = {t['Key']: t['Value'] for t in instance.get('TagList', [])}
            env = tags.get('Environment', 'unknown')

            if env == 'Production' and retention < min_retention_days:
                non_compliant.append({
                    'resource_type': 'RDS Instance',
                    'identifier': instance['DBInstanceIdentifier'],
                    'environment': env,
                    'retention_days': retention,
                    'required_days': min_retention_days,
                    'encrypted': instance.get('StorageEncrypted', False),
                    'deletion_protection': instance.get('DeletionProtection', False),
                    'multi_az': instance.get('MultiAZ', False)
                })

    # Check Aurora clusters
    paginator = rds.get_paginator('describe_db_clusters')
    for page in paginator.paginate():
        for cluster in page['DBClusters']:
            retention = cluster.get('BackupRetentionPeriod', 0)
            tags = {t['Key']: t['Value'] for t in cluster.get('TagList', [])}
            env = tags.get('Environment', 'unknown')

            if env == 'Production' and retention < min_retention_days:
                non_compliant.append({
                    'resource_type': 'Aurora Cluster',
                    'identifier': cluster['DBClusterIdentifier'],
                    'environment': env,
                    'retention_days': retention,
                    'required_days': min_retention_days,
                    'encrypted': cluster.get('StorageEncrypted', False),
                    'deletion_protection': cluster.get('DeletionProtection', False),
                    'multi_az': len(cluster.get('AvailabilityZones', [])) > 1
                })

    return non_compliant


def generate_compliance_report(regions: list[str], min_retention: int = 14) -> dict:
    report = {
        'generated_at': datetime.now(timezone.utc).isoformat(),
        'policy_min_retention_days': min_retention,
        'regions_audited': regions,
        'non_compliant_resources': [],
        'summary': {}
    }

    for region in regions:
        findings = audit_rds_backup_compliance(region, min_retention)
        report['non_compliant_resources'].extend(findings)

    total = len(report['non_compliant_resources'])
    report['summary'] = {
        'total_non_compliant': total,
        'compliance_status': 'COMPLIANT' if total == 0 else 'NON-COMPLIANT',
        'unencrypted_count': sum(
            1 for r in report['non_compliant_resources']
            if not r['encrypted']
        ),
        'no_deletion_protection_count': sum(
            1 for r in report['non_compliant_resources']
            if not r['deletion_protection']
        )
    }

    return report


# Run and emit report
report = generate_compliance_report(
    regions=['us-east-1', 'us-west-2', 'eu-west-1'],
    min_retention=14
)
print(json.dumps(report, indent=2))

    29.9 Backup Cost Management

    Backup storage costs accumulate quietly. Snapshots on a 10 TB database at 30-day retention across two regions with daily snapshots represent a storage footprint that warrants active management, not passive acceptance.

    Understanding Incremental Snapshot Storage

    RDS and Aurora snapshots are incremental after the first full snapshot — only changed blocks are stored in subsequent snapshots. This means the storage cost of daily snapshots is proportional to your daily change rate, not your total database size. A mostly-read database with low write volume will have a dramatically smaller snapshot storage footprint than a write-heavy OLTP system of the same size.

    Aurora's snapshot storage model is even more efficient: because the shared storage layer tracks changes at the block level across all snapshots, the total storage for 14 daily snapshots may be only marginally larger than the database itself if the change rate is low.

    Cost Optimization: Tiered Retention Strategy

    A tiered approach balances recovery capability against storage cost:

    | Backup Type | Frequency | Retention | Storage Location | Use Case |

    |---|---|---|---|---|

    | Automated snapshot | Daily | 14 days | Same region | Standard PITR and daily restore |

    | Manual snapshot (weekly) | Weekly | 90 days | Same region | Extended window restores |

    | Cross-region copy (weekly) | Weekly | 30 days | DR region | Regional disaster recovery |

    | Logical export (monthly) | Monthly | 1 year | S3 Glacier | Compliance archiving, table-level restores |

    Logical exports to S3 Glacier Instant Retrieval cost a fraction of RDS snapshot storage for long-term archiving. For compliance requirements mandating 7-year retention, Glacier Deep Archive is the appropriate tier — with the understanding that retrieval takes hours and is appropriate only for compliance audit scenarios, not operational recovery.

    Key Takeaways

  • → **Automated snapshots are a starting point, not a complete backup strategy.** Platform defaults — short retention windows, single-region storage, no cross-account copies — require deliberate reconfiguration before production use. The most common production backup failures involve systems where someone accepted the defaults and discovered the limitations during an actual incident.
  • → **PITR mechanics differ significantly across platforms.** RDS uploads transaction logs every five minutes (approx. five-minute RPO); Aurora's shared storage model provides near-second RPO; Cloud SQL PostgreSQL caps PITR window at seven days. Knowing these limits determines whether your platform choice is compatible with your recovery objectives before a problem occurs.
  • → **Restore always creates a new instance — plan your cutover procedure before you need it.** All three platforms (RDS, Azure SQL, Cloud SQL) restore to a new database endpoint rather than restoring in place. The rename-and-swap workflow, DNS update, or connection string change must be documented and rehearsed as part of your incident response runbooks, not improvised under pressure.
  • → **Backup validation is a recurring operational discipline, not a one-time setup task.** A restore test that checks connectivity and stops there tells you the backup file is readable, not that the database is usable. Schema completeness, constraint validity, row count variance, and statistics freshness checks are the difference between a tested recovery capability and a false sense of preparedness.
  • → **Cross-region and cross-account backup copies require explicit configuration and have encryption key implications.** Snapshots in the source region are not automatically replicated; cross-account copies require re-encryption with a destination-account KMS key; and backup vault policies should explicitly deny deletion by all principals except a designated admin role to protect against both accidental and malicious removal of recovery points.
