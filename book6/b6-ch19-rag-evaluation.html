Chapter 19: RAG Evaluation and Feedback Loops Stored in PostgreSQL

Most RAG systems ship with a retrieval pipeline and a generation step, and then the team moves on. Six weeks later, someone notices that the chatbot keeps hallucinating product names, the CEO asks why a competitor's marketing copy shows up in the support bot's answers, and nobody has the data to explain what went wrong. This chapter is about building the instrumentation that prevents that conversation from happening. You will learn how to capture every relevant signal from a RAG pipeline — retrieved chunks, reranking scores, LLM outputs, latency, user feedback — store it all in PostgreSQL, and close the loop so that bad retrievals get fixed automatically. PostgreSQL is the right place for this because evaluation is fundamentally a join problem: you need to correlate user satisfaction signals with the specific chunks that were served, the query that produced them, the embedding model that encoded them, and the generation parameters that shaped the answer. No purpose-built vector store gives you that.

---

19.1 The Evaluation Data Model

Before you can measure anything, you need a schema that captures the full chain of causality in a RAG request. A request is not a single event — it is a pipeline of decisions, each of which can succeed or fail independently. The retrieval step can return irrelevant chunks even when the embedding is good. The generation step can hallucinate even when the retrieval is perfect. The user can mark an answer as unhelpful even when it is technically correct. Your schema has to represent all of these layers without collapsing them together.

The design below uses four core tables that form a natural hierarchy: a session captures a conversation, a query captures a single user turn, a retrieval_result captures each chunk that was fetched for that query, and a generation captures the LLM's response. Feedback and evaluation scores hang off the generation table. This hierarchy means you can answer questions like "which chunks appear most often in low-rated responses" with a single query.

-- Core RAG evaluation schema
-- Run this in your application database

CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- Sessions represent a user's conversation context
CREATE TABLE rag_sessions (
    session_id      UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id         TEXT,
    app_context     TEXT NOT NULL,          -- 'support_bot', 'doc_search', etc.
    metadata        JSONB DEFAULT '{}',
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    ended_at        TIMESTAMPTZ,
    total_queries   INT DEFAULT 0,
    session_rating  SMALLINT CHECK (session_rating BETWEEN 1 AND 5)
);

-- One row per user turn in a session
CREATE TABLE rag_queries (
    query_id            UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    session_id          UUID REFERENCES rag_sessions(session_id),
    app_context         TEXT NOT NULL,       -- denormalized from rag_sessions for hot-path filtering
    query_text          TEXT NOT NULL,
    query_embedding     VECTOR(1536),        -- stored for drift detection
    query_embedding_model TEXT NOT NULL,
    rewritten_query     TEXT,               -- if query rewriting was used
    intent_label        TEXT,               -- classifier output if applicable
    created_at          TIMESTAMPTZ DEFAULT NOW(),
    retrieval_strategy  TEXT NOT NULL,      -- 'semantic', 'hybrid', 'bm25_only'
    top_k               INT NOT NULL,
    similarity_threshold FLOAT,
    retrieval_latency_ms INT,
    generation_latency_ms INT,
    total_latency_ms    INT
);

CREATE INDEX idx_rag_queries_session ON rag_queries(session_id);
CREATE INDEX idx_rag_queries_created ON rag_queries(created_at DESC);
CREATE INDEX idx_rag_queries_embedding ON rag_queries
    USING ivfflat (query_embedding vector_cosine_ops) WITH (lists = 100);

-- Each chunk retrieved for a query, with its ranking context
CREATE TABLE rag_retrieval_results (
    result_id           UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    query_id            UUID REFERENCES rag_queries(query_id) ON DELETE CASCADE,
    chunk_id            UUID NOT NULL,              -- FK to your document chunks table
    document_id         UUID NOT NULL,
    document_title      TEXT,
    chunk_text          TEXT NOT NULL,              -- snapshot at retrieval time
    chunk_embedding     VECTOR(1536),               -- snapshot for offline analysis
    rank_position       INT NOT NULL,               -- 1 = top result
    retrieval_score     FLOAT NOT NULL,             -- cosine similarity or BM25 score
    rerank_score        FLOAT,                      -- cross-encoder score if reranked
    final_rank          INT,                        -- position after reranking
    was_used_in_context BOOLEAN DEFAULT TRUE,       -- false if filtered post-retrieval
    retrieval_method    TEXT NOT NULL               -- 'vector', 'bm25', 'fusion'
);

CREATE INDEX idx_retrieval_query ON rag_retrieval_results(query_id);
CREATE INDEX idx_retrieval_chunk ON rag_retrieval_results(chunk_id);
CREATE INDEX idx_retrieval_document ON rag_retrieval_results(document_id);

-- The LLM's response and associated metadata
CREATE TABLE rag_generations (
    generation_id       UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    query_id            UUID REFERENCES rag_queries(query_id) ON DELETE CASCADE,
    model_name          TEXT NOT NULL,              -- 'claude-3-5-sonnet-20241022'
    model_provider      TEXT NOT NULL,              -- 'anthropic', 'openai'
    prompt_tokens       INT,
    completion_tokens   INT,
    total_tokens        INT,
    response_text       TEXT NOT NULL,
    finish_reason       TEXT,                       -- 'stop', 'max_tokens', etc.
    temperature         FLOAT,
    system_prompt_hash  TEXT,                       -- SHA256 of system prompt
    created_at          TIMESTAMPTZ DEFAULT NOW(),
    -- Automated evaluation scores (filled async)
    faithfulness_score  FLOAT CHECK (faithfulness_score BETWEEN 0 AND 1),
    relevance_score     FLOAT CHECK (relevance_score BETWEEN 0 AND 1),
    context_recall      FLOAT CHECK (context_recall BETWEEN 0 AND 1),
    answer_correctness  FLOAT CHECK (answer_correctness BETWEEN 0 AND 1),
    eval_model          TEXT,                       -- model used for evaluation
    eval_completed_at   TIMESTAMPTZ
);

CREATE INDEX idx_generation_query ON rag_generations(query_id);
CREATE INDEX idx_generation_model ON rag_generations(model_name);
CREATE INDEX idx_generation_scores ON rag_generations(faithfulness_score, relevance_score);

-- User feedback: thumbs, ratings, corrections
CREATE TABLE rag_feedback (
    feedback_id         UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    generation_id       UUID REFERENCES rag_generations(generation_id),
    query_id            UUID REFERENCES rag_queries(query_id),
    user_id             TEXT,
    feedback_type       TEXT NOT NULL,     -- 'thumbs_up', 'thumbs_down', 'rating', 'correction'
    rating              SMALLINT CHECK (rating BETWEEN 1 AND 5),
    comment             TEXT,
    corrected_answer    TEXT,              -- user-provided ground truth
    flagged_chunk_ids   UUID[],            -- chunks the user identified as wrong
    created_at          TIMESTAMPTZ DEFAULT NOW(),
    reviewed_by         TEXT,             -- human reviewer if escalated
    review_action       TEXT,             -- 'accepted', 'rejected', 'escalated'
    review_notes        TEXT
);

CREATE INDEX idx_feedback_generation ON rag_feedback(generation_id);
CREATE INDEX idx_feedback_created ON rag_feedback(created_at DESC);
CREATE INDEX idx_feedback_type ON rag_feedback(feedback_type);

-- Aggregate daily metrics for dashboards (populated by scheduled job)
CREATE TABLE rag_daily_metrics (
    metric_date         DATE NOT NULL,
    app_context         TEXT NOT NULL,
    model_name          TEXT NOT NULL,
    retrieval_strategy  TEXT NOT NULL,
    total_queries       INT DEFAULT 0,
    avg_faithfulness    FLOAT,
    avg_relevance       FLOAT,
    avg_context_recall  FLOAT,
    thumbs_up_count     INT DEFAULT 0,
    thumbs_down_count   INT DEFAULT 0,
    avg_retrieval_ms    FLOAT,
    avg_generation_ms   FLOAT,
    p95_total_ms        FLOAT,
    PRIMARY KEY (metric_date, app_context, model_name, retrieval_strategy)
);

19.2 Instrumenting the RAG Pipeline

The schema is only useful if the pipeline actually writes to it. The instrumentation layer needs to add minimal overhead to the request path — write the synchronous data inline, and dispatch the expensive evaluation work asynchronously. The pattern below uses a RAGPipeline class that wraps your retrieval and generation calls, writes the core rows synchronously, and enqueues an evaluation task via Celery.

# rag_pipeline.py — fully instrumented RAG pipeline
# pip install anthropic openai psycopg2-binary celery pgvector numpy

import hashlib
import time
import uuid
from datetime import datetime, timezone
from typing import Optional

import anthropic
import numpy as np
import psycopg2
import psycopg2.extras
from celery import Celery
from openai import OpenAI

psycopg2.extras.register_uuid()

# --- Configuration ---
DB_DSN = "postgresql://app_user:secret@localhost:5432/rag_app"
CELERY_BROKER = "redis://localhost:6379/0"

celery_app = Celery("rag_eval", broker=CELERY_BROKER, backend=CELERY_BROKER)
openai_client = OpenAI()
anthropic_client = anthropic.Anthropic()


def get_db():
    return psycopg2.connect(DB_DSN)


def embed_text(text: str, model: str = "text-embedding-3-small") -> list[float]:
    response = openai_client.embeddings.create(input=text, model=model)
    return response.data[0].embedding


def retrieve_chunks(
    query_embedding: list[float],
    top_k: int = 5,
    similarity_threshold: float = 0.75,
    strategy: str = "semantic",
) -> list[dict]:
    """
    Your actual retrieval logic against the document_chunks table.
    Returns list of dicts with chunk_id, document_id, chunk_text, score, etc.
    This is simplified — swap in your real retrieval query.
    """
    conn = get_db()
    cur = conn.cursor(cursor_factory=psycopg2.extras.DictCursor)
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"
    cur.execute(
        """
        SELECT
            chunk_id,
            document_id,
            document_title,
            chunk_text,
            1 - (embedding <=> %s::vector) AS score
        FROM document_chunks
        WHERE 1 - (embedding <=> %s::vector) >= %s
        ORDER BY embedding <=> %s::vector
        LIMIT %s
        """,
        (embedding_str, embedding_str, similarity_threshold, embedding_str, top_k),
    )
    rows = cur.fetchall()
    cur.close()
    conn.close()
    return [dict(r) for r in rows]


class RAGPipeline:
    def __init__(self, app_context: str, model: str = "claude-3-5-sonnet-20241022"):
        self.app_context = app_context
        self.model = model
        self.embedding_model = "text-embedding-3-small"

    def run(
        self,
        session_id: str,
        user_id: str,
        query_text: str,
        top_k: int = 5,
        temperature: float = 0.2,
    ) -> dict:
        query_id = str(uuid.uuid4())
        conn = get_db()

        try:
            # 1. Embed the query
            t0 = time.time()
            query_embedding = embed_text(query_text, model=self.embedding_model)
            embed_ms = int((time.time() - t0) * 1000)

            # 2. Retrieve chunks
            t1 = time.time()
            chunks = retrieve_chunks(query_embedding, top_k=top_k)
            retrieval_ms = int((time.time() - t1) * 1000)

            # 3. Write the query row (synchronous — fast)
            embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"
            with conn.cursor() as cur:
                cur.execute(
                    """
                    INSERT INTO rag_queries (
                        query_id, session_id, app_context, query_text, query_embedding,
                        query_embedding_model, retrieval_strategy, top_k,
                        retrieval_latency_ms
                    ) VALUES (%s, %s, %s, %s, %s::vector, %s, %s, %s, %s)
                    """,
                    (
                        query_id,
                        session_id,
                        self.app_context,
                        query_text,
                        embedding_str,
                        self.embedding_model,
                        "semantic",
                        top_k,
                        retrieval_ms,
                    ),
                )

                # 4. Write retrieval results
                for rank, chunk in enumerate(chunks, start=1):
                    cur.execute(
                        """
                        INSERT INTO rag_retrieval_results (
                            query_id, chunk_id, document_id, document_title,
                            chunk_text, rank_position, retrieval_score,
                            was_used_in_context, retrieval_method
                        ) VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
                        """,
                        (
                            query_id,
                            chunk["chunk_id"],
                            chunk["document_id"],
                            chunk.get("document_title", ""),
                            chunk["chunk_text"],
                            rank,
                            chunk["score"],
                            True,
                            "vector",
                        ),
                    )
                conn.commit()

            # 5. Build context and call LLM
            context = "\n\n---\n\n".join(c["chunk_text"] for c in chunks)
            system_prompt = (
                "You are a helpful assistant. Answer the user's question using "
                "only the context provided. If the context does not contain enough "
                "information, say so explicitly. Do not make up information."
            )
            system_hash = hashlib.sha256(system_prompt.encode()).hexdigest()[:16]

            t2 = time.time()
            response = anthropic_client.messages.create(
                model=self.model,
                max_tokens=1024,
                temperature=temperature,
                system=system_prompt,
                messages=[
                    {
                        "role": "user",
                        "content": f"Context:\n{context}\n\nQuestion: {query_text}",
                    }
                ],
            )
            generation_ms = int((time.time() - t2) * 1000)

            response_text = response.content[0].text
            generation_id = str(uuid.uuid4())

            # 6. Write generation row
            with conn.cursor() as cur:
                cur.execute(
                    """
                    INSERT INTO rag_generations (
                        generation_id, query_id, model_name, model_provider,
                        prompt_tokens, completion_tokens, total_tokens,
                        response_text, finish_reason, temperature, system_prompt_hash
                    ) VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s)
                    """,
                    (
                        generation_id,
                        query_id,
                        self.model,
                        "anthropic",
                        response.usage.input_tokens,
                        response.usage.output_tokens,
                        response.usage.input_tokens + response.usage.output_tokens,
                        response_text,
                        response.stop_reason,
                        temperature,
                        system_hash,
                    ),
                )

                # Update latency totals on the query row
                total_ms = embed_ms + retrieval_ms + generation_ms
                cur.execute(
                    """
                    UPDATE rag_queries
                    SET generation_latency_ms = %s, total_latency_ms = %s
                    WHERE query_id = %s
                    """,
                    (generation_ms, total_ms, query_id),
                )
                conn.commit()

            # 7. Enqueue async evaluation — does NOT block the response
            evaluate_generation.delay(
                generation_id=generation_id,
                query_text=query_text,
                response_text=response_text,
                context_chunks=[c["chunk_text"] for c in chunks],
            )

            return {
                "query_id": query_id,
                "generation_id": generation_id,
                "answer": response_text,
                "sources": [
                    {
                        "title": c.get("document_title"),
                        "score": c["score"],
                        "rank": i + 1,
                    }
                    for i, c in enumerate(chunks)
                ],
                "latency_ms": total_ms,
            }

        finally:
            conn.close()


@celery_app.task(bind=True, max_retries=3)
def evaluate_generation(
    self,
    generation_id: str,
    query_text: str,
    response_text: str,
    context_chunks: list[str],
):
    """
    Async task: uses an LLM-as-judge to score the generation.
    Runs after the user has already received their answer.
    """
    try:
        scores = run_llm_evaluation(query_text, response_text, context_chunks)
        conn = get_db()
        with conn.cursor() as cur:
            cur.execute(
                """
                UPDATE rag_generations SET
                    faithfulness_score   = %s,
                    relevance_score      = %s,
                    context_recall       = %s,
                    answer_correctness   = %s,
                    eval_model           = %s,
                    eval_completed_at    = NOW()
                WHERE generation_id = %s
                """,
                (
                    scores["faithfulness"],
                    scores["relevance"],
                    scores["context_recall"],
                    scores["answer_correctness"],
                    "gpt-4o-mini",
                    generation_id,
                ),
            )
            conn.commit()
        conn.close()
    except Exception as exc:
        raise self.retry(exc=exc, countdown=60)


def run_llm_evaluation(
    query: str, answer: str, context_chunks: list[str]
) -> dict[str, float]:
    """
    LLM-as-judge evaluation using GPT-4o-mini for cost efficiency.
    Returns scores between 0 and 1 for each dimension.
    """
    context = "\n\n".join(context_chunks)
    eval_prompt = f"""You are evaluating a RAG system response. Score each dimension from 0.0 to 1.0.

QUESTION: {query}

CONTEXT PROVIDED TO THE SYSTEM:
{context}

SYSTEM'S ANSWER:
{answer}

Score the following and respond with ONLY a JSON object, no explanation:
- faithfulness: Is every claim in the answer supported by the context? (1.0 = fully grounded, 0.0 = hallucinated)
- relevance: Does the answer actually address the question? (1.0 = directly answers, 0.0 = off-topic)
- context_recall: Does the answer use the most relevant information from the context? (1.0 = all key facts used)
- answer_correctness: Overall quality combining faithfulness and relevance.

Example response format:
{{"faithfulness": 0.95, "relevance": 0.88, "context_recall": 0.72, "answer_correctness": 0.85}}"""

    response = openai_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": eval_prompt}],
        temperature=0.0,
        response_format={"type": "json_object"},
    )

    import json
    scores = json.loads(response.choices[0].message.content)
    # Clamp to [0, 1]
    return {k: max(0.0, min(1.0, float(v))) for k, v in scores.items()}

19.3 Feedback Collection and User Signal Processing

Automated evaluation tells you what the model thinks of its own outputs. User feedback tells you what your users think, which is a different and more important signal. The two signals rarely agree perfectly — a user might rate an answer highly even when the faithfulness score is low, because the answer was phrased confidently. That disagreement is itself valuable data.

The feedback API below shows how to record user signals and trigger downstream processing when negative feedback accumulates on a specific chunk.

# feedback_api.py — FastAPI endpoints for feedback collection
# pip install fastapi uvicorn psycopg2-binary

import json
import select
import threading
import uuid
from typing import Optional

import psycopg2
import psycopg2.extras
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

psycopg2.extras.register_uuid()

app = FastAPI()
DB_DSN = "postgresql://app_user:secret@localhost:5432/rag_app"


class FeedbackRequest(BaseModel):
    generation_id: str
    query_id: str
    user_id: str
    feedback_type: str           # 'thumbs_up', 'thumbs_down', 'rating', 'correction'
    rating: Optional[int] = None
    comment: Optional[str] = None
    corrected_answer: Optional[str] = None
    flagged_chunk_ids: Optional[list[str]] = None


@app.post("/feedback")
def submit_feedback(req: FeedbackRequest):
    conn = psycopg2.connect(DB_DSN)
    feedback_id = str(uuid.uuid4())

    with conn.cursor() as cur:
        cur.execute(
            """
            INSERT INTO rag_feedback (
                feedback_id, generation_id, query_id, user_id,
                feedback_type, rating, comment, corrected_answer, flagged_chunk_ids
            ) VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
            """,
            (
                feedback_id,
                req.generation_id,
                req.query_id,
                req.user_id,
                req.feedback_type,
                req.rating,
                req.comment,
                req.corrected_answer,
                req.flagged_chunk_ids or [],
            ),
        )

        # Notify background workers of negative feedback via pg_notify
        if req.feedback_type == "thumbs_down" or (req.rating is not None and req.rating <= 2):
            payload = json.dumps({
                "feedback_id": feedback_id,
                "generation_id": req.generation_id,
                "query_id": req.query_id,
                "flagged_chunk_ids": req.flagged_chunk_ids or [],
            })
            cur.execute("SELECT pg_notify('rag_negative_feedback', %s)", (payload,))

        conn.commit()

    conn.close()
    return {"feedback_id": feedback_id, "status": "recorded"}


def listen_for_negative_feedback():
    """
    Background thread that listens on the rag_negative_feedback channel
    and triggers chunk quality checks when negative feedback accumulates.
    """
    conn = psycopg2.connect(DB_DSN)
    conn.set_isolation_level(psycopg2.extensions.ISOLATION_LEVEL_AUTOCOMMIT)
    cur = conn.cursor()
    cur.execute("LISTEN rag_negative_feedback;")

    while True:
        if select.select([conn], [], [], 5.0)[0]:
            conn.poll()
            while conn.notifies:
                notify = conn.notifies.pop(0)
                payload = json.loads(notify.payload)
                check_chunk_quality.delay(
                    query_id=payload["query_id"],
                    generation_id=payload["generation_id"],
                    flagged_chunk_ids=payload["flagged_chunk_ids"],
                )


# Start the listener in a background thread when the app starts
@app.on_event("startup")
def start_listener():
    t = threading.Thread(target=listen_for_negative_feedback, daemon=True)
    t.start()


@celery_app.task
def check_chunk_quality(
    query_id: str,
    generation_id: str,
    flagged_chunk_ids: list[str],
):
    """
    After negative feedback, check whether any chunk has accumulated
    enough negative signals to warrant removal or re-embedding.
    """
    conn = get_db()
    with conn.cursor(cursor_factory=psycopg2.extras.DictCursor) as cur:
        # Count recent negative feedback per chunk across all queries
        cur.execute(
            """
            SELECT
                rr.chunk_id,
                COUNT(DISTINCT f.feedback_id) AS negative_count,
                MIN(rr.retrieval_score)        AS min_score,
                MAX(rr.retrieval_score)        AS max_score,
                AVG(g.faithfulness_score)      AS avg_faithfulness
            FROM rag_retrieval_results rr
            JOIN rag_feedback f
                ON f.query_id = rr.query_id
            JOIN rag_generations g
                ON g.query_id = rr.query_id
            WHERE rr.chunk_id = ANY(%s)
              AND f.feedback_type IN ('thumbs_down', 'rating')
              AND (f.rating IS NULL OR f.rating <= 2)
              AND f.created_at >= NOW() - INTERVAL '30 days'
            GROUP BY rr.chunk_id
            HAVING COUNT(DISTINCT f.feedback_id) >= 3
            """,
            (flagged_chunk_ids,),
        )
        problem_chunks = cur.fetchall()

    for chunk in problem_chunks:
        # Flag the chunk for human review in the document_chunks table
        with conn.cursor() as cur:
            cur.execute(
                """
                UPDATE document_chunks
                SET needs_review = TRUE,
                    review_reason = 'accumulated_negative_feedback',
                    review_flagged_at = NOW()
                WHERE chunk_id = %s
                """,
                (chunk["chunk_id"],),
            )
        conn.commit()
        # Optionally: send a notification to a Slack webhook, open a ticket, etc.

    conn.close()

19.4 Analytical Queries for Evaluation

With data flowing into the schema, you can now run the analytical queries that turn raw signals into actionable insight. The queries below cover the most common diagnostic tasks.

Query 1: Identify which chunks appear most often in low-rated responses.

-- PostgreSQL
-- Chunks that consistently appear alongside poor responses
-- Useful for targeting documents that need re-chunking or re-writing

SELECT
    rr.chunk_id,
    rr.document_title,
    LEFT(rr.chunk_text, 120)                            AS chunk_preview,
    COUNT(DISTINCT rr.query_id)                         AS appearance_count,
    AVG(g.faithfulness_score)                           AS avg_faithfulness,
    AVG(g.relevance_score)                              AS avg_relevance,
    SUM(CASE WHEN f.feedback_type = 'thumbs_down' THEN 1 ELSE 0 END)
                                                        AS thumbs_down_count,
    SUM(CASE WHEN f.feedback_type = 'thumbs_up'   THEN 1 ELSE 0 END)
                                                        AS thumbs_up_count,
    ROUND(
        SUM(CASE WHEN f.feedback_type = 'thumbs_down' THEN 1.0 ELSE 0 END) /
        NULLIF(COUNT(DISTINCT f.feedback_id), 0), 3
    )                                                   AS negative_feedback_rate
FROM rag_retrieval_results rr
JOIN rag_generations       g  ON g.query_id  = rr.query_id
LEFT JOIN rag_feedback     f  ON f.query_id  = rr.query_id
WHERE rr.was_used_in_context = TRUE
  AND g.eval_completed_at IS NOT NULL
  AND g.created_at >= NOW() - INTERVAL '30 days'
GROUP BY rr.chunk_id, rr.document_title, rr.chunk_text
HAVING COUNT(DISTINCT rr.query_id) >= 5           -- only chunks seen enough times
ORDER BY negative_feedback_rate DESC, avg_faithfulness ASC
LIMIT 25;
-- SQL Server equivalent
SELECT TOP 25
    rr.chunk_id,
    rr.document_title,
    LEFT(rr.chunk_text, 120)                            AS chunk_preview,
    COUNT(DISTINCT rr.query_id)                         AS appearance_count,
    AVG(g.faithfulness_score)                           AS avg_faithfulness,
    AVG(g.relevance_score)                              AS avg_relevance,
    SUM(CASE WHEN f.feedback_type = 'thumbs_down' THEN 1 ELSE 0 END)
                                                        AS thumbs_down_count,
    SUM(CASE WHEN f.feedback_type = 'thumbs_up'   THEN 1 ELSE 0 END)
                                                        AS thumbs_up_count,
    ROUND(
        SUM(CASE WHEN f.feedback_type = 'thumbs_down' THEN 1.0 ELSE 0 END) /
        NULLIF(CAST(COUNT(DISTINCT f.feedback_id) AS FLOAT), 0), 3
    )                                                   AS negative_feedback_rate
FROM rag_retrieval_results rr
JOIN rag_generations       g  ON g.query_id  = rr.query_id
LEFT JOIN rag_feedback     f  ON f.query_id  = rr.query_id
WHERE rr.was_used_in_context = 1
  AND g.eval_completed_at IS NOT NULL
  AND g.created_at >= DATEADD(DAY, -30, GETUTCDATE())
GROUP BY rr.chunk_id, rr.document_title, rr.chunk_text
HAVING COUNT(DISTINCT rr.query_id) >= 5
ORDER BY negative_feedback_rate DESC, avg_faithfulness ASC;

Query 3: Embedding drift detection — find queries whose embeddings are outliers.

Embedding drift happens when users start asking questions that are structurally different from your indexed documents. The cosine similarity between a query embedding and the centroid of your chunk embeddings drops. You can detect this by comparing query embeddings against a stored baseline centroid.

-- PostgreSQL
-- Detect queries that are far from the corpus centroid
-- Run periodically to spot distribution shift

WITH corpus_centroid AS (
    -- Average embedding of the most recent indexed chunks
    -- In production, precompute this and store it in a config table
    SELECT AVG(embedding) AS centroid
    FROM document_chunks
    WHERE indexed_at >= NOW() - INTERVAL '90 days'
),
query_distances AS (
    SELECT
        q.query_id,
        q.query_text,
        q.created_at,
        q.app_context,
        -- Cosine distance from centroid (lower = closer to corpus)
        (q.query_embedding <=> c.centroid) AS dist_from_centroid
    FROM rag_queries q
    CROSS JOIN corpus_centroid c
    WHERE q.created_at >= NOW() - INTERVAL '7 days'
      AND q.query_embedding IS NOT NULL
)
SELECT
    query_id,
    query_text,
    created_at,
    ROUND(dist_from_centroid::NUMERIC, 4)   AS cosine_distance,
    NTILE(10) OVER (ORDER BY dist_from_centroid DESC)
                                            AS distance_decile
FROM query_distances
WHERE dist_from_centroid > (
    SELECT AVG(dist_from_centroid) + 2 * STDDEV(dist_from_centroid)
    FROM query_distances
)
ORDER BY dist_from_centroid DESC
LIMIT 50;

Query 4: Weekly trend — are scores improving after interventions?

-- PostgreSQL
-- Week-over-week evaluation score trends
-- Use this to measure the impact of re-chunking, prompt changes, or model upgrades

SELECT
    DATE_TRUNC('week', g.created_at)        AS week_start,
    q.app_context,
    COUNT(*)                                AS evaluated_responses,
    ROUND(AVG(g.faithfulness_score)::NUMERIC,  3) AS avg_faithfulness,
    ROUND(AVG(g.relevance_score)::NUMERIC,     3) AS avg_relevance,
    ROUND(AVG(g.context_recall)::NUMERIC,      3) AS avg_context_recall,
    ROUND(AVG(g.answer_correctness)::NUMERIC,  3) AS avg_correctness,
    -- Week-over-week faithfulness delta
    ROUND((
        AVG(g.faithfulness_score) -
        LAG(AVG(g.faithfulness_score)) OVER (
            PARTITION BY q.app_context
            ORDER BY DATE_TRUNC('week', g.created_at)
        )
    )::NUMERIC, 3)                          AS faithfulness_delta_wow
FROM rag_generations g
JOIN rag_queries     q ON q.query_id = g.query_id
WHERE g.eval_completed_at IS NOT NULL
  AND g.created_at >= NOW() - INTERVAL '12 weeks'
GROUP BY DATE_TRUNC('week', g.created_at), q.app_context
ORDER BY q.app_context, week_start;
-- SQL Server equivalent
SELECT
    DATEADD(WEEK, DATEDIFF(WEEK, 0, g.created_at), 0)
                                            AS week_start,
    q.app_context,
    COUNT(*)                                AS evaluated_responses,
    ROUND(AVG(g.faithfulness_score),  3)    AS avg_faithfulness,
    ROUND(AVG(g.relevance_score),     3)    AS avg_relevance,
    ROUND(AVG(g.context_recall),      3)    AS avg_context_recall,
    ROUND(AVG(g.answer_correctness),  3)    AS avg_correctness,
    ROUND(
        AVG(g.faithfulness_score) -
        LAG(AVG(g.faithfulness_score)) OVER (
            PARTITION BY q.app_context
            ORDER BY DATEADD(WEEK, DATEDIFF(WEEK, 0, g.created_at), 0)
        ), 3
    )                                       AS faithfulness_delta_wow
FROM rag_generations g
JOIN rag_queries     q ON q.query_id = g.query_id
WHERE g.eval_completed_at IS NOT NULL
  AND g.created_at >= DATEADD(WEEK, -12, GETUTCDATE())
GROUP BY DATEADD(WEEK, DATEDIFF(WEEK, 0, g.created_at), 0), q.app_context
ORDER BY q.app_context, week_start;

19.5 Closing the Feedback Loop Automatically

Collecting data is step one. Acting on it automatically is where the feedback loop closes. The three most impactful automatic actions are: requeuing failed retrievals as training examples for query rewriting, flagging chunks for re-embedding when their neighborhood in the vector space shifts, and triggering prompt-tuning experiments when faithfulness drops below a threshold. The code below implements a scheduled job that runs all three checks.

# feedback_loop.py — scheduled job that closes the RAG feedback loop
# Designed to run hourly via Celery Beat or a cron job

import json
from datetime import datetime, timezone

import psycopg2
import psycopg2.extras

DB_DSN = "postgresql://app_user:secret@localhost:5432/rag_app"
FAITHFULNESS_ALERT_THRESHOLD = 0.70   # below this triggers a prompt experiment
MIN_SAMPLE_SIZE = 50                  # need at least this many evals before acting


def get_db():
    return psycopg2.connect(DB_DSN)


@celery_app.task
def run_feedback_loop():
    """
    Hourly job: check evaluation metrics and trigger corrective actions.
    """
    conn = get_db()
    results = {}

    try:
        # --- Action 1: Collect low-faithfulness queries as rewriting candidates ---
        with conn.cursor(cursor_factory=psycopg2.extras.DictCursor) as cur:
            cur.execute(
                """
                INSERT INTO query_rewrite_candidates (
                    query_id, query_text, generation_id,
                    faithfulness_score, flagged_at, status
                )
                SELECT
                    q.query_id,
                    q.query_text,
                    g.generation_id,
                    g.faithfulness_score,
                    NOW(),
                    'pending'
                FROM rag_queries     q
                JOIN rag_generations g ON g.query_id = q.query_id
                WHERE g.faithfulness_score < 0.60
                  AND g.eval_completed_at IS NOT NULL
                  AND g.created_at >= NOW() - INTERVAL '24 hours'
                  AND NOT EXISTS (
                      SELECT 1 FROM query_rewrite_candidates qrc
                      WHERE qrc.query_id = q.query_id
                  )
                ON CONFLICT (query_id) DO NOTHING
                RETURNING query_id
                """
            )
            rewrite_candidates = cur.fetchall()
            results["rewrite_candidates_added"] = len(rewrite_candidates)
            conn.commit()

        # --- Action 2: Flag chunks whose average faithfulness has dropped ---
        with conn.cursor(cursor_factory=psycopg2.extras.DictCursor) as cur:
            cur.execute(
                """
                WITH chunk_recent_perf AS (
                    SELECT
                        rr.chunk_id,
                        COUNT(DISTINCT rr.query_id)     AS recent_appearances,
                        AVG(g.faithfulness_score)       AS recent_faithfulness,
                        AVG(g.relevance_score)          AS recent_relevance
                    FROM rag_retrieval_results rr
                    JOIN rag_generations g ON g.query_id = rr.query_id
                    WHERE rr.was_used_in_context = TRUE
                      AND g.created_at >= NOW() - INTERVAL '7 days'
                      AND g.eval_completed_at IS NOT NULL
                    GROUP BY rr.chunk_id
                    HAVING COUNT(DISTINCT rr.query_id) >= 5
                       AND AVG(g.faithfulness_score) < 0.65
                )
                UPDATE document_chunks dc
                SET needs_review      = TRUE,
                    review_reason     = 'low_faithfulness_window',
                    review_flagged_at = NOW()
                FROM chunk_recent_perf crp
                WHERE dc.chunk_id = crp.chunk_id
                  AND dc.needs_review IS DISTINCT FROM TRUE
                RETURNING dc.chunk_id
                """
            )
            flagged_chunks = cur.fetchall()
            results["chunks_flagged"] = len(flagged_chunks)
            conn.commit()

        # --- Action 3: Alert if app-level faithfulness drops below threshold ---
        with conn.cursor(cursor_factory=psycopg2.extras.DictCursor) as cur:
            cur.execute(
                """
                SELECT
                    q.app_context,
                    COUNT(*)                    AS eval_count,
                    AVG(g.faithfulness_score)   AS avg_faithfulness,
                    AVG(g.relevance_score)      AS avg_relevance
                FROM rag_generations g
                JOIN rag_queries     q ON q.query_id = g.query_id
                WHERE g.eval_completed_at IS NOT NULL
                  AND g.created_at >= NOW() - INTERVAL '1 hour'
                GROUP BY q.app_context
                HAVING COUNT(*) >= %s
                """,
                (MIN_SAMPLE_SIZE,),
            )
            hourly_metrics = cur.fetchall()

        for row in hourly_metrics:
            if row["avg_faithfulness"] < FAITHFULNESS_ALERT_THRESHOLD:
                trigger_faithfulness_alert(
                    app_context=row["app_context"],
                    avg_faithfulness=row["avg_faithfulness"],
                    eval_count=row["eval_count"],
                )

        results["status"] = "ok"
        results["ran_at"] = datetime.now(timezone.utc).isoformat()
        return results

    finally:
        conn.close()


def trigger_faithfulness_alert(
    app_context: str, avg_faithfulness: float, eval_count: int
):
    """
    Insert an alert record and optionally fire a webhook.
    In production this would integrate with PagerDuty, Slack, or your
    on-call tooling. The key thing is that it leaves an audit trail in
    the database so you can correlate alerts with deployments.
    """
    conn = get_db()
    with conn.cursor() as cur:
        cur.execute(
            """
            INSERT INTO rag_alerts (
                alert_type, app_context, metric_value,
                threshold_value, eval_count, created_at
            ) VALUES (%s, %s, %s, %s, %s, NOW())
            ON CONFLICT (alert_type, app_context, DATE_TRUNC('hour', created_at))
            DO NOTHING
            """,
            (
                "low_faithfulness",
                app_context,
                avg_faithfulness,
                FAITHFULNESS_ALERT_THRESHOLD,
                eval_count,
            ),
        )
        conn.commit()
    conn.close()

19.6 A/B Testing Retrieval Configurations

Once you have the evaluation loop running, you can use it to run controlled experiments. The simplest design is to tag each query with an experiment variant and then compare downstream metrics between variants after enough queries have accumulated. This requires no additional infrastructure beyond what you have already built — just a new column on the queries table and a routing layer that assigns variants.

# ab_testing.py — lightweight A/B routing for RAG experiments

import hashlib
import random
from dataclasses import dataclass
from typing import Optional


@dataclass
class ExperimentVariant:
    variant_id: str
    retrieval_strategy: str
    top_k: int
    similarity_threshold: float
    reranking: bool
    description: str


# Define your experiment variants
EXPERIMENTS = {
    "retrieval_comparison_v1": [
        ExperimentVariant(
            variant_id="control",
            retrieval_strategy="semantic",
            top_k=5,
            similarity_threshold=0.75,
            reranking=False,
            description="Baseline: pure semantic, top-5, no reranking",
        ),
        ExperimentVariant(
            variant_id="treatment_hybrid",
            retrieval_strategy="hybrid",
            top_k=10,
            similarity_threshold=0.65,
            reranking=True,
            description="Hybrid retrieval with cross-encoder reranking",
        ),
        ExperimentVariant(
            variant_id="treatment_larger_k",
            retrieval_strategy="semantic",
            top_k=10,
            similarity_threshold=0.70,
            reranking=True,
            description="Wider semantic retrieval with reranking",
        ),
    ]
}


def assign_variant(
    experiment_name: str,
    user_id: str,
    sticky: bool = True,
) -> Optional[ExperimentVariant]:
    """
    Assign a user to a variant. If sticky=True, the same user always gets
    the same variant (deterministic hash-based assignment). This prevents
    the same user from seeing different behaviors across sessions.
    """
    if experiment_name not in EXPERIMENTS:
        return None

    variants = EXPERIMENTS[experiment_name]

    if sticky:
        # Hash user_id + experiment_name to get a stable bucket
        hash_input = f"{user_id}:{experiment_name}".encode()
        bucket = int(hashlib.md5(hash_input).hexdigest(), 16) % len(variants)
    else:
        bucket = random.randint(0, len(variants) - 1)

    return variants[bucket]


def record_experiment_assignment(
    conn,
    query_id: str,
    experiment_name: str,
    variant: ExperimentVariant,
):
    """Store which variant was used for this query."""
    with conn.cursor() as cur:
        cur.execute(
            """
            INSERT INTO rag_experiment_assignments (
                query_id, experiment_name, variant_id,
                variant_description, assigned_at
            ) VALUES (%s, %s, %s, %s, NOW())
            ON CONFLICT (query_id, experiment_name) DO NOTHING
            """,
            (query_id, experiment_name, variant.variant_id, variant.description),
        )

The analysis query to compare experiment variants:

-- PostgreSQL
-- Compare A/B experiment variants by evaluation metrics and user satisfaction

SELECT
    ea.experiment_name,
    ea.variant_id,
    ea.variant_description,
    COUNT(DISTINCT ea.query_id)                      AS query_count,
    AVG(g.faithfulness_score)                        AS avg_faithfulness,
    AVG(g.relevance_score)                           AS avg_relevance,
    AVG(g.context_recall)                            AS avg_context_recall,
    AVG(q.retrieval_latency_ms)                      AS avg_retrieval_ms,
    -- Satisfaction rate: thumbs up / (thumbs up + thumbs down)
    SUM(CASE WHEN f.feedback_type = 'thumbs_up' THEN 1.0 ELSE 0 END) /
    NULLIF(
        SUM(CASE WHEN f.feedback_type IN ('thumbs_up','thumbs_down') THEN 1 ELSE 0 END),
        0
    )                                                AS satisfaction_rate,
    -- Confidence interval width (rough, assumes normality)
    1.96 * STDDEV(g.faithfulness_score) /
    NULLIF(SQRT(COUNT(g.faithfulness_score)), 0)     AS faithfulness_95ci_half
FROM rag_experiment_assignments ea
JOIN rag_queries     q ON q.query_id = ea.query_id
JOIN rag_generations g ON g.query_id = ea.query_id
LEFT JOIN rag_feedback f ON f.query_id = ea.query_id

  AND g.eval_completed_at IS NOT NULL
GROUP BY ea.experiment_name, ea.variant_id, ea.variant_description
ORDER BY avg_faithfulness DESC;

19.7 Populating the Daily Metrics Rollup

The rag_daily_metrics table defined in the schema is useless unless something populates it. A nightly job that upserts into it gives your dashboards a fast, pre-aggregated table to query instead of scanning months of raw event rows. The query is an upsert that recalculates the previous day's numbers (to pick up any late-arriving evaluation scores) and inserts the current day's running totals.

-- PostgreSQL
-- Nightly rollup into rag_daily_metrics
-- Parameterize :target_date to backfill historical days

INSERT INTO rag_daily_metrics (
    metric_date,
    app_context,
    model_name,
    retrieval_strategy,
    total_queries,
    avg_faithfulness,
    avg_relevance,
    avg_context_recall,
    thumbs_up_count,
    thumbs_down_count,
    avg_retrieval_ms,
    avg_generation_ms,
    p95_total_ms
)
SELECT
    DATE(q.created_at AT TIME ZONE 'UTC')       AS metric_date,
    q.app_context,
    g.model_name,
    q.retrieval_strategy,
    COUNT(DISTINCT q.query_id)                  AS total_queries,
    AVG(g.faithfulness_score)                   AS avg_faithfulness,
    AVG(g.relevance_score)                      AS avg_relevance,
    AVG(g.context_recall)                       AS avg_context_recall,
    SUM(CASE WHEN f.feedback_type = 'thumbs_up'   THEN 1 ELSE 0 END)
                                                AS thumbs_up_count,
    SUM(CASE WHEN f.feedback_type = 'thumbs_down' THEN 1 ELSE 0 END)
                                                AS thumbs_down_count,
    AVG(q.retrieval_latency_ms)                AS avg_retrieval_ms,
    AVG(q.generation_latency_ms)                AS avg_generation_ms,
    PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY q.total_latency_ms)
                                                AS p95_total_ms
FROM rag_queries      q
JOIN rag_generations  g  ON g.query_id = q.query_id
LEFT JOIN rag_feedback f  ON f.query_id = q.query_id
WHERE DATE(q.created_at AT TIME ZONE 'UTC') = CURRENT_DATE - INTERVAL '1 day'
GROUP BY
    DATE(q.created_at AT TIME ZONE 'UTC'),
    q.app_context,
    g.model_name,
    q.retrieval_strategy
ON CONFLICT (metric_date, app_context, model_name, retrieval_strategy)
DO UPDATE SET
    total_queries      = EXCLUDED.total_queries,
    avg_faithfulness   = EXCLUDED.avg_faithfulness,
    avg_relevance      = EXCLUDED.avg_relevance,
    avg_context_recall = EXCLUDED.avg_context_recall,
    thumbs_up_count    = EXCLUDED.thumbs_up_count,
    thumbs_down_count  = EXCLUDED.thumbs_down_count,
    avg_retrieval_ms   = EXCLUDED.avg_retrieval_ms,
    avg_generation_ms  = EXCLUDED.avg_generation_ms,
    p95_total_ms       = EXCLUDED.p95_total_ms;
-- SQL Server equivalent
-- Uses MERGE for the upsert pattern

MERGE INTO rag_daily_metrics AS target
USING (
    SELECT
        CAST(q.created_at AT TIME ZONE 'UTC' AS DATE)   AS metric_date,
        q.app_context,
        g.model_name,
        q.retrieval_strategy,
        COUNT(DISTINCT q.query_id)                       AS total_queries,
        AVG(g.faithfulness_score)                        AS avg_faithfulness,
        AVG(g.relevance_score)                           AS avg_relevance,
        AVG(g.context_recall)                            AS avg_context_recall,
        SUM(CASE WHEN f.feedback_type = 'thumbs_up'   THEN 1 ELSE 0 END)
                                                         AS thumbs_up_count,
        SUM(CASE WHEN f.feedback_type = 'thumbs_down' THEN 1 ELSE 0 END)
                                                         AS thumbs_down_count,
        AVG(CAST(q.retrieval_latency_ms AS FLOAT))       AS avg_retrieval_ms,
        AVG(CAST(q.generation_latency_ms AS FLOAT))      AS avg_generation_ms,
        PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY q.total_latency_ms)
            OVER (PARTITION BY
                CAST(q.created_at AT TIME ZONE 'UTC' AS DATE),
                q.app_context,
                g.model_name,
                q.retrieval_strategy)                    AS p95_total_ms
    FROM rag_queries      q
    JOIN rag_generations  g  ON g.query_id = q.query_id
    LEFT JOIN rag_feedback f  ON f.query_id = q.query_id
    WHERE CAST(q.created_at AT TIME ZONE 'UTC' AS DATE) = CAST(DATEADD(DAY, -1, GETUTCDATE()) AS DATE)
    GROUP BY
        CAST(q.created_at AT TIME ZONE 'UTC' AS DATE),
        q.app_context,
        g.model_name,
        q.retrieval_strategy,
        q.total_latency_ms
) AS source
ON  target.metric_date        = source.metric_date
AND target.app_context        = source.app_context
AND target.model_name         = source.model_name
AND target.retrieval_strategy = source.retrieval_strategy
WHEN MATCHED THEN UPDATE SET
    total_queries      = source.total_queries,
    avg_faithfulness   = source.avg_faithfulness,
    avg_relevance      = source.avg_relevance,
    avg_context_recall = source.avg_context_recall,
    thumbs_up_count    = source.thumbs_up_count,
    thumbs_down_count  = source.thumbs_down_count,
    avg_retrieval_ms   = source.avg_retrieval_ms,
    avg_generation_ms  = source.avg_generation_ms,
    p95_total_ms       = source.p95_total_ms
WHEN NOT MATCHED THEN INSERT (
    metric_date, app_context, model_name, retrieval_strategy,
    total_queries, avg_faithfulness, avg_relevance, avg_context_recall,
    thumbs_up_count, thumbs_down_count, avg_retrieval_ms, avg_generation_ms, p95_total_ms
) VALUES (
    source.metric_date, source.app_context, source.model_name, source.retrieval_strategy,
    source.total_queries, source.avg_faithfulness, source.avg_relevance, source.avg_context_recall,
    source.thumbs_up_count, source.thumbs_down_count, source.avg_retrieval_ms,
    source.avg_generation_ms, source.p95_total_ms
);

19.8 Partitioning for Long-Running Systems

A RAG system that handles meaningful query volume will accumulate millions of rows in rag_queries and rag_retrieval_results within months. Without partitioning, your analytical queries will start to slow down even with good indexes, because PostgreSQL must scan through older data that is rarely touched. The solution is range partitioning on created_at, which lets the planner skip entire months of data when your queries filter by date — which nearly all of them do.

-- PostgreSQL
-- Convert rag_queries to a partitioned table (run during initial setup,
-- or use pg_partman to migrate an existing table online)

-- Drop the existing table and recreate as partitioned
-- In production you would migrate data, not drop it. This shows the DDL shape.

CREATE TABLE rag_queries_partitioned (
    query_id              UUID NOT NULL DEFAULT uuid_generate_v4(),
    session_id            UUID,
    query_text            TEXT NOT NULL,
    query_embedding       VECTOR(1536),
    query_embedding_model TEXT NOT NULL,
    rewritten_query       TEXT,
    intent_label          TEXT,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    retrieval_strategy    TEXT NOT NULL,
    top_k                 INT NOT NULL,
    similarity_threshold  FLOAT,
    retrieval_latency_ms  INT,
    generation_latency_ms INT,
    total_latency_ms      INT,
    app_context           TEXT NOT NULL,
    PRIMARY KEY (query_id, created_at)    -- partition key must be in PK
) PARTITION BY RANGE (created_at);

-- Create monthly partitions (automate this with pg_partman in production)
CREATE TABLE rag_queries_2025_01
    PARTITION OF rag_queries_partitioned
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

CREATE TABLE rag_queries_2025_02
    PARTITION OF rag_queries_partitioned
    FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

CREATE TABLE rag_queries_2025_03
    PARTITION OF rag_queries_partitioned
    FOR VALUES FROM ('2025-03-01') TO ('2025-04-01');

-- Indexes are created per partition — the planner uses partition pruning
-- to skip months automatically when queries filter on created_at
CREATE INDEX ON rag_queries_2025_01 (created_at DESC);
CREATE INDEX ON rag_queries_2025_02 (created_at DESC);
CREATE INDEX ON rag_queries_2025_03 (created_at DESC);

For teams that do not want to manage partition creation manually, pg_partman automates this:

19.9 Connecting Evaluation Data to Your Document Pipeline

The feedback loop is only as strong as its connection back to the document pipeline. When a chunk is flagged by check_chunk_quality or the nightly run_feedback_loop, something has to happen to that chunk in the source document system. The two most common actions are re-chunking (splitting or merging the problematic chunk differently) and re-embedding (regenerating the embedding with a newer model or after the chunk text has been corrected).

The following SQL procedure coordinates both actions by reading from the document_chunks table, applying the correction, and writing the result back — all within a single transaction so that the chunk is never in a partially updated state.

-- PostgreSQL
-- Stored procedure: re-embed a flagged chunk and clear the review flag
-- Called by the document pipeline after a human reviewer approves a correction

CREATE OR REPLACE PROCEDURE reembed_flagged_chunk(
    p_chunk_id          UUID,
    p_new_embedding     VECTOR(1536),
    p_new_chunk_text    TEXT DEFAULT NULL,   -- NULL means keep existing text
    p_reviewer          TEXT DEFAULT NULL
)
LANGUAGE plpgsql AS $$
DECLARE
    v_old_embedding VECTOR(1536);
BEGIN
    -- Snapshot the old embedding before overwriting
    SELECT embedding INTO v_old_embedding
    FROM document_chunks
    WHERE chunk_id = p_chunk_id
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'chunk_id % not found', p_chunk_id;
    END IF;

    -- Update the chunk
    UPDATE document_chunks SET
        embedding          = p_new_embedding,
        chunk_text         = COALESCE(p_new_chunk_text, chunk_text),
        needs_review       = FALSE,
        review_reason      = NULL,
        review_flagged_at  = NULL,
        last_reembedded_at = NOW(),
        reembedding_count  = COALESCE(reembedding_count, 0) + 1
    WHERE chunk_id = p_chunk_id;

    -- Audit trail: record what changed
    INSERT INTO chunk_embedding_history (
        chunk_id, old_embedding, new_embedding,
        changed_at, changed_by, change_reason
    ) VALUES (
        p_chunk_id, v_old_embedding, p_new_embedding,
        NOW(), p_reviewer, 'flagged_review_reembed'
    );

    COMMIT;
END;
$$;

-- Supporting audit table
CREATE TABLE chunk_embedding_history (
    history_id      UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    chunk_id        UUID NOT NULL,
    old_embedding   VECTOR(1536),
    new_embedding   VECTOR(1536),
    changed_at      TIMESTAMPTZ DEFAULT NOW(),
    changed_by      TEXT,
    change_reason   TEXT
);

CREATE INDEX idx_chunk_history_chunk ON chunk_embedding_history(chunk_id);
CREATE INDEX idx_chunk_history_changed ON chunk_embedding_history(changed_at DESC);

The Python side of the re-embedding workflow shows how to call the stored procedure after generating a fresh embedding:

# reembed_flagged_chunks.py — process the review queue

@celery_app.task
def process_review_queue(batch_size: int = 20):
    """
    Pull flagged chunks, re-embed them, and call the stored procedure.
    Runs as a daily Celery task after human reviewers have approved corrections.
    """
    conn = get_db()
    with conn.cursor(cursor_factory=psycopg2.extras.DictCursor) as cur:
        cur.execute(
            """
            SELECT chunk_id, chunk_text, review_reason
            FROM document_chunks
            WHERE needs_review = TRUE
              AND review_reason IN ('accumulated_negative_feedback',
                                    'low_faithfulness_window')
            ORDER BY review_flagged_at ASC
            LIMIT %s
            FOR UPDATE SKIP LOCKED
            """,
            (batch_size,),
        )
        flagged = cur.fetchall()

    for chunk in flagged:
        try:
            # Generate a fresh embedding with the current model
            new_embedding = embed_text(
                chunk["chunk_text"], model="text-embedding-3-small"
            )
            embedding_str = "[" + ",".join(str(x) for x in new_embedding) + "]"

            # Call the stored procedure
            with conn.cursor() as cur:
                cur.execute(
                    "CALL reembed_flagged_chunk(%s, %s::vector, %s, %s)",
                    (
                        chunk["chunk_id"],
                        embedding_str,
                        None,           # keep existing text
                        "auto_reembed",
                    ),
                )
                # CALL with COMMIT inside the procedure; no explicit commit needed here
        except Exception as e:
            # Log and continue — don't let one bad chunk block the batch
            print(f"Failed to re-embed chunk {chunk['chunk_id']}: {e}")

    conn.close()
    return {"processed": len(flagged)}

19.10 Putting It All Together: The Evaluation Architecture

The components built across this chapter form a coherent system with clear data flow. Here is how the pieces connect at runtime:

1. Request path (synchronous, latency-sensitive): RAGPipeline.run() embeds the query, retrieves chunks, writes rag_queries and rag_retrieval_results, calls the LLM, writes rag_generations, and returns the answer. The entire synchronous path avoids any LLM evaluation work.

2. Evaluation path (asynchronous, seconds to minutes later): The evaluate_generation Celery task calls GPT-4o-mini as a judge, writes faithfulness_score, relevance_score, context_recall, and answer_correctness back to rag_generations.

3. User feedback path (event-driven): The /feedback FastAPI endpoint records rag_feedback, fires pg_notify on negative signals, and the background listener dispatches check_chunk_quality to inspect the involved chunks.

4. Scheduled maintenance path (hourly and nightly): run_feedback_loop collects rewrite candidates, flags degraded chunks, and fires alerts. rollup_daily_metrics aggregates into rag_daily_metrics for fast dashboard queries.

5. Document correction path (human-in-the-loop): A reviewer inspects flagged chunks, approves corrections, and triggers process_review_queue, which re-embeds and clears the review flag via the reembed_flagged_chunk stored procedure.

graph TD
    A[RAGPipeline.run] -->|sync| B[(rag_queries + rag_retrieval_results + rag_generations)]
    B -->|async, seconds later| C[evaluate_generation: LLM-as-judge]
    C --> B
    D["/feedback endpoint"] -->|sync| E[(rag_feedback)]
    E -->|pg_notify on negative signal| F[check_chunk_quality]
    F -->|flags chunk| G[(document_chunks.needs_review)]
    H[run_feedback_loop: hourly] --> B
    H --> G
    H --> I[(rag_alerts)]
    J[rollup_daily_metrics: nightly] --> B
    J --> K[(rag_daily_metrics)]
    G --> L[Human reviewer approves correction]
    L --> M[process_review_queue]
    M --> N[reembed_flagged_chunk procedure]
    N --> G

*Five paths — request, async evaluation, user feedback, scheduled maintenance, and document correction — all reading from and writing back to the same PostgreSQL tables.*

The result is a system that degrades gracefully — a hallucinating chunk accumulates negative signals, gets flagged automatically, and is re-embedded with minimal human intervention, while the analytical tables give you the visibility to prioritize which documents need attention first.

One operational detail worth naming: the evaluation scores written by evaluate_generation are themselves noisy. LLM-as-judge is a useful signal but not a ground truth. The architecture treats automated scores as a filter that surfaces candidates for human review, not as a final verdict. When faithfulness_score drops below 0.60 on a chunk, that is a flag to look at it — not a guarantee that the chunk is wrong. The combination of automated scoring plus user thumbs plus human review creates a multi-signal system that is more reliable than any single signal alone.

Key Takeaways

  • → **Store the full causal chain.** A RAG evaluation schema needs to link query embeddings, retrieved chunks with their ranks and scores, LLM responses, automated evaluation metrics, and user feedback in a single queryable hierarchy. Collapsing any layer makes root-cause analysis impossible.
  • → **Separate the synchronous and asynchronous paths.** LLM-as-judge evaluation is too slow and expensive to block the user response. Write the core rows synchronously and dispatch evaluation work to a task queue; the latency difference to your users is significant and the data arrives in the background within seconds.
  • → **User feedback and automated scores are complementary, not redundant.** Automated faithfulness scores catch hallucinations that users miss because the answer sounds confident. User thumbs-down signals catch failures that automated metrics miss because the answer is technically grounded but unhelpful. Both signals are needed.
  • → **PostgreSQL's relational model makes evaluation a join problem.** Identifying which chunks consistently appear in low-rated responses, comparing retrieval strategies by downstream quality, detecting embedding drift, and running A/B experiments all reduce to standard SQL aggregations and window functions over the evaluation tables — capabilities that purpose-built vector stores do not provide.
  • → **Close the loop back to the document pipeline.** Flagging a chunk is only useful if the flag triggers a re-embedding or content correction. The `reembed_flagged_chunk` stored procedure and `process_review_queue` task complete the cycle: bad retrieval data surfaces through feedback, gets flagged automatically, and is corrected in the source corpus without requiring manual database surgery.
