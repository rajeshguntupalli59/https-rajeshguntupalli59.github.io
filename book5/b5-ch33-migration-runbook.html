Chapter 33: Database Migration to Cloud: Practical Runbook

Migration is where cloud theory meets operational reality. You have spent months planning your cloud architecture, selecting instance types, designing VPC topology, and writing Terraform modules. Now someone hands you a production Oracle 19c database, a legacy SQL Server 2012 instance, or a PostgreSQL 14 cluster running on bare metal, and says: get it to cloud without losing data and without a multi-hour outage. This chapter is the runbook for that moment. It covers the full migration lifecycle from assessment through cutover — using AWS DMS, the Schema Conversion Tool, Azure Database Migration Service, and GCP Database Migration Service — with the specific commands, gotchas, and production patterns that experienced DBAs need when the pressure is on.

---

33.1 Migration Assessment: Knowing What You're Moving Before You Move It

The single most common migration failure mode is discovering surprises during execution rather than during planning. A migration that looks like a simple database lift-and-shift often hides Oracle DBMS packages, SQL Server Agent jobs, linked server dependencies, or stored procedures that reference system tables unavailable in managed services. Your assessment phase exists to eliminate those surprises.

Inventory What Managed Services Cannot Replicate

Before touching a migration tool, build an explicit incompatibility list. Managed RDS, Azure SQL, and Cloud SQL impose hard restrictions that self-managed databases do not:

  • → RDS PostgreSQL: no `pg_hba.conf` direct edit, no superuser, no OS-level extensions not on the approved list, no `wal_level = logical` on read replicas by default
  • → Azure SQL (PaaS): no SQL Agent with full capability (use Elastic Jobs instead), no linked servers to on-prem without Azure Arc, no `xp_cmdshell`, no CLR assemblies without explicit opt-in
  • → Cloud SQL PostgreSQL: no superuser, no `pg_basebackup` direct access, limited extension list per engine version
  • → Aurora PostgreSQL: `rds_superuser` role replaces `postgres` superuser; `aurora_replica_status()` replaces direct `pg_stat_replication` in some contexts

    • AWS provides the Schema Conversion Tool (SCT) for automated incompatibility scanning. Run it even for homogeneous migrations — PostgreSQL to Aurora PostgreSQL — because it catches version-specific function differences.

    # Install AWS SCT CLI wrapper and run an assessment report
# SCT itself is a GUI tool, but you can script it via its project files
# First, install SCT from: https://docs.aws.amazon.com/SchemaConversionTool/

# Generate an assessment report using SCT command line
java -jar aws-schema-conversion-tool.jar \

    Gather Baseline Metrics Before Migration

    You cannot validate a successful migration without knowing what normal looks like on the source. Capture these metrics at least two weeks before cutover:

    | Metric | Why It Matters |

    |---|---|

    | Peak TPS and QPS | Determines target instance class |

    | 95th percentile query latency | Post-migration baseline for regression detection |

    | Replication lag (if HA) | Sets your DMS replication lag acceptance threshold |

    | Database size + growth rate per week | Determines migration window length and storage provisioning |

    | Active connections at peak | Informs RDS Proxy or Azure connection pool sizing |

    | Long-running transactions (> 60 seconds) | DMS and logical replication will struggle with these |

    -- Run on source PostgreSQL to gather migration sizing data
-- Capture database sizes
SELECT
    datname AS database_name,
    pg_size_pretty(pg_database_size(datname)) AS size,
    pg_database_size(datname) AS size_bytes
FROM pg_database
WHERE datistemplate = FALSE
ORDER BY size_bytes DESC;

-- Identify tables that will cause DMS problems: no primary key
SELECT
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS total_size
FROM pg_tables t
WHERE NOT EXISTS (
    SELECT 1 FROM pg_constraint c
    JOIN pg_class cl ON c.conrelid = cl.oid
    JOIN pg_namespace n ON cl.relnamespace = n.oid
    WHERE c.contype = 'p'
      AND n.nspname = t.schemaname
      AND cl.relname = t.tablename
)
AND schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(schemaname || '.' || tablename) DESC;

-- Find objects with dependencies that may not migrate cleanly
SELECT
    dependent_ns.nspname AS dependent_schema,
    dependent_view.relname AS dependent_view,
    source_ns.nspname AS source_schema,
    source_table.relname AS source_table
FROM pg_depend
JOIN pg_rewrite ON pg_depend.objid = pg_rewrite.oid
JOIN pg_class AS dependent_view ON pg_rewrite.ev_class = dependent_view.oid
JOIN pg_class AS source_table ON pg_depend.refobjid = source_table.oid
JOIN pg_namespace dependent_ns ON dependent_ns.oid = dependent_view.relnamespace
JOIN pg_namespace source_ns ON source_ns.oid = source_table.relnamespace
WHERE source_table.relkind = 'r'
AND dependent_view.relname != source_table.relname
ORDER BY 1, 2;

    Migration Strategy Selection

    Match your strategy to your downtime budget:

    | Strategy | Downtime | Complexity | Use Case |

    |---|---|---|---|

    | Dump and restore | Hours to days | Low | Small databases < 50 GB, scheduled maintenance |

    | AWS DMS full load + CDC | Minutes | Medium | Databases up to several TB with minimal downtime requirement |

    | Logical replication (pg_logical / pglogical) | Minutes | Medium-High | PostgreSQL to PostgreSQL with full control |

    | Physical snapshot + DMS CDC | Minutes | High | Large databases > 500 GB where full DMS load is too slow |

    | AWS DataSync + DMS | Minutes | High | Very large databases with NFS/SFTP accessible backups |

    For most production migrations, the physical snapshot seeding approach is optimal at scale: restore a backup to the target, then use DMS or logical replication for CDC to catch up the delta, then cut over.

    33.2 AWS DMS: Full Load and Change Data Capture

    AWS Database Migration Service handles the replication engine so you do not have to manage Debezium, pglogical, or custom trigger-based CDC infrastructure. The trade-off is that DMS runs on managed replication instances that you cannot SSH into, and its behavior with edge cases — LOB columns, tables without primary keys, DDL changes mid-migration — requires explicit configuration.

    Provision the DMS Infrastructure with Terraform

    # terraform/dms-migration.tf
# Replication instance — this is the compute that runs DMS tasks
resource "aws_dms_replication_instance" "migration" {
  replication_instance_id     = "prod-migration-ri"
  replication_instance_class  = "dms.r6i.2xlarge"  # 8 vCPU, 64 GB — suitable for most production loads
  allocated_storage           = 500                  # GB — DMS uses this for LOB caching and logs
  engine_version              = "3.5.2"
  multi_az                    = false               # Single AZ is fine during migration; this is not HA production
  publicly_accessible         = false
  vpc_security_group_ids      = [aws_security_group.dms_sg.id]
  replication_subnet_group_id = aws_dms_replication_subnet_group.migration.id

  tags = {
    Environment = "migration"
    Project     = "db-to-cloud"
  }
}

# Source endpoint — on-premises PostgreSQL
resource "aws_dms_endpoint" "source_pg" {
  endpoint_id   = "onprem-postgres-source"
  endpoint_type = "source"
  engine_name   = "postgres"

  server_name   = "10.0.1.50"  # Internal IP of source DB, reachable via Direct Connect or VPN
  port          = 5432
  database_name = "prod_db"
  username      = "dms_replication_user"
  password      = var.source_db_password  # Store in AWS Secrets Manager, reference here

  extra_connection_attributes = join(";", [
    "pluginName=pglogical",         # Use pglogical plugin for CDC
    "heartbeatEnable=true",
    "heartbeatFrequency=5",
    "heartbeatSchema=dms_heartbeat",  # Schema must exist on source
    "captureDDLs=false",              # Disable DDL capture — apply schema changes manually

  ssl_mode = "require"
}

# Target endpoint — Aurora PostgreSQL cluster
resource "aws_dms_endpoint" "target_aurora" {
  endpoint_id   = "aurora-pg-target"
  endpoint_type = "target"
  engine_name   = "aurora-postgresql"

  port          = 5432

      {
        rule-type = "selection"
        rule-id   = "1"
        rule-name = "include-all-tables"
        object-locator = {
          schema-name = "public"
          table-name  = "%"
        }
        rule-action = "include"

      {
        # Exclude audit/log tables that are too large and not needed on target
        rule-type = "selection"
        rule-id   = "2"
        rule-name = "exclude-audit-tables"
        object-locator = {
          schema-name = "public"
          table-name  = "audit_%"
        }
        rule-action = "exclude"
      }
    ]

  replication_task_settings = jsonencode({
    TargetMetadata = {
      TargetSchema              = ""

      LimitedSizeLobMode        = true
      LobMaxSize                = 32768   # 32 MB max LOB size in limited mode
    }
    FullLoadSettings = {
      TargetTablePrepMode       = "DROP_AND_CREATE"  # Safe for initial load; change to DO_NOTHING for reseeding
      CreatePkAfterFullLoad     = true               # Apply PKs after load for performance
      StopTaskCachedChangesApplied = false
      StopTaskCachedChangesNotApplied = false
      MaxFullLoadSubTasks       = 8                  # Parallel table loads
      TransactionConsistencyTimeout = 600
      CommitRate                = 50000              # Rows per commit in full load
    }
    Logging = {
      EnableLogging = true
      LogComponents = [
        { Id = "SOURCE_UNLOAD", Severity = "LOGGER_SEVERITY_DEFAULT" },
        { Id = "TARGET_LOAD",   Severity = "LOGGER_SEVERITY_DEFAULT" },
        { Id = "TASK_MANAGER",  Severity = "LOGGER_SEVERITY_DEFAULT" }
      ]
    }
    ControlTablesSettings = {
      historyTimeslotInMinutes  = 5
      StatusTableEnabled        = true
      SuspendedTablesTableEnabled = true

    Prepare the Source PostgreSQL for DMS Logical Replication

    DMS requires logical replication to be enabled on the source and a replication user with appropriate privileges. On self-managed PostgreSQL, you control this directly. On RDS PostgreSQL source (if migrating between RDS instances), the parameter group controls it.

    -- On source PostgreSQL (self-managed): enable logical replication
-- Edit postgresql.conf or run as superuser:
ALTER SYSTEM SET wal_level = 'logical';
ALTER SYSTEM SET max_replication_slots = 10;
ALTER SYSTEM SET max_wal_senders = 10;
-- Requires a restart:
-- SELECT pg_reload_conf(); -- Only for parameters that don't require restart

-- Create the DMS replication user with minimum required privileges
CREATE USER dms_replication_user WITH
    REPLICATION
    LOGIN
    PASSWORD 'strong_password_here';

-- Grant access to all tables DMS needs to replicate
GRANT CONNECT ON DATABASE prod_db TO dms_replication_user;
GRANT USAGE ON SCHEMA public TO dms_replication_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dms_replication_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO dms_replication_user;

-- Create heartbeat schema for DMS health checks
CREATE SCHEMA IF NOT EXISTS dms_heartbeat;
GRANT ALL ON SCHEMA dms_heartbeat TO dms_replication_user;

-- If using pglogical plugin (recommended over test_decoding for production):
CREATE EXTENSION IF NOT EXISTS pglogical;

-- Verify logical replication is active
SELECT slot_name, plugin, slot_type, active, restart_lsn
FROM pg_replication_slots;

-- Monitor DMS replication lag during migration
SELECT
    slot_name,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS replication_lag_size,
    active,
    active_pid
FROM pg_replication_slots
WHERE slot_type = 'logical';

    Critical DMS Gotchas in Production

    DMS has a set of well-documented limitations that will surprise you the first time they surface at 2 AM:

    *Tables without primary keys* fall back to full-table scans for CDC, which is catastrophically slow on large tables. Run the assessment query from section 33.1 to identify these before starting. Either add surrogate primary keys to the source before migration or exclude these tables from CDC and migrate them separately at cutover.

    *LOB column handling* in limited LOB mode will silently truncate data exceeding your LobMaxSize setting. Set it conservatively high and verify with a row count and checksum comparison after full load.

    *DDL changes during CDC* — DMS does not replicate DDL by default for PostgreSQL sources. If your source application runs ALTER TABLE during the migration window, you must apply those DDL changes manually to the target and then resume replication. This is one strong argument for freeze windows on schema changes during migration.

    *DMS does not migrate sequences*. After full load completes, manually synchronize sequence values:

    -- Run on source after full load completes, before cutover
-- Generate sequence synchronization statements
SELECT
    'SELECT setval(''' || schemaname || '.' || sequencename ||
    ''', COALESCE((SELECT MAX(' || quote_ident(a.attname) ||
    ') FROM ' || schemaname || '.' || tablename || '), 1), true);' AS sync_command
FROM pg_sequences s
JOIN pg_class c ON c.relname = s.sequencename
JOIN pg_depend d ON d.objid = c.oid
JOIN pg_class ct ON d.refobjid = ct.oid
JOIN pg_attribute a ON a.attrelid = ct.oid AND a.attnum = d.refobjsubid
JOIN pg_tables t ON t.tablename = ct.relname AND t.schemaname = s.schemaname
WHERE s.schemaname = 'public';

-- Execute each of those statements on the TARGET Aurora instance
-- This is typically a 5-10 minute manual step during cutover

    33.3 Azure Database Migration Service and SQL Server Migration

    When moving SQL Server workloads to Azure SQL — either Azure SQL Database, Azure SQL Managed Instance, or SQL Server on Azure VM — the Azure Database Migration Service (DMS) handles the heavy lifting. The key architectural decision you make before starting is whether your target is Azure SQL Database (PaaS, fully managed, most restrictive), Azure SQL Managed Instance (PaaS, near-full SQL Server compatibility, fewer restrictions), or SQL Server on Azure VM (IaaS, full control, your responsibility for patching and HA).

    For most enterprise SQL Server migrations, Azure SQL Managed Instance is the right target: it supports SQL Agent, cross-database queries, linked servers, CLR, Service Broker, and the full SQL Server surface area — things Azure SQL Database does not. The trade-off is cost; Managed Instance is more expensive.

    Assess Compatibility Before Running DMS

    The Data Migration Assistant (DMA) is your pre-migration assessment tool. Run it against every source SQL Server database:

    # Azure DMA is a Windows GUI tool, but you can automate assessments via its command line
# Install: https://www.microsoft.com/en-us/download/details.aspx?id=53595

# Run DMA assessment (from Windows command prompt or PowerShell)
"C:\Program Files\Microsoft Data Migration Assistant\DmaCmd.exe" `
  /AssessmentName="ProdDBAssessment" `
  /AssessmentSourcePlatform=SqlServer `
  /AssessmentTargetPlatform=AzureSqlDatabaseManagedInstance `
  /AssessmentDatabases="Server=onprem-sql.internal;Initial Catalog=ProdDB;User Id=dma_user;Password=$env:DMA_PASSWORD" `
  /AssessmentEvaluateCompatibilityIssues=True `
  /AssessmentEvaluateFeatureParity=True `
  /AssessmentOverwriteResult=True `
  /AssessmentResultJson="C:\Reports\assessment-result.json"

# Parse results to get action items
python parse_dma_results.py --input C:\Reports\assessment-result.json
    # parse_dma_results.py — Extract blocking issues from DMA output
import json
import sys
from pathlib import Path

def parse_dma_report(report_path: str) -> None:
    with open(report_path) as f:
        report = json.load(f)

    blocking_issues = []
    warning_issues = []

    for server_report in report.get("serverReports", []):
        for db_report in server_report.get("databaseReports", []):
            db_name = db_report.get("databaseName")

            for category in db_report.get("items", []):
                for rule_result in category.get("ruleResults", []):
                    severity = rule_result.get("severity", "")
                    title = rule_result.get("title", "")
                    impact = rule_result.get("impact", "")
                    affected_objects = [
                        obj.get("name") for obj in rule_result.get("affectedObjects", [])
                    ]

                    entry = {
                        "database": db_name,
                        "title": title,
                        "impact": impact,
                        "affected_objects": affected_objects[:5],  # Top 5
                        "total_affected": len(affected_objects)
                    }

                    if severity == "Breaking":
                        blocking_issues.append(entry)
                    elif severity == "Warning":
                        warning_issues.append(entry)

    print(f"\n{'='*60}")
    print(f"BLOCKING ISSUES ({len(blocking_issues)}) — Must fix before migration:")
    print(f"{'='*60}")
    for issue in blocking_issues:
        print(f"\n[{issue['database']}] {issue['title']}")
        print(f"  Impact: {issue['impact']}")
        print(f"  Affected objects ({issue['total_affected']}): {', '.join(issue['affected_objects'])}")

    print(f"\n{'='*60}")
    print(f"WARNINGS ({len(warning_issues)}) — Review post-migration:")
    print(f"{'='*60}")
    for issue in warning_issues[:10]:  # Show top 10 warnings
        print(f"\n[{issue['database']}] {issue['title']}")

if __name__ == "__main__":
    parse_dma_report(sys.argv[1])

    Prepare the Source SQL Server for Online Migration

    Online migration to SQL MI requires full recovery model and a recent full backup. These are baseline requirements, but there are additional source-side preparations that prevent mid-migration failures:

    -- Run on source SQL Server: pre-migration preparation

-- 1. Verify databases are in FULL recovery model
SELECT name, recovery_model_desc
FROM sys.databases
WHERE name NOT IN ('master', 'model', 'msdb', 'tempdb')
ORDER BY name;

-- Fix any databases not in FULL recovery
-- ALTER DATABASE [ProdDB] SET RECOVERY FULL;

-- 2. Check for deprecated features that DMA flagged
-- Text/NText/Image columns -- must be aware of migration behavior
SELECT
    t.name AS table_name,
    c.name AS column_name,
    ty.name AS data_type
FROM sys.columns c
JOIN sys.tables t ON c.object_id = t.object_id
JOIN sys.types ty ON c.user_type_id = ty.user_type_id
WHERE ty.name IN ('text', 'ntext', 'image')
  AND t.is_ms_shipped = 0
ORDER BY t.name, c.name;

-- 3. Find linked servers that will break after migration
SELECT
    name AS linked_server_name,
    product,
    provider,
    data_source,
    is_remote_login_enabled,
    modify_date
FROM sys.servers
WHERE is_linked = 1
ORDER BY name;

-- 4. Identify SQL Agent jobs and their schedules
SELECT
    j.name AS job_name,
    j.enabled,
    j.description,
    c.name AS category,
    l.name AS owner,
    j.date_modified
FROM msdb.dbo.sysjobs j
JOIN msdb.dbo.syscategories c ON j.category_id = c.category_id
JOIN sys.syslogins l ON j.owner_sid = l.sid
ORDER BY j.name;

-- 5. Check current log backup chain — DMS needs an unbroken chain
-- If log backups have gaps, you need a new full backup
EXEC sp_helpdb 'ProdDB';

-- 6. Identify certificates and asymmetric keys (TDE, encrypted objects)
SELECT
    name,
    certificate_id,
    pvt_key_encryption_type_desc,
    is_active_for_begin_dialog
FROM sys.certificates
WHERE database_id = DB_ID('ProdDB');

-- If TDE is enabled, export the certificate BEFORE migration

    Monitor Azure DMS Migration Progress

    # Poll migration task status
watch_migration() {
    local RESOURCE_GROUP="rg-migration"
    local SERVICE="prod-migration-dms"
    local PROJECT="sql-to-mi-project"
    local TASK="online-migration-task"

    while true; do
        STATUS=$(az dms task show \
            --resource-group "${RESOURCE_GROUP}" \
            --service-name "${SERVICE}" \
            --project-name "${PROJECT}" \
            --name "${TASK}" \
            --expand output \
            --query "output[0].migrationState" \
            --output tsv 2>/dev/null)

        LAG=$(az dms task show \
            --resource-group "${RESOURCE_GROUP}" \
            --service-name "${SERVICE}" \
            --project-name "${PROJECT}" \
            --name "${TASK}" \
            --expand output \
            --query "output[0].databaseSummary.ProdDB.cdcLatency" \
            --output tsv 2>/dev/null)

        echo "[$(date '+%H:%M:%S')] State: ${STATUS} | CDC Lag: ${LAG}s"

        if [[ "${STATUS}" == "ReadyForCutover" ]]; then
            echo ">>> MIGRATION IS READY FOR CUTOVER <<<"
            break
        fi

        sleep 30
    done
}

watch_migration

# Initiate cutover when ready
az dms task cutover \
    --resource-group rg-migration \
    --service-name prod-migration-dms \
    --project-name sql-to-mi-project \
    --name online-migration-task \
    --object-name ProdDB

    33.4 GCP Database Migration Service

    Google Cloud's Database Migration Service (DMS) is the youngest of the three major cloud DMS offerings. It supports PostgreSQL-to-Cloud SQL PostgreSQL, MySQL-to-Cloud SQL MySQL, and PostgreSQL/Oracle-to-AlloyDB migrations. Its setup model differs from AWS and Azure DMS in one important way: connectivity to the source is managed through a *connection profile*, and you can route traffic through a reverse-SSH tunnel, VPN, or VPC peering — which is particularly useful when your source environment does not permit inbound connections from the cloud.

    Create a GCP DMS Migration Job via gcloud

    # Set project and region
gcloud config set project your-project-id
REGION="us-central1"
SOURCE_IP="10.0.1.50"   # On-prem PostgreSQL IP, reachable via Cloud VPN or Interconnect

# 1. Create the source connection profile
# --password with no value will prompt interactively — use Secret Manager in CI/CD
gcloud database-migration connection-profiles create postgresql \
  --region="${REGION}" \
  --connection-profile-id="onprem-pg-source" \
  --host="${SOURCE_IP}" \
  --port=5432 \
  --username="migration_user" \
  --password \
  --database-service="postgres" \
  --display-name="On-Prem PostgreSQL Source"

# 2. Create the destination connection profile (Cloud SQL instance)
gcloud database-migration connection-profiles create cloudsql \
  --region="${REGION}" \
  --connection-profile-id="cloudsql-pg-target" \
  --cloudsql-instance-id="prod-cloudsql-pg" \
  --display-name="Cloud SQL PostgreSQL Target"

# 3. Create the migration job (continuous / minimal downtime)
gcloud database-migration migration-jobs create \
  --region="${REGION}" \
  --migration-job-id="prod-pg-migration" \
  --source="onprem-pg-source" \
  --destination="cloudsql-pg-target" \
  --type=CONTINUOUS \
  --display-name="Production PostgreSQL Migration" \
  --dump-path="gs://your-migration-bucket/pg-dump/"
  # --dump-path is for initial seeding from a Cloud Storage dump;
  # omit to let DMS perform the initial dump automatically

# 4. Verify connectivity before starting
gcloud database-migration migration-jobs verify \
  --region="${REGION}" \
  --migration-job-id="prod-pg-migration"

# Expected output includes per-check pass/fail — fix any FAIL before proceeding
# Common failures: firewall rules blocking DMS egress IPs, wal_level not set to logical,
# replication user lacks REPLICATION privilege

# 5. Start the migration
gcloud database-migration migration-jobs start \
  --region="${REGION}" \
  --migration-job-id="prod-pg-migration"

# 6. Monitor status
gcloud database-migration migration-jobs describe \
  --region="${REGION}" \
  --migration-job-id="prod-pg-migration" \
  --format="yaml(state, phase, error, duration)"

    -- On source PostgreSQL for GCP DMS:

-- Required parameter settings (edit postgresql.conf or use ALTER SYSTEM)
ALTER SYSTEM SET wal_level = 'logical';

-- On managed sources (like RDS), use rds_superuser grant if applicable

GRANT SELECT ON ALL TABLES IN SCHEMA public TO gcp_dms_user;

GRANT USAGE ON SCHEMA public TO gcp_dms_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO gcp_dms_user;

-- pglogical also needs SELECT on pg_catalog system tables — superuser handles this
-- For non-superuser, grant replication role privilege:
GRANT pg_read_all_data TO gcp_dms_user;  -- PostgreSQL 14+

    33.5 Cutover Runbook: The Final 60 Minutes

    The migration tools handle data movement. Cutover is where you transition application traffic. A poorly executed cutover causes data loss or extended downtime even when the underlying migration was perfect. This section is a scripted runbook — execute each step in order, with named owners and time checkpoints.

    Pre-Cutover Checklist (T-48 hours)

    [ ] All blocking DMA/SCT issues resolved and tested on target
[ ] Application connection strings tested against target database (read-only smoke test)
[ ] DNS TTLs reduced to 60 seconds (they were at 300+ before — change 48h ahead)
[ ] Backup taken of source database within 24h of cutover
[ ] Rollback plan documented and tested (see section 33.6)
[ ] Monitoring alerts configured on target instance (CPU, connections, replication lag)
[ ] On-call rotation confirmed with names and phone numbers
[ ] Schema change freeze in effect on source (no DDL until post-cutover)
[ ] Sequence values audited — sync script ready to execute
[ ] All DMS/migration job metrics reviewed: no errors, lag < 10 seconds
    graph TD
    A[1. Verify replication
    lag under 5s] --> B[2. Enable app
    maintenance mode]
    B --> C[3. Confirm source
    quiesced, no writes]
    C --> D[4. Synchronize
    sequences]
    D --> E[5. Validate row

    *Each step gates the next — this is also the sequence a rollback must unwind if smoke tests fail within the first hour.*

    Cutover Execution (T-0)

    #!/bin/bash
# cutover.sh — Execute with two DBAs present: one driving, one verifying
# Time each step and log to a shared document in real time

set -euo pipefail
LOGFILE="/tmp/cutover-$(date +%Y%m%d-%H%M).log"
exec > >(tee -a "${LOGFILE}") 2>&1

log_step() {
    echo ""
    echo "=========================================="
    echo "[$(date '+%H:%M:%S')] STEP: $1"
    echo "=========================================="
}

#--- STEP 1: Final validation of replication lag ---#
log_step "1. Verify replication lag < 5 seconds"

# For AWS DMS:
aws dms describe-replication-tasks \
    --filters Name=replication-task-id,Values=prod-full-load-cdc \
    --query 'ReplicationTasks[0].{Status:Status,CDCLatencyTarget:CDCLatencyTarget,CDCLatencySource:CDCLatencySource}' \
    --output table

# For GCP DMS:
# gcloud database-migration migration-jobs describe --region=us-central1 --migration-job-id="prod-pg-migration"

echo "Confirm lag is acceptable before proceeding. Press ENTER to continue or Ctrl+C to abort."
read -r

#--- STEP 2: Put application in maintenance mode ---#
log_step "2. Enable maintenance mode on application"
# This is application-specific — examples:
# - Set load balancer target group to maintenance page
# - Toggle feature flag in config service
# - Scale down application pods to 0
#   kubectl scale deployment app-deployment --replicas=0 -n production

echo "Application maintenance mode enabled. Confirm no new writes to source. Press ENTER."
read -r

#--- STEP 3: Verify zero active write transactions on source ---#
log_step "3. Confirm source is quiesced (no active writes)"

# PostgreSQL source
psql -h "${SOURCE_HOST}" -U dba_user -d prod_db -c "
SELECT count(*) AS active_write_transactions
FROM pg_stat_activity
WHERE state = 'active'
  AND query !~ '^(SELECT|SHOW|EXPLAIN|--)'
  AND backend_type = 'client backend'
  AND pid != pg_backend_pid();
"

# SQL Server source
# sqlcmd -S "${SOURCE_SQL_HOST}" -U dba_user -Q "
# SELECT COUNT(*) AS active_write_spids
# FROM sys.dm_exec_sessions s
# JOIN sys.dm_exec_requests r ON s.session_id = r.session_id
# WHERE r.command NOT IN ('SELECT', 'BACKUP DATABASE', 'BACKUP LOG')
#   AND s.database_id = DB_ID('ProdDB')
#   AND s.is_user_process = 1;
# "

echo "Source quiesced. Press ENTER to proceed with sequence sync."
read -r

#--- STEP 4: Synchronize sequences ---#
log_step "4. Synchronize sequences on target"

# Generate and execute sequence sync (PostgreSQL targets)
psql -h "${SOURCE_HOST}" -U dba_user -d prod_db -t -A -c "
SELECT 'SELECT setval(''' || schemaname || '.' || sequencename ||
       ''', COALESCE((SELECT MAX(' || quote_ident(a.attname) ||
       ') FROM ' || schemaname || '.' || tablename || '), 1), true);'
FROM pg_sequences s
JOIN pg_class c ON c.relname = s.sequencename
JOIN pg_depend d ON d.objid = c.oid
JOIN pg_class ct ON d.refobjid = ct.oid
JOIN pg_attribute a ON a.attrelid = ct.oid AND a.attnum = d.refobjsubid
JOIN pg_tables t ON t.tablename = ct.relname AND t.schemaname = s.schemaname
WHERE s.schemaname NOT IN ('pg_catalog', 'information_schema');
" > /tmp/sequence_sync.sql

echo "Generated sequence sync SQL. Review /tmp/sequence_sync.sql then press ENTER."
cat /tmp/sequence_sync.sql
read -r

psql -h "${TARGET_HOST}" -U target_dba_user -d prod_db -f /tmp/sequence_sync.sql
echo "Sequences synchronized."

#--- STEP 5: Row count validation ---#
log_step "5. Validate row counts source vs target"

validate_counts() {
    local HOST=$1
    local LABEL=$2
    psql -h "${HOST}" -U dba_user -d prod_db -t -A -c "
    SELECT tablename || '|' || n_live_tup
    FROM pg_stat_user_tables
    ORDER BY tablename;
    " > "/tmp/counts_${LABEL}.txt"
}

validate_counts "${SOURCE_HOST}" "source"
validate_counts "${TARGET_HOST}" "target"

DIFF_COUNT=$(diff /tmp/counts_source.txt /tmp/counts_target.txt | grep -c "^[<>]" || true)
if [[ "${DIFF_COUNT}" -gt 0 ]]; then
    echo "WARNING: Row count differences detected:"
    diff /tmp/counts_source.txt /tmp/counts_target.txt
    echo "Investigate before proceeding. Press ENTER to continue anyway or Ctrl+C to abort."
    read -r
else
    echo "Row counts match. Proceeding."
fi

#--- STEP 6: Stop DMS task ---#
log_step "6. Stop DMS replication task"

# AWS DMS:
aws dms stop-replication-task \
    --replication-task-arn "${DMS_TASK_ARN}"

echo "Waiting for DMS task to stop..."
aws dms wait replication-task-stopped \
    --filters "Name=replication-task-arn,Values=${DMS_TASK_ARN}"

echo "DMS task stopped."

#--- STEP 7: Update DNS / connection strings ---#
log_step "7. Update application DNS to point to target"

# Update Route 53 (AWS example)
aws route53 change-resource-record-sets \
    --hosted-zone-id "${HOSTED_ZONE_ID}" \
    --change-batch '{
        "Changes": [{
            "Action": "UPSERT",
            "ResourceRecordSet": {
                "Name": "db.internal.example.com",
                "Type": "CNAME",
                "TTL": 60,
                "ResourceRecords": [{"Value": "'"${AURORA_ENDPOINT}"'"}]
            }
        }]
    }'

echo "DNS updated. TTL is 60s — wait 90 seconds for propagation."
sleep 90

#--- STEP 8: Restore application traffic ---#
log_step "8. Restore application traffic"

# Scale application back up / disable maintenance mode
# kubectl scale deployment app-deployment --replicas=4 -n production

echo "Application traffic restored. Begin smoke testing."

    33.6 Rollback Plan

    Every cutover runbook needs a tested rollback path. The time to design the rollback is not during an incident at 3 AM — it is before you start the migration. The rollback strategy depends on your migration type.

    Rollback for DMS-Based Migrations (PostgreSQL)

    If you detect data corruption or application failures within the first hour after cutover, you can roll back by directing traffic back at the source — but only if the source was not taken offline or made read-only.

    # ROLLBACK PROCEDURE — Execute only if smoke tests fail within 1 hour of cutover
# This window closes when you decommission the source or disable writes to it

log_step "ROLLBACK: Redirecting traffic to source database"

# 1. Put application in maintenance mode again
# kubectl scale deployment app-deployment --replicas=0 -n production

# 2. Revert DNS to source
aws route53 change-resource-record-sets \
    --hosted-zone-id "${HOSTED_ZONE_ID}" \
    --change-batch '{
        "Changes": [{
            "Action": "UPSERT",
            "ResourceRecordSet": {
                "Name": "db.internal.example.com",
                "Type": "CNAME",
                "TTL": 60,
                "ResourceRecords": [{"Value": "'"${SOURCE_HOST}"'"}]
            }
        }]
    }'

echo "DNS reverted to source. Waiting 90s for propagation."
sleep 90

# 3. Restore application traffic
# kubectl scale deployment app-deployment --replicas=4 -n production

echo "ROLLBACK COMPLETE. Applications are writing to source again."
echo "Assess target failures before rescheduling migration."

    Important rollback constraint: once you stop the DMS task and allow writes to the target, the replication stream is broken. If you discover a problem after writes have occurred on the target, you cannot roll back cleanly without accepting data loss. This is why the cutover window (Step 2 through Step 8 in the cutover script) must be executed quickly — typically under 15 minutes for most workloads — and smoke tests must be decisive.

    For SQL Server migrations to Azure SQL Managed Instance, Azure DMS keeps the migration task in ReadyForCutover state, and you have not yet invoked the cutover command. In this state, you can abandon the migration task without any impact to the source. Once you issue the cutover command, the commitment is final.

    33.7 Post-Migration Optimization

    The database has landed in cloud. The application is running. The work is not done. Cloud databases expose different performance characteristics than on-premises ones: network-attached storage introduces latency patterns you did not see on direct-attached SAN, the managed service's shared infrastructure imposes IOPS limits that vary by instance class, and the optimizer's statistics may not yet reflect production query patterns.

    Rebuild Statistics and Indexes on Target

    -- PostgreSQL (Aurora / Cloud SQL): rebuild statistics after full load
-- DMS full load does not run ANALYZE; statistics are stale

-- Run ANALYZE on all user tables immediately after migration
DO $$
DECLARE
    tbl RECORD;
BEGIN
    FOR tbl IN
        SELECT schemaname, tablename
        FROM pg_tables
        WHERE schemaname NOT IN ('pg_catalog', 'information_schema', 'pg_toast')
    LOOP
        EXECUTE format('ANALYZE %I.%I', tbl.schemaname, tbl.tablename);
        RAISE NOTICE 'Analyzed: %.%', tbl.schemaname, tbl.tablename;
    END LOOP;
END $$;

-- For large tables, run ANALYZE with a progress check
-- Aurora/RDS exposes pg_stat_progress_analyze (PostgreSQL 13+)
SELECT
    phase,
    sample_blks_total,
    sample_blks_scanned,
    ext_stats_total,
    ext_stats_computed,
    child_tables_total,
    child_tables_done
FROM pg_stat_progress_analyze;

-- Check for bloated indexes from the full load process
-- DMS loads data in bulk; indexes may have high dead-tuple ratios
SELECT
    schemaname,
    tablename,
    indexname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
JOIN pg_index USING (indexrelid)
WHERE idx_scan = 0  -- Indexes never used since migration
  AND NOT indisprimary
  AND NOT indisunique
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 20;
    -- SQL Server (Azure SQL MI / Azure SQL Database): post-migration statistics
-- Rebuild statistics after full load (equivalent operation)

-- Update all statistics with full scan
EXEC sp_updatestats;

-- For a more thorough rebuild on a specific database:
USE ProdDB;

DECLARE @sql NVARCHAR(MAX) = N'';
SELECT @sql += N'UPDATE STATISTICS ' + QUOTENAME(SCHEMA_NAME(t.schema_id))
    + N'.' + QUOTENAME(t.name) + N' WITH FULLSCAN;' + CHAR(10)
FROM sys.tables t
WHERE t.is_ms_shipped = 0;

-- Review before executing
PRINT @sql;
-- EXEC sp_executesql @sql;  -- Uncomment to execute

-- Identify indexes with high fragmentation post-migration
SELECT
    DB_NAME() AS database_name,
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.index_type_desc,
    ROUND(ips.avg_fragmentation_in_percent, 2) AS fragmentation_pct,
    ips.page_count,
    ips.record_count
FROM sys.dm_db_index_physical_stats(
    DB_ID(), NULL, NULL, NULL, 'LIMITED'
) ips
JOIN sys.indexes i
    ON ips.object_id = i.object_id
    AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 30
  AND ips.page_count > 1000
ORDER BY ips.avg_fragmentation_in_percent DESC;

    Verify Query Plan Stability

    The first week after migration is when query plan regressions appear. Queries that ran well on the source may receive poor plans on the target due to different optimizer defaults, missing statistics, or engine version differences.

    -- PostgreSQL: enable pg_stat_statements to catch slow queries post-migration
-- Confirm extension is installed (it should be on RDS/Aurora/Cloud SQL)
SELECT * FROM pg_available_extensions WHERE name = 'pg_stat_statements';

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 20 slowest queries by mean execution time since migration
SELECT
    round(mean_exec_time::numeric, 2) AS mean_ms,
    round(total_exec_time::numeric, 2) AS total_ms,
    calls,
    round((stddev_exec_time / NULLIF(mean_exec_time, 0) * 100)::numeric, 1) AS variability_pct,
    rows / NULLIF(calls, 0) AS avg_rows,
    left(query, 120) AS query_snippet
FROM pg_stat_statements
WHERE userid = (SELECT oid FROM pg_roles WHERE rolname = current_user)
   OR userid IN (SELECT oid FROM pg_roles WHERE rolname != 'rdsadmin')
ORDER BY mean_exec_time DESC
LIMIT 20;

-- Reset stats baseline after initial stabilization (24-48h post-migration)
-- SELECT pg_stat_statements_reset();
    -- SQL Server: use Query Store to compare plans before and after migration
-- Query Store should be enabled on Azure SQL by default

-- Check Query Store is active
SELECT name, is_query_store_on
FROM sys.databases
WHERE name = 'ProdDB';

-- Find queries with high variance in execution time (plan instability)
SELECT TOP 20
    q.query_id,
    qt.query_sql_text,
    rs.count_executions,
    ROUND(rs.avg_duration / 1000.0, 2) AS avg_duration_ms,
    ROUND(rs.max_duration / 1000.0, 2) AS max_duration_ms,
    ROUND(rs.stdev_duration / 1000.0, 2) AS stdev_duration_ms,
    rs.avg_logical_io_reads
FROM sys.query_store_query q
JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
JOIN sys.query_store_runtime_stats_interval rsi
    ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
WHERE rsi.start_time > DATEADD(HOUR, -24, GETUTCDATE())
ORDER BY rs.stdev_duration DESC;

    Key Takeaways

  • → **Assessment before tooling**: run SCT and DMA against every source database before touching a migration tool — blocking incompatibilities discovered during execution cost ten times more to fix than the same issues discovered during assessment.
  • → **DMS does not migrate everything**: sequences, SQL Agent jobs, linked servers, certificates for TDE, and DDL changes during CDC are outside the replication stream; each requires a separate manual migration step baked into the cutover runbook.
  • → **Cutover speed determines rollback viability**: the longer your cutover window stays open, the more writes accumulate on the target and the harder it becomes to roll back cleanly; practice the cutover steps in a staging environment until they execute consistently in under 15 minutes.
  • → **Statistics are stale immediately after full load**: DMS bulk load bypasses autovacuum and statistics collection; run `ANALYZE` (PostgreSQL) or `UPDATE STATISTICS` (SQL Server) as the first post-migration step before allowing application traffic, or query plans will be based on empty histograms.
  • → **Right-size after one week, not before**: provisioning decisions made before migration are guesses; only after one week of real production traffic on the target instance do CloudWatch, Azure Monitor, and Cloud Monitoring metrics provide the utilization data needed to make a defensible downsize decision without risking performance regression.
