Chapter 12: Multi-Tenant Vector Storage in PostgreSQL

Multi-tenancy is one of the oldest problems in database engineering, and it doesn't get simpler when you add vectors to the mix. If you're building a SaaS product where every customer gets their own AI-powered search, a platform where multiple teams share infrastructure for semantic retrieval, or an enterprise system where business units need data isolation, you need a coherent strategy for partitioning vector data. This chapter walks through the three canonical approaches to multi-tenant vector storage in PostgreSQL with pgvector — row-level isolation, schema-level isolation, and database-level isolation — and gives you the tools to choose between them based on your scale, compliance requirements, and operational constraints. Beyond the data model, you'll also work through index management across tenants, query routing, and the performance cliffs that catch engineers off guard in production.

---

12.1 The Three Models of Multi-Tenancy (and Where Each Breaks Down)

Before writing a single line of SQL, you need to understand the fundamental tradeoff: shared infrastructure reduces cost and operational overhead, but increases blast radius and isolation risk. Vector workloads amplify this tradeoff because index structures are not row-addressable — an HNSW index built over millions of rows cannot be surgically partitioned the way a B-tree on a primary key can.

Row-Level Isolation puts all tenants in a single table with a tenant_id column. It is the simplest model and maps directly to how most DBAs handle multi-tenancy in OLTP systems. The problem is that pgvector's approximate nearest neighbor (ANN) indexes — HNSW and IVFFlat — are built over the entire table. When you query with a WHERE tenant_id = $1 filter, the planner has two options: scan the index and post-filter, or skip the index and do a sequential scan. For a tenant with 1,000 rows in a table of 10 million, neither option is fast. The index scan produces thousands of candidates before the filter reduces them to the tenant's actual result set. The sequential scan is simply slow. This is the "tenant size disparity" problem, and it is the primary reason row-level isolation fails at scale.

Schema-Level Isolation gives each tenant their own schema within a single PostgreSQL database. Each schema contains its own embeddings table and its own HNSW index. This sidesteps the index contamination problem entirely — each tenant's index is built only over their own data. The cost is operational complexity: adding a tenant means executing DDL, managing schema-scoped connections, and ensuring your migration tooling handles hundreds or thousands of schemas without timing out. At roughly 500–1,000 schemas, operational overhead becomes a real concern; beyond 5,000 schemas, PostgreSQL's catalog can become a performance bottleneck during connection and query planning.

Database-Level Isolation gives each tenant a separate PostgreSQL database. This provides the strongest isolation — separate connection pools, separate WAL streams, separate backup targets — but multiplies your operational surface area by the number of tenants. It's appropriate for enterprise SaaS where each customer is a large organization with their own compliance requirements, not for consumer applications with thousands of small tenants.

The decision matrix looks like this in practice:

| Model | Tenants | Tenant Size | Isolation Requirement | Recommended |

|---|---|---|---|---|

| Row-level | < 100 | Roughly equal | Low | Prototyping, small SaaS |

| Schema-level | 100–5,000 | Variable | Medium | Most production SaaS |

| Database-level | < 500 | Large | High (SOC 2, HIPAA) | Enterprise, regulated |

Most production systems end up in the schema-level model. The rest of this chapter focuses there, with coverage of row-level patterns where they remain applicable.

12.2 Implementing Row-Level Vector Isolation

Row-level isolation is worth understanding thoroughly, even if you'll eventually outgrow it, because it's the right starting point for most systems and the performance problems are instructive.

The baseline schema for a row-level multi-tenant vector store looks like this:

-- PostgreSQL / pgvector
CREATE EXTENSION IF NOT EXISTS vector;

-- Core document store with tenant partitioning
CREATE TABLE tenant_embeddings (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   UUID NOT NULL,
    doc_id      TEXT NOT NULL,
    content     TEXT NOT NULL,
    embedding   vector(1536),        -- OpenAI text-embedding-3-small dimensions
    metadata    JSONB DEFAULT '{}',
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (tenant_id, doc_id)
);

-- Composite index for filtering: tenant_id first, then vector search
-- Note: this is a regular B-tree index, not a vector index
CREATE INDEX idx_tenant_embeddings_tenant
    ON tenant_embeddings (tenant_id, created_at DESC);

-- HNSW index over the full table
-- m=16, ef_construction=64 are conservative defaults for mixed workloads
CREATE INDEX idx_tenant_embeddings_hnsw
    ON tenant_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Row-level security for application-layer enforcement
ALTER TABLE tenant_embeddings ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_policy ON tenant_embeddings
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

The RLS policy requires the application to set app.current_tenant_id before executing queries. In Python using psycopg2:

# Python
import psycopg2
import numpy as np
from openai import OpenAI

openai_client = OpenAI()

def get_connection(dsn: str):
    conn = psycopg2.connect(dsn)
    conn.autocommit = False
    return conn

def set_tenant_context(conn, tenant_id: str):
    """Set the RLS context for the current connection."""
    with conn.cursor() as cur:
        cur.execute(
            "SELECT set_config('app.current_tenant_id', %s, FALSE)",
            (tenant_id,)
        )

def embed_text(text: str) -> list[float]:
    response = openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

def insert_document(conn, tenant_id: str, doc_id: str, content: str, metadata: dict):
    embedding = embed_text(content)
    embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

    with conn.cursor() as cur:
        set_tenant_context(conn, tenant_id)
        cur.execute("""
            INSERT INTO tenant_embeddings (tenant_id, doc_id, content, embedding, metadata)
            VALUES (%s, %s, %s, %s::vector, %s)
            ON CONFLICT (tenant_id, doc_id) DO UPDATE
                SET content   = EXCLUDED.content,
                    embedding = EXCLUDED.embedding,
                    metadata  = EXCLUDED.metadata
        """, (tenant_id, doc_id, content, embedding_str, psycopg2.extras.Json(metadata)))
    conn.commit()

def semantic_search(conn, tenant_id: str, query: str, top_k: int = 10):
    """
    ANN search scoped to a single tenant.
    The WHERE clause on tenant_id will post-filter HNSW results.
    For small tenants in large tables, set_limit may need adjustment.
    """
    query_embedding = embed_text(query)
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

    with conn.cursor() as cur:
        set_tenant_context(conn, tenant_id)
        # hnsw.ef_search controls recall vs speed tradeoff at query time
        cur.execute("SET hnsw.ef_search = 100")
        cur.execute("""
            SELECT
                doc_id,
                content,
                metadata,
                1 - (embedding <=> %s::vector) AS cosine_similarity
            FROM tenant_embeddings
            WHERE tenant_id = %s
            ORDER BY embedding <=> %s::vector
            LIMIT %s
        """, (embedding_str, tenant_id, embedding_str, top_k))
        return cur.fetchall()

One specific behavior to understand: when pgvector executes an HNSW search with a WHERE tenant_id = $1 predicate, it scans the HNSW graph and collects ef_search candidates, then applies the filter. If your tenant has 500 rows in a table of 2 million, the probability that any given HNSW candidate passes the filter is 0.025%. The engine may return fewer than top_k results because so few candidates pass. Increasing hnsw.ef_search to 400 or 800 improves recall but increases latency proportionally. This is the wall you hit with row-level isolation.

The mitigation, short of switching to schema-level isolation, is partial indexes. If tenant access patterns are known ahead of time, you can create a dedicated HNSW index per tenant:

-- PostgreSQL / pgvector
-- Partial HNSW index for a specific high-volume tenant
-- Only viable for tenants with > ~50,000 rows (index overhead is otherwise not justified)
CREATE INDEX idx_embeddings_tenant_acme
    ON tenant_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE tenant_id = 'a1b2c3d4-e5f6-7890-abcd-ef1234567890';

-- Check that the planner uses the partial index
EXPLAIN (ANALYZE, BUFFERS)
SELECT doc_id, embedding <=> '[0.1, 0.2, ...]'::vector AS distance
FROM tenant_embeddings
WHERE tenant_id = 'a1b2c3d4-e5f6-7890-abcd-ef1234567890'
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;

Partial indexes work well for your top 10–20 largest tenants. Beyond that, the schema-level model is a cleaner solution.

12.3 Schema-Per-Tenant Architecture

Schema-level isolation is where most production vector SaaS platforms land. Each tenant gets a dedicated schema, and within that schema you have full DDL freedom: indexes tuned to that tenant's vector count, retention policies, custom metadata columns.

The first engineering problem is provisioning automation. You need to create schemas, tables, and indexes reliably, idempotently, and fast enough that a new tenant can be onboarded within seconds.

# Python
import psycopg2
from psycopg2 import sql
import logging

logger = logging.getLogger(__name__)

TENANT_SCHEMA_DDL = """
    CREATE SCHEMA IF NOT EXISTS {schema};

    CREATE TABLE IF NOT EXISTS {schema}.embeddings (
        id          BIGSERIAL PRIMARY KEY,
        doc_id      TEXT NOT NULL UNIQUE,
        content     TEXT NOT NULL,
        embedding   vector(1536),
        metadata    JSONB DEFAULT '{{}}',
        created_at  TIMESTAMPTZ DEFAULT NOW()
    );

    -- IVFFlat is preferred at smaller scales (< 1M rows per tenant)
    -- because it has lower memory overhead than HNSW and builds faster.
    -- Switch to HNSW when tenant exceeds ~500k rows.
    CREATE INDEX IF NOT EXISTS embeddings_ivfflat_{tenant_slug}
        ON {schema}.embeddings
        USING ivfflat (embedding vector_cosine_ops)
        WITH (lists = 100);

    COMMENT ON SCHEMA {schema} IS 'Tenant: {tenant_id}';
"""

def sanitize_schema_name(tenant_id: str) -> str:
    """
    Convert a tenant UUID to a safe schema name.
    PostgreSQL identifiers must start with a letter or underscore.
    """
    safe = tenant_id.replace("-", "_")
    return f"t_{safe}"

def provision_tenant_schema(conn, tenant_id: str) -> str:
    """
    Create schema and supporting objects for a new tenant.
    Returns the schema name on success.
    Idempotent — safe to call multiple times.
    """
    schema_name = sanitize_schema_name(tenant_id)

    try:
        with conn.cursor() as cur:
            # Use psycopg2.sql for safe identifier interpolation
            # String formatting is acceptable here only for the DDL block
            # where we've already sanitized the identifier above.
            ddl = TENANT_SCHEMA_DDL.format(
                schema=schema_name,
                tenant_id=tenant_id,
                tenant_slug=schema_name
            )
            cur.execute(ddl)
        conn.commit()
        logger.info(f"Provisioned schema {schema_name} for tenant {tenant_id}")
        return schema_name
    except Exception as e:
        conn.rollback()
        logger.error(f"Failed to provision schema for tenant {tenant_id}: {e}")
        raise

def deprovision_tenant_schema(conn, tenant_id: str, dry_run: bool = True) -> str:
    """
    Remove all data for a tenant. Irreversible.
    Always run with dry_run=True first in production.
    """
    schema_name = sanitize_schema_name(tenant_id)
    drop_stmt = sql.SQL("DROP SCHEMA IF EXISTS {} CASCADE").format(
        sql.Identifier(schema_name)
    )

    if dry_run:
        logger.info(f"[DRY RUN] Would execute: {drop_stmt.as_string(conn)}")
        return schema_name

    with conn.cursor() as cur:
        cur.execute(drop_stmt)
    conn.commit()
    logger.info(f"Deprovisioned schema {schema_name}")
    return schema_name

With schemas provisioned, the query path needs to route each request to the correct schema. Connection pools complicate this: a connection checked out from PgBouncer has no inherent tenant context, so you must set search_path explicitly on every query or use session-scoped configuration.

# Python
from contextlib import contextmanager
import psycopg2.pool

# Transaction-mode pooling (PgBouncer) requires setting search_path per query.
# Session-mode pooling allows SET search_path once per connection checkout,
# but connections cannot be reused across tenants without resetting.

class TenantVectorStore:
    def __init__(self, pool: psycopg2.pool.ThreadedConnectionPool):
        self.pool = pool

    @contextmanager
    def tenant_connection(self, tenant_id: str):
        """
        Context manager that yields a connection scoped to the tenant schema.
        Resets search_path on release to prevent cross-tenant leakage.
        """
        schema_name = sanitize_schema_name(tenant_id)
        conn = self.pool.getconn()
        try:
            with conn.cursor() as cur:
                # Set search_path for this transaction block.
                # The 'public' fallback gives access to pgvector functions.
                cur.execute(
                    sql.SQL("SET LOCAL search_path TO {}, public").format(
                        sql.Identifier(schema_name)
                    )
                )
            yield conn
        finally:
            conn.reset()    # Clears SET LOCAL changes
            self.pool.putconn(conn)

    def search(self, tenant_id: str, query_embedding: list[float], top_k: int = 10):
        embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

        with self.tenant_connection(tenant_id) as conn:
            with conn.cursor() as cur:
                cur.execute("""
                    SELECT
                        doc_id,
                        content,
                        metadata,
                        1 - (embedding <=> %s::vector) AS score
                    FROM embeddings
                    ORDER BY embedding <=> %s::vector
                    LIMIT %s
                """, (embedding_str, embedding_str, top_k))
                return cur.fetchall()

    def upsert(self, tenant_id: str, doc_id: str, content: str,
               embedding: list[float], metadata: dict):
        embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

        with self.tenant_connection(tenant_id) as conn:
            with conn.cursor() as cur:
                cur.execute("""
                    INSERT INTO embeddings (doc_id, content, embedding, metadata)
                    VALUES (%s, %s, %s::vector, %s)
                    ON CONFLICT (doc_id) DO UPDATE
                        SET content   = EXCLUDED.content,
                            embedding = EXCLUDED.embedding,
                            metadata  = EXCLUDED.metadata
                """, (doc_id, content, embedding_str,
                      psycopg2.extras.Json(metadata)))
            conn.commit()

The SET LOCAL search_path approach is important: SET LOCAL applies only within the current transaction and is automatically rolled back when the transaction ends or the connection is reset. This prevents a schema from bleeding across connection pool boundaries.

12.4 Index Management at Tenant Scale

The most underestimated operational challenge in schema-per-tenant architectures is index lifecycle management. When you have 1,000 tenants, each with an IVFFlat or HNSW index, you have 1,000 separate index structures that need to be monitored, rebuilt when stale, and upgraded when you change embedding models.

When to switch index types: IVFFlat is appropriate up to approximately 500,000 vectors per tenant. The rule of thumb is lists = sqrt(row_count), so a 100,000-row tenant should have lists = ~316. Beyond 500,000 rows, HNSW provides better recall at comparable query latency because IVFFlat's probe-based search degrades when the query vector's nearest list doesn't align well with its actual neighbors.

Rebuilding indexes after bulk loads: Both IVFFlat and HNSW are static structures that don't automatically rebalance. After a bulk import that increases a tenant's row count by more than 20–30%, the index becomes stale and recall drops. You need a process to detect this and schedule rebuilds.

-- PostgreSQL / pgvector
-- Monitoring view: index staleness across all tenant schemas
-- Run this periodically to identify schemas needing index maintenance

CREATE OR REPLACE VIEW public.tenant_index_health AS
SELECT
    schemaname,
    tablename,
    n_live_tup                                    AS live_rows,
    n_dead_tup                                    AS dead_rows,
    last_vacuum,
    last_analyze,
    ROUND(n_dead_tup::NUMERIC / NULLIF(n_live_tup, 0) * 100, 2) AS dead_pct,
    pg_size_pretty(pg_total_relation_size(
        schemaname || '.' || tablename
    ))                                            AS total_size
FROM pg_stat_user_tables
WHERE tablename = 'embeddings'
  AND schemaname LIKE 't_%'    -- matches our tenant schema naming convention
ORDER BY live_rows DESC;

-- Find tenants whose index needs rebuilding:
-- Heuristic: more than 25% dead tuples, or live rows have grown > 2x since last analyze
SELECT
    schemaname,
    live_rows,
    dead_pct,
    last_analyze,
    CASE
        WHEN dead_pct > 25                        THEN 'REBUILD_URGENT'
        WHEN last_analyze < NOW() - INTERVAL '7 days'
             AND live_rows > 10000                THEN 'REBUILD_SCHEDULED'
        ELSE 'OK'
    END AS index_status
FROM public.tenant_index_health
WHERE dead_pct > 10
   OR last_analyze < NOW() - INTERVAL '7 days'
ORDER BY dead_pct DESC, live_rows DESC;

When a tenant needs an index rebuild, you want to do it without locking out queries. REINDEX CONCURRENTLY is your friend, but it requires PostgreSQL 12+ and cannot run inside a transaction block:

# shell
# Rebuild HNSW index concurrently for a specific tenant schema
# Run as the application database user with sufficient privileges
# This takes 2-10 minutes for a 500k-row tenant on typical cloud hardware

TENANT_SCHEMA="t_a1b2c3d4_e5f6_7890_abcd_ef1234567890"

psql "$DATABASE_URL" -c "
    REINDEX INDEX CONCURRENTLY
    ${TENANT_SCHEMA}.embeddings_ivfflat_${TENANT_SCHEMA};
"

# After reindex, update statistics so the planner has accurate cost estimates
psql "$DATABASE_URL" -c "
    ANALYZE ${TENANT_SCHEMA}.embeddings;
"

# Verify the index is healthy
psql "$DATABASE_URL" -c "
    SELECT
        indexname,
        pg_size_pretty(pg_relation_size(indexname::regclass)) AS index_size,
        idx_scan,
        idx_tup_read,
        idx_tup_fetch
    FROM pg_stat_user_indexes
    WHERE schemaname = '${TENANT_SCHEMA}'
      AND tablename = 'embeddings';
"

For automated index lifecycle management at scale, wrap this in a Python job that reads from the tenant_index_health view and prioritizes rebuilds:

# Python
import psycopg2
from psycopg2 import sql
import logging
from dataclasses import dataclass
from datetime import datetime, timedelta

logger = logging.getLogger(__name__)

@dataclass
class TenantIndexStatus:
    schema_name: str
    live_rows: int
    dead_pct: float
    last_analyze: datetime | None
    status: str

def get_stale_tenant_indexes(conn) -> list[TenantIndexStatus]:
    """Return tenants requiring index maintenance, ordered by urgency."""
    with conn.cursor() as cur:
        cur.execute("""
            SELECT
                schemaname,
                live_rows,
                dead_pct,
                last_analyze,
                CASE
                    WHEN dead_pct > 25 THEN 'REBUILD_URGENT'
                    WHEN last_analyze < NOW() - INTERVAL '7 days'
                         AND live_rows > 10000 THEN 'REBUILD_SCHEDULED'
                    ELSE 'OK'
                END AS status
            FROM public.tenant_index_health
            WHERE dead_pct > 10
               OR last_analyze < NOW() - INTERVAL '7 days'
            ORDER BY
                CASE WHEN dead_pct > 25 THEN 0 ELSE 1 END,
                dead_pct DESC
        """)
        rows = cur.fetchall()

    return [
        TenantIndexStatus(
            schema_name=r[0],
            live_rows=r[1],
            dead_pct=float(r[2] or 0),
            last_analyze=r[3],
            status=r[4]
        )
        for r in rows
        if r[4] != 'OK'
    ]

def rebuild_tenant_index(conn, schema_name: str) -> bool:
    """
    Rebuild the vector index for a tenant schema.
    Returns True on success, False on failure.
    REINDEX CONCURRENTLY cannot run inside a transaction — use autocommit.
    """
    original_autocommit = conn.autocommit
    conn.autocommit = True

    try:
        index_name = f"embeddings_ivfflat_{schema_name}"
        full_index = f"{schema_name}.{index_name}"

        with conn.cursor() as cur:
            logger.info(f"Starting concurrent reindex for {schema_name}")
            cur.execute(
                sql.SQL("REINDEX INDEXCONCURRENTLY {}").format(
                    sql.Identifier(schema_name, index_name)
                )
            )
            cur.execute(
                sql.SQL("ANALYZE {}.embeddings").format(
                    sql.Identifier(schema_name)
                )
            )

        logger.info(f"Reindex complete for {schema_name}")
        return True

    except Exception as e:
        logger.error(f"Reindex failed for {schema_name}: {e}")
        return False

    finally:
        conn.autocommit = original_autocommit

def run_index_maintenance(dsn: str, max_rebuilds_per_run: int = 10):
    """
    Top-level maintenance job. Call from a cron job or scheduled task.
    Processes the most urgent tenants first, capped at max_rebuilds_per_run
    to bound wall-clock time.
    """
    conn = psycopg2.connect(dsn)
    try:
        stale = get_stale_tenant_indexes(conn)
        logger.info(f"Found {len(stale)} tenants needing index maintenance")

        rebuilt = 0
        for tenant in stale[:max_rebuilds_per_run]:
            success = rebuild_tenant_index(conn, tenant.schema_name)
            if success:
                rebuilt += 1
            else:
                logger.warning(
                    f"Skipping remaining tenants after failure at {tenant.schema_name}"
                )
                break

        logger.info(f"Index maintenance complete: {rebuilt}/{len(stale)} tenants rebuilt")
    finally:
        conn.close()

Changing embedding models: When you migrate from one embedding model to another (e.g., from text-embedding-ada-002 at 1536 dimensions to a newer model at a different dimensionality), the vector column type changes. This is a disruptive migration. The safest approach is a shadow column strategy:

-- PostgreSQL / pgvector
-- Phase 1: Add new embedding column alongside the old one
ALTER TABLE {schema}.embeddings
    ADD COLUMN embedding_v2 vector(3072);   -- new model dimensionality

-- Phase 2: Backfill new embeddings in batches (done by your migration job)
-- Phase 3: Create new index on embedding_v2
CREATE INDEX CONCURRENTLY embeddings_hnsw_v2_{schema}
    ON {schema}.embeddings
    USING hnsw (embedding_v2 vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Phase 4: Once backfill complete, swap queries to use embedding_v2
-- Phase 5: Drop old column and old index
-- ALTER TABLE {schema}.embeddings DROP COLUMN embedding;

The shadow column approach lets you serve queries from the old index while the new one is being built, with zero downtime.

12.5 Cross-Tenant Query Routing

Most SaaS applications need to perform cross-tenant operations at some point: admin dashboards that aggregate stats across all tenants, internal search that spans the entire document corpus, or anomaly detection that compares embedding distributions across customers.

Cross-tenant queries in a schema-per-tenant system require either dynamic SQL that unions across schemas or a separate denormalized table. The dynamic SQL approach is more flexible but has query planning overhead for large tenant counts.

# Python
def cross_tenant_search(
    conn,
    query_embedding: list[float],
    tenant_ids: list[str],
    top_k_per_tenant: int = 5,
    final_top_k: int = 20
) -> list[dict]:
    """
    Federated vector search across multiple tenants.
    Executes one query per tenant schema and merges results client-side.

    For admin/internal use only — never expose this to tenant-scoped
    application paths. Performance scales linearly with tenant count.
    """
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"
    results = []

    with conn.cursor() as cur:
        for tenant_id in tenant_ids:
            schema_name = sanitize_schema_name(tenant_id)
            try:
                cur.execute(
                    sql.SQL("""
                        SELECT
                            %s AS tenant_id,
                            doc_id,
                            content,
                            1 - (embedding <=> %s::vector) AS score
                        FROM {schema}.embeddings
                        ORDER BY embedding <=> %s::vector
                        LIMIT %s
                    """).format(schema=sql.Identifier(schema_name)),
                    (tenant_id, embedding_str, embedding_str, top_k_per_tenant)
                )
                rows = cur.fetchall()
                results.extend({
                    "tenant_id": r[0],
                    "doc_id": r[1],
                    "content": r[2],
                    "score": float(r[3])
                } for r in rows)
            except psycopg2.errors.InvalidSchemaName:
                logger.warning(f"Schema not found for tenant {tenant_id}, skipping")
                continue

    # Merge and re-rank by score
    results.sort(key=lambda x: x["score"], reverse=True)
    return results[:final_top_k]

For larger cross-tenant operations, a materialized summary table avoids the per-schema fan-out:

-- PostgreSQL / pgvector
-- Materialized cross-tenant view for admin analytics
-- Populated by a background job, not a live view
CREATE TABLE public.cross_tenant_embeddings_summary (
    tenant_id       UUID NOT NULL,
    schema_name     TEXT NOT NULL,
    doc_id          TEXT NOT NULL,
    embedding       vector(1536),
    created_at      TIMESTAMPTZ,
    synced_at       TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (tenant_id, doc_id)
);

CREATE INDEX idx_cross_tenant_hnsw
    ON public.cross_tenant_embeddings_summary
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Query across all tenants with a single vector search
SELECT
    tenant_id,
    doc_id,
    1 - (embedding <=> '[0.1, 0.2, ...]'::vector) AS score
FROM public.cross_tenant_embeddings_summary
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 20;

The summary table trades freshness for query speed. Your sync job needs to handle inserts, updates, and deletes from all tenant schemas, which is non-trivial at scale. Logical replication or a change-data-capture pipeline (e.g., Debezium) is the production-grade approach.

12.6 Tenant-Aware Connection Pooling

Connection management is where schema-per-tenant architectures most commonly fail in production. The core tension: PgBouncer in transaction-mode pooling (the recommended mode for high-concurrency applications) does not support SET search_path persisting across transactions because connections are returned to the pool after each transaction. Session-mode pooling preserves settings but reduces effective concurrency because a connection is pinned to one application session.

The practical solution is to use SET LOCAL within a transaction, or to explicitly set search_path as part of every query batch. The code pattern in Section 12.3 already does this. Here's the infrastructure configuration to pair with it:

# pgbouncer.ini
[pgbouncer]
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 25
min_pool_size = 5
reserve_pool_size = 5
reserve_pool_timeout = 3
server_reset_query = DISCARD ALL
server_check_query = SELECT 1
server_check_delay = 30
ignore_startup_parameters = extra_float_digits

# Application database
[myapp_db]
host = 127.0.0.1
port = 5432
dbname = myapp
pool_size = 25

The server_reset_query = DISCARD ALL ensures that any session-level settings left by previous transactions are cleared when a server connection is returned to the pool. This is your safety net against schema leakage.

On the application side, always pair your schema-setting code with explicit transaction management:

# Python
# Correct pattern: SET LOCAL inside explicit transaction
# SET LOCAL is reverted automatically at transaction end
def safe_tenant_query(pool, tenant_id: str, query_sql: str, params: tuple):
    schema_name = sanitize_schema_name(tenant_id)
    conn = pool.getconn()
    try:
        conn.autocommit = False
        with conn.cursor() as cur:
            cur.execute(
                sql.SQL("SET LOCAL search_path TO {}, public").format(
                    sql.Identifier(schema_name)
                )
            )
            cur.execute(query_sql, params)
            result = cur.fetchall()
        conn.commit()
        return result
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.autocommit = True
        pool.putconn(conn)

For async workloads using asyncpg or SQLAlchemy async:

# Python (asyncpg)
import asyncpg

async def async_tenant_search(
    pool: asyncpg.Pool,
    tenant_id: str,
    query_embedding: list[float],
    top_k: int = 10
) -> list[asyncpg.Record]:
    schema_name = sanitize_schema_name(tenant_id)
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

    async with pool.acquire() as conn:
        async with conn.transaction():
            await conn.execute(
                f"SET LOCAL search_path TO {asyncpg.utils._quote_ident(schema_name)}, public"
            )
            return await conn.fetch("""
                SELECT
                    doc_id,
                    content,
                    1 - (embedding <=> $1::vector) AS score
                FROM embeddings
                ORDER BY embedding <=> $1::vector
                LIMIT $2
            """, embedding_str, top_k)

Note: asyncpg's _quote_ident is an internal utility. In production, implement your own identifier quoting or use f'"{schema_name}"' after validating the schema name against your known-safe naming scheme.

12.7 Scaling Considerations and Performance Cliffs

As tenant count and per-tenant data volume grow, several performance cliffs appear that aren't obvious from small-scale testing.

PostgreSQL catalog contention: The pg_class, pg_attribute, and pg_index system catalogs are shared across the entire instance. When you have 3,000 tenant schemas each with 10 tables and 5 indexes, you have 15,000 entries in pg_class and 75,000 in pg_index. Connection startup and query planning read these catalogs, and the catalog can become a hot read path at scale. Monitor with:

-- PostgreSQL
-- Catalog table bloat and access frequency
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    seq_scan,
    idx_scan
FROM pg_stat_sys_tables
WHERE relname IN ('pg_class', 'pg_attribute', 'pg_index', 'pg_namespace')
ORDER BY seq_scan DESC;

If you see high seq_scan counts on pg_class, you're hitting catalog contention. The mitigation is reducing schema count (consolidate small tenants to row-level partitioning) or sharding across PostgreSQL instances.

Memory pressure from concurrent index builds: HNSW index construction is memory-intensive. Each concurrent CREATE INDEX operation can consume maintenance_work_mem. With 50 tenants being provisioned simultaneously, you can exhaust available memory on the database server. Serialize index builds or cap concurrent DDL operations:

# Python
import asyncio

async def provision_tenants_with_concurrency_limit(
    tenant_ids: list[str],
    dsn: str,
    max_concurrent: int = 5
):
    """Provision tenant schemas with bounded DDL concurrency."""
    semaphore = asyncio.Semaphore(max_concurrent)

    async def provision_one(tenant_id: str):
        async with semaphore:
            # Each task gets its own connection to avoid transaction interference
            conn = await asyncpg.connect(dsn)
            try:
                await async_provision_tenant(conn, tenant_id)
            finally:
                await conn.close()

    await asyncio.gather(*[provision_one(tid) for tid in tenant_ids])

IVFFlat lists misconfiguration: The lists parameter must be set when the index is created and cannot be changed without dropping and recreating the index. A tenant provisioned with lists = 100 when it had 10,000 rows will have severely degraded recall once it grows to 1,000,000 rows (where lists = ~1000 would be appropriate). The automated index health check from Section 12.4 should flag this. Add a check:

-- PostgreSQL / pgvector
-- Detect tenants whose IVFFlat list count is under-provisioned
-- relative to current row count
SELECT
    h.schemaname,
    h.live_rows,
    (ix.reloptions::text)                          AS index_options,
    ROUND(SQRT(h.live_rows))                       AS recommended_lists,
    -- Extract the actual lists value from index options
    (
        SELECT val::int
        FROM unnest(ix.reloptions) AS opt(val_text)
        CROSS JOIN LATERAL (SELECT val_text) AS t(val)
        WHERE val LIKE 'lists=%'
        LIMIT 1
    )                                               AS current_lists
FROM public.tenant_index_health h
JOIN pg_indexes pi
    ON pi.schemaname = h.schemaname
    AND pi.tablename = 'embeddings'
    AND pi.indexdef LIKE '%ivfflat%'
JOIN pg_class ix
    ON ix.relname = pi.indexname
WHERE h.live_rows > 0
ORDER BY h.live_rows DESC;

Vacuum and autovacuum across many schemas: pgvector tables accumulate dead tuples like any other heap. With 1,000 schemas each doing moderate write activity, autovacuum workers can be spread thin. Increase autovacuum_max_workers and tune per-table autovacuum thresholds for high-churn tenant tables:

-- PostgreSQL
-- Aggressive autovacuum settings for high-write tenant embedding tables
-- Apply after provisioning for tenants with expected high write volume
ALTER TABLE {schema}.embeddings SET (
    autovacuum_vacuum_scale_factor = 0.01,  -- Vacuum after 1% of rows are dead
    autovacuum_analyze_scale_factor = 0.005, -- Analyze after 0.5% of rows change
    autovacuum_vacuum_cost_delay = 2         -- ms; reduce I/O throttling for these tables
);

12.8 A Complete Working Example

To tie together the patterns from this chapter, here is a minimal but production-representative multi-tenant vector store with FastAPI, asyncpg, and pgvector:

# Python
# main.py — FastAPI multi-tenant vector store
from fastapi import FastAPI, HTTPException, Header
from pydantic import BaseModel
import asyncpg
import os
import logging
from contextlib import asynccontextmanager
from openai import AsyncOpenAI

logger = logging.getLogger(__name__)
openai_client = AsyncOpenAI()

# ---------------------------------------------------------------------------
# Application lifecycle
# ---------------------------------------------------------------------------

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pool = await asyncpg.create_pool(
        dsn=os.environ["DATABASE_URL"],
        min_size=5,
        max_size=20,
        command_timeout=30
    )
    yield
    await app.state.pool.close()

app = FastAPI(lifespan=lifespan)

# ---------------------------------------------------------------------------
# Schema helpers (repeated from earlier sections, included for completeness)
# ---------------------------------------------------------------------------

def sanitize_schema_name(tenant_id: str) -> str:
    safe = tenant_id.replace("-", "_")
    return f"t_{safe}"

def quote_ident(name: str) -> str:
    """Minimal safe quoting for schema names we control."""
    if not all(c.isalnum() or c == '_' for c in name):
        raise ValueError(f"Unsafe identifier: {name}")
    return f'"{name}"'

PROVISION_DDL = """
    CREATE SCHEMA IF NOT EXISTS {schema};
    CREATE TABLE IF NOT EXISTS {schema}.embeddings (
        id         BIGSERIAL PRIMARY KEY,
        doc_id     TEXT NOT NULL UNIQUE,
        content    TEXT NOT NULL,
        embedding  vector(1536),
        metadata   JSONB DEFAULT '{{}}',
        created_at TIMESTAMPTZ DEFAULT NOW()
    );
    CREATE INDEX IF NOT EXISTS embeddings_hnsw
        ON {schema}.embeddings
        USING hnsw (embedding vector_cosine_ops)
        WITH (m = 16, ef_construction = 64);
"""

async def ensure_tenant_schema(pool: asyncpg.Pool, tenant_id: str):
    schema = sanitize_schema_name(tenant_id)
    ddl = PROVISION_DDL.format(schema=quote_ident(schema))
    async with pool.acquire() as conn:
        await conn.execute(ddl)

# ---------------------------------------------------------------------------
# Embedding helper
# ---------------------------------------------------------------------------

async def get_embedding(text: str) -> list[float]:
    response = await openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

# ---------------------------------------------------------------------------
# API models
# ---------------------------------------------------------------------------

class UpsertRequest(BaseModel):
    doc_id: str
    content: str
    metadata: dict = {}

class SearchRequest(BaseModel):
    query: str
    top_k: int = 10

# ---------------------------------------------------------------------------
# Routes
# ---------------------------------------------------------------------------

@app.post("/tenants/{tenant_id}/provision")
async def provision_tenant(tenant_id: str):
    await ensure_tenant_schema(app.state.pool, tenant_id)
    return {"status": "ok", "tenant_id": tenant_id}

@app.post("/tenants/{tenant_id}/documents")
async def upsert_document(tenant_id: str, req: UpsertRequest):
    schema = sanitize_schema_name(tenant_id)
    schema_q = quote_ident(schema)
    embedding = await get_embedding(req.content)
    embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

    async with app.state.pool.acquire() as conn:
        async with conn.transaction():
            await conn.execute(
                f"SET LOCAL search_path TO {schema_q}, public"
            )
            await conn.execute("""
                INSERT INTO embeddings (doc_id, content, embedding, metadata)
                VALUES ($1, $2, $3::vector, $4)
                ON CONFLICT (doc_id) DO UPDATE
                    SET content   = EXCLUDED.content,
                        embedding = EXCLUDED.embedding,
                        metadata  = EXCLUDED.metadata
            """, req.doc_id, req.content, embedding_str,
                req.metadata)

    return {"status": "ok", "doc_id": req.doc_id}

@app.post("/tenants/{tenant_id}/search")
async def search_documents(tenant_id: str, req: SearchRequest):
    schema = sanitize_schema_name(tenant_id)
    schema_q = quote_ident(schema)
    query_embedding = await get_embedding(req.query)
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

    async with app.state.pool.acquire() as conn:
        async with conn.transaction():
            await conn.execute(
                f"SET LOCAL search_path TO {schema_q}, public"
            )
            rows = await conn.fetch("""
                SELECT
                    doc_id,
                    content,
                    metadata,
                    1 - (embedding <=> $1::vector) AS score
                FROM embeddings
                ORDER BY embedding <=> $1::vector
                LIMIT $2
            """, embedding_str, req.top_k)

    return [
        {
            "doc_id": r["doc_id"],
            "content": r["content"],
            "metadata": dict(r["metadata"]),
            "score": float(r["score"])
        }
        for r in rows
    ]

@app.delete("/tenants/{tenant_id}")
async def deprovision_tenant(tenant_id: str):
    schema = sanitize_schema_name(tenant_id)
    schema_q = quote_ident(schema)
    async with app.state.pool.acquire() as conn:
        await conn.execute(f"DROP SCHEMA IF EXISTS {schema_q} CASCADE")
    return {"status": "ok", "tenant_id": tenant_id}

This example is intentionally minimal — it has no authentication, no rate limiting, and no observability instrumentation. In a real deployment you would add all three. The patterns for schema provisioning, search_path scoping, and connection management are production-ready as written.

Key Takeaways

  • → **Row-level isolation** is simple to implement but breaks down when tenant sizes diverge significantly, because HNSW and IVFFlat indexes scan the full table before applying tenant filters. Partial indexes per tenant extend row-level isolation but are operationally viable only for your largest few tenants.
  • → **Schema-per-tenant isolation** is the production default for most SaaS vector workloads. Each tenant gets its own index built only over their data, eliminating the filter post-scan problem. The cost is DDL automation complexity and PostgreSQL catalog pressure above roughly 3,000–5,000 schemas.
  • → **Index lifecycle management** requires active monitoring: IVFFlat `lists` parameters become under-provisioned as tenants grow, dead tuple accumulation degrades recall, and embedding model changes require a zero-downtime shadow-column migration strategy.
  • → **Connection pool configuration** is as important as the data model. Use `SET LOCAL search_path` within explicit transactions to scope queries to tenant schemas, and configure `DISCARD ALL` as the PgBouncer server reset query to prevent cross-tenant schema leakage.
  • → **Cross-tenant operations** — admin search, analytics, anomaly detection — require either a fan-out query that iterates tenant schemas or a separately maintained materialized summary table with its own HNSW index. The fan-out approach scales linearly with tenant count; the summary table trades freshness for constant-time queries.
