Chapter 13: Azure SQL Database vs Managed Instance vs SQL Server on VM

When you move SQL Server workloads to Azure, the first decision you face is not which region to use or how large an instance to provision — it is which deployment model to choose. Azure offers three fundamentally different ways to run SQL Server: Azure SQL Database (a fully managed PaaS service), Azure SQL Managed Instance (a near-complete SQL Server engine in a managed container), and SQL Server on Azure Virtual Machines (IaaS, essentially your on-premises server in the cloud). Each model trades administrative control for operational convenience at a different point on the spectrum. Getting this choice wrong costs money, causes compatibility headaches, and in some cases requires a full migration to correct. This chapter maps each deployment model to the scenarios where it genuinely fits, shows you how to configure them correctly from day one, and identifies the production gotchas that no marketing documentation warns you about.

---

13.1 The Three Deployment Models: Mapping the Landscape

Before writing a single line of Terraform or clicking through the Azure portal, you need to understand what you are actually buying with each model.

Azure SQL Database is a database-as-a-service offering. You provision a database (or a pool of databases), and Azure manages the underlying instance entirely. There is no SQL Server Agent in the traditional sense. Cross-database queries require elastic queries. Linked servers do not exist. Features like SQL Server Audit work, but you configure them through Azure-native tooling rather than T-SQL. The engine is constantly patched by Microsoft on a schedule you influence but do not fully control. For greenfield applications that fit the PaaS model, this is powerful. For lift-and-shift migrations, it is frequently a poor fit without application rework.

Azure SQL Managed Instance is the middle path. It runs a near-complete SQL Server engine — SQL Server Agent, cross-database queries, linked servers, CLR assemblies, Service Broker, Database Mail — inside a managed VNet-injected service. You get instance-level features that Azure SQL Database strips away. Patching still happens on Microsoft's schedule (with a configurable maintenance window), but you control far more of the engine. The compatibility surface area covers the large majority of on-premises SQL Server 2019 features, with a well-documented list of exceptions. Lift-and-shift migrations from on-premises SQL Server work with minimal code changes.

SQL Server on Azure VM is IaaS. You own the OS, you own the SQL Server installation, you patch everything yourself (though Azure provides automated patching assistance), and you have complete feature parity with on-premises SQL Server because it is on-premises SQL Server, running on Azure hardware. You pay for this control in operational overhead: OS patching, SQL Server patching, backup management, HA configuration, and storage optimization are all your responsibility.

The decision matrix looks like this in practice:

| Requirement | Azure SQL DB | Managed Instance | SQL Server on VM |

|---|---|---|---|

| Lift-and-shift from on-prem | Poor | Excellent | Excellent |

| Greenfield cloud-native app | Excellent | Good | Overkill |

| SQL Server Agent jobs | No (elastic jobs) | Yes | Yes |

| Cross-database queries | Elastic query only | Yes | Yes |

| Linked servers | No | Yes | Yes |

| CLR assemblies | No | Yes (safe only) | Yes |

| Service Broker | No | Yes | Yes |

| Full OS access | No | No | Yes |

| Windows auth / AD | Azure AD only | Full AD integration | Full AD integration |

| HADR (Always On AG) | Built-in geo-replication | Built-in auto-failover groups | Manual config |

| Maximum single DB size | 4 TB (General Purpose) | 8 TB | 64 TB (Premium SSD v2) |

One mental shift experienced DBAs need to make: Managed Instance is not a hosted SQL Server. It is a service that exposes SQL Server semantics. You cannot RDP into it. You cannot modify startup parameters freely. You cannot install third-party tools at the OS layer. If you need to run a third-party backup agent or an encryption tool that hooks into the OS, you need SQL Server on VM.

13.2 Provisioning Each Model: Infrastructure as Code Patterns

Manual portal provisioning is fine for experimentation. Production deployments require repeatable infrastructure. The following examples use Terraform, which handles all three deployment models through the AzureRM provider.

Provisioning Azure SQL Database with an Elastic Pool:

# terraform/azure_sql_database.tf

terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.75"
    }
  }
}

provider "azurerm" {
  features {}
}

resource "azurerm_resource_group" "sql_rg" {
  name     = "rg-sql-production-eastus"
  location = "East US"
}

resource "azurerm_mssql_server" "logical_server" {
  name                         = "sql-prod-eastus-001"
  resource_group_name          = azurerm_resource_group.sql_rg.name
  location                     = azurerm_resource_group.sql_rg.location
  version                      = "12.0"
  administrator_login          = "sqladmin"
  administrator_login_password = var.sql_admin_password

  # Enforce Azure AD authentication in addition to SQL auth
  azuread_administrator {
    login_username = "DBA-Admin-Group"
    object_id      = var.aad_admin_group_object_id
    tenant_id      = var.tenant_id
  }

  # Prevent public internet access — enforce private endpoint
  public_network_access_enabled = false

  tags = {
    environment = "production"
    owner       = "dba-team"
  }
}

resource "azurerm_mssql_elasticpool" "app_pool" {
  name                = "epool-prod-app-tier"
  resource_group_name = azurerm_resource_group.sql_rg.name
  location            = azurerm_resource_group.sql_rg.location
  server_name         = azurerm_mssql_server.logical_server.name

  sku {
    name     = "GP_Gen5"
    tier     = "GeneralPurpose"
    family   = "Gen5"
    capacity = 16   # 16 vCores shared across all databases in the pool
  }

  per_database_settings {
    min_capacity = 0.25   # Minimum vCores per DB — prevents starvation
    max_capacity = 8      # Maximum vCores a single DB can consume
  }

  max_size_gb = 512

  # Zone redundancy is non-negotiable for production — check current Azure pricing for your tier
  zone_redundant = true
}

resource "azurerm_mssql_database" "app_db" {
  name           = "AppDatabase"
  server_id      = azurerm_mssql_server.logical_server.id
  elastic_pool_id = azurerm_mssql_elasticpool.app_pool.id

  # collation must match your application — changing this post-creation
  # requires a full database rebuild
  collation = "SQL_Latin1_General_CP1_CI_AS"

  # geo-redundant backups add cost but are required for PITR across regions
  geo_backup_enabled = true

  short_term_retention_policy {
    retention_days           = 35
    backup_interval_in_hours = 12
  }

  long_term_retention_policy {
    weekly_retention  = "P4W"
    monthly_retention = "P12M"
    yearly_retention  = "P5Y"
    week_of_year      = 1
  }
}

Provisioning Azure SQL Managed Instance:

Managed Instance requires a dedicated subnet — this is non-negotiable and frequently misunderstood. The subnet must be delegated exclusively to Microsoft.Sql/managedInstances and cannot be shared with any other resource type.

# terraform/managed_instance.tf

resource "azurerm_virtual_network" "mi_vnet" {
  name                = "vnet-mi-production"
  resource_group_name = azurerm_resource_group.sql_rg.name
  location            = azurerm_resource_group.sql_rg.location
  address_space       = ["10.10.0.0/16"]
}

resource "azurerm_subnet" "mi_subnet" {
  name                 = "snet-managed-instance"
  resource_group_name  = azurerm_resource_group.sql_rg.name
  virtual_network_name = azurerm_virtual_network.mi_vnet.name

  # /27 gives you 27 IP addresses — enough for a 2-node MI cluster.
  # A General Purpose MI consumes ~5 IPs, Business Critical ~9 IPs.
  # Undersizing this subnet is a common and painful mistake.
  address_prefixes = ["10.10.1.0/27"]

  delegation {
    name = "managedInstanceDelegation"
    service_delegation {
      name = "Microsoft.Sql/managedInstances"
      actions = [
        "Microsoft.Network/virtualNetworks/subnets/join/action",
        "Microsoft.Network/virtualNetworks/subnets/prepareNetworkPolicies/action",
        "Microsoft.Network/virtualNetworks/subnets/unprepareNetworkPolicies/action"
      ]
    }
  }
}

resource "azurerm_mssql_managed_instance" "prod_mi" {
  name                = "mi-prod-eastus-001"
  resource_group_name = azurerm_resource_group.sql_rg.name
  location            = azurerm_resource_group.sql_rg.location

  administrator_login          = "sqladmin"
  administrator_login_password = var.sql_admin_password

  license_type       = "LicenseIncluded"   # Or "BasePrice" if you have SA
  sku_name           = "GP_Gen5"           # General Purpose, 5th generation
  vcores             = 8
  storage_size_in_gb = 256

  subnet_id = azurerm_subnet.mi_subnet.id

  # Maintenance window — choose a low-traffic window.
  # DayOfWeek 6 = Saturday, start at 02:00 UTC
  maintenance_configuration_name = "SQL_EastUS_MI_2"

  # Timezone cannot be changed post-creation
  timezone_id = "Eastern Standard Time"

  # Minimum TLS version enforcement
  minimum_tls_version = "1.2"

  tags = {
    environment = "production"
    tier        = "managed-instance"
  }
}

Important subnet sizing note: A Business Critical Managed Instance with 2 nodes consumes approximately 9 IPs during normal operation and up to 17 during failover. A /27 subnet (27 usable IPs) is the absolute minimum for a single instance. For multiple instances or upgrade scenarios, use /24. Resizing a subnet after Managed Instance deployment requires taking the instance offline — plan this correctly the first time.

Azure CLI for quick deployment validation:

# Azure CLI — validate MI readiness before Terraform apply

# Check subnet delegation is correct
az network vnet subnet show \
  --resource-group rg-sql-production-eastus \
  --vnet-name vnet-mi-production \
  --name snet-managed-instance \
  --query "delegations[].serviceName" \
  --output tsv

# Verify no conflicting NSG rules blocking MI management ports
# MI requires inbound 9000, 9003, 1438, 1440, 1452 from AzureCloud service tag
az network nsg rule list \
  --resource-group rg-sql-production-eastus \
  --nsg-name nsg-managed-instance \
  --output table

# Check the MI provisioning state — MI can take 4-6 hours to provision
az sql mi show \
  --resource-group rg-sql-production-eastus \
  --name mi-prod-eastus-001 \
  --query "{State:state, FQDN:fullyQualifiedDomainName, vCores:vCores}" \
  --output table

13.3 Networking: Private Endpoints, VNet Integration, and the Public Internet

One of the largest mental shifts for on-premises DBAs is networking. On-premises, you controlled network access through firewall rules, pg_hba.conf equivalents, SQL Server login restrictions, and physical network segmentation. In Azure, the equivalent mechanisms are Private Endpoints, VNet Service Endpoints, firewall rules on the logical server, and network security groups.

Azure SQL Database uses a logical server model. By default, the logical server has a public endpoint. Every Azure best practice guide will tell you to disable it and use Private Endpoints instead, and they are correct. A private endpoint creates a network interface in your VNet with a private IP address that maps to your logical server. Traffic never traverses the public internet.

# Azure CLI — create a private endpoint for Azure SQL Database

# Step 1: Disable public access on the logical server
az sql server update \
  --resource-group rg-sql-production-eastus \
  --name sql-prod-eastus-001 \
  --enable-public-network false

# Step 2: Create the private endpoint
az network private-endpoint create \
  --name pe-sql-prod-eastus \
  --resource-group rg-sql-production-eastus \
  --vnet-name vnet-application-eastus \
  --subnet snet-application-tier \
  --private-connection-resource-id $(az sql server show \
      --resource-group rg-sql-production-eastus \
      --name sql-prod-eastus-001 \
      --query id --output tsv) \
  --group-id sqlServer \
  --connection-name conn-sql-prod-eastus

# Step 3: Create a private DNS zone for name resolution
# Without this, your application cannot resolve the SQL server FQDN
az network private-dns zone create \
  --resource-group rg-sql-production-eastus \
  --name "privatelink.database.windows.net"

az network private-dns link vnet create \
  --resource-group rg-sql-production-eastus \
  --zone-name "privatelink.database.windows.net" \
  --name dns-link-vnet-app \
  --virtual-network vnet-application-eastus \
  --registration-enabled false

# Step 4: Create DNS zone group to auto-register the private endpoint IP
az network private-endpoint dns-zone-group create \
  --resource-group rg-sql-production-eastus \
  --endpoint-name pe-sql-prod-eastus \
  --name sql-dns-zone-group \
  --private-dns-zone "privatelink.database.windows.net" \
  --zone-name sql

# Verify resolution from within the VNet
# sql-prod-eastus-001.database.windows.net should now resolve to 10.x.x.x
nslookup sql-prod-eastus-001.database.windows.net

Managed Instance operates differently. Because it is VNet-injected, it only has a private endpoint by default — the instance lives inside your subnet. The challenge with MI networking is that it requires specific NSG rules for the management plane. Azure's MI management infrastructure must be able to reach the instance on ports 9000, 9003, 1438, 1440, and 1452. If you lock down your NSG incorrectly, the MI enters a failed state and becomes unreachable. The required NSG rule uses the SqlManagement service tag as the source.

# Verify MI management traffic is not blocked
# Run this before deploying MI — a blocked management port causes provisioning failure

az network nsg rule create \
  --resource-group rg-sql-production-eastus \
  --nsg-name nsg-managed-instance \
  --name AllowAzureManagement \
  --priority 100 \
  --source-address-prefixes SqlManagement \
  --destination-address-prefixes "*" \
  --destination-port-ranges 9000 9003 1438 1440 1452 \
  --access Allow \
  --protocol Tcp \
  --direction Inbound

# Verify connectivity to MI from application subnet
# MI uses port 1433 for TDS (same as SQL Server) and 3342 for public endpoint (if enabled)
az network watcher test-connectivity \
  --resource-group rg-sql-production-eastus \
  --source-resource /subscriptions/${SUBSCRIPTION_ID}/resourceGroups/rg-application/providers/Microsoft.Compute/virtualMachines/vm-app-001 \
  --dest-address mi-prod-eastus-001.a1b2c3d4e5f6.database.windows.net \
  --dest-port 1433

SQL Server on VM uses standard Azure VM networking. You control NSGs at the NIC and subnet level, and you configure SQL Server's firewall through SQL Server Configuration Manager — exactly as you would on-premises. The main gotcha is that Azure VM firewall rules and SQL Server's built-in firewall are independent. Both must allow traffic.

13.4 High Availability and Business Continuity

This section is where the three deployment models diverge most dramatically from on-premises patterns. On-premises, you built Always On Availability Groups manually: you configured Windows Server Failover Clustering, set up quorum, joined replicas, created the listener, and spent a weekend validating failover behavior. In Azure, HA is either built into the service layer (Azure SQL DB and MI) or your responsibility (SQL Server on VM).

Azure SQL Database HA uses a multi-replica architecture internally. General Purpose tier uses remote storage (Azure Premium Storage) with a single compute node — there is no synchronous replica, so failover involves attaching storage to a new compute node, which takes 20–30 seconds. Business Critical tier maintains 3–4 synchronous replicas using Always On AG technology under the covers. You cannot see the replicas directly, but failover is near-instantaneous (typically under 5 seconds). The Business Critical tier also exposes one read-only replica that you can redirect read workloads to without extra cost.

Auto-failover groups provide geo-redundancy across regions for both Azure SQL DB and Managed Instance:

# Azure CLI — configure auto-failover group for Azure SQL Database

# Create the secondary server in paired region
az sql server create \
  --name sql-prod-westus-001 \
  --resource-group rg-sql-production-westus \
  --location "West US" \
  --admin-user sqladmin \
  --admin-password "${SQL_ADMIN_PASSWORD}"

# Create the failover group
az sql failover-group create \
  --name fog-prod-eastus-westus \
  --server sql-prod-eastus-001 \
  --resource-group rg-sql-production-eastus \
  --partner-server sql-prod-westus-001 \
  --partner-resource-group rg-sql-production-westus \
  --failover-policy Automatic \
  --grace-period 1   # Hours before automatic failover triggers — 1 is minimum

# Add databases to the failover group
az sql failover-group update \
  --name fog-prod-eastus-westus \
  --server sql-prod-eastus-001 \
  --resource-group rg-sql-production-eastus \
  --add-db AppDatabase

# The failover group creates two listener endpoints:
# Read-write: fog-prod-eastus-westus.database.windows.net (points to primary)
# Read-only:  fog-prod-eastus-westus.secondary.database.windows.net

# Test failover — this promotes the secondary to primary
az sql failover-group set-primary \
  --name fog-prod-eastus-westus \
  --server sql-prod-westus-001 \
  --resource-group rg-sql-production-westus

RPO and RTO characteristics in production:

| Deployment | HA Tier | RTO (same region) | RTO (geo-failover) | RPO |

|---|---|---|---|---|

| Azure SQL DB - General Purpose | Built-in | 20–30 sec | ~30 min | Up to 1 hour |

| Azure SQL DB - Business Critical | Built-in | <5 sec | ~30 min | ~5 sec |

| Managed Instance - General Purpose | Built-in | ~20 sec | ~1 hour | ~1 hour |

| Managed Instance - Business Critical | Built-in | <5 sec | ~30 min | ~5 sec |

| SQL Server on VM (manual AG) | DIY | ~30 sec | DIY | Depends on sync mode |

SQL Server on Azure VM requires you to build Always On AG using Windows Server Failover Clustering. Azure provides an Internal Load Balancer for the AG listener (equivalent to the on-premises listener IP). The key difference from on-premises is that the ILB requires a probe port configured in the AG listener, and the floating IP behavior differs slightly from on-premises due to Azure's networking model.

-- SQL Server on Azure VM: AG listener with Azure ILB probe
-- The probe port (59999 here) must match the ILB health probe configuration

ALTER AVAILABILITY GROUP [AG_Production]
ADD LISTENER 'AGListener' (
    WITH IP (('10.10.2.100', '255.255.255.0')),
    PORT = 1433
);
GO

-- Configure ILB probe response — run on each replica
-- Azure ILB sends TCP probes to 59999; only the primary should respond
EXEC sp_procoption N'sp_ag_probe', 'startup', 'true';
GO

-- Verify AG health
SELECT
    ag.name                     AS availability_group,
    ar.replica_server_name,
    ars.role_desc,
    ars.synchronization_health_desc,
    ars.connected_state_desc,
    ars.last_redone_time,
    ars.log_send_queue_size      AS log_send_queue_kb,
    ars.redo_queue_size          AS redo_queue_kb
FROM sys.availability_groups ag
JOIN sys.availability_replicas ar
    ON ag.group_id = ar.group_id
JOIN sys.dm_hadr_availability_replica_states ars
    ON ar.replica_id = ars.replica_id
ORDER BY ag.name, ars.role_desc;

13.5 Security: Authentication, Encryption, and Compliance Patterns

On-premises SQL Server security centered on SQL Server logins, Windows Authentication through Active Directory, TDE for encryption at rest, and SSL/TLS for encryption in transit. Azure maps these concepts onto a cloud-native model that is simultaneously more automated and more complex to configure correctly.

Azure Active Directory Authentication replaces Windows Authentication in Azure SQL Database and Managed Instance. For applications, this means using Managed Identity — the application's Azure AD identity — rather than a SQL login with a stored password. This is the cloud equivalent of using a Kerberos service account, except the credential rotation is automatic.

# Python — connecting to Azure SQL Database using Managed Identity
# No password stored anywhere — the token is obtained from Azure AD

import struct
import pyodbc
from azure.identity import DefaultAzureCredential

def get_connection_with_managed_identity(server: str, database: str) -> pyodbc.Connection:
    """
    Connect to Azure SQL Database using Managed Identity.
    Works in Azure VMs, App Service, AKS, and Azure Functions
    where Managed Identity is assigned.
    
    On-premises equivalent: Kerberos/Windows auth with service account.
    """
    credential = DefaultAzureCredential()
    
    # Obtain an access token for Azure SQL Database
    # Resource ID for Azure SQL is always this URI
    token = credential.get_token("https://database.windows.net/.default")
    
    # SQL Server ODBC driver expects the token in a specific binary format
    # This packing is required — it is not optional
    token_bytes = token.token.encode("UTF-16-LE")
    token_struct = struct.pack(
        f"<I{len(token_bytes)}s",
        len(token_bytes),
        token_bytes
    )
    
    connection_string = (
        f"DRIVER={{ODBC Driver 18 for SQL Server}};"
        f"SERVER={server};"
        f"DATABASE={database};"
        f"Encrypt=yes;"
        f"TrustServerCertificate=no;"
    )
    
    SQL_COPT_SS_ACCESS_TOKEN = 1256  # ODBC driver attribute for token auth
    conn = pyodbc.connect(
        connection_string,
        attrs_before={SQL_COPT_SS_ACCESS_TOKEN: token_struct}
    )
    return conn


# Usage example
conn = get_connection_with_managed_identity(
    server="sql-prod-eastus-001.database.windows.net",
    database="AppDatabase"
)

# Grant the Managed Identity access inside the database
# Run this as an Azure AD admin:
"""
CREATE USER [my-app-service-name] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [my-app-service-name];
ALTER ROLE db_datawriter ADD MEMBER [my-app-service-name];
-- Grant execute on specific schemas, not broad roles, in production
GRANT EXECUTE ON SCHEMA::app TO [my-app-service-name];
"""

Transparent Data Encryption (TDE) is enabled by default on all three deployment models in Azure. The gotcha is key management. By default, TDE uses a Microsoft-managed key (service-managed TDE). For compliance scenarios requiring customer control over key material — PCI-DSS, HIPAA, some government frameworks — you need Customer-Managed Keys (CMK) stored in Azure Key Vault. Switching from service-managed to customer-managed TDE after the database is in production is possible but requires careful planning: if the Key Vault key becomes inaccessible (deleted, soft-deleted, or permissions revoked), the database becomes encrypted but unreadable within hours.

# Azure CLI — configure Customer-Managed Key TDE for Azure SQL Database

# Step 1: Create a Key Vault with soft delete and purge protection
# Purge protection is REQUIRED — without it, accidental key deletion destroys your data
az keyvault create \
  --name kv-sql-tde-prod \
  --resource-group rg-sql-production-eastus \
  --location "East US" \
  --enable-soft-delete true \
  --enable-purge-protection true \
  --sku premium   # Premium tier required for HSM-backed keys

# Step 2: Create the TDE protector key
az keyvault key create \
  --vault-name kv-sql-tde-prod \
  --name tde-protector-sql-prod \
  --kty RSA-HSM \
  --size 2048 \
  --ops wrapKey unwrapKey get

# Step 3: Grant the logical server's system-assigned identity access to the key
SERVER_IDENTITY=$(az sql server show \
  --resource-group rg-sql-production-eastus \
  --name sql-prod-eastus-001 \
  --query identity.principalId \
  --output tsv)

az keyvault set-policy \
  --name kv-sql-tde-prod \
  --object-id "${SERVER_IDENTITY}" \
  --key-permissions get wrapKey unwrapKey

# Step 4: Set the TDE protector on the logical server
KEY_ID=$(az keyvault key show \
  --vault-name kv-sql-tde-prod \
  --name tde-protector-sql-prod \
  --query key.kid \
  --output tsv)

az sql server tde-key set \
  --resource-group rg-sql-production-eastus \
  --server sql-prod-eastus-001 \
  --server-key-type AzureKeyVault \
  --kid "${KEY_ID}"

# Step 5: Enable CMK TDE on the database
az sql db tde set \
  --resource-group rg-sql-production-eastus \
  --server sql-prod-eastus-001 \
  --database AppDatabase \
  --status Enabled

Auditing and compliance works differently across the three models. Azure SQL Database and Managed Instance both support Azure SQL Audit, which writes audit records to Azure Blob Storage, Log Analytics, or Azure Event Hubs. SQL Server on VM uses SQL Server Audit (T-SQL CREATE SERVER AUDIT) writing to Windows Event Log or a file path, which you then ship to whatever SIEM you run.

-- T-SQL: Configure server-level audit on Managed Instance
-- This is equivalent to on-premises SQL Server Audit
-- Destination: Blob Storage (most common for compliance retention)

CREATE SERVER AUDIT [ComplianceAudit]
TO EXTERNAL MONITOR   -- On Managed Instance, use EXTERNAL MONITOR to route
                      -- to the Azure SQL Audit infrastructure
WITH (
    QUEUE_DELAY = 1000,    -- Milliseconds — 0 is synchronous (performance impact)
    ON_FAILURE = CONTINUE  -- FAIL_OPERATION stops workload if audit fails; evaluate carefully
);
GO

CREATE SERVER AUDIT SPECIFICATION [CriticalServerEvents]
FOR SERVER AUDIT [ComplianceAudit]
ADD (FAILED_LOGIN_GROUP),
ADD (SUCCESSFUL_LOGIN_GROUP),
ADD (SERVER_ROLE_MEMBER_CHANGE_GROUP),
ADD (DATABASE_PERMISSION_CHANGE_GROUP),
ADD (SCHEMA_OBJECT_PERMISSION_CHANGE_GROUP),
ADD (DBCC_GROUP),
ADD (BACKUP_RESTORE_GROUP)
WITH (STATE = ON);
GO

ALTER SERVER AUDIT [ComplianceAudit] WITH (STATE = ON);
GO

-- Verify audit state
SELECT
    a.name,
    a.audit_id,
    a.type_desc,
    a.on_failure_desc,
    a.queue_delay,
    a.is_state_enabled,
    asp.name          AS specification_name,
    asp.is_state_enabled AS spec_enabled
FROM sys.server_audits a
LEFT JOIN sys.server_audit_specifications asp
    ON a.audit_id = asp.audit_id;

13.6 Performance Tuning: Service Tiers, Resource Limits, and the Query Store

Performance tuning in Azure SQL differs from on-premises in one fundamental way: resources are finite and explicitly allocated. On-premises, if your SQL Server needed more CPU, the OS scheduler gave it whatever physical cores were available. In Azure, your vCore allocation is a hard ceiling. Understanding where that ceiling sits — and how to adjust it without downtime — is core DBA knowledge for this environment.

Azure SQL Database service tiers:

  • → **General Purpose (GP):** Remote Azure Premium Storage. Adequate IOPS and throughput for most OLTP workloads. Single compute node with no read replicas visible to you. Failover involves reattaching storage, so plan for brief disruptions.
  • → **Business Critical (BC):** Local SSD storage on the compute node, with 3–4 synchronous replicas. Significantly higher IOPS ceiling. One read-only replica is available for offloading reporting. Substantially higher cost.
  • → **Hyperscale:** Decouples compute from storage using a distributed storage layer. Storage scales automatically without size limits. Read replicas scale horizontally. Best for large OLAP workloads or databases growing unpredictably. The architecture is fundamentally different — not a drop-in replacement for GP or BC.

    • Scaling without downtime:

    # Azure CLI — scale Azure SQL Database vCore count

    Query Store is your primary performance diagnostic tool in Azure SQL and Managed Instance. Unlike on-premises where you might rely on Profiler, Extended Events, and third-party tools, the cloud-native approach centers on Query Store because it persists across connections and failovers, captures execution plans with runtime statistics, and does not require elevated permissions to query.

    -- Query Store: find top 10 regressed queries in the past 24 hours
-- Works identically on Azure SQL Database, Managed Instance, and SQL Server on VM

WITH RecentInterval AS (
    SELECT TOP 1 end_time AS cutoff
    FROM sys.query_store_runtime_stats_interval
    WHERE end_time >= DATEADD(HOUR, -24, GETUTCDATE())
    ORDER BY end_time ASC
)
SELECT TOP 10
    qsq.query_id,
    qsqt.query_sql_text,
    qsp.plan_id,
    qsrs.execution_type_desc,
    qsrs.count_executions,
    qsrs.avg_duration              / 1000.0  AS avg_duration_ms,
    qsrs.max_duration              / 1000.0  AS max_duration_ms,
    qsrs.avg_cpu_time              / 1000.0  AS avg_cpu_ms,
    qsrs.avg_logical_io_reads,
    qsrs.avg_rowcount,
    qsp.is_forced_plan,
    qsp.last_force_failure_reason_desc
FROM sys.query_store_query           qsq
JOIN sys.query_store_query_text      qsqt ON qsq.query_text_id  = qsqt.query_text_id
JOIN sys.query_store_plan            qsp  ON qsq.query_id        = qsp.query_id
JOIN sys.query_store_runtime_stats   qsrs ON qsp.plan_id         = qsrs.plan_id
JOIN sys.query_store_runtime_stats_interval qsrsi
                                          ON qsrs.runtime_stats_interval_id = qsrsi.runtime_stats_interval_id
CROSS JOIN RecentInterval ri
WHERE qsrsi.end_time >= ri.cutoff
  AND qsrs.execution_type = 0   -- Regular executions only
ORDER BY qsrs.avg_duration DESC;
GO

-- Force a specific plan when a regression is identified
-- This is the Azure-native equivalent of a plan guide
EXEC sys.sp_query_store_force_plan
    @query_id = 1234,
    @plan_id  = 5678;
GO

-- Verify forced plan status
SELECT
    qsq.query_id,
    qsp.plan_id,
    qsp.is_forced_plan,
    qsp.force_failure_count,
    qsp.last_force_failure_reason_desc,
    qsp.last_execution_time
FROM sys.query_store_query qsq

    Resource pressure diagnostics — when your workload is hitting the vCore ceiling, the signal is SOS_SCHEDULER_YIELD waits combined with CPU utilization pinned at 100% of your allocated vCores. In Azure SQL Database, the sys.dm_db_resource_stats DMV provides a 15-second granularity view of resource consumption that on-premises DMVs do not offer.

    -- Azure SQL Database only: resource consumption at 15-second granularity
-- Use this to identify when you are hitting CPU, I/O, or log rate limits

SELECT TOP 100
    end_time,
    avg_cpu_percent,
    avg_data_io_percent,
    avg_log_write_percent,
    avg_memory_usage_percent,
    xtp_storage_percent,
    max_worker_percent,
    max_session_percent
FROM sys.dm_db_resource_stats
ORDER BY end_time DESC;

-- Identify the top resource-consuming sessions right now
SELECT TOP 20
    s.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    r.status,
    r.wait_type,
    r.wait_time                 / 1000.0  AS wait_time_sec,
    r.cpu_time                  / 1000.0  AS cpu_time_sec,
    r.total_elapsed_time        / 1000.0  AS elapsed_sec,
    r.logical_reads,
    r.writes,
    SUBSTRING(qt.text, (r.statement_start_offset / 2) + 1,
        ((CASE r.statement_end_offset
            WHEN -1 THEN DATALENGTH(qt.text)
            ELSE r.statement_end_offset
          END - r.statement_start_offset) / 2) + 1)   AS current_statement
FROM sys.dm_exec_sessions         s
JOIN sys.dm_exec_requests         r  ON s.session_id = r.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) qt
WHERE s.is_user_process = 1
ORDER BY r.cpu_time DESC;

    13.8 Cost Optimization: Choosing the Right Tier and Right-Sizing

    Azure SQL costs money in ways on-premises does not: you pay for compute, storage, backup storage, geo-redundancy, and licensing separately. Getting the sizing wrong — especially overprovisioning — is the most common cost problem in production Azure SQL deployments.

    Reserved Instances are the single largest cost lever for predictable workloads. Committing to 1-year or 3-year reserved capacity typically yields substantial savings over pay-as-you-go pricing for the compute component. The tradeoff is that reserved capacity is committed — if you scale the instance up or down, the reservation may no longer match.

    Elastic Pools reduce cost when you have multiple databases with non-overlapping peak usage patterns. The economics work when individual databases have high peaks but low average utilization — the pool's shared vCores handle peaks from different databases at different times. The key metric to validate is the aggregate maximum concurrent vCore demand across all databases. If all databases peak simultaneously, an elastic pool provides no benefit over individually provisioned databases.

    -- Query to identify databases suitable for elastic pool consolidation
-- Run on Azure SQL Database logical server (requires master database connection)
-- Identifies databases where max utilization is high but average is low

SELECT
    d.name                              AS database_name,
    rs.avg_cpu_percent_max              AS peak_cpu_pct,
    rs.avg_cpu_percent_mean             AS avg_cpu_pct,
    rs.avg_data_io_percent_max          AS peak_io_pct,
    rs.avg_log_write_percent_max        AS peak_log_pct,
    CASE
        WHEN rs.avg_cpu_percent_max > 80
         AND rs.avg_cpu_percent_mean < 20
        THEN 'Good pool candidate'
        WHEN rs.avg_cpu_percent_max > 80
         AND rs.avg_cpu_percent_mean >= 20
        THEN 'High sustained load — poor candidate'
        ELSE 'Low utilization — good candidate'
    END                                 AS pool_recommendation
FROM sys.databases d
CROSS APPLY (
    SELECT
        MAX(avg_cpu_percent)        AS avg_cpu_percent_max,
        AVG(avg_cpu_percent)        AS avg_cpu_percent_mean,
        MAX(avg_data_io_percent)    AS avg_data_io_percent_max,
        MAX(avg_log_write_percent)  AS avg_log_write_percent_max
    FROM sys.resource_stats
    WHERE database_name = d.name
      AND start_time >= DATEADD(DAY, -14, GETUTCDATE())
) rs
WHERE d.database_id > 4   -- exclude system databases
ORDER BY rs.avg_cpu_percent_max DESC;

    13.9 Production Gotchas: What the Documentation Does Not Tell You

    This section distills the lessons that only emerge after running these services under real production load.

    Gotcha 1: Managed Instance provisioning and scaling take hours, not minutes.

    When you provision a new Managed Instance or scale its vCore count, the operation can take between 4 and 6 hours for General Purpose, and up to 8 hours for Business Critical. This is not a bug — the service is reshaping underlying cluster resources. Plan MI scaling during maintenance windows. Do not attempt to scale MI two hours before a peak load event.

    Gotcha 2: Azure SQL Database connection limits are lower than you expect.

    The maximum concurrent connections on General Purpose tier scale with vCores, but the ceiling is lower than a comparable on-premises SQL Server. A 4-vCore GP database has a maximum worker thread count that will surprise teams migrating applications that use connection-per-thread architectures. The fix is connection pooling — always use a connection pool in front of Azure SQL Database. max_worker_percent in sys.dm_db_resource_stats is your early warning signal.

    Gotcha 3: Maintenance windows do not guarantee zero-impact updates.

    Even with a maintenance window configured, Azure SQL Database and Managed Instance apply updates that cause brief connection resets. The duration is typically short — usually under 30 seconds for SQL Database and under 60 seconds for Managed Instance — but applications that do not implement retry logic on transient connection failures will surface errors to end users. Implement retry logic using exponential backoff before migration, not after.

    # Python: retry logic for transient Azure SQL errors
# Transient error codes: 40613, 40197, 40501, 40549, 49918, 49919, 49920, 4221

import time
import pyodbc
from typing import Callable, TypeVar

T = TypeVar('T')

TRANSIENT_ERROR_CODES = {40613, 40197, 40501, 40549, 49918, 49919, 49920, 4221}

def execute_with_retry(
    operation: Callable[[], T],
    max_attempts: int = 5,
    base_delay_seconds: float = 1.0
) -> T:
    """
    Execute a database operation with exponential backoff retry.
    Handles transient Azure SQL errors (connection resets during maintenance,
    throttling, temporary unavailability).
    """
    for attempt in range(1, max_attempts + 1):
        try:
            return operation()
        except pyodbc.Error as e:
            error_code = e.args[0] if e.args else None
            
            # Parse SQL error code from the error message
            sql_error_code = None
            if len(e.args) > 1:
                try:
                    sql_error_code = int(str(e.args[1]).split()[0])
                except (ValueError, IndexError):
                    pass
            
            is_transient = (
                sql_error_code in TRANSIENT_ERROR_CODES
                or "connection" in str(e).lower()
                or "timeout" in str(e).lower()
            )
            
            if not is_transient or attempt == max_attempts:
                raise
            
            delay = base_delay_seconds * (2 ** (attempt - 1))
            # Add jitter to prevent thundering herd during mass reconnect
            jitter = delay * 0.1
            sleep_time = delay + (jitter * (2 * __import__('random').random() - 1))
            
            print(f"Transient error on attempt {attempt}/{max_attempts}. "
                  f"Retrying in {sleep_time:.1f}s. Error: {e}")
            time.sleep(sleep_time)
    
    # Should not reach here — max_attempts exhausted raises in loop
    raise RuntimeError("Unreachable")

    Gotcha 4: Backup storage costs accumulate silently.

    Azure SQL Database and Managed Instance take automated backups (full, differential, log) and store them in geo-redundant storage by default. You are billed for backup storage beyond the database size included in your tier. For a 1 TB database with 35-day retention, backup storage can exceed the database storage cost itself. Audit your backup retention policy. For non-production environments, reduce retention to 7 days and switch to locally redundant backup storage.

    # Azure CLI — change backup redundancy to LRS for non-production (cost reduction)
az sql db update \
  --resource-group rg-sql-nonprod-eastus \
  --server sql-nonprod-eastus-001 \
  --name DevDatabase \
  --backup-storage-redundancy Local \
  --short-term-retention 7

# Check current backup storage consumption for a server
az sql db list-deleted \
  --resource-group rg-sql-production-eastus \
  --server sql-prod-eastus-001 \
  --output table

# For Managed Instance: set backup storage redundancy at creation time (cannot be changed after provisioning)
az sql mi create \
  --resource-group rg-sql-production-eastus \
  --name mi-prod-eastus-002 \
  --backup-storage-redundancy Geo \
  # ... other parameters

    Gotcha 5: Geo-replication lag is invisible until a failover.

    Auto-failover groups use asynchronous replication for geo-redundancy. The secondary replica lags the primary — sometimes by seconds, sometimes by minutes under heavy write load. Most teams never check the replication lag until a failover reveals that the secondary is hours behind. Monitor replication lag continuously using the DMV sys.dm_geo_replication_link_status on Azure SQL Database or the sys.dm_hadr_database_replica_states on Managed Instance.

    -- Azure SQL Database: check geo-replication lag
-- Run on the PRIMARY database

SELECT
    link_guid,
    partner_server,
    partner_database,
    replication_state_desc,
    role_desc,
    replication_lag_sec,
    last_replication,
    start_time
FROM sys.dm_geo_replication_link_status;

-- Alert threshold: if replication_lag_sec exceeds your RPO, investigate immediately
-- A sustained lag under normal write load indicates the secondary is undersized
-- or the network path between regions has degraded throughput

-- Managed Instance: equivalent check via AG DMVs
SELECT
    ag.name                                 AS availability_group,
    ar.replica_server_name,
    drs.database_id,
    DB_NAME(drs.database_id)               AS database_name,
    drs.synchronization_state_desc,
    drs.last_commit_time,
    drs.log_send_queue_size                 AS log_send_queue_kb,
    drs.redo_queue_size                     AS redo_queue_kb,
    DATEDIFF(SECOND, drs.last_redone_time, GETUTCDATE()) AS seconds_behind_primary
FROM sys.dm_hadr_database_replica_states   drs
JOIN sys.availability_replicas             ar
    ON drs.replica_id = ar.replica_id
JOIN sys.availability_groups               ag
    ON ar.group_id = ag.group_id
WHERE drs.is_local = 0   -- remote replicas only
ORDER BY seconds_behind_primary DESC;

    Gotcha 6: SQL Server on VM requires the IaaS Agent extension to be registered — and most teams skip this.

    Azure provides the SQL IaaS Agent extension for SQL Server on VMs. Without it, you lose automated backup integration with Azure Recovery Services Vault, automated patching scheduling, Key Vault integration for TDE, and the ability to apply Azure Hybrid Benefit through the portal. Register every SQL Server VM with this extension immediately after provisioning.

    # Register SQL Server VM with IaaS Agent extension
az sql vm create \
  --resource-group rg-sql-production-eastus \
  --name vm-sqlserver-prod-001 \
  --location "East US" \
  --license-type PAYG \
  --sql-mgmt-type Full   # Full management mode required for automated backup/patching

# If the VM already exists without the extension, register it:
az sql vm update \
  --resource-group rg-sql-production-eastus \
  --name vm-sqlserver-prod-001 \
  --sql-mgmt-type Full

# Configure automated backup through the extension
az sql vm update \
  --resource-group rg-sql-production-eastus \
  --name vm-sqlserver-prod-001 \
  --auto-backup-settings '{
    "enable": true,
    "retentionPeriod": 30,
    "storageAccountUrl": "https://stbackupprod.blob.core.windows.net/",
    "storageAccessToken": "'"${STORAGE_SAS_TOKEN}"'",
    "enableEncryption": true,
    "backupSystemDbs": true,
    "backupScheduleType": "Automated"
  }'

    Gotcha 7: Tempdb configuration on Managed Instance is not user-controllable.

    On-premises and SQL Server on VM, you add multiple tempdb data files (one per logical CPU, up to 8) to reduce allocation page contention. On Managed Instance, tempdb is pre-configured by the service and you cannot add or resize tempdb files directly. This matters for workloads with heavy tempdb usage (sorts, spills, temp table creation at high concurrency). If your workload generates significant tempdb contention on Managed Instance, the primary lever is vCore scaling — more vCores means more pre-configured tempdb files.

    -- Check tempdb file configuration on Managed Instance
-- You can observe but not alter the file layout

SELECT
    file_id,
    name,
    physical_name,
    type_desc,
    size * 8 / 1024     AS size_mb,
    max_size * 8 / 1024 AS max_size_mb,
    growth              AS growth_pages,
    is_percent_growth
FROM tempdb.sys.database_files
ORDER BY file_id;

-- Diagnose tempdb allocation contention
SELECT
    wait_type,
    waiting_tasks_count,
    wait_time_ms,
    max_wait_time_ms,
    signal_wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_type IN (
    'PAGELATCH_UP', 'PAGELATCH_EX', 'PAGELATCH_SH',
    'PAGEIOLATCH_UP', 'PAGEIOLATCH_EX'
)
ORDER BY wait_time_ms DESC;

-- Identify specific pages under contention (tempdb allocation pages are 1:1, 1:3)
SELECT
    session_id,
    wait_type,
    wait_duration_ms,
    resource_description   -- Look for 2:1:1, 2:1:3 (tempdb GAM/SGAM pages)
FROM sys.dm_os_waiting_tasks
WHERE wait_type LIKE 'PAGELATCH%'
ORDER BY wait_duration_ms DESC;

    13.10 Choosing Your Model: A Decision Framework

    After reading through the technical details, the selection decision reduces to a structured evaluation across four dimensions: feature requirements, operational model preference, migration complexity, and cost profile.

    Feature requirements drive the first cut. Ask these questions in order:

    1. Does your workload require OS-level access (third-party agents, custom startup procedures, non-SQL Server processes on the same host)? → SQL Server on VM. This is the only answer. No other model provides OS access.

    2. Does your workload require SQL Server Agent with complex multi-step jobs, cross-database queries, linked servers, Service Broker, or Database Mail? → Managed Instance. Azure SQL Database cannot satisfy these requirements without significant application rework.

    3. Is your workload a greenfield application or a modernized application that does not depend on instance-level features? → Azure SQL Database. It provides the most managed experience, the lowest operational overhead, and the most direct path to cloud-native patterns like elastic scaling and serverless compute.

    Operational model preference is the second cut. If your organization has a small DBA team that cannot sustain OS-level patching and HA configuration responsibilities, SQL Server on VM is a trap regardless of the feature match. Conversely, if your team includes DBAs with strong Windows Server and Always On skills, SQL Server on VM gives you the most control and the easiest path to validating the environment behaves exactly as expected.

    Migration complexity determines timeline. A same-generation SQL Server database with no blocked features can be migrated to Managed Instance in a weekend using DMS online migration. The same database migrated to Azure SQL Database may require weeks of application rework to eliminate cross-database queries, replace SQL Agent jobs, and refactor linked server dependencies. Be honest about the backlog this creates.

    Cost profile determines long-term sustainability. Managed Instance is significantly more expensive than Azure SQL Database for equivalent compute because it runs a full SQL Server instance rather than individual databases. A single 8-vCore General Purpose Managed Instance costs more than multiple small Azure SQL Databases serving the same workload. For SaaS applications with many small tenant databases, Azure SQL Database with elastic pools is almost always the correct cost model. For enterprise line-of-business applications with 10–20 databases sharing an instance, Managed Instance matches the on-premises cost model more closely.

    One final consideration that experienced DBAs overlook: Managed Instance is not immune to the limitations of a managed service. You cannot run SQL Server Profiler against it. You cannot install extended events sessions that write to files on the OS. You cannot use third-party backup software. If your compliance team requires a third-party backup verification tool or a host-based encryption agent, only SQL Server on VM satisfies that requirement. Validate your full list of operational tooling against the managed service's capability surface before committing to a deployment model.

    ---

    Key Takeaways

  • → **Deployment model selection is irreversible in the short term.** Migrating from Azure SQL Database to Managed Instance, or from Managed Instance to SQL Server on VM, requires database migrations and application changes. Invest the time to assess feature dependencies accurately before choosing a model.
  • → **Managed Instance requires dedicated subnet planning that cannot be corrected after deployment.** Size the subnet for multiple instances and upgrade headroom from day one; a /24 is preferable to a /27 for production environments expecting growth.
  • → **Always On availability and geo-redundancy behave differently across tiers.** Business Critical tier provides near-instantaneous same-region failover with a local SSD replica; General Purpose tier has a longer recovery time due to remote storage reattachment. Match your RTO requirement to the correct tier before signing off on architecture.
  • → **Retry logic for transient connection errors is mandatory, not optional, for any application connecting to Azure SQL Database or Managed Instance.** Maintenance windows and automated failovers produce brief connection resets that will surface as application errors without it.
  • → **Cost optimization requires active management.** Reserved Instances, Azure Hybrid Benefit, elastic pool consolidation, and backup storage redundancy settings each independently reduce spend. None are configured automatically — they require deliberate action at provisioning time and ongoing review as workload patterns evolve.
