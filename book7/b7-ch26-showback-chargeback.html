Chapter 26: Showback vs Chargeback Models for Database Costs

Organizations that implement formal database cost allocation models — whether showback or chargeback — consistently reduce cloud database spend by 20–35% within two quarters. The mechanism is straightforward: when engineering teams see their own name on a line item, consumption behavior changes. When those line items carry real financial consequences, behavior changes faster. This chapter covers the architectural and operational differences between showback and chargeback, how to build allocation models that survive contact with real organizational complexity, and how to automate the reporting pipelines that keep both models honest. The techniques here apply to AWS RDS, Azure SQL Database, and Google Cloud SQL, and they integrate with the tagging and labeling strategies covered in earlier chapters.

---

The Difference Between Showback and Chargeback — and Why It Matters

Showback tells teams what they would be charged if costs were allocated. Chargeback actually moves the money. Both models require identical underlying infrastructure — cost data, tag coverage, allocation rules, and reporting pipelines — but they produce very different organizational outcomes.

Showback is the right starting point for most organizations. It introduces accountability without triggering finance department processes and inter-departmental friction. Teams see their database costs broken out by environment, application, and owner. They don't pay for it directly, but their manager does receive a monthly report. In most organizations, this visibility alone produces meaningful behavior change within 60 days. Teams start asking whether that multi-AZ dev database really needs to be multi-AZ.

Chargeback allocates actual costs to cost centers, business units, or product teams. The infrastructure team charges the analytics team $4,200/month for their Aurora cluster. That charge appears in the analytics team's budget. Finance is involved. Procurement is involved. When the analytics team's database bill doubles after a poorly designed ETL job runs for a week, the pain is real and the fix comes fast.

The decision between the two often comes down to organizational maturity. A startup with three engineering teams can run showback informally through a shared dashboard. An enterprise with 40 business units running separate product lines needs chargeback backed by financial system integration.

The practical implication for DBAs: the technical implementation is the same either way. The difference is what happens after the report is generated — whether the numbers go into a dashboard or into an accounts payable process. Build the infrastructure for chargeback from day one, even if you launch with showback. Retrofitting allocation logic after finance gets involved is painful.

Shared Resource Allocation

The hardest problem in both models is shared infrastructure. A single Aurora cluster might serve three applications. An RDS Proxy might front-end six services. A multi-tenant PostgreSQL instance might host 40 schemas. You have three allocation strategies to choose from:

1. Equal split: Divide the cost by the number of consumers. Simple, inaccurate, and often politically acceptable because it's obviously wrong to everyone equally.

2. Weighted by consumption metric: Allocate based on a measurable proxy — storage used, query count, CPU seconds, connection time. More accurate, requires instrumentation, sometimes produces counterintuitive results when one team runs efficient queries and another runs terrible ones.

3. Direct assignment: Each team owns its own database resources. Clean for accounting, tends to produce resource sprawl and eliminates economies of scale.

Most mature organizations use a hybrid: direct assignment for dedicated instances, weighted allocation for shared clusters, with a periodic review cycle to catch allocation drift.

Building a Tag Coverage Foundation

Cost allocation lives or dies on tag coverage. Every RDS instance, Aurora cluster, RDS Proxy, storage volume, snapshot, and data transfer charge needs tags before allocation can work. The minimum viable tag set for database FinOps is:

Environment:    production | staging | development | sandbox
Team:           data-engineering | analytics | platform | payments
Application:    checkout-service | reporting | user-profiles
CostCenter:     CC-1042 | CC-2087
Owner:          rajan.kumar@company.com

AWS enforces tags at the resource level but not at the snapshot or automated backup level by default. Azure applies resource tags but not to bandwidth charges. GCP labels work differently from AWS tags in ways that matter for billing export queries. These gaps require explicit handling.

Auditing Tag Coverage on AWS

#!/bin/bash
# Audit RDS tag coverage across all regions
# Run weekly via scheduled Lambda or cron
# Outputs CSV report of untagged/partially-tagged instances

REQUIRED_TAGS=("Environment" "Team" "Application" "CostCenter" "Owner")
OUTPUT_FILE="rds_tag_coverage_$(date +%Y%m%d).csv"

echo "Region,DBIdentifier,Engine,InstanceClass,MissingTags" > "$OUTPUT_FILE"

for REGION in $(aws ec2 describe-regions --query 'Regions[].RegionName' --output text); do
    INSTANCES=$(aws rds describe-db-instances \
        --region "$REGION" \
        --query 'DBInstances[*].[DBInstanceIdentifier,Engine,DBInstanceClass,DBInstanceArn]' \
        --output text 2>/dev/null)

    while IFS=$'\t' read -r DB_ID ENGINE INSTANCE_CLASS DB_ARN; do
        [ -z "$DB_ID" ] && continue

        TAGS=$(aws rds list-tags-for-resource \
            --resource-name "$DB_ARN" \
            --region "$REGION" \
            --query 'TagList[*].Key' \
            --output text 2>/dev/null)

        MISSING_TAGS=""
        for REQUIRED_TAG in "${REQUIRED_TAGS[@]}"; do
            if ! echo "$TAGS" | grep -qw "$REQUIRED_TAG"; then
                MISSING_TAGS="${MISSING_TAGS}${REQUIRED_TAG};"
            fi
        done

        if [ -n "$MISSING_TAGS" ]; then
            echo "$REGION,$DB_ID,$ENGINE,$INSTANCE_CLASS,$MISSING_TAGS" >> "$OUTPUT_FILE"
        fi
    done <<< "$INSTANCES"
done

echo "Tag coverage audit complete: $OUTPUT_FILE"

# Count untagged instances and alert if above threshold
UNTAGGED_COUNT=$(wc -l < "$OUTPUT_FILE")
UNTAGGED_COUNT=$((UNTAGGED_COUNT - 1))  # subtract header

if [ "$UNTAGGED_COUNT" -gt 5 ]; then
    aws sns publish \
        --topic-arn "arn:aws:sns:us-east-1:123456789012:finops-alerts" \
        --message "RDS Tag Coverage Alert: $UNTAGGED_COUNT instances have missing required tags. Review $OUTPUT_FILE" \
        --subject "RDS Tag Coverage Failure - $(date +%Y-%m-%d)"
fi

For GCP, label coverage requires a different approach because labels are queried through the BigQuery billing export rather than through a resource API:

-- GCP: Identify Cloud SQL instances with missing labels
-- Run against the billing export dataset in BigQuery
-- Schedule as a scheduled query with weekly cadence

SELECT
  resource.name AS resource_name,
  service.description AS service,
  sku.description AS sku,
  SUM(cost) AS total_cost_usd,
  ARRAY_AGG(DISTINCT label.key ORDER BY label.key) AS present_labels,
  CASE
    WHEN NOT EXISTS (
      SELECT 1 FROM UNNEST(labels) AS label WHERE label.key = 'environment'
    ) THEN 'MISSING: environment'
    ELSE ''
  END AS missing_environment,
  CASE
    WHEN NOT EXISTS (
      SELECT 1 FROM UNNEST(labels) AS label WHERE label.key = 'team'
    ) THEN 'MISSING: team'
    ELSE ''
  END AS missing_team,
  CASE
    WHEN NOT EXISTS (
      SELECT 1 FROM UNNEST(labels) AS label WHERE label.key = 'cost-center'
    ) THEN 'MISSING: cost-center'
    ELSE ''
  END AS missing_cost_center
FROM
  `your-project.billing_export.gcp_billing_export_v1_XXXXXX_XXXXXX_XXXXXX`,
  UNNEST(labels) AS label
WHERE
  service.description LIKE '%Cloud SQL%'
  AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 30 DAY)
GROUP BY
  resource.name, service.description, sku.description, labels
HAVING
  missing_environment != ''
  OR missing_team != ''
  OR missing_cost_center != ''
ORDER BY
  total_cost_usd DESC
LIMIT 100;

Tag coverage below 90% makes any allocation model politically fragile. When a team disputes their allocation, "we couldn't tag that resource" becomes a credible defense. Drive coverage to 98% or above before launching chargeback.

Building the Allocation Model

With tag coverage solid, the allocation model translates raw billing data into team-level cost reports. This involves three layers: raw cost extraction, allocation rule application, and report generation.

AWS Cost Explorer API for Tag-Based Allocation

#!/usr/bin/env python3
"""
Database cost allocation engine for AWS RDS.
Pulls Cost Explorer data, applies allocation rules for shared resources,
and generates team-level showback reports.

Schedule: Run on the 1st of each month via EventBridge + Lambda
Output: S3 CSV + SNS notification to team leads
"""

import boto3
import json
import csv
import io
from datetime import datetime, timedelta
from dateutil.relativedelta import relativedelta
from collections import defaultdict
import os

# Allocation rules for shared resources
# Resources listed here are split by the specified method and weights
SHARED_RESOURCE_RULES = {
    "aurora-shared-analytics": {
        "method": "weighted",
        "allocations": {
            "analytics": 0.55,
            "data-engineering": 0.30,
            "platform": 0.15
        }
    },
    "rds-proxy-payments": {
        "method": "equal",
        "allocations": {
            "payments": 0.50,
            "checkout-service": 0.50
        }
    }
}

def get_rds_costs_by_tag(start_date: str, end_date: str) -> dict:
    """Pull RDS costs grouped by Team tag from Cost Explorer."""
    client = boto3.client('ce', region_name='us-east-1')

    response = client.get_cost_and_usage(
        TimePeriod={'Start': start_date, 'End': end_date},
        Granularity='MONTHLY',
        Filter={
            'And': [
                {
                    'Dimensions': {
                        'Key': 'SERVICE',
                        'Values': [
                            'Amazon Relational Database Service',
                            'Amazon Aurora'
                        ]
                    }
                }
            ]
        },
        GroupBy=[
            {'Type': 'TAG', 'Key': 'Team'},
            {'Type': 'TAG', 'Key': 'Application'},
            {'Type': 'DIMENSION', 'Key': 'USAGE_TYPE'}
        ],
        Metrics=['UnblendedCost', 'UsageQuantity']
    )

    costs = defaultdict(lambda: defaultdict(float))

    for result in response['ResultsByTime']:
        for group in result['Groups']:
            keys = group['Keys']
            team = keys[0].replace('Team$', '') or 'untagged'
            application = keys[1].replace('Application$', '') or 'unknown'
            usage_type = keys[2]

            cost = float(group['Metrics']['UnblendedCost']['Amount'])
            costs[team][application] += cost

    return dict(costs)


def apply_shared_resource_allocation(
    raw_costs: dict,
    shared_rules: dict,
    start_date: str,
    end_date: str
) -> dict:
    """
    Identify shared resources and redistribute costs per allocation rules.
    Shared resources show up under the 'shared' team tag — allocate them out.
    """
    client = boto3.client('ce', region_name='us-east-1')
    allocated_costs = defaultdict(lambda: defaultdict(float))

    # Copy direct costs
    for team, apps in raw_costs.items():
        if team == 'shared':
            continue
        for app, cost in apps.items():
            allocated_costs[team][app] += cost

    # Pull shared resource costs by resource ID
    response = client.get_cost_and_usage(
        TimePeriod={'Start': start_date, 'End': end_date},
        Granularity='MONTHLY',
        Filter={
            'Tags': {
                'Key': 'Team',
                'Values': ['shared']
            }
        },
        GroupBy=[
            {'Type': 'TAG', 'Key': 'Application'}
        ],
        Metrics=['UnblendedCost']
    )

    for result in response['ResultsByTime']:
        for group in result['Groups']:
            app_name = group['Keys'][0].replace('Application$', '')
            total_cost = float(group['Metrics']['UnblendedCost']['Amount'])

            if app_name in shared_rules:
                rule = shared_rules[app_name]
                for team, weight in rule['allocations'].items():
                    allocated_cost = total_cost * weight
                    allocated_costs[team][f"{app_name} (allocated)"] += allocated_cost
            else:
                # Unmatched shared resources go to 'unallocated' bucket
                allocated_costs['unallocated'][app_name] += total_cost

    return dict(allocated_costs)


def generate_showback_report(
    allocated_costs: dict,
    report_month: str
) -> str:
    """Generate CSV showback report and upload to S3."""
    output = io.StringIO()
    writer = csv.writer(output)
    writer.writerow([
        'Report Month', 'Team', 'Application',
        'Monthly Cost USD', 'Annualized Cost USD',
        'vs Prior Month', 'Allocation Type'
    ])

    for team, apps in sorted(allocated_costs.items()):
        for app, cost in sorted(apps.items(), key=lambda x: x[1], reverse=True):
            annualized = cost * 12
            allocation_type = 'allocated' if '(allocated)' in app else 'direct'
            writer.writerow([
                report_month,
                team,
                app,
                f"{cost:.2f}",
                f"{annualized:.2f}",
                '',  # Prior month comparison filled in by downstream process
                allocation_type
            ])

    csv_content = output.getvalue()

    # Upload to S3
    s3 = boto3.client('s3')
    bucket = os.environ.get('FINOPS_BUCKET', 'company-finops-reports')
    key = f"database-costs/{report_month}/showback-report.csv"

    s3.put_object(
        Bucket=bucket,
        Key=key,
        Body=csv_content.encode('utf-8'),
        ContentType='text/csv',
        ServerSideEncryption='AES256'
    )

    return f"s3://{bucket}/{key}"


def send_team_notifications(allocated_costs: dict, report_month: str, s3_path: str):
    """Send per-team cost summaries via SNS."""
    sns = boto3.client('sns')
    topic_arn = os.environ.get('FINOPS_TOPIC_ARN')

    if not topic_arn:
        return

    total_by_team = {
        team: sum(apps.values())
        for team, apps in allocated_costs.items()
    }

    grand_total = sum(total_by_team.values())

    message_lines = [
        f"Database Cost Showback Report — {report_month}",
        f"{'=' * 50}",
        f"Grand Total: ${grand_total:,.2f}",
        "",
        "By Team:"
    ]

    for team, total in sorted(total_by_team.items(), key=lambda x: x[1], reverse=True):
        pct = (total / grand_total * 100) if grand_total > 0 else 0
        message_lines.append(f"  {team:<25} ${total:>10,.2f}  ({pct:.1f}%)")

    message_lines.extend([
        "",
        f"Full report: {s3_path}",
        "Review your allocation and reach out to #finops-database for questions."
    ])

    sns.publish(
        TopicArn=topic_arn,
        Subject=f"Database Showback Report — {report_month}",
        Message='\n'.join(message_lines)
    )


def lambda_handler(event, context):
    """Entry point for EventBridge-scheduled monthly run."""
    today = datetime.today()
    first_of_month = today.replace(day=1)
    start_date = (first_of_month - relativedelta(months=1)).strftime('%Y-%m-%d')
    end_date = first_of_month.strftime('%Y-%m-%d')
    report_month = (first_of_month - relativedelta(months=1)).strftime('%Y-%m')

    print(f"Generating showback report for {report_month} ({start_date} to {end_date})")

    raw_costs = get_rds_costs_by_tag(start_date, end_date)
    allocated_costs = apply_shared_resource_allocation(
        raw_costs, SHARED_RESOURCE_RULES, start_date, end_date
    )

    s3_path = generate_showback_report(allocated_costs, report_month)
    send_team_notifications(allocated_costs, report_month, s3_path)

    total = sum(
        sum(apps.values())
        for apps in allocated_costs.values()
    )

    return {
        'statusCode': 200,
        'report_month': report_month,
        'total_cost_usd': round(total, 2),
        's3_path': s3_path
    }


if __name__ == '__main__':
    result = lambda_handler({}, None)
    print(json.dumps(result, indent=2))

Metering Shared Databases for Accurate Allocation

Tag-based allocation works for dedicated instances but fails for shared databases where multiple teams share a single RDS instance or Aurora cluster. Accurate allocation at that level requires consumption metering — measuring what each team actually uses.

PostgreSQL exposes per-database and per-user statistics through pg_stat_statements and pg_stat_database. The following query produces a consumption profile that feeds into the allocation model:

-- PostgreSQL: Per-team database consumption metrics for cost allocation
-- Run on shared PostgreSQL/Aurora instances
-- Correlate team with pg_roles by naming convention: team_<teamname>_role

-- Enable pg_stat_statements if not already active:
-- CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
-- ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';

-- Monthly consumption summary by database user (mapped to teams)
WITH user_stats AS (
    SELECT
        usename AS db_user,
        -- Extract team from role naming convention: app_<team>_<role>
        SPLIT_PART(usename, '_', 2) AS team,
        datname AS database_name,
        SUM(total_exec_time) AS total_exec_time_ms,
        SUM(calls) AS total_calls,
        SUM(rows) AS total_rows_returned,
        SUM(shared_blks_read) AS total_blocks_read,
        SUM(shared_blks_hit) AS total_blocks_hit,
        SUM(temp_blks_written) AS total_temp_blocks,
        -- Estimate CPU cost: exec_time is a reasonable proxy
        SUM(total_exec_time) / 1000.0 AS total_exec_time_seconds,
        -- I/O weight: penalize temp writes (spill to disk)
        SUM(shared_blks_read) + (SUM(temp_blks_written) * 3) AS weighted_io_score
    FROM
        pg_stat_statements pss
        JOIN pg_roles pr ON pss.userid = pr.oid
        JOIN pg_database pd ON pss.dbid = pd.oid
    WHERE
        -- Exclude system users and monitoring accounts
        usename NOT IN ('rdsadmin', 'datadog', 'pgbouncer', 'postgres')
        AND usename NOT LIKE 'pg_%'
    GROUP BY
        usename, datname
),
totals AS (
    SELECT
        SUM(total_exec_time_ms) AS grand_total_exec_time,
        SUM(weighted_io_score) AS grand_total_io_score
    FROM user_stats
),
allocation_weights AS (
    SELECT
        us.team,
        us.database_name,
        SUM(us.total_exec_time_ms) AS team_exec_time_ms,
        SUM(us.weighted_io_score) AS team_io_score,
        SUM(us.total_calls) AS team_total_calls,
        SUM(us.total_rows_returned) AS team_total_rows,
        -- CPU allocation weight (0.0 to 1.0)
        ROUND(
            (SUM(us.total_exec_time_ms) / NULLIF(t.grand_total_exec_time, 0))::numeric,
            4
        ) AS cpu_allocation_weight,
        -- I/O allocation weight (0.0 to 1.0)
        ROUND(
            (SUM(us.weighted_io_score) / NULLIF(t.grand_total_io_score, 0))::numeric,
            4
        ) AS io_allocation_weight
    FROM user_stats us
    CROSS JOIN totals t
    GROUP BY us.team, us.database_name, t.grand_total_exec_time, t.grand_total_io_score
)
SELECT
    team,
    database_name,
    team_total_calls AS total_queries,
    ROUND(team_exec_time_ms / 1000.0 / 60.0, 2) AS exec_time_minutes,
    team_total_rows AS rows_returned,
    team_io_score AS weighted_io_score,
    cpu_allocation_weight,
    io_allocation_weight,
    -- Blended allocation weight (60% CPU, 40% I/O)
    ROUND((cpu_allocation_weight * 0.60 + io_allocation_weight * 0.40)::numeric, 4) AS blended_weight,
    -- If instance costs $2,400/month: example allocated cost
    ROUND(
        (cpu_allocation_weight * 0.60 + io_allocation_weight * 0.40) * 2400.0,
        2
    ) AS estimated_monthly_allocation_usd
FROM allocation_weights
WHERE team IS NOT NULL AND team != ''
ORDER BY blended_weight DESC;

For Azure SQL Database, the equivalent consumption query uses Dynamic Management Views:

-- Azure SQL: Per-application consumption metrics for cost allocation
-- Run on shared Azure SQL elastic pools or shared instances
-- Uses app_name from connection string for team identification

WITH app_stats AS (
    SELECT
        -- Application name from connection context
        dest.text AS sample_query,
        qs.plan_handle,
        DB_NAME(qs.sql_handle[0]) AS database_name,
        -- Use application_name from sys.dm_exec_sessions for team mapping
        es.program_name AS application_name,
        -- Extract team name: application names should follow convention "Team:AppName"
        CASE
            WHEN es.program_name LIKE '%:%'
            THEN LEFT(es.program_name, CHARINDEX(':', es.program_name) - 1)
            ELSE 'unknown'
        END AS team,
        SUM(qs.total_worker_time) AS total_cpu_microseconds,
        SUM(qs.total_elapsed_time) AS total_elapsed_microseconds,
        SUM(qs.total_logical_reads) AS total_logical_reads,
        SUM(qs.total_physical_reads) AS total_physical_reads,
        SUM(qs.total_logical_writes) AS total_logical_writes,
        SUM(qs.total_rows) AS total_rows,
        SUM(qs.execution_count) AS total_executions
    FROM
        sys.dm_exec_query_stats qs
        CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) dest
        INNER JOIN sys.dm_exec_sessions es
            ON qs.plan_handle = es.plan_handle -- approximation; use Query Store for accuracy
    WHERE
        es.program_name NOT IN ('Microsoft SQL Server Management Studio',
                                'SQLServerCEIP', 'DatadogAgent')
        AND es.is_user_process = 1
    GROUP BY
        dest.text, qs.plan_handle, es.program_name
),
team_totals AS (
    SELECT
        team,
        SUM(total_cpu_microseconds) AS team_cpu,
        SUM(total_logical_reads + total_physical_reads) AS team_reads,
        SUM(total_executions) AS team_executions
    FROM app_stats
    GROUP BY team
),
grand_totals AS (
    SELECT
        SUM(team_cpu) AS grand_cpu,
        SUM(team_reads) AS grand_reads
    FROM team_totals
)
SELECT
    tt.team,
    tt.team_cpu / 1000000.0 AS cpu_seconds,
    tt.team_reads AS logical_reads,
    tt.team_executions AS total_query_executions,
    ROUND(CAST(tt.team_cpu AS float) / NULLIF(gt.grand_cpu, 0), 4) AS cpu_weight,
    ROUND(CAST(tt.team_reads AS float) / NULLIF(gt.grand_reads, 0), 4) AS io_weight,
    -- Blended weight and example $1,800/month allocation
    ROUND(
        (CAST(tt.team_cpu AS float) / NULLIF(gt.grand_cpu, 0) * 0.60 +
         CAST(tt.team_reads AS float) / NULLIF(gt.grand_reads, 0) * 0.40) * 1800.0,
        2
    ) AS estimated_monthly_cost_usd
FROM team_totals tt
CROSS JOIN grand_totals gt
ORDER BY cpu_weight DESC;

These queries produce the consumption weights that feed into the Python allocation engine. The critical discipline is resetting pg_stat_statements at the start of each billing cycle:

-- Reset statistics at billing cycle start (run on 1st of each month)

Automating Chargeback with Financial System Integration

Showback stops at the report. Chargeback requires feeding allocation data into financial systems — whether that's Jira for internal budget tracking, NetSuite, SAP, or simply a structured format that finance can import into their GL system.

The following automation pulls monthly allocations, applies business rules, generates itemized invoices per cost center, and delivers them in both human-readable and machine-readable formats. For AWS, the source data comes from the allocation engine built earlier. For Azure, it comes from Azure Cost Management exports.

#!/bin/bash
# Azure: Pull database cost allocation by resource tag using Azure Cost Management API
# Prerequisite: az login completed, subscription ID set
# Schedule: Run via Azure Automation or cron on 1st of month

SUBSCRIPTION_ID="${AZURE_SUBSCRIPTION_ID}"
RESOURCE_GROUP_PATTERN="*-database-*"  # Match all database resource groups
REPORT_MONTH=$(date -d "last month" +%Y-%m)
START_DATE=$(date -d "last month" +%Y-%m-01)
END_DATE=$(date +%Y-%m-01)
OUTPUT_DIR="/tmp/chargeback-${REPORT_MONTH}"
mkdir -p "$OUTPUT_DIR"

echo "Generating Azure database chargeback report for $REPORT_MONTH"

# Pull cost data grouped by team tag from Cost Management
az costmanagement query \
    --scope "subscriptions/${SUBSCRIPTION_ID}" \
    --type "Usage" \
    --timeframe "Custom" \
    --time-period "from=${START_DATE}T00:00:00Z" "to=${END_DATE}T00:00:00Z" \
    --dataset-granularity "Monthly" \
    --dataset-aggregation "totalCost=sum(Cost)" \
    --dataset-grouping \
        '{"name": "ServiceName", "type": "Dimension"}' \
        '{"name": "team", "type": "TagKey"}' \
        '{"name": "cost-center", "type": "TagKey"}' \
    --dataset-filter '{
        "and": [
            {
                "dimensions": {
                    "name": "ServiceName",
                    "operator": "In",
                    "values": [
                        "Azure SQL Database",
                        "Azure Database for PostgreSQL",
                        "Azure Database for MySQL",
                        "Azure Cosmos DB"
                    ]
                }
            }
        ]
    }' \
    --output json > "${OUTPUT_DIR}/raw_costs.json"

# Transform raw cost data into chargeback format
python3 << 'PYTHON_SCRIPT'
import json
import csv
from datetime import datetime

with open('/tmp/chargeback-'"${REPORT_MONTH}"'/raw_costs.json') as f:
    data = json.load(f)

report_month = "${REPORT_MONTH}"
output_rows = []

for row in data.get('properties', {}).get('rows', []):
    cost = float(row[0]) if row[0] else 0.0
    service_name = row[1] if len(row) > 1 else 'Unknown'
    team = row[2] if len(row) > 2 else 'untagged'
    cost_center = row[3] if len(row) > 3 else 'CC-UNASSIGNED'

    if cost > 0:
        output_rows.append({
            'report_month': report_month,
            'cost_center': cost_center,
            'team': team,
            'service': service_name,
            'cost_usd': round(cost, 2),
            'currency': 'USD',
            'charge_type': 'chargeback',
            'invoice_reference': f"DB-CB-{report_month}-{cost_center}"
        })

output_path = f'/tmp/chargeback-{report_month}/chargeback_items.csv'
with open(output_path, 'w', newline='') as f:
    if output_rows:
        writer = csv.DictWriter(f, fieldnames=output_rows[0].keys())
        writer.writeheader()
        writer.writerows(output_rows)

Handling Disputed Allocations

Every chargeback model produces disputes. A team will question why their allocation jumped 40% in a month when they didn't change anything. The answer is almost always one of three things: another team reduced their consumption (shifting relative weights), a batch jobran outside its normal window, or a shared resource was resized and the base cost changed.

Build a dispute resolution process into the model from the start. The following query produces the audit trail that resolves 90% of disputes without escalation:

-- PostgreSQL: Month-over-month allocation change audit
-- Identifies what drove allocation shifts for a specific team
-- Run on-demand when a team disputes their chargeback

WITH monthly_stats AS (
    SELECT
        DATE_TRUNC('month', query_date) AS billing_month,
        team,
        SUM(exec_time_ms) AS total_exec_ms,
        SUM(io_score) AS total_io_score,
        SUM(query_count) AS total_queries,
        SUM(rows_returned) AS total_rows
    FROM finops_consumption_log  -- populated by the monthly metering job
    WHERE team = :'disputed_team'  -- pass via psql -v disputed_team='analytics'
      AND query_date >= NOW() - INTERVAL '3 months'
    GROUP BY DATE_TRUNC('month', query_date), team
),
platform_totals AS (
    SELECT
        DATE_TRUNC('month', query_date) AS billing_month,
        SUM(exec_time_ms) AS platform_total_exec_ms,
        SUM(io_score) AS platform_total_io_score
    FROM finops_consumption_log
    WHERE query_date >= NOW() - INTERVAL '3 months'
    GROUP BY DATE_TRUNC('month', query_date)
),
allocation_history AS (
    SELECT
        ms.billing_month,
        ms.team,
        ms.total_exec_ms,
        ms.total_io_score,
        ms.total_queries,
        pt.platform_total_exec_ms,
        pt.platform_total_io_score,
        ROUND((ms.total_exec_ms::numeric / NULLIF(pt.platform_total_exec_ms, 0)) * 100, 2)
            AS cpu_share_pct,
        ROUND((ms.total_io_score::numeric / NULLIF(pt.platform_total_io_score, 0)) * 100, 2)
            AS io_share_pct,
        -- Month-over-month query volume change
        ROUND(
            (ms.total_queries - LAG(ms.total_queries) OVER (ORDER BY ms.billing_month))::numeric
            / NULLIF(LAG(ms.total_queries) OVER (ORDER BY ms.billing_month), 0) * 100,
            2
        ) AS query_volume_change_pct,
        -- Month-over-month platform total change (explains denominator shifts)
        ROUND(
            (pt.platform_total_exec_ms - LAG(pt.platform_total_exec_ms) OVER (ORDER BY ms.billing_month))::numeric
            / NULLIF(LAG(pt.platform_total_exec_ms) OVER (ORDER BY ms.billing_month), 0) * 100,
            2
        ) AS platform_total_change_pct
    FROM monthly_stats ms
    JOIN platform_totals pt USING (billing_month)
)
SELECT
    billing_month,
    team,
    total_queries,
    query_volume_change_pct AS my_query_change_pct,
    cpu_share_pct AS my_cpu_share,
    io_share_pct AS my_io_share,
    platform_total_change_pct AS platform_volume_change_pct,
    CASE
        WHEN query_volume_change_pct > 20 THEN 'Your query volume increased significantly'
        WHEN platform_total_change_pct < -15 THEN 'Other teams reduced usage — your share increased'
        WHEN platform_total_change_pct > 20 THEN 'Platform grew — your share decreased'
        WHEN query_volume_change_pct BETWEEN -5 AND 5
             AND ABS(platform_total_change_pct) > 15
            THEN 'Your usage was stable; allocation shift driven by other teams'
        ELSE 'Review raw consumption logs for this period'
    END AS dispute_explanation
FROM allocation_history
ORDER BY billing_month;

This query output goes directly into the dispute resolution email. In most cases, the explanation column settles the discussion without a meeting.

Governance, Policy Enforcement, and the FinOps Feedback Loop

Cost allocation without governance is reporting. Cost allocation with governance is cost reduction. The governance layer converts showback and chargeback data into actionable policy — team-level budgets with automated alerts, anomaly detection that fires before the end of the month, and escalation paths that involve the right people without creating noise.

The FinOps Feedback Loop

The feedback loop is the mechanism that converts cost visibility into cost reduction. It has four steps that repeat monthly:

1. Report: Showback or chargeback report lands in team leads' inboxes on the 2nd of each month, covering the prior month.

2. Review: Teams identify their top three cost drivers. The FinOps dashboard — covered in Chapter 25 — surfaces idle resources, oversized instances, and storage waste automatically.

3. Optimize: Teams take action during the current month. Rightsizing, turning off non-prod overnight, removing orphaned snapshots.

4. Verify: The following month's report confirms the savings. The reduction appears in the team's allocation. The feedback is concrete and fast.

flowchart LR
    A[1. Report] --> B[2. Review]
    B --> C[3. Optimize]
    C --> D[4. Verify]
    D --> A

*The FinOps feedback loop repeats monthly — each cycle's Verify step confirms the prior cycle's Optimize actions actually reduced the following month's allocation.*

The loop only works if the report arrives consistently and the data is trustworthy. Inconsistent or inaccurate reports destroy credibility faster than any technical failure. Automate the report generation completely. Never send a manually assembled spreadsheet. When a team disputes a number, you need to be able to show the exact query that produced it.

Anomaly Detection for Chargeback Fairness

One of the most common chargeback complaints is that a cost spike caused by an infrastructure event — a Multi-AZ failover, an unplanned snapshot, a data transfer charge from a misconfigured endpoint — lands on a team that didn't cause it. Anomaly detection, automated against the daily cost stream, catches these events and flags them for exclusion or manual review before the monthly report closes.

#!/usr/bin/env python3
"""
Database cost anomaly detector for chargeback fairness review.
Runs daily via EventBridge. Flags cost spikes that may represent
infrastructure events rather than application team consumption.
Outputs to S3 and sends Slack alert for human review.
"""

import boto3
import json
import os
from datetime import datetime, timedelta
from typing import List, Dict, Any

def get_daily_costs_by_team(days_back: int = 30) -> List[Dict[str, Any]]:
    """Pull daily RDS costs by team tag for anomaly baseline."""
    client = boto3.client('ce', region_name='us-east-1')

    end_date = datetime.today().strftime('%Y-%m-%d')
    start_date = (datetime.today() - timedelta(days=days_back)).strftime('%Y-%m-%d')

    response = client.get_cost_and_usage(
        TimePeriod={'Start': start_date, 'End': end_date},
        Granularity='DAILY',
        Filter={
            'Dimensions': {
                'Key': 'SERVICE',
                'Values': [
                    'Amazon Relational Database Service',
                    'Amazon Aurora'
                ]
            }
        },
        GroupBy=[
            {'Type': 'TAG', 'Key': 'Team'},
            {'Type': 'DIMENSION', 'Key': 'USAGE_TYPE'}
        ],
        Metrics=['UnblendedCost']
    )

    daily_records = []
    for result in response['ResultsByTime']:
        date = result['TimePeriod']['Start']
        for group in result['Groups']:
            team = group['Keys'][0].replace('Team$', '') or 'untagged'
            usage_type = group['Keys'][1]
            cost = float(group['Metrics']['UnblendedCost']['Amount'])
            if cost > 0:
                daily_records.append({
                    'date': date,
                    'team': team,
                    'usage_type': usage_type,
                    'cost': cost
                })

    return daily_records


def detect_anomalies(
    records: List[Dict[str, Any]],
    std_dev_threshold: float = 2.5
) -> List[Dict[str, Any]]:
    """
    Flag daily costs that exceed mean + N standard deviations.
    Uses a 30-day rolling window as the baseline.
    Excludes the most recent day (the day being evaluated).
    """
    from collections import defaultdict
    import statistics

    # Group by team + usage_type
    grouped = defaultdict(list)
    for record in records:
        key = (record['team'], record['usage_type'])
        grouped[key].append((record['date'], record['cost']))

    anomalies = []
    today = datetime.today().strftime('%Y-%m-%d')
    yesterday = (datetime.today() - timedelta(days=1)).strftime('%Y-%m-%d')

    for (team, usage_type), daily_costs in grouped.items():
        # Baseline: all days except yesterday (the evaluation target)
        baseline_costs = [c for d, c in daily_costs if d != yesterday]
        yesterday_cost = next((c for d, c in daily_costs if d == yesterday), None)

        if yesterday_cost is None or len(baseline_costs) < 7:
            continue  # Need at least a week of baseline

        mean_cost = statistics.mean(baseline_costs)
        if len(baseline_costs) < 2:
            continue

        std_cost = statistics.stdev(baseline_costs)
        if std_cost == 0:
            continue

        z_score = (yesterday_cost - mean_cost) / std_cost

        if z_score > std_dev_threshold:
            pct_above_mean = ((yesterday_cost - mean_cost) / mean_cost) * 100
            anomalies.append({
                'date': yesterday,
                'team': team,
                'usage_type': usage_type,
                'yesterday_cost': round(yesterday_cost, 4),
                'baseline_mean': round(mean_cost, 4),
                'z_score': round(z_score, 2),
                'pct_above_mean': round(pct_above_mean, 1),
                'baseline_days': len(baseline_costs),
                'review_action': (
                    'EXCLUDE_FROM_CHARGEBACK' if pct_above_mean > 300
                    else 'FLAG_FOR_REVIEW'
                )
            })

    return sorted(anomalies, key=lambda x: x['z_score'], reverse=True)


def post_to_slack(anomalies: List[Dict[str, Any]], webhook_url: str):
    """Post anomaly summary to Slack FinOps channel."""
    import urllib.request
    import urllib.parse

    if not anomalies:
        return

    blocks = [
        {
            "type": "header",
            "text": {
                "type": "plain_text",
                "text": f":rotating_light: Database Cost Anomalies Detected — {datetime.today().strftime('%Y-%m-%d')}"
            }
        },
        {
            "type": "section",
            "text": {
                "type": "mrkdwn",
                "text": f"*{len(anomalies)} anomalies* found in yesterday's database costs. "
                        f"Review before monthly chargeback closes."
            }
        }
    ]

    for a in anomalies[:5]:  # Top 5 only in Slack
        action_emoji = ":x:" if a['review_action'] == 'EXCLUDE_FROM_CHARGEBACK' else ":eyes:"
        blocks.append({
            "type": "section",
            "text": {
                "type": "mrkdwn",
                "text": (
                    f"{action_emoji} *{a['team']}* | `{a['usage_type']}`\n"
                    f"Yesterday: *${a['yesterday_cost']:.2f}* vs avg ${a['baseline_mean']:.2f} "
                    f"(+{a['pct_above_mean']:.0f}%, z={a['z_score']:.1f})\n"
                    f"Action: `{a['review_action']}`"
                )
            }
        })

    payload = json.dumps({"blocks": blocks}).encode('utf-8')
    req = urllib.request.Request(
        webhook_url,
        data=payload,
        headers={'Content-Type': 'application/json'}
    )
    urllib.request.urlopen(req)


def lambda_handler(event, context):
    records = get_daily_costs_by_team(days_back=30)
    anomalies = detect_anomalies(records, std_dev_threshold=2.5)

    # Save to S3 for audit trail
    if anomalies:
        s3 = boto3.client('s3')
        bucket = os.environ.get('FINOPS_BUCKET', 'company-finops-reports')
        key = f"anomalies/{datetime.today().strftime('%Y/%m/%d')}/cost_anomalies.json"
        s3.put_object(
            Bucket=bucket,
            Key=key,
            Body=json.dumps(anomalies, indent=2).encode('utf-8'),
            ContentType='application/json'
        )

    # Slack notification
    webhook_url = os.environ.get('SLACK_WEBHOOK_URL')
    if webhook_url and anomalies:
        post_to_slack(anomalies, webhook_url)

    return {
        'statusCode': 200,
        'anomalies_detected': len(anomalies),
        'auto_exclude_count': sum(
            1 for a in anomalies if a['review_action'] == 'EXCLUDE_FROM_CHARGEBACK'
        )
    }


if __name__ == '__main__':
    result = lambda_handler({}, None)
    print(json.dumps(result, indent=2))

Any anomaly flagged as EXCLUDE_FROM_CHARGEBACK enters a human review queue. A FinOps engineer reviews it within 24 hours, confirms whether it represents an infrastructure event outside team control, and approves or rejects the exclusion. This process prevents chargeback from becoming politically toxic — the model needs to be seen as fair to survive long enough to produce savings.

Key Takeaways

  • → **Showback and chargeback require identical technical infrastructure** — the only difference is what happens to the report after it is generated. Build for chargeback from day one, even if you launch with showback, because retrofitting financial system integration after the model is running is expensive and disruptive.
  • → **Tag coverage below 90% makes allocation models politically indefensible.** Run the tag coverage audit on a weekly schedule, alert on violations, and enforce tagging policy through preventive controls — AWS Config rules, Azure Policy, GCP Organization Policy — rather than reactive audits.
  • → **Shared resource allocation requires consumption metering, not just tag splitting.** Use `pg_stat_statements` on PostgreSQL and `sys.dm_exec_query_stats` on Azure SQL to generate blended CPU and I/O weights that reflect actual usage rather than arbitrary proportions.
  • → **Dispute resolution is a first-class requirement, not an afterthought.** Store monthly consumption snapshots in a `finops_consumption_log` table, build the audit trail query before the first dispute arrives, and document the methodology clearly so teams understand what they are being charged for and why.
  • → **Anomaly detection protects chargeback credibility.** A cost spike caused by a Multi-AZ failover or a misconfigured endpoint should not land on a team's monthly invoice without review. Run the anomaly detector daily, auto-flag spikes above three standard deviations, and maintain a human review queue that closes before month-end reporting.
