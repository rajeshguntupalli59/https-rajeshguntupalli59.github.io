Chapter 39: Right-Sizing Cloud Database Instances

Cloud billing has a way of focusing the mind. On-premises, a server purchased three years ago costs the same whether it runs at 8% CPU or 95%. In the cloud, every vCPU-hour, every gigabyte of provisioned IOPS, and every GB of storage is metered continuously. Right-sizing — selecting the correct instance class, storage configuration, and compute tier for each workload — is therefore not an optimization exercise you do once during migration. It is an ongoing engineering discipline that directly affects both application performance and monthly spend. This chapter covers the mechanics of right-sizing across AWS RDS and Aurora, Azure SQL Database, and Google Cloud SQL and AlloyDB: how to read the signals that indicate a mismatch between workload and instance, how to resize with minimal disruption, and how to build the automation that keeps sizing decisions current as workloads evolve.

---

39.1 Understanding the Cloud Instance Taxonomy

Before you can right-size anything, you need a working mental model of how cloud providers organize their compute offerings. Every managed database service presents a hierarchy: a general-purpose tier, a memory-optimized tier, and — on some platforms — a burstable tier that has no on-premises equivalent at all.

AWS RDS instance families follow the EC2 naming convention. db.t3.medium and db.t4g.medium are burstable instances that accumulate CPU credits when idle and burn them during bursts. db.m7g and db.m6i are the general-purpose workhorses. db.r7g, db.r6i, and db.x2idn are memory-optimized, relevant when your buffer pool needs to hold more than 32 GB in RAM. Aurora uses the same families but the underlying hardware is shared; Aurora Serverless v2 adds a fractional ACU model that sits orthogonally to the instance class hierarchy.

Azure SQL Database abstracts this differently. In the General Purpose service tier, you choose vCores (2 through 128) and the memory scales with them at a fixed ratio (approximately 5.1 GB per vCore in Gen5). The Business Critical tier uses local SSD and adds a readable secondary replica at no extra compute cost. Hyperscale decouples storage from compute entirely and adds independent read replicas called named replicas. The DTU model — which you will encounter on older provisioned databases — bundles compute, memory, and I/O into a single opaque unit; avoid it for new workloads because it gives you no visibility into which resource is actually the constraint.

Google Cloud SQL uses machine types derived from Compute Engine: shared-core for development (db-f1-micro, db-g1-small), standard (db-n1-standard-*), and high-memory (db-n1-highmem-*). AlloyDB uses a separate tier system anchored to vCPUs, with columnar memory and a distributed cache that changes the RAM sizing calculus significantly compared to vanilla Cloud SQL.

The mapping that helps on-premises DBAs most: think of memory-to-vCPU ratio, not raw core count. A db.r6i.2xlarge gives you 8 vCPUs and 64 GB RAM (8:1). A db.m6i.2xlarge gives you 8 vCPUs and 32 GB RAM (4:1). If your workload is read-heavy and buffer-pool-bound, the r6i is the right family even if it costs more per vCore. If your workload is CPU-bound — complex reporting queries, high connection rates, stored procedure execution — the m6i is more efficient.

Burstable instances deserve special attention. db.t3.medium (2 vCPU, 4 GB RAM) looks attractive for small workloads, and it often is appropriate for development and small OLTP databases. The risk is CPU credit exhaustion. When credits run out, performance drops to the CPU baseline, which for db.t3.medium is 20% of a single vCPU. On-premises you never had a server that suddenly ran at one-fifth its rated speed for sustained periods because the accounting department decided the bill was too high. In the cloud, this happens silently if you do not monitor credit balance.

-- Query to estimate buffer pool hit ratio on PostgreSQL (RDS or Cloud SQL)
-- A ratio below 0.98 on a read-heavy OLTP workload suggests the instance
-- needs more RAM, not necessarily more CPU.
SELECT
    sum(heap_blks_hit)  AS heap_hit,
    sum(heap_blks_read) AS heap_read,
    round(
        sum(heap_blks_hit)::numeric /
        nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0),
        4
    ) AS hit_ratio
FROM pg_statio_user_tables;

On a well-sized instance running a warm OLTP workload, this ratio should be 0.985 or higher. Values below 0.95 indicate the working set is larger than the buffer pool, and the correct response is a memory upgrade before anything else.

39.2 Identifying Sizing Mismatches from Cloud Metrics

Right-sizing begins with observation, and cloud monitoring platforms expose far more granular data than most on-premises monitoring setups. The challenge is knowing which metrics to read and what thresholds actually indicate a problem versus normal variation.

On AWS, CloudWatch provides the primary signal set for RDS. The metrics that matter most for sizing decisions are:

  • → `CPUUtilization` — obvious, but interpret it in the context of the instance class. 70% CPU on a `db.r6i.8xlarge` is different from 70% on a `db.t3.medium`.
  • → `FreeableMemory` — the absolute free RAM plus cache/buffers that can be reclaimed. If this drops below 10–15% of total instance RAM consistently during business hours, you are working the buffer pool hard.
  • → `ReadIOPS` / `WriteIOPS` — compare against your provisioned IOPS. If you are consistently at 90%+ of provisioned IOPS, you either need more IOPS or a faster storage type.
  • → `DatabaseConnections` — watch for this approaching the `max_connections` limit. On RDS PostgreSQL, `max_connections` defaults to a formula based on RAM (`LEAST({DBInstanceClassMemory/9531392}, 5000)`), which works out to roughly 3,600 connections on a `db.r6i.xlarge` (32 GiB of `DBInstanceClassMemory` divided by 9,531,392 bytes). Once you approach 80% of that number with real connections, connection pressure becomes a latency multiplier.
  • → `CPUCreditBalance` (burstable only) — if this trends toward zero during business hours, you have chronic CPU credit exhaustion, and the correct fix is moving to a non-burstable instance.
    • # Retrieve RDS CPUUtilization average over the last 7 days using AWS CLI
# Useful for periodic right-sizing reviews in a weekly cron or CI pipeline

aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name CPUUtilization \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-01 \
  --start-time $(date -u -d '7 days ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 3600 \
  --statistics Average Maximum \
  --output table

# Also pull FreeableMemory to pair with CPU
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name FreeableMemory \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-01 \
  --start-time $(date -u -d '7 days ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 3600 \
  --statistics Minimum \
  --output table

    On Azure SQL, the equivalent layer is Azure Monitor with Query Performance Insight built on top of Query Store. The metrics that drive sizing decisions are:

  • → `cpu_percent` — percentage of DTUs or vCores consumed. Sustained values above 80% warrant investigation.
  • → `physical_data_read_percent` — I/O consumption relative to the tier limit.
  • → `log_write_percent` — transaction log throughput as a percentage of tier limit; this is the metric most commonly missed by DBAs moving from on-premises, where log throughput limits were rarely a concern.
  • → `workers_percent` — percentage of the maximum worker thread count consumed. If this approaches 100%, connections will queue even if CPU is idle.

    • On Google Cloud SQL, Cloud Monitoring exposes metrics under the cloudsql.googleapis.com namespace. Particularly useful for right-sizing:

  • → `database/cpu/utilization` — normalized 0–1.
  • → `database/memory/utilization` — includes buffer cache in the denominator.
  • → `database/disk/read_ops_count` and `database/disk/write_ops_count` — raw I/O operations, not normalized to a tier limit.

    • For AlloyDB, the columnar memory pool (the HTAP layer) has its own memory allocation separate from PostgreSQL's shared_buffers. You need to monitor both database/memory/components to understand whether columnar memory pressure is evicting PostgreSQL buffer pool pages.

    AWS Compute Optimizer is worth enabling even if you are skeptical of automated recommendations. It ingests 14 days of CloudWatch metrics and produces a recommendation per instance that categorizes the current state as Under-provisioned, Over-provisioned, or Optimized, along with the projected cost and performance impact of moving to the recommended instance. These recommendations are not always correct — they cannot know about once-monthly batch jobs that do not appear in the 14-day window — but they are a useful starting point that on-premises DBAs would have had to build manually.

    39.3 Vertical Scaling: Resizing the Instance

    When you have identified a mismatch — too little CPU, too little RAM, or wrong storage — the corrective action on a managed database is usually a vertical resize. This is simpler than on-premises (no hardware procurement, no OS reinstall) but it is not zero-impact. Understanding the downtime windows and how to minimize them is the operational skill.

    RDS instance class changes require a brief outage. AWS performs the change by stopping the instance, modifying it, and restarting it. The typical duration is 3–10 minutes, though the official documentation declines to commit to specific numbers because workload state (dirty buffer pool pages to flush, active transactions to drain) affects the actual time. If you apply the change immediately during a maintenance window, that window is the impact boundary. If you apply it via modify-db-instance with --apply-immediately, it happens at the next low-activity moment that AWS determines — which in practice means during your next call to modify-db-instance for any reason, which is easy to forget.

    # Resize an RDS PostgreSQL instance to db.r6i.2xlarge
# --no-apply-immediately means the change waits for the next maintenance window
# Remove that flag (or use --apply-immediately) to resize at the next opportunity

aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --db-instance-class db.r6i.2xlarge \
  --no-apply-immediately \
  --region us-east-1

# Verify the pending modification
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].PendingModifiedValues' \
  --output json

    For Aurora, the vertical resize story is better. In Aurora Serverless v2, scaling is continuous and can happen without a restart: the instance scales from the minimum ACU to the maximum ACU as load increases, in increments as small as 0.5 ACUs. One Aurora Capacity Unit is approximately 2 GB of RAM and a proportional share of CPU. A minimum of 0.5 ACUs with a maximum of 128 ACUs covers the range from a tiny dev database to a 256 GB RAM instance. The catch: Aurora Serverless v2 does not scale to zero (unlike v1), and the minimum of 0.5 ACUs means you are paying for that perpetually — check the current per-ACU-hour rate for your region before budgeting, since it is a meaningful recurring floor cost even for an idle cluster.

    For provisioned Aurora instances, the resize still requires a brief restart, but if you have Aurora read replicas, you can resize the replicas first, promote one to primary via a failover, resize the old primary (now a replica), and keep application downtime to the 15–30 seconds of the failover operation rather than the full instance restart time.

    Azure SQL vertical scaling is the smoothest across all three platforms because it is a service operation rather than a VM resize. Changing vCores in the General Purpose tier takes roughly 5–10 seconds for in-memory state transfer; the connection is briefly interrupted. Changing service tiers (e.g., General Purpose to Business Critical) takes longer — 10–30 minutes — because the underlying storage layer changes.

    # Scale an Azure SQL Database from GP_Gen5_4 to GP_Gen5_8 (vCores)
az sql db update \
  --resource-group prod-rg \
  --server prod-sqlserver \
  --name prod-database \
  --service-objective GP_Gen5_8 \
  --no-wait

# Monitor the scaling operation
az sql db show \
  --resource-group prod-rg \
  --server prod-sqlserver \
  --name prod-database \
  --query '{status: status, serviceLevelObjective: currentServiceObjectiveName}' \
  --output json

    Google Cloud SQL instance tier changes require the instance to restart. For standard instances (non-HA), this is a brief outage. For HA instances (primary + standby), Cloud SQL performs a failover to the standby, resizes the old primary, then fails back — similar to the Aurora replica promotion pattern but managed transparently. The total time is typically 2–5 minutes.

    Terraform management of instance sizing deserves attention because many production environments manage infrastructure as code, and a size change that happens outside Terraform will create drift. The pattern is to encode the instance class in a variable and use a terraform plan + terraform apply workflow for all resizes:

    # terraform/rds/variables.tf
variable "db_instance_class" {
  description = "RDS instance class — change this variable to trigger a resize"
  type        = string
  default     = "db.r6i.xlarge"
}

variable "apply_immediately" {
  description = "Apply instance changes immediately vs next maintenance window"
  type        = bool
  default     = false
}

# terraform/rds/main.tf
resource "aws_db_instance" "prod_postgres" {
  identifier              = "prod-postgres-01"
  engine                  = "postgres"
  engine_version          = "15.4"
  instance_class          = var.db_instance_class
  allocated_storage       = 500
  max_allocated_storage   = 2000
  storage_type            = "gp3"
  iops                    = 6000
  apply_immediately       = var.apply_immediately
  maintenance_window      = "Sun:03:00-Sun:04:00"
  backup_window           = "01:00-02:00"
  backup_retention_period = 7

  # Prevent accidental deletion in production
  deletion_protection = true

  tags = {
    Environment    = "production"
    CostCenter     = "engineering"
    LastResizeDate = "2024-11"
  }
}

    Tagging instances with the last resize date is a low-tech but effective practice. When you pull cost reports and see a large instance that has not been reviewed in 18 months, the tag tells you whether the sizing decision was intentional or inherited.

    39.4 Storage Right-Sizing: IOPS, Throughput, and Autoscaling

    Storage is frequently the second-largest cost item on a cloud database bill, and it is the area where DBAs most commonly over-provision because the on-premises intuition (provision for peak, never run out) collides with cloud storage pricing that charges for provisioned capacity and IOPS regardless of usage.

    AWS RDS storage types:

  • → `gp2` — general-purpose SSD. IOPS scale with volume size: 3 IOPS per GB, minimum 100, maximum 16,000. If you provision 500 GB of gp2 storage, you get exactly 1,500 IOPS. This coupling of size to IOPS was the dominant reason teams over-provisioned storage.
  • → `gp3` — the 2022 successor to gp2. IOPS and throughput are independently configurable. The baseline is 3,000 IOPS and 125 MB/s included in the storage price. You can provision up to 16,000 IOPS and 1,000 MB/s separately. For most workloads, gp3 is cheaper than gp2 and gives you more control. Migrate existing gp2 instances to gp3 unless you have a specific reason not to.
  • → `io1` / `io2` — provisioned IOPS SSD. Use these when you need more than 16,000 IOPS or when sub-millisecond storage latency consistency is a hard requirement (financial systems, high-frequency OLTP). io2 Block Express supports up to 256,000 IOPS per volume at multi-attach.

    • The specific gotcha: RDS storage can only be increased, never decreased. If you provision 2 TB and decide 500 GB was sufficient, you are paying for 2 TB until you rebuild the instance. This is fundamentally different from on-premises SANs where you could reclaim LUNs. Provision conservatively and rely on Storage Autoscaling:

    # Enable storage autoscaling on an existing RDS instance
# max-allocated-storage sets the ceiling; autoscaling triggers when free
# space drops below 10% of allocated storage (sustained for 5+ minutes),
# then grows storage by whichever is larger: 10 GB or 10% of current allocation

aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --max-allocated-storage 2000 \
  --apply-immediately

# Storage autoscaling does NOT require an instance restart —
# it is one of the few RDS modifications that is truly online

    Azure SQL storage in the General Purpose tier is provisioned in 1 GB increments from 1 GB to 4 TB, and can be increased online. Unlike RDS, Azure SQL does allow storage reduction on the General Purpose tier (with some restrictions). The Business Critical tier uses local SSD attached to the compute node, so storage limits are tied to the instance size rather than being independently configurable — a BC_Gen5_4 instance gets 1 TB of local SSD.

    Google Cloud SQL storage always starts at HDD or SSD. Use SSD for any production workload; HDD pricing is lower but the latency difference is significant. Cloud SQL supports storage autoresize by default (enabled via --storage-auto-increase or the console), and it grows storage automatically when free space drops below the configured threshold — check current GCP documentation for the exact increment calculation, since it is not a fixed flat amount. The equivalent caution applies: Cloud SQL storage cannot be decreased after it has been increased.

    IOPS sizing math for RDS gp3: Start with your observed peak IOPS from the source system. Add 20% headroom. Compare that to the 3,000 IOPS baseline included in gp3. If your peak is below 3,000 IOPS, gp3 at baseline is sufficient. If your peak is 8,000 IOPS, provision 10,000 IOPS on gp3. Pull the current per-provisioned-IOPS rate from AWS pricing before estimating the monthly cost — gp3's marginal IOPS rate is priced well below io1's per-IOPS rate, which combined with gp3's free 3,000-IOPS baseline and lower per-GB storage rate is what makes it the cheaper choice at equivalent IOPS; do not assume the two volume types charge the same rate per additional IOPS.

    # Python script to calculate gp3 IOPS cost vs io1 for a given workload
# Useful for building a right-sizing cost model during migration planning

import boto3
from datetime import datetime, timedelta

def estimate_storage_cost(
    storage_gb: int,
    peak_iops: int,
    peak_throughput_mbps: int,
    region: str = "us-east-1"
) -> dict:
    """
    Compare gp3 vs io1 costs for a given storage/IOPS requirement.
    IMPORTANT: the pricing constants below are placeholders only.
    Pull current rates from the AWS Price List API (see the RDS pricing
    function earlier in this chapter) or the AWS Pricing Calculator before
    using this for a real decision — do not ship these numbers to production
    budgeting. gp3's marginal per-IOPS rate is priced well below io1's;
    they are NOT the same rate, even though both are shown here as
    placeholders pending your own lookup.
    """

    # gp3 pricing — PLACEHOLDERS, replace with current rates for your region
    GP3_STORAGE_PER_GB   = None    # $/GB-month — fetch current rate
    GP3_IOPS_INCLUDED    = 3000
    GP3_IOPS_EXTRA       = None    # $/provisioned IOPS-month above 3000 — fetch current rate
    GP3_THROUGHPUT_INCL  = 125     # MB/s included
    GP3_THROUGHPUT_EXTRA = None    # $/MB/s-month above 125 — fetch current rate

    # io1 pricing — PLACEHOLDERS, replace with current rates for your region
    IO1_STORAGE_PER_GB   = None    # $/GB-month — fetch current rate
    IO1_IOPS_PER_MONTH   = None    # $/provisioned IOPS-month — fetch current rate

    if None in (GP3_STORAGE_PER_GB, GP3_IOPS_EXTRA, GP3_THROUGHPUT_EXTRA,
                IO1_STORAGE_PER_GB, IO1_IOPS_PER_MONTH):
        raise ValueError(
            "Populate the pricing constants above with current AWS rates "
            "before running this comparison — see get_rds_ondemand_price() "
            "earlier in this chapter for the Price List API pattern."
        )

    # gp3 cost
    gp3_storage_cost = storage_gb * GP3_STORAGE_PER_GB
    gp3_extra_iops   = max(0, peak_iops - GP3_IOPS_INCLUDED)
    gp3_iops_cost    = gp3_extra_iops * GP3_IOPS_EXTRA
    gp3_extra_tput   = max(0, peak_throughput_mbps - GP3_THROUGHPUT_INCL)
    gp3_tput_cost    = gp3_extra_tput * GP3_THROUGHPUT_EXTRA
    gp3_total        = gp3_storage_cost + gp3_iops_cost + gp3_tput_cost

    # io1 cost
    io1_storage_cost = storage_gb * IO1_STORAGE_PER_GB
    io1_iops_cost    = peak_iops * IO1_IOPS_PER_MONTH
    io1_total        = io1_storage_cost + io1_iops_cost

    return {
        "gp3": {
            "storage": round(gp3_storage_cost, 2),
            "iops":    round(gp3_iops_cost, 2),
            "throughput": round(gp3_tput_cost, 2),
            "total":   round(gp3_total, 2),
        },
        "io1": {
            "storage": round(io1_storage_cost, 2),
            "iops":    round(io1_iops_cost, 2),
            "throughput": 0.0,
            "total":   round(io1_total, 2),
        },
        "recommendation": "gp3" if gp3_total < io1_total else "io1",
        "monthly_savings_with_gp3": round(io1_total - gp3_total, 2),
    }


if __name__ == "__main__":
    result = estimate_storage_cost(
        storage_gb=1000,
        peak_iops=8000,
        peak_throughput_mbps=300,
    )
    print(f"gp3 monthly total: ${result['gp3']['total']}")
    print(f"io1 monthly total: ${result['io1']['total']}")
    print(f"Recommendation: {result['recommendation']}")
    print(f"Monthly savings with gp3: ${result['monthly_savings_with_gp3']}")

    39.5 Horizontal Scaling Patterns and Read Replica Sizing

    Vertical scaling has a ceiling. Every cloud platform has a largest available instance class, and even before you reach it, the cost curve steepens sharply. When a single large instance cannot absorb the workload, horizontal scaling through read replicas is the standard answer for read-heavy workloads.

    The key principle that on-premises DBAs sometimes miss: read replicas in cloud managed databases are not just disaster recovery standbys. They are production traffic receivers. Aurora allows up to 15 read replicas per cluster. RDS PostgreSQL allows up to 5 read replicas per instance. Azure SQL Hyperscale allows up to 30 named replicas. Distributing read traffic across replicas reduces the primary's CPU and I/O burden in ways that vertical scaling cannot, because a single instance's CPU throughput is bounded even at 64 vCPUs, whereas four read replicas each running at 16 vCPUs give you a higher aggregate query throughput for read workloads.

    Sizing read replicas independently is one of the most under-utilized cloud features. On-premises, a standby server was typically identical to the primary because it might need to assume primary duties at any time. In the cloud, a read replica that will never be promoted can be a smaller, cheaper instance. An db.r6i.8xlarge primary (32 vCPUs, 256 GB RAM) does not necessarily need db.r6i.8xlarge replicas for reporting queries. If your reporting queries scan large tables but involve no writes, an db.r6i.4xlarge replica (16 vCPUs, 128 GB RAM) is often sufficient, at roughly half the compute cost.

    The constraint: the replica must be able to keep up with the primary's replication stream. If the primary is generating write-heavy traffic (large bulk loads, aggressive UPDATE workloads), a smaller replica may fall behind, and replication lag becomes an application concern. Monitor ReplicaLag in CloudWatch (for RDS) or replication_delay in pg_stat_replication to determine whether your replica sizing is adequate.

    -- On the primary: check replication lag for all connected standbys
-- Works on RDS PostgreSQL, Cloud SQL PostgreSQL, AlloyDB

SELECT
    application_name,
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    (sent_lsn - replay_lsn)        AS replication_lag_bytes,
    write_lag,
    flush_lag,
    replay_lag,
    sync_state
FROM pg_stat_replication
ORDER BY replication_lag_bytes DESC NULLS LAST;
    -- On SQL Server (Azure SQL): check secondary replica lag
-- Applies to Business Critical tier (readable secondaries) and
-- Always On Availability Groups in SQL Managed Instance

SELECT
    ar.replica_server_name,
    drs.database_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.last_commit_lsn,
    drs.last_hardened_lsn,
    -- Approximate lag in log blocks; convert to bytes or time via log_send_queue_size
    drs.log_send_queue_size       AS unsent_log_kb,
    drs.redo_queue_size           AS unredone_log_kb,
    drs.redo_rate                 AS redo_rate_kb_per_sec
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar
    ON drs.replica_id = ar.replica_id
WHERE drs.is_local = 0
ORDER BY drs.redo_queue_size DESC;

    Connection routing for read replicas is an application-layer concern that directly affects whether your correctly-sized replicas actually receive traffic. AWS provides a reader endpoint for Aurora clusters that load-balances across all available reader instances. RDS does not provide a managed reader endpoint for multi-AZ or read replica configurations — you need to route to the replica's endpoint explicitly, which means your connection pool (PgBouncer, RDS Proxy, application-level logic) must distinguish read-only connections from read-write connections.

    RDS Proxy can be an effective layer here. It maintains a pool of connections to both the primary and read replicas, and for Aurora it can direct read-only transactions to the reader endpoint automatically:

    # Terraform: RDS Proxy with separate read/write and read-only endpoints
resource "aws_db_proxy" "prod_proxy" {
  name                   = "prod-postgres-proxy"
  debug_logging          = false
  engine_family          = "POSTGRESQL"
  idle_client_timeout    = 1800
  require_tls            = true
  role_arn               = aws_iam_role.rds_proxy_role.arn
  vpc_security_group_ids = [aws_security_group.rds_proxy_sg.id]
  vpc_subnet_ids         = var.private_subnet_ids

  auth {
    auth_scheme = "SECRETS"
    description = "prod postgres credentials"
    iam_auth    = "REQUIRED"
    secret_arn  = aws_secretsmanager_secret.db_credentials.arn
  }

  tags = {
    Environment = "production"
  }
}

# Default endpoint routes to the writer
resource "aws_db_proxy_default_target_group" "prod_proxy_tg" {
  db_proxy_name = aws_db_proxy.prod_proxy.name

  connection_pool_config {
    connection_borrow_timeout    = 120
    max_connections_percent      = 100
    max_idle_connections_percent = 50
  }
}

resource "aws_db_proxy_target" "prod_proxy_target" {
  db_proxy_name          = aws_db_proxy.prod_proxy.name
  target_group_name      = aws_db_proxy_default_target_group.prod_proxy_tg.name
  db_cluster_identifier  = aws_rds_cluster.prod_aurora.id
}

# Separate read-only endpoint for reporting traffic
resource "aws_db_proxy_endpoint" "prod_proxy_readonly" {
  db_proxy_name          = aws_db_proxy.prod_proxy.name
  db_proxy_endpoint_name = "prod-postgres-proxy-ro"
  vpc_subnet_ids         = var.private_subnet_ids
  vpc_security_group_ids = [aws_security_group.rds_proxy_sg.id]
  target_role            = "READ_ONLY"
}

    AlloyDB read pool instances work differently from standard PostgreSQL replicas. AlloyDB separates the storage layer (a distributed log-structured store) from the compute nodes. Read pool nodes read from the shared storage directly rather than replaying WAL from the primary, which eliminates most of the replication lag that affects standard PostgreSQL read replicas under heavy write workloads. This makes it safer to route time-sensitive read traffic to AlloyDB read pool instances; the data is close to current by design rather than by sufficient replica capacity. You can also scale the read pool node count without restarting the primary, making AlloyDB's horizontal scaling particularly well-suited for workloads with variable read peaks.

    39.6 Automated Right-Sizing with Scheduled Scaling

    The limiting factor in most right-sizing programs is that the correct size changes over time. A database sized correctly in January may be over-provisioned in March when a batch job moves off-database, and under-provisioned in November during seasonal peak. Building automation that adjusts sizing on a schedule — or in response to metrics — addresses this without requiring manual intervention every quarter.

    Aurora Serverless v2 scheduled scaling is the most elegant solution when your workload has predictable daily patterns. You can define a schedule that increases the maximum ACU capacity ahead of a known peak and reduces it after:

    # Create an Aurora Serverless v2 scaling schedule using AWS CLI
# This raises the max capacity from 4 to 32 ACUs before business hours
# and reduces it again overnight

# Scale up before 8 AM UTC on weekdays
aws application-autoscaling put-scheduled-action \
  --service-namespace rds \
  --resource-id cluster:prod-aurora-serverless \
  --scalable-dimension rds:cluster:ReadReplicaCount \
  --scheduled-action-name weekday-scale-up \
  --schedule "cron(0 7 ? * MON-FRI *)" \
  --scalable-target-action MinCapacity=4,MaxCapacity=32

# Scale down after 8 PM UTC on weekdays
aws application-autoscaling put-scheduled-action \
  --service-namespace rds \
  --resource-id cluster:prod-aurora-serverless \
  --scalable-dimension rds:cluster:ReadReplicaCount \
  --scheduled-action-name weekday-scale-down \
  --schedule "cron(0 20 ? * MON-FRI *)" \
  --scalable-target-action MinCapacity=1,MaxCapacity=4

    Note that Aurora Serverless v2 scales compute ACUs automatically within the min/max bounds; the scheduled action adjusts the bounds themselves. During the day, the instance can scale from 4 to 32 ACUs as needed. At night, it can scale from 1 to 4. This approach limits the maximum billing exposure while keeping headroom available during peak.

    Azure SQL Elastic Jobs and Automation can be used to schedule tier changes, though tier changes in Azure SQL are more disruptive than Aurora ACU scaling. A more practical pattern on Azure is to use Elastic Pools when you have multiple databases on the same server with complementary load patterns. An Elastic Pool with a shared eDTU or vCore allocation distributes compute across databases without requiring you to right-size each database independently. A database that needs 16 vCores at 9 AM can borrow capacity from a database that only needs 4 vCores at that hour, provided the pool's total allocation covers the combined peak:

    # Create an Azure SQL Elastic Pool and add databases to it
az sql elastic-pool create \
  --resource-group prod-rg \
  --server prod-sqlserver \
  --name prod-elastic-pool \
  --edition GeneralPurpose \
  --capacity 16 \
  --family Gen5 \
  --min-capacity 0 \
  --max-capacity 16

# Add an existing database to the pool
az sql db update \
  --resource-group prod-rg \
  --server prod-sqlserver \
  --name reporting-db \
  --elastic-pool prod-elastic-pool

# Add a second database with different peak hours
az sql db update \
  --resource-group prod-rg \
  --server prod-sqlserver \
  --name operational-db \
  --elastic-pool prod-elastic-pool

    The prerequisite for Elastic Pools is that the databases share the same logical server. If you have databases on separate servers for isolation reasons, the pool option is not available without consolidating the servers first — a separate architectural decision.

    Metric-driven auto-scaling with Lambda is the most general solution, applicable across platforms and useful when workload patterns are not predictable enough to schedule in advance. The pattern is: a Lambda function runs on a CloudWatch Events schedule (every 15 minutes), reads the last 30 minutes of metrics, applies a sizing decision algorithm, and calls the modify API if the recommendation differs from the current instance class.

    # Lambda function: auto-right-size an RDS instance based on metric signals
# Deploy with an IAM role that allows cloudwatch:GetMetricStatistics
# and rds:ModifyDBInstance, rds:DescribeDBInstances

import boto3
import json
import os
from datetime import datetime, timedelta

rds    = boto3.client('rds')
cw     = boto3.client('cloudwatch')
sns    = boto3.client('sns')

INSTANCE_ID   = os.environ['DB_INSTANCE_ID']
SNS_TOPIC_ARN = os.environ['SNS_TOPIC_ARN']

# Ordered list of instance classes from smallest to largest
# Modify this list to match the families and sizes appropriate for your workload
INSTANCE_LADDER = [
    "db.r6i.xlarge",    # 4 vCPU,  32 GB
    "db.r6i.2xlarge",   # 8 vCPU,  64 GB
    "db.r6i.4xlarge",   # 16 vCPU, 128 GB
    "db.r6i.8xlarge",   # 32 vCPU, 256 GB
    "db.r6i.16xlarge",  # 64 vCPU, 512 GB
]

CPU_SCALE_UP_THRESHOLD   = 75.0   # % — scale up if avg CPU exceeds this
CPU_SCALE_DOWN_THRESHOLD = 25.0   # % — scale down candidate if avg CPU below this
MEM_SCALE_UP_THRESHOLD   = 0.10   # fraction free — scale up if below 10% free RAM


def get_metric_average(metric_name: str, stat: str, period_minutes: int = 30) -> float:
    end   = datetime.utcnow()
    start = end - timedelta(minutes=period_minutes)

    response = cw.get_metric_statistics(
        Namespace  = 'AWS/RDS',
        MetricName = metric_name,
        Dimensions = [{'Name': 'DBInstanceIdentifier', 'Value': INSTANCE_ID}],
        StartTime  = start,
        EndTime    = end,
        Period     = period_minutes * 60,
        Statistics = [stat],
    )
    datapoints = response.get('Datapoints', [])
    if not datapoints:
        return 0.0
    return datapoints[0].get(stat, 0.0)


def get_instance_class() -> str:
    resp = rds.describe_db_instances(DBInstanceIdentifier=INSTANCE_ID)
    inst = resp['DBInstances'][0]
    # If a modification is pending, return the pending class to avoid churn
    pending = inst.get('PendingModifiedValues', {}).get('DBInstanceClass')
    return pending if pending else inst['DBInstanceClass']


def get_instance_memory_gb(instance_class: str) -> float:
    """Approximate memory map for r6i family. Extend for other families."""
    memory_map = {
        "db.r6i.xlarge":   32,
        "db.r6i.2xlarge":  64,
        "db.r6i.4xlarge":  128,
        "db.r6i.8xlarge":  256,
        "db.r6i.16xlarge": 512,
    }
    return memory_map.get(instance_class, 64)


def lambda_handler(event, context):
    current_class = get_instance_class()
    current_index = INSTANCE_LADDER.index(current_class) \
        if current_class in INSTANCE_LADDER else None

    if current_index is None:
        print(f"Instance class {current_class} not in ladder; skipping.")
        return

    avg_cpu        = get_metric_average('CPUUtilization', 'Average')
    min_free_mem_b = get_metric_average('FreeableMemory',  'Minimum')
    total_mem_gb   = get_instance_memory_gb(current_class)
    free_mem_ratio = (min_free_mem_b / (1024**3)) / total_mem_gb if total_mem_gb else 1.0

    print(f"Current class: {current_class}")
    print(f"Avg CPU (30m): {avg_cpu:.1f}%  Free mem ratio: {free_mem_ratio:.3f}")

    target_class = current_class

    # Scale-up conditions
    if avg_cpu > CPU_SCALE_UP_THRESHOLD or free_mem_ratio < MEM_SCALE_UP_THRESHOLD:
        if current_index < len(INSTANCE_LADDER) - 1:
            target_class = INSTANCE_LADDER[current_index + 1]
            reason = (
                f"CPU {avg_cpu:.1f}% > {CPU_SCALE_UP_THRESHOLD}%"
                if avg_cpu > CPU_SCALE_UP_THRESHOLD
                else f"FreeMemRatio {free_mem_ratio:.3f} < {MEM_SCALE_UP_THRESHOLD}"
            )
        else:
            print("Already at maximum instance class in ladder.")
            return

    # Scale-down condition — only if CPU is low AND memory is comfortable
    elif (avg_cpu < CPU_SCALE_DOWN_THRESHOLD
          and free_mem_ratio > 0.40
          and current_index > 0):
        target_class = INSTANCE_LADDER[current_index - 1]
        reason = f"CPU {avg_cpu:.1f}% < {CPU_SCALE_DOWN_THRESHOLD}% and memory ample"

    if target_class == current_class:
        print("No resize needed.")
        return

    print(f"Recommending resize: {current_class} -> {target_class} ({reason})")

    # Notify before modifying — allows human review if SNS is wired to a Slack/PagerDuty
    sns.publish(
        TopicArn = SNS_TOPIC_ARN,
        Subject  = f"RDS Auto-Resize: {INSTANCE_ID}",
        Message  = json.dumps({
            "instance":      INSTANCE_ID,
            "from_class":    current_class,
            "to_class":      target_class,
            "reason":        reason,
            "avg_cpu_pct":   round(avg_cpu, 1),
            "free_mem_ratio": round(free_mem_ratio, 3),
            "timestamp":     datetime.utcnow().isoformat(),
        }, indent=2),
    )

    rds.modify_db_instance(
        DBInstanceIdentifier = INSTANCE_ID,
        DBInstanceClass      = target_class,
        ApplyImmediately     = False,   # Apply at next maintenance window
    )
    print(f"Modify request submitted. Change will apply at next maintenance window.")

    Two production safeguards this implementation intentionally includes: the resize is scheduled for the next maintenance window (ApplyImmediately=False), and an SNS notification fires before the API call. This gives your on-call engineer a chance to abort if the recommendation fires during an incident window where a restart would be catastrophic. If you want fully automatic immediate resizing, remove ApplyImmediately=False and add a maintenance window check — do not apply immediately outside the approved window.

    39.7 Cost Allocation and Showback Reports

    Right-sizing decisions need to be made by people who can see the cost impact clearly. If a development team has no visibility into what their oversized RDS instance costs, they have no incentive to right-size it. Cost allocation tags solve this structurally.

    Tagging strategy for databases should include at minimum:

  • → `Environment` (production, staging, development)
  • → `Team` or `CostCenter`
  • → `Application` or `Service`
  • → `LastResizedBy` and `LastResizeDate` (operational provenance)
  • → `SizingStatus` (right-sized, under-review, known-overprovisioned)

    • The SizingStatus tag is a convention you create, not something AWS, Azure, or GCP provides. Use it to mark instances that Compute Optimizer flags as over-provisioned but where you have a known reason for the current size (an upcoming load test, a quarterly batch job not visible in the 14-day metrics window). This prevents automated alerts from repeatedly nagging about a conscious decision.

    AWS Cost Explorer allows you to filter and group by tag. A monthly query that groups by Team and Application and filters to the RDS service gives each team their database bill. The API can drive automated reports:

    import boto3
from datetime import date
from dateutil.relativedelta import relativedelta

ce = boto3.client('ce', region_name='us-east-1')

def get_rds_cost_by_team(months_back: int = 1) -> list:
    end   = date.today().replace(day=1)
    start = end - relativedelta(months=months_back)

    response = ce.get_cost_and_usage(
        TimePeriod = {
            'Start': start.strftime('%Y-%m-%d'),
            'End':   end.strftime('%Y-%m-%d'),
        },
        Granularity = 'MONTHLY',
        Filter = {
            'And': [
                {'Dimensions': {'Key': 'SERVICE', 'Values': ['Amazon Relational Database Service']}},
                {'Dimensions': {'Key': 'USAGE_TYPE_GROUP', 'Values': ['RDS: Running Hours']}},
            ]
        },
        GroupBy = [
            {'Type': 'TAG', 'Key': 'Team'},
            {'Type': 'TAG', 'Key': 'Environment'},
        ],
        Metrics = ['UnblendedCost'],
    )

    results = []
    for period in response['ResultsByTime']:
        for group in period['Groups']:
            keys  = group['Keys']
            cost  = float(group['Metrics']['UnblendedCost']['Amount'])
            unit  = group['Metrics']['UnblendedCost']['Unit']
            team  = keys[0].replace('Team$', '') if keys else 'untagged'
            env   = keys[1].replace('Environment$', '') if len(keys) > 1 else 'unknown'
            results.append({
                'period': period['TimePeriod']['Start'],
                'team':   team,
                'env':    env,
                'cost':   round(cost, 2),
                'unit':   unit,
            })

    return sorted(results, key=lambda x: x['cost'], reverse=True)


if __name__ == '__main__':
    rows = get_rds_cost_by_team(months_back=3)
    print(f"{'Period':<12} {'Team':<20} {'Env':<12} {'Cost (USD)':>12}")
    print('-' * 60)
    for r in rows:
        print(f"{r['period']:<12} {r['team']:<20} {r['env']:<12} {r['cost']:>12.2f}")

    Running this monthly and distributing the output to engineering leads creates the accountability loop that drives right-sizing decisions without requiring a central FinOps team to police every instance.

    39.8 Right-Sizing During Migration Waves

    Migration projects are the natural moment to establish the right size for a database, but they are also the moment when over-provisioning is most likely to occur. The instinct is: if we are migrating a database from a 48-core on-premises server, we should land on something equivalent. This instinct is usually wrong for two reasons.

    First, on-premises servers ran at low average utilization. A 48-core server purchased to handle a projected peak that never arrived runs at 12% CPU on average. The equivalent cloud instance is not a 48-vCPU database; it is a 4–8 vCPU instance that handles 12% of a 48-core machine's capacity, which is comfortably within range for most OLTP workloads.

    Second, cloud storage I/O is different from on-premises SAN I/O. A workload that needed a 40,000 IOPS SAN because it ran on spinning disk (or on HDD with heavy caching) may need only 8,000 IOPS on cloud SSD because the lower latency reduces queue depths and the access pattern changes.

    The right-sizing process during a migration wave:

    1. Collect two weeks of on-premises metrics before migration. Peak CPU (not average), peak IOPS, peak throughput, buffer cache hit ratio, and active connection count at peak.

    2. Translate to cloud instance using the memory-first heuristic: choose a family based on the RAM needed to hold the working set (buffer pool + connection overhead + OS overhead), then verify the vCPU count is sufficient for the CPU workload.

    3. Start one tier smaller than the translation suggests. You can scale up in minutes; you cannot get the week of over-spending back.

    4. Load test on the cloud instance before cutover. Use pgbench, HammerDB, or a replay of captured query workload against the target instance.

    5. Validate for 72 hours post-cutover before declaring the size final. Real workloads differ from load tests; the first week's actual peak may reveal a bottleneck the load test did not surface.

    The following query helps you estimate buffer pool requirements on an existing PostgreSQL source instance before migrating:

    -- Estimate effective working set size on a PostgreSQL source instance
-- pg_buffercache requires the pg_buffercache extension (usually available)
-- Run on the source BEFORE migration to size the target buffer pool

CREATE EXTENSION IF NOT EXISTS pg_buffercache;

SELECT
    c.relname                          AS table_name,
    pg_size_pretty(
        count(*) * current_setting('block_size')::bigint
    )                                  AS cached_size,
    round(100.0 * count(*) /
        (SELECT count(*) FROM pg_buffercache WHERE relfilenode IS NOT NULL),
        2)                             AS pct_of_buffer_pool
FROM pg_buffercache bc
JOIN pg_class c ON bc.relfilenode = pg_relation_filenode(c.oid)
WHERE bc.relfilenode IS NOT NULL
GROUP BY c.relname
ORDER BY count(*) DESC
LIMIT 20;

    The total cached_size across all tables gives you the minimum RAM the buffer pool needs to hold the hot working set. Add 20–30% headroom for new pages, temporary sort memory, and OS file system cache, and you have a defensible RAM requirement for the target instance.

    For SQL Server workloads migrating to Azure SQL or SQL Managed Instance:

    -- Estimate SQL Server buffer pool working set before migration
-- Identifies the top consumers of buffer pool memory by database object

SELECT TOP 20
    OBJECT_NAME(p.object_id)           AS table_name,
    i.name                             AS index_name,
    COUNT_BIG(*)                       AS buffer_pages,
    COUNT_BIG(*) * 8 / 1024            AS cached_mb,
    ROUND(
        100.0 * COUNT_BIG(*) /
            (SELECT COUNT_BIG(*) FROM sys.dm_os_buffer_descriptors
             WHERE database_id = DB_ID()),
        2)                             AS pct_of_buffer_pool
FROM sys.dm_os_buffer_descriptors bd
JOIN sys.allocation_units au ON bd.allocation_unit_id = au.allocation_unit_id
JOIN sys.partitions p
    ON au.container_id = CASE
        WHEN au.type IN (1, 3) THEN p.hobt_id
        ELSE p.partition_id
       END
JOIN sys.indexes i
    ON p.object_id = i.object_id AND p.index_id = i.index_id
WHERE bd.database_id = DB_ID()
  AND bd.page_type IN ('DATA_PAGE', 'INDEX_PAGE')
GROUP BY p.object_id, i.name
ORDER BY buffer_pages DESC;

    These two queries — one for PostgreSQL, one for SQL Server — are among the most useful pre-migration tools you can run. The output from each quantifies the RAM requirement with direct evidence from production, which makes a sizing recommendation to management far more defensible than an estimate based on the source server's spec sheet.

    Key Takeaways

  • → **Memory drives family selection, CPU drives size within the family.** Use buffer pool hit ratio and FreeableMemory metrics to determine whether the primary bottleneck is RAM; reserve CPU-focused resizing for workloads that are demonstrably compute-bound rather than I/O or memory-bound.
  • → **Cloud storage cannot be shrunk after provisioning on RDS or Cloud SQL — provision conservatively and enable autoscaling.** Migrate existing RDS gp2 volumes to gp3 to decouple IOPS from storage size and reduce costs for most workloads that operate below the 16,000 IOPS gp3 maximum.
  • → **Read replicas are production traffic receivers, not just HA standbys.** Right-size replicas independently of the primary based on the query patterns they serve; monitor replication lag to confirm that a smaller replica can keep pace with the primary's write stream.
  • → **Automate the right-sizing feedback loop.** A Lambda function or scheduled job that compares CloudWatch metrics against thresholds, proposes a resize via SNS, and submits the modify API call for the next maintenance window costs almost nothing to build and prevents the drift that occurs when sizing decisions are made once and never revisited.
  • → **Migration is the best opportunity to correct on-premises over-provisioning.** Collect two weeks of source metrics, apply the memory-first sizing heuristic, start one tier smaller than the direct translation suggests, and validate under real traffic before declaring the target instance size final.
