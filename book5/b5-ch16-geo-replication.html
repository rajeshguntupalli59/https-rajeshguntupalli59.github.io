Chapter 16: Active Geo-Replication and Failover Groups

Geographic replication in cloud databases is the production answer to a question on-prem DBAs have wrestled with for decades: how do you keep a copy of your data synchronized across data centers without building your own log shipping infrastructure, managing your own replication slots, or manually promoting standby servers at 2 AM? This chapter covers how AWS Aurora Global Database, Azure SQL Active Geo-Replication and Failover Groups, and Google Cloud Spanner multi-region configurations solve this problem — and where each approach has sharp edges you need to understand before you commit to them in production. We cover configuration, latency expectations, failover mechanics, RPO/RTO characteristics, and the automation patterns that separate a well-architected geo-redundant deployment from one that fails its first real disaster recovery test.

---

16.1 The Geography Problem: What You're Actually Solving

Before touching any configuration, get the requirements straight. Geo-replication serves three distinct purposes that are often conflated:

Disaster recovery — a full regional outage requires a replica in another region to take over. RPO of seconds to low minutes is achievable. RTO depends heavily on whether failover is automatic or manual.

Read scaling — routing read traffic to replicas closer to users in other regions reduces latency without touching the primary. A user in Tokyo reading from a US-East primary adds 150–200ms of round-trip latency that disappears when queries route to an Asia-Pacific replica.

Compliance and data residency — some regulated industries require data to exist within specific geographic boundaries, but still need disaster recovery within that boundary. These are not the same as global replication and sometimes conflict with it.

On-prem, you would have built this with SQL Server's Always On availability groups across stretched clusters, or PostgreSQL streaming replication with custom failover scripts on top of Pacemaker/Corosync. The managed cloud equivalent is less flexible in some ways — you cannot, for instance, tune the replication protocol itself — but it removes an enormous amount of operational surface area.

Replication Lag Is Inherent and Physical

The speed of light is not a cloud vendor problem. At the physical limit, New York to London is roughly 70ms round-trip. Synchronous replication across that distance would add 70ms minimum to every committed write. Every cloud vendor therefore makes the same decision: cross-region replication is asynchronous. This means RPO is not zero. Measure it. Know your actual lag before a disaster occurs.

Typical lag numbers in production:

| Scenario | Expected Replication Lag |

|---|---|

| Aurora Global, same continent | 1–3 seconds typical, <5s P99 |

| Aurora Global, US to EU | 3–8 seconds typical, <10s P99 |

| Azure SQL Active Geo-Replication, paired regions | 2–5 seconds typical |

| Azure SQL Active Geo-Replication, unpaired regions | 5–15 seconds depending on write volume |

| Cloud Spanner multi-region | Sub-second within a continent configuration |

| Spanner global multi-region | 5–10 seconds external consistency latency |

These numbers change dramatically under write load. A database doing 50,000 writes per second with 8KB average row size is generating roughly 400MB/s of WAL. Moving that across a WAN link takes real bandwidth, and replication lag expands if the link cannot sustain throughput. Size your workload against these numbers, not just the idle case.

The general shape of a managed failover is the same across Aurora Global Database, Azure SQL Failover Groups, and Cloud Spanner, even though the underlying replication mechanism differs: applications connect through a stable endpoint, the primary replicates asynchronously (or, for Spanner, via synchronous quorum) to one or more secondary regions, and a failover event promotes a secondary while the endpoint layer redirects traffic.

sequenceDiagram
    participant App as Application
    participant EP as Stable Endpoint (DNS / Listener)
    participant Pri as Primary Region DB
    participant Sec as Secondary Region DB

    App->>EP: Connect via fixed endpoint
    EP->>Pri: Route to current primary
    loop Continuous replication
        Pri->>Sec: Async (or quorum) replication
        Note over Pri,Sec: Lag monitored via heartbeat + vendor metric
    end
    Note over Pri: Region outage or planned failover triggered
    Sec->>Sec: Promote to read-write primary
    EP->>Sec: Redirect routing to new primary
    App->>Sec: Resume reads/writes via same endpoint

*Generic failover topology shared across Aurora Global Database, Azure Failover Groups, and Spanner — the promotion and endpoint-redirection mechanics differ in detail per vendor, covered in the sections that follow.*

16.2 Aurora Global Database: Architecture and Configuration

Aurora Global Database uses a storage-level replication mechanism rather than logical replication. The primary region writes to Aurora's distributed storage, and those writes are replicated asynchronously at the storage layer to secondary regions. This is architecturally different from PostgreSQL streaming replication, where the primary WAL sender streams WAL records to a standby's WAL receiver. Aurora Global bypasses the Aurora writer instance in secondary regions entirely — secondary regions have their own Aurora cluster, but that cluster's storage receives writes directly from the primary's storage nodes.

The practical implications:

  • → Secondary clusters are read-only at the SQL layer
  • → You cannot use logical replication slots on a secondary cluster
  • → Secondary clusters can have their own read replicas within the secondary region
  • → Each secondary region introduces one hop of latency: primary writes to storage, storage replicates to secondary region storage, secondary cluster reads from its regional storage

    • Setting Up Aurora Global Database with AWS CLI

    First, create the primary Aurora cluster if you do not already have one:

    # Create the primary Aurora cluster in us-east-1
aws rds create-db-cluster \
  --db-cluster-identifier prod-global-primary \
  --engine aurora-postgresql \
  --engine-version 15.4 \
  --master-username pgadmin \
  --master-user-password "${DB_PASSWORD}" \
  --db-subnet-group-name prod-subnet-group \
  --vpc-security-group-ids sg-0abc123def456789 \
  --storage-encrypted \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/mrk-abc123 \
  --region us-east-1

# Create the writer instance
aws rds create-db-instance \
  --db-instance-identifier prod-global-primary-writer \
  --db-cluster-identifier prod-global-primary \
  --db-instance-class db.r7g.4xlarge \
  --engine aurora-postgresql \
  --region us-east-1

# Create the Global Database wrapper (wraps the existing cluster)
aws rds create-global-cluster \
  --global-cluster-identifier prod-aurora-global \
  --source-db-cluster-identifier arn:aws:rds:us-east-1:123456789012:cluster:prod-global-primary \
  --region us-east-1

    Adding a secondary region requires the secondary region to have its own VPC, subnet group, and KMS key. If you are using a customer-managed KMS key (which you should be in production), you need a multi-region key or separate regional keys. A common mistake is using a single-region KMS key and then being surprised when the secondary cluster creation fails.

    # Add a secondary cluster in eu-west-1
aws rds create-db-cluster \
  --db-cluster-identifier prod-global-secondary-eu \
  --engine aurora-postgresql \
  --engine-version 15.4 \
  --global-cluster-identifier prod-aurora-global \
  --db-subnet-group-name prod-subnet-group-eu \
  --vpc-security-group-ids sg-0def456abc123789 \
  --storage-encrypted \
  --kms-key-id arn:aws:kms:eu-west-1:123456789012:key/mrk-def456 \
  --region eu-west-1

# Add a reader instance in the secondary cluster
aws rds create-db-instance \
  --db-instance-identifier prod-global-secondary-eu-reader \
  --db-cluster-identifier prod-global-secondary-eu \
  --db-instance-class db.r7g.2xlarge \
  --engine aurora-postgresql \
  --region eu-west-1

    Monitoring Replication Lag with CloudWatch

    Aurora Global exposes the AuroraGlobalDBReplicationLag metric in CloudWatch. Set an alarm on this. A reasonable alert threshold for most OLTP workloads is 5 seconds; a page-worthy threshold is 30 seconds.

    # Create a CloudWatch alarm for Global DB replication lag
aws cloudwatch put-metric-alarm \
  --alarm-name aurora-global-replication-lag-warning \
  --alarm-description "Aurora Global replication lag exceeds 5 seconds" \
  --metric-name AuroraGlobalDBReplicationLag \
  --namespace AWS/RDS \
  --statistic Maximum \
  --period 60 \
  --evaluation-periods 3 \
  --threshold 5000 \
  --comparison-operator GreaterThanThreshold \
  --dimensions Name=DBClusterIdentifier,Value=prod-global-secondary-eu \
  --alarm-actions arn:aws:sns:eu-west-1:123456789012:dba-alerts \
  --treat-missing-data notBreaching \
  --region eu-west-1

    Failover Behavior and What to Expect

    Aurora Global failover is not automatic by default. There is no built-in equivalent to an Always On availability group's automatic failover with a failure detection timeout. You must either trigger it manually or build automation around it.

    When you initiate a managed failover (the preferred path that minimizes data loss), Aurora promotes the secondary cluster in the target region and demotes the primary. The process takes 1–2 minutes and involves:

    1. Stopping writes on the primary

    2. Waiting for the secondary to apply all pending replication entries

    3. Promoting the secondary to read-write

    4. Updating the Global Database configuration to reflect the new primary

    If you use an unplanned failover (the primary region is completely unavailable), you detach the secondary cluster from the Global Database and promote it independently. In this scenario, the data in-flight that had not yet replicated is lost — that is your actual RPO.

    Your application connection string must change after failover. Aurora does not automatically redirect the cluster endpoint. Applications pointing at the old primary region's cluster endpoint will fail until you update DNS or connection strings. This is a common operational gap. Solve it with Route53 health checks and a CNAME that points to whichever region is primary, or use a global accelerator pattern.

    16.3 Azure SQL Active Geo-Replication and Failover Groups

    Azure SQL offers two related but distinct features. Active Geo-Replication is the lower-level primitive: it creates readable secondary databases in up to four other regions, with asynchronous replication at the database level. Failover Groups are the higher-level abstraction: they manage one or more databases together, provide a stable listener endpoint that does not change after failover, and support automatic failover through a health-check based policy.

    If you are building a production application, use Failover Groups. Active Geo-Replication alone requires you to update connection strings after failover. Failover Groups give you a fixed endpoint — .database.windows.net for the primary and .secondary.database.windows.net for the secondary — that routes to whichever server is currently primary.

    Creating a Failover Group with Azure CLI

    # Variables
PRIMARY_SERVER="prod-sql-eastus"
SECONDARY_SERVER="prod-sql-westeu"
RESOURCE_GROUP="prod-rg"
FAILOVER_GROUP="prod-fog-01"
DATABASE_NAME="applicationdb"

# Create the secondary server in West Europe
az sql server create \
  --name $SECONDARY_SERVER \
  --resource-group $RESOURCE_GROUP \
  --location "westeurope" \
  --admin-user sqladmin \
  --admin-password "${SQL_ADMIN_PASSWORD}"

# Configure firewall rules and private endpoints on secondary
# (match whatever you have on primary)
az sql server firewall-rule create \
  --resource-group $RESOURCE_GROUP \
  --server $SECONDARY_SERVER \
  --name AllowAzureServices \
  --start-ip-address 0.0.0.0 \
  --end-ip-address 0.0.0.0

# Create the failover group
# This initiates geo-replication of all specified databases
az sql failover-group create \
  --name $FAILOVER_GROUP \
  --partner-server $SECONDARY_SERVER \
  --resource-group $RESOURCE_GROUP \
  --server $PRIMARY_SERVER \
  --add-db $DATABASE_NAME \
  --failover-policy Automatic \
  --grace-period 1

# The grace-period is in hours — 1 hour before automatic failover triggers
# Setting to 0 means immediate failover, which risks unnecessary failovers
# during transient connectivity issues between regions

    The --grace-period parameter deserves attention. Azure uses a health-check mechanism that monitors connectivity between the primary and secondary. If the primary is unreachable for longer than the grace period, automatic failover triggers. Setting this to 0 — immediate failover — risks data loss and unnecessary failovers if there are transient network issues between Azure regions that do not represent actual primary failure. For most production workloads, 1 hour is the recommended minimum, and many organizations use 2–4 hours depending on their RPO tolerance.

    Monitoring Geo-Replication Health

    Azure SQL exposes geo-replication state through sys.dm_geo_replication_link_states in the primary database:

    -- Run on the PRIMARY database
-- Check replication health for all geo-replicas
SELECT
    link_guid,
    partner_server,
    partner_database,
    last_replication,
    replication_lag_sec,
    replication_state_desc,
    role_desc,
    secondary_allow_connections_desc
FROM sys.dm_geo_replication_link_states
ORDER BY replication_lag_sec DESC;

-- Practical alert query: lag over 30 seconds is worth investigating
-- lag over 300 seconds (5 minutes) warrants a page
SELECT
    partner_server,
    partner_database,
    replication_lag_sec,
    last_replication,
    CASE
        WHEN replication_lag_sec > 300 THEN 'CRITICAL'
        WHEN replication_lag_sec > 30  THEN 'WARNING'
        ELSE 'OK'
    END AS lag_status
FROM sys.dm_geo_replication_link_states
WHERE role_desc = 'PRIMARY';

    On the secondary, you can also query sys.dm_database_replica_states to see how far behind the secondary is in terms of log send queue and redo queue — the same DMVs you know from Always On, repurposed for geo-replication context.

    Failover Group Listener and Application Connection Patterns

    The Failover Group listener endpoint is where your application connection string points. After any failover — planned or unplanned — your application continues to connect to prod-fog-01.database.windows.net without any changes. Azure's DNS resolves this to whichever server is currently primary.

    # Initiate a planned failover (controlled, no data loss)
# Run this for maintenance or DR drills
az sql failover-group set-primary \
  --name $FAILOVER_GROUP \
  --resource-group $RESOURCE_GROUP \
  --server $SECONDARY_SERVER

# Check failover group status after failover
az sql failover-group show \
  --name $FAILOVER_GROUP \
  --resource-group $RESOURCE_GROUP \
  --server $SECONDARY_SERVER \
  --query "{primaryServer:replicationRole, location:location, databases:databases}"

    One constraint that catches DBAs migrating from Always On: Failover Groups in Azure SQL Database (the fully managed PaaS tier) are limited to two servers — one primary and one secondary. You cannot have two readable secondaries in two different regions plus your primary in a single Failover Group. If you need multiple secondary regions, you use Active Geo-Replication directly and accept that you manage connection string routing yourself. SQL Managed Instance supports up to four regions in a Failover Group, which gives more flexibility.

    Hyperscale Geo-Replication Differences

    If you are using Azure SQL Hyperscale — the tier that decouples compute from storage and supports up to 100TB databases — geo-replication works differently. Hyperscale uses Named Replicas and Geo-Replicas as distinct concepts. A Geo-Replica in Hyperscale is seeded from the distributed page server layer rather than through log shipping, which means the initial seeding is extremely fast even for multi-terabyte databases — often measured in minutes rather than the hours traditional log shipping takes to initialize a large secondary.

    The tradeoff: Hyperscale Geo-Replicas have higher replication lag than standard geo-replication at high write throughput. If your Hyperscale workload generates more than roughly 100MB/s of log, expect lag to grow during peak write periods.

    16.4 Google Cloud Spanner and Cloud SQL: Multi-Region Strategies

    Google Cloud offers two fundamentally different architectures for geo-redundancy, and choosing between them depends on whether you need strong consistency or are willing to tolerate eventual consistency for the benefit of scale.

    Cloud Spanner Multi-Region Configurations

    Spanner is the only globally distributed, strongly consistent, relational database available as a managed service. This is not marketing — it is an architectural statement with real implications. Spanner uses the TrueTime API, which relies on atomic clocks and GPS receivers in Google's data centers to provide bounded clock uncertainty and enable external consistency across regions.

    When you configure a Spanner instance with a multi-region configuration, writes are synchronously committed to a quorum of regions before returning success to the application. This means you get zero RPO under region failure — but you pay for it with higher write latency.

    Spanner's regional configurations use naming conventions that encode the topology:

  • → `nam4` — dual-region, US East and US Central, optimized for low-latency writes in the Eastern US
  • → `eur3` — dual-region, Netherlands and Belgium
  • → `nam-eur-asia1` — multi-region spanning North America, Europe, and Asia (five regions total)
  • → `nam6` — six North American regions
    • # Create a Spanner instance with multi-region configuration
gcloud spanner instances create prod-spanner-global \
  --config=nam-eur-asia1 \
  --description="Production global instance" \
  --nodes=3 \
  --project=prod-project-id

# Multi-region configs replicate compute across every region in the
# configuration, so a production-grade node count (3+ for quorum headroom)
# costs meaningfully more than the same node count in a single-region
# instance. Check current Spanner pricing and the specific replica
# topology for your chosen multi-region config before committing to it.

# Check instance replication details
gcloud spanner instances describe prod-spanner-global \
  --project=prod-project-id \
  --format="yaml(config,displayName,nodeCount,state)"

# Create a database in the multi-region instance
gcloud spanner databases create applicationdb \
  --instance=prod-spanner-global \
  --project=prod-project-id

    The write latency penalty for global multi-region Spanner is real. For nam-eur-asia1, a write commit from a US East application needs to reach quorum across regions spanning multiple continents, and that commit latency is an order of magnitude higher than a single-region Spanner instance. Benchmark your own commit latency against your specific region pair before committing to a topology — published figures vary by configuration and change over time — and applications built for single-digit-millisecond write latency will need to reconsider whether global Spanner is the right tool.

    Cloud SQL for PostgreSQL: Multi-Region Read Replicas

    Cloud SQL does not offer Spanner's synchronous multi-region consistency model. Instead, it offers cross-region read replicas backed by asynchronous replication, similar to Aurora Global. The replication mechanism is standard PostgreSQL streaming replication — the same process you know from on-prem setups, managed by Google's control plane.

    # Create a Cloud SQL primary instance
gcloud sql instances create prod-postgres-primary \
  --database-version=POSTGRES_15 \
  --tier=db-custom-16-65536 \
  --region=us-central1 \
  --storage-type=SSD \
  --storage-size=500GB \
  --storage-auto-increase \
  --backup-start-time=04:00 \
  --enable-bin-log \
  --availability-type=REGIONAL \
  --project=prod-project-id

# Create a cross-region read replica in europe-west1
gcloud sql instances create prod-postgres-replica-eu \
  --master-instance-name=prod-postgres-primary \
  --region=europe-west1 \
  --tier=db-custom-8-32768 \
  --database-version=POSTGRES_15 \
  --project=prod-project-id

# Check replication lag using Cloud SQL's built-in monitoring
gcloud sql instances describe prod-postgres-replica-eu \
  --project=prod-project-id \
  --format="yaml(replicaConfiguration,replicationLagSeconds)"

    Cloud SQL cross-region replicas cannot be automatically promoted on regional failure. Promotion is a manual or scripted action. Unlike Aurora Global, there is no managed failover path that handles orchestration for you. You must:

    1. Promote the replica to a standalone instance (which breaks replication)

    2. Update your application's connection string to point to the promoted instance

    3. Once the primary region recovers, recreate the replica relationship from the newly promoted instance back toward the old primary, or rebuild from scratch

    # Promote a cross-region replica after a regional outage
# This is a one-way operation — there is no "unpromote"
gcloud sql instances promote-replica prod-postgres-replica-eu \
  --project=prod-project-id

# After promotion, the instance becomes read-write standalone
# Verify it is now accepting writes
gcloud sql instances describe prod-postgres-replica-eu \
  --project=prod-project-id \
  --format="yaml(instanceType,region,state)"
# instanceType should now be "CLOUD_SQL_INSTANCE" not "READ_REPLICA_INSTANCE"

    AlloyDB Cross-Region Considerations

    AlloyDB, Google's PostgreSQL-compatible high-performance managed database, as of 2024 supports cross-region replication through AlloyDB Omni (the self-managed distribution) and is rolling out managed cross-region secondary clusters. For production deployments requiring geo-redundancy on AlloyDB, verify the current regional availability of cross-region secondary clusters against the GCP documentation, as this feature has been in preview with limited region pairs. The architecture follows a similar storage-layer replication model to Aurora Global rather than WAL-stream replication.

    16.5 Terraform Patterns for Multi-Region Database Infrastructure

    Managing geo-replicated database infrastructure with manual CLI commands is viable for initial setup and DR drills. It is not viable for maintaining consistency across environments, tracking configuration drift, or onboarding new regions. Terraform brings the same discipline to database infrastructure that you would apply to application infrastructure.

    The following Terraform module provisions an Aurora Global Database with a primary in us-east-1 and a secondary in eu-west-1, including CloudWatch alarms and the necessary KMS multi-region keys.

    # aurora_global.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

# Provider aliases for multi-region
provider "aws" {
  alias  = "primary"
  region = "us-east-1"
}

provider "aws" {
  alias  = "secondary"
  region = "eu-west-1"
}

# Multi-region KMS key for Aurora storage encryption
resource "aws_kms_key" "aurora_global" {
  provider                = aws.primary
  description             = "Aurora Global Database encryption key"
  enable_key_rotation     = true
  multi_region            = true
  deletion_window_in_days = 30

  tags = {
    Environment = "production"
    ManagedBy   = "terraform"
  }
}

# Replicate KMS key to secondary region
resource "aws_kms_replica_key" "aurora_global_eu" {
  provider        = aws.secondary
  description     = "Aurora Global Database encryption key replica (EU)"
  primary_key_arn = aws_kms_key.aurora_global.arn
}

# Primary Aurora cluster
resource "aws_rds_cluster" "primary" {
  provider                    = aws.primary
  cluster_identifier          = "prod-global-primary"
  engine                      = "aurora-postgresql"
  engine_version              = "15.4"
  master_username             = "pgadmin"
  master_password             = var.db_master_password
  db_subnet_group_name        = var.primary_subnet_group
  vpc_security_group_ids      = var.primary_security_groups
  storage_encrypted           = true
  kms_key_id                  = aws_kms_key.aurora_global.arn
  backup_retention_period     = 14
  preferred_backup_window     = "03:00-04:00"
  preferred_maintenance_window = "sun:05:00-sun:06:00"
  deletion_protection         = true
  skip_final_snapshot         = false
  final_snapshot_identifier   = "prod-global-primary-final"

  tags = {
    Environment = "production"
    ManagedBy   = "terraform"
    Role        = "global-primary"
  }
}

resource "aws_rds_cluster_instance" "primary_writer" {
  provider             = aws.primary
  identifier           = "prod-global-primary-writer"
  cluster_identifier   = aws_rds_cluster.primary.id
  instance_class       = "db.r7g.4xlarge"
  engine               = aws_rds_cluster.primary.engine
  engine_version       = aws_rds_cluster.primary.engine_version
  db_subnet_group_name = var.primary_subnet_group
  monitoring_interval  = 60
  monitoring_role_arn  = var.rds_monitoring_role_arn

  tags = {
    Environment = "production"

  }

  global_cluster_identifier = "prod-aurora-global"
  source_db_cluster_identifier = aws_rds_cluster.primary.arn

    Variables and separation of concerns

    Keep the multi-region module clean by separating variables that differ per region from those that are shared. A common pattern is a variables.tf file at the module level with clear defaults and descriptions:

    # variables.tf
variable "db_master_password" {
  description = "Master password for the Aurora cluster. Source from AWS Secrets Manager in CI/CD."
  type        = string
  sensitive   = true
}

variable "primary_subnet_group" {
  description = "DB subnet group name in the primary region (us-east-1)."
  type        = string
}

variable "secondary_subnet_group" {
  description = "DB subnet group name in the secondary region (eu-west-1)."
  type        = string
}

variable "primary_security_groups" {
  description = "Security group IDs attached to the primary Aurora cluster."
  type        = list(string)

    16.6 Failover Automation and DR Drill Patterns

    Geo-replication that has never been tested has unknown reliability. A configuration that looks correct in Terraform output and passes all health checks in CloudWatch can still fail a real DR event due to network ACL mismatches in the secondary VPC, missing IAM permissions for the promoted cluster, applications that cached the primary endpoint at startup, or secrets that exist only in the primary region's Secrets Manager.

    The only way to discover these problems before a real disaster is to run regular, disruptive DR drills. Disruptive means you actually fail over, not that you simulate what would happen.

    Aurora Global Failover Script

    The following script performs a managed failover for Aurora Global and validates the secondary becomes the new primary. Run this quarterly at minimum, more frequently if your RTO or RPO requirements are strict.

    #!/usr/bin/env bash
# aurora_global_failover_drill.sh
# Performs a planned managed failover of Aurora Global Database
# and validates the new primary is accepting writes.
set -euo pipefail

GLOBAL_CLUSTER_ID="prod-aurora-global"
SECONDARY_CLUSTER_ARN="arn:aws:rds:eu-west-1:123456789012:cluster:prod-global-secondary-eu"
PRIMARY_REGION="us-east-1"
SECONDARY_REGION="eu-west-1"
DRILL_LOG="failover_drill_$(date +%Y%m%d_%H%M%S).log"

log() {
  echo "[$(date -u '+%Y-%m-%dT%H:%M:%SZ')] $*" | tee -a "$DRILL_LOG"
}

log "=== Aurora Global Failover Drill Starting ==="
log "Global Cluster: $GLOBAL_CLUSTER_ID"
log "Target Region: $SECONDARY_REGION"

# Capture pre-failover replication lag
PRE_LAG=$(aws cloudwatch get-metric-statistics \
  --region "$SECONDARY_REGION" \
  --namespace AWS/RDS \
  --metric-name AuroraGlobalDBReplicationLag \
  --dimensions Name=DBClusterIdentifier,Value=prod-global-secondary-eu \
  --start-time "$(date -u -d '5 minutes ago' '+%Y-%m-%dT%H:%M:%SZ')" \
  --end-time "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
  --period 300 \
  --statistics Maximum \
  --query 'Datapoints[0].Maximum' \
  --output text 2>/dev/null || echo "N/A")

log "Pre-failover replication lag (max 5min): ${PRE_LAG}ms"

if [[ "$PRE_LAG" != "N/A" ]] && (( $(echo "$PRE_LAG > 10000" | bc -l) )); then
  log "WARNING: Replication lag is ${PRE_LAG}ms — proceeding but RPO may be elevated"
fi

FAILOVER_START=$(date +%s)

log "Initiating managed planned failover..."
aws rds failover-global-cluster \
  --global-cluster-identifier "$GLOBAL_CLUSTER_ID" \
  --target-db-cluster-identifier "$SECONDARY_CLUSTER_ARN" \
  --region "$PRIMARY_REGION"

log "Failover initiated. Polling for completion..."

# Poll until the secondary cluster shows as writer
MAX_WAIT=300  # 5 minutes
ELAPSED=0
while [[ $ELAPSED -lt $MAX_WAIT ]]; do
  CLUSTER_STATUS=$(aws rds describe-db-clusters \
    --db-cluster-identifier prod-global-secondary-eu \
    --region "$SECONDARY_REGION" \
    --query 'DBClusters[0].{Status:Status,IAMAuth:IAMDatabaseAuthenticationEnabled}' \
    --output json 2>/dev/null || echo '{"Status":"unknown"}')

  GLOBAL_STATUS=$(aws rds describe-global-clusters \
    --global-cluster-identifier "$GLOBAL_CLUSTER_ID" \
    --region "$PRIMARY_REGION" \
    --query 'GlobalClusters[0].GlobalClusterMembers[?contains(DBClusterArn,`eu-west-1`)].{Writer:IsWriter}' \
    --output text 2>/dev/null || echo "False")

  if [[ "$GLOBAL_STATUS" == "True" ]]; then
    FAILOVER_END=$(date +%s)
    FAILOVER_DURATION=$((FAILOVER_END - FAILOVER_START))
    log "Failover completed in ${FAILOVER_DURATION} seconds"
    break
  fi

  sleep 10
  ELAPSED=$((ELAPSED + 10))
  log "Waiting... ${ELAPSED}s elapsed. EU writer status: $GLOBAL_STATUS"
done

if [[ $ELAPSED -ge $MAX_WAIT ]]; then
  log "ERROR: Failover did not complete within ${MAX_WAIT} seconds"
  exit 1
fi

# Validate write access on the new primary
log "Validating write access on new primary (eu-west-1)..."
# Replace with actual connection test appropriate to your environment
WRITE_TEST=$(psql \
  --host=prod-global-secondary-eu.cluster-xxxxxxxxxxxx.eu-west-1.rds.amazonaws.com \
  --username=pgadmin \
  --dbname=applicationdb \
  --no-password \
  --command="SELECT pg_is_in_recovery(), current_timestamp, inet_server_addr();" \
  --tuples-only 2>/dev/null || echo "CONNECTION_FAILED")

log "Write validation result: $WRITE_TEST"

if echo "$WRITE_TEST" | grep -q "f|"; then
  log "SUCCESS: New primary is accepting writes (pg_is_in_recovery = false)"
else
  log "WARN: Could not confirm write access — check connection string and security groups"
fi

log "=== DR Drill Complete. Review $DRILL_LOG for full record. ==="
log "ACTION REQUIRED: Update application connection string if not using Route53/CNAME abstraction."
log "ACTION REQUIRED: Fail back to us-east-1 after drill is complete."

    After the drill, record the actual failover duration. Compare it against your RTO target. If your RTO is five minutes and the failover took 90 seconds, you have margin. If failover took four minutes and 15 seconds, you have a problem at any write volume spike, and you should investigate the replication lag at the time of the drill.

    Failback After a Drill

    Failback is the reverse operation: re-adding the old primary region as a secondary and then promoting it back to primary. After a managed failover, the original primary cluster becomes a secondary. It receives replication from the new primary in eu-west-1. Once replication lag drains and the old-primary cluster is caught up, you perform another managed failover to restore the original topology.

    # After drill: check that original primary (now secondary) is caught up
aws cloudwatch get-metric-statistics \
  --region us-east-1 \
  --namespace AWS/RDS \
  --metric-name AuroraGlobalDBReplicationLag \
  --dimensions Name=DBClusterIdentifier,Value=prod-global-primary \
  --start-time "$(date -u -d '5 minutes ago' '+%Y-%m-%dT%H:%M:%SZ')" \
  --end-time "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
  --period 60 \
  --statistics Maximum \
  --output text

# Once lag is acceptable (<5 seconds), fail back
aws rds failover-global-cluster \
  --global-cluster-identifier prod-aurora-global \
  --target-db-cluster-identifier arn:aws:rds:us-east-1:123456789012:cluster:prod-global-primary \
  --region eu-west-1

    16.7 RPO Measurement and Continuous Validation

    Publishing an RPO figure in a runbook without measuring it continuously is a compliance exercise, not an engineering practice. Replication lag changes under load, during maintenance windows, during storage rebalancing events, and during transient network events between regions. The only RPO figure that means something is the one you measure continuously from production.

    PostgreSQL-Compatible RPO Tracking

    For Aurora PostgreSQL or Cloud SQL for PostgreSQL, you can measure actual replication delay from the application perspective by writing a heartbeat record and measuring how long it takes to appear on the replica.

    -- On the PRIMARY: Create a replication heartbeat table
-- Run once during setup
CREATE TABLE IF NOT EXISTS replication_heartbeat (
    id          SERIAL PRIMARY KEY,
    written_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    source      TEXT NOT NULL DEFAULT 'primary',
    sequence    BIGINT NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_heartbeat_written_at
    ON replication_heartbeat (written_at DESC);

-- Grant a monitoring user access
GRANT INSERT, SELECT ON replication_heartbeat TO monitoring_user;
GRANT USAGE, SELECT ON SEQUENCE replication_heartbeat_id_seq TO monitoring_user;
    -- Heartbeat writer — run on primary every 10 seconds from a monitoring job
-- Use pg_cron, a Lambda, or a lightweight sidecar process
INSERT INTO replication_heartbeat (written_at, source, sequence)
SELECT
    NOW(),
    'primary',
    COALESCE(MAX(sequence), 0) + 1
FROM replication_heartbeat;

-- Keep the table small: retain only the last 24 hours
DELETE FROM replication_heartbeat
WHERE written_at < NOW() - INTERVAL '24 hours';
    -- Heartbeat reader — run on REPLICA every 30 seconds from a monitoring job
-- Reports the actual observed RPO: how old is the newest heartbeat we can read?
SELECT
    MAX(written_at)                                AS latest_heartbeat_on_replica,
    NOW()                                          AS replica_clock,
    EXTRACT(EPOCH FROM (NOW() - MAX(written_at))) AS observed_rpo_seconds,
    CASE
        WHEN EXTRACT(EPOCH FROM (NOW() - MAX(written_at))) > 300 THEN 'CRITICAL'
        WHEN EXTRACT(EPOCH FROM (NOW() - MAX(written_at))) > 30  THEN 'WARNING'
        ELSE 'OK'
    END AS rpo_status
FROM replication_heartbeat;

    This query runs on the replica. If the newest heartbeat row on the replica is 45 seconds old, your observed RPO at this moment is 45 seconds. That is more meaningful than CloudWatch's AuroraGlobalDBReplicationLag metric, which measures WAL application lag — not the time-to-visibility from an application query perspective.

    SQL Server Equivalent: Azure SQL Geo-Replica RPO Tracking

    -- On PRIMARY: Create heartbeat table
CREATE TABLE dbo.ReplicationHeartbeat (
    HeartbeatId   INT IDENTITY(1,1) PRIMARY KEY,
    WrittenAt     DATETIMEOFFSET(3) NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    SourceServer  NVARCHAR(128)     NOT NULL DEFAULT @@SERVERNAME,
    Sequence      BIGINT            NOT NULL DEFAULT 0
);

CREATE INDEX IX_ReplicationHeartbeat_WrittenAt
    ON dbo.ReplicationHeartbeat (WrittenAt DESC);

-- Insert heartbeat every 10 seconds via SQL Agent job or Azure Automation
INSERT INTO dbo.ReplicationHeartbeat (WrittenAt, SourceServer, Sequence)
SELECT
    SYSDATETIMEOFFSET(),
    @@SERVERNAME,
    ISNULL((SELECT MAX(Sequence) FROM dbo.ReplicationHeartbeat), 0) + 1;

-- Purge old rows
DELETE FROM dbo.ReplicationHeartbeat
WHERE WrittenAt < DATEADD(HOUR, -24, SYSDATETIMEOFFSET());
    -- On GEO-REPLICA: Measure observed RPO
SELECT
    MAX(WrittenAt)                                              AS LatestHeartbeatOnReplica,
    SYSDATETIMEOFFSET()                                        AS ReplicaClock,
    DATEDIFF(SECOND, MAX(WrittenAt), SYSDATETIMEOFFSET())      AS ObservedRPOSeconds,
    CASE
        WHEN DATEDIFF(SECOND, MAX(WrittenAt), SYSDATETIMEOFFSET()) > 300 THEN 'CRITICAL'
        WHEN DATEDIFF(SECOND, MAX(WrittenAt), SYSDATETIMEOFFSET()) > 30  THEN 'WARNING'
        ELSE 'OK'
    END AS RPOStatus
FROM dbo.ReplicationHeartbeat;

    Push the ObservedRPOSeconds value to your observability platform as a custom metric alongside the vendor-supplied replication lag metrics. When these two numbers diverge significantly — vendor says 2 seconds, heartbeat says 45 seconds — it usually means the vendor metric measures log application lag while your heartbeat measures commit-to-visible lag including lock contention or log replay bottlenecks on the replica. The heartbeat is the more operationally relevant number.

    16.8 Common Failure Modes and Operational Traps

    Split-Brain After Unplanned Failover

    In Aurora Global, split-brain cannot occur during a managed failover because the old primary is stopped before the new primary is promoted. But in an unplanned failover — where you detach the secondary and promote it because the primary region is unreachable — the primary region may actually be reachable from some clients. If applications are still writing to the old primary and the detached secondary is also accepting writes, you have split-brain: two diverged copies of the database, both accepting writes.

    Prevent this by ensuring:

  • → Your application's primary connection string routes through a DNS layer (Route53 or Azure Traffic Manager) that you control
  • → You change DNS to point to the secondary before or immediately when you promote it
  • → You have a runbook step that explicitly verifies the old primary is no longer accepting application traffic before promoting the secondary

    • Replica Overload Under Read Scaling Patterns

    A common antipattern is pointing all reporting workloads at the secondary cluster as a cost optimization. Heavy analytical queries on the secondary consume compute and I/O that compete with the replication apply process. Under high write volume from the primary, a secondary cluster running expensive queries can fall progressively further behind. The CloudWatch lag metric climbs, alert fires, on-call investigates and finds no infrastructure problem — the secondary is simply unable to keep up with both query load and replication apply simultaneously.

    Monitor DBLoad on secondary instances alongside replication lag. If secondary DBLoad approaches the number of vCPUs consistently, resize the secondary upward or move the reporting workload to a dedicated replica that is not your only DR target.

    KMS Key Region Mismatches

    If you created an Aurora cluster encrypted with a single-region KMS key and then attempted to convert it to a Global Database, you will encounter failures when adding secondary regions. The secondary cluster's storage is encrypted with the key provided at creation time, and a single-region key cannot encrypt storage in another region. Fix: use multi-region KMS keys from the start, or use AWS-managed keys (though customer-managed keys are preferable for most regulated workloads).

    Azure SQL Failover Group and Long-Running Transactions

    Azure SQL Failover Group planned failover will wait for all active transactions to complete before switching roles. A long-running transaction — a multi-hour bulk load or an uncommitted transaction from a runaway session — blocks planned failover indefinitely. Before initiating a planned failover, query sys.dm_exec_requests and kill any transactions expected to take longer than your RTO window.

    -- Identify long-running transactions that will block planned failover
SELECT
    r.session_id,
    r.command,
    r.status,
    r.wait_type,
    r.wait_time / 1000.0                              AS wait_seconds,
    r.total_elapsed_time / 1000.0                     AS elapsed_seconds,
    SUBSTRING(st.text, (r.statement_start_offset/2)+1,
        ((CASE r.statement_end_offset
            WHEN -1 THEN DATALENGTH(st.text)
            ELSE r.statement_end_offset
          END - r.statement_start_offset)/2)+1)       AS current_statement,
    s.login_name,
    s.host_name,
    s.program_name
FROM sys.dm_exec_requests r
JOIN sys.dm_exec_sessions s ON r.session_id = s.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
WHERE r.session_id <> @@SPID
  AND r.total_elapsed_time > 60000   -- longer than 1 minute
ORDER BY r.total_elapsed_time DESC;

    Cloud SQL Replica Promotion and the Replication Slot Problem

    Cloud SQL for PostgreSQL uses logical replication slots internally for replication management. When you promote a read replica to a standalone instance, any replication slots that existed on the original primary are not transferred. If you used logical replication slots for CDC (Change Data Capture) or third-party integrations like Debezium pointing at the original primary, those slots are gone after promotion. You must re-create them on the newly promoted instance and restart your CDC consumers.

    Document your replication slot inventory as part of your DR runbook. Include the slot names, plugin types (pgoutput, wal2json, etc.), publication names, and downstream consumers. Test slot re-creation in your DR drills.

    16.9 Geo-Replication Checklist for Production Readiness

    Before treating a geo-replicated deployment as production-ready, work through the following:

    Configuration Validation

  • → [ ] Replication lag alarm set and tested (warning and critical thresholds)
  • → [ ] Heartbeat table deployed on primary; heartbeat reader running on secondary
  • → [ ] Observed RPO measured under normal load and under peak write load
  • → [ ] KMS keys are multi-region or region-appropriate (no single-region key in global setup)
  • → [ ] Secondary cluster has correct security groups, NACLs, and subnet groups
  • → [ ] Secondary cluster's monitoring and alerting is configured independently of primary region

    • Failover Readiness

  • → [ ] Failover runbook documented and reviewed by DBA team
  • → [ ] Application connection string abstracted behind DNS or listener endpoint that survives failover without code change
  • → [ ] DR drill performed (not simulated) within the last 90 days
  • → [ ] Actual failover duration measured and compared against RTO target
  • → [ ] Failback procedure documented and tested
  • → [ ] Long-running transaction kill procedure included in planned failover runbook

    • Application-Layer Considerations

  • → [ ] Application connection pools handle reconnection after failover gracefully
  • → [ ] Read replicas in secondary region configured in application connection string (read/write split)
  • → [ ] Session-level write operations not issued against the read endpoint
  • → [ ] CDC / logical replication consumers tested against promoted secondary

    • Operational Runbooks

  • → [ ] Unplanned failover procedure (primary region completely unavailable)
  • → [ ] Split-brain prevention and detection steps documented
  • → [ ] Replication slot inventory current and tested in DR drills
  • → [ ] Post-failover validation steps with expected output documented

    Key Takeaways

  • → **Cross-region replication is always asynchronous** in every managed cloud database service. The speed of light means synchronous writes across continents are impractical for OLTP workloads. Cloud Spanner is the single exception, using a quorum model with strong consistency, but at the cost of higher write latency and substantially higher per-region cost.
  • → **RPO is not a configuration parameter — it is a measurement.** Replication lag fluctuates with write volume, secondary load, and network conditions. Deploy a heartbeat table on the primary and query it from the secondary continuously to measure observed RPO, and alert when it exceeds your contractual threshold.
  • → **Abstraction layers at the connection string level are non-negotiable.** Aurora does not reroute your cluster endpoint after failover. Azure SQL Failover Groups solve this with a stable listener; Aurora Global requires you to solve it with Route53 or a similar DNS layer. Applications that hardcode regional cluster endpoints will fail during failover and require code changes under the worst possible conditions.
  • → **DR drills must be disruptive to be valid.** A drill that does not actually perform a failover discovers nothing about real failure modes: missing IAM permissions in the secondary region, security group mismatches, secrets that exist only in the primary Secrets Manager, and CDC consumers that lose their replication slots. Run full failovers quarterly at minimum, measure the actual duration against your RTO target, and fix the gaps before the next drill.
  • → **Secondary cluster resource sizing is a hidden operational trap.** Under-sized secondary clusters that serve both read traffic and replication apply will fall progressively further behind under combined load. Monitor `DBLoad` alongside replication lag on all secondary clusters, and size them based on combined replication and read query demand, not just one or the other.
