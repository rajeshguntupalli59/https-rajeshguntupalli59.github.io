Chapter 24: Building a RAG Pipeline on PostgreSQL and pgvector

Retrieval-Augmented Generation (RAG) is the pattern that makes large language models useful in enterprise settings: instead of relying solely on what a model learned during training, you give it fresh, relevant context pulled from your own data at query time. For database professionals, RAG is fundamentally a query architecture problem—one where the "query" involves embedding vectors, approximate nearest-neighbor search, and prompt assembly rather than B-tree lookups and JOIN plans. PostgreSQL with pgvector is a compelling RAG backend precisely because it lets you keep your application data, your document metadata, and your vector indexes in one system you already know how to operate, monitor, and tune. This chapter builds a complete RAG pipeline on PostgreSQL and pgvector from first principles: schema design, embedding ingestion, retrieval logic, LLM integration, and the production patterns that separate a demo from a system you'd trust in production.

---

24.1 RAG Architecture Through a Database Lens

Before writing a single line of Python, it helps to map RAG components onto database concepts you already reason about.

A RAG system has two distinct phases: ingestion (offline) and retrieval + generation (online). In database terms:

  • → **Ingestion** is a bulk ETL pipeline. You load documents, chunk them, compute embeddings, and write rows into a vector-capable table. The bottleneck is usually the embedding API call, not the database write.
  • → **Retrieval** is a query. Given a question, you embed it, run an ANN (approximate nearest-neighbor) search, and return the top-*k* rows. This is where index design and query planning matter.
  • → **Generation** is a downstream consumer of your query results. The LLM receives the retrieved rows as context and produces an answer. From the database's perspective, generation is just a client that reads your resultset.

    • The mental model that helps most: think of your document chunks as rows in a fact table, embeddings as a specialized indexed column, and the LLM as a reporting layer. The database's job is to serve relevant rows fast. The LLM's job is to synthesize them into language.

    Where PostgreSQL fits: pgvector adds a vector column type and three index types (IVFFlat, HNSW, and the newer streaming index). It supports L2 distance, cosine similarity, and inner product operators. Everything else—ACID transactions, MVCC, row-level security, JSONB metadata, full-text search, foreign keys to your application tables—comes standard from PostgreSQL. This is the core argument for pgvector over a dedicated vector database when you're already running Postgres: operational simplicity at the cost of some raw ANN throughput.

    Tradeoffs to keep in mind:

    | Property | pgvector | Dedicated vector DB |

    |---|---|---|

    | Operational overhead | Low (existing Postgres) | New system to operate |

    | Metadata filtering | Full SQL | Varies; often limited |

    | ANN throughput (vectors/sec) | ~5k–50k QPS at 1536-dim | ~50k–500k QPS |

    | Hybrid search (BM25 + vector) | Yes, via ts_rank + vector | Weaviate, Qdrant natively |

    | Transactional consistency | Full ACID | Eventually consistent |

    | Max vector dimensions | 16,000 (unindexed column); 2,000 for either HNSW or IVFFlat index | Typically 20,000+ |

    For most enterprise RAG workloads under a few hundred QPS, pgvector is sufficient and the operational simplicity is worth it.

    24.2 Schema Design for RAG Documents

    Good schema design is the foundation. A poorly designed schema makes filtering, pagination, and metadata-based access control painful to retrofit.

    Start with the domain model: a document is a source artifact (a PDF, a web page, a support ticket). A chunk is a contiguous segment of text derived from that document, sized to fit within an embedding model's token window. The embedding lives on the chunk, not the document.

    -- PostgreSQL / pgvector
-- Enable the extension (run once per database)
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- for fallback fuzzy search
CREATE EXTENSION IF NOT EXISTS unaccent;  -- for text normalization

-- Source documents
CREATE TABLE documents (
    id              BIGSERIAL PRIMARY KEY,
    source_uri      TEXT NOT NULL,          -- s3://bucket/path, https://..., etc.
    title           TEXT,
    doc_type        TEXT NOT NULL,          -- 'pdf', 'html', 'ticket', 'confluence'
    tenant_id       UUID NOT NULL,          -- multi-tenant isolation
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    metadata        JSONB NOT NULL DEFAULT '{}'::jsonb,
    content_hash    TEXT NOT NULL,          -- SHA-256; skip re-ingestion if unchanged
    UNIQUE (source_uri, tenant_id)
);

-- Chunks derived from documents
CREATE TABLE document_chunks (
    id              BIGSERIAL PRIMARY KEY,
    document_id     BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    chunk_index     INT NOT NULL,           -- position within document
    chunk_text      TEXT NOT NULL,
    token_count     INT NOT NULL,
    embedding       vector(1536),           -- OpenAI text-embedding-3-small dimension
    embedding_model TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    tsvector_col    TSVECTOR               -- for hybrid BM25 + vector search
        GENERATED ALWAYS AS (to_tsvector('english', chunk_text)) STORED,
    UNIQUE (document_id, chunk_index)
);

-- Indexes
CREATE INDEX idx_chunks_tenant      ON document_chunks (tenant_id);
CREATE INDEX idx_chunks_document    ON document_chunks (document_id);
CREATE INDEX idx_chunks_tsvector    ON document_chunks USING GIN (tsvector_col);

-- HNSW index for vector search (build after bulk load for speed)
-- m=16 and ef_construction=64 are reasonable starting points;
-- increase ef_construction to 128 for higher recall at the cost of build time
CREATE INDEX idx_chunks_embedding_hnsw ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Retrieval audit log (optional but valuable for evals)
CREATE TABLE retrieval_log (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    query_text      TEXT NOT NULL,
    query_embedding vector(1536),
    top_k           INT NOT NULL,
    retrieved_ids   BIGINT[] NOT NULL,      -- chunk ids returned
    latency_ms      INT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

    Design decisions worth explaining:

  • → `tenant_id` on every table: RAG pipelines almost always serve multiple users or teams. Row-level security policies on `tenant_id` let you enforce isolation at the database layer rather than trusting the application.
  • → `content_hash` on documents: re-ingestion is expensive (embedding API calls cost money). Comparing hashes before ingesting lets you skip unchanged documents efficiently.
  • → `tsvector_col` as a generated column: this keeps BM25 search available without application-side maintenance. Hybrid search outperforms pure vector search on factual queries, particularly for named entities, product codes, and technical terms.
  • → HNSW over IVFFlat for most workloads: HNSW doesn't require a training step (`VACUUM` triggers a rebuild with IVFFlat), has better recall at the same query latency, and handles incremental inserts gracefully. IVFFlat's advantage is lower memory usage at very large scale (tens of millions of vectors).

    24.3 The Ingestion Pipeline

    Ingestion is a pipeline with four stages: load → chunk → embed → store. Each stage has failure modes worth designing for explicitly.

    # Python
# requirements: openai>=1.0, psycopg2-binary, tiktoken, langchain-text-splitters

import hashlib
import os
import time
from typing import Iterator

import openai
import psycopg2
import psycopg2.extras
import tiktoken
from langchain_text_splitters import RecursiveCharacterTextSplitter

# --- Configuration ---
DB_DSN = os.environ["PGVECTOR_DSN"]  # postgresql://user:pass@host:5432/ragdb
OPENAI_API_KEY = os.environ["OPENAI_API_KEY"]
EMBEDDING_MODEL = "text-embedding-3-small"
EMBEDDING_DIM = 1536
CHUNK_SIZE_TOKENS = 512
CHUNK_OVERLAP_TOKENS = 64
BATCH_SIZE = 100  # embeddings per API call; OpenAI limit is 2048 inputs

openai_client = openai.OpenAI(api_key=OPENAI_API_KEY)
tokenizer = tiktoken.encoding_for_model("text-embedding-3-small")


def count_tokens(text: str) -> int:
    return len(tokenizer.encode(text))


def chunk_document(text: str) -> list[str]:
    """
    RecursiveCharacterTextSplitter respects paragraph and sentence boundaries.
    We convert the token budget to approximate character counts using a
    rough 4-chars-per-token heuristic, then verify token counts after splitting.
    """
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=CHUNK_SIZE_TOKENS * 4,
        chunk_overlap=CHUNK_OVERLAP_TOKENS * 4,
        length_function=len,
        separators=["\n\n", "\n", ". ", " ", ""],
    )
    chunks = splitter.split_text(text)
    # Drop any chunks that exceed the model's 8192-token input limit
    return [c for c in chunks if count_tokens(c) <= 8000]


def embed_batch(texts: list[str]) -> list[list[float]]:
    """
    Embed a batch of texts. Implements simple exponential backoff on rate limits.
    Returns embeddings in the same order as inputs.
    """
    for attempt in range(5):
        try:
            response = openai_client.embeddings.create(
                model=EMBEDDING_MODEL,
                input=texts,
                encoding_format="float",
            )
            # The API guarantees ordering matches input
            return [item.embedding for item in sorted(response.data, key=lambda x: x.index)]
        except openai.RateLimitError:
            wait = 2 ** attempt
            print(f"Rate limited; retrying in {wait}s")
            time.sleep(wait)
    raise RuntimeError("Embedding API failed after 5 retries")


def ingest_document(
    conn,
    source_uri: str,
    title: str,
    doc_type: str,
    tenant_id: str,
    content: str,
    metadata: dict,
) -> int:
    """
    Ingest a single document. Returns the document_id.
    Skips re-ingestion if content hash is unchanged.
    """
    content_hash = hashlib.sha256(content.encode()).hexdigest()

    with conn.cursor() as cur:
        # Upsert the document record
        cur.execute(
            """
            INSERT INTO documents (source_uri, title, doc_type, tenant_id, metadata, content_hash)
            VALUES (%s, %s, %s, %s, %s, %s)
            ON CONFLICT (source_uri, tenant_id) DO UPDATE
                SET title        = EXCLUDED.title,
                    updated_at   = now(),
                    metadata     = EXCLUDED.metadata,
                    content_hash = EXCLUDED.content_hash
            RETURNING id,
                      (xmax = 0) AS is_insert,
                      (content_hash = EXCLUDED.content_hash) AS hash_unchanged
            """,
            (source_uri, title, doc_type, tenant_id,
             psycopg2.extras.Json(metadata), content_hash),
        )
        row = cur.fetchone()
        doc_id, is_insert, hash_unchanged = row

        if not is_insert and hash_unchanged:
            conn.rollback()
            print(f"Skipping {source_uri}: content unchanged")
            return doc_id

        # Delete stale chunks before re-ingesting
        if not is_insert:
            cur.execute("DELETE FROM document_chunks WHERE document_id = %s", (doc_id,))

        conn.commit()

    # --- Chunking ---
    chunks = chunk_document(content)
    print(f"Document {doc_id}: {len(chunks)} chunks")

    # --- Embed in batches, write rows ---
    with conn.cursor() as cur:
        for batch_start in range(0, len(chunks), BATCH_SIZE):
            batch_texts = chunks[batch_start : batch_start + BATCH_SIZE]
            embeddings = embed_batch(batch_texts)

            rows = [
                (
                    doc_id,
                    tenant_id,
                    batch_start + i,
                    text,
                    count_tokens(text),
                    embedding,
                    EMBEDDING_MODEL,
                )
                for i, (text, embedding) in enumerate(zip(batch_texts, embeddings))
            ]

            psycopg2.extras.execute_values(
                cur,
                """
                INSERT INTO document_chunks
                    (document_id, tenant_id, chunk_index, chunk_text,
                     token_count, embedding, embedding_model)
                VALUES %s
                """,
                rows,
                template="(%s, %s, %s, %s, %s, %s::vector, %s)",
                page_size=50,
            )

        conn.commit()

    return doc_id

    Production notes on ingestion:

  • → **Parallelism:** The bottleneck is embedding API calls, not Postgres writes. Run multiple worker processes (not threads—the GIL hurts here) against a connection pool. A four-worker setup with `BATCH_SIZE=100` can sustain roughly 400 embeddings/second before hitting OpenAI's default rate limits.
  • → **Idempotency:** The `content_hash` check ensures re-running the pipeline on the same document is a no-op. This is important for scheduled re-ingestion of updated document sets.
  • → **Index maintenance:** HNSW indexes on pgvector maintain themselves incrementally on insert, but recall degrades slightly as the index grows fragmented. Run `REINDEX INDEX CONCURRENTLY idx_chunks_embedding_hnsw` during low-traffic windows after large bulk loads.
  • → **Token budget:** The 512-token chunk size is a reasonable default for `text-embedding-3-small`. For GPT-4 with a 128k context window you can afford larger chunks (1024–2048 tokens) and thus fewer retrieval hops. Smaller chunks improve retrieval precision; larger chunks improve the coherence of context passed to the LLM.

    24.4 The Retrieval Layer

    Retrieval is where the database work happens. A basic retrieval function runs a vector similarity search; a production retrieval function also handles metadata filtering, multi-tenancy, hybrid search, and result deduplication.

    # Python
# requirements: openai, psycopg2-binary

from dataclasses import dataclass

import openai
import psycopg2
import psycopg2.extras


@dataclass
class RetrievedChunk:
    chunk_id: int
    document_id: int
    source_uri: str
    title: str
    chunk_text: str
    chunk_index: int
    similarity: float
    metadata: dict


def retrieve(
    conn,
    query: str,
    tenant_id: str,
    top_k: int = 6,
    doc_type_filter: str | None = None,
    min_similarity: float = 0.35,
    use_hybrid: bool = True,
    hybrid_weight: float = 0.7,  # weight for vector score; (1 - weight) for BM25
) -> list[RetrievedChunk]:
    """
    Retrieve top-k relevant chunks for a query.

    Hybrid mode: linear combination of cosine similarity (vector) and
    normalized ts_rank (BM25). Hybrid consistently outperforms pure vector
    search on factual/technical queries by 8–15% NDCG@10 in internal evals.

    min_similarity filters out chunks below a cosine similarity threshold,
    reducing hallucination risk from marginally relevant context.
    """
    # Embed the query using the same model as ingestion
    response = openai_client.embeddings.create(
        model=EMBEDDING_MODEL,
        input=[query],
        encoding_format="float",
    )
    query_embedding = response.data[0].embedding
    embedding_literal = f"[{','.join(str(x) for x in query_embedding)}]"

    doc_type_clause = "AND d.doc_type = %(doc_type)s" if doc_type_filter else ""

    if use_hybrid:
        sql = f"""
            WITH vector_scores AS (
                SELECT
                    c.id,
                    1 - (c.embedding <=> %(embedding)s::vector) AS vec_score
                FROM document_chunks c
                WHERE c.tenant_id = %(tenant_id)s
                  {doc_type_clause}
                ORDER BY c.embedding <=> %(embedding)s::vector
                LIMIT %(top_k_candidate)s
            ),
            bm25_scores AS (
                SELECT
                    c.id,
                    ts_rank_cd(c.tsvector_col, plainto_tsquery('english', %(query)s)) AS bm25_score
                FROM document_chunks c
                WHERE c.tenant_id = %(tenant_id)s
                  {doc_type_clause}
                  AND c.tsvector_col @@ plainto_tsquery('english', %(query)s)
            ),
            combined AS (
                SELECT
                    v.id,
                    (%(hw)s * v.vec_score) +
                    ((1 - %(hw)s) * COALESCE(
                        b.bm25_score / NULLIF(MAX(b.bm25_score) OVER (), 0),
                        0
                    )) AS combined_score,
                    v.vec_score
                FROM vector_scores v
                LEFT JOIN bm25_scores b ON b.id = v.id
            )
            SELECT
                c.id,
                c.document_id,
                d.source_uri,
                d.title,
                c.chunk_text,
                c.chunk_index,
                cm.combined_score AS similarity,
                d.metadata
            FROM combined cm
            JOIN document_chunks c  ON c.id = cm.id
            JOIN documents d        ON d.id = c.document_id
            WHERE cm.vec_score >= %(min_sim)s
            ORDER BY cm.combined_score DESC
            LIMIT %(top_k)s
        """
    else:
        sql = f"""
            SELECT
                c.id,
                c.document_id,
                d.source_uri,
                d.title,
                c.chunk_text,
                c.chunk_index,
                1 - (c.embedding <=> %(embedding)s::vector) AS similarity,
                d.metadata
            FROM document_chunks c
            JOIN documents d ON d.id = c.document_id
            WHERE c.tenant_id = %(tenant_id)s
              {doc_type_clause}
              AND 1 - (c.embedding <=> %(embedding)s::vector) >= %(min_sim)s
            ORDER BY c.embedding <=> %(embedding)s::vector
            LIMIT %(top_k)s
        """

    params = {
        "embedding": embedding_literal,
        "tenant_id": tenant_id,
        "query": query,
        "top_k": top_k,
        "top_k_candidate": top_k * 5,  # over-fetch for hybrid reranking
        "min_sim": min_similarity,
        "hw": hybrid_weight,
        "doc_type": doc_type_filter,
    }

    with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
        cur.execute(sql, params)
        rows = cur.fetchall()

    return [
        RetrievedChunk(
            chunk_id=row["id"],
            document_id=row["document_id"],
            source_uri=row["source_uri"],
            title=row["title"] or "",
            chunk_text=row["chunk_text"],
            chunk_index=row["chunk_index"],
            similarity=float(row["similarity"]),
            metadata=row["metadata"],
        )
        for row in rows
    ]

    Tuning ef_search at query time: pgvector's HNSW index respects a session-level parameter hnsw.ef_search (default 40). Higher values improve recall at the cost of query latency.

    -- PostgreSQL / pgvector
-- Measure baseline recall vs. latency tradeoff
-- Run this against a test set of queries with known relevant chunks

SET hnsw.ef_search = 40;   -- default; ~2–4ms per query at 1M vectors

FROM document_chunks

LIMIT 10;

SET hnsw.ef_search = 100;  -- higher recall; ~6–10ms per query

-- Use ef_search = 40–60 for interactive (<50ms) workloads

    The min_similarity threshold: 0.35 cosine similarity is a reasonable starting point for text-embedding-3-small. Below that, retrieved chunks tend to be topically adjacent rather than directly relevant, and passing them to the LLM increases hallucination risk. Calibrate this threshold against your specific domain using an evaluation set—technical documentation typically needs 0.40+, while general Q&A can tolerate 0.30.

    24.5 LLM Integration and Prompt Assembly

    With a retrieval function in place, prompt assembly is the next design decision. The quality of the prompt structure affects answer quality more than almost any other variable in a RAG system.

    # Python
# requirements: openai, psycopg2-binary

import json
from typing import Any

# Reuse openai_client, retrieve() from prior sections


def build_rag_prompt(
    query: str,
    chunks: list[RetrievedChunk],
    system_instruction: str | None = None,
) -> list[dict]:
    """
    Assemble an OpenAI chat messages array for RAG.

    Key decisions:
    - Context comes before the question (reduces "lost in the middle" effect)
    - Each chunk is labeled with its source for citation
    - Explicit instructions prevent hallucination when context is insufficient
    """
    if system_instruction is None:
        system_instruction = (
            "You are a helpful assistant. Answer questions using ONLY the provided context. "
            "If the context does not contain enough information to answer the question, "
            "say 'I don't have enough information to answer that.' "
            "Cite the source document for each claim using [Source: <title>] notation."
        )

    # Deduplicate chunks from the same document that are consecutive
    # (consecutive chunks from the same document often repeat context)
    deduped_chunks = []
    seen_texts = set()
    for chunk in chunks:
        # Normalize whitespace before dedup check
        normalized = " ".join(chunk.chunk_text.split())
        if normalized not in seen_texts:
            seen_texts.add(normalized)
            deduped_chunks.append(chunk)

    # Build the context block
    context_parts = []
    for i, chunk in enumerate(deduped_chunks):
        source_label = chunk.title or chunk.source_uri
        context_parts.append(
            f"[{i+1}] Source: {source_label}\n{chunk.chunk_text.strip()}"
        )
    context_block = "\n\n---\n\n".join(context_parts)

    messages = [
        {"role": "system", "content": system_instruction},
        {
            "role": "user",
            "content": (
                f"Context:\n\n{context_block}\n\n"
                f"---\n\nQuestion: {query}"
            ),
        },
    ]
    return messages


def rag_query(
    conn,
    query: str,
    tenant_id: str,
    top_k: int = 6,
    doc_type_filter: str | None = None,
    llm_model: str = "gpt-4o-mini",
    temperature: float = 0.0,
    max_tokens: int = 1024,
    stream: bool = False,
) -> dict[str, Any]:
    """
    End-to-end RAG query: retrieve → assemble prompt → generate.

    Returns a dict with 'answer', 'sources', and 'chunks' for downstream use.
    Setting temperature=0.0 maximizes determinism for factual Q&A.
    """
    # --- Retrieval ---
    chunks = retrieve(
        conn,
        query=query,
        tenant_id=tenant_id,
        top_k=top_k,
        doc_type_filter=doc_type_filter,
    )

    if not chunks:
        return {
            "answer": "I don't have enough information to answer that.",
            "sources": [],
            "chunks": [],
        }

    # --- Prompt assembly ---
    messages = build_rag_prompt(query, chunks)

    # --- Generation ---
    if stream:
        # For streaming responses (e.g., websocket or SSE endpoints)
        response_stream = openai_client.chat.completions.create(
            model=llm_model,
            messages=messages,
            temperature=temperature,
            max_tokens=max_tokens,
            stream=True,
        )
        # Caller handles the stream iterator; return it with metadata
        return {
            "answer_stream": response_stream,
            "sources": [c.source_uri for c in chunks],
            "chunks": chunks,
        }

    response = openai_client.chat.completions.create(
        model=llm_model,
        messages=messages,
        temperature=temperature,
        max_tokens=max_tokens,
    )

    answer = response.choices[0].message.content

    return {
        "answer": answer,
        "sources": list({c.source_uri for c in chunks}),  # deduplicated
        "chunks": chunks,
        "usage": {
            "prompt_tokens": response.usage.prompt_tokens,
            "completion_tokens": response.usage.completion_tokens,
        },
    }

    Prompt design choices that matter:

  • → **Context before question:** Research on LLM attention patterns consistently shows that content near the beginning and end of a long prompt receives more "attention" than content in the middle. Placing context before the question keeps the question close to the end where the model generates, reducing the "lost in the middle" degradation.
  • → **Explicit no-answer instruction:** Without explicit instruction, LLMs tend to confabulate answers when retrieved context is insufficient. The phrase "say I don't have enough information" dramatically reduces hallucinations on out-of-scope queries.
  • → **Citation notation:** Requiring `[Source: ]` in the output gives downstream systems and users a signal to verify claims. It also makes evaluation easier—you can check whether cited sources actually appear in the retrieved context.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> **Temperature = 0.0 for factual Q&A:** For RAG over enterprise documents (policies, technical manuals, support articles), determinism is more valuable than creativity. Reserve higher temperatures for generative tasks like summarization or drafting.</li> <p class="text-gray-300 leading-relaxed">---</p> <h3 class="text-lg font-semibold text-white mt-8 mb-3">24.6 Multi-Tenancy and Row-Level Security</h3> <p class="text-gray-300 leading-relaxed">A production RAG system almost always serves multiple tenants. PostgreSQL Row-Level Security (RLS) lets you enforce tenant isolation at the database layer, which is safer than relying solely on <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">WHERE tenant_id = ?</code> clauses in application code.</p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL -- Enable RLS on the chunks table ALTER TABLE document_chunks ENABLE ROW LEVEL SECURITY; ALTER TABLE documents ENABLE ROW LEVEL SECURITY; -- Create a policy: each application role can only see its own tenant's rows. -- The application sets the current tenant via a session variable. CREATE POLICY tenant_isolation_chunks ON document_chunks USING (tenant_id = current_setting('app.current_tenant_id')::uuid); CREATE POLICY tenant_isolation_documents ON documents USING (tenant_id = current_setting('app.current_tenant_id')::uuid); -- Create a restricted application role that cannot bypass RLS CREATE ROLE rag_app_role LOGIN PASSWORD 'strong-password-here'; GRANT SELECT, INSERT, UPDATE, DELETE ON document_chunks TO rag_app_role; GRANT SELECT, INSERT, UPDATE, DELETE ON documents TO rag_app_role; GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO rag_app_role; -- Note: superusers and table owners bypass RLS by default. -- Force RLS even for table owner if needed: ALTER TABLE document_chunks FORCE ROW LEVEL SECURITY; ALTER TABLE documents FORCE ROW LEVEL SECURITY;</code></pre> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code># Python # Activate tenant context in the connection before any query def set_tenant_context(conn, tenant_id: str) -> None: """ Set the tenant_id session variable for RLS enforcement. Call this immediately after acquiring a connection from the pool. Validate that tenant_id is a valid UUID before passing to avoid injection. """ import uuid # Validate UUID format to prevent injection via session variable uuid.UUID(tenant_id) # raises ValueError if malformed with conn.cursor() as cur: cur.execute( "SELECT set_config('app.current_tenant_id', %s, false)", (tenant_id,), ) conn.commit() # Usage pattern with a connection pool (psycopg2 + psycopg2-pool) from psycopg2 import pool as pg_pool connection_pool = pg_pool.ThreadedConnectionPool( minconn=2, maxconn=20, dsn=DB_DSN, ) def get_tenant_conn(tenant_id: str): """Context manager: acquire connection, set tenant, release on exit.""" conn = connection_pool.getconn() try: set_tenant_context(conn, tenant_id) yield conn finally: connection_pool.putconn(conn)</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">RLS caveats:</strong></p> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> `set_config(..., false)` makes the setting local to the current transaction. If your connection pool reuses connections across tenants (which it will), always set the tenant context at the start of each request, not at connection creation time.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> `set_config(..., true)` would make the setting local to the current session, which is wrong for pooled connections—the value persists across requests from different tenants on the same connection.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> HNSW index scans with RLS applied can show higher latency than without RLS, because the planner must apply the predicate after the ANN scan. Ensure `tenant_id` is included as a leading column in any composite indexes, and test `EXPLAIN ANALYZE` output with RLS enabled in your load test environment.</li> <p class="text-gray-300 leading-relaxed">---</p> <h3 class="text-lg font-semibold text-white mt-8 mb-3">24.7 Evaluation: Knowing Whether Your RAG Pipeline Works</h3> <p class="text-gray-300 leading-relaxed">A RAG pipeline that returns *something* is easy to build. A RAG pipeline that returns *correct, grounded, relevant* answers requires systematic evaluation. Database professionals are well-positioned to reason about this: evaluation is fundamentally a join between ground truth and predictions.</p> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Three metrics to track from day one:</strong></p> <p class="text-gray-300 leading-relaxed">| Metric | What it measures | How to compute |</p> <p class="text-gray-300 leading-relaxed">|---|---|---|</p> <p class="text-gray-300 leading-relaxed">| Retrieval Recall@K | Are the truly relevant chunks in the top K results? | Compare retrieved IDs against a human-labeled relevance set |</p> <p class="text-gray-300 leading-relaxed">| Answer Faithfulness | Does the answer only contain claims supported by context? | LLM-as-judge or NLI model scoring |</p> <p class="text-gray-300 leading-relaxed">| Answer Relevance | Does the answer address the question? | LLM-as-judge or human rating |</p> <p class="text-gray-300 leading-relaxed">A minimal evaluation harness using the retrieval log table:</p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL -- Evaluation query: for a labeled test set, compute recall@K -- Assume a table: eval_set(query_id, query_text, relevant_chunk_ids bigint[]) -- And retrieval_log has been populated with results for each eval query WITH eval_results AS ( SELECT e.query_id, e.relevant_chunk_ids, r.retrieved_ids, -- Count how many relevant chunks appear in retrieved_ids ( SELECT COUNT(*) FROM unnest(e.relevant_chunk_ids) AS rel(id) WHERE rel.id = ANY(r.retrieved_ids) ) AS hits, array_length(e.relevant_chunk_ids, 1) AS total_relevant FROM eval_set e JOIN retrieval_log r ON r.query_text = e.query_text WHERE r.created_at > now() - interval '24 hours' ) SELECT AVG(hits::float / NULLIF(total_relevant, 0)) AS recall_at_k, AVG(hits::float / NULLIF(array_length(retrieved_ids, 1), 0)) AS precision_at_k, COUNT(*) AS eval_queries FROM eval_results;</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">LLM-as-judge faithfulness check (Python):</strong></p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code># Python def evaluate_faithfulness( query: str, context_chunks: list[RetrievedChunk], answer: str, ) -> dict: """ Ask the LLM to judge whether every claim in the answer is supported by the provided context. Returns a structured score. """ context_text = "\n\n".join(c.chunk_text for c in context_chunks) judge_prompt = [ { "role": "system", "content": ( "You are an evaluator. Your task is to assess whether an AI-generated " "answer is fully grounded in the provided context. " "Respond with JSON: {\"faithful\": true/false, \"unsupported_claims\": [...]}" ), }, { "role": "user", "content": ( f"Context:\n{context_text}\n\n" f"Question: {query}\n\n" f"Answer: {answer}\n\n" "Is every claim in the answer supported by the context?" ), }, ] response = openai_client.chat.completions.create( model="gpt-4o-mini", messages=judge_prompt, temperature=0.0, response_format={"type": "json_object"}, ) return json.loads(response.choices[0].message.content)</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Connecting evaluation to schema evolution:</strong> When you upgrade embedding models (e.g., from <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">text-embedding-3-small</code> to <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">text-embedding-3-large</code>), store both embeddings in separate columns during the transition period and run your eval set against both. This gives you an empirical recall delta before committing to a re-ingestion of the full corpus—which can be expensive at scale.</p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL -- Dual-embedding schema for model migration evaluation ALTER TABLE document_chunks ADD COLUMN embedding_large vector(3072); -- text-embedding-3-large dim CREATE INDEX idx_chunks_embedding_large_hnsw ON document_chunks USING hnsw (embedding_large vector_cosine_ops) WITH (m = 16, ef_construction = 64); -- After evaluating both models, drop the old column: -- ALTER TABLE document_chunks DROP COLUMN embedding; -- ALTER TABLE document_chunks RENAME COLUMN embedding_large TO embedding;</code></pre> <p class="text-gray-300 leading-relaxed">---</p> <h3 class="text-lg font-semibold text-white mt-8 mb-3">24.8 Production Patterns and Operational Checklist</h3> <p class="text-gray-300 leading-relaxed">Building a RAG demo takes hours. Making it production-ready takes weeks. This section distills the operational concerns that most commonly cause production incidents.</p> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Connection pooling:</strong> pgvector queries hold connections for the duration of the ANN scan plus the embedding API call latency. At even moderate concurrency (20–50 users), a naive connection-per-request model will exhaust <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">max_connections</code>. Use PgBouncer in transaction mode, or asyncpg + asyncio for async connection management. Set the pool size to roughly 2–3× the number of CPU cores on your PostgreSQL instance.</p> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Index health monitoring:</strong></p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL -- Monitor HNSW index size and fragmentation SELECT schemaname, tablename, indexname, pg_size_pretty(pg_relation_size(indexrelid)) AS index_size, idx_scan, idx_tup_read, idx_tup_fetch FROM pg_stat_user_indexes WHERE indexname LIKE '%hnsw%'; -- Check for sequential scans (may indicate index is not being used) SELECT relname, seq_scan, seq_tup_read, idx_scan FROM pg_stat_user_tables WHERE relname = 'document_chunks';</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Autovacuum configuration for high-write tables:</strong> Chunk tables under active ingestion accumulate dead tuples quickly. Tighten autovacuum for the <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">document_chunks</code> table:</p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL ALTER TABLE document_chunks SET ( autovacuum_vacuum_scale_factor = 0.01, -- vacuum when 1% of table is dead tuples autovacuum_analyze_scale_factor = 0.005, autovacuum_vacuum_cost_delay = 2 -- reduce I/O throttling for this table );</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Query timeout safeguards:</strong> An ANN scan over a large unindexed partition, or one where the HNSW index is temporarily unavailable, can run for many seconds. Set statement timeouts at the role level:</p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL ALTER ROLE rag_app_role SET statement_timeout = '5000ms'; -- 5 seconds max per query ALTER ROLE rag_app_role SET lock_timeout = '1000ms';</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Embedding model version locking:</strong> Pin the exact embedding model version in your application configuration and store it in the <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">embedding_model</code> column. OpenAI periodically updates model internals even under the same model name slug. Embeddings from different model versions are not comparable—mixing them silently degrades retrieval quality without any error signal.</p> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Observability schema:</strong></p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL -- Extend retrieval_log for operational monitoring ALTER TABLE retrieval_log ADD COLUMN llm_model TEXT, ADD COLUMN prompt_tokens INT, ADD COLUMN completion_tokens INT, ADD COLUMN faithfulness_score FLOAT, -- from LLM-as-judge eval ADD COLUMN answer_text TEXT, -- store answers for offline eval ADD COLUMN user_feedback SMALLINT; -- thumbs up/down: 1 / -1 / NULL -- Aggregate dashboard query SELECT date_trunc('hour', created_at) AS hour, COUNT(*) AS total_queries, AVG(latency_ms) AS avg_latency_ms, PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY latency_ms) AS p95_latency_ms, AVG(faithfulness_score) AS avg_faithfulness, SUM(CASE WHEN user_feedback = 1 THEN 1 ELSE 0 END)::float / NULLIF(COUNT(user_feedback), 0) AS thumbs_up_rate FROM retrieval_log WHERE created_at > now() - interval '7 days' GROUP BY 1 ORDER BY 1 DESC;</code></pre> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Backup and point-in-time recovery:</strong> Vector indexes are not included in logical backups (<code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">pg_dump</code> exports the index definition but not the index data structure; the index is rebuilt on restore). For pgvector HNSW indexes on large tables, index rebuild time after a restore can be significant—test this in your DR runbook. Physical backups (pg_basebackup, WAL archiving) capture index files and are preferred for large vector tables.</p> <p class="text-gray-300 leading-relaxed"><strong class="text-white">Scaling beyond a single PostgreSQL instance:</strong> When a single Postgres node is no longer sufficient—either due to write throughput from ingestion or read throughput from retrieval—the standard playbook applies: read replicas for retrieval queries, partitioning <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">document_chunks</code> by <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">tenant_id</code> (using <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">PARTITION BY HASH</code>) to distribute data across tablespaces, and eventually Citus for horizontal sharding if the dataset reaches hundreds of millions of vectors.</p> <pre class="bg-gray-900 border border-gray-800 rounded-xl p-5 text-xs text-gray-300 overflow-x-auto my-5"><code>-- PostgreSQL -- Hash-partition document_chunks by tenant for large multi-tenant deployments CREATE TABLE document_chunks ( -- same column definitions as before ) PARTITION BY HASH (tenant_id); CREATE TABLE document_chunks_p0 PARTITION OF document_chunks FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE document_chunks_p1 PARTITION OF document_chunks FOR VALUES WITH (MODULUS 4, REMAINDER 1); CREATE TABLE document_chunks_p2 PARTITION OF document_chunks FOR VALUES WITH (MODULUS 4, REMAINDER 2); CREATE TABLE document_chunks_p3 PARTITION OF document_chunks FOR VALUES WITH (MODULUS 4, REMAINDER 3); -- HNSW indexes must be created per partition CREATE INDEX ON document_chunks_p0 USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); CREATE INDEX ON document_chunks_p1 USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); CREATE INDEX ON document_chunks_p2 USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64); CREATE INDEX ON document_chunks_p3 USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);</code></pre> <p class="text-gray-300 leading-relaxed">This partitioning strategy keeps per-partition HNSW index sizes manageable and allows partition pruning when a query includes a <code class="bg-gray-800 px-1.5 py-0.5 rounded text-blue-300 text-xs">tenant_id</code> filter—which every well-formed RAG query should.</p> <p class="text-gray-300 leading-relaxed">---</p> <h3 class="text-lg font-semibold text-white mt-8 mb-3">Key Takeaways</h3> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> **RAG is a query architecture problem.** The database's job is to serve relevant document chunks fast and safely; the LLM's job is to synthesize them into language. Keeping these responsibilities separate simplifies both design and debugging.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> **Schema foundations matter disproportionately.** Multi-tenant isolation via `tenant_id` and row-level security, content hashing for idempotent ingestion, and a generated `tsvector` column for hybrid search are all much cheaper to add at design time than to retrofit into a live system.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> **Hybrid search (vector + BM25) outperforms pure vector search** on factual and technical queries. The `tsvector` generated column plus `plainto_tsquery` gives you BM25 in pure SQL with no additional infrastructure.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> **Evaluation must be systematic from the start.** Logging queries, retrieved chunk IDs, latencies, and LLM outputs into a `retrieval_log` table gives you the raw material for recall, faithfulness, and relevance metrics—and makes model and prompt changes measurable rather than speculative.</li> <li class="flex gap-2 text-gray-300"><span class="text-blue-400">→</span> **Operational discipline separates demos from production systems.** Connection pool sizing, autovacuum tuning for high-write chunk tables, statement timeouts, HNSW index health monitoring, and physical backups that include index files are all table-stakes requirements before going live with a pgvector RAG pipeline.</li> </div> <div class="mt-14 bg-cyan-950/40 border border-cyan-800/40 rounded-2xl p-6 flex flex-col md:flex-row items-center gap-5"> <div class="flex-1"> <p class="font-semibold text-white mb-1">QueryOptimizer — Self-Hosted SQL Performance Workbench</p> <p class="text-xs text-gray-400">EXPLAIN visualizer · Index advisor · Slow query dashboard · PostgreSQL + SQL Server</p> </div> <a href="https://rajeshguntupalli59.github.io/query-optimizer/" class="shrink-0 px-6 py-3 bg-cyan-600 hover:bg-cyan-500 text-white font-semibold rounded-xl text-sm transition"> Download Free </a> </div> <div class="mt-8 text-xs"> <a href="index.html" class="text-gray-500 hover:text-gray-300 transition">← All Chapters</a> </div> </article> <footer class="border-t border-gray-800/50 px-6 py-8"> <div class="max-w-5xl mx-auto text-xs text-gray-600 text-center">© 2026 Rajesh Guntupalli · Vector Databases & AI</div> </footer> </body> </html>
