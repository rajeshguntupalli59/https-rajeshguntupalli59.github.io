Chapter 20: AlloyDB: PostgreSQL-Compatible with ML Built In

Google's AlloyDB for PostgreSQL is not simply a managed PostgreSQL service with a different logo. It is a ground-up reimagining of the PostgreSQL storage engine — wire-compatible with PostgreSQL 14 and 15, but architecturally closer to Aurora in its separation of compute and storage, and unlike any other managed PostgreSQL offering in its native integration of machine learning inference directly at the query layer. For production DBAs who have spent years tuning autovacuum, managing WAL pressure, and hand-crafting connection pools, AlloyDB represents a shift in what the database engine itself takes responsibility for. This chapter covers how AlloyDB's columnar engine, memory-optimized storage, and ML inference extensions work in practice, how to provision and connect clusters, how to migrate existing PostgreSQL workloads, and where AlloyDB genuinely outperforms Cloud SQL for PostgreSQL and where it falls short in ways that will surprise you.

---

20.1 Architecture: What AlloyDB Actually Is Under the Hood

If you are coming from self-managed PostgreSQL, you understand the storage hierarchy: the buffer pool in shared memory, heap files on disk, WAL on a separate spindle if you are careful, and the constant negotiation between autovacuum and your OLTP workload. AlloyDB dismantles this hierarchy and reassembles it differently.

Disaggregated Storage

AlloyDB separates the primary instance compute from a distributed storage layer, similar to Aurora's approach. The storage layer — Google calls it the *Log Store* — receives and durably replicates WAL records across multiple zones before acknowledging writes; consult current AlloyDB documentation for the exact replica topology in your region. The primary instance never writes heap files directly to local disk. Instead, background storage nodes apply WAL to materialized heap pages asynchronously. This means your primary is doing dramatically less I/O work than a traditional PostgreSQL primary, and crash recovery does not require replaying hours of WAL — the storage layer maintains consistent page state independently.

What this means for you operationally:

  • → **Checkpoint pressure disappears.** In self-managed PostgreSQL, tuning `checkpoint_completion_target`, `max_wal_size`, and `checkpoint_timeout` is a ritual. In AlloyDB, checkpoints still exist in the PostgreSQL code path, but their I/O impact on the primary is negligible because no dirty pages are being flushed to local disk in the traditional sense.
  • → **Read replicas are fast to provision.** A read replica in AlloyDB attaches to the same storage layer — it does not stream WAL and rebuild a base backup. A new replica is queryable in seconds to minutes, not hours.
  • → **Replication lag behaves differently.** Because replicas read from the shared storage layer rather than applying streamed WAL, replication lag is reported differently than `pg_stat_replication.replay_lag`. AlloyDB exposes this through its own metrics, and you need to retrain your intuition about what "lag" means.

    *AlloyDB's disaggregated architecture: compute instances hold only cache layers (buffer pool + NVMe); durable page state lives in the shared Log Store, which is why new read pool instances attach in seconds rather than rebuilding from a base backup.*

    The Ultra-Fast Shared Memory Cache

    AlloyDB introduces a tiered memory architecture: beyond the standard PostgreSQL shared_buffers, it maintains a second layer called the *ultra-fast cache* built on local NVMe SSD attached to each instance. This cache survives instance restarts because it is backed by NVMe rather than DRAM. When a page is evicted from shared_buffers, it goes to this NVMe cache before it goes back to the distributed storage layer. The practical implication: your read-heavy workloads that overflow shared_buffers do not pay remote storage latency on every cache miss — NVMe latency is meaningfully lower than a round trip to the distributed storage layer, though exact figures depend on instance type and should be measured against your own workload rather than assumed.

    In sizing terms, shared_buffers in AlloyDB is set automatically based on instance size and is not a parameter you directly tune in the same way, with the NVMe cache providing another layer below it.

    The Columnar Engine

    AlloyDB includes an optional columnar engine — a PostgreSQL foreign data wrapper-style extension that maintains a compressed, columnar representation of tables or table partitions in memory. When a query contains analytical predicates (range scans, aggregations, GROUP BY) that the query planner identifies as benefiting from columnar access, it routes those operations through the columnar engine transparently. You write standard SQL; the planner decides.

    This is meaningful because it means you can run mixed OLTP and analytical workloads on the same AlloyDB cluster without physically separating your data into a separate OLAP store. The columnar engine is not a replacement for BigQuery or a data warehouse at scale — but for the DBA who has been maintaining a separate reporting replica just to run month-end aggregates without killing the OLTP primary, it is a serious operational simplification.

    Enabling the columnar engine on a table:

    -- Enable the AlloyDB columnar engine extension
-- This is typically already installed in AlloyDB clusters
SHOW alloydb_enable_columnar_engine;

-- Enable columnar engine for a specific table
ALTER TABLE orders SET (columnar_engine = 'on');

-- You can also enable it for specific columns or let AlloyDB auto-select
-- Check what the auto-columnarization has selected
SELECT *
FROM google_columnar_engine_recommended_tables()
ORDER BY estimated_memory_mb DESC;

-- View current columnar engine population status
SELECT table_name,
       status,
       rows_count,
       size_in_bytes
FROM google_columnar_engine_tables;

    The google_columnar_engine_recommended_tables() function is one of AlloyDB's genuinely useful operational functions — it analyzes your query workload and recommends which tables will benefit most from columnarization, with estimated memory requirements. Treat this output as advisory; validate with EXPLAIN (ANALYZE, BUFFERS) before and after.

    20.2 Provisioning AlloyDB Clusters and Instances

    AlloyDB uses a two-tier model: a *cluster* and *instances within that cluster*. The cluster defines the regional boundary, the VPC network, and the storage configuration. Instances are the PostgreSQL compute endpoints — a primary instance and optionally one or more read pool instances.

    Provisioning with gcloud

    # Set your project and region
gcloud config set project your-gcp-project-id
gcloud config set compute/region us-central1

# Create an AlloyDB cluster
# This provisions the storage layer — no compute yet
gcloud alloydb clusters create prod-alloydb-cluster \
  --region=us-central1 \
  --network=projects/your-gcp-project-id/global/networks/prod-vpc \
  --password=your-initial-password \
  --database-version=POSTGRES_15

# Create the primary instance
# machine-type options: db-n1-standard-2, db-n1-highmem-8, db-n1-highmem-32, etc.
gcloud alloydb instances create prod-primary \
  --cluster=prod-alloydb-cluster \
  --region=us-central1 \
  --instance-type=PRIMARY \
  --cpu-count=8 \
  --no-assign-inbound-public-ip

# Create a read pool instance (for read scaling and analytics)
# Read pools in AlloyDB are groups of nodes — min 2 for HA
gcloud alloydb instances create prod-read-pool \
  --cluster=prod-alloydb-cluster \
  --region=us-central1 \
  --instance-type=READ_POOL \
  --cpu-count=8 \
  --read-pool-node-count=2 \
  --no-assign-inbound-public-ip

# Verify both instances are READY
gcloud alloydb instances list \
  --cluster=prod-alloydb-cluster \
  --region=us-central1

    Connection Topology

    AlloyDB does not expose a CNAME-based endpoint the way Aurora does. Connection is always by private IP within your VPC. There is no AlloyDB equivalent of RDS Proxy built into the service — you bring your own connection pooler, and PgBouncer running on a GCE instance or Cloud Run is the standard pattern. If you are coming from Aurora, this is a gap you will feel immediately. The AlloyDB Auth Proxy handles IAM authentication and SSL termination and is the recommended client-side component:

    # Download and run the AlloyDB Auth Proxy
# This is the equivalent of Cloud SQL Auth Proxy — same pattern, different binary

wget https://storage.googleapis.com/alloydb-auth-proxy/v1.x.x/alloydb-auth-proxy.linux.amd64 \
  -O alloydb-auth-proxy
chmod +x alloydb-auth-proxy

# Run the proxy — it listens on localhost:5432 and handles IAM auth
./alloydb-auth-proxy \
  "projects/your-project/locations/us-central1/clusters/prod-alloydb-cluster/instances/prod-primary" \
  --port=5432 \
  --credentials-file=/path/to/service-account.json

# Application connection string then becomes:
# host=127.0.0.1 port=5432 dbname=mydb user=iam_service_account sslmode=disable
# SSL is handled by the proxy — disable in the client connection string

    The AlloyDB Auth Proxy terminates SSL and handles token refresh automatically, which means your application connection strings do not embed database passwords. Instead, the service account identity determines access. This is the same pattern you used with Cloud SQL Auth Proxy if you have worked with Cloud SQL before.

    20.3 IAM Authentication and Access Control

    In self-managed PostgreSQL, pg_hba.conf is your access control boundary. You define which hosts can connect, which users, and which authentication method — md5, scram-sha-256, cert, ldap. In AlloyDB, the network boundary is your VPC (enforced at the infrastructure level), and authentication has two modes: native PostgreSQL password authentication and IAM-based authentication.

    IAM authentication in AlloyDB works similarly to Cloud SQL's IAM auth. A Google identity — a service account or a user account — is mapped to a PostgreSQL role. The IAM-authenticated connection uses a short-lived OAuth2 token as the password, which the AlloyDB Auth Proxy or the alloydb_pg_iam_authn extension handles.

    Setting Up IAM Authentication

    # Grant IAM user or service account the AlloyDB Client role
# This is the network-level permission — required before database-level grants
gcloud projects add-iam-policy-binding your-gcp-project-id \
  --member="serviceAccount:app-service-account@your-project.iam.gserviceaccount.com" \
  --role="roles/alloydb.client"

# For IAM database authentication specifically:
gcloud projects add-iam-policy-binding your-gcp-project-id \
  --member="serviceAccount:app-service-account@your-project.iam.gserviceaccount.com" \
  --role="roles/alloydb.databaseUser"
    -- Inside the AlloyDB instance, create the IAM-mapped PostgreSQL role
-- The username format for service accounts: strip @project.iam.gserviceaccount.com
-- For user accounts: the full email address

-- Create the PostgreSQL role corresponding to the IAM service account
CREATE USER "app-service-account@your-project.iam" WITH LOGIN;

-- Grant appropriate database permissions
GRANT CONNECT ON DATABASE production TO "app-service-account@your-project.iam";
GRANT USAGE ON SCHEMA public TO "app-service-account@your-project.iam";
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public
  TO "app-service-account@your-project.iam";

-- For future tables:
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES
  TO "app-service-account@your-project.iam";

-- Verify the role exists and has the right attributes
SELECT rolname, rolcanlogin, rolsuper, rolcreatedb
FROM pg_roles
WHERE rolname LIKE '%iam%';

    What You Cannot Do That You Could in Self-Managed PostgreSQL

    The pg_hba.conf comparison is instructive here. In self-managed PostgreSQL, you can define rules like:

    # Allow cert auth from specific CIDR, reject everything else
hostssl all all 10.0.0.0/8 cert
host    all all all        reject

    In AlloyDB, your network-level controls are VPC firewall rules and Private Service Connect configuration — you cannot write arbitrary pg_hba.conf entries. AlloyDB manages its own pg_hba.conf internally. You can enable or disable IAM authentication at the cluster level, and you can require SSL (which is on by default), but fine-grained auth method selection per CIDR range or per database is not exposed. This is a real constraint for organizations that use client certificate authentication today.

    Connection from Python Using IAM Token

    import google.auth
import google.auth.transport.requests
import psycopg2
from google.oauth2 import service_account

def get_alloydb_connection_iam(
    host: str,
    database: str,
    iam_user: str,
    service_account_file: str
) -> psycopg2.extensions.connection:
    """
    Connect to AlloyDB using IAM authentication.
    The AlloyDB Auth Proxy must be running, or use direct IP with SSL.
    For proxy connections, host is 127.0.0.1 and no SSL needed at client level.
    """
    credentials = service_account.Credentials.from_service_account_file(
        service_account_file,
        scopes=["https://www.googleapis.com/auth/cloud-platform"]
    )

    # Refresh to get a current token
    auth_request = google.auth.transport.requests.Request()
    credentials.refresh(auth_request)

    # The OAuth2 token is used as the password
    token = credentials.token

    conn = psycopg2.connect(
        host=host,
        port=5432,
        database=database,
        user=iam_user,  # e.g., "app-service-account@your-project.iam"
        password=token,
        sslmode="disable"  # SSL handled by Auth Proxy
    )

    return conn

def run_query_with_retry(host: str, database: str, query: str) -> list:
    """
    Production pattern: IAM tokens expire in 1 hour.
    Use a connection factory that refreshes tokens on reconnect.
    """
    import time

    max_retries = 3
    for attempt in range(max_retries):
        try:
            conn = get_alloydb_connection_iam(
                host=host,
                database=database,
                iam_user="app-service-account@your-project.iam",
                service_account_file="/etc/secrets/sa-key.json"
            )
            with conn.cursor() as cur:
                cur.execute(query)
                results = cur.fetchall()
            conn.close()
            return results

        except psycopg2.OperationalError as e:
            if attempt < max_retries - 1:
                time.sleep(2 ** attempt)  # Exponential backoff
                continue
            raise

    return []

    The token expiry behavior is something that catches people coming from password-based PostgreSQL connections. A long-lived connection established with an IAM token does not get disconnected when the token expires — but any new connection attempt after the token expires will fail. PgBouncer in transaction pooling mode mitigates this because connections are returned to the pool and reestablished regularly, but you need to wire the token refresh into your connection factory, not just your startup code.

    20.4 ML Inference with `google_ml_integration`

    This is where AlloyDB genuinely has no equivalent in Aurora, Azure SQL, or Cloud SQL for PostgreSQL. AlloyDB includes a built-in extension called google_ml_integration that allows you to call Vertex AI hosted models directly from SQL, with the model call executing as a PostgreSQL function. The ML inference runs server-side, in the database tier, without your application code needing to orchestrate a round trip to Vertex AI.

    The practical use cases for DBAs are:

  • → **Text embedding generation** at insert time, stored as `vector` columns (AlloyDB natively supports `pgvector`)
  • → **Classification and scoring** within a query, avoiding application-side ML overhead
  • → **Semantic search** using vector similarity within standard SQL queries

    • Enabling the ML Integration Extension

    -- Enable the extension (requires superuser or alloydbsuperuser role)
CREATE EXTENSION IF NOT EXISTS google_ml_integration CASCADE;

-- Verify installation
SELECT extname, extversion
FROM pg_extension
WHERE extname IN ('google_ml_integration', 'vector');

-- Grant usage to application roles
GRANT EXECUTE ON FUNCTION embedding(text, text) TO app_role;
GRANT EXECUTE ON FUNCTION ml_predict_row(text, jsonb) TO app_role;
    # Before calling Vertex AI from AlloyDB, the AlloyDB service account
# needs permission to invoke the Vertex AI API
# Get your AlloyDB service account
gcloud alloydb clusters describe prod-alloydb-cluster \
  --region=us-central1 \
  --format="value(serviceAccountEmailAddress)"

# Grant the Vertex AI User role to the AlloyDB service account
gcloud projects add-iam-policy-binding your-gcp-project-id \
  --member="serviceAccount:alloydb-sa@your-project.iam.gserviceaccount.com" \
  --role="roles/aiplatform.user"

    Generating Embeddings in SQL

    -- Create a table with a vector column for semantic search
CREATE TABLE product_catalog (
    product_id    SERIAL PRIMARY KEY,
    product_name  TEXT NOT NULL,
    description   TEXT,
    category      TEXT,
    price         NUMERIC(10,2),
    -- 768-dimension vector for text-embedding-004 model
    description_embedding VECTOR(768)
);

-- Create an IVFFlat index for approximate nearest neighbor search
-- lists = sqrt(row_count) is a common starting point
CREATE INDEX idx_product_embedding
ON product_catalog
USING ivfflat (description_embedding vector_cosine_ops)
WITH (lists = 100);

-- Generate embeddings using Vertex AI text-embedding-004
-- The embedding() function calls Vertex AI and returns a VECTOR
UPDATE product_catalog
SET description_embedding = embedding(
    'textembedding-gecko@003',   -- Vertex AI model ID
    description                  -- The text to embed
)
WHERE description_embedding IS NULL
  AND description IS NOT NULL;

-- Semantic search: find products similar to a natural language query
-- This entire operation happens inside PostgreSQL — no app-side ML call
SELECT
    product_id,
    product_name,
    description,
    price,
    1 - (description_embedding <=> embedding(
        'textembedding-gecko@003',
        'lightweight running shoes for trail conditions'
    )) AS cosine_similarity
FROM product_catalog
WHERE category = 'footwear'
ORDER BY description_embedding <=> embedding(
    'textembedding-gecko@003',
    'lightweight running shoes for trail conditions'
)
LIMIT 10;

-- Verify the index is being used (set_limit controls IVFFlat probe count)
SET ivfflat.probes = 10;
EXPLAIN (ANALYZE, BUFFERS)
SELECT product_id, product_name,
       description_embedding <=> embedding(
           'textembedding-gecko@003',
           'trail running footwear'
       ) AS distance
FROM product_catalog
ORDER BY description_embedding <=> embedding(
    'textembedding-gecko@003',
    'trail running footwear'
)
LIMIT 5;

    Calling Custom Vertex AI Models

    Beyond the built-in embedding function, you can call any Vertex AI endpoint using ml_predict_row:

    -- Register a custom model endpoint
-- This maps a logical name to a Vertex AI endpoint URL
INSERT INTO google_ml.model_info (
    model_id,
    model_type,
    model_endpoint,
    model_qualified_name
)
VALUES (
    'churn-predictor-v2',
    'classification',
    'https://us-central1-aiplatform.googleapis.com/v1/projects/your-project/locations/us-central1/endpoints/1234567890',
    'churn-predictor-v2'
);

-- Use the model in a query to score customer churn risk
-- ml_predict_row sends each row as a JSON payload to the model endpoint
-- and returns the prediction as JSONB
SELECT
    c.customer_id,
    c.customer_name,
    c.months_active,
    c.total_spend,
    (ml_predict_row(
        'churn-predictor-v2',
        jsonb_build_object(
            'months_active',      c.months_active,
            'total_spend',        c.total_spend,
            'support_tickets',    c.support_tickets_last_90d,
            'login_frequency',    c.avg_logins_per_month,
            'last_purchase_days', EXTRACT(EPOCH FROM (NOW() - c.last_purchase_date) / 86400)
        )
    ) ->> 'churn_probability')::NUMERIC AS churn_probability
FROM customers c
WHERE c.account_status = 'active'
ORDER BY churn_probability DESC NULLS LAST
LIMIT 100;

    The ml_predict_row function sends the JSONB payload to the Vertex AI endpoint over an authenticated HTTPS call and returns the response as JSONB. The function blocks — it is a synchronous call from inside your SQL execution. This has performance implications you need to understand before putting it in a hot query path.

    Performance Considerations for In-Database ML

    Calling a remote Vertex AI endpoint from within a SQL query introduces network round-trip latency on every row where the function is evaluated. A query that calls ml_predict_row on 10,000 rows is making 10,000 sequential HTTP calls unless you batch. AlloyDB provides a batching mechanism through ml_predict (the batch variant of the function):

    -- Batch variant: operates on a set of rows rather than row by row
-- More efficient for bulk scoring operations
WITH customer_features AS (
    SELECT
        customer_id,
        jsonb_build_object(
            'months_active',      months_active,
            'total_spend',        total_spend,
            'support_tickets',    support_tickets_last_90d,
            'login_frequency',    avg_logins_per_month,
            'last_purchase_days', EXTRACT(EPOCH FROM (NOW() - last_purchase_date) / 86400)
        ) AS features
    FROM customers
    WHERE account_status = 'active'
      AND churn_score_updated_at < NOW() - INTERVAL '24 hours'
)
UPDATE customers
SET
    churn_score = (prediction ->> 'churn_probability')::NUMERIC,
    churn_score_updated_at = NOW()
FROM (
    SELECT
        customer_id,
        ml_predict_row('churn-predictor-v2', features) AS prediction
    FROM customer_features
) scored
WHERE customers.customer_id = scored.customer_id;

    In practice, treat in-database ML inference the way you treat in-database foreign data wrapper queries: appropriate for scheduled batch jobs and low-volume per-request lookups, not appropriate for your critical path OLTP queries. A customer-facing API endpoint that triggers a ml_predict_row call in its SQL will add the Vertex AI inference latency — typically 50–300ms depending on model and payload — to every request. The semantic search pattern using pre-computed embeddings stored as VECTOR columns is significantly more practical for production because the costly Vertex AI call happens at write time, and the query-time operation is pure vector arithmetic inside the database.

    20.5 Migrating PostgreSQL Workloads to AlloyDB

    AlloyDB is wire-compatible with PostgreSQL 14 and 15. Most PostgreSQL applications require no SQL or driver changes to run on AlloyDB. The migration work is concentrated in three areas: extension compatibility, parameter behavior differences, and operational tooling changes.

    Extension Compatibility

    AlloyDB supports a large subset of PostgreSQL extensions, but not all. The most common issues encountered in migrations:

    | Extension | AlloyDB Status | Notes |

    |---|---|---|

    | pg_stat_statements | Supported | Enabled by default |

    | pgvector | Supported | Native, used with google_ml_integration |

    | postgis | Supported | Standard PostGIS versions |

    | pg_cron | Supported | Runs on primary only |

    | pg_partman | Supported | Works normally |

    | timescaledb | Not supported | TimescaleDB requires its own storage hooks |

    | pg_repack | Not available | Not needed — AlloyDB handles bloat differently |

    | pg_logical | Not available | AlloyDB has its own replication architecture |

    | pg_prewarm | Not useful | Replaced by the NVMe cache layer |

    | Custom extensions | Not supported | AlloyDB does not load arbitrary .so files |

    The pg_repack absence is worth explaining: in self-managed PostgreSQL, pg_repack is your tool for rebuilding bloated tables without taking a full lock the way VACUUM FULL does. In AlloyDB, table bloat is managed differently — autovacuum runs more aggressively and the storage layer reclaims space at a lower level. In practice, AlloyDB clusters rarely accumulate the bloat levels that make pg_repack necessary in self-managed environments. If you are currently running regular pg_repack jobs as part of your maintenance routine, plan to remove them and monitor bloat in AlloyDB using pg_stat_user_tables and pgstattuple instead.

    Parameter Differences

    AlloyDB manages several PostgreSQL parameters on your behalf and does not allow you to override them:

    -- Parameters you can still tune in AlloyDB:
-- (These work the same as self-managed PostgreSQL)
ALTER SYSTEM SET work_mem = '64MB';
ALTER SYSTEM SET maintenance_work_mem = '512MB';
ALTER SYSTEM SET effective_cache_size = '48GB';  -- set based on your RAM
ALTER SYSTEM SET random_page_cost = 1.1;         -- NVMe cache makes this lower than HDD default
ALTER SYSTEM SET effective_io_concurrency = 200;
ALTER SYSTEM SET max_parallel_workers_per_gather = 4;
ALTER SYSTEM SET max_worker_processes = 16;
ALTER SYSTEM SET lock_timeout = '30s';
ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';

-- Parameters you cannot meaningfully tune (AlloyDB manages them):
-- shared_buffers  — set automatically by AlloyDB
-- wal_level       — managed internally
-- archive_mode    — managed internally
-- max_wal_senders — managed internally
-- wal_keep_size   — not applicable to AlloyDB's WAL architecture
-- checkpoint_completion_target — less relevant, but adjustable
-- full_page_writes — managed internally

-- Parameters with different behavior in AlloyDB:
-- synchronous_commit: 'on' means WAL is durable in the distributed Log Store
--   (3-zone durable), not just on the primary's local disk
SHOW synchronous_commit;

-- autovacuum is more aggressive in AlloyDB by default
-- You can still tune per-table:
ALTER TABLE high_churn_table SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_cost_delay = 2,
    autovacuum_vacuum_threshold = 100
);

    Migration Using Database Migration Service

    Google's Database Migration Service (DMS) is the recommended path for migrating to AlloyDB. DMS supports homogeneous migrations (PostgreSQL to AlloyDB) with continuous replication, meaning you can keep your source database live during migration and cut over with minimal downtime.

    # Step 1: Create a connection profile for the source PostgreSQL database
gcloud database-migration connection-profiles create source-pg \
  --region=us-central1 \
  --type=POSTGRESQL \
  --host=10.0.1.50 \
  --port=5432 \
  --username=migration_user \
  --password=migration_password

# Step 2: Create a connection profile for the AlloyDB destination
gcloud database-migration connection-profiles create dest-alloydb \
  --region=us-central1 \
  --type=ALLOYDB \
  --cluster=prod-alloydb-cluster \
  --instance=prod-primary

# Step 3: Create the migration job
# --dump-type=LOGICAL uses pg_dump under the hood for initial load
# --migration-job-type=CONTINUOUS keeps changes streaming via logical replication
gcloud database-migration migration-jobs create pg-to-alloydb-migration \
  --region=us-central1 \
  --source=source-pg \
  --destination=dest-alloydb \
  --migration-job-type=CONTINUOUS \
  --dump-type=LOGICAL

# Step 4: Start the migration
gcloud database-migration migration-jobs start pg-to-alloydb-migration \
  --region=us-central1

# Step 5: Monitor replication lag during continuous phase
# Wait until lag is consistently near zero before cutting over
gcloud database-migration migration-jobs describe pg-to-alloydb-migration \
  --region=us-central1 \
  --format="value(state,duration,error)"

    On the source PostgreSQL side, DMS requires logical replication enabled and a replication user with appropriate permissions:

    -- On the source PostgreSQL database (self-managed or Cloud SQL)
-- Ensure logical replication is enabled
SHOW wal_level;  -- must be 'logical'

-- If not logical, update postgresql.conf and restart:
-- wal_level = logical

-- Create migration user with replication permissions
CREATE USER migration_user WITH REPLICATION LOGIN PASSWORD 'secure_password';

-- Grant select on all tables that will be migrated
GRANT SELECT ON ALL TABLES IN SCHEMA public TO migration_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO migration_user;

-- Grant replication permissions for the publication
GRANT pg_read_all_data TO migration_user;

-- DMS creates its own publication — verify after DMS initializes
SELECT pubname, puballtables, pubinsert, pubupdate, pubdelete
FROM pg_publication;

    Schema Compatibility Validation

    Before starting the migration, validate schema compatibility. The most common issues are:

    -- Check for unsupported data types
-- JSONB, arrays, custom types all work in AlloyDB, but verify
SELECT
    table_schema,
    table_name,
    column_name,
    data_type,
    udt_name
FROM information_schema.columns
WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
  AND data_type IN ('USER-DEFINED')
ORDER BY table_schema, table_name;

-- Check for extensions used by your schema
SELECT extname, extversion
FROM pg_extension
WHERE extname NOT IN ('plpgsql', 'pg_stat_statements');
-- Cross-reference this with the AlloyDB supported extension list

-- Check for custom functions that reference system internals
SELECT routine_schema, routine_name, routine_definition
FROM information_schema.routines
WHERE routine_type = 'FUNCTION'
  AND routine_schema = 'public'
  AND routine_definition ILIKE '%pg_catalog%';

-- Check for triggers on system tables (not portable)
SELECT trigger_schema, trigger_name, event_object_table
FROM information_schema.triggers
WHERE trigger_schema NOT IN ('pg_catalog', 'information_schema');

-- Sequences: verify all serial/identity columns will migrate correctly
SELECT
    sequence_schema,
    sequence_name,
    start_value,
    increment,
    maximum_value
FROM information_schema.sequences
WHERE sequence_schema = 'public';

    20.6 AlloyDB vs Cloud SQL for PostgreSQL: When to Use Which

    This is the question every GCP-based PostgreSQL DBA faces when a new project starts or when an existing Cloud SQL cluster reaches its limits. AlloyDB is substantially more expensive than Cloud SQL for the same vCPU count, but it offers meaningfully different capabilities. The decision is not simply "AlloyDB is Cloud SQL Pro" — there are workloads where Cloud SQL is the correct answer and AlloyDB is overengineered overhead.

    Use AlloyDB when:

    Your workload is mixed OLTP + analytics. If you are running complex reporting queries alongside OLTP, and those queries are causing resource contention or requiring a separate reporting replica, AlloyDB's columnar engine provides a genuine architectural solution. The columnar engine is not a toy feature — for queries that scan millions of rows with aggregations, the performance difference can be dramatic.

    You need sub-second read replica provisioning. AlloyDB read pool nodes attach to the shared storage layer and can be added or removed quickly. If your application has traffic spikes that require rapid read scaling, this matters operationally.

    Your data exceeds what fits in Cloud SQL's max instance size. Cloud SQL for PostgreSQL has a maximum instance size that is substantially smaller than AlloyDB's maximum. For databases that have grown to require more RAM and CPU than Cloud SQL can provide, AlloyDB is the path forward without leaving managed PostgreSQL.

    You are building semantic search or vector similarity features. AlloyDB's native integration of pgvector and google_ml_integration provides a development and operational experience that is better than bolting pgvector onto Cloud SQL.

    Use Cloud SQL for PostgreSQL when:

    Your database is small to medium and purely OLTP. If your dataset fits comfortably in RAM, your query mix is point lookups and simple joins, and you have no analytical workload, you are paying for AlloyDB's columnar engine and distributed storage without using them. Cloud SQL delivers fine performance for standard OLTP workloads and at lower cost.

    You need specific extensions that AlloyDB does not support. If your schema depends on TimescaleDB, a custom extension loaded from .so, or pg_logical for external replication, Cloud SQL is more likely to support your requirements.

    You need cross-region replicas with native replication. Cloud SQL supports cross-region read replicas using standard PostgreSQL streaming replication. AlloyDB's cross-region capabilities are more limited — as of mid-2024, AlloyDB cross-region disaster recovery was available as a preview feature but had more operational constraints than Cloud SQL's cross-region replicas.

    You are running a development or staging environment. AlloyDB's minimum instance sizes and cluster overhead make it a poor fit for non-production environments. Cloud SQL's ability to stop instances outside business hours and its lower floor cost make it better for dev/test.

    Side-by-Side Performance Comparison Approach

    Do not rely on benchmarks from Google's documentation or third-party publications when making this decision for your specific workload. Run your own benchmark using your actual schema and query mix. The methodology:

    # Step 1: Provision equivalent-sized instances
# AlloyDB: 8 vCPU primary + 2-node read pool
# Cloud SQL: 8 vCPU PostgreSQL instance with a read replica

# Step 2: Load representative data
# Use pgbench with a scale factor that produces your typical data volume
# or restore a production backup (anonymized if needed)

pgbench -i -s 500 -h ALLOYDB_IP -U postgres benchdb
pgbench -i -s 500 -h CLOUDSQL_IP -U postgres benchdb

# Step 3: Run a mixed workload test
# Default pgbench is pure OLTP — add custom scripts for your analytical queries
pgbench -c 50 -j 4 -T 300 \
  -f oltp_script.sql \
  -f analytics_script.sql \
  -h ALLOYDB_IP -U postgres benchdb

# Step 4: Measure at the right layer
# Don't just look at pgbench TPS — measure:
# - p50, p95, p99 query latency (use pg_stat_statements)
# - CPU and memory utilization (Cloud Monitoring)
# - Replication lag under load
# - Buffer hit ratio (indicates whether columnar engine is helping)

    20.7 Monitoring AlloyDB in Production

    AlloyDB exposes metrics through Cloud Monitoring, and the query-level visibility comes through Query Insights — the same tool available in Cloud SQL but with AlloyDB-specific additions for the columnar engine.

    Essential Cloud Monitoring Metrics

    # Useful gcloud monitoring queries for AlloyDB
# (In practice, you build dashboards in the Cloud Monitoring UI or Terraform)

# List available AlloyDB metrics
gcloud monitoring metrics list \
  --filter="metric.type=starts_with('alloydb.googleapis.com')" \
  --format="value(metric.type)"

    The key metrics you should alarm on for a production AlloyDB cluster:

    | Metric | Description | Alert Threshold |

    |---|---|---|

    | alloydb.googleapis.com/instance/cpu/utilization | CPU usage on the instance | > 80% sustained |

    | alloydb.googleapis.com/instance/memory/utilization | Memory utilization | > 90% |

    | alloydb.googleapis.com/instance/postgres/replication_lag | Replica lag | > 30s |

    | alloydb.googleapis.com/instance/postgres/connections | Active connections | > 80% of max_connections |

    | alloydb.googleapis.com/instance/storage/used_bytes | Storage consumption | > 80% of provisioned |

    | alloydb.googleapis.com/instance/columnar_engine/memory_used | Columnar engine memory | > 90% of allocated |

    Query-Level Monitoring

    AlloyDB inherits pg_stat_statements and adds its own query observability layer:

    -- Top queries by total execution time (standard pg_stat_statements)
SELECT
    LEFT(query, 80) AS query_snippet,
    calls,
    ROUND(total_exec_time::NUMERIC, 2) AS total_ms,
    ROUND(mean_exec_time::NUMERIC, 2) AS mean_ms,
    ROUND(stddev_exec_time::NUMERIC, 2) AS stddev_ms,
    rows,
    ROUND(100.0 * shared_blks_hit /
          NULLIF(shared_blks_hit + shared_blks_read, 0), 2) AS buffer_hit_pct
FROM pg_stat_statements
WHERE calls > 100
ORDER BY total_exec_time DESC
LIMIT 20;

-- Identify queries that are NOT hitting the columnar engine
-- but look like they should (table scans on large tables)
SELECT
    schemaname,
    relname,
    seq_scan,
    seq_tup_read,
    idx_scan,
    n_live_tup,
    ROUND(seq_tup_read::NUMERIC / NULLIF(seq_scan, 0), 0) AS avg_rows_per_seq_scan
FROM pg_stat_user_tables
WHERE seq_scan > 10
  AND n_live_tup > 100000
ORDER BY seq_tup_read DESC
LIMIT 20;

-- Check columnar engine status and memory usage
SELECT *
FROM google_columnar_engine_tables
ORDER BY size_in_bytes DESC;

-- Check if specific queries used the columnar engine
-- Look for 'Columnar Scan' nodes in EXPLAIN output
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    category,
    DATE_TRUNC('month', order_date) AS month,
    COUNT(*) AS order_count,
    SUM(order_total) AS revenue
FROM orders
WHERE order_date >= '2023-01-01'
GROUP BY category, DATE_TRUNC('month', order_date)
ORDER BY month, revenue DESC;

-- Monitor autovacuum activity (still relevant in AlloyDB)
SELECT
    schemaname,
    relname,
    n_dead_tup,
    n_live_tup,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY dead_tup DESC
LIMIT 15;

    AlloyDB-Specific Operational Queries

    -- Check storage layer health (AlloyDB-specific view)
SELECT *
FROM pg_stat_replication;
-- Note: In AlloyDB, this shows internal replication to the storage nodes,
-- not traditional streaming replication to replicas.
-- Replica lag is monitored via Cloud Monitoring, not this view.

-- Connection count by state
SELECT
    state,
    wait_event_type,
    wait_event,
    COUNT(*) AS connection_count
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
GROUP BY state, wait_event_type, wait_event
ORDER BY connection_count DESC;

-- Long-running transactions (a leading indicator of lock contention)
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    EXTRACT(EPOCH FROM (NOW() - xact_start)) AS xact_age_seconds,
    LEFT(query, 100) AS current_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND state <> 'idle'
  AND EXTRACT(EPOCH FROM (NOW() - xact_start)) > 30
ORDER BY xact_age_seconds DESC;

-- Lock contention view
SELECT
    blocked.pid AS blocked_pid,
    blocked.usename AS blocked_user,
    blocking.pid AS blocking_pid,
    blocking.usename AS blocking_user,
    blocked.query AS blocked_query,
    blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
    ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE pg_blocking_pids(blocked.pid) <> '{}';

    20.8 High Availability and Backup in AlloyDB

    AlloyDB's HA model differs from Cloud SQL's in a way that matters for failover behavior. Cloud SQL HA uses a warm standby instance in a different zone that takes over on primary failure. AlloyDB's HA is embedded in the storage layer: because the Log Store replicates across three zones, the primary instance can fail and the storage state is immediately available for the replacement instance. Failover in AlloyDB typically completes in under 60 seconds, and because no WAL replay is needed, the new primary instance resumes from exactly the storage state at failure time.

    Failover Testing

    # Trigger a manual failover to test HA behavior
# This simulates the primary instance failing
gcloud alloydb instances failover prod-primary \
  --cluster=prod-alloydb-cluster \
  --region=us-central1

# Monitor the cluster state during failover
watch -n 5 gcloud alloydb instances list \
  --cluster=prod-alloydb-cluster \
  --region=us-central1

# After failover completes, verify the primary is healthy
gcloud alloydb instances describe prod-primary \
  --cluster=prod-alloydb-cluster \
  --region=us-central1 \
  --format="value(state,ipAddress)"

    Continuous Backup and Point-in-Time Recovery

    AlloyDB's backup model combines automated periodic backups with continuous WAL archiving to achieve PITR with recovery windows of up to 14 days. The continuous backup is not a feature you enable in addition to snapshots — it is the primary backup mechanism, and the periodic backups are baseline checkpoints within the continuous stream.

    # View available backups
gcloud alloydb backups list \
  --region=us-central1 \
  --cluster=prod-alloydb-cluster

# Restore to a point in time — this creates a NEW cluster
# AlloyDB cannot restore in-place to the same cluster
# The --restore-time is in RFC3339 format
gcloud alloydb clusters restore prod-alloydb-cluster-restored \
  --region=us-central1 \
  --network=projects/your-project/global/networks/prod-vpc \
  --source-cluster=prod-alloydb-cluster \
  --restore-time=2024-08-15T14:30:00Z

# After restore, create a primary instance in the restored cluster
gcloud alloydb instances create prod-primary \
  --cluster=prod-alloydb-cluster-restored \
  --region=us-central1 \
  --instance-type=PRIMARY \
  --cpu-count=8

    The restore-to-a-new-cluster behavior is an operational consideration: you cannot restore a backup over your existing cluster. If you need to recover from data corruption or an accidental mass delete, you restore to a new cluster, validate the data, and then either rename/reroute connections or copy the data back to the original cluster. This is the same operational pattern as Aurora's PITR restore, and it means you need a runbook for "what happens when we need to recover data" that accounts for this constraint.

    Manual Backups

    # Create an on-demand backup before a risky schema change
gcloud alloydb backups create pre-migration-backup-20240815 \
  --cluster=prod-alloydb-cluster \
  --region=us-central1 \
  --description="Backup before v2.4 schema migration"

# List backups with their retention expiration
gcloud alloydb backups list \
  --region=us-central1 \
  --format="table(name,state,createTime,expiryTime,description)"

    Key Takeaways

  • → **AlloyDB's disaggregated storage architecture** eliminates checkpoint I/O pressure on the primary and enables read replicas to provision in seconds rather than hours, but the shared Log Store model means replication lag metrics are fundamentally different from `pg_stat_replication.replay_lag` and require Cloud Monitoring for accurate measurement.
  • → **The columnar engine enables mixed OLTP and analytical workloads** on a single AlloyDB cluster by transparently routing analytical queries through a compressed, in-memory columnar representation of selected tables — use `google_columnar_engine_recommended_tables()` to identify candidates and validate with `EXPLAIN (ANALYZE, BUFFERS)` before committing to columnarization.
  • → **In-database ML inference via `google_ml_integration`** allows embedding generation and model scoring directly from SQL using Vertex AI endpoints, but synchronous per-row invocation adds Vertex AI round-trip latency to query execution time; the practical production pattern is generating embeddings at write time and using `pgvector` similarity search at query time.
  • → **AlloyDB is not a drop-in replacement for all Cloud SQL workloads** — small OLTP databases, workloads that depend on unsupported extensions like TimescaleDB, development environments, and applications that require cross-region read replicas today are better served by Cloud SQL for PostgreSQL at lower operational cost.
  • → **AlloyDB's HA failover and PITR backup model** provides sub-60-second primary failover without WAL replay, and continuous backup with up to 14-day PITR windows, but point-in-time recovery always creates a new cluster rather than restoring in-place, which requires explicit runbook design for data recovery scenarios.
