Chapter 8: Aurora MySQL vs RDS MySQL

Aurora MySQL and RDS MySQL are both managed MySQL offerings on AWS, but they are architecturally different products that share a query interface. If you've spent years tuning InnoDB buffer pools and wrestling with MySQL replication, the differences matter enormously in production. One is a drop-in replacement for a self-managed MySQL installation with a managed control plane layered on top. The other is a purpose-built distributed storage engine disguised as MySQL. This chapter walks through how Aurora MySQL diverges from RDS MySQL at the storage layer, replication model, failover behavior, and cost structure — and how to choose between them for real production workloads.

---

8.1 Architectural Differences: Storage Layer and Replication Model

The single most important thing to understand about Aurora MySQL is that it is not running the InnoDB storage engine against local EBS volumes. Aurora separates compute from storage entirely. The Aurora storage subsystem is a distributed, fault-tolerant, self-healing storage layer that spans six storage nodes across three Availability Zones. When your writer instance commits a transaction, Aurora writes redo log records to quorum across those six nodes — four of six must acknowledge before the commit returns. The actual page materialization happens asynchronously in the storage layer. Aurora does not ship full page writes from compute to storage. It ships log records.

For a DBA who has tuned innodb_flush_log_at_trx_commit and worried about the fsync pipeline, this is a meaningful shift. The durability guarantee is enforced in the storage tier, not at the instance level. A single Aurora writer can sustain significantly higher write throughput than an equivalently sized RDS MySQL instance because it is not performing double-write buffer operations to local storage. The double-write buffer exists to protect against torn page writes — a problem Aurora's storage architecture eliminates by design.

RDS MySQL, by contrast, runs MySQL — with its full InnoDB engine including double-write buffer, undo tablespaces, and local EBS storage — with AWS managing provisioning, patching, automated backups, and Multi-AZ failover. Multi-AZ RDS MySQL uses synchronous block-level replication to a standby in a second AZ. That standby is not readable. It is purely a failover target. Failover on Multi-AZ RDS MySQL typically takes 60 to 120 seconds, involves a DNS flip, and requires applications to reconnect.

Aurora MySQL failover works differently. The reader instances are not replicas in the traditional sense — they share the same distributed storage volume as the writer. A reader can be promoted to writer in 30 seconds or less in typical conditions because it already has access to the same underlying storage. There is no replication lag between the writer and readers with respect to durable data; readers do see a brief lag in their buffer cache view of in-flight transactions, but they are reading from the same storage pages. Aurora advertises sub-30-second failover and typically achieves it.

Aurora also supports up to 15 read replicas. RDS MySQL supports up to 5 read replicas, and those replicas use standard MySQL binlog replication — which means they can lag, especially under heavy write load or large transactions. A single large ALTER TABLE on RDS MySQL can cause read replicas to fall minutes or hours behind. Aurora readers don't have that problem because they are not replaying binlog; they are reading pages that have already been materialized in the shared storage layer.

The trade-off: Aurora MySQL costs more per instance-hour than an equivalently sized RDS MySQL instance, and Aurora's storage pricing model is consumption-based (billed per GB-month for storage plus per-request I/O charges — check current AWS pricing for your region). For read-heavy, low-write workloads, RDS MySQL with read replicas may be cheaper. For write-intensive workloads where replication lag on reads is unacceptable, Aurora wins.

8.2 Provisioning Aurora MySQL vs RDS MySQL with Terraform and AWS CLI

Provisioning an Aurora MySQL cluster differs structurally from provisioning an RDS MySQL instance. Aurora has two objects: the cluster and the instances within it. You provision the cluster — which owns the storage volume, the endpoints, and the parameter groups — and then you provision one or more DB instances into that cluster.

# Create an Aurora MySQL 8.0 cluster
aws rds create-db-cluster \
  --db-cluster-identifier prod-aurora-mysql \
  --engine aurora-mysql \
  --engine-version 8.0.mysql_aurora.3.04.0 \
  --master-username admin \
  --master-user-password "YourSecurePassword123!" \
  --db-subnet-group-name prod-subnet-group \
  --vpc-security-group-ids sg-0abc123def456 \
  --backup-retention-period 7 \
  --preferred-backup-window "02:00-03:00" \
  --preferred-maintenance-window "sun:04:00-sun:05:00" \
  --storage-encrypted \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/your-kms-key-id \
  --enable-cloudwatch-logs-exports '["audit","error","general","slowquery"]' \
  --deletion-protection

# Add the writer instance to the cluster
aws rds create-db-instance \
  --db-instance-identifier prod-aurora-mysql-writer \
  --db-cluster-identifier prod-aurora-mysql \
  --db-instance-class db.r6g.2xlarge \
  --engine aurora-mysql

# Add a reader instance
aws rds create-db-instance \
  --db-instance-identifier prod-aurora-mysql-reader-1 \
  --db-cluster-identifier prod-aurora-mysql \
  --db-instance-class db.r6g.xlarge \
  --engine aurora-mysql

The equivalent in Terraform makes the cluster-versus-instance separation explicit:

resource "aws_rds_cluster_instance" "writer" {

  cluster_identifier = aws_rds_cluster.aurora_mysql.id

  count              = 2

  cluster_identifier = aws_rds_cluster.aurora_mysql.id

  }

    name  = "slow_query_log"
    value = "1"

    name  = "long_query_time"
    value = "1"

  name   = "prod-aurora-mysql8-instance-params"

    value = "1"
  }

Notice that Aurora uses two tiers of parameter groups: the cluster parameter group applies to all instances in the cluster and controls settings like character sets and binlog format. The instance parameter group applies to individual instances and controls settings like buffer pool behavior. In RDS MySQL, there is only one parameter group per instance. This is one of the first configuration gotchas that trips up DBAs coming from RDS MySQL.

For RDS MySQL, provisioning is simpler because there is no cluster abstraction:

# Create an RDS MySQL 8.0 Multi-AZ instance
aws rds create-db-instance \
  --db-instance-identifier prod-rds-mysql \
  --db-instance-class db.m6g.2xlarge \
  --engine mysql \
  --engine-version 8.0.35 \
  --master-username admin \
  --master-user-password "YourSecurePassword123!" \
  --allocated-storage 500 \
  --storage-type gp3 \
  --iops 12000 \
  --storage-encrypted \
  --multi-az \
  --db-subnet-group-name prod-subnet-group \
  --vpc-security-group-ids sg-0abc123def456 \
  --backup-retention-period 7 \
  --preferred-backup-window "02:00-03:00" \
  --preferred-maintenance-window "sun:04:00-sun:05:00" \
  --enable-performance-insights \
  --performance-insights-retention-period 7 \
  --monitoring-interval 60 \
  --monitoring-role-arn arn:aws:iam::123456789012:role/rds-monitoring-role \
  --deletion-protection \
  --no-publicly-accessible

With RDS MySQL you specify storage size explicitly — 500 GB in this case, provisioned with gp3 at 12,000 IOPS. With Aurora MySQL you never specify storage size; the storage grows automatically in 10 GB increments up to 128 TB. If your workload balloons unexpectedly, Aurora handles it. With RDS MySQL, you need to monitor free storage and either resize proactively or enable storage autoscaling.

8.3 Parameter Groups: What You Can and Cannot Tune

On-prem, you owned the MySQL configuration file entirely. On managed RDS or Aurora, AWS restricts a substantial number of parameters. Understanding which parameters are tunable, which are fixed, and which behave differently than on-prem is essential before production deployment.

The following query, run against a running Aurora MySQL instance, shows you which parameters are customer-modifiable:

-- Connect to your Aurora instance and check parameter apply status
-- This is better done via AWS CLI against the parameter group

-- But once connected, verify current effective values
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_io_capacity';
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'transaction_isolation';

-- Aurora-specific variables worth checking
SHOW VARIABLES LIKE 'aurora%';
SHOW VARIABLES LIKE 'aurora_parallel_query';
SHOW VARIABLES LIKE 'aurora_read_replica_read_consistency';
# Check which parameters in your cluster parameter group are user-modifiable
aws rds describe-engine-default-cluster-parameters \
  --db-parameter-group-family aurora-mysql8.0 \
  --query 'EngineDefaults.Parameters[?IsModifiable==`true`].[ParameterName,ParameterValue,ApplyType]' \
  --output table | head -60

# Check a specific parameter's current value and constraints
aws rds describe-db-cluster-parameters \
  --db-cluster-parameter-group-name prod-aurora-mysql8-cluster-params \
  --query 'Parameters[?ParameterName==`innodb_io_capacity`]'

Key parameters and their cloud behavior:

innodb_buffer_pool_size: On RDS and Aurora, this is typically set automatically based on the instance class. On Aurora, the default is 75% of instance memory, which is generally correct. You can override it, but AWS recommends against it. On a db.r6g.2xlarge with 64 GB RAM, the buffer pool defaults to roughly 48 GB.

max_connections: Aurora sets this automatically based on a formula derived from instance memory — run SHOW VARIABLES LIKE 'max_connections' on your instance to see the actual default rather than assuming a fixed number. You can increase it, but doing so is usually a signal that you need RDS Proxy rather than a larger max_connections value. More on this in Section 8.4.

binlog_format: On Aurora MySQL, binlog is not required for replication within the cluster — Aurora uses its own log-based replication internally. However, if you're using Aurora as a source for DMS, or replicating to an external MySQL target, binlog must be enabled explicitly. Set binlog_format=ROW at the cluster parameter group level and enable log_bin if needed.

innodb_flush_log_at_trx_commit: This parameter exists on Aurora but has reduced significance. Aurora does not perform traditional InnoDB log flushing to local storage; the durability guarantee is enforced at the storage layer. The parameter is modifiable, but changing it from the default of 1 does not provide the traditional trade-off between durability and performance it would on self-managed MySQL.

Parameters you cannot change on managed services:

  • → `datadir` — fixed by AWS
  • → `innodb_data_file_path` — not applicable, Aurora manages tablespace layout
  • → `plugin_dir` — you cannot install arbitrary MySQL plugins
  • → `general_log` to a file location of your choosing — logs go to CloudWatch, not local filesystem
  • → `secure_file_priv` — `LOAD DATA INFILE` from arbitrary paths is restricted; use S3 integration instead

    • Aurora MySQL supports a native S3 integration for LOAD DATA operations:

    -- Load data from S3 into Aurora MySQL (requires aws_default_s3_role IAM role attached to cluster)
LOAD DATA FROM S3 's3://your-bucket/data/customers.csv'
INTO TABLE customers
FIELDS TERMINATED BY ','
ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 ROWS;

-- Export query results to S3
SELECT customer_id, email, created_at
INTO OUTFILE S3 's3://your-bucket/exports/customers_export'
FIELDS TERMINATED BY ','
LINES TERMINATED BY '\n'
FROM customers
WHERE created_at >= '2024-01-01';

    This replaces the on-prem pattern of mounting a network share or copying files locally before LOAD DATA INFILE. Secure it properly: the IAM role attached to the Aurora cluster needs s3:GetObject and s3:PutObject on the target bucket, with s3:ListBucket on the bucket itself.

    8.4 Connection Management: RDS Proxy and Aurora

    One of the most persistent operational pain points when migrating from self-managed MySQL to RDS is connection management. Self-managed MySQL installations behind ProxySQL or HAProxy gave you control over connection pooling, load balancing, query routing, and failover handling. AWS provides RDS Proxy as its managed connection pooler, and it integrates with both RDS MySQL and Aurora MySQL.

    RDS Proxy maintains a pool of persistent connections to the database and presents a proxy endpoint to applications. Applications connect to the proxy; the proxy multiplexes those connections against a smaller pool of real database connections. This is significant for Lambda functions, containerized applications, or any workload that opens and closes database connections frequently. Without a connection pooler, a spike in Lambda concurrency can open thousands of connections to Aurora simultaneously, exhausting max_connections and causing Too many connections errors.

    # Create an RDS Proxy for Aurora MySQL
aws rds create-db-proxy \
  --db-proxy-name prod-aurora-proxy \
  --engine-family MYSQL \
  --auth '[{
    "AuthScheme": "SECRETS",
    "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:prod/aurora/admin-AbCdEf",
    "IAMAuth": "REQUIRED"
  }]' \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0abc123 subnet-0def456 subnet-0ghi789 \
  --vpc-security-group-ids sg-0abc123def456 \
  --require-tls

# Register the Aurora cluster with the proxy
aws rds register-db-proxy-targets \
  --db-proxy-name prod-aurora-proxy \
  --db-cluster-identifiers prod-aurora-mysql

# Create a read-only proxy endpoint pointing to readers
aws rds create-db-proxy-endpoint \
  --db-proxy-name prod-aurora-proxy \
  --db-proxy-endpoint-name prod-aurora-proxy-readonly \
  --vpc-subnet-ids subnet-0abc123 subnet-0def456 subnet-0ghi789 \
  --vpc-security-group-ids sg-0abc123def456 \
  --target-role READ_ONLY

    RDS Proxy uses AWS Secrets Manager to store and rotate credentials. If you set IAMAuth: REQUIRED, applications authenticate to the proxy using IAM authentication rather than username/password. The proxy then uses the stored secret to authenticate to the actual database. This is the cloud equivalent of what you used to do with pg_hba.conf certificate authentication or LDAP integration — centralize credential management, enforce consistent authentication policies, and enable rotation without application restarts.

    import boto3
import pymysql
import os

def get_db_connection_with_iam():
    """
    Connect to RDS Proxy using IAM authentication.
    The proxy endpoint accepts an IAM auth token as the password.
    """
    region = 'us-east-1'
    proxy_host = 'prod-aurora-proxy.proxy-abc123.us-east-1.rds.amazonaws.com'
    db_user = 'app_user'
    db_name = 'appdb'
    port = 3306

    # Generate an IAM authentication token
    client = boto3.client('rds', region_name=region)
    token = client.generate_db_auth_token(
        DBHostname=proxy_host,
        Port=port,
        DBUsername=db_user,
        Region=region
    )

    # The token is used as the password; it expires after 15 minutes
    connection = pymysql.connect(
        host=proxy_host,
        user=db_user,
        password=token,
        database=db_name,
        port=port,
        ssl_ca='/path/to/us-east-1-bundle.pem',  # Download from AWS
        ssl_verify_cert=True,
        connect_timeout=5,
        read_timeout=30,
        write_timeout=30
    )
    
    return connection

def execute_with_retry(query, params=None, max_retries=3):
    """
    Production pattern: handle proxy reconnection on failover.
    RDS Proxy maintains connections across Aurora failover,
    but applications should still handle transient errors.
    """
    import time
    
    for attempt in range(max_retries):
        conn = None
        try:
            conn = get_db_connection_with_iam()
            with conn.cursor() as cursor:
                cursor.execute(query, params)
                conn.commit()
                return cursor.fetchall()
        except pymysql.err.OperationalError as e:
            error_code = e.args[0]
            # 2003: Can't connect, 2006: Server gone away
            if error_code in (2003, 2006) and attempt < max_retries - 1:
                wait = 2 ** attempt  # exponential backoff
                time.sleep(wait)
                continue
            raise
        finally:
            if conn:
                conn.close()

    RDS Proxy has important gotchas to understand before production deployment:

    Pinning: RDS Proxy multiplexes connections by reusing them between requests. When a client uses session-level state that the proxy cannot safely track — user variables (SET @var = value), temporary tables, or LOCK TABLES — the proxy "pins" that client to a specific backend connection and cannot share it. Excessive pinning defeats the purpose of connection pooling. Audit your application code for session-level state before enabling RDS Proxy. The CloudWatch metric DatabaseConnectionsCurrentlySessionPinned will tell you if this is a problem.

    Transaction pinning: Any open transaction pins a connection until commit or rollback. Long-running transactions in a pooled environment are as harmful here as they are with any connection pooler.

    Max connections to RDS Proxy: The proxy itself has a connection limit based on its size configuration. The default proxy scales automatically, but if you're routing very high connection counts through it, verify the proxy's MaxConnectionsPercent setting, which controls how much of the database's max_connections the proxy is allowed to use.

    8.5 Failover, Backups, and Aurora-Specific Features

    Failover behavior

    Aurora's failover is tier-based. You assign a failover priority from 0 to 15 to each reader instance using the PromotionTier parameter. In the event the writer fails, Aurora promotes the reader with the lowest tier number. If two readers share the same tier, Aurora promotes the one with the largest instance class. Set your highest-capacity reader to tier 0 to make failover behavior predictable.

    # Set failover priority on Aurora reader instances
aws rds modify-db-instance \
  --db-instance-identifier prod-aurora-mysql-reader-1 \
  --promotion-tier 0

aws rds modify-db-instance \
  --db-instance-identifier prod-aurora-mysql-reader-2 \
  --promotion-tier 1

# Trigger a manual failover to test promotion
aws rds failover-db-cluster \
  --db-cluster-identifier prod-aurora-mysql \
  --target-db-instance-identifier prod-aurora-mysql-reader-1

    Applications connecting to the Aurora cluster endpoint automatically route to whichever instance is the current writer. After failover, the cluster endpoint resolves to the new writer within approximately 30 seconds. Applications must handle the brief reconnection window — typically by catching connection errors and retrying with exponential backoff, as shown in the Python example above. Using RDS Proxy further reduces the impact because the proxy absorbs the failover and queues incoming requests while promotion completes.

    Backups and point-in-time recovery

    Aurora continuously backs up to S3. The backup window you configure is for the full snapshot, but redo logs are shipped to S3 continuously, enabling point-in-time recovery (PITR) to within 5 minutes of any point in the last 35 days (with maximum backup retention). RDS MySQL also supports PITR, but with a slightly different operational model: the automated snapshot establishes the restore baseline, and binary logs fill the gap between the snapshot and the target recovery time.

    To initiate a point-in-time restore for Aurora:

    # Restore Aurora cluster to a specific point in time
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier prod-aurora-mysql-restored \
  --source-db-cluster-identifier prod-aurora-mysql \
  --restore-type full-copy \
  --restore-to-time 2024-03-15T14:30:00Z \
  --db-subnet-group-name prod-subnet-group \
  --vpc-security-group-ids sg-0abc123def456 \
  --enable-cloudwatch-logs-exports '["error","slowquery"]'

# After the cluster is restored, add an instance to it
aws rds create-db-instance \
  --db-instance-identifier prod-aurora-mysql-restored-writer \
  --db-cluster-identifier prod-aurora-mysql-restored \
  --db-instance-class db.r6g.2xlarge \
  --engine aurora-mysql

    One operational advantage of Aurora's backup model is that restoring to a new cluster does not immediately read back all pages from S3. Aurora uses a lazy restore approach: the storage layer makes the cluster available immediately and fetches pages from S3 on demand as they are accessed. For large databases, this dramatically reduces the time to first query on a restored cluster compared to waiting for RDS MySQL to restore a full snapshot before the instance becomes available.

    For RDS MySQL, point-in-time restore follows the same pattern but uses restore-db-instance-to-point-in-time:

    # Restore RDS MySQL to a specific point in time
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-rds-mysql \
  --target-db-instance-identifier prod-rds-mysql-restored \
  --restore-time 2024-03-15T14:30:00Z \
  --db-instance-class db.m6g.2xlarge \
  --db-subnet-group-name prod-subnet-group \
  --no-multi-az \
  --no-publicly-accessible

    With RDS MySQL the restored instance must receive the entire snapshot to storage before it becomes accessible. For a 1 TB database this can take significantly longer than the equivalent Aurora restore.

    Aurora-specific features worth knowing in production

    *Aurora Fast Clone*: Aurora can create a clone of a cluster near-instantly using a copy-on-write mechanism at the storage layer. The clone shares storage pages with the source until writes diverge. This is extraordinarily useful for creating staging environments, schema migration tests, or load testing copies without paying for a full storage copy upfront.

    # Clone Aurora cluster (near-instant, copy-on-write storage)
aws rds restore-db-cluster-to-point-in-time \
  --db-cluster-identifier prod-aurora-mysql-clone \
  --source-db-cluster-identifier prod-aurora-mysql \
  --restore-type copy-on-write \
  --use-latest-restorable-time \
  --db-subnet-group-name staging-subnet-group \
  --vpc-security-group-ids sg-0staging123

# Add an instance to the clone
aws rds create-db-instance \
  --db-instance-identifier prod-aurora-mysql-clone-writer \
  --db-cluster-identifier prod-aurora-mysql-clone \
  --db-instance-class db.r6g.xlarge \
  --engine aurora-mysql

    The clone is independent after creation — writes to production do not appear in the clone, and vice versa. Storage divergence increases over time as writes accumulate in both clusters. This is not a synchronization mechanism; it is a fast forking mechanism for ephemeral copies.

    *Aurora Global Database*: For multi-region deployments, Aurora Global Database replicates from a primary region to up to five secondary regions using storage-level replication rather than MySQL binlog. Replication lag to secondary regions is typically under one second under normal load. Secondary regions are read-only unless you perform a planned or unplanned failover (detaching the secondary and promoting it to standalone primary). This is the pattern for disaster recovery across regions without the binlog lag and replication monitoring overhead you'd carry with RDS MySQL cross-region replicas.

    *Aurora Parallel Query*: For analytical workloads on Aurora MySQL, Parallel Query pushes query processing down to the storage layer across multiple storage nodes. For certain full-scan, aggregation-heavy queries against large tables, this can substantially reduce query execution time by parallelizing work that would otherwise run single-threaded on the compute node. Enable it selectively:

    -- Check if parallel query is available on your instance type
SHOW VARIABLES LIKE 'aurora_parallel_query';

-- Enable parallel query for the current session
SET SESSION aurora_parallel_query = ON;

-- Verify a specific query will use parallel query
EXPLAIN
SELECT region, COUNT(*), SUM(amount)
FROM orders
WHERE order_date >= '2023-01-01'
GROUP BY region;
-- Look for "Using parallel query" in the Extra column

    Not all queries benefit from Parallel Query. It adds overhead for index-range scans that are already selective. It is most beneficial for large table scans with filtering and aggregation — the OLAP edge of a mixed OLTP/OLAP workload.

    *Aurora Serverless v2*: Aurora Serverless v2 allows compute capacity to scale continuously in half-ACU (Aurora Capacity Unit) increments between a configured minimum and maximum. Unlike the original Aurora Serverless v1, v2 instances do not scale to zero (the minimum is 0.5 ACU) and they scale fast enough to handle production traffic spikes without cold-start latency. This is appropriate for workloads with highly variable load patterns where you'd otherwise overprovision a fixed instance class to handle peaks. Provisioned Aurora is still preferable for steady, predictable workloads where the per-ACU cost of Serverless v2 exceeds the equivalent provisioned instance cost.

    8.6 Monitoring Aurora MySQL vs RDS MySQL

    The monitoring surface between Aurora and RDS MySQL overlaps significantly — both surface metrics through CloudWatch and both support Performance Insights and Enhanced Monitoring. The differences lie in the Aurora-specific metrics that expose the distributed storage layer.

    Key Aurora-specific CloudWatch metrics:

  • → `AuroraVolumeBytesLeftTotal`: Storage remaining in the Aurora volume. Alert when this drops below a comfortable threshold — Aurora automatically grows storage, but there is a maximum.
  • → `AuroraBinlogReplicaLag`: Lag for external replicas (non-Aurora) replicating from the Aurora cluster. This is different from `ReplicaLag`, which measures lag on Aurora reader instances.
  • → `CommitLatency` / `CommitThroughput`: These measure the latency and rate of transaction commits at the Aurora storage layer. A spike in `CommitLatency` with stable instance CPU suggests storage-tier contention, not compute saturation.
  • → `DDLLatency` / `DMLLatency` / `SelectLatency`: Fine-grained operation-type latency metrics available on Aurora, not on RDS MySQL.
  • → `BufferCacheHitRatio`: Percentage of page reads served from the in-memory buffer pool. Sustained values below 95% warrant investigation. A falling ratio suggests your working set is larger than your buffer pool.
  • → `EngineUptime`: Useful for detecting unexpected restarts during failover testing or incidents.

    • For RDS MySQL, the key operational metrics are the standard set:

  • → `FreeStorageSpace`: Must be monitored actively; RDS MySQL does not grow storage automatically unless you enable storage autoscaling.
  • → `FreeableMemory`: If this drops to near zero, MySQL is under memory pressure. The buffer pool may need shrinking or the instance class needs increasing.
  • → `ReadLatency` / `WriteLatency`: Storage I/O latency at the EBS layer.
  • → `ReplicaLag`: Binlog replication lag in seconds on read replicas. Alert at any value above your acceptable staleness threshold.
  • → `DiskQueueDepth`: Queue of pending I/O operations to EBS. Sustained high values indicate I/O saturation; increase provisioned IOPS or switch to gp3 with higher IOPS allocation.

    • Performance Insights for identifying slow queries

    Both Aurora MySQL and RDS MySQL expose Performance Insights. Enable it at provisioning time (it is not retroactive for historical data). Performance Insights surfaces the top SQL statements by average active sessions (AAS), allowing you to identify which queries are consuming the most database time without requiring slow_query_log parsing.

    # Query Performance Insights data via CLI (last hour of top SQL)
aws pi get-resource-metrics \
  --service-type RDS \
  --identifier db-ABCDEFGHIJKLMNOPQRSTUVWXYZ \
  --metric-queries '[{
    "Metric": "db.load.avg",
    "GroupBy": {
      "Group": "db.sql",
      "Limit": 10
    }
  }]' \
  --start-time $(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period-in-seconds 60

    The db.load.avg metric represents average active sessions broken down by the grouping dimension — here, db.sql. The output ranks SQL statements by how much database load they generate. A query appearing at the top of this list with an AAS value greater than the number of vCPUs on your instance is a query that is saturating available concurrency.

    8.7 Schema Changes and Online DDL in Aurora vs RDS MySQL

    Schema changes are one of the most operationally fraught areas in MySQL production management. MySQL 8.0 improved online DDL substantially through the ALGORITHM=INSTANT path for many common operations, but not all DDL can run without locking. Understanding what runs instantly, what runs online but takes time, and what requires a full table rebuild — and how Aurora's storage architecture affects each — is essential for zero-downtime deployments.

    DDL algorithm tiers in MySQL 8.0:

  • → `ALGORITHM=INSTANT`: Modifies only metadata. Completes in milliseconds regardless of table size. Works for adding columns (with restrictions), changing default values, changing column comments, renaming indexes.
  • → `ALGORITHM=INPLACE`: Performs the rebuild in-place, allowing concurrent DML. Takes time proportional to table size, but does not copy the full table to a new location. Adding indexes falls here.
  • → `ALGORITHM=COPY`: Creates a full copy of the table. Blocks concurrent DML writes during the copy. Should be avoided on large tables in production.
    • -- Check which algorithm MySQL will use for a given ALTER
ALTER TABLE orders
  ADD COLUMN discount_code VARCHAR(50) DEFAULT NULL,
  ALGORITHM=INSTANT;  -- Will succeed instantly on MySQL 8.0.29+

-- Adding a non-nullable column without default cannot use INSTANT
-- This falls back to INPLACE or COPY
ALTER TABLE orders
  ADD COLUMN region_id INT NOT NULL,
  ALGORITHM=INPLACE,
  LOCK=NONE;  -- LOCK=NONE ensures you get an error rather than a silent lock

-- Adding an index: INPLACE, allows concurrent DML
ALTER TABLE orders
  ADD INDEX idx_customer_date (customer_id, order_date),
  ALGORITHM=INPLACE,
  LOCK=NONE;

-- Changing column data type: typically COPY, blocks writes
-- Use pt-online-schema-change or gh-ost instead
ALTER TABLE orders
  MODIFY COLUMN amount DECIMAL(12,4),
  ALGORITHM=COPY;  -- Explicitly label it so you're not surprised

    On Aurora MySQL, INPLACE DDL benefits from the storage architecture in one meaningful way: because Aurora readers share the same storage pages, there is no need to replay DDL changes on each replica as a separate binlog event. However, large INPLACE operations still consume I/O and CPU on the writer, and readers will see a brief period of elevated lag in their buffer cache view while catching up to the new page versions.

    Using gh-ost for large table changes on Aurora MySQL

    For any table change that cannot use ALGORITHM=INSTANT, and where the table exceeds a size at which INPLACE operation would cause unacceptable production impact, gh-ost (GitHub's Online Schema Tool) is the standard tool. It works by replicating binlog events from the writer in real time, applying them to a shadow table alongside the bulk copy, and atomically swapping the tables when the copy is complete.

    gh-ost requires binlog enabled on Aurora (binlog_format=ROW, binlog_row_image=FULL). To connect gh-ost to Aurora, point it at the cluster's reader endpoint as the replica source — this avoids adding binlog read load to the writer directly.

    gh-ost \
  --user="ghuser" \
  --password="ghpassword" \
  --host="prod-aurora-mysql.cluster-ro-abc123.us-east-1.rds.amazonaws.com" \
  --port=3306 \
  --database="appdb" \
  --table="orders" \
  --alter="ADD COLUMN discount_code VARCHAR(50) DEFAULT NULL" \
  --master-user="ghuser" \
  --master-password="ghpassword" \
  --assume-master-host="prod-aurora-mysql.cluster-abc123.us-east-1.rds.amazonaws.com" \
  --chunk-size=1000 \
  --max-load="Threads_running=50" \
  --critical-load="Threads_running=100" \
  --switch-to-rbr \
  --allow-on-master \
  --execute

    The --host flag points at the reader endpoint; --assume-master-host points at the writer endpoint. gh-ost reads binlog from the writer (via the explicit master host) but throttles itself based on load metrics read from the reader. Set --max-load and --critical-load conservatively for production: if the writer's Threads_running exceeds your threshold, gh-ost pauses the copy automatically.

    pt-online-schema-change from Percona Toolkit is an alternative that uses triggers rather than binlog replication. On Aurora, gh-ost is generally preferred because trigger-based approaches can introduce write amplification and unexpected locking behavior at high concurrency.

    8.8 Choosing Between Aurora MySQL and RDS MySQL

    The choice between Aurora MySQL and RDS MySQL is not always obvious and depends heavily on workload characteristics, team operational preferences, and cost sensitivity. Here is a decision framework based on production scenarios.

    Choose Aurora MySQL when:

  • → Your application requires sub-30-second failover and you cannot tolerate 60–120 seconds of downtime during a Multi-AZ RDS failover.
  • → You need more than 5 read replicas, or you cannot accept binlog replication lag on your read replicas.
  • → Your write throughput is high enough that the double-write buffer overhead on standard InnoDB would be a bottleneck. This threshold varies by instance size and I/O pattern, but Aurora's log-based storage consistently outperforms equivalent RDS MySQL instances at high sustained write rates.
  • → You want fast database cloning for staging, migration testing, or branch development environments (Aurora Fast Clone).
  • → You need multi-region replication with sub-second lag and managed failover (Aurora Global Database).
  • → Your storage needs are unpredictable or growing rapidly — Aurora auto-grows without intervention.
  • → You are deploying a new application and have no migration cost from self-managed MySQL.

    • Choose RDS MySQL when:

  • → You need a specific MySQL version or plugin that Aurora MySQL does not support. Aurora MySQL lags behind community MySQL releases, and not every plugin or storage engine is available.
  • → Your workload is read-heavy with low write rates, and cost is a priority. RDS MySQL with read replicas can be meaningfully cheaper for this profile.
  • → You rely on MySQL features that Aurora does not expose identically — for example, certain full-text search behaviors, spatial data handling, or specific InnoDB configuration parameters that Aurora overrides.
  • → You need a staging or development environment where simplicity matters more than HA — a single-AZ RDS MySQL instance is the cheapest managed MySQL option on AWS.
  • → Your team has deep on-prem MySQL operational expertise and you are migrating with minimal changes. RDS MySQL behaves more like "MySQL you recognize" and fewer Aurora-specific behaviors will surprise you during the migration.
  • → You are running an engine version or configuration that you must validate against community MySQL behavior exactly, such as for a vendor-certified application stack.

    • Cost comparison guidance

    Aurora MySQL is priced at a higher per-instance-hour rate than comparable RDS MySQL instance classes, plus per-I/O charges on storage. For write-intensive workloads, Aurora's I/O costs can accumulate significantly. Aurora I/O-Optimized pricing (a newer pricing tier that eliminates per-I/O charges in exchange for a higher instance price) is worth evaluating if your I/O cost constitutes a large fraction of your Aurora bill. Run a cost comparison using your current storage bytes, I/O operations per second (visible in CloudWatch), and retention period against both pricing models before committing to either.

    There is no single right answer. The scenarios above are starting points. Run both options through your actual workload profile, model the cost, and validate failover behavior in a staging environment before making the call in production.

    Key Takeaways

  • → **Aurora MySQL and RDS MySQL are architecturally distinct**: Aurora separates compute from storage with a distributed, quorum-based storage layer that eliminates double-write buffer overhead and enables faster failover. RDS MySQL runs standard InnoDB against local EBS storage, behaving more like a managed version of self-managed MySQL.
  • → **Failover and replication are fundamentally different**: Aurora achieves sub-30-second failover because readers share the same storage volume as the writer. RDS MySQL Multi-AZ failover relies on block-level replication to a non-readable standby and typically takes 60–120 seconds. RDS MySQL read replicas use binlog replication and can lag significantly under heavy write load; Aurora readers do not.
  • → **Parameter groups in Aurora have two tiers**: Cluster-level parameter groups control settings shared across all instances (character sets, binlog format, slow query logging). Instance-level parameter groups control per-instance settings. RDS MySQL has only instance-level parameter groups. Misconfiguring this distinction is a common migration pitfall.
  • → **RDS Proxy solves connection exhaustion but requires application awareness**: Proxy connection pooling is essential for serverless or highly concurrent application patterns, but session-level state (user variables, temporary tables, LOCK TABLES) causes connection pinning that defeats pooling efficiency. Audit your application's session state usage before enabling RDS Proxy.
  • → **Schema changes require careful DDL strategy in both products**: Use `ALGORITHM=INSTANT` wherever MySQL 8.0 supports it. For large tables requiring INPLACE or COPY operations, use `gh-ost` with binlog-based replication rather than trigger-based tools. Aurora's shared storage architecture means DDL changes do not need to be replayed individually on each reader via binlog, but large INPLACE operations still carry meaningful write-side cost on the cluster.
