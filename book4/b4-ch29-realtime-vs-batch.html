Chapter 29: Real-Time vs Batch Embedding Generation

Embedding generation sits at the boundary between your application's request path and your vector database's indexing pipeline. Every vector in your store started as a raw document, image, or structured record that passed through a model to become a float array — and the decision about *when* that transformation happens shapes your latency profile, cost structure, operational complexity, and freshness guarantees in ways that compound at scale. This chapter maps out the two fundamental strategies — real-time and batch — examines where each breaks down, and shows the hybrid architectures that production systems almost always end up building.

---

29.1 Understanding the Embedding Generation Pipeline

Before choosing a strategy, you need a clear model of what the pipeline actually does. Embedding generation is a compute-intensive inference step: a neural network reads tokens, runs a forward pass, and returns a fixed-size dense vector. That vector is then written to your vector store and becomes searchable.

Think of it like a computed column in a relational database. You have a source table of raw content and a derived representation stored separately for efficient retrieval. The question isn't whether to compute it — you must — it's whether you compute it synchronously during write operations or asynchronously in a scheduled or streaming process.

The pipeline stages:

Raw Content → Chunking/Preprocessing → Model Inference → Vector Storage → Index Build

Each stage introduces latency and can fail independently. In real-time mode, all of this sits in your request path. In batch mode, only the final query lookup is synchronous.

Key parameters that drive strategy selection:

| Parameter | Favors Real-Time | Favors Batch |

|---|---|---|

| Content ingestion rate | Low to moderate | High volume |

| Latency tolerance | < 500ms end-to-end | Minutes to hours acceptable |

| Content update frequency | Continuous | Periodic |

| Embedding model size | API-hosted, fast | Large local models |

| Cost sensitivity | Bursty, pay-per-call | Predictable volume pricing |

| Content at query time | Dynamic, user-generated | Stable corpus |

The embedding model itself is the most constrained resource. OpenAI's text-embedding-3-small processes roughly 1M tokens per minute on the API tier, costing $0.02 per 1M tokens. A local sentence-transformers/all-MiniLM-L6-v2 running on CPU processes approximately 500 sentences per second on a modern machine — fast enough for many real-time use cases, but it becomes a bottleneck as soon as content volume spikes.

---

29.2 Real-Time Embedding Generation

Real-time embedding generation means computing vectors synchronously as new content arrives — either during document ingestion or at query time for incoming search strings. The user or upstream system waits for the embedding to complete before the request continues.

When this approach works well:

  • → A user submits a search query and you need the query embedding immediately
  • → A chat application ingests user messages that must be retrievable within seconds
  • → An API receives webhook events that feed a RAG pipeline with sub-minute freshness requirements

    • When it breaks:

  • → Document ingestion volume spikes (model API rate limits become throttling events)
  • → Embedding latency becomes the dominant term in your p95 response time
  • → Upstream content sources send batches disguised as streams (100 documents at once)

    • The following example shows a FastAPI endpoint that ingests documents and generates embeddings synchronously using the OpenAI API and pgvector for storage:

    # Python
import asyncio
import time
from typing import Optional

import asyncpg
from fastapi import FastAPI, HTTPException
from openai import AsyncOpenAI
from pydantic import BaseModel

app = FastAPI()
openai_client = AsyncOpenAI()

# Connection pool — reuse across requests
pool: Optional[asyncpg.Pool] = None


async def get_pool() -> asyncpg.Pool:
    global pool
    if pool is None:
        pool = await asyncpg.create_pool(
            dsn="postgresql://app_user:secret@localhost:5432/vectordb",
            min_size=5,
            max_size=20,
        )
    return pool


class DocumentIngest(BaseModel):
    document_id: str
    content: str
    metadata: dict = {}


class SearchQuery(BaseModel):
    query: str
    top_k: int = 10


@app.post("/documents")
async def ingest_document(doc: DocumentIngest):
    """Real-time ingestion: embed and store in a single synchronous operation."""
    start = time.monotonic()

    # Step 1: Generate embedding — this is the latency bottleneck
    try:
        response = await openai_client.embeddings.create(
            model="text-embedding-3-small",
            input=doc.content,
            encoding_format="float",
        )
    except Exception as e:
        raise HTTPException(status_code=502, detail=f"Embedding API error: {e}")

    embedding = response.data[0].embedding
    embed_latency_ms = (time.monotonic() - start) * 1000

    # Step 2: Write to pgvector
    db = await get_pool()
    try:
        await db.execute(
            """
            INSERT INTO documents (document_id, content, embedding, metadata, embedded_at)
            VALUES ($1, $2, $3::vector, $4, NOW())
            ON CONFLICT (document_id) DO UPDATE
              SET content = EXCLUDED.content,
                  embedding = EXCLUDED.embedding,
                  embedded_at = NOW()
            """,
            doc.document_id,
            doc.content,
            str(embedding),
            doc.metadata,
        )
    except Exception as e:
        raise HTTPException(status_code=500, detail=f"DB write error: {e}")

    total_latency_ms = (time.monotonic() - start) * 1000

    return {
        "document_id": doc.document_id,
        "embed_latency_ms": round(embed_latency_ms, 2),
        "total_latency_ms": round(total_latency_ms, 2),
        "dimensions": len(embedding),
    }


@app.post("/search")
async def search(query: SearchQuery):
    """Query embedding is always real-time — there is no alternative."""
    response = await openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=query.query,
        encoding_format="float",
    )
    query_vector = response.data[0].embedding

    db = await get_pool()
    rows = await db.fetch(
        """
        SELECT document_id, content, metadata,
               1 - (embedding <=> $1::vector) AS cosine_similarity
        FROM documents
        ORDER BY embedding <=> $1::vector
        LIMIT $2
        """,
        str(query_vector),
        query.top_k,
    )

    return [dict(r) for r in rows]

    The critical observation here: query embedding is *always* real-time. You cannot precompute embeddings for arbitrary user queries. The only decision is whether document embeddings are also real-time or handled separately.

    Concurrency and rate limit management become the primary operational concerns. A real-time pipeline that handles 50 concurrent document writes will fire 50 simultaneous API calls. OpenAI's text-embedding-3-small has a default rate limit of 3,000 RPM (requests per minute) on paid tiers — roughly 50 per second. You need a semaphore or queue to stay within bounds:

    # Python
import asyncio
from openai import AsyncOpenAI

client = AsyncOpenAI()

# Limit concurrent embedding calls to avoid rate limit errors
EMBED_SEMAPHORE = asyncio.Semaphore(20)


async def safe_embed(text: str, model: str = "text-embedding-3-small") -> list[float]:
    """Rate-limited embedding call with exponential backoff."""
    async with EMBED_SEMAPHORE:
        for attempt in range(4):
            try:
                response = await client.embeddings.create(
                    model=model,
                    input=text,
                    encoding_format="float",
                )
                return response.data[0].embedding
            except Exception as e:
                if "rate_limit" in str(e).lower() and attempt < 3:
                    wait = (2**attempt) + 0.1
                    await asyncio.sleep(wait)
                else:
                    raise


async def embed_batch_concurrent(texts: list[str], max_concurrency: int = 20) -> list[list[float]]:
    """Embed a list of texts with bounded concurrency."""
    tasks = [safe_embed(t) for t in texts]
    return await asyncio.gather(*tasks)

    29.3 Batch Embedding Generation

    Batch processing treats embedding generation as an offline transformation job — a scheduled or event-triggered pipeline that processes accumulated content and writes vectors to the store without blocking application writes. The source system records raw content immediately; embedding happens asynchronously.

    This maps directly to the ETL/ELT model that DBAs know well. The source table stores canonical data, and a separate process materializes the derived representation. You can think of it as a materialized view that refreshes on a schedule, except the "computation" is a neural network inference rather than a SQL aggregation.

    Architecture pattern:

    Source Table (raw) → Embedding Worker → Vector Store
     ↓ writes immediately               ↑ available after job completes
     ↓ marks as embedding_status='pending'

    The embedding_status column is the coordination mechanism. Writers insert content and mark it pending; the embedding worker polls or subscribes for pending records, processes them in optimized batches, and marks them complete.

    -- PostgreSQL / pgvector

-- Source table with embedding lifecycle tracking
CREATE TABLE documents (
    id             BIGSERIAL PRIMARY KEY,
    document_id    TEXT UNIQUE NOT NULL,
    content        TEXT NOT NULL,
    content_hash   TEXT GENERATED ALWAYS AS (md5(content)) STORED,
    embedding      vector(1536),
    embed_model    TEXT,
    embedding_status TEXT NOT NULL DEFAULT 'pending'
                   CHECK (embedding_status IN ('pending', 'processing', 'complete', 'failed')),
    retry_count    INT NOT NULL DEFAULT 0,
    embedded_at    TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Index for the worker's polling query — only pending/failed rows
CREATE INDEX idx_documents_embed_queue
    ON documents (created_at)
    WHERE embedding_status IN ('pending', 'failed') AND retry_count < 3;

-- Claim a batch atomically using SKIP LOCKED — prevents double-processing
-- across multiple worker instances
CREATE OR REPLACE FUNCTION claim_embedding_batch(batch_size INT)
RETURNS SETOF documents AS $$
    UPDATE documents
    SET embedding_status = 'processing',
        updated_at = NOW()
    WHERE id IN (
        SELECT id FROM documents
        WHERE embedding_status IN ('pending', 'failed')
          AND retry_count < 3
        ORDER BY created_at
        LIMIT batch_size
        FOR UPDATE SKIP LOCKED
    )
    RETURNING *;
$$ LANGUAGE sql;

    The FOR UPDATE SKIP LOCKED pattern is the same technique used in job queue implementations like Sidekiq's PostgreSQL backend. Multiple embedding workers can run in parallel without coordination — each atomically claims its batch, processes it, and writes results back.

    # Python
import time
from datetime import datetime
from typing import Optional

import psycopg2
import psycopg2.extras
from sentence_transformers import SentenceTransformer

# Using a local model for batch processing — no API costs, full throughput control
model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
MODEL_NAME = "all-MiniLM-L6-v2"
BATCH_SIZE = 256  # Optimal for CPU inference; increase to 512+ with GPU


def get_connection():
    return psycopg2.connect(
        dsn="postgresql://app_user:secret@localhost:5432/vectordb"
    )


def process_batch(conn) -> int:
    """Claim and process one batch of pending documents. Returns count processed."""
    with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
        # Atomically claim a batch
        cur.execute("SELECT * FROM claim_embedding_batch(%s)", (BATCH_SIZE,))
        rows = cur.fetchall()
        conn.commit()

    if not rows:
        return 0

    ids = [r["id"] for r in rows]
    texts = [r["content"] for r in rows]

    start = time.monotonic()
    # sentence-transformers handles internal batching efficiently
    embeddings = model.encode(
        texts,
        batch_size=64,
        show_progress_bar=False,
        normalize_embeddings=True,  # Cosine similarity becomes dot product
    )
    inference_ms = (time.monotonic() - start) * 1000

    # Bulk update — much faster than row-by-row
    with conn.cursor() as cur:
        update_data = [
            (
                embeddings[i].tolist(),
                MODEL_NAME,
                "complete",
                datetime.utcnow(),
                ids[i],
            )
            for i in range(len(ids))
        ]
        psycopg2.extras.execute_batch(
            cur,
            """
            UPDATE documents
            SET embedding = %s::vector,
                embed_model = %s,
                embedding_status = %s,
                embedded_at = %s,
                updated_at = NOW()
            WHERE id = %s
            """,
            update_data,
            page_size=100,
        )
        conn.commit()

    throughput = len(ids) / (inference_ms / 1000)
    print(
        f"Processed {len(ids)} docs in {inference_ms:.0f}ms "
        f"({throughput:.0f} docs/sec)"
    )
    return len(ids)


def handle_failures(conn, failed_ids: list[int]):
    """Mark failed rows for retry or permanent failure."""
    with conn.cursor() as cur:
        cur.execute(
            """
            UPDATE documents
            SET embedding_status = CASE
                WHEN retry_count >= 2 THEN 'failed'
                ELSE 'pending'
            END,
            retry_count = retry_count + 1,
            updated_at = NOW()
            WHERE id = ANY(%s)
            """,
            (failed_ids,),
        )
        conn.commit()


def run_worker(idle_sleep_sec: float = 5.0):
    """Continuous worker loop."""
    conn = get_connection()
    print(f"Embedding worker started. Model: {MODEL_NAME}, Batch size: {BATCH_SIZE}")
    try:
        while True:
            processed = process_batch(conn)
            if processed == 0:
                time.sleep(idle_sleep_sec)
    finally:
        conn.close()


if __name__ == "__main__":
    run_worker()

    Throughput benchmarks with local models are worth establishing early. On a single CPU worker with all-MiniLM-L6-v2:

  • → Batch size 64: ~400 docs/sec
  • → Batch size 256: ~600 docs/sec
  • → Batch size 512: ~650 docs/sec (diminishing returns)

    • On a single A10G GPU:

  • → Batch size 256: ~4,500 docs/sec
  • → Batch size 1024: ~8,000 docs/sec

    • For comparison, OpenAI's batch embedding API (asynchronous, 50% cheaper than synchronous) processes up to 50,000 requests per batch with a 24-hour completion window.

    29.4 Hybrid Architectures: Combining Both Strategies

    Production systems rarely use pure real-time or pure batch. The practical pattern is a tiered architecture where query embeddings are always real-time, freshly ingested high-priority content uses real-time embedding with graceful degradation, and bulk content uses batch processing.

    A common pattern that works well: write the raw document to storage immediately (making it visible to the application), generate the embedding asynchronously, and return a pending state to callers that need to know embedding status. This is analogous to an eventually consistent write — your database accepts the write, your derived index catches up.

    graph TD
    A[Document ingested] --> B{Priority?}
    B -->|HIGH
    SLA < 2s| C[Synchronous embed
    + write inline]
    B -->|NORMAL
    up to 30s| D[Enqueue to
    Redis Streams / Kafka]
    B -->|LOW
    up to hours| D
    D --> E[Async worker:
    batch embed + upsert]
    C --> F[Vector store]
    E --> F
    G[Query embedding] -.always synchronous.-> F

    *Query embedding always sits on the synchronous path; document embedding is routed by priority in a hybrid tiered architecture.*

    The following example shows this pattern using Pinecone as the vector store and a message queue (Redis Streams) for coordination:

    # Python
import json
import time
import uuid
from enum import Enum
from typing import Optional

import redis
from openai import OpenAI
from pinecone import Pinecone, ServerlessSpec

# Configuration
REDIS_URL = "redis://localhost:6379"
PINECONE_API_KEY = "your-pinecone-key"
PINECONE_INDEX = "documents-prod"
EMBED_MODEL = "text-embedding-3-small"
EMBED_DIMS = 1536
STREAM_KEY = "embed:queue"
CONSUMER_GROUP = "embed-workers"

# Clients
redis_client = redis.from_url(REDIS_URL, decode_responses=True)
openai_client = OpenAI()
pc = Pinecone(api_key=PINECONE_API_KEY)

# Ensure index exists
if PINECONE_INDEX not in [i.name for i in pc.list_indexes()]:
    pc.create_index(
        name=PINECONE_INDEX,
        dimension=EMBED_DIMS,
        metric="cosine",
        spec=ServerlessSpec(cloud="aws", region="us-east-1"),
    )

index = pc.Index(PINECONE_INDEX)


class EmbedPriority(str, Enum):
    HIGH = "high"   # Real-time path: SLA < 2 seconds
    NORMAL = "normal"  # Async path: acceptable delay up to 30 seconds
    LOW = "low"        # Batch path: delay up to hours acceptable


def ingest_document(
    document_id: str,
    content: str,
    metadata: dict,
    priority: EmbedPriority = EmbedPriority.NORMAL,
) -> dict:
    """
    Write document to the queue. HIGH priority documents are embedded inline.
    NORMAL/LOW are deferred to the async worker.
    """
    if priority == EmbedPriority.HIGH:
        # Synchronous path — caller waits for embedding
        embedding = _embed_text(content)
        _write_to_pinecone(document_id, embedding, content, metadata)
        return {"document_id": document_id, "status": "indexed", "priority": priority}
    else:
        # Async path — enqueue for worker
        message = {
            "document_id": document_id,
            "content": content,
            "metadata": json.dumps(metadata),
            "priority": priority,
            "enqueued_at": time.time(),
        }
        redis_client.xadd(STREAM_KEY, message, maxlen=100_000)
        return {"document_id": document_id, "status": "pending", "priority": priority}


def _embed_text(text: str) -> list[float]:
    response = openai_client.embeddings.create(
        model=EMBED_MODEL,
        input=text,
        encoding_format="float",
    )
    return response.data[0].embedding


def _write_to_pinecone(
    document_id: str,
    embedding: list[float],
    content: str,
    metadata: dict,
):
    index.upsert(
        vectors=[{
            "id": document_id,
            "values": embedding,
            "metadata": {**metadata, "content_preview": content[:500]},
        }],
        namespace="documents",
    )


def run_async_worker(batch_size: int = 50, idle_sleep: float = 1.0):
    """
    Redis Streams consumer that processes the embedding queue.
    Multiple instances can run concurrently — each reads from the same group.
    """
    worker_id = f"worker-{uuid.uuid4().hex[:8]}"

    # Create consumer group if it doesn't exist
    try:
        redis_client.xgroup_create(STREAM_KEY, CONSUMER_GROUP, id="0", mkstream=True)
    except redis.exceptions.ResponseError:
        pass  # Group already exists

    print(f"Worker {worker_id} started, consuming from {STREAM_KEY}")

    while True:
        # Read up to batch_size messages, blocking for 1 second if queue is empty
        messages = redis_client.xreadgroup(
            groupname=CONSUMER_GROUP,
            consumername=worker_id,
            streams={STREAM_KEY: ">"},
            count=batch_size,
            block=int(idle_sleep * 1000),
        )

        if not messages:
            continue

        stream_messages = messages[0][1]  # (stream_key, [(msg_id, fields), ...])
        msg_ids = [m[0] for m in stream_messages]
        payloads = [m[1] for m in stream_messages]

        # Sort by priority — HIGH items get embedded first within the batch
        payloads_with_ids = sorted(
            zip(msg_ids, payloads),
            key=lambda x: 0 if x[1]["priority"] == EmbedPriority.HIGH else 1,
        )

        texts = [p["content"] for _, p in payloads_with_ids]

        # Batch embed — single API call for the whole batch
        try:
            response = openai_client.embeddings.create(
                model=EMBED_MODEL,
                input=texts,
                encoding_format="float",
            )
            embeddings = [d.embedding for d in response.data]
        except Exception as e:
            print(f"Embedding batch failed: {e}")
            # Messages remain in PEL (pending entries list) for reprocessing
            time.sleep(5)
            continue

        # Upsert to Pinecone in a single batch call
        vectors = []
        for i, (msg_id, payload) in enumerate(payloads_with_ids):
            vectors.append({
                "id": payload["document_id"],
                "values": embeddings[i],
                "metadata": {
                    **json.loads(payload["metadata"]),
                    "content_preview": payload["content"][:500],
                    "embedded_at": time.time(),
                },
            })

        index.upsert(vectors=vectors, namespace="documents")

        # Acknowledge successful processing
        redis_client.xack(STREAM_KEY, CONSUMER_GROUP, *msg_ids)
        print(f"Worker {worker_id}: processed {len(vectors)} documents")

    This architecture gives you exactly three knobs to tune: the concurrency of async workers, the batch size per worker iteration, and the priority threshold for synchronous embedding. Most teams start with HIGH priority for user-generated content that needs immediate search availability and NORMAL/LOW for system-generated or bulk content.

    29.5 Cost Optimization and Model Selection

    Embedding generation costs break down differently depending on your strategy. Real-time API calls are billed per token with no volume discount at standard tiers; batch jobs can qualify for discounted batch pricing or allow you to substitute cheaper local models where latency isn't constrained.

    Cost comparison for 100M tokens per month:

    | Model | Mode | Cost (per 1M tokens) | Latency (p50) |

    |---|---|---|---|

    | OpenAI text-embedding-3-small | Synchronous API | Check current pricing | ~80ms |

    | OpenAI text-embedding-3-small | Batch API | Discounted tier | Up to 24h |

    | OpenAI text-embedding-ada-002 | Synchronous API | Check current pricing | ~100ms |

    | Cohere embed-v3 | Synchronous API | Check current pricing | ~120ms |

    | all-MiniLM-L6-v2 | Local CPU(384 dims) | Infrastructure cost only | ~2ms |

    | all-mpnet-base-v2 | Local CPU (768 dims) | Infrastructure cost only | ~8ms |

    | bge-large-en-v1.5 | Local GPU (1024 dims) | Infrastructure cost only | ~0.5ms |

    The cost calculus depends on your quality requirements. all-MiniLM-L6-v2 achieves strong semantic retrieval performance on most English-language tasks; the quality gap versus OpenAI's models narrows significantly when your retrieval task is domain-specific and you fine-tune or use a retrieval-oriented model. For bulk batch processing where quality matters and cost is constrained, a local GPU-hosted model is typically the right answer once your volume justifies the infrastructure.

    Model selection decision tree:

    Need multilingual support?
  ├─ Yes → OpenAI text-embedding-3-large or Cohere embed-multilingual-v3
  └─ No → Continue
      │
Need < 200ms embedding latency (real-time path)?
  ├─ Yes → OpenAI text-embedding-3-small (API) or all-MiniLM-L6-v2 (local)
  └─ No (batch path) → any local model, batch API acceptable
      │
Volume > 50M tokens/month?
  ├─ Yes → Evaluate local GPU hosting vs. batch API pricing
  └─ No → Synchronous API is likely cost-effective
      │
Offline / air-gapped / compliance-constrained?
  └─ Always → Local model required

    Caching embeddings is an underutilized optimization in real-time pipelines. If your application re-embeds the same content (common in chat applications where system prompts are re-embedded on every session), a simple LRU cache keyed on content hash eliminates redundant API calls:

    # Python
import hashlib
from functools import lru_cache
from openai import OpenAI

client = OpenAI()


def content_hash(text: str) -> str:
    return hashlib.sha256(text.encode()).hexdigest()


# In-process LRU cache for embeddings — survives for the process lifetime
# For cross-process caching, use Redis with TTL
@lru_cache(maxsize=10_000)
def _cached_embed(text_hash: str, text: str, model: str) -> tuple[float, ...]:
    """
    LRU cache keyed by content hash. Returns tuple (hashable) rather than list.
    text_hash is included in the key to force cache invalidation on content change,
    but the actual hash computation happens outside this function.
    """
    response = client.embeddings.create(
        model=model,
        input=text,
        encoding_format="float",
    )
    return tuple(response.data[0].embedding)


def embed_with_cache(text: str, model: str = "text-embedding-3-small") -> list[float]:
    h = content_hash(text)
    return list(_cached_embed(h, text, model))

    For distributed caching across worker instances, use Redis with a content-hash key and an appropriate TTL:

    # Python
import hashlib
import json
import redis
from openai import OpenAI

client = OpenAI()
cache = redis.from_url("redis://localhost:6379", decode_responses=True)

CACHE_TTL_SECONDS = 86_400 * 7  # 7 days


def embed_with_redis_cache(
    text: str,
    model: str = "text-embedding-3-small",
) -> list[float]:
    key = f"emb:{model}:{hashlib.sha256(text.encode()).hexdigest()}"
    cached = cache.get(key)
    if cached:
        return json.loads(cached)

    response = client.embeddings.create(
        model=model,
        input=text,
        encoding_format="float",
    )
    embedding = response.data[0].embedding
    cache.setex(key, CACHE_TTL_SECONDS, json.dumps(embedding))
    return embedding

    A cache hit rate of even 30–40% on a high-traffic real-time system meaningfully reduces both API costs and p95 latency, since cache reads are an order of magnitude faster than embedding API calls.

    29.6 Monitoring and Observability

    Embedding pipelines have failure modes that are invisible to standard application monitoring. A real-time pipeline can silently degrade — API calls succeed but return nonsensical embeddings due to truncation, rate limiting, or model version drift — and you won't see it in error rates. A batch pipeline can fall arbitrarily far behind its queue without triggering obvious alerts.

    Metrics to instrument for real-time pipelines:

    # Python — using prometheus_client for illustration
from prometheus_client import Counter, Histogram, Gauge
import time

embed_latency = Histogram(
    "embedding_generation_seconds",
    "Time to generate an embedding",
    buckets=[0.05, 0.1, 0.2, 0.5, 1.0, 2.0, 5.0],
    labelnames=["model", "source"],  # source: realtime, cache, batch
)

embed_errors = Counter(
    "embedding_errors_total",
    "Embedding generation failures",
    labelnames=["model", "error_type"],  # error_type: rate_limit, timeout, other
)

embed_cache_hits = Counter(
    "embedding_cache_hits_total",
    "Embedding cache hits",
    labelnames=["model"],
)

embed_tokens = Counter(
    "embedding_tokens_total",
    "Total tokens sent for embedding",
    labelnames=["model"],
)


def instrumented_embed(text: str, model: str = "text-embedding-3-small") -> list[float]:
    start = time.monotonic()
    token_count = len(text.split())  # rough approximation

    try:
        embedding = embed_with_redis_cache(text, model)
        embed_latency.labels(model=model, source="realtime").observe(
            time.monotonic() - start
        )
        embed_tokens.labels(model=model).inc(token_count)
        return embedding
    except Exception as e:
        error_type = "rate_limit" if "rate" in str(e).lower() else "other"
        embed_errors.labels(model=model, error_type=error_type).inc()
        raise

    Metrics to instrument for batch pipelines:

    -- PostgreSQL — queue depth monitoring view
-- Run this periodically and emit to your metrics system

CREATE VIEW embedding_queue_health AS
SELECT
    embedding_status,
    COUNT(*) AS document_count,
    MIN(created_at) AS oldest_pending,
    NOW() - MIN(created_at) AS max_lag_interval,
    AVG(retry_count) AS avg_retries
FROM documents
GROUP BY embedding_status;
    # Python — scrape the health view and emit metrics
from prometheus_client import Gauge
import psycopg2

queue_depth = Gauge(
    "embedding_queue_depth",
    "Number of documents awaiting embedding",
    labelnames=["status"],
)

queue_lag_seconds = Gauge(
    "embedding_queue_lag_seconds",
    "Age of oldest pending document in the embedding queue",
)


def scrape_queue_metrics(conn):
    with conn.cursor() as cur:
        cur.execute("SELECT * FROM embedding_queue_health")
        rows = cur.fetchall()

    for row in rows:
        status, count, oldest, lag_interval, avg_retries = row
        queue_depth.labels(status=status).set(count)
        if status == "pending" and lag_interval is not None:
            queue_lag_seconds.set(lag_interval.total_seconds())

    Alert thresholds that matter in practice:

  • → Real-time: p95 embedding latency > 1 second → likely rate limiting or network issue
  • → Real-time: error rate > 0.5% over 5 minutes → alert immediately
  • → Batch: queue lag (age of oldest pending) > 10 minutes for HIGH priority content → worker stalled
  • → Batch: `failed` status count growing monotonically → retry logic broken or content issue
  • → Both: embedding dimension mismatch → model version changed, index incompatible

    • The dimension mismatch case deserves special attention. If you switch models (e.g., from text-embedding-ada-002 at 1536 dimensions to text-embedding-3-large at 3072 dimensions), you cannot mix vectors in the same index. Your pipeline needs to track embed_model alongside each vector and either maintain separate indexes per model version or perform a full re-embedding pass during migration.

    29.7 Re-Embedding and Index Migration

    Model upgrades and content updates both require re-embedding — and the strategy for doing so efficiently varies based on scale and urgency.

    Triggers for re-embedding:

    1. Content update: the underlying document changed, so the stored vector is stale

    2. Model upgrade: a better model is available and quality improvement justifies migration cost

    3. Dimension change: the new model produces vectors of a different size, requiring index rebuild

    4. Normalization change: you decide to switch from raw to normalized vectors (or vice versa)

    Detecting stale embeddings is straightforward if you store a content hash:

    -- PostgreSQL
-- Find documents whose content has changed since embedding was generated
SELECT document_id, content, embedded_at
FROM documents
WHERE content_hash != md5(content)  -- content has changed since last embed
   OR embedded_at IS NULL           -- never embedded
   OR embed_model != 'text-embedding-3-small'  -- model version changed
ORDER BY created_at DESC;

    The content_hash column defined as a generated column (as shown in section 29.3) eliminates the need to compute this manually — PostgreSQL maintains it automatically on every update.

    Zero-downtime model migration pattern:

    The safest approach for model migrations mirrors a blue/green deployment. Build the new index in parallel while the old index continues serving queries, then perform a cut-over once re-embedding is complete.

    -- PostgreSQL — dual-index migration setup

-- New index for the upgraded model (different dimension)
CREATE TABLE documents_v2 AS TABLE documents WITH NO DATA;
ALTER TABLE documents_v2 ADD COLUMN embedding_v2 vector(3072);

-- Track migration progress
ALTER TABLE documents ADD COLUMN embed_v2_status TEXT DEFAULT 'pending';

-- Worker migrates batches from documents → documents_v2
-- Queries can be directed to either table via a view
CREATE OR REPLACE VIEW documents_current AS
SELECT
    d.document_id,
    d.content,
    COALESCE(d2.embedding_v2, d.embedding) AS embedding,
    CASE
        WHEN d2.embedding_v2 IS NOT NULL THEN 'v2'
        ELSE 'v1'
    END AS embed_version
FROM documents d
LEFT JOIN documents_v2 d2 USING (document_id);

    For Weaviate, which manages its own index internally, the migration requires a different approach — create a new class (collection) with the updated vectorizer configuration, re-ingest documents, verify result quality against a held-out query set, then update your application's class references:

    # Python — Weaviate collection migration
import weaviate
from weaviate.classes.config import Configure, Property, DataType

client = weaviate.connect_to_local()

# Create v2 collection with new model
client.collections.create(
    name="DocumentsV2",
    vectorizer_config=Configure.Vectorizer.text2vec_openai(
        model="text-embedding-3-large",  # Upgraded from 3-small
    ),
    properties=[
        Property(name="document_id", data_type=DataType.TEXT),
        Property(name="content", data_type=DataType.TEXT),
    ],
)

# Re-ingest — Weaviate generates embeddings via the configured vectorizer
collection_v2 = client.collections.get("DocumentsV2")
collection_v1 = client.collections.get("Documents")

# Batch migration with Weaviate's batch API
with collection_v2.batch.dynamic() as batch:
    for item in collection_v1.iterator():
        batch.add_object({
            "document_id": item.properties["document_id"],
            "content": item.properties["content"],
        })

# After verification, update application to read from DocumentsV2
# Then delete DocumentsV2 (old collection) after traffic cutover
client.close()

    Partial re-embedding is viable when only a subset of content needs updating. Use embed_model tracking to identify rows that need refresh:

    # Python — targeted re-embedding of content using old model version
import psycopg2
import psycopg2.extras
from sentence_transformers import SentenceTransformer

OLD_MODEL = "all-MiniLM-L6-v2"
NEW_MODEL = "all-mpnet-base-v2"

new_encoder = SentenceTransformer(NEW_MODEL)


def migrate_model_batch(conn, batch_size: int = 256):
    """Re-embed documents that were embedded with the old model."""
    with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
        cur.execute(
            """
            UPDATE documents
            SET embedding_status = 'processing', updated_at = NOW()
            WHERE id IN (
                SELECT id FROM documents
                WHERE embed_model = %s
                ORDER BY id
                LIMIT %s
                FOR UPDATE SKIP LOCKED
            )
            RETURNING id, content
            """,
            (OLD_MODEL, batch_size),
        )
        rows = cur.fetchall()
        conn.commit()

    if not rows:
        return 0

    ids = [r["id"] for r in rows]
    texts = [r["content"] for r in rows]
    embeddings = new_encoder.encode(texts, normalize_embeddings=True)

    with conn.cursor() as cur:
        psycopg2.extras.execute_batch(
            cur,
            """
            UPDATE documents
            SET embedding = %s::vector,
                embed_model = %s,
                embedding_status = 'complete',
                embedded_at = NOW(),
                updated_at = NOW()
            WHERE id = %s
            """,
            [
                (embeddings[i].tolist(), NEW_MODEL, ids[i])
                for i in range(len(ids))
            ],
        )
        conn.commit()

    return len(ids)

    29.8 Choosing Your Strategy: A Practical Framework

    The decision between real-time and batch isn't binary — it's a configuration choice you revisit as your system evolves. The following framework captures the most common decision points:

    Start with real-time when:

  • → Your corpus is small (< 100K documents) and ingestion is infrequent
  • → Your application cannot tolerate embedding lag (search must reflect writes immediately)
  • → You are prototyping and operational simplicity matters more than cost
  • → Query latency is your primary SLA concern

    • Move to batch (or hybrid) when:

  • → Ingestion volume exceeds what synchronous API calls can handle without rate limiting
  • → You've profiled your real-time pipeline and embedding latency is your p95 bottleneck
  • → Cost projections for synchronous API usage are unsustainable at projected scale
  • → You need different models for different content types (a local model for bulk, API for high-priority)

    • Signs your real-time pipeline is under stress:

  • → API rate limit errors appearing in logs (even at low frequency)
  • → p95 embedding latency increasing while p50 stays stable (rate limiting backpressure)
  • → Document ingestion success rate dropping during traffic peaks
  • → Queue depth in your job system growing faster than it drains

    • Signs your batch pipeline needs tuning:

  • → Queue lag exceeding your freshness SLA
  • → Worker throughput plateauing despite available CPU/GPU capacity (usually a DB write bottleneck)
  • → Failed status count growing (retry logic or content issue)
  • → Batch sizes too small to amortize model loading overhead

    • Most teams at moderate scale land on a hybrid architecture that looks like this: a synchronous path for query-time embedding (unavoidable) and high-priority content, a Redis Streams or Kafka-backed queue for normal ingestion, and a scheduled batch job for bulk loads and re-embedding passes. The exact thresholds — what constitutes HIGH priority, how large a batch the worker pulls, how many worker instances run — are tuned empirically against your observed traffic patterns.

    The architectural principle is simple: keep the synchronous path as thin as possible. Every operation you move off the synchronous request path is latency you give back to your users and a failure mode you decouple from your ingestion API.

    ---

    Key Takeaways

  • → **Query embedding is always real-time; document embedding is the decision.** You cannot precompute embeddings for arbitrary user queries, so the synchronous embedding path always exists for search. The strategic question is whether document ingestion also lives on that path or defers to an async pipeline.
  • → **The `FOR UPDATE SKIP LOCKED` pattern enables horizontally scalable batch workers.** Multiple worker instances can safely consume from the same PostgreSQL-backed embedding queue without coordination or double-processing, using the same pattern as production job queue systems.
  • → **Content hash tracking makes stale embedding detection automatic.** Storing a generated `content_hash` column eliminates manual bookkeeping; any query comparing stored hash to current content immediately surfaces documents that need re-embedding after content updates or model migrations.
  • → **Cache embedding results at the content-hash level to reduce both cost and latency.** Re-embedding identical content (system prompts, repeated queries, templated documents) is pure waste; an in-process LRU cache or Redis cache with a content-hash key can eliminate a significant fraction of API calls in typical workloads.
  • → **Model migrations require parallel indexing and a deliberate cut-over, not an in-place update.** Changing embedding model or vector dimensions means the new vectors are incompatible with the existing index; the safe pattern is to build the new index alongside the old one while the system continues serving queries, then cut over traffic once re-embedding is complete and quality is verified.
