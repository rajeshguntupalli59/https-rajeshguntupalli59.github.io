Chapter 25: Cross-Cloud Replication Architectures

Replication across cloud providers is one of the most architecturally demanding problems a cloud DBA will face. The need arises more often than you might expect: regulatory requirements that mandate data residency in specific regions served by different providers, acquisitions that land you with a PostgreSQL workload on GCP when your primary platform is AWS, disaster recovery strategies that treat provider failure as a first-class concern, or hybrid architectures where one cloud handles analytical workloads while another handles OLTP. Whatever the driver, cross-cloud replication forces you to reason about things that same-provider replication abstracts away—network transit costs, TLS certificate management across trust boundaries, WAL format incompatibilities between managed service versions, and the operational reality that you cannot place both ends of the replication stream inside the same VPC. This chapter covers the architectural patterns, tooling options, and production configuration required to build reliable cross-cloud replication between AWS RDS/Aurora, Azure SQL Database, and Google Cloud SQL/AlloyDB.

---

25.1 Understanding the Cross-Cloud Replication Landscape

Before writing a single line of configuration, you need to accept a fundamental constraint: no managed database service natively supports another cloud's replication protocol. AWS Aurora's Global Database uses Aurora-specific storage replication. Azure SQL's active geo-replication uses proprietary log shipping. Google's Spanner uses its own Paxos-based replication internally. None of these speak to each other natively.

This means every cross-cloud replication architecture uses one of three approaches:

Logical replication over the public internet or dedicated interconnects. PostgreSQL's logical replication (via pg_logical or the native logical replication built into PostgreSQL 10+) works between any two PostgreSQL-compatible endpoints that can reach each other over TCP. AWS RDS for PostgreSQL, Google Cloud SQL for PostgreSQL, and Azure Database for PostgreSQL all support logical replication. The catch is that they may run slightly different PostgreSQL minor versions, and WAL-level logical decoding requires wal_level = logical to be set—something you control through Parameter Groups on RDS, flags on Cloud SQL, and server parameters on Azure Database for PostgreSQL.

Change Data Capture (CDC) through an intermediary. Tools like AWS DMS, Debezium, and Striim sit between the source and target, read the source's transaction log, transform the events, and write them to the target. This is the most flexible approach because the source and target do not need to run the same database engine. You can replicate from SQL Server on AWS RDS to PostgreSQL on Google Cloud SQL using DMS with SCT-generated schema mappings, for example.

Application-level dual-write. The application writes to both cloud databases simultaneously, with one treated as authoritative for conflict resolution. This is the most operationally fragile pattern and only makes sense when you cannot get replication lag below acceptable thresholds for your workload's consistency requirements.

The practical choice for most production architectures is logical replication for same-engine scenarios and CDC via DMS or Debezium for cross-engine scenarios. The remainder of this chapter covers both.

Network connectivity is the prerequisite you cannot skip. Cross-cloud replication requires stable, low-latency, encrypted connectivity between the two clouds. Your options, roughly ordered by reliability and cost:

  • → **AWS Direct Connect + Azure ExpressRoute or Google Cloud Interconnect**: dedicated private circuits, lowest jitter, highest recurring cost — check current per-port and cross-connect pricing from each provider and your colocation facility before budgeting.
  • → **VPN over the public internet**: IPsec tunnels between VGW (AWS) and VPN Gateway (Azure/GCP), adequate for lower-throughput replication, with cross-region latency typically in the tens of milliseconds and a much lower recurring cost than dedicated interconnects.
  • → **Public internet with TLS**: no dedicated circuit, lowest cost, highest variability. Acceptable for replication that can tolerate seconds of lag; not appropriate for anything approaching synchronous replication.

    • For production replication carrying more than ~100 MB/s of WAL data, you want dedicated interconnects. For secondary replicas used for disaster recovery where RPO of a few seconds is acceptable, a well-tuned VPN tunnel is usually sufficient.

    25.2 Logical Replication: PostgreSQL Across AWS, Azure, and GCP

    PostgreSQL logical replication uses a publisher/subscriber model. The publisher exposes a publication (a named set of tables), and subscribers connect to it using a replication slot, decode the WAL stream, and apply changes. This is conceptually the same as setting up pg_hba.conf to allow a replication user and granting REPLICATION privilege—except that in the managed service world, you configure connectivity through security groups, firewall rules, and IAM policies rather than filesystem-level configuration files.

    Enabling logical replication on AWS RDS for PostgreSQL:

    # Create or modify a parameter group to enable logical replication
aws rds create-db-parameter-group \
  --db-parameter-group-name prod-pg15-logical \
  --db-parameter-group-family postgres15 \
  --description "PostgreSQL 15 with logical replication enabled" \
  --region us-east-1

# Set wal_level to logical (requires reboot)
aws rds modify-db-parameter-group \
  --db-parameter-group-name prod-pg15-logical \
  --parameters \
    "ParameterName=rds.logical_replication,ParameterValue=1,ApplyMethod=pending-reboot" \
  --region us-east-1

# Apply the parameter group to the instance
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-primary \
  --db-parameter-group-name prod-pg15-logical \
  --apply-immediately \
  --region us-east-1

# Reboot to apply (schedule this during maintenance window)
aws rds reboot-db-instance \
  --db-instance-identifier prod-postgres-primary \
  --region us-east-1

    On RDS, setting rds.logical_replication = 1 automatically promotes wal_level to logical and sets max_replication_slots to at least 10 and max_wal_senders to at least 10. You do not set wal_level directly—RDS controls that parameter. This is one of the managed service constraints you adapt to rather than fight.

    Enabling logical replication on Google Cloud SQL for PostgreSQL:

    # Enable logical replication via Cloud SQL flags
gcloud sql instances patch prod-postgres-replica \
  --database-flags cloudsql.logical_decoding=on \
  --project my-gcp-project \
  --region us-central1

# Verify the flag was applied
gcloud sql instances describe prod-postgres-replica \
  --project my-gcp-project \
  --format="json(settings.databaseFlags)"

    Setting up the publication on AWS RDS (publisher side):

    -- Connect to the AWS RDS PostgreSQL instance
-- Create a dedicated replication user
CREATE ROLE replication_user WITH REPLICATION LOGIN PASSWORD 'use-a-vault-managed-secret';

-- Grant SELECT on all tables that will be replicated
GRANT SELECT ON ALL TABLES IN SCHEMA public TO replication_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO replication_user;

-- Create the publication
-- Publishing all tables is convenient but adds overhead for large schemas;
-- publishing specific tables is better for production
CREATE PUBLICATION cross_cloud_pub
  FOR TABLE orders, order_items, customers, inventory
  WITH (publish = 'insert, update, delete');

-- Verify the publication
SELECT pubname, puballtables, pubinsert, pubupdate, pubdelete
FROM pg_publication;

-- Create a replication slot for the GCP subscriber
-- Named slots track LSN position and ensure no WAL is discarded before the subscriber consumes it
SELECT pg_create_logical_replication_slot('gcp_subscriber_slot', 'pgoutput');

-- Monitor slot lag — this is critical; unconsumed slots cause WAL accumulation
SELECT slot_name,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS replication_lag_size,
       active
FROM pg_replication_slots;

    Setting up the subscription on Google Cloud SQL (subscriber side):

    -- Connect to the Google Cloud SQL PostgreSQL instance
-- The schema must exist on the subscriber before the subscription starts
-- Use pg_dump --schema-only on the publisher or SCT to generate it

-- Create the subscription pointing to the AWS RDS publisher
-- The host is the RDS endpoint; connectivity must be established first (VPN or public)
CREATE SUBSCRIPTION cross_cloud_sub
  CONNECTION 'host=prod-postgres-primary.c3bxyz123.us-east-1.rds.amazonaws.com
              port=5432
              dbname=productiondb
              user=replication_user
              password=use-a-vault-managed-secret
              sslmode=require'
  PUBLICATION cross_cloud_pub
  WITH (
    slot_name = 'gcp_subscriber_slot',
    create_slot = false,        -- we already created it on the publisher
    enabled = true,
    copy_data = true            -- performs initial table sync before streaming
  );

-- Monitor subscription status
SELECT subname,
       pid,
       received_lsn,
       latest_end_lsn,
       pg_size_pretty(pg_wal_lsn_diff(latest_end_lsn, received_lsn)) AS lag
FROM pg_stat_subscription;

    Critical production gotcha: replication slot WAL accumulation. If the GCP subscriber falls behind or disconnects, the replication slot on AWS RDS will prevent WAL segments from being recycled. A subscriber that is down for 6 hours on a write-heavy database can accumulate tens of gigabytes of WAL. RDS will run out of storage and become unavailable before it drops the slot. Set an alarm on the TransactionLogsDiskUsage CloudWatch metric and configure a slot monitoring job:

    import boto3
import psycopg2

def check_replication_slot_lag(rds_host, port, dbname, user, password, slot_name, lag_threshold_gb=10):
    """
    Monitor replication slot lag and publish to CloudWatch.
    Run this every 5 minutes from a Lambda or EC2 instance.
    """
    conn = psycopg2.connect(
        host=rds_host,
        port=port,
        dbname=dbname,
        user=user,
        password=password,
        sslmode='require'
    )
    
    cur = conn.cursor()
    cur.execute("""
        SELECT slot_name,
               active,
               pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes
        FROM pg_replication_slots
        WHERE slot_name = %s
    """, (slot_name,))
    
    row = cur.fetchone()
    if not row:
        print(f"WARNING: Slot {slot_name} does not exist")
        return
    
    slot_name_db, active, lag_bytes = row
    lag_gb = lag_bytes / (1024 ** 3)
    
    cw = boto3.client('cloudwatch', region_name='us-east-1')
    cw.put_metric_data(
        Namespace='CrossCloudReplication',
        MetricData=[{
            'MetricName': 'ReplicationSlotLagGB',
            'Dimensions': [
                {'Name': 'SlotName', 'Value': slot_name},
                {'Name': 'Instance', 'Value': rds_host.split('.')[0]}
            ],
            'Value': lag_gb,
            'Unit': 'None'
        }]
    )
    
    if lag_gb > lag_threshold_gb:
        print(f"ALERT: Slot {slot_name} lag is {lag_gb:.2f} GB — exceeds {lag_threshold_gb} GB threshold")
        # Drop the slot if subscriber has been inactive for extended period
        # Only do this if you have a clear runbook for resynchronization
        if not active:
            print(f"Slot {slot_name} is INACTIVE. Consider dropping and resynchronizing.")
    
    cur.close()
    conn.close()

    25.3 AWS DMS for Cross-Cloud CDC Replication

    AWS Database Migration Service supports continuous CDC replication to and from non-AWS endpoints. Despite the name, DMS is not just for one-time migrations—its ongoing replication mode makes it viable for keeping a GCP or Azure database synchronized with an AWS source. The key limitation is that DMS applies changes with a latency of roughly 1–10 seconds under normal load, making it appropriate for near-real-time analytics replicas and DR targets but not for synchronous replication or read scaling.

    Terraform configuration for a DMS cross-cloud replication task (AWS RDS PostgreSQL to Cloud SQL PostgreSQL):

    DMS gotchas for cross-cloud replication:

    First, DMS cannot replicate DDL changes in CDC mode for PostgreSQL by default. If a developer adds a column to a replicated table, the CDC stream will start failing for that table once rows with the new column arrive. You need a DDL change management process: apply the schema change to the target first, then apply it to the source, with a brief replication pause if the DDL is destructive.

    Second, the DMS replication instance needs connectivity to both endpoints. For a private RDS source, you route through the VPC normally. For the Cloud SQL target, you have two options: enable Cloud SQL's public IP and whitelist the DMS replication instance's Elastic IP address in the Cloud SQL authorized networks list, or use Cloud SQL Auth Proxy running on an EC2 instance in the same VPC as DMS. The proxy approach is more secure and preferred for production.

    Third, DMS requires that the PostgreSQL source has wal_level = logical and that the pglogical extension is installed. On RDS, pglogical is available as a supported extension—you create it with CREATE EXTENSION pglogical; once rds.logical_replication = 1 is set. DMS creates and manages its own replication slot; you do not create it manually.

    25.4 Azure SQL as a Cross-Cloud Replication Target

    Azure SQL Database (the PaaS offering on SQL Server's engine) does not natively participate in PostgreSQL or MySQL logical replication. Getting data into or out of Azure SQL from another cloud's database engine requires one of two approaches: DMS (which supports Azure SQL as a target), or SQL Server's own replication mechanisms—transactional replication or the Azure Data Factory copy pipelines—when Azure SQL is involved on both ends.

    For a common production scenario—AWS RDS for SQL Server replicating to Azure SQL Database for analytics or DR—you have a genuine option in SQL Server's native transactional replication, but only if the AWS side is RDS for SQL Server (not Aurora). The Azure SQL end acts as the subscriber. The challenge is that Azure SQL is always behind a fully qualified domain name in a Microsoft-managed network, and the publisher (RDS for SQL Server) must be able to reach the Azure SQL subscriber. You accomplish this through an Azure Private Link endpoint published to AWS via Transit Gateway or VPN.

    For the more common scenario today—PostgreSQL on AWS to Azure Database for PostgreSQL for cross-cloud DR—logical replication works as described in Section 25.2. Azure Database for PostgreSQL Flexible Server supports logical replication from PostgreSQL 11+ and sets wal_level = logical through the azure.replication_support server parameter.

    Enabling logical replication on Azure Database for PostgreSQL Flexible Server:

    # Set replication support level using Azure CLI
az postgres flexible-server parameter set \
  --resource-group rg-database-prod \
  --server-name prod-postgres-azure \
  --name azure.replication_support \
  --value LOGICAL

# Restart the server to apply the parameter
az postgres flexible-server restart \

  --name prod-postgres-azure

# Verify the parameter

  --end-ip-address 54.xxx.xxx.xxx

    Monitoring cross-cloud replication lag with Azure Monitor and CloudWatch together:

    A mature cross-cloud replication operation monitors lag from both ends. The publisher (AWS) measures how much WAL is in the slot waiting to be consumed. The subscriber (Azure) measures how far behind its applied LSN is from the publisher's current LSN. Building a unified view requires pulling metrics from both clouds into a single observability system—Datadog, Grafana with multi-cloud datasources, or a custom pipeline.

    import boto3
import psycopg2
from azure.monitor.query import MetricsQueryClient, MetricAggregationType
from azure.identity import DefaultAzureCredential
from datetime import datetime, timedelta, timezone

def get_cross_cloud_replication_health(
    rds_host: str,
    rds_creds: dict,
    azure_subscription_id: str,
    azure_resource_group: str,
    azure_server_name: str,
    slot_name: str
) -> dict:
    """
    Collect replication health metrics from both AWS (publisher) and Azure (subscriber).
    Returns a unified status dict suitable for alerting or dashboarding.
    """
    result = {
        'timestamp': datetime.now(timezone.utc).isoformat(),
        'publisher': {},
        'subscriber': {}
    }

    # --- AWS RDS: publisher-side metrics ---
    try:
        conn = psycopg2.connect(
            host=rds_host,
            dbname=rds_creds['dbname'],
            user=rds_creds['user'],
            password=rds_creds['password'],
            sslmode='require',
            connect_timeout=10
        )
        cur = conn.cursor()
        
        cur.execute("""
            SELECT
                slot_name,
                active,
                pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes,
                confirmed_flush_lsn::text,
                pg_current_wal_lsn()::text AS current_lsn
            FROM pg_replication_slots
            WHERE slot_name = %s
        """, (slot_name,))
        
        row = cur.fetchone()
        if row:
            result['publisher'] = {
                'slot_name': row[0],
                'slot_active': row[1],
                'lag_bytes': row[2],
                'lag_gb': round(row[2] / (1024 ** 3), 3),
                'confirmed_flush_lsn': row[3],
                'current_lsn': row[4]
            }
        else:
            result['publisher']['error'] = f"Slot {slot_name} not found"
        
        cur.close()
        conn.close()
    except Exception as e:
        result['publisher']['error'] = str(e)

    # --- Azure Database for PostgreSQL: subscriber-side metrics ---
    # Azure Monitor publishes server-level metrics; replication-specific lag
    # is best queried from the subscriber's pg_stat_subscription directly
    try:
        azure_conn = psycopg2.connect(
            host=f"{azure_server_name}.postgres.database.azure.com",
            dbname=rds_creds['dbname'],
            user=rds_creds['user'],
            password=rds_creds['password'],
            sslmode='require',
            connect_timeout=10
        )
        azure_cur = azure_conn.cursor()
        
        azure_cur.execute("""
            SELECT
                subname,
                received_lsn::text,
                last_msg_send_time,
                last_msg_receipt_time,
                latest_end_lsn::text,
                EXTRACT(EPOCH FROM (now() - last_msg_receipt_time)) AS seconds_since_last_message
            FROM pg_stat_subscription
        """)
        
        rows = azure_cur.fetchall()
        result['subscriber']['subscriptions'] = [
            {
                'name': r[0],
                'received_lsn': r[1],
                'last_msg_send_time': r[2].isoformat() if r[2] else None,
                'last_msg_receipt_time': r[3].isoformat() if r[3] else None,
                'latest_end_lsn': r[4],
                'seconds_since_last_message': float(r[5]) if r[5] else None
            }
            for r in rows
        ]
        
        azure_cur.close()
        azure_conn.close()
    except Exception as e:
        result['subscriber']['error'] = str(e)

    # Compute composite health status
    lag_gb = result['publisher'].get('lag_gb', 0)
    slot_active = result['publisher'].get('slot_active', False)
    subs = result['subscriber'].get('subscriptions', [])
    seconds_stale = max(
        (s['seconds_since_last_message'] or 0) for s in subs
    ) if subs else None

    if lag_gb > 10 or not slot_active or (seconds_stale and seconds_stale > 300):
        result['health'] = 'CRITICAL'
    elif lag_gb > 2 or (seconds_stale and seconds_stale > 60):
        result['health'] = 'WARNING'
    else:
        result['health'] = 'OK'

    return result

    This function is designed to be called from a Lambda (in the AWS account) that has network access to both the RDS instance and the Azure Database for PostgreSQL endpoint—typically via a VPN tunnel through which the Lambda's VPC can reach the Azure virtual network.

    25.5 Handling Schema Changes and DDL Propagation

    Logical replication in PostgreSQL does not replicate DDL. This is not a limitation of managed services—it is a fundamental design choice in the PostgreSQL logical replication protocol. The publication/subscription mechanism streams row-level changes (INSERTs, UPDATEs, DELETEs) and sequence changes (from PostgreSQL 16+), but ALTER TABLE, CREATE INDEX, DROP COLUMN, and every other DDL statement are invisible to the subscriber. You manage schema evolution manually, and the process matters greatly for cross-cloud architectures because the communication overhead of coordinating changes across teams in different cloud environments is higher than coordinating within a single provider.

    The safe DDL change sequence for cross-cloud logical replication:

    The sequence depends on the type of DDL operation. Additive changes (adding a nullable column, creating an index) are safer than destructive changes (dropping a column, changing a column type).

    For adding a nullable column:

    -- Step 1: Apply on the SUBSCRIBER (Azure or GCP) first
-- The subscriber must be able to handle rows with the new column
-- before the publisher starts emitting them

-- On Azure Database for PostgreSQL (subscriber):
ALTER TABLE orders ADD COLUMN fulfillment_partner_id INTEGER;

-- Step 2: Apply on the PUBLISHER (AWS RDS)
-- Once the publisher starts sending rows with the new column,
-- the subscriber is already prepared to receive them

-- On AWS RDS PostgreSQL (publisher):
ALTER TABLE orders ADD COLUMN fulfillment_partner_id INTEGER;

-- No replication disruption occurs because PostgreSQL logical replication
-- maps columns by name. A column present in the publisher but missing in
-- the subscriber causes an error. A column present in the subscriber but
-- missing in the publisher is simply ignored (the subscriber column gets NULL).

    For dropping a column, reverse the order:

    -- Step 1: Drop on the PUBLISHER first
-- Once the publisher stops sending data for the column,
-- removing it from the subscriber is safe

-- On AWS RDS PostgreSQL (publisher):
ALTER TABLE orders DROP COLUMN legacy_carrier_code;

-- Step 2: Drop on the SUBSCRIBER
-- On Azure Database for PostgreSQL (subscriber):
ALTER TABLE orders DROP COLUMN legacy_carrier_code;

    For type changes that affect wire representation (e.g., VARCHAR(50) to TEXT, or INTEGER to BIGINT), you must pause replication, apply the change on both ends, and resume. There is no safe online path for these changes in native logical replication because the encoded binary representation in the WAL changes. The practical approach:

    -- This procedure applies to column type changes that alter binary encoding.
-- For changes that are wire-compatible (VARCHAR(50) to VARCHAR(100)), replication continues.

-- Step 1: Disable the subscription on the subscriber to pause replication
-- On Azure Database for PostgreSQL (subscriber):
ALTER SUBSCRIPTION cross_cloud_sub DISABLE;

-- Step 2: Record the current LSN on the publisher before applying DDL
-- On AWS RDS PostgreSQL (publisher):
SELECT pg_current_wal_lsn();
-- Save this value: e.g., '0/1A3F28C0'

-- Step 3: Apply the type change on the publisher
-- On AWS RDS PostgreSQL (publisher):
-- PostgreSQL does not support direct ALTER COLUMN TYPE with changed encoding in-place for replicated tables.
-- Use the expand-contract pattern:
ALTER TABLE orders ADD COLUMN order_ref_v2 BIGINT;
UPDATE orders SET order_ref_v2 = order_ref::BIGINT;  -- batch this for large tables
-- At this point order_ref (INTEGER) is still the replicated column

-- Step 4: Apply the same schema change on the subscriber
-- On Azure Database for PostgreSQL (subscriber):
ALTER TABLE orders ADD COLUMN order_ref_v2 BIGINT;

-- Step 5: Add the new column to the publication
-- On AWS RDS PostgreSQL (publisher):
-- If you used FOR TABLE with explicit columns, update the publication.
-- If you used FOR ALL TABLES or FOR TABLE orders (all columns), it's included automatically.

-- Step 6: Re-enable the subscription
-- On Azure Database for PostgreSQL (subscriber):
ALTER SUBSCRIPTION cross_cloud_sub ENABLE;

-- Step 7: After validating replication of order_ref_v2,
-- drop the old column following the safe drop sequence above.

    Automating DDL propagation with an event trigger:

    For teams that prefer automated DDL capture, PostgreSQL event triggers can log DDL statements to a side table, and a separate process can replay them on the subscriber after a validation step. This is not plug-and-play—it requires careful handling of object dependencies and ordering—but it is the approach used by tools like pglogical 2.x and Bucardo.

    -- On the AWS RDS PostgreSQL publisher:
-- Create a DDL audit table
CREATE TABLE ddl_replication_log (
    id          BIGSERIAL PRIMARY KEY,
    event_time  TIMESTAMPTZ NOT NULL DEFAULT now(),
    command_tag TEXT NOT NULL,
    object_type TEXT,
    schema_name TEXT,
    object_name TEXT,
    ddl_text    TEXT,
    applied_to_subscriber BOOLEAN NOT NULL DEFAULT false
);

-- Create an event trigger function
CREATE OR REPLACE FUNCTION log_ddl_for_replication()
RETURNS event_trigger
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
    r RECORD;
BEGIN
    FOR r IN SELECT * FROM pg_event_trigger_ddl_commands()
    LOOP
        INSERT INTO ddl_replication_log (command_tag, object_type, schema_name, object_name, ddl_text)
        VALUES (
            r.command_tag,
            r.object_type,
            r.schema_name,
            r.objid::regclass::text,
            current_query()
        );
    END LOOP;
END;
$$;

-- Attach the event trigger to DDL events
CREATE EVENT TRIGGER capture_ddl_for_cross_cloud
  ON ddl_command_end
  EXECUTE FUNCTION log_ddl_for_replication();

    A scheduled job on the subscriber side polls ddl_replication_log (via a separate read connection to the publisher, not through the replication stream), reviews pending DDL entries marked applied_to_subscriber = false, applies them in order, and marks them applied. The job should include a human approval step for destructive DDL in production. This is the foundation of a DDL replication workflow—teams add validation, Slack notifications, and rollback procedures on top.

    25.6 Failover and Switchover in Cross-Cloud Architectures

    Replication is infrastructure; failover is the operational procedure that uses it. Cross-cloud replication introduces complexity to failover that same-cloud DR does not: DNS changes propagate through a different provider's infrastructure, the application tier on one cloud must redirect to a database on another cloud, and the cost of cross-cloud failover in terms of latency must be validated before you rely on it.

    The two failure modes you must plan for:

    1. Publisher failure (primary cloud becomes unavailable). The subscriber has data up to the last consumed LSN. There is no LSN on the subscriber you can promote from because PostgreSQL logical replication does not establish the subscriber as a standby in the streaming replication sense—it is a separate database cluster. Promotion here means pointing your application connection strings at the subscriber and accepting that any transactions that were committed on the publisher after the last consumed LSN are lost (RPO = replication lag at time of failure).

    2. Subscriber failure (replica cloud becomes unavailable). The publisher continues operating normally. The replication slot accumulates WAL. When the subscriber recovers, replication resumes from the slot's last confirmed LSN. The risk here is WAL accumulation causing publisher storage exhaustion, as discussed in Section 25.2.

    Automated failover runbook for publisher failure:

    #!/bin/bash
# cross_cloud_failover.sh
# Promotes the Azure/GCP logical replication subscriber to primary role.
# Prerequisites:
#   - PGPASSWORD or .pgpass configured for subscriber connection
#   - Application connection string managed through Route 53 or Azure Traffic Manager
#   - Replication lag was below RPO threshold at time of publisher failure

set -euo pipefail

SUBSCRIBER_HOST="${SUBSCRIBER_HOST:-prod-postgres-azure.postgres.database.azure.com}"
SUBSCRIBER_PORT="${SUBSCRIBER_PORT:-5432}"
SUBSCRIBER_DB="${SUBSCRIBER_DB:-productiondb}"
SUBSCRIBER_USER="${SUBSCRIBER_USER:-dbadmin}"
SUB_NAME="cross_cloud_sub"

echo "$(date -u): Starting cross-cloud failover promotion"

# Step 1: Verify the publisher is unreachable (don't fail over if it's a false alarm)
PUBLISHER_HOST="prod-postgres-primary.c3bxyz123.us-east-1.rds.amazonaws.com"
if pg_isready -h "${PUBLISHER_HOST}" -p 5432 -t 10 2>/dev/null; then
    echo "ERROR: Publisher appears to be reachable. Aborting failover to prevent split-brain."
    echo "Verify the outage independently before proceeding."
    exit 1
fi

echo "$(date -u): Publisher is confirmed unreachable. Proceeding with failover."

# Step 2: Drop the subscription on the subscriber
# This removes the replication connection and allows the subscriber to accept writes.
# The subscriber's data represents the last LSN consumed from the publisher.
psql \
    -h "${SUBSCRIBER_HOST}" \
    -p "${SUBSCRIBER_PORT}" \
    -U "${SUBSCRIBER_USER}" \
    -d "${SUBSCRIBER_DB}" \
    -c "DROP SUBSCRIPTION ${SUB_NAME};" \
    --set ON_ERROR_STOP=on

echo "$(date -u): Subscription dropped. Subscriber is now a standalone primary."

# Step 3: Record the last received LSN for post-failover reconciliation
psql \
    -h "${SUBSCRIBER_HOST}" \
    -p "${SUBSCRIBER_PORT}" \
    -U "${SUBSCRIBER_USER}" \
    -d "${SUBSCRIBER_DB}" \
    -c "SELECT pg_current_wal_lsn() AS promoted_at_lsn, now() AS promoted_at;" \
    --set ON_ERROR_STOP=on

# Step 4: Update the application connection strings
# This is environment-specific. Common approaches:
#   - Update AWS Route 53 CNAME record for db.internal.mycompany.com
#   - Update Azure Traffic Manager profile
#   - Update Kubernetes ConfigMap and trigger rolling pod restart
#   - Update AWS Systems Manager Parameter Store and trigger Lambda to notify app

echo "$(date -u): Update application connection strings to: ${SUBSCRIBER_HOST}"
echo "$(date -u): Example Route 53 update:"
echo "  aws route53 change-resource-record-sets \\"
echo "    --hosted-zone-id Z1234567890ABC \\"
echo "    --change-batch file://failover-dns-change.json"

# Step 5: Validate write capability on the promoted subscriber
psql \
    -h "${SUBSCRIBER_HOST}" \
    -p "${SUBSCRIBER_PORT}" \
    -U "${SUBSCRIBER_USER}" \
    -d "${SUBSCRIBER_DB}" \
    -c "INSERT INTO failover_events (event_type, event_time, notes)
        VALUES ('cross_cloud_failover', now(), 'Promoted from logical replication subscriber');" \
    --set ON_ERROR_STOP=on

echo "$(date -u): Failover complete. Validate application connectivity and data integrity."
echo "$(date -u): Begin post-failover runbook: reconcile lost transactions, notify stakeholders."

    Re-establishing replication after failover (switchback):

    After the original publisher recovers (or after you build a new primary in the original cloud), you must rebuild replication from scratch. There is no automatic resynchronization in PostgreSQL logical replication—you cannot simply re-enable a subscription to a recovered publisher and have it seamlessly pick up from where it left off, because the former subscriber (now the active primary) has diverged. The steps are:

    1. Take a logical dump of the current primary (former subscriber) using pg_dump.

    2. Restore it to the new replica instance (former publisher or a fresh instance).

    3. Create a new publication on the current primary and a new subscription on the new replica.

    4. Let the initial table sync (copy_data = true) bring the replica to current state before enabling streaming replication.

    This process can take hours for large databases, which is why cross-cloud RPO and RTO targets must account for resynchronization time, not just immediate failover time.

    25.7 Conflict Resolution in Bidirectional Cross-Cloud Replication

    Most cross-cloud architectures are unidirectional: one cloud is the writer, one cloud is the reader/DR target. Bidirectional replication—where both ends accept writes—introduces conflict resolution requirements that significantly increase complexity. This is worth discussing because teams ask for it frequently ("can we write to AWS in us-east-1 and also write to GCP in europe-west1 with bidirectional sync?") and the honest answer is: yes, but the operational burden is substantial.

    PostgreSQL's native logical replication has no built-in conflict resolution. If row ID 42 is updated on AWS at T1 and also updated on GCP at T2 where T1 and T2 are close together and the replication lag exceeds T2-T1, both updates succeed locally and the replication stream will attempt to apply each conflicting update to the other side. The subscriber will throw an error like:

    ERROR:  duplicate key value violates unique constraint "orders_pkey"

    or, for UPDATE conflicts:

    ERROR:  could not find row to update in table "orders"

    At this point, the subscription worker stops. You are now in manual conflict resolution territory.

    Strategies for handling bidirectional conflicts:

    Last-writer-wins with application timestamps. Include a last_modified_at TIMESTAMPTZ column in every replicated table. Write application-level triggers or a custom logical replication apply function (available in PostgreSQL 15+ with custom apply handlers) that compares timestamps and keeps the later modification.

    -- PostgreSQL 15+ custom conflict resolution function
-- Applied on the subscriber side to handle UPDATE conflicts

CREATE OR REPLACE FUNCTION resolve_update_conflict()
RETURNS void
LANGUAGE plpgsql
AS $$
BEGIN
    -- This function is called by the logical replication worker when
    -- configured as the conflict handler. The actual API for custom
    -- apply functions is implemented via pg_logical or third-party
    -- extensions in PostgreSQL 15; native support is experimental.
    -- Illustrative pattern only — production implementations use
    -- pglogical 2.x or Citus for managed bidirectional conflict resolution.
    NULL;
END;
$$;

    Partition writes by cloud. A cleaner approach for most real-world bidirectional needs: partition your write traffic so that certain entities are always owned by a specific cloud. Customers in Europe are written only to GCP europe-west1; customers in North America are written only to AWS us-east-1. Replication carries the data to both sides for read access, but writes are never truly concurrent on the same row across clouds. Conflict resolution becomes unnecessary because you have eliminated the condition that creates conflicts.

    Use a tool with built-in conflict resolution. pglogical 2.x (the commercial extension from EDB, or the open-source version) supports configurable conflict resolution policies: error (default), apply_remote (remote always wins), keep_local (local always wins), last_update_wins (timestamp comparison). Bucardo supports per-table conflict resolution functions. For teams that need genuine bidirectional replication without building a custom conflict handler, these tools are worth the operational overhead of deploying them alongside the managed service endpoints.

    25.8 Cost Modeling for Cross-Cloud Replication

    Replication traffic has a cost that is easy to underestimate in architecture reviews. Data egress from AWS costs per-GB (rates vary by region and destination; inter-region and internet egress are charged, while intra-region transfer within the same AZ is free). GCP and Azure have similar egress pricing models. When your WAL stream is moving gigabytes per hour across providers, the egress charges accumulate quickly.

    Estimating cross-cloud replication egress cost:

    def estimate_cross_cloud_replication_cost(
    write_throughput_mbps: float,
    wal_amplification_factor: float = 2.5,
    egress_cost_per_gb: float = 0.09,  # AWS to internet, per GB — verify current pricing
    hours_per_month: int = 730
) -> dict:
    """
    Estimate monthly egress cost for cross-cloud replication.

    write_throughput_mbps: Application write rate in megabits per second.
    wal_amplification_factor: WAL generated per byte of actual write data.
        Typically 2x–4x for row-level changes; higher for small, frequent updates.
    egress_cost_per_gb: Cloud provider egress rate per GB.
    """
    wal_throughput_mbps = write_throughput_mbps * wal_amplification_factor
    wal_throughput_mb_per_hour = wal_throughput_mbps * 3600 / 8  # convert mbps to MB/hour
    wal_throughput_gb_per_month = (wal_throughput_mb_per_hour * hours_per_month) / 1024

    monthly_egress_cost = wal_throughput_gb_per_month * egress_cost_per_gb

    return {
        'write_throughput_mbps': write_throughput_mbps,
        'wal_throughput_mbps': wal_throughput_mbps,
        'estimated_wal_gb_per_month': round(wal_throughput_gb_per_month, 1),
        'estimated_monthly_egress_cost_usd': round(monthly_egress_cost, 2),
        'notes': (
            "WAL amplification varies by workload. "
            "TOAST-heavy workloads (large text/JSONB) amplify less; "
            "high-update workloads on narrow rows amplify more. "
            "Verify egress pricing against current cloud provider rate cards."
        )
    }

# Example: 10 Mbps application write rate
estimate = estimate_cross_cloud_replication_cost(
    write_throughput_mbps=10,
    wal_amplification_factor=3.0
)
# Result: ~30 Mbps of WAL traffic, translating to several thousand GB/month —
# plug in current egress pricing for your provider and region to get a dollar figure
print(estimate)

    Beyond egress, factor in:

  • → **DMS replication instance cost**: an instance class like `dms.r6i.2xlarge` has a fixed hourly cost regardless of throughput — check current AWS DMS pricing for your region before budgeting.
  • → **Direct Connect or VPN**: As noted in Section 25.1, dedicated circuits add a recurring cost but eliminate per-GB egress charges between endpoints on the private circuit. For high-throughput replication, there is a crossover point where a dedicated circuit becomes cheaper than public egress — do the arithmetic for your specific throughput and current circuit pricing rather than assuming a threshold.
  • → **Monitoring and tooling**: Slot monitoring Lambda executions, CloudWatch custom metrics, Datadog per-host fees for the DMS instance—these are minor individually but add up.

    • The honest architectural advice: model the total cost of cross-cloud replication before committing to it. For many teams, the DR or compliance value justifies the cost. For others, it prompts a redesign toward a single-cloud multi-region architecture where egress stays intra-provider and costs are lower.

    Key Takeaways

  • → **No managed database service natively replicates to another cloud's engine.** Every cross-cloud replication architecture uses logical replication (for same-engine, same-version scenarios), CDC via a tool like AWS DMS or Debezium (for cross-engine or cross-version scenarios), or application-level dual-write. Choose the approach that matches your RPO tolerance and schema complexity before writing any configuration.
  • → **Replication slot WAL accumulation is the most common production failure mode for cross-cloud logical replication.** When the subscriber disconnects or falls behind, the publisher's replication slot prevents WAL recycling. Monitor slot lag continuously with a CloudWatch custom metric or equivalent, set a storage alarm well below disk capacity, and maintain a documented runbook for dropping and resynchronizing a lagged slot before it causes publisher unavailability.
  • → **DDL changes are invisible to the logical replication stream and require a coordinated manual process.** Additive DDL (adding nullable columns) must be applied to the subscriber first; destructive DDL (dropping columns) must be applied to the publisher first. Type changes that alter wire encoding require pausing the subscription, applying changes on both ends, and resuming. An event trigger DDL audit log is the practical foundation for teams needing automation in this area.
  • → **Cross-cloud failover is a distinct operation from same-cloud promotion.** Promoting a logical replication subscriber to primary means dropping the subscription (which removes the replication connection and allows writes), recording the last applied LSN, and redirecting application traffic. There is no automatic resynchronization when the original publisher recovers—you must rebuild replication from a logical dump, which is the dominant factor in RTO for this architecture.
  • → **Egress cost is a first-class architectural constraint, not an afterthought.** WAL data volumes for write-heavy workloads at cross-cloud egress rates can reach significant monthly costs before accounting for DMS instance fees, dedicated circuit costs, and monitoring overhead. Model total replication cost against the value of the cross-cloud architecture before committing to it, and revisit the model when write throughput grows substantially.
