Chapter 21: Caching Layer Economics: ElastiCache vs Database Direct

Organizations that add a properly sized Redis caching layer in front of their RDS or Aurora clusters typically see database costs drop by 30–60% within the first billing cycle. A mid-size SaaS company running an r6g.2xlarge RDS PostgreSQL instance at $876/month can often drop to an r6g.xlarge at $438/month after offloading read traffic to ElastiCache for Redis — a cache.r6g.large at $104/month — netting $334/month in savings on a $1,418 combined workload. That math gets even more compelling at scale. This chapter walks through the economics of caching layer decisions: when adding cache actually saves money, when it just adds complexity and cost, how to right-size ElastiCache clusters, and how to automate cache hit rate monitoring so you catch degradation before it shows up on your AWS bill.

---

21.1 The Caching Economics Baseline: When Cache Pays for Itself

Before spending a dollar on ElastiCache or Memorystore, you need to establish whether your workload actually benefits from caching. The economics break down into three scenarios, and only two of them favor adding a cache tier.

Scenario A — High read ratio, repetitive queries: Your database serves 90% reads, and a meaningful percentage of those reads fetch the same rows repeatedly. Product catalogs, user profiles, session data, configuration tables. Cache wins overwhelmingly here.

Scenario B — Write-heavy transactional workload: Your database is processing orders, logging events, or updating financial ledgers. Reads are largely unique. Cache adds cost without meaningful throughput benefit.

Scenario C — Mixed workload with hot data concentration: 80% of reads hit 20% of rows. This is the most common production pattern and the most nuanced to optimize.

The first diagnostic step is measuring your current read/write ratio and query repetition rate directly from the database engine. This query runs against PostgreSQL and gives you the data needed to build the business case:

-- Identify top repeated queries and estimate cache value
-- Run on PostgreSQL with pg_stat_statements enabled
SELECT
    left(query, 80)                                      AS query_preview,
    calls,
    round(total_exec_time::numeric / calls, 2)           AS avg_ms,
    round((total_exec_time / 1000)::numeric, 2)          AS total_exec_sec,
    rows,
    round(rows::numeric / calls, 1)                      AS avg_rows_returned,
    shared_blks_hit + shared_blks_read                   AS total_blocks_accessed,
    round(
        shared_blks_hit::numeric /
        NULLIF(shared_blks_hit + shared_blks_read, 0) * 100,
        1
    )                                                    AS buffer_hit_pct,
    -- Queries returning same avg rows are cache candidates
    CASE
        WHEN round(rows::numeric / calls, 1) BETWEEN 1 AND 50
         AND calls > 1000
         AND round(rows::numeric / calls, 1) = round(rows::numeric / calls, 0)
        THEN 'HIGH cache candidate'
        WHEN calls > 500 AND avg_rows_returned < 100
        THEN 'MEDIUM cache candidate'
        ELSE 'LOW cache value'
    END                                                  AS cache_recommendation
FROM
    pg_stat_statements
WHERE
    calls > 100
    AND query NOT LIKE '%pg_stat%'
    AND query NOT LIKE 'COMMIT%'
    AND query NOT LIKE 'BEGIN%'
ORDER BY
    calls DESC
LIMIT 40;

For SQL Server on RDS or Azure SQL, the equivalent analysis pulls from sys.dm_exec_query_stats:

-- SQL Server: Identify repetitive read queries suitable for caching
SELECT TOP 40
    LEFT(qt.text, 100)                                          AS query_preview,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count                 AS avg_logical_reads,
    qs.total_elapsed_time / qs.execution_count / 1000          AS avg_elapsed_ms,
    qs.total_rows / qs.execution_count                         AS avg_rows,
    qs.total_logical_reads                                      AS total_logical_reads,
    -- Estimate I/O cost: each logical read = ~8KB page
    -- At 50,000 IOPS provisioned IOPS cost on io1, each read has a cost
    CAST(qs.total_logical_reads * 8.0 / 1024 / 1024 AS DECIMAL(10,2)) AS total_data_gb_read,
    CASE
        WHEN qs.execution_count > 1000
         AND qs.total_rows / qs.execution_count < 100
        THEN 'CACHE NOW'
        WHEN qs.execution_count > 500
        THEN 'EVALUATE'
        ELSE 'SKIP'
    END                                                         AS cache_action
FROM
    sys.dm_exec_query_stats qs
    CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
WHERE
    qt.text NOT LIKE '%sys.dm%'
    AND qs.total_logical_reads > 0
ORDER BY
    qs.execution_count DESC;

Once you have a list of high-frequency, low-row-count queries, you can calculate the cache ROI with a simple formula:

Cache ROI = (Database instance savings per month) − (ElastiCache cost per month)

A real example: An r6g.4xlarge RDS PostgreSQL Multi-AZ at $3,504/month, processing 45,000 queries/minute with 72% of those being repetitive reads, can be right-sized to an r6g.2xlarge at $1,752/month after caching. Adding a cache.r6g.xlarge Redis node at $208/month (or a Multi-AZ pair at $416/month) still nets you $1,336/month in savings. Cache pays for itself in under one week.

21.2 ElastiCache Sizing and Configuration for Maximum Cost Efficiency

The single most common ElastiCache mistake is over-provisioning. Teams spin up cache.r6g.2xlarge nodes because their database is large, when the working set of frequently accessed data is often a fraction of total database size. A 500GB database might have a hot working set of only 8–12GB.

Measuring your actual working set size in PostgreSQL:

-- Estimate hot data working set: tables accessed most frequently
-- and their actual size in shared_buffers
SELECT
    schemaname,
    relname                                                     AS table_name,
    pg_size_pretty(pg_relation_size(relid))                    AS table_size,
    pg_size_pretty(pg_total_relation_size(relid))              AS total_size_with_indexes,
    heap_blks_read                                             AS disk_reads,
    heap_blks_hit                                              AS buffer_hits,
    round(
        heap_blks_hit::numeric /
        NULLIF(heap_blks_hit + heap_blks_read, 0) * 100, 1
    )                                                          AS buffer_hit_pct,
    idx_blks_hit,
    idx_blks_read,
    -- Tables with high hit rates are already cached in PG buffer pool
    -- Tables with low hit rates are the cache opportunity
    CASE
        WHEN round(heap_blks_hit::numeric /
             NULLIF(heap_blks_hit + heap_blks_read, 0) * 100, 1) < 80
        THEN pg_relation_size(relid)
        ELSE 0
    END                                                        AS bytes_needing_cache
FROM
    pg_statio_user_tables
WHERE
    heap_blks_hit + heap_blks_read > 1000
ORDER BY
    heap_blks_read DESC
LIMIT 30;

-- Total estimated cache requirement
SELECT
    pg_size_pretty(
        SUM(
            CASE
                WHEN round(heap_blks_hit::numeric /
                     NULLIF(heap_blks_hit + heap_blks_read, 0) * 100, 1) < 80
                THEN pg_relation_size(relid)
                ELSE 0
            END
        )
    ) AS estimated_cache_requirement
FROM
    pg_statio_user_tables
WHERE
    heap_blks_hit + heap_blks_read > 1000;

With an estimated working set size in hand, the ElastiCache node selection follows a straightforward mapping. For Redis on AWS, target 75–80% memory utilization at steady state to leave headroom for replication buffers and key expiration overhead:

| Working Set | Recommended Node | Memory | On-Demand/hr | Monthly |

|-------------|-----------------|--------|--------------|---------|

| < 2 GB | cache.t4g.medium | 3.09 GB | $0.032 | $23 |

| 2–6 GB | cache.r6g.large | 13.07 GB | $0.145 | $104 |

| 6–24 GB | cache.r6g.xlarge | 26.32 GB | $0.290 | $208 |

| 24–52 GB | cache.r6g.2xlarge | 52.82 GB | $0.580 | $418 |

| 52–100 GB | cache.r6g.4xlarge | 105.81 GB | $1.160 | $835 |

Reserved Instance pricing reduces these costs by 40–45% for 1-year No Upfront and up to 55% for 3-year All Upfront. A cache.r6g.xlarge on a 1-year reserved basis drops from $208/month to approximately $125/month. For any cache cluster you expect to run for more than 6 months, reserved pricing is the correct economic choice.

The Python script below automates cluster sizing recommendations by pulling CloudWatch metrics and comparing against current node specifications:

#!/usr/bin/env python3
"""
ElastiCache Sizing Analyzer
Pulls CloudWatch metrics for existing clusters and recommends right-sizing.
Schedule via CloudWatch Events or GitHub Actions weekly.
"""

import boto3
import json
from datetime import datetime, timedelta
from dataclasses import dataclass
from typing import Optional


@dataclass
class ClusterSizingRecommendation:
    cluster_id: str
    current_node_type: str
    current_monthly_cost: float
    avg_memory_utilization_pct: float
    max_memory_utilization_pct: float
    avg_cpu_utilization_pct: float
    avg_cache_hit_rate_pct: float
    recommended_node_type: Optional[str]
    recommended_monthly_cost: Optional[float]
    monthly_savings: float
    action: str
    reasoning: str


# Current on-demand hourly pricing (us-east-1, update as needed)
ELASTICACHE_PRICING = {
    "cache.t4g.micro":    {"memory_gb": 0.5,   "hourly": 0.008},
    "cache.t4g.small":    {"memory_gb": 1.37,  "hourly": 0.016},
    "cache.t4g.medium":   {"memory_gb": 3.09,  "hourly": 0.032},
    "cache.r6g.large":    {"memory_gb": 13.07, "hourly": 0.145},
    "cache.r6g.xlarge":   {"memory_gb": 26.32, "hourly": 0.290},
    "cache.r6g.2xlarge":  {"memory_gb": 52.82, "hourly": 0.580},
    "cache.r6g.4xlarge":  {"memory_gb": 105.81,"hourly": 1.160},
    "cache.r6g.8xlarge":  {"memory_gb": 209.55,"hourly": 2.320},
}

HOURS_PER_MONTH = 730


def get_cloudwatch_metric_stats(cw_client, cluster_id, metric_name,
                                 namespace, dimension_name, days=14):
    """Retrieve average and max for a CloudWatch metric over the past N days."""
    end_time = datetime.utcnow()
    start_time = end_time - timedelta(days=days)

    response = cw_client.get_metric_statistics(
        Namespace=namespace,
        MetricName=metric_name,
        Dimensions=[{"Name": dimension_name, "Value": cluster_id}],
        StartTime=start_time,
        EndTime=end_time,
        Period=3600,  # 1-hour granularity
        Statistics=["Average", "Maximum"]
    )

    datapoints = response.get("Datapoints", [])
    if not datapoints:
        return 0.0, 0.0

    avg_vals = [dp["Average"] for dp in datapoints]
    max_vals = [dp["Maximum"] for dp in datapoints]
    return sum(avg_vals) / len(avg_vals), max(max_vals)


def analyze_cluster(ec_client, cw_client, cluster_id: str,
                    node_type: str) -> ClusterSizingRecommendation:
    """Analyze a single ElastiCache cluster and generate sizing recommendation."""

    current_pricing = ELASTICACHE_PRICING.get(node_type, {})
    current_hourly = current_pricing.get("hourly", 0.0)
    current_monthly = current_hourly * HOURS_PER_MONTH

    # Pull key metrics from CloudWatch
    avg_mem, max_mem = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "DatabaseMemoryUsagePercentage",
        "AWS/ElastiCache", "CacheClusterId"
    )
    avg_cpu, max_cpu = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "CPUUtilization",
        "AWS/ElastiCache", "CacheClusterId"
    )
    avg_hits, _ = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "CacheHits",
        "AWS/ElastiCache", "CacheClusterId"
    )
    avg_misses, _ = get_cloudwatch_metric_stats(
        cw_client, cluster_id, "CacheMisses",
        "AWS/ElastiCache", "CacheClusterId"
    )

    # Calculate cache hit rate
    total_ops = avg_hits + avg_misses
    cache_hit_rate = (avg_hits / total_ops * 100) if total_ops > 0 else 0.0

    recommended_node = None
    recommended_monthly = None
    action = "KEEP"
    reasoning = ""

    # Sizing decision logic
    if avg_mem < 30 and max_mem < 45:
        # Memory significantly underutilized — downsize candidate
        node_types_sorted = sorted(
            ELASTICACHE_PRICING.items(),
            key=lambda x: x[1]["memory_gb"]
        )
        current_memory = current_pricing.get("memory_gb", 0)
        target_memory = current_memory * (max_mem / 100) * 1.5  # 50% headroom

        for node_name, node_specs in node_types_sorted:
            if node_specs["memory_gb"] >= target_memory:
                if node_specs["hourly"] < current_hourly:
                    recommended_node = node_name
                    recommended_monthly = node_specs["hourly"] * HOURS_PER_MONTH
                    action = "DOWNSIZE"
                    reasoning = (
                        f"Avg memory {avg_mem:.1f}%, max {max_mem:.1f}%. "
                        f"Node is oversized. Target memory: {target_memory:.1f}GB."
                    )
                break

    elif max_mem > 85:
        # Memory pressure — upsize required
        node_types_sorted = sorted(
            ELASTICACHE_PRICING.items(),
            key=lambda x: x[1]["memory_gb"]
        )
        current_memory = current_pricing.get("memory_gb", 0)
        target_memory = current_memory * 1.5

        for node_name, node_specs in node_types_sorted:
            if node_specs["memory_gb"] >= target_memory:
                recommended_node = node_name
                recommended_monthly = node_specs["hourly"] * HOURS_PER_MONTH
                action = "UPSIZE"
                reasoning = (
                    f"Max memory utilization {max_mem:.1f}% indicates eviction risk. "
                    f"Recommend node with {target_memory:.1f}GB+ memory."
                )
                break

    if cache_hit_rate < 80 and action == "KEEP":
        action = "INVESTIGATE"
        reasoning = (
            f"Cache hit rate {cache_hit_rate:.1f}% is below 80% threshold. "
            f"Cache may not be providing adequate value — review TTL and key strategy."
        )

    if action == "KEEP" and not reasoning:
        reasoning = (
            f"Memory utilization healthy at avg {avg_mem:.1f}%, max {max_mem:.1f}%. "
            f"Cache hit rate {cache_hit_rate:.1f}% is acceptable."
        )

    monthly_savings = 0.0
    if recommended_monthly and action == "DOWNSIZE":
        monthly_savings = current_monthly - recommended_monthly
    elif recommended_monthly and action == "UPSIZE":
        monthly_savings = -(recommended_monthly - current_monthly)  # negative = cost increase

    return ClusterSizingRecommendation(
        cluster_id=cluster_id,
        current_node_type=node_type,
        current_monthly_cost=round(current_monthly, 2),
        avg_memory_utilization_pct=round(avg_mem, 1),
        max_memory_utilization_pct=round(max_mem, 1),
        avg_cpu_utilization_pct=round(avg_cpu, 1),
        avg_cache_hit_rate_pct=round(cache_hit_rate, 1),
        recommended_node_type=recommended_node,
        recommended_monthly_cost=round(recommended_monthly, 2) if recommended_monthly else None,
        monthly_savings=round(monthly_savings, 2),
        action=action,
        reasoning=reasoning
    )


def main():
    session = boto3.Session()
    ec_client = session.client("elasticache", region_name="us-east-1")
    cw_client = session.client("cloudwatch", region_name="us-east-1")

    # Get all Redis clusters
    paginator = ec_client.get_paginator("describe_cache_clusters")
    all_clusters = []
    for page in paginator.paginate(ShowCacheNodeInfo=True):
        all_clusters.extend(page["CacheClusters"])

    recommendations = []
    total_current_monthly = 0.0
    total_potential_savings = 0.0

    print(f"\n{'='*80}")
    print(f"ElastiCache Sizing Report — {datetime.utcnow().strftime('%Y-%m-%d %H:%M UTC')}")
    print(f"{'='*80}\n")

    for cluster in all_clusters:
        cluster_id = cluster["CacheClusterId"]
        node_type = cluster["CacheNodeType"]
        engine = cluster.get("Engine", "unknown")

        if engine != "redis":
            continue

        rec = analyze_cluster(ec_client, cw_client, cluster_id, node_type)
        recommendations.append(rec)

        total_current_monthly += rec.current_monthly_cost
        if rec.monthly_savings > 0:
            total_potential_savings += rec.monthly_savings

        print(f"Cluster: {rec.cluster_id}")
        print(f"  Current Node:       {rec.current_node_type} (${rec.current_monthly_cost:.2f}/mo)")
        print(f"  Memory Util:        avg {rec.avg_memory_utilization_pct}% / max {rec.max_memory_utilization_pct}%")
        print(f"  CPU Util:           avg {rec.avg_cpu_utilization_pct}%")
        print(f"  Cache Hit Rate:     {rec.avg_cache_hit_rate_pct}%")
        print(f"  Action:             {rec.action}")
        print(f"  Reasoning:          {rec.reasoning}")
        if rec.recommended_node_type:
            print(f"  Recommended Node:   {rec.recommended_node_type} (${rec.recommended_monthly_cost:.2f}/mo)")
            print(f"  Monthly Savings:    ${rec.monthly_savings:.2f}")
        print()

    print(f"{'='*80}")
    print(f"SUMMARY")
    print(f"  Total Current Monthly Cost:     ${total_current_monthly:.2f}")
    print(f"  Total Potential Monthly Savings: ${total_potential_savings:.2f}")
    print(f"  Annual Savings Opportunity:      ${total_potential_savings * 12:.2f}")
    print(f"{'='*80}\n")

    # Write JSON output for downstream processing or ticketing
    output = {
        "generated_at": datetime.utcnow().isoformat(),
        "total_current_monthly_cost": round(total_current_monthly, 2),
        "total_potential_monthly_savings": round(total_potential_savings, 2),
        "recommendations": [
            {
                "cluster_id": r.cluster_id,
                "current_node_type": r.current_node_type,
                "current_monthly_cost": r.current_monthly_cost,
                "action": r.action,
                "recommended_node_type": r.recommended_node_type,
                "monthly_savings": r.monthly_savings,
                "reasoning": r.reasoning
            }
            for r in recommendations
        ]
    }

    with open("/tmp/elasticache_sizing_report.json", "w") as f:
        json.dump(output, f, indent=2)
    print("Report written to /tmp/elasticache_sizing_report.json")


if __name__ == "__main__":
    main()

21.3 Cache Hit Rate Monitoring and the Cost of Cache Misses

A cache that isn't hitting is worse than no cache at all — you've added infrastructure cost and latency on cache misses without reducing database load. The break-even cache hit rate for most workloads is approximately 60–70%, but the economic sweet spot is 85% or higher.

Here is the math on why cache hit rate matters so much to your bill. Consider an application serving 10,000 requests/minute:

  • → At **50% hit rate**: 5,000 requests/minute still hit the database. Database must be sized for full concurrent load.
  • → At **80% hit rate**: 2,000 requests/minute hit the database. Database can be one tier smaller.
  • → At **95% hit rate**: 500 requests/minute hit the database. Database can often drop two tiers.

    • For an r6g.4xlarge RDS PostgreSQL Multi-AZ ($3,504/month) that can be right-sized based on cache effectiveness:

  • → 80% hit rate → `r6g.2xlarge` ($1,752/month) + `cache.r6g.xlarge` ($208/month) = **$1,544/month savings**
  • → 95% hit rate → `r6g.xlarge` ($876/month) + `cache.r6g.xlarge` ($208/month) = **$2,420/
