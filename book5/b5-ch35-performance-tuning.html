Chapter 35: Query Performance Tuning on Managed Services

Query performance tuning on managed cloud databases is fundamentally the same discipline you've practiced for years — identify the slow query, understand the execution plan, fix the root cause — but the environment imposes constraints that change how you investigate, what levers you can pull, and where the bottlenecks actually live. You can't attach a profiler directly to the OS, you can't touch the kernel scheduler, and you can't install arbitrary extensions. What you get instead is a set of cloud-native observability tools, managed parameter systems, and platform-specific optimizations that, once mastered, give you most of what you need. This chapter covers the full tuning workflow on AWS RDS/Aurora, Azure SQL, and Google Cloud SQL/AlloyDB — from capturing slow queries to fixing execution plans to understanding where managed service limits actually bite you in production.

---

35.1 Capturing and Identifying Slow Queries

The first step in any tuning engagement is visibility: find the queries causing problems before you guess at solutions. On self-managed PostgreSQL, you enabled pg_stat_statements, tailed the slow query log, or ran EXPLAIN ANALYZE in a session. On managed services, the same data exists but reaches you through different channels.

AWS RDS and Aurora (PostgreSQL)

On RDS PostgreSQL, slow query logging is controlled through the parameter group. The critical parameters are log_min_duration_statement (in milliseconds), log_statement, and pg_stat_statements.track. You cannot edit the parameter group in the console and expect it to take effect instantly on production without a reboot for static parameters — but log_min_duration_statement is dynamic, so you can apply it without restart.

# Modify the RDS parameter group to enable slow query logging
aws rds modify-db-parameter-group \
  --db-parameter-group-name prod-postgres15-params \
  --parameters \
    "ParameterName=log_min_duration_statement,ParameterValue=1000,ApplyMethod=immediate" \
    "ParameterName=log_statement,ParameterValue=none,ApplyMethod=immediate" \
    "ParameterName=log_lock_waits,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=log_temp_files,ParameterValue=10240,ApplyMethod=immediate"

# Verify the change took effect without a reboot
aws rds describe-db-parameters \
  --db-parameter-group-name prod-postgres15-params \
  --query "Parameters[?ParameterName=='log_min_duration_statement']"

Logs are streamed to CloudWatch Logs automatically if you have EnableCloudwatchLogsExports set. From there, CloudWatch Logs Insights lets you run structured queries against the raw log text:

# Query CloudWatch Logs Insights for the top slow queries in the last hour
aws logs start-query \
  --log-group-name /aws/rds/instance/prod-db-01/postgresql \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-string '
    fields @timestamp, @message
    | filter @message like /duration:/
    | parse @message "duration: * ms  statement: *" as duration_ms, statement
    | stats avg(duration_ms) as avg_ms, max(duration_ms) as max_ms, count() as executions
        by statement
    | sort max_ms desc
    | limit 25
  '

This gives you query text, average duration, and execution count directly from CloudWatch — no SSH session required.

For RDS SQL Server, Performance Insights is the primary tool. It surfaces the Average Active Sessions (AAS) metric, broken down by wait type, SQL statement, host, and user. This is the managed equivalent of querying sys.dm_exec_query_stats combined with sys.dm_os_wait_stats. Enable it at instance creation or modify the instance to turn it on:

aws rds modify-db-instance \
  --db-instance-identifier prod-sqlserver-01 \
  --enable-performance-insights \
  --performance-insights-retention-period 731 \
  --apply-immediately

Performance Insights retains 7 days free; extending retention up to the 731-day maximum incurs an additional charge billed per vCPU-hour, which scales with both instance size and how far back you extend the window. Check current AWS pricing for your region before enabling extended retention fleet-wide — on a large multi-vCPU instance it becomes a meaningful recurring line item.

Azure SQL Database

Azure SQL surfaces query performance data through Query Store, which is enabled by default on Azure SQL Database (unlike on-premises SQL Server where you had to enable it manually). The Query Store captures execution plans, runtime statistics, and wait statistics automatically. Combine this with the Query Performance Insight blade in the Azure portal or query it directly:

-- Top 20 queries by total CPU time in the last 24 hours from Query Store
SELECT TOP 20
    q.query_id,
    qt.query_sql_text,
    rs.count_executions,
    rs.avg_duration / 1000.0 AS avg_duration_ms,
    rs.avg_cpu_time / 1000.0 AS avg_cpu_ms,
    rs.avg_logical_io_reads,
    rs.avg_rowcount,
    CAST(rs.avg_cpu_time * rs.count_executions / 1e6 AS DECIMAL(10,2)) AS total_cpu_seconds
FROM sys.query_store_query q
JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
JOIN sys.query_store_runtime_stats_interval rsi ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
WHERE rsi.start_time >= DATEADD(HOUR, -24, GETUTCDATE())
ORDER BY total_cpu_seconds DESC;

Google Cloud SQL and AlloyDB

Cloud SQL for PostgreSQL streams logs to Cloud Logging. Enable log_min_duration_statement through a database flag on the instance:

# Set slow query threshold to 500ms on Cloud SQL PostgreSQL
gcloud sql instances patch prod-cloudsql-pg \
  --database-flags \
    log_min_duration_statement=500,\
    log_lock_waits=on,\
    log_temp_files=10240,\
    track_io_timing=on

# Query slow queries from Cloud Logging using the logging API
gcloud logging read \
  'resource.type="cloudsql_database" AND
   textPayload=~"duration:" AND
   resource.labels.database_id="my-project:prod-cloudsql-pg"' \
  --limit=50 \
  --format="value(textPayload)" \
  --freshness=1h

AlloyDB adds the google_columnar_engine extension for OLAP acceleration and exposes query insights through the AlloyDB console UI and Cloud Monitoring. The pg_stat_statements view is available on both, and AlloyDB's Query Insights surfaces plan regressions automatically — a capability you would have built yourself with a custom baseline table in a self-managed environment.

35.2 Reading Execution Plans on Managed Services

Getting an execution plan on a managed service is mechanically simple, but interpreting the plan in the context of managed infrastructure requires calibrating your assumptions. The optimizer is the same PostgreSQL or SQL Server optimizer you know — but the cost model is tuned differently, statistics maintenance behaves differently, and some plan choices are shaped by the storage architecture.

PostgreSQL Plans on RDS and Aurora

EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) works exactly as it does on self-managed PostgreSQL. The difference on Aurora is in what the buffer counts mean: Aurora uses a distributed storage layer, so buffer hits that look like shared cache hits may actually be served from the Aurora buffer pool, while misses trigger Aurora storage I/O rather than OS page cache misses. The I/O cost model in the planner doesn't fully account for Aurora's storage characteristics, which sometimes causes the planner to prefer sequential scans when an index seek would be faster on spinning disk, because Aurora's storage is effectively SSD-backed with 6-way replication — the sequential scan penalty is lower than what the seq_page_cost parameter assumes.

-- Capture a plan with full detail and serialize it for storage
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON)
SELECT
    o.order_id,
    o.customer_id,
    o.order_date,
    SUM(oi.quantity * oi.unit_price) AS order_total
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.order_date >= '2024-01-01'
  AND o.status = 'COMPLETED'
GROUP BY o.order_id, o.customer_id, o.order_date
HAVING SUM(oi.quantity * oi.unit_price) > 500
ORDER BY order_total DESC
LIMIT 100;

When you see a sequential scan on a large table and suspect the planner is making the wrong choice, check the statistics before blaming the plan:

-- Check when statistics were last collected and how accurate they are
SELECT
    schemaname,
    tablename,
    n_live_tup,
    n_dead_tup,
    last_autoanalyze,
    last_analyze,
    last_autoanalyze - now() AS time_since_autoanalyze,
    n_mod_since_analyze
FROM pg_stat_user_tables
WHERE tablename IN ('orders', 'order_items')
ORDER BY n_mod_since_analyze DESC;

-- Check column statistics for a specific column
SELECT
    attname,
    n_distinct,
    correlation,
    most_common_vals,
    most_common_freqs
FROM pg_stats
WHERE tablename = 'orders'
  AND attname IN ('status', 'order_date');

On RDS, autovacuum runs under the managed service's control. You can tune its parameters through the parameter group, but you cannot run VACUUM manually with OS-level priority settings or kill the autovacuum workers through system commands. If statistics are stale on a large partitioned table during a bulk load window, you can run ANALYZE orders; manually as the database superuser — RDS grants you rds_superuser which has sufficient privileges for this.

Aurora-Specific Plan Considerations

Aurora PostgreSQL's parallel query feature (available on Aurora v3, which is PostgreSQL 15-compatible) can push query processing down to the distributed storage layer. When enabled, plans show Parallel Seq Scan nodes that indicate storage-level parallelism. This is structurally different from PostgreSQL's parallel workers, which run on the compute node. You can control whether a query uses Aurora parallel query by setting aurora_parallel_query:

-- Enable Aurora parallel query for a specific session and compare plans
SET aurora_parallel_query = ON;
EXPLAIN SELECT COUNT(*), AVG(total_amount) FROM orders WHERE order_date >= '2023-01-01';

SET aurora_parallel_query = OFF;
EXPLAIN SELECT COUNT(*), AVG(total_amount) FROM orders WHERE order_date >= '2023-01-01';

Parallel query shows the largest gains on full table scans of tables larger than 1 million rows where the result set fits in memory after aggregation. For OLTP queries hitting indexes, it adds overhead.

SQL Server Plans on Azure SQL

Azure SQL Database uses the same execution plan XML format as SQL Server on-premises. The key difference is that sys.dm_exec_query_plan and sys.dm_exec_query_stats are available, but sys.dm_os_ring_buffers and some internal DMVs are restricted. For plan capture and analysis, use Query Store rather than ad hoc DMV queries — Query Store persists plans across failovers, which DMV caches do not.

To force a specific plan (the equivalent of using a plan guide on-premises), Azure SQL supports Query Store plan forcing:

-- Force a specific plan for a regressed query using Query Store
-- First, identify the query_id and the plan_id of the good historical plan
SELECT
    q.query_id,
    p.plan_id,
    rs.avg_duration,
    rs.count_executions,
    p.query_plan
FROM sys.query_store_query q
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
WHERE q.query_id = 1547
ORDER BY rs.last_execution_time DESC;

-- Force the known-good plan
EXEC sys.sp_query_store_force_plan
    @query_id = 1547,
    @plan_id = 892;

-- Verify the forcing is active
SELECT
    q.query_id,
    p.plan_id,
    p.is_forced_plan,
    p.force_failure_count,
    p.last_force_failure_reason_desc
FROM sys.query_store_query q
JOIN sys.query_store_plan p ON q.query_id = p.query_id
WHERE q.query_id = 1547;

Plan forcing in Query Store survives database restarts and failovers on Azure SQL — this is a meaningful improvement over on-premises plan guides, which you had to manage separately.

35.3 Index Tuning in the Cloud: What Works and What Doesn't

Index tuning on managed services is conceptually identical to on-premises: add missing indexes, remove unused ones, choose the right index type for the access pattern. The cloud layer changes the operational mechanics — how you identify candidates, how you apply changes safely, and what the platform does automatically.

AWS RDS PostgreSQL: pg_stat_user_indexes and Missing Index Detection

PostgreSQL has no built-in missing index advisor. On self-managed systems, you'd combine pg_stat_statements with EXPLAIN output and pg_stat_user_indexes to find candidates. On RDS, you have the same data plus the option to use the RDS Performance Insights API to correlate wait events with specific queries:

-- Find indexes that are never used (candidates for removal)
-- Run this after a representative workload period (at least 7 days post-restart)
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_relation_size(indexrelid) DESC;

-- Find sequential scans on large tables that might benefit from an index
SELECT
    schemaname,
    relname AS tablename,
    seq_scan,
    seq_tup_read,
    idx_scan,
    n_live_tup,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    ROUND(seq_scan::NUMERIC / NULLIF(seq_scan + idx_scan, 0) * 100, 2) AS seq_scan_pct
FROM pg_stat_user_tables
WHERE n_live_tup > 100000
  AND seq_scan > 100
ORDER BY seq_tup_read DESC
LIMIT 20;

A gotcha on RDS: pg_stat_user_indexes.idx_scan resets when the instance restarts. RDS Multi-AZ failovers cause a restart on the new primary. If you collected baseline data before a recent failover, your unused index candidates may be incorrect. Always check pg_stat_bgwriter.stats_reset to see when statistics were last reset:

SELECT stats_reset FROM pg_stat_bgwriter;

Creating Indexes Concurrently

CREATE INDEX CONCURRENTLY works on RDS and Cloud SQL exactly as it does on-premises — it builds the index without holding an AccessExclusiveLock on the table, so production reads and writes continue. The gotcha is that if the concurrent build fails (connection drop, out-of-disk-space), it leaves an invalid index behind that you must drop manually. On Aurora, an invalid index in pg_index.indisvalid = false will not be used by the planner but still slows down DML because the executor still attempts to update it.

-- Build a partial index concurrently for the active order pattern
CREATE INDEX CONCURRENTLY idx_orders_active_date
ON orders (customer_id, order_date DESC)
WHERE status IN ('PENDING', 'PROCESSING');

-- Verify the index built successfully
SELECT
    indexname,
    indisvalid,
    indisready
FROM pg_indexes
JOIN pg_index ON indexrelid = (
    SELECT oid FROM pg_class WHERE relname = 'idx_orders_active_date'
)
WHERE tablename = 'orders'
  AND indexname = 'idx_orders_active_date';

Azure SQL: Automatic Index Recommendations

Azure SQL Database includes an automatic tuning engine that recommends and — if you enable it — automatically creates and drops indexes based on Query Store data. This is the cloud equivalent of the Database Engine Tuning Advisor, but it runs continuously and learns from production workload patterns.

# Check current automatic tuning state via Azure CLI
az sql db show \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name prod-database \
  --query "autoPauseDelay, automaticTuning"

# Enable automatic index creation recommendations (monitoring only, not auto-apply)
az sql db update \
  --resource-group prod-rg \
  --server prod-sql-server \
  --name prod-database \
  --auto-tuning-mode Auto

The recommendation: enable automatic tuning in Auto mode for index recommendations on read-heavy OLAP databases. For transactional OLTP databases where index creation causes brief write stalls and where any schema change needs a change control approval, leave it in recommendation-only mode and apply changes manually during maintenance windows.

AlloyDB: Columnar Engine for HTAP Workloads

AlloyDB's columnar engine maintains a column store in memory alongside the row store. When a query would benefit from columnar access, the planner routes it to the columnar engine automatically. You can check which tables have columnar data populated and force or hint columnar scans:

-- Check columnar engine population status
SELECT
    database_name,
    schema_name,
    table_name,
    column_count,
    row_count,
    memory_size_in_bytes / 1024 / 1024 AS memory_mb
FROM g_columnar_relations;

-- Verify a query is using the columnar engine
EXPLAIN SELECT
    product_category,
    SUM(revenue) AS total_revenue,
    AVG(margin_pct) AS avg_margin
FROM sales_facts
WHERE sale_date BETWEEN '2024-01-01' AND '2024-12-31'
GROUP BY product_category;
-- Look for "Custom Scan (columnar scan)" in the plan output

35.4 Wait Event Analysis and Resource Bottleneck Identification

Experienced DBAs know that execution time alone is incomplete — a query that runs in 10ms but waits 2 seconds for a lock isn't a query problem, it's a concurrency problem. Cloud managed services surface wait events through different mechanisms than on-premises but with equivalent depth.

RDS Performance Insights Wait Event Analysis

Performance Insights breaks down Average Active Sessions by wait event type. For PostgreSQL, the wait event categories map directly to pg_stat_activity.wait_event_type values: LWLock, Lock, BufferPin, IO, Client. For SQL Server, they map to SQL Server wait types: LCK_M_X, PAGEIOLATCH_SH, ASYNC_NETWORK_IO.

Use the Performance Insights API to pull wait data programmatically for trend analysis:

import boto3
from datetime import datetime, timedelta, timezone

pi_client = boto3.client('pi', region_name='us-east-1')

# Pull top wait events for the last 3 hours at 1-minute granularity
response = pi_client.get_resource_metrics(
    ServiceType='RDS',
    Identifier='db:prod-db-01',  # Performance Insights resource ID
    StartTime=datetime.now(timezone.utc) - timedelta(hours=3),
    EndTime=datetime.now(timezone.utc),
    PeriodInSeconds=60,
    MetricQueries=[
        {
            'Metric': 'db.load.avg',
            'GroupBy': {
                'Group': 'db.wait_event',
                'Dimensions': ['db.wait_event.type', 'db.wait_event.name'],
                'Limit': 10
            }
        }
    ]
)

for metric_list in response['MetricList']:
    key = metric_list['Key']
    wait_type = key.get('Dimensions', {}).get('db.wait_event.type', 'unknown')
    wait_name = key.get('Dimensions', {}).get('db.wait_event.name', 'unknown')
    
    # Calculate average load contribution for this wait event
    data_points = metric_list['DataPoints']
    if data_points:
        avg_load = sum(dp.get('Value', 0) for dp in data_points) / len(data_points)
        print(f"{wait_type}/{wait_name}: avg AAS contribution = {avg_load:.3f}")

On Aurora PostgreSQL, the most common problematic wait events in production:

  • → `IO:DataFileRead` — Buffer pool misses, often from missing indexes or OLAP queries on OLTP instances
  • → `Lock:relation` — DDL blocking DML or long-running transactions holding table locks
  • → `LWLock:buffer_content` — High-concurrency UPDATE hot spots (counter tables, queue tables)
  • → `Client:ClientRead` — Network latency between application and database; often a VPC placement issue or RDS Proxy connection overhead
    • graph TD
    A[Top wait event
    from Performance Insights] --> B{Wait type}
    B -->|IO:DataFileRead| C[Buffer pool miss:
    add index or increase cache]
    B -->|Lock:relation| D[Blocking DDL/long transaction:
    fix concurrency, not indexes]
    B -->|LWLock:buffer_content| E[Hot-row contention:
    redesign counter/queue pattern]
    B -->|Client:ClientRead| F[Network/app-side latency:
    check VPC placement, proxy overhead]

    *Let the dominant wait event categorize the problem before choosing a remedy — an index fix does nothing for a lock-contention problem.*

    Azure SQL: sys.dm_os_wait_stats and Extended Events

    On Azure SQL, sys.dm_os_wait_stats is available with some restrictions — the SQLTRACE_* and DBMIRROR_* wait types are filtered out as they're internal to the platform. For real-time wait analysis, Extended Events replace SQL Trace (Profiler is unsupported on Azure SQL):

    -- Create a lightweight Extended Events session to capture query waits
CREATE EVENT SESSION [prod_wait_analysis] ON DATABASE
ADD EVENT sqlserver.sql_statement_completed (
    ACTION (
        sqlserver.sql_text,
        sqlserver.query_hash,
        sqlserver.database_name,
        sqlserver.username
    )
    WHERE (
        duration > 500000  -- 500ms in microseconds
        AND sqlserver.database_name = N'ProdDB'
    )
),
ADD EVENT sqlos.wait_info (
    ACTION (sqlserver.sql_text, sqlserver.query_hash)
    WHERE (
        duration > 100000   -- 100ms wait
        AND opcode = 1      -- end of wait only
    )
)
ADD TARGET package0.ring_buffer (SET max_memory = 51200)
WITH (
    MAX_DISPATCH_LATENCY = 5 SECONDS,
    TRACK_CAUSALITY = ON
);

ALTER EVENT SESSION [prod_wait_analysis] ON DATABASE STATE = START;

-- Read the ring buffer results
SELECT
    event_data.value('(@name)', 'nvarchar(128)') AS event_name,
    event_data.value('(action[@name="sql_text"]/value)[1]', 'nvarchar(max)') AS sql_text,
    event_data.value('(data[@name="wait_type"]/text)[1]', 'nvarchar(128)') AS wait_type,
    event_data.value('(data[@name="duration"]/value)[1]', 'bigint') / 1000 AS duration_ms
FROM (
    SELECT CAST(target_data AS XML) AS target_data_xml
    FROM sys.dm_xe_database_sessions s
    JOIN sys.dm_xe_database_session_targets t ON s.address = t.event_session_address
    WHERE s.name = 'prod_wait_analysis'
      AND t.target_name = 'ring_buffer'
) AS ring_buffer_data
CROSS APPLY target_data_xml.nodes('//RingBufferTarget/event') AS XEventData(event_data)
ORDER BY duration_ms DESC;

    Cloud SQL PostgreSQL: pg_stat_activity for Live Session Analysis

    On Cloud SQL, pg_stat_activity is available with the same columns as on-premises PostgreSQL. Because you cannot attach a debugger or strace to a backend process, this view — combined with pg_locks — is your primary tool for live session and blocking investigation:

    -- Find blocking chains on Cloud SQL (works identically on RDS Aurora)
WITH RECURSIVE lock_tree AS (
    -- Base: sessions that are waiting for a lock
    SELECT
        blocked.pid AS blocked_pid,
        blocked.query AS blocked_query,
        blocked.wait_event_type,
        blocked.wait_event,
        blocked.state,
        blocking.pid AS blocking_pid,
        blocking.query AS blocking_query,
        blocking.query_start AS blocking_started,
        now() - blocking.query_start AS blocking_duration,
        1 AS depth
    FROM pg_stat_activity blocked
    JOIN pg_locks blocked_locks
        ON blocked.pid = blocked_locks.pid
        AND NOT blocked_locks.granted
    JOIN pg_locks blocking_locks
        ON blocking_locks.locktype = blocked_locks.locktype
        AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
        AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
        AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
        AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
        AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
        AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
        AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
        AND blocking_locks.granted
        AND blocking_locks.pid != blocked_locks.pid
    JOIN pg_stat_activity blocking
        ON blocking.pid = blocking_locks.pid

    UNION ALL

    -- Recursive: find sessions blocking the already-identified blockers
    SELECT
        lt.blocked_pid,
        lt.blocked_query,
        lt.wait_event_type,
        lt.wait_event,
        lt.state,
        blocking.pid AS blocking_pid,
        blocking.query AS blocking_query,
        blocking.query_start AS blocking_started,
        now() - blocking.query_start AS blocking_duration,
        lt.depth + 1
    FROM lock_tree lt
    JOIN pg_locks blocked_locks ON lt.blocking_pid = blocked_locks.pid AND NOT blocked_locks.granted
    JOIN pg_locks blocking_locks
        ON blocking_locks.locktype = blocked_locks.locktype
        AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
        AND blocking_locks.granted
        AND blocking_locks.pid != blocked_locks.pid
    JOIN pg_stat_activity blocking ON blocking.pid = blocking_locks.pid
    WHERE lt.depth < 5
)
SELECT
    depth,
    blocked_pid,
    LEFT(blocked_query, 80) AS blocked_query_snippet,
    wait_event_type || ':' || wait_event AS wait,
    blocking_pid,
    LEFT(blocking_query, 80) AS blocking_query_snippet,
    blocking_duration
FROM lock_tree
ORDER BY depth, blocking_duration DESC;

    35.5 Parameter Tuning on Managed Services

    On self-managed PostgreSQL or SQL Server, you tuned memory allocations, parallelism settings, and I/O behavior through postgresql.conf or sp_configure and had full control over the restart cycle. On managed services, parameters are set through the platform's parameter system, some changes require a restart (making them high-impact in production), and some parameters are immutable — the platform controls them.

    RDS PostgreSQL: Tunable vs. Platform-Controlled Parameters

    The most performance-relevant parameters you can tune on RDS PostgreSQL:

    | Parameter | Default | Tuning Direction | Restart Required |

    |-----------|---------|------------------|------------------|

    | shared_buffers | 25% of RAM | Increase to 25-40% RAM | Yes |

    | work_mem | 4MB | Increase carefully per session | No |

    | maintenance_work_mem | 64MB | Increase for faster VACUUM/index builds | No |

    | effective_cache_size | 4GB | Set to ~75% of total RAM | No |

    | random_page_cost | 4.0 | Lower to 1.1-1.5 for SSD/Aurora | No |

    | max_parallel_workers_per_gather | 2 | Tune based on vCPU count | No |

    | checkpoint_completion_target | 0.9 | Keep at 0.9 | No |

    | wal_buffers | auto | Usually auto is fine | Yes |

    | autovacuum_vacuum_scale_factor | 0.2 | Lower to 0.01-0.05 for large tables | No |

    Parameters RDS does not expose (they are controlled by the platform):

  • → `wal_level` — Fixed at `logical` on Aurora, `replica` on RDS standard
  • → `max_wal_size` and `min_wal_size` — Platform-managed
  • → `archive_mode` / `archive_command` — Managed by AWS for automated backups
  • → `fsync`, `full_page_writes` — Always enabled; platform guarantees these for durability

    • A common misconfiguration on RDS is leaving work_mem at its default 4MB on an instance with 64GB RAM running analytics queries. The result is excessive temp file spills. The right approach is not to set work_mem globally high — that multiplies by max_connections and exhausts RAM — but to set it per session or per role for analytics workloads:

    -- Set work_mem for an analytics role without changing the global default
ALTER ROLE analytics_user SET work_mem = '256MB';

-- Or set it for the current session only when running a known expensive query
SET work_mem = '128MB';
EXPLAIN (ANALYZE, BUFFERS) SELECT ... FROM large_aggregation_query;
RESET work_mem;

    The session-level SET approach is particularly useful when you're tuning a specific batch job that runs under a dedicated database user — it doesn't affect OLTP connections using the same instance.

    Aurora-Specific: cluster-level vs. instance-level parameter groups

    Aurora uses two layers of parameter groups: the DB cluster parameter group (applies to the whole cluster, controls parameters like rds.force_ssl, shared_preload_libraries) and the DB instance parameter group (applies to a specific instance, controls work_mem, max_connections, etc.). Mistakes happen when engineers apply changes to the wrong level. Adding pg_stat_statements to shared_preload_libraries at the instance level has no effect on Aurora — it must be in the cluster parameter group because the extension is loaded at cluster startup, not per instance.

    # Correct: add pg_stat_statements to the cluster parameter group
aws rds modify-db-cluster-parameter-group \
  --db-cluster-parameter-group-name prod-aurora-cluster-params \
  --parameters \
    "ParameterName=shared_preload_libraries,ParameterValue=pg_stat_statements,ApplyMethod=pending-reboot"

# Check which parameter group is attached to the cluster vs instance
aws rds describe-db-clusters \
  --db-cluster-identifier prod-aurora-cluster \
  --query "DBClusters[0].DBClusterParameterGroup"

aws rds describe-db-instances \
  --db-instance-identifier prod-aurora-cluster-instance-1 \
  --query "DBInstances[0].DBParameterGroups"

    Azure SQL: Resource Governance and DTU/vCore Limits

    Azure SQL Database manages memory, CPU, and I/O through its resource governance layer. In the DTU model, all resources are bundled. In the vCore model, you have more visibility: sys.dm_user_db_resource_governance shows the effective limits applied to your database:

    -- View effective resource limits for the current Azure SQL database
SELECT
    database_id,
    logical_database_guid,
    max_cpu,
    max_db_memory_mb,
    max_log_rate_mbps,
    max_workers,
    max_sessions,
    max_instance_max_db_memory_mb
FROM sys.dm_user_db_resource_governance;

-- Check current resource consumption against limits
SELECT
    avg_cpu_percent,
    avg_data_io_percent,
    avg_log_write_percent,
    avg_memory_usage_percent,
    max_worker_percent,
    max_session_percent
FROM sys.dm_db_resource_stats
ORDER BY end_time DESC
OFFSET 0 ROWS FETCH NEXT 30 ROWS ONLY;

    If avg_log_write_percent is consistently near 100%, log write throughput is the bottleneck. The fix is not to tune a parameter — you cannot increase the log rate limit without changing service tier. This is the key difference from on-premises: some bottlenecks on Azure SQL are resolved only by scaling up or out, not by configuration.

    Google Cloud SQL: Flags and Connection Limits

    Cloud SQL exposes PostgreSQL parameters as database flags. The flag naming matches PostgreSQL parameter names exactly. The most impactful flags for tuning on Cloud SQL:

    # Apply a tuning set for a high-concurrency OLTP workload on Cloud SQL
gcloud sql instances patch prod-cloudsql-pg \
  --database-flags \
    shared_buffers=8GB,\
    effective_cache_size=24GB,\
    work_mem=16MB,\
    maintenance_work_mem=2GB,\
    random_page_cost=1.1,\
    effective_io_concurrency=200,\
    max_parallel_workers_per_gather=4,\
    max_parallel_workers=8,\
    autovacuum_max_workers=5,\
    autovacuum_vacuum_scale_factor=0.02,\
    autovacuum_analyze_scale_factor=0.01,\
    log_autovacuum_min_duration=250,\
    checkpoint_completion_target=0.9,\
    wal_compression=on

# Note: shared_buffers requires an instance restart on Cloud SQL
# Cloud SQL will restart the instance automatically when static flags change

    Cloud SQL does not allow max_connections above a service-tier-specific ceiling. If your application requires more than the allowed maximum, you must use Cloud SQL Auth Proxy with connection pooling (PgBouncer or the built-in pgconnection_pool) rather than setting a higher max_connections on the instance.

    35.6 Query Rewrites and Application-Level Optimizations

    After index tuning, statistics refresh, and parameter adjustments, some queries still perform poorly because the query structure itself is inefficient for the access pattern. These rewrites are platform-agnostic in logic but have platform-specific considerations in execution.

    N+1 Patterns Detected Through pg_stat_statements

    The N+1 problem — issuing one query per row from a parent result set — produces a distinctive signature in pg_stat_statements: a parameterized query with very high calls count relative to total_exec_time, where the per-call time is low but the total time is large. This pattern is invisible in slow query logs because each individual call is fast.

    -- Identify N+1 candidates in pg_stat_statements
SELECT
    LEFT(query, 100) AS query_snippet,
    calls,
    mean_exec_time,
    total_exec_time,
    rows / calls AS avg_rows_per_call
FROM pg_stat_statements
WHERE calls > 10000
  AND mean_exec_time < 5   -- Fast individually (< 5ms)
  AND total_exec_time > 60000  -- But expensive in aggregate (> 60 seconds total)
ORDER BY total_exec_time DESC
LIMIT 20;

    The fix is a query rewrite at the application layer — replace the loop with a single query using WHERE id = ANY($1) with an array parameter, or with a JOIN. The PostgreSQL rewrite is straightforward:

    -- Before: N+1 pattern (application issues one query per order)
SELECT * FROM order_items WHERE order_id = $1;
-- (called 50,000 times in a reporting window)

-- After: single query with array unnesting
SELECT
    oi.*,
    o.customer_id,
    o.order_date
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
WHERE oi.order_id = ANY($1::bigint[]);
-- $1 is passed as an array of all order_ids needed

    The equivalent fix in SQL Server uses a table-valued parameter or a JSON array to pass multiple IDs in a single round trip:

    -- SQL Server: replace N+1 with a single query using JSON input
-- Before: called once per order_id
SELECT * FROM OrderItems WHERE OrderId = @order_id;

-- After: pass the full set as JSON
CREATE OR ALTER PROCEDURE dbo.GetOrderItemsBatch
    @order_ids NVARCHAR(MAX)  -- JSON array: [1001, 1002, 1003]
AS
BEGIN
    SELECT
        oi.*,
        o.CustomerId,
        o.OrderDate
    FROM OrderItems oi
    JOIN Orders o ON oi.OrderId = o.OrderId
    WHERE oi.OrderId IN (
        SELECT value FROM OPENJSON(@order_ids) WITH (value BIGINT '$')
    );
END;

    Pagination Anti-Patterns

    OFFSET/LIMIT (PostgreSQL) and OFFSET/FETCH (SQL Server) performance degrades as the offset grows because the database must scan and discard all rows before the offset position. On large tables with deep pagination, this becomes a full table scan disguised as a pagination query. Use keyset pagination instead:

    -- PostgreSQL: OFFSET-based pagination (slow for large offsets)
SELECT order_id, customer_id, order_date, total
FROM orders
ORDER BY order_date DESC, order_id DESC
OFFSET 50000 LIMIT 20;

-- PostgreSQL: Keyset pagination (constant time regardless of page depth)
-- Client passes the last seen (order_date, order_id) from the previous page
SELECT order_id, customer_id, order_date, total
FROM orders
WHERE (order_date, order_id) < ($last_order_date, $last_order_id)
ORDER BY order_date DESC, order_id DESC
LIMIT 20;

-- Requires a composite index to be efficient:
CREATE INDEX idx_orders_date_id ON orders (order_date DESC, order_id DESC);
    -- SQL Server: OFFSET/FETCH (slow for large page numbers)
SELECT OrderId, CustomerId, OrderDate, Total
FROM Orders
ORDER BY OrderDate DESC, OrderId DESC
OFFSET 50000 ROWS FETCH NEXT 20 ROWS ONLY;

-- SQL Server: Keyset pagination
SELECT OrderId, CustomerId, OrderDate, Total
FROM Orders
WHERE OrderDate < @last_order_date
   OR (OrderDate = @last_order_date AND OrderId < @last_order_id)
ORDER BY OrderDate DESC, OrderId DESC
OFFSET 0 ROWS FETCH NEXT 20 ROWS ONLY;

-- Supporting index:
CREATE INDEX IX_Orders_Date_Id ON Orders (OrderDate DESC, OrderId DESC);

    Covering Indexes for High-Frequency Lookup Patterns

    A covering index — one that includes all columns referenced in a query — eliminates the heap/table fetch entirely. On PostgreSQL, the INCLUDE clause adds non-key columns to the index leaf pages. On SQL Server, INCLUDE on a nonclustered index does the same:

    -- PostgreSQL: covering index with INCLUDE for a common customer lookup
CREATE INDEX CONCURRENTLY idx_orders_customer_covering
ON orders (customer_id, order_date DESC)
INCLUDE (status, total_amount, order_id);

-- Query that can be satisfied entirely from the index:
SELECT order_id, order_date, status, total_amount
FROM orders
WHERE customer_id = $1
  AND order_date >= NOW() - INTERVAL '90 days'
ORDER BY order_date DESC
LIMIT 50;
-- EXPLAIN will show "Index Only Scan" — no heap access
    -- SQL Server: covering nonclustered index with INCLUDE
CREATE NONCLUSTERED INDEX IX_Orders_Customer_Date_Covering
ON Orders (CustomerId, OrderDate DESC)
INCLUDE (Status, TotalAmount, OrderId);

-- The same query pattern uses the index without a Key Lookup:
SELECT OrderId, OrderDate, Status, TotalAmount
FROM Orders
WHERE CustomerId = @customer_id
  AND OrderDate >= DATEADD(DAY, -90, GETDATE())
ORDER BY OrderDate DESC;
-- SSMS plan should show Index Seek without Key Lookup

    35.7 Monitoring Query Performance Over Time

    One-time tuning sessions fix the immediate problem. Production systems need continuous monitoring to catch regressions before users report them. Cloud managed services provide the infrastructure for this; you provide the alerting thresholds and response playbooks.

    Automated Plan Regression Detection on Azure SQL

    Query Store's Automatic Plan Correction detects when a plan regresses (execution time degrades beyond a threshold compared to the previous plan) and forces the last known good plan automatically. You can configure the aggressiveness:

    -- Enable Automatic Plan Correction in Azure SQL
ALTER DATABASE [ProdDB]
SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON);

-- Check the history of automatic corrections
SELECT
    qsq.query_id,
    qsqt.query_sql_text,
    dra.reason,
    dra.score,
    dra.state_transition_reason,
    JSON_VALUE(dra.details, '$.implementationDetails.script') AS correction_script
FROM sys.dm_db_tuning_recommendations dra
JOIN sys.query_store_query qsq ON CAST(JSON_VALUE(dra.details, '$.queryId') AS BIGINT) = qsq.query_id
JOIN sys.query_store_query_text qsqt ON qsq.query_text_id = qsqt.query_text_id
WHERE dra.type = 'FORCE_LAST_GOOD_PLAN'
ORDER BY dra.score DESC;

    RDS: CloudWatch Alarms for Query Performance Metrics

    Set CloudWatch alarms on the database-level metrics that correlate with query performance degradation. The most reliable leading indicators are ReadLatency, WriteLatency, DiskQueueDepth, and DBLoad (via Performance Insights):

    # Create a CloudWatch alarm for high database load (>= instance vCPU count indicates saturation)
VCPU_COUNT=16  # for db.r6g.4xlarge

aws cloudwatch put-metric-alarm \
  --alarm-name "prod-db-high-load" \
  --alarm-description "DB load exceeds vCPU count - query saturation likely" \
  --metric-name DBLoad \
  --namespace AWS/RDS \
  --statistic Average \
  --period 300 \
  --evaluation-periods 3 \
  --threshold $VCPU_COUNT \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --dimensions Name=DBInstanceIdentifier,Value=prod-db-01 \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-oncall-alerts \
  --ok-actions arn:aws:sns:us-east-1:123456789012:db-oncall-alerts \
  --treat-missing-data notBreaching

# Alarm on read latency > 20ms average over 5 minutes
aws cloudwatch put-metric-alarm \
  --alarm-name "prod-db-high-read-latency" \
  --alarm-description "Read latency elevated - check for missing indexes or table scans" \
  --metric-name ReadLatency \
  --namespace AWS/RDS \
  --statistic Average \
  --period 300 \
  --evaluation-periods 2 \
  --threshold 0.020 \
  --comparison-operator GreaterThanThreshold \
  --dimensions Name=DBInstanceIdentifier,Value=prod-db-01 \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-oncall-alerts

    Building a Query Performance Baseline Table

    The most durable monitoring approach is a scheduled job that snapshots pg_stat_statements (PostgreSQL) or Query Store aggregates (SQL Server) into a history table. This lets you compare current performance against any historical baseline, detect gradual regressions over days or weeks, and tie performance changes to deployment events.

    -- PostgreSQL: create a baseline snapshot table
CREATE TABLE query_performance_snapshots (
    snapshot_time        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    queryid              BIGINT NOT NULL,
    query_text           TEXT,
    calls                BIGINT,
    total_exec_time_ms   DOUBLE PRECISION,
    mean_exec_time_ms    DOUBLE PRECISION,
    stddev_exec_time_ms  DOUBLE PRECISION,
    rows                 BIGINT,
    shared_blks_hit      BIGINT,
    shared_blks_read     BIGINT,
    temp_blks_written    BIGINT,
    PRIMARY KEY (snapshot_time, queryid)
) PARTITION BY RANGE (snapshot_time);

CREATE TABLE query_performance_snapshots_2024_q4
PARTITION OF query_performance_snapshots
FOR VALUES FROM ('2024-10-01') TO ('2025-01-01');

-- Snapshot procedure (run via pg_cron or an external scheduler)
INSERT INTO query_performance_snapshots (
    queryid, query_text, calls, total_exec_time_ms,
    mean_exec_time_ms, stddev_exec_time_ms, rows,
    shared_blks_hit, shared_blks_read, temp_blks_written
)
SELECT
    queryid,
    LEFT(query, 1000),
    calls,
    total_exec_time,
    mean_exec_time,
    stddev_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_written
FROM pg_stat_statements
WHERE calls > 10
ON CONFLICT (snapshot_time, queryid) DO UPDATE
    SET calls = EXCLUDED.calls,
        total_exec_time_ms = EXCLUDED.total_exec_time_ms,
        mean_exec_time_ms = EXCLUDED.mean_exec_time_ms;

-- Compare current performance vs. 7-day baseline
WITH baseline AS (
    SELECT
        queryid,
        AVG(mean_exec_time_ms) AS baseline_mean_ms,
        AVG(calls) AS baseline_calls_per_snapshot
    FROM query_performance_snapshots
    WHERE snapshot_time BETWEEN NOW() - INTERVAL '8 days'
                             AND NOW() - INTERVAL '1 day'
    GROUP BY queryid
),
current AS (
    SELECT
        queryid,
        mean_exec_time AS current_mean_ms,
        calls AS current_calls
    FROM pg_stat_statements
)
SELECT
    c.queryid,
    ROUND(c.current_mean_ms::NUMERIC, 2) AS current_mean_ms,
    ROUND(b.baseline_mean_ms::NUMERIC, 2) AS baseline_mean_ms,
    ROUND((c.current_mean_ms / NULLIF(b.baseline_mean_ms, 0) - 1) * 100, 1) AS pct_change,
    LEFT(ps.query, 120) AS query_snippet
FROM current c
JOIN baseline b ON c.queryid = b.queryid
JOIN pg_stat_statements ps ON c.queryid = ps.queryid
WHERE c.current_mean_ms > b.baseline_mean_ms * 1.5  -- 50% regression threshold
  AND c.current_calls > 100
ORDER BY pct_change DESC
LIMIT 20;
    -- SQL Server equivalent: snapshot Query Store runtime stats for regression detection
CREATE TABLE dbo.QueryPerfSnapshots (
    SnapshotTime         DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    QueryId              BIGINT NOT NULL,
    PlanId               BIGINT NOT NULL,
    QuerySqlText         NVARCHAR(MAX),
    CountExecutions      BIGINT,
    AvgDurationMs        FLOAT,
    AvgCpuMs             FLOAT,
    AvgLogicalIoReads    FLOAT,
    AvgRowcount          FLOAT,
    CONSTRAINT PK_QueryPerfSnapshots PRIMARY KEY (SnapshotTime, QueryId, PlanId)
);

-- Populate the snapshot (schedule via SQL Agent job)
INSERT INTO dbo.QueryPerfSnapshots (
    QueryId, PlanId, QuerySqlText, CountExecutions,
    AvgDurationMs, AvgCpuMs, AvgLogicalIoReads, AvgRowcount
)
SELECT
    q.query_id,
    p.plan_id,
    qt.query_sql_text,
    rs.count_executions,
    rs.avg_duration / 1000.0,
    rs.avg_cpu_time / 1000.0,
    rs.avg_logical_io_reads,
    rs.avg_rowcount
FROM sys.query_store_query q
JOIN sys.query_store_query_text qt ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan p ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats rs ON p.plan_id = rs.plan_id
JOIN sys.query_store_runtime_stats_interval rsi ON rs.runtime_stats_interval_id = rsi.runtime_stats_interval_id
WHERE rsi.start_time >= DATEADD(MINUTE, -15, SYSUTCDATETIME());

-- Regression detection query
WITH Baseline AS (
    SELECT
        QueryId,
        AVG(AvgDurationMs) AS BaselineDurationMs
    FROM dbo.QueryPerfSnapshots
    WHERE SnapshotTime BETWEEN DATEADD(DAY, -8, SYSUTCDATETIME())
                           AND DATEADD(DAY, -1, SYSUTCDATETIME())
    GROUP BY QueryId
),
Current AS (
    SELECT
        QueryId,
        AVG(AvgDurationMs) AS CurrentDurationMs,
        MAX(QuerySqlText) AS QuerySqlText
    FROM dbo.QueryPerfSnapshots
    WHERE SnapshotTime >= DATEADD(HOUR, -1, SYSUTCDATETIME())
    GROUP BY QueryId
)
SELECT TOP 20
    c.QueryId,
    ROUND(c.CurrentDurationMs, 2) AS CurrentDurationMs,
    ROUND(b.BaselineDurationMs, 2) AS BaselineDurationMs,
    ROUND((c.CurrentDurationMs / NULLIF(b.BaselineDurationMs, 0) - 1) * 100, 1) AS PctChange,
    LEFT(c.QuerySqlText, 150) AS QuerySnippet
FROM Current c
JOIN Baseline b ON c.QueryId = b.QueryId
WHERE c.CurrentDurationMs > b.BaselineDurationMs * 1.5
ORDER BY PctChange DESC;

    Key Takeaways

  • → **Slow query identification on managed services routes through cloud-native log sinks** — CloudWatch Logs Insights on AWS, Query Store on Azure SQL, and Cloud Logging on GCP — rather than direct filesystem access. Master the log query syntax for your platform before a production incident forces you to learn it under pressure.
  • → **Execution plans on managed PostgreSQL require Aurora-aware interpretation**: Aurora's distributed storage layer changes the effective cost of sequential scans versus index scans compared to what the planner's default cost model assumes. Set `random_page_cost` to reflect SSD-backed storage (1.1–1.5) and validate that plan choices align with observed I/O behavior through Performance Insights wait events.
  • → **Parameter tuning scope matters as much as the parameter value itself**: on Aurora, `shared_preload_libraries` must be set in the cluster parameter group or the change has no effect; on Azure SQL, hitting a resource governor ceiling (log write rate, worker threads) requires a service tier change rather than a configuration adjustment. Know which constraints are tunable and which require scaling.
  • → **Wait event analysis is the fastest path from symptom to root cause**: a query running slowly due to `Lock:relation` waits needs concurrency fixes, not index changes. A query slow due to `IO:DataFileRead` needs better cache usage or a covering index. Let the wait event categorize the problem before choosing the remedy.
  • → **Continuous regression detection requires owning the baseline data yourself**: cloud platforms surface current performance well but make week-over-week comparison difficult without a history table. Scheduling periodic snapshots of `pg_stat_statements` or Query Store aggregates into a dedicated history table gives you a durable record that survives instance restarts, failovers, and statistics resets — and lets you correlate deployment events with the performance changes they cause.
