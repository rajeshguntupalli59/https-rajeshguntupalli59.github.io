Chapter 34: Zero-Downtime Cloud Migrations

Moving a production database to the cloud without downtime is one of the most operationally demanding challenges a DBA will face. The raw mechanics—logical replication, change data capture, cutover scripting—are not new. What changes in the cloud is the tooling surface, the failure modes, and the organizational expectations. Cloud migrations often carry a political weight that on-prem upgrades did not: leadership expects zero impact, and the migration team is responsible for delivering it against managed services that hide their internals behind API abstractions. This chapter covers the full arc of a zero-downtime migration: pre-migration assessment, continuous replication setup using AWS DMS, Azure Database Migration Service, and GCP Database Migration Service, schema conversion for heterogeneous workloads, cutover orchestration, and post-migration validation. Every pattern here is drawn from production environments where downtime was measured in seconds, not minutes.

---

34.1 Pre-Migration Assessment: What You Must Know Before You Touch Anything

Zero-downtime migrations fail during planning, not during execution. The actual data movement phase is deterministic. The failures come from unexamined assumptions made weeks earlier.

Schema Complexity Inventory

Start by cataloging every object type in your source database. For PostgreSQL sources, run:

-- Inventory of all non-trivial schema objects in PostgreSQL source
SELECT
    n.nspname                        AS schema_name,
    c.relname                        AS object_name,
    CASE c.relkind
        WHEN 'r' THEN 'TABLE'
        WHEN 'v' THEN 'VIEW'
        WHEN 'm' THEN 'MATERIALIZED_VIEW'
        WHEN 'f' THEN 'FOREIGN_TABLE'
        WHEN 'p' THEN 'PARTITIONED_TABLE'
    END                              AS object_type,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
    s.n_live_tup                     AS live_rows,
    s.n_dead_tup                     AS dead_rows,
    CASE WHEN s.n_live_tup > 0
         THEN ROUND(100.0 * s.n_dead_tup / s.n_live_tup, 2)
         ELSE 0
    END                              AS bloat_pct
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_stat_user_tables s
    ON s.schemaname = n.nspname AND s.relname = c.relname
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema', 'pg_toast')
  AND c.relkind IN ('r', 'v', 'm', 'f', 'p')
ORDER BY pg_total_relation_size(c.oid) DESC NULLS LAST;

For SQL Server sources heading to Azure SQL or RDS for SQL Server, run the Database Migration Assistant (DMA) locally before involving any cloud tooling. DMA will surface blockers—cross-database queries, linked server dependencies, CLR assemblies, Service Broker endpoints—that no cloud migration service will handle automatically. A 50-table OLTP database with two linked servers and a CLR aggregate function is not a zero-downtime migration candidate until those dependencies are resolved. Treat DMA output as a go/no-go gate, not a to-do list.

Replication Eligibility

AWS DMS requires that source tables have a primary key or a unique non-nullable index for CDC (Change Data Capture) mode. Tables without either will be replicated using full-load only, meaning they receive no ongoing changes during the migration window. Query this on your source before you start:

-- Find tables with no primary key or unique constraint (PostgreSQL)
SELECT
    t.table_schema,
    t.table_name,
    pg_size_pretty(pg_total_relation_size(
        (t.table_schema || '.' || t.table_name)::regclass
    )) AS table_size
FROM information_schema.tables t
WHERE t.table_type = 'BASE TABLE'
  AND t.table_schema NOT IN ('pg_catalog', 'information_schema')
  AND NOT EXISTS (
      SELECT 1
      FROM information_schema.table_constraints tc
      WHERE tc.table_schema = t.table_schema
        AND tc.table_name   = t.table_name
        AND tc.constraint_type IN ('PRIMARY KEY', 'UNIQUE')
  )
ORDER BY pg_total_relation_size(
    (t.table_schema || '.' || t.table_name)::regclass
) DESC;

Any table returned here needs a decision: add a surrogate primary key before migration, accept full-load-only semantics for it, or exclude it from replication and handle it with a separate bulk transfer at cutover.

Network Bandwidth Estimation

The migration network path matters more than the instance size. A db.r6g.8xlarge target instance is irrelevant if your source datacenter has 1 Gbps uplink shared with production traffic. Measure actual source database write throughput during peak hours using pg_stat_bgwriter and your existing monitoring:

  • → At 100 MB/s sustained write rate, you generate 360 GB/hour of WAL. DMS CDC must consume this continuously.
  • → AWS DMS replication instance throughput scales with instance class (vCPU, memory, and network bandwidth); larger `dms.r5`/`dms.r6i` classes handle higher sustained change rates, but the ceiling for your specific workload depends on row size, LOB usage, and table count — benchmark it against your own source before committing to an instance class, rather than relying on a generic throughput figure.
  • → A 10 TB database at 50 MB/s average write rate will produce roughly 1.5 TB of change data over an 8-hour migration window. Your DMS replication instance log storage must accommodate this.

    • Budget at least 30% of your uplink capacity exclusively for migration traffic, or schedule the full-load phase during off-peak hours when application writes drop below 20% of peak.

    34.2 Continuous Replication with AWS DMS

    AWS Database Migration Service is the most commonly used tool for migrations into RDS and Aurora. It operates in two phases: full load (bulk copy) and CDC (ongoing change capture). Understanding both phases at the configuration level is what separates a successful migration from one that requires an emergency rollback.

    Infrastructure Setup

    Provision the DMS replication instance, endpoints, and task via Terraform to keep the configuration reproducible:

    # Terraform: DMS replication instance and task configuration
resource "aws_dms_replication_instance" "migration" {
  replication_instance_id     = "prod-migration-ri"
  replication_instance_class  = "dms.r5.4xlarge"
  allocated_storage           = 500          # GB — covers CDC buffer
  multi_az                    = false        # Single-AZ is fine; this is transient
  publicly_accessible         = false
  vpc_security_group_ids      = [var.migration_sg_id]
  replication_subnet_group_id = aws_dms_replication_subnet_group.migration.id
  engine_version              = "3.5.2"
  auto_minor_version_upgrade  = false

  tags = {
    Environment = "migration"
    Owner       = "dba-team"
  }
}

    TargetMetadata = {
      TargetSchema              = ""
      SupportLobs              = true
      FullLobMode              = false
      LobChunkSize             = 64
      LimitedSizeLobMode       = true
      LobMaxSize               = 32768
    }
    FullLoadSettings = {
      TargetTablePrepMode       = "DO_NOTHING"   # Schema pre-created via SCT
      CreatePkAfterFullLoad     = false
      StopTaskCachedChangesApplied  = false
      StopTaskCachedChangesNotApplied = false
      MaxFullLoadSubTasks       = 8
      TransactionConsistencyTimeout = 600
      CommitRate                = 50000
    }
    Logging = {
      EnableLogging            = true
      LogComponents = [
        { Id = "SOURCE_UNLOAD", Severity = "LOGGER_SEVERITY_DEFAULT" },
        { Id = "TARGET_LOAD",   Severity = "LOGGER_SEVERITY_DEFAULT" },
        { Id = "TASK_MANAGER",  Severity = "LOGGER_SEVERITY_DEFAULT" }
      ]
    }
    ControlTablesSettings = {
      historyTimeslotInMinutes = 5
      StatusTableEnabled       = true
      SuspendedTablesTableEnabled = true
      replicationStatusTableEnabled = true
    }

}

    Critical DMS Configuration Details

    TargetTablePrepMode = "DO_NOTHING" means DMS assumes you have pre-created the schema using the AWS Schema Conversion Tool or a manual DDL script. Never use DROP_AND_CREATE in a zero-downtime scenario—it will truncate target tables if the task is restarted.

    CreatePkAfterFullLoad = false means primary keys must exist before full load begins. This is the correct setting when you pre-create schema. If you set it to true, DMS drops constraints during load and recreates them afterward, which significantly speeds up large table loads but creates a window where the target has no constraints.

    MaxFullLoadSubTasks = 8 controls parallel table loading. On a dms.r5.4xlarge replication instance, 8 parallel subtasks is a reasonable default. Increasing this beyond 16 rarely improves throughput and increases memory pressure on the replication instance.

    Monitoring DMS Lag

    Once full load completes and CDC begins, lag monitoring is your primary operational responsibility. DMS exposes CDCLatencySource and CDCLatencyTarget via CloudWatch. CDCLatencySource is the lag between a change occurring in the source WAL and DMS reading it. CDCLatencyTarget is the lag between DMS reading the change and applying it to the target. A healthy migration keeps both metrics below 5 seconds during peak and below 30 seconds during business hours for non-time-sensitive migrations.

    # Monitor DMS CDC latency via AWS CLI
aws cloudwatch get-metric-statistics \
  --namespace AWS/DMS \
  --metric-name CDCLatencySource \
  --dimensions Name=ReplicationInstanceIdentifier,Value=prod-migration-ri \
  --start-time "$(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%SZ)" \
  --end-time "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --period 60 \
  --statistics Average,Maximum \
  --output table

# Check replication task status
aws dms describe-replication-tasks \
  --filters Name=replication-task-arn,Values=<task-arn> \
  --query 'ReplicationTasks[0].{Status:Status,FullLoadProgress:ReplicationTaskStats.FullLoadProgressPercent,TablesLoaded:ReplicationTaskStats.TablesLoaded,TablesLoading:ReplicationTaskStats.TablesLoading,TablesErrored:ReplicationTaskStats.TablesErrored,LatencySource:ReplicationTaskStats.CDCLatencySource}' \
  --output table

    PostgreSQL Source: WAL and Replication Slot Management

    DMS creates a PostgreSQL logical replication slot on the source when using pglogical or pgoutput plugins. This slot is one of the most operationally dangerous objects in your source database during migration. If DMS falls behind or stops, PostgreSQL will retain WAL segments to satisfy the slot, and your source disk will fill.

    Set max_slot_wal_keep_size in PostgreSQL 13+ to cap this:

    -- PostgreSQL 13+: Limit WAL retained for replication slots
ALTER SYSTEM SET max_slot_wal_keep_size = '50GB';
SELECT pg_reload_conf();

-- Monitor slot lag continuously during migration
SELECT
    slot_name,
    plugin,
    slot_type,
    active,
    active_pid,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS pending_wal,
    EXTRACT(EPOCH FROM (now() - pg_stat_replication.write_lag))::int AS write_lag_seconds
FROM pg_replication_slots
LEFT JOIN pg_stat_replication USING (pid)
WHERE slot_name LIKE 'dms%';

    If retained_wal exceeds 20 GB on a source with limited disk, investigate immediately. If DMS has stopped and you cannot restart it within minutes, you will need to either increase disk on the source or drop the slot and restart the task from the beginning.

    34.3 Schema Conversion and Heterogeneous Migrations

    When the source and target engines differ—Oracle or SQL Server migrating to PostgreSQL or Aurora—schema conversion is a migration project in itself. AWS Schema Conversion Tool (SCT) handles this partially. The "partially" is what you need to manage.

    SCT Assessment Report

    SCT classifies every schema object into three tiers: automatically convertible, with issues (requiring manual intervention), and unsupported. In Oracle-to-Aurora-PostgreSQL migrations, the general pattern is:

  • → Simple tables and views convert automatically in the large majority of cases
  • → Stored procedures and functions convert automatically far less consistently — the proportion depends heavily on how much the source PL/SQL relies on Oracle-specific packages, cursors, and exception handling; run the SCT assessment report against your own schema rather than assuming a conversion rate
  • → Oracle-specific types (XMLTYPE, spatial types, nested tables): manual conversion required
  • → Database links and synonyms: not converted, must be refactored at the application layer

    • For SQL Server to Azure SQL migrations, the conversion rate is higher because Microsoft designed Azure SQL to be a near-superset of SQL Server on-prem. The blockers are typically CLR user-defined types, cross-database transactions, and FILESTREAM columns.

    Running SCT from CLI for Automation

    SCT has a GUI that most DBAs use interactively, but it also has a command-line interface for automation in migration pipelines:

    #!/bin/bash
# Run AWS SCT assessment in headless mode
# Prerequisites: SCT installed, Java 11+

SCT_HOME="/opt/aws-schema-conversion-tool"
PROJECT_FILE="migration_project.sct"
REPORT_DIR="/var/migration/reports/$(date +%Y%m%d)"

mkdir -p "$REPORT_DIR"

# Generate assessment report without applying conversion
java -jar "${SCT_HOME}/AWSSchemaConversionTool.jar" \
  --project-file "${PROJECT_FILE}" \
  --assess \
  --output-folder "${REPORT_DIR}" \
  --report-name "migration_assessment" \
  --log-file "${REPORT_DIR}/sct.log" \
  --override-settings \
    sourceType=ORACLE \
    targetType=AURORA_POSTGRESQL \
    assessmentReportFormats=PDF,CSV

# Parse blockers from CSV report
echo "=== HIGH-ACTION ITEMS ==="
awk -F',' '$5 == "Action Required"' \
  "${REPORT_DIR}/migration_assessment.csv" | \
  cut -d',' -f1,2,3,6 | head -50

echo "=== CONVERSION SUMMARY ==="
grep -E "^(Total|Automatically|Manually|Could not)" \
  "${REPORT_DIR}/migration_assessment.csv"

    Handling Oracle Sequences in Aurora PostgreSQL

    Oracle sequences and Aurora PostgreSQL sequences behave differently under concurrent load mainly because of their default cache size, not because of transactional semantics — Oracle's default CACHE is 20, while PostgreSQL's default CACHE is 1, meaning every NEXTVAL call updates the sequence's on-disk state unless you raise the cache explicitly. When converting Oracle applications that rely on high-frequency sequence calls, replace them with PostgreSQL sequences that use a comparably large cache value:

    -- Aurora PostgreSQL: Replace Oracle-style sequence with cached equivalent
-- Oracle default: INCREMENT BY 1, CACHE 20
-- Under high concurrency, this causes sequence contention on Aurora

-- Correct approach for high-throughput OLTP on Aurora
CREATE SEQUENCE order_id_seq
    START WITH 1
    INCREMENT BY 1
    CACHE 1000          -- Oracle's 20 is too low for Aurora's parallel connections
    NO CYCLE;

-- Verify sequence cache in pg_sequences
SELECT
    schemaname,
    sequencename,
    start_value,
    increment_by,
    cache_size,
    last_value
FROM pg_sequences
WHERE sequencename = 'order_id_seq';

-- For UUID-based primary keys (preferred on Aurora for distributed workloads)
-- Replace integer sequences entirely
ALTER TABLE orders
    ALTER COLUMN order_id SET DEFAULT gen_random_uuid();

    The cache value of 1,000 is not arbitrary. On Aurora with 200+ concurrent connections each calling NEXTVAL on every INSERT, a cache of 20 causes the sequence to flush to storage every 20 calls. At 500 INSERTs/second across 200 connections, that is 25 storage flushes per second for sequences alone. A cache of 1,000 reduces this to one flush per connection per 1,000 inserts.

    34.4 Azure and GCP Migration Paths

    AWS DMS gets the most industry attention, but Azure Database Migration Service and GCP Database Migration Service each have distinct characteristics that affect cutover strategy.

    Azure Database Migration Service

    Azure DMS supports online (continuous sync) migration for PostgreSQL to Azure Database for PostgreSQL - Flexible Server and SQL Server to Azure SQL Managed Instance. For PostgreSQL sources, it uses the logical replication protocol—the same mechanism as DMS—but its configuration surface is smaller and its limitations are more restrictive.

    Azure DMS online migration requires that the source PostgreSQL instance have wal_level = logical, max_replication_slots >= 5, max_wal_senders >= 10, and that pg_hba.conf allows the Azure DMS IP range with replication privilege. In a managed source environment where you cannot freely edit postgresql.conf, this becomes an operational constraint.

    Set up an Azure DMS migration project via CLI:

    #!/bin/bash
# Azure CLI: Create and start an online PostgreSQL migration to Flexible Server

RESOURCE_GROUP="rg-migration-prod"
LOCATION="eastus2"
DMS_SERVICE="dms-prod-migration"
PROJECT_NAME="pg-to-flexible-migration"
TASK_NAME="pg-migration-task-01"

# Create DMS service instance (Premium tier required for online migration)
az dms create \
  --resource-group "$RESOURCE_GROUP" \
  --name "$DMS_SERVICE" \
  --location "$LOCATION" \
  --sku-name "Premium_4vCores" \
  --subnet "/subscriptions/${SUBSCRIPTION_ID}/resourceGroups/${RESOURCE_GROUP}/providers/Microsoft.Network/virtualNetworks/vnet-migration/subnets/snet-dms"

# Create migration project
az dms project create \
  --resource-group "$RESOURCE_GROUP" \
  --service-name "$DMS_SERVICE" \
  --name "$PROJECT_NAME" \
  --source-platform "PostgreSQL" \
  --target-platform "AzureDbForPostgreSql" \
  --location "$LOCATION"

# Create task with source and target connection info
az dms project task create \
  --resource-group "$RESOURCE_GROUP" \
  --service-name "$DMS_SERVICE" \
  --project-name "$PROJECT_NAME" \
  --name "$TASK_NAME" \
  --task-type "OnlineMigration" \
  --source-connection-json '{
    "serverName": "'"$SOURCE_PG_HOST"'",
    "serverPort": 5432,
    "databaseName": "'"$SOURCE_DB"'",
    "userName": "migration_user",
    "password": "'"$SOURCE_PG_PASS"'",
    "encryptConnection": true,
    "trustServerCertificate": false
  }' \
  --target-connection-json '{
    "serverName": "'"$AZURE_FLEX_HOST"'",
    "serverPort": 5432,
    "databaseName": "'"$TARGET_DB"'",
    "userName": "adminuser",
    "password": "'"$AZURE_FLEX_PASS"'",
    "encryptConnection": true
  }' \
  --selected-databases '[{
    "name": "'"$SOURCE_DB"'",
    "targetDatabaseName": "'"$TARGET_DB"'",
    "migrationSetting": {
      "desiredRpOs": 0
    },
    "sourceSetting": {},
    "targetSetting": {}
  }]'

# Monitor migration status
az dms project task show \
  --resource-group "$RESOURCE_GROUP" \
  --service-name "$DMS_SERVICE" \
  --project-name "$PROJECT_NAME" \
  --name "$TASK_NAME" \
  --expand output \
  --query 'output[0].migrationState'

    GCP Database Migration Service

    GCP DMS uses connection profiles and migration jobs as its primary abstractions. For Cloud SQL for PostgreSQL targets, GCP DMS is competitive with AWS DMS in capability. For AlloyDB targets, GCP DMS is the only supported path from external PostgreSQL sources.

    #!/bin/bash
# GCP CLI: Database Migration Service for PostgreSQL to AlloyDB

PROJECT_ID="prod-migration-project"
REGION="us-central1"
SOURCE_PROFILE="source-postgres-prod"
DEST_PROFILE="target-alloydb-prod"
JOB_ID="pg-to-alloydb-job-01"

# Create source connection profile
gcloud database-migration connection-profiles create postgresql \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --connection-profile-id="$SOURCE_PROFILE" \
  --host="$SOURCE_PG_HOST" \
  --port=5432 \
  --username="migration_user" \
  --password="$SOURCE_PG_PASS" \
  --database-service="$SOURCE_DB" \
  --display-name="Production PostgreSQL Source"

# Create destination connection profile (AlloyDB)
gcloud database-migration connection-profiles create alloydb \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --connection-profile-id="$DEST_PROFILE" \
  --cluster="projects/${PROJECT_ID}/locations/${REGION}/clusters/alloydb-prod" \
  --display-name="AlloyDB Production Target"

# Create migration job (continuous replication)
gcloud database-migration migration-jobs create \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --migration-job-id="$JOB_ID" \
  --type=CONTINUOUS \
  --source="$SOURCE_PROFILE" \
  --destination="$DEST_PROFILE" \
  --display-name="PostgreSQL to AlloyDB Production Migration"

# Verify migration job configuration before starting
gcloud database-migration migration-jobs verify \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --migration-job-id="$JOB_ID"

# Start migration (begins full dump followed by CDC)
gcloud database-migration migration-jobs start \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --migration-job-id="$JOB_ID"

# Monitor status
gcloud database-migration migration-jobs describe \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --migration-job-id="$JOB_ID" \
  --format="value(state,phase,error.message)"

    GCP DMS handles the replication slot lifecycle internally for AlloyDB targets. Unlike AWS DMS, you do not need to pre-create the slot or manage its retention manually. However, GCP DMS requires that the source PostgreSQL server is reachable from a GCP-managed IP range, which means configuring pg_hba.conf for a CIDR block that GCP publishes and updates periodically. Check the current published ranges before migration and add them to source firewall rules.

    GCP DMS Lag Monitoring via Cloud Monitoring

    # Query CDC replication lag for GCP DMS job using gcloud metrics
gcloud monitoring metrics list \
  --filter="metric.type = starts_with('datamigration.googleapis.com')" \
  --format="value(metric.type)"

# Via Cloud Monitoring API (suitable for integration into alerting pipelines)
gcloud monitoring dashboards create --config-from-file=dms-dashboard.json

# Direct lag check via DMS describe (includes lag in seconds when available)
gcloud database-migration migration-jobs describe \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --migration-job-id="$JOB_ID" \
  --format="json" | jq '.cdc.maximumLag, .phase, .state'

    34.5 Cutover Orchestration

    Cutover is the moment the migration earns its "zero-downtime" qualifier—or loses it. The mechanics must be scripted, rehearsed, and timed. Improvisation during cutover is the primary cause of unexpected downtime.

    The Cutover Decision Gate

    Cutover should only proceed when three conditions are simultaneously true:

    1. CDC lag on both source and target legs is below your agreed threshold (typically 5 seconds or less).

    2. Row counts on the target match the source for all tables (verified by the pre-cutover validation script below).

    3. The application team has a validated rollback plan: connection strings pointing back to the source can be restored within your rollback time objective.

    graph TD
    A[Check CDC lag] --> B{Lag below
    threshold?}
    B -->|No| Z[Abort cutover]
    B -->|Yes| C[Set source read-only,
    drain in-flight writes]
    C --> D{CDC lag reaches
    zero within wait limit?}
    D -->|No| E[Revert source to
    read-write, abort]
    D -->|Yes| F[Stop DMS task]
    F --> G[Advance sequences /
    reseed identity columns]
    G --> H[Flip application
    connection string]
    H --> I[Post-cutover validation
    and monitoring]

    *The cutover decision gate: every branch that fails routes back to a safe, reversible state rather than pressing forward.*

    Pre-Cutover Row Count Validation

    Run this on both source and target immediately before cutover. Any discrepancy halts the cutover.

    -- PostgreSQL: Generate row counts for all user tables (run on source AND target)
-- Compare output side by side; differences indicate replication gaps

SELECT
    schemaname,
    tablename,
    n_live_tup                          AS estimated_rows,
    pg_size_pretty(pg_total_relation_size(
        schemaname || '.' || tablename
    ))                                  AS table_size,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY schemaname, tablename;

-- For exact counts on critical tables (slower but authoritative)
-- Run this for tables where estimated counts diverge between source and target
DO $$
DECLARE
    r RECORD;
    cnt BIGINT;
    sql TEXT;
BEGIN
    FOR r IN
        SELECT schemaname, tablename
        FROM pg_stat_user_tables
        WHERE schemaname = 'public'
        ORDER BY tablename
    LOOP
        sql := format('SELECT COUNT(*) FROM %I.%I', r.schemaname, r.tablename);
        EXECUTE sql INTO cnt;
        RAISE NOTICE 'Table: %.% | Count: %', r.schemaname, r.tablename, cnt;
    END LOOP;
END $$;

    For SQL Server sources and Azure SQL targets:

    -- SQL Server / Azure SQL: Row count comparison across all tables
SELECT
    s.name                              AS schema_name,
    t.name                              AS table_name,
    p.rows                              AS row_count,
    SUM(a.total_pages) * 8 / 1024      AS total_size_mb
FROM sys.tables t
JOIN sys.schemas s ON s.schema_id = t.schema_id
JOIN sys.indexes i ON i.object_id = t.object_id
    AND i.index_id IN (0, 1)           -- heap or clustered index
JOIN sys.partitions p ON p.object_id = t.object_id
    AND p.index_id = i.index_id
JOIN sys.allocation_units a ON a.container_id = p.partition_id
WHERE t.is_ms_shipped = 0
GROUP BY s.name, t.name, p.rows
ORDER BY s.name, t.name;

    The Cutover Runbook

    A production cutover runbook is a sequence of time-boxed steps with a "proceed/abort" decision at each gate. The following template covers a PostgreSQL-to-Aurora cutover via AWS DMS:

    #!/bin/bash
# cutover_runbook.sh — PostgreSQL to Aurora zero-downtime cutover
# Execute this interactively. Each step requires explicit confirmation.
# Total expected duration: 8–12 minutes from start to traffic on target.

set -euo pipefail

SOURCE_HOST="prod-pg-primary.internal"
SOURCE_DB="appdb"
SOURCE_USER="migration_user"
TARGET_HOST="aurora-cluster.cluster-xxxx.us-east-1.rds.amazonaws.com"
TARGET_DB="appdb"
TARGET_USER="admin"
DMS_TASK_ARN="arn:aws:dms:us-east-1:123456789:task:XXXXXXX"
APP_CONFIG_SSM="/prod/app/db_connection_string"
ROLLBACK_SSM="/prod/app/db_connection_string_rollback"

log() { echo "[$(date -u +%H:%M:%SZ)] $*"; }
confirm() {
    read -r -p "==> $1 [y/N]: " resp
    [[ "${resp,,}" == "y" ]] || { log "ABORTED by operator."; exit 1; }
}

# STEP 1: Verify CDC lag is below threshold
log "STEP 1: Checking DMS CDC lag..."
LAG=$(aws dms describe-replication-tasks \
  --filters Name=replication-task-arn,Values="$DMS_TASK_ARN" \
  --query 'ReplicationTasks[0].ReplicationTaskStats.CDCLatencySource' \
  --output text)

log "Current CDCLatencySource: ${LAG} seconds"
if (( $(echo "$LAG > 10" | bc -l) )); then
    log "ERROR: CDC lag ${LAG}s exceeds 10s threshold. ABORTING."
    exit 1
fi
confirm "CDC lag is acceptable. Proceed to STEP 2?"

# STEP 2: Set source database to read-only to drain in-flight writes
log "STEP 2: Setting source database read_only..."
PGPASSWORD="$SOURCE_PG_PASS" psql -h "$SOURCE_HOST" -U "$SOURCE_USER" -d "$SOURCE_DB" <<'SQL'
-- Terminate active write connections (allow reads to continue)
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE datname = current_database()
  AND state = 'active'
  AND query NOT ILIKE '%select%'
  AND pid <> pg_backend_pid();

-- Set default transaction to read-only for new connections
ALTER DATABASE appdb SET default_transaction_read_only = on;
SQL
log "Source database is now read-only."
confirm "Source is read-only. Proceed to wait for CDC to drain?"

# STEP 3: Wait for CDC lag to reach zero
log "STEP 3: Waiting for CDC lag to reach zero..."
WAIT_LIMIT=120  # seconds
ELAPSED=0
while true; do
    LAG=$(aws dms describe-replication-tasks \
      --filters Name=replication-task-arn,Values="$DMS_TASK_ARN" \
      --query 'ReplicationTasks[0].ReplicationTaskStats.CDCLatencySource' \
      --output text)
    log "  CDCLatencySource: ${LAG}s (elapsed: ${ELAPSED}s)"
    if (( $(echo "$LAG <= 1" | bc -l) )); then
        log "CDC lag drained to ${LAG}s. Proceeding."
        break
    fi
    if (( ELAPSED >= WAIT_LIMIT )); then
        log "ERROR: CDC did not drain within ${WAIT_LIMIT}s. ABORTING."
        # Roll back read-only immediately
        PGPASSWORD="$SOURCE_PG_PASS" psql -h "$SOURCE_HOST" \
          -U "$SOURCE_USER" -d "$SOURCE_DB" \
          -c "ALTER DATABASE appdb SET default_transaction_read_only = off;"
        exit 1
    fi
    sleep 5
    ELAPSED=$(( ELAPSED + 5 ))
done
confirm "CDC drained. Proceed to stop DMS task and flip traffic?"

# STEP 4: Stop DMS task
log "STEP 4: Stopping DMS replication task..."
aws dms stop-replication-task --replication-task-arn "$DMS_TASK_ARN"
log "DMS task stop initiated. Waiting for STOPPED state..."
aws dms wait replication-task-stopped \
  --filters Name=replication-task-arn,Values="$DMS_TASK_ARN"
log "DMS task stopped."

# STEP 5: Flip application connection string in SSM Parameter Store
log "STEP 5: Updating application connection string in SSM..."
NEW_CONN="postgresql://${TARGET_USER}@${TARGET_HOST}:5432/${TARGET_DB}?sslmode=require"
aws ssm put-parameter \
  --name "$APP_CONFIG_SSM" \
  --value "$NEW_CONN" \
  --type SecureString \
  --overwrite
log "SSM parameter updated. Application will pick up new connection on next config reload."

# STEP 6: Trigger application config reload (deployment-specific)
log "STEP 6: Triggering application config reload..."
# Example: ECS service update to force new task launch with updated SSM param
aws ecs update-service \
  --cluster prod-cluster \
  --service app-service \
  --force-new-deployment \
  --query 'service.deploymentConfiguration'

confirm "Deployment triggered. Monitor application metrics for 5 minutes before declaring success."

# STEP 7: Post-cutover validation
log "STEP 7: Running post-cutover row count spot check on target..."
PGPASSWORD="$TARGET_PG_PASS" psql -h "$TARGET_HOST" -U "$TARGET_USER" \
  -d "$TARGET_DB" -c "
SELECT schemaname, tablename, n_live_tup
FROM pg_stat_user_tables
WHERE schemaname = 'public'
ORDER BY n_live_tup DESC
LIMIT 20;
"

log "Cutover complete. Monitor dashboards for 30 minutes."
log "Rollback: revert SSM parameter to value stored in ${ROLLBACK_SSM} and re-enable writes on source."

    Sequence Numbers and Auto-Increment Gaps

    After cutover, the target database's sequences will not automatically advance to match the source's current value. If DMS replicated an INSERT with id = 450000 but the Aurora sequence still starts at 1, the first application-generated INSERT after cutover will collide. Fix this before opening writes on the target:

    -- Aurora PostgreSQL: Advance all sequences to match source maximum values
-- Run this AFTER CDC drains but BEFORE allowing write traffic

DO $$
DECLARE
    r RECORD;
    max_val BIGINT;
    seq_name TEXT;
    sql TEXT;
BEGIN
    FOR r IN
        SELECT
            t.table_schema,
            t.table_name,
            c.column_name,
            pg_get_serial_sequence(t.table_schema || '.' || t.table_name, c.column_name) AS seq
        FROM information_schema.tables t
        JOIN information_schema.columns c
            ON c.table_schema = t.table_schema
           AND c.table_name = t.table_name
        WHERE t.table_type = 'BASE TABLE'
          AND t.table_schema = 'public'
          AND c.column_default LIKE 'nextval%'
    LOOP
        IF r.seq IS NOT NULL THEN
            sql := format('SELECT MAX(%I) FROM %I.%I',
                r.column_name, r.table_schema, r.table_name);
            EXECUTE sql INTO max_val;
            IF max_val IS NOT NULL THEN
                PERFORM setval(r.seq, max_val, true);
                RAISE NOTICE 'Advanced sequence % to %', r.seq, max_val;
            END IF;
        END IF;
    END LOOP;
END $$;

    For SQL Server to Azure SQL migrations, identity columns require a different approach:

    -- Azure SQL: Reseed identity columns after migration
-- Run against each table where identity column exists on target

DECLARE @table_name NVARCHAR(256);
DECLARE @col_name   NVARCHAR(256);
DECLARE @max_val    BIGINT;
DECLARE @sql        NVARCHAR(MAX);

DECLARE identity_cursor CURSOR FOR
    SELECT
        OBJECT_NAME(ic.object_id) AS table_name,
        COL_NAME(ic.object_id, ic.column_id) AS column_name
    FROM sys.identity_columns ic
    JOIN sys.tables t ON t.object_id = ic.object_id
    WHERE t.is_ms_shipped = 0;

OPEN identity_cursor;
FETCH NEXT FROM identity_cursor INTO @table_name, @col_name;

WHILE @@FETCH_STATUS = 0
BEGIN
    SET @sql = N'SELECT @max = MAX(' + QUOTENAME(@col_name) + N') FROM ' + QUOTENAME(@table_name);
    EXEC sp_executesql @sql, N'@max BIGINT OUTPUT', @max = @max_val OUTPUT;

    IF @max_val IS NOT NULL
    BEGIN
        SET @sql = N'DBCC CHECKIDENT (''' + @table_name + N''', RESEED, ' + CAST(@max_val AS NVARCHAR) + N')';
        EXEC sp_executesql @sql;
        PRINT 'Reseeded ' + @table_name + '.' + @col_name + ' to ' + CAST(@max_val AS NVARCHAR);
    END

    FETCH NEXT FROM identity_cursor INTO @table_name, @col_name;
END

CLOSE identity_cursor;
DEALLOCATE identity_cursor;

    34.6 Post-Migration Validation

    Declaring the migration complete before validation is complete is an operational mistake. The application may be writing to the new database, but that does not mean the data is correct, the performance is acceptable, or the ancillary objects (triggers, functions, views) are functioning correctly.

    Data Integrity Validation

    Use a hash-based approach for tables where row counts alone are insufficient. Hash comparison on sorted row data detects column-level data corruption that row counts miss:

    -- PostgreSQL: Hash-based table validation (run on source, compare to target output)
-- Use MD5 for speed; use SHA256 if regulatory requirements demand it

CREATE OR REPLACE FUNCTION validate_table_hash(
    p_schema TEXT,
    p_table  TEXT
)
RETURNS TABLE(
    schema_name   TEXT,
    table_name    TEXT,
    row_count     BIGINT,
    content_hash  TEXT,
    sampled_at    TIMESTAMPTZ
)
LANGUAGE plpgsql AS $$
DECLARE
    v_sql TEXT;
    v_cols TEXT;
BEGIN
    -- Build column list, casting all columns to TEXT for consistent hashing
    SELECT string_agg(
        'COALESCE(' || quote_ident(column_name) || '::TEXT, '''')',
        ' || ''|'' || '
        ORDER BY ordinal_position
    )
    INTO v_cols
    FROM information_schema.columns
    WHERE table_schema = p_schema
      AND table_name   = p_table;

    v_sql := format(
        'SELECT %L, %L, COUNT(*), MD5(STRING_AGG(row_hash, '''' ORDER BY row_hash)), NOW()
         FROM (
             SELECT MD5(%s) AS row_hash
             FROM %I.%I
         ) subq',
        p_schema, p_table, v_cols, p_schema, p_table
    );

    RETURN QUERY EXECUTE v_sql;
END $$;

-- Run for all tables in public schema
SELECT * FROM validate_table_hash('public', 'orders');
SELECT * FROM validate_table_hash('public', 'customers');
SELECT * FROM validate_table_hash('public', 'order_items');

    This function works for tables with up to tens of millions of rows within a reasonable time window. For tables with hundreds of millions of rows, sample-based validation is more practical:

    -- PostgreSQL: Sample-based validation for very large tables
-- Compare random 1% sample hash between source and target using same random seed

SELECT
    MD5(STRING_AGG(row_hash, '' ORDER BY id))   AS sample_hash,
    COUNT(*)                                      AS sample_count
FROM (
    SELECT
        id,
        MD5(COALESCE(id::TEXT, '')
         || COALESCE(customer_id::TEXT, '')
         || COALESCE(total_amount::TEXT, '')
         || COALESCE(status, '')
         || COALESCE(created_at::TEXT, '')) AS row_hash
    FROM orders
    TABLESAMPLE BERNOULLI (1) REPEATABLE (42)   -- same seed on source and target
) t;

    Performance Baseline Validation

    After cutover, the top-20 queries by total execution time on the source should perform within an acceptable range on the target. Capture baseline query performance on the source before migration using pg_stat_statements:

    -- PostgreSQL: Capture query performance baseline on SOURCE before migration
-- Export this to a file and compare against target after cutover

SELECT
    LEFT(query, 120)                    AS query_preview,
    calls,
    ROUND(total_exec_time::numeric, 2)  AS total_exec_ms,
    ROUND(mean_exec_time::numeric, 2)   AS mean_exec_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_exec_ms,
    rows,
    ROUND(100.0 * total_exec_time /
        SUM(total_exec_time) OVER (), 2) AS pct_total_time,
    shared_blks_hit,
    shared_blks_read
FROM pg_stat_statements
WHERE calls > 100
ORDER BY total_exec_time DESC
LIMIT 30;

    Run the same query on the target 24 hours post-migration and compare. Queries that are significantly slower on the target typically point to one of three causes:

    1. Missing indexes — SCT or manual schema migration missed an index, or an index was not yet rebuilt after full load.

    2. Stale statistics — Aurora runs ANALYZE automatically, but freshly loaded tables may not have had time for autovacuum to gather representative statistics. Run ANALYZE VERBOSE on affected tables immediately after cutover.

    3. Parameter differences — the source PostgreSQL instance had tuned work_mem, effective_cache_size, or random_page_cost values that the cloud managed instance does not match. Review and apply equivalent parameter group settings on the target.

    Functional Validation: Stored Procedures and Triggers

    For heterogeneous migrations (Oracle or SQL Server to PostgreSQL), converted stored procedures require functional testing against the target. Automate this with a suite of stored procedure call tests that compare output between source and target for identical inputs:

    -- PostgreSQL: Validate converted function returns expected results
-- Run on target after migration; compare output against source baseline captured pre-migration

CREATE OR REPLACE PROCEDURE validate_function_outputs()
LANGUAGE plpgsql AS $$
DECLARE
    test_results JSONB := '[]'::JSONB;
    result_row   RECORD;
BEGIN
    -- Test 1: calculate_order_total function
    FOR result_row IN
        SELECT
            order_id,
            calculate_order_total(order_id)          AS computed_total,
            expected_total,
            ABS(calculate_order_total(order_id)
                - expected_total) < 0.01             AS passed
        FROM migration_validation.expected_function_outputs
        WHERE function_name = 'calculate_order_total'
        LIMIT 1000
    LOOP
        IF NOT result_row.passed THEN
            RAISE WARNING 'FUNCTION MISMATCH: order_id=% computed=% expected=%',
                result_row.order_id,
                result_row.computed_total,
                result_row.expected_total;
        END IF;
    END LOOP;

    RAISE NOTICE 'Function validation complete.';
END $$;

CALL validate_function_outputs();

    The migration_validation.expected_function_outputs table is populated pre-migration by running the same function calls against the source and capturing their outputs. This pattern—capture expected outputs on source, validate actual outputs on target—is the most reliable functional validation approach for converted procedures.

    34.7 Rollback Strategy and Post-Migration Cleanup

    Zero-downtime migration is not complete without a tested rollback path. The rollback window closes when you cannot reconnect the source to production traffic—either because the source has been decommissioned, the replication slot has been dropped, or the source instance has been scaled down. Keep the source operational and writable for at minimum 72 hours post-cutover, and keep the DMS task in STOPPED (not deleted) state so it can be restarted if needed.

    Activating Rollback

    If a critical issue is detected post-cutover, the rollback sequence is the reverse of the cutover sequence:

    #!/bin/bash
# rollback.sh — Emergency rollback from target back to source
# Execute only when declared by the migration lead after post-cutover incident detection.

set -euo pipefail

SOURCE_HOST="prod-pg-primary.internal"
SOURCE_DB="appdb"
SOURCE_USER="migration_user"
APP_CONFIG_SSM="/prod/app/db_connection_string"
ROLLBACK_CONN_SSM="/prod/app/db_connection_string_rollback"

log() { echo "[$(date -u +%H:%M:%SZ)] ROLLBACK: $*"; }

# STEP R1: Restore source database to read-write
log "R1: Restoring source database to read-write mode..."
PGPASSWORD="$SOURCE_PG_PASS" psql -h "$SOURCE_HOST" -U "$SOURCE_USER" \
  -d "$SOURCE_DB" \
  -c "ALTER DATABASE appdb SET default_transaction_read_only = off;"
log "Source is read-write."

# STEP R2: Revert application connection string
log "R2: Reverting SSM connection string to source..."
ROLLBACK_CONN=$(aws ssm get-parameter \
  --name "$ROLLBACK_CONN_SSM" \
  --with-decryption \
  --query 'Parameter.Value' \
  --output text)
aws ssm put-parameter \
  --name "$APP_CONFIG_SSM" \
  --value "$ROLLBACK_CONN" \
  --type SecureString \
  --overwrite
log "SSM parameter reverted."

# STEP R3: Force application redeployment to pick up old connection
log "R3: Forcing ECS service redeployment..."
aws ecs update-service \
  --cluster prod-cluster \
  --service app-service \
  --force-new-deployment \
  --query 'service.deployments[0].status'

log "Rollback initiated. Verify application health on source database."
log "Do NOT restart DMS task until post-incident review is complete."

    Post-Migration Cleanup Checklist

    After a 72-hour observation window with no issues, decommission migration infrastructure:

    1. Drop the DMS replication slot on the source: SELECT pg_drop_replication_slot('dms_migration_slot'); — failure to do this will cause WAL accumulation on the source indefinitely.

    2. Delete the DMS task, endpoints, and replication instance via Terraform destroy or AWS console to stop instance billing.

    3. Remove migration-specific database users from the source and target.

    4. Drop the dms_heartbeat schema from the source if created during DMS configuration.

    5. Reset default_transaction_read_only on the source to off (if not already done during rollback path).

    6. Archive the SCT project file, migration runbook, and DMS task configuration to the team's migration artifact repository for audit purposes.

    7. Verify that max_slot_wal_keep_size is reset or removed from the source's postgresql.conf if it was added specifically for this migration.

    -- PostgreSQL: Post-migration cleanup on source database
-- Run after 72-hour observation window confirms migration success

-- 1. Verify no active replication slots remain from migration
SELECT slot_name, active, plugin, restart_lsn
FROM pg_replication_slots
WHERE slot_name LIKE 'dms%';

-- 2. Drop migration slot if inactive
SELECT pg_drop_replication_slot(slot_name)
FROM pg_replication_slots
WHERE slot_name LIKE 'dms%' AND active = false;

-- 3. Remove migration user
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM migration_user;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM migration_user;
ALTER ROLE migration_user WITH NOREPLICATION;   -- REPLICATION is a role attribute, not a grantable privilege
REVOKE rds_replication FROM migration_user;     -- if on RDS source
DROP USER migration_user;

-- 4. Drop heartbeat schema
DROP SCHEMA IF EXISTS dms_heartbeat CASCADE;

-- 5. Confirm WAL retention is back to normal
SELECT name, setting, unit
FROM pg_settings
WHERE name IN ('max_slot_wal_keep_size', 'wal_keep_size', 'max_replication_slots');

    Key Takeaways

  • → **Pre-migration assessment is the highest-leverage activity in a zero-downtime migration.** Tables without primary keys, linked server dependencies, and unsupported object types identified before replication begins are solvable problems. Identified during cutover, they become outages.
  • → **AWS DMS, Azure DMS, and GCP DMS all use logical replication under the hood, but they expose different operational surfaces.** DMS on AWS requires explicit replication slot management and WAL retention monitoring on the source; GCP DMS manages the slot lifecycle internally; Azure DMS requires pg_hba.conf configuration for managed IP ranges. Know which operational responsibility belongs to you versus the service.
  • → **Cutover is a scripted, time-boxed procedure, not an ad hoc event.** Setting the source to read-only, draining CDC lag to near-zero, advancing sequences on the target, and flipping the application connection string must each be rehearsed in a staging environment before the production window.
  • → **Post-migration validation closes the loop that replication cannot.** Row count checks confirm volume, hash-based comparisons confirm content integrity, and query performance baselines confirm that the target is behaviorally equivalent to the source under production load.
  • → **The rollback window is a contractual obligation, not an afterthought.** Keep the source database operational and writable, the DMS task stopped but not deleted, and the rollback connection string pre-staged in your secrets store for a minimum of 72 hours post-cutover. The cost of maintaining this rollback posture is far lower than the cost of an unrecoverable production incident on a freshly migrated database.
