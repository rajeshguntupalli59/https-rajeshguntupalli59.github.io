Chapter 10: RDS Proxy: Connection Pooling at Scale

Connection pooling is a problem every production DBA has solved before — PgBouncer on a dedicated VM, SQL Server's built-in connection pooling through the driver, ProxySQL sitting between your application tier and MySQL. You know the problem well: thousands of application threads each wanting their own database connection, a database engine that pays real memory and CPU cost per connection, and an impedance mismatch between how application frameworks think about concurrency and how database engines actually work. In the cloud, that problem doesn't disappear — it gets worse. Serverless functions spin up hundreds of ephemeral connections in milliseconds. Auto-scaling application tiers surge from 10 to 500 instances in minutes. Lambda functions have no persistent process to maintain a connection pool. RDS Proxy is AWS's managed answer to this problem, and understanding it deeply — its architecture, its limits, its failure modes — is what separates a cloud DBA who simply enables it from one who operates it confidently in production.

---

10.1 Why Connection Pooling Is Different in the Cloud

On-premises, you controlled both ends of the connection. You knew exactly how many application servers existed, you sized PgBouncer or pgpool-II based on those numbers, and you tuned max_connections in postgresql.conf to match. The population was relatively static. In a cloud-native architecture, the application tier is ephemeral by design.

Consider what happens when you deploy an AWS Lambda function that queries RDS PostgreSQL. Lambda has a concurrency limit of up to 10,000 simultaneous executions per account per region by default. If each invocation opens a database connection — even briefly — and your RDS PostgreSQL instance is sized at db.r6g.2xlarge with 64 GB RAM, your practical max_connections default is capped at 5,000 (PostgreSQL's default formula is LEAST(DBInstanceClassMemory/9531392, 5000) for RDS — at 64 GB of instance memory the formula's uncapped result already exceeds 5,000, so the hard cap is what applies; you can verify the actual value by querying the parameter group). A traffic spike that triggers 2,000 concurrent Lambda invocations doesn't just degrade performance — it throws FATAL: sorry, too many clients already errors and your application fails completely.

The same dynamic applies to containerized applications on ECS or EKS where horizontal pod autoscaling responds faster than your database can absorb connection growth. Each new pod starts fresh, establishes its own connections, and the old pod's connections may linger in TIME_WAIT or hold idle transactions open while the process terminates.

What RDS Proxy does architecturally is sit as a fully managed, highly available connection pooling layer between your clients and your RDS or Aurora database. It maintains a pool of long-lived connections to the database and multiplexes thousands of client connections across that pool. From your database's perspective, it sees a small, stable number of connections from the proxy. From your application's perspective, it sees a normal database endpoint.

The fundamental multiplexing mechanism is called *connection pinning* in RDS Proxy's terminology — and understanding when pinning happens is the most important operational concept in this chapter.

Connection pinning occurs when RDS Proxy cannot safely multiplex a client connection across the shared pool and must dedicate a backend database connection exclusively to that client for the duration of the session. When a connection is pinned, you lose the pooling benefit entirely for that client. Pinning is triggered by:

  • → `SET` statements that change session-level configuration (e.g., `SET search_path TO myschema`)
  • → Temporary tables (`CREATE TEMP TABLE`)
  • → Table locks (`LOCK TABLE`)
  • → Cursors opened with `HOLD`
  • → Prepared statements (in certain configurations)
  • → `SET TRANSACTION ISOLATION LEVEL` before a transaction begins

    • For PostgreSQL users who relied on SET search_path in connection strings — a common pattern — this is an immediate compatibility issue. The fix is to set search_path at the user level in the database itself (ALTER ROLE myapp SET search_path TO myschema) rather than at session level in the connection string.

    For SQL Server users, RDS Proxy does not support SQL Server. RDS Proxy supports MySQL-compatible engines (RDS MySQL, Aurora MySQL) and PostgreSQL-compatible engines (RDS PostgreSQL, Aurora PostgreSQL). SQL Server on RDS still uses driver-level connection pooling. Keep that limitation in mind throughout this chapter.

    Maximum connections math: When you create an RDS Proxy, you set a --max-connections-percent parameter (1–100, default 100). This tells the proxy what percentage of the database's max_connections it may use for the backend pool. The proxy itself can accept far more client connections than that — check current AWS documentation for the exact client-connection ceiling, but it is designed to comfortably exceed the backend connection pool by a wide margin. The multiplexing ratio is what gives you scale. If your db.r6g.2xlarge has max_connections = 1700 and you leave max-connections-percent at 100, the proxy will hold up to 1,700 backend connections but can serve tens of thousands of client connections across them — provided those client connections aren't all executing transactions simultaneously and aren't pinned.

    10.2 Creating and Configuring RDS Proxy

    RDS Proxy runs inside your VPC. It creates network interfaces in your subnets and registers against your RDS endpoint. The proxy itself is managed by AWS — you have no EC2 instances to patch, no process to restart — but you do have configuration choices that matter.

    IAM authentication is mandatory for RDS Proxy. The proxy authenticates to your database using credentials stored in AWS Secrets Manager. This is non-negotiable — you cannot use a proxy without Secrets Manager. The proxy fetches credentials from Secrets Manager on your behalf, which means the IAM role attached to the proxy must have secretsmanager:GetSecretValue on the specific secret. Your application, meanwhile, can authenticate to the proxy either using the same database credentials (passed through) or using IAM authentication (where the application gets an auth token from STS and uses it as a password).

    Here is the sequence using AWS CLI to create a proxy for an Aurora PostgreSQL cluster:

    # Step 1: Create the Secrets Manager secret for the database user
aws secretsmanager create-secret \
  --name "prod/aurora-pg/appuser" \
  --description "RDS Proxy credentials for appuser" \
  --secret-string '{"username":"appuser","password":"StrongPassword123!"}' \
  --region us-east-1

# Step 2: Get the secret ARN (you'll need this)
SECRET_ARN=$(aws secretsmanager describe-secret \
  --secret-id "prod/aurora-pg/appuser" \
  --query 'ARN' \
  --output text)

# Step 3: Create an IAM role for RDS Proxy
# First, create the trust policy document
cat > /tmp/proxy-trust-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "rds.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
EOF

aws iam create-role \
  --role-name RDSProxyRole \
  --assume-role-policy-document file:///tmp/proxy-trust-policy.json

# Step 4: Create and attach the permissions policy
cat > /tmp/proxy-permissions.json << EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "${SECRET_ARN}"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/your-kms-key-id",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "secretsmanager.us-east-1.amazonaws.com"
        }
      }
    }
  ]
}
EOF

aws iam put-role-policy \
  --role-name RDSProxyRole \
  --policy-name RDSProxySecretsAccess \
  --policy-document file:///tmp/proxy-permissions.json

ROLE_ARN=$(aws iam get-role --role-name RDSProxyRole --query 'Role.Arn' --output text)

# Step 5: Create the RDS Proxy
aws rds create-db-proxy \
  --db-proxy-name prod-aurora-pg-proxy \
  --engine-family POSTGRESQL \
  --auth '[
    {
      "Description": "App user credentials",
      "AuthScheme": "SECRETS",
      "SecretArn": "'"${SECRET_ARN}"'",
      "IAMAuth": "DISABLED"
    }
  ]' \
  --role-arn "${ROLE_ARN}" \
  --vpc-subnet-ids subnet-0a1b2c3d subnet-0e4f5a6b subnet-0c7d8e9f \
  --vpc-security-group-ids sg-0123456789abcdef0 \
  --require-tls \
  --idle-client-timeout 1800 \
  --debug-logging false \
  --region us-east-1

# Step 6: Register the Aurora cluster as the proxy target
aws rds register-db-proxy-targets \
  --db-proxy-name prod-aurora-pg-proxy \
  --db-cluster-identifiers prod-aurora-cluster \
  --region us-east-1

# Step 7: Verify proxy status (takes 3-5 minutes to become available)
aws rds describe-db-proxies \
  --db-proxy-name prod-aurora-pg-proxy \
  --query 'DBProxies[0].{Status:Status,Endpoint:Endpoint}' \
  --output table

    The --idle-client-timeout parameter (in seconds, default 1800) determines how long the proxy waits before closing a client connection that has sent no traffic. This is distinct from the connection keep-alive at the backend. Tune this to be shorter than any NAT gateway or load balancer timeout in your network path — hitting a silent TCP timeout from a middlebox is harder to debug than an explicit proxy timeout.

    The session_pinning_filters = ["EXCLUDE_VARIABLE_SETS"] setting in the connection pool configuration is worth highlighting. When enabled, the proxy does not pin connections when it encounters SET statements for a specific list of safe variables — those that don't affect transaction semantics. Check the current AWS documentation for which variables qualify, as the list expands with proxy engine updates. This reduces pinning significantly for applications that use SET for read-only configuration like application_name or TimeZone.

    The connection_borrow_timeout (120 seconds by default) is the time a client waits for the proxy to make a backend connection available before returning a timeout error. If you see applications timing out at exactly 120 seconds during traffic spikes, this is why — and the fix is usually to reduce max_connections_percent slightly so the proxy maintains more idle connections available for borrowing rather than running the pool at full saturation.

    10.3 IAM Authentication Through the Proxy

    IAM database authentication through RDS Proxy adds a second authentication layer and changes how you think about credential management. Instead of application code storing database passwords, applications generate short-lived authentication tokens using AWS STS. Those tokens expire after 15 minutes and are cryptographically tied to the IAM identity that generated them.

    The flow is:

    1. Your EC2 instance, Lambda function, or ECS task has an IAM role attached.

    2. The application code calls rds.generate_db_auth_token() (boto3) to generate a token.

    3. The application connects to the proxy endpoint using that token as the password.

    4. The proxy validates the token against IAM, then presents stored credentials to the actual database.

    This is the cloud equivalent of what you used to manage with .pgpass files, SSL certificates, and Kerberos — except IAM handles the identity federation and there are no long-lived passwords in your application configuration. What you did with pg_hba.conf entries and certificate authentication, you now do with IAM policies that specify which IAM principals can generate tokens for which database users.

    # Python application code: IAM auth token generation for RDS Proxy
# This pattern works for Lambda, ECS tasks, and EC2 instances

import boto3
import psycopg2
import os
from botocore.exceptions import ClientError

def get_db_connection_iam():
    """
    Establish a database connection using IAM authentication through RDS Proxy.
    The IAM role attached to this execution environment must have
    rds-db:connect permission for the target database user.
    """
    
    rds_client = boto3.client('rds', region_name='us-east-1')
    
    proxy_endpoint = os.environ['DB_PROXY_ENDPOINT']
    # e.g., "prod-aurora-pg-proxy.proxy-abc123.us-east-1.rds.amazonaws.com"
    
    db_user = os.environ['DB_USER']  # "appuser" — must match IAM policy resource
    db_name = os.environ['DB_NAME']  # "production"
    db_port = int(os.environ.get('DB_PORT', '5432'))
    
    try:
        # Token is valid for 15 minutes; generate fresh on each connection
        # For connection pools in long-running processes, regenerate before expiry
        auth_token = rds_client.generate_db_auth_token(
            DBHostname=proxy_endpoint,
            Port=db_port,
            DBUsername=db_user,
            Region='us-east-1'
        )
    except ClientError as e:
        raise RuntimeError(f"Failed to generate IAM auth token: {e.response['Error']['Message']}")
    
    # SSL is required for IAM authentication — the proxy enforces TLS
    # Download the RDS certificate bundle from AWS:
    # https://truststore.pki.rds.amazonaws.com/us-east-1/us-east-1-bundle.pem
    ssl_cert_path = '/etc/ssl/certs/us-east-1-bundle.pem'
    
    conn = psycopg2.connect(
        host=proxy_endpoint,
        port=db_port,
        database=db_name,
        user=db_user,
        password=auth_token,
        sslmode='verify-full',
        sslrootcert=ssl_cert_path,
        connect_timeout=10,
        application_name='my-production-service'
    )
    
    return conn


def get_db_connection_pool_iam():
    """
    For long-running services (ECS, EC2), use a connection pool with token refresh.
    psycopg2's connection pool doesn't handle token expiry natively —
    this wrapper handles the 15-minute token refresh requirement.
    """
    import psycopg2.pool
    import threading
    import time
    
    class IAMConnectionPool:
        def __init__(self, min_conn, max_conn, **conn_kwargs):
            self.conn_kwargs = conn_kwargs
            self.min_conn = min_conn
            self.max_conn = max_conn
            self._lock = threading.Lock()
            self._pool = None
            self._token_expiry = 0
            self._refresh_pool()
        
        def _generate_token(self):
            rds_client = boto3.client('rds', region_name='us-east-1')
            return rds_client.generate_db_auth_token(
                DBHostname=self.conn_kwargs['host'],
                Port=self.conn_kwargs['port'],
                DBUsername=self.conn_kwargs['user'],
                Region='us-east-1'
            )
        
        def _refresh_pool(self):
            """Recreate the pool with a fresh token. Called when token approaches expiry."""
            token = self._generate_token()
            self._token_expiry = time.time() + (14 * 60)  # refresh at 14 min, expires at 15
            
            if self._pool:
                self._pool.closeall()
            
            self._pool = psycopg2.pool.ThreadedConnectionPool(
                self.min_conn,
                self.max_conn,
                password=token,
                **self.conn_kwargs
            )
        
        def getconn(self):
            with self._lock:
                if time.time() > self._token_expiry:
                    self._refresh_pool()
            return self._pool.getconn()
        
        def putconn(self, conn):
            self._pool.putconn(conn)
    
    return IAMConnectionPool(
        min_conn=2,
        max_conn=20,
        host=os.environ['DB_PROXY_ENDPOINT'],
        port=5432,
        database=os.environ['DB_NAME'],
        user=os.environ['DB_USER'],
        sslmode='verify-full',
        sslrootcert='/etc/ssl/certs/us-east-1-bundle.pem',
        connect_timeout=10
    )


# Lambda handler example — Lambda has no persistent pool,
# but RDS Proxy handles the pooling on the server side
def lambda_handler(event, context):
    conn = None
    try:
        conn = get_db_connection_iam()
        with conn.cursor() as cur:
            cur.execute("SELECT COUNT(*) FROM orders WHERE status = %s", ('pending',))
            count = cur.fetchone()[0]
        conn.commit()
        return {'pending_orders': count}
    except Exception as e:
        if conn:
            conn.rollback()
        raise
    finally:
        if conn:
            conn.close()  # Returns connection to proxy pool, not actual DB disconnection

    The IAM policy that allows this token generation must specify the database user as part of the resource ARN:

    # Create IAM policy permitting IAM DB auth for specific user through the proxy
aws iam create-policy \
  --policy-name RDSProxyIAMAuth \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": "rds-db:connect",
        "Resource": "arn:aws:rds-db:us-east-1:123456789012:dbuser:prx-0a1b2c3d4e5f/appuser"
      }
    ]
  }'

# Attach this policy to the Lambda execution role or ECS task role
aws iam attach-role-policy \
  --role-name MyLambdaExecutionRole \
  --policy-arn arn:aws:iam::123456789012:policy/RDSProxyIAMAuth

# The resource ARN format for proxy IAM auth is:
# arn:aws:rds-db:{region}:{account-id}:dbuser:{proxy-resource-id}/{db-username}
# Get the proxy resource ID:
aws rds describe-db-proxies \
  --db-proxy-name prod-aurora-pg-proxy \
  --query 'DBProxies[0].DBProxyArn' \
  --output text
# Extract "prx-XXXXXXXXXX" from the ARN — that's the resource ID portion

    One gotcha that bites teams regularly: the IAM resource ARN uses the proxy resource ID (the prx- identifier), not the proxy name or the cluster ARN. When the policy is wrong, the application gets a generic authentication failure with no indication that IAM authorization is the cause — the proxy rejects the token before the database is involved, and the error looks identical to a wrong password. Always test token generation separately from the connection attempt when debugging IAM auth failures.

    10.4 Monitoring Proxy Performance and Connection Pinning

    CloudWatch publishes RDSProxy metrics under the AWS/RDS namespace with the dimension ProxyName. The metrics you care about operationally break into three categories: connection counts, pooling efficiency, and latency.

    Connection count metrics:

    | Metric | What it tells you |

    |---|---|

    | ClientConnections | Current number of client connections to the proxy |

    | DatabaseConnections | Current number of backend connections the proxy holds to the database |

    | DatabaseConnectionsSetupSucceeded | Rate of successful backend connection establishments |

    | DatabaseConnectionsSetupFailed | Rate of failed backend connection establishments |

    | ClientConnectionsClosed | Rate of client connection closures |

    The ratio of ClientConnections to DatabaseConnections is your effective multiplexing ratio. If you have 2,000 client connections and 300 database connections, the proxy is working as intended. If those numbers are equal — or worse, DatabaseConnections is approaching your max_connections limit while ClientConnections is only modestly higher — you have a pinning problem.

    The pinning metric you must alarm on:

    DatabaseConnectionsCurrentlySessionPinned

    This metric reports how many backend connections are currently pinned to a specific client. A non-zero value is not necessarily a crisis — some applications legitimately use temporary tables or multi-statement transactions that require pinning. But a value that climbs toward your total DatabaseConnections count means you are getting no benefit from the proxy's multiplexing, and you should investigate which application code paths are causing the pins.

    10.5 Failover Behavior: What RDS Proxy Changes (and What It Doesn't)

    RDS Proxy's behavior during an Aurora failover is one of its strongest operational selling points, and it is also one of the most commonly misunderstood. Let's be precise.

    Without the proxy, an Aurora failover looks like this from the application's perspective:

    1. The writer instance fails or is manually failed over.

    2. Aurora promotes a reader to writer — this typically completes within 30 to 60 seconds for Aurora PostgreSQL.

    3. The cluster writer DNS endpoint (cluster-id.cluster-xyz.region.rds.amazonaws.com) updates its CNAME to point to the new writer — DNS TTL is typically 5 seconds, but client-side DNS caching in the JVM, Linux nscd, or application-level caching may hold the old IP for longer.

    4. Existing connections are dropped (TCP RST or timeout depending on the failure mode).

    5. Application must reconnect. If reconnect logic is not implemented, the application stays broken until a process restart.

    With the proxy, the application's view changes substantially:

    1. The writer instance fails.

    2. Aurora promotes a reader to writer.

    3. The proxy detects the topology change and transparently redirects new backend connections to the new writer — the proxy maintains its own connection to the cluster and watches for failover events through the Aurora internal notification mechanism, not just DNS.

    4. The proxy endpoint for your application does not change. There is no DNS re-resolution required at the application level.

    5. Client connections to the proxy that were idle (not mid-transaction) are preserved transparently — the proxy queues incoming requests briefly while re-establishing its backend connections.

    6. Client connections that were mid-transaction when the failover hit will receive an error. This is unavoidable — the in-flight transaction was on the old writer and is gone. The proxy cannot make a transaction that was lost on a failed instance appear to succeed.

    The practical result: the proxy reduces failover impact from "reconnect storm plus DNS propagation delay plus application-level reconnect logic" to "brief queuing plus mid-transaction errors only". Applications with appropriate retry logic on the transaction level — not just the connection level — see dramatically reduced failover disruption. Applications that assume a single query can never fail still break, but they break for a shorter window and recover without needing to re-establish thousands of connections simultaneously.

    A concrete test: you can observe this behavior by intentionally triggering a failover against a proxied Aurora cluster while running a connection monitor. The following script measures perceived downtime from the application side:

    # scripts/failover_test.py
# Run this WHILE triggering a manual failover to measure client-side impact

import psycopg2
import time
import datetime
import os

PROXY_ENDPOINT = os.environ['DB_PROXY_ENDPOINT']
DB_NAME = os.environ['DB_NAME']
DB_USER = os.environ['DB_USER']
DB_PASSWORD = os.environ['DB_PASSWORD']

def make_connection():
    return psycopg2.connect(
        host=PROXY_ENDPOINT,
        port=5432,
        database=DB_NAME,
        user=DB_USER,
        password=DB_PASSWORD,
        sslmode='require',
        connect_timeout=5,
        application_name='failover-test'
    )

def probe_once(conn=None):
    """Returns (success, latency_ms, error_message)"""
    start = time.monotonic()
    try:
        if conn is None:
            conn = make_connection()
        with conn.cursor() as cur:
            cur.execute("SELECT 1")
            cur.fetchone()
        conn.commit()
        latency = (time.monotonic() - start) * 1000
        return True, latency, None, conn
    except psycopg2.OperationalError as e:
        latency = (time.monotonic() - start) * 1000
        # Connection lost — try fresh reconnect
        try:
            new_conn = make_connection()
            return False, latency, str(e), new_conn
        except Exception as reconnect_err:
            return False, latency, f"reconnect failed: {reconnect_err}", None

print(f"{'Timestamp':<26} {'Status':<10} {'Latency(ms)':<15} {'Notes'}")
print("-" * 70)

conn = make_connection()
errors_seen = 0
first_error_time = None
last_error_time = None

for _ in range(600):  # 10 minutes of probing at 1-second intervals
    ts = datetime.datetime.now().isoformat(timespec='milliseconds')
    success, latency_ms, error_msg, conn = probe_once(conn)
    
    status = "OK" if success else "ERROR"
    note = ""
    
    if not success:
        errors_seen += 1
        if first_error_time is None:
            first_error_time = ts
        last_error_time = ts
        note = error_msg[:50] if error_msg else ""
    
    print(f"{ts:<26} {status:<10} {latency_ms:<15.1f} {note}")
    time.sleep(1)

print(f"\nSummary: {errors_seen} errors observed")
if first_error_time:
    print(f"First error: {first_error_time}")
    print(f"Last error:  {last_error_time}")

    Run this script before triggering the failover (aws rds failover-db-cluster --db-cluster-identifier prod-aurora-cluster). The output will show you exactly how many seconds of errors your application tier experiences. Without the proxy, you typically see a sustained error period during DNS propagation. With the proxy, you typically see a brief burst of errors confined to the moment of the writer promotion, followed by immediate recovery — the proxy requeues requests and re-establishes its backend connections without your application needing to reconnect.

    The multi-AZ RDS (non-Aurora) failover story is slightly different. Standard RDS Multi-AZ failover relies on DNS failover to the standby. RDS Proxy helps here too — the proxy tracks the database endpoint and handles the backend reconnection, still giving you the same client-connection stability benefit. However, the failover duration for standard Multi-AZ RDS is longer than Aurora failover because the promotion process involves more steps, and the proxy is waiting for the new primary to become available before re-establishing the backend pool. The proxy does not shorten the database failover itself — it only reduces the application-side reconnection overhead once the new primary is up.

    10.6 Sizing and Scaling Considerations

    RDS Proxy scales its own compute automatically — you do not choose an instance size for the proxy. AWS manages horizontal scaling of the proxy fleet. What you do control is the configuration that determines how efficiently the proxy uses backend connections, and that is where DBA judgment is applied.

    Backend connection pool sizing decisions:

    The max_connections_percent parameter is your primary lever. Setting it to 100 (the default) instructs the proxy to potentially use all of the database's max_connections for the proxy pool. In practice this is rarely correct for two reasons:

    First, you almost always want to reserve some connections for emergency direct access. If a runaway proxy behavior or an application bug exhausts the pool, you need to be able to connect directly to the database as an administrator to diagnose the problem. A good rule of thumb is to reserve at least 5–10 connections for direct administrative access. With max-connections-percent = 90 and your max_connections set to 1,000, the proxy can use up to 900 connections and you always have 100 available for direct connections.

    Second, the proxy is most efficient when it is not running at full pool saturation. A fully saturated pool means every incoming client request must wait for a backend connection to become free. The queuing delay compounds under load. Setting max-connections-percent to 75–85% of what your database can actually sustain under realistic load gives the pool breathing room.

    max_idle_connections_percent controls how many idle connections the proxy keeps warm in the backend pool. Idle connections consume memory on the database host — each PostgreSQL connection holds a backend process in memory even when doing nothing. Set this too high and you're paying connection memory cost constantly. Set it too low and the proxy must establish new backend connections under sudden traffic spikes, which adds latency during the connection establishment phase. A value of 50 (the default) means the proxy keeps up to half its maximum backend connections open and idle, ready to be assigned to incoming client requests immediately.

    Instance sizing for the database itself does not change because of the proxy — the proxy reduces the number of backend connections the database manages, but the database still needs to be sized for the actual query workload. Where the proxy helps is that you can often run a smaller database instance than you would have needed without it, because you are no longer allocating 9 MB of RAM per potential connection when only a fraction of those connections are ever active simultaneously.

    A sizing worked example (qualitative, not prescriptive):

    Suppose you have an ECS service that autoscales from 10 to 200 tasks, each with a connection pool of 5 connections, giving a maximum potential connection demand of 1,000. Without the proxy, you size your database to handle 1,000 connections plus admin headroom. With the proxy, the database might actually only see 150–300 backend connections at peak because the proxy's multiplexing collapses idle-connection demand. You can size the database for the actual query concurrency rather than the theoretical connection count.

    Validate this by watching DatabaseConnections in CloudWatch during your peak traffic period after deploying the proxy. The actual number you observe is your actual database connection load. Use that to inform whether you're running with more backend pool headroom than needed, or whether you're running close to saturation and should consider scaling the database.

    10.7 Limitations and When Not to Use RDS Proxy

    Every managed service has a boundary at which it stops being the right tool. Knowing that boundary for RDS Proxy is as important as knowing how to configure it.

    Long-running transactions: RDS Proxy multiplexes connections between requests, but while a transaction is open, the backend connection is held exclusively for that client — this is the same as pinning for the duration of the transaction. Applications that open transactions and hold them open for seconds or minutes while doing application-side work (processing data between SQL statements, waiting for user input in web applications, etc.) will see poor pool utilization. Design your application transactions to be short: open late, close early. If your application design fundamentally requires long-held transactions, the proxy's multiplexing benefit is largely lost.

    Stored procedures and session state: Applications that rely heavily on session-level state — temporary tables across multiple requests, SET LOCAL in transaction-scoped ways, advisory locks held across connections — require careful audit before proxying. None of these patterns become impossible with the proxy, but they may require session pinning, reducing the multiplexing benefit.

    Binary protocols and non-standard drivers: RDS Proxy supports the standard PostgreSQL wire protocol and the MySQL wire protocol. Applications using non-standard connection mechanisms, administrative tools that use direct socket connections, or drivers with unusual protocol behavior may encounter compatibility issues. Test all connection paths — not just your main application — before enabling the proxy in production.

    Cost considerations: RDS Proxy is not free. AWS charges per vCPU of the underlying database instance, per hour, while the proxy is attached. For small database instances with low connection counts, the cost may exceed the operational benefit. Evaluate the cost against the alternative of running a self-managed PgBouncer on an EC2 instance — for small workloads, PgBouncer on a t3.small can be significantly cheaper. For large, high-connection workloads, RDS Proxy's managed nature and Aurora-native integration justify the cost. Review current AWS pricing for your region before committing.

    SQL Server is not supported: Repeat this for your team: SQL Server on RDS does not support RDS Proxy. SQL Server's connection pooling is handled by the ODBC or ADO.NET driver, which is session-based. If you're running SQL Server on RDS and need connection pooling, you have three options: driver-level pooling (built into most .NET and Java connection frameworks), a third-party proxy like ProxySQL (which has limited SQL Server support), or refactoring to reduce connection pressure at the application level.

    Proxy-to-database network latency: The proxy sits in your VPC and adds one network hop between your application and the database. For latency-sensitive OLTP workloads executing many small queries, this hop is measurable. In practice it is a fraction of a millisecond within a region, but if you are optimizing for sub-millisecond query execution times, measure the added latency in your environment before committing to the proxy architecture.

    10.8 Practical Runbook: Diagnosing a Connection Pool Exhaustion Event

    When an on-call engineer gets paged at 2 AM with "database connections exhausted," having a structured diagnostic path matters more than knowing every possible cause. Here is the runbook as a DBA would actually use it.

    Step 1: Establish current state

    # What does the proxy see right now?
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ClientConnections \
  --dimensions Name=ProxyName,Value=prod-aurora-pg-proxy \
  --start-time $(date -u -d '10 minutes ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 \
  --statistics Average Maximum \
  --output table

aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DatabaseConnections \
  --dimensions Name=ProxyName,Value=prod-aurora-pg-proxy \
  --start-time $(date -u -d '10 minutes ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 \
  --statistics Average Maximum \
  --output table

aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DatabaseConnectionsCurrentlySessionPinned \
  --dimensions Name=ProxyName,Value=prod-aurora-pg-proxy \
  --start-time $(date -u -d '10 minutes ago' +%Y-%m-%dT%H:%M:%SZ) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 \
  --statistics Average Maximum \
  --output table

    Step 2: Connect directly to the database (bypassing the proxy) and query pg_stat_activity

    -- PostgreSQL: connect directly on port 5432 to the writer endpoint, not via proxy
-- You reserved direct connections for exactly this scenario

-- Who is connected and what are they doing?
SELECT 
    pid,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    now() - query_start    AS query_duration,
    now() - state_change   AS state_duration,
    LEFT(query, 100)       AS query_snippet
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY query_duration DESC NULLS LAST;

-- Count by state and application
SELECT 
    application_name,
    state,
    COUNT(*) AS connection_count,
    MAX(now() - state_change) AS longest_in_state
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY application_name, state
ORDER BY connection_count DESC;

-- Are there long-running idle-in-transaction connections?
-- These hold backend connections pinned in the proxy
SELECT 
    pid,
    usename,
    application_name,
    state,
    now() - state_change AS idle_in_tx_duration,
    LEFT(query, 200) AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND now() - state_change > interval '30 seconds'
ORDER BY idle_in_tx_duration DESC;

    Step 3: If idle-in-transaction connections are the cause, terminate them

    -- PostgreSQL: terminate long-idle-in-transaction connections
-- Use pg_terminate_backend, not pg_cancel_backend
-- (cancel only stops the running query; terminate closes the connection)

-- First preview what you'd terminate:
SELECT 
    pid,
    usename,
    application_name,
    now() - state_change AS idle_duration
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND now() - state_change > interval '2 minutes';

-- Then terminate:
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND now() - state_change > interval '2 minutes';

-- Verify the terminations took effect:
SELECT COUNT(*) 
FROM pg_stat_activity 
WHERE state = 'idle in transaction';

    Step 4: Check if a specific application host is responsible

    The proxy logs client IP addresses in debug mode. If debug logging is not already enabled:

    # Enable debug logging temporarily
aws rds modify-db-proxy \
  --db-proxy-name prod-aurora-pg-proxy \
  --debug-logging

# Wait 60 seconds for logs to appear, then query for connection events by client IP
aws logs filter-log-events \
  --log-group-name "/aws/rds/proxy/prod-aurora-pg-proxy" \
  --filter-pattern "[timestamp, requestId, level, clientId, message=\"*client*connected*\"]" \
  --start-time $(date -d '5 minutes ago' +%s000) \
  --query 'events[*].message' \
  --output text | sort | uniq -c | sort -rn | head -20

    Step 5: Immediate mitigation options

    If the pool is exhausted and the application is failing:

    # Option A: Temporarily increase max_connections_percent to give more backend connections
# This only works if the database instance has headroom
aws rds modify-db-proxy-target-group \
  --db-proxy-name prod-aurora-pg-proxy \
  --target-group-name default \
  --connection-pool-config MaxConnectionsPercent=95

# Option B: If a runaway process has filled the pool, restart the ECS service
# (replace with your actual cluster/service names)
aws ecs update-service \
  --cluster prod-cluster \
  --service my-application-service \
  --force-new-deployment

# Option C: If an autoscaling event caused the spike and you need to shed connections,
# reduce ECS desired count temporarily
aws ecs update-service \
  --cluster prod-cluster \
  --service my-application-service \
  --desired-count 10

    Step 6: After mitigation, set a idle_in_transaction_session_timeout to prevent recurrence

    -- PostgreSQL: set at the database level to auto-terminate stuck transactions
-- This catches connections that the proxy cannot clean up itself

ALTER DATABASE production 
  SET idle_in_transaction_session_timeout = '5min';

-- Or at the role level for the application user specifically
ALTER ROLE appuser 
  SET idle_in_transaction_session_timeout = '5min';

-- Verify the setting:
SHOW idle_in_transaction_session_timeout;

    This setting causes PostgreSQL to automatically terminate any backend that has been idle within a transaction for longer than the specified duration. The proxy will see the backend connection dropped and will establish a fresh one. Pairing this database-level protection with the proxy's idle-client-timeout gives you defense in depth: the proxy closes idle client connections before they accumulate, and the database closes stuck transactions before they pin backend connections indefinitely.

    Key Takeaways

  • → **RDS Proxy multiplexes thousands of client connections onto a much smaller backend connection pool**, reducing per-connection memory overhead on the database and eliminating reconnect storms during traffic spikes — but this benefit only materializes when client connections are not session-pinned. Monitor `DatabaseConnectionsCurrentlySessionPinned` and treat a rising pinning ratio as a signal to audit application code for `SET` statements, temporary tables, and long-held idle transactions.
  • → **Connection pinning is the primary operational hazard of RDS Proxy**. Common causes include `SET search_path` in connection strings, `CREATE TEMP TABLE` in application code, and open cursors with `HOLD`. Fix pinning at the source: move role defaults to `ALTER ROLE ... SET`, avoid temporary tables in hot paths, and set `session_pinning_filters = ["EXCLUDE_VARIABLE_SETS"]` in the proxy target group configuration to exclude low-risk `SET` statements from triggering pins.
  • → **IAM authentication through RDS Proxy eliminates long-lived passwords from application configuration**, replacing them with 15-minute cryptographic tokens tied to IAM roles. The IAM resource ARN in the `rds-db:connect` policy must reference the proxy's resource ID (the `prx-` identifier), not the proxy name or cluster ARN — a mistake that produces authentication errors indistinguishable from a wrong password at the application level.
  • → **During Aurora failover, RDS Proxy preserves the application-facing endpoint and transparently re-establishes backend connections to the promoted writer**, reducing failover impact to mid-transaction errors only rather than a full reconnect storm across all application instances. The proxy does not shorten the Aurora failover duration itself — it reduces the application-side recovery work that follows.
  • → **RDS Proxy is not universally the right choice**: SQL Server on RDS is not supported, long-held transactions negate the multiplexing benefit, and for low-connection workloads the per-vCPU cost may exceed the value of the managed service compared to running self-managed PgBouncer. Validate the business case with actual connection count metrics, test `max_connections_percent` and `max_idle_connections_percent` against your real traffic patterns, and always reserve a portion of `max_connections` for direct administrative access independent of the proxy pool.
