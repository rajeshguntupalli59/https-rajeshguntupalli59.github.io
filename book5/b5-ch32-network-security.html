Chapter 32: VPC, Private Endpoints, and Network Security

Network security for cloud databases is where experienced on-prem DBAs often feel the most disoriented. On-premises, you controlled the physical network, configured firewall rules on the host, and trusted that your database server sat inside a known perimeter. In the cloud, that perimeter dissolves and reforms as a collection of software-defined constructs — VPCs, subnets, security groups, private endpoints, and DNS resolution chains — that you must understand completely before putting production data anywhere near them. This chapter covers how AWS, Azure, and Google Cloud each implement database network isolation, how to connect applications to managed databases without exposing them to the public internet, and how to build defense-in-depth network security that will survive a security audit. The patterns here apply equally to RDS, Aurora, Azure SQL, Cloud SQL, and AlloyDB.

---

32.1 Virtual Networks: The Foundation of Cloud Database Isolation

Before touching a single database configuration, you need a clear mental model of how virtual networks work across the three clouds. The terminology differs but the concepts are nearly identical.

Mapping Your On-Prem Concepts

On-premises, you had VLANs, subnets, ACLs, and firewall rules implemented in hardware. In the cloud:

| On-Premises Concept | AWS | Azure | GCP |

|---|---|---|---|

| Data center network | VPC | Virtual Network (VNet) | VPC |

| VLAN / network segment | Subnet | Subnet | Subnet |

| Firewall rules (host-based) | Security Group | NSG (Network Security Group) | Firewall Rules |

| Network-level ACL | Network ACL | NSG on subnet | VPC Firewall Rules |

| Private RFC 1918 space | Private subnets | Private subnets | Private subnets |

| DNS server | Route 53 Private Hosted Zone | Azure Private DNS Zone | Cloud DNS private zone |

The one thing that consistently surprises on-prem DBAs: security groups in AWS are stateful (return traffic is automatically allowed), while Network ACLs are stateless. For database connectivity, you typically work with security groups, not NACLs directly.

Subnet Architecture for Database Workloads

The standard production layout places your database instances in private subnets — subnets with no route to an internet gateway. Your application tier sits in separate subnets, and all traffic flows through security group rules, not public IP addresses.

For RDS and Aurora, AWS requires subnets in at least two Availability Zones to create a DB Subnet Group. This is not optional — it is a hard requirement even for single-AZ deployments:

# Create a DB subnet group spanning two AZs — required before any RDS deployment
aws rds create-db-subnet-group \
  --db-subnet-group-name prod-db-subnet-group \
  --db-subnet-group-description "Production database subnets" \
  --subnet-ids subnet-0a1b2c3d4e5f67890 subnet-0f9e8d7c6b5a43210 \
  --tags Key=Environment,Value=production Key=Team,Value=database

# Verify the subnet group is in the correct VPC and AZs
aws rds describe-db-subnet-groups \
  --db-subnet-group-name prod-db-subnet-group \
  --query 'DBSubnetGroups[0].{VpcId:VpcId,Subnets:Subnets[*].{AZ:SubnetAvailabilityZone.Name,Id:SubnetIdentifier}}'

The equivalent in Terraform, which is how most production environments should be managing this:

# Terraform: VPC layout for production RDS deployment
resource "aws_vpc" "prod" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = {
    Name        = "prod-vpc"
    Environment = "production"
  }
}

resource "aws_subnet" "database_az1" {
  vpc_id            = aws_vpc.prod.id
  cidr_block        = "10.0.32.0/24"
  availability_zone = "us-east-1a"

  tags = {
    Name = "prod-db-subnet-az1"
    Tier = "database"
  }
}

resource "aws_subnet" "database_az2" {
  vpc_id            = aws_vpc.prod.id
  cidr_block        = "10.0.33.0/24"
  availability_zone = "us-east-1b"

  tags = {
    Name = "prod-db-subnet-az2"
    Tier = "database"
  }
}

resource "aws_db_subnet_group" "prod" {
  name       = "prod-db-subnet-group"
  subnet_ids = [aws_subnet.database_az1.id, aws_subnet.database_az2.id]

  tags = {
    Name = "Production DB Subnet Group"
  }
}

# Security group: database instances
# Only allows inbound from the application tier security group
resource "aws_security_group" "database" {
  name        = "prod-database-sg"
  description = "Security group for RDS/Aurora instances"
  vpc_id      = aws_vpc.prod.id

  ingress {
    description     = "PostgreSQL from application tier"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.application.id]
  }

  egress {
    description = "All outbound — needed for IAM auth token validation"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "prod-database-sg"
  }
}

What You Cannot Control in Managed Services

On self-managed PostgreSQL, you had pg_hba.conf for host-based authentication, could bind to specific interfaces, and could install host-level firewalls. With RDS:

  • → You cannot access the operating system or configure pg_hba.conf directly
  • → You cannot install host-based firewall rules
  • → You cannot bind to a specific IP address — RDS assigns its own private IP within your subnet
  • → The RDS endpoint DNS name resolves to different IPs during failover — never hardcode IPs in connection strings

    • This last point is where on-prem DBAs get burned. Always use the CNAME endpoint, never the underlying IP address.

    32.2 Private Endpoints and Private Link: Eliminating Public Exposure

    The default configuration for many cloud services — including Azure SQL — allows public connectivity. Turning it off and routing all traffic through private endpoints is non-negotiable for production database workloads.

    AWS PrivateLink and RDS

    For RDS and Aurora, the database instance itself sits in your private subnet and never has a public IP if you configure it correctly (PubliclyAccessible: false). But connectivity from other AWS services — Lambda, ECS tasks, other VPCs — requires either VPC peering, AWS Transit Gateway, or VPC endpoints for the AWS APIs your database tooling uses.

    For Aurora Serverless v2 and RDS Proxy, you also need VPC endpoints for Secrets Manager if you are rotating credentials:

    # Verify RDS instance is NOT publicly accessible — this should be false in production
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].{PubliclyAccessible:PubliclyAccessible,Endpoint:Endpoint,VpcId:DBSubnetGroup.VpcId}'

# Create VPC endpoint for Secrets Manager — required for RDS Proxy credential rotation
# without routing through the public internet
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0a1b2c3d4e5f67890 \
  --service-name com.amazonaws.us-east-1.secretsmanager \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-0a1b2c3d4e5f67890 subnet-0f9e8d7c6b5a43210 \
  --security-group-ids sg-0a1b2c3d4e5f67890 \
  --private-dns-enabled \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=secretsmanager-endpoint}]'

    Azure SQL Private Endpoint Configuration

    Azure SQL has both a public endpoint (disabled by requirement in secure environments) and supports Private Link, which creates a private IP in your VNet that maps to the Azure SQL managed instance or logical server. The Azure CLI workflow:

    # Step 1: Disable public access on Azure SQL Server
az sql server update \
  --name prod-sql-server \
  --resource-group prod-rg \
  --enable-public-network false

# Step 2: Create private endpoint in your VNet
az network private-endpoint create \
  --name prod-sql-private-endpoint \
  --resource-group prod-rg \
  --vnet-name prod-vnet \
  --subnet prod-db-subnet \
  --private-connection-resource-id \
    /subscriptions/{subscription-id}/resourceGroups/prod-rg/providers/Microsoft.Sql/servers/prod-sql-server \
  --group-id sqlServer \
  --connection-name prod-sql-private-link

# Step 3: Create private DNS zone for Azure SQL
az network private-dns zone create \
  --resource-group prod-rg \
  --name "privatelink.database.windows.net"

# Step 4: Link DNS zone to your VNet
az network private-dns link vnet create \
  --resource-group prod-rg \
  --zone-name "privatelink.database.windows.net" \
  --name prod-vnet-dns-link \
  --virtual-network prod-vnet \
  --registration-enabled false

# Step 5: Create DNS record for the private endpoint
az network private-endpoint dns-zone-group create \
  --resource-group prod-rg \
  --endpoint-name prod-sql-private-endpoint \
  --name sql-dns-zone-group \
  --private-dns-zone "privatelink.database.windows.net" \
  --zone-name sql

    After completing this sequence, your application connects to prod-sql-server.database.windows.net and the private DNS zone resolves it to the private IP address in your VNet — not the public Azure SQL endpoint. Verify this from within the VNet:

    # From a VM in the VNet — should resolve to a 10.x.x.x private IP
nslookup prod-sql-server.database.windows.net
# Expected: Non-authoritative answer showing a 10.x.x.x address
# If it shows a public Azure IP, your DNS zone or link is misconfigured

    Google Cloud Private Service Connect for Cloud SQL

    Google Cloud SQL uses Private Service Connect (PSC) or older VPC peering. PSC is the current recommended approach and creates a forwarding rule with a private IP in your VPC:

    # Enable Private Service Connect on Cloud SQL instance
gcloud sql instances patch prod-postgres-instance \
  --project=my-project \
  --enable-private-service-connect \
  --allowed-psc-projects=consumer-project-id

# Get the PSC service attachment URI from the instance
gcloud sql instances describe prod-postgres-instance \
  --project=my-project \
  --format='value(settings.ipConfiguration.pscConfig.serviceAttachmentLink)'

# Create a forwarding rule pointing to the PSC attachment
gcloud compute forwarding-rules create prod-cloudsql-psc \
  --region=us-central1 \
  --network=prod-vpc \
  --address=prod-cloudsql-private-ip \
  --target-service-attachment=projects/PRODUCER_PROJECT/regions/us-central1/serviceAttachments/ATTACHMENT_NAME \
  --project=my-project

# Create DNS entry so applications use a consistent hostname
gcloud dns record-sets create prod-postgres.internal.example.com. \
  --rrdatas=10.0.32.15 \
  --type=A \
  --ttl=300 \
  --zone=internal-zone \
  --project=my-project

    The Common Gotcha: DNS Resolution

    Private endpoints are useless if your application's DNS resolver bypasses the private zone. This happens most frequently when:

    1. Applications run in a different VPC without VPC peering and shared DNS resolution

    2. Containers use their own DNS servers instead of the VPC resolver

    3. On-premises systems connecting over VPN or Direct Connect use corporate DNS that does not forward to the cloud private zones

    Test DNS resolution from every network segment that needs database access, not just from one representative host.

    graph TD
    A[Application tier
    private subnet] -->|Security group reference,
    not CIDR| B[Private endpoint /
    PrivateLink ENI]
    B -->|Private IP, resolved via
    private DNS zone| C[Database instance
    private subnet]
    D[Public internet] -.->|No route,
    no public IP| C
    A -.->|DNS query for
    db hostname| E[Private DNS zone
    linked to VNet/VPC]
    E -->|Resolves to
    private IP| B

    *Traffic never leaves the VPC/VNet: the private DNS zone is what keeps applications from silently falling back to the public endpoint.*

    32.3 Security Groups, Firewall Rules, and the Principle of Least Privilege

    Think of security groups as the evolved equivalent of iptables rules — but managed, stateful, and attached to resources rather than hosts. For databases, the configuration philosophy is the same as on-prem: explicit allow, implicit deny, minimum necessary access.

    Security Group Design for Multi-Tier Applications

    The correct pattern chains security groups by reference, not by CIDR range. This means the database security group allows traffic from the application security group, not from 10.0.0.0/8. When auto-scaling adds application instances, they inherit the application security group automatically and immediately get database access — no rule changes required.

    # Audit existing RDS security group rules — look for 0.0.0.0/0 which should never appear
aws ec2 describe-security-groups \
  --group-ids sg-0a1b2c3d4e5f67890 \
  --query 'SecurityGroups[0].IpPermissions[*].{
    Port:FromPort,
    Protocol:IpProtocol,
    Sources:IpRanges[*].CidrIp,
    SGSources:UserIdGroupPairs[*].GroupId
  }' \
  --output table

# Add RDS Proxy security group as an allowed source to the database SG
# This is required when you introduce RDS Proxy in front of your instances
aws ec2 authorize-security-group-ingress \
  --group-id sg-database-sg-id \
  --protocol tcp \
  --port 5432 \
  --source-group sg-rdsproxy-sg-id

# Verify: RDS Proxy needs outbound to the database, database needs inbound from proxy
# Application needs outbound to proxy, proxy needs inbound from application
# These are four distinct security group rules, not two

    Azure SQL Firewall Rules and Service Endpoints

    Azure SQL has two distinct layers: server-level firewall rules (IP-based, older model) and VNet service endpoints or Private Endpoints (the correct production model). Service endpoints are a middle-ground — they restrict access to specific VNet subnets but traffic still traverses the Azure backbone routing to the public endpoint. Private Endpoints are stronger: traffic stays entirely within your VNet.

    # Remove overly permissive firewall rules from Azure SQL
# First, list all existing rules
az sql server firewall-rule list \
  --server prod-sql-server \
  --resource-group prod-rg \
  --output table

# Delete any rule that allows 0.0.0.0 to 255.255.255.255 ("Allow Azure Services")
# This rule allows ALL Azure services, including other tenants' services
az sql server firewall-rule delete \
  --server prod-sql-server \
  --resource-group prod-rg \
  --name "AllowAllWindowsAzureIps"

# Add VNet rule for your application subnet (service endpoint approach)
az sql server vnet-rule create \
  --server prod-sql-server \
  --resource-group prod-rg \
  --name allow-app-subnet \
  --vnet-name prod-vnet \
  --subnet app-subnet

    Note that "Allow Azure Services" firewall rule in Azure SQL is frequently misunderstood. It does not mean "allow only my services" — it means allow any traffic originating from any Azure datacenter IP, including other customers' Azure services. Remove it.

    GCP Firewall Rules for Cloud SQL

    Cloud SQL with Private Service Connect or VPC peering does not use GCP firewall rules directly for database port access — the peering or PSC handles routing. However, you still need firewall rules to control which compute resources can reach the database:

    # GCP Firewall rule: allow PostgreSQL from application instances
# Tagged approach — apply 'db-client' tag to instances that need database access
gcloud compute firewall-rules create allow-postgres-from-app \
  --project=my-project \
  --network=prod-vpc \
  --direction=INGRESS \
  --priority=1000 \
  --action=ALLOW \
  --rules=tcp:5432 \
  --source-tags=db-client \
  --target-tags=db-server \
  --description="Allow PostgreSQL from tagged application instances"

# For Cloud SQL specifically, also allow the Cloud SQL proxy if used
gcloud compute firewall-rules create allow-cloudsql-proxy \
  --project=my-project \
  --network=prod-vpc \
  --direction=EGRESS \
  --priority=1000 \
  --action=ALLOW \
  --rules=tcp:3307 \
  --destination-ranges=35.191.0.0/16,130.211.0.0/22 \
  --description="Allow outbound to Cloud SQL proxy API"

    32.4 Cross-VPC Connectivity: Peering, Transit Gateway, and PrivateLink

    Production environments rarely have a single VPC. You will have dedicated VPCs for different applications, different environments (dev, staging, prod), or different business units. Getting databases to talk across these boundaries without exposing them to the internet requires deliberate architecture.

    AWS VPC Peering vs. Transit Gateway

    VPC peering connects two VPCs directly. It does not support transitive routing — if VPC A peers with VPC B, and VPC B peers with VPC C, VPC A cannot reach VPC C through VPC B. For database access patterns where multiple application VPCs need to reach a central database VPC, this forces a hub-and-spoke design with Transit Gateway:

    # Terraform: Transit Gateway setup for central database VPC access
resource "aws_ec2_transit_gateway" "main" {
  description                     = "Central TGW for database connectivity"
  default_route_table_association = "disable"
  default_route_table_propagation = "disable"
  dns_support                     = "enable"
  vpn_ecmp_support                = "enable"

  tags = {
    Name = "prod-tgw"
  }
}

# Attach the database VPC to the Transit Gateway
resource "aws_ec2_transit_gateway_vpc_attachment" "database_vpc" {
  transit_gateway_id = aws_ec2_transit_gateway.main.id
  vpc_id             = aws_vpc.database.id
  subnet_ids         = [aws_subnet.database_az1.id, aws_subnet.database_az2.id]

  dns_support    = "enable"
  ipv6_support   = "disable"

  tags = {
    Name = "db-vpc-attachment"
  }
}

# Attach an application VPC
resource "aws_ec2_transit_gateway_vpc_attachment" "app_vpc" {
  transit_gateway_id = aws_ec2_transit_gateway.main.id
  vpc_id             = aws_vpc.application.id
  subnet_ids         = [aws_subnet.app_az1.id, aws_subnet.app_az2.id]

  tags = {
    Name = "app-vpc-attachment"
  }
}

# Route table: application VPC -> database VPC only
# Database traffic is 10.0.0.0/16, restrict to only that CIDR
resource "aws_ec2_transit_gateway_route_table" "app_to_db" {
  transit_gateway_id = aws_ec2_transit_gateway.main.id

  tags = {
    Name = "app-to-db-only"
  }
}

resource "aws_ec2_transit_gateway_route" "app_to_db" {
  destination_cidr_block         = "10.0.0.0/16"  # Database VPC CIDR
  transit_gateway_attachment_id  = aws_ec2_transit_gateway_vpc_attachment.database_vpc.id
  transit_gateway_route_table_id = aws_ec2_transit_gateway_route_table.app_to_db.id
}

    Connecting On-Premises to Cloud Databases

    This is the most common architecture during migration phases: on-premises applications need to reach cloud databases, or cloud databases need to reach on-premises systems for DMS replication. The options in order of preference:

    1. AWS Direct Connect / Azure ExpressRoute / GCP Dedicated Interconnect — dedicated physical connection, predictable latency (typically 1–5ms for co-located facilities), no internet exposure. Required for any data volume above a few hundred MB/day and for compliance environments

    2. Site-to-Site VPN — encrypted tunnel over internet, variable latency (20–100ms typical), acceptable for lower-volume migration workloads

    3. Public internet with SSL/TLS — last resort, acceptable only for development

    For Direct Connect with RDS, you still need a Virtual Private Gateway attached to your VPC and route propagation configured. The database endpoint resolves to a private IP that routes over the Direct Connect circuit:

    # Verify that RDS endpoint resolves to a private IP from on-premises
# (run this from an on-premises host after Direct Connect + BGP route propagation)
dig +short prod-postgres-01.cluster-xyz.us-east-1.rds.amazonaws.com
# Should return: 10.x.x.x (private IP in your VPC subnet)
# If returns: 52.x.x.x or 34.x.x.x (public AWS IP), your routing is misconfigured

# Check route propagation from Virtual Private Gateway
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values=vpc-0a1b2c3d4e5f67890 \
  --query 'RouteTables[*].Routes[?GatewayId!=`local`].{Destination:DestinationCidrBlock,Target:GatewayId,State:State}'

    Azure VNet Peering for SQL Managed Instance

    Azure SQL Managed Instance (not the logical server) requires its own dedicated subnet within a VNet and has strict requirements: the subnet must be delegated to Microsoft.Sql/managedInstances, must have a route table attached, and must have specific NSG rules. Peering from application VNets to the Managed Instance VNet requires the peering to allow gateway transit:

    # Create VNet peering from application VNet to SQL MI VNet
az network vnet peering create \
  --name app-to-sqlmi-peering \
  --resource-group prod-rg \
  --vnet-name app-vnet \
  --remote-vnet /subscriptions/{sub-id}/resourceGroups/prod-rg/virtualNetworks/sqlmi-vnet \
  --allow-vnet-access true \
  --allow-forwarded-traffic true

# Create the reverse peering (required — Azure peering is not automatically bidirectional)
az network vnet peering create \
  --name sqlmi-to-app-peering \
  --resource-group prod-rg \
  --vnet-name sqlmi-vnet \
  --remote-vnet /subscriptions/{sub-id}/resourceGroups/prod-rg/virtualNetworks/app-vnet \
  --allow-vnet-access true \
  --allow-forwarded-traffic true

# Verify peering state — both sides must show "Connected" not "Initiated"
az network vnet peering show \
  --name app-to-sqlmi-peering \
  --resource-group prod-rg \
  --vnet-name app-vnet \
  --query peeringState

    32.5 IAM Authentication vs. Network Authentication: Combining Database and Network Security

    Network controls limit which machines can attempt a connection. Database authentication controls which identities succeed when they do. Production security requires both layers, and the cloud adds a third layer: cloud IAM integration with the database authentication system itself.

    AWS IAM Database Authentication

    RDS and Aurora support IAM authentication as an alternative to password-based logins. Instead of storing a password, the application generates a short-lived authentication token using its AWS IAM identity (an IAM role). The token is valid for 15 minutes and is generated locally using AWS credentials — it never requires a call to an external auth service at connection time, only for token generation.

    The workflow:

    1. Create a database user mapped to IAM

    2. Grant the rds_iam role (Aurora PostgreSQL) or equivalent

    3. Application uses its EC2 instance profile or ECS task role to generate the token

    4. Application connects with the token as the password

    -- PostgreSQL on RDS/Aurora: create IAM-authenticated user
-- Run this as the master user
CREATE USER app_service WITH LOGIN;
GRANT rds_iam TO app_service;

-- Verify the IAM role association
SELECT rolname, rolsuper, rolinherit
FROM pg_roles
WHERE rolname IN ('rds_iam', 'app_service');
    -- SQL Server on RDS: IAM auth uses Windows authentication via Active Directory
-- or certificate-based auth — IAM token auth is PostgreSQL/MySQL-specific
-- For SQL Server, use AD integration instead:
CREATE LOGIN [DOMAIN\app-service-account] FROM WINDOWS;
CREATE USER [DOMAIN\app-service-account] FOR LOGIN [DOMAIN\app-service-account];
ALTER ROLE db_datareader ADD MEMBER [DOMAIN\app-service-account];

    Generating the token from application code (Python example pattern):

    import boto3
import psycopg2

def get_rds_auth_token(host, port, db_user, region):
    """Generate a short-lived IAM auth token for RDS."""
    client = boto3.client('rds', region_name=region)
    token = client.generate_db_auth_token(
        DBHostname=host,
        Port=port,
        DBUsername=db_user,
        Region=region
    )
    return token

def connect_with_iam_auth():
    host = "prod-postgres-01.cluster-xyz.us-east-1.rds.amazonaws.com"
    port = 5432
    db_user = "app_service"
    region = "us-east-1"

    token = get_rds_auth_token(host, port, db_user, region)

    conn = psycopg2.connect(
        host=host,
        port=port,
        database="appdb",
        user=db_user,
        password=token,
        sslmode="verify-full",
        sslrootcert="/etc/ssl/certs/rds-ca-bundle.pem"
    )
    return conn

    Note the sslmode="verify-full" — IAM authentication requires SSL. Without it, the token cannot be validated. This is a hard requirement, not a suggestion, and it means you must distribute the RDS CA certificate bundle to your application hosts.

    AWS IAM Auth: Performance Considerations

    Token generation makes an API call to rds.amazonaws.com. If your application opens many short-lived connections (poor connection pooling, Lambda without RDS Proxy), this adds latency. The solution: use RDS Proxy with IAM auth. The proxy handles token generation and maintains a persistent connection pool. Applications authenticate to the proxy using IAM, and the proxy handles the database connection:

    # Create RDS Proxy with IAM authentication
aws rds create-db-proxy \
  --db-proxy-name prod-postgres-proxy \
  --engine-family POSTGRESQL \
  --auth '[{
    "AuthScheme": "SECRETS",
    "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:prod/postgres/credentials",
    "IAMAuth": "REQUIRED"
  }]' \
  --role-arn arn:aws:iam::123456789012:role/RDSProxyRole \
  --vpc-subnet-ids subnet-0a1b2c3d4e5f67890 subnet-0f9e8d7c6b5a43210 \
  --vpc-security-group-ids sg-rdsproxy-sg-id \
  --require-tls

# Register the RDS cluster with the proxy
aws rds register-db-proxy-targets \
  --db-proxy-name prod-postgres-proxy \
  --db-cluster-identifiers prod-aurora-cluster

    Azure SQL and Azure Active Directory Authentication

    Azure SQL supports three authentication modes: SQL authentication (username/password stored in the database), Azure AD authentication (identities managed by Azure AD), and mixed mode. In production, enforce Azure AD-only:

    # Set Azure AD admin on SQL Server — this enables AAD auth
az sql server ad-admin create \
  --server prod-sql-server \
  --resource-group prod-rg \
  --display-name "DBA-Team" \
  --object-id $(az ad group show --group "DBA-Team" --query id -o tsv)

# Disable SQL (password-based) authentication — Azure AD only
az sql server update \
  --name prod-sql-server \
  --resource-group prod-rg \
  --set administratorLogin="" \
  --minimal-tls-version 1.2

    Creating contained database users mapped to Azure AD identities (managed identities for applications):

    -- Azure SQL: create user for a managed identity (application service principal)
-- Run as Azure AD admin
CREATE USER [my-app-managed-identity] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [my-app-managed-identity];
ALTER ROLE db_datawriter ADD MEMBER [my-app-managed-identity];

-- For a service principal (app registration):
CREATE USER [my-app-registration] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [my-app-registration];

-- Verify contained users
SELECT name, type_desc, authentication_type_desc
FROM sys.database_principals
WHERE type IN ('E', 'X')  -- E=external user, X=external group
ORDER BY name;

    GCP Cloud SQL and IAM Database Authentication

    Cloud SQL PostgreSQL supports IAM database authentication where the Google Cloud IAM identity (service account) maps to a PostgreSQL role:

    # Enable IAM database authentication on Cloud SQL instance
gcloud sql instances patch prod-postgres-instance \
  --project=my-project \
  --database-flags=cloudsql.iam_authentication=on

# Add IAM service account as a Cloud SQL user
gcloud sql users create app-service@my-project.iam.gserviceaccount.com \
  --instance=prod-postgres-instance \
  --project=my-project \
  --type=CLOUD_IAM_SERVICE_ACCOUNT

-- Grant appropriate privileges
GRANT CONNECT ON DATABASE appdb TO "app-service@my-project.iam";
GRANT USAGE ON SCHEMA public TO "app-service@my-project.iam";
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public
  TO "app-service@my-project.iam";

-- For future tables:
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES
  TO "app-service@my-project.iam";

-- Verify the IAM user in pg_roles
SELECT rolname, rolcanlogin
FROM pg_roles
WHERE rolname LIKE '%iam%' OR rolname LIKE '%gserviceaccount%';

    32.6 TLS Enforcement and Certificate Management

    Network isolation prevents unwanted access. TLS encryption protects the data in transit from eavesdropping on the connections that are allowed. For managed cloud databases, you should be enforcing TLS everywhere and verifying certificates, not just encrypting.

    Enforcing TLS on AWS RDS

    RDS PostgreSQL and MySQL use parameter group settings to enforce SSL. Without enforcement, clients can connect unencrypted even when SSL is available:

    # Create a parameter group that enforces SSL for PostgreSQL
aws rds create-db-cluster-parameter-group \
  --db-cluster-parameter-group-name prod-postgres-enforced-ssl \
  --db-parameter-group-family aurora-postgresql15 \
  --description "Forces all connections to use SSL"

# Set rds.force_ssl = 1 (1 = reject non-SSL connections)
aws rds modify-db-cluster-parameter-group \
  --db-cluster-parameter-group-name prod-postgres-enforced-ssl \
  --parameters ParameterName=rds.force_ssl,ParameterValue=1,ApplyMethod=immediate

# Apply to your cluster
aws rds modify-db-cluster \
  --db-cluster-identifier prod-aurora-cluster \
  --db-cluster-parameter-group-name prod-postgres-enforced-ssl \
  --apply-immediately
    -- PostgreSQL: verify SSL is required — check current connections
SELECT pid, usename, application_name, client_addr, ssl, ssl_version, ssl_cipher
FROM pg_stat_ssl
JOIN pg_stat_activity USING (pid)
WHERE backend_type = 'client backend'
ORDER BY ssl, client_addr;

-- SQL Server on RDS: check SSL/TLS for existing connections
SELECT session_id, encrypt_option, net_transport, auth_scheme
FROM sys.dm_exec_connections
ORDER BY encrypt_option;

    Certificate Verification: The Difference Between Encryption and Security

    Using SSL without certificate verification protects against passive eavesdropping but not against man-in-the-middle attacks. Applications should verify the server certificate using the RDS Certificate Authority bundle. AWS periodically rotates CA certificates (the rds-ca-rsa2048-g1 to rds-ca-rsa4096-g1 rotation is an example), and failing to update the CA bundle in applications causes connection failures:

    # Download current RDS CA bundle
curl -o /etc/ssl/certs/global-bundle.pem \
  https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem

# Verify what CA your RDS instance is currently using
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].CACertificateIdentifier'

# Check when the certificate expires
aws rds describe-certificates \
  --certificate-identifier rds-ca-rsa2048-g1 \
  --query 'Certificates[0].{ValidTill:ValidTill,CustomerOverride:CustomerOverride}'

# List all available CA certificates
aws rds describe-certificates \
  --query 'Certificates[*].{ID:CertificateIdentifier,ValidFrom:ValidFrom,ValidTill:ValidTill}' \
  --output table

    For Azure SQL, the DigiCert root CA is used. The connection string must include Encrypt=True;TrustServerCertificate=False; — if TrustServerCertificate=True, certificate verification is bypassed, which is acceptable only in development:

    # Correct production Azure SQL connection string (ADO.NET style)
Server=tcp:prod-sql-server.database.windows.net,1433;
Initial Catalog=appdb;
Authentication=Active Directory Managed Identity;
Encrypt=True;
TrustServerCertificate=False;
Connection Timeout=30;

# Incorrect — TrustServerCertificate=True means no cert verification
Server=tcp:prod-sql-server.database.windows.net,1433;
Initial Catalog=appdb;
User ID=sqladmin;Password=...;
Encrypt=True;
TrustServerCertificate=True;  # DO NOT USE IN PRODUCTION

    Minimum TLS Version Enforcement

    TLS 1.0 and 1.1 have known vulnerabilities. Enforce TLS 1.2 as the minimum everywhere:

    # AWS RDS: enforce minimum TLS via parameter group
# For PostgreSQL, this is controlled by ssl_min_protocol_version
aws rds modify-db-cluster-parameter-group \
  --db-cluster-parameter-group-name prod-postgres-enforced-ssl \
  --parameters ParameterName=ssl_min_protocol_version,ParameterValue=TLSv1.2,ApplyMethod=immediate

# Azure SQL: set minimum TLS version at server level
az sql server update \
  --name prod-sql-server \
  --resource-group prod-rg \
  --minimal-tls-version 1.2

# GCP Cloud SQL: set minimum TLS version
gcloud sql instances patch prod-postgres-instance \
  --project=my-project \
  --database-flags=ssl_min_protocol_version=TLSv1.2

    32.7 Auditing Network Access and Detecting Anomalies

    Configuration is not complete without visibility. You need logs showing who connected from where, and alerts when connection patterns deviate from baseline.

    AWS VPC Flow Logs for Database Traffic

    VPC Flow Logs capture connection-level metadata (source IP, destination IP, port, protocol, accept/reject) for all traffic in your VPC. Enabling them on the database subnets gives you a full record of connection attempts:

    # Enable VPC Flow Logs on database subnets, sending to CloudWatch Logs
aws ec2 create-flow-logs \
  --resource-type Subnet \
  --resource-ids subnet-0a1b2c3d4e5f67890 subnet-0f9e8d7c6b5a43210 \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name /vpc/database-subnet-flow-logs \
  --deliver-logs-permission-arn arn:aws:iam::123456789012:role/VPCFlowLogsRole \
  --log-format '${version} ${account-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status}'

# Query flow logs in CloudWatch Insights for rejected connections to PostgreSQL port
# This reveals port-scanning or misconfigured application connectivity
# (CloudWatch Insights query — run in the console or via CLI)
    # CloudWatch Logs Insights query: rejected connections to port 5432
fields @timestamp, srcaddr, dstaddr, srcport, dstport, action
| filter dstport = 5432 and action = "REJECT"
| stats count(*) as attempts by srcaddr
| sort attempts desc
| limit 20

    RDS Enhanced Monitoring and Connection Tracking

    RDS Enhanced Monitoring, distinct from standard CloudWatch metrics, runs a monitoring agent inside the RDS instance and provides per-process metrics at 1-second granularity. For connection tracking, the CloudWatch metric DatabaseConnections combined with RDS.DBConnections provides aggregate counts. For per-client connection tracking, use the PostgreSQL pg_stat_activity view:

    -- PostgreSQL: connection audit — active connections by client IP and user
SELECT
    client_addr,
    usename,
    application_name,
    state,
    COUNT(*) AS connection_count,
    MAX(EXTRACT(EPOCH FROM (NOW() - state_change))) AS max_idle_seconds
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY client_addr, usename, application_name, state
ORDER BY connection_count DESC;

-- Identify connections from unexpected source addresses
-- Baseline: connections should come only from known application server IPs
SELECT DISTINCT client_addr, usename
FROM pg_stat_activity
WHERE client_addr NOT IN (
    '10.0.1.10',   -- app server 1
    '10.0.1.11',   -- app server 2
    '10.0.2.5'     -- batch processing host
)
AND backend_type = 'client backend';
    -- SQL Server: audit active connections by login and application
SELECT
    login_name,
    host_name,
    program_name,
    client_net_address,
    COUNT(*) AS session_count,
    SUM(CASE WHEN status = 'sleeping' THEN 1 ELSE 0 END) AS idle_sessions
FROM sys.dm_exec_sessions s
JOIN sys.dm_exec_connections c ON s.session_id = c.session_id
WHERE s.is_user_process = 1
GROUP BY login_name, host_name, program_name, client_net_address
ORDER BY session_count DESC;

    Azure SQL Auditing

    Azure SQL has a built-in auditing feature that logs connection events, query executions, and schema changes to Azure Blob Storage, Log Analytics, or Event Hub. Enable it at the server level to cover all databases:

    # Enable Azure SQL auditing to Log Analytics workspace
az sql server audit-policy update \
  --server prod-sql-server \
  --resource-group prod-rg \
  --state Enabled \
  --log-analytics-target-state Enabled \
  --log-analytics-workspace-resource-id \
    /subscriptions/{sub-id}/resourceGroups/prod-rg/providers/Microsoft.OperationalInsights/workspaces/prod-law

# Enable Advanced Threat Protection — detects anomalous connection patterns,
# SQL injection attempts, and access from unusual locations
az sql server threat-policy update \
  --server prod-sql-server \
  --resource-group prod-rg \
  --state Enabled \
  --storage-account prod-audit-storage \
  --email-addresses dba-team@company.com security@company.com \
  --email-account-admins Enabled

    Querying Azure SQL audit logs from Log Analytics:

    // KQL: Failed login attempts to Azure SQL in the last 24 hours
AzureDiagnostics
| where ResourceType == "SERVERS/DATABASES"
| where Category == "SQLSecurityAuditEvents"
| where action_name_s == "LOGIN FAILED"
| where TimeGenerated > ago(24h)
| summarize FailedAttempts = count() by client_ip_s, server_instance_name_s, succeeded_s
| order by FailedAttempts desc

// KQL: Connections from unexpected IP ranges
AzureDiagnostics
| where Category == "SQLSecurityAuditEvents"
| where action_name_s == "LOGIN SUCCEEDED"
| where client_ip_s !startswith "10.0."   // adjust to your private CIDR
| project TimeGenerated, client_ip_s, server_principal_name_s, database_principal_name_s
| order by TimeGenerated desc

    32.8 Network Security Automation and Infrastructure as Code

    Manual security group changes are how security incidents happen. Every network configuration change affecting database access should go through code review, be tracked in version control, and be deployed through CI/CD. This section covers the patterns for automating network security configuration.

    Detecting Security Group Drift

    Configuration drift — when the live environment diverges from what Terraform (or CloudFormation) defines — is the silent enemy of security posture. Terraform plan run against an existing environment will show drift:

    # Run terraform plan to detect any manual changes made outside Terraform
# Output showing changes = drift that needs investigation
cd infrastructure/network
terraform plan -out=plan.out

# For a more targeted audit, use AWS Config rules
# This rule checks that RDS instances are not publicly accessible
aws configservice get-compliance-details-by-config-rule \
  --config-rule-name rds-instance-public-access-check \
  --compliance-types NON_COMPLIANT \
  --query 'EvaluationResults[*].{ResourceId:EvaluationResultIdentifier.EvaluationResultQualifier.ResourceId,Annotation:Annotation}'

    AWS Config Rules for Database Network Security

    AWS Config provides managed rules that continuously evaluate your RDS configuration against defined security policies:

    # Enable key Config rules for database network security
# These rules run continuously and flag non-compliant resources

# Rule 1: RDS must not be publicly accessible
aws configservice put-config-rule \
  --config-rule '{
    "ConfigRuleName": "rds-instance-public-access-check",
    "Source": {
      "Owner": "AWS",
      "SourceIdentifier": "RDS_INSTANCE_PUBLIC_ACCESS_CHECK"
    },
    "Scope": {
      "ComplianceResourceTypes": ["AWS::RDS::DBInstance"]
    }
  }'

# Rule 2: RDS instances must be in a VPC
aws configservice put-config-rule \
  --config-rule '{
    "ConfigRuleName": "rds-instance-deployment-in-vpc",
    "Source": {
      "Owner": "AWS",
      "SourceIdentifier": "RDS_IN_BACKUP_PLAN"
    }
  }'

# Rule 3: No security group should allow unrestricted inbound access
aws configservice put-config-rule \
  --config-rule '{
    "ConfigRuleName": "restricted-common-ports",
    "Source": {
      "Owner": "AWS",
      "SourceIdentifier": "RESTRICTED_INCOMING_TRAFFIC"
    },
    "InputParameters": "{\"blockedPort1\": \"5432\", \"blockedPort2\": \"1433\", \"blockedPort3\": \"3306\"}"
  }'

    Automated Remediation for Security Violations

    Detecting a violation is valuable. Automatically remediating it is better for low-risk, high-confidence rules. For an RDS instance found to have PubliclyAccessible: true, you can configure AWS Config to invoke a Lambda that immediately corrects it:

    # Lambda function: auto-remediate RDS public accessibility violations
import boto3
import json

def lambda_handler(event, context):
    """
    Triggered by AWS Config when an RDS instance is found publicly accessible.
    Immediately sets PubliclyAccessible=False and logs the action.
    """
    config_item = event.get('configurationItem', {})
    resource_id = config_item.get('resourceId')
    resource_type = config_item.get('resourceType')

    if resource_type != 'AWS::RDS::DBInstance':
        return {'statusCode': 200, 'body': 'Not an RDS instance, skipping'}

    rds = boto3.client('rds')

    # Check current state before modifying
    response = rds.describe_db_instances(DBInstanceIdentifier=resource_id)
    instance = response['DBInstances'][0]

    if not instance['PubliclyAccessible']:
        return {'statusCode': 200, 'body': f'{resource_id} already not publicly accessible'}

    # Remediate: disable public accessibility
    rds.modify_db_instance(
        DBInstanceIdentifier=resource_id,
        PubliclyAccessible=False,
        ApplyImmediately=True
    )

    # Log to CloudWatch for audit trail
    print(json.dumps({
        'action': 'remediated_public_rds',
        'instance_id': resource_id,
        'previous_state': 'PubliclyAccessible=True',
        'new_state': 'PubliclyAccessible=False',
        'triggered_by': 'AWS Config auto-remediation'
    }))

    return {
        'statusCode': 200,
        'body': f'Successfully remediated {resource_id}: PubliclyAccessible set to False'
    }

    Terraform Security Group Policy as Code

    For teams using Terraform across multiple environments, a shared module that enforces security group structure prevents permissive rules from being introduced:

    # modules/database-security-group/main.tf
# Reusable module that enforces correct database security group structure

variable "vpc_id" {
  description = "VPC ID where the database security group will be created"
  type        = string
}

variable "allowed_security_group_ids" {
  description = "List of security group IDs allowed to connect to the database"
  type        = list(string)
}

variable "database_port" {
  description = "Database port (5432 for PostgreSQL, 1433 for SQL Server)"
  type        = number
  validation {
    condition     = contains([5432, 1433, 3306, 5439], var.database_port)
    error_message = "Database port must be a known database port (5432, 1433, 3306, 5439)."
  }
}

variable "environment" {
  type = string
}

resource "aws_security_group" "database" {
  name        = "${var.environment}-database-sg"
  description = "Database security group — managed by Terraform, do not modify manually"
  vpc_id      = var.vpc_id

  # No ingress from CIDR ranges — only from specific security groups
  dynamic "ingress" {
    for_each = var.allowed_security_group_ids
    content {
      description     = "Database access from approved security group"
      from_port       = var.database_port
      to_port         = var.database_port
      protocol        = "tcp"
      security_groups = [ingress.value]
    }
  }

  # Egress: minimal — only what the database actually needs outbound
  # RDS needs HTTPS outbound for IAM auth token validation and enhanced monitoring
  egress {
    description = "HTTPS for IAM auth and AWS APIs"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  lifecycle {
    # Prevent accidental deletion of the security group
    prevent_destroy = true
  }

  tags = {
    Name        = "${var.environment}-database-sg"
    Environment = var.environment
    ManagedBy   = "terraform"
    Security    = "database-tier"
  }
}

output "security_group_id" {
  value       = aws_security_group.database.id
  description = "Security group ID for the database tier"
}

    32.9 Common Misconfigurations and How to Find Them

    The security incidents that affect cloud databases almost never involve a sophisticated zero-day exploit. They result from misconfigurations that are entirely preventable. Here is a systematic checklist for auditing your database network security.

    The Audit Checklist

    #!/bin/bash
# Database network security audit script — AWS
# Run this periodically or as part of a CI/CD security gate

echo "=== RDS Network Security Audit ==="
echo ""

echo "--- Checking for publicly accessible RDS instances ---"
aws rds describe-db-instances \
  --query 'DBInstances[?PubliclyAccessible==`true`].{ID:DBInstanceIdentifier,Engine:Engine,PubliclyAccessible:PubliclyAccessible}' \
  --output table

echo ""
echo "--- Checking for RDS instances NOT in a VPC ---"
aws rds describe-db-instances \
  --query 'DBInstances[?DBSubnetGroup==null].{ID:DBInstanceIdentifier,Engine:Engine}' \
  --output table

echo ""
echo "--- Checking for security groups with 0.0.0.0/0 on database ports ---"
for port in 5432 1433 3306 5439 27017; do
  echo "Port $port:"
  aws ec2 describe-security-groups \
    --filters "Name=ip-permission.from-port,Values=$port" \
              "Name=ip-permission.to-port,Values=$port" \
              "Name=ip-permission.cidr,Values=0.0.0.0/0" \
    --query 'SecurityGroups[*].{ID:GroupId,Name:GroupName,VPC:VpcId}' \
    --output table
done

echo ""
echo "--- Checking RDS parameter groups for SSL enforcement ---"
aws rds describe-db-cluster-parameter-groups \
  --query 'DBClusterParameterGroups[*].DBClusterParameterGroupName' \
  --output text | tr '\t' '\n' | while read pgname; do
    ssl_setting=$(aws rds describe-db-cluster-parameters \
      --db-cluster-parameter-group-name "$pgname" \
      --query "Parameters[?ParameterName=='rds.force_ssl'].ParameterValue" \
      --output text)
    echo "Parameter group: $pgname | rds.force_ssl = ${ssl_setting:-not_set}"
done

echo ""
echo "--- Checking for RDS snapshots that are publicly accessible ---"
aws rds describe-db-snapshots \
  --query 'DBSnapshots[?Attribute==`restore` && contains(AttributeValues, `all`)].{ID:DBSnapshotIdentifier,Instance:DBInstanceIdentifier}' \
  --output table 2>/dev/null || \
  aws rds describe-db-snapshots \
    --include-shared \
    --query 'DBSnapshots[?SnapshotType==`public`].{ID:DBSnapshotIdentifier,Instance:DBInstanceIdentifier}' \
    --output table

echo ""
echo "=== Audit complete ==="

    Publicly Accessible Snapshots

    One of the highest-severity misconfigurations that is easy to miss: RDS snapshots can be made public, allowing anyone with an AWS account to copy and restore them. This has been the source of several well-documented data exposures. The audit script above checks for this, but the explicit remediation:

    # Find and remediate public RDS snapshots
aws rds describe-db-snapshots \
  --snapshot-type public \
  --query 'DBSnapshots[*].DBSnapshotIdentifier' \
  --output text | tr '\t' '\n' | while read snapshot_id; do
    echo "Revoking public access from snapshot: $snapshot_id"
    aws rds modify-db-snapshot-attribute \
      --db-snapshot-identifier "$snapshot_id" \
      --attribute-name restore \
      --values-to-remove all
done

    The "Allow Azure Services" Trap

    Already mentioned in section 32.3, but worth repeating because it appears in so many production Azure SQL deployments: the "Allow access to Azure services" toggle in the Azure SQL firewall adds a rule from 0.0.0.0 to 0.0.0.0 that permits any traffic from Azure datacenters. This is often added during initial setup to make connectivity easy, then forgotten. Audit for it:

    # Audit Azure SQL firewall rules — look for the overly permissive rule
az sql server firewall-rule list \
  --server prod-sql-server \
  --resource-group prod-rg \
  --query "[?startIpAddress=='0.0.0.0' || endIpAddress=='255.255.255.255'].{Name:name,Start:startIpAddress,End:endIpAddress}" \
  --output table

# If you see "AllowAllWindowsAzureIps" or 0.0.0.0/255.255.255.255 entries, remove them
az sql server firewall-rule list \
  --server prod-sql-server \
  --resource-group prod-rg \
  --output table

    RDS Subnet Group in Public Subnets

    A subnet group can be created with public subnets (subnets with a route to an internet gateway). If PubliclyAccessible is also set to true, the database gets a public IP. Audit for subnet groups containing public subnets:

    # Check if subnets in DB subnet groups have routes to internet gateway
# First, get all subnet IDs used by DB subnet groups
aws rds describe-db-subnet-groups \
  --query 'DBSubnetGroups[*].Subnets[*].SubnetIdentifier' \
  --output text | tr '\t' '\n' | sort -u | while read subnet_id; do
    # Check if subnet has a route to an internet gateway (0.0.0.0/0 -> igw-*)
    igw_route=$(aws ec2 describe-route-tables \
      --filters "Name=association.subnet-id,Values=$subnet_id" \
      --query "RouteTables[*].Routes[?GatewayId!=null && starts_with(GatewayId,'igw-')].GatewayId" \
      --output text)

    if [ -n "$igw_route" ]; then
      echo "WARNING: Subnet $subnet_id has route to Internet Gateway: $igw_route"
      echo "  This subnet should NOT be used for database instances"
    fi
done

    Key Takeaways

  • → **Network isolation is the first line of defense**: Place all managed database instances in private subnets with no route to an internet gateway, use security groups chained by reference rather than CIDR range, and explicitly audit for `PubliclyAccessible: true` and public snapshot exposure on a scheduled basis — these misconfigurations are the most common source of cloud database exposure.
  • → **Private endpoints require correct DNS to be effective**: Configuring an Azure Private Endpoint, AWS VPC endpoint, or GCP Private Service Connect attachment does nothing for hosts whose DNS resolver does not consult the private DNS zone. Verify name resolution from every network segment — application servers, Lambda functions, containers, and on-premises hosts connected via VPN or Direct Connect — not just from a single representative host.
  • → **Cloud IAM authentication combines network and identity security**: AWS IAM auth tokens, Azure AD managed identity logins, and GCP Cloud SQL IAM authentication eliminate long-lived passwords from application configurations. Pairing IAM auth with RDS Proxy or Azure AD-only mode removes the credential rotation problem entirely and makes the cloud IAM audit trail your authoritative record of who connected and when.
  • → **TLS enforcement means both encryption and certificate verification**: Setting `rds.force_ssl=1` or `Encrypt=True` encrypts the wire but does not prevent a man-in-the-middle attack if the application uses `TrustServerCertificate=True` or skips `sslmode=verify-full`. Distribute CA bundles to application hosts, pin to a minimum TLS version of 1.2 at the server level across all three clouds, and track CA certificate expiration dates in your change calendar.
  • → **Automate detection and remediation of network drift**: Manual security group changes and portal-level firewall modifications that bypass Terraform are how production security posture silently degrades. Use AWS Config managed rules, Azure Policy, or GCP Organization Policies to continuously evaluate compliance, pipe violations into your alerting system, and — for high-confidence rules like RDS public accessibility — trigger automated remediation so the window between misconfiguration and correction is measured in minutes rather than audit cycles.
