Chapter 12: Vertical Scaling Decisions: When to Go Up vs Optimize Queries

Teams that reflexively scale up their RDS or Cloud SQL instances when performance degrades spend an average of 34% more annually on database compute than teams that investigate first. A single vertical scaling decision — moving from an db.r6g.2xlarge ($0.528/hr) to a db.r6g.4xlarge ($1.056/hr) on AWS RDS — adds roughly $4,600 per year before storage or I/O costs are counted. This chapter gives you a structured decision framework to determine whether your workload genuinely needs more compute or whether a targeted query optimization, index addition, connection pooling configuration, or parameter tuning change will recover the same performance for a fraction of the cost. Used consistently, this framework saves most teams between $15,000 and $80,000 annually on database compute alone.

---

12.1 Reading the Signals Correctly: Is This Really a Compute Problem?

The most expensive mistake in database operations is treating a symptom as a diagnosis. High CPU utilization looks like a compute problem. So does high memory pressure. But in most production databases, these conditions originate from query inefficiency, missing indexes, connection storms, or suboptimal buffer pool configuration — none of which are solved by adding vCPUs.

Before any vertical scaling decision moves forward, the following signals must be distinguished from each other.

CPU saturation from compute-bound work means the database is genuinely doing mathematical or procedural work that requires more processor cycles. Examples include complex analytical aggregations, window functions over large result sets, encryption and decryption operations, and procedural language execution. This is the rare case where vertical scaling helps.

CPU saturation from I/O wait means the processor is technically busy but most of that "business" is waiting for disk reads. The CPU metric is misleading — the actual constraint is storage throughput or IOPS. Scaling to a larger instance class does nothing because a larger instance waiting for the same slow disk is still waiting.

CPU saturation from query inefficiency is the most common pattern. A query that performs a sequential scan on a 50-million-row table will consume CPU proportional to the rows it touches, not proportional to what it actually needs to return. Adding a single composite index can drop that query from 12 seconds to 40 milliseconds, reducing CPU utilization by 60% without touching instance size.

Memory pressure from working set size occurs when the database's active data genuinely cannot fit in buffer pool or shared buffers, forcing repeated physical disk reads. This is a legitimate case for vertical scaling — but only after confirming that the buffer pool is tuned to use available memory and that no single runaway query is monopolizing the cache by scanning enormous tables repeatedly.

Memory pressure from connection count is entirely different. Each database connection on PostgreSQL consumes between 5 MB and 10 MB of process memory. One thousand connections consume 5 GB to 10 GB of RAM before a single query executes. This is a pgBouncer problem, not an instance size problem.

The following query identifies which category your current bottleneck falls into by correlating wait event data with query execution patterns.

-- PostgreSQL: Identify top wait events and correlate with specific queries
-- Run this against your RDS PostgreSQL or Aurora PostgreSQL instance
-- Requires pg_stat_activity and pg_stat_statements

WITH active_waits AS (
    SELECT
        wait_event_type,
        wait_event,
        COUNT(*)                            AS sessions_waiting,
        ROUND(COUNT(*) * 100.0 /
            NULLIF(SUM(COUNT(*)) OVER (), 0), 2) AS pct_of_sessions
    FROM pg_stat_activity
    WHERE state = 'active'
      AND wait_event IS NOT NULL
      AND pid <> pg_backend_pid()
    GROUP BY wait_event_type, wait_event
    ORDER BY sessions_waiting DESC
),
expensive_queries AS (
    SELECT
        LEFT(query, 100)                    AS query_preview,
        calls,
        ROUND((total_exec_time / calls)::numeric, 2) AS avg_ms,
        ROUND(total_exec_time::numeric, 2)  AS total_ms,
        rows,
        ROUND((rows::numeric / NULLIF(calls, 0)), 0) AS avg_rows,
        shared_blks_hit,
        shared_blks_read,
        ROUND(
            shared_blks_read * 100.0 /
            NULLIF(shared_blks_hit + shared_blks_read, 0),
        2)                                  AS cache_miss_pct
    FROM pg_stat_statements
    WHERE calls > 50
    ORDER BY total_exec_time DESC
    LIMIT 15
)
SELECT 'WAIT EVENTS' AS section, * FROM active_waits
UNION ALL
SELECT 'TOP QUERIES', NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL
UNION ALL
SELECT 'QUERY', query_preview, calls::text, avg_ms::text,
       total_ms::text, avg_rows::text, NULL, shared_blks_hit::text,
       shared_blks_read::text, cache_miss_pct::text, NULL
FROM expensive_queries;

Interpret the results as follows. If the dominant wait event type is IO (specifically DataFileRead), your bottleneck is storage, not compute. If it is Lock or LWLock, you have contention issues. If it is CPU with no wait events at all, compute pressure may be legitimate. If your top queries show cache miss percentages above 15%, your working set exceeds shared buffers, and you should consider memory before vCPUs.

For SQL Server on Azure SQL or RDS SQL Server, the equivalent diagnostic uses wait statistics:

-- SQL Server: Top wait stats indicating resource pressure type
-- Works on Azure SQL Managed Instance, RDS SQL Server, and self-managed
SELECT TOP 20
    wait_type,
    waiting_tasks_count,
    wait_time_ms,
    max_wait_time_ms,
    signal_wait_time_ms,
    -- signal wait > 25% of total suggests CPU saturation (real compute pressure)
    ROUND(signal_wait_time_ms * 100.0 / NULLIF(wait_time_ms, 0), 2)
                                            AS signal_wait_pct,
    -- Categories to help diagnosis
    CASE
        WHEN wait_type LIKE 'PAGEIO%'         THEN 'Storage I/O Bottleneck'
        WHEN wait_type LIKE 'LATCH%'          THEN 'Memory/Buffer Contention'
        WHEN wait_type LIKE 'LCK_%'           THEN 'Lock Contention'
        WHEN wait_type = 'CXPACKET'           THEN 'Parallelism (check MAXDOP)'
        WHEN wait_type = 'THREADPOOL'         THEN 'Worker Thread Exhaustion'
        WHEN wait_type LIKE 'SOS_SCHEDULER%'  THEN 'CPU Pressure (Legitimate)'
        WHEN wait_type LIKE 'ASYNC_IO%'       THEN 'Async I/O Queue'
        ELSE 'Investigate'
    END                                     AS diagnosis
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN (
    -- Filter out benign background waits
    'SLEEP_TASK', 'BROKER_TO_FLUSH', 'BROKER_TASK_STOP',
    'CLR_AUTO_EVENT', 'DISPATCHER_QUEUE_SEMAPHORE',
    'FT_IFTS_SCHEDULER_IDLE_WAIT', 'HADR_FILESTREAM_IOMGR_IOCOMPLETION',
    'HADR_WORK_QUEUE', 'LAZYWRITER_SLEEP', 'LOGMGR_QUEUE',
    'REQUEST_FOR_DEADLOCK_SEARCH', 'RESOURCE_QUEUE', 'SERVER_IDLE_CHECK',
    'SLEEP_DBSTARTUP', 'SLEEP_DCOMSTARTUP', 'SLEEP_MASTERDBREADY',
    'SLEEP_MASTERMDREADY', 'SLEEP_MASTERUPGRADED', 'SLEEP_MSDBSTARTUP',
    'SLEEP_SYSTEMTASK', 'SLEEP_TEMPDBSTARTUP', 'SNI_HTTP_ACCEPT',
    'SP_SERVER_DIAGNOSTICS_SLEEP', 'SQLTRACE_BUFFER_FLUSH',
    'WAITFOR', 'XE_DISPATCHER_WAIT', 'XE_TIMER_EVENT'
)
ORDER BY wait_time_ms DESC;

When SOS_SCHEDULER_SLEEP dominates and signal_wait_pct exceeds 25%, you have real CPU pressure. Everything else requires targeted remediation before instance resizing.

12.2 The Cost of Getting It Wrong: Pricing Math Across AWS, Azure, and GCP

Vertical scaling decisions are budget decisions. Before any discussion of remediation, the DBA and the engineering leadership need to understand the actual cost delta of scaling decisions. These numbers are not theoretical — they appear on your bill every month.

AWS RDS PostgreSQL pricing (us-east-1, Multi-AZ, On-Demand, 2024 rates):

| Instance Class | vCPUs | RAM | $/hr | $/month | $/year |

|---|---|---|---|---|---|

| db.t4g.medium | 2 | 4 GB | $0.068 | $49 | $595 |

| db.r6g.large | 2 | 16 GB | $0.240 | $173 | $2,102 |

| db.r6g.xlarge | 4 | 32 GB | $0.480 | $346 | $4,205 |

| db.r6g.2xlarge | 8 | 64 GB | $0.960 | $691 | $8,409 |

| db.r6g.4xlarge | 16 | 128 GB | $1.920 | $1,382 | $16,819 |

| db.r6g.8xlarge | 32 | 256 GB | $3.840 | $2,765 | $33,638 |

Every step up the r6g ladder exactly doubles your compute cost. The question this chapter answers is: which of those steps actually buys you performance, and which ones are just buying comfort?

Azure SQL Database (General Purpose, 8 vCores vs 16 vCores, East US):

Moving from 8 vCores ($1.1424/hr) to 16 vCores ($2.2848/hr) costs $9,989 more per year. Azure Hyperscale at 16 vCores runs $14,965/year just in compute, before storage.

Google Cloud SQL PostgreSQL (us-central1):

Moving from db-custom-8-32768 ($0.5290/hr, 8 vCPUs, 32 GB) to db-custom-16-65536 ($1.0580/hr) costs $4,638 more per year. Cloud SQL for PostgreSQL Enterprise Plus at 16 vCPUs approaches $1.40/hr, or $12,264/year.

These are the numbers that make query optimization worth the effort. A developer spending two weeks optimizing a slow query at $200,000 annual fully-loaded salary costs roughly $7,700. If that optimization prevents a vertical scaling event that would have cost $9,000 per year, it pays for itself in under 13 months — and the savings compound every subsequent year.

The following script pulls your actual RDS spend over the last 90 days using the AWS Cost Explorer API and projects what your bill would look like if you could reduce average CPU utilization by 30%, which typically allows a downgrade of one instance size tier.

#!/bin/bash
# Script: rds_cost_analysis.sh
# Purpose: Pull RDS compute costs and model downgrade savings
# Prerequisites: AWS CLI configured, jq installed
# Schedule: Run weekly via cron or EventBridge

set -euo pipefail

REGION="${AWS_DEFAULT_REGION:-us-east-1}"
END_DATE=$(date +%Y-%m-%d)
START_DATE=$(date -d "90 days ago" +%Y-%m-%d 2>/dev/null || \
             date -v-90d +%Y-%m-%d)  # macOS fallback

echo "=== RDS Cost Analysis: ${START_DATE} to ${END_DATE} ==="
echo ""

# Fetch RDS costs grouped by instance type tag
aws ce get-cost-and-usage \
    --time-period Start="${START_DATE}",End="${END_DATE}" \
    --granularity MONTHLY \
    --filter '{
        "Dimensions": {
            "Key": "SERVICE",
            "Values": ["Amazon Relational Database Service"]
        }
    }' \
    --group-by '[
        {"Type": "DIMENSION", "Key": "USAGE_TYPE"}
    ]' \
    --metrics "BlendedCost" "UsageQuantity" \
    --output json > /tmp/rds_costs_raw.json

echo "--- Top RDS Usage Types by Cost (Last 90 Days) ---"
jq -r '
  .ResultsByTime[].Groups[]
  | select(.Metrics.BlendedCost.Amount | tonumber > 10)
  | "\(.Keys[0])\t$\(.Metrics.BlendedCost.Amount | tonumber | . * 100 | round / 100)"
' /tmp/rds_costs_raw.json | sort -t'$' -k2 -rn | head -20

# Fetch CloudWatch average CPU for all RDS instances
echo ""
echo "--- Average CPU Utilization by RDS Instance (Last 14 Days) ---"
aws rds describe-db-instances \
    --region "${REGION}" \
    --query 'DBInstances[*].[DBInstanceIdentifier,DBInstanceClass,MultiAZ,Engine]' \
    --output text | while IFS=$'\t' read -r db_id db_class multi_az engine; do

    CPU_AVG=$(aws cloudwatch get-metric-statistics \
        --namespace AWS/RDS \
        --metric-name CPUUtilization \
        --dimensions Name=DBInstanceIdentifier,Value="${db_id}" \
        --start-time "$(date -d '14 days ago' -Iseconds 2>/dev/null || \
                        date -v-14d -Iseconds)" \
        --end-time "$(date -Iseconds)" \
        --period 86400 \
        --statistics Average \
        --query 'sort_by(Datapoints,&Timestamp)[-1].Average' \
        --output text 2>/dev/null || echo "N/A")

    # Flag instances below 25% average CPU as candidates for downsizing
    if [[ "${CPU_AVG}" != "N/A" && "${CPU_AVG}" != "None" ]]; then
        CPU_INT=$(echo "${CPU_AVG}" | awk '{printf "%.0f", $1}')
        FLAG=""
        if (( CPU_INT < 25 )); then
            FLAG="  <-- DOWNSIZE CANDIDATE"
        fi
        printf "%-40s %-20s %-8s %-10s CPU:%.1f%%%s\n" \
            "${db_id}" "${db_class}" "${multi_az}" "${engine}" \
            "${CPU_AVG}" "${FLAG}"
    fi
done

# Compute Optimizer recommendations
echo ""
echo "--- AWS Compute Optimizer RDS Recommendations ---"
aws compute-optimizer get-rds-database-recommendations \
    --region "${REGION}" \
    --output json 2>/dev/null | \
jq -r '
  .rdsDBRecommendations[]?
  | select(.finding == "Overprovisioned")
  | "\(.resourceArn | split(":")[6])\t\(.currentDBInstanceClass)\t-->\t\(.recommendationOptions[0].dbInstanceClass)\tSaving: $\(.recommendationOptions[0].estimatedMonthlySavings.value // "N/A")"
' | column -t || echo "  (No Compute Optimizer recommendations available — ensure it is enabled)"

echo ""
echo "Analysis complete. Review DOWNSIZE CANDIDATES above before any instance changes."

Run this script weekly. When an instance appears consistently below 25% average CPU over 14 days, it is a downgrade candidate, not an upgrade candidate.

12.3 Query Optimization Before Vertical Scaling: The Technical Playbook

When wait event analysis reveals that CPU pressure stems from inefficient queries rather than from legitimate compute-bound work, the remediation sequence is: identify → analyze → fix → measure → decide. Vertical scaling remains an option throughout this process but is deferred until the optimization ceiling is reached.

Step 1: Identify the highest-cost queries by CPU contribution

PostgreSQL's pg_stat_statements extension (enabled by default on RDS PostgreSQL) provides cumulative execution statistics. The critical metric for CPU-driven cost is total_exec_time — this is wall-clock time the database spent on each query across all calls.

-- PostgreSQL: CPU cost ranking with optimization opportunity scoring
-- Reset stats periodically: SELECT pg_stat_statements_reset();
-- Run after collecting at least 1 hour of production traffic

SELECT
    pss.queryid,
    LEFT(pss.query, 120)                        AS query_preview,
    pss.calls,
    ROUND(pss.total_exec_time::numeric / 1000, 2)
                                                AS total_exec_sec,
    ROUND((pss.total_exec_time / pss.calls)::numeric, 2)
                                                AS avg_exec_ms,
    ROUND(pss.rows::numeric / NULLIF(pss.calls, 0), 0)
                                                AS avg_rows_returned,

    -- Estimated CPU cost contribution as % of all query time
    ROUND(pss.total_exec_time * 100.0 /
        SUM(pss.total_exec_time) OVER (), 2)    AS pct_total_cpu,

    -- Buffer efficiency: high read ratio = missing index or large scan
    pss.shared_blks_hit + pss.shared_blks_read  AS total_blks_accessed,
    ROUND(pss.shared_blks_read * 100.0 /
        NULLIF(pss.shared_blks_hit + pss.shared_blks_read, 0), 2)
                                                AS physical_read_pct,

    -- Rows vs blocks: low rows per block access = inefficient access pattern
    CASE
        WHEN pss.shared_blks_read > 10000
         AND pss.rows < pss.shared_blks_read * 5
            THEN 'MISSING INDEX LIKELY'
        WHEN pss.total_exec_time / NULLIF(pss.calls, 0) > 5000
         AND pss.rows < 1000
            THEN 'SINGLE QUERY VERY SLOW'
        WHEN pss.calls > 10000
         AND pss.total_exec_time / NULLIF(pss.calls, 0) > 100
            THEN 'HIGH FREQUENCY + SLOW'
        WHEN pss.total_exec_time * 100.0 /
             NULLIF(SUM(pss.total_exec_time) OVER (), 0) > 10
            THEN 'HIGH TOTAL CPU SHARE'
        ELSE 'REVIEW IF IN TOP 10'
    END                                         AS optimization_signal,

    -- Temp file usage indicates sort/hash spill to disk
    pss.temp_blks_written,
    CASE WHEN pss.temp_blks_written > 1000
         THEN 'SORT SPILL - TUNE work_mem'
         ELSE '' END                            AS memory_signal

FROM pg_stat_statements pss
JOIN pg_database pd ON pd.oid = pss.dbid
WHERE pd.datname = current_database()
  AND pss.calls >= 10
  AND pss.total_exec_time > 1000  -- At least 1 second total execution time
ORDER BY pss.total_exec_time DESC
LIMIT 25;

Step 2: Analyze execution plans for the top offenders

Once the top queries are identified, execution plan analysis reveals what is actually happening. The key markers in PostgreSQL EXPLAIN (ANALYZE, BUFFERS) output that signal optimization headroom rather than compute need:

  • → `Seq Scan` on a large table where a selective `WHERE` clause exists → missing index
  • → `Sort` operations with large `Memory Usage` values exceeding `work_mem` → increasing `work_mem` for that session or globally can eliminate disk spills
  • → `Hash Join` with very large `Batches: N` values → hash spill to disk, increase `work_mem`
  • → Nested loop joins over large sets → join order or index issues
  • → High `rows=X` estimates that are wildly inaccurate compared to `actual rows=Y` → stale statistics, run `ANALYZE`

    • Step 3: Apply targeted fixes in order of effort-to-impact

    The following sequence resolves the majority of CPU pressure issues without instance resizing, ordered from fastest to most time-intensive:

    1. Update statistics — ANALYZE tablename or ANALYZE VERBOSE. Free, takes seconds, can immediately improve plan quality. On RDS, autovacuum handles this but may lag behind rapid data changes.

    2. Add missing indexes — Use the query from Step 1 to find high physical_read_pct queries, then EXPLAIN ANALYZE to confirm sequential scans on selective predicates. Creating a CONCURRENTLY index has zero downtime impact on PostgreSQL.

    3. Tune work_mem — Queries with temp_blks_written > 0 are spilling sorts or hash joins to disk. SET work_mem = '64MB' at the session level for specific heavy queries, or set it globally if most connections run large analytical queries. Caution: work_mem is per-sort-operation per connection, so multiplying by connection count before setting globally is necessary to avoid OOM.

    4. Connection pooling via pgBouncer — If memory pressure is connection-driven (see 12.1), deploying pgBouncer in transaction mode in front of your RDS instance can reduce active backend connections from 800 to 50 while handling identical throughput. This frequently recovers 4–8 GB of RAM, which may entirely eliminate the need for a memory upgrade.

    5. Rewrite pathological queries — Queries returning 500,000 rows to an application that filters them in code should be rewritten to push that filter into the database. This is a development task but has the highest ceiling for improvement.
