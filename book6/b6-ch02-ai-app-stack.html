Chapter 2 of 40 AI-Native Apps on PostgreSQL

Chapter 2: The AI Application Stack: LLM + Vector + Relational Together

Modern AI applications are not single-layer systems. A chatbot that just calls an LLM and returns text will fail in production — it has no memory, no grounding in your actual data, no access controls, and no audit trail. The applications that work — the ones users trust and businesses depend on — layer three capabilities on top of each other: language model reasoning, semantic vector search, and relational data management. This chapter shows you how those three layers fit together architecturally, how PostgreSQL sits at the center of all of them, and how to build the concrete schemas and service patterns that make the whole stack function as a coherent system.

---

The Three-Layer Architecture

Before writing a single line of code, you need a clear mental model of what each layer does and why you cannot skip any of them.

The language model layer handles reasoning, generation, and language understanding. The LLM reads context and produces text — answers, summaries, structured output, tool call decisions. What the LLM cannot do is remember anything between calls, query your database, or know what happened in your system an hour ago. Every capability beyond raw language generation must be injected as context.

The vector layer handles semantic retrieval. When a user asks a question in natural language, keyword search fails because the question uses different words than the documents. Vector embeddings convert text into high-dimensional numerical representations where semantic similarity becomes geometric proximity. You retrieve relevant chunks not by keyword but by meaning. pgvector brings this capability directly into PostgreSQL as a native index type.

The relational layer handles everything else — and everything else turns out to be most of your application. User identity and authentication. Conversation history and session state. Document metadata and access permissions. Audit logs and compliance records. Structured product catalogs, customer records, orders, and configurations. The relationships between all of these entities. The transactional guarantees that keep them consistent.

The insight that makes PostgreSQL uniquely powerful here is that these three layers do not have to live in three separate systems. pgvector makes PostgreSQL a vector store. JSONB makes it a document store. The relational engine makes it a transactional system. You get all three — with joins, transactions, row-level security, and a thirty-year-old query planner — in a single database.

Here is the architectural reality compared to the "polyglot" alternative:

Polyglot Stack:                         PostgreSQL Stack:
─────────────────                       ────────────────────────────────
LLM API (OpenAI/Anthropic)              LLM API (OpenAI/Anthropic)
     │                                       │
Pinecone (vectors)   ←── sync? ──→     PostgreSQL
Postgres (relational)                    ├── pgvector (semantic search)
Redis (sessions)                         ├── JSONB (document storage)
Elasticsearch (search)                   ├── relational tables (everything)
     │                                   ├── pg_notify (events)
4 systems to operate,                    └── row-level security (access)
4 consistency models,
4 failure domains                        1 system. ACID everywhere.

This is not religious preference. It is operational economics. Every additional system multiplies your failure surface, your operational burden, and your consistency complexity. For most AI applications — including high-scale production ones — PostgreSQL as the unified data layer is the right architecture.

Schema Design: The Foundation Tables

The schema for an AI application has a recognizable shape regardless of what the application does. You will always need tables for users, conversations, messages, documents, embeddings, and audit events. Getting these right at the start saves you from painful migrations later.

-- Enable required extensions
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS pg_trgm;  -- for hybrid search

-- Core user and tenant management
-- ─────────────────────────────────────────────────────────

CREATE TABLE tenants (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    settings        JSONB NOT NULL DEFAULT '{}',

);

-- Conversation and message history

CREATE TABLE conversations (

CREATE INDEX idx_conversations_user_id ON conversations(user_id, created_at DESC);
CREATE INDEX idx_conversations_tenant_id ON conversations(tenant_id, status);

CREATE TABLE messages (

    latency_ms      INTEGER,        -- how long the LLM took

    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_messages_conversation_id ON messages(conversation_id, created_at ASC);
CREATE INDEX idx_messages_created_at ON messages(created_at DESC);

-- Document storage and embedding tables
-- ─────────────────────────────────────────────────────────

CREATE TABLE document_collections (

    embedding_model TEXT NOT NULL DEFAULT 'text-embedding-3-small',

    chunk_strategy  JSONB NOT NULL DEFAULT '{"size": 512, "overlap": 64}',
    document_count  INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (tenant_id, name)
);

CREATE TABLE documents (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    collection_id   UUID NOT NULL REFERENCES document_collections(id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    title           TEXT NOT NULL,
    source_uri      TEXT,           -- s3://, https://, file://, etc.
    source_type     TEXT NOT NULL DEFAULT 'text',  -- 'pdf', 'markdown', 'html', 'sql'
    content_hash    TEXT NOT NULL,  -- SHA-256 for deduplication
    raw_content     TEXT,           -- original text (may be large)
    metadata        JSONB NOT NULL DEFAULT '{}',  -- author, date, tags, etc.
    status          TEXT NOT NULL DEFAULT 'pending'
                        CHECK (status IN ('pending', 'processing', 'indexed', 'failed')),
    error_message   TEXT,
    chunk_count     INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    indexed_at      TIMESTAMPTZ,
    UNIQUE (collection_id, content_hash)
);

CREATE INDEX idx_documents_collection_status ON documents(collection_id, status);
CREATE INDEX idx_documents_tenant_id ON documents(tenant_id);
CREATE INDEX idx_documents_metadata ON documents USING GIN(metadata);

CREATE TABLE document_chunks (
    id              UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    document_id     UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    collection_id   UUID NOT NULL REFERENCES document_collections(id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    chunk_index     INTEGER NOT NULL,  -- position within document
    content         TEXT NOT NULL,
    content_tokens  INTEGER,
    embedding       vector(1536),      -- pgvector column
    embedding_model TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    metadata        JSONB NOT NULL DEFAULT '{}',  -- inherited + chunk-specific
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (document_id, chunk_index)
);

-- HNSW index for fast approximate nearest neighbor search
CREATE INDEX idx_chunks_embedding ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Full-text search index for hybrid retrieval
CREATE INDEX idx_chunks_content_fts ON document_chunks
    USING GIN(to_tsvector('english', content));

-- Tenant-scoped retrieval index
CREATE INDEX idx_chunks_tenant_collection ON document_chunks(tenant_id, collection_id);

-- ─────────────────────────────────────────────────────────
-- Audit and observability
-- ─────────────────────────────────────────────────────────

CREATE TABLE ai_audit_log (
    id              BIGSERIAL,
    tenant_id       UUID REFERENCES tenants(id),
    user_id         UUID REFERENCES users(id),
    conversation_id UUID REFERENCES conversations(id),
    event_type      TEXT NOT NULL,  -- 'message', 'retrieval', 'tool_call', 'error'
    model           TEXT,
    input_tokens    INTEGER,
    output_tokens   INTEGER,
    cost_usd        NUMERIC(10, 6),
    latency_ms      INTEGER,
    retrieval_count INTEGER,        -- how many chunks were retrieved
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- partition key column, so (id) alone is rejected by Postgres here.

) PARTITION BY RANGE (created_at);

-- Monthly partitions for audit log
CREATE TABLE ai_audit_log_2025_01 PARTITION OF ai_audit_log
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
CREATE TABLE ai_audit_log_2025_02 PARTITION OF ai_audit_log
    FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

-- ─────────────────────────────────────────────────────────

ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON conversations
    USING (tenant_id = current_setting('app.tenant_id')::UUID);

CREATE POLICY tenant_isolation ON messages
    USING (conversation_id IN (
        SELECT id FROM conversations
        WHERE tenant_id = current_setting('app.tenant_id')::UUID
    ));

CREATE POLICY tenant_isolation ON document_chunks
    USING (tenant_id = current_setting('app.tenant_id')::UUID);

Notice what this schema does beyond just storing text. The messages table records cost and latency per LLM call — you need this for billing and SLA monitoring. The document_chunks table carries both a vector embedding and a full-text search index — you need both for production retrieval quality. The audit log partitions by month — you need this when the table hits hundreds of millions of rows. Row-level security enforces tenant isolation at the database level — no amount of application bugs can leak one tenant's data to another.

Implementation: The RAG Retrieval Pipeline

Retrieval-augmented generation is the workhorse pattern for grounding LLM responses in real data. The implementation has four steps: embed the query, retrieve relevant chunks, assemble a context window, and call the LLM. PostgreSQL is the active participant in steps two and three.

graph TD
    U[User message] --> Save1[Save user message]
    Save1 --> Ret["Hybrid retrieval: vector + full-text, RRF-fused"]
    Ret --> Hist[Load conversation history]
    Hist --> Assemble["Assemble system prompt + retrieved context + history"]
    Assemble --> LLM[Call Claude]
    LLM --> Save2[Save assistant message]
    Save2 --> Audit[(Write ai_audit_log entry)]
    Audit --> Resp[Return response + sources]

*rag_chat_turn walks through all seven steps in order — every stage before and after the LLM call reads or writes PostgreSQL.*

# rag_pipeline.py
# Full RAG pipeline using pgvector + OpenAI + Anthropic
# Requirements: psycopg2-binary, openai, anthropic, fastapi

import hashlib
import time
from typing import Optional
from uuid import UUID

import anthropic
import openai
import psycopg2
from psycopg2.extras import RealDictCursor, execute_values

# ─────────────────────────────────────────────────────────
# Database connection (use PgBouncer DSN in production)
# ─────────────────────────────────────────────────────────

def get_db_connection(tenant_id: str):
    """
    In production this comes from a connection pool (PgBouncer).
    We set app.tenant_id so RLS policies fire correctly.
    """
    conn = psycopg2.connect(
        host="pgbouncer",          # PgBouncer sits in front of Postgres
        port=6432,
        dbname="aiapp",
        user="app_user",
        password="...",
    )
    with conn.cursor() as cur:
        # Activate RLS for this tenant
        cur.execute("SET app.tenant_id = %s", (str(tenant_id),))
    return conn


# ─────────────────────────────────────────────────────────
# Embedding generation
# ─────────────────────────────────────────────────────────

openai_client = openai.OpenAI()
anthropic_client = anthropic.Anthropic()

def embed_text(text: str, model: str = "text-embedding-3-small") -> list[float]:
    """Generate an embedding vector for a piece of text."""
    response = openai_client.embeddings.create(
        model=model,
        input=text.replace("\n", " "),  # normalize whitespace
    )
    return response.data[0].embedding


# ─────────────────────────────────────────────────────────
# Hybrid retrieval: vector + full-text search with RRF
# ─────────────────────────────────────────────────────────

HYBRID_SEARCH_SQL = """
WITH vector_search AS (
    SELECT
        dc.id,
        dc.document_id,
        dc.content,
        dc.metadata,
        dc.chunk_index,
        d.title        AS document_title,
        d.source_uri,
        1 - (dc.embedding <=> %s::vector) AS vector_score,
        ROW_NUMBER() OVER (ORDER BY dc.embedding <=> %s::vector) AS vector_rank
    FROM document_chunks dc
    JOIN documents d ON d.id = dc.document_id
    WHERE dc.tenant_id = current_setting('app.tenant_id')::UUID
      AND dc.collection_id = ANY(%s::UUID[])
      AND dc.embedding IS NOT NULL
    ORDER BY dc.embedding <=> %s::vector
    LIMIT 40
),
fts_search AS (
    SELECT
        dc.id,
        dc.document_id,
        dc.content,
        dc.metadata,
        dc.chunk_index,
        d.title        AS document_title,
        d.source_uri,
        ts_rank_cd(to_tsvector('english', dc.content), query) AS fts_score,
        ROW_NUMBER() OVER (
            ORDER BY ts_rank_cd(to_tsvector('english', dc.content), query) DESC
        ) AS fts_rank
    FROM document_chunks dc
    JOIN documents d ON d.id = dc.document_id,
         plainto_tsquery('english', %s) query
    WHERE dc.tenant_id = current_setting('app.tenant_id')::UUID
      AND dc.collection_id = ANY(%s::UUID[])
      AND to_tsvector('english', dc.content) @@ query
    ORDER BY fts_score DESC
    LIMIT 40
),
-- Reciprocal Rank Fusion combines both result sets
rrf_scores AS (
    SELECT
        COALESCE(v.id, f.id)                       AS id,
        COALESCE(v.document_id, f.document_id)     AS document_id,
        COALESCE(v.content, f.content)             AS content,
        COALESCE(v.metadata, f.metadata)           AS metadata,
        COALESCE(v.chunk_index, f.chunk_index)     AS chunk_index,
        COALESCE(v.document_title, f.document_title) AS document_title,
        COALESCE(v.source_uri, f.source_uri)       AS source_uri,
        COALESCE(v.vector_score, 0)                AS vector_score,
        COALESCE(f.fts_score, 0)                   AS fts_score,
        -- RRF formula: 1/(k + rank) summed across result sets
        COALESCE(1.0 / (60 + v.vector_rank), 0) +
        COALESCE(1.0 / (60 + f.fts_rank), 0)      AS rrf_score
    FROM vector_search v
    FULL OUTER JOIN fts_search f ON v.id = f.id
)
SELECT *
FROM rrf_scores
ORDER BY rrf_score DESC
LIMIT %s;
"""

def retrieve_chunks(
    conn,
    query: str,
    collection_ids: list[str],
    top_k: int = 8,
) -> list[dict]:
    """
    Hybrid retrieval combining vector similarity and full-text search
    using Reciprocal Rank Fusion.
    """
    query_embedding = embed_text(query)
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

    with conn.cursor(cursor_factory=RealDictCursor) as cur:
        cur.execute(
            HYBRID_SEARCH_SQL,
            (
                embedding_str,  # vector search embedding (first occurrence)
                embedding_str,  # for ORDER BY
                collection_ids, # allowed collections
                embedding_str,  # for ORDER BY in CTE
                query,          # FTS query text
                collection_ids, # allowed collections (FTS)
                top_k,
            ),
        )
        return [dict(row) for row in cur.fetchall()]


# ─────────────────────────────────────────────────────────
# Context assembly and LLM call
# ─────────────────────────────────────────────────────────

def format_context(chunks: list[dict]) -> str:
    """Build the context block that goes into the LLM prompt."""
    sections = []
    for i, chunk in enumerate(chunks, 1):
        source = chunk.get("document_title", "Unknown")
        if chunk.get("source_uri"):
            source += f" ({chunk['source_uri']})"
        sections.append(
            f"[Source {i}: {source}]\n{chunk['content']}"
        )
    return "\n\n---\n\n".join(sections)


def load_conversation_history(conn, conversation_id: str) -> list[dict]:
    """Load recent messages for a conversation — the LLM's working memory."""
    with conn.cursor(cursor_factory=RealDictCursor) as cur:
        cur.execute(
            """
            SELECT role, content, tool_calls, tool_call_id
            FROM (
                -- Take the 20 most recent rows first, then re-sort them
                -- chronologically — ORDER BY ... ASC LIMIT 20 alone would
                -- return the OLDEST 20 messages, not the most recent ones.
                SELECT role, content, tool_calls, tool_call_id, created_at
                FROM messages
                WHERE conversation_id = %s
                ORDER BY created_at DESC
                -- In production, use token counting and trim intelligently
                LIMIT 20
            ) recent
            ORDER BY created_at ASC
            """,
            (conversation_id,),
        )
        rows = cur.fetchall()

    messages = []
    for row in rows:
        msg: dict = {"role": row["role"], "content": row["content"]}
        if row["tool_calls"]:
            msg["tool_calls"] = row["tool_calls"]  # JSONB → dict
        if row["tool_call_id"]:
            msg["tool_call_id"] = row["tool_call_id"]
        messages.append(msg)
    return messages


def save_message(conn, conversation_id: str, role: str, content: str,
                 model: str = None, latency_ms: int = None,
                 input_tokens: int = None, output_tokens: int = None) -> str:
    """Persist a message and update conversation counters atomically."""
    # Rough cost estimate for claude-3-5-sonnet
    cost_usd = None
    if input_tokens and output_tokens:
        cost_usd = (input_tokens * 3.0 + output_tokens * 15.0) / 1_000_000

    with conn.cursor() as cur:
        cur.execute(
            """
            INSERT INTO messages
                (conversation_id, role, content, model, latency_ms, cost_usd)
            VALUES (%s, %s, %s, %s, %s, %s)
            RETURNING id
            """,
            (conversation_id, role, content, model, latency_ms, cost_usd),
        )
        message_id = cur.fetchone()[0]

        # Update conversation counters and last_message_at
        cur.execute(
            """
            UPDATE conversations
            SET message_count = message_count + 1,
                token_count   = token_count + COALESCE(%s, 0) + COALESCE(%s, 0),
                last_message_at = NOW(),
                updated_at    = NOW()
            WHERE id = %s
            """,
            (input_tokens, output_tokens, conversation_id),
        )
    conn.commit()
    return str(message_id)


# ─────────────────────────────────────────────────────────
# The full RAG turn
# ─────────────────────────────────────────────────────────

def rag_chat_turn(
    tenant_id: str,
    user_id: str,
    conversation_id: str,
    collection_ids: list[str],
    user_message: str,
    system_prompt: Optional[str] = None,
) -> dict:
    """
    A single RAG chat turn:
    1. Save the user message
    2. Retrieve relevant chunks
    3. Load conversation history
    4. Call Claude with context
    5. Save the assistant message
    6. Return the response with sources
    """
    conn = get_db_connection(tenant_id)
    start_time = time.time()

    try:
        # Step 1: Save the user message
        save_message(conn, conversation_id, "user", user_message)

        # Step 2: Retrieve relevant chunks via hybrid search
        chunks = retrieve_chunks(conn, user_message, collection_ids, top_k=8)
        context_text = format_context(chunks)

        # Step 3: Load conversation history
        history = load_conversation_history(conn, conversation_id)

        # Step 4: Assemble the prompt
        default_system = (
            "You are a helpful assistant. Answer questions based on the provided "
            "context. If the answer is not in the context, say so clearly rather "
            "than speculating. Cite sources by their [Source N] label."
        )
        system = system_prompt or default_system

        # Build messages list: history + new user message with context injected
        # We inject context into the final user message, not the system prompt,
        # so the model can clearly attribute which context it used.
        messages = history[:-1] if history else []  # exclude last user msg we already have
        messages.append({
            "role": "user",
            "content": (
                f"Context from knowledge base:\n\n{context_text}\n\n"
                f"---\n\nQuestion: {user_message}"
            )
        })

        # Step 5: Call the LLM
        llm_start = time.time()
        response = anthropic_client.messages.create(
            model="claude-3-5-sonnet-20241022",
            max_tokens=2048,
            system=system,
            messages=messages,
        )
        latency_ms = int((time.time() - llm_start) * 1000)

        assistant_text = response.content[0].text
        input_tokens = response.usage.input_tokens
        output_tokens = response.usage.output_tokens

        # Step 6: Save assistant response
        save_message(
            conn,
            conversation_id,
            "assistant",
            assistant_text,
            model="claude-3-5-sonnet-20241022",
            latency_ms=latency_ms,
            input_tokens=input_tokens,
            output_tokens=output_tokens,
        )

        # Step 7: Write audit log entry
        with conn.cursor() as cur:
            cur.execute(
                """
                INSERT INTO ai_audit_log
                    (tenant_id, user_id, conversation_id, event_type,
                     model, input_tokens, output_tokens, latency_ms,
                     retrieval_count, metadata)
                VALUES (%s, %s, %s, 'message', %s, %s, %s, %s, %s, %s)
                """,
                (
                    tenant_id, user_id, conversation_id,
                    "claude-3-5-sonnet-20241022",
                    input_tokens, output_tokens, latency_ms,
                    len(chunks),
                    {"rrf_scores": [c["rrf_score"] for c in chunks]},
                ),
            )
        conn.commit()

        return {
            "response": assistant_text,
            "sources": [
                {
                    "title": c["document_title"],
                    "source_uri": c["source_uri"],
                    "chunk_index": c["chunk_index"],
                    "rrf_score": float(c["rrf_score"]),
                    "vector_score": float(c["vector_score"]),
                }
                for c in chunks
            ],
            "usage": {
                "input_tokens": input_tokens,
                "output_tokens": output_tokens,
                "latency_ms": latency_ms,
            },
        }

    finally:
        conn.close()

The retrieval SQL deserves close attention. The hybrid approach uses two separate CTEs — one for vector search and one for full-text search — then combines them using Reciprocal Rank Fusion. RRF is the right default fusion strategy because it is robust to score scale differences: vector similarity scores and BM25-style text ranking scores use completely different scales, so you cannot simply add them. RRF converts both to rank-based scores (1/(k + rank)) that are comparable regardless of the underlying metric.

The constant k=60 in the RRF formula is a tunable parameter. Lower values weight top-ranked results more aggressively; higher values distribute credit more evenly across the rank list. The value 60 is a common starting point from information retrieval literature, but you should tune it against your own query distribution once you have enough usage data.

Document Ingestion Pipeline

RAG is only as good as what you ingest. A poorly chunked document collection produces retrieval results that look superficially relevant but fail to actually answer questions. The ingestion pipeline needs to handle chunking, deduplication, and error recovery.

# ingestion.py
# Document ingestion pipeline with chunking and deduplication

import hashlib
from typing import Iterator

import psycopg2
from psycopg2.extras import execute_values


# ─────────────────────────────────────────────────────────
# Text chunking
# ─────────────────────────────────────────────────────────

def chunk_text(
    text: str,
    chunk_size: int = 512,
    overlap: int = 64,
) -> list[str]:
    """
    Simple token-approximate chunking with overlap.
    In production, use a proper tokenizer (tiktoken for OpenAI models)
    to chunk by actual token count rather than character count.

    This implementation uses a sentence-aware split so chunks
    do not break mid-sentence.
    """
    # Split on sentence boundaries first
    import re
    sentences = re.split(r'(?<=[.!?])\s+', text.strip())

    chunks = []
    current_chunk: list[str] = []
    current_len = 0

    for sentence in sentences:
        # Approximate token count: 4 characters ≈ 1 token
        sentence_len = len(sentence) // 4

        if current_len + sentence_len > chunk_size and current_chunk:
            chunks.append(" ".join(current_chunk))
            # Keep the overlap: last N tokens worth of sentences
            overlap_sentences = []
            overlap_len = 0
            for s in reversed(current_chunk):
                s_len = len(s) // 4
                if overlap_len + s_len <= overlap:
                    overlap_sentences.insert(0, s)
                    overlap_len += s_len
                else:
                    break
            current_chunk = overlap_sentences
            current_len = overlap_len

        current_chunk.append(sentence)
        current_len += sentence_len

    if current_chunk:
        chunks.append(" ".join(current_chunk))

    return [c for c in chunks if c.strip()]


# ─────────────────────────────────────────────────────────
# Batch embedding with retry
# ─────────────────────────────────────────────────────────

import time
import openai

openai_client = openai.OpenAI()

def embed_batch(texts: list[str], model: str = "text-embedding-3-small") -> list[list[float]]:
    """
    Embed a batch of texts. OpenAI allows up to 2048 texts per call
    for text-embedding-3-small. We batch in groups of 256 to stay
    well within limits and keep retry windows small.
    """
    all_embeddings = []
    batch_size = 256

    for i in range(0, len(texts), batch_size):
        batch = texts[i : i + batch_size]
        for attempt in range(3):
            try:
                response = openai_client.embeddings.create(
                    model=model,
                    input=[t.replace("\n", " ") for t in batch],
                )
                all_embeddings.extend([d.embedding for d in response.data])
                break
            except openai.RateLimitError:
                wait = 2 ** attempt
                time.sleep(wait)
        else:
            raise RuntimeError(f"Embedding batch failed after 3 retries at offset {i}")

    return all_embeddings

# Full ingestion pipeline
# ─────────────────────────────────────────────────────────

def ingest_document(
    conn,
    collection_id: str,
    tenant_id: str,
    title: str,
    content: str,
    source_uri: str = None,
    source_type: str = "text",
    metadata: dict = None,
    chunk_size: int = 512,
    overlap: int = 64,
) -> dict:
    """
    Ingest a document into the knowledge base.

    Idempotent: if the same content hash already exists in the collection,
    returns the existing document ID without re-embedding.

    Returns: {"document_id": str, "chunk_count": int, "was_duplicate": bool}
    """
    content_hash = hashlib.sha256(content.encode()).hexdigest()
    metadata = metadata or {}

    with conn.cursor() as cur:
        # Check for duplicate
        cur.execute(
            """
            SELECT id, chunk_count FROM documents
            WHERE collection_id = %s AND content_hash = %s
            """,
            (collection_id, content_hash),
        )
        existing = cur.fetchone()
        if existing:
            return {
                "document_id": str(existing[0]),
                "chunk_count": existing[1],
                "was_duplicate": True,
            }

        # Insert document record in 'processing' state
        cur.execute(
            """
            INSERT INTO documents
                (collection_id, tenant_id, title, source_uri, source_type,
                 content_hash, raw_content, metadata, status)
            VALUES (%s, %s, %s, %s, %s, %s, %s, %s, 'processing')
            RETURNING id
            """,
            (collection_id, tenant_id, title, source_uri, source_type,
             content_hash, content, metadata),
        )
        document_id = cur.fetchone()[0]
    conn.commit()

    try:
        # Chunk the document
        chunks = chunk_text(content, chunk_size=chunk_size, overlap=overlap)

        # Generate embeddings for all chunks in one batched call
        embeddings = embed_batch(chunks)

        # Bulk insert chunks with embeddings
        with conn.cursor() as cur:
            chunk_rows = [
                (
                    str(document_id),
                    collection_id,
                    tenant_id,
                    idx,
                    chunk_text_val,
                    len(chunk_text_val) // 4,   # approximate token count
                    "[" + ",".join(str(x) for x in emb) + "]",
                    "text-embedding-3-small",
                    metadata,
                )
                for idx, (chunk_text_val, emb) in enumerate(zip(chunks, embeddings))
            ]

            execute_values(
                cur,
                """
                INSERT INTO document_chunks
                    (document_id, collection_id, tenant_id, chunk_index,
                     content, content_tokens, embedding, embedding_model, metadata)
                VALUES %s
                """,
                chunk_rows,
                template="(%s, %s, %s, %s, %s, %s, %s::vector, %s, %s)",
            )

            # Mark document as indexed
            cur.execute(
                """
                UPDATE documents
                SET status = 'indexed',
                    chunk_count = %s,
                    indexed_at = NOW()
                WHERE id = %s
                """,
                (len(chunks), document_id),
            )

            # Update collection document count
            cur.execute(
                """
                UPDATE document_collections
                SET document_count = document_count + 1
                WHERE id = %s
                """,
                (collection_id,),
            )

        conn.commit()

        return {
            "document_id": str(document_id),
            "chunk_count": len(chunks),
            "was_duplicate": False,
        }

    except Exception as e:
        # Mark document as failed so it can be retried
        with conn.cursor() as cur:
            cur.execute(
                """
                UPDATE documents
                SET status = 'failed', error_message = %s
                WHERE id = %s
                """,
                (str(e), document_id),
            )
        conn.commit()
        raise

The idempotency check on content_hash matters more than it might seem. In production, ingestion pipelines re-run. S3 event triggers fire more than once. Batch jobs get retried after failures. Without the hash check, you accumulate duplicate chunks that dilute retrieval quality and waste storage. The check is cheap: a simple equality lookup on an indexed column.

The status state machine — pending → processing → indexed | failed — gives you operational visibility. You can query for stuck documents (status = 'processing' older than ten minutes indicates a crashed worker) and failed documents that need attention. This matters when you are ingesting thousands of documents across many tenants.

The SQL Server Parallel: Azure SQL and SQL Server 2025

If your organization runs SQL Server rather than PostgreSQL, the same architectural patterns apply, but the implementation details differ significantly. SQL Server 2025 introduces native vector support; Azure SQL has had it in preview for some time. Here is how the core tables and retrieval query translate.

Schema in SQL Server / Azure SQL:

-- SQL Server 2025 / Azure SQL vector support
-- Vector columns use the VECTOR(dimensions) type

CREATE TABLE document_chunks (
    id              UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    document_id     UNIQUEIDENTIFIER NOT NULL
                        REFERENCES documents(id) ON DELETE CASCADE,
    collection_id   UNIQUEIDENTIFIER NOT NULL
                        REFERENCES document_collections(id),
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    chunk_index     INT NOT NULL,
    content         NVARCHAR(MAX) NOT NULL,
    content_tokens  INT,
    embedding       VECTOR(1536),          -- native SQL Server 2025 vector type
    embedding_model NVARCHAR(100) NOT NULL DEFAULT 'text-embedding-3-small',
    metadata        NVARCHAR(MAX) NOT NULL DEFAULT '{}',  -- JSON
    created_at      DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
    UNIQUE (document_id, chunk_index)
);

-- SQL Server 2025 vector index (DiskANN-based)
CREATE VECTOR INDEX idx_chunks_embedding
    ON document_chunks (embedding)
    WITH (METRIC = 'cosine');

-- Full-text index for hybrid search
CREATE FULLTEXT INDEX ON document_chunks (content)
    KEY INDEX PK__document_chunks
    WITH STOPLIST = SYSTEM;

Hybrid retrieval in SQL Server / Azure SQL:

-- Hybrid vector + full-text retrieval with RRF in SQL Server
DECLARE @query_embedding VECTOR(1536) = @embedding_param;
DECLARE @query_text NVARCHAR(500) = @query_param;
DECLARE @tenant_id UNIQUEIDENTIFIER = @tenant_param;
DECLARE @top_k INT = 8;

WITH vector_search AS (
    SELECT
        dc.id,
        dc.document_id,
        dc.content,
        dc.metadata,
        dc.chunk_index,
        d.title         AS document_title,
        d.source_uri,
        -- SQL Server 2025 vector distance function
        1 - VECTOR_DISTANCE('cosine', dc.embedding, @query_embedding)  AS vector_score,
        ROW_NUMBER() OVER (
            ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_embedding)
        ) AS vector_rank
    FROM document_chunks dc
    JOIN documents d ON d.id = dc.document_id
    WHERE dc.tenant_id = @tenant_id
      AND dc.embedding IS NOT NULL
    ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_embedding)
    OFFSET 0 ROWS FETCH NEXT 40 ROWS ONLY
),
fts_search AS (
    SELECT
        dc.id,
        dc.document_id,
        dc.content,
        dc.metadata,
        dc.chunk_index,
        d.title         AS document_title,
        d.source_uri,
        ftt.RANK        AS fts_score,
        ROW_NUMBER() OVER (ORDER BY ftt.RANK DESC) AS fts_rank
    FROM document_chunks dc
    JOIN documents d ON d.id = dc.document_id
    INNER JOIN CONTAINSTABLE(document_chunks, content, @query_text) AS ftt
        ON dc.id = ftt.[KEY]
    WHERE dc.tenant_id = @tenant_id
),
rrf_scores AS (
    SELECT
        COALESCE(v.id, f.id)                           AS id,
        COALESCE(v.document_id, f.document_id)         AS document_id,
        COALESCE(v.content, f.content)                 AS content,
        COALESCE(v.document_title, f.document_title)   AS document_title,
        COALESCE(v.source_uri, f.source_uri)           AS source_uri,
        COALESCE(v.chunk_index, f.chunk_index)         AS chunk_index,
        COALESCE(v.vector_score, 0)                    AS vector_score,
        COALESCE(f.fts_score, 0)                       AS fts_score,
        COALESCE(1.0 / (60 + v.vector_rank), 0) +
        COALESCE(1.0 / (60 + f.fts_rank), 0)          AS rrf_score
    FROM vector_search v
    FULL OUTER JOIN fts_search f ON v.id = f.id
)
SELECT TOP (@top_k) *
FROM rrf_scores
ORDER BY rrf_score DESC;

The SQL Server implementation differs from the PostgreSQL version in several places worth noting:

  • → SQL Server uses `VECTOR_DISTANCE('cosine', ...)` where PostgreSQL uses the `<=>` cosine distance operator from pgvector.
  • → SQL Server's full-text search uses `CONTAINSTABLE` for ranked results, while PostgreSQL uses `ts_rank_cd` with `to_tsvector`/`plainto_tsquery`.
  • → The vector index uses DiskANN internally in SQL Server 2025; PostgreSQL's pgvector offers both HNSW and IVFFlat.
  • → SQL Server uses `TOP (n)` for limiting results; PostgreSQL uses `LIMIT n`.
  • → Row-level security in SQL Server uses `CREATE SECURITY POLICY` with a predicate function rather than PostgreSQL's simpler `CREATE POLICY ... USING (...)` syntax.

    • For organizations already invested in the Microsoft stack — Azure infrastructure, Active Directory, SQL Server licensing — Azure SQL with vector support is a legitimate path to the same architectural pattern. The conceptual model is identical: store embeddings alongside relational data, do hybrid retrieval in the database engine, keep everything in a single transactional system.

    Connecting PostgreSQL to the LLM: The Context Window as Interface

    The practical interface between PostgreSQL and an LLM is the context window. Everything the model knows about your application state must be serialized into text and injected there. This means every architectural decision about how you store and retrieve data is ultimately a decision about what information you can afford to inject — and in what form.

    Several patterns have emerged for structuring this injection.

    Structured context blocks. Rather than dumping raw database rows, format retrieved data into labeled sections with clear headings. The model parses structure in text more reliably than it parses unlabeled blobs.

    def format_user_context(user: dict, conversation_stats: dict) -> str:
    return f"""
## User Context
- Name: {user['display_name']}
- Role: {user['role']}
- Tenant plan: {user['plan']}
- Conversations this month: {conversation_stats['count']}
- Total tokens used: {conversation_stats['total_tokens']:,}
""".strip()

def format_retrieved_documents(chunks: list[dict]) -> str:
    if not chunks:
        return "No relevant documents found in the knowledge base."

    parts = ["## Retrieved Knowledge Base Content"]
    for i, chunk in enumerate(chunks, 1):
        parts.append(
            f"\n### Source {i}: {chunk['document_title']}\n"
            f"Relevance score: {chunk['rrf_score']:.3f}\n\n"
            f"{chunk['content']}"
        )
    return "\n".join(parts)

    Injecting relational state. Beyond document chunks, you often need to inject structured application state — the user's current account, active orders, recent activity. Query this from PostgreSQL and serialize it into the context block.

    def get_user_context_data(conn, user_id: str, tenant_id: str) -> dict:
    """
    Pull structured context data for a user from PostgreSQL.
    This goes into the LLM context alongside retrieved document chunks.
    """

        # User and tenant info
        cur.execute(
            """
            SELECT u.display_name, u.role, u.metadata,
                   t.plan, t.settings
            FROM users u
            JOIN tenants t ON t.id = u.tenant_id
            WHERE u.id = %s AND u.tenant_id = %s
            """,
            (user_id, tenant_id),
        )
        user_row = dict(cur.fetchone())

        # Usage stats for current month
        cur.execute(
            """
            SELECT COUNT(*) AS conversation_count,
                   COALESCE(SUM(token_count), 0) AS total_tokens,
                   COALESCE(SUM(
                       (SELECT COALESCE(SUM(cost_usd), 0)
                        FROM messages m
                        WHERE m.conversation_id = c.id)
                   ), 0) AS total_cost_usd
            FROM conversations c
            WHERE c.user_id = %s
              AND c.created_at >= DATE_TRUNC('month', NOW())
            """,
            (user_id,),
        )
        stats = dict(cur.fetchone())

    return {**user_row, **stats}

    Token budget management. The context window is finite. With a 200K token window you have more room than with an 8K one, but the constraint is always there — and longer contexts cost more. The right approach is to allocate your token budget explicitly and trim when you exceed it.

    # Approximate token budgeting
CONTEXT_BUDGET = {
    "system_prompt": 500,
    "user_context": 300,
    "conversation_history": 3000,
    "retrieved_chunks": 4000,
    "response_reserve": 2048,
}
# Total: ~10,000 tokens — fits comfortably in any modern model

def trim_history_to_budget(
    history: list[dict],
    token_budget: int,
    chars_per_token: int = 4,
) -> list[dict]:
    """
    Trim conversation history from the oldest end to fit within a token budget.
    Always preserve the first message (initial context) and keep
    the most recent messages.
    """
    if not history:
        return history

    char_budget = token_budget * chars_per_token
    total_chars = sum(len(m.get("content", "")) for m in history)

    if total_chars <= char_budget:
        return history

    # Keep the first message (if it's a system or user context message)
    # and trim from index 1 forward
    result = [history[0]]
    remaining_budget = char_budget - len(history[0].get("content", ""))

    for msg in reversed(history[1:]):
        msg_len = len(msg.get("content", ""))
        if remaining_budget - msg_len >= 0:
            result.insert(1, msg)
            remaining_budget -= msg_len
        else:
            break

    return result

    Observability: Querying What Your AI System Is Doing

    The ai_audit_log table is not just for compliance — it is your primary operational instrument. Here are the queries you will run daily in production.

    -- ─────────────────────────────────────────────────────────
-- Daily cost and usage summary by tenant
-- ─────────────────────────────────────────────────────────
SELECT
    t.name                                  AS tenant_name,
    t.plan,
    COUNT(*)                                AS total_requests,
    SUM(a.input_tokens)                     AS total_input_tokens,
    SUM(a.output_tokens)                    AS total_output_tokens,
    SUM(a.cost_usd)                         AS total_cost_usd,
    AVG(a.latency_ms)                       AS avg_latency_ms,
    PERCENTILE_CONT(0.95) WITHIN GROUP
        (ORDER BY a.latency_ms)             AS p95_latency_ms
FROM ai_audit_log a
JOIN tenants t ON t.id = a.tenant_id
WHERE a.created_at >= NOW() - INTERVAL '24 hours'
  AND a.event_type = 'message'
GROUP BY t.id, t.name, t.plan
ORDER BY total_cost_usd DESC;

-- ─────────────────────────────────────────────────────────
-- Retrieval quality signal: requests that returned zero chunks
-- ─────────────────────────────────────────────────────────
SELECT
    DATE_TRUNC('hour', a.created_at)       AS hour,
    COUNT(*)                               AS total_requests,
    SUM(CASE WHEN a.retrieval_count = 0
             THEN 1 ELSE 0 END)            AS zero_retrieval_count,
    ROUND(
        100.0 * SUM(CASE WHEN a.retrieval_count = 0
                         THEN 1 ELSE 0 END)
        / COUNT(*), 2
    )                                      AS zero_retrieval_pct
FROM ai_audit_log a
WHERE a.created_at >= NOW() - INTERVAL '7 days'
  AND a.event_type = 'message'
GROUP BY 1
ORDER BY 1 DESC;

-- ─────────────────────────────────────────────────────────
-- Latency percentiles over the last hour (SLA monitoring)
-- ─────────────────────────────────────────────────────────
SELECT
    PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY latency_ms) AS p50_ms,
    PERCENTILE_CONT(0.90) WITHIN GROUP (ORDER BY latency_ms) AS p90_ms,
    PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY latency_ms) AS p95_ms,
    PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY latency_ms) AS p99_ms,
    MAX(latency_ms)                                           AS max_ms,
    COUNT(*)                                                  AS request_count
FROM ai_audit_log
WHERE created_at >= NOW() - INTERVAL '1 hour'
  AND event_type = 'message';

-- ─────────────────────────────────────────────────────────
-- Most expensive conversations (useful for identifying
-- runaway agentic loops or unusually long sessions)
-- ─────────────────────────────────────────────────────────
SELECT
    c.id                                AS conversation_id,
    u.email                             AS user_email,
    t.name                              AS tenant_name,
    c.message_count,
    c.token_count,
    SUM(m.cost_usd)                     AS total_cost_usd,
    c.created_at,
    c.last_message_at
FROM conversations c
JOIN users u ON u.id = c.user_id
JOIN tenants t ON t.id = c.tenant_id
JOIN messages m ON m.conversation_id = c.id
WHERE c.created_at >= NOW() - INTERVAL '24 hours'
GROUP BY c.id, u.email, t.name, c.message_count,
         c.token_count, c.created_at, c.last_message_at
ORDER BY total_cost_usd DESC
LIMIT 20;

    These queries work because everything is in one database with referential integrity. In a polyglot stack, correlating LLM API logs with user records with conversation history requires a data warehouse and an ETL pipeline. Here it is a join.

  • → A **hybrid retrieval pipeline** that combines pgvector's HNSW index for semantic search with PostgreSQL's full-text search, fused with Reciprocal Rank Fusion for production-quality retrieval.
  • → An **ingestion pipeline** with idempotent deduplication, batch embedding, and a status state machine for operational visibility into document processing.
  • → **Context assembly patterns** for injecting both retrieved documents and structured relational state into LLM context windows, with token budget management.
  • → **Observability queries** that give you cost attribution, latency percentiles, and retrieval quality signals directly from the audit log.
  • → **A FastAPI service** that wires all of it together behind an HTTP API a frontend can call.
  • → The **SQL Server / Azure SQL equivalent** of the core schema and retrieval query, for organizations on the Microsoft stack.

    Key Takeaways

  • → **AI applications require three layers working together**: language model reasoning, semantic vector retrieval, and relational data management. No single layer is sufficient on its own, and skipping any of them produces systems that fail in predictable ways in production.
  • → **PostgreSQL with pgvector is a legitimate unified data layer**: by combining vector indexes, full-text search, JSONB document storage, row-level security, and transactional consistency in one engine, you eliminate the operational and consistency complexity of running separate vector, relational, session, and search systems.
  • → **Hybrid retrieval with RRF outperforms pure vector search**: Reciprocal Rank Fusion combines vector similarity rankings and full-text rankings in a way that is robust to score-scale differences, recovering results that semantic search alone misses due to vocabulary mismatch.
  • → **Schema decisions made early determine what you can observe later**: storing cost, latency, token counts, and retrieval metadata per message and per audit event means your observability queries are joins, not ETL pipelines — but only if you design those columns in from the start.
  • → **The context window is the only interface between PostgreSQL and the LLM**: every retrieval, context assembly, and token budgeting decision is ultimately about what information fits in that window and in what form — making the data access patterns that populate it as important as any prompt engineering choice.
