Chapter 40: The Cloud DBA's Cost and Performance Dashboard

Every cloud DBA eventually faces the same uncomfortable conversation with finance: "Why did our database bill jump 40% last month?" The honest answer is almost always the same — visibility was incomplete, and decisions were made without a unified view of cost alongside performance. On-premises, you knew exactly what the hardware cost because you signed the purchase order. In the cloud, costs are fluid, metered by the second, and shaped by dozens of variables — instance class, storage IOPS, data transfer, backup retention, cross-AZ replication, and licensing uplift. A performance fix that doubles your IOPS can simultaneously double your bill without anyone noticing until the invoice arrives.

This final chapter brings together everything covered in this book into a practical, deployable dashboard framework that spans AWS RDS, Aurora, Azure SQL, and Google Cloud SQL. You will build monitoring views that correlate query latency with cost drivers, set up alerting thresholds grounded in real production numbers, and establish the governance habits that prevent runaway spend. This is the operational layer that ties cloud database engineering together — not a collection of theoretical advice, but the actual queries, CLI commands, and Terraform configurations used in production environments.

---

40.1 The Cost-Performance Relationship in Cloud Databases

On-premises DBAs think about performance in isolation from cost because the hardware is already paid for. A slow query costs you nothing extra in dollars — it only costs time and user experience. In the cloud, that mental model breaks immediately. A query that triggers a full table scan on an Aurora cluster with Serverless v2 scaling will literally increase your AWS bill as the ACU count climbs to handle the load. A missing index on Azure SQL Hyperscale is not just a performance problem — it is a spending problem.

The fundamental shift is this: in cloud databases, compute and I/O are metered continuously. This creates a tight coupling between query efficiency, configuration choices, and monthly cost that has no analog in on-premises work.

The three cost drivers every cloud DBA must track:

Compute is typically the largest line item. An db.r6g.4xlarge on RDS costs approximately $0.96/hour in us-east-1 (On-Demand). Running it 24/7 for 30 days is roughly $691. A Reserved Instance (1-year, no upfront) drops that to around $0.57/hour — $410/month — a 40% reduction. DBAs who migrate from on-prem and leave everything On-Demand for six months are leaving tens of thousands of dollars on the table.

Storage on RDS gp3 is $0.115/GB/month with a baseline of 3,000 IOPS and 125 MB/s throughput included. If your application was provisioned with io1 at 10,000 IOPS, you are paying approximately $0.065/IOPS/month on top of storage — that is $650/month in IOPS alone for a moderately sized database. Migrating from io1 to gp3 with manually provisioned IOPS is one of the highest-ROI changes a cloud DBA can make.

Data transfer is the stealth cost. Reads stay within a region cheaply, but every byte leaving a VPC to the internet costs $0.09/GB. Cross-AZ traffic between your application tier and your RDS Multi-AZ instance costs $0.02/GB each direction. For a high-throughput reporting database that ships hundreds of gigabytes to an analytics layer, this becomes significant.

The dashboard you build must surface all three drivers alongside the performance metrics that cause them to spike.

40.2 Building the Unified Monitoring Foundation

Before building dashboards, you need the telemetry infrastructure in place. CloudWatch, Azure Monitor, and Cloud Monitoring each require specific configuration to expose database-level metrics at useful granularity.

AWS: Enabling Enhanced Monitoring and Performance Insights

Standard CloudWatch RDS metrics report at 1-minute intervals and cover CPU, storage, and basic connection counts. Enhanced Monitoring adds 50+ OS-level metrics at intervals down to 1 second — this is what you need to catch connection storms, memory pressure, and disk saturation that standard metrics miss.

# Enable Enhanced Monitoring and Performance Insights on an existing RDS instance
# Enhanced Monitoring requires an IAM role with the rds-monitoring policy

# Step 1: Create the monitoring role if it doesn't exist
aws iam create-role \
  --role-name rds-enhanced-monitoring-role \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {"Service": "monitoring.rds.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }]
  }'

aws iam attach-role-policy \
  --role-name rds-enhanced-monitoring-role \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonRDSEnhancedMonitoringRole

# Step 2: Enable Enhanced Monitoring (granularity: 5 seconds)
# and Performance Insights (retention: 7 days free, 731 days = paid)
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --monitoring-interval 5 \
  --monitoring-role-arn arn:aws:iam::123456789012:role/rds-enhanced-monitoring-role \
  --enable-performance-insights \
  --performance-insights-retention-period 7 \
  --apply-immediately

# Step 3: Verify the changes applied
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].{
    MonitoringInterval:MonitoringInterval,
    PIEnabled:PerformanceInsightsEnabled,
    PIRetention:PerformanceInsightsRetentionPeriod
  }'

Azure SQL: Enabling Diagnostic Settings

Azure SQL does not ship query-level metrics to Log Analytics by default. You must explicitly configure Diagnostic Settings for each database or elastic pool. Without this, you are flying blind on query performance data.

# Assumes you have a Log Analytics workspace already created

RESOURCE_GROUP="prod-rg"
SQL_SERVER="prod-sql-server-eastus"
DATABASE="prod-db-01"
WORKSPACE_ID="/subscriptions/xxxx/resourceGroups/prod-rg/providers/Microsoft.OperationalInsights/workspaces/prod-law"

# Get the full resource ID of the database
DB_RESOURCE_ID=$(az sql db show \
  --resource-group $RESOURCE_GROUP \
  --server $SQL_SERVER \
  --name $DATABASE \
  --query id -o tsv)

# Create diagnostic setting — capture QueryStoreRuntimeStatistics,

Google Cloud SQL: Enabling Query Insights

Cloud SQL's Query Insights is the equivalent of Performance Insights — it captures per-query latency, wait events, and execution plans. It is not enabled by default.

# Enable Query Insights on Cloud SQL for PostgreSQL
# Note: Requires restart for some flags on Cloud SQL

gcloud sql instances patch prod-postgres-instance \
  --database-flags="cloudsql.enable_query_insights=on" \
  --project=my-gcp-project

# Set sampling rate (1000 = 100% of queries sampled, 0 = disabled)
# For high-traffic instances, use a lower rate to control overhead
gcloud sql instances patch prod-postgres-instance \
  --database-flags="\
    cloudsql.enable_query_insights=on,\
    cloudsql.query_insights_sample_rate=200,\
    cloudsql.query_string_length=1024,\
    cloudsql.record_application_tags=on,\
    cloudsql.record_client_address=on" \
  --project=my-gcp-project

# Verify current flags
gcloud sql instances describe prod-postgres-instance \
  --project=my-gcp-project \
  --format="json" | jq '.settings.databaseFlags'

The monitoring coverage matrix — before building dashboards, verify you have the following telemetry active on every production instance:

| Signal | AWS RDS | Azure SQL | Cloud SQL |

|---|---|---|---|

| CPU/Memory | CloudWatch (1m) | Azure Monitor (1m) | Cloud Monitoring (1m) |

| Per-query stats | Performance Insights | Query Store + Log Analytics | Query Insights |

| Wait events | Performance Insights | sys.dm_os_wait_stats | pg_stat_activity |

| Replication lag | CloudWatch ReplicaLag | sys.dm_hadr_database_replica_states | Cloud Monitoring replication/replica_lag |

| Storage I/O | Enhanced Monitoring | Azure Monitor IOPS metrics | Cloud Monitoring disk/write_ops_count |

| Cost allocation | Cost Explorer tags | Azure Cost Management tags | Cloud Billing labels |

40.3 Query-Level Cost Attribution

The most actionable insight a cloud DBA can provide is answering: "Which queries are costing us the most money?" This is not a theoretical exercise. On Aurora Serverless v2, a single unoptimized reporting query that runs at 2 AM and scales the cluster from 2 ACUs to 32 ACUs for 20 minutes is generating a measurable cost spike. Identifying and fixing it is both a performance win and a direct cost reduction.

AWS RDS/Aurora: Extracting Top Queries from Performance Insights

import boto3
from datetime import datetime, timezone, timedelta
import json

def get_top_cost_queries(db_instance_id: str, region: str = "us-east-1", top_n: int = 20):
    """
    Retrieve the top SQL queries by db.load (average active sessions)
    from Performance Insights. High db.load on cloud = high cost.
    
    db.load is the primary metric — it represents the number of active
    sessions normalized against vCPU count. A db.load > vCPU count means
    your instance is under pressure. On Serverless, it triggers scaling.
    """
    client = boto3.client("pi", region_name=region)
    
    # Get the DI (Data Source) identifier for this instance
    rds_client = boto3.client("rds", region_name=region)
    instance_info = rds_client.describe_db_instances(
        DBInstanceIdentifier=db_instance_id
    )
    dbi_resource_id = instance_info["DBInstances"][0]["DbiResourceId"]
    
    end_time = datetime.now(timezone.utc)
    start_time = end_time - timedelta(hours=24)
    
    response = client.get_resource_metrics(
        ServiceType="RDS",
        Identifier=dbi_resource_id,
        MetricQueries=[
            {
                "Metric": "db.load.avg",
                "GroupBy": {
                    "Group": "db.sql",
                    "Dimensions": ["db.sql.id", "db.sql.tokenized_id"],
                    "Limit": top_n
                }
            }
        ],
        StartTime=start_time,
        EndTime=end_time,
        PeriodInSeconds=3600  # 1-hour buckets
    )
    
    # Extract and sort by average load contribution
    query_loads = []
    for key_metric in response.get("MetricList", []):
        sql_id = key_metric["Key"].get("Dimensions", {}).get("db.sql.tokenized_id", "unknown")
        
        # Calculate average load across the 24h window
        data_points = key_metric.get("DataPoints", [])
        if data_points:
            avg_load = sum(
                dp["Value"] for dp in data_points if "Value" in dp
            ) / len(data_points)
            
            query_loads.append({
                "sql_tokenized_id": sql_id,
                "avg_db_load": round(avg_load, 4),
                "data_points": len(data_points)
            })
    
    # Sort by average load — highest first
    query_loads.sort(key=lambda x: x["avg_db_load"], reverse=True)
    
    print(f"\nTop {top_n} queries by DB Load (24h window) — {db_instance_id}")
    print(f"{'Rank':<6} {'Avg DB Load':<15} {'SQL Tokenized ID'}")
    print("-" * 60)
    for rank, q in enumerate(query_loads[:top_n], 1):
        print(f"{rank:<6} {q['avg_db_load']:<15} {q['sql_tokenized_id']}")
    
    return query_loads


def estimate_aurora_serverless_cost_impact(
    avg_load_units: float,
    vcpu_per_acu: float = 0.5,
    acu_price_per_hour: float = 0.12,
    hours_window: int = 24
) -> dict:
    """
    Estimate the cost contribution of a workload component on Aurora Serverless v2.
    
    Aurora Serverless v2 pricing:
    - Each ACU = 2 GB RAM + ~0.5 vCPU equivalent
    - Price: $0.12/ACU-hour (us-east-1)
    - Min ACUs: 0.5, Max ACUs: 128
    
    If a query contributes 4.0 units of db.load and baseline is 2.0,
    it's doubling the required ACU footprint.
    """
    estimated_acus_consumed = avg_load_units / vcpu_per_acu
    estimated_cost = estimated_acus_consumed * acu_price_per_hour * hours_window
    
    return {
        "avg_load_units": avg_load_units,
        "estimated_acus": round(estimated_acus_consumed, 2),
        "estimated_cost_24h": round(estimated_cost, 4),
        "acu_price_per_hour": acu_price_per_hour
    }


# Example usage
if __name__ == "__main__":
    queries = get_top_cost_queries(
        db_instance_id="prod-aurora-postgres-cluster-instance-1",
        region="us-east-1",
        top_n=10
    )
    
    if queries:
        top_query = queries[0]
        cost_impact = estimate_aurora_serverless_cost_impact(
            avg_load_units=top_query["avg_db_load"]
        )
        print(f"\nCost impact estimate for top query:")
        print(json.dumps(cost_impact, indent=2))

Azure SQL: Query Store Cost Attribution

On Azure SQL, Query Store is the equivalent telemetry system. Unlike Performance Insights, it lives inside the database itself and persists across connections. Because you already know Query Store from SQL Server on-premises, the transition here is familiar — but the DTU/vCore billing layer makes query efficiency directly financial.

-- Azure SQL: Top 20 queries by total CPU time over the last 24 hours
-- This directly maps to DTU consumption and therefore billing cost.
-- On Azure SQL Hyperscale, CPU cost = vCore seconds consumed.
-- Cross-reference with Query Store wait statistics to find root cause.

WITH recent_interval AS (
    SELECT
        rsi.start_time,
        rsi.end_time,
        rsi.runtime_stats_interval_id
    FROM sys.query_store_runtime_stats_intervals rsi
    WHERE rsi.start_time >= DATEADD(HOUR, -24, GETUTCDATE())
),
query_stats AS (
    SELECT
        qsq.query_id,
        qsqt.query_sql_text,
        qsq.object_id,
        OBJECT_NAME(qsq.object_id)                          AS proc_name,
        COUNT(*)                                             AS execution_count,
        SUM(qsrs.count_executions)                          AS total_executions,
        AVG(qsrs.avg_cpu_time)                              AS avg_cpu_us,
        MAX(qsrs.max_cpu_time)                              AS max_cpu_us,
        SUM(qsrs.avg_cpu_time * qsrs.count_executions)      AS total_cpu_us,
        AVG(qsrs.avg_duration)                              AS avg_duration_us,
        AVG(qsrs.avg_logical_io_reads)                      AS avg_logical_reads,
        SUM(qsrs.avg_logical_io_reads * qsrs.count_executions) AS total_logical_reads,
        AVG(qsrs.avg_rowcount)                              AS avg_rows_returned,
        -- Regressed queries: max > 3x average is a flag for plan instability
        CASE
            WHEN MAX(qsrs.max_cpu_time) > AVG(qsrs.avg_cpu_time) * 3
            THEN 'PLAN_REGRESSION_RISK'
            ELSE 'STABLE'
        END                                                  AS plan_stability
    FROM sys.query_store_query qsq
    JOIN sys.query_store_query_text qsqt
        ON qsq.query_text_id = qsqt.query_text_id
    JOIN sys.query_store_plan qsp
        ON qsq.query_id = qsp.query_id
    JOIN sys.query_store_runtime_stats qsrs
        ON qsp.plan_id = qsrs.plan_id
    JOIN recent_interval ri
        ON qsrs.runtime_stats_interval_id = ri.runtime_stats_interval_id
    WHERE qsq.is_internal_query = 0  -- Exclude system queries
    GROUP BY
        qsq.query_id,
        qsqt.query_sql_text,
        qsq.object_id
),
ranked AS (
    SELECT
        *,
        RANK() OVER (ORDER BY total_cpu_us DESC) AS cpu_rank,
        RANK() OVER (ORDER BY total_logical_reads DESC) AS io_rank,
        -- Composite cost score: CPU contributes 60%, I/O contributes 40%
        -- Adjust weights based on your instance's bottleneck profile
        (RANK() OVER (ORDER BY total_cpu_us DESC) * 0.6 +
         RANK() OVER (ORDER BY total_logical_reads DESC) * 0.4) AS composite_cost_rank
    FROM query_stats
)
SELECT TOP 20
    cpu_rank,
    io_rank,
    CAST(composite_cost_rank AS INT)            AS composite_rank,
    query_id,
    LEFT(query_sql_text, 120)                   AS query_preview,
    proc_name,
    total_executions,
    CAST(avg_cpu_us / 1000.0 AS DECIMAL(10,2))  AS avg_cpu_ms,
    CAST(total_cpu_us / 1000000.0 AS DECIMAL(12,2)) AS total_cpu_seconds,
    CAST(avg_duration_us / 1000.0 AS DECIMAL(10,2)) AS avg_duration_ms,
    avg_logical_reads,
    total_logical_reads,
    plan_stability
FROM ranked
ORDER BY composite_cost_rank ASC;

40.4 Cost Governance with Terraform and Tagging

Cost dashboards without governance are just reports. The operational change that prevents budget overruns is enforcing tagging standards at provisioning time and building Terraform modules that emit cost-compatible configurations by default.

Every RDS instance, Azure SQL server, and Cloud SQL instance in production should carry tags/labels that answer: Which team owns it? Which application uses it? What environment is it in? Without this, your cost reports show a single line item — "RDS" — and no one can determine what is wasting money.

Terraform: Production-Grade RDS Module with Cost Controls

# terraform/modules/rds_postgres/main.tf
# Production RDS PostgreSQL module with mandatory tagging,
# cost-optimized storage defaults, and alerting configuration.
#
# Key cost decisions enforced in this module:
# - gp3 storage by default (not io1, not gp2)
# - Performance Insights enabled (no cost at 7-day retention)
# - Enhanced Monitoring enabled (minimal CloudWatch cost vs. visibility gained)
# - deletion_protection = true (prevents accidental teardown and data recovery costs)
# - Reserved Instance: NOT managed in Terraform — handled separately via
#   AWS console or aws_db_reserved_instances_offering resource

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

variable "identifier" {
  type        = string
  description = "RDS instance identifier — must be unique within the AWS account/region"
}

variable "instance_class" {
  type        = string
  description = "RDS instance class. Cost reference: db.r6g.large ~$0.24/hr, db.r6g.xlarge ~$0.48/hr, db.r6g.2xlarge ~$0.96/hr (us-east-1 On-Demand)"
  default     = "db.r6g.large"

  validation {
    # Prevent accidentally provisioning oversized instances without explicit intent
    condition     = !contains(["db.r6g.8xlarge", "db.r6g.16xlarge", "db.r5.8xlarge", "db.r5.16xlarge"], var.instance_class)
    error_message = "Instances larger than 4xlarge require explicit approval. Contact the platform team."
  }
}

variable "allocated_storage_gb" {
  type        = number
  description = "Initial storage in GB. gp3 baseline: 3,000 IOPS and 125 MB/s throughput included."
  default     = 100

  validation {
    condition     = var.allocated_storage_gb >= 20 && var.allocated_storage_gb <= 65536
    error_message = "Storage must be between 20 GB and 65,536 GB."
  }
}

variable "max_allocated_storage_gb" {
  type        = number

  default     = 500

variable "engine_version" {
  type    = string
  default = "16.3"

variable "database_name" {
  type = string
}

  type = string
}

variable "subnet_group_name" {
  type        = string
  description = "DB subnet group — must be in private subnets only"
}

  type = list(string)
}

  type    = string
  default = null
}

  type        = string

  type    = string

  type        = number

variable "tags" {
  type        = map(string)

  validation {

      contains(keys(var.tags), "application"),
      contains(keys(var.tags), "environment"),

# Local computed values
locals {
  # Merge mandatory module-level tags with caller-provided tags
  merged_tags = merge(var.tags, {
    "managed-by"   = "terraform"
    "module"       = "rds_postgres"
    "engine"       = "postgres-${var.engine_version}"

  })
}

resource "aws_db_instance" "this" {
  identifier        = var.identifier
  engine            = "postgres"
  engine_version    = var.engine_version
  instance_class    = var.instance_class

  # Storage: gp3 by default — cost-optimized vs. io1/gp2
  # gp3 includes 3,000 IOPS and 125 MB/s at no extra charge
  # Provision additional IOPS only if pg_stat_io shows consistent saturation
  storage_type          = "gp3"
  allocated_storage     = var.allocated_storage_gb
  max_allocated_storage = var.max_allocated_storage_gb > 0 ? var.max_allocated_storage_gb : null
  storage_encrypted     = true

  db_name  = var.database_name
  username = var.master_username
  # Password managed via Secrets Manager — not in Terraform state
  manage_master_user_password = true

  db_subnet_group_name   = var.subnet_group_name
  vpc_security_group_ids = var.vpc_security_group_ids

  parameter_group_name = var.parameter_group_name
  
  # Multi-AZ: required for production

  performance_insights_enabled          = true

  # Enhanced Monitoring: 5-second granularity
  monitoring_interval = 5
  monitoring_role_arn = var.monitoring_role_arn

  # Prevent accidental deletion
  deletion_protection = true
  skip_final_snapshot = false
  final_snapshot_identifier = "${var.identifier}-final-snapshot"

  auto_minor_version_upgrade = true

}

  sensitive = false
  description = "DbiResourceId — needed for Performance Insights API calls"
}

The tagging enforcement gap — one gotcha worth flagging: Terraform validation on tags only applies when you provision through Terraform. If someone creates an RDS instance through the console, the validation never runs. Pair this module with an AWS Config rule (required-tags) that fires a non-compliant finding on any RDS instance missing your mandatory tag keys. You can enforce this organization-wide via AWS Organizations Service Control Policies to make untagged database creation impossible.

40.5 The Production Dashboard: Queries, Views, and Composite Metrics

A useful cost-performance dashboard answers five questions at a glance:

1. Are any instances currently under resource pressure?

2. Which queries are responsible for the most resource consumption in the last 24 hours?

3. Is there any replication lag that would affect read-replica routing decisions?

4. What is the current storage consumption trajectory — will we hit autoscaling in the next 30 days?

5. Are there any cost optimization opportunities visible right now?

PostgreSQL: Consolidated Health View

This view works on RDS for PostgreSQL, Aurora PostgreSQL, Cloud SQL for PostgreSQL, and AlloyDB. It aggregates the most cost-relevant metrics from the PostgreSQL statistics system.```sql

-- pg_cloud_dba_dashboard.sql

-- Unified health and cost-attribution view for PostgreSQL on any cloud provider.

-- Deploy as a view in a dedicated monitoring schema.

-- Requires: pg_stat_statements extension enabled (add to shared_preload_libraries

-- via Parameter Group on RDS, or via database flags on Cloud SQL).

--

-- On RDS: pg_stat_statements is available but must be enabled in the parameter group.

-- On Cloud SQL: add cloudsql.enable_pg_stat_statements=on to database flags.

-- On AlloyDB: enabled by default in pg_stat_statements compatible form.

CREATE SCHEMA IF NOT EXISTS dba_monitor;

-- View 1: Top queries by total cost (CPU + I/O composite)

CREATE OR REPLACE VIEW dba_monitor.top_queries_by_cost AS

WITH query_stats AS (

SELECT

pss.userid,

pss.dbid,

pss.queryid,

pss.query,

pss.calls,

pss.total_exec_time,

pss.mean_exec_time,

pss.stddev_exec_time,

pss.rows,

pss.shared_blks_hit,

pss.shared_blks_read, -- Physical reads = storage I/O cost

pss.shared_blks_dirtied,

pss.shared_blks_written,

pss.temp_blks_read, -- Temp block usage = work_mem spill to disk

pss.temp_blks_written,

pss.blk_read_time,

pss.blk_write_time,

-- Buffer hit ratio per query — below 95% indicates I/O pressure

CASE

WHEN (pss.shared_blks_hit + pss.shared_blks_read) > 0

THEN ROUND(

(pss.shared_blks_hit::NUMERIC /

(pss.shared_blks_hit + pss.shared_blks_read) * 100), 2

)

ELSE 100.0

END AS buffer_hit_pct,

-- Total I/O time as percentage of execution time

CASE

WHEN pss.total_exec_time > 0

THEN ROUND(

((pss.blk_read_time + pss.blk_write_time) /

pss.total_exec_time * 100), 2

)

ELSE 0

END AS io_time_pct,

-- Work mem spill indicator — temp blocks > 0 means sort/hash went to disk

CASE

WHEN pss.temp_blks_written > 0 THEN 'SPILLING_TO_DISK'

ELSE 'IN_MEMORY'

END AS sort_behavior,

-- Composite cost score (normalized)

-- Higher = more resource-intensive = higher cloud cost contribution

ROUND(

(pss.total_exec_time / NULLIF(SUM(pss.total_exec_time) OVER (), 0) * 60) +

(pss.shared_blks_read / NULLIF(SUM(pss.shared_blks_read) OVER (), 0) * 40),

4

) AS composite_cost_score

FROM pg_stat_statements pss

JOIN pg_database pd ON pss.dbid = pd.oid

WHERE pd.datname = current_database()

AND pss.calls > 10 -- Filter out one-off queries

AND pss.mean_exec_time > 1 -- Filter sub-millisecond queries

)

SELECT

queryid,

LEFT(query, 150) AS query_preview,

calls,

ROUND(total_exec_time::NUMERIC, 2) AS total_exec_time_ms,

ROUND(mean_exec_time::NUMERIC, 2) AS mean_exec_time_ms,

ROUND(stddev_exec_time::NUMERIC, 2) AS stddev_exec_time_ms,

-- High stddev relative to mean = plan instability

CASE

WHEN stddev_exec_time > mean_exec_time * 0.5 THEN 'UNSTABLE'

ELSE 'STABLE'

END AS execution_stability,

ROUND(rows::NUMERIC / NULLIF(calls, 0), 0) AS avg_rows_per_call,

shared_blks_hit,

shared_blks_read,

buffer_hit_pct,

io_time_pct,

temp_blks_written,

sort_behavior,

composite_cost_score,

RANK() OVER (ORDER BY composite_cost_score DESC) AS cost_rank

FROM query_stats

ORDER BY composite_cost_score DESC

LIMIT 25;

-- View 2: Table-level bloat and I/O pressure

-- Bloat causes unnecessary I/O → unnecessary storage reads → unnecessary cloud cost

CREATE OR REPLACE VIEW dba_monitor.table_io_and_bloat AS

SELECT

schemaname,

relname AS table_name,

n_live_tup AS live_rows,

n_dead_tup AS dead_rows,

-- Dead tuple ratio > 10% indicates autovacuum is not keeping up

CASE

WHEN (n_live_tup + n_dead_tup) > 0

THEN ROUND(n_dead_tup::NUMERIC /

(n_live_tup + n_dead_tup) * 100, 2)

ELSE 0

END AS dead_tuple_pct,

last_vacuum,

last_autovacuum,

last_analyze,

last_autoanalyze,

heap_blks_read AS heap_physical_reads,

heap_blks_hit AS heap_buffer_hits,

CASE

WHEN (heap_blks_hit + heap_blks_read) > 0

THEN ROUND(heap_blks_hit::NUMERIC /

(heap_blks_hit + heap_blks_read) * 100, 2)

ELSE 100

END AS table_buffer_hit_pct,

idx_blks_read AS index_physical_reads,

idx_blks_hit AS index_buffer_hits,

-- pg_relation_size requires access but gives actual on-disk bytes

pg_size_pretty(pg_total_relation_size(schemaname || '.' || relname)) AS total_size,

pg_total_relation_size(schemaname || '.' || relname) AS total_size_bytes

FROM pg_stat_user_tables pst

JOIN pg_statio_user_tables psio USING (schemaname, relname)

WHERE pg_total_relation_size(schemaname || '.' || relname) > 104857600 -- > 100 MB

ORDER BY total_size_bytes DESC;

-- View 3: Replication lag monitoring (read replica routing decisions)

-- On RDS read replicas, lag > 30 seconds should trigger alerts.

-- On Aurora, replica lag is typically < 100ms but can spike during DDL.

-- On Cloud SQL read replicas, lag > 60 seconds is the default alert threshold.

CREATE OR REPLACE VIEW dba_monitor.replication_health AS

SELECT

client_addr AS replica_address,

application_name AS replica_name,

state,

sent_lsn,

write_lsn,

flush_lsn,

replay_lsn,

-- Bytes of WAL not yet replayed on the standby

(sent_lsn - replay_lsn) AS replication_lag_bytes,

pg_size_pretty(sent_lsn - replay_lsn) AS replication_lag_pretty,

write_lag,

flush_lag,

replay_lag,

sync_state,

-- Flag replicas that are falling behind threshold

CASE

WHEN (sent_lsn - replay_lsn) > 536870912 -- 512 MB lag

THEN 'CRITICAL'

WHEN (sent_lsn - replay_lsn) > 104857600 -- 100 MB lag

THEN 'WARNING'

ELSE 'HEALTHY'

END AS lag_status

FROM pg_stat_replication

ORDER BY replication_lag_bytes DESC NULLS LAST;

-- View 4: Connection pool pressure

-- On RDS, max_connections is set by instance class and cannot exceed it.

-- db.r6g.large: max_connections ~ 683 (formula: LEAST(DBInstanceClassMemory/9531392, 5000))

-- If you are within 20% of max_connections, you need RDS Proxy or pgBouncer.

CREATE OR REPLACE VIEW dba_monitor.connection_pressure AS

SELECT

datname AS database_name,

numbackends AS active_connections,

xact_commit AS committed_transactions,

xact_rollback AS rolled_back_transactions,

ROUND(

xact_rollback::NUMERIC /

NULLIF(xact_commit + xact_rollback, 0) * 100, 2

) AS rollback_rate_pct,

blks_read AS physical_reads,

blks_hit AS buffer_hits,

ROUND(blks_hit::NUMERIC /

NULLIF(blks_hit + blks_read, 0) * 100, 2) AS db_buffer_hit_pct,

deadlocks,

temp_files,

temp_bytes,

pg_size_pretty(temp_bytes) AS temp_usage_pretty

FROM pg_stat_database

WHERE datname = current_database();

-- Composite dashboard query: run this to get a single-screen health snapshot

-- Useful for morning standup checks and on-call handoff summaries

SELECT

'TOP_QUERIES' AS metric_group,

cost_rank::TEXT AS rank,

query_preview AS detail,

mean_exec_time_ms::TEXT AS value,

'ms avg' AS unit,

execution_stability AS status

FROM dba_monitor.top_queries_by_cost

WHERE cost_rank <= 5

UNION ALL

SELECT

'REPLICATION',

replica_name,

state,

replication_lag_bytes::TEXT,

'bytes lag',

lag_status

FROM dba_monitor.replication_health

UNION ALL

SELECT

'TABLE_HEALTH',

table_name,

'dead_tuple_pct: ' || dead_tuple_pct::TEXT,

table_buffer_hit_pct::TEXT,

'% buffer hit',

CASE

WHEN dead_tuple_pct > 10 THEN 'BLOATED'

WHEN table_buffer_hit_pct < 95 THEN 'IO_PRESSURE'

ELSE 'HEALTHY'

END

FROM dba_monitor.table_io_and_bloat

WHERE dead_tuple_pct > 5 OR table_buffer_hit_pct < 95

LIMIT 10

ORDER BY metric_group, rank;

### 40.6 Reserved Capacity, Right-Sizing, and the 30-Day Review Cadence

The SQL views and CLI commands in this chapter give you the data. The 30-day review cadence is how you act on it. Cloud database cost optimization is not a one-time project — it is an operational habit, the same way on-premises DBAs ran index maintenance jobs and reviewed wait statistics weekly.

**The Right-Sizing Decision Framework**

Right-sizing is determining whether your provisioned instance class matches your actual workload. The failure mode almost every migrating team hits is provisioning based on peak on-premises hardware specifications and never revisiting it. An on-premises server with 256 GB RAM running at 30% utilization becomes a `db.r6g.16xlarge` ($5.73/hour) in RDS when a `db.r6g.2xlarge` ($0.96/hour) would handle the actual workload. The delta is approximately $3,000/month per instance.

**Right-sizing signals and thresholds:**

| Metric | Downsize Candidate | Correctly Sized | Upsize Needed |
|---|---|---|---|
| Average CPU (30-day) | < 20% | 20–70% | Sustained > 75% |
| FreeableMemory | Always > 4 GB free | 1–4 GB free | < 512 MB free |
| ReadIOPS vs. provisioned | < 40% of baseline | 40–80% | Sustained > 85% |
| DB load vs. vCPU count | < 0.5x vCPU | 0.5–0.8x vCPU | > 1x vCPU sustained |
| Max connections used | < 30% of max | 30–70% of max | > 80% of max |

When FreeableMemory is consistently above 4 GB on a `db.r6g.xlarge` (32 GB RAM), you have headroom to drop to `db.r6g.large` (16 GB RAM). Verify using 30-day CloudWatch data, not 7-day — you need to capture the end-of-month reporting spike, the weekly batch, and any irregular jobs before making the call.

**Aurora Serverless v2 as an Alternative to Right-Sizing**

For workloads with genuine variability — development environments, reporting databases that spike on business hours, staging systems — Aurora Serverless v2 eliminates the right-sizing problem by billing per ACU-second. A development Aurora cluster set to min 0.5 ACU, max 4 ACU costs essentially nothing overnight and scales during business hours. The gotcha: Aurora Serverless v2 has a minimum of 0.5 ACU, which still costs approximately $0.06/hour ($43/month) even when idle. For a completely idle environment, stopping the cluster entirely (RDS supports stopping instances for up to 7 days) is free.

**The 30-Day Cost and Performance Review Checklist**

Run this review on the first Monday of each month across all production database instances:

#!/usr/bin/env bash

# monthly_rds_cost_review.sh

# Run this script monthly to identify cost optimization opportunities.

# Requires: AWS CLI configured with read access to CloudWatch, RDS, and Cost Explorer.

set -euo pipefail

REGION="${AWS_DEFAULT_REGION:-us-east-1}"

LOOKBACK_DAYS=30

END_DATE=$(date '+%Y-%m-%d')

START_DATE=$(date -d "${LOOKBACK_DAYS} days ago" '+%Y-%m-%d')

echo "=============================================="

echo " Monthly RDS Cost and Performance Review"

echo " Period: ${START_DATE} to ${END_DATE}"

echo " Region: ${REGION}"

echo "=============================================="

echo ""

# 1. List all RDS instances and their classes

echo "--- Active RDS Instances ---"

aws rds describe-db-instances \

--region "${REGION}" \

--query 'DBInstances[?DBInstanceStatus==available].{

ID:DBInstanceIdentifier,

Class:DBInstanceClass,

Engine:Engine,

EngineVersion:EngineVersion,

Storage:AllocatedStorage,

StorageType:StorageType,

MultiAZ:MultiAZ,

PIEnabled:PerformanceInsightsEnabled

}' \

--output table

echo ""

# 2. Check for instances without mandatory tags (compliance gap)

echo "--- Instances Missing Required Tags ---"

aws rds describe-db-instances \

--region "${REGION}" \

--query 'DBInstances[?DBInstanceStatus==available].{

ID:DBInstanceIdentifier,

Tags:TagList

}' \

--output json | python3 -c "

import json, sys

REQUIRED_TAGS = {'team', 'application', 'environment', 'cost-center'}

data = json.load(sys.stdin)

missing_found = False

for instance in data:

tag_keys = {t['Key'] for t in instance.get('Tags', [])}

missing = REQUIRED_TAGS - tag_keys

if missing:

missing_found = True

print(f\" MISSING TAGS: {instance['ID']} — missing: {', '.join(sorted(missing))}\")

if not missing_found:

print(' All instances have required tags. Good.')

"

echo ""

# 3. Identify instances not covered by Reserved Instances

echo "--- Reserved Instance Coverage Check ---"

# Get active reservations

aws rds describe-reserved-db-instances \

--region "${REGION}" \

--query 'ReservedDBInstances[?State==active].{

Class:DBInstanceClass,

Engine:ProductDescription,

Count:DBInstanceCount,

ExpirationDate:EndTime

}' \

--output table

echo ""

echo " Compare the above reservations against active instances."

echo " Any provisioned instance class WITHOUT a matching reservation"

echo " is running at On-Demand price — typically 40-60% more expensive."

echo ""

# 4. Check for gp2 storage volumes that should be migrated to gp3

echo "--- Storage Type Audit (gp2 → gp3 migration candidates) ---"

aws rds describe-db-instances \

--region "${REGION}" \

--query 'DBInstances[?StorageType==gp2].{

ID:DBInstanceIdentifier,

StorageGB:AllocatedStorage,

StorageType:StorageType

}' \

--output json | python3 -c "

import json, sys

data = json.load(sys.stdin)

if not data:

print(' No gp2 instances found. All instances on gp3 or io1.')

else:

# gp2 vs gp3 cost difference:

# gp2: \$0.115/GB-month, IOPS scale with storage (3 IOPS/GB, max 16,000)

# gp3: \$0.115/GB-month, 3,000 IOPS baseline included FREE, up to 16,000 for \$0.02/IOPS

# For most workloads, gp3 costs the same or less and performs better.

print(' GP2 instances found — consider migrating to gp3:')

for i in data:

gp2_iops = min(i['StorageGB'] * 3, 16000)

print(f\" {i['ID']}: {i['StorageGB']} GB gp2 ({gp2_iops} IOPS via storage scaling)\")

print(f\" → gp3 would provide 3,000 IOPS baseline free, same storage cost\")

"

echo ""

# 5. RDS Cost breakdown from Cost Explorer (last 30 days)

echo "--- RDS Cost Breakdown (Last 30 Days) ---"

aws ce get-cost-and-usage \

--time-period "Start=${START_DATE},End=${END_DATE}" \

--granularity MONTHLY \

--filter '{"Dimensions":{"Key":"SERVICE","Values":["Amazon Relational Database Service"]}}' \

--group-by '[{"Type":"DIMENSION","Key":"USAGE_TYPE"}]' \

--metrics BlendedCost \

--query 'ResultsByTime[0].Groups[*].{

UsageType:Keys[0],

Cost:Metrics.BlendedCost.Amount

}' \

--output json | python3 -c "

import json, sys

data = json.load(sys.stdin)

data.sort(key=lambda x: float(x['Cost']), reverse=True)

total = sum(float(x['Cost']) for x in data)

print(f' Total RDS spend (30 days): \${total:.2f}')

print('')

print(f' {\"Usage Type\":<55} {\"Cost\":>10}')

print(' ' + '-' * 67)

for item in data[:15]:

cost = float(item['Cost'])

pct = cost / total * 100 if total > 0 else 0

print(f\" {item['UsageType']:<55} \${cost:>8.2f} ({pct:.1f}%)\")

"

echo ""

echo "=============================================="

echo " Review complete. Action items:"

echo " 1. Purchase Reserved Instances for unprotected On-Demand instances"

echo " 2. Migrate gp2 volumes to gp3"

echo " 3. Tag all untagged instances before next billing cycle"

echo " 4. Check Performance Insights for top queries on high-spend instances"

echo " 5. Validate right-sizing decisions against 30-day CloudWatch averages"

echo "=============================================="
