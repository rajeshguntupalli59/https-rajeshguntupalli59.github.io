Chapter 18: Multi-Tenant RAG: One Database, Many Customers

Building a RAG system for one tenant is a solved problem. Building one that serves hundreds of enterprise customers — each with their own documents, their own access controls, their own embedding models, and their own usage quotas — while sharing a single PostgreSQL cluster is a different animal entirely. This chapter walks through the complete architecture for multi-tenant RAG: how to partition knowledge, enforce isolation at the database level, handle per-tenant configuration, and scale embedding ingestion without turning your cluster into a bottleneck. PostgreSQL's combination of row-level security, pgvector, JSONB, and logical replication makes it uniquely suited to this problem in ways that purpose-built vector databases simply cannot match.

---

The Case for Shared Infrastructure

Before jumping into schema design, it's worth being explicit about why you'd run all tenants on the same PostgreSQL cluster rather than giving each tenant their own database or their own instance.

The naive approach — one database per customer — sounds appealing from an isolation perspective. It fails in practice for three reasons. First, PostgreSQL connection overhead multiplies badly: a hundred tenants each needing ten connections means a thousand connections before you've written a line of application code. Second, schema migrations become an operational nightmare — deploying a new embedding column means coordinating across a hundred databases simultaneously. Third, you lose cross-tenant analytics, aggregate billing queries, and system-wide monitoring that your operations team needs.

The shared-schema approach solves all three. One schema, one migration path, one connection pool. PostgreSQL's row-level security (RLS) gives you tenant isolation at the database engine level — not in application code, where it can be accidentally bypassed.

The key insight: tenant isolation in a shared schema is a database responsibility, not an application responsibility. When you enforce isolation via RLS policies on every table, even a buggy query that forgets a WHERE tenant_id = $1 clause returns zero rows instead of leaking data across customers. That guarantee is worth the schema complexity.

Schema Design: Tenants, Documents, and Vectors

The foundation is a tenant registry table that drives everything downstream. Every table in the system has a tenant_id foreign key that anchors rows to a specific customer.

-- Core tenant registry
CREATE TABLE tenants (
    tenant_id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            TEXT NOT NULL,
    slug            TEXT NOT NULL UNIQUE,
    plan            TEXT NOT NULL DEFAULT 'starter'
                    CHECK (plan IN ('starter', 'professional', 'enterprise')),
    embedding_model TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    llm_model       TEXT NOT NULL DEFAULT 'gpt-4o-mini',
    max_documents   INTEGER NOT NULL DEFAULT 1000,
    max_tokens_day  BIGINT NOT NULL DEFAULT 1000000,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_active       BOOLEAN NOT NULL DEFAULT TRUE
);

-- Per-tenant API credentials (encrypted at rest via pgcrypto)
CREATE TABLE tenant_api_keys (
    key_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id   UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    key_hash    TEXT NOT NULL UNIQUE,  -- SHA-256 of the actual key
    key_prefix  TEXT NOT NULL,         -- first 8 chars for display
    name        TEXT NOT NULL,
    scopes      TEXT[] NOT NULL DEFAULT ARRAY['read', 'write'],
    last_used   TIMESTAMPTZ,
    expires_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_active   BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE INDEX idx_tenant_api_keys_hash ON tenant_api_keys(key_hash);
CREATE INDEX idx_tenant_api_keys_tenant ON tenant_api_keys(tenant_id);

-- Document metadata — no vectors here, those live in a separate table
CREATE TABLE documents (
    document_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    title           TEXT NOT NULL,
    source_uri      TEXT,
    content_type    TEXT NOT NULL DEFAULT 'text/plain',
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending', 'processing', 'ready', 'failed', 'archived')),
    chunk_count     INTEGER NOT NULL DEFAULT 0,
    token_count     INTEGER NOT NULL DEFAULT 0,
    metadata        JSONB NOT NULL DEFAULT '{}',
    -- File-level hash to detect duplicate uploads
    content_hash    TEXT,
    ingested_at     TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_documents_tenant ON documents(tenant_id);
CREATE INDEX idx_documents_status ON documents(tenant_id, status);
CREATE INDEX idx_documents_content_hash ON documents(tenant_id, content_hash);

-- Chunks with embeddings — this is where pgvector lives
CREATE TABLE document_chunks (
    chunk_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    document_id     UUID NOT NULL REFERENCES documents(document_id) ON DELETE CASCADE,
    chunk_index     INTEGER NOT NULL,
    content         TEXT NOT NULL,
    token_count     INTEGER NOT NULL,
    embedding       VECTOR(1536),      -- OpenAI small / ada-002 compatible
    embedding_model TEXT NOT NULL,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (document_id, chunk_index)
);

-- HNSW index scoped by tenant — the magic that makes per-tenant search fast
-- We'll discuss the partitioning strategy for this index below
CREATE INDEX idx_chunks_embedding_hnsw ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

CREATE INDEX idx_chunks_tenant ON document_chunks(tenant_id);
CREATE INDEX idx_chunks_document ON document_chunks(document_id);

-- Conversation history — full context per tenant, per session
CREATE TABLE conversations (
    conversation_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    user_id         TEXT NOT NULL,     -- tenant's own user identifier
    title           TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_message_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_conversations_tenant_user ON conversations(tenant_id, user_id);

CREATE TABLE conversation_messages (
    message_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(conversation_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system')),
    content         TEXT NOT NULL,
    -- Track which chunks were used to generate this response
    source_chunk_ids UUID[],
    -- Token accounting
    prompt_tokens   INTEGER,
    completion_tokens INTEGER,
    model           TEXT,
    latency_ms      INTEGER,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_messages_conversation ON conversation_messages(conversation_id, created_at);
CREATE INDEX idx_messages_tenant ON conversation_messages(tenant_id);

-- Usage tracking for billing and quota enforcement
CREATE TABLE usage_events (
    event_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    event_type      TEXT NOT NULL,  -- 'embedding', 'completion', 'retrieval'
    tokens_used     INTEGER NOT NULL DEFAULT 0,
    model           TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Partition usage_events by month for query performance
CREATE INDEX idx_usage_tenant_date ON usage_events(tenant_id, created_at);

-- Audit log — immutable record of all data access
CREATE TABLE audit_log (
    log_id          BIGSERIAL PRIMARY KEY,
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id),
    actor_key_id    UUID REFERENCES tenant_api_keys(key_id),
    action          TEXT NOT NULL,
    resource_type   TEXT,
    resource_id     UUID,
    ip_address      INET,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_audit_tenant_time ON audit_log(tenant_id, created_at DESC);

Notice several design decisions embedded in this schema. The tenant_id column appears on every table — not just documents — so RLS policies can be applied uniformly without joining back to a parent table. The embedding_model column lives on both tenants (the default) and document_chunks (the actual model used) because tenants may change models over time and you need to know which model generated each vector for correct similarity comparisons. Usage events are a separate table rather than counters on the tenant row, which avoids lock contention and gives you a full audit trail for billing disputes.

Row-Level Security: Making Tenant Isolation Automatic

RLS is the load-bearing wall of the multi-tenant architecture. Once it's in place, every query — regardless of which application code path executes it — automatically scopes to the current tenant.

-- Enable RLS on all tenant-scoped tables
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE document_chunks ENABLE ROW LEVEL SECURITY;
ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;
ALTER TABLE conversation_messages ENABLE ROW LEVEL SECURITY;
ALTER TABLE usage_events ENABLE ROW LEVEL SECURITY;
ALTER TABLE audit_log ENABLE ROW LEVEL SECURITY;
ALTER TABLE tenant_api_keys ENABLE ROW LEVEL SECURITY;

-- Application role — this is what your FastAPI app connects as
CREATE ROLE app_user;
GRANT CONNECT ON DATABASE ragdb TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO app_user;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_user;

-- Admin role — bypasses RLS for migrations and ops
CREATE ROLE rag_admin BYPASSRLS;
GRANT ALL ON ALL TABLES IN SCHEMA public TO rag_admin;

-- The session variable that controls which tenant is active
-- Application sets this at the start of every connection/transaction
-- current_setting('app.tenant_id') returns the active tenant UUID

CREATE POLICY tenant_isolation_documents ON documents
    FOR ALL TO app_user
    USING (tenant_id = current_setting('app.tenant_id')::UUID)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::UUID);

    FOR ALL TO app_user

    WITH CHECK (tenant_id = current_setting('app.tenant_id')::UUID);

-- Helper function to set tenant context and validate the API key in one shot
CREATE OR REPLACE FUNCTION set_tenant_context(p_api_key TEXT)
RETURNS UUID AS $$
DECLARE
    v_tenant_id UUID;
    v_key_id    UUID;
    v_key_hash  TEXT;
BEGIN
    v_key_hash := encode(sha256(p_api_key::bytea), 'hex');

    SELECT t.tenant_id, k.key_id
    INTO v_tenant_id, v_key_id
    FROM tenant_api_keys k
    JOIN tenants t ON t.tenant_id = k.tenant_id
    WHERE k.key_hash = v_key_hash
      AND k.is_active = TRUE
      AND t.is_active = TRUE
      AND (k.expires_at IS NULL OR k.expires_at > NOW());

    IF v_tenant_id IS NULL THEN
        RAISE EXCEPTION 'Invalid or expired API key' USING ERRCODE = '28000';
    END IF;

    -- Set the session variable — all subsequent queries use this
    PERFORM set_config('app.tenant_id', v_tenant_id::TEXT, true);  -- true = transaction-local

    -- Update last_used asynchronously via trigger or background job
    UPDATE tenant_api_keys
    SET last_used = NOW()
    WHERE key_id = v_key_id;

    RETURN v_tenant_id;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- Quota check function — call before expensive operations
CREATE OR REPLACE FUNCTION check_tenant_quota(
    p_tenant_id UUID,
    p_tokens_needed INTEGER DEFAULT 0
)
RETURNS BOOLEAN AS $$
DECLARE
    v_tenant        tenants%ROWTYPE;
    v_doc_count     INTEGER;
    v_tokens_today  BIGINT;
BEGIN
    SELECT * INTO v_tenant FROM tenants WHERE tenant_id = p_tenant_id;

    SELECT COUNT(*) INTO v_doc_count
    FROM documents
    WHERE tenant_id = p_tenant_id
      AND status != 'archived';

    IF v_doc_count >= v_tenant.max_documents THEN
        RAISE EXCEPTION 'Document quota exceeded: % of % used',
            v_doc_count, v_tenant.max_documents
            USING ERRCODE = '53400';
    END IF;

    SELECT COALESCE(SUM(tokens_used), 0) INTO v_tokens_today
    FROM usage_events
    WHERE tenant_id = p_tenant_id
      AND created_at >= DATE_TRUNC('day', NOW());

    IF v_tokens_today + p_tokens_needed > v_tenant.max_tokens_day THEN
        RAISE EXCEPTION 'Daily token quota exceeded: % used, % limit',
            v_tokens_today, v_tenant.max_tokens_day
            USING ERRCODE = '53400';
    END IF;

    RETURN TRUE;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

The session variable app.tenant_id is the pivot point. Every connection — whether from PgBouncer, a direct FastAPI handler, or a background Celery worker — must call set_config('app.tenant_id', ...) before executing any data query. With transaction-local = true, the setting expires at the end of the transaction, which means a connection returned to the pool can't accidentally carry a previous tenant's context into the next request.

graph TD
    A[Request with X-API-Key] --> B[set_tenant_context]
    B --> C{Key valid + not expired?}
    C -->|no| D[Raise 28000: invalid API key]
    C -->|yes| E["set_config('app.tenant_id', tenant_id, true)"]
    E --> F[Query runs as app_user]
    F --> G[RLS policy: tenant_id = current_setting]
    G --> H[(Only this tenant's rows)]
    E -.transaction ends.-> I[Setting cleared before connection returns to pool]

*Every query on a pooled connection is scoped by a transaction-local session variable set at the start of the request — RLS enforces the filter regardless of what the application code remembers to do.*

Ingestion Pipeline: Per-Tenant Embeddings at Scale

Document ingestion is where multi-tenancy gets complicated. Different tenants use different embedding models. Some are on your free tier with a 1,000 document limit; others are enterprise customers ingesting 50,000 documents. You need a pipeline that's fair, observable, and resilient.

The architecture uses Celery for async task queuing with Redis as the broker, FastAPI for the upload endpoint, and PostgreSQL itself for task state tracking via pg_notify.

# ingestion/tasks.py — Celery tasks for multi-tenant embedding ingestion
import hashlib
import re
from typing import Optional
import asyncpg
import openai
import anthropic
from celery import Celery
from celery.utils.log import get_task_logger
import tiktoken
import uuid

logger = get_task_logger(__name__)

app = Celery(
    "rag_ingestion",
    broker="redis://localhost:6379/0",
    backend="redis://localhost:6379/1",
)

app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    task_routes={
        "ingestion.tasks.embed_document_enterprise": {"queue": "enterprise"},
        "ingestion.tasks.embed_document_standard": {"queue": "standard"},
    },
    worker_prefetch_multiplier=1,   # Don't grab more tasks than you can handle
    task_acks_late=True,            # Only ack after task completes successfully
)

DATABASE_URL = "postgresql://app_user:password@localhost/ragdb"

EMBEDDING_MODELS = {
    "text-embedding-3-small": {"dims": 1536, "provider": "openai"},
    "text-embedding-3-large": {"dims": 3072, "provider": "openai"},
    "text-embedding-ada-002":  {"dims": 1536, "provider": "openai"},
    # Claude chat models don't expose an embeddings endpoint; Voyage AI is
    # Anthropic's recommended third-party embeddings provider for tenants
    # who standardize on Claude for generation.
    "voyage-3": {"dims": 1024, "provider": "voyage"},
}

def chunk_text(text: str, max_tokens: int = 512, overlap_tokens: int = 50) -> list[dict]:
    """Split text into overlapping chunks with token counting."""
    enc = tiktoken.get_encoding("cl100k_base")
    tokens = enc.encode(text)
    chunks = []
    start = 0
    chunk_index = 0

    while start < len(tokens):
        end = min(start + max_tokens, len(tokens))
        chunk_tokens = tokens[start:end]
        chunk_text_str = enc.decode(chunk_tokens)

        chunks.append({
            "content": chunk_text_str,
            "token_count": len(chunk_tokens),
            "chunk_index": chunk_index,
        })

        if end == len(tokens):
            break

        start = end - overlap_tokens
        chunk_index += 1

    return chunks


async def get_embedding_openai(text: str, model: str) -> list[float]:
    client = openai.AsyncOpenAI()
    response = await client.embeddings.create(input=text, model=model)
    return response.data[0].embedding


async def get_embedding_anthropic(text: str) -> list[float]:
    # Claude has no native embeddings endpoint, so tenants standardized on
    # Claude for generation use Voyage AI (Anthropic's recommended
    # third-party embeddings provider) for the embedding step instead.
    import voyageai
    client = voyageai.AsyncClient()
    result = await client.embed([text], model="voyage-3")
    return result.embeddings[0]


async def embed_chunks_batch(
    chunks: list[dict],
    model: str,
    provider: str,
    batch_size: int = 100,
) -> list[list[float]]:
    """Embed chunks in batches to respect API rate limits."""
    embeddings = []
    for i in range(0, len(chunks), batch_size):
        batch = chunks[i : i + batch_size]
        texts = [c["content"] for c in batch]

        if provider == "openai":
            client = openai.AsyncOpenAI()
            response = await client.embeddings.create(input=texts, model=model)
            batch_embeddings = [item.embedding for item in response.data]
        elif provider == "voyage":
            import voyageai
            client = voyageai.AsyncClient()
            result = await client.embed(texts, model="voyage-3")
            batch_embeddings = result.embeddings

        embeddings.extend(batch_embeddings)

    return embeddings


@app.task(
    bind=True,
    max_retries=3,
    default_retry_delay=60,
    name="ingestion.tasks.embed_document_enterprise",
)
def embed_document_enterprise(self, document_id: str, tenant_id: str):

    return _process_document(self, document_id, tenant_id)


@app.task(
    bind=True,
    max_retries=3,
    default_retry_delay=120,
    name="ingestion.tasks.embed_document_standard",

    """Standard ingestion for free/professional tenants."""
    return _process_document(self, document_id, tenant_id)


import asyncio

def _process_document(task_instance, document_id: str, tenant_id: str):
    """Core ingestion logic — shared between priority queues."""
    return asyncio.get_event_loop().run_until_complete(
        _process_document_async(task_instance, document_id, tenant_id)
    )


async def _process_document_async(task_instance, document_id: str, tenant_id: str):
    conn = await asyncpg.connect(DATABASE_URL)
    try:
        # Bypass RLS for internal worker — set admin context
        await conn.execute("SET ROLE rag_admin")

        # Fetch document and tenant config
        row = await conn.fetchrow(
            """
            SELECT d.document_id, d.content_type, d.metadata,
                   t.embedding_model, t.plan, t.tenant_id
            FROM documents d
            JOIN tenants t ON t.tenant_id = d.tenant_id
            WHERE d.document_id = $1 AND d.tenant_id = $2 AND d.status = 'pending'
            """,
            uuid.UUID(document_id),
            uuid.UUID(tenant_id),
        )

        if not row:
            logger.warning(f"Document {document_id} not found or already processed")
            return {"status": "skipped"}

        # Mark as processing
        await conn.execute(
            "UPDATE documents SET status = 'processing', updated_at = NOW() WHERE document_id = $1",
            uuid.UUID(document_id),
        )

        # Notify the application layer that processing started
        await conn.execute(
            "SELECT pg_notify($1, $2)",
            f"document_status_{tenant_id}",
            f'{{"document_id": "{document_id}", "status": "processing"}}',
        )

        # Retrieve raw content from metadata (stored path or inline text)
        raw_content = row["metadata"].get("raw_text", "")
        if not raw_content:
            logger.error(f"No raw text found for document {document_id}")
            await conn.execute(
                "UPDATE documents SET status = 'failed', updated_at = NOW() WHERE document_id = $1",
                uuid.UUID(document_id),
            )
            return {"status": "failed", "reason": "no_content"}

        # Chunk the document
        chunks = chunk_text(raw_content, max_tokens=512, overlap_tokens=50)
        logger.info(f"Document {document_id}: {len(chunks)} chunks")

        # Embed all chunks
        model = row["embedding_model"]
        provider_info = EMBEDDING_MODELS.get(model, {"dims": 1536, "provider": "openai"})
        provider = provider_info["provider"]

        embeddings = await embed_chunks_batch(chunks, model, provider)

        # Insert chunks and embeddings in a single transaction
        async with conn.transaction():
            # Delete any stale chunks from a previous failed attempt
            await conn.execute(
                "DELETE FROM document_chunks WHERE document_id = $1",
                uuid.UUID(document_id),
            )

            total_tokens = 0
            for chunk, embedding in zip(chunks, embeddings):
                await conn.execute(
                    """
                    INSERT INTO document_chunks
                        (chunk_id, tenant_id, document_id, chunk_index,
                         content, token_count, embedding, embedding_model)
                    VALUES
                        (gen_random_uuid(), $1, $2, $3, $4, $5, $6::vector, $7)
                    """,
                    uuid.UUID(tenant_id),
                    uuid.UUID(document_id),
                    chunk["chunk_index"],
                    chunk["content"],
                    chunk["token_count"],
                    str(embedding),   # asyncpg passes vector as text; pgvector casts it
                    model,
                )
                total_tokens += chunk["token_count"]

            # Update document status and counters
            await conn.execute(
                """
                UPDATE documents
                SET status = 'ready',
                    chunk_count = $2,
                    token_count = $3,
                    ingested_at = NOW(),
                    updated_at  = NOW()
                WHERE document_id = $1
                """,
                uuid.UUID(document_id),
                len(chunks),
                total_tokens,
            )

            # Record a usage event for billing
            await conn.execute(
                """
                INSERT INTO usage_events (tenant_id, event_type, tokens_used, model)
                VALUES ($1, 'embedding', $2, $3)
                """,
                uuid.UUID(tenant_id),
                total_tokens,
                model,
            )

        # Notify success
        await conn.execute(
            "SELECT pg_notify($1, $2)",
            f"document_status_{tenant_id}",
            f'{{"document_id": "{document_id}", "status": "ready", "chunks": {len(chunks)}}}',
        )

        logger.info(f"Document {document_id} ingested: {len(chunks)} chunks, {total_tokens} tokens")
        return {"status": "ready", "chunks": len(chunks), "tokens": total_tokens}

    except Exception as exc:
        logger.exception(f"Ingestion failed for document {document_id}: {exc}")
        await conn.execute(
            "UPDATE documents SET status = 'failed', updated_at = NOW() WHERE document_id = $1",
            uuid.UUID(document_id),
        )
        raise task_instance.retry(exc=exc)

    finally:
        await conn.close()

The routing logic that decides which queue gets the task lives in the upload endpoint:

# api/upload.py — FastAPI document upload endpoint
from fastapi import FastAPI, UploadFile, File, Header, HTTPException, Depends
from fastapi.responses import JSONResponse
import asyncpg
import hashlib
import uuid

app_api = FastAPI()

async def get_db():
    conn = await asyncpg.connect("postgresql://app_user:password@localhost/ragdb")
    try:
        yield conn
    finally:
        await conn.close()

async def authenticate_tenant(x_api_key: str = Header(...), conn=Depends(get_db)):
    """Authenticate API key and set tenant context on the connection."""
    try:
        tenant_id = await conn.fetchval(
            "SELECT set_tenant_context($1)", x_api_key
        )
        return tenant_id
    except asyncpg.exceptions.InvalidAuthorizationSpecificationError:
        raise HTTPException(status_code=401, detail="Invalid API key")

@app_api.post("/documents/upload")
async def upload_document(
    file: UploadFile = File(...),
    tenant_id: uuid.UUID = Depends(authenticate_tenant),
    conn=Depends(get_db),
):
    content = await file.read()
    raw_text = content.decode("utf-8", errors="replace")
    content_hash = hashlib.sha256(content).hexdigest()

    # Check for duplicate
    existing = await conn.fetchrow(
        "SELECT document_id FROM documents WHERE tenant_id = $1 AND content_hash = $2",
        tenant_id, content_hash,
    )
    if existing:
        return JSONResponse(
            status_code=200,
            content={"document_id": str(existing["document_id"]), "status": "duplicate"},
        )

    # Quota check
    await conn.execute("SELECT check_tenant_quota($1, $2)", tenant_id, len(raw_text.split()))

    # Create document record
    document_id = await conn.fetchval(
        """
        INSERT INTO documents (tenant_id, title, content_hash, metadata)
        VALUES ($1, $2, $3, $4)
        RETURNING document_id
        """,
        tenant_id,
        file.filename,
        content_hash,
        {"raw_text": raw_text},  # Stored inline here; prod should use object storage
    )

    # Fetch plan to determine queue priority
    plan = await conn.fetchval(
        "SELECT plan FROM tenants WHERE tenant_id = $1", tenant_id
    )

    # Route to the correct Celery queue
    if plan == "enterprise":
        from ingestion.tasks import embed_document_enterprise
        embed_document_enterprise.apply_async(
            args=[str(document_id), str(tenant_id)],
            queue="enterprise",
        )
    else:
        from ingestion.tasks import embed_document_standard
        embed_document_standard.apply_async(
            args=[str(document_id), str(tenant_id)],
            queue="standard",
        )

    return JSONResponse(
        status_code=202,
        content={"document_id": str(document_id), "status": "pending"},
    )

Enterprise tenants get a dedicated Celery queue with more workers allocated to it. Standard tenants share a second queue. This prevents a single large tenant from starving smaller ones and gives you a straightforward lever for SLA differentiation without complex scheduling logic.

Multi-Tenant Retrieval: Vector Search with RLS

The retrieval path is simpler than ingestion, but it has its own subtleties. The HNSW index on document_chunks is shared across all tenants, which means a nearest-neighbor scan will explore vectors from every tenant before the RLS filter narrows results. For a cluster where one tenant has millions of chunks and another has a hundred, this can feel unfair — the small tenant's query touches the large tenant's index entries even though they'll be filtered out.

There are two mitigation strategies: partition the table by tenant_id (PostgreSQL table partitioning), or accept the HNSW overhead and tune ef_search to return enough candidates that filtered results are still good quality. For most deployments with fewer than a few hundred tenants, the simpler shared-index approach is sufficient. The partition approach makes sense when individual tenants are large enough to justify their own HNSW index segments.

Here is the core retrieval function that runs inside PostgreSQL, callable from application code:

-- Similarity search scoped to the current tenant context
CREATE OR REPLACE FUNCTION search_chunks(
    p_query_embedding    VECTOR(1536),
    p_match_count        INTEGER DEFAULT 5,
    p_similarity_threshold FLOAT DEFAULT 0.7,
    p_document_ids       UUID[] DEFAULT NULL,   -- optional filter to specific docs
    p_metadata_filter    JSONB DEFAULT NULL      -- optional metadata predicate
)
RETURNS TABLE (
    chunk_id        UUID,
    document_id     UUID,
    chunk_index     INTEGER,
    content         TEXT,
    similarity      FLOAT,
    document_title  TEXT,
    metadata        JSONB
) AS $$
BEGIN
    RETURN QUERY
    SELECT
        dc.chunk_id,
        dc.document_id,
        dc.chunk_index,
        dc.content,
        1 - (dc.embedding <=> p_query_embedding) AS similarity,
        d.title AS document_title,
        dc.metadata
    FROM document_chunks dc
    JOIN documents d ON d.document_id = dc.document_id
    WHERE
        -- RLS enforces tenant_id match; this explicit filter helps the planner
        -- use the tenant index before touching the HNSW index
        dc.tenant_id = current_setting('app.tenant_id')::UUID
        AND d.status = 'ready'
        AND (p_document_ids IS NULL OR dc.document_id = ANY(p_document_ids))
        AND (p_metadata_filter IS NULL OR dc.metadata @> p_metadata_filter)
        AND 1 - (dc.embedding <=> p_query_embedding) >= p_similarity_threshold
    ORDER BY dc.embedding <=> p_query_embedding
    LIMIT p_match_count;
END;
$$ LANGUAGE plpgsql STABLE SECURITY DEFINER;

On the Python side, the retrieval call is straightforward because the heavy lifting happens in the database:

# retrieval/search.py
import asyncpg
import openai
import uuid
from typing import Optional

async def retrieve_chunks(
    conn: asyncpg.Connection,
    query: str,
    tenant_id: uuid.UUID,
    embedding_model: str,
    match_count: int = 5,
    similarity_threshold: float = 0.7,
    document_ids: Optional[list[uuid.UUID]] = None,
    metadata_filter: Optional[dict] = None,
) -> list[dict]:
    """
    Embed the query using the tenant's configured model, then
    call search_chunks() to retrieve the nearest neighbors.
    """
    # Generate query embedding using the tenant's model
    oai = openai.AsyncOpenAI()
    resp = await oai.embeddings.create(input=query, model=embedding_model)
    query_embedding = resp.data[0].embedding
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

    rows = await conn.fetch(
        "SELECT * FROM search_chunks($1::vector, $2, $3, $4, $5)",
        embedding_str,
        match_count,
        similarity_threshold,
        document_ids,
        metadata_filter,
    )

    return [dict(r) for r in rows]

One detail deserves attention: the query embedding must use the same model that was used during ingestion. Because different tenants may use different models, the function reads the tenant's embedding_model from the tenants table before calling the embedding API. If a tenant switches models, existing chunks retain their old embeddings and will produce incorrect similarity scores against new-model query vectors. The correct handling is to mark all existing chunks for re-embedding and process them through the ingestion pipeline again — a one-time migration cost, not an ongoing operational burden.

Hybrid Search: Combining Vector and Full-Text Retrieval

Pure vector search misses exact keyword matches that happen to have low cosine similarity. A tenant searching for a specific product code, a proper noun, or a technical acronym will get poor results from embedding search alone. Hybrid search — combining pgvector's ANN results with PostgreSQL's built-in full-text search — dramatically improves retrieval quality.

-- Add full-text search index to document_chunks
ALTER TABLE document_chunks ADD COLUMN content_tsv TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('english', content)) STORED;

CREATE INDEX idx_chunks_fts ON document_chunks USING GIN(content_tsv);

-- Hybrid search with Reciprocal Rank Fusion (RRF)
-- RRF score = sum of 1 / (rank + k) across all result lists
CREATE OR REPLACE FUNCTION search_chunks_hybrid(
    p_query_embedding       VECTOR(1536),
    p_query_text            TEXT,
    p_match_count           INTEGER DEFAULT 5,
    p_rrf_k                 INTEGER DEFAULT 60,  -- RRF constant; 60 is standard
    p_vector_weight         FLOAT   DEFAULT 0.7,
    p_fts_weight            FLOAT   DEFAULT 0.3
)
RETURNS TABLE (
    chunk_id        UUID,
    document_id     UUID,
    content         TEXT,
    rrf_score       FLOAT,
    vector_rank     INTEGER,
    fts_rank        INTEGER,
    document_title  TEXT
) AS $$
WITH vector_results AS (
    SELECT
        dc.chunk_id,
        dc.document_id,
        dc.content,
        ROW_NUMBER() OVER (ORDER BY dc.embedding <=> p_query_embedding) AS rank
    FROM document_chunks dc
    JOIN documents d ON d.document_id = dc.document_id
    WHERE dc.tenant_id = current_setting('app.tenant_id')::UUID
      AND d.status = 'ready'
    ORDER BY dc.embedding <=> p_query_embedding
    LIMIT p_match_count * 4  -- Fetch more candidates before fusion
),
fts_results AS (
    SELECT
        dc.chunk_id,
        dc.document_id,
        dc.content,
        ROW_NUMBER() OVER (
            ORDER BY ts_rank_cd(dc.content_tsv, query) DESC
        ) AS rank
    FROM document_chunks dc
    JOIN documents d ON d.document_id = dc.document_id,
    to_tsquery('english', regexp_replace(p_query_text, '\s+', ' & ', 'g')) AS query
    WHERE dc.tenant_id = current_setting('app.tenant_id')::UUID
      AND d.status = 'ready'
      AND dc.content_tsv @@ query
    LIMIT p_match_count * 4
),
fused AS (
    SELECT
        COALESCE(v.chunk_id, f.chunk_id)       AS chunk_id,
        COALESCE(v.document_id, f.document_id) AS document_id,
        COALESCE(v.content, f.content)         AS content,
        COALESCE(v.rank, p_match_count * 4 + 1) AS vector_rank,
        COALESCE(f.rank, p_match_count * 4 + 1) AS fts_rank,
        p_vector_weight * (1.0 / (p_rrf_k + COALESCE(v.rank, p_match_count * 4 + 1)))
        + p_fts_weight  * (1.0 / (p_rrf_k + COALESCE(f.rank, p_match_count * 4 + 1)))
            AS rrf_score
    FROM vector_results v
    FULL OUTER JOIN fts_results f USING (chunk_id)
)
SELECT
    fused.chunk_id,
    fused.document_id,
    fused.content,
    fused.rrf_score,
    fused.vector_rank::INTEGER,
    fused.fts_rank::INTEGER,
    d.title AS document_title
FROM fused
JOIN documents d ON d.document_id = fused.document_id
ORDER BY fused.rrf_score DESC
LIMIT p_match_count;
$$ LANGUAGE SQL STABLE SECURITY DEFINER;

RRF is preferable to a weighted sum of raw scores because it's robust to score scale differences between retrieval methods. The vector similarity score and the ts_rank_cd score live on completely different numeric scales; adding them directly produces unpredictable results. RRF works on ranks instead, which are always integers starting at 1, making the fusion deterministic and tunable via the k constant alone.

The p_vector_weight and p_fts_weight parameters let per-tenant configuration tune the balance. A tenant whose knowledge base is full of dense prose benefits from higher vector weight; a tenant with structured data, product SKUs, and version numbers benefits from higher FTS weight. Store these in the tenants.metadata JSONB column and read them at query time.

Per-Tenant Configuration and Model Routing

Enterprise customers frequently want control over which LLM generates their responses — some have vendor agreements, some have data residency requirements, some want Claude for its longer context window, others want GPT-4o for its multimodal capabilities. The tenants table already stores llm_model, but you need a router in application code that translates model names into the correct API client.

# generation/router.py — model-agnostic LLM response generation
from typing import AsyncIterator
import openai
import anthropic

OPENAI_MODELS = {
    "gpt-4o", "gpt-4o-mini", "gpt-4-turbo",
    "gpt-3.5-turbo",
}

ANTHROPIC_MODELS = {
    "claude-opus-4-5", "claude-sonnet-4-5",
    "claude-haiku-3-5", "claude-3-5-sonnet-20241022",
}

async def generate_response(
    messages: list[dict],
    model: str,
    max_tokens: int = 1024,
    temperature: float = 0.1,
    stream: bool = False,
) -> dict:
    """
    Route a completion request to the correct provider based on model name.
    Returns a normalized response dict with content, prompt_tokens, completion_tokens.
    """
    if model in OPENAI_MODELS:
        return await _openai_completion(messages, model, max_tokens, temperature, stream)
    elif model in ANTHROPIC_MODELS:
        return await _anthropic_completion(messages, model, max_tokens, temperature, stream)
    else:
        raise ValueError(f"Unknown model: {model}. Add it to the router.")


async def _openai_completion(messages, model, max_tokens, temperature, stream):
    client = openai.AsyncOpenAI()
    if stream:
        # Return an async generator for streaming
        async def _stream():
            async with client.chat.completions.stream(
                model=model,
                messages=messages,
                max_tokens=max_tokens,
                temperature=temperature,
            ) as s:
                async for chunk in s:
                    delta = chunk.choices[0].delta.content
                    if delta:
                        yield delta

        return {"stream": _stream()}

    response = await client.chat.completions.create(
        model=model,
        messages=messages,
        max_tokens=max_tokens,
        temperature=temperature,
    )
    return {
        "content": response.choices[0].message.content,
        "prompt_tokens": response.usage.prompt_tokens,
        "completion_tokens": response.usage.completion_tokens,
        "model": model,
    }


async def _anthropic_completion(messages, model, max_tokens, temperature, stream):
    client = anthropic.AsyncAnthropic()

    # Anthropic expects system prompt as a separate param, not in messages list
    system_msg = next((m["content"] for m in messages if m["role"] == "system"), None)
    user_messages = [m for m in messages if m["role"] != "system"]

    kwargs = dict(
        model=model,
        max_tokens=max_tokens,
        temperature=temperature,
        messages=user_messages,
    )
    if system_msg:
        kwargs["system"] = system_msg

    if stream:
        async def _stream():
            async with client.messages.stream(**kwargs) as s:
                async for text in s.text_stream:
                    yield text

        return {"stream": _stream()}

    response = await client.messages.create(**kwargs)
    return {
        "content": response.content[0].text,
        "prompt_tokens": response.usage.input_tokens,
        "completion_tokens": response.usage.output_tokens,
        "model": model,
    }

This router is intentionally thin — it normalizes the interface between providers so that the RAG query handler above it doesn't need to know which provider it's talking to. Adding a new provider (Gemini, a self-hosted Ollama instance, a fine-tuned model endpoint) requires adding a new routing branch and a new _provider_completion function, with no changes to the retrieval or context-building logic.

The Full RAG Query Handler

With retrieval and generation separated into clean modules, the query handler assembles them:

# api/query.py — the main RAG endpoint
import time
import uuid
import asyncpg
import openai
from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel
from typing import Optional

from retrieval.search import retrieve_chunks
from generation.router import generate_response

router = APIRouter()

class QueryRequest(BaseModel):
    query: str
    conversation_id: Optional[uuid.UUID] = None
    match_count: int = 5
    use_hybrid: bool = True
    document_ids: Optional[list[uuid.UUID]] = None
    metadata_filter: Optional[dict] = None
    stream: bool = False

class QueryResponse(BaseModel):
    answer: str
    conversation_id: uuid.UUID
    message_id: uuid.UUID
    source_chunks: list[dict]
    prompt_tokens: int
    completion_tokens: int
    latency_ms: int

RAG_SYSTEM_PROMPT = """You are a helpful assistant. Answer the user's question
using ONLY the provided context. If the context does not contain enough information
to answer the question, say so clearly. Do not fabricate information.

Context:
{context}
"""

@router.post("/query", response_model=QueryResponse)
async def rag_query(
    request: QueryRequest,
    tenant_id: uuid.UUID = Depends(authenticate_tenant),
    conn: asyncpg.Connection = Depends(get_db),
):
    start_time = time.monotonic()

    # Fetch tenant config in one query
    tenant = await conn.fetchrow(
        "SELECT embedding_model, llm_model, metadata FROM tenants WHERE tenant_id = $1",
        tenant_id,
    )
    if not tenant:
        raise HTTPException(status_code=404, detail="Tenant not found")

    embedding_model = tenant["embedding_model"]
    llm_model = tenant["llm_model"]

    # Per-tenant retrieval tuning from metadata
    vector_weight = float(tenant["metadata"].get("vector_weight", 0.7))
    fts_weight = float(tenant["metadata"].get("fts_weight", 0.3))
    similarity_threshold = float(tenant["metadata"].get("similarity_threshold", 0.65))

    # Retrieve relevant chunks
    if request.use_hybrid:
        # Embed the query once up front so both the vector and FTS legs of
        # search_chunks_hybrid() run in the same call — avoids a second
        # embedding API round trip.
        oai = openai.AsyncOpenAI()
        query_embedding_resp = await oai.embeddings.create(
            input=request.query, model=embedding_model
        )
        query_embedding_str = (
            "[" + ",".join(str(x) for x in query_embedding_resp.data[0].embedding) + "]"
        )
        rows = await conn.fetch(
            "SELECT * FROM search_chunks_hybrid($1::vector, $2, $3, 60, $4, $5)",
            query_embedding_str,
            request.query,
            request.match_count,
            vector_weight,
            fts_weight,
        )
    else:
        rows = await retrieve_chunks(
            conn=conn,
            query=request.query,
            tenant_id=tenant_id,
            embedding_model=embedding_model,
            match_count=request.match_count,
            similarity_threshold=similarity_threshold,
            document_ids=request.document_ids,
            metadata_filter=request.metadata_filter,
        )

    source_chunks = [dict(r) for r in rows]

    # Build context string
    context = "\n\n---\n\n".join(
        f"[Source: {c['document_title']}, chunk {c.get('chunk_index', '')}]\n{c['content']}"
        for c in source_chunks
    )

    # Retrieve conversation history
    conversation_id = request.conversation_id
    if conversation_id is None:
        conversation_id = await conn.fetchval(
            """
            INSERT INTO conversations (tenant_id, user_id)
            VALUES ($1, 'anonymous')
            RETURNING conversation_id
            """,
            tenant_id,
        )

    prior_messages = await conn.fetch(
        """
        SELECT role, content FROM conversation_messages
        WHERE conversation_id = $1
        ORDER BY created_at
        LIMIT 20
        """,
        conversation_id,
    )

    # Assemble the prompt
    messages = [
        {"role": "system", "content": RAG_SYSTEM_PROMPT.format(context=context)}
    ]
    for msg in prior_messages:
        messages.append({"role": msg["role"], "content": msg["content"]})
    messages.append({"role": "user", "content": request.query})

    # Generate the response
    result = await generate_response(
        messages=messages,
        model=llm_model,
        max_tokens=1024,
        temperature=0.1,
    )

    answer = result["content"]
    prompt_tokens = result["prompt_tokens"]
    completion_tokens = result["completion_tokens"]
    latency_ms = int((time.monotonic() - start_time) * 1000)

    # Persist the exchange
    async with conn.transaction():
        # User message
        await conn.execute(
            """
            INSERT INTO conversation_messages
                (conversation_id, tenant_id, role, content)
            VALUES ($1, $2, 'user', $3)
            """,
            conversation_id, tenant_id, request.query,
        )

        # Assistant message
        message_id = await conn.fetchval(
            """
            INSERT INTO conversation_messages
                (conversation_id, tenant_id, role, content,
                 source_chunk_ids, prompt_tokens, completion_tokens, model, latency_ms)
            VALUES ($1, $2, 'assistant', $3, $4, $5, $6, $7, $8)
            RETURNING message_id
            """,
            conversation_id, tenant_id, answer,
            [c["chunk_id"] for c in source_chunks],
            prompt_tokens, completion_tokens, llm_model, latency_ms,
        )

        # Update conversation timestamp
        await conn.execute(
            "UPDATE conversations SET last_message_at = NOW() WHERE conversation_id = $1",
            conversation_id,
        )

        # Record usage
        await conn.execute(
            """
            INSERT INTO usage_events (tenant_id, event_type, tokens_used, model)
            VALUES ($1, 'completion', $2, $3)
            """,
            tenant_id, prompt_tokens + completion_tokens, llm_model,
        )

    return QueryResponse(
        answer=answer,
        conversation_id=conversation_id,
        message_id=message_id,
        source_chunks=source_chunks,
        prompt_tokens=prompt_tokens,
        completion_tokens=completion_tokens,
        latency_ms=latency_ms,
    )

Monitoring and Observability Across Tenants

Operating a multi-tenant system without per-tenant observability is flying blind. You need to know which tenants are hitting quota, which have slow retrieval, which are generating errors, and which are growing fastest.

PostgreSQL's own tables are a rich source of this data. The following queries give you a live operations dashboard without any external monitoring infrastructure:

-- Per-tenant usage summary for the last 30 days
SELECT
    t.name,
    t.plan,
    COUNT(DISTINCT d.document_id)               AS total_documents,
    SUM(d.chunk_count)                           AS total_chunks,
    COALESCE(SUM(ue.tokens_used), 0)             AS tokens_30d,
    t.max_tokens_day * 30                        AS token_quota_30d,
    ROUND(
        100.0 * COALESCE(SUM(ue.tokens_used), 0)
        / NULLIF(t.max_tokens_day * 30, 0), 1
    )                                            AS quota_pct_used
FROM tenants t
LEFT JOIN documents d ON d.tenant_id = t.tenant_id AND d.status != 'archived'
LEFT JOIN usage_events ue ON ue.tenant_id = t.tenant_id
    AND ue.created_at >= NOW() - INTERVAL '30 days'
WHERE t.is_active
GROUP BY t.tenant_id, t.name, t.plan, t.max_tokens_day
ORDER BY tokens_30d DESC;

-- Retrieval latency percentiles by tenant (from conversation_messages)
SELECT
    t.name,
    t.plan,
    COUNT(*)                                        AS total_queries,
    PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY m.latency_ms) AS p50_ms,
    PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY m.latency_ms) AS p95_ms,
    PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY m.latency_ms) AS p99_ms
FROM conversation_messages m
JOIN conversations c ON c.conversation_id = m.conversation_id
JOIN tenants t ON t.tenant_id = m.tenant_id
WHERE m.role = 'assistant'
  AND m.created_at >= NOW() - INTERVAL '7 days'
GROUP BY t.tenant_id, t.name, t.plan
ORDER BY p95_ms DESC;

-- Documents stuck in processing (potential ingestion failures)
SELECT
    t.name,
    d.document_id,
    d.title,
    d.status,
    d.updated_at,
    NOW() - d.updated_at AS stuck_for
FROM documents d
JOIN tenants t ON t.tenant_id = d.tenant_id
WHERE d.status IN ('pending', 'processing')
  AND d.updated_at < NOW() - INTERVAL '10 minutes'
ORDER BY d.updated_at;

-- Tenants approaching document quota
SELECT
    t.name,
    t.plan,
    COUNT(d.document_id)    AS doc_count,
    t.max_documents          AS doc_limit,
    ROUND(100.0 * COUNT(d.document_id) / t.max_documents, 1) AS pct_used
FROM tenants t
LEFT JOIN documents d ON d.tenant_id = t.tenant_id AND d.status != 'archived'
WHERE t.is_active
GROUP BY t.tenant_id, t.name, t.plan, t.max_documents
HAVING COUNT(d.document_id) >= 0.8 * t.max_documents
ORDER BY pct_used DESC;

These queries run efficiently because every join is anchored to the tenant_id index, and the usage_events table's time-range index makes rolling aggregations fast. For external monitoring, export these results to Prometheus via postgres_exporter custom queries, or pipe them into Grafana using the PostgreSQL data source directly.

Scaling Considerations: When One Cluster Isn't Enough

A single primary PostgreSQL instance with pgvector will serve most multi-tenant RAG deployments until the vector index grows large enough that memory pressure becomes the dominant constraint. The HNSW index ideally fits entirely in shared_buffers or the operating system page cache; once it doesn't, every ANN query starts hitting disk, and latency degrades sharply.

Several scaling levers are available before you need to shard:

Read replicas via logical replication. Route all search_chunks queries to one or more streaming replicas. The embedding index is replicated along with the data. Write traffic (ingestion) stays on the primary; read traffic (retrieval) distributes across replicas. PgBouncer in front of the replica pool makes this transparent to the application — write connections go to primary DSN, read connections go to replica DSN.

Partitioning document_chunks by tenant_id. PostgreSQL range or hash partitioning lets large tenants occupy their own partition with a dedicated HNSW index. The query planner automatically prunes to the correct partition based on the tenant_id filter, so small tenants pay no overhead for the large tenant's vectors. The trade-off is operational complexity: partition management requires tooling, and adding a new partition for a fast-growing tenant is a planned operation, not automatic.

Archiving cold tenants. Inactive tenants whose documents haven't been queried in months can have their chunks exported to object storage and their rows removed from the hot table. A re-activation API re-ingests documents on demand. This keeps the hot HNSW index compact and fast for active tenants without permanently deleting data.

Dedicated pgvector instances for very large tenants. When a single enterprise tenant's corpus is large enough to dominate the shared cluster — say, tens of millions of chunks — it may make operational sense to provision a separate PostgreSQL instance for that tenant alone and route requests via the model router. The application-level tenant context mechanism stays the same; only the database DSN changes. This is the "escape hatch" that lets you preserve the shared-schema architecture for the long tail of tenants while giving hyperscale tenants their own hardware.

Here is the partitioning setup for deployments that need it:

-- Partition document_chunks by tenant hash for large deployments
-- This replaces the unpartitioned table above.

CREATE TABLE document_chunks_partitioned (
    chunk_id        UUID NOT NULL DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL REFERENCES tenants(tenant_id) ON DELETE CASCADE,
    document_id     UUID NOT NULL,
    chunk_index     INTEGER NOT NULL,
    content         TEXT NOT NULL,
    token_count     INTEGER NOT NULL,
    embedding       VECTOR(1536),
    embedding_model TEXT NOT NULL,
    metadata        JSONB NOT NULL DEFAULT '{}',
    content_tsv     TSVECTOR GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (document_id, chunk_index, tenant_id)
) PARTITION BY HASH (tenant_id);

-- Create 8 hash partitions — tune to your tenant count and server count
CREATE TABLE document_chunks_p0 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE document_chunks_p1 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 1);
CREATE TABLE document_chunks_p2 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 2);
CREATE TABLE document_chunks_p3 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 3);
CREATE TABLE document_chunks_p4 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 4);
CREATE TABLE document_chunks_p5 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 5);
CREATE TABLE document_chunks_p6 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 6);
CREATE TABLE document_chunks_p7 PARTITION OF document_chunks_partitioned
    FOR VALUES WITH (MODULUS 8, REMAINDER 7);

-- Each partition gets its own HNSW index
-- This means ANN searches on a pruned partition are faster and the
-- index for each partition stays smaller, fitting more easily in cache.
CREATE INDEX idx_chunks_p0_hnsw ON document_chunks_p0
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX idx_chunks_p1_hnsw ON document_chunks_p1
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
-- ... repeat for p2 through p7

-- Per-partition FTS indexes
CREATE INDEX idx_chunks_p0_fts ON document_chunks_p0 USING GIN(content_tsv);
CREATE INDEX idx_chunks_p1_fts ON document_chunks_p1 USING GIN(content_tsv);
-- ... repeat for p2 through p7

-- Per-partition tenant lookup indexes
CREATE INDEX idx_chunks_p0_tenant ON document_chunks_p0(tenant_id);
CREATE INDEX idx_chunks_p1_tenant ON document_chunks_p1(tenant_id);
-- ... repeat for p2 through p7

With hash partitioning, every query that includes a tenant_id = $1 predicate benefits from partition pruning — the planner routes the query directly to the one or two partitions that could contain that tenant's rows, skipping the rest. The HNSW index on each partition is correspondingly smaller, and the total index memory footprint is spread across partitions.

The practical guidance: start with the unpartitioned design. Add partitioning when either your p95 retrieval latency starts climbing as the chunk table grows, or when the HNSW index no longer fits comfortably in RAM. Partitioning is a migration, not a rebuild — you can migrate rows partition by partition using INSERT INTO ... SELECT with minimal downtime.

Data Isolation Verification: Testing Your RLS Policies

No multi-tenant system is production-ready until the isolation guarantees are tested explicitly. RLS bugs are silent — a missing policy doesn't throw an error, it just returns rows from the wrong tenant. Write a test suite that specifically exercises cross-tenant boundary conditions.

# tests/test_rls_isolation.py

Run these tests in your CI pipeline on every schema migration. A schema change that accidentally drops an RLS policy should fail immediately in the test suite rather than in production. The zero-vector test approach is practical: you don't need real embeddings to verify isolation; you just need rows in the table.

SQL Server Equivalent: Multi-Tenant RAG on Azure SQL

For teams running on Azure SQL or SQL Server, the equivalent architecture uses Row-Level Security with security predicates rather than session variables, and FREETEXTTABLE / CONTAINSTABLE for full-text search. Vector search in Azure SQL is available as a native type in preview; for production workloads, Azure AI Search is the more mature option, but the relational metadata and RLS layer can still live in Azure SQL.

-- Azure SQL: tenant registry (syntax nearly identical to PostgreSQL)
CREATE TABLE tenants (
    tenant_id       UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    name            NVARCHAR(255) NOT NULL,
    slug            NVARCHAR(100) NOT NULL,
    plan            NVARCHAR(50) NOT NULL DEFAULT 'starter',
    embedding_model NVARCHAR(100) NOT NULL DEFAULT 'text-embedding-3-small',
    llm_model       NVARCHAR(100) NOT NULL DEFAULT 'gpt-4o-mini',
    max_documents   INT NOT NULL DEFAULT 1000,
    max_tokens_day  BIGINT NOT NULL DEFAULT 1000000,
    metadata        NVARCHAR(MAX) NOT NULL DEFAULT '{}',  -- JSON stored as nvarchar
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    is_active       BIT NOT NULL DEFAULT 1
);

CREATE TABLE documents (
    document_id     UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    tenant_id       UNIQUEIDENTIFIER NOT NULL REFERENCES tenants(tenant_id),
    title           NVARCHAR(500) NOT NULL,
    status          NVARCHAR(50) NOT NULL DEFAULT 'pending',
    chunk_count     INT NOT NULL DEFAULT 0,
    token_count     INT NOT NULL DEFAULT 0,
    content_hash    NVARCHAR(64),
    metadata        NVARCHAR(MAX) NOT NULL DEFAULT '{}',
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    updated_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET()
);

CREATE INDEX idx_documents_tenant ON documents(tenant_id);

-- Azure SQL RLS: security predicate function
-- Azure SQL uses a schema-bound inline function rather than a session variable.
-- The application passes the tenant ID as a session context value via
-- SESSION_CONTEXT, which is the Azure SQL equivalent of set_config().

CREATE SCHEMA rls;
GO

CREATE FUNCTION rls.fn_tenant_predicate(@tenant_id UNIQUEIDENTIFIER)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS result
    WHERE
        -- SESSION_CONTEXT is set by the application at connection time
        CONVERT(UNIQUEIDENTIFIER, SESSION_CONTEXT(N'tenant_id')) = @tenant_id;
GO

-- Apply the security policy to documents
CREATE SECURITY POLICY rls.tenant_documents_policy
    ADD FILTER PREDICATE rls.fn_tenant_predicate(tenant_id) ON dbo.documents,
    ADD BLOCK PREDICATE  rls.fn_tenant_predicate(tenant_id) ON dbo.documents
WITH (STATE = ON);
GO

-- Apply to other tables
CREATE SECURITY POLICY rls.tenant_chunks_policy
    ADD FILTER PREDICATE rls.fn_tenant_predicate(tenant_id) ON dbo.document_chunks,
    ADD BLOCK PREDICATE  rls.fn_tenant_predicate(tenant_id) ON dbo.document_chunks
WITH (STATE = ON);
GO

-- Setting tenant context in the application (C# / ADO.NET equivalent)
-- sp_set_session_context is the Azure SQL mechanism for SESSION_CONTEXT
EXEC sp_set_session_context N'tenant_id', @tenant_uuid_value;

-- Hybrid search in Azure SQL using CONTAINSTABLE for full-text
-- and vector_distance for semantic search (Azure SQL preview vector type)
SELECT TOP (@match_count)
    dc.chunk_id,
    dc.document_id,
    dc.content,
    d.title AS document_title,
    -- RRF fusion of vector rank and FTS rank
    (1.0 / (60 + vr.vector_rank)) * 0.7
    + (1.0 / (60 + ISNULL(ft.fts_rank, @match_count * 4 + 1))) * 0.3
        AS rrf_score
FROM document_chunks dc
JOIN documents d ON d.document_id = dc.document_id
-- Vector search subquery (Azure SQL preview syntax)
JOIN (
    SELECT chunk_id,
           ROW_NUMBER() OVER (ORDER BY VECTOR_DISTANCE('cosine', embedding, @query_embedding)) AS vector_rank
    FROM document_chunks
    WHERE tenant_id = CONVERT(UNIQUEIDENTIFIER, SESSION_CONTEXT(N'tenant_id'))
) vr ON vr.chunk_id = dc.chunk_id
-- Full-text search subquery
LEFT JOIN (
    SELECT dc2.chunk_id,
           ROW_NUMBER() OVER (ORDER BY ft2.RANK DESC) AS fts_rank
    FROM document_chunks dc2
    INNER JOIN CONTAINSTABLE(document_chunks, content, @fts_query) ft2
        ON dc2.chunk_id = ft2.[KEY]
    WHERE dc2.tenant_id = CONVERT(UNIQUEIDENTIFIER, SESSION_CONTEXT(N'tenant_id'))
) ft ON ft.chunk_id = dc.chunk_id
WHERE d.status = 'ready'
ORDER BY rrf_score DESC;

The key difference from PostgreSQL is that Azure SQL's SESSION_CONTEXT is set via sp_set_session_context and read via the SESSION_CONTEXT() function — functionally equivalent to PostgreSQL's set_config / current_setting pair. The BLOCK PREDICATE in Azure SQL's security policy enforces both the filter (reads) and the insert/update guard in a single declaration, while PostgreSQL separates these into USING and WITH CHECK clauses.

Key Takeaways

  • → **Row-Level Security is the correct layer for tenant isolation.** Enforcing isolation at the database engine level via RLS policies means a buggy application query that omits a tenant filter returns zero rows rather than leaking data — a fail-safe property that application-level filtering cannot provide.
  • → **Separate embedding model configuration from query-time assumptions.** Store both the tenant's current `embedding_model` preference and the model actually used per chunk, because tenants will change models over time. Using a query embedding generated by a different model than the stored chunk embeddings produces meaningless similarity scores.
  • → **Priority queues for ingestion fairness are simple to implement and prevent large tenants from starving small ones.** Routing Celery tasks by tenant plan to separate queues with different worker allocations costs almost nothing to build and has an outsized effect on perceived SLA quality for smaller customers.
  • → **Reciprocal Rank Fusion beats weighted score addition for hybrid search.** Because vector similarity scores and BM25/`ts_rank` scores live on incompatible numeric scales, fusing by rank (RRF) rather than raw score produces reliable, tunable results without the need to normalize or calibrate individual score distributions.
  • → **Start with a shared unpartitioned schema and partition only when memory pressure or query latency forces it.** Hash-partitioning `document_chunks` by `tenant_id` lets each partition carry its own smaller HNSW index, but it adds operational complexity; the migration path from unpartitioned to partitioned is straightforward and can be deferred until the cluster's HNSW index no longer fits comfortably in RAM.
