Chapter 16: Compressing Data at Rest: Savings and Tradeoffs

Storage compression is one of the most underutilized levers in cloud database cost management. Organizations running 2–5 TB of uncompressed transactional data on AWS RDS, Azure SQL, or Google Cloud SQL regularly see 40–70% storage reduction after enabling the right compression strategy — translating to $800–$3,500 per month in direct storage savings on a single database instance before accounting for reduced backup costs, lower data transfer fees, and faster I/O on compressed pages. This chapter walks through how to identify what is compressible, which compression algorithms and engine features to use per cloud platform, how to measure the performance tradeoff honestly, and how to automate compression enforcement across a fleet of databases so savings compound over time rather than remaining a one-off project.

---

16.1 Understanding What You Are Actually Paying For Before Compressing Anything

Compression that targets the wrong data delivers almost nothing. A 500 GB database where 400 GB is already binary BLOBs, encrypted payloads, or JPEG thumbnails stored as bytea will see near-zero compression gain. Before touching a single compression setting, spend thirty minutes identifying which data is actually compressible.

The Storage Cost Breakdown

On AWS RDS with gp3 storage, you pay $0.115 per GB-month for the primary volume. Multi-AZ doubles that to $0.230 per GB-month because RDS replicates the entire EBS volume to the standby. Automated backups stored in S3 add another $0.095 per GB-month for retention beyond the free tier. On a 3 TB Multi-AZ PostgreSQL instance with 14-day backup retention, the all-in storage cost looks like this:

| Component | Size | Rate | Monthly Cost |

|---|---|---|---|

| Primary EBS (gp3) | 3,000 GB | $0.115 | $345.00 |

| Standby EBS (Multi-AZ) | 3,000 GB | $0.115 | $345.00 |

| Automated backups | ~2,400 GB | $0.095 | $228.00 |

| Total | | | $918.00/month |

If compression reduces the primary volume to 1,200 GB — a 60% reduction common with mixed OLTP data — the same table drops to $367.20/month. That is $550.80 in monthly savings on storage alone, not counting backup savings, before you touch instance sizing.

Azure SQL Managed Instance on Business Critical tier charges $0.115 per GB-month (General Purpose is $0.115 as well, but Business Critical adds locally redundant replicas automatically). Google Cloud SQL for PostgreSQL charges $0.170 per GB-month on SSD storage with HA, making storage compression proportionally more valuable on GCP than on AWS.

Finding Compressible Data in PostgreSQL

Start by identifying table-level bloat, data type distribution, and actual compression readiness:

-- Identify the largest tables and their estimated compression potential
-- Run this on AWS RDS PostgreSQL, Aurora PostgreSQL, or Cloud SQL for PostgreSQL

WITH table_sizes AS (
    SELECT
        schemaname,
        tablename,
        pg_total_relation_size(schemaname || '.' || tablename) AS total_bytes,
        pg_relation_size(schemaname || '.' || tablename) AS table_bytes,
        pg_total_relation_size(schemaname || '.' || tablename)
            - pg_relation_size(schemaname || '.' || tablename) AS index_bytes
    FROM pg_tables
    WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
),
column_type_analysis AS (
    SELECT
        c.table_schema,
        c.table_name,
        COUNT(*) FILTER (WHERE data_type IN ('text', 'character varying', 'json', 'jsonb', 'xml')) AS text_columns,
        COUNT(*) FILTER (WHERE data_type IN ('bytea', 'bit varying')) AS binary_columns,
        COUNT(*) AS total_columns
    FROM information_schema.columns c
    WHERE c.table_schema NOT IN ('pg_catalog', 'information_schema')
    GROUP BY c.table_schema, c.table_name
)
SELECT
    ts.schemaname,
    ts.tablename,
    pg_size_pretty(ts.total_bytes) AS total_size,
    pg_size_pretty(ts.table_bytes) AS table_data_size,
    pg_size_pretty(ts.index_bytes) AS index_size,
    ct.text_columns,
    ct.binary_columns,
    ct.total_columns,
    ROUND(ct.text_columns::numeric / NULLIF(ct.total_columns, 0) * 100, 1) AS pct_text_columns,
    -- Tables with >40% text columns and >100MB are compression candidates
    CASE
        WHEN ct.text_columns::numeric / NULLIF(ct.total_columns, 0) > 0.4
             AND ts.table_bytes > 104857600
        THEN 'HIGH PRIORITY'
        WHEN ct.text_columns::numeric / NULLIF(ct.total_columns, 0) > 0.2
             AND ts.table_bytes > 52428800
        THEN 'MEDIUM PRIORITY'
        ELSE 'LOW PRIORITY'
    END AS compression_priority
FROM table_sizes ts
JOIN column_type_analysis ct
    ON ts.schemaname = ct.table_schema
    AND ts.tablename = ct.table_name
WHERE ts.total_bytes > 10485760  -- Only tables > 10 MB
ORDER BY ts.total_bytes DESC
LIMIT 50;

Finding Compressible Data in SQL Server (Azure SQL / RDS SQL Server)

-- Estimate compression savings before applying compression on SQL Server
-- Works on Azure SQL Database, Azure SQL Managed Instance, and RDS for SQL Server

SELECT
    s.name AS schema_name,
    t.name AS table_name,
    p.partition_number,
    p.rows,
    a.total_pages * 8 / 1024 AS total_size_mb,
    a.used_pages * 8 / 1024 AS used_size_mb,
    -- sp_estimate_data_compression_savings equivalent inline view
    -- Run the stored procedure separately per table for exact estimates
    CASE
        WHEN a.total_pages * 8 / 1024 > 1000 THEN 'Run sp_estimate_data_compression_savings'
        ELSE 'Small table - compress in bulk'
    END AS recommendation
FROM sys.tables t
INNER JOIN sys.schemas s ON t.schema_id = s.schema_id
INNER JOIN sys.partitions p ON t.object_id = p.object_id
INNER JOIN sys.allocation_units a ON p.partition_id = a.container_id
WHERE p.index_id IN (0, 1)  -- Heap or clustered index only
  AND a.total_pages * 8 / 1024 > 50  -- Tables > 50 MB
ORDER BY a.total_pages DESC;

-- For each candidate table, run this to get actual estimated savings:
-- EXEC sp_estimate_data_compression_savings
--     @schema_name = 'dbo',
--     @object_name = 'YourTableName',
--     @index_id = NULL,
--     @partition_number = NULL,
--     @data_compression = 'PAGE';

The output from sp_estimate_data_compression_savings gives you size_with_current_compression_setting, size_with_requested_compression_setting, and the delta as a percentage. Run this across your top twenty tables, sum the delta column, and you have a credible number to present to a budget holder.

16.2 Compression Options by Database Engine and Cloud Platform

Each database engine offers different compression mechanisms, and each cloud platform has its own constraints on which ones are available. Using the right compression at the right layer is the difference between a 60% reduction and a 5% reduction.

PostgreSQL: TOAST, pg_compress, and tablespace-level approaches

PostgreSQL uses TOAST (The Oversized-Attribute Storage Technique) automatically for column values exceeding approximately 2 KB. TOAST compresses the value using LZ4 (PostgreSQL 14+) or PGLZ (earlier versions) before writing it to the TOAST table. The key insight is that this is transparent — no schema changes required — but you control which algorithm it uses.

PostgreSQL 14 and later (available on RDS PostgreSQL 14+, Aurora PostgreSQL 14+, and Cloud SQL for PostgreSQL 14+) allows setting the compression method per column:

-- Check current TOAST compression settings for a table
SELECT
    attname AS column_name,
    attstorage AS storage_mode,
    attcompression AS compression_method,
    -- attstorage values: 'p'=plain, 'e'=external, 'x'=extended (TOAST+compress), 'm'=main
    CASE attstorage
        WHEN 'p' THEN 'No TOAST - always inline'
        WHEN 'e' THEN 'External TOAST - no compression'
        WHEN 'x' THEN 'Extended - TOAST with compression (best)'
        WHEN 'm' THEN 'Main - compress first, TOAST if needed'
    END AS storage_description,
    CASE attcompression
        WHEN '' THEN 'Default (pglz on PG13-, lz4 on PG14+)'
        WHEN 'p' THEN 'pglz'
        WHEN 'l' THEN 'lz4'
    END AS compression_algorithm
FROM pg_attribute
WHERE attrelid = 'your_schema.your_table'::regclass
  AND attnum > 0
  AND NOT attisdropped
ORDER BY attnum;

-- Switch a text column from pglz to lz4 (PostgreSQL 14+, RDS PG14+, Aurora PG14+)
-- lz4 is 3-5x faster to compress/decompress than pglz with similar compression ratios
ALTER TABLE your_schema.your_table
    ALTER COLUMN description SET COMPRESSION lz4;

ALTER TABLE your_schema.your_table
    ALTER COLUMN payload SET COMPRESSION lz4;

-- Force recompression of existing rows by rewriting the table
-- Schedule during a maintenance window - this takes an ACCESS EXCLUSIVE lock
-- For large tables, use pg_repack instead (no lock):
-- pg_repack --table your_schema.your_table -d your_database
VACUUM FULL your_schema.your_table;

-- Verify compression took effect on existing TOAST data
SELECT
    pg_size_pretty(pg_total_relation_size('your_schema.your_table')) AS total_with_toast,
    pg_size_pretty(pg_relation_size('your_schema.your_table')) AS main_table,
    pg_size_pretty(
        pg_total_relation_size('your_schema.your_table')
        - pg_relation_size('your_schema.your_table')
    ) AS toast_and_indexes;

SQL Server on Azure SQL and RDS: Row and Page Compression

SQL Server offers two compression levels that matter operationally:

*Row compression* stores fixed-length data types (INT, CHAR, DATETIME) in variable-length format, eliminating trailing zeros and padding. Typical savings: 10–25% for OLTP tables.

*Page compression* applies row compression first, then adds prefix compression (stores repeated column prefixes once per page) and dictionary compression (deduplicates repeated values within a page). Typical savings: 30–60% for tables with repeating values in indexed columns.

Page compression costs more CPU — typically 5–15% additional CPU utilization on read-heavy workloads and up to 25% on write-heavy workloads. On Azure SQL, where you pay for DTUs or vCores, that CPU tradeoff needs to be weighed against storage savings. On a Business Critical instance with 8 vCores at $1.008/hour, a 15% CPU increase costs roughly $108/month. If page compression saves 800 GB of storage at $0.115/GB, that is $92/month in pure storage — a net loss. Row compression at 5% CPU overhead saving the same 300 GB is easily worth it.

-- Apply page compression to a table on Azure SQL or RDS SQL Server
-- First, estimate savings (separate statement per table)
EXEC sp_estimate_data_compression_savings
    @schema_name = 'Sales',
    @object_name = 'OrderLineItems',
    @index_id = NULL,
    @partition_number = NULL,
    @data_compression = 'PAGE';

-- Apply row compression (lower CPU cost, moderate savings)
ALTER TABLE Sales.OrderLineItems
REBUILD WITH (DATA_COMPRESSION = ROW);

-- Apply page compression to the clustered index
ALTER TABLE Sales.OrderLineItems
REBUILD PARTITION = ALL WITH (DATA_COMPRESSION = PAGE);

-- Apply page compression to a specific nonclustered index
ALTER INDEX IX_OrderLineItems_OrderDate ON Sales.OrderLineItems
REBUILD WITH (DATA_COMPRESSION = PAGE);

-- Check current compression status across all tables
SELECT
    s.name AS schema_name,
    t.name AS table_name,
    i.name AS index_name,
    i.type_desc AS index_type,
    p.data_compression_desc AS current_compression,
    SUM(a.total_pages) * 8 / 1024 AS size_mb
FROM sys.tables t
INNER JOIN sys.schemas s ON t.schema_id = s.schema_id
INNER JOIN sys.indexes i ON t.object_id = i.object_id
INNER JOIN sys.partitions p ON i.object_id = p.object_id AND i.index_id = p.index_id
INNER JOIN sys.allocation_units a ON p.partition_id = a.container_id
GROUP BY s.name, t.name, i.name, i.type_desc, p.data_compression_desc
ORDER BY SUM(a.total_pages) DESC;

MySQL / Aurora MySQL: InnoDB Compression and Page Size

InnoDB row format compression (ROW_FORMAT=COMPRESSED) has been available since MySQL 5.5 but carries a significant caveat: it halves the effective buffer pool utilization because InnoDB keeps both compressed and uncompressed versions of each page in the buffer pool. This makes InnoDB row compression a poor choice for frequently accessed hot tables.

The better option for Aurora MySQL and RDS MySQL 8.0+ is Barracuda file format with KEY_BLOCK_SIZE tuning. For cold or archive tables, ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8 achieves 40–60% compression with acceptable performance since those pages rarely appear in the buffer pool.

The right approach for Aurora MySQL specifically is to use the Aurora storage engine's built-in compression, which operates at the storage layer and does not penalize the buffer pool — it is always on and transparent. Measuring Aurora storage savings therefore requires comparing Aurora's reported volume size against what the same data would occupy on a standard MySQL installation.

16.3 Measuring the Real Performance Tradeoff

Enabling compression without measuring its CPU and latency impact is how organizations discover problems in production at 2 AM. The measurement methodology below runs before and after compression to capture an honest before/after comparison.

PostgreSQL: Measuring Query Performance Against Compressed TOAST Data

-- Capture baseline query performance before compression changes
-- Run this before altering any compression settings

-- Enable pg_stat_statements if not already enabled
-- (On RDS, add pg_stat_statements to shared_preload_libraries via parameter group)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Capture baseline for queries touching the tables you plan to compress
SELECT
    left(query, 100) AS query_snippet,
    calls,
    ROUND(total_exec_time::numeric, 2) AS total_ms,
    ROUND(mean_exec_time::numeric, 4) AS mean_ms,
    ROUND(stddev_exec_time::numeric, 4) AS stddev_ms,
    rows,
    shared_blks_read,
    shared_blks_hit,
    ROUND(
        shared_blks_hit::numeric /
        NULLIF(shared_blks_hit + shared_blks_read, 0) * 100, 2
    ) AS buffer_hit_pct
FROM pg_stat_statements
WHERE query ILIKE '%your_table_name%'
  AND calls > 100
ORDER BY mean_exec_time DESC;

-- Reset stats, apply compression, run workload for 1 hour, then compare
SELECT pg_stat_statements_reset();
