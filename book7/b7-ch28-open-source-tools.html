Chapter 28: Open-Source Tools for Cloud Database Cost Analysis

Teams that shift database cost visibility from vendor consoles to open-source tooling typically identify 15–40% in previously invisible waste within the first 30 days. That is not a projection — it reflects what happens when you stop relying on AWS Cost Explorer's monthly rollups and start querying your own infrastructure telemetry at the row level. This chapter walks through the open-source ecosystem that makes that possible: tools for ingesting cloud billing data, querying database-level performance signals, correlating cost with workload, and automating remediation. Every tool covered here is free, actively maintained, and battle-tested in production environments serving databases ranging from 50 GB development instances to 50 TB analytical workloads.

---

The Open-Source Cost Visibility Stack

Before installing anything, understand what each layer of the stack actually does. The cloud provider billing APIs tell you what you spent. Database-internal statistics tell you what caused that spending. A correlation layer connects the two. Most teams have one or two of these layers but rarely all three, which is why waste persists.

Layer 1 — Cloud billing ingestion

The most widely adopted open-source tool for this layer is Infracost (cost estimation from IaC), paired with CloudQuery or Steampipe for live account inventory. Steampipe deserves particular attention: it exposes AWS, Azure, and GCP resources as PostgreSQL-compatible tables, meaning you can write standard SQL against your cloud account the same way you write queries against a database.

Install Steampipe and the AWS plugin:

# Install Steampipe
brew install turbot/tap/steampipe   # macOS
# or for Linux:
sudo /bin/sh -c "$(curl -fsSL https://steampipe.io/install/steampipe.sh)"

# Install the AWS plugin
steampipe plugin install aws

# Install Azure and GCP plugins
steampipe plugin install azure
steampipe plugin install gcp

# Verify installed plugins
steampipe plugin list

# Launch the interactive query shell
steampipe query

Once Steampipe is running, query your RDS inventory directly:

-- List all RDS instances with their approximate monthly cost footprint
-- Run this inside: steampipe query
SELECT
    db_instance_identifier,
    db_instance_class,
    engine,
    engine_version,
    multi_az,
    storage_type,
    allocated_storage,
    db_instance_status,
    -- Estimate: gp2 storage is ~$0.115/GB-month in us-east-1
    ROUND(allocated_storage * 0.115, 2)          AS estimated_storage_cost_usd,
    -- Flag instances that are stopped but still billing for storage
    CASE
        WHEN db_instance_status = 'stopped' THEN 'BILLING FOR STORAGE ONLY - review'
        WHEN multi_az = false
         AND db_instance_class NOT LIKE '%micro%'
         AND db_instance_class NOT LIKE '%small%' THEN 'Single-AZ prod risk'
        ELSE 'OK'
    END                                           AS cost_flag,
    publicly_accessible,
    region
FROM
    aws_rds_db_instance
ORDER BY
    allocated_storage DESC;

This single query, run against a real AWS account, commonly surfaces stopped instances still accruing storage costs. A stopped db.r6g.4xlarge with a 2 TB gp2 volume costs $230/month in storage alone while producing zero useful work.

Layer 2 — Database-internal statistics

PostgreSQL's pg_stat_statements and pg_stat_user_tables, SQL Server's sys.dm_exec_query_stats, and MySQL's performance_schema are the authoritative sources for understanding what workload is driving your compute and I/O costs. These are built into the engine — no additional installation required beyond enabling the extension.

Layer 3 — Correlation and dashboarding

Grafana with the CloudWatch, Azure Monitor, or Cloud Monitoring data sources connects billing signals to performance signals in a single pane. Prometheus with the postgres_exporter or mysqld_exporter provides the time-series foundation for alerting on cost-correlated metrics like blks_read (indicative of IOPS billing) and temp_files (indicative of memory pressure that forces scale-up).

Querying Database-Level Cost Signals

Cloud bills reflect infrastructure consumption. The root cause of that consumption lives inside the database engine. The following queries give you the operational data needed to map expensive cloud line items back to specific queries, tables, and access patterns.

PostgreSQL — identifying high-IOPS queries

IOPS on RDS gp2 storage costs are implicit: you pay for provisioned IOPS on io1/io2, but on gp2 and gp3 you pay for the storage tier itself and suffer performance degradation when you exhaust burst credits. Either way, identifying queries that generate excessive block reads is a direct cost-reduction exercise.

-- Enable pg_stat_statements if not already enabled
-- Add to postgresql.conf or RDS parameter group:
-- shared_preload_libraries = 'pg_stat_statements'
-- pg_stat_statements.track = all

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 20 queries by total disk block reads (maps to IOPS cost)
SELECT
    LEFT(query, 120)                                    AS query_preview,
    calls,
    total_exec_time::NUMERIC(18,2)                      AS total_exec_ms,
    ROUND((total_exec_time / calls)::NUMERIC, 2)        AS avg_exec_ms,
    shared_blks_read,
    shared_blks_hit,
    -- Cache hit ratio: closer to 1.0 = less disk I/O
    ROUND(
        shared_blks_hit::NUMERIC /
        NULLIF(shared_blks_hit + shared_blks_read, 0),
        4
    )                                                   AS cache_hit_ratio,
    -- Queries with cache_hit_ratio < 0.90 are disk-bound
    -- Each shared_blks_read = 8KB page fetched from storage
    ROUND(shared_blks_read * 8.0 / 1024, 2)            AS total_mb_read_from_disk,
    temp_blks_written,
    -- temp_blks_written signals sorts/hashes spilling to disk
    -- On RDS, this adds I/O and may indicate undersized work_mem
    ROUND(temp_blks_written * 8.0 / 1024, 2)           AS temp_writes_mb
FROM
    pg_stat_statements
WHERE
    calls > 100                          -- filter out one-time queries
ORDER BY
    shared_blks_read DESC
LIMIT 20;

A query showing total_mb_read_from_disk = 45000 across 10,000 calls is reading approximately 4.5 MB of pages per call from storage. If that query runs every 30 seconds around the clock, it is generating roughly 12.9 TB of logical reads per day — a primary driver of IOPS exhaustion and a direct argument for adding the right index or materializing an intermediate result set.

SQL Server on Azure SQL / RDS SQL Server — execution stats

-- Top 25 queries by total logical reads on SQL Server
-- Maps directly to I/O pressure and storage tier requirements
SELECT TOP 25
    qs.total_logical_reads                              AS total_logical_reads,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count         AS avg_logical_reads,
    qs.total_elapsed_time / 1000                        AS total_elapsed_ms,
    qs.total_elapsed_time / qs.execution_count / 1000   AS avg_elapsed_ms,
    qs.total_worker_time / qs.execution_count / 1000    AS avg_cpu_ms,
    -- Worker time maps to DTU consumption in Azure SQL
    -- High avg_cpu_ms on frequently executed queries = DTU ceiling risk
    SUBSTRING(
        st.text,
        (qs.statement_start_offset / 2) + 1,
        (
            CASE qs.statement_end_offset
                WHEN -1 THEN DATALENGTH(st.text)
                ELSE qs.statement_end_offset
            END - qs.statement_start_offset
        ) / 2 + 1
    )                                                   AS query_text,
    DB_NAME(st.dbid)                                    AS database_name,
    qp.query_plan
FROM
    sys.dm_exec_query_stats AS qs
CROSS APPLY
    sys.dm_exec_sql_text(qs.sql_handle) AS st
CROSS APPLY
    sys.dm_exec_query_plan(qs.plan_handle) AS qp
WHERE
    qs.execution_count > 50
ORDER BY
    qs.total_logical_reads DESC;

On Azure SQL Database, DTU consumption ties directly to logical reads and CPU. A query averaging 50,000 logical reads per execution running 200 times per minute will by itself justify an upgrade from S3 (100 DTUs, ~$150/month) to P1 (125 DTUs, ~$465/month). Finding that query and adding a covering index can eliminate the need for that tier upgrade entirely — a saving of roughly $315/month from one index.

MySQL / Aurora — identifying table scan costs

-- Identify tables with high full-scan ratios
-- Full scans = unnecessary IOPS = unnecessary storage tier costs
SELECT
    object_schema                                       AS db_name,
    object_name                                         AS table_name,
    count_read,
    count_fetch,
    count_full_scan,                                    -- full scans without index use
    ROUND(
        count_full_scan * 100.0 / NULLIF(count_read, 0),
        2
    )                                                   AS pct_full_scan,
    sum_rows_examined,
    sum_rows_sent,
    -- rows_examined / rows_sent ratio: higher = more waste per query
    ROUND(
        sum_rows_examined * 1.0 / NULLIF(sum_rows_sent, 0),
        1
    )                                                   AS examination_ratio
FROM
    performance_schema.table_io_waits_summary_with_full_scans
WHERE
    count_full_scan > 0
ORDER BY
    count_full_scan DESC
LIMIT 20;

An examination_ratio above 100 on a high-traffic table means the engine is reading 100 rows to return 1. On Aurora with I/O-Optimized pricing disabled, that translates directly to per-million-request I/O charges. Aurora I/O-Optimized eliminates per-request charges at the cost of a 25% instance price premium — the crossover point is approximately $0.22/million I/O requests × 10M requests/day, meaning I/O-Optimized pays off at roughly 45 million I/O requests per day. Tables with high examination_ratio on I/O-billed Aurora clusters are the exact targets to fix before that crossover calculation even matters.

Open-Source Tools for Billing Data Analysis

Three open-source projects stand out for transforming raw cloud billing exports into actionable database cost intelligence.

OpenCost

OpenCost is a CNCF sandbox project originally built for Kubernetes cost allocation, but its billing ingestion pipeline works equally well for RDS and managed database services when pointed at AWS Cost and Usage Reports (CUR). It exposes a Prometheus-compatible metrics endpoint, making it trivially consumable by existing Grafana dashboards.

# Export AWS Cost and Usage Report to S3 (one-time setup via CLI)
aws cur create-report-definition \
  --report-definition '{
    "ReportName": "database-finops-cur",
    "TimeUnit": "HOURLY",
    "Format": "Parquet",
    "Compression": "Parquet",
    "AdditionalSchemaElements": ["RESOURCES"],
    "S3Bucket": "your-cur-bucket",
    "S3Prefix": "cur/database-finops",
    "S3Region": "us-east-1",
    "ReportVersioning": "OVERWRITE_REPORT",
    "AdditionalArtifacts": ["ATHENA"],
    "RefreshClosedReports": true
  }'

# Verify the report definition was created
aws cur describe-report-definitions \
  --query 'ReportDefinitions[?ReportName==`database-finops-cur`]'

# Query the CUR via Athena once data has been delivered (typically 24h)
# This query extracts RDS-specific line items with resource-level granularity
aws athena start-query-execution \
  --query-string "
    SELECT
        line_item_resource_id,
        line_item_usage_type,
        line_item_usage_amount,
        line_item_blended_cost,
        line_item_unblended_cost,
        resource_tags_user_environment,
        resource_tags_user_team,
        line_item_usage_start_date
    FROM database_finops_cur
    WHERE line_item_product_code = 'AmazonRDS'
      AND line_item_line_item_type = 'Usage'
      AND line_item_usage_start_date >= DATE_ADD('day', -30, CURRENT_DATE)
    ORDER BY line_item_unblended_cost DESC
    LIMIT 500
  " \
  --query-execution-context Database=athenacurcfn_database_finops_cur \
  --result-configuration OutputLocation=s3://your-cur-bucket/athena-results/

Infracost — cost estimation before you deploy

Infracost scans Terraform plans and outputs a cost breakdown before any infrastructure change is applied. For database teams, this means you see the monthly cost of an RDS instance modification — changing storage type, resizing, enabling Multi-AZ — before it happens, not after the bill arrives.

# Install Infracost
brew install infracost    # macOS
# or:
curl -fsSL https://raw.githubusercontent.com/infracost/infracost/master/scripts/install.sh | sh

# Authenticate (free tier available)
infracost auth login

# Generate a cost diff for a Terraform change
# Assume you have a module that defines an RDS instance

# Baseline: cost of current state
infracost breakdown \
  --path ./terraform/rds-module \
  --format json \
  --out-file infracost-base.json

# After modifying the Terraform (e.g., changing db.r6g.2xlarge to db.r6g.xlarge):
infracost diff \
  --path ./terraform/rds-module \
  --compare-to infracost-base.json \
  --format table

# Example output interpretation:
# db.r6g.2xlarge  (us-east-1, On-Demand):  $0.480/hr  =  $350.40/mo
# db.r6g.xlarge   (us-east-1, On-Demand):  $0.240/hr  =  $175.20/mo
# Monthly saving:  -$175.20
# Annual saving:  -$2,102.40

# Generate a comment-ready report for a pull request
infracost comment github \
  --path infracost-base.json \
  --repo your-org/your-infra-repo \
  --pull-request 142 \
  --behavior update

The pull request integration is particularly valuable for platform engineering teams: every Terraform change that touches an RDS resource automatically gets a cost impact comment before merge approval. This single workflow shift prevents expensive configuration changes from reaching production without financial review.

Steampipe cost dashboards

Beyond inventory queries, Steampipe's aws_cost_by_service_monthly table provides programmatic access to Cost Explorer data without the AWS console:

-- Monthly RDS cost trend for the last 6 months
-- Run in Steampipe query shell
SELECT
    period_start,
    service,
    ROUND(blended_cost_amount::NUMERIC, 2)          AS blended_cost_usd,
    ROUND(unblended_cost_amount::NUMERIC, 2)        AS unblended_cost_usd,
    unit
FROM
    aws_cost_by_service_monthly
WHERE
    service = 'Amazon Relational Database Service'
    AND period_start >= DATE_TRUNC('month', NOW() - INTERVAL '6 months')
ORDER BY
    period_start DESC;

-- RDS cost broken down by resource tag (requires Cost Allocation Tags enabled)
SELECT
    dimension_value                                  AS rds_instance_id,
    ROUND(SUM(blended_cost_amount::NUMERIC), 2)     AS total_cost_usd,
    COUNT(DISTINCT period_start)                    AS months_billed
FROM
    aws_cost_by_resource_monthly
WHERE
    service = 'Amazon Relational Database Service'
    AND period_start >= DATE_TRUNC('month', NOW() - INTERVAL '3 months')
GROUP BY
    dimension_value
ORDER BY
    total_cost_usd DESC
LIMIT 30;

Automating Cost Analysis Pipelines

One-time queries identify problems. Scheduled pipelines track them over time and alert when costs deviate from baseline. The following Python script implements a weekly cost analysis pipeline that queries pg_stat_statements, correlates findings with CloudWatch IOPS metrics, and writes a summary to a Slack webhook. Schedule it with cron or a managed workflow tool like Apache Airflow.

#!/usr/bin/env python3
"""
db_cost_analyzer.py
Weekly database cost analysis pipeline.
Correlates pg_stat_statements I/O data with CloudWatch RDS metrics
and posts a cost summary to Slack.

Schedule: cron 0 8 * * 1  (every Monday at 08:00)
Dependencies: psycopg2-binary, boto3, requests
"""

import json
import os
import logging
from datetime import datetime, timedelta, timezone

import boto3
import psycopg2
import psycopg2.extras
import requests

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s"
)
logger = logging.getLogger(__name__)

# ---------------------------------------------------------------------------
# Configuration — load from environment variables in production
# ---------------------------------------------------------------------------
DB_CONFIG = {
    "host":     os.environ["RDS_ENDPOINT"],
    "port":     int(os.environ.get("RDS_PORT", "5432")),
    "dbname":   os.environ["RDS_DBNAME"],
    "user":     os.environ["RDS_USER"],
    "password": os.environ["RDS_PASSWORD"],
    "sslmode":  "require",
    "connect_timeout": 10,
}

RDS_INSTANCE_ID   = os.environ["RDS_INSTANCE_ID"]    # e.g. "prod-postgres-01"
AWS_REGION        = os.environ.get("AWS_REGION", "us-east-1")
SLACK_WEBHOOK_URL = os.environ["SLACK_WEBHOOK_URL"]
COST_ALERT_USD    = float(os.environ.get("COST_ALERT_THRESHOLD_USD", "500"))

# gp3 storage cost per GB-month in us-east-1 (update if using different region)
GP3_COST_PER_GB_MONTH    = 0.08
GP2_COST_PER_GB_MONTH    = 0.115
IO1_COST_PER_IOPS_MONTH  = 0.065
IO1_COST_PER_GB_MONTH    = 0.125


# ---------------------------------------------------------------------------
# Step 1: Query pg_stat_statements for top I/O consumers
# ---------------------------------------------------------------------------
def get_top_io_queries(conn, limit: int = 10) -> list[dict]:
    """Return the top N queries ranked by disk blocks read this week."""
    sql = """
        SELECT
            queryid,
            LEFT(query, 200)                                AS query_preview,
            calls,
            ROUND(total_exec_time::NUMERIC / 1000, 2)      AS total_exec_sec,
            ROUND(mean_exec_time::NUMERIC, 2)               AS avg_exec_ms,
            shared_blks_read,
            shared_blks_hit,
            ROUND(
                shared_blks_hit::NUMERIC /
                NULLIF(shared_blks_hit + shared_blks_read, 0) * 100,
                2
            )                                               AS cache_hit_pct,
            ROUND(shared_blks_read * 8.0 / 1024 / 1024, 3) AS disk_read_gb,
            temp_blks_written,
            ROUND(temp_blks_written * 8.0 / 1024, 2)       AS temp_write_mb
        FROM pg_stat_statements
        WHERE calls > 50
          AND shared_blks_read > 0
        ORDER BY shared_blks_read DESC
        LIMIT %s;
    """
    with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
        cur.execute(sql, (limit,))
        return [dict(row) for row in cur.fetchall()]


# ---------------------------------------------------------------------------
# Step 2: Query CloudWatch for RDS IOPS and storage metrics
# ---------------------------------------------------------------------------
def get_rds_cloudwatch_metrics(
    instance_id: str,
    region: str,
    lookback_days: int = 7
) -> dict:
    """
    Retrieve key RDS CloudWatch metrics for the past N days.
    Returns averages and peaks for cost-correlated metrics.
    """
    cw = boto3.client("cloudwatch", region_name=region)
    end_time   = datetime.now(timezone.utc)
    start_time = end_time - timedelta(days=lookback_days)

    metrics_to_fetch = [
        ("ReadIOPS",           "Average"),
        ("WriteIOPS",          "Average"),
        ("ReadIOPS",           "Maximum"),
        ("WriteIOPS",          "Maximum"),
        ("FreeStorageSpace",   "Minimum"),
        ("CPUUtilization",     "Average"),
        ("DatabaseConnections","Average"),
        ("FreeableMemory",     "Minimum"),
    ]

    results = {}
    for metric_name, stat in metrics_to_fetch:
        key = f"{metric_name}_{stat.lower()}"
        try:
            response = cw.get_metric_statistics(
                Namespace="AWS/RDS",
                MetricName=metric_name,
                Dimensions=[
                    {"Name": "DBInstanceIdentifier", "Value": instance_id}
                ],
                StartTime=start_time,
                EndTime=end_time,
                Period=3600,          # 1-hour granularity
                Statistics=[stat],
            )
            data_points = response.get("Datapoints", [])
            if data_points:
                values = [dp[stat] for dp in data_points]
                results[key] = round(sum(values) / len(values), 2)
            else:
                results[key] = None
        except Exception as exc:
            logger.warning("CloudWatch fetch failed for %s: %s", key, exc)
            results[key] = None

    return results


# ---------------------------------------------------------------------------
# Step 3: Query RDS instance metadata via boto3
# ---------------------------------------------------------------------------
def get_rds_instance_info(instance_id: str, region: str) -> dict:
    """Retrieve current RDS instance configuration for cost calculations."""
    rds = boto3.client("rds", region_name=region)
    response = rds.describe_db_instances(DBInstanceIdentifier=instance_id)
    db = response["DBInstances"][0]

    return {
        "instance_class":   db["DBInstanceClass"],
        "engine":           db["Engine"],
        "engine_version":   db["EngineVersion"],
        "storage_type":     db["StorageType"],
        "allocated_storage_gb": db["AllocatedStorage"],
        "iops":             db.get("Iops", 0),
        "multi_az":         db["MultiAZ"],
        "status":           db["DBInstanceStatus"],
    }


# ---------------------------------------------------------------------------
# Step 4: Calculate cost estimates and identify optimization opportunities
# ---------------------------------------------------------------------------
def analyze_cost_opportunities(
    instance_info: dict,
    cw_metrics: dict,
    top_queries: list[dict]
) -> dict:
    """
    Produce a structured cost analysis with concrete saving estimates.
    """
    findings = []
    total_potential_saving_usd = 0.0

    storage_gb   = instance_info["allocated_storage_gb"]
    storage_type = instance_info["storage_type"]
    iops_provisioned = instance_info.get("iops", 0)

    # ---- Storage type optimization ----
    if storage_type == "gp2":
        current_storage_cost = storage_gb * GP2_COST_PER_GB_MONTH
        gp3_storage_cost     = storage_gb * GP3_COST_PER_GB_MONTH
        monthly_saving       = round(current_storage_cost - gp3_storage_cost, 2)
        total_potential_saving_usd += monthly_saving
        findings.append({
            "category":   "Storage Type",
            "issue":      f"Using gp2 storage ({storage_gb} GB)",
            "action":     "Migrate to gp3",
            "current_cost_usd":  round(current_storage_cost, 2),
            "new_cost_usd":      round(gp3_storage_cost, 2),
            "monthly_saving_usd": monthly_saving,
            "annual_saving_usd":  round(monthly_saving * 12, 2),
        })

    if storage_type == "io1" and iops_provisioned > 0:
        avg_read_iops  = cw_metrics.get("ReadIOPS_average") or 0
        avg_write_iops = cw_metrics.get("WriteIOPS_average") or 0
        avg_total_iops = avg_read_iops + avg_write_iops
        # io1: IOPS utilization check — if <50% utilized, consider gp3
        if avg_total_iops < iops_provisioned * 0.5:
            current_io1_cost = (
                storage_gb * IO1_COST_PER_GB_MONTH +
                iops_provisioned * IO1_COST_PER_IOPS_MONTH
            )
            # gp3 provides 3000 IOPS baseline + can provision up to 16000
            # For demonstration, assume target IOPS = actual average * 1.5 headroom
            target_iops  = max(3000, int(avg_total_iops * 1.5))
            gp3_iops_cost = (
                storage_gb * GP3_COST_PER_GB_MONTH +
                max(0, target_iops - 3000) * 0.005   # $0.005/IOPS-month over baseline
            )
            monthly_saving = round(current_io1_cost - gp3_iops_cost, 2)
            total_potential_saving_usd += max(0, monthly_saving)
            findings.append({
                "category":   "Overprovisioned IOPS",
                "issue":      (f"io1 with {iops_provisioned} provisioned IOPS, "
                               f"avg utilization {avg_total_iops:.0f} IOPS "
                               f"({avg_total_iops/iops_provisioned*100:.1f}%)"),
                "action":     f"Migrate to gp3 with {target_iops} IOPS",
                "current_cost_usd":   round(current_io1_cost, 2),
                "new_cost_usd":       round(gp3_iops_cost, 2),
                "monthly_saving_usd": max(0, monthly_saving),
                "annual_saving_usd":  round(max(0, monthly_saving) * 12, 2),
            })

    # ---- Query I/O efficiency ----
    disk_heavy_queries = [
        q for q in top_queries
        if q.get("cache_hit_pct") is not None
        and float(q["cache_hit_pct"]) < 85.0
    ]
    if disk_heavy_queries:
        findings.append({
            "category": "Query I/O Efficiency",
            "issue":    (f"{len(disk_heavy_queries)} queries have cache hit rate <85% — "
                         "generating unnecessary disk reads"),
            "action":   "Review indexes and shared_buffers configuration",
            "details":  [
                {
                    "query":         q["query_preview"][:100],
                    "cache_hit_pct": q["cache_hit_pct"],
                    "disk_read_gb":  q["disk_read_gb"],
                    "calls":         q["calls"],
                }
                for q in disk_heavy_queries[:3]
            ],
            "monthly_saving_usd": 0,   # indirect — I/O reduction enables tier downsize
            "annual_saving_usd":  0,
        })

    # ---- Connection count check (pgBouncer opportunity) ----
    avg_connections = cw_metrics.get("DatabaseConnections_average") or 0
    if avg_connections > 80:
        findings.append({
            "category": "Connection Pooling",
            "issue":    (f"Average {avg_connections:.0f} direct database connections. "
                         "High connection counts waste memory (each ~5-10 MB on PostgreSQL)"),
            "action":   "Deploy pgBouncer in transaction pooling mode",
            "monthly_saving_usd": 0,   # enables smaller instance class
            "annual_saving_usd":  0,
            "note":     ("Reducing connections by 60% via pgBouncer commonly allows "
                         "one instance size downgrade, saving ~$175/mo on r6g.xlarge -> r6g.large"),
        })

    # ---- CPU headroom check ----
    avg_cpu = cw_metrics.get("CPUUtilization_average") or 0
    if avg_cpu < 15.0 and not instance_info["multi_az"]:
        findings.append({
            "category": "Overprovisioned Compute",
            "issue":    (f"Average CPU utilization {avg_cpu:.1f}% — "
                         "instance may be significantly oversized"),
            "action":   "Evaluate one instance class reduction after peak load analysis",
            "monthly_saving_usd": 0,
            "annual_saving_usd":  0,
            "note":     ("A db.r6g.2xlarge -> db.r6g.xlarge saves $175.20/month. "
                         "Validate with 2-week peak window before acting."),
        })

    return {
        "instance_id":            RDS_INSTANCE_ID,
        "analysis_date":          datetime.now(timezone.utc).isoformat(),
        "instance_info":          instance_info,
        "total_potential_monthly_saving_usd": round(total_potential_saving_usd, 2),
        "total_potential_annual_saving_usd":  round(total_potential_saving_usd * 12, 2),
        "findings":               findings,
        "cloudwatch_summary":     cw_metrics,
    }


# ---------------------------------------------------------------------------
# Step 5: Post summary to Slack

def main() -> None:
    logger.info("Starting weekly database cost analysis for %s", RDS_INSTANCE_ID)

    # Connect to PostgreSQL
    try:
        conn = psycopg2.connect(**DB_CONFIG)
        conn.set_session(readonly=True, autocommit=True)
        logger.info("Database connection established.")
    except psycopg2.OperationalError as exc:
        logger.error("Failed to connect to database: %s", exc)
        raise

    try:
        top_queries   = get_top_io_queries(conn, limit=10)
        logger.info("Fetched %d top I/O queries from pg_stat_statements.", len(top_queries))
    finally:
        conn.close()

    cw_metrics    = get_rds_cloudwatch_metrics(RDS_INSTANCE_ID, AWS_REGION, lookback_days=7)
    logger.info("CloudWatch metrics retrieved: %s", list(cw_metrics.keys()))

    instance_info = get_rds_instance_info(RDS_INSTANCE_ID, AWS_REGION)
    logger.info("RDS instance info: %s / %s / %d GB",
                instance_info["instance_class"],
                instance_info["storage_type"],
                instance_info["allocated_storage_gb"])

    analysis = analyze_cost_opportunities(instance_info, cw_metrics, top_queries)

    # Write full JSON report to local file for audit trail
    report_path = f"cost_analysis_{RDS_INSTANCE_ID}_{datetime.now().strftime('%Y%m%d')}.json"
    with open(report_path, "w") as fh:
        json.dump(analysis, fh, indent=2, default=str)
    logger.info("Full report written to %s", report_path)

    # Post summary to Slack
    post_to_slack(analysis, SLACK_WEBHOOK_URL)

    # Exit with non-zero code if savings exceed alert threshold
    # Useful for CI/CD pipelines that gate on cost regression
    if analysis["total_potential_monthly_saving_usd"] >= COST_ALERT_USD:
        logger.warning(
            "Potential monthly saving $%.2f exceeds alert threshold $%.2f. "
            "Review findings before next billing cycle.",
            analysis["total_potential_monthly_saving_usd"],
            COST_ALERT_USD,
        )
        raise SystemExit(1)

    logger.info(
        "Analysis complete. Potential monthly saving: $%.2f",
        analysis["total_potential_monthly_saving_usd"],
    )


if __name__ == "__main__":
    main()

Grafana Dashboards for Continuous Cost Visibility

A weekly Python report is valuable for trend tracking, but continuous dashboards catch cost anomalies in real time. The most effective open-source dashboard stack for database FinOps combines Grafana with the CloudWatch data source and the postgres_exporter Prometheus exporter. Together they display cloud billing signals and database-internal metrics on a single screen.

Install postgres_exporter alongside your application stack:

# Download and install postgres_exporter

tar xvf postgres_exporter-0.15.0.linux-amd64.tar.gz
sudo mv postgres_exporter-0.15.0.linux-amd64/postgres_exporter /usr/local/bin/

# Create a dedicated monitoring user in PostgreSQL
# Run this against your RDS instance
psql -h "$RDS_ENDPOINT" -U master_user -d postgres << 'SQL'
CREATE USER postgres_exporter WITH PASSWORD 'strong_password_here';
GRANT pg_monitor TO postgres_exporter;
GRANT SELECT ON pg_stat_statements TO postgres_exporter;
-- Grant connect on all databases you want to monitor
GRANT CONNECT ON DATABASE appdb TO postgres_exporter;
SQL

# Create the exporter configuration file
cat > /etc/postgres_exporter/queries.yaml << 'EOF'
pg_stat_statements_io:
  query: |
    SELECT
      queryid::text,
      LEFT(query, 80) AS query_preview,
      calls,
      shared_blks_read,
      shared_blks_hit,
      temp_blks_written,
      ROUND(shared_blks_hit * 100.0 / NULLIF(shared_blks_hit + shared_blks_read, 0), 2) AS cache_hit_pct
    FROM pg_stat_statements
    WHERE calls > 10
    ORDER BY shared_blks_read DESC
    LIMIT 20
  metrics:
    - queryid:
        usage: "LABEL"
        description: "Query ID"
    - query_preview:
        usage: "LABEL"
        description: "Query text preview"
    - calls:
        usage: "COUNTER"
        description: "Total executions"
    - shared_blks_read:
        usage: "COUNTER"
        description: "Disk blocks read"
    - shared_blks_hit:
        usage: "COUNTER"
        description: "Buffer cache hits"
    - temp_blks_written:
        usage: "COUNTER"
        description: "Temp blocks written to disk"
    - cache_hit_pct:
        usage: "GAUGE"
        description: "Buffer cache hit percentage"
EOF

    Reserved Instance and Savings Plan Analysis with Open-Source Tools

    The cloud providers' native RI recommendation tools are intentionally conservative — they protect vendor revenue by suggesting shorter commitment terms and lower coverage percentages. Open-source tools give you the raw data to run your own analysis with coverage targets that match your actual risk tolerance.

    ec2instances.info (open-source, hosted at instances.vantage.sh) provides machine-readable pricing for RDS instance types. Combine it with your CloudWatch utilization data to build a custom RI recommendation:

    # Fetch current RDS pricing for PostgreSQL in us-east-1
# The instances.vantage.sh API returns structured JSON
curl -s "https://ec2instances.info/rds/json" \
  | jq '[.[] | select(.region == "us-east-1" and .database_engine == "PostgreSQL") |
    {
      instance_type: .instance_type,
      vcpu: .vcpu,
      memory: .memory,
      ondemand_hourly: .pricing["us-east-1"].ondemand,
      reserved_1yr_no_upfront: .pricing["us-east-1"]["reserved"]["yrTerm1Standard.noUpfront"],
      reserved_1yr_all_upfront: .pricing["us-east-1"]["reserved"]["yrTerm1Standard.allUpfront"],
      reserved_3yr_no_upfront: .pricing["us-east-1"]["reserved"]["yrTerm3Standard.noUpfront"]
    }
  ] | sort_by(.ondemand_hourly | tonumber) | reverse' \
  > rds-pricing-us-east-1.json

# Calculate break-even and savings for a specific instance type
# Example: db.r6g.2xlarge
INSTANCE="db.r6g.2xlarge"

jq --arg inst "$INSTANCE" '
  .[] | select(.instance_type == $inst) |
  {
    instance_type: .instance_type,
    ondemand_monthly: (.ondemand_hourly | tonumber) * 730,
    reserved_1yr_monthly: (.reserved_1yr_no_upfront | tonumber),
    reserved_3yr_monthly: (.reserved_3yr_no_upfront | tonumber),
    saving_1yr_pct: (
      ((.ondemand_hourly | tonumber) - (.reserved_1yr_no_upfront | tonumber)) /
      (.ondemand_hourly | tonumber) * 100
    ),
    saving_3yr_pct: (
      ((.ondemand_hourly | tonumber) - (.reserved_3yr_no_upfront | tonumber)) /
      (.ondemand_hourly | tonumber) * 100
    ),
    annual_saving_1yr: (
      ((.ondemand_hourly | tonumber) - (.reserved_1yr_no_upfront | tonumber)) * 730 * 12
    )
  }
' rds-pricing-us-east-1.json

    For a db.r6g.2xlarge running PostgreSQL in us-east-1, the math works out as follows: On-Demand runs at approximately $0.480/hour ($350.40/month). A 1-year No-Upfront Reserved Instance drops that to approximately $0.288/hour ($210.24/month) — a saving of $1,682/year per instance. A 3-year No-Upfront RI pushes the saving to approximately $2,520/year. For a fleet of ten such instances, that single commitment decision is worth $16,820–$25,200 per year.

    The key constraint is utilization confidence. Use the following query to identify instances that have run continuously for the past 90 days — these are your safest RI candidates:

    # Identify RDS instances with 90+ days of continuous operation
# These are prime Reserved Instance candidates
aws rds describe-db-instances \
  --query 'DBInstances[*].{
    ID:DBInstanceIdentifier,
    Class:DBInstanceClass,
    Engine:Engine,
    Status:DBInstanceStatus,
    Created:InstanceCreateTime,
    MultiAZ:MultiAZ,
    StorageType:StorageType
  }' \
  --output json \
  | jq '[.[] | select(.Status == "available") | . + {
      age_days: (
        (now - (.Created | split(".")[0] + "Z" | fromdateiso8601)) / 86400 | floor
      )
    }
  ] | sort_by(.age_days) | reverse
    | .[] | select(.age_days >= 90)' \
  | jq -s '
    . | map({
      instance_id:    .ID,
      instance_class: .Class,
      engine:         .Engine,
      age_days:       .age_days,
      ri_candidate:   (if .age_days >= 365 then "HIGH — 3yr RI"
                       elif .age_days >= 90 then "MEDIUM — 1yr RI"
                       else "LOW — monitor" end)
    })
  '

    Key Takeaways

  • → **Steampipe transforms cloud inventory into SQL**: Writing standard `SELECT` queries against your AWS, Azure, or GCP account surfaces stopped instances, oversized storage, and untagged resources in minutes — waste that vendor consoles obscure behind navigation layers and monthly aggregates.
  • → **pg_stat_statements and sys.dm_exec_query_stats are the root-cause layer**: Every expensive cloud bill line item traces back to a specific query, table scan, or access pattern inside the database engine. Running the I/O correlation queries in this chapter weekly identifies the top three to five queries that justify your IOPS tier — and often reveals that removing one full-table scan eliminates the need for a storage tier upgrade entirely.
  • → **Infracost in the CI/CD pipeline stops cost regressions before they reach production**: Attaching a cost diff comment to every Terraform pull request that touches an RDS resource creates a financial review gate with zero additional process overhead. Teams that implement this report catching expensive misconfigurations — accidentally enabled Multi-AZ, oversized instance class selections, io1 where gp3 suffices — before they run for a full billing cycle.
  • → **The automated weekly pipeline pays for itself in the first finding**: The Python script in this chapter runs in under two minutes, requires no additional paid tooling, and consistently identifies at least one actionable finding per instance per month. A single gp2-to-gp3 migration flagged by the script on a 2 TB volume saves **$70/month indefinitely** — the script's entire annual value exceeds most paid FinOps SaaS subscriptions.
  • → **Reserved Instance decisions require utilization confidence, not just age**: The `jq` pipeline that identifies instances with 90-plus days of continuous operation gives you the evidence base for RI commitment conversations with finance. The math is straightforward — a `db.r6g.2xlarge` fleet of ten instances saves between $16,820 and $25,200 per year on 1-year versus 3-year RIs — but only when the instances have demonstrated stable, sustained utilization that makes the commitment credible.
