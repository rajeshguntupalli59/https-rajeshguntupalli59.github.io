Chapter 26: Multi-Agent Coordination via Shared PostgreSQL State

When you move beyond single-agent architectures into systems where multiple AI agents run concurrently — each with its own specialty, each handling a slice of a larger workflow — you immediately run into the coordination problem. How does a research agent know that a summarization agent has already processed a document? How does a planner agent hand off a subtask to a worker agent without race conditions? How do you debug what happened when five agents were all writing state at once? The answer that scales, audits cleanly, and integrates naturally with the rest of your application stack is PostgreSQL as the shared state backbone. This chapter shows you how to design that backbone, wire real agents to it, and run it in production without losing your mind.

---

The Coordination Problem in Multi-Agent Systems

Most multi-agent frameworks hide coordination behind in-memory queues or proprietary state stores. That works in demos. In production, it creates a second system you have to operate, monitor, back up, and reason about — separate from your application database. More importantly, it separates your agent state from your business data, which means you lose the ability to join them, audit them together, or apply the same access control policies to both.

The core coordination challenges that PostgreSQL solves well:

Task assignment and work stealing. Agents need to claim work atomically. Without atomic claiming, two agents pick up the same task. PostgreSQL's SELECT ... FOR UPDATE SKIP LOCKED is the correct primitive for this — it was built for exactly this pattern and has been production-hardened for years.

State visibility across agents. An orchestrator agent needs to see the current state of all worker agents: what they're doing, what they've produced, where they've failed. If that state lives in five different in-memory structures across five processes, you have no coherent view.

Event-driven wake-up. When agent A finishes its work, agent B should learn about it immediately without polling. PostgreSQL's LISTEN/NOTIFY mechanism (backed by pg_notify) gives you sub-millisecond event delivery within the database connection pool.

Audit and replay. When a multi-agent workflow produces wrong output, you need to reconstruct exactly what each agent did, in what order, with what inputs. An append-only event log in PostgreSQL gives you this for free.

Why not Redis? Redis excels at ephemeral queuing and caching, and we'll use it for exactly that — caching embedding lookups and rate-limit counters. But Redis is not your source of truth. You can't do a transactional join between your Redis agent state and your PostgreSQL user table. You can't apply row-level security to Redis keys. You can't write a migration that reshapes your coordination schema and run it through your normal deployment pipeline. PostgreSQL handles the parts that need to be true.

Schema Design for Multi-Agent Coordination

The schema has to carry three concerns simultaneously: the workflow definition (what work needs to happen), the execution state (what's happening right now), and the event log (what happened and when). These map to three table groups.

CREATE INDEX idx_tasks_assigned ON agent_tasks(assigned_to)

-- ============================================================
-- SHARED AGENT MEMORY / BLACKBOARD
-- ============================================================

-- The blackboard is the shared memory space all agents can read and write.
-- Named after the AI blackboard architecture pattern from the 1980s —
-- still the right abstraction for multi-agent coordination.

CREATE TABLE blackboard (
    entry_id        UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    run_id          UUID NOT NULL REFERENCES workflow_runs(run_id) ON DELETE CASCADE,
    namespace       TEXT NOT NULL,               -- 'facts', 'hypotheses', 'artifacts', 'context'
    key             TEXT NOT NULL,
    value           JSONB NOT NULL,
    embedding       vector(1536),               -- for semantic search across blackboard entries
    written_by      TEXT NOT NULL,              -- agent instance that wrote this
    written_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ,
    version         INTEGER NOT NULL DEFAULT 1,
    is_current      BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (run_id, namespace, key, version)
);

CREATE INDEX idx_blackboard_lookup ON blackboard(run_id, namespace, key)
    WHERE is_current = TRUE;
CREATE INDEX idx_blackboard_embedding ON blackboard
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100)
    WHERE embedding IS NOT NULL AND is_current = TRUE;

-- ============================================================
-- EVENT LOG (append-only)
-- ============================================================

CREATE TABLE agent_events (
    event_id        UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    run_id          UUID REFERENCES workflow_runs(run_id),
    task_id         UUID REFERENCES agent_tasks(task_id),
    agent_instance  TEXT NOT NULL,
    event_type      TEXT NOT NULL,               -- 'task_claimed', 'llm_call_start', 'llm_call_end',
                                                 -- 'tool_invoked', 'blackboard_write', 'task_complete', etc.
    event_data      JSONB NOT NULL DEFAULT '{}',
    token_usage     JSONB,                       -- {prompt_tokens, completion_tokens, model}
    duration_ms     INTEGER,
    occurred_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Partition by month for manageable table sizes in production
-- (shown without partitioning here for clarity; add it before going live)
CREATE INDEX idx_events_run ON agent_events(run_id, occurred_at DESC);
CREATE INDEX idx_events_task ON agent_events(task_id, occurred_at DESC);
CREATE INDEX idx_events_type ON agent_events(event_type, occurred_at DESC);

-- ============================================================
-- AGENT HEARTBEATS (detect stalled agents)
-- ============================================================

CREATE TABLE agent_heartbeats (
    agent_instance  TEXT PRIMARY KEY,
    agent_type      TEXT NOT NULL,
    current_task_id UUID REFERENCES agent_tasks(task_id),
    process_id      INTEGER,
    host            TEXT,
    last_seen       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    metadata        JSONB NOT NULL DEFAULT '{}'
);

-- ============================================================
-- Helper function: notify on task state changes
-- ============================================================

CREATE OR REPLACE FUNCTION notify_task_change()
RETURNS TRIGGER AS $$
DECLARE
    payload JSONB;
BEGIN
    payload := jsonb_build_object(
        'task_id',   NEW.task_id,
        'run_id',    NEW.run_id,
        'task_type', NEW.task_type,
        'status',    NEW.status,
        'priority',  NEW.priority
    );
    PERFORM pg_notify('agent_tasks_' || NEW.task_type, payload::TEXT);
    PERFORM pg_notify('agent_tasks_all', payload::TEXT);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_task_notify
    AFTER INSERT OR UPDATE OF status ON agent_tasks
    FOR EACH ROW EXECUTE FUNCTION notify_task_change();

-- ============================================================
-- Helper function: update updated_at automatically
-- ============================================================

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_tasks_updated_at
    BEFORE UPDATE ON agent_tasks
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();

This schema gives every agent a consistent interface. The blackboard table is the key innovation here — it's a versioned, semantically searchable shared memory space. An agent can write a discovery, another agent can search that discovery space with a vector query ("find all facts related to this topic"), and the whole thing is transactionally consistent with the task state.

Implementing the Core Agent Coordination Patterns

With the schema in place, three patterns make everything work: atomic task claiming, blackboard read/write with semantic search, and event-driven agent wake-up via pg_notify.

# agent_base.py — base class for all agents in the system
import asyncio
import json
import logging
import os
import socket
import uuid
from contextlib import asynccontextmanager
from datetime import datetime, timezone
from typing import Any, Optional

import asyncpg
import openai
from openai import AsyncOpenAI
from pgvector.asyncpg import register_vector

logger = logging.getLogger(__name__)

OPENAI_CLIENT = AsyncOpenAI(api_key=os.environ["OPENAI_API_KEY"])
DATABASE_URL = os.environ["DATABASE_URL"]

class AgentBase:
    """
    Base class for all agents in the multi-agent system.
    Provides atomic task claiming, blackboard access, heartbeat,
    event logging, and pg_notify listener setup.
    """

    def __init__(self, agent_type: str, concurrency: int = 1):
        self.agent_type = agent_type
        self.concurrency = concurrency
        self.instance_id = f"{agent_type}:{socket.gethostname()}:{os.getpid()}:{uuid.uuid4().hex[:8]}"
        self.pool: Optional[asyncpg.Pool] = None
        self._running = False

    async def start(self):
        self.pool = await asyncpg.create_pool(
            DATABASE_URL,
            min_size=2,
            max_size=self.concurrency + 4,  # workers + heartbeat + listener + overhead
            command_timeout=30,
            # Registers the pgvector codec on every connection so a Python
            # list can be passed straight into a `vector` column parameter
            # without manually formatting it as a "[...]" string — this is
            # what makes the blackboard_write() vector insert below work.
            init=register_vector,
        )
        self._running = True
        logger.info(f"Agent {self.instance_id} started")

        await asyncio.gather(
            self._heartbeat_loop(),
            self._listen_and_work(),
            self._stall_detector(),
        )

    async def stop(self):
        self._running = False
        if self.pool:
            await self.pool.close()

    # ------------------------------------------------------------------
    # ATOMIC TASK CLAIMING — the most important pattern
    # ------------------------------------------------------------------

    async def claim_task(self, conn: asyncpg.Connection) -> Optional[dict]:
        """
        Atomically claim the next available task for this agent type,
        respecting dependency ordering and priority.

        SELECT FOR UPDATE SKIP LOCKED ensures two agents never claim the same task,
        even under high concurrency, without any application-level locking.
        """
        row = await conn.fetchrow("""
            WITH ready_tasks AS (
                SELECT t.task_id
                FROM agent_tasks t
                WHERE t.task_type = $1
                  AND t.status = 'pending'
                  AND (
                    -- No dependencies, OR all dependencies completed
                    t.depends_on = '{}'
                    OR NOT EXISTS (
                        SELECT 1 FROM agent_tasks dep
                        WHERE dep.task_id = ANY(t.depends_on)
                          AND dep.status != 'completed'
                    )
                  )
                  AND (t.deadline IS NULL OR t.deadline > NOW())
                ORDER BY t.priority ASC, t.created_at ASC
                LIMIT 1
                FOR UPDATE SKIP LOCKED
            )
            UPDATE agent_tasks
            SET status      = 'claimed',
                assigned_to = $2,
                claimed_at  = NOW(),
                updated_at  = NOW()
            FROM ready_tasks
            WHERE agent_tasks.task_id = ready_tasks.task_id
            RETURNING
                agent_tasks.task_id,
                agent_tasks.run_id,
                agent_tasks.task_name,
                agent_tasks.task_type,
                agent_tasks.input_data,
                agent_tasks.retry_count,
                agent_tasks.max_retries,
                agent_tasks.parent_task_id
        """, self.agent_type, self.instance_id)

        if row:
            await self._log_event(conn, row["run_id"], row["task_id"], "task_claimed", {
                "task_name": row["task_name"],
                "retry_count": row["retry_count"],
            })

        return dict(row) if row else None

    async def complete_task(
        self,
        conn: asyncpg.Connection,
        task_id: str,
        run_id: str,
        output_data: dict,
        duration_ms: int,
    ):
        await conn.execute("""
            UPDATE agent_tasks
            SET status       = 'completed',
                output_data  = $2,
                completed_at = NOW(),
                updated_at   = NOW()
            WHERE task_id = $1
        """, uuid.UUID(task_id), json.dumps(output_data))

        await self._log_event(conn, run_id, task_id, "task_complete", {
            "output_keys": list(output_data.keys()),
        }, duration_ms=duration_ms)

    async def fail_task(
        self,
        conn: asyncpg.Connection,
        task_id: str,
        run_id: str,
        error: Exception,
        retry: bool = True,
    ):
        task = await conn.fetchrow(
            "SELECT retry_count, max_retries FROM agent_tasks WHERE task_id = $1",
            uuid.UUID(task_id)
        )

        if retry and task["retry_count"] < task["max_retries"]:
            await conn.execute("""
                UPDATE agent_tasks
                SET status      = 'pending',
                    assigned_to = NULL,
                    claimed_at  = NULL,
                    retry_count = retry_count + 1,
                    error_detail = $2,
                    updated_at  = NOW()
                WHERE task_id = $1
            """, uuid.UUID(task_id), json.dumps({
                "error": str(error),
                "failed_by": self.instance_id,
                "attempt": task["retry_count"] + 1,
            }))
            await self._log_event(conn, run_id, task_id, "task_retry_scheduled", {
                "attempt": task["retry_count"] + 1,
                "error": str(error)[:500],
            })
        else:
            await conn.execute("""
                UPDATE agent_tasks
                SET status      = 'failed',
                    error_detail = $2,
                    completed_at = NOW(),
                    updated_at  = NOW()
                WHERE task_id = $1
            """, uuid.UUID(task_id), json.dumps({"error": str(error), "failed_by": self.instance_id}))
            await self._log_event(conn, run_id, task_id, "task_failed", {"error": str(error)[:500]})

    # ------------------------------------------------------------------
    # BLACKBOARD ACCESS
    # ------------------------------------------------------------------

    async def blackboard_write(
        self,
        conn: asyncpg.Connection,
        run_id: str,
        namespace: str,
        key: str,
        value: Any,
        embed: bool = False,
    ):
        """
        Write to the shared blackboard. Handles versioning automatically —
        old versions are marked is_current=FALSE, new version is inserted.
        """
        text_for_embedding = None
        if embed and isinstance(value, (str, dict)):
            text_for_embedding = value if isinstance(value, str) else json.dumps(value)

        embedding = None
        if text_for_embedding:
            response = await OPENAI_CLIENT.embeddings.create(
                model="text-embedding-3-small",
                input=text_for_embedding
            )
            embedding = response.data[0].embedding

        async with conn.transaction():
            # Retire current version
            current_version = await conn.fetchval("""
                UPDATE blackboard
                SET is_current = FALSE
                WHERE run_id = $1 AND namespace = $2 AND key = $3 AND is_current = TRUE
                RETURNING version
            """, uuid.UUID(run_id), namespace, key)

            next_version = (current_version or 0) + 1

            await conn.execute("""
                INSERT INTO blackboard
                    (run_id, namespace, key, value, embedding, written_by, version, is_current)
                VALUES ($1, $2, $3, $4, $5, $6, $7, TRUE)
            """,
                uuid.UUID(run_id),
                namespace,
                key,
                json.dumps(value),
                embedding,       # asyncpg handles vector type via the pgvector codec
                self.instance_id,
                next_version,
            )

        await self._log_event(conn, run_id, None, "blackboard_write", {
            "namespace": namespace, "key": key, "version": next_version
        })

    async def blackboard_read(
        self,
        conn: asyncpg.Connection,
        run_id: str,
        namespace: str,
        key: str,
    ) -> Optional[Any]:
        row = await conn.fetchrow("""
            SELECT value, written_by, written_at, version
            FROM blackboard
            WHERE run_id = $1 AND namespace = $2 AND key = $3 AND is_current = TRUE
        """, uuid.UUID(run_id), namespace, key)

        return json.loads(row["value"]) if row else None

    async def blackboard_search(
        self,
        conn: asyncpg.Connection,
        run_id: str,
        query: str,
        namespace: Optional[str] = None,
        top_k: int = 5,
    ) -> list[dict]:
        """Semantic search across blackboard entries for this run."""
        response = await OPENAI_CLIENT.embeddings.create(
            model="text-embedding-3-small",
            input=query
        )
        query_embedding = response.data[0].embedding

        namespace_filter = "AND namespace = $4" if namespace else ""
        params = [uuid.UUID(run_id), query_embedding, top_k]
        if namespace:
            params.append(namespace)

        rows = await conn.fetch(f"""
            SELECT
                namespace,
                key,
                value,
                written_by,
                written_at,
                1 - (embedding <=> $2::vector) AS similarity
            FROM blackboard
            WHERE run_id = $1
              AND is_current = TRUE
              AND embedding IS NOT NULL
              {namespace_filter}
            ORDER BY embedding <=> $2::vector
            LIMIT $3
        """, *params)

        return [dict(r) | {"value": json.loads(r["value"])} for r in rows]

    # ------------------------------------------------------------------
    # EVENT LOGGING
    # ------------------------------------------------------------------

    async def _log_event(
        self,
        conn: asyncpg.Connection,
        run_id: Optional[str],
        task_id: Optional[str],
        event_type: str,
        event_data: dict,
        duration_ms: Optional[int] = None,
        token_usage: Optional[dict] = None,
    ):
        await conn.execute("""
            INSERT INTO agent_events
                (run_id, task_id, agent_instance, event_type, event_data, duration_ms, token_usage)
            VALUES ($1, $2, $3, $4, $5, $6, $7)
        """,
            uuid.UUID(run_id) if run_id else None,
            uuid.UUID(task_id) if task_id else None,
            self.instance_id,
            event_type,
            json.dumps(event_data),
            duration_ms,
            json.dumps(token_usage) if token_usage else None,
        )

    # ------------------------------------------------------------------
    # HEARTBEAT
    # ------------------------------------------------------------------

    async def _heartbeat_loop(self):
        while self._running:
            try:
                async with self.pool.acquire() as conn:
                    await conn.execute("""
                        INSERT INTO agent_heartbeats
                            (agent_instance, agent_type, host, process_id, last_seen)
                        VALUES ($1, $2, $3, $4, NOW())
                        ON CONFLICT (agent_instance)
                        DO UPDATE SET last_seen = NOW()
                    """, self.instance_id, self.agent_type, socket.gethostname(), os.getpid())
            except Exception as e:
                logger.warning(f"Heartbeat failed: {e}")
            await asyncio.sleep(10)

    # ------------------------------------------------------------------
    # STALL DETECTOR — reclaim tasks from dead agents
    # ------------------------------------------------------------------

    async def _stall_detector(self):
        """
        Periodically look for tasks that are 'claimed' or 'running' but
        whose agent has stopped sending heartbeats. Reset them to 'pending'
        so another agent can pick them up.
        """
        while self._running:
            await asyncio.sleep(30)
            try:
                async with self.pool.acquire() as conn:
                    stalled = await conn.fetch("""
                        UPDATE agent_tasks
                        SET status      = 'pending',
                            assigned_to = NULL,
                            claimed_at  = NULL,
                            retry_count = retry_count + 1,
                            error_detail = jsonb_build_object(
                                'reason', 'stalled_agent',
                                'previous_agent', assigned_to,
                                'detected_at', NOW()::TEXT
                            ),
                            updated_at  = NOW()
                        WHERE status IN ('claimed', 'running')
                          AND task_type = $1
                          AND assigned_to NOT IN (
                              SELECT agent_instance FROM agent_heartbeats
                              WHERE last_seen > NOW() - INTERVAL '30 seconds'
                          )
                          AND retry_count < max_retries
                        RETURNING task_id, run_id, assigned_to
                    """, self.agent_type)

                    for row in stalled:
                        logger.warning(
                            f"Reclaimed stalled task {row['task_id']} "
                            f"from dead agent {row['assigned_to']}"
                        )
                        await self._log_event(
                            conn,
                            str(row["run_id"]),
                            str(row["task_id"]),
                            "task_reclaimed_from_stall",
                            {"previous_agent": row["assigned_to"]},
                        )
            except Exception as e:
                logger.error(f"Stall detector error: {e}")

    # ------------------------------------------------------------------
    # LISTEN / WORK LOOP
    # ------------------------------------------------------------------

    async def _listen_and_work(self):
        """
        Open a dedicated connection for LISTEN. When a notification arrives
        for our task type, attempt to claim and process tasks. Also poll
        every few seconds as a safety net for missed notifications.
        """
        listen_conn = await asyncpg.connect(DATABASE_URL)
        channel = f"agent_tasks_{self.agent_type}"

        queue: asyncio.Queue = asyncio.Queue(maxsize=self.concurrency * 2)

        async def on_notify(connection, pid, channel, payload):
            try:
                queue.put_nowait(json.loads(payload))
            except asyncio.QueueFull:
                pass  # We'll catch it on the next poll cycle

        await listen_conn.add_listener(channel, on_notify)
        logger.info(f"Agent {self.instance_id} listening on {channel}")

        semaphore = asyncio.Semaphore(self.concurrency)

        async def process_one():
            async with semaphore:
                async with self.pool.acquire() as conn:
                    async with conn.transaction():
                        task = await self.claim_task(conn)
                        if not task:
                            return
                    # Task is claimed; now run it outside the claim transaction
                    # so the claim is visible to other agents immediately
                    await self._run_task(task)

        try:
            while self._running:
                # Drain any pending notifications or wait up to 5s for one
                try:
                    await asyncio.wait_for(queue.get(), timeout=5.0)
                except asyncio.TimeoutError:
                    pass  # safety-net poll tick

                # Spin up workers up to concurrency limit
                tasks_to_launch = self.concurrency
                coros = [process_one() for _ in range(tasks_to_launch)]
                await asyncio.gather(*coros, return_exceptions=True)
        finally:
            await listen_conn.remove_listener(channel, on_notify)
            await listen_conn.close()

    async def _run_task(self, task: dict):
        """Override in subclasses to implement agent-specific logic."""
        raise NotImplementedError

The _listen_and_work loop is the engine. It uses a dedicated connection for LISTEN (PostgreSQL requires that LISTEN commands sit on a long-lived connection, not a pooled one), and it uses the pool for all actual data operations. The semaphore ensures we never exceed concurrency simultaneous task executions regardless of how many notifications arrive in a burst.

Building Concrete Agents

With the base class in place, building a specific agent means overriding _run_task and implementing the agent's logic. Here is a research agent and a summarization agent that collaborate through the blackboard.

# research_agent.py
import asyncio
import json
import time
import uuid
from typing import Any

import asyncpg
from agent_base import AgentBase, OPENAI_CLIENT, logger


RESEARCH_SYSTEM_PROMPT = """You are a research agent. Given a topic or question,
you produce a structured research summary with key facts, sources (when available),
open questions, and a confidence assessment. Output valid JSON only."""


class ResearchAgent(AgentBase):

    def __init__(self):
        super().__init__(agent_type="researcher", concurrency=3)

                if depth in ("standard", "deep") and result.get("facts"):

        except Exception as e:

            async with self.pool.acquire() as conn:
                await self.fail_task(conn, task_id, run_id, e)

    async def _do_research(self, topic: str, depth: str, run_id: str) -> dict:
        max_tokens = {"quick": 512, "standard": 1024, "deep": 2048}.get(depth, 1024)

        # Check blackboard first — maybe a prior agent already researched this
        async with self.pool.acquire() as conn:
            existing = await self.blackboard_search(
                conn, run_id, query=topic, namespace="facts", top_k=3
            )

        if existing and existing[0]["similarity"] > 0.92:
            logger.info(f"Research cache hit for '{topic}' (similarity {existing[0]['similarity']:.3f})")
            return existing[0]["value"]

        messages = [
            {"role": "system", "content": RESEARCH_SYSTEM_PROMPT},
            {"role": "user", "content": f"Research topic: {topic}\nDepth: {depth}\n\n"
             "Return JSON with keys: summary, facts (list), confidence (0-1), "
             "open_questions (list), methodology_notes."},
        ]

        response = await OPENAI_CLIENT.chat.completions.create(
            model="gpt-4o",
            messages=messages,
            max_tokens=max_tokens,
            response_format={"type": "json_object"},
            temperature=0.2,
        )

        token_usage = {
            "prompt_tokens": response.usage.prompt_tokens,
            "completion_tokens": response.usage.completion_tokens,
            "model": response.model,
        }

        result = json.loads(response.choices[0].message.content)
        result["_token_usage"] = token_usage
        return result

        research_result: dict,

        )

The SQL Server Equivalent

For teams whose application layer runs against SQL Server, the same coordination model translates directly, with two differences: SQL Server uses sp_getapplock or UPDLOCK/READPAST hints in place of SKIP LOCKED, and it uses Service Broker or WAITFOR in place of LISTEN/NOTIFY.

-- SQL Server: agent_tasks table (key differences highlighted)
CREATE TABLE agent_tasks (
    task_id         UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWSEQUENTIALID(),
    run_id          UNIQUEIDENTIFIER NOT NULL,
    parent_task_id  UNIQUEIDENTIFIER NULL,
    task_type       NVARCHAR(64) NOT NULL,
    task_name       NVARCHAR(256) NOT NULL,
    priority        INT NOT NULL DEFAULT 5,
    status          NVARCHAR(32) NOT NULL DEFAULT 'pending'
                        CONSTRAINT chk_task_status CHECK (status IN
                            ('pending','claimed','running','completed',
                             'failed','cancelled','retrying')),
    retry_count     INT NOT NULL DEFAULT 0,
    max_retries     INT NOT NULL DEFAULT 3,
    input_data      NVARCHAR(MAX) NOT NULL DEFAULT '{}',  -- JSON stored as NVARCHAR
    output_data     NVARCHAR(MAX) NULL,
    error_detail    NVARCHAR(MAX) NULL,
    assigned_to     NVARCHAR(256) NULL,
    claimed_at      DATETIMEOFFSET NULL,
    started_at      DATETIMEOFFSET NULL,
    completed_at    DATETIMEOFFSET NULL,
    deadline        DATETIMEOFFSET NULL,
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    updated_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET()
);

-- Filtered index equivalent for the claimable queue
CREATE INDEX idx_tasks_claimable
    ON agent_tasks(task_type, priority, created_at)
    WHERE status = 'pending';

-- SQL Server: atomic task claiming with UPDLOCK + READPAST
-- READPAST skips locked rows (equivalent to SKIP LOCKED in PostgreSQL)
CREATE OR ALTER PROCEDURE dbo.ClaimNextTask
    @task_type   NVARCHAR(64),
    @agent_id    NVARCHAR(256),
    @task_id     UNIQUEIDENTIFIER OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET @task_id = NULL;

    BEGIN TRANSACTION;

    -- READPAST skips rows locked by other agents; UPDLOCK prevents phantom reads
    ;WITH ready AS (
        SELECT TOP 1 t.task_id
        FROM agent_tasks t WITH (UPDLOCK, READPAST, ROWLOCK)
        WHERE t.task_type  = @task_type
          AND t.status     = 'pending'
          AND (t.deadline IS NULL OR t.deadline > SYSDATETIMEOFFSET())
          AND NOT EXISTS (
              SELECT 1 FROM agent_tasks dep
              WHERE dep.task_id IN (
                  SELECT value FROM OPENJSON(t.input_data, '$.depends_on')
              )
              AND dep.status != 'completed'
          )
        ORDER BY t.priority ASC, t.created_at ASC
    )
    UPDATE agent_tasks
    SET status      = 'claimed',
        assigned_to = @agent_id,
        claimed_at  = SYSDATETIMEOFFSET(),
        updated_at  = SYSDATETIMEOFFSET()
    OUTPUT INSERTED.task_id INTO @task_id
    FROM agent_tasks
    INNER JOIN ready ON agent_tasks.task_id = ready.task_id;

    COMMIT TRANSACTION;
END;

The SQL Server READPAST hint is conceptually equivalent to SKIP LOCKED but has one important behavioral difference: READPAST only skips rows locked at the row level within a transaction that is actively holding those locks. For the queue pattern, this distinction almost never matters in practice, but it is worth knowing when diagnosing unexpected blocking.

For event-driven wake-up on SQL Server, Service Broker provides durable queuing with delivery guarantees, while WAITFOR (RECEIVE ...) provides the blocking wait. The implementation is more verbose than pg_notify but achieves the same result:

-- SQL Server: lightweight notification via Service Broker
-- Create message type, contract, queues, and service (one-time setup)

CREATE MESSAGE TYPE [AgentTaskNotification]
    VALIDATION = WELL_FORMED_XML;

CREATE CONTRACT [AgentTaskContract]
    ([AgentTaskNotification] SENT BY INITIATOR);

CREATE QUEUE AgentNotificationQueue;

CREATE SERVICE [AgentNotificationService]
    ON QUEUE AgentNotificationQueue
    ([AgentTaskContract]);

-- Trigger to fire a notification when a task becomes pending
CREATE OR ALTER TRIGGER trg_task_notify
ON agent_tasks
AFTER INSERT, UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    IF EXISTS (SELECT 1 FROM inserted WHERE status = 'pending')
    BEGIN
        DECLARE @msg XML;
        SELECT @msg = (
            SELECT task_id, task_type, status
            FROM inserted
            WHERE status = 'pending'
            FOR XML PATH('task'), ROOT('tasks')
        );

        DECLARE @handle UNIQUEIDENTIFIER;
        BEGIN DIALOG CONVERSATION @handle
            FROM SERVICE [AgentNotificationService]
            TO SERVICE 'AgentNotificationService'
            ON CONTRACT [AgentTaskContract]
            WITH ENCRYPTION = OFF;

        SEND ON CONVERSATION @handle
            MESSAGE TYPE [AgentTaskNotification]
            (@msg);
    END
END;

-- Agent process: blocking wait for notification (Python side calls this in a loop)
WAITFOR (
    RECEIVE TOP(10)
        conversation_handle,
        message_body
    FROM AgentNotificationQueue
), TIMEOUT 5000;   -- 5 second timeout, then poll anyway

The Python agent on SQL Server replaces asyncpg's add_listener with a thread that repeatedly calls WAITFOR (RECEIVE ...) and posts results into the same asyncio.Queue the rest of the agent logic reads from. The work-claiming and blackboard logic is otherwise structurally identical — only the SQL dialect changes.

Orchestrator Agent: Driving the Whole Workflow

Individual worker agents handle their slice of work. An orchestrator agent's job is different: it watches run-level state, makes planning decisions, spawns new tasks based on what it learns, and decides when a workflow run is complete.

# orchestrator_agent.py
import asyncio
import json
import uuid
import time
from typing import Optional

from agent_base import AgentBase, OPENAI_CLIENT, logger


PLANNER_SYSTEM_PROMPT = """You are a workflow orchestrator. Given the current state
of a research workflow — what tasks are pending, running, completed, or failed,
and what facts and artifacts have been written to the blackboard — decide what
to do next. You can spawn new tasks, mark the run as complete, or escalate a failure.

Output JSON with keys:
  action: "spawn_tasks" | "mark_complete" | "escalate" | "wait"
  tasks: (if spawn_tasks) list of {task_type, task_name, input_data, priority, depends_on}
  reason: brief explanation
  completion_summary: (if mark_complete) summary of what was accomplished
"""


class OrchestratorAgent(AgentBase):

    def __init__(self):
        super().__init__(agent_type="orchestrator", concurrency=1)

    async def _run_task(self, task: dict):
        task_id = str(task["task_id"])
        run_id = str(task["run_id"])
        input_data = task["input_data"]

        start = time.monotonic()

        try:
            decision = await self._plan(run_id, input_data)
            duration_ms = int((time.monotonic() - start) * 1000)

            async with self.pool.acquire() as conn:
                async with conn.transaction():
                    if decision["action"] == "spawn_tasks":
                        for t in decision.get("tasks", []):
                            await conn.execute("""
                                INSERT INTO agent_tasks
                                    (run_id, task_type, task_name, priority,
                                     input_data, depends_on)
                                VALUES ($1, $2, $3, $4, $5, $6)
                            """,
                                uuid.UUID(run_id),
                                t["task_type"],
                                t["task_name"],
                                t.get("priority", 5),
                                json.dumps(t.get("input_data", {})),
                                [uuid.UUID(d) for d in t.get("depends_on", [])],
                            )
                        logger.info(
                            f"Orchestrator spawned {len(decision['tasks'])} tasks "
                            f"for run {run_id}"
                        )

                    elif decision["action"] == "mark_complete":
                        await conn.execute("""
                            UPDATE workflow_runs
                            SET status       = 'completed',
                                completed_at = NOW(),
                                metadata     = metadata || $2
                            WHERE run_id = $1
                        """,
                            uuid.UUID(run_id),
                            json.dumps({"completion_summary": decision.get("completion_summary", "")}),
                        )

                    elif decision["action"] == "escalate":
                        await conn.execute("""
                            UPDATE workflow_runs
                            SET status        = 'failed',
                                completed_at  = NOW(),
                                error_message = $2
                            WHERE run_id = $1
                        """, uuid.UUID(run_id), decision.get("reason", "Escalated by orchestrator"))

                    await self.complete_task(conn, task_id, run_id, decision, duration_ms)

        except Exception as e:
            logger.exception(f"Orchestrator task {task_id} failed: {e}")
            async with self.pool.acquire() as conn:
                await self.fail_task(conn, task_id, run_id, e)

    async def _plan(self, run_id: str, context: dict) -> dict:
        """Gather current workflow state and ask the LLM what to do next."""
        async with self.pool.acquire() as conn:
            # Current task summary
            task_summary = await conn.fetch("""
                SELECT task_type, task_name, status, COUNT(*) AS count
                FROM agent_tasks
                WHERE run_id = $1
                GROUP BY task_type, task_name, status
                ORDER BY task_type, status
            """, uuid.UUID(run_id))

            # Recent blackboard entries
            blackboard_entries = await conn.fetch("""
                SELECT namespace, key, written_by, written_at
                FROM blackboard
                WHERE run_id = $1 AND is_current = TRUE
                ORDER BY written_at DESC
                LIMIT 20
            """, uuid.UUID(run_id))

            # Any failed tasks
            failed_tasks = await conn.fetch("""
                SELECT task_name, task_type, error_detail, retry_count, max_retries
                FROM agent_tasks
                WHERE run_id = $1 AND status = 'failed'
            """, uuid.UUID(run_id))

        state_description = {
            "run_id": run_id,
            "original_goal": context.get("goal", ""),
            "task_summary": [dict(r) for r in task_summary],
            "blackboard_entries": [
                {**dict(r), "written_at": r["written_at"].isoformat()}
                for r in blackboard_entries
            ],
            "failed_tasks": [
                {**dict(r), "error_detail": json.loads(r["error_detail"] or "{}")}
                for r in failed_tasks
            ],
        }

        messages = [
            {"role": "system", "content": PLANNER_SYSTEM_PROMPT},
            {"role": "user", "content": json.dumps(state_description, indent=2)},
        ]

        response = await OPENAI_CLIENT.chat.completions.create(
            model="gpt-4o",
            messages=messages,
            max_tokens=1024,
            response_format={"type": "json_object"},
            temperature=0.1,
        )

        return json.loads(response.choices[0].message.content)

The orchestrator is itself just another agent that processes tasks of type orchestrator. This means it gets the same retry logic, heartbeat monitoring, and event logging as all other agents. The planner LLM call receives a structured snapshot of the entire workflow state — task counts by status, blackboard entry list, failed task details — and returns a structured action. Keeping the LLM's decision as structured JSON means you can log, audit, and replay planning decisions as first-class events.

Handling Workflow Failures Gracefully

Production multi-agent systems fail in ways that single-agent systems do not: a task can fail while its downstream dependents are already queued, a stalled agent can hold a task indefinitely, or an entire run can get stuck in a partial-completion state where some branches succeeded and others failed. PostgreSQL transactions give you the tools to handle each of these cleanly.

The key insight is that failure handling belongs in the database, not in application logic scattered across agent implementations. A set of SQL functions and scheduled jobs handles the common failure modes uniformly.

-- PostgreSQL: cancel all downstream tasks when an ancestor fails permanently
CREATE OR REPLACE FUNCTION cancel_downstream_tasks(failed_task_id UUID)
RETURNS INTEGER AS $$
DECLARE
    cancelled_count INTEGER := 0;
    current_frontier UUID[] := ARRAY[failed_task_id];
    next_frontier UUID[];
    iteration INTEGER := 0;
    max_iterations CONSTANT INTEGER := 20;  -- prevent infinite loops on cycles
BEGIN
    LOOP
        EXIT WHEN array_length(current_frontier, 1) IS NULL;
        EXIT WHEN iteration >= max_iterations;
        iteration := iteration + 1;

        -- Find all pending tasks that depend on any task in current frontier
        WITH cancelled AS (
            UPDATE agent_tasks
            SET status     = 'cancelled',
                error_detail = jsonb_build_object(
                    'reason',           'upstream_failure',
                    'failed_ancestor',  failed_task_id
                ),
                updated_at = NOW()
            WHERE status = 'pending'
              AND depends_on && current_frontier  -- array overlap operator
            RETURNING task_id
        )
        SELECT array_agg(task_id) INTO next_frontier FROM cancelled;

        cancelled_count := cancelled_count + COALESCE(array_length(next_frontier, 1), 0);
        current_frontier := next_frontier;
    END LOOP;

    RETURN cancelled_count;
END;
$$ LANGUAGE plpgsql;

-- Trigger: when a task fails permanently (retry_count >= max_retries),
-- cascade the cancellation downstream
CREATE OR REPLACE FUNCTION handle_permanent_task_failure()
RETURNS TRIGGER AS $$
DECLARE
    downstream_count INTEGER;
BEGIN
    IF NEW.status = 'failed' AND OLD.status != 'failed' THEN
        SELECT cancel_downstream_tasks(NEW.task_id) INTO downstream_count;
        IF downstream_count > 0 THEN
            RAISE NOTICE 'Cancelled % downstream tasks after permanent failure of %',
                downstream_count, NEW.task_id;
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_handle_permanent_failure
    AFTER UPDATE OF status ON agent_tasks
    FOR EACH ROW
    WHEN (NEW.status = 'failed')
    EXECUTE FUNCTION handle_permanent_task_failure();

-- PostgreSQL: mark a run as failed if it has been stuck too long
-- (called by a scheduled job every minute)
CREATE OR REPLACE FUNCTION timeout_stalled_runs(timeout_minutes INTEGER DEFAULT 60)
RETURNS TABLE (
    run_id    UUID,
    reason    TEXT
) AS $$
BEGIN
    RETURN QUERY
    UPDATE workflow_runs wr
    SET status        = 'failed',
        completed_at  = NOW(),
        error_message = format(
            'Run timed out after %s minutes with no progress',
            timeout_minutes
        )
    WHERE wr.status = 'running'
      AND NOT EXISTS (
          SELECT 1 FROM agent_tasks t
          WHERE t.run_id = wr.run_id
            AND t.updated_at > NOW() - (timeout_minutes || ' minutes')::INTERVAL
      )
      AND wr.started_at < NOW() - (timeout_minutes || ' minutes')::INTERVAL
    RETURNING wr.run_id,
              format('Timed out: no task activity in %s minutes', timeout_minutes);
END;
$$ LANGUAGE plpgsql;

-- Cancel downstream tasks (iterative CTE approach)
CREATE OR ALTER PROCEDURE dbo.CancelDownstreamTasks
    @failed_task_id  UNIQUEIDENTIFIER,
    @cancelled_count INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET @cancelled_count = 0;

    -- Build transitive closure of dependents iteratively
    CREATE TABLE #frontier (task_id UNIQUEIDENTIFIER PRIMARY KEY);
    INSERT INTO #frontier VALUES (@failed_task_id);

    DECLARE @batch_count INT = 1;
    DECLARE @iteration   INT = 0;

    WHILE @batch_count > 0 AND @iteration < 20
    BEGIN
        SET @iteration += 1;

        UPDATE t
        SET t.status       = 'cancelled',
            t.error_detail = JSON_OBJECT(
                'reason':          'upstream_failure',
                'failed_ancestor': CAST(@failed_task_id AS NVARCHAR(36))
            ),
            t.updated_at   = SYSDATETIMEOFFSET()
        OUTPUT INSERTED.task_id INTO #frontier
        FROM agent_tasks t
        WHERE t.status = 'pending'
          AND EXISTS (
              SELECT 1
              FROM OPENJSON(t.input_data, '$.depends_on') dep
              JOIN #frontier f ON CAST(dep.value AS UNIQUEIDENTIFIER) = f.task_id
          );

        SET @batch_count = @@ROWCOUNT;
        SET @cancelled_count += @batch_count;
    END;

    DROP TABLE #frontier;
END;

-- Timeout stalled runs
CREATE OR ALTER PROCEDURE dbo.TimeoutStalledRuns
    @timeout_minutes INT = 60
AS
BEGIN
    SET NOCOUNT ON;

    UPDATE wr
    SET wr.status        = 'failed',
        wr.completed_at  = SYSDATETIMEOFFSET(),
        wr.error_message = CONCAT(
            'Run timed out after ', @timeout_minutes,
            ' minutes with no progress'
        )
    FROM workflow_runs wr
    WHERE wr.status = 'running'
      AND wr.started_at < DATEADD(MINUTE, -@timeout_minutes, SYSDATETIMEOFFSET())
      AND NOT EXISTS (
          SELECT 1 FROM agent_tasks t
          WHERE t.run_id = wr.run_id
            AND t.updated_at > DATEADD(MINUTE, -@timeout_minutes, SYSDATETIMEOFFSET())
      );
END;

The downstream cancellation logic uses an iterative frontier expansion rather than a recursive CTE. This is intentional: in production, dependency graphs occasionally develop cycles due to bugs in orchestrator logic, and the max_iterations guard prevents an infinite loop that a naive recursive CTE would not protect against.

Scaling to Many Agents: Connection Management

When you run fifty or a hundred agent processes, each with a connection pool of its own, naive connection management will exhaust PostgreSQL's max_connections limit quickly. The solution has two parts: PgBouncer in transaction-mode pooling in front of PostgreSQL for all read/write operations, and a separate small pool of direct connections for the LISTEN channels (because LISTEN requires a persistent connection that transaction-mode pooling cannot support).

# connection_config.py — shared across all agent processes
import os

# All standard read/write operations go through PgBouncer
PGBOUNCER_URL = os.environ["PGBOUNCER_URL"]       # e.g. postgresql://host:6432/db

# LISTEN connections go directly to PostgreSQL — kept to one per agent process
POSTGRES_DIRECT_URL = os.environ["DATABASE_URL"]   # e.g. postgresql://host:5432/db

# Recommended pool sizes per agent process
POOL_MIN_SIZE = 2
POOL_MAX_SIZE = 4   # small — PgBouncer multiplexes from here to PostgreSQL

import asyncpg

async def create_work_pool() -> asyncpg.Pool:
    """Pool for all task claiming, blackboard, and event logging operations."""
    return await asyncpg.create_pool(
        PGBOUNCER_URL,
        min_size=POOL_MIN_SIZE,
        max_size=POOL_MAX_SIZE,
        # PgBouncer transaction mode doesn't support prepared statements
        statement_cache_size=0,
    )

async def create_listen_connection() -> asyncpg.Connection:
    """Single persistent connection for LISTEN/NOTIFY — bypasses PgBouncer."""
    return await asyncpg.connect(
        POSTGRES_DIRECT_URL,
        statement_cache_size=0,
    )

With PgBouncer in transaction mode, each agent's POOL_MAX_SIZE=4 translates to four server-side connections at PgBouncer, but those are multiplexed across many agent processes. Fifty agents each holding four pool connections in PgBouncer translate to far fewer actual PostgreSQL backend connections than fifty agents each holding four direct connections. The statement_cache_size=0 setting disables asyncpg's automatic prepared statement caching, which is incompatible with transaction-mode pooling (prepared statements are connection-scoped, and transaction-mode pooling routes transactions to different connections).

Observability: Reconstructing What Happened

The event log is only useful if you can query it fluently. These patterns cover the most common observability needs.

-- PostgreSQL: full timeline reconstruction for a single run
-- useful when debugging a run that produced unexpected output
SELECT
    ae.occurred_at,
    ae.agent_instance,
    ae.event_type,
    t.task_name,
    t.task_type,
    ae.duration_ms,
    (ae.token_usage->>'prompt_tokens')::INT    AS prompt_tokens,
    (ae.token_usage->>'completion_tokens')::INT AS completion_tokens,
    ae.event_data
FROM agent_events ae
LEFT JOIN agent_tasks t ON t.task_id = ae.task_id
WHERE ae.run_id = $1   -- substitute actual run_id
ORDER BY ae.occurred_at ASC;

-- PostgreSQL: token spend by agent type for cost attribution
SELECT
    t.task_type,
    COUNT(DISTINCT ae.task_id)                                   AS task_count,
    SUM((ae.token_usage->>'prompt_tokens')::INT)                 AS total_prompt_tokens,
    SUM((ae.token_usage->>'completion_tokens')::INT)             AS total_completion_tokens,
    SUM((ae.token_usage->>'prompt_tokens')::INT
      + (ae.token_usage->>'completion_tokens')::INT)             AS total_tokens,
    ae.token_usage->>'model'                                     AS model
FROM agent_events ae
JOIN agent_tasks t ON t.task_id = ae.task_id
WHERE ae.token_usage IS NOT NULL
  AND ae.occurred_at > NOW() - INTERVAL '24 hours'
GROUP BY t.task_type, ae.token_usage->>'model'
ORDER BY total_tokens DESC;

-- PostgreSQL: detect error patterns across runs
SELECT
    t.task_type,
    t.error_detail->>'error'                                     AS error_message,
    COUNT(*)                                                     AS occurrence_count,
    MAX(t.completed_at)                                          AS last_seen,
    AVG(t.retry_count)                                           AS avg_retries_before_failure
FROM agent_tasks t
WHERE t.status = 'failed'
  AND t.completed_at > NOW() - INTERVAL '7 days'
GROUP BY t.task_type, t.error_detail->>'error'
HAVING COUNT(*) >= 3
ORDER BY occurrence_count DESC;

-- PostgreSQL: blackboard knowledge graph — what did agents discover and share?
SELECT
    b.written_by                                                 AS author_agent,
    b.namespace,
    b.key,
    b.written_at,
    b.version,
    jsonb_array_length(
        CASE jsonb_typeof(b.value)
             WHEN 'array' THEN b.value
             ELSE NULL
        END
    )                                                            AS array_length,
    LENGTH(b.value::TEXT)                                        AS value_size_bytes
FROM blackboard b
WHERE b.run_id = $1
  AND b.is_current = TRUE
ORDER BY b.written_at ASC;

These queries work against the live tables during a run — there is no separate analytics database needed for operational debugging. The same schema that drives agent coordination also drives your debugging workflow.

Testing the Coordination System

Multi-agent coordination code is notoriously hard to test because the interesting behaviors emerge from concurrent execution. A testing approach that works well in practice combines three levels: unit tests against the SQL functions, integration tests using a real PostgreSQL instance with time-accelerated scenarios, and chaos tests that inject failures.

# test_coordination.py
import asyncio
import json

import pytest
import asyncpg

# Assumes a test database URL in the environment

@pytest.mark.asyncio
async def test_atomic_claim_no_double_claim(pool, clean_run):
    """Two concurrent claim attempts on the same task must yield exactly one success."""
    run_id = clean_run
    async with pool.acquire() as conn:
        task_id = await insert_task(conn, run_id)

    claim_query = """
        WITH ready AS (
            SELECT task_id FROM agent_tasks
            WHERE task_type = 'researcher' AND status = 'pending'
            LIMIT 1
            FOR UPDATE SKIP LOCKED
        )
        UPDATE agent_tasks
        SET status = 'claimed', assigned_to = $1, claimed_at = NOW()
        FROM ready
        WHERE agent_tasks.task_id = ready.task_id
        RETURNING agent_tasks.task_id
    """

    # Race two concurrent claim attempts
    async def do_claim(agent_id):
        async with pool.acquire() as conn:
            async with conn.transaction():
                row = await conn.fetchrow(claim_query, agent_id)
                await asyncio.sleep(0.05)  # hold the lock briefly
                return row

    results = await asyncio.gather(
        do_claim("agent-1"),
        do_claim("agent-2"),
        return_exceptions=True,
    )

    successes = [r for r in results if r is not None and not isinstance(r, Exception)]
    assert len(successes) == 1, (
        f"Expected exactly one successful claim, got {len(successes)}: {results}"
    )


@pytest.mark.asyncio
async def test_dependency_ordering(pool, clean_run):
    """A task with an incomplete dependency must not be claimable."""
    run_id = clean_run
    async with pool.acquire() as conn:
        parent_id = await insert_task(conn, run_id, status="running")
        child_id  = await insert_task(conn, run_id, depends_on=[parent_id])

    async with pool.acquire() as conn:
        row = await conn.fetchrow("""
            WITH ready AS (
                SELECT task_id FROM agent_tasks
                WHERE task_type = 'researcher'
                  AND status = 'pending'
                  AND (
                      depends_on = '{}'
                      OR NOT EXISTS (
                          SELECT 1 FROM agent_tasks dep
                          WHERE dep.task_id = ANY(depends_on)
                            AND dep.status != 'completed'
                      )
                  )
                LIMIT 1 FOR UPDATE SKIP LOCKED

            UPDATE agent_tasks SET status='claimed', assigned_to='test-agent'
            FROM ready WHERE agent_tasks.task_id = ready.task_id
            RETURNING agent_tasks.task_id

    assert row is None, "Child task should not be claimable while parent is running"

    # Now complete the parent
    async with pool.acquire() as conn:
        await conn.execute(
            "UPDATE agent_tasks SET status='completed' WHERE task_id=$1",
            uuid.UUID(parent_id)
        )
        # Child should now be claimable
        row = await conn.fetchrow("""
            WITH ready AS (
                SELECT task_id FROM agent_tasks
                WHERE task_type = 'researcher'
                  AND status = 'pending'
                  AND (
                      depends_on = '{}'
                      OR NOT EXISTS (

                          WHERE dep.task_id = ANY(depends_on)
                            AND dep.status != 'completed'

@pytest.mark.asyncio
async def test_downstream_cancellation(pool, clean_run):
    """A permanently failed task should cascade cancellation to its dependents."""
    run_id = clean_run
    async with pool.acquire() as conn:
        parent_id = await insert_task(conn, run_id)
        child_id  = await insert_task(conn, run_id, depends_on=[parent_id])
        grand_id  = await insert_task(conn, run_id, depends_on=[child_id])

        # Permanently fail the parent
        await conn.execute(
            "UPDATE agent_tasks SET status='failed', retry_count=3, max_retries=3 "
            "WHERE task_id=$1",
            uuid.UUID(parent_id)
        )

        # The trigger should have fired; verify downstream cancellations
        rows = await conn.fetch(
            "SELECT task_id, status FROM agent_tasks WHERE run_id=$1 AND task_id != $2",
            uuid.UUID(run_id), uuid.UUID(parent_id)
        )

    status_map = {str(r["task_id"]): r["status"] for r in rows}
    assert status_map.get(child_id) == "cancelled"
    assert status_map.get(grand_id) == "cancelled"

These tests catch the behavioral contracts that matter most: the SKIP LOCKED guarantee prevents double-claiming, dependency ordering is enforced by the claim query, and downstream cancellation propagates correctly through the trigger. Running them against a real PostgreSQL instance (not a mock) is non-negotiable — the behavior you care about is implemented in the database engine, not in Python.

Production Deployment Checklist

Deploying a multi-agent coordination system requires attention to a set of database configuration details that do not matter in development but break things at scale.

Partition agent_events by month. The event log grows fast — a busy system can write tens of thousands of rows per hour. Without partitioning, your queries slow down and your vacuum overhead grows. Declarative partitioning on occurred_at with monthly partitions is the standard approach. Create partitions for the next three months in advance; add a cron job that creates the next month's partition on the first of each month.

-- Convert agent_events to a partitioned table (do this before go-live)
CREATE TABLE agent_events (
    event_id        UUID NOT NULL DEFAULT uuid_generate_v4(),
    run_id          UUID,
    task_id         UUID,
    agent_instance  TEXT NOT NULL,
    event_type      TEXT NOT NULL,
    event_data      JSONB NOT NULL DEFAULT '{}',
    token_usage     JSONB,
    duration_ms     INTEGER,
    occurred_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (occurred_at);

-- Create initial partitions
CREATE TABLE agent_events_2025_01
    PARTITION OF agent_events
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

CREATE TABLE agent_events_2025_02
    PARTITION OF agent_events
    FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

-- Repeat for upcoming months...

-- Each partition gets its own indexes
CREATE INDEX ON agent_events_2025_01 (run_id, occurred_at DESC);
CREATE INDEX ON agent_events_2025_01 (task_id, occurred_at DESC);

Set lock_timeout on agent connections. If a lock wait exceeds your expected claim latency, something is wrong and the agent should back off rather than piling up waiting connections.

-- Set at connection time in your agent pool setup
SET lock_timeout = '2s';
SET statement_timeout = '30s';

Monitor pg_stat_activity for long-running transactions. An agent that crashes mid-transaction holds its locks until the connection is closed. PgBouncer's server_idle_transaction_timeout will clean these up, but you should also alert when pg_stat_activity shows transactions older than your heartbeat interval.

-- Alert query: transactions running longer than 60 seconds
SELECT
    pid,
    usename,
    application_name,
    state,
    EXTRACT(EPOCH FROM (NOW() - xact_start)) AS transaction_age_seconds,
    LEFT(query, 200) AS query_snippet
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND EXTRACT(EPOCH FROM (NOW() - xact_start)) > 60
ORDER BY transaction_age_seconds DESC;

Use pg_partman or a scheduled procedure to drop old event partitions. Keeping event data forever is expensive. Define a retention policy — ninety days is common for debugging purposes — and enforce it by dropping old partitions rather than running DELETE statements. Dropping a partition is nearly instantaneous; deleting millions of rows is not.

Index the blackboard table's embedding column only after initial data load. IVFFlat indexes require a training pass over the data. If you build the index on an empty table (as the schema definition does), it will work but will not be well-calibrated until you add significant data. For production, build the index after you have a representative data set, and plan to rebuild it periodically as your data distribution shifts.

Key Takeaways

  • → **PostgreSQL's `SELECT ... FOR UPDATE SKIP LOCKED` is the correct primitive for multi-agent task queuing.** It provides atomic, non-blocking task claiming without any application-level locking, deadlock risk, or external queue infrastructure. Two agents will never receive the same task.
  • → **The blackboard pattern — a versioned, semantically searchable shared memory table — gives agents a structured way to share discoveries.** By embedding blackboard entries with pgvector, any agent can perform semantic search over everything the collective system has learned within a run, enabling knowledge reuse without tight coupling between agent types.
  • → **`LISTEN/NOTIFY` provides sub-second event-driven wake-up, but requires a dedicated persistent connection per agent process.** Use a separate direct connection for `LISTEN` and route all actual data operations through PgBouncer in transaction mode to keep total PostgreSQL backend connection count manageable at scale.
  • → **Failure handling should live in the database layer as triggers and functions, not scattered across agent implementations.** Downstream cascade cancellation, stall detection, and run timeout logic expressed as SQL are applied uniformly regardless of which agent type or language triggers the failure — eliminating an entire class of failure-mode inconsistencies.
  • → **The event log and blackboard together give you full workflow observability using plain SQL.** You can reconstruct the complete timeline of any run, attribute token costs by agent type, detect recurring error patterns, and understand what each agent contributed to the shared knowledge space — all without a separate observability stack.
