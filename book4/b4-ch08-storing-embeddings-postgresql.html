Chapter 8: Creating and Storing Embeddings in PostgreSQL

Embeddings are the bridge between unstructured text and the mathematical operations that make semantic search possible. If you've spent years designing schemas for structured data, the shift to storing 1,536-dimensional floating-point vectors alongside your rows can feel disorienting—but the underlying database engineering is familiar territory. This chapter walks through the complete workflow: generating embeddings from text using the OpenAI API and open-source alternatives, storing them efficiently in PostgreSQL using the pgvector extension, and structuring your schema for the query patterns you'll actually run in production. By the end, you'll have a working embedding pipeline that integrates with existing PostgreSQL infrastructure and handles the edge cases that break naive implementations.

---

8.1 How Embeddings Fit Into a PostgreSQL Schema

Before writing any code, it helps to understand what you're actually storing. An embedding is a fixed-length array of 32-bit floats. The OpenAI text-embedding-3-small model produces 1,536 floats per input string. A single embedding consumes 1,536 × 4 bytes = 6,144 bytes, or roughly 6 KB. At 1 million rows, that's approximately 6 GB of raw vector data before indexes.

From a PostgreSQL internals perspective, pgvector introduces a new column type called vector(n) where n is the number of dimensions. This type stores the float array in a binary format with a header, and it participates in standard PostgreSQL mechanics: TOAST for oversized tuples, MVCC, WAL, logical replication, and point-in-time recovery all work as expected. The extension adds three distance operators that map directly to similarity functions:

| Operator | Function | Use Case |

|---|---|---|

| <-> | L2 (Euclidean) distance | When absolute magnitude matters |

| <#> | Negative inner product | Max inner product search, dot product similarity |

| <=> | Cosine distance | Normalized text embeddings (most common) |

For text embeddings from OpenAI, Cohere, or sentence-transformers, cosine distance (<=>) is almost always correct. These models output normalized or near-normalized vectors, and cosine distance measures the angle between them regardless of magnitude. L2 distance works better for embeddings where magnitude carries meaning, such as certain vision or audio models.

A minimal schema that stores document embeddings alongside their source text looks like this:

-- PostgreSQL / pgvector

-- Enable the extension (requires superuser or pg_extension_owner membership)
CREATE EXTENSION IF NOT EXISTS vector;

-- Core documents table
CREATE TABLE documents (
    id          BIGSERIAL PRIMARY KEY,
    source_url  TEXT,
    title       TEXT NOT NULL,
    body        TEXT NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Chunks table — documents are split before embedding
-- Typical chunk size: 256–512 tokens for retrieval tasks
CREATE TABLE document_chunks (
    id              BIGSERIAL PRIMARY KEY,
    document_id     BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    chunk_index     INT NOT NULL,           -- position within parent document
    chunk_text      TEXT NOT NULL,          -- the actual text that was embedded
    token_count     INT,                    -- tokens used for this chunk
    embedding       vector(1536),           -- OpenAI text-embedding-3-small dimensions
    model_name      TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    embedded_at     TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (document_id, chunk_index)
);

-- Standard B-tree indexes for filtered queries
CREATE INDEX ON document_chunks (document_id);
CREATE INDEX ON document_chunks (model_name);
CREATE INDEX ON document_chunks (embedded_at);

-- Partial index: only index rows where embedding is populated
-- This avoids wasting index space on unprocessed chunks
CREATE INDEX ON document_chunks (id) WHERE embedding IS NULL;

The separation between documents and document_chunks is not optional for production systems. Embedding models have token limits—OpenAI's embedding models cap at 8,191 tokens. More importantly, shorter chunks produce more precise retrieval results. A chunk of 256–512 tokens typically outperforms a full 2,000-token document on recall benchmarks because the embedding captures a specific concept rather than a diffuse mixture of topics. The chunk_index column preserves ordering so you can reconstruct context windows around matching chunks during retrieval.

8.2 Generating Embeddings with the OpenAI API

The OpenAI embeddings endpoint is the most common starting point. The API is stateless and synchronous: you send text, you receive a vector. The key operational concerns are batching, error handling, token limits, and cost.

OpenAI's text-embedding-3-small costs $0.02 per million tokens as of mid-2024, compared to $0.13 per million tokens for text-embedding-3-large. For most retrieval applications, text-embedding-3-small at 1,536 dimensions outperforms the older text-embedding-ada-002 at the same cost point, making it the default choice for new projects.

The following Python script handles the full embedding generation workflow: chunking a document, calling the API in batches, and inserting results into PostgreSQL via psycopg2. Batching up to 2,048 inputs per API call is supported by OpenAI; staying at 100–500 per batch is a practical compromise between throughput and memory pressure.

# Python
import os
import time
import psycopg2
import psycopg2.extras
from openai import OpenAI
from typing import Generator

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

DB_DSN = os.environ.get(
    "DATABASE_URL",
    "postgresql://postgres:password@localhost:5432/vectordb"
)

EMBEDDING_MODEL = "text-embedding-3-small"
EMBEDDING_DIMENSIONS = 1536
BATCH_SIZE = 100          # inputs per API call
MAX_TOKENS_PER_CHUNK = 500  # approximate; 1 token ≈ 4 characters


def chunk_text(text: str, max_chars: int = 2000) -> Generator[str, None, None]:
    """
    Simple paragraph-aware chunker.
    Production systems should use tiktoken for precise token counting.
    """
    paragraphs = text.split("\n\n")
    current_chunk = []
    current_len = 0

    for para in paragraphs:
        para = para.strip()
        if not para:
            continue
        if current_len + len(para) > max_chars and current_chunk:
            yield "\n\n".join(current_chunk)
            current_chunk = [para]
            current_len = len(para)
        else:
            current_chunk.append(para)
            current_len += len(para)

    if current_chunk:
        yield "\n\n".join(current_chunk)


def get_embeddings(texts: list[str], retries: int = 3) -> list[list[float]]:
    """
    Call OpenAI embeddings API with retry logic for rate limits.
    Returns a list of embedding vectors in the same order as input texts.
    """
    for attempt in range(retries):
        try:
            response = client.embeddings.create(
                model=EMBEDDING_MODEL,
                input=texts,
            )
            # The API guarantees same-order response as input
            return [item.embedding for item in response.data]
        except Exception as e:
            if "rate_limit" in str(e).lower() and attempt < retries - 1:
                wait = 2 ** attempt  # exponential backoff: 1s, 2s, 4s
                print(f"Rate limited. Waiting {wait}s before retry {attempt + 1}")
                time.sleep(wait)
            else:
                raise


def embed_document(document_id: int, title: str, body: str) -> int:
    """
    Chunk and embed a document, storing results in document_chunks.
    Returns the number of chunks created.
    """
    chunks = list(chunk_text(body))
    if not chunks:
        return 0

    conn = psycopg2.connect(DB_DSN)
    inserted = 0

    try:
        # Process in batches to respect API limits
        for batch_start in range(0, len(chunks), BATCH_SIZE):
            batch_texts = chunks[batch_start : batch_start + BATCH_SIZE]
            embeddings = get_embeddings(batch_texts)

            rows = []
            for i, (text, embedding) in enumerate(zip(batch_texts, embeddings)):
                chunk_index = batch_start + i
                token_estimate = len(text) // 4  # rough estimate
                rows.append({
                    "document_id": document_id,
                    "chunk_index": chunk_index,
                    "chunk_text": text,
                    "token_count": token_estimate,
                    "embedding": embedding,
                    "model_name": EMBEDDING_MODEL,
                })

            with conn.cursor() as cur:
                psycopg2.extras.execute_values(
                    cur,
                    """
                    INSERT INTO document_chunks
                        (document_id, chunk_index, chunk_text, token_count, embedding, model_name)
                    VALUES %s
                    ON CONFLICT (document_id, chunk_index) DO UPDATE
                        SET chunk_text  = EXCLUDED.chunk_text,
                            token_count = EXCLUDED.token_count,
                            embedding   = EXCLUDED.embedding,
                            model_name  = EXCLUDED.model_name,
                            embedded_at = NOW()
                    """,
                    [
                        (
                            r["document_id"],
                            r["chunk_index"],
                            r["chunk_text"],
                            r["token_count"],
                            r["embedding"],
                            r["model_name"],
                        )
                        for r in rows
                    ],
                    template="(%s, %s, %s, %s, %s::vector, %s)",
                    page_size=BATCH_SIZE,
                )
            conn.commit()
            inserted += len(rows)

    finally:
        conn.close()

    return inserted


if __name__ == "__main__":
    # Example: insert a document and embed it
    conn = psycopg2.connect(DB_DSN)
    with conn.cursor() as cur:
        cur.execute(
            "INSERT INTO documents (title, body) VALUES (%s, %s) RETURNING id",
            ("PostgreSQL Architecture", "PostgreSQL uses a process-per-connection model...\n\n"
             "The shared buffer pool is the primary caching mechanism...\n\n"
             "Write-ahead logging ensures durability across crashes..."),
        )
        doc_id = cur.fetchone()[0]
    conn.commit()
    conn.close()

    count = embed_document(doc_id, "PostgreSQL Architecture", "sample body text")
    print(f"Created {count} embedded chunks for document {doc_id}")

Three implementation details here are worth explaining. First, the ON CONFLICT ... DO UPDATE clause handles re-embedding gracefully. When you upgrade models or fix chunking logic, you re-run the pipeline without managing deletes. Second, the explicit ::vector cast in the execute_values template is required—psycopg2 doesn't know how to serialize Python lists as the pgvector type natively. Third, token estimation using character count divided by 4 is intentionally rough; production systems should use the tiktoken library for precise counts.

8.3 Using Open-Source Embedding Models

The OpenAI API introduces a network call, a cost, and a dependency on an external service. For on-premises deployments, regulated industries, or high-throughput scenarios where per-token costs accumulate quickly, running an embedding model locally is the correct tradeoff.

The sentence-transformers library provides access to hundreds of pretrained models that run on CPU or GPU. The all-MiniLM-L6-v2 model produces 384-dimensional embeddings and runs at roughly 14,000 sentences per second on an 8-core CPU. The BAAI/bge-large-en-v1.5 model at 1,024 dimensions scores near OpenAI's ada-002 on the MTEB benchmark while running entirely locally. For most RAG applications, one of these two models is the right starting point.

# Python
import os
import numpy as np
import psycopg2
import psycopg2.extras
from sentence_transformers import SentenceTransformer

# Model selection:
# all-MiniLM-L6-v2 → 384 dims, fast, good for general retrieval
# BAAI/bge-large-en-v1.5 → 1024 dims, higher quality, 2x slower
# intfloat/e5-large-v2 → 1024 dims, strong on asymmetric retrieval tasks
MODEL_NAME = "BAAI/bge-large-en-v1.5"
EMBEDDING_DIMENSIONS = 1024

# Load once at module level — model loading takes 2–5 seconds
model = SentenceTransformer(MODEL_NAME)

DB_DSN = os.environ.get(
    "DATABASE_URL",
    "postgresql://postgres:password@localhost:5432/vectordb"
)


def embed_texts_local(texts: list[str], batch_size: int = 64) -> np.ndarray:
    """
    Generate embeddings using a local sentence-transformers model.
    Returns a numpy array of shape (len(texts), EMBEDDING_DIMENSIONS).

    BGE models expect a query prefix for retrieval tasks:
    - Documents: embed as-is
    - Queries: prefix with "Represent this sentence: "
    """
    embeddings = model.encode(
        texts,
        batch_size=batch_size,
        normalize_embeddings=True,   # ensures cosine similarity = dot product
        show_progress_bar=len(texts) > 100,
        convert_to_numpy=True,
    )
    return embeddings


def embed_query(query_text: str) -> list[float]:
    """
    Embed a user query. BGE models use a different prefix for queries vs. documents.
    This asymmetric encoding improves retrieval quality on BGE models.
    """
    prefixed = f"Represent this sentence for searching relevant passages: {query_text}"
    embedding = model.encode([prefixed], normalize_embeddings=True)
    return embedding[0].tolist()


def bulk_embed_pending_chunks(batch_size: int = 500) -> int:
    """
    Find chunks without embeddings and fill them using the local model.
    Designed to run as a background job or one-time migration.
    """
    conn = psycopg2.connect(DB_DSN)
    total_processed = 0

    try:
        while True:
            with conn.cursor() as cur:
                # Use the partial index we created on (id) WHERE embedding IS NULL
                cur.execute(
                    """
                    SELECT id, chunk_text
                    FROM document_chunks
                    WHERE embedding IS NULL
                    ORDER BY id
                    LIMIT %s
                    """,
                    (batch_size,),
                )
                rows = cur.fetchall()

            if not rows:
                break

            ids = [r[0] for r in rows]
            texts = [r[1] for r in rows]

            embeddings = embed_texts_local(texts)

            update_data = [
                (embedding.tolist(), model_id)
                for embedding, model_id in zip(embeddings, ids)
            ]

            with conn.cursor() as cur:
                psycopg2.extras.execute_values(
                    cur,
                    """
                    UPDATE document_chunks AS dc
                    SET embedding  = data.embedding::vector,
                        model_name = %s,
                        embedded_at = NOW()
                    FROM (VALUES %s) AS data(embedding, id)
                    WHERE dc.id = data.id::bigint
                    """,
                    update_data,
                    template="(%s, %s)",
                )

            conn.commit()
            total_processed += len(rows)
            print(f"Embedded {total_processed} chunks so far...")

    finally:
        conn.close()

    return total_processed


if __name__ == "__main__":
    # Smoke test: embed a single query and print its first 5 dimensions
    vec = embed_query("How does PostgreSQL handle concurrent writes?")
    print(f"Query embedding: {len(vec)} dimensions, first 5: {vec[:5]}")

    # Run the backfill job
    count = bulk_embed_pending_chunks()
    print(f"Total chunks embedded: {count}")

One tradeoff to understand: sentence-transformers models are session-local. On a multi-process application server, each worker loads the model separately, consuming 500 MB–2 GB of RAM per worker depending on the model. The standard mitigation is to move embedding generation out of the web application entirely—into a dedicated embedding service or a background queue that workers dispatch to asynchronously.

The dimension mismatch between models is a schema problem that must be handled explicitly. If you embed documents with all-MiniLM-L6-v2 (384 dimensions) and later migrate to BAAI/bge-large-en-v1.5 (1,024 dimensions), the column type vector(384) will reject new inserts. The model_name column in the schema above makes this tractable: you can run both models simultaneously during a migration window by using separate columns or a second table, verify retrieval quality, then cut over.

8.4 Building the Vector Index

Storing vectors without an index is viable only up to approximately 100,000 rows. Beyond that threshold, every similarity query becomes a full sequential scan—PostgreSQL reads every row, computes the distance, and sorts. At 1 million rows and 1,536 dimensions, a sequential scan typically takes 3–8 seconds depending on hardware. With an HNSW index, the same query returns in 5–50 milliseconds.

pgvector supports two index types: IVFFlat (inverted file with flat quantization) and HNSW (Hierarchical Navigable Small World graphs). The performance characteristics follow directly from their algorithms:

  • → **IVFFlat** partitions the vector space into `lists` (Voronoi cells) during index build. At query time, it searches only the nearest `probes` cells. Build is fast, memory footprint is low, but recall is lower than HNSW at equivalent speed. Requires data to be pre-loaded before building (`CREATE INDEX AFTER` populating, not before).
  • → **HNSW** builds a multi-layer proximity graph. Query traversal is faster and recall is higher, but the index takes longer to build and consumes more memory (approximately 6–10 bytes per vector per edge, plus the vectors themselves). New rows are inserted directly into the graph, making it better for append-heavy workloads.

    • For most production deployments, HNSW is the right default. The following SQL creates and tunes it:

    -- PostgreSQL / pgvector

-- HNSW index using cosine distance
-- m: number of connections per layer (default 16, range 4–64)
--    Higher m → better recall, larger index, slower build
-- ef_construction: size of the dynamic candidate list during build (default 64)
--    Higher ef_construction → better recall, much slower build
--    Recommended range: 64–200 for production

CREATE INDEX CONCURRENTLY idx_chunks_embedding_hnsw
ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- For filtered queries (e.g., "find similar chunks within document X"),
-- you CANNOT rely on the HNSW index alone — PostgreSQL may choose a seq scan
-- when the WHERE clause is selective. Partial indexes help:

-- Index only chunks from a specific model version
CREATE INDEX CONCURRENTLY idx_chunks_embedding_v2
ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64)
WHERE model_name = 'text-embedding-3-small';

-- Control query-time recall vs. speed tradeoff
-- ef_search=40 is the default; higher values improve recall at cost of latency
-- Set this per-session for queries that require higher accuracy
SET hnsw.ef_search = 100;

-- Verify the index is being used
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    dc.id,
    dc.chunk_text,
    dc.embedding <=> '[0.1, 0.2, ...]'::vector AS distance
FROM document_chunks dc
WHERE dc.model_name = 'text-embedding-3-small'
ORDER BY distance
LIMIT 10;

-- Check index size and usage statistics
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexname::regclass)) AS index_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE tablename = 'document_chunks';

    One operational gotcha: CREATE INDEX CONCURRENTLY on an HNSW index with 1 million rows and ef_construction = 64 takes 20–90 minutes depending on hardware and dimensionality. Plan for this in maintenance windows. The index build is CPU-bound; parallelism is controlled by max_parallel_maintenance_workers. Setting this to 4–8 for the index build session reduces wall-clock time significantly:

    -- PostgreSQL / pgvector

-- Increase parallel workers for this session before running the index build
SET max_parallel_maintenance_workers = 4;

-- For IVFFlat, the rule of thumb for lists is sqrt(row_count)
-- At 1M rows: lists = 1000
-- probes at query time: typically lists / 10 = 100 (higher → better recall, slower)
CREATE INDEX CONCURRENTLY idx_chunks_embedding_ivfflat
ON document_chunks
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 1000);

-- Set probes at query time
SET ivfflat.probes = 100;

    The recall-latency tradeoff is a parameter you tune against your data, not a fixed property of the extension. For RAG applications where top-10 recall at 95% is the target, HNSW with m=16, ef_construction=64, and ef_search=80 is a reasonable starting configuration. Run the MTEB retrieval benchmarks against a sample of your own data to validate.

    8.5 Querying Embeddings in Production

    The query pattern for semantic search in a RAG pipeline has three stages: embed the user query, find nearest neighbors, join to retrieve context. Each stage has production considerations that aren't visible in tutorial examples.

    graph LR
    D[Document] --> CH[Chunk
    256-512 tokens]
    CH --> EMB[Embedding API
    OpenAI / local model]
    EMB --> ST[(document_chunks
    vector column)]
    ST --> IDX[HNSW index]
    Q[User query] --> EMBQ[Embed query]
    EMBQ --> IDX
    IDX --> RES[Top-K chunks]

    *The write path (chunk, embed, store, index) and the read path (embed query, search index) share the same embedding model — that's what makes the vectors comparable.*

    The query below represents a full production pattern: embedding generation, nearest neighbor retrieval with metadata filters, and result hydration in a single round-trip using a parameterized query:

    # Python
import os
import psycopg2
import psycopg2.extras
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
DB_DSN = os.environ.get("DATABASE_URL", "postgresql://postgres:password@localhost:5432/vectordb")

EMBEDDING_MODEL = "text-embedding-3-small"
RETRIEVAL_LIMIT = 10       # retrieve top-10, re-rank to top-5 before sending to LLM
SIMILARITY_THRESHOLD = 0.3  # cosine distance; 0 = identical, 2 = opposite


def embed_query_openai(query: str) -> list[float]:
    response = client.embeddings.create(model=EMBEDDING_MODEL, input=[query])
    return response.data[0].embedding


def retrieve_chunks(
    query: str,
    document_ids: list[int] | None = None,
    limit: int = RETRIEVAL_LIMIT,
) -> list[dict]:
    """
    Retrieve the most semantically similar chunks for a query, optionally filtered by document IDs.
    Returns results ordered by cosine similarity (ascending distance = descending similarity).
    """
    query_embedding = embed_query_openai(query)

    conn = psycopg2.connect(DB_DSN)
    try:
        with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
            # Build the filter clause dynamically
            filter_clause = "WHERE dc.embedding IS NOT NULL"
            params: list = [query_embedding, SIMILARITY_THRESHOLD]

            if document_ids:
                filter_clause += " AND dc.document_id = ANY(%s)"
                params.append(document_ids)

            params.append(limit)

            cur.execute(
                f"""
                SELECT
                    dc.id                AS chunk_id,
                    dc.document_id,
                    dc.chunk_index,
                    dc.chunk_text,
                    dc.token_count,
                    d.title              AS document_title,
                    d.source_url,
                    dc.embedding <=> %s::vector  AS cosine_distance,
                    1 - (dc.embedding <=> %s::vector) AS cosine_similarity
                FROM document_chunks dc
                JOIN documents d ON d.id = dc.document_id
                {filter_clause}
                ORDER BY dc.embedding <=> %s::vector
                LIMIT %s
                """,
                [query_embedding, query_embedding, *params[2:]],
            )
            results = cur.fetchall()
    finally:
        conn.close()

    # Post-filter: discard results below similarity threshold
    return [
        dict(r) for r in results
        if r["cosine_distance"] <= SIMILARITY_THRESHOLD * 2
    ]

    There is a subtle parameter duplication in that query: the embedding vector appears twice in the SELECT list (once for the cosine_distance alias, once for cosine_similarity) and again in the ORDER BY. PostgreSQL does not evaluate the expression three times against the index; the planner recognizes the repeated expression and the ORDER BY drives index access. However, passing the embedding as a bind parameter three times is unavoidable in parameterized queries—you cannot reference a positional parameter by name in standard PostgreSQL parameter syntax. A cleaner approach uses a CTE to bind the embedding once:

    # Python
def retrieve_chunks_cte(
    query: str,
    document_ids: list[int] | None = None,
    limit: int = RETRIEVAL_LIMIT,
) -> list[dict]:
    """
    Same retrieval logic, but binds the query embedding exactly once via a CTE.
    Cleaner parameter management for complex queries.
    """
    query_embedding = embed_query_openai(query)

    conn = psycopg2.connect(DB_DSN)
    try:
        with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
            filter_clause = "WHERE dc.embedding IS NOT NULL"
            params: list = [query_embedding]

            if document_ids:
                filter_clause += " AND dc.document_id = ANY(%s)"
                params.append(document_ids)

            params.append(limit)

            cur.execute(
                f"""
                WITH query_vec AS (
                    SELECT %s::vector AS vec
                )
                SELECT
                    dc.id                              AS chunk_id,
                    dc.document_id,
                    dc.chunk_index,
                    dc.chunk_text,
                    dc.token_count,
                    d.title                            AS document_title,
                    d.source_url,
                    dc.embedding <=> qv.vec            AS cosine_distance,
                    1 - (dc.embedding <=> qv.vec)      AS cosine_similarity
                FROM document_chunks dc
                JOIN documents d ON d.id = dc.document_id
                CROSS JOIN query_vec qv
                {filter_clause}
                ORDER BY dc.embedding <=> qv.vec
                LIMIT %s
                """,
                params,
            )
            results = cur.fetchall()
    finally:
        conn.close()

    return [dict(r) for r in results]

    The CTE version passes the embedding once. The CROSS JOIN query_vec qv adds zero overhead—the CTE materializes a single row, and PostgreSQL folds it into the scan. This pattern becomes especially valuable when the vector participates in multiple distance expressions within the same query, such as hybrid scoring that weights cosine distance against a BM25-style text rank.

    #### Filtered Vector Search and the Pre-Filter Problem

    The most common performance trap in production pgvector deployments is combining WHERE clause filters with ORDER BY distance. Consider this query:

    -- PostgreSQL / pgvector

-- Naive: filter by document_id, then find nearest neighbors
-- The HNSW index searches the full graph first, then filters — this is POST-filtering
-- If document_id = 42 contains only 0.5% of rows, recall collapses

SELECT dc.chunk_text, dc.embedding <=> '[...]'::vector AS dist
FROM document_chunks dc
WHERE dc.document_id = 42
ORDER BY dist
LIMIT 10;

    When PostgreSQL evaluates this query, the planner has two options. If the HNSW index is used, it performs approximate nearest neighbor search across the entire table and then applies the document_id = 42 filter to the candidates returned from the index. If the filtered set is a small fraction of the total table, the index may return fewer than 10 usable results even with a large candidate pool. This is called the post-filter problem.

    The alternative is a sequential scan: PostgreSQL ignores the HNSW index, scans only the rows matching document_id = 42 (using the B-tree index on that column), computes exact distances, and sorts. For highly selective filters—when the filtered set contains thousands to tens of thousands of rows—the sequential scan often produces better results with lower latency than the HNSW post-filter approach.

    The practical strategy is to force this tradeoff explicitly by understanding your data distribution:

    -- PostgreSQL / pgvector

-- Check how many chunks exist per document to understand filter selectivity
SELECT
    document_id,
    COUNT(*) AS chunk_count,
    COUNT(*) * 100.0 / SUM(COUNT(*)) OVER () AS pct_of_total
FROM document_chunks
GROUP BY document_id
ORDER BY chunk_count DESC
LIMIT 20;

-- For small filtered sets (< ~10,000 rows), disable HNSW and use exact search
-- This forces the planner to scan the filtered rows exactly
SET enable_indexscan = off;   -- disables index scans including HNSW
SELECT dc.chunk_text, dc.embedding <=> '[...]'::vector AS dist
FROM document_chunks dc
WHERE dc.document_id = 42
ORDER BY dist
LIMIT 10;
RESET enable_indexscan;

-- Better long-term solution: partition the table by a high-cardinality filter column
-- or use a partial HNSW index per logical partition (e.g., per tenant in SaaS)

-- Partial index for a specific document (useful if one document is queried very frequently)
CREATE INDEX CONCURRENTLY idx_chunks_doc42_hnsw
ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64)
WHERE document_id = 42;

    For multi-tenant SaaS applications where queries are always scoped to a single tenant, building one partial HNSW index per tenant is the cleanest solution when tenant data sizes are large enough to warrant it. For smaller tenants, exact search over their filtered rows is faster than any approximate index.

    #### Hybrid Search: Combining Vector Similarity with Full-Text Search

    Pure vector search misses exact keyword matches. A query for "PostgreSQL 16 logical replication slot" may semantically match a document about replication in general while missing a document that uses those exact terms in a different context. Hybrid search combines cosine similarity with PostgreSQL's built-in full-text search to capture both signals.

    -- PostgreSQL / pgvector

-- Add a full-text search column to the chunks table
ALTER TABLE document_chunks
ADD COLUMN ts_chunk TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('english', chunk_text)) STORED;

CREATE INDEX ON document_chunks USING GIN (ts_chunk);

-- Hybrid search: combine BM25 rank with cosine similarity
-- Reciprocal Rank Fusion (RRF) is a parameter-free fusion method
-- rrf_score = 1 / (k + rank), with k = 60 being the standard value

WITH query_vec AS (
    SELECT '[...]'::vector AS vec  -- substitute actual query embedding
),
query_text AS (
    SELECT to_tsquery('english', 'postgresql & replication & slot') AS tsq
),
vector_ranked AS (
    SELECT
        dc.id,
        dc.chunk_text,
        dc.document_id,
        ROW_NUMBER() OVER (ORDER BY dc.embedding <=> qv.vec) AS vector_rank
    FROM document_chunks dc
    CROSS JOIN query_vec qv
    WHERE dc.embedding IS NOT NULL
    ORDER BY dc.embedding <=> qv.vec
    LIMIT 60   -- retrieve top-60 from each signal, fuse to top-10
),
text_ranked AS (
    SELECT
        dc.id,
        ts_rank_cd(dc.ts_chunk, qt.tsq) AS text_score,
        ROW_NUMBER() OVER (ORDER BY ts_rank_cd(dc.ts_chunk, qt.tsq) DESC) AS text_rank
    FROM document_chunks dc
    CROSS JOIN query_text qt
    WHERE dc.ts_chunk @@ qt.tsq
    ORDER BY text_score DESC
    LIMIT 60
),
fused AS (
    SELECT
        COALESCE(vr.id, tr.id)                        AS chunk_id,
        COALESCE(1.0 / (60 + vr.vector_rank), 0)
            + COALESCE(1.0 / (60 + tr.text_rank), 0)  AS rrf_score
    FROM vector_ranked vr
    FULL OUTER JOIN text_ranked tr ON tr.id = vr.id
)
SELECT
    f.chunk_id,
    dc.chunk_text,
    d.title AS document_title,
    f.rrf_score
FROM fused f
JOIN document_chunks dc ON dc.id = f.chunk_id
JOIN documents d ON d.id = dc.document_id
ORDER BY f.rrf_score DESC
LIMIT 10;

    Reciprocal Rank Fusion is favored in production because it requires no tuning: the constant k = 60 dampens the impact of extreme ranks and is robust to score scale differences between the two signals. Alternatives like linear combination (alpha * cosine_score + (1 - alpha) * bm25_score) require careful per-dataset calibration.

    8.6 Schema Evolution and Model Migration

    Embedding models improve over time. When OpenAI released text-embedding-3-small as a replacement for text-embedding-ada-002, the new model outperformed its predecessor while costing less. Any production system that embeds documents must have a migration path for re-embedding with a new model.

    The naive approach—dropping the embedding column and re-running—has zero downtime resilience. Applications querying during the migration return no results or errors. The correct approach uses a multi-column shadow migration:

    -- PostgreSQL / pgvector

-- Step 1: Add a new column for the new model without touching the old one
ALTER TABLE document_chunks
ADD COLUMN embedding_v2 vector(1536);   -- adjust dimensions if model differs

-- Step 2: Add a migration-tracking index
CREATE INDEX ON document_chunks (id) WHERE embedding_v2 IS NULL;

-- Step 3: Run the backfill in the background (Python job iterates this query)
-- Application continues using embedding column during this window

-- Step 4: After backfill completes, verify coverage
SELECT
    COUNT(*) FILTER (WHERE embedding IS NOT NULL)    AS old_embedded,
    COUNT(*) FILTER (WHERE embedding_v2 IS NOT NULL) AS new_embedded,
    COUNT(*)                                          AS total
FROM document_chunks;

-- Step 5: Switch application queries to use embedding_v2
-- This is a code deploy, not a schema change

-- Step 6: Build the production HNSW index on embedding_v2
CREATE INDEX CONCURRENTLY idx_chunks_embedding_v2_hnsw
ON document_chunks
USING hnsw (embedding_v2 vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Step 7: After the index is live and application is using embedding_v2,
-- drop the old column and its index
DROP INDEX CONCURRENTLY idx_chunks_embedding_hnsw;
ALTER TABLE document_chunks DROP COLUMN embedding;

-- Step 8: Rename for clarity
ALTER TABLE document_chunks RENAME COLUMN embedding_v2 TO embedding;
ALTER INDEX idx_chunks_embedding_v2_hnsw RENAME TO idx_chunks_embedding_hnsw;

    This approach is explicit and reversible. At any point during the backfill, the old index is live and queries work. The application code switch at step 5 is instantaneous and rollback-safe—you simply revert the code deploy.

    For systems with strict schema change policies, a separate migration table avoids column proliferation when migrating through multiple model versions:

    -- PostgreSQL / pgvector

-- Separate table to hold embeddings by model version
-- Allows multiple embedding versions to coexist without schema changes
CREATE TABLE chunk_embeddings (
    chunk_id    BIGINT NOT NULL REFERENCES document_chunks(id) ON DELETE CASCADE,
    model_name  TEXT NOT NULL,
    dimensions  INT NOT NULL,
    embedding   vector(1536),  -- must match maximum expected dimensions
    embedded_at TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (chunk_id, model_name)
);

CREATE INDEX CONCURRENTLY idx_chunk_embeddings_hnsw
ON chunk_embeddings
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64)
WHERE model_name = 'text-embedding-3-small';

    The separate-table design has a cost: every similarity query requires a JOIN. For high-QPS applications, the join overhead is measurable. The tradeoff is flexibility during migration versus query performance during steady state. Most teams start with the single-column approach and add the separation only when managing three or more model versions simultaneously.

    8.7 Operational Monitoring and Maintenance

    Running vectors in production adds two monitoring concerns that don't exist in purely relational schemas: index health and embedding pipeline throughput.

    #### Index Bloat and VACUUM

    HNSW indexes in pgvector do not support in-place deletion of dead vectors from the graph. When rows are updated or deleted, the corresponding nodes in the HNSW graph become logically deleted but remain in the structure until a VACUUM operation cleans them. High update rates on the embedding column—typical during initial backfills or model migrations—can create significant bloat. Monitor with:

    -- PostgreSQL

-- Check for dead tuples and bloat in the chunks table
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
    last_vacuum,
    last_autovacuum,
    last_analyze
FROM pg_stat_user_tables
WHERE relname = 'document_chunks';

-- If dead_pct is high after a migration, run a manual VACUUM ANALYZE
VACUUM ANALYZE document_chunks;

-- For autovacuum tuning on embedding-heavy tables:
-- Lower the threshold so autovacuum triggers more frequently
ALTER TABLE document_chunks SET (
    autovacuum_vacuum_scale_factor = 0.01,  -- trigger at 1% dead tuples
    autovacuum_analyze_scale_factor = 0.01
);

    #### Embedding Pipeline Monitoring

    Track these metrics in your application observability stack:

    # Python — instrumentation pattern for embedding pipelines

import time
import logging
from dataclasses import dataclass, field
from datetime import datetime

logger = logging.getLogger(__name__)


@dataclass
class EmbeddingPipelineMetrics:
    chunks_processed: int = 0
    chunks_failed: int = 0
    api_calls: int = 0
    total_tokens: int = 0
    total_latency_ms: float = 0.0
    start_time: datetime = field(default_factory=datetime.utcnow)

    def record_batch(
        self,
        batch_size: int,
        token_count: int,
        latency_ms: float,
        success: bool = True,
    ) -> None:
        self.api_calls += 1
        self.total_latency_ms += latency_ms
        if success:
            self.chunks_processed += batch_size
            self.total_tokens += token_count
        else:
            self.chunks_failed += batch_size

    def report(self) -> dict:
        elapsed = (datetime.utcnow() - self.start_time).total_seconds()
        return {
            "chunks_processed": self.chunks_processed,
            "chunks_failed": self.chunks_failed,
            "api_calls": self.api_calls,
            "total_tokens": self.total_tokens,
            "avg_latency_ms": self.total_latency_ms / max(self.api_calls, 1),
            "throughput_chunks_per_sec": self.chunks_processed / max(elapsed, 1),
            "elapsed_seconds": elapsed,
        }


def get_embedding_pipeline_lag(conn) -> dict:
    """
    Returns metrics on how many chunks are waiting to be embedded.
    Run this as a scheduled job and emit to your metrics system.
    """
    with conn.cursor() as cur:
        cur.execute(
            """
            SELECT
                COUNT(*) FILTER (WHERE embedding IS NULL)     AS pending,
                COUNT(*) FILTER (WHERE embedding IS NOT NULL) AS embedded,
                COUNT(*)                                       AS total,
                MIN(created_at) FILTER (WHERE embedding IS NULL) AS oldest_pending
            FROM document_chunks
            """
        )
        row = cur.fetchone()
        return {
            "pending_chunks": row[0],
            "embedded_chunks": row[1],
            "total_chunks": row[2],
            "oldest_pending_at": row[3].isoformat() if row[3] else None,
        }

    Tracking oldest_pending_at is more operationally useful than raw count. A backlog of 50,000 chunks is acceptable if they arrived in the last hour; the same number is alarming if the oldest chunk is 12 hours old, indicating a pipeline stall.

    Key Takeaways

  • → **Embeddings are fixed-size float arrays stored in `vector(n)` columns.** For OpenAI `text-embedding-3-small`, that is 1,536 dimensions consuming 6 KB per row. Separate the documents table from a chunks table to handle token limits and improve retrieval precision.
  • → **Batch your API calls and handle rate limits with exponential backoff.** The OpenAI embeddings endpoint supports up to 2,048 inputs per request; 100–500 per batch is a practical production target. Use `ON CONFLICT DO UPDATE` to make the pipeline idempotent.
  • → **Choose the HNSW index for append-heavy workloads and IVFFlat when you need lower memory overhead with acceptable recall.** Tune `ef_search` at query time to balance recall against latency without rebuilding the index.
  • → **Filtered vector search requires explicit strategy.** The post-filter problem means HNSW recall collapses for highly selective WHERE clauses. Use partial indexes for frequently filtered subsets, or allow the planner to fall back to exact sequential scan for small filtered sets.
  • → **Model migration follows a shadow-column pattern.** Add a new embedding column, backfill in the background, switch application code to use the new column, build the new index, then drop the old column. This keeps queries functional at every step and makes the cutover instantaneous and rollback-safe.
