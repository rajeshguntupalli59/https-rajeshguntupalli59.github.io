Chapter 34: Access Control on Vector Data

Vector databases introduce a category of access control problems that traditional RBAC models weren't designed to solve. A row in a relational table is discrete and bounded — you can grant SELECT on a specific table, filter rows by tenant ID, and call it done. A vector embedding is a compressed semantic fingerprint of content that may span topics, contain implicit references to sensitive material, or be retrievable through queries that have no obvious surface-level connection to the underlying data. When a similarity search returns the top-k nearest neighbors, you cannot predict at query time which documents will surface. This chapter covers how to apply row-level security, namespace isolation, API key scoping, and query-time filtering to vector data across pgvector, Pinecone, Weaviate, and Qdrant — and how to build a unified authorization layer that treats vector search as a first-class security boundary.

---

Why Vector Access Control Is Different

In a traditional database, access control answers a simple question: does this user have permission to read this row? The data model is explicit. You can enumerate rows, apply predicates, and reason about what any given query will return before it executes.

Vector search inverts this relationship. You start with a query embedding and find what's similar. The result set is determined by geometric proximity in high-dimensional space, not by a filter predicate written at design time. A user querying for "quarterly financial projections" might pull a document fragment that was never explicitly tagged as sensitive but happens to be semantically close to their query vector. Conversely, strict keyword-based filtering might block a legitimate user from finding a document because the metadata doesn't match even though the content is relevant.

Three properties of vector data create novel access control challenges:

Semantic bleed. Embeddings from different security domains can cluster near each other if the underlying content is topically adjacent. A public FAQ about drug interactions and a restricted clinical trial protocol might embed within similar vector space because they share vocabulary. Namespace separation prevents this — you don't filter after the fact, you never allow the query to reach restricted vectors.

Inference risk. Even if a user cannot read a document directly, the fact that a similarity search returns zero results from a namespace they have permission to query can reveal that certain content exists. This is a vector analogue of a timing side-channel. Designing around it requires either returning null results uniformly regardless of permission state or ensuring the user never knows a restricted namespace exists.

Metadata exposure. Most vector databases store metadata payloads alongside embeddings. The embedding itself may be meaningless to an attacker, but the metadata often contains document titles, author IDs, timestamps, and excerpts. Access control that secures the embedding but exposes the payload is incomplete.

The practical architecture for addressing these challenges combines three layers: storage-level isolation (namespaces and collections), query-time filtering (metadata predicates applied before returning results), and application-level enforcement (authorization checks before the vector query is even dispatched).

Row-Level Security in pgvector

PostgreSQL's Row-Level Security (RLS) is the most mature access control mechanism available in the vector database ecosystem because pgvector is a PostgreSQL extension. Every security primitive PostgreSQL exposes — roles, policies, column-level grants, views — applies directly to vector data.

The baseline pattern stores a tenant_id or user_id alongside the embedding vector and attaches RLS policies that automatically filter queries to rows the current user owns.

-- PostgreSQL / pgvector

-- Create the documents table with tenant isolation
CREATE TABLE document_embeddings (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id   TEXT NOT NULL,
    content     TEXT NOT NULL,
    embedding   vector(1536),
    metadata    JSONB DEFAULT '{}',
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- Index for ANN search
CREATE INDEX ON document_embeddings 
USING ivfflat (embedding vector_cosine_ops) 
WITH (lists = 100);

-- Index for tenant filtering (critical for performance)
CREATE INDEX ON document_embeddings (tenant_id);

-- Enable RLS
ALTER TABLE document_embeddings ENABLE ROW LEVEL SECURITY;

-- Policy: tenants can only read their own rows
CREATE POLICY tenant_isolation ON document_embeddings
    FOR ALL
    USING (tenant_id = current_setting('app.current_tenant', true));

-- Policy: service role bypasses RLS for admin operations
CREATE POLICY service_bypass ON document_embeddings
    FOR ALL
    TO service_role
    USING (true);

-- Grant table access to application role (RLS handles row filtering)
GRANT SELECT, INSERT ON document_embeddings TO app_role;

At query time, the application sets the tenant context before issuing the vector search:

-- PostgreSQL / pgvector

-- Set tenant context for the current session
SET LOCAL app.current_tenant = 'tenant_acme_corp';

-- Similarity search — RLS automatically scopes to tenant_acme_corp rows
SELECT 
    id,
    content,
    metadata,
    1 - (embedding <=> $1::vector) AS similarity_score
FROM document_embeddings
WHERE 1 - (embedding <=> $1::vector) > 0.75
ORDER BY embedding <=> $1::vector
LIMIT 10;

-- Verify the plan respects RLS (check for Filter on tenant_id)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, content, 1 - (embedding <=> $1::vector) AS score
FROM document_embeddings
ORDER BY embedding <=> $1::vector
LIMIT 10;

A frequent performance pitfall: when RLS adds a WHERE tenant_id = X predicate to an IVFFlat or HNSW scan, PostgreSQL must evaluate the policy after the ANN index returns candidates, not before. If your lists = 100 index returns 200 candidates but only 3 belong to the current tenant, your effective recall is severely degraded and you've wasted I/O on irrelevant rows.

The solution is to use a composite index that includes the tenant ID as a partition key, or to maintain separate IVFFlat indexes per tenant using table partitioning:

-- PostgreSQL / pgvector

-- Partition by tenant for performance isolation
CREATE TABLE document_embeddings_partitioned (
    id          UUID NOT NULL DEFAULT gen_random_uuid(),
    tenant_id   TEXT NOT NULL,
    content     TEXT NOT NULL,
    embedding   vector(1536),
    metadata    JSONB DEFAULT '{}'
) PARTITION BY LIST (tenant_id);

-- Create per-tenant partitions
CREATE TABLE doc_embeddings_acme 
    PARTITION OF document_embeddings_partitioned
    FOR VALUES IN ('tenant_acme_corp');

CREATE TABLE doc_embeddings_globex
    PARTITION OF document_embeddings_partitioned
    FOR VALUES IN ('tenant_globex');

-- Per-partition IVFFlat indexes
CREATE INDEX ON doc_embeddings_acme 
USING ivfflat (embedding vector_cosine_ops) WITH (lists = 50);

CREATE INDEX ON doc_embeddings_globex
USING ivfflat (embedding vector_cosine_ops) WITH (lists = 50);

-- RLS still applies, but the planner now prunes to a single partition
ALTER TABLE document_embeddings_partitioned ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_partitioned ON document_embeddings_partitioned
    FOR ALL
    USING (tenant_id = current_setting('app.current_tenant', true));

For Supabase deployments, which run managed PostgreSQL with pgvector, this RLS pattern works identically. Supabase's auth system automatically populates auth.uid() which you can use as the tenant identifier directly in policies:

-- PostgreSQL / pgvector (Supabase)

-- Supabase-specific policy using auth context
CREATE POLICY user_owns_documents ON document_embeddings
    FOR SELECT
    USING (user_id = auth.uid());

CREATE POLICY user_inserts_own ON document_embeddings
    FOR INSERT
    WITH CHECK (user_id = auth.uid());

Namespace Isolation in Pinecone and Weaviate

Managed vector databases handle multi-tenancy through namespace and collection isolation rather than SQL-style policies. The security model is coarser — you're working at the API key and namespace level rather than per-row policies — but the operational simplicity trades off well for most SaaS applications.

Pinecone namespaces partition vectors within an index so that operations on one namespace never touch vectors in another. All three operations — upsert, query, and delete — accept a namespace parameter. Vectors without a namespace land in the default namespace, which is a common source of tenant data leakage during development.

# Python
import os
from pinecone import Pinecone, ServerlessSpec
from openai import OpenAI

pc = Pinecone(api_key=os.environ["PINECONE_API_KEY"])
openai_client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

# Create index if it doesn't exist
index_name = "document-store"
if index_name not in pc.list_indexes().names():
    pc.create_index(
        name=index_name,
        dimension=1536,
        metric="cosine",
        spec=ServerlessSpec(cloud="aws", region="us-east-1")
    )

index = pc.Index(index_name)

def embed_text(text: str) -> list[float]:
    response = openai_client.embeddings.create(
        input=text,
        model="text-embedding-3-small"
    )
    return response.data[0].embedding

def upsert_for_tenant(tenant_id: str, documents: list[dict]) -> None:
    """
    All writes are scoped to the tenant's namespace.
    Cross-namespace writes require separate API key issuance at the
    infrastructure level — namespaces themselves are not credential-bound.
    """
    vectors = []
    for doc in documents:
        embedding = embed_text(doc["content"])
        vectors.append({
            "id": doc["id"],
            "values": embedding,
            "metadata": {
                "content": doc["content"],
                "source": doc.get("source", ""),
                "tenant_id": tenant_id,   # redundant but useful for audit
                "classification": doc.get("classification", "internal")
            }
        })
    
    # namespace= is the hard isolation boundary
    index.upsert(vectors=vectors, namespace=tenant_id)

def query_for_tenant(
    tenant_id: str, 
    query_text: str, 
    top_k: int = 10,
    classification_filter: str | None = None
) -> list[dict]:
    """
    Query is restricted to tenant namespace.
    Optional metadata filter further restricts by classification.
    """
    query_embedding = embed_text(query_text)
    
    # Build metadata filter if classification scope is provided
    filter_dict = None
    if classification_filter:
        filter_dict = {"classification": {"$eq": classification_filter}}
    
    results = index.query(
        vector=query_embedding,
        top_k=top_k,
        namespace=tenant_id,          # hard namespace isolation
        filter=filter_dict,            # optional metadata predicate
        include_metadata=True
    )
    
    return [
        {
            "id": match.id,
            "score": match.score,
            "content": match.metadata.get("content", ""),
            "classification": match.metadata.get("classification", "")
        }
        for match in results.matches
    ]

# Usage
upsert_for_tenant("acme_corp", [
    {"id": "doc-001", "content": "Q3 revenue targets", "classification": "confidential"},
    {"id": "doc-002", "content": "Employee handbook", "classification": "internal"}
])

# This query cannot reach globex_corp documents — namespace enforces that
results = query_for_tenant("acme_corp", "financial targets", classification_filter="confidential")

Pinecone's namespace model has a significant architectural constraint: there is no native per-namespace API key. A single API key has access to all namespaces in the index. This means namespace isolation is enforced entirely by your application layer — if your query function is called with the wrong tenant ID, you'll get cross-tenant data. The architecture that addresses this is a server-side authorization proxy that validates the caller's identity before injecting the namespace parameter:

# Python
# Authorization proxy pattern — never trust client-supplied tenant_id
import jwt
from functools import wraps
from fastapi import FastAPI, HTTPException, Depends
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

app = FastAPI()
security = HTTPBearer()

SECRET_KEY = os.environ["JWT_SECRET"]

def get_verified_tenant(
    credentials: HTTPAuthorizationCredentials = Depends(security)
) -> str:
    """
    Validate JWT and extract tenant claim.
    The tenant_id used in Pinecone namespace queries comes ONLY
    from the verified token, never from the request body.
    """
    try:
        payload = jwt.decode(
            credentials.credentials, 
            SECRET_KEY, 
            algorithms=["HS256"]
        )
        tenant_id = payload.get("tenant_id")
        if not tenant_id:
            raise HTTPException(status_code=403, detail="No tenant claim in token")
        return tenant_id
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Token expired")
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid token")

@app.post("/search")
async def search_documents(
    query: str,
    top_k: int = 10,
    tenant_id: str = Depends(get_verified_tenant)  # extracted from JWT, not request
):
    results = query_for_tenant(tenant_id, query, top_k=top_k)
    return {"results": results, "tenant": tenant_id}

Weaviate organizes data into classes (schema types) and supports multi-tenancy as a first-class feature. In modern Weaviate versions, tenant isolation can be enabled at the class level, after which each tenant's data is stored in separate segments and queries must specify a tenant key:

# Python
import weaviate
from weaviate.classes.config import Configure, Property, DataType
from weaviate.classes.tenants import Tenant

client = weaviate.connect_to_cloud(
    cluster_url=os.environ["WEAVIATE_URL"],
    auth_credentials=weaviate.auth.AuthApiKey(os.environ["WEAVIATE_API_KEY"])
)

# Create a multi-tenant collection
documents = client.collections.create(
    name="Document",
    multi_tenancy_config=Configure.multi_tenancy(enabled=True),
    properties=[
        Property(name="content", data_type=DataType.TEXT),
        Property(name="source", data_type=DataType.TEXT),
        Property(name="classification", data_type=DataType.TEXT),
    ],
    vectorizer_config=Configure.Vectorizer.text2vec_openai(
        model="text-embedding-3-small"
    )
)

# Register tenants explicitly
documents.tenants.create([
    Tenant(name="acme_corp"),
    Tenant(name="globex"),
])

# Insert objects scoped to a tenant
acme_collection = client.collections.get("Document").with_tenant("acme_corp")
acme_collection.data.insert({
    "content": "Annual security audit findings for ACME infrastructure",
    "source": "security-team",
    "classification": "restricted"
})

# Query scoped to a tenant — physically isolated from other tenants
def search_weaviate(tenant_id: str, query: str, top_k: int = 5) -> list[dict]:
    collection = client.collections.get("Document").with_tenant(tenant_id)
    
    results = collection.query.near_text(
        query=query,
        limit=top_k,
        filters=weaviate.classes.query.Filter.by_property("classification").equal("restricted"),
        return_properties=["content", "source", "classification"]
    )
    
    return [
        {
            "content": obj.properties["content"],
            "classification": obj.properties["classification"],
            "distance": obj.metadata.distance if obj.metadata else None
        }
        for obj in results.objects
    ]

results = search_weaviate("acme_corp", "security vulnerabilities")
client.close()

Weaviate's multi-tenancy implementation physically separates tenant data into different segments on disk, which means a misconfigured query that omits the tenant key raises an error rather than silently returning cross-tenant data. This fail-closed behavior is architecturally superior to Pinecone's namespace model for high-assurance environments.

Metadata Filtering as a Security Predicate

Namespace and collection isolation enforces coarse-grained boundaries between tenants. Within a tenant's namespace, you often need finer-grained access control: a user in acme_corp should only see documents classified at or below their clearance level, or only documents in projects they're assigned to.

Metadata filters serve this purpose, but they carry an important caveat: metadata filters are not a substitute for namespace isolation. They operate after the ANN index has already identified candidate vectors. If a metadata filter is the only barrier between a user and restricted data, a misconfigured filter or a library bug that drops the filter predicate is a security incident.

The correct architecture stacks both controls:

1. Namespace/collection isolation prevents cross-tenant data access unconditionally.

2. Metadata filters enforce within-tenant access control.

# Python
# Qdrant with payload filtering for within-tenant access control
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Distance, VectorParams, PointStruct,
    Filter, FieldCondition, MatchValue, MatchAny,
    models
)

client = QdrantClient(
    url=os.environ["QDRANT_URL"],
    api_key=os.environ["QDRANT_API_KEY"]
)

# Create collection
client.recreate_collection(
    collection_name="documents_acme_corp",  # collection per tenant
    vectors_config=VectorParams(size=1536, distance=Distance.COSINE)
)

def build_access_filter(user_roles: list[str], clearance_level: int) -> Filter:
    """
    Build a Qdrant filter from user's authorization attributes.
    This filter is constructed server-side from the verified identity —
    the calling user never constructs this directly.
    """
    # Map clearance levels: 1=public, 2=internal, 3=confidential, 4=restricted
    allowed_classifications = []
    level_map = {1: "public", 2: "internal", 3: "confidential", 4: "restricted"}
    for level in range(1, clearance_level + 1):
        if level in level_map:
            allowed_classifications.append(level_map[level])
    
    conditions = [
        FieldCondition(
            key="classification",
            match=MatchAny(any=allowed_classifications)
        )
    ]
    
    # Role-based project access
    if "engineering" in user_roles:
        conditions.append(
            FieldCondition(key="department", match=MatchAny(any=["engineering", "all"]))
        )
    elif "finance" in user_roles:
        conditions.append(
            FieldCondition(key="department", match=MatchAny(any=["finance", "all"]))
        )
    
    return Filter(must=conditions)


def authorized_search(
    collection_name: str,
    query_vector: list[float],
    user_roles: list[str],
    clearance_level: int,
    top_k: int = 10
) -> list[dict]:
    access_filter = build_access_filter(user_roles, clearance_level)
    
    results = client.search(
        collection_name=collection_name,
        query_vector=query_vector,
        query_filter=access_filter,
        limit=top_k,
        with_payload=True
    )
    
    # Secondary enforcement: verify returned results match expected criteria
    # Defense in depth — catch any filter bypass at application layer
    verified_results = []
    for result in results:
        payload = result.payload or {}
        doc_classification = payload.get("classification", "restricted")
        
        if doc_classification not in [
            "public", "internal", "confidential", "restricted"
        ][:clearance_level]:
            # Log this as a potential security anomaly and skip
            print(f"SECURITY: Unexpected classification {doc_classification} for user clearance {clearance_level}")
            continue
        
        verified_results.append({
            "id": result.id,
            "score": result.score,
            "content": payload.get("content", ""),
            "classification": doc_classification
        })
    
    return verified_results

The double-verification pattern — filter at the database level AND check again at the application layer — is defense in depth. It adds a small amount of application-side overhead but ensures that a misconfigured index, a library version change that silently drops filter syntax, or an API contract change doesn't result in unauthorized data exposure.

API Key Management and Least-Privilege Design

Every managed vector database issues API keys that carry full read/write/delete privileges by default. For production systems serving multiple users or integration points, this is architecturally equivalent to sharing a database superuser password. The correct approach is to issue the minimum credential required for each integration point.

Pinecone distinguishes between Admin keys (can create/delete indexes) and project-scoped keys (read/write to indexes within a project). Weaviate supports API key authentication with role assignments. Qdrant Cloud has JWT-based API keys with optional scope restrictions.

For systems where the vector database doesn't offer per-namespace API key scoping, the standard pattern is a service mesh or API gateway that:

1. Authenticates the calling service or user with your identity provider

2. Maps the identity to permitted namespaces and operations

3. Injects the appropriate vector DB API key into the upstream request

4. Logs the operation for audit

# Python
# Centralized credential and namespace management
import boto3
import json
from dataclasses import dataclass
from enum import Enum

class VectorOperation(Enum):
    READ = "read"
    WRITE = "write"
    DELETE = "delete"
    ADMIN = "admin"

@dataclass
class VectorAccess:
    tenant_namespace: str
    permitted_operations: list[VectorOperation]
    classification_ceiling: str  # maximum classification this credential can access

class VectorAccessController:
    """
    Mediates all vector database access.
    API keys are stored in AWS Secrets Manager.
    Access decisions are driven by IAM role of the calling service.
    """
    
    def __init__(self):
        self.secrets_client = boto3.client("secretsmanager", region_name="us-east-1")
        self._key_cache = {}
    
    def _get_pinecone_key(self, key_type: str = "app") -> str:
        """Retrieve Pinecone API key from Secrets Manager."""
        secret_name = f"vector-db/pinecone/{key_type}"
        if secret_name not in self._key_cache:
            response = self.secrets_client.get_secret_value(SecretId=secret_name)
            secret = json.loads(response["SecretString"])
            self._key_cache[secret_name] = secret["api_key"]
        return self._key_cache[secret_name]
    
    def get_access_context(self, jwt_payload: dict) -> VectorAccess:
        """
        Map a verified JWT to a VectorAccess context.
        The JWT comes from your IdP (Okta, Auth0, Cognito, etc.)
        """
        tenant_id = jwt_payload["tenant_id"]
        user_roles = jwt_payload.get("roles", [])
        
        # Determine permitted operations from roles
        ops = [VectorOperation.READ]
        if "data-engineer" in user_roles or "service-account" in user_roles:
            ops.append(VectorOperation.WRITE)
        if "data-admin" in user_roles:
            ops.append(VectorOperation.DELETE)
        if "vector-admin" in user_roles:
            ops.append(VectorOperation.ADMIN)
        
        # Determine classification ceiling from clearance attribute
        clearance = jwt_payload.get("clearance_level", 1)
        ceiling_map = {1: "public", 2: "internal", 3: "confidential", 4: "restricted"}
        classification_ceiling = ceiling_map.get(clearance, "public")
        
        return VectorAccess(
            tenant_namespace=tenant_id,
            permitted_operations=ops,
            classification_ceiling=classification_ceiling
        )
    
    def can_perform(self, access: VectorAccess, operation: VectorOperation) -> bool:
        return operation in access.permitted_operations
    
    def execute_query(
        self,
        access: VectorAccess,
        query_vector: list[float],
        top_k: int = 10
    ) -> list[dict]:
        """
        Execute a read operation if the access context permits it.
        The Pinecone API key is retrieved from Secrets Manager,
        never passed through the calling code.
        """
        if not self.can_perform(access, VectorOperation.READ):
            raise PermissionError(f"Tenant {access.tenant_namespace} lacks READ permission")
        
        api_key = self._get_pinecone_key(key_type="app")
        pc = Pinecone(api_key=api_key)
        index = pc.Index("document-store")
        
        # Classification filter derived from access context, not caller input
        classification_filter = self._classification_filter(access.classification_ceiling)
        
        results = index.query(
            vector=query_vector,
            top_k=top_k,
            namespace=access.tenant_namespace,
            filter=classification_filter,
            include_metadata=True
        )
        
        return [
            {
                "id": match.id,
                "score": match.score,
                "content": match.metadata.get("content", ""),
                "classification": match.metadata.get("classification", "")
            }
            for match in results.matches
        ]
    
    def _classification_filter(self, ceiling: str) -> dict:
        allowed = {
            "public": ["public"],
            "internal": ["public", "internal"],
            "confidential": ["public", "internal", "confidential"],
            "restricted": ["public", "internal", "confidential", "restricted"]
        }
        return {"classification": {"$in": allowed.get(ceiling, ["public"])}}

Audit Logging for Vector Queries

Access control without audit logging is incomplete. In regulated environments — HIPAA, SOC 2, FedRAMP — you must be able to answer: who queried what, when, and what did they receive? For vector databases this is non-trivial because the query is a floating-point vector and the result is a ranked list, neither of which is easily stored in a traditional audit log.

A practical audit schema stores the semantic query (the text before embedding), the resolved tenant and access context, and enough result metadata to reconstruct what was exposed without storing the full document contents:

-- PostgreSQL audit log table
CREATE TABLE vector_query_audit (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    occurred_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    tenant_id       TEXT NOT NULL,
    user_id         TEXT NOT NULL,
    query_text      TEXT,               -- the original natural language query
    query_hash      TEXT,               -- SHA-256 of the embedding for deduplication
    top_k           INTEGER,
    namespace       TEXT,
    classification_ceiling  TEXT,
    result_count    INTEGER,
    result_ids      TEXT[],             -- IDs of returned documents
    result_scores   FLOAT[],            -- similarity scores
    request_ip      INET,
    user_agent      TEXT,
    duration_ms     INTEGER
);

-- Index for compliance queries
CREATE INDEX ON vector_query_audit (tenant_id, occurred_at DESC);
CREATE INDEX ON vector_query_audit (user_id, occurred_at DESC);

-- Retention policy: audit rows are append-only
-- Use pg_partman or a cron job to archive/drop old partitions
ALTER TABLE vector_query_audit ENABLE ROW LEVEL SECURITY;

-- Only audit readers (compliance role) and service accounts can read audit rows
CREATE POLICY audit_read ON vector_query_audit
    FOR SELECT
    TO compliance_role, service_role
    USING (true);

-- Application role can only insert, never update or delete
CREATE POLICY audit_insert ON vector_query_audit
    FOR INSERT
    TO app_role
    WITH CHECK (true);
# Python
# Audit logging wrapper around vector search
import hashlib
import time
import psycopg2
from contextlib import contextmanager

class AuditedVectorSearch:
    def __init__(self, vector_client, audit_db_conn_string: str):
        self.vector_client = vector_client
        self.audit_conn_string = audit_db_conn_string
    
    def search(
        self,
        tenant_id: str,
        user_id: str,
        query_text: str,
        query_vector: list[float],
        namespace: str,
        classification_ceiling: str,
        top_k: int = 10,
        request_ip: str = None,
        user_agent: str = None
    ) -> list[dict]:
        start = time.monotonic()
        
        # Compute query fingerprint for deduplication analysis
        query_hash = hashlib.sha256(
            bytes(str(query_vector), "utf-8")
        ).hexdigest()
        
        # Execute vector search
        results = self.vector_client.execute_query(
            access=VectorAccess(
                tenant_namespace=tenant_id,
                permitted_operations=[VectorOperation.READ],
                classification_ceiling=classification_ceiling
            ),
            query_vector=query_vector,
            top_k=top_k
        )
        
        duration_ms = int((time.monotonic() - start) * 1000)
        
        # Write audit record — this happens regardless of result content
        self._write_audit(
            tenant_id=tenant_id,
            user_id=user_id,
            query_text=query_text,
            query_hash=query_hash,
            top_k=top_k,
            namespace=namespace,
            classification_ceiling=classification_ceiling,
            result_count=len(results),
            result_ids=[r["id"] for r in results],
            result_scores=[r["score"] for r in results],
            request_ip=request_ip,
            user_agent=user_agent,
            duration_ms=duration_ms
        )
        
        return results
    
    def _write_audit(self, **kwargs) -> None:
        with psycopg2.connect(self.audit_conn_string) as conn:
            with conn.cursor() as cur:
                cur.execute("""
                    INSERT INTO vector_query_audit (
                        tenant_id, user_id, query_text, query_hash,
                        top_k, namespace, classification_ceiling,
                        result_count, result_ids, result_scores,
                        request_ip, user_agent, duration_ms
                    ) VALUES (
                        %(tenant_id)s, %(user_id)s, %(query_text)s, %(query_hash)s,
                        %(top_k)s, %(namespace)s, %(classification_ceiling)s,
                        %(result_count)s, %(result_ids)s, %(result_scores)s,
                        %(request_ip)s, %(user_agent)s, %(duration_ms)s
                    )
                """, kwargs)
            conn.commit()

One important design decision: whether to log the query_text (the natural language query before embedding) depends on your data classification policy. In some environments, the query itself — "show me documents about patient discharge against medical advice" — is as sensitive as the returned content. In those cases, log only the hash, and ensure the hash-to-text mapping is stored in a separate, higher-classification system accessible only to the compliance team.

Handling Sensitive Data in Embedding Pipelines

Access control at the vector database level is the last line of defense. The embedding pipeline — where raw text is converted to vectors — is an earlier and often overlooked attack surface. If your pipeline sends data to a third-party embedding API (OpenAI, Cohere, Google), that data leaves your security boundary.

The mitigations depend on your threat model:

Private embedding models eliminate the third-party exposure entirely. Running an open-source model like all-MiniLM-L6-v2 from sentence-transformers on infrastructure you control means the raw text never leaves your network. The embedding quality may differ from frontier models, but for most enterprise retrieval tasks the gap is acceptable.

# Python
# On-premises embedding with sentence-transformers
from sentence_transformers import SentenceTransformer
import torch

class PrivateEmbedder:
    """
    Embed text using a locally-hosted model.
    No data leaves the network boundary.
    """
    def __init__(self, model_name: str = "all-MiniLM-L6-v2"):
        device = "cuda" if torch.cuda.is_available() else "cpu"
        self.model = SentenceTransformer(model_name, device=device)
        self.dimension = self.model.get_sentence_embedding_dimension()
    
    def embed(self, texts: list[str]) -> list[list[float]]:
        embeddings = self.model.encode(
            texts,
            batch_size=64,
            normalize_embeddings=True,  # unit vectors for cosine similarity
            show_progress_bar=False
        )
        return embeddings.tolist()
    
    def embed_one(self, text: str) -> list[float]:
        return self.embed([text])[0]

embedder = PrivateEmbedder()

Data masking before embedding applies when you must use a third-party API but some fields in your documents are sensitive PII or proprietary content. Before sending text to the embedding API, strip or replace the sensitive spans with placeholder tokens:

# Python
import re

class DataMaskingPreprocessor:
    """
    Remove or replace sensitive patterns before embedding.
    Masking is irreversible — the stored vector reflects the masked text,
    so exact-match retrieval on original PII is not possible.
    Use this only when semantic retrieval on non-PII context is sufficient.
    """
    
    PATTERNS = {
        "ssn": (r"\b\d{3}-\d{2}-\d{4}\b", "[SSN]"),
        "credit_card": (r"\b(?:\d{4}[- ]?){3}\d{4}\b", "[CARD]"),
        "email": (r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b", "[EMAIL]"),
        "phone": (r"\b(?:\+1[-.\s]?)?\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}\b", "[PHONE]"),
    }
    
    def mask(self, text: str) -> tuple[str, dict]:
        """
        Returns masked text and a record of replacements.
        The replacement record should be stored in your secure vault,
        not alongside the vector.
        """
        replacements = {}
        masked = text
        
        for pattern_name, (pattern, placeholder) in self.PATTERNS.items():
            matches = re.findall(pattern, masked)
            if matches:
                replacements[pattern_name] = matches
                masked = re.sub(pattern, placeholder, masked)
        
        return masked, replacements

preprocessor = DataMaskingPreprocessor()
masked_text, pii_record = preprocessor.mask(
    "Contact John at john.doe@acme.com or 555-123-4567 about invoice #A-4492"
)
# masked_text: "Contact John at [EMAIL] or [PHONE] about invoice #A-4492"
# pii_record stored separately in your secrets vault

VPC endpoints and private links are the network-level complement to data masking. AWS PrivateLink for Bedrock, Azure Private Endpoints for Azure OpenAI, and GCP Private Service Connect for Vertex AI all allow your embedding calls to traverse private network paths rather than the public internet, reducing the exposure surface even when using managed embedding APIs.

A Unified Authorization Layer

Production systems rarely use a single vector database. A typical architecture might use pgvector for low-latency operational queries, Pinecone for high-scale semantic search, and Weaviate for knowledge graph traversal with vector similarity. Each database has its own access control model. Building authorization logic independently for each creates inconsistency and maintenance burden.

A unified authorization layer abstracts the vector database behind a policy engine that speaks a single language regardless of the underlying store:

# Python
from abc import ABC, abstractmethod
from typing import Protocol
import opa_client  # Open Policy Agent Python client

class VectorSearchBackend(Protocol):
    def search(
        self, 
        collection: str, 
        vector: list[float], 
        filter_: dict,
        top_k: int
    ) -> list[dict]: ...

class PineconeBackend:
    def __init__(self, api_key: str, index_name: str):
        self.pc = Pinecone(api_key=api_key)
        self.index = self.pc.Index(index_name)
    
    def search(self, collection: str, vector: list[float], filter_: dict, top_k: int) -> list[dict]:
        results = self.index.query(
            vector=vector,
            top_k=top_k,
            namespace=collection,
            filter=filter_,
            include_metadata=True
        )
        return [{"id": m.id, "score": m.score, **m.metadata} for m in results.matches]

class QdrantBackend:
    def __init__(self, url: str, api_key: str):
        self.client = QdrantClient(url=url, api_key=api_key)
    
    def search(self, collection: str, vector: list[float], filter_: dict, top_k: int) -> list[dict]:
        # Convert unified filter dict to Qdrant filter model
        qdrant_filter = self._translate_filter(filter_)
        results = self.client.search(
            collection_name=collection,
            query_vector=vector,
            query_filter=qdrant_filter,
            limit=top_k,
            with_payload=True
        )
        return [{"id": str(r.id), "score": r.score, **(r.payload or {})} for r in results]
    
    def _translate_filter(self, filter_dict: dict) -> Filter | None:
        if not filter_dict:
            return None
        conditions = []
        for key, value in filter_dict.items():
            if isinstance(value, list):
                conditions.append(FieldCondition(key=key, match=MatchAny(any=value)))
            else:
                conditions.append(FieldCondition(key=key, match=MatchValue(value=value)))
        return Filter(must=conditions)


class UnifiedVectorAuthority:
    """
    Single entry point for all vector search operations.
    Policy decisions are delegated to Open Policy Agent.
    Backend selection is driven by routing configuration.
    """
    
    def __init__(self, opa_url: str, backends: dict[str, VectorSearchBackend]):
        self.opa = opa_client.OpaClient(opa_url)
        self.backends = backends  # e.g., {"pinecone": PineconeBackend(...), "qdrant": QdrantBackend(...)}
    
    def _evaluate_policy(self, identity: dict, resource: dict, action: str) -> dict:
        """
        Query OPA for access decision.
        Returns {"allow": bool, "filter": dict, "redact_fields": list[str]}
        """
        input_data = {
            "identity": identity,
            "resource": resource,
            "action": action
        }
        result = self.opa.check_policy_rule(
            policy_name="vector/authz",
            rule_name="decision",
            input_data=input_data
        )
        return result.get("result", {"allow": False, "filter": {}, "redact_fields": []})
    
    def search(
        self,
        identity: dict,          # {tenant_id, user_id, roles, clearance_level}
        backend_name: str,       # "pinecone" | "qdrant" | "pgvector"
        collection: str,
        query_vector: list[float],
        top_k: int = 10
    ) -> list[dict]:
        # Step 1: Policy evaluation
        decision = self._evaluate_policy(
            identity=identity,
            resource={"backend": backend_name, "collection": collection},
            action="vector:search"
        )
        
        if not decision["allow"]:
            raise PermissionError(
                f"User {identity['user_id']} is not permitted to search {collection}"
            )
        
        # Step 2: Backend selection and query execution
        backend = self.backends.get(backend_name)
        if not backend:
            raise ValueError(f"Unknown backend: {backend_name}")
        
        # filter_ comes from OPA policy, never from caller
        results = backend.search(
            collection=collection,
            vector=query_vector,
            filter_=decision.get("filter", {}),
            top_k=top_k
        )
        
        # Step 3: Field-level redaction based on policy output
        redact_fields = decision.get("redact_fields", [])
        if redact_fields:
            results = [
                {k: ("[REDACTED]" if k in redact_fields else v) for k, v in r.items()}
                for r in results
            ]
        
        return results

This architecture provides a clean separation of concerns: the vector database handles geometry, the policy engine handles authorization, and the application handles business logic. Rotating a credential, tightening a classification rule, or adding a new backend requires changes in exactly one place.

Key Takeaways

  • → **Vector access control requires layered defenses.** Namespace or collection isolation prevents cross-tenant data access at the storage level; metadata filters enforce within-tenant classification controls; application-layer verification catches filter bypass scenarios. No single layer is sufficient on its own.
  • → **PostgreSQL RLS integrates directly with pgvector**, but ANN index performance degrades when RLS predicates are applied post-scan. Partition by tenant to ensure the query planner prunes to a single partition before scanning the vector index.
  • → **Managed vector databases (Pinecone, Weaviate, Qdrant) have different isolation guarantees.** Weaviate's multi-tenancy model is fail-closed — queries without a tenant key raise an error. Pinecone's namespace model is fail-open — omitting the namespace silently queries the default namespace. Design your application wrapper to enforce namespace injection server-side from a verified identity token, never from client-supplied input.
  • → **API keys should follow least-privilege principles.** Store keys in a secrets manager, scope them to the minimum required operations, and retrieve them at runtime through an authorization proxy rather than distributing them to calling services or clients directly.
  • → **Audit logs for vector queries must capture the semantic intent, not just the raw vector.** Log the natural language query text (or its hash if the query itself is sensitive), the resolved access context, the result document IDs, and the similarity scores. This record supports compliance investigations, anomaly detection on unusual query patterns, and incident response when a potential data exposure needs to be scoped.
