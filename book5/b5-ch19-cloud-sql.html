Chapter 19: Cloud SQL: PostgreSQL and SQL Server on GCP

Google Cloud SQL is the workhorse managed database service on GCP — not the most glamorous product in Google's portfolio, but the one that most production teams actually run day-to-day. This chapter covers two of its three supported engines: PostgreSQL and SQL Server. If you've spent years tuning postgresql.conf, managing WAL archiving, and nursing SQL Server AlwaysOn through network partitions, Cloud SQL will feel both familiar and occasionally frustrating. Google handles the infrastructure, but the tradeoffs are real: you gain automated patching, HA failover, and integrated backups while giving up superuser access, direct OS-level tuning, and certain PostgreSQL extensions you may have relied on. This chapter maps your existing DBA knowledge onto Cloud SQL's architecture, walks through production configuration for both engines, covers HA and replication patterns, and shows you how IAM authentication, Private Service Connect, and Cloud SQL Auth Proxy replace the access-control mechanisms you've used on-premises.

---

19.1 Cloud SQL Architecture: What GCP Manages and What You Still Own

Cloud SQL instances run on managed VMs inside Google's infrastructure. Unlike AWS RDS, which abstracts the underlying VM almost completely from day one, Cloud SQL has historically been more transparent — you can see machine types (shared-core, standard, high-memory), attached SSD storage, and even the regional zone placement directly in the console and API.

What Google manages:

  • → OS patching and kernel updates (maintenance windows apply)
  • → Storage encryption at rest (Google-managed or customer-managed CMEK)
  • → Automated backups and point-in-time recovery (PITR)
  • → High availability via synchronous regional replication
  • → Minor and major version upgrades (in-place for PostgreSQL, with caveats)
  • → The physical failover between primary and standby

    • What you still own:

  • → Database schema and query performance
  • → Flag configuration (the Cloud SQL equivalent of `postgresql.conf` and SQL Server sp_configure)
  • → User management and privilege grants
  • → Connection pooling (Cloud SQL does not include a built-in proxy equivalent to PgBouncer — the Auth Proxy handles TLS tunneling, not pooling)
  • → Logical replication setup for outbound replication to external consumers
  • → Extension management within the allowed extension list

    • The superuser question: On Cloud SQL for PostgreSQL, you never get a true PostgreSQL superuser. The default administrative user (postgres) is a highly privileged user, but certain system-level operations are blocked. You cannot run pg_read_file(), cannot directly manipulate pg_hba.conf, and cannot install arbitrary extensions from source. The allowed extension list is maintained by Google and includes common extensions such as pgvector, pg_stat_statements, postgis, pg_partman, and pglogical — but not plsh, multicorn, or any extension requiring loading of an external .so not included in the base image. Check the current Cloud SQL documentation for the exact list per PostgreSQL version, since it changes over time.

    For SQL Server, Cloud SQL runs SQL Server 2017, 2019, and 2022 across Enterprise, Standard, and Express editions. You get sysadmin-equivalent access via the sqlserver user, but you cannot execute xp_cmdshell (disabled and blocked at the API level), cannot directly manage SQL Server Agent jobs through T-SQL in the traditional sense (the agent is present but surfaced through GCP APIs), and cannot access the underlying file system.

    Instance sizing follows Google Compute Engine machine families:

    | Tier | vCPUs | RAM | Max Storage | Max Connections (PG) |

    |---|---|---|---|---|

    | db-f1-micro | 1 (shared) | 0.6 GB | 3 TB | ~25 |

    | db-n1-standard-4 | 4 | 15 GB | 64 TB | ~500 |

    | db-n1-highmem-8 | 8 | 52 GB | 64 TB | ~1000 |

    | db-custom-16-65536 | 16 | 64 GB | 64 TB | ~2000 |

    | db-custom-96-393216 | 96 | 384 GB | 64 TB | ~12000 |

    The connection limits shown are practical guideline values — Cloud SQL does not hard-cap connections at these numbers by default, but PostgreSQL's max_connections defaults to 100 for db-f1-micro and scales with memory. For anything above 500 connections, you should plan your connection pooling architecture before deployment, not after.

    19.2 Provisioning Cloud SQL Instances: PostgreSQL and SQL Server

    Provisioning with gcloud

    The fastest path to a production-ready Cloud SQL instance uses gcloud sql instances create. Every flag here maps to something you configured manually on-premises.

    # Create a Cloud SQL for PostgreSQL 15 instance
# -- equivalent to provisioning a new PostgreSQL server with WAL archiving,
#    streaming replication standby, and daily base backups preconfigured

gcloud sql instances create prod-pg-01 \
  --database-version=POSTGRES_15 \
  --tier=db-custom-8-32768 \
  --region=us-central1 \
  --availability-type=REGIONAL \
  --storage-type=SSD \
  --storage-size=500GB \
  --storage-auto-increase \
  --backup-start-time=02:00 \
  --enable-bin-log \
  --retained-backups-count=14 \
  --retained-transaction-log-days=7 \
  --maintenance-window-day=SUN \
  --maintenance-window-hour=4 \
  --deletion-protection \
  --no-assign-ip \
  --network=projects/my-project/global/networks/prod-vpc

# Create the default database and application user
gcloud sql databases create appdb --instance=prod-pg-01

gcloud sql users create appuser \
  --instance=prod-pg-01 \
  --password=CHANGE_ME_USE_SECRET_MANAGER

    A few things worth noting here:

  • → `--availability-type=REGIONAL` enables synchronous HA replication to a standby in a second zone within the same region. This is not cross-region. The standby is not readable — it exists only for failover. Cross-region reads require read replicas configured separately.
  • → `--enable-bin-log` on PostgreSQL enables WAL archiving for PITR. Without it, you only get daily backup restoration. For production, this flag is non-negotiable.
  • → `--no-assign-ip` with `--network` places the instance on a private IP in your VPC. Always do this. Public IP Cloud SQL instances exist, but deploying them in production means relying entirely on authorized networks IP allowlisting, which is a fragile access control model.

    • Cloud SQL for SQL Server:

    # Create Cloud SQL for SQL Server 2022 Standard Edition
gcloud sql instances create prod-mssql-01 \
  --database-version=SQLSERVER_2022_STANDARD \
  --tier=db-custom-8-32768 \
  --region=us-east1 \
  --availability-type=REGIONAL \
  --storage-type=SSD \
  --storage-size=1TB \
  --storage-auto-increase \
  --backup-start-time=03:00 \
  --retained-backups-count=14 \
  --maintenance-window-day=SAT \
  --maintenance-window-hour=2 \
  --deletion-protection \
  --no-assign-ip \
  --network=projects/my-project/global/networks/prod-vpc \
  --root-password=CHANGE_ME_USE_SECRET_MANAGER

# Create a database
gcloud sql databases create SalesDB --instance=prod-mssql-01

# Create a SQL login
gcloud sql users create sqladmin \
  --instance=prod-mssql-01 \
  --password=CHANGE_ME_USE_SECRET_MANAGER

    Provisioning with Terraform is the right pattern for production environments where you need reproducible, version-controlled infrastructure:

    # terraform/modules/cloud_sql_postgres/main.tf

resource "google_sql_database_instance" "prod_pg" {
  name             = "prod-pg-01"
  database_version = "POSTGRES_15"
  region           = "us-central1"
  deletion_protection = true

  settings {
    tier              = "db-custom-8-32768"
    availability_type = "REGIONAL"
    disk_type         = "PD_SSD"
    disk_size         = 500
    disk_autoresize   = true

    backup_configuration {
      enabled                        = true
      start_time                     = "02:00"
      point_in_time_recovery_enabled = true
      transaction_log_retention_days = 7
      backup_retention_settings {
        retained_backups = 14
        retention_unit   = "COUNT"
      }
    }

    maintenance_window {
      day          = 7   # Sunday
      hour         = 4
      update_track = "stable"
    }

    ip_configuration {
      ipv4_enabled    = false
      private_network = "projects/${var.project_id}/global/networks/prod-vpc"
    }

    database_flags {
      name  = "max_connections"
      value = "500"
    }

    database_flags {
      name  = "log_min_duration_statement"
      value = "1000"  # Log queries slower than 1 second
    }

    database_flags {
      name  = "pg_stat_statements.track"
      value = "all"
    }

    insights_config {
      query_insights_enabled  = true
      query_string_length     = 4096
      record_application_tags = true
      record_client_address   = true
    }
  }
}

resource "google_sql_database" "appdb" {
  name     = "appdb"
  instance = google_sql_database_instance.prod_pg.name
}

resource "google_sql_user" "appuser" {
  name     = "appuser"
  instance = google_sql_database_instance.prod_pg.name
  password = var.db_password  # Sourced from Secret Manager via data source
}

    The insights_config block enables Query Insights, which is Cloud SQL's integrated slow query analysis tool — think of it as a managed pg_stat_statements dashboard built into the GCP console. It captures query plans, wait events, and client attribution. For PostgreSQL shops accustomed to pg_stat_statements + pgBadger, this is a useful first-line tool, though it doesn't replace dedicated APM for complex workloads.

    19.3 Database Flags: Configuring PostgreSQL and SQL Server Parameters

    What you previously controlled through postgresql.conf and pg_hba.conf (PostgreSQL) or sp_configure and SQL Server Configuration Manager (SQL Server) is surfaced in Cloud SQL as database flags. Most parameters are settable; some are fixed by Google and cannot be changed regardless of your flag configuration.

    Fixed parameters in Cloud SQL for PostgreSQL (you cannot override these):

  • → `wal_level` — fixed at `logical` (actually beneficial for logical replication)
  • → `archive_mode` — managed by Google for PITR
  • → `ssl` — always `on`
  • → `log_destination` — managed by Cloud Logging
  • → `shared_preload_libraries` — you can add to this list from approved extensions, but certain libraries are always present

    • Configurable flags (selected important ones):

    # Apply multiple performance flags to a PostgreSQL instance
# Note: Some flags require instance restart; Cloud SQL will warn you

gcloud sql instances patch prod-pg-01 \
  --database-flags=\
max_connections=500,\
shared_buffers=8192MB,\
work_mem=64MB,\
maintenance_work_mem=2GB,\
effective_cache_size=24576MB,\
checkpoint_completion_target=0.9,\
wal_buffers=64MB,\
random_page_cost=1.1,\
log_min_duration_statement=1000,\
log_checkpoints=on,\
log_connections=on,\
log_lock_waits=on,\
autovacuum_vacuum_scale_factor=0.02,\
autovacuum_analyze_scale_factor=0.01,\
pg_stat_statements.track=all,\
track_io_timing=on

    An important gotcha: Cloud SQL does not let you set shared_buffers directly by name on some tiers — the flag name is shared_buffers and the value must be expressed in kB or MB, not the shorthand notation PostgreSQL accepts directly. Always check the [Cloud SQL flags documentation](https://cloud.google.com/sql/docs/postgres/flags) for your specific database version because accepted value formats differ from what you'd type in postgresql.conf.

    For work_mem: be conservative. work_mem=64MB sounds modest but with 200 concurrent connections each potentially running a sort or hash join, your effective RAM usage for working memory alone is 200 × 64 MB × (number of sort operations per query) = easily 25+ GB on a busy OLTP instance. The number in postgresql.conf is per-sort-node, not per-connection — this is a footgun that causes OOM kills even on generously sized instances.

    SQL Server flags are surfaced similarly but map to sp_configure options:

    # Configure SQL Server instance flags
gcloud sql instances patch prod-mssql-01 \
  --database-flags=\
max\ degree\ of\ parallelism=4,\
cost\ threshold\ for\ parallelism=50,\
optimize\ for\ ad\ hoc\ workloads=on,\
remote\ query\ timeout\ \(s\)=600,\
fill\ factor\ \(\%\)=80

    What you cannot do with SQL Server on Cloud SQL:

  • → `xp_cmdshell` is permanently disabled. There is no workaround.
  • → Linked servers are supported in limited form (to other Cloud SQL instances and Cloud Spanner via a preview connector), but not to arbitrary external servers.
  • → SQL Server Integration Services (SSIS) is not available. For ETL, you're expected to use Dataflow or Cloud Data Fusion.
  • → SQL Server Reporting Services (SSRS) is not available.
  • → SQL Server Analysis Services (SSAS) is not available.
  • → Database mirroring is replaced by the HA standby (which is automatic and not configurable as a traditional mirroring endpoint).

    • If your current SQL Server environment depends heavily on SSIS packages, linked servers to Oracle, or SSRS-based reporting, Cloud SQL is not the right target without significant architectural changes.

    19.4 High Availability, Replication, and Failover

    Regional HA in Cloud SQL works through synchronous replication to a standby instance in a different zone within the same region. This is conceptually similar to PostgreSQL synchronous streaming replication (synchronous_commit = remote_apply) but implemented entirely by Google's infrastructure layer. You don't configure replication slots, recovery.conf, or standby postgresql.conf. When you set --availability-type=REGIONAL, the standby materializes automatically.

    Failover characteristics:

  • → **Automatic failover** triggers when the primary becomes unavailable, typically completing in 60–120 seconds. This is not near-instantaneous like some marketing materials imply.
  • → The standby is in a **different zone** but the **same region**. A full regional outage takes down both primary and standby.
  • → The standby is **not readable**. There is no hot-standby query capability on the HA standby. For read scaling, you need read replicas.
  • → After failover, the old primary becomes the standby. You can initiate a manual failover (called a "switchover" in Cloud SQL) to return the primary to the original zone.
    • graph TD
    App[Application] --> Primary[Primary instance
    zone A]
    Primary -- synchronous replication --> Standby[HA standby
    zone B, not readable]
    Primary -- asynchronous replication --> Replica1[Read replica
    same or cross-region]
    Primary -- asynchronous replication --> Replica2[Read replica
    cascade tier]
    Standby -.promoted on failover.-> Primary

    *Regional HA gives synchronous, non-readable failover protection within one region; read replicas are separate, asynchronously replicated instances used for read scaling and cross-region access.*

    # Initiate a manual failover (useful for DR testing)
gcloud sql instances failover prod-pg-01

# Check replication status
gcloud sql instances describe prod-pg-01 \
  --format="value(settings.availabilityType,failoverReplica)"

    Read replicas are separate Cloud SQL instances that receive asynchronous replication from the primary:

    # Create a read replica in a different region (cross-region replica)
gcloud sql instances create prod-pg-01-replica-us-east \
  --master-instance-name=prod-pg-01 \
  --region=us-east1 \
  --tier=db-custom-4-16384 \
  --availability-type=ZONAL \
  --no-assign-ip \
  --network=projects/my-project/global/networks/prod-vpc

# Promote a replica to a standalone instance (for migrations or DR activation)
gcloud sql instances promote-replica prod-pg-01-replica-us-east

    Cascade replicas (replicas of replicas) are supported in Cloud SQL for PostgreSQL — useful when you want to offload replication traffic from the primary by having multiple tiers of read replicas without every replica pulling directly from the primary.

    Replication lag monitoring should be part of your operational baseline. Cloud SQL surfaces replication lag as a Cloud Monitoring metric:

    # Query replication lag for all replicas using gcloud monitoring
# (More practical to set up an alerting policy via Terraform)
gcloud monitoring metrics list \
  --filter="metric.type=cloudsql.googleapis.com/database/replication/replica_lag"

    In practice, you want an alerting policy that fires when replica_lag exceeds 30 seconds for OLTP replicas used for read traffic, and perhaps 300 seconds for reporting replicas. Lag above 30 seconds on a read replica that's serving application queries means users are reading stale data that may materially affect application behavior.

    External replication — Cloud SQL supports acting as a replica of an external PostgreSQL primary (for live migrations from on-premises) and also supports serving as a primary to external PostgreSQL replicas via logical replication (using pglogical or native logical replication in PostgreSQL 10+). This architecture is commonly used for zero-downtime migrations:

    -- On your on-premises PostgreSQL primary:
-- Enable logical replication (wal_level must be logical)
-- Create a replication publication
CREATE PUBLICATION cloud_migration_pub
  FOR TABLE orders, customers, products, order_items;

-- On Cloud SQL (after setting up as external replica):
-- Cloud SQL handles the subscription setup via the import/replica mechanism,
-- but for pglogical you would configure it as follows after enabling the extension:

CREATE EXTENSION pglogical;

SELECT pglogical.create_node(
  node_name := 'cloud_sql_subscriber',
  dsn := 'host=127.0.0.1 port=5432 dbname=appdb'
);

SELECT pglogical.create_subscription(
  subscription_name := 'onprem_to_cloudsql',
  provider_dsn := 'host=10.0.1.50 port=5432 dbname=appdb 
                   user=replication_user password=REPL_PASS',
  replication_sets := ARRAY['default']
);

    19.5 IAM Authentication and Network Security

    On-premises PostgreSQL access control lives in two places: pg_hba.conf controls who can connect from where and via which authentication method, and pg_ident.conf handles OS user mapping. In Cloud SQL, this model is replaced — and improved in some ways — by IAM integration and Cloud SQL Auth Proxy.

    IAM database authentication lets you authenticate to PostgreSQL or SQL Server using a Google Cloud service account or user identity token instead of a database password. This is meaningful for production because it eliminates the credential rotation problem: IAM tokens are short-lived (1 hour), and service accounts can be centrally managed through IAM policies without touching the database.

    # Grant IAM authentication to a service account for PostgreSQL
# The user format is the service account email address

gcloud sql users create "myapp-sa@my-project.iam.gserviceaccount.com" \
  --instance=prod-pg-01 \
  --type=CLOUD_IAM_SERVICE_ACCOUNT

# Grant IAM authentication to a user account (for human access)
gcloud sql users create "dba@mycompany.com" \
  --instance=prod-pg-01 \
  --type=CLOUD_IAM_USER

# Then grant database-level permissions using standard PostgreSQL GRANT
# Connect as the postgres user first, then:
    -- Grant the IAM service account access to the application database
-- The IAM user appears in PostgreSQL as the email address (service account)
-- or as the user portion before @ for human accounts
GRANT CONNECT ON DATABASE appdb TO "myapp-sa@my-project.iam.gserviceaccount.com";
GRANT USAGE ON SCHEMA public TO "myapp-sa@my-project.iam.gserviceaccount.com";
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public 
  TO "myapp-sa@my-project.iam.gserviceaccount.com";

-- For new tables created in the future:
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES 
  TO "myapp-sa@my-project.iam.gserviceaccount.com";

    Cloud SQL Auth Proxy handles TLS tunnel establishment and IAM-based authentication. Think of it as the operational layer between your application and the database — it intercepts connections, authenticates to Google's APIs, and forwards traffic over an encrypted tunnel. It is not a connection pooler. Applications that open many short-lived connections still need PgBouncer or pgpool-II in front of the Auth Proxy.

    # Download and run Cloud SQL Auth Proxy (Linux/amd64)
curl -o cloud-sql-proxy \
  https://storage.googleapis.com/cloud-sql-connectors/cloud-sql-proxy/v2.7.0/cloud-sql-proxy.linux.amd64
chmod +x cloud-sql-proxy

# Start proxy for a single PostgreSQL instance
# Applications connect to localhost:5432
./cloud-sql-proxy \
  --address 127.0.0.1 \
  --port 5432 \
  my-project:us-central1:prod-pg-01

# For Kubernetes deployments, run Auth Proxy as a sidecar container
# The GKE workload identity binds the pod's service account to the GCP service account
# No credential files needed — identity is automatic

# For multiple instances (useful in multi-tenant architectures)
./cloud-sql-proxy \
  my-project:us-central1:prod-pg-01?port=5432 \
  my-project:us-central1:prod-pg-02?port=5433 \
  my-project:us-east1:prod-pg-01-replica-us-east?port=5434

    Private Service Connect is Google's newer private connectivity mechanism, replacing the older Private IP approach for certain architectures. Where Private IP places the Cloud SQL instance directly on your VPC subnet via a VPC peering arrangement, Private Service Connect creates a private endpoint in your VPC that routes to a Cloud SQL instance without requiring VPC peering or consuming IP ranges from your subnet. This matters at enterprise scale where VPC peering IP range exhaustion becomes a real operational constraint.

    # Create a Private Service Connect endpoint for Cloud SQL
# First, ensure the Cloud SQL instance has PSC enabled (set at creation time
# or via patch if the feature is available for the tier)

gcloud sql instances patch prod-pg-01 \
  --enable-private-service-connect \
  --allowed-psc-projects=my-project,consumer-project-1,consumer-project-2

# Create the Private Service Connect forwarding rule in the consumer VPC
gcloud compute forwarding-rules create cloud-sql-psc-endpoint \
  --region=us-central1 \
  --network=prod-vpc \
  --address=10.100.0.50 \
  --target-service-attachment=\
projects/my-project/regions/us-central1/serviceAttachments/prod-pg-01-psc

    Authorized networks (IP allowlisting) applies only to public IP instances. If you've correctly configured your instance with private IP only, authorized networks are irrelevant. For development instances with public IP, the mechanism is straightforward but operationally brittle for anything beyond a small static set of IPs.

    19.6 Backup, Recovery, and PITR

    Cloud SQL's backup model has two components that work together for full recovery capability: automated backups (full daily snapshots) and transaction log archiving (continuous WAL archiving for PostgreSQL, transaction log backups for SQL Server). Understanding the distinction matters when you're designing your RTO/RPO targets.

    Automated backups are taken once daily during the backup window you configure. They are stored in Google-managed Cloud Storage buckets across two regions automatically — you do not manage this storage directly, and it does not appear in your own GCS bucket unless you explicitly export. Retention is configurable up to 365 backups.

    Point-in-time recovery requires transaction log retention to be enabled (--enable-bin-log on the gcloud create command, or point_in_time_recovery_enabled = true in Terraform). With PITR enabled, you can recover to any second within the retained log window, which you configure from 1 to 7 days. Logs are stored in addition to daily backups; both contribute to your storage bill.

    Recovery operations:

    # List available backups for an instance
gcloud sql backups list --instance=prod-pg-01

# Restore from a specific backup to the same instance
# WARNING: This overwrites the existing instance data
gcloud sql backups restore BACKUP_ID \
  --restore-instance=prod-pg-01

# Restore from a backup to a NEW instance (preferred for production DR testing)
gcloud sql backups restore BACKUP_ID \
  --restore-instance=prod-pg-01-restored \
  --backup-instance=prod-pg-01

# Point-in-time recovery: restore to a specific timestamp
# The target time must fall within the transaction log retention window
gcloud sql instances clone prod-pg-01 prod-pg-01-pitr \
  --point-in-time=2024-10-15T14:30:00.000Z

# For SQL Server: same mechanism, different timestamp format is accepted
gcloud sql instances clone prod-mssql-01 prod-mssql-01-pitr \
  --point-in-time=2024-10-15T14:30:00.000Z

    The clone command with --point-in-time is the practical approach for PITR in Cloud SQL. It creates a new instance restored to the target time without touching the original. This is valuable: you can validate the recovery, run queries against the cloned instance to confirm data integrity, and then either promote the clone or discard it. This is operationally cleaner than the on-premises pattern of restoring to the same server and hoping you got the recovery target right.

    On-demand backups are useful before risky schema changes or data migrations:

    # Trigger an on-demand backup
gcloud sql backups create --instance=prod-pg-01 \
  --description="Pre-migration backup before schema change 2024-10-15"

# Export to Cloud Storage (for long-term retention beyond the 365-backup limit,
# or for cross-project/cross-region portability)
gcloud sql export sql prod-pg-01 \
  gs://my-backups-bucket/exports/prod-pg-01-$(date +%Y%m%d).sql \
  --database=appdb \
  --offload  # Runs export from a serverless offload process, not on the instance

# For SQL Server: export as BAK file to GCS
gcloud sql export bak prod-mssql-01 \
  gs://my-backups-bucket/exports/SalesDB-$(date +%Y%m%d).bak \
  --database=SalesDB \
  --bak-type=FULL

    The --offload flag for PostgreSQL SQL exports is worth emphasizing. Without it, the export process consumes CPU and I/O on the primary instance directly. With --offload, Google runs the export using a serverless process that reads from a snapshot, relieving production load. Always use --offload for large databases.

    Import operations follow the reverse path:

    # Import a SQL dump into a Cloud SQL PostgreSQL instance
# The GCS bucket must be accessible by the Cloud SQL service account
gcloud sql import sql prod-pg-01 \
  gs://my-backups-bucket/imports/dump.sql \
  --database=appdb

# Import a SQL Server BAK file
gcloud sql import bak prod-mssql-01 \
  gs://my-backups-bucket/imports/SalesDB.bak \
  --database=SalesDB \
  --bak-type=FULL

    Recovery testing cadence: Backups that are never tested are a liability. Automate a monthly or quarterly recovery test using Cloud Scheduler + Cloud Functions or a simple Cloud Run job that triggers a PITR clone, runs a validation query set (row counts, critical business logic checks), and then deletes the clone. This pattern takes the human out of the loop and gives you documented evidence that your recovery capability actually works.

    # Example: automated PITR test script (called from Cloud Scheduler)
#!/bin/bash
set -euo pipefail

INSTANCE="prod-pg-01"
TEST_INSTANCE="prod-pg-01-pitr-test"
PROJECT="my-project"
# Restore to 4 hours ago
RECOVERY_TIME=$(date -u -d '4 hours ago' +%Y-%m-%dT%H:%M:%S.000Z)

echo "Starting PITR test: restoring ${INSTANCE} to ${RECOVERY_TIME}"

gcloud sql instances clone "${INSTANCE}" "${TEST_INSTANCE}" \
  --point-in-time="${RECOVERY_TIME}" \
  --project="${PROJECT}"

# Wait for the clone to become RUNNABLE
for i in {1..30}; do
  STATUS=$(gcloud sql instances describe "${TEST_INSTANCE}" \
    --format="value(state)" --project="${PROJECT}")
  if [[ "${STATUS}" == "RUNNABLE" ]]; then
    echo "Clone is RUNNABLE"
    break
  fi
  echo "Waiting for clone... status=${STATUS}"
  sleep 30
done

# Run validation queries via Cloud SQL Auth Proxy
./cloud-sql-proxy "${PROJECT}:us-central1:${TEST_INSTANCE}" \
  --port=5433 &
PROXY_PID=$!
sleep 5

PGPASSWORD="${DB_PASSWORD}" psql \
  -h 127.0.0.1 -p 5433 -U postgres -d appdb \
  -c "SELECT COUNT(*) FROM orders; SELECT MAX(created_at) FROM orders;"

VALIDATION_RESULT=$?
kill "${PROXY_PID}"

# Cleanup regardless of validation result
gcloud sql instances delete "${TEST_INSTANCE}" \
  --quiet --project="${PROJECT}"

if [[ "${VALIDATION_RESULT}" -ne 0 ]]; then
  echo "PITR validation FAILED"
  exit 1
fi

echo "PITR test PASSED"

    19.7 Performance Tuning: PostgreSQL on Cloud SQL

    Performance tuning Cloud SQL for PostgreSQL follows the same fundamentals as tuning any PostgreSQL instance — the query planner, index structures, VACUUM behavior, and statistics collection are identical to community PostgreSQL. What changes is where you intervene and what visibility you have.

    Query Insights is your first stop. Accessible in the GCP console under Cloud SQL → Instance → Query Insights, it surfaces:

  • → Top queries by total execution time, mean latency, and call count
  • → Query plans with execution time breakdowns
  • → Wait event analysis (lock waits, I/O waits, client wait)
  • → Application tag attribution (requires `pg_stat_statements` and application-level tagging via the `application_name` connection parameter)

    • For deeper investigation, connect directly and query pg_stat_statements:

    -- Top 20 queries by total time in PostgreSQL on Cloud SQL
-- (pg_stat_statements must be enabled as a flag)
SELECT
  LEFT(query, 120)                                    AS query_snippet,
  calls,
  ROUND(total_exec_time::numeric, 2)                  AS total_ms,
  ROUND(mean_exec_time::numeric, 2)                   AS mean_ms,
  ROUND(stddev_exec_time::numeric, 2)                 AS stddev_ms,
  ROUND((100 * total_exec_time /
    SUM(total_exec_time) OVER ())::numeric, 2)        AS pct_total,
  rows
FROM pg_stat_statements
WHERE query NOT ILIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC
LIMIT 20;

-- Identify queries with high variance (unstable execution plans)
SELECT
  LEFT(query, 120)                                    AS query_snippet,
  calls,
  ROUND(mean_exec_time::numeric, 2)                   AS mean_ms,
  ROUND(stddev_exec_time::numeric, 2)                 AS stddev_ms,
  ROUND((stddev_exec_time / NULLIF(mean_exec_time,0))::numeric, 4) AS cv
FROM pg_stat_statements
WHERE calls > 100
  AND mean_exec_time > 100
ORDER BY cv DESC
LIMIT 20;

    Index bloat and table bloat are tuning concerns that exist in Cloud SQL exactly as they do in self-managed PostgreSQL. AUTOVACUUM runs by default and can be tuned via flags, but you have the same visibility into its behavior:

    -- Check autovacuum activity
SELECT
  schemaname,
  tablename,
  last_vacuum,
  last_autovacuum,
  last_analyze,
  last_autoanalyze,
  n_live_tup,
  n_dead_tup,
  ROUND(n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;

-- Estimate table bloat (approximate)
SELECT
  schemaname,
  tablename,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
  pg_size_pretty(pg_relation_size(schemaname||'.'||tablename))       AS table_size,
  pg_size_pretty(
    pg_total_relation_size(schemaname||'.'||tablename)
    - pg_relation_size(schemaname||'.'||tablename)
  )                                                                   AS index_size
FROM pg_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC
LIMIT 20;

    Connection pooling architecture is an operational prerequisite for PostgreSQL on Cloud SQL at scale. Cloud SQL does not include PgBouncer. Your options:

    1. PgBouncer on GKE or a GCE VM in the same VPC, fronting Cloud SQL via private IP. This is the most common pattern and gives you full PgBouncer configuration control.

    2. Cloud SQL Auth Proxy + PgBouncer: Deploy Auth Proxy on the same host as PgBouncer. Auth Proxy handles TLS and IAM auth; PgBouncer handles connection multiplexing. Applications connect to PgBouncer; PgBouncer connects to Auth Proxy.

    3. AlloyDB instead of Cloud SQL: Google's AlloyDB for PostgreSQL includes a built-in connection pooler. If connection pooling complexity is a significant operational burden, AlloyDB is worth evaluating for large PostgreSQL workloads (though it costs more than Cloud SQL).

    A minimal PgBouncer configuration for Cloud SQL:

    # pgbouncer.ini for Cloud SQL PostgreSQL
[databases]
appdb = host=10.100.0.10 port=5432 dbname=appdb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 20
min_pool_size = 5
reserve_pool_size = 5
reserve_pool_timeout = 3
server_idle_timeout = 600
client_idle_timeout = 0
log_connections = 0
log_disconnections = 0
log_pooler_errors = 1
stats_period = 60

# TLS to Cloud SQL
server_tls_sslmode = require

    pool_mode = transaction is the correct mode for most OLTP applications on Cloud SQL — it multiplexes connections efficiently because it releases the server connection back to the pool after each transaction, not after each session. The tradeoff is that session-level state (SET, temporary tables, advisory locks) does not persist across transactions. Applications that depend on session-level PostgreSQL state must use pool_mode = session instead.

    Parallel query in PostgreSQL on Cloud SQL works the same way as in self-managed PostgreSQL, governed by max_parallel_workers_per_gather and max_parallel_workers. For OLTP workloads, you often want to reduce or disable parallel query to prevent a single analytical query from consuming all available worker processes:

    -- Disable parallelism for a specific query (OLTP sessions)
SET max_parallel_workers_per_gather = 0;

-- Check current parallel query settings
SELECT name, setting, unit, category
FROM pg_settings
WHERE name LIKE '%parallel%'
ORDER BY name;

    19.8 Performance Tuning: SQL Server on Cloud SQL

    SQL Server tuning on Cloud SQL follows standard SQL Server DBA practice for the most part. The query optimizer, statistics management, index maintenance, and wait statistics analysis are identical to on-premises SQL Server. The constraints are around what you can configure and what diagnostic tools you can reach.

    Wait statistics are your primary diagnostic entry point:

    -- Top wait types on SQL Server Cloud SQL instance
-- Identical to on-premises SQL Server DMV usage
SELECT TOP 20
  wait_type,
  waiting_tasks_count,
  wait_time_ms,
  max_wait_time_ms,
  signal_wait_time_ms,
  wait_time_ms - signal_wait_time_ms     AS resource_wait_time_ms,
  CAST(100.0 * wait_time_ms
    / SUM(wait_time_ms) OVER ()
    AS DECIMAL(5,2))                     AS pct_total
FROM sys.dm_os_wait_stats
WHERE wait_type NOT IN (
  -- Filter out benign background waits
  'SLEEP_TASK', 'BROKER_TO_FLUSH', 'BROKER_EVENTHANDLER',
  'CHECKPOINT_QUEUE', 'DBMIRROR_EVENTS_QUEUE', 'SQLTRACE_BUFFER_FLUSH',
  'CLR_AUTO_EVENT', 'DISPATCHER_QUEUE_SEMAPHORE', 'XE_TIMER_EVENT',
  'WAIT_XTP_OFFLINE_CKPT_NEW_LOG', 'LAZYWRITER_SLEEP', 'LOGMGR_QUEUE',
  'ONDEMAND_TASK_QUEUE', 'REQUEST_FOR_DEADLOCK_SEARCH', 'RESOURCE_QUEUE',
  'SERVER_IDLE_CHECK', 'SLEEP_DBSTARTUP', 'SLEEP_DBRECOVER',
  'SLEEP_MASTERDBREADY', 'SLEEP_MASTERMDREADY', 'SLEEP_MASTERUPGRADED',
  'SLEEP_MSDBSTARTUP', 'SLEEP_SYSTEMTASK', 'SLEEP_TEMPDBSTARTUP',
  'SNI_HTTP_ACCEPT', 'SP_SERVER_DIAGNOSTICS_SLEEP', 'SQLTRACE_INCREMENTAL_FLUSH_SLEEP',
  'WAITFOR', 'XE_DISPATCHER_WAIT', 'XE_DISPATCHER_JOIN'
)
ORDER BY wait_time_ms DESC;

-- Query store: top queries by total CPU (SQL Server 2017+)
-- Query Store is enabled by default on Cloud SQL for SQL Server
SELECT TOP 20
  qs.query_id,
  LEFT(qt.query_sql_text, 150)           AS query_snippet,
  SUM(rs.count_executions)               AS total_executions,
  SUM(rs.avg_cpu_time * rs.count_executions) / 1000.0  AS total_cpu_ms,
  AVG(rs.avg_cpu_time) / 1000.0          AS avg_cpu_ms,
  AVG(rs.avg_duration) / 1000.0          AS avg_duration_ms,
  AVG(rs.avg_logical_io_reads)           AS avg_logical_reads
FROM sys.query_store_query           qs
JOIN sys.query_store_query_text      qt ON qt.query_text_id = qs.query_text_id
JOIN sys.query_store_plan            qp ON qp.query_id      = qs.query_id
JOIN sys.query_store_runtime_stats   rs ON rs.plan_id        = qp.plan_id
GROUP BY qs.query_id, qt.query_sql_text
ORDER BY total_cpu_ms DESC;

    Index maintenance follows the same rebuild/reorganize pattern but you must run it through T-SQL rather than SQL Server Agent GUI (since the Agent is surfaced through GCP APIs rather than directly). A standard index maintenance script works without modification:

    -- Index maintenance script for Cloud SQL SQL Server
-- Reorganize fragmented indexes, rebuild heavily fragmented ones
DECLARE @SchemaName  NVARCHAR(128),
        @TableName   NVARCHAR(128),
        @IndexName   NVARCHAR(128),
        @Fragmentation FLOAT,
        @SQL         NVARCHAR(MAX);

DECLARE index_cursor CURSOR FOR
SELECT
  s.name,
  t.name,
  i.name,
  ps.avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(
       DB_ID(), NULL, NULL, NULL, 'LIMITED') ps
JOIN sys.indexes     i ON i.object_id = ps.object_id
                       AND i.index_id  = ps.index_id
JOIN sys.tables      t ON t.object_id = i.object_id
JOIN sys.schemas     s ON s.schema_id = t.schema_id
WHERE ps.avg_fragmentation_in_percent > 10
  AND ps.page_count > 1000
  AND i.name IS NOT NULL
ORDER BY ps.avg_fragmentation_in_percent DESC;

OPEN index_cursor;
FETCH NEXT FROM index_cursor
  INTO @SchemaName, @TableName, @IndexName, @Fragmentation;

WHILE @@FETCH_STATUS = 0
BEGIN
  IF @Fragmentation > 30
    SET @SQL = N'ALTER INDEX ' + QUOTENAME(@IndexName)
             + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName)
             + N' REBUILD WITH (ONLINE = ON, FILLFACTOR = 80);';
  ELSE
    SET @SQL = N'ALTER INDEX ' + QUOTENAME(@IndexName)
             + N' ON ' + QUOTENAME(@SchemaName) + N'.' + QUOTENAME(@TableName)
             + N' REORGANIZE;';

  EXEC sp_executesql @SQL;

  FETCH NEXT FROM index_cursor
    INTO @SchemaName, @TableName, @IndexName, @Fragmentation;
END;

CLOSE index_cursor;
DEALLOCATE index_cursor;

    Statistics update should follow index maintenance:

    -- Update all statistics in the current database after index maintenance
EXEC sp_updatestats;

-- Or update specific table statistics with full scan
UPDATE STATISTICS dbo.Orders WITH FULLSCAN;

    TempDB configuration on Cloud SQL for SQL Server: unlike on-premises SQL Server where DBA best practice is to create multiple TempDB data files equal to the number of logical processor cores (up to 8), Cloud SQL manages TempDB file configuration internally. You cannot directly alter the number of TempDB files. If you observe heavy PAGELATCH contention on TempDB allocation pages (indicated by PAGELATCH_EX or PAGELATCH_SH waits on page types 2:1:1, 2:1:2, 2:1:3), this is a constraint of the managed service rather than something you can resolve through normal TempDB tuning.

    Memory-optimized tables (In-Memory OLTP) are not available in Cloud SQL for SQL Server. If your workload depends on in-memory OLTP objects (SCHEMA_AND_DATA memory-optimized tables, natively compiled stored procedures), Cloud SQL is not a compatible migration target without significant application rework.

    19.9 Monitoring, Alerting, and Operational Visibility

    Cloud SQL integrates with Cloud Monitoring (formerly Stackdriver) for metrics, Cloud Logging for database logs, and Query Insights for query-level analysis. As a DBA migrating from on-premises, you're replacing your existing monitoring stack (Nagios, Zabbix, DataDog, custom Grafana dashboards against pg_stat_* views) with a combination of GCP-native tools and whatever you choose to layer on top.

    Key Cloud Monitoring metrics for Cloud SQL:

    | Metric | Type | Alert Threshold (example) |

    |---|---|---|

    | cloudsql.googleapis.com/database/cpu/utilization | Gauge | > 0.80 for 5 min |

    | cloudsql.googleapis.com/database/memory/utilization | Gauge | > 0.90 for 5 min |

    | cloudsql.googleapis.com/database/disk/utilization | Gauge | > 0.85 |

    | cloudsql.googleapis.com/database/disk/write_ops_count | Delta | Baseline + 3σ |

    | cloudsql.googleapis.com/database/replication/replica_lag | Gauge | > 30s for read replicas |

    | cloudsql.googleapis.com/database/postgresql/num_backends | Gauge | > 80% of max_connections |

    | cloudsql.googleapis.com/database/postgresql/deadlock_count | Delta | > 0 (any deadlock) |

    | cloudsql.googleapis.com/database/postgresql/transaction_count | Delta | Baseline deviation |

    | cloudsql.googleapis.com/database/sqlserver/connections/count | Gauge | > 80% of max |

    Terraform-managed alerting policy for PostgreSQL connection saturation:

    # terraform/monitoring/cloud_sql_alerts.tf

resource "google_monitoring_alert_policy" "pg_connection_saturation" {
  display_name = "Cloud SQL PostgreSQL - Connection Saturation"
  combiner     = "OR"

  conditions {
    display_name = "PostgreSQL connections > 80% of max_connections"

    condition_threshold {
      filter = <<-EOT
        resource.type = "cloudsql_database"
        AND resource.labels.database_id = "my-project:prod-pg-01"
        AND metric.type = "cloudsql.googleapis.com/database/postgresql/num_backends"
      EOT

      comparison      = "COMPARISON_GT"
      threshold_value = 400   # 80% of max_connections=500
      duration        = "300s"

      aggregations {
        alignment_period   = "60s"
        per_series_aligner = "ALIGN_MEAN"
      }
    }
  }

  notification_channels = [var.pagerduty_channel_id]

  alert_strategy {
    auto_close = "1800s"
  }
}

resource "google_monitoring_alert_policy" "pg_replication_lag" {
  display_name = "Cloud SQL PostgreSQL - Replica Lag Excessive"
  combiner     = "OR"

  conditions {
    display_name = "Replication lag > 30 seconds"

    condition_threshold {
      filter = <<-EOT
        resource.type = "cloudsql_database"
        AND metric.type = "cloudsql.googleapis.com/database/replication/replica_lag"
      EOT

      comparison      = "COMPARISON_GT"
      threshold_value = 30
      duration        = "120s"

      aggregations {
        alignment_period   = "60s"

      }

    Cloud Logging captures PostgreSQL log output routed through Cloud Logging's structured logging pipeline. The database flags log_min_duration_statement, log_connections, log_disconnections, log_lock_waits, and log_checkpoints all write to Cloud Logging when enabled. Query these logs with Log Explorer using structured filter syntax:

    # Log Explorer filter: slow queries from Cloud SQL PostgreSQL
resource.type="cloudsql_database"
resource.labels.database_id="my-project:prod-pg-01"
textPayload=~"duration: [0-9]+ ms"
severity>=DEFAULT

# Filter for lock wait events
resource.type="cloudsql_database"
textPayload=~"process [0-9]+ acquired"

    For production observability, consider exporting Cloud Logging to BigQuery for long-term retention and ad-hoc analysis of historical query patterns:

    # Log sink to BigQuery for Cloud SQL logs
resource "google_logging_project_sink" "cloud_sql_to_bq" {
  name        = "cloud-sql-logs-to-bigquery"
  destination = "bigquery.googleapis.com/projects/my-project/datasets/cloud_sql_logs"

  filter = <<-EOT
    resource.type="cloudsql_database"
    AND (
      textPayload=~"duration:"
      OR textPayload=~"deadlock"
      OR textPayload=~"checkpoint"
      OR textPayload=~"lock wait"
    )
  EOT

  unique_writer_identity = true
}

    Custom dashboards via Grafana are a common complement to the GCP console for teams that want unified visibility across Cloud SQL and other infrastructure. The Cloud Monitoring data source plugin for Grafana connects directly to the Cloud Monitoring API using a service account, pulling the same metrics surfaced in the GCP console into your existing Grafana environment. No Cloud SQL-specific agent or exporter is needed.

    19.10 Migrations to Cloud SQL: Practical Patterns

    Most production migrations to Cloud SQL come from one of three sources: on-premises PostgreSQL or SQL Server, another cloud provider's managed database service, or a self-managed database on GCE. The migration approach depends on your acceptable downtime window and database size.

    Database Migration Service (DMS) is Google's managed migration tool for Cloud SQL. It supports continuous replication migrations (minimal downtime) and one-time migrations. For PostgreSQL, DMS uses logical replication under the hood. For SQL Server, it uses backup/restore from GCS followed by ongoing transaction log shipping.

    # Create a DMS migration job for PostgreSQL (minimal downtime migration)
# Prerequisites:
# - Source PostgreSQL must have wal_level=logical
# - Cloud SQL target must exist
# - Connectivity between source and Cloud SQL (VPN, Interconnect, or public IP)

# Step 1: Create a connection profile for the source
gcloud database-migration connection-profiles create pg-source \
  --region=us-central1 \
  --type=POSTGRES \
  --host=10.0.1.50 \
  --port=5432 \
  --username=migration_user \
  --password=MIGRATION_PASS \
  --display-name="On-Premises PostgreSQL Source"

# Step 2: Create a connection profile for the Cloud SQL target
gcloud database-migration connection-profiles create pg-target \
  --region=us-central1 \
  --type=CLOUDSQL \
  --cloudsql-instance-id=prod-pg-01 \
  --display-name="Cloud SQL Target"

# Step 3: Create the migration job
gcloud database-migration migration-jobs create pg-migration-01 \
  --region=us-central1 \
  --type=CONTINUOUS \
  --source=pg-source \
  --destination=pg-target \
  --display-name="Production PostgreSQL Migration"

# Step 4: Start the migration (initial full load + continuous CDC)
gcloud database-migration migration-jobs start pg-migration-01 \
  --region=us-central1

# Monitor migration status
gcloud database-migration migration-jobs describe pg-migration-01 \
  --region=us-central1

# Step 5: Promote (cutover) when ready
# This stops replication and promotes Cloud SQL as the primary
gcloud database-migration migration-jobs promote pg-migration-01 \
  --region=us-central1

    Manual migration for PostgreSQL using pg_dump and pg_restore is appropriate for databases under a few hundred gigabytes where a maintenance window is acceptable:

    # Dump from source (run on a host with access to both source and Cloud SQL)
pg_dump \
  -h source-pg-host \
  -U postgres \
  -d appdb \
  -Fc \
  --no-owner \
  --no-acl \
  -f appdb_dump.pgc

# Restore to Cloud SQL via Auth Proxy
./cloud-sql-proxy my-project:us-central1:prod-pg-01 --port=5432 &

pg_restore \
  -h 127.0.0.1 \
  -p 5432 \
  -U postgres \
  -d appdb \
  --no-owner \
  --no-acl \
  -j 4 \   # Parallel restore with 4 workers
  appdb_dump.pgc

    The --no-owner and --no-acl flags are typically needed because Cloud SQL's postgres user cannot set ownership to roles that don't exist on the target, and ACL re-application may fail if the source had superuser-only grants. Review ownership and permissions manually after the restore.

    For SQL Server migrations, the typical pattern is:

    1. Take a full backup on source as a .bak file

    2. Upload the .bak file to a GCS bucket accessible by Cloud SQL

    3. Import using gcloud sql import bak

    4. Configure transaction log shipping from source to Cloud SQL for the cutover window (via DMS continuous migration)

    # Upload SQL Server backup to GCS
gsutil cp SalesDB_full.bak gs://my-migration-bucket/SalesDB_full.bak

# Import to Cloud SQL SQL Server
gcloud sql import bak prod-mssql-01 \
  gs://my-migration-bucket/SalesDB_full.bak \
  --database=SalesDB \
  --bak-type=FULL \
  --no-recovery  # Leave in restoring state for subsequent log restores

# Apply transaction log backups during the migration window
gcloud sql import bak prod-mssql-01 \
  gs://my-migration-bucket/SalesDB_log_001.bak \
  --database=SalesDB \
  --bak-type=TLOG \
  --no-recovery

# Final log backup with recovery (brings database online)
gcloud sql import bak prod-mssql-01 \
  gs://my-migration-bucket/SalesDB_log_final.bak \
  --database=SalesDB \
  --bak-type=TLOG
  # No --no-recovery on the final restore

    Post-migration validation should be scripted and run before decommissioning the source:

    -- PostgreSQL: row count comparison across all tables
-- Run on both source and target, compare output
SELECT
  schemaname,
  tablename,
  n_live_tup AS estimated_rows
FROM pg_stat_user_tables
ORDER BY schemaname, tablename;

-- More precise (slower on large tables):
SELECT
  table_schema,
  table_name,
  (xpath('/row/cnt/text()',
    query_to_xml(
      format('SELECT COUNT(*) AS cnt FROM %I.%I',
             table_schema, table_name),
      false, true, ''))
  )[1]::text::bigint AS exact_row_count
FROM information_schema.tables
WHERE table_type = 'BASE TABLE'
  AND table_schema NOT IN ('pg_catalog', 'information_schema')
ORDER BY table_schema, table_name;
    -- SQL Server: row count comparison across all tables
SELECT
  s.name           AS schema_name,
  t.name           AS table_name,
  p.rows           AS row_count
FROM sys.tables      t
JOIN sys.schemas     s ON s.schema_id = t.schema_id
JOIN sys.partitions  p ON p.object_id = t.object_id AND p.index_id IN (0, 1)
ORDER BY s.name, t.name;

    Key Takeaways

  • → **Cloud SQL gives you managed PostgreSQL and SQL Server without OS-level access**, replacing `postgresql.conf`, `pg_hba.conf`, and `sp_configure` with database flags surfaced through the gcloud CLI, Console, and Terraform. The allowed configuration space is large enough for production tuning but excludes superuser-only operations, arbitrary extension installation, and OS-level interventions like TempDB file count changes on SQL Server.
  • → **HA in Cloud SQL is synchronous and regional, not global**: the standby lives in a different zone within the same region and is not readable. Cross-region resilience and read scaling require separately configured read replicas, and replica lag monitoring must be part of your operational baseline rather than an afterthought.
  • → **IAM database authentication and Cloud SQL Auth Proxy replace the `pg_hba.conf` + password credential model** for production access control. Short-lived IAM tokens eliminate static credential rotation, workload identity on GKE removes credential files entirely, and Private Service Connect addresses IP range exhaustion at enterprise scale — but Auth Proxy is a TLS tunnel, not a connection pooler, so PgBouncer or an equivalent remains necessary for high-connection OLTP workloads.
  • → **PITR via instance clone is the operationally correct recovery pattern** on Cloud SQL: clone to a new instance at the target timestamp, validate data integrity with row count and business-logic checks, then promote or discard. Automating this monthly with Cloud Scheduler removes the human dependency and produces documented recovery evidence. For SQL Server migrations, the `--no-recovery` flag on intermediate log restores preserves the restoring state for sequential log application before final cutover.
  • → **Performance tuning fundamentals are unchanged** — `pg_stat_statements`, wait statistics, index fragmentation analysis, and autovacuum tuning apply identically to Cloud SQL as to self-managed instances. What changes is the tooling layer: Query Insights replaces pgBadger as the first-line slow query tool, Cloud Monitoring replaces Nagios/Zabbix for infrastructure alerting, and Cloud Logging with BigQuery export replaces local log retention for historical analysis. Gaps remain (no In-Memory OLTP, no SSIS, no arbitrary PostgreSQL extensions) and must be identified before committing to Cloud SQL as a migration target.
