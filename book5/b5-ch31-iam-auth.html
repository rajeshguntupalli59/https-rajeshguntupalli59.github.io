Chapter 31: IAM-Based Database Authentication

Cloud-managed databases fundamentally change how you think about authentication. The pg_hba.conf entries you've maintained for years, the SQL Server logins tied to Windows accounts, the service accounts rotated manually every quarter — all of that shifts toward a unified identity model built on the cloud provider's IAM plane. IAM-based database authentication means the database validates identity through short-lived tokens issued by the cloud provider rather than long-lived passwords stored in the database itself. This chapter walks through how AWS RDS, Azure SQL, and Google Cloud SQL implement IAM authentication, how to configure it for production workloads, and where the sharp edges are. The goal is not to replace your understanding of database security — it is to map that knowledge onto the identity primitives each cloud provider offers.

---

31.1 Why IAM Authentication Changes the Security Model

Traditional database authentication operates on a shared-secret model. A password is created, stored in the database, distributed to the application, and periodically rotated. Each step introduces risk: passwords end up in configuration files, rotation breaks connections, and auditing who authenticated when requires database-level logging that many teams never configure properly.

IAM authentication flips this. Instead of a password, a client requests a short-lived token from the IAM service — typically valid for 15 minutes — and presents that token as the password to the database. The database validates the token against the IAM service in real time. No static secret leaves the IAM boundary. When the token expires, it cannot be reused. Rotation happens automatically because tokens are never stored.

The analogy to your existing knowledge: if pg_hba.conf is the gatekeeper that says "this IP range may connect with md5 authentication," then IAM roles are the gatekeeper that says "this EC2 instance profile or this Kubernetes service account may connect with a token it obtained from the IAM service." The database still has user accounts — a PostgreSQL role or a SQL Server login — but the credential used to prove identity is ephemeral and cloud-managed.

The operational implications are significant. You no longer rotate passwords; you manage which IAM principals have permission to generate tokens. Audit trails move from database logs into CloudTrail, Azure Activity Log, or Cloud Audit Logs — platforms with retention, alerting, and SIEM integration that most teams already operate. The attack surface of stolen credentials shrinks because a token captured in transit is useless after 15 minutes.

The tradeoffs are real. Applications that open connections slowly or use connection pools with long-lived connections need to handle token renewal. Not every database engine on every cloud platform supports IAM authentication. Some configurations require specific parameter groups or engine versions. You need to understand these constraints before committing to IAM auth in production.

graph LR
    A[Application /
IAM principal] -->|1. Request token| B[Cloud IAM service]
    B -->|2. Short-lived signed token| A

31.2 IAM Authentication on AWS RDS and Aurora

AWS supports IAM database authentication for RDS MySQL, RDS PostgreSQL, Aurora MySQL, and Aurora PostgreSQL. It is not available for RDS SQL Server, RDS Oracle, or RDS MariaDB. The mechanism is the same across supported engines: the application calls generate-db-auth-token to get a signed token, then passes that token as the password when connecting. The token is valid for 15 minutes.

Enabling IAM Authentication

IAM authentication is an instance-level setting, not a database-level setting. You enable it when creating or modifying an instance.

# Enable IAM authentication on an existing RDS PostgreSQL instance
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --enable-iam-database-authentication \
  --apply-immediately

# Verify the setting
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].IAMDatabaseAuthenticationEnabled'

Enabling IAM auth does not disable password authentication. Existing users can still connect with passwords. You enable IAM auth at the instance level, then selectively grant the rds_iam role to specific database users. This lets you migrate gradually.

Creating the Database User

On PostgreSQL, you create a regular role and grant it the rds_iam group. The role must not have a password — or more precisely, the password is irrelevant because it will never be used for IAM-authenticated connections.

-- On RDS PostgreSQL or Aurora PostgreSQL
-- Create an application user that authenticates via IAM
CREATE USER app_service WITH LOGIN;
GRANT rds_iam TO app_service;

-- Grant necessary schema privileges
GRANT CONNECT ON DATABASE production TO app_service;
GRANT USAGE ON SCHEMA public TO app_service;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_service;

-- For future tables created in the schema
ALTER DEFAULT PRIVILEGES IN SCHEMA public 
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_service;

On RDS MySQL and Aurora MySQL, the syntax is slightly different:

-- On RDS MySQL or Aurora MySQL
CREATE USER 'app_service'@'%' IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS';
GRANT SELECT, INSERT, UPDATE, DELETE ON production.* TO 'app_service'@'%';

IAM Policy for Token Generation

The IAM principal that needs database access — an EC2 instance role, an ECS task role, a Lambda execution role, a Kubernetes service account with IRSA — needs an IAM policy that allows the rds-db:connect action. The resource ARN encodes the database instance, region, account, and database username.

# Get the resource ID needed for the IAM policy (it's NOT the instance identifier)
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].DbiResourceId'
# Returns something like: db-ABCDEFGHIJKLMNOPQRSTUVWXYZ

The IAM policy:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "rds-db:connect",
      "Resource": "arn:aws:rds-db:us-east-1:123456789012:dbuser:db-ABCDEFGHIJKLMNOPQRSTUVWXYZ/app_service"
    }
  ]
}

The resource format is: arn:aws:rds-db:::dbuser:/. Using the DbiResourceId rather than the instance identifier is a common gotcha — the IAM policy silently allows the action but the token will not work if you use the wrong resource identifier.

Generating and Using the Auth Token

import boto3
import psycopg2
import ssl

def get_connection():
    rds_client = boto3.client('rds', region_name='us-east-1')
    
    # Token is valid for 15 minutes — generate it close to connection time
    token = rds_client.generate_db_auth_token(
        DBHostname='prod-postgres-01.abc123.us-east-1.rds.amazonaws.com',
        Port=5432,
        DBUsername='app_service',
        Region='us-east-1'
    )
    
    # SSL is required for IAM authentication — the token is useless without it
    # Download the RDS CA bundle: https://truststore.pki.rds.amazonaws.com/
    ssl_context = ssl.create_default_context()
    ssl_context.load_verify_locations('us-east-1-bundle.pem')
    
    conn = psycopg2.connect(
        host='prod-postgres-01.abc123.us-east-1.rds.amazonaws.com',
        port=5432,
        database='production',
        user='app_service',
        password=token,
        sslmode='verify-full',
        sslrootcert='us-east-1-bundle.pem'
    )
    
    return conn

SSL is mandatory, not optional. AWS validates the token only over encrypted connections. If your application currently connects with sslmode=disable or sslmode=allow, IAM authentication will not work regardless of how correctly you've configured everything else.

IAM Auth with RDS Proxy

RDS Proxy adds an important capability: it handles token renewal on behalf of the application. When using RDS Proxy with IAM authentication, the application authenticates to the Proxy using a token, but the Proxy manages the connection pool to the underlying RDS instance using whatever credential model you've configured. This is the recommended pattern for Lambda and ECS applications that open many short-lived connections.

# Create an RDS Proxy with IAM authentication enabled
aws rds create-db-proxy \
  --db-proxy-name prod-postgres-proxy \
  --engine-family POSTGRESQL \
  --auth '[{
    "AuthScheme": "SECRETS",
    "IAMAuth": "REQUIRED",
    "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:rds-proxy-secret"
  }]' \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-abc123 subnet-def456 \
  --vpc-security-group-ids sg-789xyz \
  --require-tls

With IAMAuth: REQUIRED on the proxy, every connection to the proxy endpoint must use a valid IAM token. The proxy handles the actual database connection internally.

31.3 Azure SQL and Entra ID (Azure Active Directory) Authentication

Azure SQL calls its IAM authentication "Microsoft Entra ID authentication" (formerly Azure Active Directory authentication). The architecture differs from AWS: rather than generating a token manually, the application obtains an OAuth 2.0 access token from the Entra ID endpoint and uses it as the password for SQL connections. The token is bearer-based, valid for approximately one hour.

Azure SQL supports Entra ID authentication for Azure SQL Database, Azure SQL Managed Instance, and Azure Synapse Analytics. Unlike AWS, where password and IAM auth coexist on the same user, Azure SQL can enforce Entra-only authentication at the server level, blocking all SQL authentication logins.

Configuring Entra ID Authentication

# Set an Entra ID admin for the Azure SQL server
# This is a prerequisite — Entra ID auth requires an Entra admin be set
az sql server ad-admin create \
  --resource-group prod-rg \
  --server prod-sql-server \
  --display-name "DBA-Admin-Group" \
  --object-id "a1b2c3d4-e5f6-7890-abcd-ef1234567890"

# Optionally enforce Entra-only authentication (disables SQL logins entirely)
az sql server ad-only-auth enable \
  --resource-group prod-rg \
  --name prod-sql-server

# Verify the setting
az sql server ad-only-auth get \
  --resource-group prod-rg \
  --name prod-sql-server

The ad-only-auth enable command is a one-way operation in terms of impact — it immediately breaks any application using SQL authentication. Test this in staging with realistic connection patterns before applying to production. The master admin password continues to work even with Entra-only auth enabled because Azure maintains an emergency bypass for server administration, but you cannot create new SQL logins or reset passwords for existing ones.

Creating Entra ID Users in the Database

-- Connect to the Azure SQL database as the Entra ID admin
-- Create a contained database user mapped to an Entra ID service principal
-- (No password is specified — authentication happens at the Entra level)

-- For an Entra ID group
CREATE USER [platform-data-app-group] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [platform-data-app-group];
ALTER ROLE db_datawriter ADD MEMBER [platform-data-app-group];

-- For a specific managed identity (application service principal)
CREATE USER [prod-app-service-identity] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [prod-app-service-identity];
ALTER ROLE db_datawriter ADD MEMBER [prod-app-service-identity];

-- Check what external users exist in the database
SELECT name, type_desc, authentication_type_desc
FROM sys.database_principals
WHERE authentication_type_desc = 'EXTERNAL';

The FROM EXTERNAL PROVIDER clause is the Azure SQL equivalent of creating a Windows-authenticated login in SQL Server on-premises. If you've managed SQL Server in a domain environment, this will feel familiar — except you're mapping to Entra ID identities instead of Active Directory accounts.

Acquiring Tokens and Connecting from Applications

from azure.identity import DefaultAzureCredential, ManagedIdentityCredential
import pyodbc
import struct

def get_azure_sql_connection():
    # DefaultAzureCredential tries: environment variables, managed identity,
    # Azure CLI credentials, Visual Studio Code — in that order.
    # In production on Azure (App Service, AKS, VM), this resolves to managed identity.
    credential = DefaultAzureCredential()
    
    # Request a token for Azure SQL Database
    token = credential.get_token("https://database.windows.net/.default")
    
    # pyodbc requires the token in a specific binary format
    # This is a known gotcha — the raw token string does not work directly
    token_bytes = token.token.encode("UTF-16-LE")
    token_struct = struct.pack(f'<I{len(token_bytes)}s', len(token_bytes), token_bytes)
    
    SQL_COPT_SS_ACCESS_TOKEN = 1256  # defined in msodbcsql.h
    
    conn = pyodbc.connect(
        "Driver={ODBC Driver 18 for SQL Server};"
        "Server=prod-sql-server.database.windows.net,1433;"
        "Database=production;"
        "Encrypt=yes;"
        "TrustServerCertificate=no;",
        attrs_before={SQL_COPT_SS_ACCESS_TOKEN: token_struct}
    )
    
    return conn

The struct.pack step is the most common source of errors when first implementing this. The ODBC driver expects the token encoded as UTF-16-LE with a 4-byte little-endian length prefix. Passing the token as a plain string in the connection password field does not work with pyodbc; it works only with certain JDBC drivers that handle token injection differently.

System-Assigned vs. User-Assigned Managed Identity

For Azure resources connecting to Azure SQL, managed identities are the standard pattern. A system-assigned managed identity is created with the resource and deleted when the resource is deleted. A user-assigned managed identity is a standalone Azure resource you can assign to multiple services — useful when you want multiple App Service instances to share a single database identity without maintaining separate database users for each.

# Create a user-assigned managed identity
az identity create \
  --name prod-app-db-identity \
  --resource-group prod-rg \
  --location eastus

# Assign it to an App Service
az webapp identity assign \
  --resource-group prod-rg \
  --name prod-web-app \
  --identities /subscriptions/sub-id/resourceGroups/prod-rg/providers/Microsoft.ManagedIdentity/userAssignedIdentities/prod-app-db-identity

# Get the client ID — needed when explicitly requesting a token for a specific identity
az identity show \
  --name prod-app-db-identity \
  --resource-group prod-rg \
  --query clientId

When a resource has multiple managed identities assigned, DefaultAzureCredential may not select the right one. In that case, use ManagedIdentityCredential(client_id="") explicitly to target the correct identity.

31.4 Google Cloud SQL and AlloyDB IAM Authentication

Google Cloud SQL supports IAM database authentication for PostgreSQL instances and MySQL instances. AlloyDB for PostgreSQL supports IAM authentication as well. The implementation on Cloud SQL uses the Cloud SQL Auth Proxy or the direct IAM authentication feature added in later versions; both ultimately validate against the Google Cloud IAM service.

Enabling IAM Authentication on Cloud SQL

# Create a Cloud SQL PostgreSQL instance with IAM authentication enabled
gcloud sql instances create prod-postgres-01 \
  --database-version=POSTGRES_15 \
  --tier=db-custom-8-32768 \
  --region=us-central1 \
  --availability-type=REGIONAL \
  --storage-type=SSD \
  --storage-size=500GB \
  --storage-auto-increase \
  --database-flags=cloudsql.iam_authentication=on

# Enable IAM authentication on an existing instance
gcloud sql instances patch prod-postgres-01 \
  --database-flags=cloudsql.iam_authentication=on

# Verify
gcloud sql instances describe prod-postgres-01 \
  --format="json(settings.databaseFlags)"

Adding IAM Users

On Cloud SQL, IAM users are added at the instance level through the Cloud SQL API, which automatically creates the corresponding PostgreSQL role. You do not create the role manually in psql.

# Add a service account as an IAM database user
# The username in PostgreSQL will be the service account email truncated at the @ symbol
gcloud sql users create prod-app-sa@project-id.iam.gserviceaccount.com \
  --instance=prod-postgres-01 \
  --type=CLOUD_IAM_SERVICE_ACCOUNT

# Add a human user (Google account)
gcloud sql users create rajesh@company.com \
  --instance=prod-postgres-01 \
  --type=CLOUD_IAM_USER

# List IAM users on the instance
gcloud sql users list --instance=prod-postgres-01

After adding the IAM user at the instance level, you still need to grant database-level privileges inside PostgreSQL. The service account email becomes a PostgreSQL role, but the PostgreSQL role name drops the domain suffix:

-- Connect to the database as the superuser
-- Grant privileges to the IAM service account role
-- Note: the role name is truncated — just the part before the @
GRANT CONNECT ON DATABASE production TO "prod-app-sa";
GRANT USAGE ON SCHEMA public TO "prod-app-sa";
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO "prod-app-sa";

-- The full email format is used for CLOUD_IAM_USER types
GRANT CONNECT ON DATABASE production TO "rajesh@company.com";

-- Verify the roles exist
SELECT rolname, rolcanlogin FROM pg_roles 
WHERE rolname IN ('prod-app-sa', 'rajesh@company.com');

Using the Cloud SQL Auth Proxy

The Cloud SQL Auth Proxy handles IAM authentication and SSL termination transparently. It runs as a sidecar process alongside your application and listens on a local port. Your application connects to 127.0.0.1:5432 as if connecting to a local PostgreSQL instance; the proxy handles authentication to Cloud SQL.

# Download and run the Cloud SQL Auth Proxy
# In Kubernetes, this runs as a sidecar container
curl -o cloud-sql-proxy \
  https://storage.googleapis.com/cloud-sql-connectors/cloud-sql-proxy/v2.7.0/cloud-sql-proxy.linux.amd64
chmod +x cloud-sql-proxy

# Run the proxy with IAM authentication
./cloud-sql-proxy \
  --auto-iam-authn \
  --port=5432 \
  project-id:us-central1:prod-postgres-01

# The application then connects to localhost:5432 with the IAM username
# No password needed — the proxy provides the credential
psql "host=127.0.0.1 port=5432 dbname=production user=prod-app-sa sslmode=disable"

The --auto-iam-authn flag is what enables IAM-based authentication through the proxy. Without it, the proxy provides SSL termination and authorized network access but still requires password authentication. When connecting through the proxy with IAM auth, you do not provide a password — the proxy inserts the token automatically.

Kubernetes Deployment Pattern

In GKE, the Cloud SQL Auth Proxy runs as a sidecar container within the application pod. The pod uses a Kubernetes service account annotated with Workload Identity to assume a Google service account.

# Create a Google service account for the application
gcloud iam service-accounts create prod-app-db-sa \
  --display-name="Production App Database SA"

# Grant it the Cloud SQL Client role
gcloud projects add-iam-policy-binding project-id \
  --member="serviceAccount:prod-app-db-sa@project-id.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"

# Allow the Kubernetes service account to impersonate the Google service account
gcloud iam service-accounts add-iam-policy-binding prod-app-db-sa@project-id.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="serviceAccount:project-id.svc.id.goog[prod-namespace/prod-app-ksa]"

# Annotate the Kubernetes service account
kubectl annotate serviceaccount prod-app-ksa \
  --namespace prod-namespace \
  iam.gke.io/gcp-service-account=prod-app-db-sa@project-id.iam.gserviceaccount.com

31.5 Connection Pooling and Token Renewal in Production

The 15-minute token lifetime on AWS and the approximately one-hour token lifetime on Azure and GCP create a challenge for connection pools. A connection pool that opens connections at startup and reuses them indefinitely will present expired tokens when it tries to open new connections after the token window has passed. The existing connections continue to work — IAM authentication validates the token at connection establishment, not on every query — but new connections will fail.

This distinction matters: IAM auth does not re-validate the token on every query. Once a connection is established, it stays open until closed or until the database server terminates it. The problem occurs when the pool needs to create a new connection, typically because the application load increases or an idle connection times out.

AWS with PgBouncer

PgBouncer in transaction or session pooling mode works with IAM authentication if you implement token rotation in the configuration. PgBouncer reads the password from its userlist.txt file; you need an external process to refresh that file with a new token before expiration.

A practical pattern: run a sidecar process that regenerates the token every 10 minutes and rewrites userlist.txt, then sends RELOAD to PgBouncer:

#!/bin/bash
# token-refresher.sh — runs as a sidecar alongside PgBouncer
# Refresh interval is 10 minutes, well within the 15-minute token window

PGBOUNCER_USERLIST="/etc/pgbouncer/userlist.txt"
DB_HOST="prod-postgres-01.abc123.us-east-1.rds.amazonaws.com"
DB_USER="app_service"
DB_REGION="us-east-1"

while true; do
    TOKEN=$(aws rds generate-db-auth-token \
        --hostname "$DB_HOST" \
        --port 5432 \
        --username "$DB_USER" \
        --region "$DB_REGION")

    if [ $? -eq 0 ]; then
        # Write the new token — escape any special characters
        echo "\"${DB_USER}\" \"${TOKEN}\"" > "${PGBOUNCER_USERLIST}.tmp"
        mv "${PGBOUNCER_USERLIST}.tmp" "$PGBOUNCER_USERLIST"
        
        # Signal PgBouncer to reload its configuration
        psql -h 127.0.0.1 -p 6432 -U pgbouncer pgbouncer -c "RELOAD"
        echo "$(date): Token refreshed successfully"
    else
        echo "$(date): Token generation failed — keeping existing token" >&2
    fi

    sleep 600  # 10-minute interval
done

The mv (atomic rename) prevents PgBouncer from reading a partially written file. The RELOAD command causes PgBouncer to re-read its configuration without dropping existing connections — the active connection pool is preserved; only the credential used for new connections is updated.

AWS with RDS Proxy

As mentioned in Section 31.2, RDS Proxy is the cleanest solution to the token renewal problem on AWS. The proxy maintains a persistent connection pool to RDS using credentials from Secrets Manager; it handles renewal internally. The application presents a token to the proxy endpoint and never needs to worry about pool-level token expiration.

Azure SQL with Connection Pools

Azure SQL tokens have a longer validity window, but the pattern is the same. The azure-identity SDK caches tokens and handles renewal automatically when you use DefaultAzureCredential or ManagedIdentityCredential. If you call credential.get_token(...) on every new connection from the pool, the SDK returns the cached token when it still has sufficient lifetime and transparently requests a new one when needed.

from azure.identity import ManagedIdentityCredential
from azure.core.credentials import AccessToken
import pyodbc
import struct
import threading
import time

class AzureSQLConnectionFactory:
    """
    Token-aware connection factory for use with any connection pool
    that accepts a factory callable for creating new connections.
    The azure-identity SDK handles token caching internally — we simply
    call get_token() on every new connection request.
    """
    
    def __init__(self, server: str, database: str, client_id: str):
        self.server = server
        self.database = database
        self.credential = ManagedIdentityCredential(client_id=client_id)
        self._token_resource = "https://database.windows.net/.default"

    def _token_to_struct(self, token_str: str) -> bytes:
        token_bytes = token_str.encode("UTF-16-LE")
        return struct.pack(f'<I{len(token_bytes)}s', len(token_bytes), token_bytes)

    def create_connection(self) -> pyodbc.Connection:
        token = self.credential.get_token(self._token_resource)
        token_struct = self._token_to_struct(token.token)

        conn = pyodbc.connect(
            f"Driver={{ODBC Driver 18 for SQL Server}};"
            f"Server={self.server},1433;"
            f"Database={self.database};"
            f"Encrypt=yes;"
            f"TrustServerCertificate=no;",
            attrs_before={1256: token_struct}
        )
        return conn

With SQLAlchemy, you pass a creator callable to create_engine:

from sqlalchemy import create_engine

factory = AzureSQLConnectionFactory(
    server="prod-sql-server.database.windows.net",
    database="production",
    client_id="<user-assigned-managed-identity-client-id>"
)

engine = create_engine(
    "mssql+pyodbc://",
    creator=factory.create_connection,
    pool_size=10,
    max_overflow=20,
    pool_pre_ping=True,   # validates connections before checkout
    pool_recycle=1800     # recycle connections every 30 minutes to prevent stale tokens
)

The pool_recycle=1800 setting ensures that even connections that are never explicitly closed get recycled every 30 minutes, which is well within the token validity window for Azure. pool_pre_ping=True sends a lightweight query before handing a connection to the application, catching broken connections before the application sees an error.

GCP with the Cloud SQL Python Connector

Google provides an official Cloud SQL Python Connector library that integrates directly with the IAM authentication mechanism, handles connection refreshes, and manages the certificate rotation that the Cloud SQL service uses internally.

from google.cloud.sql.connector import Connector, IPTypes
import sqlalchemy
import pg8000

def create_cloud_sql_engine(
    instance_connection_name: str,  # "project:region:instance"
    database: str,
    db_user: str,
    ip_type: IPTypes = IPTypes.PRIVATE
) -> sqlalchemy.engine.Engine:

    connector = Connector(ip_type=ip_type)

    def getconn() -> pg8000.dbapi.Connection:
        conn = connector.connect(
            instance_connection_name,
            "pg8000",
            user=db_user,
            db=database,
            enable_iam_auth=True,   # use IAM authentication instead of password
            ip_type=ip_type,
        )
        return conn

    engine = sqlalchemy.create_engine(
        "postgresql+pg8000://",
        creator=getconn,
        pool_size=5,
        max_overflow=10,
        pool_pre_ping=True,
    )
    
    return engine

# Usage
engine = create_cloud_sql_engine(
    instance_connection_name="my-project:us-central1:prod-postgres-01",
    database="production",
    db_user="prod-app-sa",  # truncated service account name (before the @)
)

The Connector object maintains background threads that refresh connection certificates and tokens before they expire. A single Connector instance is meant to be long-lived — create it once at application startup, not per request. Creating a new Connector on every request defeats the refresh logic and adds latency.

31.6 Auditing and Monitoring IAM-Authenticated Connections

One of the core arguments for IAM authentication is that it shifts your audit trail to the cloud provider's logging infrastructure. That shift is only an improvement if you actually configure logging to capture what you need.

AWS CloudTrail for RDS IAM Events

Every generate-db-auth-token API call is a data plane event that CloudTrail captures if you enable data events for RDS. Management events (creating instances, modifying parameter groups) are captured by default; data events require explicit configuration.

# Create a CloudTrail trail with RDS data events enabled
aws cloudtrail create-trail \
  --name prod-database-audit \
  --s3-bucket-name prod-audit-logs-bucket \
  --is-multi-region-trail \
  --enable-log-file-validation

# Start logging
aws cloudtrail start-logging --name prod-database-audit

# Add data event logging for RDS
aws cloudtrail put-event-selectors \
  --trail-name prod-database-audit \
  --event-selectors '[{
    "ReadWriteType": "All",
    "IncludeManagementEvents": true,
    "DataResources": [{
      "Type": "AWS::RDS::DBInstance",
      "Values": ["arn:aws:rds:us-east-1:123456789012:db:prod-postgres-01"]
    }]
  }]'

In the CloudTrail logs, a successful generate-db-auth-token call shows the userIdentity of the IAM principal (the role ARN of the EC2 instance, ECS task, or Lambda function), the timestamp, the source IP, and the target database username. This gives you a precise record of which workload generated credentials to connect as which database user at what time.

At the database level, RDS PostgreSQL's log_connections and log_disconnections parameters capture the connection events alongside the PostgreSQL role name. Correlating CloudTrail token generation events with PostgreSQL connection logs gives you end-to-end traceability.

-- Enable connection logging on RDS PostgreSQL via parameter group
-- (Set in the RDS parameter group, not directly in postgresql.conf)
-- log_connections = 1
-- log_disconnections = 1
-- log_line_prefix = '%t [%p]: [%l-1] user=%u,db=%d,app=%a,client=%h '

-- Query pg_stat_activity to see current IAM-authenticated connections
-- IAM-authenticated connections look identical to password connections at the pg_stat level
-- The distinction is visible only in the authentication log messages
SELECT 
    pid,
    usename,
    application_name,
    client_addr,
    backend_start,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
WHERE usename = 'app_service'
ORDER BY backend_start DESC;

Azure SQL Auditing

Azure SQL has a built-in auditing feature that writes events to Azure Blob Storage, Log Analytics, or an Event Hub. For Entra ID authentication specifically, audit logs capture the authentication type alongside the principal name.

# Enable auditing to a Log Analytics workspace
az sql server audit-policy update \
  --resource-group prod-rg \
  --name prod-sql-server \
  --state Enabled \
  --log-analytics-workspace-resource-id /subscriptions/sub-id/resourceGroups/prod-rg/providers/Microsoft.OperationalInsights/workspaces/prod-log-analytics \
  --log-analytics-target-state Enabled

# Configure database-level diagnostic settings
az monitor diagnostic-settings create \
  --name sql-audit-diagnostics \
  --resource /subscriptions/sub-id/resourceGroups/prod-rg/providers/Microsoft.Sql/servers/prod-sql-server/databases/production \
  --workspace /subscriptions/sub-id/resourceGroups/prod-rg/providers/Microsoft.OperationalInsights/workspaces/prod-log-analytics \
  --logs '[{"category": "SQLSecurityAuditEvents", "enabled": true}]'

Once events are in Log Analytics, you can query them with Kusto Query Language:

// Find all Entra ID authentication events in the last 24 hours
AzureDiagnostics
| where Category == "SQLSecurityAuditEvents"
| where TimeGenerated > ago(24h)
| where action_name_s == "DATABASE AUTHENTICATION SUCCEEDED"
| where authentication_type_s == "EXTERNAL PROVIDER"
| project TimeGenerated, 
          server_instance_name_s, 
          database_name_s,
          session_server_principal_name_s,
          client_ip_s,
          application_name_s
| order by TimeGenerated desc

// Alert on authentication failures for Entra ID users
AzureDiagnostics
| where Category == "SQLSecurityAuditEvents"
| where TimeGenerated > ago(1h)
| where action_name_s == "DATABASE AUTHENTICATION FAILED"
| where authentication_type_s == "EXTERNAL PROVIDER"
| summarize FailureCount = count() by session_server_principal_name_s, client_ip_s
| where FailureCount > 5

GCP Cloud Audit Logs

Cloud SQL IAM authentication events appear in the Cloud Audit Logs under Data Access logs. You need to explicitly enable data access logging for the Cloud SQL API, as it is not on by default due to volume considerations.

# Enable data access audit logging for Cloud SQL
# This is done at the project level in IAM policy
gcloud projects get-iam-policy project-id --format=json > policy.json

# Edit policy.json to add the auditLogConfig, then update:

The audit config JSON block to add:

{
  "auditConfigs": [
    {
      "service": "cloudsql.googleapis.com",
      "auditLogConfigs": [
        {"logType": "DATA_READ"},
        {"logType": "DATA_WRITE"}
      ]
    }
  ]
}

Querying the logs in Cloud Logging:

protoPayload.serviceName="cloudsql.googleapis.com"

31.7 Troubleshooting IAM Authentication Failures

IAM authentication failures produce error messages that are often less informative than standard password authentication failures. The database typically reports a generic authentication error; the real cause is in the IAM policy, the token generation process, or the SSL configuration. A systematic approach to diagnosis saves significant time.

Common AWS RDS IAM Auth Failures

FATAL: PAM authentication failed for user "app_service"

Despite mentioning PAM, this error appears when RDS IAM authentication fails for PostgreSQL. The actual causes in order of frequency:

1. Wrong DbiResourceId in the IAM policy. Verify by running aws rds describe-db-instances --query 'DBInstances[0].DbiResourceId' and comparing to what's in the IAM policy resource ARN.

2. The rds_iam grant is missing. Confirm inside the database: SELECT * FROM pg_roles WHERE rolname = 'app_service'; and check that rds_iam appears in pg_auth_members.

3. SSL not enforced on the client side. The token is a signed URL-style string; if the connection is not encrypted, it will not validate. Confirm sslmode=verify-full or at minimum sslmode=require.

4. Token generated for the wrong hostname. The token is cryptographically bound to the hostname passed to generate-db-auth-token. If you connect via an alias, CNAME, or Route 53 record, generate the token with that same hostname.

5. Clock skew. The token includes a timestamp; if the client's clock is more than a few minutes ahead of or behind the AWS service clock, validation fails. On EC2, this is rare; in containers, it can occur if the host NTP configuration is broken.

# Quick diagnostic: test token generation and connection from the environment
# where the failure is occurring, not from your workstation

TOKEN=$(aws rds generate-db-auth-token \
    --hostname prod-postgres-01.abc123.us-east-1.rds.amazonaws.com \
    --port 5432 \
    --username app_service \
    --region us-east-1)

echo "Token generated: ${TOKEN:0:50}..."  # Print first 50 chars to confirm non-empty

PGPASSWORD="$TOKEN" psql \
    "host=prod-postgres-01.abc123.us-east-1.rds.amazonaws.com \
     port=5432 \
     dbname=production \
     user=app_service \
     sslmode=require \
     sslrootcert=us-east-1-bundle.pem"

Common Azure SQL Entra ID Failures

Login failed for user '<token-identified principal>'. 
Error: 18456, Severity: 14, State: 1

This error from Azure SQL with Entra ID authentication usually points to one of:

1. The managed identity has not been added as a database user. The CREATE USER ... FROM EXTERNAL PROVIDER step in Section 31.3 is easy to miss. The identity can have the Entra ID admin role on the server and still fail to connect to individual databases if the contained database user is not created.

2. The managed identity client ID is wrong. When a VM or App Service has multiple managed identities, specifying the wrong client_id in ManagedIdentityCredential results in a token for a different identity that has no database access.

3. The Entra ID admin is not set on the server. Entra ID authentication on Azure SQL requires an Entra admin to be designated, even if that admin is not the one connecting.

# Verify the Entra admin is set
az sql server ad-admin list \
  --resource-group prod-rg \
  --server-name prod-sql-server

# Verify the database user exists for the managed identity
# Connect using the Entra ID admin and check
# (Use Azure Data Studio or sqlcmd with an interactive Entra ID login)
sqlcmd -S prod-sql-server.database.windows.net \
       -d production \
       -G \
       -Q "SELECT name, type_desc, authentication_type_desc FROM sys.database_principals WHERE type IN ('E','X');"
# -G enables Azure Active Directory authentication

Common GCP Cloud SQL IAM Failures

FATAL:  Cloud SQL IAM user authentication failed for user "prod-app-sa"

GCP-specific issues to check:

1. The username format mismatch. For service accounts, the PostgreSQL role name is the service account email address with the @project-id.iam.gserviceaccount.com portion truncated — only the part before the @ is used. If the service account is prod-app-sa@myproject.iam.gserviceaccount.com, the PostgreSQL user is prod-app-sa. For accounts with project IDs in the name, this truncation can be unintuitive.

2. The Cloud SQL IAM service account was added at the instance level but not granted PostgreSQL privileges. Adding the user via gcloud sql users create creates the PostgreSQL role, but that role has no database privileges until you explicitly grant them inside the database.

3. The cloudsql.iam_authentication flag is not set. The instance-level flag must be enabled. Verify with gcloud sql instances describe --format="json(settings.databaseFlags)".

4. Workload Identity binding is incomplete. In GKE, if the binding between the Kubernetes service account and the Google service account is missing or the annotation is incorrect, the pod runs without the expected identity and token generation fails silently or falls back to the compute metadata service default identity.

# Verify the Workload Identity binding from inside the GKE pod
kubectl exec -it <pod-name> -n prod-namespace -- \
  curl -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/email"
# Should return the expected service account email

# Test token acquisition directly
kubectl exec -it <pod-name> -n prod-namespace -- \
  curl -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"

31.8 Security Hardening Beyond Basic IAM Authentication

Enabling IAM authentication is a starting point. Production security posture requires additional controls layered on top.

Enforce SSL at the Parameter Group Level

Never rely on client-side SSL configuration alone. Enforce SSL at the database engine level so that connections attempting to bypass SSL are rejected even if IAM token validation somehow succeeded.

# AWS: enforce SSL via parameter group (PostgreSQL)
aws rds modify-db-parameter-group \
  --db-parameter-group-name prod-postgres-params \
  --parameters "ParameterName=rds.force_ssl,ParameterValue=1,ApplyMethod=immediate"

# Azure: enforced by default for Entra-only auth
# Verify SSL enforcement on Azure SQL
az sql server show \
  --resource-group prod-rg \
  --name prod-sql-server \
  --query "minimalTlsVersion"

# GCP: enforce SSL
gcloud sql instances patch prod-postgres-01 \
  --require-ssl

Principle of Least Privilege on IAM Policies

The rds-db:connect resource ARN scopes permission to a specific combination of instance and database username. Avoid wildcards:

{
  "Effect": "Allow",
  "Action": "rds-db:connect",
  "Resource": "arn:aws:rds-db:us-east-1:123456789012:dbuser:db-ABCDEFG/app_service"
}

This is preferable to:

{
  "Effect": "Allow",
  "Action": "rds-db:connect",
  "Resource": "arn:aws:rds-db:us-east-1:123456789012:dbuser:*"
}

The wildcard form grants the IAM principal permission to authenticate as any database user on any RDS instance in the account — a significant overreach that is easy to miss because the ARN format is unfamiliar territory for most developers.

Separate IAM Roles by Workload Function

Rather than a single database IAM role shared across all application components, create separate roles for distinct workloads: one for the web tier (read-write on specific tables), one for the reporting service (read-only, different schema), one for the migration tool (DDL permissions, used only during deployment windows). This matches the principle of least privilege and makes the audit trail actionable — you can distinguish between a spike in read traffic and unexpected write activity by identity alone.

Regular Review of IAM-to-Database User Mappings

IAM principals proliferate. Service accounts get created for short-lived projects, EC2 instances are retired but their roles persist, merge activity adds roles from acquired companies. Schedule a periodic review:

-- PostgreSQL: list all roles with rds_iam or IAM authentication access
SELECT 
    r.rolname AS database_user,
    r.rolcanlogin,
    r.rolcreaterole,
    r.rolcreatedb,
    array_agg(g.rolname) AS granted_roles
FROM pg_roles r
LEFT JOIN pg_auth_members m ON r.oid = m.member
LEFT JOIN pg_roles g ON m.roleid = g.oid
WHERE g.rolname = 'rds_iam' OR r.rolname IN (
    SELECT usename FROM pg_user WHERE usesuper = false
)
GROUP BY r.rolname, r.rolcanlogin, r.rolcreaterole, r.rolcreatedb
HAVING array_agg(g.rolname) @> ARRAY['rds_iam']
ORDER BY r.rolname;
-- Azure SQL: list all external (Entra ID) users and their role memberships
SELECT 
    dp.name AS database_user,
    dp.type_desc,
    dp.authentication_type_desc,
    STRING_AGG(rp.name, ', ') AS database_roles
FROM sys.database_principals dp
LEFT JOIN sys.database_role_members drm ON dp.principal_id = drm.member_principal_id
LEFT JOIN sys.database_principals rp ON drm.role_principal_id = rp.principal_id
WHERE dp.authentication_type_desc = 'EXTERNAL'
GROUP BY dp.name, dp.type_desc, dp.authentication_type_desc
ORDER BY dp.name;

Cross-reference the results against your active IAM principals. Any database user whose corresponding IAM principal no longer exists in the cloud account should be dropped from the database. The cloud IAM principal being deleted does not automatically remove the database user — that cleanup must be done manually.

Key Takeaways

  • → IAM database authentication replaces long-lived passwords with short-lived tokens issued by the cloud provider's identity service, eliminating the credential storage and rotation challenges of traditional shared-secret authentication, but requiring applications to handle token renewal when establishing new connections after the token window expires.
  • → Each cloud provider implements IAM auth differently at the protocol level: AWS generates a signed token passed as the password field; Azure SQL uses an OAuth 2.0 bearer token injected via a driver-level connection attribute in a specific binary format; Google Cloud SQL uses either the Auth Proxy sidecar or the Python Connector library, which handle token management transparently alongside SSL certificate rotation.
  • → SSL encryption is not optional with IAM authentication on any of the three platforms — the token is meaningful only over an encrypted channel, and all three providers enforce this at the connection level regardless of client-side configuration.
  • → Connection pooling requires deliberate design around token expiry: AWS RDS Proxy handles renewal transparently at the proxy layer; Azure's `azure-identity` SDK caches and renews tokens automatically when `get_token()` is called per connection; GCP's Cloud SQL Connector manages refresh internally via background threads in a long-lived `Connector` instance.
  • → Enabling IAM authentication shifts the primary audit trail from database-level logs to the cloud provider's centralized logging infrastructure (CloudTrail, Azure Monitor/Log Analytics, Cloud Audit Logs), but realizing that shift requires explicitly enabling data access logging — which is off by default on all three platforms due to volume — and performing cross-database user cleanup when IAM principals are retired, since deleting a cloud identity does not automatically remove the corresponding database user.
