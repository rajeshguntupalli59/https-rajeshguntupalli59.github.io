Chapter 12: Multi-User Memory Isolation

When you build a single-tenant chatbot, memory management is straightforward — one conversation history table, one embedding space, one user. The moment you add a second user, every assumption breaks. Their memories bleed into each other's context, their embeddings compete in the same vector space, their conversation histories mix in ways that produce hallucinations, privacy violations, and deeply confused AI responses. Multi-user memory isolation is the engineering discipline that prevents this, and PostgreSQL's row-level security, schema design, and vector capabilities make it the ideal foundation for getting it right.

This chapter covers the full architecture: how to model user identity in a way that AI pipelines can enforce, how to use PostgreSQL Row Level Security to make memory isolation automatic and tamper-resistant, how to structure embedding tables so semantic search never crosses user boundaries, how to handle shared knowledge alongside private memory, and how to build the FastAPI layer that connects authenticated users to their isolated AI context. These patterns apply whether you are building a customer support chatbot, a personal AI assistant, a multi-tenant SaaS product, or an enterprise agent platform.

---

12.1 The Memory Isolation Problem in Multi-User AI Systems

Consider what "memory" means in a production AI application. It is not a single thing. It is at least four distinct layers:

1. Conversation history — the raw message turns from prior sessions

2. Episodic summaries — compressed representations of what happened in prior conversations

3. User-specific embeddings — vectors derived from documents, notes, or context that belong to one user

4. Shared knowledge embeddings — vectors from a corpus that all users should be able to query (product documentation, company knowledge base)

Each layer has different isolation requirements. Conversation history is strictly private. Episodic summaries are strictly private. User-specific embeddings are strictly private. Shared knowledge embeddings are read-accessible to all authenticated users but write-controlled.

The naive implementation puts everything in the same tables with a user_id column and filters in application code. This works until it doesn't — a missing WHERE clause in a query, a developer testing in production with the wrong session, a bug in the ORM layer. Application-level filtering is defense in one layer. PostgreSQL Row Level Security is defense at the database layer, making data leakage impossible regardless of what the application layer does.

The other failure mode is vector search. If user A has uploaded private financial documents and user B runs a semantic similarity search, an unguarded pgvector query will happily return results from user A's embedding space alongside user B's. The ORDER BY cosine similarity does not know about tenancy. The database policy does.

graph TD
    App[Application code] -->|"set_config('app.current_user_id', ...)"| Conn[DB connection / transaction]
    Conn --> Q1[Query: conversation history]
    Conn --> Q2[Query: episodic summaries]
    Conn --> Q3[Query: user embeddings]
    Conn --> Q4[Query: shared knowledge embeddings]
    Q1 --> RLS1[RLS: user_id = current_setting]
    Q2 --> RLS2[RLS: user_id = current_setting]
    Q3 --> RLS3[RLS: user_id = current_setting]
    Q4 --> RLS4[RLS: tenant_id = current_setting OR global]
    RLS1 --> R[Rows returned — never another user's data]
    RLS2 --> R
    RLS3 --> R
    RLS4 --> R

*Every query, regardless of what application code intended, passes through the same per-connection policy check before a row is returned.*

Here is the foundational schema that everything in this chapter builds from:

-- Core user identity table — the anchor for all isolation policies
CREATE TABLE users (
    user_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    external_id     TEXT UNIQUE NOT NULL,           -- from your auth provider (Auth0, Clerk, etc.)
    tenant_id       UUID NOT NULL,                  -- for multi-tenant SaaS; same as user_id for personal apps
    email           TEXT,
    display_name    TEXT,
    memory_tier     TEXT NOT NULL DEFAULT 'standard'
                        CHECK (memory_tier IN ('standard', 'extended', 'unlimited')),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_active       BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE INDEX idx_users_external_id ON users(external_id);
CREATE INDEX idx_users_tenant_id ON users(tenant_id);

-- Session tracking — connects JWT tokens to database identity
CREATE TABLE user_sessions (
    session_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    started_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_active     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ NOT NULL,
    ip_address      INET,
    user_agent      TEXT,
    is_revoked      BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE INDEX idx_sessions_user_id ON user_sessions(user_id);
CREATE INDEX idx_sessions_expires ON user_sessions(expires_at) WHERE NOT is_revoked;

-- The PostgreSQL role that all application connections use
-- This is NOT a superuser — it has no permissions by default
CREATE ROLE ai_app_user LOGIN PASSWORD 'changeme_in_production';

-- Grant connect on the database
GRANT CONNECT ON DATABASE ai_production TO ai_app_user;
GRANT USAGE ON SCHEMA public TO ai_app_user;

-- Grant table-level permissions — RLS will enforce row-level access
GRANT SELECT, INSERT, UPDATE ON users TO ai_app_user;
GRANT SELECT, INSERT, UPDATE ON user_sessions TO ai_app_user;

The tenant_id column deserves explanation. In a pure personal AI assistant, tenant_id = user_id. In a B2B SaaS product, multiple users share a tenant. Some data is isolated per user within a tenant; other data is shared across the tenant. The schema handles both by carrying both identifiers everywhere.

12.2 Conversation History Tables with Row Level Security

Conversation history is the most privacy-sensitive memory layer. A single leaked message from another user's conversation is a serious incident. Here is the complete schema and RLS configuration:

-- Conversations group related message turns
CREATE TABLE conversations (
    conversation_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    title           TEXT,
    model_id        TEXT NOT NULL DEFAULT 'claude-3-5-sonnet-20241022',
    system_prompt   TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}',
    token_count     INTEGER NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    archived_at     TIMESTAMPTZ
);

CREATE INDEX idx_conversations_user_id ON conversations(user_id);
CREATE INDEX idx_conversations_tenant_id ON conversations(tenant_id);
CREATE INDEX idx_conversations_updated ON conversations(user_id, updated_at DESC);

-- Individual message turns within a conversation
CREATE TABLE messages (
    message_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(conversation_id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool')),
    content         TEXT NOT NULL,
    content_tokens  INTEGER,
    tool_calls      JSONB,
    tool_results    JSONB,
    model_id        TEXT,
    finish_reason   TEXT,
    latency_ms      INTEGER,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_messages_conversation ON messages(conversation_id, created_at);
CREATE INDEX idx_messages_user_id ON messages(user_id);
-- Partial index for recent messages — most queries only need recent history
CREATE INDEX idx_messages_recent ON messages(conversation_id, created_at DESC)
    WHERE created_at > NOW() - INTERVAL '90 days';

-- Episodic memory summaries — compressed representations of past conversations
CREATE TABLE memory_summaries (
    summary_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    conversation_id UUID REFERENCES conversations(conversation_id) ON DELETE SET NULL,
    summary_text    TEXT NOT NULL,
    key_facts       JSONB NOT NULL DEFAULT '[]',   -- extracted entities and facts
    importance      FLOAT NOT NULL DEFAULT 0.5,    -- 0.0 to 1.0, used for retrieval ranking
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    valid_until     TIMESTAMPTZ                    -- NULL = permanent memory
);

CREATE INDEX idx_summaries_user_id ON memory_summaries(user_id, importance DESC);

-- Enable RLS on all user-data tables
ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;
ALTER TABLE memory_summaries ENABLE ROW LEVEL SECURITY;

-- The application sets this at connection time from the JWT
-- current_setting('app.current_user_id') returns the user_id
-- current_setting('app.current_tenant_id') returns the tenant_id

-- Conversations: users see only their own; tenant admins see the whole tenant
CREATE POLICY conversations_isolation ON conversations
    FOR ALL
    TO ai_app_user
    USING (
        user_id = current_setting('app.current_user_id')::UUID
        OR (
            tenant_id = current_setting('app.current_tenant_id')::UUID
            AND current_setting('app.is_tenant_admin')::BOOLEAN = TRUE
        )
    )
    WITH CHECK (
        user_id = current_setting('app.current_user_id')::UUID
        AND tenant_id = current_setting('app.current_tenant_id')::UUID
    );

-- Messages: inherit conversation access — user_id check is redundant but explicit
CREATE POLICY messages_isolation ON messages
    FOR ALL
    TO ai_app_user
    USING (
        user_id = current_setting('app.current_user_id')::UUID
        OR (
            tenant_id = current_setting('app.current_tenant_id')::UUID
            AND current_setting('app.is_tenant_admin')::BOOLEAN = TRUE
        )
    )
    WITH CHECK (
        user_id = current_setting('app.current_user_id')::UUID
        AND tenant_id = current_setting('app.current_tenant_id')::UUID
    );

-- Memory summaries: strictly per-user, no tenant admin override
CREATE POLICY summaries_isolation ON memory_summaries
    FOR ALL
    TO ai_app_user
    USING (user_id = current_setting('app.current_user_id')::UUID)
    WITH CHECK (
        user_id = current_setting('app.current_user_id')::UUID
        AND tenant_id = current_setting('app.current_tenant_id')::UUID
    );

-- Helper function to set the session context from application code
CREATE OR REPLACE FUNCTION set_user_context(
    p_user_id UUID,
    p_tenant_id UUID,
    p_is_tenant_admin BOOLEAN DEFAULT FALSE
) RETURNS VOID
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
BEGIN
    PERFORM set_config('app.current_user_id', p_user_id::TEXT, TRUE);
    PERFORM set_config('app.current_tenant_id', p_tenant_id::TEXT, TRUE);
    PERFORM set_config('app.is_tenant_admin', p_is_tenant_admin::TEXT, TRUE);
END;
$$;

-- Grant execute only to the app role
GRANT EXECUTE ON FUNCTION set_user_context TO ai_app_user;

The set_config(..., TRUE) call at the end sets the configuration as local to the current transaction. This is important: with PgBouncer in transaction pooling mode, each transaction gets a potentially different physical connection, so the session-local settings must be re-established per transaction. If you are using session pooling, you can use FALSE to persist across the session, but you must explicitly clear context on logout.

12.3 Isolated Vector Embeddings for Private User Memory

Semantic search across user documents is where multi-user isolation gets architecturally interesting. You need fast approximate nearest-neighbor search within a user's embedding space while keeping it completely separated from other users' spaces. pgvector handles this elegantly with partial indexes.

-- Enable pgvector
CREATE EXTENSION IF NOT EXISTS vector;

-- User document store — private documents uploaded by each user
CREATE TABLE user_documents (
    document_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    filename        TEXT,
    content_type    TEXT NOT NULL DEFAULT 'text/plain',
    raw_content     TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}',
    ingested_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    chunk_count     INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_user_docs_user_id ON user_documents(user_id);
ALTER TABLE user_documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_docs_isolation ON user_documents
    FOR ALL TO ai_app_user
    USING (user_id = current_setting('app.current_user_id')::UUID)
    WITH CHECK (
        user_id = current_setting('app.current_user_id')::UUID
        AND tenant_id = current_setting('app.current_tenant_id')::UUID
    );

-- Embedding chunks — each document is split into chunks with vector embeddings
CREATE TABLE user_embeddings (
    embedding_id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id     UUID NOT NULL REFERENCES user_documents(document_id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,
    chunk_index     INTEGER NOT NULL,
    chunk_text      TEXT NOT NULL,
    embedding       VECTOR(1536),          -- OpenAI text-embedding-3-small dimensions
    token_count     INTEGER,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Standard index for lookup by user + document
CREATE INDEX idx_user_embeddings_user ON user_embeddings(user_id, document_id);

-- Per-user HNSW indexes using partial indexes
-- This is the key pattern: each user gets efficient ANN search within their own space
-- For a small number of power users, you might create these dynamically
-- For large multi-tenant systems, use the partitioned approach below

-- Example: partial HNSW index for a specific high-volume user
-- In practice, create these for users above a document threshold
CREATE INDEX idx_embeddings_hnsw_user_example ON user_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE user_id = '00000000-0000-0000-0000-000000000001'::UUID;

-- For the general case: a single HNSW index on user_id + embedding
-- pgvector will use the user_id filter to narrow candidates
-- This is less optimal than per-user indexes but works for most scales
CREATE INDEX idx_embeddings_hnsw_all ON user_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Shared knowledge base — accessible to all users in a tenant
-- No user_id here — these are tenant-level or global resources
CREATE TABLE shared_knowledge (
    knowledge_id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID,                  -- NULL = global (platform-wide)
    source_name     TEXT NOT NULL,
    chunk_text      TEXT NOT NULL,
    embedding       VECTOR(1536),
    metadata        JSONB NOT NULL DEFAULT '{}',
    published_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMPTZ
);

CREATE INDEX idx_shared_knowledge_hnsw ON shared_knowledge
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

CREATE INDEX idx_shared_knowledge_tenant ON shared_knowledge(tenant_id);

-- RLS for shared knowledge: all authenticated users can read; only admins can write
ALTER TABLE shared_knowledge ENABLE ROW LEVEL SECURITY;

CREATE POLICY shared_knowledge_read ON shared_knowledge
    FOR SELECT TO ai_app_user
    USING (
        tenant_id IS NULL  -- global knowledge
        OR tenant_id = current_setting('app.current_tenant_id')::UUID
    );

CREATE POLICY shared_knowledge_write ON shared_knowledge
    FOR INSERT TO ai_app_user
    WITH CHECK (
        current_setting('app.is_tenant_admin')::BOOLEAN = TRUE
        AND (tenant_id IS NULL OR tenant_id = current_setting('app.current_tenant_id')::UUID)
    );

-- Semantic search function that automatically respects user context
-- RLS handles the isolation; this function provides a clean API
CREATE OR REPLACE FUNCTION search_user_memory(
    query_embedding VECTOR(1536),
    p_limit INTEGER DEFAULT 5,
    p_threshold FLOAT DEFAULT 0.7
) RETURNS TABLE (
    source          TEXT,
    chunk_text      TEXT,
    similarity      FLOAT,
    metadata        JSONB
)
LANGUAGE sql
STABLE
AS $$
    -- Search private user embeddings
    SELECT
        'private'::TEXT as source,
        ue.chunk_text,
        1 - (ue.embedding <=> query_embedding) as similarity,
        ue.metadata
    FROM user_embeddings ue
    WHERE 1 - (ue.embedding <=> query_embedding) >= p_threshold
    -- RLS automatically filters to current user — no explicit WHERE needed
    UNION ALL
    -- Search shared knowledge (tenant + global)
    SELECT
        'shared'::TEXT as source,
        sk.chunk_text,
        1 - (sk.embedding <=> query_embedding) as similarity,
        sk.metadata
    FROM shared_knowledge sk
    WHERE 1 - (sk.embedding <=> query_embedding) >= p_threshold
    -- RLS automatically filters to current tenant
    ORDER BY similarity DESC
    LIMIT p_limit;
$$;

The search_user_memory function looks dangerously simple — no explicit user_id filter anywhere. That is intentional and correct. RLS policies on user_embeddings and shared_knowledge enforce the context set at the start of the transaction. The function just expresses the query shape; PostgreSQL's policy engine does the enforcement transparently.

12.4 The Python Application Layer with Context Propagation

The database layer is solid, but the application layer must reliably set user context on every database interaction. A connection pool complicates this — connections are reused across requests, and if context-setting fails silently, RLS cannot protect you. Here is the complete FastAPI + async SQLAlchemy pattern:

# memory_isolation/database.py

import uuid
from contextlib import asynccontextmanager
from typing import AsyncGenerator, Optional

from sqlalchemy.ext.asyncio import (
    AsyncConnection,
    AsyncEngine,
    create_async_engine,
)
from sqlalchemy import text

# Use asyncpg driver — required for async PostgreSQL
DATABASE_URL = "postgresql+asyncpg://ai_app_user:changeme@localhost/ai_production"

engine: AsyncEngine = create_async_engine(
    DATABASE_URL,
    pool_size=20,
    max_overflow=10,
    pool_pre_ping=True,
    # Important: echo=False in production — logs contain user data
    echo=False,
)


class UserContext:
    """Carries authenticated user identity through the request lifecycle."""

    def __init__(
        self,
        user_id: uuid.UUID,
        tenant_id: uuid.UUID,
        is_tenant_admin: bool = False,
    ):
        self.user_id = user_id
        self.tenant_id = tenant_id
        self.is_tenant_admin = is_tenant_admin


@asynccontextmanager
async def get_user_connection(
    ctx: UserContext,
) -> AsyncGenerator[AsyncConnection, None]:
    """
    Acquire a database connection and set user context via RLS.

    This context manager MUST be used for every database operation in the
    request handler. Never use a bare connection without setting context.
    """
    async with engine.connect() as conn:
        # Set user context — this enables RLS policies
        # Using set_config with local=TRUE scopes settings to the transaction
        await conn.execute(
            text(
                "SELECT set_user_context("
                "    :user_id::UUID,"
                "    :tenant_id::UUID,"
                "    :is_admin"
                ")"
            ),
            {
                "user_id": str(ctx.user_id),
                "tenant_id": str(ctx.tenant_id),
                "is_admin": ctx.is_tenant_admin,
            },
        )
        try:
            yield conn
            await conn.commit()
        except Exception:
            await conn.rollback()
            raise


# memory_isolation/memory_service.py

import uuid
from datetime import datetime
from typing import Optional

import numpy as np
from openai import AsyncOpenAI
from anthropic import AsyncAnthropic
from sqlalchemy import text

from .database import UserContext, get_user_connection

openai_client = AsyncOpenAI()
anthropic_client = AsyncAnthropic()


async def get_embedding(text_content: str) -> list[float]:
    """Generate embedding using OpenAI text-embedding-3-small."""
    response = await openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=text_content,
    )
    return response.data[0].embedding


async def get_conversation_context(
    ctx: UserContext,
    conversation_id: uuid.UUID,
    max_messages: int = 20,
) -> list[dict]:
    """
    Retrieve recent message history for a conversation.
    RLS ensures only the authenticated user's messages are returned.
    """
    async with get_user_connection(ctx) as conn:
        result = await conn.execute(
            text("""
                SELECT role, content, tool_calls, tool_results, created_at
                FROM messages
                WHERE conversation_id = :conv_id
                ORDER BY created_at DESC
                LIMIT :limit
            """),
            {"conv_id": str(conversation_id), "limit": max_messages},
        )
        rows = result.fetchall()

    # Return in chronological order for the LLM
    messages = []
    for row in reversed(rows):
        msg = {"role": row.role, "content": row.content}
        if row.tool_calls:
            msg["tool_calls"] = row.tool_calls
        messages.append(msg)

    return messages


async def search_user_context(
    ctx: UserContext,
    query: str,
    limit: int = 5,
    threshold: float = 0.7,
) -> list[dict]:
    """
    Semantic search across private user embeddings and shared knowledge.
    The search_user_memory() PostgreSQL function handles isolation.
    """
    query_embedding = await get_embedding(query)
    embedding_str = "[" + ",".join(str(x) for x in query_embedding) + "]"

    async with get_user_connection(ctx) as conn:
        result = await conn.execute(
            text("""
                SELECT source, chunk_text, similarity, metadata
                FROM search_user_memory(
                    :embedding::vector,
                    :limit,
                    :threshold
                )
            """),
            {
                "embedding": embedding_str,
                "limit": limit,
                "threshold": threshold,
            },
        )
        rows = result.fetchall()

    return [
        {
            "source": row.source,
            "text": row.chunk_text,
            "similarity": float(row.similarity),
            "metadata": row.metadata or {},
        }
        for row in rows
    ]


async def save_message(
    ctx: UserContext,
    conversation_id: uuid.UUID,
    role: str,
    content: str,
    model_id: Optional[str] = None,
    latency_ms: Optional[int] = None,
) -> uuid.UUID:
    """Persist a message turn. RLS WITH CHECK ensures user_id matches context."""
    message_id = uuid.uuid4()

    async with get_user_connection(ctx) as conn:
        await conn.execute(
            text("""
                INSERT INTO messages (
                    message_id, conversation_id, user_id, tenant_id,
                    role, content, model_id, latency_ms
                ) VALUES (:message_id, :conversation_id, :user_id, :tenant_id,
                    :role, :content, :model_id, :latency_ms
                )
            """),
            {
                "message_id": str(message_id),
                "conversation_id": str(conversation_id),
                "user_id": str(ctx.user_id),
                "tenant_id": str(ctx.tenant_id),
                "role": role,
                "content": content,
                "model_id": model_id,
                "latency_ms": latency_ms,
            },
        )

    return message_id


async def create_conversation(
    ctx: UserContext,
    title: Optional[str] = None,
    model_id: str = "claude-3-5-sonnet-20241022",
    system_prompt: Optional[str] = None,
) -> uuid.UUID:
    """Create a new conversation for the authenticated user."""
    conversation_id = uuid.uuid4()

    async with get_user_connection(ctx) as conn:
        await conn.execute(
            text("""
                INSERT INTO conversations (
                    conversation_id, user_id, tenant_id, title, model_id, system_prompt
                ) VALUES (
                    :conversation_id, :user_id, :tenant_id, :title, :model_id, :system_prompt
                )
            """),
            {
                "conversation_id": str(conversation_id),
                "user_id": str(ctx.user_id),
                "tenant_id": str(ctx.tenant_id),
                "title": title,
                "model_id": model_id,
                "system_prompt": system_prompt,
            },
        )

    return conversation_id


async def generate_and_save_response(
    ctx: UserContext,
    conversation_id: uuid.UUID,
    user_message: str,
    system_prompt: Optional[str] = None,
) -> str:
    """
    Full RAG + memory pipeline for one message turn:
    1. Save user message
    2. Retrieve relevant context (private + shared)
    3. Get conversation history
    4. Call Claude with full context
    5. Save assistant response
    """
    import time

    # 1. Save the incoming user message
    await save_message(ctx, conversation_id, "user", user_message)

    # 2. Semantic retrieval — isolated to this user by RLS
    relevant_context = await search_user_context(ctx, user_message, limit=5)

    # 3. Conversation history — isolated to this user by RLS
    history = await get_conversation_context(ctx, conversation_id, max_messages=20)

    # 4. Build the prompt with retrieved context
    context_block = ""
    if relevant_context:
        private_ctx = [c for c in relevant_context if c["source"] == "private"]
        shared_ctx = [c for c in relevant_context if c["source"] == "shared"]

        if private_ctx:
            context_block += "\n\n<user_documents>\n"
            for item in private_ctx:
                context_block += f"[similarity: {item['similarity']:.3f}]\n{item['text']}\n\n"
            context_block += "</user_documents>"

        if shared_ctx:
            context_block += "\n\n<knowledge_base>\n"
            for item in shared_ctx:
                context_block += f"[similarity: {item['similarity']:.3f}]\n{item['text']}\n\n"
            context_block += "</knowledge_base>"

    base_system = system_prompt or (
        "You are a helpful AI assistant. You have access to the user's personal documents "
        "and a shared knowledge base. Use them to provide accurate, personalized responses."
    )

    full_system = base_system + context_block

    # 5. Call Claude — history already contains prior turns in order
    # Remove the last message (the one we just saved) from history
    # since we pass user_message directly as the last human turn
    api_history = [m for m in history if m["content"] != user_message or m["role"] != "user"]

    start_time = time.time()
    response = await anthropic_client.messages.create(
        model="claude-3-5-sonnet-20241022",
        max_tokens=2048,
        system=full_system,
        messages=api_history + [{"role": "user", "content": user_message}],
    )
    latency = int((time.time() - start_time) * 1000)

    assistant_content = response.content[0].text

    # 6. Save the assistant response
    await save_message(
        ctx,
        conversation_id,
        "assistant",
        assistant_content,
        model_id="claude-3-5-sonnet-20241022",
        latency_ms=latency,
    )

    return assistant_content

# memory_isolation/api.py

security = HTTPBearer()

# In production, load from environment variables
JWT_SECRET = "your-jwt-secret-here"
JWT_ALGORITHM = "HS256"


def verify_jwt_token(token: str) -> dict:
    """
    Verify and decode a JWT token.
    In production, use asymmetric keys (RS256) and validate against
    your auth provider's JWKS endpoint.
    """
    try:
        payload = jwt.decode(token, JWT_SECRET, algorithms=[JWT_ALGORITHM])
        return payload
    except jwt.ExpiredSignatureError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Token has expired",
        )
    except jwt.InvalidTokenError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid token",
        )


async def get_current_user(
    credentials: Annotated[HTTPAuthorizationCredentials, Depends(security)],
) -> UserContext:
    """
    Dependency that extracts UserContext from a Bearer token.
    Every route that touches user data must declare this dependency.
    """
    payload = verify_jwt_token(credentials.credentials)

    # Your auth provider puts these claims in the JWT
    user_id_str = payload.get("sub")
    tenant_id_str = payload.get("tenant_id")
    is_admin = payload.get("is_tenant_admin", False)

    if not user_id_str or not tenant_id_str:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Token missing required claims",
        )

    try:
        user_id = uuid.UUID(user_id_str)
        tenant_id = uuid.UUID(tenant_id_str)
    except ValueError:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid user or tenant identifier in token",
        )

    return UserContext(
        user_id=user_id,
        tenant_id=tenant_id,
        is_tenant_admin=is_admin,
    )

12.6 Document Ingestion Pipeline with Isolated Embeddings

When users upload documents, the ingestion pipeline must associate every chunk and embedding with the correct user. Here is the complete upload and chunking flow:

# memory_isolation/ingestion.py

import uuid
import re
from typing import Optional

from sqlalchemy import text

from .database import UserContext, get_user_connection
from .memory_service import get_embedding


def chunk_text(
    text: str,
    chunk_size: int = 512,
    overlap: int = 64,
) -> list[str]:
    """
    Split text into overlapping chunks by token approximation.
    Uses whitespace tokenization; in production use tiktoken for accurate counts.
    """
    words = text.split()
    chunks = []
    start = 0

    while start < len(words):
        end = min(start + chunk_size, len(words))
        chunk = " ".join(words[start:end])
        chunks.append(chunk)

        if end >= len(words):
            break
        start += chunk_size - overlap

    return chunks


async def ingest_document(
    ctx: UserContext,
    filename: str,
    content: str,
    content_type: str = "text/plain",
    metadata: Optional[dict] = None,
) -> uuid.UUID:
    """
    Ingest a document into the user's private embedding space.
    
    Steps:
    1. Insert document record (RLS-protected)
    2. Chunk the text
    3. Generate embeddings for each chunk in batches
    4. Insert embeddings (RLS-protected)
    5. Update chunk count
    """
    document_id = uuid.uuid4()
    chunks = chunk_text(content)
    extra_metadata = metadata or {}

    async with get_user_connection(ctx) as conn:
        # Step 1: Insert document record
        await conn.execute(
            text("""
                INSERT INTO user_documents (
                    document_id, user_id, tenant_id,
                    filename, content_type, raw_content, metadata
                ) VALUES (
                    :doc_id, :user_id, :tenant_id,
                    :filename, :content_type, :content, :metadata
                )
            """),
            {
                "doc_id": str(document_id),
                "user_id": str(ctx.user_id),
                "tenant_id": str(ctx.tenant_id),
                "filename": filename,
                "content_type": content_type,
                "content": content,
                "metadata": extra_metadata,
            },
        )

        # Steps 2-4: Chunk, embed, and insert — batch for efficiency
        BATCH_SIZE = 20
        for batch_start in range(0, len(chunks), BATCH_SIZE):
            batch = chunks[batch_start: batch_start + BATCH_SIZE]
            # Generate all embeddings in this batch concurrently
            import asyncio
            embeddings = await asyncio.gather(
                *[get_embedding(chunk) for chunk in batch]
            )

            for idx, (chunk, embedding) in enumerate(zip(batch, embeddings)):
                chunk_index = batch_start + idx
                embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

                await conn.execute(
                    text("""
                        INSERT INTO user_embeddings (
                            document_id, user_id, tenant_id,
                            chunk_index, chunk_text, embedding,
                            token_count, metadata
                        ) VALUES (
                            :doc_id, :user_id, :tenant_id,
                            :chunk_index, :chunk_text, :embedding::vector,
                            :token_count, :metadata
                        )
                    """),
                    {
                        "doc_id": str(document_id),
                        "user_id": str(ctx.user_id),
                        "tenant_id": str(ctx.tenant_id),
                        "chunk_index": chunk_index,
                        "chunk_text": chunk,
                        "embedding": embedding_str,
                        "token_count": len(chunk.split()),
                        "metadata": {"filename": filename, **extra_metadata},
                    },
                )

        # Step 5: Update chunk count
        await conn.execute(
            text("""
                UPDATE user_documents
                SET chunk_count = :count
                WHERE document_id = :doc_id
            """),
            {"count": len(chunks), "doc_id": str(document_id)},
        )

    return document_id

The entire ingestion happens within a single get_user_connection transaction context. If embedding generation fails partway through, the transaction rolls back and no partial document record is left in the database. The user_id and tenant_id are explicitly passed on every insert even though RLS would reject mismatched values — this is defense in depth: the application layer's explicit assignments plus the database layer's policy enforcement.

12.7 Memory Compaction: Episodic Summaries Across Sessions

Long-running AI applications accumulate message history that exceeds context windows. The standard solution is episodic summarization — periodically compress conversation history into durable summaries that persist in memory_summaries. Here is the compaction pipeline:

# memory_isolation/compaction.py

import uuid
from typing import Optional

from sqlalchemy import text
from anthropic import AsyncAnthropic

from .database import UserContext, get_user_connection

anthropic_client = AsyncAnthropic()

COMPACTION_PROMPT = """You are summarizing a conversation to create a long-term memory record.

Extract and preserve:
1. KEY FACTS: Specific facts about the user (name, preferences, role, goals, constraints)
2. DECISIONS: Important decisions made during the conversation  
3. CONTEXT: Background information that will be needed in future conversations
4. UNRESOLVED: Open questions or pending items

Format as:
SUMMARY: [2-4 sentence narrative summary]
KEY_FACTS: [JSON array of {"fact": "...", "category": "preference|identity|context|decision"}]

Be precise. Omit pleasantries and filler. This summary will be used to maintain continuity."""


async def compact_conversation(
    ctx: UserContext,
    conversation_id: uuid.UUID,
    min_messages: int = 30,
) -> Optional[uuid.UUID]:
    """
    Compress a conversation's message history into an episodic summary.
    Only compacts if the conversation has more than min_messages turns.
    Returns the summary_id if compaction occurred, None otherwise.
    """
    async with get_user_connection(ctx) as conn:
        # Get message count for this conversation
        count_result = await conn.execute(
            text("""
                SELECT COUNT(*) as msg_count
                FROM messages
                WHERE conversation_id = :conv_id
            """),
            {"conv_id": str(conversation_id)},
        )
        count_row = count_result.fetchone()
        if not count_row or count_row.msg_count < min_messages:
            return None

        # Retrieve messages for summarization (older portion, not the most recent 10)
        messages_result = await conn.execute(
            text("""
                SELECT role, content
                FROM messages
                WHERE conversation_id = :conv_id
                ORDER BY created_at ASC
                LIMIT (
                    SELECT GREATEST(COUNT(*) - 10, 0)
                    FROM messages WHERE conversation_id = :conv_id
                )
            """),
            {"conv_id": str(conversation_id)},
        )
        rows = messages_result.fetchall()

    if not rows:
        return None

    # Format messages for the summarization LLM
    conversation_text = "\n".join(
        f"{row.role.upper()}: {row.content[:500]}" for row in rows
    )

    # Generate episodic summary using Claude
    response = await anthropic_client.messages.create(
        model="claude-3-5-sonnet-20241022",
        max_tokens=1024,
        system=COMPACTION_PROMPT,
        messages=[
            {
                "role": "user",
                "content": f"Summarize this conversation:\n\n{conversation_text}",
            }
        ],
    )

    summary_text = response.content[0].text

    # Parse key facts from the structured output
    import json
    import re

    key_facts = []
    facts_match = re.search(r"KEY_FACTS:\s*(\[.*?\])", summary_text, re.DOTALL)
    if facts_match:
        try:
            key_facts = json.loads(facts_match.group(1))
        except json.JSONDecodeError:
            key_facts = []

    # Store the summary — RLS ensures it's attributed to the correct user
    summary_id = uuid.uuid4()
    async with get_user_connection(ctx) as conn:
        await conn.execute(
            text("""
                INSERT INTO memory_summaries (
                    summary_id, user_id, tenant_id,
                    conversation_id, summary_text, key_facts, importance
                ) VALUES (
                    :summary_id, :user_id, :tenant_id,
                    :conv_id, :summary_text, :key_facts::jsonb, :importance
                )
            """),
            {
                "summary_id": str(summary_id),
                "user_id": str(ctx.user_id),
                "tenant_id": str(ctx.tenant_id),
                "conv_id": str(conversation_id),
                "summary_text": summary_text,
                "key_facts": json.dumps(key_facts),
                "importance": 0.7,  # Default importance; can be ML-scored later
            },
        )

    return summary_id


async def retrieve_relevant_summaries(
    ctx: UserContext,
    current_query: str,
    limit: int = 3,
) -> list[dict]:
    """
    Retrieve memory summaries most relevant to the current conversation.
    Filters by importance and recency; does not use vector similarity here
    (summaries are short enough that keyword matching is often sufficient).
    For large summary collections, add an embedding column to memory_summaries.
    """
    async with get_user_connection(ctx) as conn:
        result = await conn.execute(
            text("""
                SELECT summary_id, summary_text, key_facts, importance, created_at
                FROM memory_summaries
                WHERE (valid_until IS NULL OR valid_until > NOW())
                ORDER BY importance DESC, created_at DESC
                LIMIT :limit
            """),
            {"limit": limit},
        )
        rows = result.fetchall()

    return [
        {
            "summary_id": str(row.summary_id),
            "summary_text": row.summary_text,
            "key_facts": row.key_facts or [],
            "importance": float(row.importance),
            "created_at": row.created_at.isoformat(),
        }
        for row in rows
    ]

async def test_rls_context_not_set():
    """

    This tests that RLS fails closed, not open.
    """
    engine = create_async_engine(TEST_DB_URL)
    async with engine.connect() as conn:
        # Deliberately do NOT call set_user_context
        try:
            result = await conn.execute(text("SELECT COUNT(*) FROM conversations"))
            count = result.scalar()
            # If RLS is working, this should either raise an error
            # or return 0 (because current_setting returns empty string)
            # Either outcome is acceptable; data must not leak
            assert count == 0 or count is None, (

            # This is also acceptable — fail closed
            pass

The final test, test_rls_context_not_set, verifies fail-closed behavior. If someone bypasses the get_user_connection context manager and executes a query on a raw connection, the policy using current_setting('app.current_user_id') will either raise a PostgreSQL error (because the setting does not exist) or return no rows (because an empty string does not match any UUID). Both are correct outcomes. You can make this explicitly fail-closed by setting a default:

-- Fail-closed default: unset context matches no user
ALTER DATABASE ai_production SET app.current_user_id = '00000000-0000-0000-0000-000000000000';
ALTER DATABASE ai_production SET app.current_tenant_id = '00000000-0000-0000-0000-000000000000';
ALTER DATABASE ai_production SET app.is_tenant_admin = 'false';

With these defaults, any connection that forgets to set context sees an unmatched nil UUID and gets zero rows across every RLS-protected table.

12.9 SQL Server Equivalent: Memory Isolation with Row-Level Security

SQL Server (Azure SQL Database, SQL Server 2016+) has Row Level Security as a first-class feature with a nearly identical mental model to PostgreSQL's. The main differences are: SQL Server uses inline table-valued functions as security predicates rather than boolean expressions; context is passed via SESSION_CONTEXT rather than set_config; and SECURITY_DEFINER is replaced by schema binding and execution context.

-- SQL Server equivalent schema

-- Users table (SQL Server syntax)
CREATE TABLE dbo.users (
    user_id         UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    external_id     NVARCHAR(256) NOT NULL UNIQUE,
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    email           NVARCHAR(256),
    display_name    NVARCHAR(256),
    memory_tier     NVARCHAR(50) NOT NULL DEFAULT 'standard'
                        CHECK (memory_tier IN ('standard', 'extended', 'unlimited')),
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    is_active       BIT NOT NULL DEFAULT 1
);

-- Conversations table
CREATE TABLE dbo.conversations (
    conversation_id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    user_id         UNIQUEIDENTIFIER NOT NULL REFERENCES dbo.users(user_id),
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    title           NVARCHAR(500),
    model_id        NVARCHAR(100) NOT NULL DEFAULT 'claude-3-5-sonnet-20241022',
    system_prompt   NVARCHAR(MAX),
    token_count     INT NOT NULL DEFAULT 0,
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    updated_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    archived_at     DATETIMEOFFSET
);

-- Messages table
CREATE TABLE dbo.messages (
    message_id      UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    conversation_id UNIQUEIDENTIFIER NOT NULL REFERENCES dbo.conversations(conversation_id),
    user_id         UNIQUEIDENTIFIER NOT NULL REFERENCES dbo.users(user_id),
    tenant_id       UNIQUEIDENTIFIER NOT NULL,
    role            NVARCHAR(20) NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool')),
    content         NVARCHAR(MAX) NOT NULL,
    model_id        NVARCHAR(100),
    latency_ms      INT,
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET()
);

-- Set user context using SESSION_CONTEXT (SQL Server 2016+)
-- Call this stored procedure at the start of every session/transaction
CREATE OR ALTER PROCEDURE dbo.SetUserContext
    @user_id        UNIQUEIDENTIFIER,
    @tenant_id      UNIQUEIDENTIFIER,
    @is_tenant_admin BIT = 0
AS
BEGIN
    SET NOCOUNT ON;
    EXEC sp_set_session_context @key = N'current_user_id',    @value = @user_id,        @read_only = 0;
    EXEC sp_set_session_context @key = N'current_tenant_id',  @value = @tenant_id,      @read_only = 0;
    EXEC sp_set_session_context @key = N'is_tenant_admin',    @value = @is_tenant_admin, @read_only = 0;
END;
GO

-- Security predicate function for conversations
-- SQL Server RLS uses inline TVFs, not boolean expressions
CREATE OR ALTER FUNCTION dbo.fn_conversations_predicate(@user_id UNIQUEIDENTIFIER, @tenant_id UNIQUEIDENTIFIER)
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS result
    WHERE
        -- Row belongs to the current user
        @user_id = CONVERT(UNIQUEIDENTIFIER, SESSION_CONTEXT(N'current_user_id'))
        OR (
            -- OR: tenant admin accessing their own tenant's rows
            @tenant_id = CONVERT(UNIQUEIDENTIFIER, SESSION_CONTEXT(N'current_tenant_id'))
            AND CONVERT(BIT, SESSION_CONTEXT(N'is_tenant_admin')) = 1
        );
GO

-- Apply filter predicate to conversations (SELECT, UPDATE, DELETE)

The BLOCK PREDICATE variants in SQL Server map to PostgreSQL's WITH CHECK clause — they prevent INSERT and UPDATE operations that would create rows the current principal cannot see. SQL Server distinguishes AFTER INSERT and AFTER UPDATE blocks explicitly; PostgreSQL's WITH CHECK covers both. The functional result is identical: you cannot write a row into a table if you would not be able to read it back.

For vector similarity search in SQL Server, the native option as of SQL Server 2025 is the VECTOR data type with built-in distance functions. For earlier versions, Azure SQL Database supports vector search through its preview vector type. The SQL Server equivalent of the search_user_memory function follows the same logical structure — UNION of a private embeddings query and a shared knowledge query — with vectors stored as VECTOR(1536) and distance computed via VECTOR_DISTANCE('cosine', embedding, @query_embedding):

-- Combined semantic search stored procedure
CREATE OR ALTER PROCEDURE dbo.SearchUserMemory
    @query_embedding    VECTOR(1536),
    @limit              INT = 5,
    @threshold          FLOAT = 0.7
AS
BEGIN
    SET NOCOUNT ON;

    SELECT TOP (@limit)
        source,
        chunk_text,
        similarity,
        metadata
    FROM (
        -- Private user embeddings (RLS filters to current user automatically)
        SELECT
            N'private' AS source,
            ue.chunk_text,
            1.0 - VECTOR_DISTANCE('cosine', ue.embedding, @query_embedding) AS similarity,
            N'{}' AS metadata
        FROM dbo.user_embeddings ue
        WHERE 1.0 - VECTOR_DISTANCE('cosine', ue.embedding, @query_embedding) >= @threshold

        UNION ALL

        -- Shared knowledge (RLS filters to current tenant + global)
        SELECT
            N'shared' AS source,
            sk.chunk_text,
            1.0 - VECTOR_DISTANCE('cosine', sk.embedding, @query_embedding) AS similarity,
            N'{}' AS metadata
        FROM dbo.shared_knowledge sk
        WHERE 1.0 - VECTOR_DISTANCE('cosine', sk.embedding, @query_embedding) >= @threshold
    ) combined
    ORDER BY similarity DESC;
END;
GO

One important SQL Server nuance: SESSION_CONTEXT values survive connection pool reuse just as PostgreSQL's set_config session-local values do. When using connection pooling middleware (such as SQL Server's built-in pooling or an external proxy), you must call dbo.SetUserContext at the start of every transaction, not just at connection establishment. The pattern is identical to what was described for PostgreSQL with PgBouncer.

12.10 Operational Considerations: Monitoring and Auditing Isolation

Isolation that you cannot observe is isolation you cannot trust. These are the monitoring patterns that tell you your policies are working and alert you when something unusual happens.

async def get_conversation_context(
    ctx: UserContext,
    conversation_id: uuid.UUID,
    max_messages: int = 20,
) -> list[dict]:
    async with get_user_connection(ctx) as conn:
        result = await conn.execute(
            text("""
                SELECT role, content, tool_calls, tool_results, created_at
                FROM messages
                WHERE conversation_id = :conv_id
                ORDER BY created_at DESC
                LIMIT :limit
            """),
            {"conv_id": str(conversation_id), "limit": max_messages},
        )
        rows = result.fetchall()

        # Log zero-result accesses to existing conversations — potential probing
        if not rows:
            await conn.execute(
                text("""
                    SELECT record_access_attempt(
                        'READ_CONVERSATION',
                        :resource_id::UUID,
                        0,
                        :details::jsonb
                    )
                """),
                {
                    "resource_id": str(conversation_id),
                    "details": '{"note": "zero_results_may_indicate_cross_user_probe"}',
                },
            )

    messages = []
    for row in reversed(rows):
        msg = {"role": row.role, "content": row.content}
        if row.tool_calls:
            msg["tool_calls"] = row.tool_calls
        messages.append(msg)

    return messages

Monitoring queries for isolation health:

-- Find users with unusually high zero-result conversation access attempts
-- (possible enumeration attack or application bug)
SELECT
    user_id,
    COUNT(*) AS zero_result_attempts,
    MIN(occurred_at) AS first_seen,
    MAX(occurred_at) AS last_seen
FROM audit_log
WHERE
    operation = 'READ_CONVERSATION'
    AND result_count = 0
    AND occurred_at > NOW() - INTERVAL '24 hours'
GROUP BY user_id
HAVING COUNT(*) > 10
ORDER BY zero_result_attempts DESC;

-- Verify RLS policies are enabled on all user-data tables
SELECT
    schemaname,
    tablename,
    rowsecurity AS rls_enabled,
    forcerowsecurity AS rls_forced
FROM pg_tables
WHERE schemaname = 'public'
    AND tablename IN (
        'conversations', 'messages', 'memory_summaries',
        'user_documents', 'user_embeddings', 'shared_knowledge'
    )
ORDER BY tablename;

-- List all active RLS policies
SELECT
    schemaname,
    tablename,
    policyname,
    permissive,
    roles,
    cmd,
    qual,
    with_check
FROM pg_policies
WHERE schemaname = 'public'
ORDER BY tablename, policyname;

The policy listing query is particularly useful during deployment validation. Running it after a schema migration confirms that newly created tables have their policies correctly attached before the application starts routing traffic to them.

Key Takeaways

  • → **Row Level Security enforces isolation at the database layer**, making data leakage impossible regardless of application-layer bugs. The pattern — set user context via `set_config` (PostgreSQL) or `SESSION_CONTEXT` (SQL Server) at transaction start, define policies that reference that context — is the same in both systems and should be the default architecture for any multi-user AI application.
  • → **Vector search isolation requires explicit attention**. pgvector's approximate nearest-neighbor search has no awareness of tenancy; RLS policies on the embeddings table are what confine similarity queries to a single user's private space. The `search_user_memory` function demonstrates how RLS and semantic search compose cleanly: the function expresses query shape, the policy engine enforces boundaries.
  • → **The `get_user_connection` context manager is the security perimeter**. Every database interaction in the application must flow through it. Setting fail-closed database defaults (`app.current_user_id = nil UUID`) ensures that any code path that bypasses context-setting sees zero rows rather than all rows.
  • → **Episodic summarization and memory compaction must carry user identity through every step**. Summaries are as privacy-sensitive as raw messages; the `memory_summaries` table uses the strictest RLS variant (per-user only, no tenant admin override) to reflect this. Compaction pipelines must use the same `UserContext`-aware connection patterns as interactive request handlers.
  • → **Isolation is a property that must be tested and monitored**, not assumed. The test suite in section 12.8 specifically exercises cross-user and cross-tenant leakage scenarios; the audit logging pattern in section 12.10 surfaces zero-result probing attempts that may indicate application bugs or adversarial enumeration. Combine schema-level enforcement with behavioral monitoring to maintain confidence in isolation guarantees over time.
