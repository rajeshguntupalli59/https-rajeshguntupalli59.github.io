Chapter 13: pgvector on RDS, Aurora, AlloyDB, and Supabase

Running pgvector in production rarely means spinning up a raw EC2 instance and compiling the extension by hand. Most teams arrive at vector search through the managed PostgreSQL services they already operate—Amazon RDS, Amazon Aurora, Google AlloyDB, or Supabase—and they need to know exactly what each platform delivers, what it costs, and where the walls are. This chapter maps pgvector's behavior across all four environments: how to enable it, how to tune it, where each platform diverges from vanilla PostgreSQL, and how to architect a production embedding pipeline that survives traffic spikes, schema migrations, and the cost pressure that follows any successful AI feature launch.

---

13.1 Platform Landscape: What You're Actually Getting

Before touching a single SQL statement, understand what managed pgvector actually means across these four providers.

Amazon RDS for PostgreSQL added pgvector support in October 2023 for PostgreSQL 15.x and later, and backported it to 14.x and 13.x shortly after. You get the standard pgvector extension installed by the engine—no custom builds, no OS-level access. The version you get is whatever RDS has packaged; you cannot upgrade the extension independently of the engine minor version. As of mid-2024, RDS ships pgvector 0.6.x on PostgreSQL 15 and 0.7.x on PostgreSQL 16. This matters because HNSW index support landed in pgvector 0.5.0, and the halfvec and bit types for memory-efficient storage arrived in 0.7.0.

Amazon Aurora PostgreSQL-Compatible shares the same extension packaging as RDS but adds Aurora-specific behavior: storage auto-scaling, the Aurora parallel query engine, and Global Database replication. Vector data lives in Aurora's distributed storage layer, which means your HNSW index pages are stored across the distributed volume rather than local disk—a meaningful difference when reasoning about index build I/O and buffer pool pressure.

Google AlloyDB is Google's PostgreSQL-compatible managed service with a disaggregated storage architecture and a built-in columnar engine. AlloyDB added pgvector support in 2023 and additionally offers google_ml_integration, which lets you call Vertex AI embedding models directly from SQL. The columnar engine can accelerate certain vector workload patterns—specifically full-table scans during exact KNN searches on small-to-medium datasets—in ways that standard PostgreSQL storage cannot.

Supabase is a developer-focused platform built on PostgreSQL with pgvector pre-enabled on every project. Supabase wraps the database with a REST API layer (PostgREST), a real-time subscription engine, and a JavaScript/Python SDK that integrates directly with vector operations. This makes Supabase the fastest path from zero to a working vector search endpoint, but the tradeoff is reduced control over low-level PostgreSQL configuration parameters that matter at scale—work_mem, effective_cache_size, and maintenance_work_mem are not directly tunable on the free and Pro tiers.

The following table summarizes the key operational differences:

| Feature | RDS PostgreSQL | Aurora PostgreSQL | AlloyDB | Supabase |

|---|---|---|---|---|

| pgvector version control | Engine-tied | Engine-tied | Engine-tied | Engine-tied |

| HNSW support | ✓ (PG 15+) | ✓ (PG 15+) | ✓ | ✓ |

| halfvec type | ✓ (PG 16+) | ✓ (PG 16+) | ✓ | ✓ |

| Max dimensions | 16,000 | 16,000 | 16,000 | 16,000 |

| Direct ML integration | ❌ | ❌ | Vertex AI | ❌ |

| PostgREST API | ❌ | ❌ | ❌ | ✓ |

| Custom GUC tuning | Full | Full | Partial | Limited |

| Read replicas for search | ✓ | ✓ (serverless optional) | ✓ | ✓ (paid tiers) |

13.2 Enabling pgvector and Schema Design on Managed Services

Enabling the extension follows the same SQL command on all four platforms, but the prerequisites differ.

On RDS and Aurora, you need to be connected as the master user or a user with the rds_superuser role:

-- PostgreSQL / pgvector
-- Run as master user (e.g., postgres or your RDS master username)
CREATE EXTENSION IF NOT EXISTS vector;

-- Verify version
SELECT extversion FROM pg_extension WHERE extname = 'vector';
-- Returns: 0.7.0 (or whatever RDS has packaged)

On AlloyDB, the extension is pre-loaded in the shared library. Enable it the same way, but note that google_ml_integration must also be enabled to use the ML embedding functions:

-- PostgreSQL / pgvector (AlloyDB)
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS google_ml_integration;

-- Grant the AlloyDB service account access to Vertex AI
-- (Done in GCP IAM, not SQL — the AlloyDB instance's service account
--  needs roles/aiplatform.user on the project)

-- Test a Vertex AI embedding call directly from SQL
SELECT google_ml.embedding(
    'textembedding-gecko@003',
    'What is the boiling point of water?'
)::vector(768);

On Supabase, the extension is already enabled. Connect via the Supabase dashboard's SQL editor or any PostgreSQL client using the connection string from your project settings:

-- PostgreSQL / pgvector (Supabase — extension already active)
-- Verify it's available
SELECT extversion FROM pg_extension WHERE extname = 'vector';

-- Create a table for document embeddings
CREATE TABLE documents (
    id          BIGSERIAL PRIMARY KEY,
    content     TEXT NOT NULL,
    metadata    JSONB,
    embedding   VECTOR(1536),  -- OpenAI text-embedding-ada-002 dimensions
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

Schema design decisions that matter at production scale:

The dimension count is fixed at column definition time. If you switch embedding models—which happens more often than teams expect—you need to add a new column or rebuild the table. Design for this from the start by keeping the embedding model name in metadata:

-- PostgreSQL / pgvector
CREATE TABLE document_embeddings (
    id              BIGSERIAL PRIMARY KEY,
    document_id     BIGINT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    model_name      TEXT NOT NULL,           -- 'text-embedding-ada-002', 'embed-english-v3.0', etc.
    model_version   TEXT NOT NULL,           -- track model versions explicitly
    embedding       VECTOR(1536),
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (document_id, model_name, model_version)
);

-- Partial index to serve only the current production model
-- without filtering overhead on every query
CREATE INDEX ON document_embeddings (model_name, model_version)
    WHERE model_name = 'text-embedding-ada-002' AND model_version = '002';

For large tables where you want memory efficiency, use halfvec (available in pgvector 0.7.0+) to halve the storage footprint at the cost of marginally reduced precision—typically less than 0.5% recall loss on standard benchmarks:

-- PostgreSQL / pgvector
-- halfvec uses 2 bytes per dimension vs 4 bytes for vector
ALTER TABLE document_embeddings
    ADD COLUMN embedding_half halfvec(1536);

-- Cast from full precision if migrating
UPDATE document_embeddings
    SET embedding_half = embedding::halfvec(1536)
    WHERE model_name = 'text-embedding-ada-002';

13.3 Index Strategy: HNSW vs. IVFFlat on Managed Infrastructure

Managed PostgreSQL adds constraints that change the optimal index choice compared to self-hosted deployments. You cannot tune kernel memory parameters, cannot pin HNSW graphs in OS-level hugepages, and you're competing with the rest of your workload for shared buffer space.

IVFFlat builds faster and consumes less memory during construction, but requires a training step (clustering) that scans the entire table. On Aurora, this clustering scan goes through the distributed storage layer and generates significant I/O that competes with OLTP traffic. On a 10M-row embeddings table, an IVFFlat build with lists = 1000 can run 2–4 hours on a db.r6g.2xlarge and consume the majority of I/O throughput during that window.

HNSW builds more slowly in wall-clock time and requires substantial maintenance_work_mem during construction (plan for 4–8 GB for a million 1536-dimensional vectors), but it requires no training data and delivers better recall at equivalent query latency. It's the right default for production on managed services unless you're constrained on build-time memory.

-- PostgreSQL / pgvector
-- HNSW index for cosine similarity (typical for OpenAI and Cohere embeddings)
-- Set maintenance_work_mem high before building
SET maintenance_work_mem = '8GB';

CREATE INDEX CONCURRENTLY idx_embeddings_hnsw
    ON document_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 128);

-- m = 16: connections per node in the graph (higher = better recall, more memory)
-- ef_construction = 128: candidate list size during build
--   (higher = better recall, slower build)

-- For query time, set ef_search on the session or transaction:
SET hnsw.ef_search = 100;  -- default is 40; increase for better recall at cost of latency

-- Verify index is being used
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, content, 1 - (embedding <=> '[0.1, 0.2, ...]'::vector) AS similarity
FROM document_embeddings
WHERE model_name = 'text-embedding-ada-002'
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;

On RDS Multi-AZ and Aurora, CREATE INDEX CONCURRENTLY is strongly preferred over a blocking index build—the index can be built without holding an exclusive lock on the table, which matters when your embeddings table is being written to by an ingestion pipeline. The concurrency trade-off is a longer build time (typically 20–40% more wall clock) and the requirement that no transaction runs for the duration of the build.

AlloyDB columnar engine deserves a specific note here. For exact KNN search (no approximate index, full table scan with ORDER BY distance LIMIT k), AlloyDB's columnar engine can execute the distance computation in vectorized batches that outperform row-by-row execution by 3–10x on tables up to roughly 500K rows. Beyond that threshold, approximate index search with HNSW will consistently beat even the columnar engine, so treat the columnar path as an optimization for smaller "hot" tables, not a replacement for index design:

-- PostgreSQL / pgvector (AlloyDB specific)
-- Enable columnar scan hint for a specific query
-- AlloyDB uses its columnar engine automatically for eligible scans,
-- but you can check with EXPLAIN

EXPLAIN (ANALYZE, FORMAT TEXT)
SELECT id, 1 - (embedding <=> $1::vector) AS similarity
FROM document_embeddings
ORDER BY embedding <=> $1::vector
LIMIT 20;
-- Look for "Columnar Scan" in the plan output — indicates AlloyDB's engine
-- is handling the distance computation in vectorized form

13.4 Ingestion Pipelines: Embedding Generation and Bulk Loading

The vector search index is only as good as the embeddings feeding it. On managed services, the ingestion pipeline sits outside the database and must handle embedding API rate limits, model versioning, failure recovery, and bulk insert efficiency.

The following Python pipeline handles document ingestion against a Supabase or RDS/Aurora backend, using the OpenAI Embeddings API and batch-aware upsert logic:

# Python
import os
import time
import psycopg2
import psycopg2.extras
from openai import OpenAI
from typing import Generator

openai_client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

# Connection string from environment — works for RDS, Aurora, AlloyDB, or Supabase
# For Supabase, use the "direct connection" string (port 5432), not the connection pooler,
# for bulk inserts to avoid pgBouncer transaction-mode limitations with COPY
DB_DSN = os.environ["DATABASE_URL"]

def chunk_documents(documents: list[dict], chunk_size: int = 500) -> Generator:
    """Yield successive chunks of documents with basic token-aware splitting."""
    for doc in documents:
        text = doc["content"]
        # Simple word-count chunking — replace with tiktoken-aware chunking in production
        words = text.split()
        for i in range(0, len(words), chunk_size):
            chunk_text = " ".join(words[i:i + chunk_size])
            yield {
                "document_id": doc["id"],
                "content": chunk_text,
                "chunk_index": i // chunk_size,
                "metadata": doc.get("metadata", {}),
            }

def generate_embeddings_batch(
    texts: list[str],
    model: str = "text-embedding-3-small",
    max_retries: int = 3
) -> list[list[float]]:
    """
    Call OpenAI Embeddings API with exponential backoff.
    text-embedding-3-small: 1536 dims, $0.02/1M tokens
    text-embedding-3-large: 3072 dims, $0.13/1M tokens
    text-embedding-ada-002: 1536 dims, $0.10/1M tokens (legacy)
    """
    for attempt in range(max_retries):
        try:
            response = openai_client.embeddings.create(
                input=texts,
                model=model,
                encoding_format="float"
            )
            return [item.embedding for item in response.data]
        except Exception as e:
            if attempt == max_retries - 1:
                raise
            wait = 2 ** attempt
            print(f"Embedding API error (attempt {attempt + 1}): {e}. Retrying in {wait}s.")
            time.sleep(wait)

def ingest_documents(documents: list[dict], batch_size: int = 100) -> int:
    """
    Ingest documents into pgvector with batch embedding and upsert.
    Returns count of rows inserted/updated.
    """
    conn = psycopg2.connect(DB_DSN)
    conn.autocommit = False

    upsert_sql = """
        INSERT INTO document_embeddings
            (document_id, model_name, model_version, embedding, chunk_index, chunk_text)
        VALUES %s
        ON CONFLICT (document_id, model_name, model_version, chunk_index)
        DO UPDATE SET
            embedding = EXCLUDED.embedding,
            chunk_text = EXCLUDED.chunk_text,
            updated_at = NOW()
    """

    total_inserted = 0
    batch: list[dict] = []

    try:
        with conn.cursor() as cur:
            for chunk in chunk_documents(documents):
                batch.append(chunk)

                if len(batch) >= batch_size:
                    texts = [c["content"] for c in batch]
                    embeddings = generate_embeddings_batch(texts)

                    rows = [
                        (
                            c["document_id"],
                            "text-embedding-3-small",
                            "3-small-v1",
                            embedding,  # psycopg2 will serialize list to vector literal
                            c["chunk_index"],
                            c["content"],
                        )
                        for c, embedding in zip(batch, embeddings)
                    ]

                    psycopg2.extras.execute_values(
                        cur, upsert_sql, rows, page_size=batch_size
                    )
                    total_inserted += len(rows)
                    conn.commit()
                    print(f"Committed batch of {len(rows)} rows. Total: {total_inserted}")
                    batch = []

            # Flush remaining
            if batch:
                texts = [c["content"] for c in batch]
                embeddings = generate_embeddings_batch(texts)
                rows = [
                    (c["document_id"], "text-embedding-3-small", "3-small-v1",
                     embedding, c["chunk_index"], c["content"])
                    for c, embedding in zip(batch, embeddings)
                ]
                psycopg2.extras.execute_values(cur, upsert_sql, rows)
                total_inserted += len(rows)
                conn.commit()

    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()

    return total_inserted

One pattern worth calling out explicitly: never embed inside a database transaction that also holds row locks. If the OpenAI API call takes 800ms and you're holding a lock on a row you just inserted, you've introduced an 800ms lock wait for any concurrent writer touching the same document. Always generate embeddings before opening the transaction, then insert or upsert atomically.

13.5 Query Patterns, Connection Pooling, and Performance Tuning

Vector similarity queries have a shape that differs from typical OLTP queries: they're read-heavy, they frequently run against large tables with selective WHERE clauses, and they benefit significantly from connection routing to read replicas. This section covers the tuning knobs that actually move the needle on managed services.

Query structure for hybrid search — combining vector similarity with metadata filters—is one of the most common production patterns:

-- PostgreSQL / pgvector
-- Hybrid search: semantic similarity + metadata filter + recency boost
-- This is the pattern used in most production RAG pipelines

SET hnsw.ef_search = 80;  -- tune per-query based on latency/recall requirements

SELECT
    de.id,
    de.chunk_text,
    d.title,
    d.source_url,
    d.published_at,
    1 - (de.embedding <=> $1::vector(1536)) AS semantic_score,
    -- Recency boost: decays over 90 days
    EXP(-EXTRACT(EPOCH FROM (NOW() - d.published_at)) / (90 * 86400)) AS recency_score,
    -- Combined score
    (0.7 * (1 - (de.embedding <=> $1::vector(1536))))
    + (0.3 * EXP(-EXTRACT(EPOCH FROM (NOW() - d.published_at)) / (90 * 86400)))
    AS combined_score
FROM document_embeddings de
JOIN documents d ON d.id = de.document_id
WHERE
    de.model_name = 'text-embedding-3-small'
    AND de.model_version = '3-small-v1'
    AND d.tenant_id = $2          -- partition by tenant for SaaS architectures
    AND d.category = ANY($3)      -- optional category filter passed as text[]
ORDER BY combined_score DESC
LIMIT 10;

-- Index to support the metadata filters efficiently
-- Create this before the HNSW index — the planner will use it for filter pushdown
CREATE INDEX idx_docs_tenant_category ON documents (tenant_id, category);
CREATE INDEX idx_embeddings_model ON document_embeddings (model_name, model_version);

Connection pooling considerations on managed services:

RDS and Aurora benefit from RDS Proxy for connection pooling at the infrastructure level. RDS Proxy uses connection multiplexing but switches to session mode when prepared statements are used—pgvector queries typically use parameterized queries with $1::vector, which counts as a prepared statement pattern. This can inadvertently increase actual backend connection counts. Monitor DatabaseConnections in CloudWatch alongside DBConnectionsCurrentlyBorrowed on the proxy to detect this.

Supabase exposes two connection strings: one through Supavisor (their connection pooler, transaction mode) and one direct to PostgreSQL. For vector ingestion pipelines using COPY or multi-statement transactions, always use the direct connection string on port 5432, not the pooler on port 6543. Transaction-mode poolers will fail or misbehave on COPY and explicit transaction blocks.

Partition strategy for large embedding tables: On Aurora and RDS, if your embeddings table exceeds ~50M rows, partitioning by a hash of document_id improves HNSW index build parallelism (each partition builds its own index) and makes individual partition vacuums faster:

-- PostgreSQL / pgvector
-- Range partition by creation date for time-series workloads,
-- or hash partition for even distribution across tenants

CREATE TABLE document_embeddings (
    id              BIGSERIAL,
    document_id     BIGINT NOT NULL,
    model_name      TEXT NOT NULL,
    model_version   TEXT NOT NULL,
    embedding       VECTOR(1536),
    chunk_text      TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- Create monthly partitions
CREATE TABLE document_embeddings_2024_01
    PARTITION OF document_embeddings
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE document_embeddings_2024_02
    PARTITION OF document_embeddings
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Each partition gets its own HNSW index
CREATE INDEX ON document_embeddings_2024_01
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

CREATE INDEX ON document_embeddings_2024_02
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

Autovacuum and bloat are significant concerns with high-ingestion embedding tables. Each new embedding is an INSERT, not an UPDATE, which keeps bloat lower than update-heavy workloads—but re-embedding existing documents (when you switch models) generates dead tuples at the rate of your ingestion pipeline. Set aggressive autovacuum parameters on the embeddings table:

-- PostgreSQL / pgvector
ALTER TABLE document_embeddings SET (
    autovacuum_vacuum_scale_factor = 0.01,   -- vacuum when 1% of rows are dead (default: 20%)
    autovacuum_analyze_scale_factor = 0.005, -- analyze when 0.5% of rows change
    autovacuum_vacuum_cost_delay = 2         -- reduce cost delay for this table
);

Supabase-specific query path via PostgREST: For applications using the Supabase client library, vector search runs through a PostgreSQL function exposed via PostgREST:

# Python
# Supabase vector search using the Python client
# The match_documents function encapsulates the similarity query
from supabase import create_client, Client
import os

url: str = os.environ["SUPABASE_URL"]
key: str = os.environ["SUPABASE_ANON_KEY"]

supabase: Client = create_client(url, key)

def search_documents(
    query_embedding: list[float],
    match_threshold: float = 0.78,
    match_count: int = 10,
    tenant_id: int = None
) -> list[dict]:
    """
    Calls a Supabase RPC function that performs vector similarity search.
    The function must be created in the database first (see SQL below).
    """
    params = {
        "query_embedding": query_embedding,
        "match_threshold": match_threshold,
        "match_count": match_count,
    }
    if tenant_id is not None:
        params["filter_tenant_id"] = tenant_id

    result = supabase.rpc("match_documents", params).execute()
    return result.data

The corresponding PostgreSQL function that PostgREST exposes:

-- PostgreSQL / pgvector (Supabase)
CREATE OR REPLACE FUNCTION match_documents(
    query_embedding    VECTOR(1536),
    match_threshold    FLOAT DEFAULT 0.78,
    match_count        INT   DEFAULT 10,
    filter_tenant_id   BIGINT DEFAULT NULL
)
RETURNS TABLE (
    id            BIGINT,
    chunk_text    TEXT,
    similarity    FLOAT,
    metadata      JSONB
)
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY
    SELECT
        de.id,
        de.chunk_text,
        1 - (de.embedding <=> query_embedding) AS similarity,
        d.metadata
    FROM document_embeddings de
    JOIN documents d ON d.id = de.document_id
    WHERE
        de.model_name = 'text-embedding-3-small'
        AND de.model_version = '3-small-v1'
        AND (filter_tenant_id IS NULL OR d.tenant_id = filter_tenant_id)
        AND 1 - (de.embedding <=> query_embedding) > match_threshold
    ORDER BY de.embedding <=> query_embedding
    LIMIT match_count;
END;
$$;

-- Grant execute permission to the anon and authenticated roles
GRANT EXECUTE ON FUNCTION match_documents TO anon, authenticated;

One important detail: the match_threshold filter (1 - (embedding <=> query_embedding) > threshold) is evaluated *after* the HNSW index scans its candidate list. It does not pre-filter the index scan. If your threshold is very high (e.g., 0.95), you may get fewer than match_count results even though matching rows exist in the table—because the index returned only ef_search candidates and none of the truly similar rows beyond that count were examined. In these cases, increase hnsw.ef_search or lower the threshold and rerank in application code.

13.6 Aurora Serverless v2 and Cost Architecture

Aurora Serverless v2 introduced a different cost model for vector workloads: you pay for Aurora Capacity Units (ACUs) consumed rather than instance hours. Vector similarity search is CPU-intensive, especially during HNSW graph traversal at high ef_search values. Understanding how ACU consumption maps to query patterns is necessary to avoid bill shock.

Each ACU provides approximately 2 GB of RAM and proportional CPU. An HNSW query against a 1M-row table with ef_search = 100 typically requires holding several hundred megabytes of index graph in buffer cache for low-latency execution. If Aurora Serverless v2 scales down between query bursts, the buffer cache is cold and the first queries after scale-up will trigger index page reads from the Aurora storage layer, adding latency.

To manage this:

-- PostgreSQL / pgvector (Aurora Serverless v2)
-- Set minimum ACU capacity to a value that keeps the HNSW index warm in shared_buffers
-- Do this at the cluster level via the AWS Console or CLI — not in SQL
-- Example: for a 1M-row, 1536-dim table, the HNSW index occupies roughly
-- m * dimensions * 4 bytes * rows = 16 * 1536 * 4 * 1,000,000 ≈ 98 GB worst case
-- In practice, pgvector HNSW uses significantly less (roughly 1.5-2x the raw vector size),
-- but plan for 4-8 GB of buffer cache for warm HNSW query performance

-- Check current buffer cache hit rate for the embeddings table
SELECT
    relname,
    heap_blks_read,
    heap_blks_hit,
    idx_blks_read,
    idx_blks_hit,
    ROUND(
        100.0 * idx_blks_hit / NULLIF(idx_blks_hit + idx_blks_read, 0),
        2
    ) AS idx_cache_hit_pct
FROM pg_statio_user_tables
WHERE relname = 'document_embeddings';

-- A healthy index cache hit rate is above 95%; below 80% indicates the HNSW
-- index is not fitting in shared_buffers and you need to increase memory/ACUs

Cost optimization patterns for Aurora and RDS:

Route all vector search traffic to read replicas. On Aurora, read replicas share the same storage layer as the primary, so they serve queries from a warm buffer cache that the primary populated. The replica lag for embeddings tables is low because embedding updates are typically batched, not real-time:

# Python
# Connection routing: writes to primary, reads to replica
import psycopg2
from contextlib import contextmanager

PRIMARY_DSN = os.environ["DATABASE_URL_PRIMARY"]
REPLICA_DSN = os.environ["DATABASE_URL_REPLICA"]

@contextmanager
def read_connection():
    """Use read replica for all similarity search queries."""
    conn = psycopg2.connect(REPLICA_DSN)
    try:
        yield conn
    finally:
        conn.close()

@contextmanager
def write_connection():
    """Use primary for ingestion and updates."""
    conn = psycopg2.connect(PRIMARY_DSN)
    try:
        yield conn
    finally:
        conn.close()

def search_similar(query_embedding: list[float], top_k: int = 10) -> list[dict]:
    with read_connection() as conn:
        with conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor) as cur:
            cur.execute("SET hnsw.ef_search = 80")
            cur.execute("""
                SELECT id, chunk_text,
                       1 - (embedding <=> %s::vector) AS similarity
                FROM document_embeddings
                WHERE model_name = 'text-embedding-3-small'
                ORDER BY embedding <=> %s::vector
                LIMIT %s
            """, (query_embedding, query_embedding, top_k))
            return [dict(row) for row in cur.fetchall()]

13.7 AlloyDB ML Integration: Embedding Without Leaving SQL

AlloyDB's google_ml_integration extension closes the gap between embedding model calls and database operations, which matters for pipelines that need low-latency, transactionally consistent embedding generation.

The practical use case: you receive a document, insert it, embed it, and store the embedding in a single database-side function call. No application middleware needed for the embedding step:

-- PostgreSQL / pgvector (AlloyDB)
-- End-to-end document insert + embed in a single function
CREATE OR REPLACE FUNCTION insert_document_with_embedding(
    p_content      TEXT,
    p_metadata     JSONB DEFAULT '{}'
)
RETURNS BIGINT
LANGUAGE plpgsql
AS $$
DECLARE
    v_doc_id     BIGINT;
    v_embedding  VECTOR(768);  -- textembedding-gecko@003 produces 768 dims
BEGIN
    -- Insert the document
    INSERT INTO documents (content, metadata)
    VALUES (p_content, p_metadata)
    RETURNING id INTO v_doc_id;

    -- Generate embedding via Vertex AI (network call from AlloyDB to Vertex AI)
    v_embedding := google_ml.embedding(
        'textembedding-gecko@003',
        p_content
    )::vector(768);

    -- Insert the embedding
    INSERT INTO document_embeddings
        (document_id, model_name, model_version, embedding)
    VALUES
        (v_doc_id, 'textembedding-gecko', '003', v_embedding);

    RETURN v_doc_id;
END;
$$;

-- Usage
SELECT insert_document_with_embedding(
    'PostgreSQL HNSW indexes support concurrent builds without exclusive table locks.',
    '{"source": "manual", "category": "database"}'::jsonb
);

This pattern has a significant limitation to be aware of: the Vertex AI embedding call happens inside the transaction. If the Vertex AI endpoint is slow or unavailable, your database transaction blocks until it times out. For high-throughput ingestion, this approach can create connection pool exhaustion faster than a decoupled pipeline. Use it for low-volume, latency-sensitive use cases (e.g., embedded in a trigger for small tables) or for background enrichment jobs with low concurrency.

AlloyDB also supports online schema changes for vector columns via ALTER TABLE ... ADD COLUMN, which is non-blocking for additions. Combined with a background job that populates the new embedding column, you can roll out a new embedding model with zero downtime:

-- PostgreSQL / pgvector (AlloyDB)
-- Step 1: Add new column for updated model (non-blocking)
ALTER TABLE document_embeddings
    ADD COLUMN embedding_v2 VECTOR(768);  -- switching to gecko@003 from a custom model

-- Step 2: Background populate (run as a batch job, not inline)
-- Populate in batches to avoid long-running transactions
DO $$
DECLARE
    batch_size INT := 500;
    last_id    BIGINT := 0;
    max_id     BIGINT;
BEGIN
    SELECT MAX(id) INTO max_id FROM document_embeddings WHERE embedding_v2 IS NULL;

    WHILE last_id < max_id LOOP
        UPDATE document_embeddings de
        SET embedding_v2 = google_ml.embedding(
            'textembedding-gecko@003',
            (SELECT content FROM documents d WHERE d.id = de.document_id)
        )::vector(768)
        WHERE de.id > last_id
          AND de.id <= last_id + batch_size
          AND de.embedding_v2 IS NULL;

        last_id := last_id + batch_size;
        PERFORM pg_sleep(0.05);  -- brief pause to reduce I/O pressure
    END LOOP;
END;
$$;

-- Step 3: Build HNSW index on new column
CREATE INDEX CONCURRENTLY idx_embeddings_v2_hnsw
    ON document_embeddings
    USING hnsw (embedding_v2 vector_cosine_ops)
    WITH (m = 16, ef_construction = 128);

-- Step 4: Drop old column (non-blocking on AlloyDB, brief lock on standard PG)
-- Only after verifying queries use the new index
ALTER TABLE document_embeddings DROP COLUMN embedding;
ALTER TABLE document_embeddings RENAME COLUMN embedding_v2 TO embedding;

13.8 Monitoring and Observability

Production vector search requires a monitoring strategy beyond standard database metrics. The key additional signals are: index build status, index size, cache hit rates for vector index pages, and per-query recall (if approximate indexes are used).

-- PostgreSQL / pgvector
-- Index health and size monitoring
SELECT
    i.relname AS index_name,
    t.relname AS table_name,
    pg_size_pretty(pg_relation_size(i.oid)) AS index_size,
    ix.indisvalid AS is_valid,
    ix.indisready AS is_ready
FROM pg_index ix
JOIN pg_class i ON i.oid = ix.indexrelid
JOIN pg_class t ON t.oid = ix.indrelid
WHERE t.relname = 'document_embeddings'
ORDER BY pg_relation_size(i.oid) DESC;

-- Active index builds (useful during CONCURRENTLY builds)
SELECT
    phase,
    blocks_done,
    blocks_total,
    ROUND(100.0 * blocks_done / NULLIF(blocks_total, 0), 1) AS pct_complete,
    tuples_done,
    tuples_total
FROM pg_stat_progress_create_index
WHERE relid = 'document_embeddings'::regclass;

-- Long-running vector queries (queries over 5 seconds)
SELECT
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query,
    state
FROM pg_stat_activity
WHERE (now() - pg_stat_activity.query_start) > INTERVAL '5 seconds'
  AND query ILIKE '%<=>%'  -- vector distance operator
ORDER BY duration DESC;

For Supabase, the dashboard exposes query performance metrics through the built-in Query Performance analyzer, which is backed by pg_stat_statements. Add the extension if it is not already enabled (it is on paid tiers):

-- PostgreSQL / pgvector (Supabase)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 slowest vector queries
SELECT
    LEFT(query, 120) AS query_preview,
    calls,
    ROUND((mean_exec_time)::numeric, 2) AS avg_ms,
    ROUND((total_exec_time / 1000)::numeric, 2) AS total_sec,
    rows
FROM pg_stat_statements
WHERE query ILIKE '%<=>%'
ORDER BY mean_exec_time DESC
LIMIT 10;

For RDS and Aurora, publish Performance Insights metrics to CloudWatch and set alarms on:

  • → `DBLoad` exceeding the vCPU count (indicates vector query CPU saturation)
  • → `ReadIOPS` sustained above baseline during non-build periods (indicates index cache misses)
  • → `FreeableMemory` falling below 15% (HNSW index pages are being evicted)

    13.9 Migration Path: Moving Between Platforms

    Teams frequently start on Supabase for the development velocity and migrate to Aurora or AlloyDB as scale demands grow. The migration is mechanically straightforward—pgvector data is just PostgreSQL data—but the operational gaps require planning.

    Exporting from Supabase:

    # Shell
# pg_dump from Supabase — use the direct connection string (port 5432)
# The connection string is in Project Settings > Database
pg_dump \
    --host=db.abcdefghijklmnop.supabase.co \
    --port=5432 \
    --username=postgres \
    --dbname=postgres \
    --no-password \
    --format=custom \
    --compress=9 \
    --table=documents \
    --table=document_embeddings \
    --file=embeddings_export.dump

# This exports the data but NOT the Supabase-specific auth tables (auth.users, etc.)
# For a full application migration, handle auth separately using the Supabase migration tools

    Restoring to Aurora or RDS:

    # Shell
# Restore to Aurora PostgreSQL
# Ensure the target DB has the vector extension enabled first
psql \
    --host=your-aurora-cluster.cluster-xxxx.us-east-1.rds.amazonaws.com \
    --port=5432 \
    --username=postgres \
    --dbname=yourdb \
    --command="CREATE EXTENSION IF NOT EXISTS vector;"

pg_restore \
    --host=your-aurora-cluster.cluster-xxxx.us-east-1.rds.amazonaws.com \
    --port=5432 \
    --username=postgres \
    --dbname=yourdb \
    --jobs=4 \        # parallel restore — match to vCPU count
    --no-owner \
    --no-acl \
    embeddings_export.dump

    The indexes do not need to be exported and restored—they can be rebuilt on the target after data load. In fact, restoring with --section=data (no indexes) and then rebuilding indexes on the target is faster than serializing and deserializing HNSW graph structures:

    # Shell
# Export data only (no indexes), then rebuild indexes on target
pg_dump \
    --section=pre-data \
    --section=data \
    # --section=post-data is omitted — this skips index creation
    --format=custom \
    --table=document_embeddings \
    --file=embeddings_data_only.dump

# After restore, rebuild HNSW index with target-appropriate parameters

    13.10 Practical Checklist Before Going to Production

    The following covers the decisions that cause the most production incidents on managed pgvector deployments:

    1. Confirm pgvector version and feature availability

    -- PostgreSQL / pgvector
SELECT extversion FROM pg_extension WHERE extname = 'vector';
-- Minimum for HNSW: 0.5.0
-- Minimum for halfvec: 0.7.0
-- Minimum for binary quantization (bit type): 0.7.0

    2. Set maintenance_work_mem before every index build

    On RDS and Aurora, this is a session parameter—it resets after the connection closes. Add it to your migration script or index-build runbook:

    -- PostgreSQL / pgvector
SET maintenance_work_mem = '6GB';  -- Adjust based on instance class
-- db.r6g.xlarge (32 GB RAM): safe to set 8 GB for index builds
-- db.r6g.large (16 GB RAM): use 4 GB; leave headroom for other queries
CREATE INDEX CONCURRENTLY ...

    3. Verify HNSW index is actually used by the planner

    -- PostgreSQL / pgvector
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, 1 - (embedding <=> '[...]'::vector) AS similarity
FROM document_embeddings
ORDER BY embedding <=> '[...]'::vector
LIMIT 10;
-- Must show "Index Scan using idx_embeddings_hnsw" — if you see "Seq Scan",
-- the planner has decided sequential scan is cheaper (common on very small tables
-- or when enable_indexscan is off)

    4. Test recall explicitly

    HNSW is approximate. Before deploying, measure recall against an exact KNN baseline on a representative sample:

    # Python
def measure_recall(
    conn,
    query_embedding: list[float],
    k: int = 10,
    ef_search: int = 80
) -> float:
    """Compare HNSW results against exact KNN to measure recall."""
    with conn.cursor() as cur:
        # Exact KNN (seq scan, no index)
        cur.execute("SET enable_indexscan = OFF")
        cur.execute("""
            SELECT id FROM document_embeddings
            ORDER BY embedding <=> %s::vector
            LIMIT %s
        """, (query_embedding, k))
        exact_ids = {row[0] for row in cur.fetchall()}

        # HNSW approximate KNN
        cur.execute("SET enable_indexscan = ON")
        cur.execute(f"SET hnsw.ef_search = {ef_search}")
        cur.execute("""
            SELECT id FROM document_embeddings
            ORDER BY embedding <=> %s::vector
            LIMIT %s
        """, (query_embedding, k))
        approx_ids = {row[0] for row in cur.fetchall()}

    return len(exact_ids & approx_ids) / k

    5. Plan for HNSW index rebuild during model transitions

    When you switch embedding models, the existing HNSW index is worthless—it was built on vectors from the old model, and new-model vectors will not be nearby in the same space. Create the new column and index before dropping the old one, and serve from both during the transition window.

    Key Takeaways

  • → **Managed pgvector is engine-version-locked**: The pgvector version you get on RDS, Aurora, AlloyDB, or Supabase is determined by the platform's PostgreSQL engine packaging, not independently upgradable. Verify feature availability (HNSW, `halfvec`, `bit`) before committing to a schema design.
  • → **HNSW is the right default for production on managed services**, but requires substantial `maintenance_work_mem` during index construction (plan for 4–8 GB for million-row, high-dimensional tables). Always build with `CREATE INDEX CONCURRENTLY` on live systems to avoid table-level locks.
  • → **Ingestion pipelines must decouple embedding generation from database transactions**: Calling external embedding APIs (OpenAI, Vertex AI) inside a database transaction holds locks and blocks connections. Generate embeddings first, then commit atomically. AlloyDB's SQL-level Vertex AI integration is the exception, and it comes with its own concurrency trade-offs.
  • → **Hybrid search (vector + metadata filters) requires both an HNSW index and supporting B-tree indexes** on the filter columns. The planner combines them via bitmap scans or index scans with filter pushdown. Without B-tree indexes on tenant ID, category, or date range columns, metadata filters will cause sequential scans that defeat the purpose of the vector index.
  • → **Connection routing and buffer cache warmth determine real-world vector query latency**: On Aurora and RDS, route search traffic to read replicas to protect write throughput. On Aurora Serverless v2, set a minimum ACU capacity that keeps your HNSW index warm in shared buffers—cold-start latency after scale-down can be an order of magnitude higher than steady-state latency.
