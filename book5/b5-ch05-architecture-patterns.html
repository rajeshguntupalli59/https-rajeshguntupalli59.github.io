Chapter 5 of 40 The Cloud Database Engineer

Chapter 5: Cloud Database Architecture Patterns

Cloud databases don't just move your workload to someone else's hardware — they introduce architectural patterns that simply don't exist in on-premises environments. Multi-AZ failover that completes automatically within minutes, read replicas that spin up in minutes, serverless capacity that scales from zero to 128 ACUs without a DBA touching a single configuration file: these capabilities change how you design systems from the ground up. This chapter covers the core architectural patterns you'll implement on AWS RDS, Azure SQL, and Google Cloud SQL, maps them to what you already know from on-premises work, and shows you exactly where managed services expand your options and where they constrain them.

---

5.1 High Availability and Failover Architecture

#### From Manual Standbys to Managed HA

On premises, you built HA with Pacemaker/Corosync clusters, SQL Server Always On Availability Groups with manual witness configuration, or PostgreSQL streaming replication with Patroni. You managed VIPs, fencing, and split-brain scenarios yourself. In the cloud, the managed HA layer abstracts most of this — but understanding what's happening underneath matters when things go wrong at 2 AM.

AWS RDS Multi-AZ deploys a synchronous standby replica in a separate Availability Zone. The standby is not a readable replica — it exists solely for failover. RDS uses a DNS endpoint; when failover occurs, the CNAME flips from primary to standby. Client applications must handle the DNS TTL-based reconnect window — AWS states standard RDS Multi-AZ failover typically completes within 60–120 seconds. The standby is on different physical hardware, a different power domain, and in some cases a different facility within the same AWS region. Your application connection string doesn't change; only the IP behind the DNS name does.

Aurora goes further. Aurora Multi-AZ isn't traditional synchronous replication — the storage layer itself is shared across six copies in three AZs. The "replica" Aurora creates is a hot standby that already has the data; failover is a matter of promoting the reader endpoint to writer, not copying data. Aurora failover typically completes in under 30 seconds with no data loss because Aurora replicas share the storage layer with the primary. This is meaningfully different from RDS Multi-AZ, which is block-level replication of the EBS volume.

Azure SQL offers multiple HA tiers. The General Purpose tier uses remote storage with a hot standby; failover takes 20–30 seconds. Business Critical tier maintains three synchronous replicas locally (similar in concept to Always On AG with three synchronous partners) and typically fails over in well under 30 seconds. Hyperscale uses a page server architecture with compute and storage fully separated, similar in philosophy to Aurora, and supports rapid replica addition.

Cloud SQL (GCP) uses regional instances with a standby in a second zone within the same region. Failover is automatic and typically completes in 60–120 seconds — meaningfully slower than Aurora or Azure Business Critical. AlloyDB for PostgreSQL, Google's premium offering, uses a Paxos-based distributed storage layer similar to Aurora, with failover under 60 seconds and readable replicas that share the underlying storage.

#### Configuring Multi-AZ on RDS

# Create a Multi-AZ RDS PostgreSQL instance
aws rds create-db-instance \
  --db-instance-identifier prod-postgres-primary \
  --db-instance-class db.r6g.4xlarge \
  --engine postgres \
  --engine-version 15.4 \
  --master-username dbadmin \
  --master-user-password "${DB_PASSWORD}" \
  --allocated-storage 500 \
  --storage-type gp3 \
  --iops 12000 \
  --storage-throughput 500 \
  --multi-az \
  --vpc-security-group-ids sg-0a1b2c3d4e5f \
  --db-subnet-group-name prod-db-subnet-group \
  --backup-retention-period 7 \
  --preferred-backup-window "03:00-04:00" \
  --preferred-maintenance-window "sun:05:00-sun:06:00" \
  --deletion-protection \
  --enable-performance-insights \
  --performance-insights-retention-period 7 \
  --no-publicly-accessible

# Verify Multi-AZ status and get endpoint
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-primary \
  --query 'DBInstances[0].{MultiAZ:MultiAZ,Endpoint:Endpoint.Address,SecondaryAZ:SecondaryAvailabilityZone,Status:DBInstanceStatus}'

#### Configuring Aurora Cluster HA with Terraform

# Aurora PostgreSQL cluster with Multi-AZ writer and readers
resource "aws_rds_cluster" "prod_aurora" {
  cluster_identifier     = "prod-aurora-postgres"
  engine                 = "aurora-postgresql"
  engine_version         = "15.4"
  database_name          = "proddb"
  master_username        = "dbadmin"
  master_password        = var.db_password
  
  # Storage is automatically distributed across 3 AZs
  availability_zones     = ["us-east-1a", "us-east-1b", "us-east-1c"]
  
  backup_retention_period   = 7
  preferred_backup_window   = "03:00-04:00"
  preferred_maintenance_window = "sun:05:00-sun:06:00"
  
  vpc_security_group_ids = [aws_security_group.aurora_sg.id]
  db_subnet_group_name   = aws_db_subnet_group.prod.name
  
  deletion_protection    = true
  skip_final_snapshot    = false
  final_snapshot_identifier = "prod-aurora-final-${formatdate("YYYY-MM-DD", timestamp())}"
  
  enabled_cloudwatch_logs_exports = ["postgresql"]
  
  db_cluster_parameter_group_name = aws_rds_cluster_parameter_group.prod.name

    Environment = "production"

resource "aws_rds_cluster_instance" "writer" {

  instance_class     = "db.r6g.4xlarge"
  engine             = aws_rds_cluster.prod_aurora.engine
  engine_version     = aws_rds_cluster.prod_aurora.engine_version

  performance_insights_enabled = true
  performance_insights_retention_period = 7
  
  auto_minor_version_upgrade = false
}

# Reader instances — one each in 1b and 1c for AZ redundancy
resource "aws_rds_cluster_instance" "readers" {
  count              = 2
  identifier         = "prod-aurora-reader-${count.index + 1}"
  cluster_identifier = aws_rds_cluster.prod_aurora.id
  instance_class     = "db.r6g.2xlarge"
  engine             = aws_rds_cluster.prod_aurora.engine
  engine_version     = aws_rds_cluster.prod_aurora.engine_version
  
  availability_zone  = count.index == 0 ? "us-east-1b" : "us-east-1c"
  
  performance_insights_enabled = true
  performance_insights_retention_period = 7
}

#### What You Can't Control

On a self-managed PostgreSQL cluster, you control the exact failover timing: synchronous_commit, synchronous_standby_names, and the Patroni TTL settings. In RDS Multi-AZ, you don't choose the replication protocol — it's block-level synchronous replication of EBS volumes managed by AWS. You can't query the replication lag on the standby because it isn't a readable PostgreSQL replica; it's a shadow volume. You can't apply patches independently to the standby before promoting it. You accept these constraints in exchange for not managing the HA stack yourself.

The one genuine gotcha: RDS Multi-AZ failover requires DNS TTL propagation. If your application has hardcoded IP addresses or DNS caches with long TTLs, failover won't be transparent. Always configure your JDBC, psycopg2, or .NET connection strings to use the RDS DNS endpoint and set connect_timeout values that allow for reconnection. In Java, set socketTimeout=30 and implement retry logic — don't assume the managed service makes reconnection unnecessary.

5.2 Read Scaling and Replica Patterns

#### Shifting the Mental Model

On premises, adding a read replica meant provisioning a server, configuring streaming replication, managing replication slots, and worrying about max_replication_slots and max_wal_senders. In the cloud, replicas are a billing line item — you add them with a CLI call. The architectural question shifts from "can we afford the operational overhead?" to "how do we route traffic, manage replica lag, and avoid read-your-own-writes consistency bugs?"

RDS Read Replicas are asynchronous replicas using native PostgreSQL streaming replication or SQL Server log shipping. They're readable, each with their own endpoint, and can be promoted to standalone instances. You can have up to five read replicas per RDS instance. Replication lag is the same concern you had on-premises: under normal conditions you'll see sub-second lag, but long-running transactions on the primary that generate heavy WAL, or large bulk operations, can push lag to minutes. Monitor ReplicaLag in CloudWatch and alert at 30 seconds; investigate at 60 seconds.

Aurora Replicas work differently. Because all Aurora instances share the same storage layer, a reader instance doesn't need to ship or apply WAL — it reads the same storage pages the writer uses, with a lag that reflects only page cache propagation. Aurora replica lag is typically under 20ms for reads. You can have up to 15 Aurora replicas. This is a genuinely different operational experience from PostgreSQL streaming replication, and it means Aurora replicas are appropriate for latency-sensitive reporting workloads that RDS read replicas are not.

Azure SQL Hyperscale supports named replicas (up to 30) that also share the underlying page server storage. This is Microsoft's architectural answer to Aurora's storage disaggregation. The General Purpose and Business Critical tiers support geo-replicas for disaster recovery, but they have higher replication lag than Hyperscale named replicas.

#### RDS Proxy for Connection Pooling

One on-premises pattern that doesn't translate cleanly to RDS is PgBouncer or pgpool-II sitting in front of your replica pool. RDS Proxy is the managed alternative. It maintains a connection pool to your RDS or Aurora instances and exposes a single endpoint to applications. When you have Lambda functions or containerized microservices opening thousands of short-lived connections — a workload that would exhaust max_connections on PostgreSQL — RDS Proxy pins connections to backend instances and handles multiplexing.

# Create RDS Proxy in front of Aurora cluster
aws rds create-db-proxy \
  --db-proxy-name prod-aurora-proxy \
  --engine-family POSTGRESQL \
  --auth '[
    {
      "AuthScheme": "SECRETS",
      "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789:secret:prod/aurora/dbadmin",
      "IAMAuth": "REQUIRED"
    }
  ]' \
  --role-arn arn:aws:iam::123456789:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0a1b2c3d subnet-0e5f6g7h subnet-0i9j0k1l \
  --vpc-security-group-ids sg-0proxy1234 \
  --require-tls

# Register the Aurora cluster as the proxy target
aws rds register-db-proxy-targets \
  --db-proxy-name prod-aurora-proxy \
  --db-cluster-identifiers prod-aurora-postgres

# Create a separate proxy endpoint for read replicas
aws rds create-db-proxy-endpoint \
  --db-proxy-name prod-aurora-proxy \
  --db-proxy-endpoint-name prod-aurora-proxy-reader \
  --vpc-subnet-ids subnet-0a1b2c3d subnet-0e5f6g7h subnet-0i9j0k1l \
  --vpc-security-group-ids sg-0proxy1234 \
  --target-role READ_ONLY

RDS Proxy has a real limitation that catches DBAs by surprise: it doesn't support all PostgreSQL client features. COPY commands, LISTEN/NOTIFY, pg_terminate_backend(), and SET LOCAL within certain transaction modes behave unexpectedly through the proxy. If your application relies on advisory locks or NOTIFY-based event queuing, test against the proxy endpoint explicitly before deploying to production. The proxy also pins connections (holds a dedicated backend connection for a client) when it detects certain session-state changes, which reduces the multiplexing benefit. Keep transactions short and avoid session-level SET commands that force connection pinning.

#### Aurora Global Database for Cross-Region Reads

For applications serving multiple geographic regions, Aurora Global Database adds cross-region replication with typical lag under one second. This is different from RDS cross-region read replicas, which use the native PostgreSQL replication stream and typically show 2–10 seconds of lag depending on bandwidth.

# boto3: describe Aurora Global Cluster replication lag
import boto3

rds = boto3.client('rds', region_name='us-east-1')

response = rds.describe_global_clusters(
    GlobalClusterIdentifier='prod-global-cluster'
)

for cluster in response['GlobalClusters']:
    print(f"Global Cluster: {cluster['GlobalClusterIdentifier']}")
    print(f"Status: {cluster['Status']}")
    print(f"Engine: {cluster['EngineVersion']}")
    
    for member in cluster['GlobalClusterMembers']:
        print(f"  Member: {member['DBClusterArn']}")
        print(f"  Is Writer: {member['IsWriter']}")
        
        if not member['IsWriter']:
            # Fetch replication lag from the secondary region's CloudWatch
            secondary_region = member['DBClusterArn'].split(':')[3]
            cw = boto3.client('cloudwatch', region_name=secondary_region)
            
            lag_response = cw.get_metric_statistics(
                Namespace='AWS/RDS',
                MetricName='AuroraGlobalDBReplicationLag',
                Dimensions=[{'Name': 'DBClusterIdentifier', 
                             'Value': member['DBClusterArn'].split(':')[-1]}],
                StartTime='2024-01-15T00:00:00Z',
                EndTime='2024-01-15T01:00:00Z',
                Period=60,
                Statistics=['Average', 'Maximum']
            )
            
            for point in lag_response['Datapoints'][-5:]:
                print(f"  Lag: avg={point['Average']:.1f}ms max={point['Maximum']:.1f}ms")

5.3 Storage Architecture and Auto-Scaling

#### Cloud Storage Is Not a SAN

On premises, your DBA team provisioned LUNs from a SAN, set RAID levels, tuned stripe sizes, and called the storage team when you needed more space — a process that took days. In AWS RDS, storage is gp3 or io2 backed by networked EBS volumes. The performance characteristics are fundamentally different from local NVMe, and understanding those differences prevents over-provisioning and unexpected I/O bottlenecks.

RDS gp3 provides a baseline of 3,000 IOPS and 125 MB/s throughput for any volume, regardless of size. Unlike gp2 (which was 3 IOPS/GB with a burst bucket), gp3 decouples IOPS from capacity. You can have a 100GB volume with 12,000 IOPS if you need it. Maximum gp3 performance is 16,000 IOPS and 1,000 MB/s. For PostgreSQL workloads with heavy random I/O — OLTP with small row updates, index-heavy queries — gp3 at 12,000–16,000 IOPS covers the majority of production workloads on instances up to db.r6g.8xlarge.

RDS io2 is the choice for I/O-intensive OLTP — think 50,000–256,000 IOPS, 4,000 MB/s throughput. At these levels you're typically also running db.r6g.16xlarge or db.r6i.32xlarge, where the network bandwidth to the EBS volume (25–50 Gbps) becomes the binding constraint, not the storage tier itself.

Aurora storage auto-scales in 10GB increments up to 128TB and you pay only for what you use. There is no pre-provisioning step; Aurora handles storage growth automatically. However, Aurora storage doesn't shrink automatically — once expanded to 50TB, the billing floor is 50TB even if you delete data. Run VACUUM and monitor aurora_storage_utilization to understand actual versus allocated space.

Cloud SQL storage auto-increases by default: when free space runs low, Cloud SQL automatically adds capacity in an incremental step, up to the configured maximum (check current GCP documentation for the exact trigger threshold and increment size, as these have changed over time). You can disable this and manage storage manually, but for production workloads the auto-increase behavior is generally preferable.

-- Query Aurora storage utilization (run from psql connected to Aurora)
SELECT 
    current_setting('server_version') AS pg_version,
    pg_size_pretty(sum(pg_database_size(datname))) AS total_logical_size,
    -- Aurora-specific storage stats via aurora_stat_utils extension
    pg_size_pretty(
        (SELECT sum(allocated_storage) 
         FROM aurora_storage_object_stats() 
         WHERE object_type = 'data')
    ) AS aurora_allocated_storage;

-- Monitor bloat that inflates Aurora storage costs
SELECT 
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
    pg_size_pretty(
        pg_total_relation_size(schemaname||'.'||tablename) - 
        pg_relation_size(schemaname||'.'||tablename)
    ) AS bloat_estimate,
    n_dead_tup,
    last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 100000
ORDER BY n_dead_tup DESC
LIMIT 20;

#### Storage Scaling Gotchas

RDS storage scaling is one-directional and time-bounded. You can increase allocated storage, but you cannot decrease it. Once you scale from 500GB to 1TB, your minimum billing is 1TB from that point on. More critically, during an RDS storage scale operation on Multi-AZ instances, the process scales the standby first, then performs a failover, then scales the former primary (now standby). The entire operation can take 30–60 minutes for large volumes, during which a maintenance window effectively exists for any workload that can't tolerate the failover window.

For Azure SQL, storage scales online within the same service tier with no downtime for Business Critical and General Purpose. The Hyperscale tier is unique: Hyperscale storage auto-scales to 100TB with no size pre-configuration required, and this is genuinely transparent to the application. The Hyperscale architecture separates log service, page servers, and compute nodes so that storage scaling doesn't touch the compute layer at all.

5.4 Network Architecture: VPC, Private Link, and Connectivity

#### The pg_hba.conf Replacement

On premises, pg_hba.conf controlled which hosts could connect to PostgreSQL and with what authentication method. In the cloud, that control is split across multiple layers, and understanding which layer does what determines whether you have a security gap.

VPC Security Groups (AWS) act as stateful host-based firewalls at the instance level. You configure inbound rules that specify source CIDR ranges, specific security group IDs, or individual IPs. For a production RDS instance, you should never open port 5432 to 0.0.0.0/0. The pattern is:

1. RDS instance lives in a private subnet with no internet gateway route

2. Application servers have a security group (e.g., sg-app-tier)

3. RDS security group allows inbound 5432 only from sg-app-tier

4. Any DBA access uses a bastion host, VPN, or AWS Systems Manager Session Manager tunneling

# Create an RDS security group that allows only from the app tier security group
aws ec2 create-security-group \
  --group-name prod-rds-sg \
  --description "Production RDS - allow from app tier only" \
  --vpc-id vpc-0a1b2c3d4e5f6789

export RDS_SG_ID=$(aws ec2 describe-security-groups \
  --filters Name=group-name,Values=prod-rds-sg \
  --query 'SecurityGroups[0].GroupId' \
  --output text)

# Allow PostgreSQL port from app security group only
aws ec2 authorize-security-group-ingress \
  --group-id ${RDS_SG_ID} \
  --protocol tcp \
  --port 5432 \
  --source-group sg-0app12345678

# Verify no public access rule exists
aws ec2 describe-security-groups \
  --group-ids ${RDS_SG_ID} \
  --query 'SecurityGroups[0].IpPermissions'

# Create DB subnet group using private subnets only
aws rds create-db-subnet-group \
  --db-subnet-group-name prod-private-subnets \
  --db-subnet-group-description "Private subnets for production RDS" \
  --subnet-ids subnet-private-1a subnet-private-1b subnet-private-1c

AWS PrivateLink solves a specific architectural problem: you need to access an RDS instance from a different VPC or from an on-premises network via Direct Connect without exposing the database to the public internet or setting up full VPC peering. PrivateLink creates an interface VPC endpoint with a private IP in your VPC that proxies to the RDS endpoint. This is the right pattern for:

  • → SaaS applications that need to query a customer's database
  • → Analytics platforms in a centralized VPC querying databases in spoke VPCs
  • → On-premises applications connecting through Direct Connect to RDS

    • Azure SQL network isolation uses service endpoints (simple, lower complexity) or Private Endpoint (production recommended). With a Private Endpoint, Azure SQL gets a private IP in your VNet. The Azure equivalent of VPC security groups is Network Security Groups (NSGs), and Azure SQL also supports a firewall rule layer at the server level — you configure allowed IP ranges and VNet rules. Unlike AWS, Azure SQL has a server-level "Allow Azure services and resources to access this server" toggle that is enabled by default and should be disabled in production environments where all connectivity is via Private Endpoint.

    # Create Azure SQL Private Endpoint
az network private-endpoint create \
  --name prod-sql-private-endpoint \
  --resource-group prod-rg \
  --vnet-name prod-vnet \
  --subnet private-endpoints-subnet \
  --private-connection-resource-id \
    $(az sql server show --name prod-sql-server --resource-group prod-rg \
      --query id --output tsv) \
  --group-ids sqlServer \
  --connection-name prod-sql-private-connection

# Create private DNS zone for Azure SQL resolution
az network private-dns zone create \
  --resource-group prod-rg \
  --name "privatelink.database.windows.net"

az network private-dns link vnet create \
  --resource-group prod-rg \
  --zone-name "privatelink.database.windows.net" \
  --name prod-vnet-dns-link \
  --virtual-network prod-vnet \
  --registration-enabled false

# Create DNS record for the private endpoint
az network private-endpoint dns-zone-group create \
  --resource-group prod-rg \
  --endpoint-name prod-sql-private-endpoint \
  --name prod-sql-dns-zone-group \
  --private-dns-zone "privatelink.database.windows.net" \
  --zone-name sql

    Cloud SQL uses Private IP (VPC peering between your VPC and Google's service producer VPC) or Private Service Connect (analogous to AWS PrivateLink). For new deployments, Private Service Connect is preferred: it doesn't require VPC peering, avoids IP range overlap issues that plague large organizations, and gives you a single IP in your VPC subnet that routes to Cloud SQL. The older Private IP approach with VPC peering works but creates a transitive routing constraint — you can't reach Cloud SQL through a VPN or Interconnect from on-premises without additional configuration via Cloud DNS and route export settings.

    # Create Cloud SQL instance with Private Service Connect
gcloud sql instances create prod-cloudsql-pg \
  --database-version=POSTGRES_15 \
  --tier=db-custom-8-32768 \
  --region=us-central1 \
  --no-assign-ip \
  --enable-private-service-connect \
  --allowed-psc-projects=my-project-id \
  --storage-type=SSD \
  --storage-size=500GB \
  --storage-auto-increase \
  --backup-start-time=03:00 \
  --maintenance-window-day=SUN \
  --maintenance-window-hour=5 \
  --availability-type=REGIONAL

# Get the PSC service attachment URI
gcloud sql instances describe prod-cloudsql-pg \
  --format="value(settings.ipConfiguration.pscConfig.serviceAttachmentLink)"

# Create a forwarding rule in your VPC pointing to the PSC attachment
# (Use the service attachment URI from the previous command)
gcloud compute forwarding-rules create prod-cloudsql-psc-endpoint \
  --region=us-central1 \
  --network=prod-vpc \
  --subnet=private-subnet-us-central1 \
  --address=prod-cloudsql-psc-ip \
  --target-service-attachment=<SERVICE_ATTACHMENT_URI>

    5.5 Parameter Tuning in Managed Environments

    #### What You Can Change vs. What Is Fixed

    On premises, you had full authority over postgresql.conf — every GUC was yours to set. In managed cloud environments, you work within parameter groups (AWS), server parameters (Azure), and database flags (GCP), and some parameters that matter most to performance are fixed or bounded by the managed service.

    The parameters you cannot change in RDS PostgreSQL:

  • → `max_connections` — configurable but bounded by instance class (db.r6g.large forces a lower ceiling than on-premises because RDS manages memory for its own processes)
  • → `wal_level` — always `logical` in RDS (which is actually more permissive than on-premises defaults)
  • → `archive_mode` — always `on` in RDS (RDS manages WAL archival for backups and Point-in-Time Recovery)
  • → `superuser` access — you get `rds_superuser` role, not true PostgreSQL superuser; certain system catalog writes and extensions requiring superuser are unavailable

    • The parameters you should tune in RDS PostgreSQL parameter groups:

    -- Check current settings and their sources (run from psql)
SELECT 
    name,
    setting,
    unit,
    source,
    context,
    short_desc
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'effective_cache_size',
    'work_mem',
    'maintenance_work_mem',
    'max_worker_processes',
    'max_parallel_workers',
    'max_parallel_workers_per_gather',
    'checkpoint_completion_target',
    'wal_buffers',
    'default_statistics_target',
    'random_page_cost',
    'effective_io_concurrency',
    'autovacuum_vacuum_scale_factor',
    'autovacuum_analyze_scale_factor',
    'autovacuum_vacuum_cost_delay',
    'log_min_duration_statement',
    'log_autovacuum_min_duration'
)
ORDER BY name;

    In AWS, you apply these through a parameter group. For RDS, changes to parameters with context = postmaster require an instance reboot; context = sighup parameters apply without a reboot.

    # Create a custom RDS parameter group for PostgreSQL 15
aws rds create-db-parameter-group \
  --db-parameter-group-name prod-postgres15-params \
  --db-parameter-group-family postgres15 \
  --description "Production PostgreSQL 15 parameters"

# Apply key performance parameters
aws rds modify-db-parameter-group \
  --db-parameter-group-name prod-postgres15-params \
  --parameters \
    "ParameterName=effective_cache_size,ParameterValue=75%,ApplyMethod=pending-reboot" \
    "ParameterName=work_mem,ParameterValue=65536,ApplyMethod=pending-reboot" \
    "ParameterName=maintenance_work_mem,ParameterValue=2097152,ApplyMethod=pending-reboot" \
    "ParameterName=checkpoint_completion_target,ParameterValue=0.9,ApplyMethod=immediate" \
    "ParameterName=default_statistics_target,ParameterValue=200,ApplyMethod=immediate" \
    "ParameterName=random_page_cost,ParameterValue=1.1,ApplyMethod=immediate" \
    "ParameterName=effective_io_concurrency,ParameterValue=200,ApplyMethod=immediate" \
    "ParameterName=autovacuum_vacuum_scale_factor,ParameterValue=0.02,ApplyMethod=immediate" \
    "ParameterName=autovacuum_analyze_scale_factor,ParameterValue=0.01,ApplyMethod=immediate" \
    "ParameterName=autovacuum_vacuum_cost_delay,ParameterValue=2,ApplyMethod=immediate" \
    "ParameterName=log_min_duration_statement,ParameterValue=1000,ApplyMethod=immediate" \
    "ParameterName=log_autovacuum_min_duration,ParameterValue=0,ApplyMethod=immediate"

    > Note on shared_buffers in RDS: AWS manages shared_buffers automatically based on instance class and sets it to 25% of total instance RAM, which is the standard PostgreSQL recommendation. You can override this in the parameter group, but AWS will not let you set it above a ceiling they manage — and exceeding 40% of available RAM in a managed environment where RDS also has memory reserved for its own processes can trigger OOM conditions. Accept the managed default here unless you have profiled evidence of a specific benefit.

    #### Azure SQL Parameter Equivalent

    Azure SQL (SQL Server) exposes server properties rather than a flat parameter file. The equivalent configuration surface area is sp_configure, Query Store settings, and database-level compatibility settings. Azure SQL manages memory (max server memory) automatically based on your vCore tier — you don't set it. What you do control:

    -- Azure SQL: Check current configuration options
SELECT 
    name,
    value,
    value_in_use,
    description,
    is_dynamic,
    is_advanced
FROM sys.configurations
WHERE name IN (
    'max degree of parallelism',
    'cost threshold for parallelism',
    'optimize for ad hoc workloads',
    'backup compression default',
    'remote query timeout (s)',
    'fill factor (%)'
)
ORDER BY name;

-- Set MAXDOP and cost threshold (Business Critical tier example)
-- Azure SQL allows sp_configure changes for non-memory parameters

    5.6 Serverless and Auto-Scaling Database Patterns

    #### When Serverless Makes Architectural Sense

    Serverless databases — Aurora Serverless v2, Azure SQL Serverless, Neon, AlloyDB Omni — solve a specific problem: workloads with highly variable or intermittent demand where the cost of provisioning for peak is prohibitive and the operational overhead of manual scaling is unacceptable. The trade-offs are real: cold start latency, capacity limits, and pricing models that favor sustained workloads less than provisioned instances do.

    Aurora Serverless v2 scales ACUs (Aurora Capacity Units, where 1 ACU ≈ 2GB RAM and proportional CPU) between a configured minimum and maximum. Scaling is continuous — it doesn't round to whole numbers or cause connection drops. Unlike Serverless v1, v2 can maintain state during scaling; it doesn't drop connections on a scale event. For a development database that runs overnight jobs but sits idle during business hours, a min of 0.5 ACU and max of 8 ACU might reduce costs substantially versus a provisioned db.r6g.large. For production OLTP with a sustained 10,000 TPS, a provisioned instance is almost always the right choice — the per-ACU pricing of Serverless v2 at steady state typically exceeds provisioned pricing above a moderate utilization threshold.

    # Aurora Serverless v2 — mixed cluster: serverless writer, provisioned readers
resource "aws_rds_cluster" "serverless_v2" {
  cluster_identifier  = "staging-aurora-serverless"
  engine              = "aurora-postgresql"
  engine_version      = "15.4"
  database_name       = "stagingdb"
  master_username     = "dbadmin"
  master_password     = var.db_password
  
  serverlessv2_scaling_configuration {
    min_capacity = 0.5
    max_capacity = 16
  }

}

It auto-pauses after a configurable idle period (minimum 1 hour) and resumes on the next connection — the resume latency is typically several seconds to tens of seconds, making it unsuitable for production latency-sensitive applications. It's well-suited to development and test environments, infrequently accessed reporting databases, or any workload where the first query of the day can tolerate an initial delay.

    5.7 Multi-Region and Disaster Recovery Architecture

    #### RPO and RTO in Managed Cloud Environments

    The cloud doesn't change what RPO and RTO mean — it changes what's achievable at a given operational complexity and cost. On premises, achieving sub-minute RPO typically meant synchronous replication to a co-located DR site with dedicated hardware. In the cloud, the same capability exists across geographic regions, but the network latency between regions (typically 30–80ms between US regions, 80–180ms between continents) means synchronous replication across regions is latency-additive for every write transaction.

    AWS cross-region strategy options (RDS PostgreSQL):

    | Option | RPO | RTO | Notes |

    |--------|-----|-----|-------|

    | Cross-region read replica | Seconds to minutes | 20–40 min (manual promote) | Async; lag depends on write rate |

    | Aurora Global Database | < 1 second | < 1 minute (managed failover) | Shared storage; fast recovery |

    | RDS automated backups + S3 cross-region copy | Hours | Hours | Restore from snapshot |

    | AWS Backup cross-region | Hours | Hours | Policy-driven, integrates with RDS |

    For RPO near zero and RTO under one minute, Aurora Global Database is the only native AWS solution. For RTO of 30–60 minutes and RPO of seconds to a few minutes, cross-region read replicas with manual promotion is the standard approach.

    #### Aurora Global Database Failover Procedure

    Aurora Global Database supports two failover modes: managed planned failover (for maintenance, testing) and unmanaged failover (for disaster recovery when the primary region is unavailable). The difference is operationally important.

    Managed planned failover gracefully promotes a secondary region to primary, drains the primary, and reconfigures the global cluster. This is safe and reversible.

    Unmanaged failover (detach-and-promote) is used when the primary region is inaccessible. The secondary cluster is detached from the global cluster and promoted independently. After recovery, you must manually re-establish the global cluster or rebuild the replication topology — the old primary cannot simply re-join as a secondary without a rebuild.

    # Initiate Aurora Global Database managed failover (boto3)
import boto3
import time

rds = boto3.client('rds', region_name='us-east-1')

def initiate_global_failover(global_cluster_id, target_db_cluster_arn):
    """
    Perform managed planned failover of Aurora Global Database.
    target_db_cluster_arn: the secondary cluster to promote to primary.
    """
    print(f"Initiating managed failover to {target_db_cluster_arn}")
    
    response = rds.failover_global_cluster(
        GlobalClusterIdentifier=global_cluster_id,
        TargetDbClusterIdentifier=target_db_cluster_arn
    )
    
    print(f"Failover initiated. Status: {response['GlobalCluster']['Status']}")
    
    # Poll for completion
    while True:
        status_response = rds.describe_global_clusters(
            GlobalClusterIdentifier=global_cluster_id
        )
        status = status_response['GlobalClusters'][0]['Status']
        members = status_response['GlobalClusters'][0]['GlobalClusterMembers']
        
        writer = next((m for m in members if m['IsWriter']), None)
        print(f"Status: {status} | Writer: {writer['DBClusterArn'] if writer else 'None'}")
        
        if status == 'available':
            print("Failover complete.")
            break
        
        time.sleep(15)

# Example: fail over to us-west-2 secondary
initiate_global_failover(
    global_cluster_id='prod-global-cluster',
    target_db_cluster_arn='arn:aws:rds:us-west-2:123456789:cluster:prod-aurora-secondary'
)

    #### Azure SQL Geo-Replication and Failover Groups

    Azure SQL Business Critical supports active geo-replication (up to four readable secondary databases in different regions) and auto-failover groups (a layer on top of geo-replication that provides a single listener endpoint and automatic failover). Failover groups are the preferred production pattern because they provide a stable connection endpoint that doesn't change during failover.

    # Create a failover group for Azure SQL
az sql failover-group create \
  --name prod-sql-failover-group \
  --partner-server prod-sql-server-westus2 \
  --resource-group prod-rg \
  --server prod-sql-server-eastus \
  --add-db prod-database \
  --failover-policy Automatic \
  --grace-period 1

# Check failover group status and replication state
az sql failover-group show \
  --name prod-sql-failover-group \
  --resource-group prod-rg \
  --server prod-sql-server-eastus \
  --query '{role:replicationRole,state:replicationState,partnerServers:partnerServers[].{location:location,role:replicationRole}}'

# Initiate manual planned failover (to secondary)
az sql failover-group set-primary \
  --name prod-sql-failover-group \
  --resource-group prod-rg \
  --server prod-sql-server-westus2

    When using Azure SQL failover groups, your application connects to the failover group listener endpoint (e.g., prod-sql-failover-group.database.windows.net) rather than the individual server endpoint. The listener endpoint routes to whichever server is currently primary. After failover, your connection string doesn't change. This is the Azure equivalent of the Aurora cluster endpoint — one DNS name regardless of which physical node is primary.

    #### GCP Cloud SQL Cross-Region Replicas and AlloyDB

    Cloud SQL cross-region read replicas are straightforward: you create a read replica in a different region, and GCP handles the asynchronous replication. Promoting a cross-region replica to a standalone instance for DR is a manual operation — there is no equivalent to Aurora Global Database's managed cross-region failover with automatic reconfiguration.

    AlloyDB's approach to HA and DR is more sophisticated: within a region, AlloyDB uses Paxos-based distributed storage with automatic failover under 60 seconds. For cross-region DR, AlloyDB supports cross-region replicas. At the time of writing, AlloyDB cross-region replica promotion is also a manual operation requiring DBA intervention. If your RPO/RTO requirements demand automated cross-region failover with sub-minute recovery, Aurora Global Database remains the most mature managed option across the three major cloud providers.

    5.8 Observability Architecture: Metrics, Logs, and Tracing

    #### The Monitoring Stack You Inherit

    On premises you assembled your own monitoring stack — Prometheus + Grafana + postgres_exporter, or Zabbix, or a commercial monitoring product. In the cloud, each provider ships integrated monitoring that is "good enough" for most situations and has specific gaps that matter at scale.

    AWS CloudWatch automatically collects ~40 RDS metrics: CPUUtilization, DatabaseConnections, FreeableMemory, ReadIOPS, WriteIOPS, ReadLatency, WriteLatency, ReplicaLag, DiskQueueDepth. These are sufficient for high-level health monitoring but insufficient for query-level performance work. RDS Performance Insights fills that gap — it samples pg_stat_activity, wait events, and top SQL every second and presents a visual breakdown of what the database was doing. Performance Insights is the single most valuable monitoring tool in the RDS ecosystem, and the 7-day free retention tier is adequate for most incident analysis. Extend to 2 years for regulatory environments.

    5.9 Cost Architecture: Designing for Efficiency

    #### The Bill Is Part of the Architecture

    On premises, infrastructure cost was largely sunk — the servers existed whether queries ran or not. In the cloud, every ACU, IOPS, byte of storage, and GB of data transfer is a billing event. Designing a cloud database architecture without modeling the cost profile is incomplete design.

    RDS cost drivers, in rough order of impact for a typical production deployment:

    1. Instance class (db.r6g.4xlarge Multi-AZ ≈ 2x single-AZ hourly rate)

    2. Storage (gp3 vs. io2 is a large cost difference at high IOPS provisioning)

    3. Data transfer (same-region same-AZ is free; cross-AZ data transfer is billed; cross-region is billed at a higher rate)

    4. Snapshot storage (retained backups beyond the automated window; cross-region snapshot copies)

    5. RDS Proxy (flat hourly charge per vCPU)

    6. Performance Insights extended retention (beyond 7 days)

    Immediate cost-reduction patterns that don't require re-architecting:

  • → Use **Reserved Instances** (1-year or 3-year) for production databases with predictable workloads. The discount versus on-demand pricing is substantial and consistent across instance families. Convertible Reserved Instances allow you to exchange instance family within the same region, which is valuable as you right-size.
  • → **Right-size with Performance Insights data** before committing to Reserved Instances. Look at `DBLoad` over 4–6 weeks; if average DBLoad is consistently below 2 on a db.r6g.4xlarge (which has 16 vCPUs), a db.r6g.2xlarge may be appropriate.
  • → **Aurora I/O-Optimized pricing** (available since mid-2023) bundles I/O costs into the instance price. If your Aurora cluster's I/O charges exceed roughly 25% of your total cluster cost, I/O-Optimized pricing reduces the total bill.
  • → Use **gp3 over gp2** for RDS if you haven't migrated yet — gp3 is the same or lower price per GB and allows IOPS configuration independent of capacity.
    • # Simple cost estimation helper for RDS instance sizing decision
# Uses boto3 to fetch current running config and CloudWatch metrics

import boto3
from datetime import datetime, timedelta, timezone

def estimate_rightsizing_opportunity(instance_id, region='us-east-1'):
    rds = boto3.client('rds', region_name=region)
    cw = boto3.client('cloudwatch', region_name=region)
    
    instance = rds.describe_db_instances(
        DBInstanceIdentifier=instance_id
    )['DBInstances'][0]
    
    instance_class = instance['DBInstanceClass']
    multi_az = instance['MultiAZ']
    
    print(f"Instance: {instance_id}")
    print(f"Class: {instance_class} | MultiAZ: {multi_az}")
    
    # Pull 7-day average CPU and memory metrics
    end_time = datetime.now(timezone.utc)
    start_time = end_time - timedelta(days=7)
    
    def get_metric_avg(metric_name):
        response = cw.get_metric_statistics(
            Namespace='AWS/RDS',
            MetricName=metric_name,
            Dimensions=[{'Name': 'DBInstanceIdentifier', 'Value': instance_id}],
            StartTime=start_time,
            EndTime=end_time,
            Period=3600,
            Statistics=['Average']
        )
        if response['Datapoints']:
            values = [dp['Average'] for dp in response['Datapoints']]
            return sum(values) / len(values)
        return None
    
    avg_cpu = get_metric_avg('CPUUtilization')
    avg_freeable_memory_mb = (get_metric_avg('FreeableMemory') or 0) / (1024 * 1024)
    avg_connections = get_metric_avg('DatabaseConnections')
    
    print(f"\n7-Day Averages:")
    print(f"  CPU Utilization: {avg_cpu:.1f}%" if avg_cpu else "  CPU: No data")
    print(f"  Freeable Memory: {avg_freeable_memory_mb:.0f} MB" if avg_freeable_memory_mb else "  Memory: No data")
    print(f"  Connections: {avg_connections:.0f}" if avg_connections else "  Connections: No data")
    
    # Heuristic recommendations
    if avg_cpu and avg_cpu < 20:
        print(f"\n  >> CPU consistently below 20% — consider downsizing instance class")
    if avg_freeable_memory_mb and avg_freeable_memory_mb > 8192:
        print(f"\n  >> Over 8GB consistently free — memory may be over-provisioned")
    if avg_cpu and avg_cpu > 75:
        print(f"\n  >> CPU consistently above 75% — consider upsizing or read replica offload")

estimate_rightsizing_opportunity('prod-postgres-primary')

    #### Cross-AZ Data Transfer Costs

    A hidden cost that regularly surprises teams moving from on-premises is cross-AZ data transfer. In AWS, traffic between Availability Zones is billed in both directions. If your application tier in us-east-1a queries an RDS instance in us-east-1b (common in Multi-AZ setups where the primary has failed over), every query response traverses AZ boundaries. The per-GB rate is modest, but at high query volumes it accumulates.

    The architectural mitigation is to ensure your application's Auto Scaling Group or ECS tasks are AZ-aware and prefer the same AZ as the current database primary when possible. This is practical only when you can detect which AZ the current primary is in (available via the RDS AvailabilityZone attribute from the API) and route accordingly. Most teams accept the cross-AZ transfer cost as the price of AZ-resilient architecture and focus cost optimization efforts on instance sizing and Reserved Instance coverage instead.

    Azure equivalent: Azure charges for data transfer between Availability Zones within a region similarly. Azure SQL with Private Endpoint generally keeps traffic within the VNet and minimizes unexpected egress charges, but inter-zone traffic between application VMs and Azure SQL in a different zone is still billed.

    GCP equivalent: Cloud SQL cross-zone traffic within a region follows GCP's standard inter-zone pricing, with the same general pattern: intra-region cross-zone is billed at a lower rate than inter-region, but it accumulates at scale.

    5.10 Extension and Feature Constraints by Cloud Provider

    #### Not All PostgreSQL Is the Same PostgreSQL

    A common misconception when migrating from self-managed PostgreSQL is that any PostgreSQL extension that compiles will work on RDS, Cloud SQL, or AlloyDB. The managed service controls which extensions are available, and the list differs meaningfully across providers. This affects schema migration, PostGIS deployments, and custom procedural language usage.

    RDS PostgreSQL has one of the most permissive extension lists among managed providers. Extensions are installed with CREATE EXTENSION and the available set is documented per engine version. Key extensions available on RDS: pg_stat_statements, pgaudit, pg_cron, PostGIS, uuid-ossp, btree_gin, btree_gist, pg_partman, aws_s3 (AWS-specific, for S3 import/export), aws_lambda (for invoking Lambda from PostgreSQL), vector (pgvector, for ML embedding similarity search).

    Extensions not available on RDS that require a self-managed PostgreSQL: anything requiring CREATE EXTENSION with superuser privileges not delegated to rds_superuser, custom shared libraries loaded via shared_preload_libraries that aren't on the approved list (you can't load your own .so file), and extensions that require OS-level access.

    -- Check available extensions on RDS PostgreSQL
SELECT 
    name,
    default_version,
    installed_version,
    comment
FROM pg_available_extensions
WHERE installed_version IS NOT NULL
   OR name IN (
       'pg_stat_statements',
       'pgaudit',
       'pg_cron',
       'postgis',
       'vector',
       'pg_partman',
       'aws_s3'
   )
ORDER BY name;

-- Install pgvector for ML embedding storage (available in RDS PostgreSQL 15+)
CREATE EXTENSION IF NOT EXISTS vector;

-- Verify installation
SELECT extname, extversion 
FROM pg_extension 
WHERE extname = 'vector';

-- Create a table using the vector type
CREATE TABLE document_embeddings (
    id          BIGSERIAL PRIMARY KEY,
    document_id BIGINT NOT NULL,
    content     TEXT,
    embedding   vector(1536),  -- OpenAI Ada-002 embedding dimension
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Create an IVFFlat index for approximate nearest-neighbor search
CREATE INDEX ON document_embeddings 
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

    Cloud SQL PostgreSQL has a somewhat more restricted extension list than RDS. PostGIS is fully supported. pg_cron is not available as of current versions — scheduled jobs must use Cloud Scheduler calling a Cloud Run function or a direct API call. pgaudit is available. pg_partman is not available; partition management must be handled through application logic or Cloud Scheduler–triggered stored procedures. The vector extension (pgvector) was added to Cloud SQL's extension support; check the current GCP documentation for the exact minimum Cloud SQL version that supports it, as availability was added after the initial pgvector release.

    AlloyDB for PostgreSQL is worth distinguishing from Cloud SQL: AlloyDB has a broader extension set and includes google_ml_integration, a proprietary extension that enables calling Vertex AI models directly from SQL — a feature that has no direct equivalent on RDS or Cloud SQL.

    -- AlloyDB: Call a Vertex AI model from SQL using google_ml_integration
-- (AlloyDB-specific; not available on Cloud SQL or RDS)
CREATE EXTENSION IF NOT EXISTS google_ml_integration;

-- Generate embeddings for text stored in a PostgreSQL table
SELECT 
    id,
    content,
    embedding('textembedding-gecko@003', content) AS text_embedding
FROM documents
LIMIT 10;

    Azure SQL (SQL Server) extension semantics are different — SQL Server doesn't use PostgreSQL's extension system. The Azure SQL equivalent constraint is which CLR assemblies are permitted, which linked server providers are available, and which features require SQL Server Agent (which runs in a limited form in Azure SQL). Full-text search, In-Memory OLTP, and columnstore indexes are fully available in Azure SQL. R and Python external scripts (sp_execute_external_script) are available in SQL Server on VMs but not in Azure SQL Database PaaS; for ML workloads in Azure SQL, you use Azure ML integration instead.

    Key Takeaways

  • → **Cloud HA is managed abstraction, not magic**: Aurora's shared-storage architecture gives sub-30-second failover with no data loss, while RDS Multi-AZ relies on DNS TTL propagation and requires application-side reconnect logic. Understanding the mechanism determines how you write your connection handling code.
  • → **Read replica lag is architecturally different across services**: Aurora replicas share the storage layer and show sub-20ms lag; RDS and Cloud SQL read replicas use asynchronous streaming replication and can show meaningful lag under write pressure. Use the right replica type for the consistency requirement of each read workload.
  • → **Storage scaling is one-directional and has operational windows**: RDS storage increases are permanent, and scaling a Multi-AZ instance triggers a failover cycle. Aurora storage auto-scales transparently but doesn't shrink. Model your storage growth trajectory before provisioning and prefer Aurora for workloads with unpredictable data volume growth.
  • → **Network isolation requires multiple layers**: VPC security groups (or NSGs in Azure) are necessary but not sufficient. Private Endpoint or PrivateLink is the production-standard connectivity pattern — public endpoints with IP allowlisting are not an equivalent security control. Validate that your application and DBA tooling can operate without public database access before deploying.
  • → **Extension and feature availability varies significantly across managed providers**: An extension-dependent architecture built on self-managed PostgreSQL may not port directly to any managed service. Audit your `pg_extension` list early in a cloud migration, check availability against the target provider's current documentation, and design mitigation patterns — application-layer alternatives, Cloud Scheduler–based replacements for `pg_cron`, or a provider switch — before the migration cutover.
