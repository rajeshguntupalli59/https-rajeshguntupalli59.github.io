Chapter 40: Building a Production Vector DB Monitoring Dashboard

Monitoring a vector database in production is not the same as monitoring a relational database. The familiar metrics—query throughput, lock waits, buffer hit ratio, replication lag—still matter when the underlying engine is PostgreSQL or a similar system, but they tell you nothing about the health of your embedding pipeline, the quality of your search results, or whether your index structures are serving queries efficiently under load. This chapter brings together everything from earlier in the book and shows you how to build a dashboard that covers all three layers: infrastructure metrics, vector-specific operational metrics, and application-layer quality signals. By the end, you will have runnable code for a Prometheus/Grafana stack that monitors pgvector, Pinecone, and Weaviate simultaneously, a Python-based quality probe that runs continuously against your RAG pipeline, and a pattern for surfacing drift and recall degradation before your users notice.

---

The Three-Layer Monitoring Model

Most teams start with infrastructure monitoring because it is familiar: CPU, memory, disk I/O, and connection counts. That baseline is necessary but insufficient for vector workloads. You need to think in three distinct layers, each requiring different instrumentation.

Layer 1 — Infrastructure and Engine Metrics

These are the metrics your existing tools already collect. For pgvector on PostgreSQL, that means pg_stat_statements, autovacuum activity, shared_buffers utilization, and WAL generation rate. For Pinecone, it means pod CPU and memory exposed through the Pinecone console API. For Weaviate, it means the built-in /v1/nodes endpoint and Prometheus scrape target.

Layer 2 — Vector Index Operational Metrics

These metrics are specific to the vector engine and have no direct SQL equivalent. Index build status, HNSW graph construction rate, quantization compression ratio, segment count, and—most importantly—approximate nearest neighbor (ANN) query latency at the 50th, 95th, and 99th percentiles. Think of the HNSW index as an analogy to a B-tree: just as you would monitor B-tree bloat and split frequency, you monitor HNSW graph connectivity and segment merger rates.

Layer 3 — Embedding and Search Quality Metrics

This layer has no equivalent in traditional database monitoring. It answers questions like: Are the embeddings being stored still aligned with the model that generated the query embeddings? Is the top-k recall degrading as new data is inserted without re-indexing? Are cosine similarity scores drifting toward lower values, indicating that the vector space is becoming less discriminative? These signals require synthetic probes—queries you run against the database with known expected results—and they need to run on a schedule, not just when a user complains.

*A Layer 3 failure — recall or similarity drift — typically shows up weeks before it cascades into a visible Layer 2 or Layer 1 problem, which is why quality probes matter as much as infrastructure dashboards.*

The architectural principle is that your dashboard should surface a failure at Layer 3 before it becomes visible at Layer 2, and a Layer 2 failure before it cascades to Layer 1. In practice, embedding drift shows up weeks before your HNSW index becomes so fragmented that query latency spikes.

Instrumenting pgvector with Prometheus and Custom Metrics

PostgreSQL does not expose vector-specific metrics natively. You need to instrument them yourself, either through a custom postgres_exporter configuration or by running a metrics collection script that queries system views and writes to a Prometheus pushgateway.

The following script collects the most important pgvector operational metrics and pushes them to a Prometheus pushgateway on a 60-second interval. It covers index status, approximate row counts per collection, and query latency histograms derived from pg_stat_statements.

# Python
# pgvector_metrics_collector.py
# Requires: psycopg2, prometheus_client, schedule

import time
import schedule
import psycopg2
import psycopg2.extras
from prometheus_client import (
    CollectorRegistry,
    Gauge,
    Histogram,
    push_to_gateway,
)

PUSHGATEWAY_URL = "http://localhost:9091"
PG_DSN = "host=localhost dbname=vectordb user=monitor password=monitor_pass"

registry = CollectorRegistry()

# Gauge: number of live rows per vector table
vector_table_row_count = Gauge(
    "pgvector_table_live_rows",
    "Estimated live row count for vector tables",
    ["table_name", "index_name"],
    registry=registry,
)

# Gauge: index size in bytes
vector_index_size_bytes = Gauge(
    "pgvector_index_size_bytes",
    "On-disk size of vector indexes",
    ["index_name", "table_name"],
    registry=registry,
)

# Gauge: HNSW index build progress (0=not building, 1=building)
vector_index_building = Gauge(
    "pgvector_index_building",
    "Whether an HNSW index is currently being built (1=yes)",
    ["index_name"],
    registry=registry,
)

# Histogram: ANN query latency from pg_stat_statements (p50, p95, p99)
vector_query_latency_ms = Gauge(
    "pgvector_ann_query_mean_latency_ms",
    "Mean latency in ms for ANN queries (from pg_stat_statements)",
    ["query_pattern"],
    registry=registry,
)

vector_query_calls_total = Gauge(
    "pgvector_ann_query_calls_total",
    "Total call count for ANN query patterns",
    ["query_pattern"],
    registry=registry,
)


def collect_metrics():
    conn = psycopg2.connect(PG_DSN)
    cur = conn.cursor(cursor_factory=psycopg2.extras.DictCursor)

    # Collect live row counts and index sizes for vector tables
    # Identify vector tables by looking for vector-typed columns
    cur.execute("""
        SELECT
            c.relname                          AS table_name,
            i.relname                          AS index_name,
            pg_relation_size(i.oid)            AS index_size_bytes,
            pg_stat_get_live_tuples(c.oid)     AS live_rows,
            am.amname                          AS index_method
        FROM
            pg_class c
            JOIN pg_index ix ON c.oid = ix.indrelid
            JOIN pg_class i  ON i.oid = ix.indexrelid
            JOIN pg_am am    ON i.relam = am.oid
            JOIN pg_attribute a ON a.attrelid = c.oid
                AND a.attnum = ANY(ix.indkey)
            JOIN pg_type t  ON a.atttypid = t.oid
        WHERE
            t.typname = 'vector'
            AND c.relkind = 'r'
            AND am.amname IN ('hnsw', 'ivfflat')
        ORDER BY
            c.relname, i.relname;
    """)
    rows = cur.fetchall()
    for row in rows:
        vector_table_row_count.labels(
            table_name=row["table_name"],
            index_name=row["index_name"],
        ).set(row["live_rows"])
        vector_index_size_bytes.labels(
            index_name=row["index_name"],
            table_name=row["table_name"],
        ).set(row["index_size_bytes"])

    # Detect in-progress index builds
    cur.execute("""
        SELECT
            relname AS index_name,
            phase,
            blocks_done,
            blocks_total
        FROM
            pg_stat_progress_create_index
        WHERE
            command = 'CREATE INDEX CONCURRENTLY'
            OR command = 'CREATE INDEX';
    """)
    building = cur.fetchall()
    # Reset all to 0 first, then set active ones
    for row in building:
        vector_index_building.labels(index_name=row["index_name"]).set(1)

    # ANN query latency from pg_stat_statements
    # Filter for queries that contain '<->' (L2), '<=>' (cosine), or '<#>' (inner product)
    cur.execute("""
        SELECT
            LEFT(query, 80)                             AS query_pattern,
            calls                                       AS total_calls,
            mean_exec_time                              AS mean_ms
        FROM
            pg_stat_statements
        WHERE
            query LIKE '%<->%'
            OR query LIKE '%<=>%'
            OR query LIKE '%<#>%'
        ORDER BY
            total_exec_time DESC
        LIMIT 20;
    """)
    query_rows = cur.fetchall()
    for qrow in query_rows:
        label = qrow["query_pattern"].strip().replace("\n", " ")[:60]
        vector_query_latency_ms.labels(query_pattern=label).set(qrow["mean_ms"])
        vector_query_calls_total.labels(query_pattern=label).set(qrow["total_calls"])

    cur.close()
    conn.close()

    push_to_gateway(
        PUSHGATEWAY_URL,
        job="pgvector_metrics",
        registry=registry,
    )
    print(f"[{time.strftime('%H:%M:%S')}] Metrics pushed to Prometheus gateway")


schedule.every(60).seconds.do(collect_metrics)

if __name__ == "__main__":
    collect_metrics()  # Run immediately on start
    while True:
        schedule.run_pending()
        time.sleep(1)

This script intentionally uses pg_stat_statements rather than wrapping every query with timing code. That means it captures the full query load from all connections, not just the ones your application explicitly instruments. The mean_exec_time from pg_stat_statements is a rolling mean since the last statistics reset; pair it with the calls counter and you can compute a rate-weighted average in Grafana.

For the Grafana dashboard, create a panel with this PromQL expression to show the top-5 slowest ANN query patterns:

# shell
# Prometheus query for Grafana panel: Top 5 slowest ANN query patterns
# Panel type: Table
# PromQL:
topk(5, pgvector_ann_query_mean_latency_ms)

# Panel type: Time series for index size growth
# PromQL:
rate(pgvector_index_size_bytes[5m]) * 300
# Multiplied by 300 seconds (5-minute interval) to get bytes added per scrape window

# Alert rule: ANN query latency exceeds 200ms mean
# In Prometheus alerting rules YAML:
# alert: VectorQueryLatencyHigh
# expr: pgvector_ann_query_mean_latency_ms > 200
# for: 5m
# labels:
#   severity: warning
# annotations:
#   summary: "ANN query mean latency > 200ms for {{ $labels.query_pattern }}"

Monitoring Pinecone and Weaviate via Their Native APIs

Pinecone and Weaviate expose operational metrics through REST APIs, but they each have different granularity and different concepts of what "healthy" means.

Pinecone Monitoring

Pinecone's Python client exposes describe_index_stats(), which gives you namespace-level vector counts and fullness. The fullness metric is the single most important operational signal for a pod-based Pinecone deployment: when it exceeds 0.90, query latency climbs steeply and inserts may fail.

# Python
# pinecone_metrics_collector.py
# Requires: pinecone-client>=3.0, prometheus_client

import os
import time
import schedule
from pinecone import Pinecone
from prometheus_client import (
    CollectorRegistry,
    Gauge,
    push_to_gateway,
)

PUSHGATEWAY_URL = "http://localhost:9091"
PINECONE_API_KEY = os.environ["PINECONE_API_KEY"]

pc = Pinecone(api_key=PINECONE_API_KEY)

registry = CollectorRegistry()

pinecone_vector_count = Gauge(
    "pinecone_namespace_vector_count",
    "Number of vectors in a Pinecone namespace",
    ["index_name", "namespace"],
    registry=registry,
)

pinecone_index_fullness = Gauge(
    "pinecone_index_fullness_ratio",
    "Index fullness ratio (0.0 to 1.0). Alert at > 0.85",
    ["index_name"],
    registry=registry,
)

pinecone_index_dimension = Gauge(
    "pinecone_index_dimension",
    "Vector dimension for a Pinecone index",
    ["index_name", "metric"],
    registry=registry,
)

pinecone_index_ready = Gauge(
    "pinecone_index_ready",
    "1 if the index state is Ready, 0 otherwise",
    ["index_name"],
    registry=registry,
)


def collect_pinecone_metrics():
    indexes = pc.list_indexes()

    for index_info in indexes:
        index_name = index_info.name
        idx = pc.Index(index_name)

        # Index status
        desc = pc.describe_index(index_name)
        is_ready = 1 if desc.status.ready else 0
        pinecone_index_ready.labels(index_name=index_name).set(is_ready)
        pinecone_index_dimension.labels(
            index_name=index_name,
            metric=desc.metric,
        ).set(desc.dimension)

        # Stats per namespace
        stats = idx.describe_index_stats()
        pinecone_index_fullness.labels(index_name=index_name).set(
            stats.index_fullness
        )

        for namespace, ns_stats in stats.namespaces.items():
            pinecone_vector_count.labels(
                index_name=index_name,
                namespace=namespace if namespace else "__default__",
            ).set(ns_stats.vector_count)

    push_to_gateway(
        PUSHGATEWAY_URL,
        job="pinecone_metrics",
        registry=registry,
    )
    print(f"[{time.strftime('%H:%M:%S')}] Pinecone metrics pushed")


schedule.every(30).seconds.do(collect_pinecone_metrics)

if __name__ == "__main__":
    collect_pinecone_metrics()
    while True:
        schedule.run_pending()
        time.sleep(1)

Weaviate Monitoring

Weaviate ships with a built-in Prometheus endpoint at http://:2112/metrics when you set PROMETHEUS_MONITORING_ENABLED=true in the environment. The native metrics cover object count, index segment count, vector dimension, and batch import throughput. Beyond those, you want to query the /v1/nodes REST endpoint for cluster health.

# Python
# weaviate_health_probe.py
# Requires: weaviate-client>=4.0, requests, prometheus_client

import os
import time
import requests
import schedule
import weaviate
from weaviate.classes.init import Auth
from prometheus_client import (
    CollectorRegistry,
    Gauge,
    push_to_gateway,
)

PUSHGATEWAY_URL = "http://localhost:9091"
WEAVIATE_URL = os.environ.get("WEAVIATE_URL", "http://localhost:8080")
WEAVIATE_API_KEY = os.environ.get("WEAVIATE_API_KEY", "")

registry = CollectorRegistry()

weaviate_node_status = Gauge(
    "weaviate_node_healthy",
    "1 if the Weaviate node is healthy",
    ["node_name"],
    registry=registry,
)

weaviate_object_count = Gauge(
    "weaviate_collection_object_count",
    "Number of objects in a Weaviate collection",
    ["collection_name", "node_name"],
    registry=registry,
)

weaviate_shard_count = Gauge(
    "weaviate_collection_shard_count",
    "Number of shards for a Weaviate collection",
    ["collection_name"],
    registry=registry,
)

weaviate_vector_index_queue_length = Gauge(
    "weaviate_async_index_queue_length",
    "Number of objects waiting to be indexed asynchronously",
    ["collection_name", "shard_name"],
    registry=registry,
)


def collect_weaviate_metrics():
    # Use REST directly for /v1/nodes — gives richer cluster info than client
    headers = {}
    if WEAVIATE_API_KEY:
        headers["Authorization"] = f"Bearer {WEAVIATE_API_KEY}"

    try:
        resp = requests.get(
            f"{WEAVIATE_URL}/v1/nodes",
            headers=headers,
            params={"output": "verbose"},
            timeout=10,
        )
        resp.raise_for_status()
        nodes_data = resp.json()
    except Exception as e:
        print(f"Failed to reach Weaviate nodes endpoint: {e}")
        return

    collection_shards: dict[str, int] = {}
    collection_objects: dict[tuple, int] = {}

    for node in nodes_data.get("nodes", []):
        node_name = node.get("name", "unknown")
        node_status = node.get("status", "UNHEALTHY")
        weaviate_node_status.labels(node_name=node_name).set(
            1 if node_status == "HEALTHY" else 0
        )

        for shard in node.get("shards", []) or []:
            coll_name = shard.get("class", "unknown")
            shard_name = shard.get("name", "unknown")
            obj_count = shard.get("objectCount", 0)
            queue_len = shard.get("vectorIndexingQueue", 0)

            collection_shards[coll_name] = (
                collection_shards.get(coll_name, 0) + 1
            )
            key = (coll_name, node_name)
            collection_objects[key] = collection_objects.get(key, 0) + obj_count

            weaviate_vector_index_queue_length.labels(
                collection_name=coll_name,
                shard_name=shard_name,
            ).set(queue_len)

    for (coll_name, node_name), count in collection_objects.items():
        weaviate_object_count.labels(
            collection_name=coll_name,
            node_name=node_name,
        ).set(count)

    for coll_name, shard_count in collection_shards.items():
        weaviate_shard_count.labels(collection_name=coll_name).set(shard_count)

    push_to_gateway(
        PUSHGATEWAY_URL,
        job="weaviate_metrics",
        registry=registry,
    )
    print(f"[{time.strftime('%H:%M:%S')}] Weaviate metrics pushed")


schedule.every(30).seconds.do(collect_weaviate_metrics)

if __name__ == "__main__":
    collect_weaviate_metrics()
    while True:
        schedule.run_pending()
        time.sleep(1)

The weaviate_async_index_queue_length metric is particularly important when using Weaviate's async indexing mode. A queue that grows monotonically without draining indicates that your import rate exceeds the indexing throughput—the vector equivalent of a replication lag that never catches up. Set an alert at queue depth > 50,000 for most workloads, and > 10,000 for latency-sensitive applications.

Embedding Quality and Recall Probes

Infrastructure metrics tell you whether your database is running. Quality probes tell you whether it is working. This distinction matters enormously for RAG applications because a system can show green on every infrastructure dashboard while silently returning wrong results.

The right way to implement quality probes is to maintain a golden dataset: a small set of queries (typically 50–200) for which you know the correct top-k results. These are generated once, stored in a separate table or file, and then replayed continuously. The probe computes recall@k—the fraction of expected results that appear in the actual results—and reports it as a metric.

# Python
# quality_probe.py
# Runs recall@10 probes against pgvector, Pinecone, and Weaviate
# Requires: psycopg2, pinecone-client>=3.0, weaviate-client>=4.0,
#           sentence-transformers, prometheus_client, numpy

import os
import json
import time
import numpy as np
import psycopg2
import psycopg2.extras
import schedule
import weaviate
import requests
from pinecone import Pinecone
from sentence_transformers import SentenceTransformer
from prometheus_client import (
    CollectorRegistry,
    Gauge,
    Histogram,
    push_to_gateway,
)

PUSHGATEWAY_URL = "http://localhost:9091"
GOLDEN_DATASET_PATH = "golden_queries.json"
EMBED_MODEL = "all-MiniLM-L6-v2"          # 384-dim, fast, good baseline
TOP_K = 10

# Load golden dataset once
# Format: [{"query": "...", "expected_ids": ["id1", "id2", ...], "collection": "docs"}]
with open(GOLDEN_DATASET_PATH) as f:
    golden_queries = json.load(f)

embedder = SentenceTransformer(EMBED_MODEL)

registry = CollectorRegistry()

recall_at_k = Gauge(
    "vector_search_recall_at_k",
    "Recall@K for a named golden query set",
    ["backend", "collection", "k"],
    registry=registry,
)

mean_similarity_score = Gauge(
    "vector_search_mean_top1_similarity",
    "Mean cosine similarity of the top-1 result across golden queries",
    ["backend", "collection"],
    registry=registry,
)

probe_latency_ms = Gauge(
    "vector_search_probe_latency_ms",
    "Mean query latency in ms during quality probe run",
    ["backend", "collection"],
    registry=registry,
)


# ─── pgvector probe ──────────────────────────────────────────────────────────

def probe_pgvector():
    conn = psycopg2.connect(os.environ["PG_DSN"])
    cur = conn.cursor(cursor_factory=psycopg2.extras.DictCursor)

    # Group golden queries by collection (maps to table name in pgvector)
    from itertools import groupby
    from operator import itemgetter

    grouped = {}
    for q in golden_queries:
        if q.get("backend", "pgvector") != "pgvector":
            continue
        coll = q["collection"]
        grouped.setdefault(coll, []).append(q)

    for collection, queries in grouped.items():
        recalls = []
        similarities = []
        latencies = []

        for gq in queries:
            query_vec = embedder.encode(gq["query"]).tolist()
            expected = set(gq["expected_ids"])

            t0 = time.perf_counter()
            cur.execute(
                f"""
                SELECT id, 1 - (embedding <=> %s::vector) AS cosine_sim
                FROM {collection}
                ORDER BY embedding <=> %s::vector
                LIMIT %s
                """,
                (query_vec, query_vec, TOP_K),
            )
            rows = cur.fetchall()
            elapsed_ms = (time.perf_counter() - t0) * 1000

            returned_ids = {str(r["id"]) for r in rows}
            hit_count = len(expected & returned_ids)
            recall = hit_count / len(expected) if expected else 0.0
            recalls.append(recall)

            if rows:
                similarities.append(rows[0]["cosine_sim"])
            latencies.append(elapsed_ms)

        recall_at_k.labels(
            backend="pgvector",
            collection=collection,
            k=str(TOP_K),
        ).set(np.mean(recalls))

        mean_similarity_score.labels(
            backend="pgvector",
            collection=collection,
        ).set(np.mean(similarities) if similarities else 0.0)

        probe_latency_ms.labels(
            backend="pgvector",
            collection=collection,
        ).set(np.mean(latencies))

    cur.close()
    conn.close()


# ─── Pinecone probe ───────────────────────────────────────────────────────────

def probe_pinecone():
    pc = Pinecone(api_key=os.environ["PINECONE_API_KEY"])

    grouped = {}
    for q in golden_queries:
        if q.get("backend", "pinecone") != "pinecone":
            continue
        coll = q["collection"]
        grouped.setdefault(coll, []).append(q)

    for index_name, queries in grouped.items():
        idx = pc.Index(index_name)
        recalls = []
        similarities = []
        latencies = []

        for gq in queries:
            query_vec = embedder.encode(gq["query"]).tolist()
            expected = set(gq["expected_ids"])
            namespace = gq.get("namespace", "")

            t0 = time.perf_counter()
            result = idx.query(
                vector=query_vec,
                top_k=TOP_K,
                namespace=namespace,
                include_metadata=False,
            )
            elapsed_ms = (time.perf_counter() - t0) * 1000

            returned_ids = {m.id for m in result.matches}
            hit_count = len(expected & returned_ids)
            recall = hit_count / len(expected) if expected else 0.0
            recalls.append(recall)

            if result.matches:
                similarities.append(result.matches[0].score)
            latencies.append(elapsed_ms)

        recall_at_k.labels(
            backend="pinecone",
            collection=index_name,
            k=str(TOP_K),
        ).set(np.mean(recalls))

        mean_similarity_score.labels(
            backend="pinecone",
            collection=index_name,
        ).set(np.mean(similarities) if similarities else 0.0)

        probe_latency_ms.labels(
            backend="pinecone",
            collection=index_name,
        ).set(np.mean(latencies))


# ─── Weaviate probe ───────────────────────────────────────────────────────────

def probe_weaviate():
    weaviate_url = os.environ.get("WEAVIATE_URL", "http://localhost:8080")
    weaviate_api_key = os.environ.get("WEAVIATE_API_KEY", "")
    headers = {}
    if weaviate_api_key:
        headers["Authorization"] = f"Bearer {weaviate_api_key}"

    grouped = {}
    for q in golden_queries:
        if q.get("backend", "weaviate") != "weaviate":
            continue
        coll = q["collection"]
        grouped.setdefault(coll, []).append(q)

    for collection_name, queries in grouped.items():
        recalls = []
        similarities = []
        latencies = []

        for gq in queries:
            query_vec = embedder.encode(gq["query"]).tolist()
            expected = set(gq["expected_ids"])

            # Use Weaviate's GraphQL nearVector API
            graphql_query = {
                "query": f"""
                {{
                  Get {{
                    {collection_name}(
                      nearVector: {{
                        vector: {json.dumps(query_vec)}
                        certainty: 0.0
                      }}
                      limit: {TOP_K}
                    ) {{
                      _additional {{
                        id
                        certainty
                      }}
                    }}
                  }}
                }}
                """
            }

            t0 = time.perf_counter()
            resp = requests.post(
                f"{weaviate_url}/v1/graphql",
                json=graphql_query,
                headers=headers,
                timeout=15,
            )
            elapsed_ms = (time.perf_counter() - t0) * 1000
            resp.raise_for_status()
            data = resp.json()

            objects = (
                data.get("data", {})
                    .get("Get", {})
                    .get(collection_name, []) or []
            )
            returned_ids = {
                obj["_additional"]["id"]
                for obj in objects
                if obj.get("_additional", {}).get("id")
            }
            hit_count = len(expected & returned_ids)
            recall = hit_count / len(expected) if expected else 0.0
            recalls.append(recall)

            if objects:
                top_certainty = objects[0].get("_additional", {}).get("certainty", 0.0)
                similarities.append(top_certainty)
            latencies.append(elapsed_ms)

        recall_at_k.labels(
            backend="weaviate",
            collection=collection_name,
            k=str(TOP_K),
        ).set(np.mean(recalls))

        mean_similarity_score.labels(
            backend="weaviate",
            collection=collection_name,
        ).set(np.mean(similarities) if similarities else 0.0)

        probe_latency_ms.labels(
            backend="weaviate",
            collection=collection_name,
        ).set(np.mean(latencies))


# ─── Orchestration ────────────────────────────────────────────────────────────

def run_all_probes():
    try:
        probe_pgvector()
    except Exception as e:
        print(f"pgvector probe failed: {e}")

    try:
        probe_pinecone()
    except Exception as e:
        print(f"Pinecone probe failed: {e}")

    try:
        probe_weaviate()
    except Exception as e:
        print(f"Weaviate probe failed: {e}")

    push_to_gateway(
        PUSHGATEWAY_URL,
        job="vector_quality_probes",
        registry=registry,
    )
    print(f"[{time.strftime('%H:%M:%S')}] Quality probe metrics pushed")


schedule.every(5).minutes.do(run_all_probes)

if __name__ == "__main__":
    run_all_probes()
    while True:
        schedule.run_pending()
        time.sleep(1)

Building the Golden Dataset

The quality probe is only as good as the dataset it runs against. Building that dataset correctly is the step most teams skip, and skipping it is why they discover recall regressions from user complaints rather than from dashboards.

The golden dataset should satisfy three properties:

Coverage: Queries should represent the real distribution of production queries. If your RAG application handles product support questions, customer onboarding topics, and billing inquiries in roughly equal measure, your golden set should reflect those proportions. Capture 30 days of production query logs, cluster them by topic using k-means on their embeddings, then sample representative queries from each cluster.

Stability: The expected results must be verified by a human or by a higher-quality reference retrieval system, not by your production system at a point in time. If you generate ground truth by querying your own system and storing what it returns, you are measuring consistency, not correctness. Run your golden queries against a re-ranked or BM25+vector hybrid result set, review the top-10 by hand for a sample, and store verified IDs.

Versioning: When you upgrade your embedding model, your golden dataset expected IDs become invalid because the same document will have a different ID if it was re-embedded and re-inserted, or a different vector if the document ID is stable but the model changed. Tag each golden query with the embedding model version that was used to generate both the query embedding and the document embeddings. When you rotate models, regenerate the golden set for the new model in parallel before cutting over.

The following SQL creates the golden dataset table in PostgreSQL:

-- PostgreSQL
-- Schema for the golden query dataset

CREATE TABLE monitoring.golden_queries (
    id              SERIAL PRIMARY KEY,
    query_text      TEXT        NOT NULL,
    backend         TEXT        NOT NULL CHECK (backend IN ('pgvector', 'pinecone', 'weaviate')),
    collection_name TEXT        NOT NULL,
    namespace       TEXT,
    embedding_model TEXT        NOT NULL,
    expected_ids    TEXT[]      NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    retired_at      TIMESTAMPTZ,
    notes           TEXT
);

CREATE INDEX ON monitoring.golden_queries (backend, collection_name)
    WHERE retired_at IS NULL;

COMMENT ON TABLE monitoring.golden_queries IS
    'Ground-truth query/result pairs for continuous recall monitoring. '
    'Retire rows (set retired_at) when embedding model changes; do not delete.';
-- SQL Server
-- Schema for the golden query dataset

CREATE TABLE monitoring.golden_queries (
    id              INT IDENTITY(1,1) PRIMARY KEY,
    query_text      NVARCHAR(MAX)   NOT NULL,
    backend         NVARCHAR(20)    NOT NULL
        CHECK (backend IN ('pgvector', 'pinecone', 'weaviate')),
    collection_name NVARCHAR(256)   NOT NULL,
    namespace       NVARCHAR(256)   NULL,
    embedding_model NVARCHAR(128)   NOT NULL,
    -- SQL Server has no native array type; store as JSON
    expected_ids    NVARCHAR(MAX)   NOT NULL
        CHECK (ISJSON(expected_ids) = 1),
    created_at      DATETIMEOFFSET  NOT NULL DEFAULT SYSDATETIMEOFFSET(),
    retired_at      DATETIMEOFFSET  NULL,
    notes           NVARCHAR(MAX)   NULL
);

CREATE INDEX IX_golden_queries_backend_collection
    ON monitoring.golden_queries (backend, collection_name)
    WHERE retired_at IS NULL;

Note that SQL Server does not have a native array column type, so expected_ids is stored as a JSON string (e.g., '["id1","id2"]') and the ISJSON check constraint validates the format. Your probe code reads from this table and deserializes accordingly.

Alerting Rules and Escalation Thresholds

Collecting metrics is only half the problem. The other half is deciding when to page someone versus when to log a warning and move on. The thresholds below are starting points calibrated for a production RAG application with moderate query volume; you will tune them based on your baseline.

Recall degradation alert: Fire a warning when vector_search_recall_at_k (for any backend or collection) drops below 0.80 for two consecutive probe cycles. Fire a critical alert when it drops below 0.65. A drop from your established baseline of, say, 0.92 to 0.85 warrants investigation; a drop to below 0.65 typically indicates a model mismatch or index corruption that affects users now.

Index fullness alert (Pinecone): Warning at 0.80 fullness; critical at 0.90. Above 0.90, Pinecone pod-based indexes begin rejecting upserts silently in some configurations. Scale your pods before hitting this threshold.

Async indexing queue alert (Weaviate): Warning when weaviate_async_index_queue_length exceeds 25,000 for more than 10 minutes. Critical when it exceeds 100,000. At high queue depths, newly inserted objects are searchable via object lookup but not yet via vector similarity—users may see recently-uploaded documents missing from search results.

ANN query latency alert (pgvector): Warning when pgvector_ann_query_mean_latency_ms exceeds 150ms; critical at 500ms. The primary causes are: (1) HNSW ef_search set too high for the current load, (2) shared_buffers too small to keep the HNSW graph in memory, or (3) concurrent index builds competing for I/O.

Similarity score drift: Track the 7-day rolling mean of vector_search_mean_top1_similarity. If it drops more than 0.08 below the 30-day baseline, emit a warning. Gradual similarity score decline with no change in recall usually means your corpus is becoming more heterogeneous—new document categories whose embeddings populate different regions of the vector space, pulling average top-1 similarity down without reducing accuracy. Sudden drops in both recall and similarity together almost always indicate an embedding model change was applied to queries but not to stored documents.

The Prometheus alerting rules YAML for the recall and latency alerts:

      - alert: PgvectorANNLatencyCritical

Handling Embedding Model Rotation

One operational scenario that defeats most monitoring setups is an embedding model rotation: the moment when your team switches from one model (say, text-embedding-ada-002 at 1536 dimensions) to another (say, a fine-tuned 768-dimension model). The transition period creates a mixed-state problem where some documents use the old embeddings and some use the new, and queries always use one or the other, never both.

Your monitoring dashboard needs to detect this state explicitly. The most reliable signal is a sudden change in vector_search_mean_top1_similarity combined with a drop in vector_search_recall_at_k. Similarity alone is ambiguous—a new model in a new vector space has different absolute similarity scales. Recall dropping while the system appears operationally healthy is the diagnostic signature of a model mismatch.

The operational procedure for a safe model rotation:

1. Create a new collection/index alongside the existing one. Never overwrite in-place.

2. Run dual-write: new documents are embedded with both models and inserted into both collections.

3. Re-embed the corpus in the new collection using a background job. Track progress with a dedicated Prometheus gauge (embedding_backfill_progress_ratio, embedding_backfill_rows_complete, embedding_backfill_rows_total).

4. Promote the new collection as the read target only when embedding_backfill_progress_ratio >= 1.0 AND vector_search_recall_at_k (measured against a golden set generated with the new model) exceeds your baseline threshold.

5. Retire the old collection after a soak period of at least 72 hours with no recall alerts.

# Python
# backfill_progress_tracker.py
# Reports embedding backfill progress as a Prometheus metric

import os
import time
import psycopg2
import schedule
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

PUSHGATEWAY_URL = "http://localhost:9091"
registry = CollectorRegistry()

backfill_progress = Gauge(
    "embedding_backfill_progress_ratio",
    "Fraction of rows re-embedded for a collection (0.0 to 1.0)",
    ["collection_name", "new_model"],
    registry=registry,
)

backfill_rows_complete = Gauge(
    "embedding_backfill_rows_complete",
    "Count of rows that have been re-embedded",
    ["collection_name", "new_model"],
    registry=registry,
)

backfill_rows_total = Gauge(
    "embedding_backfill_rows_total",
    "Total rows to re-embed for the collection",
    ["collection_name", "new_model"],
    registry=registry,
)


def collect_backfill_metrics():
    conn = psycopg2.connect(os.environ["PG_DSN"])
    cur = conn.cursor()

    # This query assumes a backfill_status table that your backfill job maintains
    cur.execute("""
        SELECT
            collection_name,
            new_model,
            rows_complete,
            rows_total,
            CASE WHEN rows_total > 0
                 THEN rows_complete::float / rows_total
                 ELSE 0
            END AS progress_ratio
        FROM
            monitoring.embedding_backfill_status
        WHERE
            completed_at IS NULL;
    """)
    for row in cur.fetchall():
        coll, model, done, total, ratio = row
        backfill_progress.labels(collection_name=coll, new_model=model).set(ratio)
        backfill_rows_complete.labels(collection_name=coll, new_model=model).set(done)
        backfill_rows_total.labels(collection_name=coll, new_model=model).set(total)

    cur.close()
    conn.close()

    push_to_gateway(PUSHGATEWAY_URL, job="backfill_progress", registry=registry)


schedule.every(30).seconds.do(collect_backfill_metrics)

if __name__ == "__main__":
    collect_backfill_metrics()
    while True:
        schedule.run_pending()
        time.sleep(1)

Key Takeaways

  • → **Three-layer monitoring is non-negotiable for vector workloads.** Infrastructure metrics alone will not show you recall degradation or embedding drift. You need Layer 1 (infrastructure), Layer 2 (vector index operations), and Layer 3 (embedding quality probes) running simultaneously before problems become user-visible.
  • → **The golden dataset is your most valuable monitoring asset.** A set of 50–200 human-verified query/result pairs, tagged by embedding model version, lets you compute recall@k continuously. Build it early, version it carefully, and regenerate it whenever you rotate embedding models.
  • → **Pinecone fullness, Weaviate async queue depth, and pgvector HNSW latency are the three backend-specific metrics that most directly predict user-facing degradation.** Alert on them with two-tier thresholds (warning and critical) so on-call engineers can act before users are affected.
  • → **Embedding model rotation is the highest-risk operational event in a vector database's lifecycle.** A mixed-state corpus—some documents on the old model, some on the new—will degrade recall quietly and systematically. The safe pattern is: create a parallel collection, dual-write, backfill, measure recall against a new-model golden set, then promote. Never overwrite in-place.
  • → **Continuous quality probes make the invisible visible.** Cosine similarity score drift and recall degradation are silent failures. A probe that runs every five minutes against your golden dataset and pushes recall and similarity metrics to Prometheus gives you a continuous signal that your search system is doing what it was built to do—something no infrastructure metric can tell you.
