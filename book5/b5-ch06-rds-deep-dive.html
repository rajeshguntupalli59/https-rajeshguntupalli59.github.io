Chapter 6 of 40 The Cloud Database Engineer

Chapter 6: RDS Deep Dive: Engines, Instance Types, and Storage

Amazon RDS is where most DBAs begin their cloud journey, and for good reason — it takes the engines you already know (PostgreSQL, MySQL, SQL Server, Oracle) and wraps them in a managed layer that handles provisioning, patching, and backups. But "managed" does not mean "transparent." The choices you make about engine version, instance family, and storage type have cascading effects on performance, cost, and operational flexibility that cannot be undone without downtime or data migration. This chapter breaks down those choices with the specificity that production systems demand: which instance families to use and why, how RDS storage behaves differently from what you know on-premises, where the hard limits are, and what you give up when AWS takes over the OS layer.

---

6.1 Engine Selection and Version Strategy

RDS supports six database engines: MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server, and Amazon Aurora (which gets its own chapter, but shares the RDS console). Each engine runs on a managed EC2 instance underneath, and the distinction between "RDS for PostgreSQL" and "self-managed PostgreSQL on EC2" is not just operational convenience — it represents a fundamental trade-off in control.

What you lose versus self-managed PostgreSQL on EC2:

  • → No OS-level access. You cannot SSH into the underlying host.
  • → No `pg_hba.conf` direct editing. Authentication rules are enforced through security groups, IAM database authentication, and SSL certificate requirements set via parameter groups.
  • → No superuser. The `rds_superuser` role grants most capabilities, but it is not true superuser — you cannot load arbitrary shared libraries, and you cannot access system catalogs in ways that require true OS-level privilege.
  • → No WAL archive access. You can enable WAL archiving to S3 for logical replication, but you cannot read the raw WAL files directly.
  • → No `pg_basebackup` from the instance. Backups are managed by RDS using EBS snapshots.

    • What you gain:

  • → Automated backups with point-in-time recovery (PITR) up to 35 days.
  • → Automated minor version upgrades on a configurable maintenance window.
  • → Multi-AZ failover handled by the platform without you managing Pacemaker or Patroni.
  • → Monitoring metrics surfaced through CloudWatch without running exporters.

    • Engine version selection is not just about features — it determines your upgrade path. RDS maintains a list of supported minor versions, and AWS periodically deprecates older ones, issuing mandatory upgrades. PostgreSQL 11 reached end of life on AWS in 2023 and instances still running it received forced upgrades. You should never run more than one major version behind current in production.

    Check available versions before provisioning:

    # List all available PostgreSQL engine versions in us-east-1
aws rds describe-db-engine-versions \
  --engine postgres \
  --query 'DBEngineVersions[*].[EngineVersion,DBEngineVersionDescription]' \
  --output table \
  --region us-east-1

# Check which versions support a specific feature (e.g., Kerberos auth)
aws rds describe-db-engine-versions \
  --engine postgres \
  --query 'DBEngineVersions[?contains(SupportedFeatureNames, `kerberos`) == `true`].[EngineVersion]' \
  --output text \
  --region us-east-1

    SQL Server licensing deserves separate attention. RDS SQL Server offers two licensing models: License Included (LI) and Bring Your Own License (BYOL). License Included is available for Standard and Enterprise editions, with the license cost embedded in the hourly rate. Enterprise edition on a large instance class adds a substantial license-included premium to the hourly rate — check current AWS pricing for the specific instance class and edition. If your organization already has SQL Server Enterprise Agreement licenses, BYOL reduces that cost significantly — but BYOL requires Software Assurance, and AWS audits eligibility.

    Oracle on RDS follows the same LI vs. BYOL model. Oracle Enterprise Edition is only available as BYOL. Standard Edition 2 is available as License Included. The moment you need features like Partitioning, Advanced Compression, or Real Application Testing, you're in Enterprise Edition territory, which means BYOL and your own Oracle licensing agreement.

    Version pinning strategy: In production, pin your minor version explicitly. Do not enable auto minor version upgrade on database instances that have application dependencies on specific behavior (pg_catalog views changed significantly between PostgreSQL 13 and 14, for example). Enable auto minor version upgrade only on development and QA instances.

    # Disable auto minor version upgrade on an existing instance
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-01 \
  --no-auto-minor-version-upgrade \
  --apply-immediately \
  --region us-east-1

# Verify the change
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-01 \
  --query 'DBInstances[0].AutoMinorVersionUpgrade' \
  --region us-east-1

    6.2 Instance Families and Sizing

    The RDS instance naming convention follows the same pattern as EC2: db.{family}{generation}.{size}. Understanding the family is more important than the size, because each family has different CPU architecture, memory ratios, and network characteristics.

    Current generation families:

    | Family | vCPU:Memory Ratio | Use Case | Example |

    |--------|-------------------|----------|---------|

    | db.t4g | Burstable, 1:2 | Dev/test, small workloads | db.t4g.medium: 2 vCPU, 4 GB |

    | db.m7g | General purpose, 1:4 | Web applications, moderate OLTP | db.m7g.4xlarge: 16 vCPU, 64 GB |

    | db.r7g | Memory optimized, 1:8 | Large buffers, analytics | db.r7g.8xlarge: 32 vCPU, 256 GB |

    | db.r7i | Memory optimized, Intel | SQL Server (no ARM support) | db.r7i.16xlarge: 64 vCPU, 512 GB |

    | db.x2idn | Memory intensive, 1:32 | SAP HANA, large in-memory | db.x2idn.16xlarge: 64 vCPU, 2048 GB |

    The g suffix means Graviton (ARM-based). Graviton instances offer 10–20% better price-performance for PostgreSQL and MySQL workloads compared to equivalent Intel or AMD instances. The catch: SQL Server and Oracle are not supported on Graviton because AWS cannot run those binaries on ARM. PostgreSQL and MySQL have native ARM builds that run well on Graviton.

    T-series instances (burstable) in production: The T-series uses CPU credits. When the instance is idle, it accumulates credits. Under sustained load, it burns through credits and throttles to its baseline CPU (which is 20–40% of nominal). This behavior is catastrophic for production OLTP workloads that have sustained query pressure. The only legitimate production use of T-series is for small read replicas with light traffic, or internal tooling databases with infrequent queries.

    You can detect credit exhaustion in CloudWatch:

    # Check CPU credit balance for a burstable instance
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name CPUCreditBalance \
  --dimensions Name=DBInstanceIdentifier,Value=dev-postgres-t4g \
  --start-time 2024-01-15T00:00:00Z \
  --end-time 2024-01-15T23:59:59Z \
  --period 3600 \
  --statistics Minimum \
  --output table

# Also check CPU credit usage rate
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name CPUCreditUsage \
  --dimensions Name=DBInstanceIdentifier,Value=dev-postgres-t4g \
  --start-time 2024-01-15T00:00:00Z \
  --end-time 2024-01-15T23:59:59Z \
  --period 3600 \
  --statistics Sum \
  --output table

    Sizing recommendations for PostgreSQL migration: When migrating a self-managed PostgreSQL instance, the most important metric from your source system is shared_buffers utilization — specifically, what fraction of your working set fits in the buffer cache. On RDS, shared_buffers defaults to 25% of instance memory for PostgreSQL. A db.r7g.4xlarge has 128 GB of RAM, giving you ~32 GB of shared_buffers. If your on-premises system has a 40 GB buffer pool with reasonable hit rates, move to db.r7g.8xlarge (256 GB RAM, ~64 GB shared_buffers) with headroom.

    The right way to size using actual database metrics:

    -- Run this on your SOURCE PostgreSQL instance before migration
-- to understand buffer cache behavior

-- Buffer hit rate (should be >95% in production)
SELECT 
    sum(heap_blks_hit) AS heap_hits,
    sum(heap_blks_read) AS heap_reads,
    round(
        sum(heap_blks_hit)::numeric / 
        nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) * 100, 2
    ) AS buffer_hit_rate_pct
FROM pg_statio_user_tables;

-- Working set estimate: tables + indexes that fit in cache
SELECT 
    schemaname,
    relname AS table_name,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||relname)) AS total_size,
    round(
        heap_blks_hit::numeric / nullif(heap_blks_hit + heap_blks_read, 0) * 100, 1
    ) AS table_hit_rate_pct
FROM pg_statio_user_tables
WHERE heap_blks_hit + heap_blks_read > 10000
ORDER BY pg_total_relation_size(schemaname||'.'||relname) DESC
LIMIT 20;

-- Identify tables causing physical reads (candidates for shared_buffers increase)
SELECT 
    schemaname,
    relname,
    heap_blks_read AS physical_reads,
    heap_blks_hit AS cache_hits
FROM pg_statio_user_tables
WHERE heap_blks_read > 1000
ORDER BY heap_blks_read DESC
LIMIT 10;

    Changing instance class: RDS instance class changes require a reboot. On Single-AZ, this means downtime of 3–10 minutes. On Multi-AZ, AWS performs the change on the standby first, then fails over — total visible downtime is typically 30–120 seconds for the failover. Plan instance resizing during low-traffic windows regardless of Multi-AZ, because the failover itself causes connection drops.

    6.3 RDS Storage: gp2, gp3, io1, io2, and Magnetic

    Storage in RDS is EBS-backed, and the storage type you choose determines IOPS characteristics, throughput ceilings, and cost. Getting this wrong is the most common cause of RDS performance problems, because storage bottlenecks in managed services are much harder to diagnose than on-premises where you can run iostat directly.

    Available storage types:

    gp2 (General Purpose SSD): The legacy default. Delivers 3 IOPS per GB of storage, with a burst pool for volumes under 1 TB. A 100 GB gp2 volume gets 300 IOPS baseline with burst to 3,000 IOPS using credits (same credit model as T-series CPU). Above roughly 5.3 TB (where 3 IOPS/GB reaches the 16,000 IOPS ceiling), you get the full ceiling without burst dependency. Maximum throughput: 250 MB/s. Do not use gp2 for new deployments — it has been superseded entirely by gp3.

    gp3 (General Purpose SSD v2): The current recommended default. Provides a baseline of 3,000 IOPS and 125 MB/s throughput regardless of volume size. You can independently provision additional IOPS up to 16,000 and throughput up to 1,000 MB/s at additional cost. A 100 GB gp3 volume gets 3,000 IOPS — the same as a 1 TB gp2 volume, at one-tenth the storage cost. For most OLTP workloads under 16,000 IOPS, gp3 is the right choice.

    io1 (Provisioned IOPS SSD): Allows IOPS provisioning independent of storage size, up to 64,000 IOPS on supported instance types. Maximum throughput: 1,000 MB/s. More expensive than gp3 for the same IOPS level. io1 made sense before gp3 existed; today, it's primarily for workloads needing more IOPS than gp3 provides but that don't require io2's higher durability or ceiling.

    io2 (Provisioned IOPS SSD v2): Higher durability (99.999% vs 99.8% for io1), same IOPS ceiling. For SQL Server and Oracle, io2 supports up to 256,000 IOPS. For most PostgreSQL and MySQL workloads, gp3 with provisioned IOPS is sufficient and cheaper.

    Magnetic (standard): Legacy spinning disk. Do not use this for any workload. It exists only for backward compatibility.

    Storage autoscaling: RDS supports automatic storage scaling. When free storage drops below 10% of allocated storage (or below 5 GB, whichever is smaller), RDS automatically increases storage. Autoscaling only increases storage — it never shrinks it. You cannot reduce allocated storage on an RDS instance without creating a new instance and migrating data. Set your initial storage thoughtfully; you will pay for every GB permanently.

    Configure a new PostgreSQL instance with gp3 and autoscaling via Terraform:

    # terraform/rds_instance.tf
# Production PostgreSQL RDS with gp3 storage and appropriate settings

resource "aws_db_instance" "prod_postgres" {
  identifier        = "prod-postgres-primary"
  engine            = "postgres"
  engine_version    = "16.3"
  instance_class    = "db.r7g.4xlarge"

  # Storage configuration
  storage_type          = "gp3"
  allocated_storage     = 500          # GB - initial allocation
  max_allocated_storage = 2000         # GB - autoscaling ceiling
  iops                  = 12000        # Additional provisioned IOPS above gp3 baseline (3000)
  storage_throughput    = 500          # MB/s - above gp3 baseline (125 MB/s)
  storage_encrypted     = true
  kms_key_id            = aws_kms_key.rds_encryption.arn

  # Engine configuration
  db_name  = "appdb"
  username = "dbadmin"
  password = var.db_password   # Use Secrets Manager in production

  # High availability
  multi_az               = true
  availability_zone      = "us-east-1a"   # for single-AZ; ignored when multi_az=true

  # Backup and maintenance
  backup_retention_period = 14
  backup_window           = "03:00-04:00"
  maintenance_window      = "sun:04:30-sun:05:30"
  deletion_protection     = true

  # Network
  db_subnet_group_name   = aws_db_subnet_group.private.name
  vpc_security_group_ids = [aws_security_group.rds_postgres.id]
  publicly_accessible    = false

  # Parameter and option groups
  parameter_group_name = aws_db_parameter_group.postgres16_prod.name

  # Monitoring
  monitoring_interval             = 60   # Enhanced monitoring every 60 seconds
  monitoring_role_arn             = aws_iam_role.rds_enhanced_monitoring.arn
  performance_insights_enabled    = true
  performance_insights_retention_period = 731  # 2 years

  # Upgrade behavior
  auto_minor_version_upgrade = false
  apply_immediately          = false   # Apply changes during maintenance window

  tags = {
    Environment = "production"
    Team        = "platform-db"
    CostCenter  = "engineering"
  }
}

resource "aws_db_parameter_group" "postgres16_prod" {
  name   = "postgres16-prod"
  family = "postgres16"

  parameter {
    name  = "shared_buffers"
    value = "{DBInstanceClassMemory/4}"   # 25% of instance memory
  }

  parameter {
    name  = "effective_cache_size"
    value = "{DBInstanceClassMemory*3/4}"
  }

  parameter {
    name  = "max_connections"
    value = "500"
  }

  parameter {
    name  = "log_min_duration_statement"
    value = "1000"  # Log queries over 1 second
  }

  parameter {
    name  = "log_checkpoints"
    value = "1"
  }

  parameter {
    name  = "log_lock_waits"
    value = "1"
  }

  parameter {
    name  = "track_io_timing"
    value = "1"
  }

  parameter {
    name  = "pg_stat_statements.track"
    value = "all"
  }

  parameter {
    name  = "rds.log_retention_period"
    value = "10080"   # 7 days in minutes
  }
}

    IOPS math for production sizing: On gp3, the baseline 3,000 IOPS costs nothing extra, and each additional IOPS above that baseline is billed incrementally — check current AWS pricing for the exact rate, since it changes. Provisioned IOPS on io1/io2 are billed per-IOPS-month at a materially higher rate than gp3's incremental IOPS pricing, which is why gp3 is the default recommendation for most workloads that don't need io2's higher ceiling or durability.

    Monitoring storage saturation in CloudWatch:

    # Check storage I/O metrics for an RDS instance
# ReadIOPS and WriteIOPS tell you current throughput
# ReadLatency and WriteLatency tell you if storage is saturating

aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ReadLatency \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-primary \
  --start-time 2024-01-15T09:00:00Z \
  --end-time 2024-01-15T10:00:00Z \
  --period 60 \
  --statistics Average Maximum \
  --output table

# DiskQueueDepth > 1 consistently indicates storage saturation
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name DiskQueueDepth \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-primary \
  --start-time 2024-01-15T09:00:00Z \
  --end-time 2024-01-15T10:00:00Z \
  --period 60 \
  --statistics Average Maximum \
  --output table

    If DiskQueueDepth averages above 1 and WriteLatency exceeds 10ms consistently, your provisioned IOPS are insufficient. Increase provisioned IOPS without downtime on gp3 — the change is applied immediately (though it takes up to 6 hours for the modification to complete depending on volume size).

    The storage full emergency: RDS will put your database in read-only mode when storage reaches 100%. At that point, you cannot write data including WAL. The sequence of events is: free storage drops → autoscaling triggers (if enabled) → scaling takes 5–15 minutes → if autoscaling is not enabled or is at ceiling, the database goes read-only. Set a CloudWatch alarm at 20% free storage, not 10%, so you have time to respond before hitting autoscaling or the ceiling.

    6.4 Parameter Groups: The Replacement for postgresql.conf

    On a self-managed PostgreSQL instance, you edit /etc/postgresql/16/main/postgresql.conf directly and reload with SELECT pg_reload_conf() or restart the service. On RDS, that file is read-only. All configuration changes go through Parameter Groups — a named collection of configuration values that you associate with one or more DB instances.

    There are two types: DB Parameter Groups (instance-level) and DB Cluster Parameter Groups (Aurora cluster-level). For non-Aurora RDS, you use DB Parameter Groups.

    A parameter group has a family (e.g., postgres16, mysql8.0, sqlserver-se-15.0) and contains every configurable parameter for that engine version. AWS ships a default.postgres16 parameter group that contains AWS-optimized defaults. You cannot modify the default group — you must create a custom one and attach it to your instance.

    Parameters have two apply types:

  • → **Static:** Requires a database restart to take effect. Examples: `shared_buffers`, `max_connections`, `wal_level`.
  • → **Dynamic:** Takes effect immediately on `apply_immediately` or after the maintenance window. Examples: `log_min_duration_statement`, `effective_cache_size`, `work_mem`.

    • Common PostgreSQL parameter customizations for RDS:

    # Create a custom parameter group and configure key parameters

aws rds create-db-parameter-group \
  --db-parameter-group-name postgres16-prod \
  --db-parameter-group-family postgres16 \
  --description "Production PostgreSQL 16 parameters" \
  --region us-east-1

# Apply multiple parameters in one call
aws rds modify-db-parameter-group \
  --db-parameter-group-name postgres16-prod \
  --parameters \
    "ParameterName=log_min_duration_statement,ParameterValue=1000,ApplyMethod=immediate" \
    "ParameterName=log_checkpoints,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=log_lock_waits,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=track_io_timing,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=work_mem,ParameterValue=16384,ApplyMethod=immediate" \
    "ParameterName=maintenance_work_mem,ParameterValue=262144,ApplyMethod=immediate" \
    "ParameterName=checkpoint_completion_target,ParameterValue=0.9,ApplyMethod=immediate" \
    "ParameterName=random_page_cost,ParameterValue=1.1,ApplyMethod=immediate" \
  --region us-east-1

# Static parameters require pending reboot — apply these separately
aws rds modify-db-parameter-group \
  --db-parameter-group-name postgres16-prod \
  --parameters \
    "ParameterName=max_connections,ParameterValue=500,ApplyMethod=pending-reboot" \
    "ParameterName=wal_level,ParameterValue=logical,ApplyMethod=pending-reboot" \
    "ParameterName=max_replication_slots,ParameterValue=10,ApplyMethod=pending-reboot" \
    "ParameterName=max_wal_senders,ParameterValue=10,ApplyMethod=pending-reboot" \
  --region us-east-1

# Apply the parameter group to the instance (takes effect after maintenance window
# unless you use --apply-immediately, which causes a brief interruption)
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-primary \
  --db-parameter-group-name postgres16-prod \
  --region us-east-1

    Verifying parameter group status: After applying a parameter group, check whether the instance requires a reboot for any parameters to take effect:

    # Check for pending reboot parameters
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-primary \
  --query 'DBInstances[0].DBParameterGroups' \
  --region us-east-1

    The response includes a ParameterApplyStatus field. A value of pending-reboot means at least one static parameter has been changed and the instance must be restarted before it takes effect. A value of in-sync means all parameters are active.

    You can also verify parameter values from inside PostgreSQL after applying:

    -- PostgreSQL: Check current effective values of key parameters
SELECT name, setting, unit, context, source
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'work_mem',
    'maintenance_work_mem',
    'max_connections',
    'effective_cache_size',
    'checkpoint_completion_target',
    'random_page_cost',
    'wal_level',
    'track_io_timing',
    'log_min_duration_statement'
)
ORDER BY name;

-- Check which parameters are still using default values vs. customized
SELECT name, setting, boot_val, reset_val, source
FROM pg_settings
WHERE source != 'default'
  AND source != 'override'
ORDER BY name;

    For SQL Server on RDS, parameter groups work somewhat differently. SQL Server exposes fewer runtime-adjustable parameters through the RDS parameter group interface than PostgreSQL does. Many SQL Server settings that you'd configure via sp_configure on a self-managed instance are either fixed by RDS, exposed as parameter group settings, or must be set at the database level.

    SQL Server parameter group equivalent — key settings:

    -- SQL Server: Check current sp_configure settings on RDS
-- (These reflect what RDS has applied from the parameter group)
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

EXEC sp_configure;
GO

-- Check settings that affect query performance
SELECT 
    name,
    value,
    value_in_use,
    description
FROM sys.configurations
WHERE name IN (
    'max degree of parallelism',
    'cost threshold for parallelism',
    'max server memory (MB)',
    'min server memory (MB)',
    'optimize for ad hoc workloads',
    'remote query timeout (s)'
)
ORDER BY name;

    Parameter group gotchas:

    1. shared_buffers uses a formula syntax on RDS. You cannot set it to a raw byte value like 8GB. Instead, RDS uses the expression {DBInstanceClassMemory/4} which resolves at runtime to 25% of instance memory. This is actually better than a hardcoded value because when you resize the instance, the buffer pool scales automatically.

    2. max_connections is hardcoded per instance class as a default. AWS sets conservative defaults (roughly 1 connection per 9.6 MB of RAM for PostgreSQL). On a db.r7g.4xlarge with 128 GB RAM, the default is around 5,000 connections — far more than any application should open directly. If you're running PgBouncer or RDS Proxy, reduce this to 500–1000 to limit the overhead of idle connection memory.

    3. log_min_duration_statement is one of the most impactful parameters to set immediately. The default is -1 (disabled). Set it to 1000 (milliseconds) in production and 100 in QA. Slow query logging is how you identify query performance regressions during deployments.

    4. Parameter group changes do not propagate to read replicas automatically. Each read replica has its own parameter group association. If you want replicas to use the same configuration, create a common parameter group and attach it to each instance individually.

    6.5 Multi-AZ, Read Replicas, and High Availability Architecture

    RDS offers two distinct HA constructs that serve different purposes: Multi-AZ deployments and Read Replicas. They are often conflated by engineers new to RDS, and using them incorrectly produces systems that are either more expensive than necessary or less resilient than assumed.

    Multi-AZ: Synchronous standby for failover

    In a Multi-AZ deployment, RDS maintains a synchronous standby replica in a different Availability Zone. Every write to the primary is synchronously replicated to the standby before the write is acknowledged to the application. This means:

  • → RPO is effectively zero (no committed transactions are lost on failover).
  • → RTO is 60–120 seconds for automatic failover (DNS propagation + database promotion).
  • → The standby cannot serve reads. It exists solely for failover.
  • → You pay for two instances but get one connection endpoint.

    • The Multi-AZ standby is completely transparent to applications — they connect to the instance endpoint (e.g., prod-postgres-primary.abc123.us-east-1.rds.amazonaws.com), and that DNS record is automatically updated to point to the new primary after failover.

    Multi-AZ with two readable standbys (RDS Multi-AZ Cluster): AWS introduced a newer Multi-AZ option called Multi-AZ Cluster that provides two readable standby instances instead of one non-readable standby. This gives you read scalability built into the HA tier. It's available for MySQL 8.0 and PostgreSQL 13+. The cluster endpoint handles writes; reader endpoints handle reads. This is distinct from Aurora's multi-AZ model (covered in Chapter 7), and is worth considering for PostgreSQL workloads that need both HA and read scaling without the Aurora pricing model.

    RDS Multi-AZ Cluster configuration:

    # Create a Multi-AZ Cluster for PostgreSQL (not a standard Multi-AZ instance)
aws rds create-db-cluster \
  --db-cluster-identifier prod-postgres-cluster \
  --engine postgres \
  --engine-version 16.3 \
  --db-cluster-instance-class db.r7g.4xlarge \
  --master-username dbadmin \
  --master-user-password "${DB_PASSWORD}" \
  --storage-type io1 \
  --iops 12000 \
  --allocated-storage 500 \
  --backup-retention-period 14 \
  --vpc-security-group-ids sg-0abc123def456789 \
  --db-subnet-group-name private-db-subnets \
  --region us-east-1

    Read Replicas: Asynchronous copies for read scaling and cross-region DR

    Read Replicas use asynchronous replication. The primary does not wait for the replica to confirm a write. This means:

  • → Replicas have some replication lag (usually sub-second to a few seconds on healthy systems, potentially minutes under heavy write load).
  • → Replicas can serve reads, offloading analytical queries from the primary.
  • → Replicas can be in different AWS regions (cross-region read replicas), which provides geographic DR.
  • → A Read Replica can be promoted to a standalone primary — the promotion takes 5–15 minutes and creates a new independent instance.

    • Read Replicas are not a substitute for Multi-AZ on the primary. If your primary is Single-AZ and you have five Read Replicas, you still have a single point of failure on the primary. The correct production architecture is Multi-AZ primary with Read Replicas for read scaling.

    Creating Read Replicas:

    # Create a read replica in the same region
aws rds create-db-instance-read-replica \
  --db-instance-identifier prod-postgres-replica-01 \
  --source-db-instance-identifier prod-postgres-primary \
  --db-instance-class db.r7g.2xlarge \
  --availability-zone us-east-1b \
  --storage-type gp3 \
  --publicly-accessible false \
  --region us-east-1

# Create a cross-region read replica (for DR or regional read scaling)
# Run this in the target region
aws rds create-db-instance-read-replica \
  --db-instance-identifier prod-postgres-replica-usw2 \
  --source-db-instance-identifier arn:aws:rds:us-east-1:123456789012:db:prod-postgres-primary \
  --db-instance-class db.r7g.2xlarge \
  --storage-type gp3 \
  --region us-west-2

    Monitoring replication lag:

    # CloudWatch metric for replication lag (in seconds)
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ReplicaLag \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-replica-01 \
  --start-time 2024-01-15T00:00:00Z \
  --end-time 2024-01-15T23:59:59Z \
  --period 300 \
  --statistics Average Maximum \
  --output table
    -- PostgreSQL: Check replication lag from within the primary
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS replay_lag_bytes,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication
ORDER BY replay_lag DESC NULLS LAST;

-- From within the replica: check how far behind primary
SELECT
    now() - pg_last_xact_replay_timestamp() AS replication_lag,
    pg_is_in_recovery() AS is_replica,
    pg_last_wal_receive_lsn() AS received_lsn,
    pg_last_wal_replay_lsn() AS replayed_lsn,
    pg_wal_lsn_diff(
        pg_last_wal_receive_lsn(),
        pg_last_wal_replay_lsn()
    ) AS lag_bytes;

    RDS Proxy: Connection pooling as a managed service

    RDS Proxy sits between your application and the RDS instance and multiplexes database connections. It maintains a warm pool of connections to the database, allowing thousands of application connections to share a smaller number of actual database connections. This is most impactful for:

  • → Serverless workloads (Lambda functions that open and close connections on every invocation)
  • → Applications using a connection-per-request pattern
  • → Instances where `max_connections` is a bottleneck

    • RDS Proxy also provides a secondary benefit: during Multi-AZ failover, the proxy handles connection re-routing, reducing application-visible downtime from 60–120 seconds to as low as a few seconds.

    # Create an RDS Proxy for the PostgreSQL instance
aws rds create-db-proxy \
  --db-proxy-name prod-postgres-proxy \
  --engine-family POSTGRESQL \
  --auth '[{
    "AuthScheme": "SECRETS",
    "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:prod/postgres/dbadmin",
    "IAMAuth": "DISABLED"
  }]' \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0abc123 subnet-0def456 subnet-0ghi789 \
  --vpc-security-group-ids sg-0proxy123 \
  --require-tls \
  --region us-east-1

# Register the target (point proxy at the RDS instance)
aws rds register-db-proxy-targets \
  --db-proxy-name prod-postgres-proxy \
  --db-instance-identifiers prod-postgres-primary \
  --region us-east-1

    RDS Proxy has one significant limitation for PostgreSQL: it does not support all PostgreSQL authentication methods and it does not support all connection parameters. Specifically, it does not support SET SESSION AUTHORIZATION, advisory locks that depend on connection identity, or LISTEN/NOTIFY. If your application relies on any of these, test thoroughly before putting Proxy in front of a production PostgreSQL instance.

    6.6 Backup, Restore, and PITR

    RDS automated backups use EBS volume snapshots plus WAL archiving to enable point-in-time recovery. Understanding the mechanics matters because the recovery behavior has important implications for your RTO.

    How automated backups work:

    1. During the backup window, RDS takes an EBS snapshot of the storage volume. For Multi-AZ, the snapshot is taken from the standby to avoid I/O impact on the primary.

    2. Transaction logs (WAL for PostgreSQL, binary logs for MySQL) are continuously uploaded to S3 every 5 minutes.

    3. PITR works by restoring the nearest snapshot before the target time, then replaying logs forward to the exact target timestamp.

    Retention period: Backups are retained for 0–35 days. Setting retention to 0 disables automated backups (and PITR). Never set retention to 0 on a production instance. The standard retention for production is 14 days; compliance-heavy environments often require 35 days.

    Manual snapshots are independent of the retention period. They persist until you explicitly delete them. Before any major change (schema migration, engine upgrade, instance resizing), take a manual snapshot:

    # Take a manual snapshot before a risky operation
aws rds create-db-snapshot \
  --db-instance-identifier prod-postgres-primary \
  --db-snapshot-identifier prod-postgres-before-migration-20240115 \
  --region us-east-1

# Wait for the snapshot to complete
aws rds wait db-snapshot-completed \
  --db-snapshot-identifier prod-postgres-before-migration-20240115 \
  --region us-east-1

echo "Snapshot complete — safe to proceed with migration"

    Point-in-time restore: PITR creates a new RDS instance restored to the specified timestamp. It does not restore in-place — you always get a new instance. This means you must update your application's connection string after a PITR recovery.

    # Restore to a specific point in time (creates a NEW instance)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier prod-postgres-primary \
  --target-db-instance-identifier prod-postgres-recovered-20240115 \
  --restore-time 2024-01-15T08:30:00Z \
  --db-instance-class db.r7g.4xlarge \
  --storage-type gp3 \
  --multi-az \
  --region us-east-1

# Monitor restoration progress
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-recovered-20240115 \
  --query 'DBInstances[0].[DBInstanceStatus,PercentProgress]' \
  --output table \
  --region us-east-1

    The PITR recovery window: The earliest restorable time is limited by the oldest retained backup snapshot. You can check the exact recovery window:

    # Check the earliest and latest restorable times
aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-primary \
  --query 'DBInstances[0].{
    EarliestRestorableTime: EarliestRestorableTime,
    LatestRestorableTime: LatestRestorableTime,
    BackupRetentionPeriod: BackupRetentionPeriod
  }' \
  --output table \
  --region us-east-1

    Restoring a snapshot to a different instance class or storage type: This is useful when you want to test a configuration change. Restore a production snapshot to a smaller instance in a non-production environment, validate, and then apply the same change to production.

    # Restore from a manual snapshot to a different (cheaper) instance class
# for testing or data recovery purposes
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier staging-postgres-from-prod-snap \
  --db-snapshot-identifier prod-postgres-before-migration-20240115 \
  --db-instance-class db.r7g.xlarge \
  --storage-type gp3 \
  --no-multi-az \
  --no-publicly-accessible \
  --vpc-security-group-ids sg-0staging123 \
  --db-subnet-group-name staging-db-subnets \
  --region us-east-1

    Cross-region backup copies: Automated backups do not automatically copy to other regions. For DR, you need to either configure cross-region automated backup copy or copy manual snapshots. AWS recently added automated cross-region backup to RDS, but manual snapshot copy remains the most flexible approach:

    # Copy a manual snapshot to another region for DR
aws rds copy-db-snapshot \
  --source-db-snapshot-identifier \
    arn:aws:rds:us-east-1:123456789012:snapshot:prod-postgres-before-migration-20240115 \
  --target-db-snapshot-identifier prod-postgres-before-migration-20240115-copy \
  --kms-key-id arn:aws:kms:us-west-2:123456789012:key/mrk-abc123 \
  --region us-west-2

    Note that cross-region snapshot copies transfer data across AWS backbone networks and incur data transfer costs. For large databases, automate periodic snapshot copies rather than copying every snapshot.

    6.7 Upgrade Paths and Maintenance Windows

    RDS engine upgrades come in two types: minor version upgrades (e.g., 16.2 → 16.3) and major version upgrades (e.g., 15 → 16). The operational complexity and risk differ significantly.

    Minor version upgrades:

  • → Applied automatically if `AutoMinorVersionUpgrade` is enabled, during the maintenance window.
  • → Can be applied manually at any time.
  • → For Multi-AZ: zero-downtime upgrade (standby upgraded first, then failover, then original primary upgraded).
  • → For Single-AZ: brief downtime (~5 minutes) during the upgrade.
  • → Generally safe with no application changes required.

    • Major version upgrades:

  • → Always require explicit action — no automatic major version upgrades.
  • → Require a compatible parameter group for the new version (you must create one in advance).
  • → In-place major version upgrades on RDS work for some engine combinations (PostgreSQL 14 → 15 → 16 is supported) but not all.
  • → For PostgreSQL, in-place upgrade uses `pg_upgrade` underneath. This takes a snapshot first, runs the upgrade, and if it fails, rolls back to the snapshot.
  • → Estimated downtime: 10–60 minutes depending on database size and version gap.

    • Pre-upgrade checklist for PostgreSQL major version upgrade:

    -- Run these on the CURRENT version before upgrading
-- to identify potential incompatibilities

-- Check for deprecated settings that changed between versions
SELECT name, setting
FROM pg_settings
WHERE name IN (
    'operator_precedence_warning',  -- removed in PG14
    'vacuum_cleanup_index_scale_factor',  -- removed in PG14
    'stats_temp_directory'  -- removed in PG15
);

-- Check for tables using deprecated data types or features
SELECT 
    n.nspname AS schema,
    c.relname AS table_name,
    a.attname AS column_name,
    t.typname AS data_type
FROM pg_attribute a
JOIN pg_class c ON a.attrelid = c.oid
JOIN pg_type t ON a.atttypid = t.oid
JOIN pg_namespace n ON c.relnamespace = n.oid
WHERE t.typname IN ('abstime', 'reltime', 'tinterval')  -- removed in PG12
  AND c.relkind = 'r'
  AND a.attnum > 0;

-- Check for extensions that may not be available in the target version
SELECT name, default_version, installed_version
FROM pg_available_extensions
WHERE installed_version IS NOT NULL
ORDER BY name;

-- Check for any invalid indexes (should be zero before upgrade)
SELECT schemaname, tablename, indexname
FROM pg_indexes
WHERE NOT EXISTS (
    SELECT 1 FROM pg_class c
    JOIN pg_index i ON i.indexrelid = c.oid
    WHERE c.relname = indexname
      AND pg_index_column_has_property(i.indexrelid, 1, 'returnable') IS NOT NULL
);

    Performing a major version upgrade with pre-upgrade snapshot:

    # Step 1: Take a manual snapshot before upgrading
aws rds create-db-snapshot \
  --db-instance-identifier prod-postgres-primary \
  --db-snapshot-identifier pre-upgrade-pg15-to-pg16-$(date +%Y%m%d) \
  --region us-east-1

aws rds wait db-snapshot-completed \
  --db-snapshot-identifier pre-upgrade-pg15-to-pg16-$(date +%Y%m%d) \
  --region us-east-1

# Step 2: Create the parameter group for the new major version FIRST
aws rds create-db-parameter-group \
  --db-parameter-group-name postgres16-prod \
  --db-parameter-group-family postgres16 \
  --description "Production PostgreSQL 16 parameters" \
  --region us-east-1

# Re-apply all your custom parameters to the new group (use the same
# modify-db-parameter-group commands from section 6.4)

# Step 3: Initiate the upgrade
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-primary \
  --engine-version 16.3 \
  --db-parameter-group-name postgres16-prod \
  --allow-major-version-upgrade \
  --apply-immediately \
  --region us-east-1

# Step 4: Monitor upgrade progress
watch -n 30 'aws rds describe-db-instances \
  --db-instance-identifier prod-postgres-primary \
  --query "DBInstances[0].[DBInstanceStatus,EngineVersion,PendingModifiedValues]" \
  --output table \
  --region us-east-1'

    Maintenance windows deserve careful thought in production. The default maintenance window is a 30-minute window during off-peak hours in the instance's region. AWS applies minor patches, security updates, and approved configuration changes during this window. For global applications with no true off-peak window, schedule maintenance during the lowest-traffic window you have, and ensure your application handles connection drops gracefully (retry logic, connection pool reconnect on error).

    # Update the maintenance window to Sunday 2am-3am UTC
aws rds modify-db-instance \
  --db-instance-identifier prod-postgres-primary \
  --preferred-maintenance-window "sun:02:00-sun:03:00" \
  --region us-east-1

# Check pending maintenance actions (AWS may schedule security patches)
aws rds describe-pending-maintenance-actions \
  --region us-east-1 \
  --query 'PendingMaintenanceActions[*].{
    ResourceIdentifier: ResourceIdentifier,
    Action: PendingMaintenanceActionDetails[0].Action,
    AutoAppliedAfterDate: PendingMaintenanceActionDetails[0].AutoAppliedAfterDate,
    Description: PendingMaintenanceActionDetails[0].Description
  }' \
  --output table

    If AWS schedules a forced patch with an AutoAppliedAfterDate, that patch will apply automatically after that date regardless of your maintenance window preference. Monitor this endpoint and apply patches proactively before AWS forces them, so you control the timing.

    6.8 RDS Operational Monitoring and Alerting

    The monitoring stack for RDS has three tiers: CloudWatch Basic Metrics (free, 1-minute granularity), Enhanced Monitoring (paid, 1–60 second granularity, OS-level metrics), and Performance Insights (paid, query-level attribution).

    CloudWatch Basic Metrics include CPU utilization, database connections, free storage, read/write IOPS, read/write latency, replica lag, and network throughput. These are sufficient for capacity trend monitoring but insufficient for diagnosing query-level performance issues.

    Enhanced Monitoring adds OS-level metrics that the basic metrics don't expose: per-process CPU, memory by component (RDS process, OS, file system cache), and disk I/O broken down by read/write and user/kernel. Enhanced Monitoring sends data to CloudWatch Logs rather than CloudWatch Metrics, which means you query it differently:

    # Enhanced Monitoring is in the RDSOSMetrics log group
# Get the latest OS metrics for an instance
aws logs filter-log-events \
  --log-group-name "RDSOSMetrics" \
  --log-stream-name-prefix "prod-postgres-primary" \
  --start-time $(date -d '5 minutes ago' +%s000) \
  --limit 5 \
  --query 'events[*].message' \
  --output text \
  --region us-east-1

    The output is JSON with detailed OS metrics. Parse it with jq for usable output:

    aws logs filter-log-events \
  --log-group-name "RDSOSMetrics" \
  --log-stream-name-prefix "prod-postgres-primary" \
  --start-time $(date -d '5 minutes ago' +%s000) \
  --limit 1 \
  --query 'events[0].message' \
  --output text \
  --region us-east-1 | \
  jq '{
    timestamp: .timestamp,
    cpu_idle: .cpuUtilization.idle,
    cpu_user: .cpuUtilization.user,
    memory_free_mb: (.memory.free / 1024 / 1024),
    disk_read_iops: .diskIO[0].readIOsPS,
    disk_write_iops: .diskIO[0].writeIOsPS,
    load_average_1m: .loadAverageMinute.one
  }'

    Performance Insights is the most powerful diagnostic tool for RDS. It collects query-level wait event data and lets you answer "what was the database doing at 2:34am when latency spiked?" It shows the database load broken down by wait event, SQL statement, user, host, or application. For PostgreSQL, it leverages pg_stat_activity and pg_stat_statements internally.

    Set Performance Insights retention to at least 7 days (the free tier) and ideally to 731 days (2 years, paid) for production systems where you need to compare behavior across deployments and seasonal traffic patterns.

    Essential CloudWatch alarms for any production RDS instance:

    # Alarm: CPU utilization above 80% for 10 minutes
aws cloudwatch put-metric-alarm \
  --alarm-name rds-prod-postgres-cpu-high \
  --metric-name CPUUtilization \
  --namespace AWS/RDS \
  --dimensions Name=DBInstanceIdentifier,Value=prod-postgres-primary \
  --statistic Average \
  --period 300 \
  --evaluation-periods 2 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-alerts \

  --namespace AWS/RDS \

  --statistic Average \
  --period 300 \
  --evaluation-periods 1 \
  --threshold 107374182400 \
  --comparison-operator LessThanThreshold \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:db-alerts \
  --region us-east-1

# Alarm: Replica lag above 30 seconds
aws cloudwatch put-metric-alarm \
  --alarm-name rds-prod-postgres-replica-lag \
  --metric-name ReplicaLag \
  --namespace AWS/RDS \

  --region us-east-1

    Querying Performance Insights via API for automated reporting:

    Key Takeaways

  • → **Engine version and licensing choices are harder to reverse than they appear.** Pin minor versions in production, stay within one major version of current, and understand the SQL Server and Oracle licensing models before committing to an instance size and edition — the hourly cost difference between editions on large instances is substantial.
  • → **Instance family selection matters more than raw size.** Graviton (g-suffix) instances offer better price-performance for PostgreSQL and MySQL, while SQL Server and Oracle require Intel or AMD families. Never use T-series burstable instances for production OLTP workloads that sustain CPU pressure — CPU credit exhaustion causes silent, unpredictable throttling.
  • → **gp3 storage is the correct default for nearly all new RDS deployments.** It decouples IOPS and throughput from storage size, eliminating the gp2 credit model at lower cost. Monitor `DiskQueueDepth` and `WriteLatency` to detect storage saturation; provision additional IOPS on gp3 before reaching the throughput ceiling rather than after observing latency spikes.
  • → **Multi-AZ and Read Replicas solve different problems and are not interchangeable.** Multi-AZ provides synchronous failover with near-zero RPO but the standby cannot serve reads. Read Replicas provide asynchronous read scaling and cross-region DR but have replication lag and do not auto-failover. Production architectures typically need both: a Multi-AZ primary with Read Replicas for workload offloading.
  • → **RDS backup and restore behavior requires architectural awareness.** PITR always produces a new instance — recovery requires updating application connection strings, not just waiting for an in-place restore. Automated backups do not copy cross-region by default. Take manual snapshots before any major change, verify the earliest restorable time matches your RPO requirements, and set CloudWatch alarms at 20% free storage rather than relying solely on autoscaling.
