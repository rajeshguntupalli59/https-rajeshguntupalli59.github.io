Chapter 16: Metadata Filtering with SQL and Vector Search Together

Most vector search tutorials show you a single embedding column, a distance operator, and a LIMIT 10. That works for demos. In production AI applications, you almost never want the top-10 most semantically similar documents from your entire corpus — you want the top-10 most semantically similar documents *that belong to this tenant, in this language, published after this date, with this approval status, and not already shown to this user*. The moment you add those constraints, you are doing metadata filtering combined with vector search, and how you implement that combination determines whether your RAG system is fast, accurate, and correct — or slow, leaky, and wrong.

This chapter covers the full stack: schema design that makes filtering efficient, the different architectural patterns for combining SQL predicates with ANN search, how pgvector's HNSW index interacts with WHERE clauses, query patterns for common RAG filtering scenarios, and the Python layer that ties it all together into a production-ready retrieval pipeline.

*The estimate_filtered_set_size helper picks the strategy per request — small filtered sets favor a sequential scan, large ones favor letting HNSW do the initial narrowing.*

---

Why Metadata Filtering Is Not an Afterthought

Vector similarity search answers a deceptively simple question: which embeddings in this set are closest to my query embedding? The problem is that "this set" — the entire embedding table — is almost never the right scope for a production query.

Consider a multi-tenant knowledge base serving 500 companies. Each company has uploaded their own documents. Without metadata filtering, a similarity search for "how do I reset my password?" might return results from a competitor's documentation. This is not a minor inconvenience — it is a data isolation failure. Row-level security and tenant-scoped queries are standard database thinking, and they apply equally to vector search.

Beyond multi-tenancy, filtering requirements in real RAG systems include:

  • → **Temporal filters** — only retrieve documents updated within the last 90 days, because older content may be stale
  • → **Status filters** — only retrieve `published` or `approved` documents, not drafts
  • → **Language filters** — retrieve documents matching the detected user language
  • → **Category/taxonomy filters** — pre-narrow the corpus by topic before semantic ranking
  • → **Permission filters** — only show content the authenticated user has access to
  • → **Deduplication** — exclude document IDs already retrieved in previous turns

    • Each of these is a standard SQL predicate. PostgreSQL is extraordinarily good at evaluating them. The engineering challenge is combining them efficiently with the approximate nearest neighbor (ANN) search that pgvector provides.

    The fundamental tension is this: HNSW and IVFFlat indexes are built to traverse the vector space efficiently, but they work best when they can consider a large candidate set. If your SQL WHERE clause eliminates 99% of rows before the index traversal, the ANN index may not help much — or may even be bypassed in favor of a sequential scan. Understanding this tradeoff lets you design schemas and queries that give you both correctness and speed.

    ---

    Schema Design for Filterable Vector Search

    The schema is where the filtering strategy lives. A common mistake is storing metadata as a single JSONB blob and expecting ad-hoc filtering to be fast. Some metadata should be JSONB; most filtering attributes should be typed columns with indexes.

    Here is a realistic schema for a multi-tenant document knowledge base:

    -- Extensions
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;  -- for text search on titles

-- Tenants
CREATE TABLE tenants (
    tenant_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name          TEXT NOT NULL,
    plan          TEXT NOT NULL DEFAULT 'free',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Document sources (S3 buckets, web crawls, uploads, etc.)
CREATE TABLE document_sources (
    source_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     UUID NOT NULL REFERENCES tenants(tenant_id),
    name          TEXT NOT NULL,
    source_type   TEXT NOT NULL,  -- 'upload', 'web_crawl', 'api_sync'
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Documents (parent records — a PDF, a web page, a Confluence article)
CREATE TABLE documents (
    document_id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     UUID NOT NULL REFERENCES tenants(tenant_id),
    source_id     UUID REFERENCES document_sources(source_id),
    title         TEXT NOT NULL,
    url           TEXT,
    language      TEXT NOT NULL DEFAULT 'en',
    status        TEXT NOT NULL DEFAULT 'draft',
        -- CHECK constraint ensures valid statuses
        CONSTRAINT documents_status_check
            CHECK (status IN ('draft', 'processing', 'published', 'archived')),
    category      TEXT,
    tags          TEXT[] NOT NULL DEFAULT '{}',
    author_id     UUID,
    word_count    INTEGER,
    -- Timestamps matter for recency filtering
    content_updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- Arbitrary metadata that doesn't need indexing
    extra_metadata      JSONB NOT NULL DEFAULT '{}'
);

-- Indexes for common filter patterns
CREATE INDEX idx_documents_tenant_status
    ON documents (tenant_id, status);

CREATE INDEX idx_documents_tenant_language
    ON documents (tenant_id, language);

CREATE INDEX idx_documents_tenant_category
    ON documents (tenant_id, category)
    WHERE category IS NOT NULL;

CREATE INDEX idx_documents_content_updated_at
    ON documents (tenant_id, content_updated_at DESC)
    WHERE status = 'published';

CREATE INDEX idx_documents_tags
    ON documents USING GIN (tags);

-- Chunks (the actual units of retrieval — documents split into overlapping chunks)
CREATE TABLE document_chunks (
    chunk_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id     UUID NOT NULL REFERENCES documents(document_id) ON DELETE CASCADE,
    tenant_id       UUID NOT NULL,  -- denormalized for faster filtering
    chunk_index     INTEGER NOT NULL,
    chunk_text      TEXT NOT NULL,
    token_count     INTEGER,
    -- Denormalized filter columns from parent document
    -- This is intentional: avoids JOINs during hot-path retrieval
    language        TEXT NOT NULL DEFAULT 'en',
    status          TEXT NOT NULL DEFAULT 'draft',
    category        TEXT,
    tags            TEXT[] NOT NULL DEFAULT '{}',
    content_updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- The embedding
    embedding       vector(1536),  -- OpenAI text-embedding-3-small dimensions
    -- Bookkeeping
    embedding_model TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_chunk_tenant
        FOREIGN KEY (tenant_id) REFERENCES tenants(tenant_id)
);

-- Partial index: only index published chunks
-- This is the most important optimization for metadata-filtered vector search
CREATE INDEX idx_chunks_embedding_published
    ON document_chunks
    USING hnsw (embedding vector_cosine_ops)
    WHERE status = 'published';

-- Composite b-tree indexes for metadata filtering
CREATE INDEX idx_chunks_tenant_status
    ON document_chunks (tenant_id, status);

CREATE INDEX idx_chunks_tenant_language_status
    ON document_chunks (tenant_id, language, status);

CREATE INDEX idx_chunks_tenant_category
    ON document_chunks (tenant_id, category, status)
    WHERE category IS NOT NULL;

CREATE INDEX idx_chunks_tags
    ON document_chunks USING GIN (tags)
    WHERE status = 'published';

-- User retrieval history (for deduplication across conversation turns)
CREATE TABLE retrieval_history (
    id              BIGSERIAL PRIMARY KEY,
    session_id      UUID NOT NULL,
    user_id         UUID NOT NULL,
    tenant_id       UUID NOT NULL,
    chunk_id        UUID NOT NULL REFERENCES document_chunks(chunk_id),
    retrieved_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_retrieval_history_session
    ON retrieval_history (session_id, retrieved_at DESC);

    The key design decisions here:

    Denormalized filter columns on chunks — tenant_id, language, status, category, and tags are duplicated from the parent document onto every chunk. This avoids a JOIN on every retrieval query. The JOIN cost matters when you are running hundreds of queries per second.

    Partial HNSW index on status = 'published' — The HNSW index only covers rows where status = 'published'. This means the index is smaller (faster to build and traverse), and queries that filter on status = 'published' can use the index efficiently. Draft documents never pollute semantic search results.

    Typed columns for high-cardinality filters — tenant_id, language, category, and status are typed columns, not JSONB keys. These can be covered by B-tree composite indexes that PostgreSQL's planner knows how to use.

    ---

    The Three Patterns for Combining Filters and Vector Search

    There are three fundamental architectural patterns for combining SQL predicates with vector similarity search. PostgreSQL supports all three, and the right choice depends on your data distribution and query selectivity.

    Pattern 1: Pre-filter then search (SQL first)

    Apply the SQL WHERE clause to narrow the candidate set, then do vector search on the result.

    -- Pre-filter pattern: PostgreSQL evaluates the WHERE clause,
-- then applies vector distance ordering within the filtered set
SELECT
    dc.chunk_id,
    dc.document_id,
    dc.chunk_text,
    dc.category,
    dc.content_updated_at,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity
FROM document_chunks dc
WHERE
    dc.tenant_id    = $2
    AND dc.status   = 'published'
    AND dc.language = $3
    AND dc.content_updated_at >= NOW() - INTERVAL '90 days'
ORDER BY dc.embedding <=> $1::vector
LIMIT 10;

    This pattern works well when filters are highly selective — if tenant_id + status + language reduces the candidate set to a few thousand rows, PostgreSQL will scan those rows and compute distances sequentially. With a small filtered set, sequential distance computation is fast enough that the HNSW index may not be needed.

    Pattern 2: Search then post-filter (vector first)

    Retrieve a large pool of nearest neighbors from the full vector space, then apply SQL filters to the pool.

    -- Post-filter pattern: retrieve k*multiplier candidates, then filter
-- Use a CTE to make the intent explicit
WITH vector_candidates AS (
    SELECT
        chunk_id,
        document_id,
        chunk_text,
        tenant_id,
        status,
        language,
        category,
        content_updated_at,
        1 - (embedding <=> $1::vector) AS cosine_similarity
    FROM document_chunks
    ORDER BY embedding <=> $1::vector
    LIMIT 200  -- retrieve 20x more than we need, then filter
),
filtered AS (
    SELECT *
    FROM vector_candidates
    WHERE
        tenant_id    = $2
        AND status   = 'published'
        AND language = $3
        AND content_updated_at >= NOW() - INTERVAL '90 days'
)
SELECT
    chunk_id,
    document_id,
    chunk_text,
    category,
    content_updated_at,
    cosine_similarity
FROM filtered
ORDER BY cosine_similarity DESC
LIMIT 10;

    This pattern works well when filters have low selectivity (most documents match) or when you cannot afford a sequential scan of the filtered set (the filtered set is still very large). The risk is that your filters might eliminate most of the 200 candidates, leaving you with fewer than 10 results. You need to tune the over-fetch multiplier.

    Pattern 3: Partitioned HNSW indexes (partition-per-tenant)

    For large multi-tenant deployments, partition the table by tenant_id and build separate HNSW indexes per partition. Each tenant's vector search is isolated to their partition.

    -- Create a partitioned chunks table
CREATE TABLE document_chunks_partitioned (
    chunk_id        UUID NOT NULL DEFAULT gen_random_uuid(),
    document_id     UUID NOT NULL,
    tenant_id       UUID NOT NULL,
    chunk_index     INTEGER NOT NULL,
    chunk_text      TEXT NOT NULL,
    language        TEXT NOT NULL DEFAULT 'en',
    status          TEXT NOT NULL DEFAULT 'draft',
    category        TEXT,
    tags            TEXT[] NOT NULL DEFAULT '{}',
    content_updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    embedding       vector(1536),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, chunk_id)
) PARTITION BY HASH (tenant_id);

-- Create 16 partitions
DO $$
BEGIN
    FOR i IN 0..15 LOOP
        EXECUTE format(
            'CREATE TABLE document_chunks_p%s
             PARTITION OF document_chunks_partitioned
             FOR VALUES WITH (modulus 16, remainder %s)',
            i, i
        );
    END LOOP;
END;
$$;

-- Create HNSW indexes on each partition
DO $$
BEGIN
    FOR i IN 0..15 LOOP
        EXECUTE format(
            'CREATE INDEX idx_chunks_p%s_embedding
             ON document_chunks_p%s
             USING hnsw (embedding vector_cosine_ops)
             WITH (m = 16, ef_construction = 64)
             WHERE status = ''published''',
            i, i
        );
    END LOOP;
END;
$$;

    When you query with WHERE tenant_id = $1, PostgreSQL's partition pruning eliminates all partitions not matching the hash of that tenant ID. The HNSW index on the remaining partition is smaller and faster to traverse.

    Implementation: The Retrieval Pipeline in Python

    Here is a production retrieval pipeline using FastAPI, asyncpg, and the OpenAI embedding API. It handles all three filter patterns, chooses the right strategy based on query parameters, and integrates with a Redis cache for repeated queries.

    # retrieval/pipeline.py
import asyncio
import hashlib
import json
import logging
from dataclasses import dataclass, field
from datetime import datetime, timedelta
from typing import Optional
from uuid import UUID

import asyncpg
import openai
import redis.asyncio as aioredis
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel, Field

logger = logging.getLogger(__name__)

app = FastAPI(title="RAG Retrieval Service")


# --- Configuration -----------------------------------------------------------

EMBEDDING_MODEL = "text-embedding-3-small"
EMBEDDING_DIMENSIONS = 1536
CACHE_TTL_SECONDS = 300  # 5 minutes for embedding cache
RETRIEVAL_CACHE_TTL = 60  # 1 minute for retrieval results


# --- Request/Response models -------------------------------------------------

class RetrievalRequest(BaseModel):
    query: str
    tenant_id: UUID
    session_id: UUID
    user_id: UUID
    language: Optional[str] = "en"
    category: Optional[str] = None
    tags: Optional[list[str]] = None
    max_age_days: Optional[int] = 90
    exclude_chunk_ids: Optional[list[UUID]] = None
    top_k: int = Field(default=8, ge=1, le=25)
    # Strategy hint: 'auto', 'pre_filter', 'post_filter'
    strategy: str = Field(default="auto")


@dataclass
class RetrievedChunk:
    chunk_id: str
    document_id: str
    chunk_text: str
    cosine_similarity: float
    category: Optional[str]
    content_updated_at: datetime
    document_title: str


# --- Database and cache setup ------------------------------------------------

async def get_db_pool() -> asyncpg.Pool:
    return await asyncpg.create_pool(
        dsn="postgresql://app_user:secret@localhost/knowledge_base",
        min_size=5,
        max_size=20,
        command_timeout=10,
    )


async def get_redis() -> aioredis.Redis:
    return await aioredis.from_url(
        "redis://localhost:6379",
        encoding="utf-8",
        decode_responses=False,
    )


# Initialize at startup (in production, use lifespan events)
_db_pool: Optional[asyncpg.Pool] = None
_redis: Optional[aioredis.Redis] = None


# --- Embedding with caching --------------------------------------------------

async def get_embedding(
    text: str,
    redis_client: aioredis.Redis,
    openai_client: openai.AsyncOpenAI,
) -> list[float]:
    """
    Embed a query string. Cache embeddings in Redis to avoid
    re-embedding repeated queries (common in chat applications).
    """
    cache_key = f"emb:{hashlib.sha256(text.encode()).hexdigest()}"

    cached = await redis_client.get(cache_key)
    if cached:
        return json.loads(cached)

    response = await openai_client.embeddings.create(
        model=EMBEDDING_MODEL,
        input=text,
        dimensions=EMBEDDING_DIMENSIONS,
    )
    embedding = response.data[0].embedding

    await redis_client.setex(
        cache_key,
        CACHE_TTL_SECONDS,
        json.dumps(embedding),
    )
    return embedding


# --- Core retrieval queries --------------------------------------------------

PRE_FILTER_QUERY = """
SELECT
    dc.chunk_id::text,
    dc.document_id::text,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity,
    dc.category,
    dc.content_updated_at,
    d.title AS document_title
FROM document_chunks dc
JOIN documents d ON d.document_id = dc.document_id
WHERE
    dc.tenant_id    = $2::uuid
    AND dc.status   = 'published'
    AND dc.language = $3
    AND dc.content_updated_at >= NOW() - ($4 || ' days')::INTERVAL
    AND ($5::text IS NULL OR dc.category = $5)
    AND ($6::text[] IS NULL OR dc.tags && $6::text[])
    AND ($7::uuid[] IS NULL OR dc.chunk_id != ALL($7::uuid[]))
ORDER BY dc.embedding <=> $1::vector
LIMIT $8;
"""

POST_FILTER_QUERY = """
WITH vector_candidates AS (
    SELECT
        dc.chunk_id,
        dc.document_id,
        dc.chunk_text,
        dc.tenant_id,
        dc.language,
        dc.category,
        dc.tags,
        dc.content_updated_at,
        1 - (dc.embedding <=> $1::vector) AS cosine_similarity
    FROM document_chunks dc
    WHERE dc.status = 'published'
    ORDER BY dc.embedding <=> $1::vector
    LIMIT $8  -- over-fetch: top_k * multiplier
),
filtered AS (
    SELECT vc.*, d.title AS document_title
    FROM vector_candidates vc
    JOIN documents d ON d.document_id = vc.document_id
    WHERE
        vc.tenant_id    = $2::uuid
        AND vc.language = $3
        AND vc.content_updated_at >= NOW() - ($4 || ' days')::INTERVAL
        AND ($5::text IS NULL OR vc.category = $5)
        AND ($6::text[] IS NULL OR vc.tags && $6::text[])
        AND ($7::uuid[] IS NULL OR vc.chunk_id != ALL($7::uuid[]))
)
SELECT
    chunk_id::text,
    document_id::text,
    chunk_text,
    cosine_similarity,
    category,
    content_updated_at,
    document_title
FROM filtered
ORDER BY cosine_similarity DESC
LIMIT $9;  -- actual top_k
"""


async def pre_filter_retrieve(
    conn: asyncpg.Connection,
    embedding: list[float],
    request: RetrievalRequest,
) -> list[RetrievedChunk]:
    embedding_str = f"[{','.join(str(x) for x in embedding)}]"
    exclude_ids = (
        [str(cid) for cid in request.exclude_chunk_ids]
        if request.exclude_chunk_ids
        else None
    )

    rows = await conn.fetch(
        PRE_FILTER_QUERY,
        embedding_str,
        str(request.tenant_id),
        request.language,
        str(request.max_age_days or 90),
        request.category,
        request.tags,
        exclude_ids,
        request.top_k,
    )

    return [
        RetrievedChunk(
            chunk_id=row["chunk_id"],
            document_id=row["document_id"],
            chunk_text=row["chunk_text"],
            cosine_similarity=float(row["cosine_similarity"]),
            category=row["category"],
            content_updated_at=row["content_updated_at"],
            document_title=row["document_title"],
        )
        for row in rows
    ]


async def post_filter_retrieve(
    conn: asyncpg.Connection,
    embedding: list[float],
    request: RetrievalRequest,
    over_fetch_multiplier: int = 20,
) -> list[RetrievedChunk]:
    embedding_str = f"[{','.join(str(x) for x in embedding)}]"
    exclude_ids = (
        [str(cid) for cid in request.exclude_chunk_ids]
        if request.exclude_chunk_ids
        else None
    )
    over_fetch_k = request.top_k * over_fetch_multiplier

    rows = await conn.fetch(
        POST_FILTER_QUERY,
        embedding_str,
        str(request.tenant_id),
        request.language,
        str(request.max_age_days or 90),
        request.category,
        request.tags,
        exclude_ids,
        over_fetch_k,
        request.top_k,
    )

    return [
        RetrievedChunk(
            chunk_id=row["chunk_id"],
            document_id=row["document_id"],
            chunk_text=row["chunk_text"],
            cosine_similarity=float(row["cosine_similarity"]),
            category=row["category"],
            content_updated_at=row["content_updated_at"],
            document_title=row["document_title"],
        )
        for row in rows
    ]


# --- Strategy selection ------------------------------------------------------

async def estimate_filtered_set_size(
    conn: asyncpg.Connection,
    request: RetrievalRequest,
) -> int:
    """
    Use PostgreSQL statistics to estimate the size of the filtered candidate set.
    EXPLAIN with no actual execution gives us the planner's row estimate.
    This estimate is good enough for strategy selection.
    """
    explain_query = """
    EXPLAIN (FORMAT JSON)
    SELECT 1
    FROM document_chunks
    WHERE
        tenant_id    = $1::uuid
        AND status   = 'published'
        AND language = $2
        AND content_updated_at >= NOW() - ($3 || ' days')::INTERVAL
        AND ($4::text IS NULL OR category = $4)
    """
    result = await conn.fetchval(
        explain_query,
        str(request.tenant_id),
        request.language,
        str(request.max_age_days or 90),
        request.category,
    )
    plan = json.loads(result)
    estimated_rows = plan[0]["Plan"]["Plan Rows"]
    return int(estimated_rows)


async def retrieve_chunks(
    request: RetrievalRequest,
    db_pool: asyncpg.Pool,
    redis_client: aioredis.Redis,
    openai_client: openai.AsyncOpenAI,
) -> list[RetrievedChunk]:
    # Step 1: Embed the query (with Redis caching)
    embedding = await get_embedding(request.query, redis_client, openai_client)

    async with db_pool.acquire() as conn:
        # Step 2: Choose retrieval strategy
        if request.strategy == "auto":
            estimated_rows = await estimate_filtered_set_size(conn, request)
            # If the filtered set is small enough for a sequential scan,
            # pre-filter is faster (avoids over-fetching from the HNSW index).
            # If the filtered set is large, post-filter lets HNSW do its job.
            if estimated_rows < 50_000:
                strategy = "pre_filter"
            else:
                strategy = "post_filter"
            logger.debug(
                "Auto-selected strategy=%s for estimated_rows=%d",
                strategy,
                estimated_rows,
            )
        else:
            strategy = request.strategy

        # Step 3: Execute the chosen strategy
        if strategy == "pre_filter":
            chunks = await pre_filter_retrieve(conn, embedding, request)
        else:
            chunks = await post_filter_retrieve(conn, embedding, request)

    # Step 4: Log retrieval history for deduplication in future turns
    if chunks:
        async with db_pool.acquire() as conn:
            await conn.executemany(
                """
                INSERT INTO retrieval_history
                    (session_id, user_id, tenant_id, chunk_id)
                VALUES ($1, $2, $3, $4::uuid)
                ON CONFLICT DO NOTHING
                """,
                [
                    (
                        str(request.session_id),
                        str(request.user_id),
                        str(request.tenant_id),
                        chunk.chunk_id,
                    )
                    for chunk in chunks
                ],
            )

    return chunks


# --- FastAPI endpoint --------------------------------------------------------

@app.post("/retrieve")
async def retrieve_endpoint(request: RetrievalRequest):
    global _db_pool, _redis

    if _db_pool is None:
        _db_pool = await get_db_pool()
    if _redis is None:
        _redis = await get_redis()

    openai_client = openai.AsyncOpenAI()

    try:
        chunks = await retrieve_chunks(
            request=request,
            db_pool=_db_pool,
            redis_client=_redis,
            openai_client=openai_client,
        )
    except asyncpg.PostgresError as exc:
        logger.exception("Database error during retrieval")
        raise HTTPException(status_code=500, detail="Retrieval failed") from exc

    return {
        "chunks": [
            {
                "chunk_id": c.chunk_id,
                "document_id": c.document_id,
                "chunk_text": c.chunk_text,
                "cosine_similarity": c.cosine_similarity,
                "category": c.category,
                "content_updated_at": c.content_updated_at.isoformat(),
                "document_title": c.document_title,
            }
            for c in chunks
        ],
        "count": len(chunks),
    }

    The estimate_filtered_set_size helper is worth examining. By running EXPLAIN (FORMAT JSON) without actually executing the query, we get PostgreSQL's planner row estimate in milliseconds. That estimate is based on table statistics collected by AUTOVACUUM — it is not perfectly accurate, but it is accurate enough to choose between pre-filter and post-filter. If the planner thinks the filtered set contains fewer than 50,000 rows, sequential distance computation across that filtered set is fast enough that we do not need the HNSW index for candidate generation. Above that threshold, we let the HNSW index find the nearest neighbors globally and filter afterward.

    ---

    Tuning HNSW for Filtered Workloads

    The HNSW index has two parameters that affect its interaction with filtered queries:

    m — the number of bidirectional connections per node. Higher m improves recall at the cost of more memory and slower inserts. For filtered workloads where the effective search space is smaller, a higher m (24–32) can help because the graph needs richer connectivity to efficiently navigate to the relevant subspace.

    ef_construction — the size of the dynamic candidate list during index build. Higher values improve recall but slow down index construction. For production schemas, ef_construction = 128 is a reasonable default.

    ef_search — set at query time via SET hnsw.ef_search = N. This controls how many candidates are explored during a query. The default is 40. For filtered workloads, increasing ef_search tells the index to explore more of the graph before returning, which improves the chance that enough candidates survive the post-filter step.

    -- Increase ef_search for a specific query session
-- when you know filters are aggressive
SET LOCAL hnsw.ef_search = 200;

SELECT
    dc.chunk_id,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity
FROM document_chunks dc
WHERE
    dc.tenant_id = $2
    AND dc.status = 'published'
    AND dc.category = $3
ORDER BY dc.embedding <=> $1::vector
LIMIT 10;

-- Reset after the query (SET LOCAL resets automatically at transaction end)

    You can also set ef_search in the Python layer per request when you detect that a query has many filters:

    async def pre_filter_retrieve(
    conn: asyncpg.Connection,
    embedding: list[float],
    request: RetrievalRequest,
    ef_search: int = 40,
) -> list[RetrievedChunk]:
    # Boost ef_search if we have many simultaneous filters
    active_filter_count = sum([
        request.category is not None,
        request.tags is not None and len(request.tags) > 0,
        request.max_age_days is not None and request.max_age_days < 180,
        request.language != "en",
    ])
    if active_filter_count >= 3:
        ef_search = 200

    await conn.execute(f"SET LOCAL hnsw.ef_search = {ef_search}")

    embedding_str = f"[{','.join(str(x) for x in embedding)}]"
    # ... rest of the function unchanged

    Note the use of SET LOCAL rather than SET. SET LOCAL scopes the parameter change to the current transaction and resets automatically when the transaction ends. Since asyncpg connections are reused from a pool, using bare SET would leak the configuration change to subsequent queries on the same connection.

    Partial Indexes: The Most Underused Optimization

    A partial HNSW index with a WHERE status = 'published' clause was shown in the schema above. This is frequently the single most impactful optimization for production RAG systems. Here is why.

    In a typical document pipeline, the status distribution might be roughly:

  • → `published` — the fraction of content that should be retrieved
  • → `draft`, `processing`, `archived` — all other states

    • If you index all rows but almost all queries filter to published, the HNSW graph is unnecessarily large. Every insertion (including drafts) forces HNSW to update the graph. The graph traversal during search must evaluate distance to nodes that will be immediately excluded by the WHERE filter.

    A partial index on WHERE status = 'published' means:

  • → The index is smaller, fitting better in shared buffers
  • → Graph construction during inserts only happens for published rows, which typically arrive after a processing step
  • → Queries that include `AND status = 'published'` in their WHERE clause can use this partial index
    • -- Check whether your query is using the partial index
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT chunk_id, chunk_text, embedding <=> '[0.1, 0.2, ...]'::vector AS dist
FROM document_chunks
WHERE tenant_id = 'some-uuid' AND status = 'published'
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;

-- You want to see "Index Scan using idx_chunks_embedding_published"
-- in the output, not "Seq Scan" or "Parallel Seq Scan"

    If your query plans show sequential scans even when you expect HNSW to be used, the most common causes are:

    1. The planner estimates that the filtered set is small enough that sequential scan beats index scan. This is often correct — trust it unless you have measured otherwise.

    2. The query does not exactly match the partial index predicate. WHERE status = 'published' must appear literally in the query; the planner does not infer it.

    3. The embedding column contains NULLs for some rows, which can cause the planner to choose a different path.

    4. enable_indexscan is disabled at the session level (uncommon, but worth checking in debugging scenarios).

    Multi-Filter Query Patterns Reference

    The following examples cover the most common filtering scenarios you will encounter building RAG systems. Each example uses the schema defined earlier.

    Tenant-scoped search with recency and category:

    -- PostgreSQL
SELECT
    dc.chunk_id,
    dc.document_id,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector)  AS cosine_similarity,
    dc.category,
    d.title
FROM document_chunks dc
JOIN documents d ON d.document_id = dc.document_id
WHERE
    dc.tenant_id          = $2::uuid
    AND dc.status         = 'published'
    AND dc.category       = $3
    AND dc.content_updated_at >= NOW() - INTERVAL '30 days'
ORDER BY dc.embedding <=> $1::vector
LIMIT $4;
    -- SQL Server equivalent using a hypothetical vector similarity function
-- (SQL Server 2025+ adds native VECTOR type and similarity functions)
SELECT TOP (@top_k)
    dc.chunk_id,
    dc.document_id,
    dc.chunk_text,
    VECTOR_DISTANCE('cosine', dc.embedding, @query_vector) AS cosine_distance,
    dc.category,
    d.title
FROM document_chunks dc
JOIN documents d ON d.document_id = dc.document_id
WHERE
    dc.tenant_id          = @tenant_id
    AND dc.status         = 'published'
    AND dc.category       = @category
    AND dc.content_updated_at >= DATEADD(day, -30, GETUTCDATE())
ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vector);

    Tag-based filtering with array overlap:

    -- PostgreSQL: find chunks tagged with ANY of the requested tags
-- Use the @> operator for "contains all" or && for "overlaps any"
SELECT
    dc.chunk_id,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity,
    dc.tags
FROM document_chunks dc
WHERE
    dc.tenant_id = $2::uuid
    AND dc.status = 'published'
    AND dc.tags && $3::text[]   -- && means "any element in common"
ORDER BY dc.embedding <=> $1::vector
LIMIT $4;
    -- SQL Server: tags stored as JSON array, requires JSON_VALUE or OPENJSON
-- This is more verbose without native array support
SELECT TOP (@top_k)
    dc.chunk_id,
    dc.chunk_text,
    VECTOR_DISTANCE('cosine', dc.embedding, @query_vector) AS cosine_distance
FROM document_chunks dc
CROSS APPLY OPENJSON(dc.tags_json) AS tag_values
WHERE
    dc.tenant_id = @tenant_id
    AND dc.status = 'published'
    AND tag_values.value IN (SELECT value FROM OPENJSON(@requested_tags_json))
GROUP BY dc.chunk_id, dc.chunk_text, dc.embedding
ORDER BY VECTOR_DISTANCE('cosine', dc.embedding, @query_vector);

    Deduplication across conversation turns:

    -- PostgreSQL: exclude chunks already shown to this user in this session
SELECT
    dc.chunk_id,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity
FROM document_chunks dc
WHERE
    dc.tenant_id = $2::uuid
    AND dc.status = 'published'
    AND dc.chunk_id NOT IN (
        SELECT rh.chunk_id
        FROM retrieval_history rh
        WHERE
            rh.session_id = $3::uuid
            AND rh.retrieved_at >= NOW() - INTERVAL '2 hours'
    )
ORDER BY dc.embedding <=> $1::vector
LIMIT $4;

    For performance, an anti-join is generally faster than NOT IN when the subquery returns many rows. Here is the rewritten version using LEFT JOIN ... IS NULL:

    -- More performant anti-join pattern
SELECT
    dc.chunk_id,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity
FROM document_chunks dc
LEFT JOIN retrieval_history rh
    ON  rh.chunk_id   = dc.chunk_id
    AND rh.session_id = $3::uuid
    AND rh.retrieved_at >= NOW() - INTERVAL '2 hours'
WHERE
    dc.tenant_id = $2::uuid
    AND dc.status = 'published'
    AND rh.chunk_id IS NULL          -- anti-join condition
ORDER BY dc.embedding <=> $1::vector
LIMIT $4;

    Cross-tenant federated search (internal admin use):

    -- Search across specific tenants (e.g., an enterprise admin searching
-- across all their subsidiary companies' knowledge bases)
SELECT
    dc.chunk_id,
    dc.tenant_id,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity,
    t.name AS tenant_name
FROM document_chunks dc
JOIN tenants t ON t.tenant_id = dc.tenant_id
WHERE
    dc.tenant_id = ANY($2::uuid[])   -- array of permitted tenant IDs
    AND dc.status = 'published'
    AND dc.language = $3
ORDER BY dc.embedding <=> $1::vector
LIMIT $4;

    Handling Dynamic Filter Sets

    In practice, not every query has the same set of active filters. A user might specify a category but not a language; another query might have tags but no date constraint. Hard-coding every filter combination as a separate SQL string creates unmaintainable code with exponential growth in query variants.

    The correct approach is parameterized query construction in Python, using a helper that builds the WHERE clause dynamically while still using parameterized values (not string interpolation of user data):

    # retrieval/query_builder.py
from dataclasses import dataclass, field
from typing import Any
from uuid import UUID


@dataclass
class FilteredVectorQuery:
    """
    Builds a parameterized vector similarity query with optional filters.
    All user-supplied values go through parameters, never into the SQL string.
    """
    top_k: int = 10
    _conditions: list[str] = field(default_factory=list)
    _params: list[Any] = field(default_factory=list)
    _param_index: int = field(default=1)

    def _next_param(self) -> str:
        idx = self._param_index
        self._param_index += 1
        return f"${idx}"

    def set_embedding(self, embedding: list[float]) -> "FilteredVectorQuery":
        """Embedding is always parameter $1."""
        assert self._param_index == 1, "Call set_embedding first"
        self._params.append(f"[{','.join(str(x) for x in embedding)}]")
        self._param_index += 1
        return self

    def add_tenant(self, tenant_id: UUID) -> "FilteredVectorQuery":
        p = self._next_param()
        self._conditions.append(f"dc.tenant_id = {p}::uuid")
        self._params.append(str(tenant_id))
        return self

    def add_status(self, status: str = "published") -> "FilteredVectorQuery":
        p = self._next_param()
        self._conditions.append(f"dc.status = {p}")
        self._params.append(status)
        return self

    def add_language(self, language: str) -> "FilteredVectorQuery":
        p = self._next_param()
        self._conditions.append(f"dc.language = {p}")
        self._params.append(language)
        return self

    def add_category(self, category: str) -> "FilteredVectorQuery":
        p = self._next_param()
        self._conditions.append(f"dc.category = {p}")
        self._params.append(category)
        return self

    def add_tags_any(self, tags: list[str]) -> "FilteredVectorQuery":
        p = self._next_param()
        self._conditions.append(f"dc.tags && {p}::text[]")
        self._params.append(tags)
        return self

    def add_max_age_days(self, days: int) -> "FilteredVectorQuery":
        p = self._next_param()
        self._conditions.append(
            f"dc.content_updated_at >= NOW() - ({p} || ' days')::INTERVAL"
        )
        self._params.append(str(days))
        return self

    def add_exclude_chunks(self, chunk_ids: list[UUID]) -> "FilteredVectorQuery":
        if not chunk_ids:
            return self
        p = self._next_param()
        self._conditions.append(f"dc.chunk_id != ALL({p}::uuid[])")
        self._params.append([str(cid) for cid in chunk_ids])
        return self

    def build(self) -> tuple[str, list[Any]]:
        where_clause = "\n    AND ".join(self._conditions)
        p_top_k = self._next_param()
        self._params.append(self.top_k)

        sql = f"""
SELECT
    dc.chunk_id::text,
    dc.document_id::text,
    dc.chunk_text,
    1 - (dc.embedding <=> $1::vector) AS cosine_similarity,
    dc.category,
    dc.content_updated_at,
    d.title AS document_title
FROM document_chunks dc
JOIN documents d ON d.document_id = dc.document_id
WHERE
    {where_clause}
ORDER BY dc.embedding <=> $1::vector
LIMIT {p_top_k};
"""
        return sql, self._params


def build_retrieval_query(
    request: "RetrievalRequest",  # forward reference to avoid circular import
    embedding: list[float],
) -> tuple[str, list[Any]]:
    """
    Build a parameterized retrieval query from a RetrievalRequest.
    Only active filters are included in the WHERE clause.
    """
    qb = FilteredVectorQuery(top_k=request.top_k)
    qb.set_embedding(embedding)
    qb.add_tenant(request.tenant_id)
    qb.add_status("published")  # always filter to published

    if request.language:
        qb.add_language(request.language)
    if request.category:
        qb.add_category(request.category)
    if request.tags:
        qb.add_tags_any(request.tags)
    if request.max_age_days:
        qb.add_max_age_days(request.max_age_days)
    if request.exclude_chunk_ids:
        qb.add_exclude_chunks(request.exclude_chunk_ids)

    return qb.build()

    This builder ensures that user-supplied values never appear in the SQL string itself — they are always bound parameters. The asyncpg driver handles type coercion for the parameterized values. The generated SQL is still readable and debuggable by logging it alongside the query at debug level.

    Observability: Query Plan Logging and Slow Query Monitoring

    Production RAG systems need visibility into retrieval performance. The most useful instrumentation is logging slow queries with their plans.

    # retrieval/instrumented_query.py
import asyncio
import logging
import time
from typing import Any

import asyncpg

logger = logging.getLogger(__name__)

SLOW_QUERY_THRESHOLD_MS = 200


async def execute_with_instrumentation(
    conn: asyncpg.Connection,
    sql: str,
    params: list[Any],
    query_label: str = "retrieval",
) -> list[asyncpg.Record]:
    """
    Execute a query and log timing. If the query exceeds the slow
    query threshold, capture and log the EXPLAIN ANALYZE output.
    """
    start = time.perf_counter()
    rows = await conn.fetch(sql, *params)
    elapsed_ms = (time.perf_counter() - start) * 1000

    logger.info(
        "query_label=%s elapsed_ms=%.1f row_count=%d",
        query_label,
        elapsed_ms,
        len(rows),
    )

    if elapsed_ms > SLOW_QUERY_THRESHOLD_MS:
        logger.warning(
            "Slow query detected: label=%s elapsed_ms=%.1f — capturing plan",
            query_label,
            elapsed_ms,
        )
        await _log_query_plan(conn, sql, params, query_label)

    return rows


async def _log_query_plan(
    conn: asyncpg.Connection,
    sql: str,
    params: list[Any],
    query_label: str,
) -> None:
    """
    Run EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) and log the plan.
    Uses a short timeout to avoid compounding the latency problem.
    """
    explain_sql = f"EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) {sql}"
    try:
        plan_json = await asyncio.wait_for(
            conn.fetchval(explain_sql, *params),
            timeout=5.0,
        )
        logger.warning(
            "slow_query_plan label=%s plan=%s",
            query_label,
            plan_json,
        )
    except asyncio.TimeoutError:
        logger.warning("Plan capture timed out for label=%s", query_label)
    except asyncpg.PostgresError as exc:
        logger.warning("Plan capture failed for label=%s: %s", query_label, exc)

    In addition to application-level instrumentation, configure PostgreSQL's pg_stat_statements extension to track query patterns at the database level:

    -- Enable pg_stat_statements (requires restart if not already loaded)
-- In postgresql.conf: shared_preload_libraries = 'pg_stat_statements'

-- After enabling, inspect the slowest retrieval queries
SELECT
    left(query, 120)                AS query_snippet,
    calls,
    round(mean_exec_time::numeric, 1) AS mean_ms,
    round(total_exec_time::numeric, 1) AS total_ms,
    round(stddev_exec_time::numeric, 1) AS stddev_ms,
    rows / calls                     AS avg_rows
FROM pg_stat_statements
WHERE
    query ILIKE '%document_chunks%'
    AND query ILIKE '%embedding%'
ORDER BY mean_exec_time DESC
LIMIT 20;

    This view lets you identify which filter combinations are consistently slow, which guides index tuning decisions.

    Managing Index Freshness with Incremental Updates

    One operational concern with HNSW indexes is that they are not updated transactionally — inserting a new row triggers an incremental graph update, but the graph may temporarily be less optimal than one built from scratch. For workloads with very high insert rates, this can degrade recall over time.

    The practical mitigation is to use REINDEX CONCURRENTLY during low-traffic windows for tables with significant write churn:

    -- Rebuild the HNSW index without locking out reads
-- This is safe to run in production during off-peak hours
REINDEX INDEX CONCURRENTLY idx_chunks_embedding_published;

    For tables where you publish documents in batches (for example, a nightly sync of a CMS), consider a workflow that updates the status column from processing to published in a single batch transaction. This triggers the HNSW index updates for the new rows in bulk rather than one-at-a-time, which is more efficient:

    -- Publish a batch of processed documents atomically
-- The partial index will pick up these new rows after this transaction commits
UPDATE document_chunks
SET status = 'published'
WHERE
    document_id IN (
        SELECT document_id FROM documents
        WHERE status = 'processing'
          AND processing_completed_at < NOW() - INTERVAL '5 minutes'
    )
    AND status = 'processing';

    Key Takeaways

  • → **Metadata filtering is a correctness requirement, not just a performance concern.** Without tenant isolation filters, a vector search can return data across security boundaries. Build tenant scoping into every retrieval query from the start, not as an afterthought.
  • → **Denormalize filter columns onto the chunk table.** Storing `tenant_id`, `status`, `language`, and `category` directly on `document_chunks` avoids JOIN overhead on the hot retrieval path and lets PostgreSQL use composite B-tree indexes for those columns efficiently.
  • → **Partial HNSW indexes on `status = 'published'` reduce index size and improve recall quality.** By excluding drafts and archived documents from the index, the graph is smaller, inserts are faster, and queries can use the index without post-filtering noise from non-published rows.
  • → **Choose pre-filter or post-filter strategy based on estimated selectivity.** When SQL filters reduce the candidate set below roughly 50,000 rows, a sequential scan over the filtered set is often faster than over-fetching from HNSW. Use `EXPLAIN (FORMAT JSON)` without execution to get planner row estimates cheaply and select the right strategy at query time.
  • → **Dynamic query builders protect against SQL injection and combinatorial query proliferation.** Rather than maintaining separate query strings for every filter combination, use a parameterized builder that constructs the WHERE clause from active filters at runtime, keeping all user-supplied values in bound parameters rather than embedded in the SQL string.
