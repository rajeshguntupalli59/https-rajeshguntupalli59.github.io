Chapter 4: Google Cloud SQL and AlloyDB Pricing Deep Dive

Organizations running production workloads on Google Cloud SQL and AlloyDB routinely overspend by 35–55% compared to their optimized baseline. A mid-sized engineering team running three Cloud SQL for PostgreSQL instances—a db-custom-8-32768 primary, a read replica, and a dev instance left running around the clock—can easily accumulate $4,200/month in avoidable charges before anyone notices. This chapter breaks down exactly how Google prices Cloud SQL and AlloyDB, where the hidden costs live, and how to systematically eliminate waste. By the end, a disciplined implementation of the techniques here can recover $1,500–$8,000/month for a typical team running five to fifteen database instances.

---

4.1 How Google Cloud SQL and AlloyDB Pricing Actually Works

Understanding the billing model is the first step to controlling it. Cloud SQL and AlloyDB look similar on the surface but have meaningfully different pricing structures that affect optimization strategy.

Cloud SQL Pricing Components

Cloud SQL bills across five independent dimensions:

1. Instance (vCPU + RAM) — billed per second, based on machine type

2. Storage — billed per GB/month, separate from compute

3. Networking — egress to other regions, internet, or cross-zone replicas

4. Backups — beyond the free tier (equal to instance storage size)

5. IP address — $0.01/hour for a public IPv4 address when the instance is running

For a db-custom-8-32768 instance (8 vCPU, 32 GB RAM) running PostgreSQL 15 in us-central1, the on-demand pricing breaks down as:

| Component | Unit Price | Example Usage | Monthly Cost |

|---|---|---|---|

| vCPU | $0.0413/vCPU/hour | 8 vCPU × 730h | $241.59 |

| RAM | $0.0070/GB/hour | 32 GB × 730h | $163.84 |

| SSD Storage | $0.170/GB/month | 500 GB | $85.00 |

| Backup storage | $0.08/GB/month | 200 GB over free | $16.00 |

| IPv4 address | $0.01/hour | 730h | $7.30 |

| Total | | | $513.73 |

Add a same-region read replica with identical specs and you're at $1,027.46/month before any data egress. That's a useful baseline to anchor your optimization work.

Cloud SQL Committed Use Discounts (CUDs)

Google offers 1-year and 3-year committed use discounts for Cloud SQL compute (not storage):

  • → **1-year CUD**: 25% discount on vCPU and RAM
  • → **3-year CUD**: 52% discount on vCPU and RAM

    • For the 8 vCPU, 32 GB instance above, a 1-year CUD reduces the compute portion from $405.43 to $304.07—a savings of $101.36/month or $1,216.32/year. A 3-year CUD drops it to $194.61/month, saving $210.82/month or $2,529.84/year.

    Storage, networking, backups, and IP addresses are excluded from CUDs and billed at on-demand rates regardless.

    AlloyDB Pricing Components

    AlloyDB uses a fundamentally different model that trips up teams migrating from Cloud SQL:

    1. Cluster compute — billed per vCPU/hour for the primary and each read pool instance

    2. Storage — a unified, automatically managed storage layer billed per GB/month across the cluster

    3. I/O requests — billed separately at $0.10 per million read/write operations (this is the most common surprise cost)

    4. Backups — $0.023/GB/month for automated backups beyond the database size

    The I/O charge is what catches teams off guard. A busy OLTP database performing 500 million I/O operations per day generates $1,500/month in I/O costs alone. AlloyDB's storage is intelligent—it caches aggressively and reduces physical I/O compared to Cloud SQL—but the billing unit is logical I/O at the application layer, not physical disk operations.

    AlloyDB compute pricing in us-central1:

  • → vCPU: $0.0722/vCPU/hour
  • → RAM: $0.00963/GB/hour

    • A 16-vCPU, 128 GB AlloyDB primary instance costs approximately $1,743/month in compute before storage or I/O. AlloyDB CUDs provide 25% (1-year) and 52% (3-year) discounts on compute only.

    The Right Tool for the Right Workload

    Before optimizing, confirm you're on the right product:

  • → **Cloud SQL** is cost-effective for standard OLTP workloads under ~5,000 QPS with moderate I/O
  • → **AlloyDB** pays for itself on analytical and mixed OLAP/OLTP workloads where its columnar engine eliminates full table scans, or for workloads requiring 4× faster reads than Cloud SQL
  • → Running AlloyDB for a simple 200 QPS web application backend will cost 2–3× more than Cloud SQL with no performance benefit
    • graph TD
    A[New database workload] --> B{Analytical queries or\nmixed OLAP/OLTP?}
    B -->|Yes| C[AlloyDB]
    B -->|No| D{Standard OLTP\nunder ~5,000 QPS?}
    D -->|Yes| E[Cloud SQL]
    D -->|No, needs 4x faster reads| C

    *Choosing between Cloud SQL and AlloyDB before any cost optimization begins — picking the wrong product costs more than any tuning saves.*

    4.2 Diagnosing Where Your Money Is Going

    Before making changes, establish a clear picture of current spend by instance, component, and time pattern. The GCP Cost Table in BigQuery is the most granular source of billing data available.

    Setting Up BigQuery Billing Export

    If you haven't already enabled billing export to BigQuery, do it now—you need this data for everything that follows.

    Once billing data is flowing into BigQuery, the following queries give you a complete cost map.

    Query 1: Cloud SQL Cost Breakdown by Instance and Component

    -- Run this in BigQuery against your billing export table
-- Replace the table name with your actual export table
WITH cloud_sql_costs AS (
  SELECT
    -- Extract instance name from resource labels
    resource.labels['database_id'] AS instance_id,
    resource.labels['region']      AS region,
    sku.description                AS cost_component,
    
    -- Categorize cost types for easier filtering
    CASE
      WHEN sku.description LIKE '%vCPU%'    THEN 'Compute-vCPU'
      WHEN sku.description LIKE '%RAM%'     THEN 'Compute-RAM'
      WHEN sku.description LIKE '%Storage%' THEN 'Storage'
      WHEN sku.description LIKE '%Backup%'  THEN 'Backup'
      WHEN sku.description LIKE '%Network%' THEN 'Network'
      WHEN sku.description LIKE '%IP%'      THEN 'IP-Address'
      ELSE 'Other'
    END AS cost_category,
    
    SUM(cost)                            AS total_cost_usd,
    SUM(usage.amount)                    AS total_usage,
    usage.unit                           AS usage_unit,
    
    -- Month for trending
    FORMAT_DATE('%Y-%m', DATE(usage_start_time)) AS billing_month
    
  FROM `YOUR_PROJECT.billing_export.gcp_billing_export_v1_XXXXXX`
  WHERE
    service.description = 'Cloud SQL'
    AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
    AND cost > 0
  GROUP BY 1, 2, 3, 4, 9, 10
),

-- Pivot to show monthly trend per instance
instance_summary AS (
  SELECT
    instance_id,
    region,
    cost_category,
    billing_month,
    ROUND(total_cost_usd, 2) AS monthly_cost_usd
  FROM cloud_sql_costs
)

SELECT
  instance_id,
  region,
  cost_category,
  SUM(CASE WHEN billing_month = FORMAT_DATE('%Y-%m', DATE_SUB(CURRENT_DATE(), INTERVAL 1 MONTH))
           THEN monthly_cost_usd ELSE 0 END) AS last_month_usd,
  SUM(CASE WHEN billing_month = FORMAT_DATE('%Y-%m', DATE_SUB(CURRENT_DATE(), INTERVAL 2 MONTH))
           THEN monthly_cost_usd ELSE 0 END) AS two_months_ago_usd,
  SUM(CASE WHEN billing_month = FORMAT_DATE('%Y-%m', DATE_SUB(CURRENT_DATE(), INTERVAL 3 MONTH))
           THEN monthly_cost_usd ELSE 0 END) AS three_months_ago_usd
FROM instance_summary
GROUP BY 1, 2, 3
ORDER BY last_month_usd DESC;

    Query 2: AlloyDB I/O Cost Analysis

    AlloyDB I/O costs require separate tracking because they scale with query volume, not instance size. This query identifies your I/O spend trend and flags instances where I/O exceeds 30% of total cluster cost—a threshold that indicates optimization opportunity.

    -- BigQuery query to analyze AlloyDB I/O costs
WITH alloydb_costs AS (
  SELECT
    resource.labels['cluster_id']    AS cluster_id,
    resource.labels['instance_id']   AS instance_id,
    resource.labels['region']        AS region,
    sku.description                  AS sku_description,
    
    CASE
      WHEN sku.description LIKE '%Read IO%'   THEN 'IO-Read'
      WHEN sku.description LIKE '%Write IO%'  THEN 'IO-Write'
      WHEN sku.description LIKE '%vCPU%'      THEN 'Compute-vCPU'
      WHEN sku.description LIKE '%Memory%'    THEN 'Compute-RAM'
      WHEN sku.description LIKE '%Storage%'   THEN 'Storage'
      WHEN sku.description LIKE '%Backup%'    THEN 'Backup'
      ELSE 'Other'
    END AS cost_category,
    
    FORMAT_DATE('%Y-%m', DATE(usage_start_time)) AS billing_month,
    SUM(cost)                                    AS total_cost_usd,
    SUM(usage.amount)                            AS total_usage_units
    
  FROM `YOUR_PROJECT.billing_export.gcp_billing_export_v1_XXXXXX`
  WHERE
    service.description = 'AlloyDB for PostgreSQL'
    AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
  GROUP BY 1, 2, 3, 4, 5, 6
),

cluster_totals AS (
  SELECT
    cluster_id,
    billing_month,
    SUM(total_cost_usd) AS cluster_total_cost
  FROM alloydb_costs
  GROUP BY 1, 2
),

io_costs AS (
  SELECT
    cluster_id,
    billing_month,
    SUM(total_cost_usd) AS io_total_cost
  FROM alloydb_costs
  WHERE cost_category IN ('IO-Read', 'IO-Write')
  GROUP BY 1, 2
)

SELECT
  a.cluster_id,
  a.billing_month,
  ROUND(c.cluster_total_cost, 2)    AS cluster_total_usd,
  ROUND(i.io_total_cost, 2)         AS io_cost_usd,
  ROUND(
    SAFE_DIVIDE(i.io_total_cost, c.cluster_total_cost) * 100, 1
  )                                 AS io_pct_of_total,
  CASE
    WHEN SAFE_DIVIDE(i.io_total_cost, c.cluster_total_cost) > 0.30
    THEN 'REVIEW: High I/O ratio - check for missing indexes or full scans'
    ELSE 'OK'
  END                               AS recommendation
FROM alloydb_costs a
JOIN cluster_totals c USING (cluster_id, billing_month)
JOIN io_costs i USING (cluster_id, billing_month)
GROUP BY 1, 2, 3, 4, 5, 6
ORDER BY billing_month DESC, cluster_total_usd DESC;

    Identifying Idle and Underutilized Instances

    Cloud Monitoring provides the CPU and connection utilization data needed to flag idle instances. An instance consuming less than 5% average CPU over 30 days with fewer than 5 concurrent connections is a strong candidate for deletion or significant downsizing.

    #!/bin/bash
# Script: find_idle_cloud_sql_instances.sh
# Scans all Cloud SQL instances in a project for low CPU utilization
# Schedule this with Cloud Scheduler weekly

PROJECT_ID="${1:-$(gcloud config get-value project)}"
LOOKBACK_DAYS=30
CPU_THRESHOLD=5  # Flag instances below 5% average CPU
CONN_THRESHOLD=5 # Flag instances with fewer than 5 avg connections

echo "Analyzing Cloud SQL instances in project: $PROJECT_ID"
echo "Lookback period: $LOOKBACK_DAYS days"
echo "---"

# Get all Cloud SQL instances
INSTANCES=$(gcloud sql instances list \
  --project="$PROJECT_ID" \
  --format="value(name,region,databaseVersion,settings.tier)" \
  --filter="state=RUNNABLE")

echo "Instance,Region,Engine,Tier,Avg_CPU_Pct,Avg_Connections,Status"

while IFS=$'\t' read -r INSTANCE REGION ENGINE TIER; do
  # Query Cloud Monitoring for average CPU over lookback period
  AVG_CPU=$(gcloud monitoring read \
    "metric.type=\"cloudsql.googleapis.com/database/cpu/utilization\" \
    resource.labels.database_id=\"$PROJECT_ID:$INSTANCE\"" \
    --freshness="$((LOOKBACK_DAYS * 24))h" \
    --format="value(points[0].value.doubleValue)" \
    2>/dev/null | awk '{sum+=$1; count++} END {printf "%.1f", (sum/count)*100}')

  # Query average connections
  AVG_CONN=$(gcloud monitoring read \
    "metric.type=\"cloudsql.googleapis.com/database/network/connections\" \
    resource.labels.database_id=\"$PROJECT_ID:$INSTANCE\"" \
    --freshness="$((LOOKBACK_DAYS * 24))h" \
    --format="value(points[0].value.int64Value)" \
    2>/dev/null | awk '{sum+=$1; count++} END {printf "%.0f", sum/count}')

  # Default to 0 if metric fetch failed
  AVG_CPU=${AVG_CPU:-0}
  AVG_CONN=${AVG_CONN:-0}

  # Classify the instance
  if (( $(echo "$AVG_CPU < $CPU_THRESHOLD" | bc -l) )) && \
     (( AVG_CONN < CONN_THRESHOLD )); then
    STATUS="IDLE - CANDIDATE FOR DELETION OR STOP"
  elif (( $(echo "$AVG_CPU < 20" | bc -l) )); then
    STATUS="UNDERUTILIZED - CONSIDER DOWNSIZING"
  else
    STATUS="ACTIVE"
  fi

  echo "$INSTANCE,$REGION,$ENGINE,$TIER,${AVG_CPU}%,$AVG_CONN,$STATUS"

done <<< "$INSTANCES"

    4.3 Right-Sizing Cloud SQL Instances

    Right-sizing is consistently the largest single savings lever available—larger than CUDs, larger than storage optimization, and larger than any architectural change. The reason is straightforward: most teams provision for peak capacity that never materializes, then leave those instances running at 8–15% CPU for months.

    The Cloud SQL Machine Type Landscape

    Cloud SQL offers three tiers:

  • → **Shared core** (`db-f1-micro`, `db-g1-small`): Dev/test only, not suitable for production
  • → **Standard machine types** (`db-n1-standard-*`, `db-n2-standard-*`): Fixed vCPU/RAM ratios
  • → **Custom machine types** (`db-custom-N-M`): Choose any vCPU count and RAM independently

    • Custom machine types are almost always cheaper than standard types for real workloads because you pay only for what you configure. A db-custom-4-15360 (4 vCPU, 15 GB RAM) costs less than db-n1-standard-4 (4 vCPU, 15 GB RAM) in most regions because the custom type uses N2 generation pricing which is more cost-efficient per unit.

    The Memory-to-vCPU Ratio Decision

    The most common right-sizing mistake is provisioning too much RAM relative to vCPU count, or vice versa. Use this framework:

    | Workload Pattern | Recommended Ratio | Example |

    |---|---|---|

    | OLTP, high concurrency | 4–8 GB RAM per vCPU | db-custom-8-32768 |

    | Analytics, large datasets | 8–16 GB RAM per vCPU | db-custom-4-61440 |

    | Connection-heavy, small queries | 2–4 GB RAM per vCPU | db-custom-16-32768 |

    | Batch processing | 4 GB RAM per vCPU | db-custom-4-16384 |

    Querying Actual Resource Utilization from pg_stat

    Before recommending a right-size target, pull actual utilization data from the database itself:

    -- Run directly on your Cloud SQL PostgreSQL instance
-- This query gives a complete utilization picture for right-sizing decisions

WITH 
-- Memory pressure assessment
memory_stats AS (
  SELECT
    name,
    setting,
    unit,
    CASE name
      WHEN 'shared_buffers'      THEN setting::bigint * 8192
      WHEN 'work_mem'            THEN setting::bigint * 1024
      WHEN 'maintenance_work_mem' THEN setting::bigint * 1024
      WHEN 'effective_cache_size' THEN setting::bigint * 8192
    END AS bytes
  FROM pg_settings
  WHERE name IN (
    'shared_buffers', 'work_mem', 
    'maintenance_work_mem', 'effective_cache_size',
    'max_connections'
  )
),

-- Buffer cache hit ratio (lower than 95% suggests memory pressure)
cache_stats AS (
  SELECT
    sum(heap_blks_read)  AS heap_disk_reads,
    sum(heap_blks_hit)   AS heap_cache_hits,
    ROUND(
      100.0 * sum(heap_blks_hit) / 
      NULLIF(sum(heap_blks_hit) + sum(heap_blks_read), 0), 2
    )                    AS cache_hit_ratio_pct
  FROM pg_statio_user_tables
),

-- Active connections vs. configured max
connection_stats AS (
  SELECT
    count(*)                           AS total_connections,
    count(*) FILTER (WHERE state = 'active')   AS active_connections,
    count(*) FILTER (WHERE state = 'idle')     AS idle_connections,
    count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_txn,
    max(now() - query_start) FILTER (WHERE state = 'active') AS longest_active_query,
    (SELECT setting::int FROM pg_settings WHERE name = 'max_connections') AS max_connections_cfg
  FROM pg_stat_activity
  WHERE pid <> pg_backend_pid()
),

-- Top CPU-consuming queries (requires pg_stat_statements)
top_queries AS (
  SELECT
    LEFT(query, 80)          AS query_preview,
    calls,
    ROUND(total_exec_time::numeric / 1000, 2) AS total_exec_sec,
    ROUND(mean_exec_time::numeric, 2)         AS avg_exec_ms,
    ROUND(stddev_exec_time::numeric, 2)       AS stddev_exec_ms,
    rows
  FROM pg_stat_statements
  ORDER BY total_exec_time DESC
  LIMIT 5
)

-- Combined output
SELECT 'CACHE HIT RATIO'            AS metric_type,
       cache_hit_ratio_pct::text    AS value,
       CASE WHEN cache_hit_ratio_pct < 95 
            THEN 'WARNING: Consider increasing shared_buffers or instance RAM'
            ELSE 'OK: Cache hit ratio is healthy'
       END                          AS recommendation
FROM cache_stats

UNION ALL

SELECT 'CONNECTION UTILIZATION',
       ROUND(100.0 * total_connections / max_connections_cfg, 1)::text || '%',
       CASE 
         WHEN 100.0 * total_connections / max_connections_cfg > 80
         THEN 'WARNING: Consider pgBouncer or increasing max_connections'
         WHEN idle_in_txn > 10
         THEN 'WARNING: ' || idle_in_txn || ' idle-in-transaction connections - check for connection leaks'
         ELSE 'OK'
       END
FROM connection_stats

UNION ALL

SELECT 'IDLE CONNECTIONS',
       idle_connections::text,
       CASE WHEN idle_connections > 50
            THEN 'COST ALERT: ' || idle_connections || 
                 ' idle connections consuming RAM. Deploy pgBouncer to reduce instance RAM needs.'
            ELSE 'OK'
       END
FROM connection_stats;

    Calculating Right-Size Savings

    Here is the actual math for a common right-sizing scenario. Suppose Cloud Monitoring shows your db-custom-8-32768 instance averages 18% CPU and 12 GB RAM in use over 30 days. The right-size target is db-custom-4-16384:

    | Metric | Current | Right-Sized | Savings |

    |---|---|---|---|

    | vCPU | 8 × $0.0413 × 730h | 4 × $0.0413 × 730h | $120.79/mo |

    | RAM | 32 GB × $0.007 × 730h | 16 GB × $0.007 × 730h | $81.92/mo |

    | Monthly savings | $513.73 | $310.01 | $203.72/mo |

    | Annual savings | | | $2,444.64 |

    Apply a 1-year CUD to the right-sized instance — remembering that the discount applies only to the vCPU and RAM portion, not storage, backup, or IP — and the monthly cost drops further to $259.58, for a total monthly savings of $254.15 versus the original on-demand oversized instance.

    Stopping Dev Instances After Hours

    A dev instance running 24/7 versus running 10 hours/day on weekdays only costs 3× more than necessary. Cloud SQL supports instance start/stop via the API. A db-custom-4-16384 dev instance at on-demand pricing costs approximately $202/month running continuously. Stopping it outside working hours—say, 7 AM to 7 PM Monday through Friday—reduces runtime from 730 hours to roughly 260 hours per month, cutting the compute bill to about $72/month. Storage still accrues while the instance is stopped, but that's a small fraction of total cost.

    #!/bin/bash
# Script: schedule_dev_instance_stop_start.sh
# Deploy this via Cloud Scheduler + Cloud Run Jobs or Cloud Functions
# Two jobs: one to start (07:00 Mon-Fri), one to stop (19:00 Mon-Fri)

PROJECT_ID="${GOOGLE_CLOUD_PROJECT}"
INSTANCE_NAME="${CLOUD_SQL_INSTANCE}"
ACTION="${1}"  # "start" or "stop"

if [[ -z "$PROJECT_ID" || -z "$INSTANCE_NAME" || -z "$ACTION" ]]; then
  echo "ERROR: Required environment variables not set"
  exit 1
fi

case "$ACTION" in
  start)
    echo "Starting Cloud SQL instance: $INSTANCE_NAME"
    gcloud sql instances patch "$INSTANCE_NAME" \
      --project="$PROJECT_ID" \
      --activation-policy=ALWAYS
    echo "Instance start initiated at $(date -u)"
    ;;
  stop)
    echo "Stopping Cloud SQL instance: $INSTANCE_NAME"
    gcloud sql instances patch "$INSTANCE_NAME" \
      --project="$PROJECT_ID" \
      --activation-policy=NEVER
    echo "Instance stop initiated at $(date -u)"
    ;;
  *)
    echo "ERROR: Unknown action '$ACTION'. Use 'start' or 'stop'."
    exit 1
    ;;
esac

# Verify the state change
sleep 10
STATE=$(gcloud sql instances describe "$INSTANCE_NAME" \
  --project="$PROJECT_ID" \
  --format="value(state)")
echo "Current instance state: $STATE"

    To wire this up with Cloud Scheduler:

    Two cautions when implementing instance scheduling: first, Cloud SQL does not gracefully drain connections on stop—applications need to handle connection errors with retry logic. Second, Cloud SQL charges for storage while stopped, so a stopped 500 GB instance still accrues $85/month in storage costs. For truly long-lived dev instances that are rarely used, consider exporting the data, deleting the instance, and restoring from the export on demand.

    4.4 Storage Optimization for Cloud SQL and AlloyDB

    Storage costs are easy to dismiss as a rounding error, but they compound in two ways that make them worth managing: Cloud SQL storage only grows automatically (it never shrinks), and backup storage accumulates silently beyond the free tier threshold.

    The Automatic Storage Increase Trap

    Cloud SQL's "Enable automatic storage increases" setting is enabled by default and is appropriate for production instances. The problem is that it only triggers upward—there is no automatic decrease. A database that grew to 800 GB during a bulk load six months ago, then had most data purged, still shows 800 GB of provisioned storage at $136/month even if only 200 GB is actually occupied.

    To recover over-provisioned storage, you must export the data, delete the instance, and recreate it at the correct size. This is disruptive and requires a maintenance window, so do the math before committing:

    -- PostgreSQL: Measure actual database sizes vs. provisioned storage
-- Run on Cloud SQL PostgreSQL to understand actual storage consumption

SELECT
  datname                              AS database_name,
  pg_size_pretty(pg_database_size(datname))  AS database_size,
  pg_database_size(datname)            AS size_bytes,
  ROUND(pg_database_size(datname) / 1024.0^3, 2) AS size_gb
FROM pg_database
WHERE datname NOT IN ('template0', 'template1', 'cloudsqladmin')
ORDER BY size_bytes DESC;

-- Also check table bloat within your primary database
-- Significant bloat means VACUUM hasn't run effectively
SELECT
  schemaname,
  tablename,
  pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS total_size,
  pg_size_pretty(pg_relation_size(schemaname || '.' || tablename))       AS table_size,
  pg_size_pretty(
    pg_total_relation_size(schemaname || '.' || tablename)
    - pg_relation_size(schemaname || '.' || tablename)
  )                                                                       AS index_size,
  ROUND(
    100.0 * (pg_total_relation_size(schemaname || '.' || tablename)
             - pg_relation_size(schemaname || '.' || tablename))
    / NULLIF(pg_total_relation_size(schemaname || '.' || tablename), 0), 1
  )                                                                       AS index_pct
FROM pg_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema', 'pg_toast')
ORDER BY pg_total_relation_size(schemaname || '.' || tablename) DESC
LIMIT 20;

    Reclaiming Space Without Recreating the Instance

    Before planning a full export-and-recreate cycle, attempt in-place space reclamation:

    1. Run VACUUM FULL on bloated tables — rewrites table files and returns disk space to the OS. It requires an exclusive lock, so run this during a maintenance window.

    2. Drop unused indexes — Chapter 5 covers this in depth, but indexes frequently account for 20–40% of total database size in over-indexed schemas.

    3. Archive and purge old data — moving records older than your retention requirement to Cloud Storage as Parquet files via Dataflow typically recovers more storage than any tuning approach.

    -- PostgreSQL: Find tables with significant dead tuple bloat
-- These are candidates for VACUUM FULL
SELECT
  schemaname,
  relname                              AS table_name,
  n_live_tup                           AS live_rows,
  n_dead_tup                           AS dead_rows,
  ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1)
                                       AS dead_row_pct,
  last_vacuum,
  last_autovacuum,
  pg_size_pretty(pg_total_relation_size(schemaname || '.' || relname))
                                       AS total_size
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
  AND (n_dead_tup::float / NULLIF(n_live_tup + n_dead_tup, 0)) > 0.10
ORDER BY n_dead_tup DESC
LIMIT 20;

    Backup Storage Cost Control

    Cloud SQL automatically backs up your instances daily and retains those backups for 7 days by default. The free tier for backup storage equals the provisioned instance storage size. Any backup storage beyond that threshold costs $0.08/GB/month.

    If your instance has 500 GB of provisioned storage but only 150 GB of actual data, you're potentially storing seven 150 GB compressed backups. Google's compression typically yields 2–4× reduction for typical relational data, so actual backup storage per day might be around 40–75 GB. Over seven days that's 280–525 GB. Subtracting the 500 GB free tier, the overage is small in this example—but for larger instances or teams that have extended retention to 30 days without justification, the costs add up quickly.

  --format="table(name,settings.backupConfiguration.enabled,
                  settings.backupConfiguration.binaryLogEnabled,

                  diskSizeGb)"

# For a specific instance, list actual backups and their sizes
gcloud sql backups list \
  --instance="YOUR_INSTANCE_NAME" \
  --project="$PROJECT_ID" \
  --format="table(id,status,startTime,endTime,diskEncryptionConfiguration,

    For most teams, reducing backup retention from 30 days to 7 days—or from 14 to 7—for non-production instances alone recovers meaningful storage cost. A production instance with genuine compliance requirements for 30-day retention should keep it, but dev and staging instances rarely need more than 3–5 days of backup history.

    AlloyDB Storage: The Unified Layer Consideration

    AlloyDB manages storage differently from Cloud SQL. The storage layer is distributed and automatically tiered across hot and cold data. You pay for the total data volume stored, not provisioned capacity, which means you never pay for empty space. This eliminates the automatic-storage-increase trap.

    However, AlloyDB does not shrink its storage accounting when you delete data—rows deleted from AlloyDB tables are not immediately reclaimed at the storage billing layer until the storage background compaction process runs. For workloads with heavy delete patterns (log tables, event streams, rolling window aggregation), this means storage costs can lag actual data volume by days. Plan accordingly when evaluating AlloyDB storage bills against actual data sizes.

    4.5 Reducing AlloyDB I/O Costs Through Query Optimization

    AlloyDB I/O billing is the most actionable cost lever unique to the product. Every full table scan, every unindexed lookup, every cartesian join produces I/O operations that appear on your bill. The path to reducing I/O cost is identical to the path to improving query performance—which means I/O optimization pays a double dividend.

    Identifying High-I/O Queries

    AlloyDB exposes query statistics through the google_sys.query_stats system view, which is seeded by the google_columnar_engine and standard PostgreSQL pg_stat_statements extensions.

    -- AlloyDB PostgreSQL: Find the top I/O-generating queries
-- These are the queries most directly responsible for your I/O bill

SELECT
  LEFT(query, 100)                          AS query_preview,
  calls,
  ROUND(total_exec_time::numeric / 1000, 2) AS total_exec_sec,
  ROUND(mean_exec_time::numeric, 2)         AS avg_exec_ms,
  shared_blks_read                          AS buffer_misses,
  shared_blks_hit                           AS buffer_hits,
  shared_blks_read + shared_blks_hit        AS total_blocks_accessed,
  ROUND(
    100.0 * shared_blks_read 
    / NULLIF(shared_blks_read + shared_blks_hit, 0), 1
  )                                         AS miss_rate_pct,
  -- Blocks read from disk directly correspond to I/O billing units
  ROUND(shared_blks_read * 8.0 / 1024, 2)  AS estimated_data_read_mb
FROM pg_stat_statements
WHERE calls > 100
  AND shared_blks_read > 10000  -- Focus on high-I/O queries only
ORDER BY shared_blks_read DESC
LIMIT 20;

    A query appearing at the top of this list with a high miss_rate_pct tells you that the working set for that query is not in buffer cache—it's going to storage on every execution. The fix is one of four things:

    1. Add a covering index that satisfies the query without a heap access

    2. Increase shared_buffers to cache more of the hot dataset

    3. Use AlloyDB's columnar engine to serve analytical queries from compressed column-oriented storage

    4. Partition the table to reduce the scan range for time-series or range queries

    Using the AlloyDB Columnar Engine to Reduce I/O

    AlloyDB includes an in-memory columnar engine that stores compressed column-oriented representations of tables alongside the standard row-oriented heap. Queries that scan large portions of a table benefit enormously—the columnar engine typically reads 5–10× less data than the equivalent row scan, which directly translates to fewer I/O billing units.

    Enabling the columnar engine is straightforward:

    -- AlloyDB: Enable and configure the columnar engine
-- This requires the alloydb.enable_columnar_engine flag set to 'on' in instance settings
-- Verify it is active:
SHOW alloydb.enable_columnar_engine;

-- Check current columnar engine memory allocation
SHOW alloydb.columnar_engine_memory;

-- Populate the columnar engine for a specific table
-- AlloyDB can auto-populate, but manual population ensures immediate benefit
SELECT google_columnar_engine_add('public.orders');
SELECT google_columnar_engine_add('public.order_line_items');

-- Verify which tables are in the columnar engine
SELECT
  relation_name,
  column_count,
  state,
  pg_size_pretty(size_in_bytes::bigint) AS columnar_size,
  pg_size_pretty(heap_size_in_bytes::bigint) AS heap_size,
  ROUND(
    100.0 * (1 - size_in_bytes::float / NULLIF(heap_size_in_bytes, 0)), 1
  )                                           AS compression_pct
FROM google_columnar_engine_tables();

    When the columnar engine serves a query, EXPLAIN (ANALYZE, BUFFERS) shows a Columnar Scan node instead of Seq Scan. The Buffers output shows dramatically fewer blocks read, which corresponds directly to lower I/O billing. For an analytical query scanning a 100 GB orders table, the difference between a sequential heap scan and a columnar scan can be the difference between 13 million I/O operations and 1.2 million—a reduction of more than 90% on that query's I/O bill.

    Index Strategy for I/O Reduction

    For OLTP workloads where the columnar engine is not appropriate (single-row lookups, small result sets, high-concurrency point queries), indexes are the primary I/O reduction tool. The principle is to eliminate every sequential scan that touches more rows than will ultimately be returned.

    -- AlloyDB/Cloud SQL PostgreSQL: Find sequential scans on large tables
-- These are the highest-priority indexing opportunities for I/O cost reduction

SELECT
  schemaname,
  relname                              AS table_name,
  seq_scan,
  seq_tup_read,
  idx_scan,
  idx_tup_fetch,
  ROUND(seq_tup_read::numeric / NULLIF(seq_scan, 0), 0)
                                       AS avg_rows_per_seqscan,
  pg_size_pretty(pg_total_relation_size(schemaname || '.' || relname))
                                       AS table_size,
  pg_total_relation_size(schemaname || '.' || relname)
                                       AS size_bytes
FROM pg_stat_user_tables
WHERE seq_scan > 100
  AND pg_total_relation_size(schemaname || '.' || relname) > 10 * 1024 * 1024  -- > 10 MB
ORDER BY seq_tup_read DESC
LIMIT 20;

    A table with high seq_scan count and large avg_rows_per_seqscan is one where queries are scanning the entire table but returning a small fraction of rows—the textbook case for a missing index. Building the right index on such a table can reduce I/O for that query pattern by two to three orders of magnitude.

    The Equivalent SQL Server Pattern

    For teams maintaining cross-platform references, here is the equivalent diagnostic query for SQL Server (applicable to Azure SQL Database and SQL Server on Google Cloud Compute Engine):

    -- SQL Server: Find high-logical-read queries from plan cache
-- Equivalent to the pg_stat_statements I/O analysis above

SELECT TOP 20
  SUBSTRING(st.text, (qs.statement_start_offset / 2) + 1,
    ((CASE qs.statement_end_offset
        WHEN -1 THEN DATALENGTH(st.text)
        ELSE qs.statement_end_offset
      END - qs.statement_start_offset) / 2) + 1
  )                                        AS query_text,
  qs.execution_count,
  qs.total_logical_reads,
  qs.total_logical_reads / qs.execution_count
                                           AS avg_logical_reads,
  qs.total_elapsed_time / 1000             AS total_elapsed_ms,
  qs.total_elapsed_time / qs.execution_count / 1000
                                           AS avg_elapsed_ms,
  qp.query_plan
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) qp
WHERE qs.execution_count > 100
ORDER BY qs.total_logical_reads DESC;

    4.6 Network Egress Cost Reduction

    Network costs in Cloud SQL and AlloyDB are easy to ignore until they appear as a line item larger than your storage bill. Understanding the pricing tiers is the first step.

    Cloud SQL Network Pricing

  • → **Same-zone traffic**: Free
  • → **Cross-zone within same region**: $0.01/GB
  • → **Cross-region**: $0.02–$0.08/GB depending on regions
  • → **Internet egress**: $0.08–$0.23/GB depending on destination
  • → **Cloud SQL Auth Proxy over the internet**: Charges apply at the internet egress rate

    • The most common source of avoidable network cost is read replicas in different regions provisioned for disaster recovery but receiving continuous replication traffic. A primary instance in us-central1 replicating to a replica in us-east1 generates cross-region traffic at $0.02/GB for every byte of WAL streamed. A write-heavy database generating 50 GB/day of WAL can accumulate $30/day or roughly $900/month in cross-region replication egress alone.

    Diagnosing Network Costs from Billing Export

    -- BigQuery: Break down Cloud SQL network costs by destination type
SELECT
  resource.labels['database_id']  AS instance_id,
  sku.description                  AS network_sku,
  FORMAT_DATE('%Y-%m', DATE(usage_start_time)) AS billing_month,
  ROUND(SUM(cost), 2)             AS cost_usd,
  ROUND(SUM(usage.amount), 2)     AS usage_gb
FROM `YOUR_PROJECT.billing_export.gcp_billing_export_v1_XXXXXX`
WHERE
  service.description = 'Cloud SQL'
  AND (sku.description LIKE '%Network%' 
       OR sku.description LIKE '%Egress%'
       OR sku.description LIKE '%Ingress%')
  AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
GROUP BY 1, 2, 3
ORDER BY cost_usd DESC;

    Practical Network Cost Reduction Tactics

    1. Use Private IP exclusively for application connections. Public IP adds $7.30/month per instance and routes traffic externally even when application and database are in the same VPC. Disable public IP on all production instances reachable only by internal services.

    2. Co-locate application and database in the same zone. Same-zone traffic is free. If your Cloud Run service is in us-central1-a and your Cloud SQL instance is in us-central1-b, you are paying $0.01/GB for every byte of query results returned. Aligning zones eliminates this.

    3. Evaluate cross-region replica necessity. If the cross-region read replica exists for DR purposes but receives zero read traffic, you are paying both for the replica compute and for replication egress with no read-side benefit. A snapshot-based backup strategy using Cloud Storage cross-region replication at $0.02/GB versus continuous WAL streaming can reduce DR costs by 60–80% for write-heavy workloads.

    4. Use Connection pooling to reduce connection overhead. PgBouncer deployed in the same zone as your Cloud SQL instance reduces the number of TCP connections and the associated per-connection overhead, indirectly reducing the volume of small network round trips.

    4.7 Committed Use Discounts: Strategy and Gotchas

    CUDs for Cloud SQL and AlloyDB reduce compute costs by 25% (1-year) or 52% (3-year) but commit you to a specific vCPU and RAM quantity for the duration. Getting the commitment strategy wrong is expensive—you pay for committed units whether you use them or not.

    When to Commit

    Apply CUDs only when you can answer yes to all three of these:

    1. The instance will exist for the full commitment term

    2. The vCPU and RAM configuration will not decrease significantly

    3. You have at least 60 days of billing history showing stable utilization

    Dev instances, recently provisioned production instances, and instances expected to be consolidated within the year should not receive CUDs.

    CUD Scope and Flexibility

    Cloud SQL CUDs are applied at the project level and cover any Cloud SQL instance in the project that matches the committed resource type (PostgreSQL, MySQL, or SQL Server) and region. This means a single CUD covering 16 vCPU in us-central1 can cover two 8-vCPU PostgreSQL instances, one 16-vCPU instance, or any other combination that sums to 16 vCPU of PostgreSQL in that region.

    This flexibility is significant: you can commit at the aggregate project level without tying a commitment to a specific instance. If you decommission one instance and spin up another, the CUD continues to apply as long as the total committed vCPU is consumed.

    # List existing CUDs in a project
gcloud compute commitments list \
  --project="$PROJECT_ID" \
  --filter="category=MACHINE" \
  --format="table(name,region,plan,status,endTimestamp,
                  resources[0].type,resources[0].amount)"

    Calculating the Right Commitment Size

    The risk in over-committing is paying for unused capacity. The risk in under-committing is leaving discount on the table. Target your commitment at the stable baseline—the vCPU count that is consumed even at low traffic periods—and leave peak capacity on-demand.

    -- BigQuery: Calculate CUD coverage recommendation
-- Based on 90-day minimum daily compute spend as the safe commitment baseline

WITH daily_compute AS (
  SELECT
    DATE(usage_start_time)                      AS usage_date,
    resource.labels['region']                   AS region,
    -- Infer database type from SKU
    CASE
      WHEN sku.description LIKE '%PostgreSQL%'  THEN 'PostgreSQL'
      WHEN sku.description LIKE '%MySQL%'       THEN 'MySQL'
      WHEN sku.description LIKE '%SQL Server%'  THEN 'SQL Server'
      ELSE 'Unknown'
    END                                         AS db_type,
    SUM(cost)                                   AS daily_compute_cost
  FROM `YOUR_PROJECT.billing_export.gcp_billing_export_v1_XXXXXX`
  WHERE
    service.description = 'Cloud SQL'
    AND (sku.description LIKE '%vCPU%' OR sku.description LIKE '%RAM%')
    AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
  GROUP BY 1, 2, 3
)

SELECT
  region,
  db_type,
  ROUND(MIN(daily_compute_cost), 2)   AS min_daily_compute_usd,
  ROUND(AVG(daily_compute_cost), 2)   AS avg_daily_compute_usd,
  ROUND(MAX(daily_compute_cost), 2)   AS max_daily_compute_usd,
  -- Safe 1-year commitment = 90% of minimum daily spend annualized
  ROUND(MIN(daily_compute_cost) * 365 * 0.90, 2)  AS recommended_1yr_commit_usd,
  -- Projected 1-year savings at 25% discount on committed portion
  ROUND(MIN(daily_compute_cost) * 365 * 0.90 * 0.25, 2) AS projected_1yr_savings_usd
FROM daily_compute
GROUP BY 1, 2
ORDER BY avg_daily_compute_usd DESC;

    Weekly Cost Anomaly Report via Cloud Scheduler + BigQuery

    The most reliable ongoing governance mechanism is a weekly automated report delivered to a Slack channel or email list. This keeps the conversation about database costs visible without requiring manual effort from engineers.

    # cloud_function/weekly_cost_report.py
# Deploy as a Cloud Function triggered by Cloud Scheduler weekly

import functions_framework
from google.cloud import bigquery
import requests
import os
from datetime import datetime, timedelta

BIGQUERY_TABLE = os.environ["BILLING_TABLE"]
SLACK_WEBHOOK  = os.environ["SLACK_WEBHOOK_URL"]
PROJECT_ID     = os.environ["GOOGLE_CLOUD_PROJECT"]

@functions_framework.http
def weekly_cost_report(request):
    client = bigquery.Client(project=PROJECT_ID)

    query = f"""
    WITH this_week AS (
      SELECT
        resource.labels['database_id'] AS instance_id,
        ROUND(SUM(cost), 2)            AS cost_usd
      FROM `{BIGQUERY_TABLE}`
      WHERE
        service.description = 'Cloud SQL'
        AND DATE(usage_start_time) >= DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY)
      GROUP BY 1
    ),
    last_week AS (
      SELECT
        resource.labels['database_id'] AS instance_id,
        ROUND(SUM(cost), 2)            AS cost_usd
      FROM `{BIGQUERY_TABLE}`
      WHERE
        service.description = 'Cloud SQL'
        AND DATE(usage_start_time) BETWEEN
          DATE_SUB(CURRENT_DATE(), INTERVAL 14 DAY)
          AND DATE_SUB(CURRENT_DATE(), INTERVAL 7 DAY)
      GROUP BY 1
    )
    SELECT
      t.instance_id,
      t.cost_usd                                     AS this_week_usd,
      l.cost_usd                                     AS last_week_usd,
      ROUND(t.cost_usd - COALESCE(l.cost_usd, 0), 2) AS delta_usd,
      ROUND(
        100.0 * (t.cost_usd - COALESCE(l.cost_usd, 0))
        / NULLIF(l.cost_usd, 0), 1
      )                                              AS pct_change
    FROM this_week t
    LEFT JOIN last_week l USING (instance_id)
    ORDER BY this_week_usd DESC
    """

    results = list(client.query(query).result())

    total_this_week = sum(r.this_week_usd for r in results)
    anomalies = [r for r in results if r.pct_change and abs(r.pct_change) > 20]

    # Build Slack message
    blocks = [
        {
            "type": "header",
            "text": {"type": "plain_text",
                     "text": f"☁️ Cloud SQL Weekly Cost Report — {datetime.now().strftime('%b %d, %Y')}"}
        },
        {
            "type": "section",
            "text": {"type": "mrkdwn",
                     "text": f"*Total this week:* ${total_this_week:,.2f}"}
        }
    ]

    if anomalies:
        anomaly_text = "\n".join([
            f"• `{r.instance_id}`: ${r.this_week_usd:.2f} "
            f"({'▲' if r.delta_usd > 0 else '▼'} "
            f"${abs(r.delta_usd):.2f}, {r.pct_change:+.1f}%)"
            for r in anomalies
        ])
        blocks.append({
            "type": "section",
            "text": {"type": "mrkdwn",
                     "text": f"*⚠️ Cost Anomalies (>20% week-over-week):*\n{anomaly_text}"}
        })

    top_instances_text = "\n".join([
        f"• `{r.instance_id}`: ${r.this_week_usd:.2f}"
        for r in results[:5]
    ])
    blocks.append({
        "type": "section",
        "text": {"type": "mrkdwn",
                 "text": f"*Top 5 Instances by Cost:*\n{top_instances_text}"}
    })

    response = requests.post(SLACK_WEBHOOK, json={"blocks": blocks})
    return f"Report sent. Status: {response.status_code}", 200

    Key Takeaways

  • → **Cloud SQL and AlloyDB have structurally different cost models**: Cloud SQL charges for provisioned compute and storage, while AlloyDB adds a per-I/O charge that scales directly with query volume and index efficiency. Understanding which model you are on determines which optimization lever to reach for first.
  • → **Right-sizing is consistently the largest savings opportunity**: Most Cloud SQL instances run at 8–20% average CPU with provisioned resources sized for a peak that rarely materializes. Matching instance tier to the 90th-percentile utilization observed over 30 days—not the theoretical maximum—typically recovers 30–50% of compute spend, amplified further by applying CUDs to the right-sized baseline.
  • → **AlloyDB I/O costs are query performance costs in disguise**: Every sequential scan, every missing index, every unnecessary full table read generates billable I/O operations. Enabling the AlloyDB columnar engine for analytical workloads and maintaining a disciplined index strategy for OLTP patterns pay a double dividend: faster queries and a lower monthly bill.
  • → **Terraform and policy-as-code prevent cost regression**: Point-in-time optimizations erode quickly without guardrails. Encoding approved instance tiers per environment in Terraform modules and enforcing them via Sentinel policies or Open Policy Agent catches oversized provisioning before the first invoice arrives, keeping the savings permanent rather than episodic.
  • → **Automated monitoring closes the feedback loop**: Budget alerts set at 50%, 90%, and 100% of expected monthly spend, combined with a weekly BigQuery cost anomaly report delivered to a shared Slack channel, ensure that cost increases are visible to the team within days rather than discovered at month-end reconciliation. The operational habit of reviewing this report is what sustains the gains made by right-sizing and CUDs over time.
