Chapter 22: Separating Analytics from OLTP: The Financial Case

Organizations that run analytical queries directly against their production OLTP databases routinely overpay for compute by 40–70%. A single poorly-timed BI report hitting an db.r6g.2xlarge RDS instance at peak transaction hours can cost the same as running a dedicated analytics cluster for an entire month — and that assumes the report finishes without triggering a CPU alarm or degrading customer-facing latency. This chapter quantifies the financial damage of mixed workloads, shows you how to measure the exact cost of analytics queries running on OLTP infrastructure, and builds the business case for routing those workloads to purpose-built, cheaper infrastructure. Done right, workload separation typically reduces the primary OLTP instance tier by one to two sizes, cuts storage IOPS costs by 30–50%, and moves analytics to infrastructure that costs 60–80% less per query-hour.

---

The Hidden Cost of Shared Infrastructure

The fundamental problem with running analytics on OLTP instances is a pricing mismatch. OLTP databases are sized for memory and IOPS — you pay premium prices for fast, consistent transaction throughput. Analytics workloads need CPU and sequential scan throughput, which is exactly what columnar stores and MPP engines provide at a fraction of the row-store cost.

Consider a production setup on AWS: an db.r6g.4xlarge RDS PostgreSQL instance running in Multi-AZ. At US East pricing, that is approximately $1.53 per hour for the primary, or $2,196 per month for the pair. Now consider what actually runs on that instance. Performance Insights might reveal that 35% of active session time belongs to reporting queries — dashboard aggregations, month-end rollups, data export jobs. That 35% equates to roughly $769 per month in compute cost attributed purely to analytics.

The same queries on Amazon Redshift Serverless, priced at $0.375 per RPU-hour, would consume perhaps 8–12 RPU-hours for a typical daily analytics batch. Monthly cost: $90–$135. The math alone closes the case before you have written a single line of migration code.

On Azure, the picture is similar. An GP_Gen5_8 Azure SQL Database at around $1,150 per month shared with Power BI DirectQuery connections sees the same compression ratio when workloads move to Azure Synapse Analytics serverless SQL pools, billed at $5 per TB scanned.

The first step is measuring your current baseline with precision.

-- PostgreSQL: Identify analytics queries consuming disproportionate resources
-- Run on RDS PostgreSQL or Aurora PostgreSQL with pg_stat_statements enabled
SELECT
    left(query, 120)                                         AS query_snippet,
    calls,
    round((total_exec_time / 1000)::numeric, 2)             AS total_exec_sec,
    round((mean_exec_time  / 1000)::numeric, 4)             AS mean_exec_sec,
    round((total_exec_time / sum(total_exec_time) OVER ()
           * 100)::numeric, 2)                              AS pct_total_time,
    round(rows / calls::numeric, 0)                         AS avg_rows_returned,
    shared_blks_read + shared_blks_hit                      AS total_blocks_accessed,
    -- High rows returned + long execution = likely analytics, not OLTP
    CASE
        WHEN mean_exec_time > 5000
             AND rows / calls > 10000 THEN 'ANALYTICS_CANDIDATE'
        WHEN mean_exec_time > 1000
             AND rows / calls > 1000  THEN 'REVIEW_NEEDED'
        ELSE 'OLTP'
    END                                                     AS workload_classification
FROM pg_stat_statements
WHERE calls > 10
ORDER BY total_exec_time DESC
LIMIT 40;

This query gives you the classification foundation. Any query returning more than 10,000 rows on average or running longer than 5 seconds mean execution time is an analytics candidate that does not belong on an OLTP instance. Export this result set. It becomes the financial exhibit in your executive presentation.

For SQL Server on Azure SQL or AWS RDS SQL Server, the equivalent pull from sys.dm_exec_query_stats is:

-- SQL Server: Classify workloads by execution profile
SELECT TOP 50
    SUBSTRING(st.text, (qs.statement_start_offset / 2) + 1,
              ((CASE qs.statement_end_offset
                    WHEN -1 THEN DATALENGTH(st.text)
                    ELSE qs.statement_end_offset
               END - qs.statement_start_offset) / 2) + 1)  AS query_text,
    qs.execution_count,
    ROUND(qs.total_elapsed_time / 1e6, 2)                   AS total_elapsed_sec,
    ROUND(qs.total_elapsed_time / qs.execution_count / 1e6,
          4)                                                AS avg_elapsed_sec,
    ROUND(CAST(qs.total_elapsed_time AS FLOAT)
          / SUM(qs.total_elapsed_time) OVER () * 100, 2)   AS pct_total_elapsed,
    qs.total_logical_reads / qs.execution_count             AS avg_logical_reads,
    qs.total_rows / qs.execution_count                      AS avg_rows,
    CASE
        WHEN qs.total_elapsed_time / qs.execution_count > 5000000
             AND qs.total_rows / qs.execution_count > 10000 THEN 'ANALYTICS_CANDIDATE'
        WHEN qs.total_logical_reads / qs.execution_count > 100000 THEN 'HEAVY_SCAN'
        ELSE 'OLTP'
    END                                                     AS workload_type
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
WHERE qs.execution_count > 5
ORDER BY qs.total_elapsed_time DESC;

Quantifying the Dollar Value of Separation

Having identified analytics candidates, the next step is attaching a dollar figure to each. This requires combining query execution data with instance cost data. The Python script below pulls Performance Insights metrics from CloudWatch and maps CPU consumption per query group to hourly instance cost.

#!/usr/bin/env python3
"""
analytics_cost_attribution.py

Pulls RDS Performance Insights data and attributes hourly compute cost
to OLTP vs. analytics query workloads.

Requires: boto3, psycopg2, pandas
Schedule: Daily via EventBridge + Lambda or cron
"""

import boto3
import pandas as pd
from datetime import datetime, timedelta, timezone
from dataclasses import dataclass
from typing import Dict, List

# ── Configuration ────────────────────────────────────────────────────────────
DB_INSTANCE_ID  = "prod-postgres-01"
REGION          = "us-east-1"
INSTANCE_TYPE   = "db.r6g.4xlarge"
MULTI_AZ        = True

# On-demand hourly pricing (update from AWS pricing page quarterly)
HOURLY_RATES: Dict[str, float] = {
    "db.r6g.xlarge":  0.384,
    "db.r6g.2xlarge": 0.768,
    "db.r6g.4xlarge": 1.536,
    "db.r6g.8xlarge": 3.072,
}

LOOKBACK_HOURS = 24

# ── Helpers ──────────────────────────────────────────────────────────────────
@dataclass
class WorkloadCostSummary:
    period_hours: int
    total_instance_cost_usd: float
    analytics_cost_usd: float
    oltp_cost_usd: float
    analytics_pct: float
    projected_monthly_analytics_cost: float


def get_pi_metrics(client, db_id: str, hours: int = 24) -> pd.DataFrame:
    """Fetch DBLoad by sql digest from Performance Insights."""
    end_time   = datetime.now(timezone.utc)
    start_time = end_time - timedelta(hours=hours)

    response = client.get_resource_metrics(
        ServiceType="RDS",
        Identifier=db_id,
        MetricQueries=[
            {
                "Metric": "db.load.avg",
                "GroupBy": {
                    "Group": "db.sql",
                    "Dimensions": ["db.sql.statement"],
                    "Limit": 25,
                },
            }
        ],
        StartTime=start_time,
        EndTime=end_time,
        PeriodInSeconds=3600,
    )

    records = []
    for metric_list in response.get("MetricList", []):
        sql_text = (
            metric_list.get("Key", {})
            .get("Dimensions", {})
            .get("db.sql.statement", "unknown")
        )
        for dp in metric_list.get("DataPoints", []):
            records.append(
                {
                    "timestamp": dp["Timestamp"],
                    "db_load":   dp.get("Value", 0.0),
                    "sql_text":  sql_text[:200],
                }
            )
    return pd.DataFrame(records)


def classify_query(sql: str) -> str:
    """
    Heuristic classification. Replace with pg_stat_statements
    integration for production use.
    """
    sql_upper = sql.upper()
    analytics_signals = [
        "GROUP BY", "HAVING", "ROLLUP", "CUBE",
        "WINDOW", "PARTITION BY", "PERCENTILE",
        "EXTRACT(", "DATE_TRUNC",
    ]
    if any(sig in sql_upper for sig in analytics_signals):
        return "ANALYTICS"
    return "OLTP"


def compute_cost_attribution(df: pd.DataFrame,
                              instance_type: str,
                              multi_az: bool,
                              lookback_hours: int) -> WorkloadCostSummary:
    base_rate   = HOURLY_RATES.get(instance_type, 1.536)
    effective_rate = base_rate * (2 if multi_az else 1)
    total_cost  = effective_rate * lookback_hours

    df["workload"] = df["sql_text"].apply(classify_query)

    total_load    = df["db_load"].sum() or 1.0
    analytics_load = df.loc[df["workload"] == "ANALYTICS", "db_load"].sum()
    analytics_pct  = (analytics_load / total_load) * 100

    analytics_cost = total_cost * (analytics_pct / 100)
    oltp_cost      = total_cost - analytics_cost

    # Project to 30 days
    hourly_analytics_cost   = analytics_cost / lookback_hours
    monthly_analytics_cost  = hourly_analytics_cost * 730

    return WorkloadCostSummary(
        period_hours=lookback_hours,
        total_instance_cost_usd=round(total_cost, 2),
        analytics_cost_usd=round(analytics_cost, 2),
        oltp_cost_usd=round(oltp_cost, 2),
        analytics_pct=round(analytics_pct, 1),
        projected_monthly_analytics_cost=round(monthly_analytics_cost, 2),
    )


def main():
    pi_client = boto3.client("pi",  region_name=REGION)

    print(f"Fetching Performance Insights for {DB_INSTANCE_ID} "
          f"over last {LOOKBACK_HOURS}h …\n")

    df = get_pi_metrics(pi_client, DB_INSTANCE_ID, LOOKBACK_HOURS)

    if df.empty:
        print("No PI data returned. Verify PI is enabled and the instance ID is correct.")
        return

    summary = compute_cost_attribution(
        df, INSTANCE_TYPE, MULTI_AZ, LOOKBACK_HOURS
    )

    print("=" * 60)
    print(f"  Instance:                 {DB_INSTANCE_ID} ({INSTANCE_TYPE})")
    print(f"  Analysis window:          {LOOKBACK_HOURS} hours")
    print(f"  Total compute cost:       ${summary.total_instance_cost_usd:>8.2f}")
    print(f"  OLTP cost:                ${summary.oltp_cost_usd:>8.2f}")
    print(f"  Analytics cost:           ${summary.analytics_cost_usd:>8.2f}  "
          f"({summary.analytics_pct}%)")
    print(f"  Projected monthly waste:  ${summary.projected_monthly_analytics_cost:>8.2f}")
    print("=" * 60)

    if summary.analytics_pct > 20:
        print("\n⚠  RECOMMENDATION: Analytics load exceeds 20% of total DB load.")
        print("   Consider offloading to Redshift Serverless, Athena, or a")
        print("   read replica sized for analytics workloads.")


if __name__ == "__main__":
    main()

Run this daily via a scheduled Lambda or cron job. When projected_monthly_analytics_cost exceeds $500 consistently, you have your financial justification. When it exceeds $2,000, the conversation with your CTO writes itself.

Choosing the Right Analytics Target Infrastructure

Workload separation is not a single architecture. The correct target depends on query patterns, data freshness requirements, and the volume of data scanned. Getting this wrong means you trade one cost problem for another.

Scenario 1 — Latency-tolerant batch analytics, large data volumes: Amazon Redshift Serverless (AWS), Azure Synapse Analytics serverless SQL pools (Azure), or BigQuery (GCP). These are columnar MPP engines billed per query or per RPU-hour. A query scanning 500 GB of Parquet in BigQuery costs $2.50 flat. The same query on an r6g.4xlarge RDS instance spending 45 minutes of CPU time costs roughly $1.15 in compute plus weeks of DBA time managing contention. Over a month of daily runs, BigQuery at $2.50 per day is $75; the RDS share is $840.

Scenario 2 — Near-real-time dashboards against production data, sub-minute lag tolerance: Aurora read replicas or RDS read replicas. The replica runs on a smaller instance — you do not need the same IOPS tier as primary. An Aurora PostgreSQL read replica on db.r6g.xlarge at $0.384/hour costs $280/month versus the db.r6g.4xlarge primary at $2,196/month. Dashboard queries go to the replica; primary stays clean for writes.

Scenario 3 — Ad-hoc analyst queries against recent data already exported: Amazon Athena over S3. Export a daily snapshot of your OLTP tables to S3 in Parquet format. Athena charges $5 per TB scanned, and column pruning plus Parquet compression typically means analysts scan 90–95% less data than the raw row size. A 100 GB Parquet file holding 1 TB of logical data costs $0.50 per full scan instead of $5.00.

The following script sets up a daily export from RDS PostgreSQL to S3 using pg_dump via AWS CLI, enabling Athena queries without touching production:

#!/usr/bin/env bash
# daily_analytics_export.sh
# Exports selected analytical tables from RDS to S3 as CSV,
# convertible to Parquet via AWS Glue or Athena CTAS.
# Schedule: cron 0 2 * * * (02:00 UTC daily)

set -euo pipefail

DB_HOST="prod-postgres-01.cluster-xyz.us-east-1.rds.amazonaws.com"
DB_NAME="appdb"
DB_USER="readonly_analytics"
S3_BUCKET="s3://my-company-analytics-lake"
DATE_PREFIX=$(date +%Y/%m/%d)
PGPASSWORD="${ANALYTICS_DB_PASSWORD}"   # sourced from SSM Parameter Store at runtime

export PGPASSWORD

TABLES=(
  "orders"
  "order_items"
  "customers"
  "products"
  "events"
)

echo "[$(date -u +%FT%T)] Starting analytics export …"

for TABLE in "${TABLES[@]}"; do
  LOCAL_FILE="/tmp/${TABLE}_$(date +%Y%m%d).csv"

  echo "  Exporting ${TABLE} …"
  psql \
    --host="${DB_HOST}" \
    --username="${DB_USER}" \
    --dbname="${DB_NAME}" \
    --no-password \
    --command="\COPY (SELECT * FROM ${TABLE} WHERE updated_at >= NOW() - INTERVAL '1 day')
               TO STDOUT WITH CSV HEADER" \
    > "${LOCAL_FILE}"

  # Upload to date-partitioned S3 prefix
  aws s3 cp "${LOCAL_FILE}" \
    "${S3_BUCKET}/raw/${TABLE}/${DATE_PREFIX}/${TABLE}.csv" \
    --storage-class INTELLIGENT_TIERING \
    --sse aws:kms

  rm -f "${LOCAL_FILE}"
  echo "  ✓ ${TABLE} uploaded."
done

# Optionally trigger Glue crawler to update Athena catalog
aws glue start-crawler --name "analytics-lake-crawler" || true

echo "[$(date -u +%FT%T)] Export complete."
unset PGPASSWORD

The --storage-class INTELLIGENT_TIERING flag is intentional. Analytics data accessed heavily the day after export and rarely thereafter fits the Intelligent-Tiering pattern, which automatically moves objects to lower-cost tiers after 30 and 90 days of inactivity. For a 500 GB dataset, this can reduce S3 storage cost from $11.50/month (Standard) to $6.00/month within two months.

Right-Sizing OLTP After Workload Removal

The separation is only half the saving. The other half comes from downsizing the OLTP instance once analytics load is removed. This is where DBAs often leave money on the table — they successfully move the analytics workload but never revisit the instance type because "production changes are scary."

Use AWS Compute Optimizer and RDS recommendations to make the case with data rather than intuition.

#!/usr/bin/env bash
# get_rds_rightsizing_recommendations.sh
# Pulls Compute Optimizer recommendations for all RDS instances in account.
# Prerequisites: AWS CLI configured, Compute Optimizer enabled.

set -euo pipefail

REGION="us-east-1"
OUTPUT_FILE="rds_rightsizing_$(date +%Y%m%d).json"

echo "Fetching Compute Optimizer recommendations for RDS …"

aws compute-optimizer get-rds-database-recommendations \
  --region "${REGION}" \
  --filters name=Finding,values=Overprovisioned \
  --query 'rdsDBRecommendations[*].{
      Instance:resourceArn,
      CurrentType:currentDBInstanceClass,
      RecommendedType:recommendationOptions[0].dbInstanceClass,
      CurrentMonthlyPrice:currentMonthlyPrice.value,
      RecommendedMonthlyPrice:recommendationOptions[0].monthlyPrice.value,
      SavingsMonthly:currentMonthlyPrice.value
          - recommendationOptions[0].monthlyPrice.value,
      CPUUtilizationP99:utilizationMetrics[?name==`CPU`].value | [0],
      MemoryUtilizationP99:utilizationMetrics[?name==`Memory`].value | [0]
  }' \
  --output json \
  | tee "${OUTPUT_FILE}"

# Summarize total potential savings
echo ""
echo "Summary of potential monthly savings:"
python3 - <<'PYEOF'
import json, sys

with open("${OUTPUT_FILE}") as f:
    recs = json.load(f)

if not recs:
    print("  No overprovisioned instances found — or Compute Optimizer needs more data.")
    sys.exit(0)

total_current     = sum(r.get("CurrentMonthlyPrice",     0) or 0 for r in recs)
total_recommended = sum(r.get("RecommendedMonthlyPrice", 0) or 0 for r in recs)
total_savings     = total_current - total_recommended

print(f"  Instances reviewed:       {len(recs)}")
print(f"  Current monthly spend:    \${total_current:>10,.2f}")
print(f"  Optimized monthly spend:  \${total_recommended:>10,.2f}")
print(f"  Potential monthly saving: \${total_savings:>10,.2f}")
print(f"  Annualized saving:        \${total_savings * 12:>10,.2f}")
PYEOF

In practice, after removing analytics load from an db.r6g.4xlarge, Compute Optimizer frequently recommends dropping to db.r6g.2xlarge. At US East Multi-AZ pricing, that is a reduction from $2,196/month to $1,098/month — $1,098/month saved on the OLTP instance alone. Combined with the analytics migration to a cheaper target, total monthly savings often land between $1,200 and $1,800 for a single database cluster.

The instance downsize also has a compounding effect on reserved instance pricing. A 1-year no-upfront Reserved Instance for db.r6g.2xlarge costs approximately $686/month versus $1,098 on-demand — a further 37% reduction. When presenting the business case, the three-layer stack of savings (analytics offload + instance downsize + RI purchase) often produces a number that immediately gets CTO approval.
