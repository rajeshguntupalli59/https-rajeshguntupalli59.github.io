Chapter 38: GDPR and AI: Right to Be Forgotten with Embeddings

When a user submits a GDPR deletion request — "erase everything about me" — your PostgreSQL DELETE statements are the easy part. The hard part is the embedding. That user's words, preferences, and personal details may have been vectorized and stored in pgvector tables, woven into RAG indices, cached in Redis, queued in Celery jobs, and potentially absorbed into model fine-tuning datasets. A row deletion satisfies the letter of the law; actually removing personal information from an AI system's memory requires a coordinated strategy across the entire stack.

This chapter covers how to design PostgreSQL-backed AI systems that can honor GDPR's Right to Be Forgotten without destroying your AI features. You will build deletion pipelines that scrub user data from embedding tables, invalidate caches, regenerate affected indices, audit every step, and prove compliance — all while keeping the rest of the system operational.

---

38.1 What "Forgotten" Actually Means in an AI System

GDPR Article 17 requires erasure of personal data. In a traditional application this means deleting database rows. In an AI-native application, personal data can exist in at least six places simultaneously:

Structured rows — user profiles, conversation history, preferences, metadata.

Embeddings — vector representations of user-authored content. The embedding itself is a mathematical transformation of text that contained personal information. Courts and regulators have not fully settled whether embeddings constitute personal data, but the conservative and defensible position is that embeddings derived from personal content must also be deleted.

RAG document chunks — if a user uploaded documents or their conversation turns were indexed for retrieval, those chunks live in your document store alongside their vectors.

Caches — Redis may hold pre-computed embeddings or LLM responses that referenced the user.

Async job queues — Celery jobs may still be processing documents that contain user data.

Audit and log tables — these often need to be retained for compliance, but must be scrubbed of PII while preserving the audit trail.

The architecture you need is one where every piece of user-derived AI content is traceable back to a user_id. PostgreSQL's relational model is your ally here. A pure vector database with no relational structure makes this nearly impossible. With PostgreSQL and pgvector, every embedding row can carry a user_id foreign key, and a single deletion event can cascade correctly through the schema.

Start with the foundational schema that makes GDPR compliance tractable:

-- Core user registry with deletion tracking
CREATE TABLE users (
    user_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           TEXT NOT NULL UNIQUE,
    display_name    TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deletion_requested_at TIMESTAMPTZ,
    deletion_completed_at TIMESTAMPTZ,
    deletion_job_id UUID,
    is_active       BOOLEAN NOT NULL DEFAULT TRUE
);

-- Every piece of user-authored content is tracked here
-- This is the master registry for AI-derived artifacts
CREATE TABLE user_content (
    content_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
    content_type    TEXT NOT NULL, -- 'message', 'document', 'profile_bio', 'preference'
    source_text     TEXT,          -- original text, nulled out after deletion
    content_hash    TEXT,          -- SHA-256 for deduplication, kept after deletion
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

CREATE INDEX idx_user_content_user_id ON user_content(user_id);
CREATE INDEX idx_user_content_type    ON user_content(content_type);
CREATE INDEX idx_user_content_deleted ON user_content(deleted_at) WHERE deleted_at IS NULL;

-- Embeddings table — every vector is owned by a user
CREATE TABLE content_embeddings (
    embedding_id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    content_id      UUID NOT NULL REFERENCES user_content(content_id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
    model_name      TEXT NOT NULL,          -- 'text-embedding-3-small', 'embed-english-v3.0'
    embedding_dim   INTEGER NOT NULL,
    embedding        vector(1536),          -- pgvector column
    chunk_index     INTEGER NOT NULL DEFAULT 0,
    chunk_text      TEXT,                   -- the actual chunk text, nulled on deletion
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

CREATE INDEX idx_embeddings_user_id    ON content_embeddings(user_id);
CREATE INDEX idx_embeddings_content_id ON content_embeddings(content_id);
CREATE INDEX idx_embeddings_deleted    ON content_embeddings(deleted_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_embeddings_model      ON content_embeddings(model_name);

-- HNSW index only on active embeddings
CREATE INDEX idx_embeddings_vector ON content_embeddings 
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE deleted_at IS NULL;

-- Conversation history — must be fully scrubbed
CREATE TABLE conversations (
    conversation_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,
    title           TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

CREATE TABLE conversation_turns (
    turn_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(conversation_id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system')),
    content         TEXT,          -- nulled after deletion
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,
    token_count     INTEGER,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

CREATE INDEX idx_turns_user_id ON conversation_turns(user_id);
CREATE INDEX idx_turns_conv_id ON conversation_turns(conversation_id);

-- Deletion audit log — this is kept forever for compliance
-- but contains NO personal data
CREATE TABLE deletion_audit_log (
    audit_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    deletion_job_id UUID NOT NULL,
    user_id_hash    TEXT NOT NULL,  -- SHA-256 of user_id, not the user_id itself
    event_type      TEXT NOT NULL,  -- 'deletion_requested', 'step_completed', 'deletion_verified'
    step_name       TEXT,
    records_affected INTEGER,
    executed_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    executor        TEXT NOT NULL,  -- 'system', 'celery_worker', 'manual_dba'
    notes           TEXT,
    checksum        TEXT            -- SHA-256 of row content for tamper detection
);

-- Row-level security so users can only see their own data
ALTER TABLE user_content        ENABLE ROW LEVEL SECURITY;
ALTER TABLE content_embeddings  ENABLE ROW LEVEL SECURITY;
ALTER TABLE conversations       ENABLE ROW LEVEL SECURITY;
ALTER TABLE conversation_turns  ENABLE ROW LEVEL SECURITY;

    USING (user_id = current_setting('app.current_user_id', TRUE)::UUID);

CREATE POLICY turns_isolation ON conversation_turns
    USING (user_id = current_setting('app.current_user_id', TRUE)::UUID);

38.2 The Deletion Job Pipeline

A GDPR deletion is not an instantaneous operation in an AI system. It is a workflow. The user submits a request; the system has 30 days to comply under GDPR (though best practice is faster). You need a tracked, idempotent, audited pipeline that handles partial failures gracefully.

The pipeline stages are: request intake → scope identification → content deletion → embedding deletion → cache invalidation → queue drain → verification → notification.

graph TD
    A[initiate_deletion_request] -->|pg_notify: deletion_requests| B[Celery: process_deletion_job]
    B --> C[scrub_conversation_turns]
    C --> D[scrub_content_source_text]
    D --> E[delete_embeddings, hard delete]
    E --> F[scrub_user_profile]
    F --> G[Invalidate Redis caches]
    G --> H[Revoke pending Celery ingestion jobs]
    H --> I[verify_deletion]
    I -->|all checks pass| J[notify_user_deletion_complete]
    I -->|any check fails| K[alert_dpo_verification_failure]

*Every step writes to deletion_audit_log with only a hashed user_id — the audit trail itself never becomes personal data subject to its own erasure request.*

PostgreSQL drives the coordination via a deletion jobs table and pg_notify for real-time handoff to async workers:

-- Deletion job coordination table
CREATE TABLE deletion_jobs (
    job_id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(user_id),
    requested_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deadline_at     TIMESTAMPTZ NOT NULL DEFAULT (NOW() + INTERVAL '30 days'),
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending', 'running', 'verifying', 'completed', 'failed')),
    current_step    TEXT,
    steps_completed JSONB NOT NULL DEFAULT '[]',
    error_details   TEXT,
    started_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    verified_at     TIMESTAMPTZ,
    notified_at     TIMESTAMPTZ,
    retry_count     INTEGER NOT NULL DEFAULT 0,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

CREATE INDEX idx_deletion_jobs_user    ON deletion_jobs(user_id);
CREATE INDEX idx_deletion_jobs_status  ON deletion_jobs(status) WHERE status != 'completed';
CREATE INDEX idx_deletion_jobs_deadline ON deletion_jobs(deadline_at) WHERE status != 'completed';

-- Function to initiate a deletion and fire notification
CREATE OR REPLACE FUNCTION initiate_deletion_request(p_user_id UUID)
RETURNS UUID
LANGUAGE plpgsql
AS $$
DECLARE
    v_job_id UUID;
    v_user_hash TEXT;
BEGIN
    -- Mark user as pending deletion (stops new data creation)
    UPDATE users
    SET deletion_requested_at = NOW(),
        is_active = FALSE
    WHERE user_id = p_user_id
      AND deletion_requested_at IS NULL;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'User % not found or deletion already in progress', p_user_id;
    END IF;

    -- Create deletion job
    INSERT INTO deletion_jobs (user_id)
    VALUES (p_user_id)
    RETURNING job_id INTO v_job_id;

    -- Link job to user
    UPDATE users SET deletion_job_id = v_job_id WHERE user_id = p_user_id;

    -- Write audit entry with hashed user_id (no PII in audit log)
    v_user_hash := encode(digest(p_user_id::TEXT, 'sha256'), 'hex');

    INSERT INTO deletion_audit_log (
        deletion_job_id, user_id_hash, event_type, step_name,
        executor, notes
    ) VALUES (
        v_job_id, v_user_hash, 'deletion_requested', 'intake',
        'system', 'Deletion job created and user marked inactive'
    );

    -- Notify async workers via pg_notify
    PERFORM pg_notify(
        'deletion_requests',
        json_build_object(
            'job_id', v_job_id,
            'user_id', p_user_id,
            'requested_at', NOW()
        )::TEXT
    );

    RETURN v_job_id;
END;
$$;

-- Function to get the full scope of what must be deleted
CREATE OR REPLACE FUNCTION get_deletion_scope(p_user_id UUID)
RETURNS TABLE (
    artifact_type   TEXT,
    count           BIGINT,
    oldest_record   TIMESTAMPTZ,
    newest_record   TIMESTAMPTZ
)
LANGUAGE sql
AS $$
    SELECT 'user_content'::TEXT, COUNT(*), MIN(created_at), MAX(created_at)
    FROM user_content WHERE user_id = p_user_id AND deleted_at IS NULL
    UNION ALL
    SELECT 'content_embeddings', COUNT(*), MIN(created_at), MAX(created_at)
    FROM content_embeddings WHERE user_id = p_user_id AND deleted_at IS NULL
    UNION ALL
    SELECT 'conversation_turns', COUNT(*), MIN(created_at), MAX(created_at)
    FROM conversation_turns WHERE user_id = p_user_id AND deleted_at IS NULL
    UNION ALL
    SELECT 'conversations', COUNT(*), MIN(created_at), MAX(created_at)
    FROM conversations WHERE user_id = p_user_id AND deleted_at IS NULL;
$$;

-- Atomic step executor with audit logging
CREATE OR REPLACE FUNCTION execute_deletion_step(
    p_job_id    UUID,
    p_step_name TEXT,
    p_user_id   UUID
)
RETURNS INTEGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_affected   INTEGER := 0;
    v_user_hash  TEXT;
BEGIN
    v_user_hash := encode(digest(p_user_id::TEXT, 'sha256'), 'hex');

    UPDATE deletion_jobs
    SET current_step = p_step_name,
        status = 'running',
        started_at = COALESCE(started_at, NOW())
    WHERE job_id = p_job_id;

    IF p_step_name = 'scrub_conversation_turns' THEN
        UPDATE conversation_turns
        SET content = NULL,
            deleted_at = NOW(),
            metadata = jsonb_set(metadata, '{gdpr_deleted}', 'true')
        WHERE user_id = p_user_id AND deleted_at IS NULL;
        GET DIAGNOSTICS v_affected = ROW_COUNT;

    ELSIF p_step_name = 'scrub_content_source_text' THEN
        UPDATE user_content
        SET source_text = NULL,
            deleted_at = NOW(),
            metadata = jsonb_set(metadata, '{gdpr_deleted}', 'true')
        WHERE user_id = p_user_id AND deleted_at IS NULL;
        GET DIAGNOSTICS v_affected = ROW_COUNT;

    ELSIF p_step_name = 'delete_embeddings' THEN
        -- Hard delete embeddings — nulling a vector field is not sufficient
        -- because the vector IS the personal data
        DELETE FROM content_embeddings
        WHERE user_id = p_user_id;
        GET DIAGNOSTICS v_affected = ROW_COUNT;

    ELSIF p_step_name = 'scrub_user_profile' THEN
        UPDATE users
        SET email = 'deleted-' || encode(digest(email, 'sha256'), 'hex') || '@deleted.invalid',
            display_name = NULL,
            deletion_completed_at = NOW()
        WHERE user_id = p_user_id;
        GET DIAGNOSTICS v_affected = ROW_COUNT;
    END IF;

    -- Record completed step on the job
    UPDATE deletion_jobs
    SET steps_completed = steps_completed || jsonb_build_object(
        'step', p_step_name,
        'completed_at', NOW(),
        'records_affected', v_affected
    )
    WHERE job_id = p_job_id;

    -- Audit log entry
    INSERT INTO deletion_audit_log (
        deletion_job_id, user_id_hash, event_type,
        step_name, records_affected, executor
    ) VALUES (
        p_job_id, v_user_hash, 'step_completed',
        p_step_name, v_affected, 'celery_worker'
    );

    RETURN v_affected;
END;
$$;

38.3 The Python Deletion Worker

The Celery worker listens to pg_notify events, orchestrates each deletion step, handles cache invalidation in Redis, and re-indexes any shared knowledge base content that happened to co-mingle with user data.

# deletion_worker.py
# Celery worker for GDPR deletion pipeline

import asyncio
import hashlib
import json
import logging
from datetime import datetime, timezone
from typing import Any
from uuid import UUID

import asyncpg
import redis  # sync client used inside Celery tasks below
import redis.asyncio as aioredis  # used only by the pg_notify listener's async context
from celery import Celery
from openai import OpenAI
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine

logger = logging.getLogger(__name__)

# ── Celery configuration ──────────────────────────────────────────────────────

celery_app = Celery(
    "deletion_pipeline",
    broker="redis://localhost:6379/1",
    backend="redis://localhost:6379/2",
)

celery_app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    task_acks_late=True,           # don't ack until task completes
    task_reject_on_worker_lost=True,
    worker_prefetch_multiplier=1,  # one deletion job at a time per worker
)

# ── pg_notify listener (runs alongside Celery) ────────────────────────────────

async def listen_for_deletion_requests(dsn: str):
    """
    Listen on the 'deletion_requests' channel and dispatch Celery tasks.
    Run this in a separate process or as an asyncio task.
    """
    conn = await asyncpg.connect(dsn)
    await conn.add_listener("deletion_requests", handle_deletion_notification)
    logger.info("Listening for GDPR deletion requests on pg_notify channel")
    try:
        while True:
            await asyncio.sleep(1)
    finally:
        await conn.remove_listener("deletion_requests", handle_deletion_notification)
        await conn.close()


def handle_deletion_notification(connection, pid, channel, payload):
    data = json.loads(payload)
    logger.info(f"Received deletion request for job {data['job_id']}")
    # Dispatch to Celery — fully async handoff
    process_deletion_job.apply_async(
        args=[data["job_id"], data["user_id"]],
        countdown=5,  # small delay to let the DB transaction settle
        queue="deletions",
    )


# ── Core deletion task ────────────────────────────────────────────────────────

@celery_app.task(
    bind=True,
    name="deletion_pipeline.process_deletion_job",
    max_retries=5,
    default_retry_delay=60,
    queue="deletions",
)
def process_deletion_job(self, job_id: str, user_id: str):
    """
    Orchestrates the full GDPR deletion pipeline for one user.
    Each step is idempotent — safe to retry on failure.
    """
    import psycopg2
    from psycopg2.extras import RealDictCursor

    db_dsn = "postgresql://app:password@localhost:5432/aiapp"
    redis_client = redis.Redis(host="localhost", port=6379, db=0)

    # Ordered deletion steps
    steps = [
        "scrub_conversation_turns",
        "scrub_content_source_text",
        "delete_embeddings",
        "scrub_user_profile",
    ]

    try:
        with psycopg2.connect(db_dsn) as conn:
            conn.autocommit = False
            with conn.cursor(cursor_factory=RealDictCursor) as cur:

                # Check job status — skip completed steps (idempotency)
                cur.execute(
                    "SELECT steps_completed, status FROM deletion_jobs WHERE job_id = %s",
                    (job_id,)
                )
                job = cur.fetchone()
                if not job:
                    raise ValueError(f"Job {job_id} not found")
                if job["status"] == "completed":
                    logger.info(f"Job {job_id} already completed, skipping")
                    return

                completed_steps = {
                    s["step"] for s in (job["steps_completed"] or [])
                }

                # Execute each pending step
                for step in steps:
                    if step in completed_steps:
                        logger.info(f"Step {step} already done, skipping")
                        continue

                    logger.info(f"Executing step: {step} for user {user_id}")
                    cur.execute(
                        "SELECT execute_deletion_step(%s, %s, %s)",
                        (job_id, step, user_id)
                    )
                    affected = cur.fetchone()["execute_deletion_step"]
                    conn.commit()
                    logger.info(f"Step {step} completed: {affected} records affected")

                # Invalidate all Redis caches for this user
                _invalidate_redis_cache(redis_client, user_id)

                # Cancel any pending Celery ingestion jobs for this user
                _revoke_pending_ingestion_jobs(user_id)

                # Mark job as complete
                cur.execute(
                    """
                    UPDATE deletion_jobs
                    SET status = 'verifying',
                        current_step = 'verification'
                    WHERE job_id = %s
                    """,
                    (job_id,)
                )
                conn.commit()

        # Trigger verification as a separate task
        verify_deletion.apply_async(
            args=[job_id, user_id],
            queue="deletions",
            countdown=10,
        )

    except Exception as exc:
        logger.exception(f"Deletion job {job_id} failed: {exc}")
        with psycopg2.connect(db_dsn) as conn:
            with conn.cursor() as cur:
                cur.execute(
                    """
                    UPDATE deletion_jobs
                    SET status = 'failed',
                        error_details = %s,
                        retry_count = retry_count + 1
                    WHERE job_id = %s
                    """,
                    (str(exc), job_id)
                )
                conn.commit()
        raise self.retry(exc=exc, countdown=60 * (self.request.retries + 1))


def _invalidate_redis_cache(redis_client: redis.Redis, user_id: str):
    """
    Delete all Redis keys associated with this user.
    Key patterns used by the application:
      embedding:{user_id}:*     — cached embeddings
      session:{user_id}:*       — conversation sessions
      rag_ctx:{user_id}:*       — cached RAG context windows
      user_profile:{user_id}    — cached user profile
    """
    patterns = [
        f"embedding:{user_id}:*",
        f"session:{user_id}:*",
        f"rag_ctx:{user_id}:*",
        f"user_profile:{user_id}",
        f"conv_summary:{user_id}:*",
    ]
    total_deleted = 0
    for pattern in patterns:
        keys = redis_client.keys(pattern)
        if keys:
            total_deleted += redis_client.delete(*keys)

    logger.info(f"Invalidated {total_deleted} Redis keys for user {user_id}")


def _revoke_pending_ingestion_jobs(user_id: str):
    """
    Revoke any Celery tasks that are still pending for this user.
    Uses Celery's inspect API to find tasks by routing metadata.
    """
    from celery.app.control import Inspect
    inspector = celery_app.control.inspect()
    reserved = inspector.reserved() or {}

    for worker, tasks in reserved.items():
        for task in tasks:
            task_args = task.get("args", [])
            task_kwargs = task.get("kwargs", {})
            # Check if this task belongs to the user being deleted
            if user_id in str(task_args) or user_id in str(task_kwargs):
                celery_app.control.revoke(task["id"], terminate=True)
                logger.info(f"Revoked task {task['id']} for user {user_id}")


# ── Verification task ─────────────────────────────────────────────────────────

@celery_app.task(
    name="deletion_pipeline.verify_deletion",
    queue="deletions",
)
def verify_deletion(job_id: str, user_id: str):
    """
    Verifies that all personal data has been removed. Produces a signed
    audit record that can be presented as proof of compliance.
    """
    import psycopg2
    from psycopg2.extras import RealDictCursor

    db_dsn = "postgresql://app:password@localhost:5432/aiapp"
    user_id_hash = hashlib.sha256(user_id.encode()).hexdigest()

    checks = {}

    with psycopg2.connect(db_dsn) as conn:
        with conn.cursor(cursor_factory=RealDictCursor) as cur:

            # Verify no active embeddings remain
            cur.execute(
                "SELECT COUNT(*) AS cnt FROM content_embeddings WHERE user_id = %s",
                (user_id,)
            )
            checks["embeddings_remaining"] = cur.fetchone()["cnt"]

            # Verify no unredacted conversation turns remain
            cur.execute(
                """
                SELECT COUNT(*) AS cnt FROM conversation_turns
                WHERE user_id = %s AND content IS NOT NULL
                """,
                (user_id,)
            )
            checks["unredacted_turns_remaining"] = cur.fetchone()["cnt"]

            # Verify no unredacted source text remains
            cur.execute(
                """
                SELECT COUNT(*) AS cnt FROM user_content
                WHERE user_id = %s AND source_text IS NOT NULL
                """,
                (user_id,)
            )
            checks["unredacted_source_text_remaining"] = cur.fetchone()["cnt"]

            # Verify user email has been anonymized
            cur.execute(
                "SELECT email FROM users WHERE user_id = %s",
                (user_id,)
            )
            row = cur.fetchone()
            checks["email_anonymized"] = (
                row is not None and row["email"].endswith("@deleted.invalid")
            )

            all_clear = (
                checks["embeddings_remaining"] == 0
                and checks["unredacted_turns_remaining"] == 0
                and checks["unredacted_source_text_remaining"] == 0
                and checks["email_anonymized"]
            )

            if all_clear:
                # Build a tamper-evident checksum of the verification record
                verification_payload = json.dumps(
                    {
                        "job_id": job_id,
                        "user_id_hash": user_id_hash,
                        "checks": checks,
                        "verified_at": datetime.now(timezone.utc).isoformat(),
                    },
                    sort_keys=True,
                )
                checksum = hashlib.sha256(verification_payload.encode()).hexdigest()

                cur.execute(
                    """
                    INSERT INTO deletion_audit_log (
                        deletion_job_id, user_id_hash, event_type,
                        step_name, executor, notes, checksum
                    ) VALUES (%s, %s, 'deletion_verified', 'verification',
                              'celery_worker', %s, %s)
                    """,
                    (job_id, user_id_hash, json.dumps(checks), checksum)
                )

                cur.execute(
                    """
                    UPDATE deletion_jobs
                    SET status = 'completed',
                        current_step = 'done',
                        verified_at = NOW(),
                        completed_at = NOW()
                    WHERE job_id = %s
                    """,
                    (job_id,)
                )
                conn.commit()
                logger.info(f"Deletion job {job_id} verified and completed")

                # Send confirmation notification
                notify_user_deletion_complete.apply_async(
                    args=[job_id, user_id_hash],
                    queue="notifications",
                )

            else:
                logger.error(
                    f"Verification FAILED for job {job_id}: {checks}"
                )
                cur.execute(
                    """
                    UPDATE deletion_jobs
                    SET status = 'failed',
                        error_details = %s
                    WHERE job_id = %s
                    """,
                    (json.dumps(checks), job_id)
                )
                conn.commit()
                # Alert the data protection officer
                alert_dpo_verification_failure.apply_async(
                    args=[job_id, user_id_hash, checks],
                    queue="alerts",
                )

38.4 Handling the HNSW Index After Deletion

Deleting rows from content_embeddings creates a subtle problem with HNSW indices. HNSW is an approximate nearest-neighbor index that builds a graph structure at index creation time. When you delete rows, PostgreSQL marks the heap tuples as dead but the HNSW index nodes may still be traversed during searches before VACUUM cleans them. This can cause ghost results — similarity searches that return embedding IDs for rows that no longer exist in the heap. Your application code must handle empty-join results, but more importantly you need a deliberate vacuuming strategy.

The partial index defined in section 38.1 (WHERE deleted_at IS NULL) helps with this pattern only when you soft-delete rows. When you hard-delete embeddings (which is the correct approach for GDPR — a nulled-out vector field still occupies space in the index), you need VACUUM to reclaim those index entries.

-- Monitor dead tuple accumulation after bulk deletions
CREATE OR REPLACE VIEW embedding_index_health AS
SELECT
    schemaname,
    relname                         AS table_name,
    n_live_tup                      AS live_rows,
    n_dead_tup                      AS dead_rows,
    ROUND(
        100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2
    )                               AS dead_pct,
    last_vacuum,
    last_autovacuum,
    last_analyze
FROM pg_stat_user_tables
WHERE relname = 'content_embeddings';

-- After a large deletion job completes, trigger an immediate vacuum
-- This is called from the deletion worker post-verification
CREATE OR REPLACE FUNCTION post_deletion_maintenance(p_user_id UUID)
RETURNS VOID
LANGUAGE plpgsql
AS $$
BEGIN
    -- Aggressive autovacuum settings for this table temporarily
    -- These are reset by the next ANALYZE
    EXECUTE 'VACUUM ANALYZE content_embeddings';
    EXECUTE 'VACUUM ANALYZE user_content';
    EXECUTE 'VACUUM ANALYZE conversation_turns';

    -- Log maintenance completion
    INSERT INTO deletion_audit_log (
        deletion_job_id,
        user_id_hash,
        event_type,
        step_name,
        executor,
        notes
    )
    SELECT
        dj.job_id,
        encode(digest(p_user_id::TEXT, 'sha256'), 'hex'),
        'step_completed',
        'post_deletion_vacuum',
        'system',
        'VACUUM ANALYZE completed on embedding tables'
    FROM deletion_jobs dj
    WHERE dj.user_id = p_user_id
      AND dj.status IN ('completed', 'verifying')
    ORDER BY dj.requested_at DESC
    LIMIT 1;
END;
$$;

For high-volume systems where deletions happen continuously, configure autovacuum more aggressively on the embeddings table:

-- Make autovacuum more responsive on the embeddings table
-- Dead tuples from deletions trigger vacuum sooner
ALTER TABLE content_embeddings SET (
    autovacuum_vacuum_scale_factor     = 0.01,  -- vacuum after 1% dead tuples
    autovacuum_analyze_scale_factor    = 0.01,
    autovacuum_vacuum_cost_delay       = 2,     -- milliseconds, less I/O throttling
    autovacuum_vacuum_threshold        = 100    -- minimum 100 dead tuples before vacuum
);

If your deployment receives bursts of deletion requests — as happens when users exercise GDPR rights following a data breach notification — a single shared HNSW index across all users will suffer significant fragmentation. The architectural mitigation is per-user or per-tenant index partitioning. Rather than one monolithic content_embeddings table, partition by user_id hash range. Deletion of a partition is instantaneous and leaves no dead tuples:

-- Partitioned embeddings table — each partition covers a hash range of user_ids
-- This enables DROP PARTITION for complete tenant/user erasure

CREATE TABLE content_embeddings_partitioned (
    embedding_id    UUID NOT NULL DEFAULT gen_random_uuid(),
    content_id      UUID NOT NULL,
    user_id         UUID NOT NULL,
    model_name      TEXT NOT NULL,
    embedding_dim   INTEGER NOT NULL,
    embedding       vector(1536),
    chunk_index     INTEGER NOT NULL DEFAULT 0,
    chunk_text      TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at      TIMESTAMPTZ,
    metadata        JSONB NOT NULL DEFAULT '{}'
) PARTITION BY HASH (user_id);

-- Create 16 partitions — tune partition count to your user volume
DO $$
BEGIN
    FOR i IN 0..15 LOOP
        EXECUTE format(
            'CREATE TABLE content_embeddings_p%s
             PARTITION OF content_embeddings_partitioned
             FOR VALUES WITH (MODULUS 16, REMAINDER %s)',
            i, i
        );
        -- Each partition gets its own HNSW index
        EXECUTE format(
            'CREATE INDEX idx_emb_p%s_vector
             ON content_embeddings_p%s
             USING hnsw (embedding vector_cosine_ops)
             WITH (m = 16, ef_construction = 64)
             WHERE deleted_at IS NULL',
            i, i
        );
    END LOOP;
END;
$$;

With hash partitioning by user_id, a deletion job can DELETE FROM content_embeddings_partitioned WHERE user_id = $1 hitting only a single partition, making the operation faster and confining index fragmentation to one of sixteen partitions rather than the whole table.

38.5 The Shadow Embedding Problem

The most difficult GDPR scenario in AI systems is what we call the shadow embedding problem: embeddings that were generated not from a single user's content in isolation, but from content that mixed multiple users' data together. This arises in three common scenarios:

Shared document indexing — a user uploads a document that is indexed into a shared knowledge base. The document is chunked and embedded alongside content from other users or internal data. Deleting the user's document should remove those chunks, but the shared knowledge base index may need to be rebuilt.

Conversation-context embeddings — some architectures embed entire conversation windows for retrieval. A single embedding may represent a conversation where the user's messages are interleaved with assistant responses. The embedding is not purely personal data, but it contains a representation of personal data.

Cross-user fine-tuned models — if you have fine-tuned a model on user conversations, the model weights contain a statistical representation of personal data. This is the hardest case and is discussed separately below.

For the first two cases, the solution is source tracking with attribution flags:

-- Track which content contributed to a shared embedding
CREATE TABLE embedding_sources (
    source_id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    embedding_id    UUID NOT NULL REFERENCES content_embeddings(embedding_id) ON DELETE CASCADE,
    contributing_content_id UUID REFERENCES user_content(content_id),
    contributing_user_id    UUID REFERENCES users(user_id),
    contribution_type TEXT NOT NULL,  -- 'primary', 'context', 'system_prompt'
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_emb_sources_user   ON embedding_sources(contributing_user_id);
CREATE INDEX idx_emb_sources_emb_id ON embedding_sources(embedding_id);

-- Find all embeddings that contain a user's content as any contributor
CREATE OR REPLACE FUNCTION find_tainted_embeddings(p_user_id UUID)
RETURNS TABLE (
    embedding_id            UUID,
    is_sole_contributor     BOOLEAN,
    contributor_count       BIGINT,
    content_types           TEXT[]
)
LANGUAGE sql
AS $$
    WITH tainted AS (
        SELECT
            es.embedding_id,
            COUNT(DISTINCT es.contributing_user_id) AS contributor_count,
            ARRAY_AGG(DISTINCT es.contribution_type) AS content_types
        FROM embedding_sources es
        WHERE es.contributing_user_id = p_user_id
        GROUP BY es.embedding_id
    )
    SELECT
        t.embedding_id,
        (t.contributor_count = 1) AS is_sole_contributor,
        t.contributor_count,
        t.content_types
    FROM tainted t;
$$;

The deletion worker uses find_tainted_embeddings to categorize work:

def handle_tainted_embeddings(conn, user_id: str, job_id: str):
    """
    Embeddings where the user is the sole contributor → hard delete.
    Embeddings where the user is one of several contributors → 
      delete the source attribution, then flag for regeneration
      without the user's content.
    """
    with conn.cursor() as cur:
        cur.execute(
            "SELECT * FROM find_tainted_embeddings(%s)",
            (user_id,)
        )
        tainted = cur.fetchall()

    sole_contributor_ids = [
        row["embedding_id"] for row in tainted if row["is_sole_contributor"]
    ]
    shared_contributor_ids = [
        row["embedding_id"] for row in tainted if not row["is_sole_contributor"]
    ]

    with conn.cursor() as cur:
        # Hard delete sole-contributor embeddings
        if sole_contributor_ids:
            cur.execute(
                "DELETE FROM content_embeddings WHERE embedding_id = ANY(%s)",
                (sole_contributor_ids,)
            )
            logger.info(
                f"Deleted {len(sole_contributor_ids)} sole-contributor embeddings"
            )

        # For shared embeddings: remove attribution, queue regeneration
        if shared_contributor_ids:
            cur.execute(
                """
                DELETE FROM embedding_sources
                WHERE embedding_id = ANY(%s)
                  AND contributing_user_id = %s
                """,
                (shared_contributor_ids, user_id)
            )
            # Mark these embeddings for regeneration without the user's content
            cur.execute(
                """
                UPDATE content_embeddings
                SET metadata = jsonb_set(
                    metadata,
                    '{needs_regeneration}',
                    'true'
                ),
                deleted_at = NOW()
                WHERE embedding_id = ANY(%s)
                """,
                (shared_contributor_ids,)
            )
            logger.info(
                f"Marked {len(shared_contributor_ids)} shared embeddings "
                f"for regeneration"
            )
            # Queue regeneration tasks
            for emb_id in shared_contributor_ids:
                regenerate_embedding_without_user.apply_async(
                    args=[str(emb_id), user_id],
                    queue="embeddings",
                    countdown=30,
                )

        conn.commit()

38.6 Fine-Tuned Models and the Unlearning Problem

When you fine-tune a language model on user conversations, the resulting model weights encode a compressed, statistical representation of all the training data — including personal information from users who later submit deletion requests. This is known as the machine unlearning problem and is one of the most active areas of AI compliance research.

PostgreSQL cannot solve this problem directly, but your database design determines how tractable it becomes. The key architectural principle is: never mix user personal data into fine-tuning datasets without maintaining per-user contribution records.

-- Fine-tuning dataset registry
CREATE TABLE finetuning_datasets (
    dataset_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    model_base      TEXT NOT NULL,       -- 'gpt-4o-mini', 'llama-3-8b'
    training_job_id TEXT,                -- external training platform ID
    status          TEXT NOT NULL DEFAULT 'draft',
    record_count    INTEGER,
    description     TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

-- Track which users contributed to each dataset
CREATE TABLE finetuning_contributions (
    contribution_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    dataset_id      UUID NOT NULL REFERENCES finetuning_datasets(dataset_id),
    user_id         UUID NOT NULL REFERENCES users(user_id) ON DELETE RESTRICT,
    content_id      UUID REFERENCES user_content(content_id),
    contributed_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    row_count       INTEGER,
    removed_at      TIMESTAMPTZ,    -- set when user requests deletion
    removal_reason  TEXT
);

CREATE INDEX idx_ft_contrib_user    ON finetuning_contributions(user_id);
CREATE INDEX idx_ft_contrib_dataset ON finetuning_contributions(dataset_id);

-- Find all fine-tuned models that contain a user's data
CREATE OR REPLACE FUNCTION get_affected_models(p_user_id UUID)
RETURNS TABLE (
    dataset_id      UUID,
    model_base      TEXT,
    training_job_id TEXT,
    row_count       INTEGER,
    contributed_at  TIMESTAMPTZ
)
LANGUAGE sql
AS $$
    SELECT fd.dataset_id, fd.model_base, fd.training_job_id,
           fc.row_count, fc.contributed_at
    FROM finetuning_contributions fc
    JOIN finetuning_datasets fd ON fc.dataset_id = fd.dataset_id
    WHERE fc.user_id = p_user_id
      AND fc.removed_at IS NULL;
$$;

When a deletion is requested and the user contributed to a fine-tuning dataset, you face three options ordered by compliance strength:

Option 1 — Document and retain. Record that the user's contribution cannot be removed from weights already trained. This is sometimes acceptable if the personal data contribution was minimal and if the training data was sufficiently anonymized before training. Document the legal basis in your deletion audit log.

Option 2 — Retrain without the user's data. Remove the user's contribution records from the training dataset and trigger a new fine-tuning run. This is expensive but clean. Your dataset contribution records in PostgreSQL make it straightforward to reconstruct a dataset minus one user's rows.

Option 3 — Retire the model. If retraining is not feasible and the contribution is significant, retire the affected model version and route traffic to a base model or a retrained successor.

def handle_finetuning_impact(conn, user_id: str, job_id: str):
    """
    Assess and respond to fine-tuning model impact for a GDPR deletion.
    """
    user_id_hash = hashlib.sha256(user_id.encode()).hexdigest()

    with conn.cursor() as cur:
        cur.execute("SELECT * FROM get_affected_models(%s)", (user_id,))
        affected_models = cur.fetchall()

    if not affected_models:
        logger.info(f"No fine-tuned model impact for user {user_id}")
        return

    for model in affected_models:
        logger.warning(
            f"User contributed {model['row_count']} rows to dataset "
            f"{model['dataset_id']} (model base: {model['model_base']})"
        )

        # Mark contribution as removed in the registry
        with conn.cursor() as cur:
            cur.execute(
                """
                UPDATE finetuning_contributions
                SET removed_at = NOW(),
                    removal_reason = 'gdpr_deletion'
                WHERE dataset_id = %s AND user_id = %s
                """,
                (model["dataset_id"], user_id)
            )
            conn.commit()

        # Log to audit trail — DPO must decide on retraining
        with conn.cursor() as cur:
            cur.execute(
                """
                INSERT INTO deletion_audit_log (
                    deletion_job_id, user_id_hash, event_type,
                    step_name, executor, notes
                ) VALUES (%s, %s, 'step_completed', 'finetuning_impact_assessed',
                          'celery_worker', %s)
                """,
                (
                    job_id,
                    user_id_hash,
                    json.dumps({
                        "dataset_id": str(model["dataset_id"]),
                        "model_base": model["model_base"],
                        "training_job_id": model["training_job_id"],
                        "row_count": model["row_count"],
                        "action_required": "dpo_review_retraining_decision",
                    }),
                )
            )
            conn.commit()

        # Create a DPO review task
        create_dpo_review_task.apply_async(
            args=[job_id, str(model["dataset_id"]), user_id_hash],
            queue="compliance",
        )

38.7 Proving Compliance: The Audit Report

GDPR requires that you be able to demonstrate compliance. When a supervisory authority investigates a complaint, you need a clear, tamper-evident record proving that the deletion was complete and timely. The deletion_audit_log table was designed for this.

-- Generate a compliance report for a deletion job
-- This report contains NO personal data — only hashes and event metadata
CREATE OR REPLACE FUNCTION generate_compliance_report(p_job_id UUID)
RETURNS JSONB
LANGUAGE plpgsql
AS $$
DECLARE
    v_report JSONB;
    v_job    RECORD;
    v_events JSONB;
BEGIN
    SELECT * INTO v_job FROM deletion_jobs WHERE job_id = p_job_id;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Job % not found', p_job_id;
    END IF;

    SELECT json_agg(
        json_build_object(
            'audit_id',         audit_id,
            'event_type',       event_type,
            'step_name',        step_name,
            'records_affected', records_affected,
            'executed_at',      executed_at,
            'executor',         executor,
            'checksum',         checksum
        ) ORDER BY executed_at
    )
    INTO v_events
    FROM deletion_audit_log
    WHERE deletion_job_id = p_job_id;

    v_report := jsonb_build_object(
        'report_generated_at',  NOW(),
        'job_id',               p_job_id,
        'user_id_hash',         encode(
                                    digest(v_job.user_id::TEXT, 'sha256'), 'hex'
                                ),
        'requested_at',         v_job.requested_at,
        'deadline_at',          v_job.deadline_at,
        'completed_at',         v_job.completed_at,
        'verified_at',          v_job.verified_at,
        'within_deadline',      (v_job.completed_at <= v_job.deadline_at),
        'days_to_complete',     EXTRACT(
                                    EPOCH FROM (v_job.completed_at - v_job.requested_at)
                                ) / 86400.0,
        'final_status',         v_job.status,
        'steps_completed',      v_job.steps_completed,
        'audit_trail',          v_events,
        'report_checksum',      encode(
                                    digest(
                                        v_job.user_id::TEXT ||
                                        p_job_id::TEXT ||
                                        COALESCE(v_job.completed_at::TEXT, 'incomplete'),
                                        'sha256'
                                    ),
                                    'hex'
                                )
    );

    RETURN v_report;
END;
$$;

The report checksum ties the user_id, job_id, and completed_at timestamp together. A regulator can verify that the report has not been retroactively altered by recomputing this hash. Because the report contains only the SHA-256 of the user_id (not the user_id itself), the report can be stored and shared without itself constituting personal data under GDPR — an important property since you need to retain it indefinitely.

-- SQL Server equivalent schema for GDPR deletion tracking

CREATE TABLE users (

    -- SQL Server does not have native vector type as of SQL Server 2022;
    -- store as VARBINARY or use Azure AI extension on Azure SQL

    checksum        NVARCHAR(64)
);

-- SQL Server procedure to initiate deletion
CREATE OR ALTER PROCEDURE dbo.InitiateDeletionRequest
    @p_user_id UNIQUEIDENTIFIER
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @v_job_id UNIQUEIDENTIFIER = NEWID();
    DECLARE @v_user_hash NVARCHAR(64);

    -- Compute SHA-256 hash of user_id as hex string
    SELECT @v_user_hash = LOWER(
        CONVERT(NVARCHAR(64),
            HASHBYTES('SHA2_256', CAST(@p_user_id AS NVARCHAR(36))),
            2)
    );

    BEGIN TRANSACTION;

    UPDATE users
    SET deletion_requested_at = SYSDATETIMEOFFSET(),
        is_active = 0,
        deletion_job_id = @v_job_id
    WHERE user_id = @p_user_id
      AND deletion_requested_at IS NULL;

    IF @@ROWCOUNT = 0
    BEGIN
        ROLLBACK;
        THROW 50001, 'User not found or deletion already in progress', 1;
    END

    INSERT INTO deletion_jobs (job_id, user_id)
    VALUES (@v_job_id, @p_user_id);

    INSERT INTO deletion_audit_log (
        deletion_job_id, user_id_hash, event_type,
        step_name, executor, notes
    ) VALUES (
        @v_job_id, @v_user_hash, 'deletion_requested',
        'intake', 'system', 'Deletion job created and user marked inactive'
    );

    COMMIT;

    -- SQL Server Service Broker message or Azure Service Bus call
    -- replaces pg_notify for async worker handoff
    -- EXEC dbo.SendDeletionMessage @v_job_id, @p_user_id;

    SELECT @v_job_id AS job_id;
END;
GO

-- SQL Server step executor
CREATE OR ALTER PROCEDURE dbo.ExecuteDeletionStep
    @p_job_id   UNIQUEIDENTIFIER,
    @p_step_name NVARCHAR(100),
    @p_user_id  UNIQUEIDENTIFIER
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @v_affected    INT = 0;
    DECLARE @v_user_hash   NVARCHAR(64);

    SELECT @v_user_hash = LOWER(
        CONVERT(NVARCHAR(64),
            HASHBYTES('SHA2_256', CAST(@p_user_id AS NVARCHAR(36))),
            2)
    );

    UPDATE deletion_jobs
    SET current_step = @p_step_name,
        status = 'running',
        started_at = COALESCE(started_at, SYSDATETIMEOFFSET())
    WHERE job_id = @p_job_id;

    IF @p_step_name = 'scrub_conversation_turns'
    BEGIN
        UPDATE conversation_turns
        SET content = NULL,
            deleted_at = SYSDATETIMEOFFSET()
        WHERE user_id = @p_user_id AND deleted_at IS NULL;
        SET @v_affected = @@ROWCOUNT;
    END
    ELSE IF @p_step_name = 'scrub_content_source_text'
    BEGIN
        UPDATE user_content
        SET source_text = NULL,
            deleted_at = SYSDATETIMEOFFSET()
        WHERE user_id = @p_user_id AND deleted_at IS NULL;
        SET @v_affected = @@ROWCOUNT;
    END
    ELSE IF @p_step_name = 'delete_embeddings'
    BEGIN
        DELETE FROM content_embeddings WHERE user_id = @p_user_id;
        SET @v_affected = @@ROWCOUNT;
    END
    ELSE IF @p_step_name = 'scrub_user_profile'
    BEGIN
        UPDATE users
        SET email = 'deleted-' + LOWER(
                        CONVERT(NVARCHAR(64),
                            HASHBYTES('SHA2_256', CAST(email AS NVARCHAR(320))),
                            2)
                    ) + '@deleted.invalid',
            display_name = NULL,
            deletion_completed_at = SYSDATETIMEOFFSET()
        WHERE user_id = @p_user_id;
        SET @v_affected = @@ROWCOUNT;
    END

    INSERT INTO deletion_audit_log (
        deletion_job_id, user_id_hash, event_type,
        step_name, records_affected, executor
    ) VALUES (
        @p_job_id, @v_user_hash, 'step_completed',
        @p_step_name, @v_affected, 'worker'
    );

    SELECT @v_affected AS records_affected;
END;
GO

Azure SQL Managed Instance and Azure SQL Database (as of the vector preview features introduced in 2024) support a native VECTOR data type, making the embedding_blob VARBINARY(MAX) workaround unnecessary for teams on Azure. The deletion semantics remain identical: DELETE FROM content_embeddings WHERE user_id = @p_user_id removes the row and its vector column together regardless of whether the type is VECTOR or VARBINARY(MAX).

38.9 Monitoring and SLA Enforcement

GDPR's 30-day deadline is a hard legal obligation. Your monitoring system must alert well before that window closes, not after. Build deadline-aware queries into your operational dashboards:

-- Jobs approaching the 30-day deadline
CREATE OR REPLACE VIEW deletion_jobs_at_risk AS
SELECT
    job_id,
    user_id,
    status,
    requested_at,
    deadline_at,
    deadline_at - NOW()                         AS time_remaining,
    EXTRACT(EPOCH FROM (deadline_at - NOW()))
        / 86400.0                               AS days_remaining,
    current_step,
    retry_count
FROM deletion_jobs
WHERE status NOT IN ('completed')
  AND deadline_at < NOW() + INTERVAL '7 days'   -- alert with 7 days to spare
ORDER BY deadline_at ASC;

-- Overdue jobs — immediate escalation required
CREATE OR REPLACE VIEW deletion_jobs_overdue AS
SELECT
    job_id,
    status,
    requested_at,
    deadline_at,
    NOW() - deadline_at         AS overdue_by,
    current_step,
    error_details
FROM deletion_jobs
WHERE status NOT IN ('completed')
  AND deadline_at < NOW()
ORDER BY deadline_at ASC;

-- Summary statistics for the compliance dashboard
CREATE OR REPLACE VIEW deletion_compliance_summary AS
SELECT
    COUNT(*)                                        AS total_jobs,
    COUNT(*) FILTER (WHERE status = 'completed')    AS completed,
    COUNT(*) FILTER (WHERE status = 'failed')       AS failed,
    COUNT(*) FILTER (WHERE status IN ('pending','running','verifying'))
                                                    AS in_progress,
    COUNT(*) FILTER (WHERE status != 'completed'
                       AND deadline_at < NOW())     AS overdue,
    COUNT(*) FILTER (WHERE status != 'completed'
                       AND deadline_at < NOW() + INTERVAL '7 days'
                       AND deadline_at >= NOW())    AS at_risk,
    AVG(
        EXTRACT(EPOCH FROM (completed_at - requested_at)) / 3600.0
    ) FILTER (WHERE status = 'completed')           AS avg_completion_hours,
    MAX(
        EXTRACT(EPOCH FROM (completed_at - requested_at)) / 3600.0
    ) FILTER (WHERE status = 'completed')           AS max_completion_hours
FROM deletion_jobs;

Wire these views into your alerting system — Prometheus with a PostgreSQL exporter, Datadog, or a simple cron job that emails your DPO — so that any overdue or at-risk job triggers a response before the legal deadline passes:

# monitoring.py — Prometheus metrics for GDPR deletion SLA

from prometheus_client import Gauge, start_http_server
import psycopg2
import time
import logging

logger = logging.getLogger(__name__)

# Gauges exported to Prometheus
gdpr_jobs_overdue = Gauge(
    "gdpr_deletion_jobs_overdue_total",
    "Number of GDPR deletion jobs past their 30-day deadline"
)
gdpr_jobs_at_risk = Gauge(
    "gdpr_deletion_jobs_at_risk_total",
    "Number of GDPR deletion jobs within 7 days of deadline"
)
gdpr_jobs_in_progress = Gauge(
    "gdpr_deletion_jobs_in_progress_total",
    "Number of GDPR deletion jobs currently being processed"
)
gdpr_avg_completion_hours = Gauge(
    "gdpr_deletion_avg_completion_hours",
    "Average hours to complete a GDPR deletion job"
)


def collect_deletion_metrics(db_dsn: str):
    """Poll PostgreSQL and update Prometheus gauges."""
    try:
        with psycopg2.connect(db_dsn) as conn:
            with conn.cursor() as cur:
                cur.execute("SELECT * FROM deletion_compliance_summary")
                row = cur.fetchone()
                if row:
                    (total, completed, failed, in_progress,
                     overdue, at_risk, avg_hours, max_hours) = row

                    gdpr_jobs_overdue.set(overdue or 0)
                    gdpr_jobs_at_risk.set(at_risk or 0)
                    gdpr_jobs_in_progress.set(in_progress or 0)
                    gdpr_avg_completion_hours.set(avg_hours or 0)

                    if (overdue or 0) > 0:
                        logger.critical(
                            f"GDPR COMPLIANCE ALERT: {overdue} deletion jobs are overdue!"
                        )
                    if (at_risk or 0) > 0:
                        logger.warning(
                            f"GDPR WARNING: {at_risk} deletion jobs expire within 7 days"
                        )
    except Exception as e:
        logger.error(f"Failed to collect deletion metrics: {e}")


def run_metrics_server(db_dsn: str, port: int = 9090):
    start_http_server(port)
    logger.info(f"Prometheus metrics server started on port {port}")
    while True:
        collect_deletion_metrics(db_dsn)
        time.sleep(60)

Key Takeaways

  • → **Embeddings are personal data by default.** The conservative and legally defensible position is that vectors derived from user-authored content must be hard-deleted, not just soft-deleted, when a GDPR erasure request is received. PostgreSQL's `user_id` foreign keys on every embedding row make this tractable.
  • → **The deletion pipeline is a workflow, not a single query.** A production-grade GDPR deletion spans conversation turns, source text, embeddings, Redis caches, Celery job queues, and potentially fine-tuning datasets. PostgreSQL's deletion jobs table, `pg_notify`, and Celery workers provide the coordination layer that makes each step idempotent, auditable, and retriable.
  • → **The shadow embedding problem requires source attribution.** Embeddings generated from mixed-user content cannot be deleted without first understanding their provenance. The `embedding_sources` table tracks every contributing user per embedding, enabling the worker to distinguish sole-contributor deletions (hard delete) from shared-contributor deletions (attribution removal plus regeneration).
  • → **Fine-tuned models demand pre-emptive contribution tracking.** Once a model has been trained on personal data, the weights cannot be surgically edited. Recording every user's contribution to every fine-tuning dataset in PostgreSQL at training time is the only way to make a retraining-minus-one-user operation operationally feasible when a deletion request arrives.
  • → **Compliance proof must be tamper-evident and PII-free.** The `deletion_audit_log` stores SHA-256 hashes of user IDs rather than user IDs themselves, allowing indefinite retention of the audit trail without the log itself constituting personal data. Row-level checksums and the compliance report's own checksum field enable a supervisory authority to verify that records have not been retroactively altered.
