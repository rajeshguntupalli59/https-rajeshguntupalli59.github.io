Chapter 29: Streaming Results from AI Back into PostgreSQL

Streaming is where AI applications stop feeling like batch jobs and start feeling alive. When a user sends a message to your LLM-powered application, they don't want to stare at a spinner for eight seconds — they want tokens to appear as the model generates them. But streaming creates a genuine engineering challenge: you're receiving a response as a river of partial chunks, and PostgreSQL stores complete, consistent records. Bridging that gap — capturing streamed AI output incrementally, persisting it reliably, and making it available to downstream systems in real time — is what this chapter is about. You'll learn how to wire together server-sent events, async Python, pg_notify, and PostgreSQL's own JSONB and logical replication machinery so that streaming AI responses become first-class database objects, not ephemeral byproducts of an API call.

---

29.1 Understanding the Streaming Architecture

Before writing a single line of code, you need a clear mental model of what actually moves through the system when an LLM streams a response.

The token lifecycle

When you call the OpenAI or Anthropic API with stream=True, the response comes back as a series of server-sent events (SSE). Each event carries a delta — typically one to three tokens — along with metadata like finish reason, model name, and usage statistics. Your application receives these chunks in an async generator loop, and it has several responsibilities simultaneously:

1. Forward chunks to the client (WebSocket, SSE endpoint, gRPC stream)

2. Accumulate chunks into a coherent buffer

3. Persist the buffer to PostgreSQL at appropriate intervals

4. Signal completion and write final metadata

graph TD
    LLM[LLM streams tokens] --> Fwd[Forward chunk to client via SSE]
    LLM --> Buf[Accumulate into in-memory buffer]
    Buf --> Write[(INSERT into message_stream_chunks)]
    Write -->|every N chunks| Notify[pg_notify: stream_progress]
    LLM -->|stream ends| Final[Assemble full content]
    Final --> Update[(UPDATE messages: content, is_complete = TRUE)]
    Update --> Done[pg_notify: stream_complete]

*Four responsibilities run per chunk; only the final assembly and the completion notification happen once, after the loop ends.*

The naive approach — buffer everything in memory, write once at the end — breaks when users close their browser tab mid-stream, when network errors interrupt the connection, or when you need audit trails of partial responses. The robust approach writes to PostgreSQL incrementally, using PostgreSQL itself as the coordination layer.

Schema first

Every conversation in a production AI system needs a persistent record. Here's the schema that anchors the rest of this chapter:

-- Core conversation tables for streaming AI responses
CREATE TABLE conversations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    session_id      UUID NOT NULL,
    title           TEXT,
    model           TEXT NOT NULL DEFAULT 'gpt-4o',
    system_prompt   TEXT,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE messages (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool')),
    content         TEXT,                     -- final assembled content
    content_chunks  JSONB NOT NULL DEFAULT '[]', -- raw streaming chunks
    token_count     INTEGER,
    finish_reason   TEXT,
    model           TEXT,
    stream_started_at  TIMESTAMPTZ,
    stream_completed_at TIMESTAMPTZ,
    is_complete     BOOLEAN NOT NULL DEFAULT FALSE,
    error           JSONB,
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Partial chunks table for high-frequency incremental writes
CREATE TABLE message_stream_chunks (
    id              BIGSERIAL PRIMARY KEY,
    message_id      UUID NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    chunk_index     INTEGER NOT NULL,
    chunk_content   TEXT NOT NULL,
    chunk_raw       JSONB NOT NULL,           -- full API response delta
    received_at     TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX idx_message_stream_chunks_message_id 
    ON message_stream_chunks(message_id, chunk_index);

CREATE INDEX idx_messages_conversation_created 
    ON messages(conversation_id, created_at);

CREATE INDEX idx_conversations_user_session 
    ON conversations(user_id, session_id);

-- Function to auto-update updated_at
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$;

CREATE TRIGGER messages_updated_at
    BEFORE UPDATE ON messages
    FOR EACH ROW EXECUTE FUNCTION update_updated_at();

CREATE TRIGGER conversations_updated_at
    BEFORE UPDATE ON conversations
    FOR EACH ROW EXECUTE FUNCTION update_updated_at();

The design gives you two levels of persistence: message_stream_chunks captures every delta as it arrives (useful for debugging, replay, and billing verification), while messages.content holds the assembled final string. The content_chunks JSONB array on messages stores the raw API deltas, preserving finish reasons, usage data, and any tool call fragments that arrived during the stream.

29.2 Streaming from OpenAI and Anthropic into PostgreSQL

The implementation splits into three concerns: receiving the stream, writing to PostgreSQL asynchronously, and notifying downstream consumers. Here's a complete async pattern using asyncpg and the OpenAI streaming API.

# stream_writer.py — captures OpenAI streaming responses into PostgreSQL
import asyncio
import json
import uuid
from datetime import datetime, timezone
from typing import AsyncGenerator, Optional

import asyncpg
from openai import AsyncOpenAI

openai_client = AsyncOpenAI()

class StreamWriter:
    """
    Captures an OpenAI streaming response into PostgreSQL incrementally.
    Writes chunks to message_stream_chunks in real time, then assembles
    the final content into messages once streaming completes.
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def create_message_record(
        self,
        conversation_id: str,
        role: str = "assistant",
        model: str = "gpt-4o",
    ) -> str:
        """Creates a placeholder message row before streaming begins."""
        message_id = str(uuid.uuid4())
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO messages (
                    id, conversation_id, role, model,
                    stream_started_at, is_complete
                ) VALUES ($1, $2, $3, $4, $5, FALSE)
                """,
                message_id,
                conversation_id,
                role,
                model,
                datetime.now(timezone.utc),
            )
        return message_id

    async def write_chunk(
        self,
        conn: asyncpg.Connection,
        message_id: str,
        chunk_index: int,
        content: str,
        raw_delta: dict,
    ) -> None:
        """Writes a single streaming chunk to the chunks table."""
        await conn.execute(
            """
            INSERT INTO message_stream_chunks (
                message_id, chunk_index, chunk_content, chunk_raw
            ) VALUES ($1, $2, $3, $4)
            """,
            message_id,
            chunk_index,
            content,
            json.dumps(raw_delta),
        )

    async def finalize_message(
        self,
        conn: asyncpg.Connection,
        message_id: str,
        full_content: str,
        all_chunks: list,
        finish_reason: Optional[str],
        usage: Optional[dict],
    ) -> None:
        """Assembles final content and marks the message complete."""
        token_count = usage.get("completion_tokens") if usage else None
        await conn.execute(
            """
            UPDATE messages SET
                content = $1,
                content_chunks = $2,
                token_count = $3,
                finish_reason = $4,
                stream_completed_at = $5,
                is_complete = TRUE,
                metadata = metadata || $6
            WHERE id = $7
            """,
            full_content,
            json.dumps(all_chunks),
            token_count,
            finish_reason,
            datetime.now(timezone.utc),
            json.dumps({"usage": usage} if usage else {}),
            message_id,
        )

    async def notify_stream_progress(
        self,
        conn: asyncpg.Connection,
        message_id: str,
        chunk_index: int,
        content_so_far: str,
    ) -> None:
        """Fires pg_notify so subscribers can follow along in real time."""
        payload = json.dumps({
            "message_id": message_id,
            "chunk_index": chunk_index,
            "content_length": len(content_so_far),
        })
        # pg_notify payload is limited to 8000 bytes
        await conn.execute(
            "SELECT pg_notify('stream_progress', $1)", payload
        )

    async def stream_and_persist(
        self,
        conversation_id: str,
        messages: list[dict],
        model: str = "gpt-4o",
        notify_every_n_chunks: int = 5,
    ) -> AsyncGenerator[str, None]:
        """
        Main entry point. Streams from OpenAI, persists every chunk,
        and yields content tokens so the caller can forward them downstream.
        """
        message_id = await self.create_message_record(
            conversation_id, model=model
        )

        accumulated_content = []
        all_raw_chunks = []
        finish_reason = None
        usage = None
        chunk_index = 0

        async with self.pool.acquire() as conn:
            stream = await openai_client.chat.completions.create(
                model=model,
                messages=messages,
                stream=True,
                stream_options={"include_usage": True},
            )

            async for chunk in stream:
                choice = chunk.choices[0] if chunk.choices else None
                delta_content = ""

                if choice and choice.delta and choice.delta.content:
                    delta_content = choice.delta.content
                    accumulated_content.append(delta_content)

                if choice and choice.finish_reason:
                    finish_reason = choice.finish_reason

                if hasattr(chunk, "usage") and chunk.usage:
                    usage = {
                        "prompt_tokens": chunk.usage.prompt_tokens,
                        "completion_tokens": chunk.usage.completion_tokens,
                        "total_tokens": chunk.usage.total_tokens,
                    }

                raw_delta = {
                    "id": chunk.id,
                    "model": chunk.model,
                    "delta_content": delta_content,
                    "finish_reason": finish_reason,
                }
                all_raw_chunks.append(raw_delta)

                if delta_content:
                    await self.write_chunk(
                        conn, message_id, chunk_index,
                        delta_content, raw_delta
                    )

                    if chunk_index % notify_every_n_chunks == 0:
                        content_so_far = "".join(accumulated_content)
                        await self.notify_stream_progress(
                            conn, message_id, chunk_index, content_so_far
                        )

                    chunk_index += 1
                    yield delta_content  # forward to the caller

            # Write the assembled final message
            full_content = "".join(accumulated_content)
            await self.finalize_message(
                conn, message_id, full_content,
                all_raw_chunks, finish_reason, usage
            )

            # Final notification — stream is complete
            final_payload = json.dumps({
                "message_id": message_id,
                "event": "complete",
                "finish_reason": finish_reason,
                "token_count": usage.get("completion_tokens") if usage else None,
            })
            await conn.execute(
                "SELECT pg_notify('stream_complete', $1)", final_payload
            )

The key design decision here is using a persistent connection for the entire streaming session rather than acquiring a new connection per chunk. Connection acquisition has overhead — with asyncpg and PgBouncer in transaction mode, you'd lose your connection between chunks anyway. Holding one connection for the duration of a stream keeps the write path fast and consistent.

The Anthropic version uses the same structure with a different SDK surface:

# anthropic_stream_writer.py
import anthropic
import asyncio
import json
import uuid
from typing import AsyncGenerator

import asyncpg

anthropic_client = anthropic.AsyncAnthropic()

async def stream_claude_to_postgres(
    pool: asyncpg.Pool,
    conversation_id: str,
    messages: list[dict],
    system_prompt: str = "",
    model: str = "claude-opus-4-5",
) -> AsyncGenerator[str, None]:
    """
    Streams a Claude response and writes it incrementally to PostgreSQL.
    Claude's streaming API uses a context manager pattern.
    """
    message_id = str(uuid.uuid4())

    async with pool.acquire() as conn:
        # Pre-insert the message shell
        await conn.execute(
            """
            INSERT INTO messages (
                id, conversation_id, role, model,
                stream_started_at, is_complete
            ) VALUES ($1, $2, 'assistant', $3, NOW(), FALSE)
            """,
            message_id, conversation_id, model,
        )

        accumulated = []
        input_tokens = 0
        output_tokens = 0
        chunk_index = 0
        stop_reason = None

        async with anthropic_client.messages.stream(
            model=model,
            max_tokens=4096,
            system=system_prompt,
            messages=messages,
        ) as stream:

            async for event in stream:
                # Anthropic uses typed events rather than raw deltas
                if event.type == "content_block_delta":
                    if hasattr(event.delta, "text"):
                        token = event.delta.text
                        accumulated.append(token)

                        await conn.execute(
                            """
                            INSERT INTO message_stream_chunks
                                (message_id, chunk_index, chunk_content, chunk_raw)
                            VALUES ($1, $2, $3, $4)
                            """,
                            message_id,
                            chunk_index,
                            token,
                            json.dumps({
                                "type": "text_delta",
                                "text": token,
                                "index": event.index,
                            }),
                        )
                        chunk_index += 1
                        yield token

                elif event.type == "message_delta":
                    if hasattr(event.usage, "output_tokens"):
                        output_tokens = event.usage.output_tokens
                    if hasattr(event.delta, "stop_reason"):
                        stop_reason = event.delta.stop_reason

                elif event.type == "message_start":
                    if hasattr(event.message, "usage"):
                        input_tokens = event.message.usage.input_tokens

        # Finalize
        full_content = "".join(accumulated)
        await conn.execute(
            """
            UPDATE messages SET
                content = $1,
                token_count = $2,
                finish_reason = $3,
                stream_completed_at = NOW(),
                is_complete = TRUE,
                metadata = metadata || $4
            WHERE id = $5
            """,
            full_content,
            output_tokens,
            stop_reason,
            json.dumps({
                "input_tokens": input_tokens,
                "output_tokens": output_tokens,
            }),
            message_id,
        )

        await conn.execute(
            "SELECT pg_notify('stream_complete', $1)",
            json.dumps({
                "message_id": message_id,
                "event": "complete",
                "stop_reason": stop_reason,
            }),
        )

29.3 FastAPI SSE Endpoints and pg_notify Consumers

Having the data in PostgreSQL is only half the picture. Your frontend needs a way to receive the stream in real time. The standard approach is Server-Sent Events — a unidirectional HTTP stream that's simpler than WebSockets and natively handled by browsers.

# api/stream_endpoint.py — FastAPI endpoint with SSE forwarding
import asyncio
import json
from typing import AsyncGenerator

import asyncpg
from fastapi import FastAPI, Depends, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()

# Dependency: get connection pool
async def get_pool() -> asyncpg.Pool:
    return app.state.pool

class ChatRequest(BaseModel):
    conversation_id: str
    content: str
    model: str = "gpt-4o"

async def sse_event(data: str, event: str = "chunk") -> str:
    """Format a server-sent event."""
    return f"event: {event}\ndata: {data}\n\n"

@app.post("/api/v1/chat/stream")
async def stream_chat(
    request: ChatRequest,
    pool: asyncpg.Pool = Depends(get_pool),
):
    """
    Accepts a chat message, streams the LLM response via SSE,
    and persists every chunk to PostgreSQL.
    """
    # Verify conversation exists and user has access
    async with pool.acquire() as conn:
        conv = await conn.fetchrow(
            """
            SELECT id, system_prompt, model
            FROM conversations
            WHERE id = $1
            """,
            request.conversation_id,
        )
        if not conv:
            raise HTTPException(status_code=404, detail="Conversation not found")

        # Persist the user message first
        await conn.execute(
            """
            INSERT INTO messages (
                id, conversation_id, role, content,
                is_complete, stream_completed_at
            ) VALUES (gen_random_uuid(), $1, 'user', $2, TRUE, NOW())
            """,
            request.conversation_id,
            request.content,
        )

        # Load conversation history for context
        history = await conn.fetch(
            """
            SELECT role, content
            FROM messages
            WHERE conversation_id = $1
              AND is_complete = TRUE
              AND role IN ('user', 'assistant')
            ORDER BY created_at ASC
            LIMIT 20
            """,
            request.conversation_id,
        )

    messages_payload = [
        {"role": row["role"], "content": row["content"]}
        for row in history
        if row["content"]  # exclude empty/incomplete messages
    ]

    system_prompt = conv["system_prompt"] or ""
    if system_prompt:
        messages_payload.insert(0, {"role": "system", "content": system_prompt})

    writer = StreamWriter(pool)

    async def generate() -> AsyncGenerator[str, None]:
        try:
            async for token in writer.stream_and_persist(
                conversation_id=request.conversation_id,
                messages=messages_payload,
                model=request.model or conv["model"],
            ):
                yield await sse_event(
                    json.dumps({"token": token}),
                    event="chunk",
                )
        except Exception as e:
            yield await sse_event(
                json.dumps({"error": str(e)}),
                event="error",
            )
        finally:
            yield await sse_event(
                json.dumps({"done": True}),
                event="done",
            )

    return StreamingResponse(
        generate(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",  # critical for nginx
            "Connection": "keep-alive",
        },
    )

pg_notify as a coordination bus

Beyond the SSE endpoint, pg_notify lets other parts of your system react to stream events without polling. A background worker listening on the stream_complete channel can trigger embedding generation, audit logging, or cache invalidation the moment an AI response finishes.

# workers/stream_listener.py — pg_notify listener for post-stream processing
import asyncio
import json
import logging

import asyncpg

logger = logging.getLogger(__name__)

async def on_stream_complete(
    conn: asyncpg.Connection,
    pid: int,
    channel: str,
    payload: str,
) -> None:
    """
    Callback fired when a stream_complete notification arrives.
    Triggers embedding generation and cache invalidation.
    """
    try:
        data = json.loads(payload)
        message_id = data.get("message_id")
        if not message_id:
            return

        logger.info(f"Stream complete for message {message_id}, "
                    f"tokens={data.get('token_count')}")

        # Dispatch to Celery for async embedding + cache work
        from workers.tasks import generate_message_embedding, invalidate_conversation_cache
        generate_message_embedding.delay(message_id)
        invalidate_conversation_cache.delay(data.get("conversation_id"))

    except Exception as e:
        logger.error(f"Error handling stream_complete: {e}")

async def on_stream_error(
    conn: asyncpg.Connection,
    pid: int,
    channel: str,
    payload: str,
) -> None:
    data = json.loads(payload)
    logger.error(f"Stream error: {data}")
    # write to an errors table for monitoring
    await conn.execute(
        """
        INSERT INTO stream_errors (message_id, error, occurred_at)
        VALUES ($1, $2, NOW())
        """,
        data.get("message_id"),
        json.dumps(data),
    )

async def run_listener(dsn: str) -> None:
    """
    Long-running listener process. Uses a dedicated connection
    (not from the pool) for LISTEN/NOTIFY.
    """
    conn = await asyncpg.connect(dsn)

    await conn.add_listener("stream_complete", on_stream_complete)
    await conn.add_listener("stream_progress", lambda *a: None)  # no-op for now

    logger.info("Listening on stream_complete channel...")

    try:
        # Keep the connection alive indefinitely
        while True:
            await asyncio.sleep(1)
    finally:
        await conn.remove_listener("stream_complete", on_stream_complete)
        await conn.close()

if __name__ == "__main__":
    import os
    asyncio.run(run_listener(os.environ["DATABASE_URL"]))

One subtlety: LISTEN/NOTIFY connections must *not* come from PgBouncer in transaction-mode pooling. PgBouncer returns connections to the pool between transactions, and a connection that was listening won't be the same one your backend code holds after a new transaction starts. For listener processes, always connect directly to PostgreSQL.

29.4 Celery Workers for Async Post-Stream Processing

Stream completion triggers a cascade of downstream work: embedding the assistant's response for RAG retrieval, updating the conversation summary, writing to audit logs, and invalidating Redis caches. Doing this synchronously in the streaming path adds latency. Celery absorbs it asynchronously.

# workers/tasks.py — Celery tasks triggered after stream completion
import json
import os
from celery import Celery
import redis
import psycopg2
from psycopg2.extras import Json

from openai import OpenAI

celery_app = Celery(
    "stream_tasks",
    broker=os.environ["REDIS_URL"],
    backend=os.environ["REDIS_URL"],
)

openai_client = OpenAI()

def get_db_conn():
    return psycopg2.connect(os.environ["DATABASE_URL"])

def get_redis():
    return redis.from_url(os.environ["REDIS_URL"])

@celery_app.task(
    bind=True,
    max_retries=3,
    default_retry_delay=60,
)
def generate_message_embedding(self, message_id: str) -> None:
    """
    Generates a vector embedding for a completed assistant message
    and stores it for RAG retrieval.
    """
    conn = get_db_conn()
    try:
        with conn.cursor() as cur:
            # Fetch the completed message content
            cur.execute(
                """
                SELECT m.content, m.conversation_id, m.model
                FROM messages m
                WHERE m.id = %s AND m.is_complete = TRUE AND m.role = 'assistant'
                """,
                (message_id,),
            )
            row = cur.fetchone()
            if not row:
                return  # message not ready or already processed

            content, conversation_id, model = row

            if not content or len(content.strip()) < 10:
                return  # not worth embedding

            # Generate embedding via OpenAI
            response = openai_client.embeddings.create(
                input=content,
                model="text-embedding-3-small",
            )
            embedding = response.data[0].embedding

            # Upsert into the message_embeddings table
            cur.execute(
                """
                INSERT INTO message_embeddings (
                    message_id, conversation_id, embedding,
                    embedding_model, created_at
                ) VALUES (%s, %s, %s::vector, %s, NOW())
                ON CONFLICT (message_id) DO UPDATE SET
                    embedding = EXCLUDED.embedding,
                    embedding_model = EXCLUDED.embedding_model,
                    created_at = NOW()
                """,
                (
                    message_id,
                    conversation_id,
                    str(embedding),
                    "text-embedding-3-small",
                ),
            )
            conn.commit()
    except Exception as exc:
        conn.rollback()
        raise self.retry(exc=exc)
    finally:
        conn.close()


@celery_app.task(bind=True, max_retries=3)
def invalidate_conversation_cache(self, conversation_id: str) -> None:
    """
    Clears Redis cache keys for a conversation after a new message
    has been persisted. Downstream endpoints re-fetch from PostgreSQL.
    """
    r = get_redis()
    try:
        # Collect all cache keys related to this conversation
        pattern = f"conv:{conversation_id}:*"
        keys = r.keys(pattern)
        if keys:
            r.delete(*keys)

        # Also clear the conversation list cache for the owning user
        # (we look up user_id from the DB to construct the key)
        conn = get_db_conn()
        try:
            with conn.cursor() as cur:
                cur.execute(
                    "SELECT user_id FROM conversations WHERE id = %s",
                    (conversation_id,),
                )
                row = cur.fetchone()
                if row:
                    user_id = row[0]
                    r.delete(f"user:{user_id}:conversations")
        finally:
            conn.close()

    except Exception as exc:
        raise self.retry(exc=exc)


@celery_app.task(bind=True, max_retries=2)
def update_conversation_summary(self, conversation_id: str) -> None:
    """
    After every few messages, regenerates a short summary of the
    conversation for display in the sidebar. This is a non-streaming
    LLM call since summaries are background work.
    """
    conn = get_db_conn()
    try:
        with conn.cursor() as cur:
            # Only update summary every 5 complete assistant messages
            cur.execute(
                """
                SELECT COUNT(*) FROM messages
                WHERE conversation_id = %s
                  AND role = 'assistant'
                  AND is_complete = TRUE
                """,
                (conversation_id,),
            )
            count = cur.fetchone()[0]
            if count == 0 or count % 5 != 0:
                return

            # Pull last 10 turns for summarization context
            cur.execute(
                """
                SELECT role, content
                FROM messages
                WHERE conversation_id = %s
                  AND is_complete = TRUE
                  AND role IN ('user', 'assistant')
                ORDER BY created_at DESC
                LIMIT 10
                """,
                (conversation_id,),
            )
            rows = cur.fetchall()
            history = [
                {"role": r[0], "content": r[1]}
                for r in reversed(rows)
                if r[1]
            ]

            summary_prompt = [
                {
                    "role": "system",
                    "content": (
                        "Summarize the following conversation in one sentence, "
                        "capturing the main topic. Be concise and factual."
                    ),
                },
                *history,
            ]

            response = openai_client.chat.completions.create(
                model="gpt-4o-mini",
                messages=summary_prompt,
                max_tokens=60,
            )
            summary = response.choices[0].message.content.strip()

            cur.execute(
                """
                UPDATE conversations
                SET title = %s, updated_at = NOW()
                WHERE id = %s AND (title IS NULL OR title = '')
                """,
                (summary, conversation_id),
            )
            conn.commit()
    except Exception as exc:
        conn.rollback()
        raise self.retry(exc=exc)
    finally:
        conn.close()

29.5 Handling Interruptions, Partial Responses, and Retries

Real users close tabs. Networks hiccup. LLM APIs return 503s at inconvenient moments. Your streaming pipeline needs to survive all of this gracefully.

Detecting interrupted streams

A message row with stream_started_at set but is_complete = FALSE more than a few minutes old is almost certainly abandoned. A housekeeping job can detect and mark these:

-- PostgreSQL: find and mark stale incomplete streams
UPDATE messages
SET
    is_complete = TRUE,
    finish_reason = 'interrupted',
    stream_completed_at = NOW(),
    content = (
        -- Reconstruct what we got from the chunks table
        SELECT string_agg(chunk_content, '' ORDER BY chunk_index)
        FROM message_stream_chunks
        WHERE message_id = messages.id
    ),
    error = '{"reason": "stream_interrupted", "source": "housekeeping"}'::jsonb
WHERE
    is_complete = FALSE
    AND stream_started_at < NOW() - INTERVAL '5 minutes'
RETURNING id, conversation_id, stream_started_at;
-- SQL Server equivalent
UPDATE m
SET
    m.is_complete = 1,
    m.finish_reason = 'interrupted',
    m.stream_completed_at = SYSDATETIMEOFFSET(),
    m.content = (
        SELECT STRING_AGG(chunk_content, '' ORDER BY chunk_index)
        FROM message_stream_chunks msc
        WHERE msc.message_id = m.id
    ),
    m.error = '{"reason": "stream_interrupted", "source": "housekeeping"}'
FROM messages m
WHERE
    m.is_complete = 0
    AND m.stream_started_at < DATEADD(MINUTE, -5, SYSDATETIMEOFFSET())
OUTPUT inserted.id, inserted.conversation_id, inserted.stream_started_at;

Resume and replay from chunks

Because every chunk is durably stored in message_stream_chunks, you can reconstruct what arrived before an interruption:

async def reconstruct_partial_response(
    pool: asyncpg.Pool,
    message_id: str,
) -> str:
    """
    Reassembles accumulated content from chunk records.
    Useful for showing users what the model had generated
    before the connection dropped.
    """
    async with pool.acquire() as conn:
        rows = await conn.fetch(
            """
            SELECT chunk_content
            FROM message_stream_chunks
            WHERE message_id = $1
            ORDER BY chunk_index ASC
            """,
            message_id,
        )
    return "".join(row["chunk_content"] for row in rows)

Retry with exponential backoff for API errors

When the LLM API itself returns a transient error mid-stream, you want to retry from the beginning (since streaming APIs don't support resumption):

import asyncio
import random
from typing import AsyncGenerator

async def stream_with_retry(
    writer: StreamWriter,
    conversation_id: str,
    messages: list[dict],
    model: str = "gpt-4o",
    max_attempts: int = 3,
) -> AsyncGenerator[str, None]:
    """
    Wraps stream_and_persist with exponential backoff.
    On retry, creates a fresh message record — the failed
    attempt is left in the DB with finish_reason='error'.
    """
    base_delay = 1.0

    for attempt in range(max_attempts):
        try:
            async for token in writer.stream_and_persist(
                conversation_id=conversation_id,
                messages=messages,
                model=model,
            ):
                yield token
            return  # success
        except Exception as e:
            if attempt == max_attempts - 1:
                raise  # exhausted retries

            jitter = random.uniform(0, 0.5)
            delay = base_delay * (2 ** attempt) + jitter
            await asyncio.sleep(delay)

29.6 Logical Replication for Downstream Consumers

pg_notify works well for low-fan-out use cases: one or two background workers reacting to stream events. When you need many independent consumers — a monitoring dashboard, an audit pipeline, a real-time analytics system, a multi-tenant notification bus — logical replication gives you a durable, ordered, replayable event stream based on PostgreSQL's WAL.

Setting up a logical replication publication

-- PostgreSQL: create a publication for the streaming tables
-- Run as a superuser or a role with REPLICATION privilege

-- First, ensure the server is configured for logical replication
-- (already done in postgresql.conf: wal_level = logical)

CREATE PUBLICATION ai_stream_events
    FOR TABLE messages, message_stream_chunks
    WITH (publish = 'insert, update');

-- Verify
SELECT pubname, pubtables FROM pg_publication_tables
WHERE pubname = 'ai_stream_events';

Python consumer using pg_replication

        # a decoder library. This shows the structural pattern.

        await message.acknowledge()

Logical replication gives you something pg_notify cannot: persistence and replay. If your consumer goes down for an hour, it resumes from exactly where it left off — no events are lost. The trade-off is operational complexity: you need to manage replication slots, monitor slot lag (an unbounded lag will cause WAL accumulation and disk pressure), and handle the binary pgoutput protocol.

For most applications, the right answer is pg_notify for low-latency local signalling and a Debezium connector (or a managed CDC service) for durable fan-out to external systems. Debezium reads PostgreSQL's WAL and forwards events to Kafka, giving you the best of both worlds without writing your own pgoutput decoder.

29.7 Batched Writes and Performance Tuning

If your application handles thousands of concurrent streaming sessions, the message_stream_chunks table will accumulate inserts at high velocity. Three techniques manage this load:

1. Write-coalescing in the application layer

Instead of inserting every chunk individually, buffer chunks in memory for a short window (50–100ms) and write them in a single multi-row INSERT:

import asyncio
from collections import defaultdict
from typing import NamedTuple

class ChunkBuffer(NamedTuple):
    message_id: str
    chunk_index: int
    content: str
    raw: dict

class BatchedStreamWriter:
    """
    Buffers chunks in memory and flushes to PostgreSQL periodically.
    Reduces per-row INSERT overhead at high concurrency.
    """

    def __init__(self, pool: asyncpg.Pool, flush_interval: float = 0.1):
        self.pool = pool
        self.flush_interval = flush_interval
        self._buffer: list[ChunkBuffer] = []
        self._lock = asyncio.Lock()
        self._flush_task: asyncio.Task | None = None

    async def start(self) -> None:
        self._flush_task = asyncio.create_task(self._periodic_flush())

    async def stop(self) -> None:
        if self._flush_task:
            self._flush_task.cancel()
        await self._flush_now()  # drain remaining buffer

    async def add_chunk(
        self,
        message_id: str,
        chunk_index: int,
        content: str,
        raw: dict,
    ) -> None:
        async with self._lock:
            self._buffer.append(
                ChunkBuffer(message_id, chunk_index, content, raw)
            )

    async def _periodic_flush(self) -> None:
        while True:
            await asyncio.sleep(self.flush_interval)
            await self._flush_now()

    async def _flush_now(self) -> None:
        async with self._lock:
            if not self._buffer:
                return
            batch = self._buffer.copy()
            self._buffer.clear()

        if not batch:
            return

        async with self.pool.acquire() as conn:
            await conn.executemany(
                """
                INSERT INTO message_stream_chunks
                    (message_id, chunk_index, chunk_content, chunk_raw)
                VALUES ($1, $2, $3, $4)
                """,
                [
                    (c.message_id, c.chunk_index, c.content, json.dumps(c.raw))
                    for c in batch
                ],
            )

2. Partitioning message_stream_chunks by time

At scale, this table grows fast and the old data is rarely queried. Declarative partitioning lets you drop old partitions cheaply:

-- PostgreSQL: partition message_stream_chunks by week
CREATE TABLE message_stream_chunks (
    id              BIGSERIAL,
    message_id      UUID NOT NULL,
    chunk_index     INTEGER NOT NULL,
    chunk_content   TEXT NOT NULL,
    chunk_raw       JSONB NOT NULL,
    received_at     TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
) PARTITION BY RANGE (received_at);

-- Create partitions; automate this with pg_partman in production
CREATE TABLE message_stream_chunks_2025_w01
    PARTITION OF message_stream_chunks
    FOR VALUES FROM ('2025-01-01') TO ('2025-01-08');

CREATE TABLE message_stream_chunks_2025_w02
    PARTITION OF message_stream_chunks
    FOR VALUES FROM ('2025-01-08') TO ('2025-01-15');

-- Each partition gets its own index (created automatically if
-- the parent index was created with CREATE INDEX ... ON ONLY parent)
CREATE INDEX ON message_stream_chunks_2025_w01 (message_id, chunk_index);
CREATE INDEX ON message_stream_chunks_2025_w02 (message_id, chunk_index);

-- Drop old partitions without VACUUM overhead:
-- DROP TABLE message_stream_chunks_2024_w52;
-- SQL Server: equivalent with table partitioning
-- Create partition function and scheme first
CREATE PARTITION FUNCTION pf_stream_chunks_weekly (DATETIME2)
AS RANGE RIGHT FOR VALUES (
    '2025-01-08', '2025-01-15', '2025-01-22'
    -- add more boundaries as needed
);

CREATE PARTITION SCHEME ps_stream_chunks_weekly
AS PARTITION pf_stream_chunks_weekly
ALL TO ([PRIMARY]);   -- map all partitions to PRIMARY filegroup

CREATE TABLE message_stream_chunks (
    id              BIGINT IDENTITY(1,1),
    message_id      UNIQUEIDENTIFIER NOT NULL,
    chunk_index     INT NOT NULL,
    chunk_content   NVARCHAR(MAX) NOT NULL,
    chunk_raw       NVARCHAR(MAX) NOT NULL,  -- JSON
    received_at     DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
) ON ps_stream_chunks_weekly(received_at);

CREATE INDEX idx_msc_message ON message_stream_chunks(message_id, chunk_index)
ON ps_stream_chunks_weekly(received_at);

3. Retention policy and archival

Chunks are most valuable immediately after a stream completes — for debugging and billing reconciliation. After a week, the assembled content in messages is sufficient. Automate chunk archival with pg_cron or an external scheduler:

-- PostgreSQL: pg_cron job to archive old chunks to cold storage
-- (Assumes chunks older than 7 days are safe to delete since
-- messages.content already holds the assembled text.)

SELECT cron.schedule(
    'archive-old-stream-chunks',
    '0 3 * * *',   -- 3 AM daily
    $$
    DELETE FROM message_stream_chunks
    WHERE received_at < NOW() - INTERVAL '7 days';
    $$
);
-- SQL Server: equivalent with SQL Server Agent job
-- (Truncate the oldest partition instead of row-by-row DELETE for efficiency)
DECLARE @boundary DATETIME2 = DATEADD(DAY, -7, SYSUTCDATETIME());

-- Switch old partition to a staging table, then truncate it
-- (partition switching is metadata-only, so it's instant)
ALTER TABLE message_stream_chunks
SWITCH PARTITION 1 TO message_stream_chunks_archive PARTITION 1;

TRUNCATE TABLE message_stream_chunks_archive;

29.8 Observability: Tracking Stream Health in PostgreSQL

PostgreSQL can double as the observability store for your streaming pipeline. A few targeted queries give you real-time and historical health signals.

-- PostgreSQL: streaming pipeline health dashboard queries

-- 1. Active streams (currently in flight)
SELECT
    m.id          AS message_id,
    c.id          AS conversation_id,
    c.user_id,
    m.model,
    m.stream_started_at,
    EXTRACT(EPOCH FROM (NOW() - m.stream_started_at)) AS age_seconds,
    COUNT(msc.id) AS chunks_received
FROM messages m
JOIN conversations c ON c.id = m.conversation_id
LEFT JOIN message_stream_chunks msc ON msc.message_id = m.id
WHERE m.is_complete = FALSE
  AND m.stream_started_at > NOW() - INTERVAL '10 minutes'
GROUP BY m.id, c.id, c.user_id, m.model, m.stream_started_at
ORDER BY m.stream_started_at;

-- 2. Stream completion rate by model (last 24 hours)
SELECT
    model,
    COUNT(*)                                                         AS total_streams,
    COUNT(*) FILTER (WHERE finish_reason = 'stop')                  AS clean_completions,
    COUNT(*) FILTER (WHERE finish_reason = 'interrupted')           AS interrupted,
    COUNT(*) FILTER (WHERE error IS NOT NULL)                       AS errored,
    ROUND(
        100.0 * COUNT(*) FILTER (WHERE finish_reason = 'stop')
        / NULLIF(COUNT(*), 0), 2
    )                                                                AS completion_pct,
    AVG(token_count)::INTEGER                                       AS avg_tokens,
    PERCENTILE_CONT(0.5) WITHIN GROUP (
        ORDER BY EXTRACT(EPOCH FROM (stream_completed_at - stream_started_at))
    )                                                                AS p50_duration_s,
    PERCENTILE_CONT(0.95) WITHIN GROUP (
        ORDER BY EXTRACT(EPOCH FROM (stream_completed_at - stream_started_at))
    )                                                                AS p95_duration_s
FROM messages
WHERE role = 'assistant'
  AND stream_started_at > NOW() - INTERVAL '24 hours'
GROUP BY model
ORDER BY total_streams DESC;

-- 3. Token throughput — tokens per second per model
SELECT
    model,
    DATE_TRUNC('hour', stream_completed_at)                         AS hour,
    SUM(token_count)                                                 AS total_tokens,
    COUNT(*)                                                         AS message_count,
    ROUND(
        SUM(token_count) /
        NULLIF(
            SUM(EXTRACT(EPOCH FROM (stream_completed_at - stream_started_at))),
        0), 2
    )                                                                AS tokens_per_second
FROM messages
WHERE role = 'assistant'
  AND is_complete = TRUE
  AND stream_started_at > NOW() - INTERVAL '48 hours'
GROUP BY model, DATE_TRUNC('hour', stream_completed_at)
ORDER BY hour DESC, tokens_per_second DESC;

-- 4. Error breakdown
SELECT
    error->>'reason'  AS error_reason,
    COUNT(*)          AS occurrences,
    MAX(updated_at)   AS last_seen
FROM messages
WHERE error IS NOT NULL
  AND created_at > NOW() - INTERVAL '7 days'
GROUP BY error->>'reason'
ORDER BY occurrences DESC;
-- SQL Server equivalents

-- 1. Active streams
SELECT
    m.id          AS message_id,
    c.id          AS conversation_id,
    c.user_id,
    m.model,
    m.stream_started_at,
    DATEDIFF(SECOND, m.stream_started_at, SYSDATETIMEOFFSET()) AS age_seconds,
    COUNT(msc.id) AS chunks_received
FROM messages m
JOIN conversations c ON c.id = m.conversation_id
LEFT JOIN message_stream_chunks msc ON msc.message_id = m.id
WHERE m.is_complete = 0
  AND m.stream_started_at > DATEADD(MINUTE, -10, SYSDATETIMEOFFSET())
GROUP BY m.id, c.id, c.user_id, m.model, m.stream_started_at
ORDER BY m.stream_started_at;

-- 2. Stream completion rate by model (last 24 hours)
SELECT
    model,
    COUNT(*)                                                         AS total_streams,
    SUM(CASE WHEN finish_reason = 'stop' THEN 1 ELSE 0 END)        AS clean_completions,
    SUM(CASE WHEN finish_reason = 'interrupted' THEN 1 ELSE 0 END) AS interrupted,
    SUM(CASE WHEN error IS NOT NULL THEN 1 ELSE 0 END)             AS errored,
    ROUND(
        100.0 * SUM(CASE WHEN finish_reason = 'stop' THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*), 0), 2
    )                                                                AS completion_pct,
    AVG(token_count)                                                AS avg_tokens
FROM messages
WHERE role = 'assistant'
  AND stream_started_at > DATEADD(HOUR, -24, SYSDATETIMEOFFSET())
GROUP BY model
ORDER BY total_streams DESC;

These queries give you the raw material for a Grafana dashboard (or any metrics tool that can query PostgreSQL) without needing a separate time-series database for operational data. For high-cardinality metrics like per-second token throughput, you'd eventually outgrow SQL-level aggregation and reach for a dedicated metrics store — but for most applications, PostgreSQL holds the operational picture well.

29.9 End-to-End Wiring: Putting It Together

The following shows how all the pieces integrate in a minimal but production-structured application. The entry point is a FastAPI app with startup lifecycle management, the streaming path runs through StreamWriter, background work flows through Celery, and PostgreSQL sits at the center.

# main.py — application entry point
import asyncio
import logging
import os

import asyncpg
from fastapi import FastAPI
from contextlib import asynccontextmanager

from api.stream_endpoint import app as stream_router
from workers.stream_listener import run_listener

logger = logging.getLogger(__name__)

@asynccontextmanager
async def lifespan(application: FastAPI):
    # Startup: create the connection pool
    dsn = os.environ["DATABASE_URL"]
    application.state.pool = await asyncpg.create_pool(
        dsn,
        min_size=5,
        max_size=20,
        command_timeout=60,
    )
    logger.info("Database pool created")

    # Start the pg_notify listener as a background task
    listener_task = asyncio.create_task(run_listener(dsn))

    yield  # application runs

    # Shutdown: clean up
    listener_task.cancel()
    await application.state.pool.close()
    logger.info("Database pool closed")

app = FastAPI(lifespan=lifespan)
app.include_router(stream_router)

Key Takeaways

  • → **Stream first, write incrementally.** The `message_stream_chunks` table captures every delta durably, giving you a complete audit trail, billing-reconciliation data, and the ability to reconstruct partial responses after interruption — without blocking the streaming path.
  • → **Use a single persistent connection per stream.** Acquiring a new connection per chunk introduces latency and breaks under PgBouncer transaction-mode pooling. Hold one `asyncpg` connection for the full lifetime of a streaming session and release it only after finalization.
  • → **`pg_notify` for low-latency local signalling; logical replication for durable fan-out.** `pg_notify` is the right tool for a small number of co-located consumers that need sub-second reaction times. For external systems, Kafka integration via Debezium and PostgreSQL logical replication provides persistence, replay, and consumer independence.
  • → **Partition `message_stream_chunks` by time and enforce a retention policy.** Chunk data accumulates at high velocity in busy applications. Weekly partitions let you drop old data with a metadata-only operation rather than a slow DELETE, and a `pg_cron` job keeps disk usage bounded without touching the assembled `messages.content` that clients actually read.
  • → **PostgreSQL is your observability layer too.** The completion-rate, token-throughput, and error-breakdown queries in Section 29.8 give you a real-time operational picture without a separate time-series database. As traffic grows, these queries scale to a read replica or a materialized view before you need to reach for dedicated metrics infrastructure.
