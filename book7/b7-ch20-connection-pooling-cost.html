Chapter 20: Connection Pooling to Reduce Compute Overhead

Organizations running PostgreSQL on AWS RDS, Azure Database for PostgreSQL, or Cloud SQL routinely overpay for compute by 30–50% simply because each application thread holds a dedicated database connection whether it is actively executing a query or sitting idle. A db.r6g.2xlarge RDS instance running at $0.48/hour — $346/month — often spends the majority of its CPU cycles managing connection overhead rather than executing SQL. By deploying PgBouncer in transaction pooling mode in front of that instance, teams consistently reduce their active connection count from several hundred to fewer than fifty, which in turn allows them to right-size to a db.r6g.xlarge at $173/month — saving $173/month on a single instance without changing a line of application code. Across a fleet of ten such instances the annual saving reaches $20,760. This chapter covers how to diagnose connection waste, size a connection pool correctly, deploy and automate PgBouncer on each major cloud platform, and wire the entire operation into a scheduled cost-audit pipeline so savings are permanent rather than one-time.

---

Diagnosing Connection Overhead Before You Optimize

No optimization survives a budget review without a before-state baseline. Connection overhead manifests in three measurable ways: high max_connections utilization, elevated CPU on the database instance while query throughput is low, and spikes in pg_stat_activity showing processes in idle or idle in transaction state.

The following query exposes the exact distribution of connection states on a live PostgreSQL instance. Run it against every RDS or Cloud SQL instance in your fleet and export the results to a spreadsheet:

-- Connection state audit: run on each PostgreSQL instance
-- Identifies idle connections that are burning compute capacity
SELECT
    datname                          AS database_name,
    usename                          AS username,
    state,
    wait_event_type,
    wait_event,
    COUNT(*)                         AS connection_count,
    ROUND(COUNT(*) * 100.0
          / SUM(COUNT(*)) OVER (), 2) AS pct_of_total,
    MAX(EXTRACT(EPOCH FROM (NOW() - state_change))::INT)
                                     AS max_idle_seconds,
    AVG(EXTRACT(EPOCH FROM (NOW() - state_change))::INT)
                                     AS avg_idle_seconds
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()        -- exclude this monitoring session
GROUP BY datname, usename, state, wait_event_type, wait_event
ORDER BY connection_count DESC;

Interpret the output with these thresholds:

| Condition | Meaning | Action |

|---|---|---|

| idle > 40% of total | Application not releasing connections | Pool immediately |

| idle in transaction > 5% | Long transactions or ORM misuse | Fix ORM + Pool |

| max_idle_seconds > 300 | Connections parked for 5+ minutes | Reduce pool timeout |

| Total connections > 80% of max_connections | Near exhaustion | Pool + raise limit |

Pull the current max_connections ceiling and see how close you are to it:

-- Current connection ceiling vs. actual usage
SELECT
    'max_connections'                          AS name,
    setting::INT                               AS configured_value,
    (SELECT COUNT(*) FROM pg_stat_activity)    AS current_connections,
    ROUND(
        (SELECT COUNT(*) FROM pg_stat_activity)::NUMERIC
        / setting::INT * 100, 1
    )                                          AS utilization_pct
FROM pg_settings
WHERE name = 'max_connections';

On AWS RDS, cross-reference this data with CloudWatch. The metric DatabaseConnections sampled over 24 hours tells you peak and average. Pull it with the CLI so you can baseline before and after pooling:

"

When peak connections are high and mean CPU is below 20%, the instance is sized for connection overhead rather than query work. That gap is your cost recovery opportunity.

Sizing the Pool: The Math Behind Right-Sizing

The common mistake is deploying PgBouncer with default settings and calling it done. The pool size determines whether you can actually downsize the instance, and the instance determines the monthly bill. Get the math right first.

PostgreSQL performs best when the number of *active* (non-idle) connections does not exceed 2 × vCPU count. For a db.r6g.2xlarge (8 vCPUs), the optimal active connection count is 16. Every connection above that figure competes for the same CPU cores and increases context-switching overhead — you pay for a larger instance to manage connections, not to execute queries.

The PgBouncer pool target formula:

server_pool_size = 2 × vCPU_count_of_target_instance
max_client_conn  = peak_application_threads × safety_factor (1.25)

Example calculation for a migration from db.r6g.2xlarge to db.r6g.xlarge:

| Parameter | Before | After |

|---|---|---|

| Instance | db.r6g.2xlarge (8 vCPU) | db.r6g.xlarge (4 vCPU) |

| On-Demand price | $0.480/hr | $0.240/hr |

| Monthly cost | $346.56 | $172.80 |

| Monthly saving | — | $173.76 |

| max_connections on RDS | 5,000* | 2,500* |

| Application threads | 400 | 400 |

| PgBouncer default_pool_size | — | 8 |

| PgBouncer max_client_conn | — | 500 |

*RDS sets max_connections automatically based on instance RAM; values shown are illustrative.

The key insight: 400 application threads share 8 server-side connections. Each thread waits at most a few milliseconds for a connection in transaction pooling mode because transactions complete in tens of milliseconds on OLTP workloads. Average wait is negligible compared to the compute saving.

Before committing to a smaller instance, validate the pool size calculation against pg_stat_statements. The following query identifies the 95th-percentile query duration, which determines how long a server connection is held per transaction:

-- Estimate transaction duration from pg_stat_statements
-- This determines whether transaction pooling is safe and effective
SELECT
    LEFT(query, 80)                                           AS query_sample,
    calls,
    ROUND((total_exec_time / calls)::NUMERIC, 2)             AS avg_exec_ms,
    ROUND(
        PERCENTILE_CONT(0.95) WITHIN GROUP
        (ORDER BY total_exec_time / calls)
        OVER ()::NUMERIC, 2)                                  AS p95_exec_ms,
    ROUND((mean_exec_time)::NUMERIC, 2)                       AS mean_exec_ms,
    rows / calls                                              AS avg_rows_returned
FROM pg_stat_statements
WHERE calls > 100
  AND query NOT LIKE '%pg_stat%'   -- exclude monitoring queries
ORDER BY total_exec_time DESC
LIMIT 20;

If p95 query duration is under 100ms (typical for OLTP), transaction pooling is safe. If you see queries above 5,000ms regularly, those long-running queries will hold server connections and reduce the effectiveness of the pool — address query performance before right-sizing compute.

Deploying PgBouncer on Each Cloud Platform

PgBouncer sits between the application and the RDS/Cloud SQL instance. It multiplexes hundreds of client connections onto a small number of server connections. The deployment pattern differs slightly by cloud platform.

flowchart LR
    subgraph App["Application tier"]
        T1[Thread 1]
        T2[Thread 2]
        T3["... 400 threads"]
    end
    T1 & T2 & T3 --> PB["PgBouncer
(transaction pooling)"]
    PB --> S1[Server conn 1]
    PB --> S2[Server conn 2]
    PB --> S3["... 8 conns"]
    S1 & S2 & S3 --> DB[(RDS / Cloud SQL)]

*PgBouncer multiplexes hundreds of application threads onto a handful of server-side connections — this is what makes right-sizing the database instance itself possible.*

#### AWS: PgBouncer on EC2 or ECS

The lowest-latency placement for PgBouncer on AWS is an EC2 instance in the same Availability Zone as the primary RDS instance, or a Fargate task in ECS if you want managed infrastructure. A t3.small ($0.0208/hr, $15/month) handles tens of thousands of application connections with negligible CPU usage — it is purely I/O and memory bounded.

The following Bash script provisions PgBouncer on an Amazon Linux 2023 EC2 instance, configures it for transaction pooling, and registers it as a systemd service:

#!/bin/bash
# deploy_pgbouncer_aws.sh
# Installs and configures PgBouncer on Amazon Linux 2023
# Run as ec2-user with sudo privileges
# Requires: RDS endpoint, DB name, credentials in AWS Secrets Manager

set -euo pipefail

RDS_ENDPOINT="${RDS_ENDPOINT:?Set RDS_ENDPOINT environment variable}"
RDS_PORT="${RDS_PORT:-5432}"
DB_NAME="${DB_NAME:?Set DB_NAME environment variable}"
SECRET_ARN="${SECRET_ARN:?Set SECRET_ARN for Secrets Manager}"
PGBOUNCER_PORT=6432
POOL_SIZE="${POOL_SIZE:-16}"         # 2 × vCPU of target instance
MAX_CLIENT_CONN="${MAX_CLIENT_CONN:-500}"

echo "[1/6] Installing PgBouncer..."
sudo dnf install -y pgbouncer

echo "[2/6] Fetching credentials from Secrets Manager..."
SECRET=$(aws secretsmanager get-secret-value \
    --secret-id "$SECRET_ARN" \
    --query SecretString \
    --output text)
DB_USER=$(echo "$SECRET" | python3 -c "import sys,json; print(json.load(sys.stdin)['username'])")
DB_PASS=$(echo "$SECRET" | python3 -c "import sys,json; print(json.load(sys.stdin)['password'])")

echo "[3/6] Writing pgbouncer.ini..."
sudo tee /etc/pgbouncer/pgbouncer.ini > /dev/null << INIEOF
[databases]
${DB_NAME} = host=${RDS_ENDPOINT} port=${RDS_PORT} dbname=${DB_NAME}

[pgbouncer]
listen_addr          = 0.0.0.0
listen_port          = ${PGBOUNCER_PORT}
auth_type            = scram-sha-256
auth_file            = /etc/pgbouncer/userlist.txt

; TRANSACTION mode: connection returned to pool after each transaction
; This is the mode that enables compute right-sizing
pool_mode            = transaction

default_pool_size    = ${POOL_SIZE}
min_pool_size        = 2
reserve_pool_size    = 5
reserve_pool_timeout = 3
max_client_conn      = ${MAX_CLIENT_CONN}

; Connection hygiene — recycle idle server connections
server_idle_timeout  = 60
client_idle_timeout  = 300
server_lifetime      = 3600

; Logging for cost audit trail
log_connections      = 1
log_disconnections   = 1
stats_period         = 60

; TLS toward RDS
server_tls_sslmode   = require

; Admin interface — restrict to localhost
admin_users          = pgbouncer_admin
stats_users          = pgbouncer_stats
INIEOF

echo "[4/6] Writing userlist.txt..."
# PgBouncer needs MD5 or SCRAM hashes; use pg_shadow query for production
# For initial setup, write plaintext and migrate to scram-sha-256 hashes
sudo tee /etc/pgbouncer/userlist.txt > /dev/null << USEREOF
"${DB_USER}" "${DB_PASS}"
"pgbouncer_admin" "changeme_admin_pw"
"pgbouncer_stats" "changeme_stats_pw"
USEREOF
sudo chmod 600 /etc/pgbouncer/userlist.txt
sudo chown pgbouncer:pgbouncer /etc/pgbouncer/userlist.txt

echo "[5/6] Enabling and starting systemd service..."
sudo systemctl enable pgbouncer
sudo systemctl restart pgbouncer
sudo systemctl status pgbouncer --no-pager

echo "[6/6] Verification..."
echo "Connecting to PgBouncer admin interface..."
PGPASSWORD="changeme_admin_pw" psql \
    -h 127.0.0.1 -p $PGBOUNCER_PORT \
    -U pgbouncer_admin pgbouncer \
    -c "SHOW POOLS;" \
    -c "SHOW STATS;" \
    -c "SHOW CONFIG;" 2>&1 | head -60

echo ""
echo "=== Deployment complete ==="
echo "Application connection string:"
echo "  host=<this-ec2-ip> port=${PGBOUNCER_PORT} dbname=${DB_NAME} user=${DB_USER}"
echo ""
echo "Next step: update application connection strings, then right-size RDS instance."

#### Azure: PgBouncer Built-In vs. Sidecar

Azure Database for PostgreSQL Flexible Server includes PgBouncer as a built-in feature — enable it with a single CLI command at no additional cost:

#!/bin/bash
# enable_pgbouncer_azure.sh
# Enables built-in PgBouncer on Azure Database for PostgreSQL Flexible Server
# Requires: az CLI logged in, Contributor role on the server resource

RESOURCE_GROUP="${RESOURCE_GROUP:?Set RESOURCE_GROUP}"
SERVER_NAME="${SERVER_NAME:?Set SERVER_NAME}"
SUBSCRIPTION="${SUBSCRIPTION:-$(az account show --query id -o tsv)}"

echo "=== Enabling PgBouncer on Azure PostgreSQL Flexible Server ==="
echo "Server      : $SERVER_NAME"
echo "Resource Grp: $RESOURCE_GROUP"

# Enable the pgbouncer extension and set pool parameters
az postgres flexible-server parameter set \
    --resource-group "$RESOURCE_GROUP" \
    --server-name    "$SERVER_NAME" \
    --name           "pgbouncer.enabled" \
    --value          "true"

az postgres flexible-server parameter set \
    --resource-group "$RESOURCE_GROUP" \
    --server-name    "$SERVER_NAME" \
    --name           "pgbouncer.default_pool_size" \
    --value          "16"

az postgres flexible-server parameter set \
    --resource-group "$RESOURCE_GROUP" \
    --server-name    "$SERVER_NAME" \
    --name           "pgbouncer.max_client_conn" \
    --value          "500"

az postgres flexible-server parameter set \
    --resource-group "$RESOURCE_GROUP" \
    --server-name    "$SERVER_NAME" \
    --name           "pgbouncer.pool_mode" \
    --value          "transaction"

az postgres flexible-server parameter set \
    --resource-group "$RESOURCE_GROUP" \
    --server-name    "$SERVER_NAME" \
    --name           "pgbouncer.server_idle_timeout" \
    --value          "60"

echo ""
echo "=== Verifying PgBouncer status ==="
az postgres flexible-server parameter list \
    --resource-group "$RESOURCE_GROUP" \
    --server-name    "$SERVER_NAME" \
    --query          "[?starts_with(name, 'pgbouncer')]" \
    --output         table

echo ""
echo "=== PgBouncer connection endpoint ==="
SERVER_FQDN=$(az postgres flexible-server show \
    --resource-group "$RESOURCE_GROUP" \
    --name           "$SERVER_NAME" \
    --query          "fullyQualifiedDomainName" \
    --output         tsv)

echo "Standard port (direct) : ${SERVER_FQDN}:5432"
echo "PgBouncer port         : ${SERVER_FQDN}:6432"
echo ""
echo "Update application connection strings to port 6432."
echo "Monitor via Azure Monitor metric: active_connections"

For Google Cloud SQL, the native proxy (cloud-sql-proxy) handles authentication but does not pool connections. Deploy PgBouncer as a Cloud Run sidecar or on a single e2-micro ($0.0084/hr, $6/month) in the same region.

Measuring the Cost Impact and Automating Continuous Monitoring

Deploying PgBouncer is a one-time action. The ongoing value comes from continuously verifying that pooling efficiency is maintained as the application evolves — new features often add new connection patterns that erode pool efficiency over time. The following Python script runs on a cron schedule, compares current connection behavior against a stored baseline, and posts an alert to Slack when efficiency drops below threshold. It also queries the AWS Cost Explorer API to correlate connection count changes with actual spend.

#!/usr/bin/env python3
"""
pgbouncer_cost_monitor.py

Scheduled cost-efficiency monitor for PgBouncer deployments.
Queries PgBouncer admin interface + AWS Cost Explorer and reports
on connection efficiency and compute cost trends.

Schedule: run every 6 hours via cron or EventBridge Scheduler
  0 */6 * * * /usr/bin/python3 /opt/dba-tools/pgbouncer_cost_monitor.py

Dependencies: psycopg2, boto3, requests
  pip install psycopg2-binary boto3 requests
"""

import os
import json
import datetime
import psycopg2
import boto3
import requests
from dataclasses import dataclass, asdict
from typing import Optional

# ── Configuration ────────────────────────────────────────────────────────────
PGBOUNCER_HOST  = os.environ.get("PGBOUNCER_HOST", "127.0.0.1")
PGBOUNCER_PORT  = int(os.environ.get("PGBOUNCER_PORT", 6432))
PGBOUNCER_ADMIN = os.environ.get("PGBOUNCER_ADMIN_USER", "pgbouncer_admin")
PGBOUNCER_PASS  = os.environ.get("PGBOUNCER_ADMIN_PASS")

AWS_REGION      = os.environ.get("AWS_REGION", "us-east-1")
RDS_INSTANCE_ID = os.environ.get("RDS_INSTANCE_ID")       # for Cost Explorer filter
SLACK_WEBHOOK   = os.environ.get("SLACK_WEBHOOK_URL")      # optional

EFFICIENCY_THRESHOLD = 0.30   # alert if server_conn / cl_active drops below 30%
IDLE_RATIO_THRESHOLD = 0.50   # alert if idle client ratio exceeds 50%

# ── Data classes ─────────────────────────────────────────────────────────────
@dataclass
class PoolStats:
    database:       str
    cl_active:      int    # active client connections
    cl_waiting:     int    # clients waiting for a server connection
    sv_active:      int    # active server connections
    sv_idle:        int    # idle server connections
    sv_used:        int    # server connections used and returned to pool
    maxwait:        int    # longest wait time (seconds)
    pool_mode:      str

@dataclass
class CostReport:
    period_start:       str
    period_end:         str
    rds_compute_cost:   float
    currency:           str
    instance_id:        str

# ── PgBouncer queries ────────────────────────────────────────────────────────
def get_pool_stats(host: str, port: int, user: str, password: str) -> list[PoolStats]:
    """Query PgBouncer admin interface for current pool statistics."""
    conn = psycopg2.connect(
        host=host, port=port,
        user=user, password=password,
        dbname="pgbouncer",
        connect_timeout=5
    )
    conn.autocommit = True
    cur = conn.cursor()
    cur.execute("SHOW POOLS;")
    cols = [desc[0] for desc in cur.description]
    rows = cur.fetchall()
    cur.close()
    conn.close()

    stats = []
    for row in rows:
        row_dict = dict(zip(cols, row))
        stats.append(PoolStats(
            database   = row_dict.get("database", ""),
            cl_active  = int(row_dict.get("cl_active",  0)),
            cl_waiting = int(row_dict.get("cl_waiting", 0)),
            sv_active  = int(row_dict.get("sv_active",  0)),
            sv_idle    = int(row_dict.get("sv_idle",    0)),
            sv_used    = int(row_dict.get("sv_used",    0)),
            maxwait    = int(row_dict.get("maxwait",    0)),
            pool_mode  = row_dict.get("pool_mode", ""),
        ))
    return stats


def get_global_stats(host: str, port: int, user: str, password: str) -> dict:
    """Query SHOW STATS for aggregate throughput and timing metrics."""
    conn = psycopg2.connect(
        host=host, port=port,
        user=user, password=password,
        dbname="pgbouncer",
        connect_timeout=5
    )
    conn.autocommit = True
    cur = conn.cursor()
    cur.execute("SHOW STATS;")
    cols = [desc[0] for desc in cur.description]
    rows = cur.fetchall()
    cur.close()
    conn.close()
    return [dict(zip(cols, row)) for row in rows]


# ── AWS Cost Explorer ─────────────────────────────────────────────────────────
def get_rds_cost_last_30_days(instance_id: Optional[str]) -> Optional[CostReport]:
    """Fetch RDS compute spend for the last 30 days from Cost Explorer."""
    if not instance_id:
        return None

    ce = boto3.client("ce", region_name="us-east-1")   # CE is global; always us-east-1
    end   = datetime.date.today()
    start = end - datetime.timedelta(days=30)

    try:
        response = ce.get_cost_and_usage(
            TimePeriod={"Start": start.isoformat(), "End": end.isoformat()},
            Granularity="MONTHLY",
            Filter={
                "And": [
                    {"Dimensions": {"Key": "SERVICE",
                                    "Values": ["Amazon Relational Database Service"]}},
                    {"Dimensions": {"Key": "RESOURCE_ID",
                                    "Values": [instance_id]}},
                ]
            },
            Metrics=["UnblendedCost"],
        )
        total = sum(
            float(p["Total"]["UnblendedCost"]["Amount"])
            for p in response["ResultsByTime"]
        )
        currency = response["ResultsByTime"][0]["Total"]["UnblendedCost"]["Unit"] \
            if response["ResultsByTime"] else "USD"
        return CostReport(
            period_start     = start.isoformat(),
            period_end       = end.isoformat(),
            rds_compute_cost = round(total, 2),
            currency         = currency,
            instance_id      = instance_id,
        )
    except Exception as exc:
        print(f"[WARN] Cost Explorer query failed: {exc}")
        return None


# ── Analysis ──────────────────────────────────────────────────────────────────
def analyze_pools(stats: list[PoolStats]) -> dict:
    """
    Compute efficiency ratios and flag pools that need attention.
    Returns a dict with aggregate metrics and a list of alerts.
    """
    alerts = []
    total_cl_active  = sum(s.cl_active  for s in stats)
    total_sv_active  = sum(s.sv_active  for s in stats)
    total_sv_idle    = sum(s.sv_idle    for s in stats)
    total_cl_waiting = sum(s.cl_waiting for s in stats)

    # Multiplexing ratio: how many client connections share one server connection
    if total_sv_active > 0:
        mux_ratio = round(total_cl_active / total_sv_active, 1)
    else:
        mux_ratio = 0.0

    # Server utilization: fraction of server connections that are active vs. idle
    total_sv = total_sv_active + total_sv_idle
    sv_utilization = round(total_sv_active / total_sv, 2) if total_sv > 0 else 0.0

    for s in stats:
        sv_total = s.sv_active + s.sv_idle
        if sv_total == 0:
            continue
        efficiency = s.sv_active / sv_total
        if efficiency < EFFICIENCY_THRESHOLD:
            alerts.append({
                "level":   "WARNING",
                "database": s.database,
                "message": (
                    f"Pool efficiency {efficiency:.0%} is below threshold "
                    f"{EFFICIENCY_THRESHOLD:.0%}. "
                    f"sv_idle={s.sv_idle}, sv_active={s.sv_active}. "
                    "Consider reducing default_pool_size."
                ),
            })
        if s.maxwait > 5:
            alerts.append({
                "level":    "CRITICAL",
                "database": s.database,
                "message": (
                    f"Clients waiting {s.maxwait}s for a server connection. "
                    "Pool is undersized — increase default_pool_size or "
                    "right-size the target instance upward."
                ),
            })
        if s.cl_waiting > 0:
            alerts.append({
                "level":    "WARNING",
                "database": s.database,
                "message": (
                    f"{s.cl_waiting} client(s) currently queued for a server "
                    "connection. Investigate query duration or increase pool size."
                ),
            })

    return {
        "timestamp":        datetime.datetime.utcnow().isoformat() + "Z",
        "total_cl_active":  total_cl_active,
        "total_sv_active":  total_sv_active,
        "total_sv_idle":    total_sv_idle,
        "total_cl_waiting": total_cl_waiting,
        "mux_ratio":        mux_ratio,
        "sv_utilization":   sv_utilization,
        "alerts":           alerts,
        "pool_detail":      [asdict(s) for s in stats],
    }


# ── Slack notification ────────────────────────────────────────────────────────
def post_slack(webhook_url: str, report: dict, cost: Optional[CostReport]) -> None:
    """Format and post a summary to a Slack webhook."""
    alert_lines = "\n".join(
        f"• [{a['level']}] {a['database']}: {a['message']}"
        for a in report["alerts"]
    ) or "• No alerts — pool operating within thresholds."

    cost_line = (
        f"RDS compute cost last 30 days: "
        f"{cost.currency} {cost.rds_compute_cost:,.2f} "
        f"(instance: {cost.instance_id})"
        if cost else "Cost Explorer data unavailable."
    )

    text = (
        f"*PgBouncer Cost Monitor — {report['timestamp']}*\n"
        f"Multiplexing ratio  : {report['mux_ratio']}:1 "
        f"(client connections per server connection)\n"
        f"Server utilization  : {report['sv_utilization']:.0%}\n"
        f"Clients waiting now : {report['total_cl_waiting']}\n"
        f"{cost_line}\n\n"
        f"*Alerts*\n{alert_lines}"
    )
    payload = {"text": text}
    try:
        resp = requests.post(webhook_url, json=payload, timeout=10)
        resp.raise_for_status()
    except Exception as exc:
        print(f"[WARN] Slack notification failed: {exc}")


# ── Main ──────────────────────────────────────────────────────────────────────
def main():
    print(f"[{datetime.datetime.utcnow().isoformat()}Z] PgBouncer cost monitor starting...")

    # 1. Pull pool stats
    pool_stats = get_pool_stats(
        PGBOUNCER_HOST, PGBOUNCER_PORT,
        PGBOUNCER_ADMIN, PGBOUNCER_PASS
    )
    global_stats = get_global_stats(
        PGBOUNCER_HOST, PGBOUNCER_PORT,
        PGBOUNCER_ADMIN, PGBOUNCER_PASS
    )

    # 2. Analyse
    report = analyze_pools(pool_stats)

    # 3. Pull cost data
    cost_report = get_rds_cost_last_30_days(RDS_INSTANCE_ID)

    # 4. Print structured JSON to stdout (captured by CloudWatch Logs or similar)
    output = {
        "pool_report":  report,
        "cost_report":  asdict(cost_report) if cost_report else None,
        "global_stats": global_stats,
    }
    print(json.dumps(output, indent=2, default=str))

    # 5. Alert via Slack if configured
    if SLACK_WEBHOOK:
        post_slack(SLACK_WEBHOOK, report, cost_report)

    # 6. Exit non-zero if critical alerts exist so cron can trigger further alerting
    critical = [a for a in report["alerts"] if a["level"] == "CRITICAL"]
    if critical:
        print(f"[ERROR] {len(critical)} CRITICAL alert(s) detected. Exiting 1.")
        raise SystemExit(1)

    print("Monitor run complete — no critical issues.")


if __name__ == "__main__":
    main()

Validating the Right-Sizing Decision Before Executing It

Committing to a smaller instance class carries risk. The following checklist, implemented as a Bash validation script, guards against the most common failure modes before you modify the instance in production.

#!/bin/bash
# validate_rightsize.sh
# Pre-flight checks before right-sizing an RDS instance behind PgBouncer
# Run this script and review all outputs before modifying the instance class.

set -euo pipefail

INSTANCE_ID="${1:?Usage: $0 <db-instance-id> <region> <target-class>}"
REGION="${2:-us-east-1}"
TARGET_CLASS="${3:?Provide target instance class, e.g. db.r6g.xlarge}"

PGB_HOST="${PGBOUNCER_HOST:-127.0.0.1}"
PGB_PORT="${PGBOUNCER_PORT:-6432}"
PGB_ADMIN="${PGBOUNCER_ADMIN_USER:-pgbouncer_admin}"
PGB_PASS="${PGBOUNCER_ADMIN_PASS:?Set PGBOUNCER_ADMIN_PASS}"

PASS=0
FAIL=0
WARN=0

check() {
    local label="$1" result="$2" expected="$3" severity="${4:-FAIL}"
    if [ "$result" = "$expected" ]; then
        echo "  [PASS] $label"
        PASS=$((PASS+1))
    else
        echo "  [$severity] $label (got: $result, expected: $expected)"
        [ "$severity" = "FAIL" ] && FAIL=$((FAIL+1)) || WARN=$((WARN+1))
    fi
}

echo "============================================================"
echo " Pre-flight validation: $INSTANCE_ID → $TARGET_CLASS"
echo " Region: $REGION"
echo " $(date -u)"
echo "============================================================"

# ── Check 1: PgBouncer is running and reachable ───────────────────────────────
echo ""
echo "--- Check 1: PgBouncer availability ---"
PGB_UP=$(PGPASSWORD="$PGB_PASS" psql \
    -h "$PGB_HOST" -p "$PGB_PORT" -U "$PGB_ADMIN" pgbouncer \
    -c "SHOW VERSION;" -tA 2>/dev/null | head -1 | grep -c "PgBouncer" || echo "0")
check "PgBouncer reachable" "$PGB_UP" "1"

# ── Check 2: Pool mode is transaction ────────────────────────────────────────
echo ""
echo "--- Check 2: Pool mode ---"
POOL_MODE=$(PGPASSWORD="$PGB_PASS" psql \
    -h "$PGB_HOST" -p "$PGB_PORT" -U "$PGB_ADMIN" pgbouncer \
    -c "SHOW CONFIG;" -tA 2>/dev/null \
    | grep "^pool_mode" | awk -F'|' '{print $2}' | tr -d ' ')
check "pool_mode=transaction" "$POOL_MODE" "transaction"

# ── Check 3: No clients currently waiting ────────────────────────────────────
echo ""
echo "--- Check 3: Client wait queue ---"
CL_WAITING=$(PGPASSWORD="$PGB_PASS" psql \
    -h "$PGB_HOST" -p "$PGB_PORT" -U "$PGB_ADMIN" pgbouncer \
    -c "SHOW POOLS;" -tA 2>/dev/null \
    | awk -F'|' '{sum += $5} END {print sum+0}')
check "No clients waiting (cl_waiting=0)" "$CL_WAITING" "0" "WARN"

# ── Check 4: Server connection count fits target instance ────────────────────
echo ""
echo "--- Check 4: Server connection headroom ---"
SV_ACTIVE=$(PGPASSWORD="$PGB_PASS" psql \
    -h "$PGB_HOST" -p "$PGB_PORT" -U "$PGB_ADMIN" pgbouncer \
    -c "SHOW POOLS;" -tA 2>/dev/null \
    | awk -F'|' '{sum += $3} END {print sum+0}')
# Extract vCPU count from target instance class name (r6g.xlarge = 4, r6g.2xlarge = 8)
TARGET_VCPU=$(aws ec2 describe-instance-types \
    --instance-types "${TARGET_CLASS/db./}" \
    --query "InstanceTypes[0].VCpuInfo.DefaultVCpus" \
    --output text --region "$REGION" 2>/dev/null || echo "4")
RECOMMENDED_POOL=$((TARGET_VCPU * 2))
HEADROOM=$(( RECOMMENDED_POOL - SV_ACTIVE ))
if [ "$HEADROOM" -ge 0 ]; then
    echo "  [PASS] sv_active=$SV_ACTIVE ≤ recommended pool size=$RECOMMENDED_POOL for $TARGET_CLASS (${TARGET_VCPU} vCPU)"
    PASS=$((PASS+1))
else
    echo "  [FAIL] sv_active=$SV_ACTIVE exceeds recommended pool size=$RECOMMENDED_POOL — reduce default_pool_size first"
    FAIL=$((FAIL+1))
fi

# ── Check 5: RDS CPU not saturated at current workload ────────────────────────
echo ""
echo "--- Check 5: Current RDS CPU utilization (last 30 minutes) ---"
PEAK_CPU=$(aws cloudwatch get-metric-statistics \
    --region "$REGION" \
    --namespace AWS/RDS \
    --metric-name CPUUtilization \
    --dimensions Name=DBInstanceIdentifier,Value="$INSTANCE_ID" \
    --start-time "$(date -u -d '30 minutes ago' '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null \
                  || date -u -v-30M '+%Y-%m-%dT%H:%M:%SZ')" \
    --end-time "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
    --period 300 \
    --statistics Maximum \
    --output json \
    | python3 -c "
import sys, json
d = json.load(sys.stdin)
pts = d.get('Datapoints', [])
print(f'{max((p[\"Maximum\"] for p in pts), default=0):.1f}')
")
# Safe to right-size if peak CPU on current (larger) instance is below 40%
# because the smaller instance will have proportionally fewer vCPUs
CPU_OK=$(python3 -c "print('yes' if float('${PEAK_CPU}') < 40.0 else 'no')")
check "Peak CPU < 40% (current workload safe for smaller instance)" "$CPU_OK" "yes"
echo "  Peak CPU last 30 min: ${PEAK_CPU}%"

# ── Check 6: No long-running transactions ────────────────────────────────────
echo ""
echo "--- Check 6: Long-running transactions on RDS ---"
# Connect directly to RDS for this check (bypasses PgBouncer)
RDS_ENDPOINT=$(aws rds describe-db-instances \
    --db-instance-identifier "$INSTANCE_ID" \
    --region "$REGION" \
    --query "DBInstances[0].Endpoint.Address" \
    --output text 2>/dev/null || echo "")

if [ -n "$RDS_ENDPOINT" ] && [ -n "${PGPASSWORD:-}" ]; then
    LONG_TXN=$(psql "host=$RDS_ENDPOINT port=5432 sslmode=require" \
        -c "SELECT COUNT(*) FROM pg_stat_activity
            WHERE state = 'idle in transaction'
              AND EXTRACT(EPOCH FROM (NOW() - xact_start)) > 60;" \
        -tA 2>/dev/null || echo "0")
    check "No long idle-in-transaction (>60s)" "$LONG_TXN" "0" "WARN"
else
    echo "  [SKIP] RDS direct connection not available for long-txn check"
    WARN=$((WARN+1))
fi

# ── Summary ──────────────────────────────────────────────────────────────────
echo ""
echo "============================================================"
echo " Validation summary"
echo "   PASS : $PASS"
echo "   WARN : $WARN"
echo "   FAIL : $FAIL"
echo "============================================================"

if [ "$FAIL" -gt 0 ]; then
    echo ""
    echo "ACTION REQUIRED: $FAIL check(s) failed."
    echo "Resolve failures before modifying the instance class."
    exit 1
elif [ "$WARN" -gt 0 ]; then
    echo ""
    echo "WARNINGS present: $WARN check(s). Review before proceeding."
    echo "Right-sizing is likely safe but review each warning above."
    exit 0
else
    echo ""
    echo "All checks passed. Safe to proceed with right-sizing:"
    echo ""
    echo "  aws rds modify-db-instance \\"
    echo "      --db-instance-identifier $INSTANCE_ID \\"
    echo "      --db-instance-class $TARGET_CLASS \\"
    echo "      --apply-immediately \\"
    echo "      --region $REGION"
    echo ""
    echo "Estimated monthly saving:"
    aws rds describe-db-instances \
        --db-instance-identifier "$INSTANCE_ID" \
        --region "$REGION" \
        --query "DBInstances[0].DBInstanceClass" \
        --output text 2>/dev/null \
        | xargs -I{} echo "  Current class: {} → Target: $TARGET_CLASS"
    exit 0
fi

Run the validation script at least one full business day before executing the instance modification. If it exits 0 and all checks pass, issue the aws rds modify-db-instance command during a maintenance window or low-traffic period.

Extending the Pattern to Azure SQL and SQL Server

Azure SQL Database and SQL Server on RDS manage connections differently from PostgreSQL. They use a thread-based architecture where each connection consumes roughly 7–8 MB of memory and a small CPU overhead. The equivalent optimization is connection pool management at the application layer via ADO.NET, JDBC, or SQLAlchemy connection pool settings, not an external proxy.

The diagnostic query for SQL Server shows idle connection distribution in the same way the PostgreSQL query does:

-- SQL Server: connection state audit
-- Identifies idle sessions and their resource consumption
-- Run on Azure SQL Database or SQL Server on RDS
SELECT
    s.session_id,
    s.status,
    s.login_name,
    s.host_name,
    s.program_name,
    DB_NAME(s.database_id)                              AS database_name,
    s.cpu_time                                          AS cpu_time_ms,
    s.memory_usage * 8                                  AS memory_kb,
    s.reads,
    s.writes,
    DATEDIFF(SECOND, s.last_request_end_time, GETUTCDATE())
                                                        AS idle_seconds,
    r.command                                           AS active_command,
    r.wait_type,
    r.blocking_session_id
FROM sys.dm_exec_sessions  s
LEFT JOIN sys.dm_exec_requests r ON r.session_id = s.session_id
WHERE s.is_user_process = 1
  AND s.session_id <> @@SPID
ORDER BY idle_seconds DESC;

The SQL Server equivalent of pooling analysis focuses on idle seconds and memory consumption per session. Sessions idle for more than 300 seconds while consuming memory are candidates for pool timeout reduction in the application tier. The corresponding PostgreSQL diagnostic was shown earlier in this chapter; the two queries paired serve as your cross-platform connection audit toolkit.

For Azure SQL specifically, pull the DTU or vCore consumption alongside connection counts using the built-in DMV:

-- Azure SQL: vCore / DTU consumption correlated with active connections
-- Run on Azure SQL Database (not on-premise SQL Server)
SELECT
    end_time,
    avg_cpu_percent,
    avg_data_io_percent,
    avg_log_write_percent,
    max_session_percent,
    max_worker_percent,
    avg_memory_usage_percent,
    -- Derived: sessions as a fraction of the tier limit
    max_session_percent / 100.0 * 30000   AS estimated_sessions  -- 30000 = General Purpose limit
FROM sys.dm_db_resource_stats
ORDER BY end_time DESC
OFFSET 0 ROWS FETCH NEXT 96 ROWS ONLY;  -- last 24 hours at 15-minute intervals

When max_session_percent is consistently below 20% and avg_cpu_percent is below 20%, the Azure SQL tier is oversized relative to actual workload and connection count. The right-sizing action on Azure SQL is to reduce the vCore count or move from General Purpose to a lower service tier — the connection pool on the application side limits the effective session demand, enabling the downsize just as PgBouncer does for PostgreSQL.

---

Key Takeaways

  • → **Diagnose before deploying**: use `pg_stat_activity` (PostgreSQL) or `sys.dm_exec_sessions` (SQL Server / Azure SQL) to quantify idle connections and establish a before-state baseline; optimization without measurement is guesswork that cannot survive a budget review.
  • → **Size the pool with math, not defaults**: set `default_pool_size` to 2 × vCPU of the *target* (smaller) instance, and set `max_client_conn` to 1.25 × peak application thread count; this arithmetic directly determines which instance class becomes feasible and therefore which monthly bill becomes achievable.
  • → **Transaction pooling mode unlocks the largest savings**: session pooling returns a connection to the pool only when the client disconnects, which provides minimal multiplexing; transaction pooling returns the server connection after every commit, multiplexing hundreds of client threads onto a handful of server connections and enabling the compute right-sizing that drives cost reduction.
  • → **Automate continuous verification**: pool efficiency degrades silently as applications evolve — new ORMs, new services, and new query patterns all introduce connection behavior that can erode multiplexing ratios; the scheduled monitor script in this chapter detects degradation and correlates it with actual AWS Cost Explorer spend before the next billing cycle closes.
  • → **The pattern generalizes across clouds**: PgBouncer on EC2 or ECS for AWS RDS, the built-in PgBouncer feature on Azure Database for PostgreSQL Flexible Server, and a Cloud Run or Compute Engine sidecar for Google Cloud SQL all implement the same multiplexing principle; for SQL Server and Azure SQL the equivalent lever is application-tier connection pool tuning surfaced through `sys.dm_exec_sessions` and `sys.dm_db_resource_stats` rather than an external proxy.
