Chapter 27 of 40 The Cloud Database Engineer

Chapter 27: Hybrid Cloud: On-Premises and Cloud Together

Most production environments do not migrate to the cloud in a single weekend. They live in the space between — some databases running on-premises in your data center, some running in RDS or Azure SQL or Cloud SQL, and the two worlds needing to communicate as if the network boundary does not exist. This chapter is about that in-between state: how to architect it correctly, how to keep data synchronized across boundaries, how to handle failover and latency, and how to run hybrid configurations in production without turning them into a maintenance nightmare. If you are three months into a cloud migration and still have seventeen on-premises SQL Server instances feeding data to Azure SQL, this chapter is written for your situation.

---

27.1 Network Architecture: Connecting Your Data Center to the Cloud

The foundation of any hybrid database architecture is the network. Before a single row of data moves between your on-premises PostgreSQL instance and RDS, before DMS can reach your source database, and before an application server in AWS can query your on-premises Oracle, the network path must be stable, low-latency, and secured. This is not optional plumbing — it is the structural prerequisite that determines whether your hybrid architecture works or falls apart under production load.

#### The Two Options: VPN vs. Direct Connect (and Their Azure/GCP Equivalents)

AWS gives you two primary options for connecting on-premises infrastructure to your VPC: AWS Site-to-Site VPN and AWS Direct Connect.

Site-to-Site VPN runs over the public internet, uses IPSec encryption, and is inexpensive to set up. Bandwidth is limited to approximately 1.25 Gbps per tunnel, latency is variable (typically 20–100ms depending on geography and ISP), and it is prone to jitter. For database replication where your logs are small and your RPO tolerance is measured in minutes, VPN is acceptable. For bulk migration of a 20 TB database or for real-time streaming replication where lag matters in seconds, VPN will create problems.

AWS Direct Connect provides a dedicated physical connection from your data center to an AWS Direct Connect location. It delivers 1 Gbps, 10 Gbps, or 100 Gbps connections with consistent latency (typically 2–10ms from most data centers to a nearby AWS region). You pay for port hours and data transfer, but you eliminate the jitter and bandwidth contention of internet-based VPN. For production hybrid database architectures where you are replicating continuously or running applications that span on-premises and cloud, Direct Connect is the correct choice.

Azure's equivalents are Azure VPN Gateway (VPN) and Azure ExpressRoute (dedicated circuit). GCP offers Cloud VPN and Cloud Interconnect (Dedicated or Partner). The architectural decisions are identical regardless of cloud provider — VPN for non-critical or low-bandwidth scenarios, dedicated connectivity for production.

#### Setting Up an AWS Site-to-Site VPN to Your Data Center

# Step 1: Create a Customer Gateway representing your on-premises VPN device
aws ec2 create-customer-gateway \
  --type ipsec.1 \
  --public-ip 203.0.113.12 \
  --bgp-asn 65000 \
  --region us-east-1 \
  --tag-specifications 'ResourceType=customer-gateway,Tags=[{Key=Name,Value=datacenter-primary}]'

# Step 2: Create a Virtual Private Gateway and attach it to your VPC
aws ec2 create-vpn-gateway \
  --type ipsec.1 \
  --amazon-side-asn 64512 \
  --region us-east-1

# Capture the VpnGatewayId from the output, then attach
aws ec2 attach-vpn-gateway \
  --vpn-gateway-id vgw-0abc123def456789a \
  --vpc-id vpc-0123456789abcdef0

# Step 3: Create the Site-to-Site VPN connection
aws ec2 create-vpn-connection \
  --type ipsec.1 \
  --customer-gateway-id cgw-0abc123def456789a \
  --vpn-gateway-id vgw-0abc123def456789a \
  --options '{"StaticRoutesOnly":false}' \
  --region us-east-1

# Step 4: Enable route propagation so VPC route tables learn on-premises CIDRs
aws ec2 enable-vgw-route-propagation \
  --route-table-id rtb-0123456789abcdef0 \
  --gateway-id vgw-0abc123def456789a

Once the VPN is established, your RDS instances inside the VPC can communicate with on-premises servers using private IP addresses. Your security groups control what traffic is allowed — treat your on-premises CIDR block (say, 10.0.0.0/8) as a trusted network source, but be precise about which ports you open. Port 5432 for PostgreSQL, 1433 for SQL Server, 3306 for MySQL — no broader rules.

#### Private Link for Specific Service Exposure

If you do not want to route your entire data center network into a VPC, AWS PrivateLink lets you expose a single service endpoint across a network boundary without full VPC peering or VPN. This is useful when an on-premises application needs to reach a specific RDS endpoint and nothing else.

Azure Private Link functions identically for Azure SQL: you create a private endpoint inside a VNet, and the on-premises network (connected via ExpressRoute or VPN Gateway) reaches the database through that private IP rather than the public Azure SQL endpoint.

# Create a PrivateLink endpoint for an RDS instance
# First, the VPC endpoint service must exist — RDS uses Interface Endpoints

aws ec2 create-vpc-endpoint \
  --vpc-endpoint-type Interface \
  --vpc-id vpc-0123456789abcdef0 \
  --service-name com.amazonaws.us-east-1.rds \
  --subnet-ids subnet-0abc123def456789a subnet-0abc123def456790b \
  --security-group-ids sg-0abc123def456789a \
  --private-dns-enabled \
  --region us-east-1

#### What Latency Actually Means for Your Databases

When your application is in AWS and your database is on-premises (or vice versa), every synchronous query crosses the network. A 20ms round-trip added to every SELECT statement compounds quickly when an ORM generates 40 queries per page load. The math is brutal: 40 queries × 20ms = 800ms of pure network time before any query execution.

Measure your actual latency before you commit to any hybrid query pattern. Run a simple ping and then a pgbench or sysbench test across the VPN or Direct Connect circuit before you design your application topology. If your latency is above 5ms, co-locate the application with its primary database. Use async replication and caching to bridge the gap rather than synchronous cross-boundary queries.

27.2 Data Synchronization Patterns Across Boundaries

With the network established, the next problem is data: how do you keep data synchronized between an on-premises database and its cloud counterpart? The answer depends entirely on whether you need bidirectional synchronization, unidirectional replication, or bulk periodic loads — and on how much lag you can tolerate.

#### AWS Database Migration Service for Ongoing Replication

AWS DMS is covered in detail in Chapter 25 in the context of migration. In hybrid architectures, DMS is also a production replication tool. You can configure a replication instance, a source endpoint pointing at your on-premises PostgreSQL or SQL Server, and a target endpoint pointing at RDS, and run DMS in continuous replication (CDC) mode indefinitely.

The on-premises PostgreSQL source requires logical replication enabled and a replication slot. For SQL Server, the source must have MS-CDC enabled on the database and each table you want to replicate.

# Create DMS replication instance in the VPC that has connectivity to on-premises
aws dms create-replication-instance \
  --replication-instance-identifier hybrid-repl-01 \
  --replication-instance-class dms.r6i.xlarge \
  --allocated-storage 200 \
  --vpc-security-group-ids sg-0abc123def456789a \
  --replication-subnet-group-identifier my-dms-subnet-group \
  --multi-az \
  --engine-version 3.5.2 \
  --publicly-accessible false

# Source endpoint: on-premises PostgreSQL at 10.10.5.20
aws dms create-endpoint \
  --endpoint-identifier onprem-pg-source \
  --endpoint-type source \
  --engine-name postgres \
  --username dms_replication_user \
  --password 'SecureP@ssword123' \
  --server-name 10.10.5.20 \
  --port 5432 \
  --database-name production_db \
  --extra-connection-attributes "captureDdls=true;pluginName=pglogical"

# Target endpoint: RDS PostgreSQL
aws dms create-endpoint \
  --endpoint-identifier rds-pg-target \
  --endpoint-type target \
  --engine-name postgres \
  --username dms_target_user \
  --password 'SecureP@ssword123' \
  --server-name mydb.c9akciq32.us-east-1.rds.amazonaws.com \
  --port 5432 \
  --database-name production_db

# Create and start the replication task in CDC mode
aws dms create-replication-task \
  --replication-task-identifier hybrid-cdc-task \
  --source-endpoint-arn arn:aws:dms:us-east-1:123456789012:endpoint:ABCDEF... \
  --target-endpoint-arn arn:aws:dms:us-east-1:123456789012:endpoint:GHIJKL... \
  --replication-instance-arn arn:aws:dms:us-east-1:123456789012:rep:MNOPQR... \
  --migration-type cdc \
  --table-mappings file://table-mappings.json \
  --replication-task-settings file://task-settings.json

Monitor your DMS task latency continuously. In hybrid configurations, replication lag above 60 seconds is a warning threshold — above 300 seconds, investigate immediately. DMS exposes CDCLatencySource and CDCLatencyTarget metrics in CloudWatch.

import boto3

cloudwatch = boto3.client('cloudwatch', region_name='us-east-1')

def get_dms_replication_lag(task_arn_suffix: str) -> dict:
    """
    Fetch CDC latency metrics for a DMS replication task.
    task_arn_suffix is the last segment of the replication task ARN.
    """
    response = cloudwatch.get_metric_statistics(
        Namespace='AWS/DMS',
        MetricName='CDCLatencyTarget',
        Dimensions=[
            {
                'Name': 'ReplicationInstanceIdentifier',
                'Value': 'hybrid-repl-01'
            },
            {
                'Name': 'ReplicationTaskIdentifier',
                'Value': 'hybrid-cdc-task'
            }
        ],
        StartTime='2024-03-01T00:00:00Z',
        EndTime='2024-03-01T01:00:00Z',
        Period=60,
        Statistics=['Average', 'Maximum']
    )
    
    datapoints = response['Datapoints']
    if not datapoints:
        return {'status': 'no_data', 'lag_seconds': None}
    
    latest = sorted(datapoints, key=lambda x: x['Timestamp'])[-1]
    lag = latest['Maximum']
    
    status = 'healthy'
    if lag > 60:
        status = 'warning'
    if lag > 300:
        status = 'critical'
    
    return {
        'status': status,
        'lag_seconds': lag,
        'timestamp': latest['Timestamp'].isoformat()
    }

result = get_dms_replication_lag('hybrid-cdc-task')
print(f"DMS replication lag: {result['lag_seconds']}s — Status: {result['status']}")

#### Native Replication as an Alternative to DMS

DMS is convenient but it adds a layer of abstraction with its own failure modes. For PostgreSQL-to-PostgreSQL hybrid replication, you can use native logical replication directly — your on-premises primary publishes, your RDS instance subscribes.

-- On the on-premises PostgreSQL primary (source):
-- Ensure wal_level = logical in postgresql.conf
-- Then create a publication for the tables you want to replicate

CREATE PUBLICATION hybrid_pub
FOR TABLE
    orders,
    order_items,
    customers,
    products
WITH (publish = 'insert, update, delete');

-- Grant replication privilege to the user RDS will connect as
CREATE USER rds_subscriber WITH REPLICATION LOGIN PASSWORD 'ReplicaP@ss456';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO rds_subscriber;
-- On RDS PostgreSQL (target) — the subscriber side:
-- Tables must already exist with matching schema

CREATE SUBSCRIPTION hybrid_sub
CONNECTION 'host=10.10.5.20 port=5432 dbname=production_db user=rds_subscriber password=ReplicaP@ss456'
PUBLICATION hybrid_pub
WITH (
    copy_data = true,
    create_slot = true,
    enabled = true,
    connect = true
);

-- Verify subscription status
SELECT subname, subenabled, subslotname, subpublications
FROM pg_subscription;

-- Check replication slot on the source to monitor lag
-- Run this on the on-premises primary:
SELECT slot_name,
       confirmed_flush_lsn,
       pg_current_wal_lsn() - confirmed_flush_lsn AS lag_bytes,
       pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS lag_pretty
FROM pg_replication_slots
WHERE slot_type = 'logical';

The important difference between native logical replication and DMS: native replication maintains a replication slot on the source. If the connection drops or the subscriber falls behind, the source accumulates WAL files to serve those changes when the slot reconnects. On-premises servers often have less disk than cloud instances — an unconsumed replication slot can fill your pg_wal directory and crash your primary. Set max_slot_wal_keep_size in PostgreSQL 13+ to cap this growth.

#### Azure Data Sync for SQL Server Hybrid

Azure SQL Data Sync is Microsoft's native solution for bidirectional synchronization between on-premises SQL Server and Azure SQL Database. Unlike DMS (which is unidirectional from source to target), Data Sync can handle bidirectional sync — useful when applications write to both the on-premises database and Azure SQL simultaneously.

The configuration involves a Hub database in Azure SQL, a Data Sync Agent installed on your on-premises server, and member databases at both locations. Sync happens on a configurable schedule (minimum 5 minutes) rather than in real time. This is not a replication solution for low-lag requirements — it is a synchronization solution for scenarios where eventual consistency over minutes is acceptable.

Know the limits: Azure Data Sync does not support TRUNCATE, does not replicate DDL changes, has a 500-column limit per table, and cannot handle tables without primary keys. These are hard limits, not configuration options.

27.3 Hybrid Failover and Disaster Recovery

The most valuable use case for hybrid architecture is disaster recovery: your on-premises data center serves as DR for your cloud environment, or cloud serves as DR for your on-premises production. Either direction requires careful design around failover triggering, DNS cutover, and data divergence.

#### Cloud as DR for On-Premises Production

In this pattern, your on-premises PostgreSQL or SQL Server is the primary. The cloud database (RDS, Azure SQL) is a continuously-updated replica. If your data center fails, you promote the cloud replica, update your DNS or application connection strings, and resume operations.

The technical requirements are straightforward. The architectural challenges are operational: who decides to trigger failover? What is the SLA that justifies activating it? How do you handle applications that are split between on-premises compute and the cloud replica?

For PostgreSQL, native streaming replication or logical replication keeps the RDS replica current. Monitor pg_stat_replication on the primary and alert when lag exceeds your RPO threshold.

-- Run on the on-premises primary to monitor replica lag toward RDS
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    sent_lsn - replay_lsn AS total_lag_bytes,
    pg_size_pretty(sent_lsn - replay_lsn) AS lag_pretty,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication
WHERE application_name = 'rds_replica';

-- If lag_pretty exceeds your RPO threshold (e.g., 100MB ~ 60s at typical write rates),
-- alert your on-call DBA before it becomes a recovery gap problem.

When you need to promote the RDS replica after an on-premises failure, the process for RDS PostgreSQL involves breaking the replication and promoting the read replica:

# Promote the RDS Read Replica to a standalone instance
aws rds promote-read-replica \
  --db-instance-identifier rds-dr-replica \
  --backup-retention-period 7 \
  --preferred-backup-window "03:00-04:00" \
  --region us-east-1

# Monitor until the instance status becomes "available"
aws rds wait db-instance-available \
  --db-instance-identifier rds-dr-replica

# Update the CNAME record for your application database endpoint
# (Using Route 53 here — adapt to your DNS provider)
aws route53 change-resource-record-sets \
  --hosted-zone-id Z1D633PJN98FT9 \
  --change-batch '{
    "Changes": [{
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "db.internal.example.com",
        "Type": "CNAME",
        "TTL": 60,
        "ResourceRecords": [{"Value": "rds-dr-replica.c9akciq32.us-east-1.rds.amazonaws.com"}]
      }
    }]
  }'

Set your DNS TTL to 60 seconds — not 300 or 3600. When you need to cut over, you want the change to propagate in one minute, not five.

#### On-Premises as DR for Cloud Production

This is less common but occurs when regulatory requirements mandate that a copy of data remain in a specific physical location, or when cloud costs make on-premises a more economical secondary tier.

For RDS PostgreSQL, you cannot configure standard streaming replication *from* RDS to an external server the way you would between two self-managed instances. RDS does not expose the primary's WAL stream for external replication subscription without specific configuration. You have two options:

1. Use RDS logical replication (rds.logical_replication = 1 in the parameter group) to publish from RDS to an on-premises PostgreSQL subscriber.

2. Use AWS DMS in reverse — RDS as the source, on-premises as the target.

# Enable logical replication on RDS PostgreSQL via Parameter Group
aws rds modify-db-parameter-group \
  --db-parameter-group-name production-pg15-params \
  --parameters 'ParameterName=rds.logical_replication,ParameterValue=1,ApplyMethod=pending-reboot'

# Reboot is required for this parameter
aws rds reboot-db-instance \
  --db-instance-identifier prod-pg-primary

# After reboot, on the RDS instance, create the publication:
# (Connect via psql first)
# CREATE PUBLICATION onprem_dr_pub FOR ALL TABLES;

# On the on-premises PostgreSQL DR server, create the subscription:
# CREATE SUBSCRIPTION onprem_dr_sub
# CONNECTION 'host=prod-pg-primary.c9akciq32.us-east-1.rds.amazonaws.com
#             port=5432 dbname=production_db
#             user=replication_user password=SecurePassword'
# PUBLICATION onprem_dr_pub;

27.4 Hybrid Identity and Access Management

Network connectivity handles the infrastructure layer. Identity handles the security layer. In your on-premises data center, you used pg_hba.conf, Active Directory service accounts, or LDAP for database authentication. In the cloud, IAM controls who and what can connect. Hybrid environments need a coherent identity strategy that spans both worlds.

#### AWS IAM Database Authentication Across Boundaries

RDS supports IAM authentication for PostgreSQL and MySQL. Instead of a username/password, the application generates a short-lived authentication token using its AWS IAM credentials. The token is valid for 15 minutes. This works perfectly for applications running inside AWS. For on-premises applications, it requires that the on-premises server has access to IAM credentials — either through an IAM user's access key (acceptable for service accounts, not ideal) or through AWS STS and cross-account role assumption.

The practical pattern: create an IAM user specifically for on-premises database access, assign it a policy that allows rds-db:connect for the specific RDS resource and database user, and rotate the access keys using AWS Secrets Manager rotation.

import boto3
import psycopg2

def connect_to_rds_from_onpremises(
    db_host: str,
    db_port: int,
    db_name: str,
    db_user: str,
    region: str,
    aws_access_key_id: str,
    aws_secret_access_key: str
) -> psycopg2.extensions.connection:
    """
    Connect to RDS PostgreSQL from an on-premises server using IAM authentication.
    The IAM user must have rds-db:connect permission on the db resource.
    """
    # Generate the auth token using STS credentials
    session = boto3.Session(
        aws_access_key_id=aws_access_key_id,
        aws_secret_access_key=aws_secret_access_key,
        region_name=region
    )
    
    rds_client = session.client('rds')
    
    # This generates a token valid for 15 minutes
    auth_token = rds_client.generate_db_auth_token(
        DBHostname=db_host,
        Port=db_port,
        DBUsername=db_user,
        Region=region
    )
    
    # Connect using the token as the password
    # SSL is required when using IAM auth
    conn = psycopg2.connect(
        host=db_host,
        port=db_port,
        database=db_name,
        user=db_user,
        password=auth_token,
        sslmode='verify-full',
        sslrootcert='/path/to/us-east-1-bundle.pem'
    )
    
    return conn

# Usage from on-premises server
connection = connect_to_rds_from_onpremises(
    db_host='prod-rds.c9akciq32.us-east-1.rds.amazonaws.com',
    db_port=5432,
    db_name='production',
    db_user='app_iam_user',
    region='us-east-1',
    aws_access_key_id='AKIAIOSFODNN7EXAMPLE',
    aws_secret_access_key='wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY'
)

The IAM user's policy for this access:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["rds-db:connect"],
      "Resource": [
        "arn:aws:rds-db:us-east-1:123456789012:dbuser:db-ABC123/app_iam_user"]
    }
  ]
}

Note the resource ARN format: rds-db (not rds), followed by the db-resource-id (available from aws rds describe-db-instances, look for DbiResourceId), and the specific database user name. The database user must exist in PostgreSQL and must have the rds_iam role granted:

-- On the RDS PostgreSQL instance, create the IAM-authenticated user
CREATE USER app_iam_user WITH LOGIN;
GRANT rds_iam TO app_iam_user;

-- Grant this user the permissions it needs
GRANT CONNECT ON DATABASE production TO app_iam_user;
GRANT USAGE ON SCHEMA public TO app_iam_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_iam_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_iam_user;

#### Active Directory Integration for SQL Server Hybrid

For SQL Server shops, Active Directory integration is typically the correct identity bridge. On-premises SQL Server already authenticates Windows accounts via Kerberos. Azure SQL Managed Instance supports Azure AD-joined authentication, and Azure AD Connect can synchronize your on-premises AD with Azure AD, giving you a unified identity surface.

For plain Azure SQL Database (not Managed Instance), you use Azure AD authentication with on-premises AD synchronized through Azure AD Connect. The SQL Server client on-premises connects using an Azure AD token rather than a SQL login.

-- On Azure SQL Database: create a contained database user from Azure AD
-- (Run as Azure AD admin)
CREATE USER [corp\svc_appaccount] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [corp\svc_appaccount];
ALTER ROLE db_datawriter ADD MEMBER [corp\svc_appaccount];

-- On-premises SQL Server: check linked server connectivity using Windows auth passthrough
-- Create a linked server from on-premises SQL Server to Azure SQL
EXEC sp_addlinkedserver
    @server = N'AzureSQLLinked',
    @srvproduct = N'',
    @provider = N'MSOLEDBSQL',
    @datasrc = N'yourserver.database.windows.net',
    @catalog = N'production_db';

EXEC sp_addlinkedsrvlogin
    @rmtsrvname = N'AzureSQLLinked',
    @useself = N'FALSE',
    @locallogin = NULL,
    @rmtuser = N'svc_appaccount@corp.example.com',
    @rmtpassword = N'ServiceAccountPassword';

-- Test the linked server
SELECT TOP 10 * FROM AzureSQLLinked.production_db.dbo.orders;

Linked servers across cloud boundaries work — but they carry the same latency penalty described in section 27.1. A distributed query that joins a local on-premises table to an Azure SQL table via linked server will ship the entire remote result set across the network unless the optimizer pushes the predicate remotely. Test your execution plans with SET STATISTICS IO ON and verify that remote row counts are bounded.

27.5 Cross-Boundary Query Patterns and Their Performance Implications

Section 27.1 established that latency is the enemy of synchronous cross-boundary queries. This section goes deeper into the specific patterns that appear in hybrid architectures and how to engineer around their limitations.

#### The Linked Server Anti-Pattern

Developers who discover linked servers (SQL Server) or dblink/postgres_fdw (PostgreSQL) sometimes treat them as a transparent way to query remote tables as if they are local. This works adequately in same-datacenter scenarios. Across a hybrid cloud boundary, it becomes a performance problem at any meaningful scale.

-- SQL Server: this query looks innocent but can be expensive across a WAN link
SELECT
    o.order_id,
    o.customer_id,
    c.customer_name,    -- c comes from on-premises
    p.product_name      -- p comes from Azure SQL via linked server
FROM dbo.orders o                                       -- local (Azure SQL)
INNER JOIN AzureSQLLinked.production.dbo.customers c    -- remote (on-premises)
    ON o.customer_id = c.customer_id
INNER JOIN dbo.products p                               -- local (Azure SQL)
    ON o.product_id = p.product_id
WHERE o.order_date >= '2024-01-01';

-- Check how SQL Server plans this
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
-- If the Remote Query operator shows millions of rows, you have a problem.
-- The optimizer may fetch the entire customers table and filter locally.

The fix is rarely at the query level. The fix is to replicate the lookup tables (customers, products) to both sides of the boundary so cross-boundary joins become local joins with a small synchronization lag.

-- PostgreSQL equivalent using postgres_fdw
-- Demonstrate the same anti-pattern and the monitoring approach

-- First, set up the foreign server and user mapping
CREATE EXTENSION IF NOT EXISTS postgres_fdw;

CREATE SERVER onprem_pg
    FOREIGN DATA WRAPPER postgres_fdw
    OPTIONS (host '10.10.5.20', port '5432', dbname 'production_db');

CREATE USER MAPPING FOR current_user
    SERVER onprem_pg
    OPTIONS (user 'fdw_user', password 'FdwP@ssword789');

-- Import the remote schema
IMPORT FOREIGN SCHEMA public
    LIMIT TO (customers, products)
    FROM SERVER onprem_pg
    INTO remote_tables;

-- Check estimated vs. actual row counts for foreign scans
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    o.order_id,
    c.customer_name
FROM orders o
JOIN remote_tables.customers c ON o.customer_id = c.customer_id
WHERE o.order_date >= '2024-01-01';

-- Look for "Foreign Scan" nodes in the plan.
-- If rows= estimate is far from actual, update statistics:
ANALYZE remote_tables.customers;

For postgres_fdw, set use_remote_estimate = true on the foreign server to let PostgreSQL query the remote server for row count estimates. This dramatically improves plan quality for foreign tables:

ALTER SERVER onprem_pg OPTIONS (ADD use_remote_estimate 'true');

#### Materialized Caching Pattern

The correct pattern for frequently-queried reference data that lives on the other side of a cloud boundary is to replicate it locally with a controlled refresh cycle. Call it a materialized cache, a shadow table, or a local replica — the concept is the same.

-- PostgreSQL: create a local shadow of the on-premises customers table
-- This runs on the RDS side and refreshes on a schedule

CREATE TABLE customers_shadow (
    customer_id     BIGINT PRIMARY KEY,
    customer_name   TEXT NOT NULL,
    email           TEXT,
    region          TEXT,
    created_at      TIMESTAMPTZ,
    synced_at       TIMESTAMPTZ DEFAULT now()  -- tracks when we last pulled this row
);

CREATE INDEX idx_customers_shadow_region ON customers_shadow (region);

-- Refresh function: pull changes from the foreign table since last sync
CREATE OR REPLACE FUNCTION refresh_customers_shadow()
RETURNS void
LANGUAGE plpgsql
AS $$
DECLARE
    v_last_sync TIMESTAMPTZ;
    v_rows_affected INT;
BEGIN
    SELECT COALESCE(MAX(synced_at), '1970-01-01'::TIMESTAMPTZ)
    INTO v_last_sync
    FROM customers_shadow;

    -- Upsert changes from the foreign table
    INSERT INTO customers_shadow (
        customer_id, customer_name, email, region, created_at, synced_at
    )
    SELECT
        customer_id,
        customer_name,
        email,
        region,
        created_at,
        now()
    FROM remote_tables.customers
    WHERE created_at > v_last_sync
       OR updated_at > v_last_sync   -- assumes updated_at column exists on source

    ON CONFLICT (customer_id) DO UPDATE SET
        customer_name = EXCLUDED.customer_name,
        email         = EXCLUDED.email,
        region        = EXCLUDED.region,
        synced_at     = EXCLUDED.synced_at;

    GET DIAGNOSTICS v_rows_affected = ROW_COUNT;

    RAISE NOTICE 'customers_shadow refreshed: % rows upserted', v_rows_affected;
END;
$$;

-- Schedule via pg_cron (if available) or an external scheduler
-- SELECT cron.schedule('*/5 * * * *', 'SELECT refresh_customers_shadow()');
-- SQL Server equivalent: shadow table and refresh stored procedure

CREATE TABLE dbo.customers_shadow (
    customer_id     BIGINT          NOT NULL PRIMARY KEY,
    customer_name   NVARCHAR(255)   NOT NULL,
    email           NVARCHAR(320)   NULL,
    region          NVARCHAR(50)    NULL,
    created_at      DATETIME2       NULL,
    synced_at       DATETIME2       NOT NULL DEFAULT SYSUTCDATETIME()
);

CREATE NONCLUSTERED INDEX ix_customers_shadow_region
    ON dbo.customers_shadow (region);
GO

CREATE OR ALTER PROCEDURE dbo.usp_RefreshCustomersShadow
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @last_sync DATETIME2;
    SELECT @last_sync = ISNULL(MAX(synced_at), '19700101')
    FROM dbo.customers_shadow;

    MERGE dbo.customers_shadow AS tgt
    USING (
        SELECT customer_id, customer_name, email, region, created_at
        FROM AzureSQLLinked.production_db.dbo.customers
        WHERE created_at > @last_sync
           OR updated_at > @last_sync
    ) AS src
    ON tgt.customer_id = src.customer_id

    WHEN MATCHED THEN UPDATE SET
        tgt.customer_name = src.customer_name,
        tgt.email         = src.email,
        tgt.region        = src.region,
        tgt.synced_at     = SYSUTCDATETIME()

    WHEN NOT MATCHED BY TARGET THEN INSERT (
        customer_id, customer_name, email, region, created_at, synced_at
    ) VALUES (
        src.customer_id, src.customer_name, src.email,
        src.region, src.created_at, SYSUTCDATETIME()
    );

    PRINT CAST(@@ROWCOUNT AS VARCHAR) + ' rows merged into customers_shadow.';
END;
GO

The shadow table approach decouples your application queries from the remote source. When the VPN connection degrades or the on-premises server is under maintenance, your cloud-side application continues to work against the last-synced data. The lag is controlled and predictable — you know exactly how stale the shadow can be because you control the refresh interval.

27.6 Monitoring a Hybrid Database Environment

Monitoring is harder in hybrid environments because your observability tools exist on both sides of the boundary, and combining their signals into a coherent view requires deliberate design.

#### Centralized Metrics Collection

The pattern that works at scale is to centralize all database metrics into your cloud monitoring layer and push on-premises metrics to it. CloudWatch agent, Azure Monitor agent, or the Prometheus node_exporter with remote_write can all collect on-premises metrics and ship them to the cloud.

For PostgreSQL, the postgres_exporter (Prometheus) running on your on-premises server can scrape database metrics and push them to a centralized Prometheus/Thanos or Victoria Metrics deployment.

# prometheus.yml: scrape config for both on-premises and RDS PostgreSQL
# On-premises instances are scraped directly.
# RDS instances are scraped via postgres_exporter running in the VPC.

global:
  scrape_interval: 30s
  evaluation_interval: 30s

scrape_configs:
  - job_name: 'postgres_onprem'
    static_configs:
      - targets:
          - '10.10.5.20:9187'   # postgres_exporter on on-premises server
          - '10.10.5.21:9187'
    labels:
      environment: 'onpremises'
      datacenter: 'dc-east'

  - job_name: 'postgres_rds'
    static_configs:
      - targets:
          - '10.100.1.50:9187'  # postgres_exporter in VPC, scraping RDS
    labels:
      environment: 'aws'
      region: 'us-east-1'

The postgres_exporter configuration for RDS must use a connection string pointing at the RDS endpoint — the exporter runs inside your VPC and connects to RDS over the private endpoint, then exposes its HTTP metrics port for Prometheus to scrape.

#### Alerting Across Boundaries

Define alerts that specifically watch for hybrid-specific failure modes. These are the signals that pure cloud or pure on-premises setups never need to alert on:

1. Replication slot lag exceeding disk safety threshold — On-premises primary running out of WAL disk because the cloud subscriber is behind.

2. DMS task latency spike — Network congestion or VPN instability causing CDC lag to build.

3. Cross-boundary query response time degradation — P99 latency on federated queries rising above acceptable threshold.

4. VPN tunnel state change — The network layer itself going down is a database event from your perspective.

5. Shadow table staleness — The refresh procedure last ran more than N minutes ago, meaning your local cache is drifting.

# Prometheus alerting rules for hybrid-specific conditions

groups:
  - name: hybrid_database_alerts
    rules:

      - alert: ReplicationSlotLagCritical
        expr: |
          pg_replication_slots_pg_wal_lsn_diff{slot_type="logical"} > 10737418240
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Replication slot {{ $labels.slot_name }} lag exceeds 10GB"
          description: >
            The logical replication slot {{ $labels.slot_name }} on
            {{ $labels.instance }} has {{ $value | humanize1024 }}B of unconsumed WAL.
            If the subscriber does not catch up, disk will fill and the primary will stop.

      - alert: ShadowTableStalenessWarning
        expr: |
          (time() - pg_shadow_table_last_refresh_epoch{table="customers_shadow"}) > 600
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "customers_shadow has not refreshed in over 10 minutes"
          description: >
            The shadow table customers_shadow on {{ $labels.instance }}
            last refreshed {{ $value | humanizeDuration }} ago.
            Check the refresh job and VPN connectivity.

      - alert: DMSReplicationLagCritical
        expr: |
          aws_dms_cdc_latency_target_maximum > 300
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "DMS task replication lag exceeds 300 seconds"
          description: >
            AWS DMS task on replication instance {{ $labels.replication_instance }}
            has a target latency of {{ $value }}s.
            Investigate network connectivity and DMS task errors.

#### Tracing Queries Across Boundaries in SQL Server

For SQL Server, Extended Events and Query Store give you the on-premises view. Azure SQL has its own Query Store, sys.dm_exec_requests, and Azure Monitor. Correlating a slow distributed query that hits both sides requires matching timestamps and session identifiers manually — there is no native end-to-end tracing for linked-server queries.

The pragmatic approach: log the session ID and the start timestamp of every distributed query in your application layer, then correlate with SQL Server's DMVs using that information after the fact.

-- SQL Server: capture distributed query performance with Extended Events
-- Run this on the on-premises instance to capture remote query costs

CREATE EVENT SESSION [hybrid_query_trace] ON SERVER
ADD EVENT sqlserver.sql_statement_completed (
    WHERE (
        sqlserver.database_name = N'production_db'
        AND package0.greater_than_equal_uint64(duration, 1000000)  -- >= 1 second
    )
    ACTION (
        sqlserver.sql_text,
        sqlserver.session_id,
        sqlserver.client_hostname,
        sqlserver.username
    )
),
ADD EVENT sqlserver.rpc_completed (
    WHERE (
        package0.greater_than_equal_uint64(duration, 1000000)
    )
    ACTION (
        sqlserver.sql_text,
        sqlserver.session_id
    )
)
ADD TARGET package0.ring_buffer (SET max_memory = 51200)
WITH (
    MAX_DISPATCH_LATENCY = 5 SECONDS,
    TRACK_CAUSALITY = ON       -- enables cross-event correlation via activity_id
);

ALTER EVENT SESSION [hybrid_query_trace] ON SERVER STATE = START;

27.7 Managing Schema Changes Across Hybrid Environments

Schema changes are the most operationally treacherous part of hybrid database management. When your production schema exists in two places — on-premises and cloud — every migration must be coordinated. Applied out of order, a schema change will break replication, corrupt data, or crash applications.

#### The Synchronization Problem

Logical replication (both native PostgreSQL and DMS) replicates data but not DDL in most configurations. If you add a column to the on-premises source table, the RDS target does not automatically receive that column. Your replication task will fail when it encounters an INSERT with a column count the target does not recognize.

DMS's default behavior on DDL changes is to stop the task with an error. Native PostgreSQL logical replication will fail with a type mismatch or column count error. Azure Data Sync ignores DDL changes entirely and lets data become inconsistent.

The correct migration sequence for adding a column in a hybrid environment:

1. Apply the schema change to the TARGET (cloud) FIRST
2. Verify the change is present and replication is healthy
3. Apply the schema change to the SOURCE (on-premises)
4. Verify replication resumes without errors

This order matters because the target can accept rows that do not fill optional columns (NULL-able additions), but the source cannot replicate data into a column that does not exist on the target. Adding the column to the target first gives you a window of grace.

-- Step 1: Apply on the RDS target (PostgreSQL) FIRST
-- Connect to RDS and run:
ALTER TABLE orders ADD COLUMN discount_code TEXT;
ALTER TABLE orders ADD COLUMN discount_amount NUMERIC(10,2) DEFAULT 0.00;

-- Verify logical replication slot is still active and not lagging
SELECT slot_name, active, confirmed_flush_lsn,
       pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS slot_lag
FROM pg_replication_slots;

-- Step 2: Apply on the on-premises source SECOND
-- Connect to on-premises PostgreSQL and run:
ALTER TABLE orders ADD COLUMN discount_code TEXT;
ALTER TABLE orders ADD COLUMN discount_amount NUMERIC(10,2) DEFAULT 0.00;

-- Verify replication is flowing normally after the DDL on the source
SELECT pid, usename, application_name, client_addr, state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
-- SQL Server equivalent for DMS replication:
-- Step 1: Apply on RDS SQL Server target FIRST
ALTER TABLE dbo.orders ADD discount_code NVARCHAR(50) NULL;
ALTER TABLE dbo.orders ADD discount_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00;

-- Step 2: Verify DMS task is healthy in CloudWatch before proceeding
-- (Check CDCLatencyTarget in CloudWatch — should remain stable)

-- Step 3: Apply on on-premises SQL Server source SECOND
ALTER TABLE dbo.orders ADD discount_code NVARCHAR(50) NULL;
ALTER TABLE dbo.orders ADD discount_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00;

-- MS-CDC captures the DDL event; DMS will handle the new columns on the next batch
-- Monitor DMS task for errors for 10 minutes after source DDL application

#### Schema Migration Tools in Hybrid Context

Tools like Flyway and Liquibase can manage schema versions across multiple environments, but they need explicit configuration to understand that your "on-premises" and "cloud" targets are logically the same schema lineage.

The pattern that works: treat the on-premises and cloud databases as two members of the same migration graph, but always execute the cloud target migration first (via your CI/CD pipeline connecting to the RDS endpoint), then execute the on-premises migration immediately after (via your CI/CD pipeline connecting to the on-premises endpoint through the VPN).

<!-- Liquibase: hybrid migration pipeline configuration -->
<!-- liquibase-cloud.properties — targets RDS first -->
changeLogFile=db/changelog/db.changelog-master.xml
url=jdbc:postgresql://rds-primary.c9akciq32.us-east-1.rds.amazonaws.com:5432/production_db
username=liquibase_runner
password=${LIQUIBASE_PASSWORD}
driver=org.postgresql.Driver

<!-- liquibase-onprem.properties — targets on-premises second -->
changeLogFile=db/changelog/db.changelog-master.xml
url=jdbc:postgresql://10.10.5.20:5432/production_db
username=liquibase_runner
password=${LIQUIBASE_PASSWORD_ONPREM}
driver=org.postgresql.Driver
#!/bin/bash
# hybrid-migration.sh — always apply cloud target before on-premises source

set -e  # Exit on any error

echo "=== Applying migration to cloud target (RDS) ==="
liquibase --defaultsFile=liquibase-cloud.properties update

echo "=== Verifying replication health before applying to source ==="
python3 check_replication_lag.py --max-lag-seconds 60 || {
    echo "ERROR: Replication lag too high. Do not apply migration to source yet."
    exit 1
}

echo "=== Applying migration to on-premises source ==="
liquibase --defaultsFile=liquibase-onprem.properties update

echo "=== Migration complete. Monitoring replication for 5 minutes ==="
for i in $(seq 1 10); do
    sleep 30
    python3 check_replication_lag.py --max-lag-seconds 120
done

echo "=== Hybrid migration pipeline completed successfully ==="

The check_replication_lag.py script queries pg_stat_replication on the on-premises primary and exits with a non-zero code if lag exceeds the threshold. This gate prevents applying source-side DDL when the target is already behind, which would compound the risk.

27.8 Cost Engineering in Hybrid Architectures

Hybrid architectures incur costs on both sides of the boundary simultaneously. On-premises hardware, power, and administration costs do not disappear when you add cloud costs. Network egress pricing adds a third dimension. Understanding where the money goes lets you make trade-offs rather than just absorb them.

#### Data Transfer Costs Across the Hybrid Boundary

AWS charges for data transfer OUT of AWS to the internet (and in some configurations to on-premises over VPN). Direct Connect has its own data transfer rates. Azure charges for egress. GCP charges for egress. The pattern is consistent: inbound data to the cloud is typically free, outbound is not.

For hybrid database replication, your primary concern is the volume of change data flowing from source to target — or from cloud primary to on-premises DR. If your database generates 50 GB of WAL changes per day and you are shipping all of it across Direct Connect at the outbound rate, that is a meaningful monthly line item.

Minimize cross-boundary data movement through:

1. Filtering replication scope: replicate only the tables that need to exist on both sides. DMS table mappings and PostgreSQL publication table lists let you be selective.

2. Compressing replication streams: PostgreSQL logical replication does not inherently compress WAL. DMS compresses its transfer stream. For Direct Connect, work with your network team on link-level compression.

3. Co-locating the application with the data it reads most: if 90% of your application's reads are against the cloud database, do not run the application on-premises and pay for every result set to traverse the boundary.

#### Right-Sizing Your Hybrid Footprint

A common mistake is running both the on-premises and cloud databases at full production sizing simultaneously. If your cloud database is a DR replica that is rarely queried, size it as a DR replica — smaller instance class, minimal IOPS provisioning, no Multi-AZ until you are within a maintenance window of promoting it. Promote it to full production sizing as part of your DR activation runbook.

# Example: DR replica running at reduced capacity in normal operation
aws rds create-db-instance-read-replica \
  --db-instance-identifier prod-dr-replica \
  --source-db-instance-identifier prod-primary \
  --db-instance-class db.r6g.large \      # Smaller than production's db.r6g.4xlarge
  --publicly-accessible false \
  --region us-west-2

# The DR activation runbook scales it up BEFORE promotion:
aws rds modify-db-instance \
  --db-instance-identifier prod-dr-replica \
  --db-instance-class db.r6g.4xlarge \
  --apply-immediately

aws rds wait db-instance-available \
  --db-instance-identifier prod-dr-replica

# Then promote
aws rds promote-read-replica \
  --db-instance-identifier prod-dr-replica

One caveat: apply the scale-up before promoting, not after. After promotion, the instance is no longer a replica and carries full production traffic. Scaling a primary under load is riskier than scaling a cold replica.

Key Takeaways

  • → **Network is the foundation**: every hybrid database pattern — replication, cross-boundary queries, failover — depends on stable, low-latency connectivity. Use Direct Connect or ExpressRoute for production workloads; accept Site-to-Site VPN only for low-bandwidth or non-critical scenarios. Measure actual latency before designing your query topology.
  • → **Synchronous cross-boundary queries do not scale**: latency compounds across every query in a page load or transaction. Use native replication, DMS CDC, or the materialized shadow table pattern to bring frequently-needed data to the same side as its consumers. Reserve linked servers and `postgres_fdw` for administrative queries and low-volume operations.
  • → **DDL changes must be sequenced target-first**: when logical replication is in place, always apply schema changes to the replication target before the source. Applying them to the source first will break replication. Build this ordering into your migration automation with a replication lag check as a gate between the two steps.
  • → **Replication slots and WAL accumulation are on-premises-specific risks**: cloud databases manage WAL retention with built-in safeguards; on-premises servers can fill their `pg_wal` directory and crash if a logical replication subscriber falls behind. Set `max_slot_wal_keep_size`, monitor slot lag aggressively, and build alerts that fire well before disk is exhausted.
  • → **Right-size your hybrid footprint continuously**: DR replicas do not need production-class instance sizing until the moment they are activated. Run them smaller, scale up as part of your DR runbook before promotion, and reduce cloud spend during normal operation without sacrificing recovery capability.
