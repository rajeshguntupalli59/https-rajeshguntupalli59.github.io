Chapter 28: PostgreSQL LISTEN/NOTIFY for Event-Driven AI

PostgreSQL's LISTEN/NOTIFY mechanism has existed since version 6.4, quietly doing useful work for developers who needed lightweight pub/sub without reaching for a separate message broker. In AI-native applications, it turns out to be remarkably well-suited for a problem that keeps coming up: how do you trigger AI processing in reaction to database events without adding operational complexity, introducing consistency gaps between your data store and your queue, or polling tables in a loop? This chapter covers how to build event-driven AI pipelines using LISTEN/NOTIFY as the signal layer — connecting PostgreSQL triggers to Python consumers that invoke LLMs, update embeddings, route agent tasks, and fan out notifications to downstream systems. You'll see how this integrates with FastAPI, Celery, Redis, and the Anthropic and OpenAI SDKs, and how to operate these pipelines safely in production.

---

28.1 Why LISTEN/NOTIFY Belongs in Your AI Stack

Before building anything, it's worth understanding what LISTEN/NOTIFY actually is and what it isn't.

What it is: A lightweight, in-process pub/sub system built into PostgreSQL. A session issues NOTIFY channel_name, 'payload' and every session currently listening on that channel receives the payload asynchronously. Notifications are transactional — a NOTIFY issued inside a transaction isn't delivered until that transaction commits. If the transaction rolls back, the notification is never sent.

What it isn't: A durable message queue. If no listener is connected when a NOTIFY fires, the notification is lost. There is no persistence, no replay, no dead-letter queue. The payload is limited to 8,000 bytes.

For AI applications, this combination — transactional delivery, zero persistence, low latency — makes LISTEN/NOTIFY ideal as a *signal layer* rather than a *delivery layer*. The pattern is:

1. Data changes in PostgreSQL (new document, updated record, user message)

2. A trigger fires NOTIFY with a lightweight payload (usually just a row ID)

3. A Python consumer receives the notification and fetches the full record

4. The consumer invokes an LLM or embedding model

5. Results are written back to PostgreSQL

The notification is the trigger. The database is the source of truth. The consumer is stateless. If the consumer crashes, you need a recovery path (we'll cover that), but the data itself is safe.

sequenceDiagram
    participant App as Writer (INSERT/UPDATE)
    participant PG as PostgreSQL
    participant Trig as Trigger
    participant Listener as Python Consumer (LISTEN)
    participant AI as LLM / Embedding API

    App->>PG: INSERT/UPDATE row
    PG->>Trig: fires on commit
    Trig->>PG: write ai_events row (durable log)
    Trig-->>Listener: pg_notify(channel, row id)
    Listener->>PG: fetch full record
    Listener->>AI: invoke model
    AI-->>Listener: result
    Listener->>PG: write result, mark event processed

*The trigger-log-notify pattern: NOTIFY gives low-latency delivery while the ai_events row gives a durable recovery path if no consumer was listening.*

Why not just use Celery with a broker? You can, and for heavy workloads you should — and we'll show how they compose. But adding Redis or RabbitMQ as a required dependency means you now have infrastructure to manage, a potential consistency gap (the row was inserted but was the task enqueued?), and operational overhead. For many AI features — embedding new content as it's inserted, routing agent events, invalidating LLM caches — LISTEN/NOTIFY is sufficient and dramatically simpler. The transactional guarantee is the key: you cannot accidentally queue a task for a row that doesn't exist yet.

Good schema design here means structuring your tables so that triggers can extract meaningful signals and consumers can efficiently fetch what they need.

Now the trigger infrastructure. The key design decision: triggers write to ai_events *and* issue NOTIFY. The event log gives you durability and recovery; the notification gives you low-latency delivery.

-- Generic notification function — used by multiple triggers
CREATE OR REPLACE FUNCTION notify_ai_event()
RETURNS TRIGGER AS $$
DECLARE
    v_channel   TEXT;
    v_event_type TEXT;
    v_entity_id  UUID;
    v_tenant_id  UUID;
    v_payload    JSONB;
    v_event_id   BIGINT;
    v_notify_payload TEXT;
BEGIN
    -- Determine event type
    v_event_type := TG_OP;  -- INSERT, UPDATE, DELETE

    -- Extract entity info based on table
    IF TG_TABLE_NAME = 'documents' THEN
        v_channel   := 'ai_documents';
        v_entity_id := NEW.id;
        v_tenant_id := NEW.tenant_id;
        v_payload   := jsonb_build_object(
            'operation', TG_OP,
            'id', NEW.id,
            'tenant_id', NEW.tenant_id,
            'status', NEW.status,
            'has_body', length(NEW.body) > 0
        );

        -- Only notify on meaningful state changes
        IF TG_OP = 'UPDATE' AND OLD.body = NEW.body AND OLD.status = NEW.status THEN
            RETURN NEW;
        END IF;

    ELSIF TG_TABLE_NAME = 'messages' THEN
        v_channel   := 'ai_messages';
        v_entity_id := NEW.id;
        v_tenant_id := NEW.tenant_id;
        v_payload   := jsonb_build_object(
            'operation', TG_OP,
            'id', NEW.id,
            'conversation_id', NEW.conversation_id,
            'tenant_id', NEW.tenant_id,
            'role', NEW.role
        );

        -- Only process user messages for LLM response generation
        IF NEW.role != 'user' THEN
            RETURN NEW;
        END IF;

    ELSIF TG_TABLE_NAME = 'agent_tasks' THEN
        v_channel   := 'ai_agent_tasks';
        v_entity_id := NEW.id;
        v_tenant_id := NEW.tenant_id;
        v_payload   := jsonb_build_object(
            'operation', TG_OP,
            'id', NEW.id,
            'agent_id', NEW.agent_id,
            'task_type', NEW.task_type,
            'status', NEW.status,
            'priority', NEW.priority
        );

        IF TG_OP = 'UPDATE' AND NEW.status != 'queued' THEN
            RETURN NEW;
        END IF;
    END IF;

    -- Write durable event record first
    INSERT INTO ai_events (
        event_type, entity_type, entity_id, tenant_id,
        payload, channel
    ) VALUES (
        v_event_type, TG_TABLE_NAME, v_entity_id, v_tenant_id,
        v_payload, v_channel
    ) RETURNING id INTO v_event_id;

    -- Notify payload is minimal — just enough to fetch the record
    v_notify_payload := jsonb_build_object(
        'event_id', v_event_id,
        'entity_id', v_entity_id,
        'event_type', v_event_type,
        'table', TG_TABLE_NAME
    )::text;

    -- Enforce 8000 byte limit
    IF length(v_notify_payload) > 8000 THEN
        v_notify_payload := jsonb_build_object(
            'event_id', v_event_id,
            'entity_id', v_entity_id
        )::text;
    END IF;

    PERFORM pg_notify(v_channel, v_notify_payload);

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Attach to tables
CREATE TRIGGER trg_documents_ai_notify
    AFTER INSERT OR UPDATE ON documents
    FOR EACH ROW EXECUTE FUNCTION notify_ai_event();

CREATE TRIGGER trg_messages_ai_notify
    AFTER INSERT ON messages
    FOR EACH ROW EXECUTE FUNCTION notify_ai_event();

CREATE TRIGGER trg_agent_tasks_ai_notify
    AFTER INSERT OR UPDATE ON agent_tasks
    FOR EACH ROW EXECUTE FUNCTION notify_ai_event();

-- Recovery function: find events that were notified but never processed
CREATE OR REPLACE FUNCTION get_unprocessed_events(
    p_channel TEXT,
    p_older_than_seconds INT DEFAULT 30,
    p_limit INT DEFAULT 100
)
RETURNS TABLE (
    event_id    BIGINT,
    entity_id   UUID,
    entity_type TEXT,
    payload     JSONB,
    notified_at TIMESTAMPTZ,
    retry_count INT
) AS $$
BEGIN
    RETURN QUERY
    SELECT
        e.id,
        e.entity_id,
        e.entity_type,
        e.payload,
        e.notified_at,
        e.retry_count
    FROM ai_events e
    WHERE e.channel = p_channel
      AND e.status IN ('notified', 'failed')
      AND e.notified_at < now() - (p_older_than_seconds || ' seconds')::interval
      AND e.retry_count < 5
    ORDER BY e.notified_at ASC
    LIMIT p_limit;
END;
$$ LANGUAGE plpgsql;

28.3 Python Consumers with asyncpg

The Python side uses asyncpg for async LISTEN/NOTIFY support. asyncio event loop, connection pooling, and the AI SDK calls all compose cleanly.

# listener.py — core LISTEN/NOTIFY consumer for AI events
import asyncio
import asyncpg
import json
import logging
import signal
import time
import uuid
from contextlib import asynccontextmanager
from dataclasses import dataclass, field
from typing import Any, Callable, Coroutine

import anthropic
import openai
from openai import AsyncOpenAI

logger = logging.getLogger(__name__)

DATABASE_URL = "postgresql://app_user:secret@localhost:5432/aiapp"
PROCESSOR_ID = f"worker-{uuid.uuid4().hex[:8]}"


@dataclass
class NotificationEvent:
    channel: str
    payload: dict
    event_id: int
    entity_id: str
    entity_type: str
    event_type: str


class AIEventConsumer:
    """
    Listens on PostgreSQL NOTIFY channels and dispatches to AI processors.
    Handles reconnection, recovery, and graceful shutdown.
    """

    def __init__(self, dsn: str, channels: list[str]):
        self.dsn = dsn
        self.channels = channels
        self.conn: asyncpg.Connection | None = None
        self.pool: asyncpg.Pool | None = None
        self.handlers: dict[str, Callable] = {}
        self.running = False
        self.shutdown_event = asyncio.Event()
        self._notification_queue: asyncio.Queue = asyncio.Queue(maxsize=1000)

    def register_handler(self, channel: str, handler: Callable) -> None:
        self.handlers[channel] = handler

    async def start(self) -> None:
        self.running = True
        self.pool = await asyncpg.create_pool(
            self.dsn,
            min_size=2,
            max_size=10,
            command_timeout=60,
        )

        # Start listener connection (separate from pool — LISTEN requires dedicated connection)
        await self._connect_listener()

        # Start worker tasks
        tasks = [
            asyncio.create_task(self._listen_loop()),
            asyncio.create_task(self._dispatch_loop()),
            asyncio.create_task(self._recovery_loop()),
        ]

        logger.info(f"Consumer {PROCESSOR_ID} started, listening on: {self.channels}")

        await asyncio.gather(*tasks)

    async def _connect_listener(self) -> None:
        """Establish dedicated connection for LISTEN commands."""
        self.conn = await asyncpg.connect(self.dsn)

        def _on_notification(conn, pid, channel, payload):
            """Called by asyncpg from the connection's receive loop."""
            try:
                parsed = json.loads(payload)
                event = NotificationEvent(
                    channel=channel,
                    payload=parsed,
                    event_id=parsed.get("event_id", 0),
                    entity_id=parsed.get("entity_id", ""),
                    entity_type=parsed.get("table", ""),
                    event_type=parsed.get("event_type", ""),
                )
                # Non-blocking put — drop if queue is full (backpressure)
                try:
                    self._notification_queue.put_nowait(event)
                except asyncio.QueueFull:
                    logger.warning(
                        f"Notification queue full, dropping event {event.event_id} "
                        f"on channel {channel}. Recovery loop will catch it."
                    )
            except json.JSONDecodeError as e:
                logger.error(f"Failed to parse notification payload: {payload!r}: {e}")

        self.conn.add_listener(None, _on_notification)  # None = all channels

        for channel in self.channels:
            await self.conn.execute(f"LISTEN {channel}")
            logger.debug(f"Listening on channel: {channel}")

    async def _listen_loop(self) -> None:
        """Keep listener connection alive with reconnection logic."""
        while self.running:
            try:
                if self.conn is None or self.conn.is_closed():
                    logger.warning("Listener connection lost, reconnecting...")
                    await asyncio.sleep(2)
                    await self._connect_listener()

                # Keep the connection alive — asyncpg delivers notifications
                # through the connection's internal receive loop; we just need
                # to hold the event loop open
                await asyncio.sleep(1)

            except asyncpg.PostgresConnectionStatusError:
                logger.exception("Connection error in listen loop")
                self.conn = None
                await asyncio.sleep(5)
            except asyncio.CancelledError:
                break
            except Exception:
                logger.exception("Unexpected error in listen loop")
                await asyncio.sleep(5)

    async def _dispatch_loop(self) -> None:
        """Pull from notification queue and invoke handlers."""
        while self.running:
            try:
                event = await asyncio.wait_for(
                    self._notification_queue.get(),
                    timeout=1.0,
                )
                handler = self.handlers.get(event.channel)
                if handler is None:
                    logger.warning(f"No handler for channel: {event.channel}")
                    continue

                # Claim the event in the database
                claimed = await self._claim_event(event.event_id)
                if not claimed:
                    logger.debug(f"Event {event.event_id} already claimed by another worker")
                    continue

                # Dispatch without blocking the queue
                asyncio.create_task(
                    self._run_handler(handler, event)
                )

            except asyncio.TimeoutError:
                continue
            except asyncio.CancelledError:
                break
            except Exception:
                logger.exception("Error in dispatch loop")

    async def _claim_event(self, event_id: int) -> bool:
        """
        Atomically claim an event for this processor.
        Returns True if successfully claimed, False if already taken.
        """
        async with self.pool.acquire() as conn:
            result = await conn.fetchval(
                """
                UPDATE ai_events
                SET status = 'processing',
                    processor_id = $1
                WHERE id = $2
                  AND status = 'notified'
                RETURNING id
                """,
                PROCESSOR_ID,
                event_id,
            )
            return result is not None

    async def _run_handler(self, handler: Callable, event: NotificationEvent) -> None:
        """Execute handler and record result."""
        start = time.monotonic()
        try:
            result = await handler(event, self.pool)
            elapsed = time.monotonic() - start

            async with self.pool.acquire() as conn:
                await conn.execute(
                    """
                    UPDATE ai_events
                    SET status = 'completed',
                        processed_at = now(),
                        result = $1
                    WHERE id = $2
                    """,
                    json.dumps({"elapsed_ms": int(elapsed * 1000), "result": result}),
                    event.event_id,
                )
        except Exception as exc:
            logger.exception(f"Handler failed for event {event.event_id}")
            async with self.pool.acquire() as conn:
                await conn.execute(
                    """
                    UPDATE ai_events
                    SET status = 'failed',
                        error = $1,
                        retry_count = retry_count + 1
                    WHERE id = $2
                    """,
                    str(exc),
                    event.event_id,
                )

    async def _recovery_loop(self) -> None:
        """
        Periodically scan for unprocessed events — handles the case where
        notifications were dropped (queue full, consumer was down, etc.)
        """
        while self.running:
            try:
                await asyncio.sleep(30)  # Check every 30 seconds

                async with self.pool.acquire() as conn:
                    for channel in self.channels:
                        rows = await conn.fetch(
                            "SELECT * FROM get_unprocessed_events($1, 60, 50)",
                            channel,
                        )
                        if rows:
                            logger.info(
                                f"Recovery: found {len(rows)} unprocessed events on {channel}"
                            )
                        for row in rows:
                            event = NotificationEvent(
                                channel=channel,
                                payload=dict(row["payload"]),
                                event_id=row["event_id"],
                                entity_id=str(row["entity_id"]),
                                entity_type=row["entity_type"],
                                event_type=row["payload"].get("operation", ""),
                            )
                            await self._notification_queue.put(event)

            except asyncio.CancelledError:
                break
            except Exception:
                logger.exception("Error in recovery loop")

    async def stop(self) -> None:
        self.running = False
        if self.conn:
            await self.conn.close()
        if self.pool:
            await self.pool.close()
        logger.info(f"Consumer {PROCESSOR_ID} stopped")

28.4 AI Handlers: Embeddings, LLM Responses, and Agent Routing

With the consumer infrastructure in place, the handlers contain the actual AI logic. Here are three complete handlers covering the most common patterns.

# handlers.py — AI processing handlers for each channel

import asyncio
import asyncpg
import json
import logging
from typing import Any

import anthropic
import tiktoken
from openai import AsyncOpenAI

from listener import NotificationEvent

logger = logging.getLogger(__name__)

openai_client = AsyncOpenAI(api_key="sk-...")
anthropic_client = anthropic.AsyncAnthropic(api_key="sk-ant-...")

EMBEDDING_MODEL = "text-embedding-3-small"
EMBEDDING_DIMENSIONS = 1536
CHAT_MODEL = "claude-3-5-sonnet-20241022"


# ── Handler 1: Document Embedding ──────────────────────────────────────────

async def handle_document_event(
    event: NotificationEvent,
    pool: asyncpg.Pool,
) -> dict:
    """
    Triggered when a document is inserted or updated.
    Generates embeddings and updates the document record.
    """
    doc_id = event.entity_id

    # Fetch the full document
    async with pool.acquire() as conn:
        doc = await conn.fetchrow(
            """
            SELECT id, title, body, metadata, tenant_id, embedding_model
            FROM documents
            WHERE id = $1
              AND status IN ('pending', 'indexed')
            FOR UPDATE SKIP LOCKED
            """,
            doc_id,
        )

    if doc is None:
        logger.info(f"Document {doc_id} not found or locked by another worker")
        return {"skipped": True}

    # Mark as processing
    async with pool.acquire() as conn:
        await conn.execute(
            "UPDATE documents SET status = 'processing', updated_at = now() WHERE id = $1",
            doc_id,
        )

    try:
        # Build the text to embed — title + body with separator
        text_to_embed = f"{doc['title']}\n\n{doc['body']}"

        # Truncate if needed (text-embedding-3-small supports up to 8191 tokens)
        encoding = tiktoken.get_encoding("cl100k_base")
        tokens = encoding.encode(text_to_embed)
        if len(tokens) > 8000:
            tokens = tokens[:8000]
            text_to_embed = encoding.decode(tokens)
            logger.warning(f"Document {doc_id} truncated to 8000 tokens for embedding")

        # Call OpenAI embeddings API
        response = await openai_client.embeddings.create(
            model=EMBEDDING_MODEL,
            input=text_to_embed,
            dimensions=EMBEDDING_DIMENSIONS,
        )
        embedding = response.data[0].embedding
        usage = response.usage

        # Write embedding back to document
        async with pool.acquire() as conn:
            await conn.execute(
                """
                UPDATE documents
                SET embedding       = $1::vector,
                    embedding_model = $2,
                    embedding_at    = now(),
                    indexed_at      = now(),
                    status          = 'indexed',
                    updated_at      = now()
                WHERE id = $3
                """,
                str(embedding),
                EMBEDDING_MODEL,
                doc_id,
            )

        logger.info(
            f"Embedded document {doc_id}: "
            f"{usage.total_tokens} tokens, model={EMBEDDING_MODEL}"
        )
        return {
            "embedded": True,
            "doc_id": doc_id,
            "tokens": usage.total_tokens,
            "model": EMBEDDING_MODEL,
        }

    except Exception as exc:
        # Roll back status to failed so recovery can retry
        async with pool.acquire() as conn:
            await conn.execute(
                """
                UPDATE documents
                SET status = 'failed',
                    updated_at = now()
                WHERE id = $1
                """,
                doc_id,
            )
        raise


# ── Handler 2: Conversational AI Response ──────────────────────────────────

async def handle_message_event(
    event: NotificationEvent,
    pool: asyncpg.Pool,
) -> dict:
    """
    Triggered when a user message is inserted.
    Fetches conversation history, calls LLM, inserts assistant response.
    """
    message_id = event.entity_id

    async with pool.acquire() as conn:
        # Fetch the triggering message
        msg = await conn.fetchrow(
            """
            SELECT m.id, m.conversation_id, m.tenant_id, m.role, m.content,
                   c.metadata AS conv_metadata
            FROM messages m
            JOIN conversations c ON c.id = m.conversation_id
            WHERE m.id = $1
              AND m.role = 'user'
            """,
            message_id,
        )

        if msg is None:
            return {"skipped": True, "reason": "message not found or not user role"}

        # Fetch recent conversation history (last 20 messages)
        history = await conn.fetch(
            """
            SELECT role, content
            FROM messages
            WHERE conversation_id = $1
            ORDER BY created_at ASC
            LIMIT 20
            """,
            msg["conversation_id"],
        )

    # Build message list for Anthropic
    messages = [
        {"role": row["role"], "content": row["content"]}
        for row in history
        if row["role"] in ("user", "assistant")
    ]

    # Extract system prompt from conversation metadata if present
    conv_metadata = msg["conv_metadata"] or {}
    system_prompt = conv_metadata.get(
        "system_prompt",
        "You are a helpful AI assistant. Be concise and accurate.",
    )

    try:
        response = await anthropic_client.messages.create(
            model=CHAT_MODEL,
            max_tokens=2048,
            system=system_prompt,
            messages=messages,
        )

        assistant_content = response.content[0].text
        input_tokens = response.usage.input_tokens
        output_tokens = response.usage.output_tokens

        # Insert the assistant response — this will also fire the message trigger,
        # but the trigger filters out non-user roles, so no infinite loop.
        async with pool.acquire() as conn:
            new_msg_id = await conn.fetchval(
                """
                INSERT INTO messages (
                    conversation_id, tenant_id, role, content,
                    content_tokens, metadata
                ) VALUES ($1, $2, 'assistant', $3, $4, $5)
                RETURNING id
                """,
                msg["conversation_id"],
                msg["tenant_id"],
                assistant_content,
                output_tokens,
                json.dumps({
                    "model": CHAT_MODEL,
                    "input_tokens": input_tokens,
                    "output_tokens": output_tokens,
                    "in_response_to": message_id,
                }),
            )

            # Update conversation timestamp
            await conn.execute(
                "UPDATE conversations SET updated_at = now() WHERE id = $1",
                msg["conversation_id"],
            )

        logger.info(
            f"Generated response for conversation {msg['conversation_id']}: "
            f"{input_tokens} in / {output_tokens} out tokens"
        )
        return {
            "conversation_id": str(msg["conversation_id"]),
            "response_message_id": str(new_msg_id),
            "input_tokens": input_tokens,
            "output_tokens": output_tokens,
        }

    except anthropic.RateLimitError as exc:
        logger.warning(f"Rate limited on conversation {msg['conversation_id']}: {exc}")
        raise
    except anthropic.APIError as exc:
        logger.error(f"Anthropic API error for message {message_id}: {exc}")
        raise


# ── Handler 3: Agent Task Routing ──────────────────────────────────────────

AGENT_REGISTRY: dict[str, str] = {
    "document_qa":      "ai_agent_doc_qa",
    "web_search":       "ai_agent_web_search",
    "code_review":      "ai_agent_code",
    "data_analysis":    "ai_agent_data",
    "email_draft":      "ai_agent_email",
}


async def handle_agent_task_event(
    event: NotificationEvent,
    pool: asyncpg.Pool,
) -> dict:
    """
    Triggered when a new agent task is queued.
    Routes to the appropriate agent sub-channel via NOTIFY.
    """
    task_id = event.entity_id

    async with pool.acquire() as conn:
        task = await conn.fetchrow(
            """
            SELECT id, agent_id, task_type, input, priority, tenant_id,
                   parent_task_id, retry_count, max_retries
            FROM agent_tasks
            WHERE id = $1
              AND status = 'queued'
            FOR UPDATE SKIP LOCKED
            """,
            task_id,
        )

    if task is None:
        return {"skipped": True, "reason": "task not found, locked, or not queued"}

    task_type = task["task_type"]
    agent_channel = AGENT_REGISTRY.get(task_type)

    if agent_channel is None:
        logger.error(f"No agent registered for task type: {task_type}")
        async with pool.acquire() as conn:
            await conn.execute(
                """
                UPDATE agent_tasks
                SET status = 'failed',
                    error = $1,
                    completed_at = now()
                WHERE id = $2
                """,
                f"No agent registered for task type: {task_type}",
                task_id,
            )
        return {"routed": False, "reason": "unknown task type"}

    # Fan out to agent-specific channel
    notify_payload = json.dumps({
        "task_id": str(task["id"]),
        "task_type": task_type,
        "priority": task["priority"],
        "tenant_id": str(task["tenant_id"]) if task["tenant_id"] else None,
        "parent_task_id": str(task["parent_task_id"]) if task["parent_task_id"] else None,
    })

    async with pool.acquire() as conn:
        await conn.execute(
            "SELECT pg_notify($1, $2)",
            agent_channel,
            notify_payload,
        )
        # Update task status to indicate it's been dispatched
        await conn.execute(
            """
            UPDATE agent_tasks
            SET status = 'running',
                started_at = now()
            WHERE id = $1
            """,
            task_id,
        )

    logger.info(f"Routed task {task_id} (type={task_type}) to channel {agent_channel}")
    return {
        "routed": True,
        "task_id": str(task_id),
        "agent_channel": agent_channel,
    }

@app.get("/conversations/{conv_id}/stream")

    conv_id: uuid.UUID,
    pool: asyncpg.Pool = Depends(get_db),
):
    """
    Server-Sent Events endpoint. Uses a dedicated LISTEN connection
    to push new messages to the client as they arrive.
    """
    async def event_generator():
        conn = await asyncpg.connect(DATABASE_URL)
        message_queue: asyncio.Queue = asyncio.Queue()

        def on_notify(c, pid, channel, payload):
            try:
                data = json.loads(payload)
                if str(data.get("conversation_id")) == str(conv_id):
                    message_queue.put_nowait(data)
            except Exception:
                pass

        conn.add_listener(None, on_notify)
        await conn.execute("LISTEN ai_messages")

        try:
            yield f"data: {json.dumps({'type': 'connected', 'conv_id': str(conv_id)})}\n\n"
            while True:
                try:
                    event = await asyncio.wait_for(message_queue.get(), timeout=30.0)
                    # Fetch the actual message content
                    async with pool.acquire() as db_conn:
                        msg_row = await db_conn.fetchrow(
                            "SELECT id, role, content, created_at FROM messages WHERE id = $1",
                            event.get("entity_id"),
                        )
                    if msg_row:
                        payload = {
                            "type": "message",
                            "id": str(msg_row["id"]),
                            "role": msg_row["role"],
                            "content": msg_row["content"],
                            "created_at": msg_row["created_at"].isoformat(),
                        }
                        yield f"data: {json.dumps(payload)}\n\n"
                except asyncio.TimeoutError:
                    # Keepalive comment
                    yield ": keepalive\n\n"
        finally:
            await conn.close()

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )

28.6 Scaling with Celery and Redis

LISTEN/NOTIFY handles the signal; for CPU-heavy AI workloads — large batch embeddings, multi-step agent pipelines, image processing alongside LLM calls — you want Celery workers handling the actual execution. The integration is straightforward: the LISTEN/NOTIFY consumer receives the notification and immediately enqueues a Celery task rather than executing inline.

def generate_embedding_task(self, doc_id: str, event_id: int):
    """
    Synchronous Celery task that generates and stores a document embedding.
    Celery workers are sync by default; use asyncio.run for async AI clients.
    """

    from handlers import handle_document_event
    from listener import NotificationEvent

async def handle_document_via_celery(
    event: NotificationEvent,
    pool: asyncpg.Pool,
) -> dict:
    """
    Lightweight handler: receives notification, enqueues Celery task immediately.
    The actual embedding work happens in a Celery worker process.
    """
    task = generate_embedding_task.apply_async(
        args=[event.entity_id, event.event_id],
        priority=5,           # Celery task priority (0=high, 9=low)
        countdown=0,          # No delay

    )
    return {"celery_task_id": task.id, "doc_id": event.entity_id}

    task = generate_llm_response_task.apply_async(
        args=[event.entity_id, event.event_id],
        priority=3,   # LLM responses get higher priority than embeddings

The result is a clean separation of concerns: PostgreSQL owns the signal and the data, the LISTEN/NOTIFY consumer is a thin routing layer, and Celery workers handle the heavy lifting. The ai_events table still tracks every event regardless of which execution path was taken.

28.7 Multi-Tenant Isolation and Channel Naming

In SaaS applications with multiple tenants, you have two options for channel naming: a single shared channel with tenant ID in the payload (simpler), or per-tenant channels (stronger isolation, more connections). The shared channel approach is almost always the right starting point.

-- Shared channel approach: tenant filtering happens in the consumer
-- (already shown above — tenant_id is in the payload)

-- Per-tenant channels: useful when tenants need different processing SLAs
CREATE OR REPLACE FUNCTION notify_tenant_channel()
RETURNS TRIGGER AS $$
DECLARE
    v_channel TEXT;
    v_payload TEXT;
BEGIN
    -- Route to tenant-specific channel
    v_channel := 'ai_tenant_' || replace(NEW.tenant_id::text, '-', '_');

    v_payload := jsonb_build_object(
        'id', NEW.id,
        'tenant_id', NEW.tenant_id,
        'event', TG_OP,
        'table', TG_TABLE_NAME
    )::text;

    PERFORM pg_notify(v_channel, v_payload);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
# Dynamic channel subscription for per-tenant isolation
class TenantAwareConsumer(AIEventConsumer):
    """
    Extends AIEventConsumer to subscribe to tenant-specific channels
    dynamically as tenants are onboarded.
    """

    async def subscribe_tenant(self, tenant_id: str) -> None:
        """Subscribe to a tenant's channel at runtime."""
        channel = f"ai_tenant_{tenant_id.replace('-', '_')}"
        if channel not in self.channels:
            self.channels.append(channel)
            if self.conn and not self.conn.is_closed():
                await self.conn.execute(f"LISTEN {channel}")
                self.handlers[channel] = self.handlers.get(
                    "ai_documents",  # Reuse default handler
                    lambda e, p: None,
                )
                logger.info(f"Subscribed to tenant channel: {channel}")

    async def unsubscribe_tenant(self, tenant_id: str) -> None:
        """Unsubscribe from a tenant's channel when tenant is deactivated."""
        channel = f"ai_tenant_{tenant_id.replace('-', '_')}"
        if channel in self.channels:
            self.channels.remove(channel)
            if self.conn and not self.conn.is_closed():
                await self.conn.execute(f"UNLISTEN {channel}")
            self.handlers.pop(channel, None)
            logger.info(f"Unsubscribed from tenant channel: {channel}")

One practical limit to keep in mind: each PostgreSQL connection can LISTEN on many channels, but each LISTEN does register a server-side listener. At very large tenant counts (thousands), you'll hit practical limits and should consolidate back to shared channels with payload-based routing.

28.8 Monitoring, Observability, and Dead-Letter Handling

Production event-driven pipelines need visibility into what's happening. The ai_events table is your primary observability instrument.

-- Operations dashboard view
CREATE OR REPLACE VIEW ai_event_metrics AS
SELECT
    channel,
    status,
    date_trunc('hour', notified_at) AS hour,
    count(*)                         AS event_count,
    avg(extract(epoch FROM (processed_at - notified_at)) * 1000)::int AS avg_latency_ms,
    max(extract(epoch FROM (processed_at - notified_at)) * 1000)::int AS max_latency_ms,
    count(*) FILTER (WHERE retry_count > 0)  AS retried_count,
    count(*) FILTER (WHERE status = 'failed') AS failed_count
FROM ai_events
WHERE notified_at > now() - interval '24 hours'
GROUP BY channel, status, hour
ORDER BY hour DESC, channel;

-- Dead letter: events that exhausted retries
CREATE OR REPLACE VIEW ai_dead_letter AS
SELECT
    id,
    channel,
    entity_type,
    entity_id,
    event_type,
    payload,
    error,
    retry_count,
    notified_at,
    extract(epoch FROM (now() - notified_at)) / 3600 AS age_hours
FROM ai_events
WHERE status = 'failed'
  AND retry_count >= 5
ORDER BY notified_at DESC;

-- Stuck processing events (claimed but never completed)
CREATE OR REPLACE VIEW ai_stuck_events AS
SELECT
    id,
    channel,
    entity_id,
    processor_id,
    status,
    notified_at,
    extract(epoch FROM (now() - notified_at)) / 60 AS age_minutes
FROM ai_events
WHERE status = 'processing'
  AND notified_at < now() - interval '5 minutes'
ORDER BY notified_at;
# monitoring.py — Prometheus metrics for the consumer

from prometheus_client import Counter, Histogram, Gauge, start_http_server
import time

EVENTS_RECEIVED = Counter(
    "ai_events_received_total",
    "Total NOTIFY events received",
    ["channel"],
)
EVENTS_PROCESSED = Counter(
    "ai_events_processed_total",
    "Total events successfully processed",
    ["channel"],
)
EVENTS_FAILED = Counter(
    "ai_events_failed_total",
    "Total events that failed processing",
    ["channel"],
)
PROCESSING_LATENCY = Histogram(
    "ai_event_processing_latency_seconds",
    "End-to-end latency from notification to completion",
    ["channel"],
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0, 30.0, 60.0],
)
QUEUE_DEPTH = Gauge(
    "ai_notification_queue_depth",
    "Current depth of the in-memory notification queue",
)
PENDING_RECOVERY = Gauge(
    "ai_pending_recovery_events",
    "Events awaiting recovery processing",
    ["channel"],
)


class InstrumentedConsumer(AIEventConsumer):
    """AIEventConsumer with Prometheus instrumentation."""

    async def _dispatch_loop(self) -> None:
        while self.running:
            try:
                QUEUE_DEPTH.set(self._notification_queue.qsize())
                event = await asyncio.wait_for(
                    self._notification_queue.get(),
                    timeout=1.0,
                )
                EVENTS_RECEIVED.labels(channel=event.channel).inc()

                handler = self.handlers.get(event.channel)
                if handler is None:
                    logger.warning(f"No handler for channel: {event.channel}")
                    continue

                claimed = await self._claim_event(event.event_id)
                if not claimed:
                    logger.debug(f"Event {event.event_id} already claimed")
                    continue

                asyncio.create_task(
                    self._run_instrumented_handler(handler, event)
                )

            except asyncio.TimeoutError:
                QUEUE_DEPTH.set(self._notification_queue.qsize())
                continue
            except asyncio.CancelledError:
                break
            except Exception:
                logger.exception("Error in dispatch loop")

    async def _run_instrumented_handler(
        self, handler, event: NotificationEvent
    ) -> None:
        start = time.monotonic()
        try:
            result = await handler(event, self.pool)
            elapsed = time.monotonic() - start
            EVENTS_PROCESSED.labels(channel=event.channel).inc()
            PROCESSING_LATENCY.labels(channel=event.channel).observe(elapsed)

            async with self.pool.acquire() as conn:
                await conn.execute(
                    """
                    UPDATE ai_events
                    SET status = 'completed',
                        processed_at = now(),
                        result = $1
                    WHERE id = $2
                    """,
                    json.dumps({"elapsed_ms": int(elapsed * 1000), "result": result}),
                    event.event_id,
                )
        except Exception as exc:
            EVENTS_FAILED.labels(channel=event.channel).inc()
            logger.exception(f"Handler failed for event {event.event_id}")
            async with self.pool.acquire() as conn:
                await conn.execute(
                    """
                    UPDATE ai_events
                    SET status = 'failed',
                        error = $1,
                        retry_count = retry_count + 1
                    WHERE id = $2
                    """,
                    str(exc),
                    event.event_id,
                )

For alerting, wire up your monitoring system to check these conditions:

  • → `ai_stuck_events` count > 0 for more than 10 minutes → worker may be hung
  • → `ai_dead_letter` growing rapidly → handler logic has a systematic bug
  • → `ai_notification_queue_depth` consistently near `maxsize` → add consumer replicas or move to Celery
  • → `ai_events_failed_total` rate spike → check LLM API status pages
    • -- Periodic maintenance: archive old completed events, reset stuck ones
CREATE OR REPLACE PROCEDURE maintain_ai_events()
LANGUAGE plpgsql AS $$
BEGIN
    -- Reset stuck processing events so recovery loop can retry them
    UPDATE ai_events
    SET status = 'notified',
        processor_id = NULL
    WHERE status = 'processing'
      AND notified_at < now() - interval '10 minutes';

    -- Archive completed events older than 7 days into a cold table
    -- (assumes ai_events_archive exists with same schema)
    INSERT INTO ai_events_archive
    SELECT * FROM ai_events
    WHERE status = 'completed'
      AND processed_at < now() - interval '7 days';

    DELETE FROM ai_events
    WHERE status = 'completed'
      AND processed_at < now() - interval '7 days';

    -- Mark truly abandoned events
    UPDATE ai_events
    SET status = 'abandoned'
    WHERE status = 'failed'
      AND retry_count >= 5
      AND notified_at < now() - interval '24 hours';
END;
$$;

    28.9 Production Deployment Patterns

    Running multiple consumer instances: The _claim_event update (WHERE status = 'notified') is atomic — only one consumer wins the row. You can run as many consumer processes as you like against the same PostgreSQL cluster; each LISTEN connection receives the notification independently, but only the first to claim the event in ai_events does the work.     Connection count management: Each consumer process holds one dedicated LISTEN connection plus a pool. With three consumer replicas and a pool of min 2 / max 10, you're looking at three dedicated connections plus up to 30 pool connections — 33 connections per consumer group. Factor this against max_connections in your PostgreSQL configuration. For high connection counts, use PgBouncer in session mode (transaction mode does not support LISTEN/NOTIFY).

    28.10 SQL Server Equivalent: Service Broker

    SQL Server's equivalent to PostgreSQL LISTEN/NOTIFY is Service Broker — a persistent, transactional message queuing system built into the database engine. It's significantly more capable (durable, ordered, guaranteed delivery) but also more complex to set up.

    -- SQL Server: Service Broker setup for AI event routing

-- Enable Service Broker on the database
ALTER DATABASE AiApp SET ENABLE_BROKER WITH ROLLBACK IMMEDIATE;

-- Create message type
CREATE MESSAGE TYPE [//AiApp/DocumentEvent]
    VALIDATION = WELL_FORMED_XML;

-- Create contract
CREATE CONTRACT [//AiApp/DocumentContract]
    ([//AiApp/DocumentEvent] SENT BY INITIATOR);

-- Create queues
CREATE QUEUE DocumentEventQueue
    WITH STATUS = ON,
         RETENTION = OFF,
         ACTIVATION (
             STATUS = ON,
             PROCEDURE_NAME = dbo.ProcessDocumentEvent,
             MAX_QUEUE_READERS = 5,
             EXECUTE AS OWNER
         );

CREATE QUEUE DocumentEventResponseQueue
    WITH STATUS = ON;

-- Create services
CREATE SERVICE [//AiApp/DocumentEventService]
    ON QUEUE DocumentEventQueue
    ([//AiApp/DocumentContract]);

CREATE SERVICE [//AiApp/DocumentEventResponseService]
    ON QUEUE DocumentEventResponseQueue
    ([//AiApp/DocumentContract]);

-- Trigger to send Service Broker message on document insert
CREATE OR ALTER TRIGGER trg_Documents_SBNotify
ON dbo.Documents
AFTER INSERT, UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @conv_handle UNIQUEIDENTIFIER;
    DECLARE @message_body XML;
    DECLARE @doc_id UNIQUEIDENTIFIER;
    DECLARE @tenant_id UNIQUEIDENTIFIER;

    SELECT @doc_id = i.Id, @tenant_id = i.TenantId
    FROM inserted i;

    -- Only proceed if content changed or new record
    IF NOT EXISTS (
        SELECT 1 FROM deleted d
        JOIN inserted i ON d.Id = i.Id
        WHERE d.Body = i.Body AND d.Status = i.Status
    ) OR NOT EXISTS (SELECT 1 FROM deleted)
    BEGIN
        SET @message_body = (
            SELECT
                @doc_id   AS DocumentId,
                @tenant_id AS TenantId,
                'INSERT'  AS Operation
            FOR XML PATH('DocumentEvent'), ROOT('Root')
        );

        BEGIN DIALOG CONVERSATION @conv_handle
            FROM SERVICE [//AiApp/DocumentEventResponseService]
            TO SERVICE '//AiApp/DocumentEventService'
            ON CONTRACT [//AiApp/DocumentContract]
            WITH ENCRYPTION = OFF,
                 LIFETIME = 3600;

        SEND ON CONVERSATION @conv_handle
            MESSAGE TYPE [//AiApp/DocumentEvent]
            (@message_body);
    END;
END;

-- Activation stored procedure: called automatically by Service Broker
-- when messages arrive in the queue
CREATE OR ALTER PROCEDURE dbo.ProcessDocumentEvent
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @conv_handle UNIQUEIDENTIFIER;
    DECLARE @message_type NVARCHAR(256);
    DECLARE @message_body XML;
    DECLARE @doc_id UNIQUEIDENTIFIER;

    WHILE (1 = 1)
    BEGIN
        BEGIN TRANSACTION;

        WAITFOR (
            RECEIVE TOP(1)
                @conv_handle  = conversation_handle,
                @message_type = message_type_name,
                @message_body = CAST(message_body AS XML)
            FROM DocumentEventQueue
        ), TIMEOUT 5000;

        IF @@ROWCOUNT = 0
        BEGIN
            ROLLBACK;
            BREAK;
        END;

        IF @message_type = '//AiApp/DocumentEvent'
        BEGIN
            SET @doc_id = @message_body.value('(/Root/DocumentEvent/DocumentId)[1]', 'UNIQUEIDENTIFIER');

            -- Mark document as processing
            UPDATE dbo.Documents
            SET Status = 'processing',
                UpdatedAt = SYSUTCDATETIME()
            WHERE Id = @doc_id
              AND Status IN ('pending', 'indexed');

            -- Log the event (external process picks it up for LLM call)
            INSERT INTO dbo.AiEventLog (
                EventType, EntityType, EntityId, QueuedAt, Status
            ) VALUES (
                'EMBED_REQUEST', 'Document', @doc_id, SYSUTCDATETIME(), 'queued'
            );

            END CONVERSATION @conv_handle;
        END
        ELSE IF @message_type = 'http://schemas.microsoft.com/SQL/ServiceBroker/EndDialog'
        BEGIN
            END CONVERSATION @conv_handle;
        END
        ELSE IF @message_type = 'http://schemas.microsoft.com/SQL/ServiceBroker/Error'
        BEGIN
            -- Log error and end conversation
            INSERT INTO dbo.AiEventLog (EventType, EntityType, EntityId, QueuedAt, Status, ErrorMessage)
            VALUES ('BROKER_ERROR', 'System', NEWID(), SYSUTCDATETIME(), 'failed',
                    @message_body.value('(/Error/Description)[1]', 'NVARCHAR(4000)'));
            END CONVERSATION @conv_handle;
        END;

        COMMIT;
    END;
END;

    The key differences between PostgreSQL LISTEN/NOTIFY and SQL Server Service Broker are worth summarizing clearly:

    | Aspect | PostgreSQL LISTEN/NOTIFY | SQL Server Service Broker |

    |---|---|---|

    | Durability | None — fire and forget | Full — messages persisted in queue table |

    | Delivery guarantee | At-most-once | Exactly-once (with proper ack) |

    | Payload size | 8,000 bytes | Limited by row size (~2GB theoretical) |

    | Setup complexity | Trivial | Moderate (services, contracts, queues) |

    | External consumer | Required | Optional — activation procs run in-process |

    | Ordering | Not guaranteed | Per-conversation ordering guaranteed |

    | Multi-database | Single database only | Cross-database and cross-server |

    | Recovery path needed | Yes — event log pattern | No — queue is the durable store |

    For AI applications on SQL Server, Service Broker's durability means you don't need the ai_events event log pattern we built for PostgreSQL — the queue itself is the durable record. The activation stored procedure replaces the Python consumer for in-database processing, though for LLM API calls you'll still need an external process reading from AiEventLog.

    Key Takeaways

  • → **LISTEN/NOTIFY is a signal layer, not a delivery layer.** Its transactional delivery guarantee — notifications only fire on commit — eliminates the consistency gap between data changes and AI processing triggers, but you must pair it with a durable event log (`ai_events`) to handle cases where the consumer is down or the notification queue overflows.
  • → **The trigger-log-notify pattern provides both low latency and recoverability.** Triggers write to `ai_events` and issue `pg_notify` atomically within the committing transaction. The LISTEN consumer gets sub-second delivery when connected; the recovery loop finds unprocessed events when it wasn't. Neither path requires application code changes.
  • → **Consumer-side claiming with `FOR UPDATE SKIP LOCKED` semantics enables safe horizontal scaling.** Multiple consumer replicas each receive every notification, but the atomic `UPDATE ... WHERE status = 'notified' RETURNING id` pattern ensures only one worker processes each event. Scale consumers freely without coordination infrastructure.
  • → **LISTEN/NOTIFY composes cleanly with Celery and Redis for heavy workloads.** The consumer becomes a thin routing layer — it claims the event and immediately enqueues a Celery task. This gives you PostgreSQL's transactional trigger guarantees at the entry point and Celery's worker scaling, retry logic, and task routing for the actual LLM and embedding work.
  • → **SQL Server Service Broker provides stronger built-in guarantees at the cost of setup complexity.** Unlike LISTEN/NOTIFY, Service Broker persists messages in queue tables, guaranteeing delivery even if no consumer is connected. For SQL Server AI pipelines, this removes the need for a separate event log but requires defining message types, contracts, and services before any data flows.
