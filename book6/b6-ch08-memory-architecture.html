Chapter 8: Short-Term vs Long-Term Memory Architecture

Memory is the difference between a chatbot and an intelligent assistant. Without it, every conversation starts from zero — the AI has no context about who you are, what you've discussed, or what you prefer. With well-designed memory architecture, an AI application can maintain coherent multi-turn conversations, recall decisions made weeks ago, learn user preferences over time, and surface relevant past context at exactly the right moment. PostgreSQL, with its combination of relational integrity, JSONB flexibility, pgvector similarity search, and real-time notification systems, is uniquely positioned to be the memory backbone for production AI applications. This chapter walks through building a complete two-tier memory system: short-term conversation buffers that keep current sessions coherent, and long-term episodic and semantic memory that persists knowledge across sessions and scales to millions of users.

---

The Two-Tier Memory Model

Human cognition operates across multiple time scales. Working memory holds what you're thinking about right now. Long-term memory stores experiences, facts, and learned patterns. AI applications need the same architecture — and conflating the two tiers is one of the most common mistakes in early AI application design.

Short-term memory serves the active conversation. It answers the question: *what has been said in this session?* It needs to be fast, ordered, and bounded. You don't need to store every conversation forever — you need the last N turns accessible in milliseconds. This is your conversation history buffer.

Long-term memory serves the persistent self. It answers the question: *what do we know about this user, this domain, and past decisions?* It can be slower to retrieve but needs to be semantically searchable. You can't retrieve it by position — you retrieve it by relevance. This is your episodic memory, your user profile, and your knowledge base.

The failure mode of conflating these is obvious in production: either you pass 100,000 tokens of conversation history into every LLM call (expensive, slow, and often irrelevant), or you throw away context between sessions and users feel unrecognized.

graph TD
    U[User message] --> ST[Short-term memory: ordered, bounded, session-scoped]
    U --> Q[Embed message]
    Q --> LT[Long-term memory: pgvector similarity search, user-scoped]
    ST --> CTX[Assembled LLM context]
    LT --> CTX
    CTX --> LLM[LLM call]
    LLM --> WRITE[New turn written back]
    WRITE --> ST
    WRITE -->|consolidation job| LT

*Short-term memory answers "what was just said"; long-term memory answers "what do we know" — both feed the same context assembly step, but retrieved differently.*

Here is the foundational schema that separates these two concerns cleanly:

This schema draws a hard line between the two memory tiers. Conversation messages are relational — ordered by sequence, linked to sessions and users, queryable by position. Memory entries are semantic — embedded, importance-ranked, tagged, and searchable by similarity.

Building the Short-Term Memory Layer

Short-term memory has two jobs: feed the LLM the right context for the current conversation, and do it fast enough that users don't notice the overhead. The implementation involves a conversation buffer that selects recent messages, respects token limits, and serializes cleanly into the format each LLM API expects.

The token budget is the core constraint. GPT-4o has a 128K context window; Claude 3.5 Sonnet has 200K. But sending 100K tokens of history on every turn is expensive and slow. A practical short-term buffer targets 4,000–8,000 tokens for conversation history, leaving room for the system prompt, retrieved long-term memories, and the actual response.

-- Short-term memory retrieval functions

-- Get recent messages for a session, with token budget control
CREATE OR REPLACE FUNCTION get_session_context(
    p_session_id    UUID,
    p_max_messages  INTEGER DEFAULT 20,
    p_max_tokens    INTEGER DEFAULT 6000
)
RETURNS TABLE (
    message_id      UUID,
    sequence_number INTEGER,
    role            TEXT,
    content         TEXT,
    tool_calls      JSONB,
    tool_results    JSONB,
    created_at      TIMESTAMPTZ,
    cumulative_tokens INTEGER
) AS $$
BEGIN
    RETURN QUERY
    WITH ranked_messages AS (
        SELECT
            cm.message_id,
            cm.sequence_number,
            cm.role,
            cm.content,
            cm.tool_calls,
            cm.tool_results,
            cm.created_at,
            cm.content_tokens,
            ROW_NUMBER() OVER (ORDER BY cm.sequence_number DESC) AS rn
        FROM conversation_messages cm
        WHERE cm.session_id = p_session_id
        ORDER BY cm.sequence_number DESC
        LIMIT p_max_messages
    ),
    with_cumulative AS (
        SELECT
            rm.*,
            SUM(COALESCE(rm.content_tokens, LENGTH(rm.content) / 4))
                OVER (ORDER BY rm.rn ASC) AS cum_tokens
        FROM ranked_messages rm
    )
    SELECT
        wc.message_id,
        wc.sequence_number,
        wc.role,
        wc.content,
        wc.tool_calls,
        wc.tool_results,
        wc.created_at,
        wc.cum_tokens::INTEGER AS cumulative_tokens
    FROM with_cumulative wc
    WHERE wc.cum_tokens <= p_max_tokens
    ORDER BY wc.sequence_number ASC;
END;
$$ LANGUAGE plpgsql STABLE;

-- Append a message and update session counters atomically
CREATE OR REPLACE FUNCTION append_message(
    p_session_id    UUID,
    p_user_id       UUID,
    p_role          TEXT,
    p_content       TEXT,
    p_model_used    TEXT DEFAULT NULL,
    p_latency_ms    INTEGER DEFAULT NULL,
    p_tool_calls    JSONB DEFAULT NULL,
    p_tool_results  JSONB DEFAULT NULL,
    p_metadata      JSONB DEFAULT '{}'
)
RETURNS UUID AS $$
DECLARE
    v_sequence      INTEGER;
    v_message_id    UUID;
    v_token_estimate INTEGER;
BEGIN
    -- Get next sequence number with row lock to prevent race conditions
    SELECT COALESCE(MAX(sequence_number), 0) + 1
    INTO v_sequence
    FROM conversation_messages
    WHERE session_id = p_session_id
    FOR UPDATE;

    -- Rough token estimate: 4 chars ≈ 1 token
    v_token_estimate := CEIL(LENGTH(p_content)::FLOAT / 4);

    INSERT INTO conversation_messages (
        session_id, user_id, sequence_number, role, content,
        content_tokens, model_used, latency_ms,
        tool_calls, tool_results, metadata
    )
    VALUES (
        p_session_id, p_user_id, v_sequence, p_role, p_content,
        v_token_estimate, p_model_used, p_latency_ms,
        p_tool_calls, p_tool_results, p_metadata
    )
    RETURNING message_id INTO v_message_id;

    -- Update session counters
    UPDATE conversation_sessions
    SET
        last_message_at = NOW(),
        message_count   = message_count + 1,
        total_tokens    = total_tokens + v_token_estimate
    WHERE session_id = p_session_id;

    RETURN v_message_id;
END;
$$ LANGUAGE plpgsql;

-- Summarize a session when it grows too long (called before archiving)
CREATE TABLE session_summaries (

Now the Python layer that sits on top of this schema. This is where short-term memory gets wired into actual LLM calls:

# short_term_memory.py
# Full short-term memory implementation with OpenAI and Claude support

import asyncio
from datetime import datetime, timezone
from typing import Optional
from uuid import UUID

import asyncpg
import tiktoken
from openai import AsyncOpenAI
import anthropic

# Initialize clients
openai_client = AsyncOpenAI()
anthropic_client = anthropic.Anthropic()


class ConversationMemory:
    """
    Manages short-term conversation memory backed by PostgreSQL.
    Handles session creation, message persistence, and context assembly.
    """

    def __init__(self, pool: asyncpg.Pool, max_context_tokens: int = 6000):
        self.pool = pool
        self.max_context_tokens = max_context_tokens
        self.encoder = tiktoken.encoding_for_model("gpt-4o")

    def count_tokens(self, text: str) -> int:
        return len(self.encoder.encode(text))

    async def get_or_create_session(
        self, user_external_id: str, session_id: Optional[str] = None
    ) -> tuple[str, str]:
        """
        Returns (user_id, session_id). Creates user and session if needed.
        """
        async with self.pool.acquire() as conn:
            # Upsert user
            user_row = await conn.fetchrow(
                """
                INSERT INTO users (external_id)
                VALUES ($1)
                ON CONFLICT (external_id) DO UPDATE
                    SET last_active_at = NOW()
                RETURNING user_id
                """,
                user_external_id,
            )
            user_id = str(user_row["user_id"])

            # Use existing session or create new one
            if session_id:
                session_row = await conn.fetchrow(
                    "SELECT session_id FROM conversation_sessions WHERE session_id = $1",
                    UUID(session_id),
                )
                if session_row:
                    return user_id, session_id

            # Create new session
            session_row = await conn.fetchrow(
                """
                INSERT INTO conversation_sessions (user_id)
                VALUES ($1::uuid)
                RETURNING session_id
                """,
                user_id,
            )
            return user_id, str(session_row["session_id"])

    async def load_context(self, session_id: str) -> list[dict]:
        """
        Load recent messages formatted for LLM APIs (OpenAI/Anthropic format).
        Respects token budget via the database function.
        """
        async with self.pool.acquire() as conn:
            rows = await conn.fetch(
                """
                SELECT role, content, tool_calls, tool_results, sequence_number
                FROM get_session_context($1::uuid, $2, $3)
                ORDER BY sequence_number ASC
                """,
                UUID(session_id),
                20,
                self.max_context_tokens,
            )

        messages = []
        for row in rows:
            msg = {"role": row["role"], "content": row["content"]}

            # Reconstruct tool call messages for agent conversations
            if row["tool_calls"]:
                msg["tool_calls"] = row["tool_calls"]
            if row["tool_results"] and row["role"] == "tool":
                msg["content"] = row["tool_results"]

            messages.append(msg)

        return messages

    async def save_message(
        self,
        session_id: str,
        user_id: str,
        role: str,
        content: str,
        model_used: Optional[str] = None,
        latency_ms: Optional[int] = None,
        metadata: Optional[dict] = None,
    ) -> str:
        """Save a message and return its message_id."""
        async with self.pool.acquire() as conn:
            message_id = await conn.fetchval(
                """
                SELECT append_message(
                    $1::uuid, $2::uuid, $3, $4, $5, $6, NULL, NULL, $7
                )
                """,
                UUID(session_id),
                UUID(user_id),
                role,
                content,
                model_used,
                latency_ms,
                metadata or {},
            )
        return str(message_id)

    async def chat_with_memory(
        self,
        user_external_id: str,
        user_message: str,
        session_id: Optional[str] = None,
        system_prompt: str = "You are a helpful assistant.",
        model: str = "gpt-4o",
    ) -> tuple[str, str, str]:
        """
        Full chat turn with memory. Returns (response_text, session_id, message_id).
        Loads context from DB → calls LLM → saves both messages to DB.
        """
        user_id, session_id = await self.get_or_create_session(
            user_external_id, session_id
        )

        # Save user message first
        await self.save_message(session_id, user_id, "user", user_message)

        # Load conversation context
        history = await self.load_context(session_id)

        # Build messages for API call
        messages = history  # already includes the user message we just saved

        start_time = datetime.now(timezone.utc)

        if model.startswith("gpt") or model.startswith("o"):
            # OpenAI path
            response = await openai_client.chat.completions.create(
                model=model,
                messages=[{"role": "system", "content": system_prompt}] + messages,
                temperature=0.7,
            )
            reply = response.choices[0].message.content
            finish_reason = response.choices[0].finish_reason

        elif model.startswith("claude"):
            # Anthropic path — system prompt is separate
            response = anthropic_client.messages.create(
                model=model,
                max_tokens=2048,
                system=system_prompt,
                messages=messages,
            )
            reply = response.content[0].text
            finish_reason = response.stop_reason

        else:
            raise ValueError(f"Unsupported model: {model}")

        latency_ms = int(
            (datetime.now(timezone.utc) - start_time).total_seconds() * 1000
        )

        # Save assistant response
        message_id = await self.save_message(
            session_id,
            user_id,
            "assistant",
            reply,
            model_used=model,
            latency_ms=latency_ms,
            metadata={"finish_reason": finish_reason},
        )

        return reply, session_id, message_id


# FastAPI endpoint wiring
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()


class ChatRequest(BaseModel):
    user_id: str
    message: str
    session_id: Optional[str] = None
    model: str = "gpt-4o"


class ChatResponse(BaseModel):
    reply: str
    session_id: str
    message_id: str


@app.post("/chat", response_model=ChatResponse)
async def chat_endpoint(request: ChatRequest):
    """Chat endpoint with automatic short-term memory management."""
    # pool is set up at app startup via lifespan
    memory = ConversationMemory(app.state.pool)

    try:
        reply, session_id, message_id = await memory.chat_with_memory(
            user_external_id=request.user_id,
            user_message=request.message,
            session_id=request.session_id,
            model=request.model,
        )
        return ChatResponse(reply=reply, session_id=session_id, message_id=message_id)
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

The get_session_context function in PostgreSQL does the heavy lifting: it walks backward through messages, accumulates token counts, and stops when the budget is exhausted. This means the Python layer never pulls more data than it needs, and the token budget is enforced at the database level — not in application code where it's easy to forget.

Building the Long-Term Memory Layer

Long-term memory is where PostgreSQL truly distinguishes itself from pure vector stores. You need semantic search *and* relational filtering. When retrieving memories for a user, you want to find embeddings that are close to the current conversation topic *and* that belong to this specific user *and* that haven't expired *and* that have high importance scores. A standalone vector database can do the first filter; PostgreSQL with pgvector does all four simultaneously.

The long-term memory layer has three components:

1. Extraction — identifying what's worth remembering from a conversation

2. Storage — embedding and storing extracted memories

3. Retrieval — finding relevant past memories to inject into new conversations

-- Long-term memory retrieval and management

-- Retrieve memories relevant to current conversation turn
CREATE OR REPLACE FUNCTION retrieve_relevant_memories(
    p_user_id           UUID,
    p_query_embedding   vector(1536),
    p_memory_types      TEXT[]      DEFAULT ARRAY['episodic', 'semantic', 'procedural'],
    p_limit             INTEGER     DEFAULT 5,
    p_min_importance    FLOAT       DEFAULT 0.3,
    p_similarity_threshold FLOAT   DEFAULT 0.70
)
RETURNS TABLE (
    memory_id       UUID,
    memory_type     TEXT,
    content         TEXT,
    importance_score FLOAT,
    similarity      FLOAT,
    access_count    INTEGER,
    created_at      TIMESTAMPTZ,
    tags            TEXT[]
) AS $$
BEGIN
    RETURN QUERY
    SELECT
        me.memory_id,
        me.memory_type,
        me.content,
        me.importance_score,
        1 - (me.embedding <=> p_query_embedding) AS similarity,
        me.access_count,
        me.created_at,
        me.tags
    FROM memory_entries me
    WHERE
        me.user_id = p_user_id
        AND me.is_active = TRUE
        AND me.memory_type = ANY(p_memory_types)
        AND me.importance_score >= p_min_importance
        AND (me.expires_at IS NULL OR me.expires_at > NOW())
        AND 1 - (me.embedding <=> p_query_embedding) >= p_similarity_threshold
    ORDER BY
        -- Blend similarity with importance and recency
        (1 - (me.embedding <=> p_query_embedding)) * 0.6
        + me.importance_score * 0.3
        + (1.0 / (1.0 + EXTRACT(EPOCH FROM (NOW() - me.created_at)) / 86400.0)) * 0.1
    DESC
    LIMIT p_limit;
END;
$$ LANGUAGE plpgsql STABLE;

-- Update access stats when a memory is surfaced
CREATE OR REPLACE FUNCTION touch_memories(p_memory_ids UUID[])
RETURNS VOID AS $$
BEGIN
    UPDATE memory_entries
    SET
        access_count     = access_count + 1,
        last_accessed_at = NOW()
    WHERE memory_id = ANY(p_memory_ids);
END;
$$ LANGUAGE plpgsql;

-- Store a new long-term memory
CREATE OR REPLACE FUNCTION store_memory(
    p_user_id           UUID,
    p_content           TEXT,
    p_memory_type       TEXT,
    p_embedding         vector(1536),
    p_importance_score  FLOAT       DEFAULT 0.5,
    p_source_session_id UUID        DEFAULT NULL,
    p_source_message_id UUID        DEFAULT NULL,
    p_tags              TEXT[]      DEFAULT '{}',
    p_expires_at        TIMESTAMPTZ DEFAULT NULL,
    p_metadata          JSONB       DEFAULT '{}'
)
RETURNS UUID AS $$
DECLARE
    v_memory_id UUID;
BEGIN
    INSERT INTO memory_entries (
        user_id, content, memory_type, embedding,
        importance_score, source_session_id, source_message_id,
        tags, expires_at, metadata
    )
    VALUES (
        p_user_id, p_content, p_memory_type, p_embedding,
        p_importance_score, p_source_session_id, p_source_message_id,
        p_tags, p_expires_at, p_metadata
    )
    RETURNING memory_id INTO v_memory_id;

    RETURN v_memory_id;
END;
$$ LANGUAGE plpgsql;

-- Deduplicate memories: find existing memories too close to a new one
CREATE OR REPLACE FUNCTION find_duplicate_memories(
    p_user_id           UUID,
    p_embedding         vector(1536),
    p_memory_type       TEXT,
    p_similarity_cutoff FLOAT DEFAULT 0.92
)
RETURNS TABLE (
    memory_id       UUID,
    content         TEXT,
    similarity      FLOAT,
    importance_score FLOAT
) AS $$
BEGIN
    RETURN QUERY
    SELECT
        me.memory_id,
        me.content,
        1 - (me.embedding <=> p_embedding) AS similarity,
        me.importance_score
    FROM memory_entries me
    WHERE
        me.user_id       = p_user_id
        AND me.memory_type   = p_memory_type
        AND me.is_active     = TRUE
        AND 1 - (me.embedding <=> p_embedding) >= p_similarity_cutoff
    ORDER BY similarity DESC
    LIMIT 5;
END;
$$ LANGUAGE plpgsql STABLE;

-- Merge or supersede a duplicate memory rather than creating a near-duplicate
CREATE OR REPLACE FUNCTION upsert_memory(
    p_user_id           UUID,
    p_content           TEXT,
    p_memory_type       TEXT,
    p_embedding         vector(1536),
    p_importance_score  FLOAT       DEFAULT 0.5,
    p_source_session_id UUID        DEFAULT NULL,
    p_tags              TEXT[]      DEFAULT '{}',
    p_metadata          JSONB       DEFAULT '{}'
)
RETURNS UUID AS $$
DECLARE
    v_existing_id   UUID;
    v_memory_id     UUID;
BEGIN
    -- Check for near-duplicate
    SELECT memory_id INTO v_existing_id
    FROM find_duplicate_memories(p_user_id, p_embedding, p_memory_type, 0.92)
    LIMIT 1;

    IF v_existing_id IS NOT NULL THEN
        -- Update existing memory: refresh content, bump importance, merge tags
        UPDATE memory_entries
        SET
            content          = p_content,
            embedding        = p_embedding,
            importance_score = GREATEST(importance_score, p_importance_score),
            tags             = ARRAY(
                                   SELECT DISTINCT UNNEST(tags || p_tags)
                               ),
            metadata         = metadata || p_metadata,
            source_session_id = COALESCE(p_source_session_id, source_session_id)
        WHERE memory_id = v_existing_id;

        RETURN v_existing_id;
    ELSE
        -- No duplicate — insert fresh
        v_memory_id := store_memory(
            p_user_id, p_content, p_memory_type, p_embedding,
            p_importance_score, p_source_session_id, NULL,
            p_tags, NULL, p_metadata
        );
        RETURN v_memory_id;
    END IF;
END;
$$ LANGUAGE plpgsql;

Now the Python side — the memory extractor that reads a completed conversation turn and decides what to commit to long-term memory:

# long_term_memory.py
# Memory extraction, storage, and retrieval using PostgreSQL + pgvector

import json
import re
from dataclasses import dataclass
from typing import Optional
from uuid import UUID

import asyncpg
import numpy as np
from openai import AsyncOpenAI

openai_client = AsyncOpenAI()


@dataclass
class ExtractedMemory:
    content: str
    memory_type: str       # episodic | semantic | procedural
    importance_score: float
    tags: list[str]


MEMORY_EXTRACTION_PROMPT = """You are a memory extraction system. Analyze the conversation 
exchange below and identify information worth storing in long-term memory.

Rules:
- Extract ONLY genuinely useful, persistent information.
- Ignore greetings, filler, and transient details.
- Assign importance: 0.8-1.0 = critical preference or fact, 0.5-0.7 = useful context, 
  0.3-0.4 = minor detail worth noting.
- memory_type:
    "episodic"   = something that happened ("user mentioned they're a Python developer")
    "semantic"   = a preference or fact ("user prefers short answers with code examples")
    "procedural" = a workflow rule ("when user asks about deployments, mention Kubernetes")

Return a JSON array. Each element: {content, memory_type, importance_score, tags[]}
If nothing is worth storing, return an empty array [].

Conversation:
{conversation}
"""


class LongTermMemory:
    """
    Manages long-term memory: extraction from conversations,
    embedding and storage, and semantic retrieval.
    """

    def __init__(self, pool: asyncpg.Pool, embedding_model: str = "text-embedding-3-small"):
        self.pool = pool
        self.embedding_model = embedding_model
        self.embedding_dim = 1536

    async def embed(self, text: str) -> list[float]:
        """Embed a single text string."""
        response = await openai_client.embeddings.create(
            model=self.embedding_model,
            input=text,
        )
        return response.data[0].embedding

    async def embed_batch(self, texts: list[str]) -> list[list[float]]:
        """Embed a batch of texts in one API call."""
        response = await openai_client.embeddings.create(
            model=self.embedding_model,
            input=texts,
        )
        return [item.embedding for item in sorted(response.data, key=lambda x: x.index)]

    async def extract_memories(
        self,
        conversation_turns: list[dict],
        session_id: Optional[str] = None,
    ) -> list[ExtractedMemory]:
        """
        Use an LLM to extract memorable facts from recent conversation turns.
        conversation_turns: list of {"role": ..., "content": ...}
        """
        # Format conversation for the extraction prompt
        formatted = "\n".join(
            f"{turn['role'].upper()}: {turn['content']}"
            for turn in conversation_turns
            if turn["role"] in ("user", "assistant")
        )

        prompt = MEMORY_EXTRACTION_PROMPT.format(conversation=formatted)

        response = await openai_client.chat.completions.create(
            model="gpt-4o-mini",     # cheaper model is fine for extraction
            messages=[{"role": "user", "content": prompt}],
            temperature=0.1,
            response_format={"type": "json_object"},
        )

        raw = response.choices[0].message.content
        try:
            # The prompt asks for an array but response_format wraps it
            parsed = json.loads(raw)
            memories_list = parsed if isinstance(parsed, list) else parsed.get("memories", parsed.get("items", []))
        except json.JSONDecodeError:
            return []

        results = []
        for item in memories_list:
            if not isinstance(item, dict):
                continue
            content = item.get("content", "").strip()
            if not content:
                continue
            results.append(
                ExtractedMemory(
                    content=content,
                    memory_type=item.get("memory_type", "episodic"),
                    importance_score=float(item.get("importance_score", 0.5)),
                    tags=item.get("tags", []),
                )
            )

        return results

    async def consolidate_memories(
        self,
        user_id: str,
        conversation_turns: list[dict],
        session_id: Optional[str] = None,
    ) -> list[str]:
        """
        Extract memories from a conversation and persist them.
        Returns list of memory_ids that were stored or updated.
        """
        extracted = await self.extract_memories(conversation_turns, session_id)
        if not extracted:
            return []

        # Embed all extracted memories in one batch call
        embeddings = await self.embed_batch([m.content for m in extracted])

        memory_ids = []
        async with self.pool.acquire() as conn:
            for memory, embedding in zip(extracted, embeddings):
                memory_id = await conn.fetchval(
                    """
                    SELECT upsert_memory(
                        $1::uuid, $2, $3, $4::vector, $5, $6::uuid, $7, $8
                    )
                    """,
                    UUID(user_id),
                    memory.content,
                    memory.memory_type,
                    embedding,
                    memory.importance_score,
                    UUID(session_id) if session_id else None,
                    memory.tags,
                    {},
                )
                memory_ids.append(str(memory_id))

        return memory_ids

    async def retrieve_for_context(
        self,
        user_id: str,
        current_message: str,
        top_k: int = 5,
        memory_types: Optional[list[str]] = None,
    ) -> list[dict]:
        """
        Retrieve memories relevant to the current message.
        Returns formatted memory objects ready for prompt injection.
        """
        query_embedding = await self.embed(current_message)

        types = memory_types or ["episodic", "semantic", "procedural"]

        async with self.pool.acquire() as conn:
            rows = await conn.fetch(
                """
                SELECT memory_id, memory_type, content, importance_score,
                       similarity, access_count, created_at, tags
                FROM retrieve_relevant_memories(
                    $1::uuid, $2::vector, $3, $4, $5, $6
                )
                """,
                UUID(user_id),
                query_embedding,
                types,
                top_k,
                0.3,    # min_importance
                0.68,   # similarity_threshold
            )

            if not rows:
                return []

            # Update access stats asynchronously
            memory_ids = [row["memory_id"] for row in rows]
            await conn.execute(
                "SELECT touch_memories($1::uuid[])",
                memory_ids,
            )

        return [
            {
                "memory_id": str(row["memory_id"]),
                "type": row["memory_type"],
                "content": row["content"],
                "importance": row["importance_score"],
                "similarity": float(row["similarity"]),
                "tags": row["tags"],
            }
            for row in rows
        ]

    def format_memories_for_prompt(self, memories: list[dict]) -> str:
        """
        Format retrieved memories for injection into a system prompt.
        """
        if not memories:
            return ""

        lines = ["[Relevant context from memory]"]
        for mem in memories:
            prefix = {
                "episodic": "Past event",
                "semantic": "Known preference",
                "procedural": "Behavioral rule",
            }.get(mem["type"], "Memory")
            lines.append(f"- [{prefix}] {mem['content']}")

        return "\n".join(lines)

The scoring formula inside retrieve_relevant_memories deserves attention. Raw cosine similarity alone is a weak signal. A memory recorded two years ago that is slightly more similar than a memory from yesterday may be less useful. The blended score — 60% similarity, 30% importance, 10% recency — reflects that semantic relevance is the dominant signal, but importance and freshness both matter. Tune these weights for your application: a medical assistant should weight importance heavily, a casual chat assistant might weight recency more.

Wiring Short-Term and Long-Term Memory Together

The real power emerges when both tiers are combined in a single chat turn. Before calling the LLM, you retrieve long-term memories relevant to the current message and inject them into the system prompt. After the turn, you optionally consolidate new memories from the exchange. The orchestrator pattern looks like this:

# memory_orchestrator.py
# Combines short-term and long-term memory in a single chat turn

from datetime import datetime, timezone
from typing import Optional

import asyncpg

from short_term_memory import ConversationMemory
from long_term_memory import LongTermMemory
from openai import AsyncOpenAI

openai_client = AsyncOpenAI()


class MemoryOrchestrator:
    """
    Unified memory manager that combines short-term (session) and
    long-term (episodic/semantic) memory in each conversation turn.
    """

    BASE_SYSTEM_PROMPT = """You are a helpful, personalized assistant.
You have access to relevant memories about this user — use them naturally 
without explicitly announcing that you're reading from memory.
Always be consistent with previously established facts about the user."""

    def __init__(
        self,
        pool: asyncpg.Pool,
        model: str = "gpt-4o",
        consolidate_every_n_turns: int = 4,
    ):
        self.pool = pool
        self.model = model
        self.consolidate_every_n_turns = consolidate_every_n_turns
        self.short_term = ConversationMemory(pool, max_context_tokens=5000)
        self.long_term = LongTermMemory(pool)

    async def chat(
        self,
        user_external_id: str,
        user_message: str,
        session_id: Optional[str] = None,
    ) -> dict:
        """
        Full memory-augmented chat turn.
        Returns dict with reply, session_id, and memory metadata.
        """
        # 1. Ensure user and session exist
        user_id, session_id = await self.short_term.get_or_create_session(
            user_external_id, session_id
        )

        # 2. Retrieve relevant long-term memories (before saving new user message)
        memories = await self.long_term.retrieve_for_context(
            user_id=user_id,
            current_message=user_message,
            top_k=5,
        )

        # 3. Build enriched system prompt
        memory_context = self.long_term.format_memories_for_prompt(memories)
        system_prompt = self.BASE_SYSTEM_PROMPT
        if memory_context:
            system_prompt = f"{system_prompt}\n\n{memory_context}"

        # 4. Save user message to short-term store
        await self.short_term.save_message(session_id, user_id, "user", user_message)

        # 5. Load short-term conversation context
        history = await self.short_term.load_context(session_id)

        # 6. Call LLM
        start_time = datetime.now(timezone.utc)
        response = await openai_client.chat.completions.create(
            model=self.model,
            messages=[{"role": "system", "content": system_prompt}] + history,
            temperature=0.7,
        )
        reply = response.choices[0].message.content
        latency_ms = int(
            (datetime.now(timezone.utc) - start_time).total_seconds() * 1000
        )

        # 7. Save assistant reply to short-term store
        await self.short_term.save_message(
            session_id, user_id, "assistant", reply,
            model_used=self.model, latency_ms=latency_ms,
        )

        # 8. Periodic long-term memory consolidation
        async with self.pool.acquire() as conn:
            message_count = await conn.fetchval(
                "SELECT message_count FROM conversation_sessions WHERE session_id = $1::uuid",
                session_id,
            )

        new_memory_ids = []
        if message_count % self.consolidate_every_n_turns == 0:
            # Consolidate the last N turns into long-term memory
            recent_turns = history[-self.consolidate_every_n_turns:]
            new_memory_ids = await self.long_term.consolidate_memories(
                user_id=user_id,
                conversation_turns=recent_turns,
                session_id=session_id,
            )

        return {
            "reply": reply,
            "session_id": session_id,
            "latency_ms": latency_ms,
            "memories_used": len(memories),
            "memories_stored": len(new_memory_ids),
            "memory_ids_stored": new_memory_ids,
        }

The consolidation cadence (consolidate_every_n_turns = 4) controls how frequently short-term exchanges get distilled into long-term memories. Set it too low and you extract trivial details on nearly every turn; too high and you risk a session ending before anything meaningful is stored. Four to six turns is a reasonable default for most applications. For sessions that may end abruptly — like support chats — you can also trigger consolidation when a session is explicitly closed or when the process shuts down gracefully.

-- Short-term context retrieval (SQL Server equivalent of get_session_context)
CREATE OR ALTER PROCEDURE get_session_context
    @session_id     UNIQUEIDENTIFIER,
    @max_messages   INT = 20,
    @max_tokens     INT = 6000
AS
BEGIN
    SET NOCOUNT ON;

    WITH ranked_messages AS (
        SELECT TOP (@max_messages)
            message_id,
            sequence_number,
            role,
            content,
            created_at,
            COALESCE(content_tokens, LEN(content) / 4) AS token_estimate,
            ROW_NUMBER() OVER (ORDER BY sequence_number DESC) AS rn
        FROM conversation_messages
        WHERE session_id = @session_id
        ORDER BY sequence_number DESC
    ),
    with_cumulative AS (
        SELECT
            message_id,
            sequence_number,
            role,
            content,
            created_at,
            token_estimate,
            SUM(token_estimate) OVER (
                ORDER BY rn ASC
                ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
            ) AS cumulative_tokens
        FROM ranked_messages
    )
    SELECT
        message_id,
        sequence_number,
        role,
        content,
        created_at,
        cumulative_tokens
    FROM with_cumulative
    WHERE cumulative_tokens <= @max_tokens
    ORDER BY sequence_number ASC;
END;
GO

-- Append message with sequence control (SQL Server)
CREATE OR ALTER PROCEDURE append_message
    @session_id     UNIQUEIDENTIFIER,
    @user_id        UNIQUEIDENTIFIER,
    @role           NVARCHAR(20),
    @content        NVARCHAR(MAX),
    @model_used     NVARCHAR(100) = NULL,
    @latency_ms     INT           = NULL,
    @metadata       NVARCHAR(MAX) = '{}'
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @sequence       INT;
    DECLARE @message_id     UNIQUEIDENTIFIER = NEWID();
    DECLARE @token_estimate INT;

    BEGIN TRANSACTION;

    -- Serialized sequence number acquisition
    SELECT @sequence = COALESCE(MAX(sequence_number), 0) + 1
    FROM conversation_messages WITH (UPDLOCK, HOLDLOCK)
    WHERE session_id = @session_id;

    SET @token_estimate = CEILING(CAST(LEN(@content) AS FLOAT) / 4);

    INSERT INTO conversation_messages (
        message_id, session_id, user_id, sequence_number,
        role, content, content_tokens, model_used, latency_ms, metadata
    )
    VALUES (
        @message_id, @session_id, @user_id, @sequence,
        @role, @content, @token_estimate, @model_used, @latency_ms, @metadata
    );

    UPDATE conversation_sessions
    SET
        last_message_at = SYSDATETIMEOFFSET(),
        message_count   = message_count + 1,
        total_tokens    = total_tokens + @token_estimate
    WHERE session_id = @session_id;

    COMMIT TRANSACTION;

    SELECT @message_id AS message_id;
END;
GO

The key difference is the external_vector_id column in memory_entries. When a memory is stored, the embedding goes to the sidecar vector store and the returned ID is recorded here. At retrieval time, your application queries the vector store for similar IDs, then fetches full memory records from SQL Server by those IDs — applying the importance and expiry filters there. It is two round-trips instead of one, but it keeps the relational integrity intact until native vector support matures.

Memory Lifecycle Management

Memory systems accumulate data. Without active lifecycle management, you end up with stale preferences from years ago outcompeting fresh context, near-duplicate memories multiplying with every session, and storage costs that grow unbounded. Production memory systems need four lifecycle operations: expiry, decay, deduplication, and archival.

-- Memory lifecycle management jobs
-- These are intended to run as scheduled jobs (pg_cron, external cron, etc.)

-- 1. Expire working memory past its TTL
CREATE OR REPLACE FUNCTION expire_working_memory()
RETURNS INTEGER AS $$
DECLARE
    v_count INTEGER;
BEGIN
    UPDATE memory_entries
    SET is_active = FALSE
    WHERE
        memory_type = 'working'
        AND expires_at IS NOT NULL
        AND expires_at <= NOW()
        AND is_active = TRUE;

    GET DIAGNOSTICS v_count = ROW_COUNT;
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

-- 2. Decay importance of memories that are old and rarely accessed
CREATE OR REPLACE FUNCTION decay_memory_importance(
    p_decay_rate        FLOAT DEFAULT 0.02,   -- importance reduction per 30-day period
    p_min_importance    FLOAT DEFAULT 0.10,   -- floor: never decay below this
    p_days_inactive     INTEGER DEFAULT 30    -- only decay if not accessed in this window
)
RETURNS INTEGER AS $$
DECLARE
    v_count INTEGER;
BEGIN
    UPDATE memory_entries
    SET importance_score = GREATEST(
        p_min_importance,
        importance_score * (1.0 - p_decay_rate)
    )
    WHERE
        is_active = TRUE
        AND memory_type IN ('episodic', 'semantic')
        AND (
            last_accessed_at IS NULL
            OR last_accessed_at < NOW() - (p_days_inactive || ' days')::INTERVAL
        )
        AND created_at < NOW() - (p_days_inactive || ' days')::INTERVAL;

    GET DIAGNOSTICS v_count = ROW_COUNT;
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

-- 3. Deactivate memories that have decayed below the floor
CREATE OR REPLACE FUNCTION prune_low_importance_memories(
    p_importance_cutoff FLOAT DEFAULT 0.12,
    p_min_age_days      INTEGER DEFAULT 90
)
RETURNS INTEGER AS $$
DECLARE
    v_count INTEGER;
BEGIN
    UPDATE memory_entries
    SET is_active = FALSE
    WHERE
        is_active = TRUE
        AND importance_score < p_importance_cutoff
        AND created_at < NOW() - (p_min_age_days || ' days')::INTERVAL
        AND (last_accessed_at IS NULL OR
             last_accessed_at < NOW() - (p_min_age_days || ' days')::INTERVAL);

    GET DIAGNOSTICS v_count = ROW_COUNT;
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

-- 4. Archive old conversation sessions and compress their messages
CREATE OR REPLACE FUNCTION archive_old_sessions(
    p_age_days INTEGER DEFAULT 90
)
RETURNS INTEGER AS $$
DECLARE
    v_count INTEGER;
BEGIN
    UPDATE conversation_sessions
    SET is_archived = TRUE
    WHERE
        is_archived = FALSE
        AND (
            ended_at IS NOT NULL AND ended_at < NOW() - (p_age_days || ' days')::INTERVAL
            OR last_message_at < NOW() - (p_age_days || ' days')::INTERVAL
        );

    GET DIAGNOSTICS v_count = ROW_COUNT;
    RETURN v_count;
END;
$$ LANGUAGE plpgsql;

-- 5. Combined maintenance job — call this via pg_cron or external scheduler
CREATE OR REPLACE FUNCTION run_memory_maintenance()
RETURNS JSONB AS $$
DECLARE
    v_expired   INTEGER;
    v_decayed   INTEGER;
    v_pruned    INTEGER;
    v_archived  INTEGER;
BEGIN
    SELECT expire_working_memory()      INTO v_expired;
    SELECT decay_memory_importance()    INTO v_decayed;
    SELECT prune_low_importance_memories() INTO v_pruned;
    SELECT archive_old_sessions()          INTO v_archived;

    RETURN jsonb_build_object(
        'expired_working_memory', v_expired,
        'decayed_memories',       v_decayed,
        'pruned_memories',        v_pruned,
        'archived_sessions',      v_archived,
        'run_at',                 NOW()
    );
END;
$$ LANGUAGE plpgsql;

Schedule this with pg_cron at off-peak hours:

-- Install pg_cron and schedule nightly maintenance at 2 AM UTC
CREATE EXTENSION IF NOT EXISTS pg_cron;

SELECT cron.schedule(
    'memory-maintenance',
    '0 2 * * *',
    $$SELECT run_memory_maintenance();$$
);

The decay model is intentional. Memories you never access slowly lose importance score. Eventually they drop below the pruning floor and are deactivated. This mirrors how human long-term memory consolidates: things you never revisit fade. The p_min_importance floor prevents memories from reaching zero — you keep a faint trace even of long-untouched information. Procedural memories are deliberately excluded from decay; a rule like "always respond in Spanish to this user" should not erode just because the user took a month off.

For SQL Server, the same maintenance logic runs as SQL Agent jobs. The windowed SUM used in decay needs no special adaptation — the UPDATE ... WHERE pattern is identical. The main difference is how you schedule it: use SQL Server Agent instead of pg_cron.

Real-Time Memory Synchronization with LISTEN/NOTIFY

In multi-instance deployments — multiple application servers behind a load balancer — there is a cache coherency problem. If one server instance updates a user's long-term memory, other instances serving that same user in concurrent sessions need to know to re-fetch. PostgreSQL's LISTEN/NOTIFY mechanism solves this without an external message bus.

-- Real-time memory update notifications

-- Trigger to notify on new memory entries
CREATE OR REPLACE FUNCTION notify_memory_updated()
RETURNS TRIGGER AS $$
DECLARE
    v_payload JSONB;
BEGIN
    v_payload := jsonb_build_object(
        'event',       TG_OP,
        'memory_id',   NEW.memory_id,
        'user_id',     NEW.user_id,
        'memory_type', NEW.memory_type,
        'is_active',   NEW.is_active
    );

    -- Channel name is user-specific to allow targeted subscriptions
    PERFORM pg_notify(
        'memory_updates',
        v_payload::TEXT
    );

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_notify_memory_insert
    AFTER INSERT ON memory_entries
    FOR EACH ROW EXECUTE FUNCTION notify_memory_updated();

CREATE TRIGGER trg_notify_memory_update
    AFTER UPDATE OF is_active, importance_score, content ON memory_entries
    FOR EACH ROW
    WHEN (OLD.is_active IS DISTINCT FROM NEW.is_active
       OR OLD.importance_score IS DISTINCT FROM NEW.importance_score
       OR OLD.content IS DISTINCT FROM NEW.content)
    EXECUTE FUNCTION notify_memory_updated();

Now the Python listener that runs in each application instance to keep an in-process LRU cache coherent:

# memory_sync.py
# LISTEN/NOTIFY-based memory cache invalidation for multi-instance deployments

import asyncio
import json
import logging
from collections import OrderedDict
from typing import Optional

import asyncpg

logger = logging.getLogger(__name__)


class MemoryCache:
    """
    Simple in-process LRU cache for recently retrieved memory sets.
    Keyed by (user_id, query_hash) -> list of memory dicts.
    """

    def __init__(self, max_size: int = 500, ttl_seconds: int = 120):
        self._cache: OrderedDict[str, tuple[float, list]] = OrderedDict()
        self.max_size = max_size
        self.ttl_seconds = ttl_seconds

    def _make_key(self, user_id: str, query_hash: str) -> str:
        return f"{user_id}:{query_hash}"

    def get(self, user_id: str, query_hash: str) -> Optional[list]:
        import time
        key = self._make_key(user_id, query_hash)
        if key not in self._cache:
            return None
        ts, value = self._cache[key]
        if time.monotonic() - ts > self.ttl_seconds:
            del self._cache[key]
            return None
        self._cache.move_to_end(key)
        return value

    def set(self, user_id: str, query_hash: str, value: list) -> None:
        import time
        key = self._make_key(user_id, query_hash)
        self._cache[key] = (time.monotonic(), value)
        self._cache.move_to_end(key)
        if len(self._cache) > self.max_size:
            self._cache.popitem(last=False)

    def invalidate_user(self, user_id: str) -> int:
        """Remove all cache entries for a given user_id. Returns count removed."""
        prefix = f"{user_id}:"
        keys_to_remove = [k for k in self._cache if k.startswith(prefix)]
        for k in keys_to_remove:
            del self._cache[k]
        return len(keys_to_remove)


class MemorySyncListener:
    """
    Listens for PostgreSQL NOTIFY events on the 'memory_updates' channel
    and invalidates the in-process cache for affected users.
    """

    def __init__(self, dsn: str, cache: MemoryCache):
        self.dsn = dsn
        self.cache = cache
        self._conn: Optional[asyncpg.Connection] = None
        self._running = False

    async def start(self) -> None:
        self._conn = await asyncpg.connect(self.dsn)
        await self._conn.add_listener("memory_updates", self._on_notify)
        self._running = True
        logger.info("Memory sync listener started on channel 'memory_updates'")

    async def stop(self) -> None:
        self._running = False
        if self._conn:
            await self._conn.remove_listener("memory_updates", self._on_notify)
            await self._conn.close()
            logger.info("Memory sync listener stopped")

    def _on_notify(
        self,
        conn: asyncpg.Connection,
        pid: int,
        channel: str,
        payload: str,
    ) -> None:
        try:
            data = json.loads(payload)
            user_id = data.get("user_id")
            if user_id:
                invalidated = self.cache.invalidate_user(str(user_id))
                if invalidated:
                    logger.debug(
                        "Invalidated %d cache entries for user %s (event: %s)",
                        invalidated,
                        user_id,
                        data.get("event"),
                    )
        except json.JSONDecodeError:
            logger.warning("Received malformed NOTIFY payload: %s", payload)

    async def run_forever(self) -> None:
        """Keep the listener alive; reconnect on transient failures."""
        while True:
            try:
                await self.start()
                # Block indefinitely — asyncpg fires the callback from the event loop
                while self._running:
                    await asyncio.sleep(30)
                    # Keepalive ping to detect dropped connections
                    await self._conn.execute("SELECT 1")
            except (asyncpg.PostgresConnectionStatusError, OSError) as e:
                logger.warning("Memory sync listener lost connection: %s — reconnecting", e)
                await asyncio.sleep(5)
            except asyncio.CancelledError:
                await self.stop()
                return

The pattern is clean: each application server runs a MemorySyncListener background task. When any server writes a new memory or updates one, the trigger fires pg_notify. Every listener receives the payload and invalidates the in-process cache for that user. The next memory retrieval for that user hits the database fresh. This avoids the stale-read window that would otherwise cause one server to return outdated context while another has newer memories loaded.

For SQL Server environments, the equivalent is SQL Server Service Broker or an application-level pub/sub (Redis Pub/Sub is common here), since SQL Server does not have a native LISTEN/NOTIFY analogue. The behavioral contract is identical — write triggers a notification, listeners invalidate caches — but the transport differs.

Scaling Memory to Millions of Users

Single-user demos become multi-tenant production systems quickly. The schema above handles single users cleanly; production at scale requires partitioning, connection pooling, and index tuning that changes as the data grows.

Table partitioning for conversation messages is the first scaling lever. At millions of users with active conversations, conversation_messages becomes the largest table. Partition it by created_at so that old partitions can be moved to cold storage or dropped entirely:

Connection pooling with PgBouncer is non-negotiable at scale. Each application server instance maintaining a pool of 10–20 connections to PostgreSQL multiplied across many servers quickly exhausts the database's connection limit. PgBouncer in transaction-mode pooling lets hundreds of application instances share a much smaller database connection pool:

# pgbouncer.ini — transaction-mode pooling for the memory system

[databases]
memory_db = host=postgres-primary port=5432 dbname=memory_db

[pgbouncer]
pool_mode = transaction
max_client_conn = 2000
default_pool_size = 40
reserve_pool_size = 10
reserve_pool_timeout = 3
server_idle_timeout = 600
log_connections = 0
log_disconnections = 0

One caveat with transaction-mode pooling: PostgreSQL session-level features like SET LOCAL and advisory locks do not persist across transactions in PgBouncer because the underlying connection may change. The LISTEN/NOTIFY listener connections must bypass PgBouncer and connect directly to the database — pg_notify requires a persistent session connection.

Read replicas for memory retrieval separate read-heavy workloads (retrieving context, searching long-term memories) from write-heavy ones (appending messages, storing new memories). Direct reads to a streaming replica:

# connection_pool_setup.py
# Separate read and write pools for the memory system

import asyncpg
from typing import Optional


async def create_memory_pools(
    primary_dsn: str,
    replica_dsn: Optional[str] = None,
) -> tuple[asyncpg.Pool, asyncpg.Pool]:
    """
    Returns (write_pool, read_pool).
    If no replica is configured, both point to the primary.
    """
    write_pool = await asyncpg.create_pool(
        dsn=primary_dsn,
        min_size=5,
        max_size=20,
        command_timeout=30,
        statement_cache_size=100,
    )

    if replica_dsn:
        read_pool = await asyncpg.create_pool(
            dsn=replica_dsn,
            min_size=5,
            max_size=40,           # read pool can be larger
            command_timeout=15,    # reads should be fast
            statement_cache_size=100,
        )
    else:
        read_pool = write_pool

    return write_pool, read_pool

Route retrieve_for_context and load_context through the read pool; route save_message, consolidate_memories, and upsert_memory through the write pool. The replication lag (typically well under a second on a healthy replica) means retrieved memories may be fractionally stale, but for memory retrieval this is almost always acceptable.

Observability: Tracking Memory System Health

A memory system that degrades silently is worse than no memory system. You need metrics that surface when memory retrieval is slow, when consolidation is failing, or when a user's memory has grown so large that retrieval is dominated by irrelevant entries.

-- Memory system observability queries

-- Per-user memory health overview
CREATE OR REPLACE VIEW memory_health_per_user AS
SELECT
    u.external_id,
    COUNT(me.memory_id) FILTER (WHERE me.is_active)             AS active_memories,
    COUNT(me.memory_id) FILTER (WHERE NOT me.is_active)         AS inactive_memories,
    AVG(me.importance_score) FILTER (WHERE me.is_active)        AS avg_importance,
    MAX(me.importance_score) FILTER (WHERE me.is_active)        AS max_importance,
    MIN(me.importance_score) FILTER (WHERE me.is_active)        AS min_importance,
    COUNT(me.memory_id) FILTER (
        WHERE me.is_active AND me.last_accessed_at > NOW() - INTERVAL '7 days'
    )                                                            AS accessed_last_7d,
    MAX(me.created_at)                                           AS latest_memory_at
FROM users u
LEFT JOIN memory_entries me ON me.user_id = u.user_id
GROUP BY u.user_id, u.external_id;

-- Session engagement stats
CREATE OR REPLACE VIEW session_engagement AS
SELECT
    DATE_TRUNC('day', started_at)   AS day,
    COUNT(*)                        AS sessions_started,
    COUNT(*) FILTER (WHERE ended_at IS NOT NULL)    AS sessions_completed,
    AVG(message_count)              AS avg_messages_per_session,
    AVG(total_tokens)               AS avg_tokens_per_session,
    PERCENTILE_CONT(0.95)
        WITHIN GROUP (ORDER BY message_count) AS p95_message_count
FROM conversation_sessions
GROUP BY DATE_TRUNC('day', started_at)
ORDER BY day DESC;

-- Memory retrieval latency tracking (requires pg_stat_statements)
-- Use this to identify slow retrieval queries
SELECT
    calls,
    mean_exec_time,
    stddev_exec_time,
    rows,
    LEFT(query, 80) AS query_snippet
FROM pg_stat_statements
WHERE query ILIKE '%retrieve_relevant_memories%'
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Identify users with runaway memory growth
SELECT
    u.external_id,
    COUNT(me.memory_id) AS total_active,
    MAX(me.created_at) AS newest,
    MIN(me.created_at) AS oldest,
    SUM(LENGTH(me.content)) AS total_content_bytes
FROM memory_entries me
JOIN users u ON u.user_id = me.user_id
WHERE me.is_active = TRUE
GROUP BY u.user_id, u.external_id
HAVING COUNT(me.memory_id) > 500
ORDER BY total_active DESC;

Wire these into your monitoring stack via a metrics exporter. The queries above are suited to Prometheus with postgres_exporter custom queries, or you can poll them from your application on a scheduled basis and push to your observability platform of choice. The key signals to alert on are: average retrieval latency climbing above your SLA, users accumulating memories faster than the decay and pruning jobs can contain, and the ratio of accessed_last_7d to active_memories dropping — a sign that your retrieval scoring is failing to surface useful memories.

Key Takeaways

  • → **Separate short-term and long-term memory into distinct schema layers.** Short-term memory is ordered, bounded, and session-scoped; long-term memory is embedded, importance-weighted, and user-scoped. Conflating them leads to either bloated LLM context or discarded cross-session knowledge.
  • → **Enforce token budgets at the database level, not the application level.** The `get_session_context` function walks backward through messages and halts at the token ceiling. This keeps the constraint close to the data and prevents application code drift from silently inflating costs.
  • → **Use a blended retrieval score that combines semantic similarity, importance, and recency.** Raw cosine similarity alone retrieves the most verbally similar memory, not the most useful one. Weighting in importance and a recency discount produces more relevant context injections.
  • → **Implement memory lifecycle management — decay, pruning, expiry, and archival — as scheduled database jobs.** Without it, old preferences crowd out fresh context and storage grows without bound. Procedural memories should be exempt from decay to preserve user-specific behavioral rules.
  • → **In multi-instance deployments, use PostgreSQL `LISTEN/NOTIFY` to synchronize in-process memory caches across application servers.** This eliminates stale-read windows without requiring an external message broker, keeping the architecture minimal while ensuring each server always retrieves up-to-date context.
