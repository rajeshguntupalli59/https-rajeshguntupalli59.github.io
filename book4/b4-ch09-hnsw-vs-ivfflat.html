Chapter 9: HNSW vs IVFFlat Indexing: Performance Tradeoffs

Vector search at scale lives or dies by its index structure. When you move beyond brute-force exact search — the vector equivalent of a full table scan — you enter the world of Approximate Nearest Neighbor (ANN) algorithms, and two of them dominate production deployments: HNSW (Hierarchical Navigable Small World) and IVFFlat (Inverted File Index with Flat quantization). Both solve the same fundamental problem — find the k most similar vectors to a query without scanning every row — but they make dramatically different engineering tradeoffs around memory, build time, query latency, and recall accuracy. This chapter unpacks how each algorithm works, where the numbers actually land in practice, and how to make the right choice for your workload. Database engineers will find familiar analogies throughout: if B-tree vs. hash index decisions feel natural to you, this chapter will feel like home.

---

How Vector Indexes Work: The ANN Problem

Exact nearest neighbor search requires computing the distance from a query vector to every stored vector. At 1 million vectors with 1536 dimensions (OpenAI's text-embedding-ada-002 output size), that's 1.5 billion floating-point operations per query. Even with SIMD parallelism, you're looking at hundreds of milliseconds — unacceptable for interactive applications.

ANN algorithms trade a small amount of recall accuracy for dramatic speed improvements. The core insight is identical to why you don't read every page of a book to find a topic — you use an index that organizes content spatially, letting you skip most of the data.

Recall is the ANN equivalent of query correctness. A recall of 0.95 means that for any query, your ANN search returns 95% of the same results that a brute-force exact search would return. Production systems typically target 0.90–0.99 recall depending on application sensitivity. A recommendation engine might tolerate 0.90. A medical record retrieval system needs 0.99+.

Think of it this way: recall in vector search maps roughly to what DBAs know as index selectivity, except you control the tradeoff dynamically through search parameters rather than waiting for a statistics update.

---

IVFFlat: The Inverted Index Approach

IVFFlat follows a partitioning strategy that any DBA who has worked with table partitioning will recognize immediately.

How it works:

During index build, IVFFlat runs k-means clustering on your vector dataset, dividing all vectors into lists number of clusters. Each cluster has a centroid — a representative vector at its geometric center. At query time, the algorithm:

1. Computes distance from the query vector to all centroids

2. Selects the probes closest centroids (you control this number)

3. Scans every vector in those selected clusters for exact distance comparisons

4. Returns the top-k results

This is structurally identical to a partitioned table with a partition pruning step. The centroids are your partition keys, and probes is how many partitions you're willing to scan.

Build-time parameters:

  • → `lists`: Number of clusters. Rule of thumb: `sqrt(n)` for datasets up to 1 million rows; `n/1000` for larger datasets. More lists = faster queries but slower build and higher minimum `probes` needed for good recall.
  • → Build time scales with dataset size roughly linearly after the k-means phase.

    • Query-time parameters:

  • → `probes`: Number of clusters to scan. Higher values increase recall but increase query latency proportionally. Default is 1 (fast, low recall). Setting `probes = lists` degrades to exact search.
    • -- PostgreSQL / pgvector
-- Create a table and populate it
CREATE TABLE documents (
    id          BIGSERIAL PRIMARY KEY,
    content     TEXT,
    embedding   vector(1536)
);

-- Build an IVFFlat index
-- lists = sqrt(1,000,000) ≈ 1000 for a 1M row dataset
CREATE INDEX ON documents
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 1000);

-- At query time, set probes in the session or transaction
-- probes = 10 gives ~0.90 recall; probes = 50 gives ~0.98 recall
SET ivfflat.probes = 10;

SELECT id, content, 1 - (embedding <=> '[...]'::vector) AS similarity
FROM documents
ORDER BY embedding <=> '[...]'::vector
LIMIT 10;

-- For higher-stakes queries, bump probes in the same session
SET ivfflat.probes = 50;

SELECT id, content, 1 - (embedding <=> '[...]'::vector) AS similarity
FROM documents
ORDER BY embedding <=> '[...]'::vector
LIMIT 10;

    IVFFlat performance characteristics (illustrative, not measured):

    The directional pattern is consistent across IVFFlat deployments: raising probes relative to lists trades query throughput for recall, and both build time and query cost scale with dataset size. The rough shape looks like this —

    | Dataset Size | lists | probes (low → high) | Recall (low → high) | Relative QPS (low → high) |

    |---|---|---|---|---|

    | 100K vectors | 100 | low | lower | higher |

    | 100K vectors | 100 | high | higher | lower |

    | 1M vectors | 1000 | low | lower | higher |

    | 1M vectors | 1000 | high | higher | lower |

    Do not treat these as target numbers. Actual recall, QPS, and build time depend heavily on your embedding model, data distribution, CPU, and PostgreSQL configuration — measure them on your own dataset using the benchmarking scripts later in this chapter before setting production parameters.

    Critical limitation: IVFFlat requires the index to be built on a fully populated (or near-final) dataset. The k-means centroids are computed once at build time. If your data distribution shifts significantly — because you've added a new category of documents that clusters differently — you'll need to rebuild the index to restore recall. This is not unlike rebuilding a hash-partitioned table after a distribution skew event.

    HNSW: The Graph Navigation Approach

    HNSW works on a fundamentally different principle. Rather than partitioning the vector space, it builds a multi-layer graph where nodes are your vectors and edges connect nearby vectors. The "hierarchical" part means the graph has multiple layers: upper layers are sparse long-range connections, lower layers are dense short-range connections. This mirrors skip list data structures — upper lanes for coarse navigation, lower lanes for precise landing.

    How it works:

    During index build, each vector is inserted into the graph. HNSW assigns each vector a random maximum layer (following an exponential distribution so most vectors appear only in layer 0). Edges are drawn greedily to the M nearest neighbors at each layer.

    At query time:

    1. Start at the entry point in the top layer

    2. Greedily traverse edges toward the query vector, descending layers

    3. At layer 0 (the base layer with all vectors), run a beam search with width ef_search

    4. Return the top-k candidates

    Build-time parameters:

  • → `m`: Number of bidirectional edges per node (typically 8–64). Higher values increase recall and memory usage. Memory per vector scales as `O(m)`.
  • → `ef_construction`: Size of the dynamic candidate list during build. Higher values improve index quality but slow build time. Typically 64–512.

    • Query-time parameters:

  • → `ef_search` (called `hnsw.ef_search` in pgvector): Beam width during search. Higher values increase recall but increase latency. Never set lower than `k` (your LIMIT value).
    • -- PostgreSQL / pgvector
-- HNSW index with tuned parameters
-- m=16 is the default; ef_construction=64 is the default
CREATE INDEX ON documents
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Set ef_search at query time
-- ef_search = 40 gives ~0.95 recall
-- ef_search = 100 gives ~0.99 recall
SET hnsw.ef_search = 64;

SELECT id, content, 1 - (embedding <=> '[...]'::vector) AS similarity
FROM documents
ORDER BY embedding <=> '[...]'::vector
LIMIT 10;

-- Check index size
SELECT pg_size_pretty(pg_relation_size('documents_embedding_idx'));

-- Inspect index build progress (pgvector 0.6+)
SELECT phase, blocks_done, blocks_total,
       tuples_done, tuples_total
FROM pg_stat_progress_create_index
WHERE relid = 'documents'::regclass;

    HNSW performance characteristics (illustrative, not measured):

    The same directional pattern applies to HNSW: raising ef_search improves recall at the cost of query throughput, and larger m/ef_construction improve recall further but push build time up substantially. The rough shape —

    | Dataset Size | m | ef_construction | ef_search (low → high) | Recall (low → high) | Relative QPS (low → high) |

    |---|---|---|---|---|---|

    | 100K vectors | 16 | 64 | low | lower | higher |

    | 100K vectors | 16 | 64 | high | higher | lower |

    | 1M vectors | 16 | 64 | moderate | high | moderate |

    | 1M vectors | 32 | 128 | high | highest | lowest |

    Treat these as directional only — do not use them as capacity-planning numbers. The build time gap between the two algorithms is real and gets worse at scale: HNSW build at the million-vector range commonly takes an order of magnitude longer than IVFFlat at a comparable recall target, but the exact multiplier depends on your hardware and parameters and should be measured on your own dataset using the benchmarking scripts later in this chapter.

    Memory footprint: HNSW stores the graph structure in memory. At m=16 with 1M float32 vectors at 1536 dimensions:

  • → Raw vector data: ~6 GB
  • → HNSW graph overhead: ~500 MB–1 GB
  • → Total working set: ~7 GB

    • This is the primary reason HNSW can saturate RAM on large datasets before you hit query performance limits.

    Head-to-Head Comparison: When to Choose Which

    graph TD
    subgraph HQ["HNSW query path"]
        S1[Entry point,
    top layer] --> S2[Greedy descent
    through layers]
        S2 --> S3["Layer 0: beam search
    (width = ef_search)"]
        S3 --> S4[Top-k results]
    end
    subgraph IQ["IVFFlat query path"]
        P1[Compute distance
    to all centroids] --> P2["Select nprobe
    closest lists"]
        P2 --> P3[Exact scan within
    selected lists]
        P3 --> P4[Top-k results]
    end

    *HNSW narrows in by descending graph layers; IVFFlat narrows in by selecting clusters, then scans exactly within them.*

    The choice between HNSW and IVFFlat comes down to five operational axes. Every production decision should be evaluated against all five simultaneously.

    1. Query Latency

    HNSW wins at low concurrency. Its graph traversal is CPU cache-friendly and predictable, and at a comparable recall target it typically shows lower and more consistent p99 latency than IVFFlat on the same dataset, because IVFFlat performs brute-force scans within each probed cluster, which has worse cache behavior at high dimensionality. The actual gap between the two varies with hardware, dimensionality, and parameter choice — measure it on your own data rather than assuming a fixed ratio.

    At high concurrency (50+ simultaneous queries), the memory bandwidth requirements of HNSW's graph traversal become a bottleneck, and the gap narrows.

    2. Index Build Time

    IVFFlat wins decisively. For a 1M vector dataset, IVFFlat builds in minutes; HNSW takes hours. For 10M+ vectors, HNSW build time can extend into days without parallelism. If your pipeline requires frequent full index rebuilds — for example, after bulk data loads or schema migrations — IVFFlat is the pragmatic choice.

    3. Incremental Insert Behavior

    HNSW wins. Inserting new vectors into an HNSW index is a graph operation: find neighbors, add edges, done. No rebalancing required. Query recall degrades gracefully as vectors are inserted.

    IVFFlat cannot efficiently accommodate new vectors that fall outside the distribution of the original k-means clusters. New vectors get assigned to their nearest centroid, but if the new data represents a genuinely new cluster (say, you started indexing documents in a new domain), recall drops because the probed clusters won't contain the relevant neighbors. You're rebuilding.

    # Python
# Demonstrating incremental insert behavior difference with pgvector via psycopg2
import psycopg2
import numpy as np
from pgvector.psycopg2 import register_vector

conn = psycopg2.connect("dbname=vectordb user=postgres")
register_vector(conn)
cur = conn.cursor()

def insert_batch(embeddings: list[np.ndarray], contents: list[str]):
    """
    HNSW: insert works seamlessly; graph expands with each new node.
    IVFFlat: insert works but may degrade recall if new vectors
             fall outside existing cluster centroids.
    """
    for embedding, content in zip(embeddings, contents):
        cur.execute(
            "INSERT INTO documents (content, embedding) VALUES (%s, %s)",
            (content, embedding)
        )
    conn.commit()
    print(f"Inserted {len(embeddings)} vectors.")

def measure_recall(query_vector: np.ndarray, k: int = 10) -> float:
    """
    Compare ANN results against exact search to estimate recall.
    """
    # Exact search (sequential scan, bypasses index)
    cur.execute("SET enable_indexscan = off")
    cur.execute(
        "SELECT id FROM documents ORDER BY embedding <=> %s LIMIT %s",
        (query_vector, k)
    )
    exact_ids = set(row[0] for row in cur.fetchall())

    # ANN search (uses index)
    cur.execute("SET enable_indexscan = on")
    cur.execute("SET hnsw.ef_search = 64")
    cur.execute(
        "SELECT id FROM documents ORDER BY embedding <=> %s LIMIT %s",
        (query_vector, k)
    )
    ann_ids = set(row[0] for row in cur.fetchall())

    recall = len(exact_ids & ann_ids) / k
    return recall

# Simulate incremental inserts and recall measurement
rng = np.random.default_rng(42)
batch_size = 10_000
num_batches = 5

for batch_num in range(num_batches):
    # Simulate new embeddings arriving (e.g., from OpenAI API)
    new_embeddings = [rng.standard_normal(1536).astype(np.float32)
                      for _ in range(batch_size)]
    new_contents = [f"doc_batch{batch_num}_{i}" for i in range(batch_size)]
    
    insert_batch(new_embeddings, new_contents)
    
    # Sample query to measure recall after each batch
    query = rng.standard_normal(1536).astype(np.float32)
    recall = measure_recall(query)
    
    cur.execute("SELECT COUNT(*) FROM documents")
    total = cur.fetchone()[0]
    print(f"After batch {batch_num + 1}: {total:,} total vectors, recall = {recall:.3f}")

cur.close()
conn.close()

    4. Memory Usage

    IVFFlat wins on memory efficiency. The inverted lists are compact structures; only the centroid vectors and the flat vector lists need to stay in memory for good performance. HNSW's graph layer — the bidirectional edge lists — consumes memory proportional to m * n, where n is the number of vectors. At m=16 and 10M vectors, the graph alone occupies ~2.5 GB before the vector data itself.

    For memory-constrained deployments (small cloud instances, embedded applications), IVFFlat often fits where HNSW does not.

    5. Recall Consistency

    HNSW produces more consistent recall across diverse query distributions. IVFFlat recall is uneven: queries whose nearest neighbors span multiple clusters get worse recall than queries whose neighborhood is tightly contained within one cluster. This is the partitioning equivalent of a query that crosses partition boundaries — you'll miss results unless you increase probes.

    HNSW's graph traversal is more distribution-agnostic. It navigates toward the answer regardless of how the vector space is partitioned, which is why it tends to be the default recommendation for general-purpose vector search.

    Managed Vector Databases: How They Expose These Tradeoffs

    The same fundamental tradeoffs appear in every managed vector database, even when the interface abstracts away the implementation details.

    # Python
# Weaviate: HNSW configuration (Weaviate default index type)
import weaviate
from weaviate.classes.config import Configure, VectorDistances

client = weaviate.connect_to_local()

# Create a collection with explicit HNSW tuning
client.collections.create(
    name="Documents",
    vectorizer_config=Configure.Vectorizer.none(),  # bring-your-own vectors
    vector_index_config=Configure.VectorIndex.hnsw(
        distance_metric=VectorDistances.COSINE,
        ef_construction=128,   # higher = better index quality, slower build
        max_connections=32,    # equivalent to m in HNSW
        ef=64,                 # ef_search equivalent; can be overridden per query
        dynamic_ef_min=100,    # auto-tune ef_search based on load
        dynamic_ef_max=500,
        dynamic_ef_factor=8,
    )
)

# Create a collection with flat (exact) index for small datasets
client.collections.create(
    name="SmallDocuments",
    vectorizer_config=Configure.Vectorizer.none(),
    vector_index_config=Configure.VectorIndex.flat(
        distance_metric=VectorDistances.COSINE,
        # Flat index = exact search; appropriate for < 10K vectors
        # No recall tradeoff, but latency scales linearly with dataset size
    )
)

# Query with per-request ef override
collection = client.collections.get("Documents")
results = collection.query.near_vector(
    near_vector=[0.1, 0.2, ...],  # 1536-dim query vector
    limit=10,
    return_metadata=["distance"],
)

for obj in results.objects:
    print(f"ID: {obj.uuid}, Distance: {obj.metadata.distance:.4f}")

client.close()

    Pinecone abstracts index type selection entirely — you choose a serverless or pod-based deployment, and the platform manages the underlying algorithm. Pod-based deployments expose metric (cosine, euclidean, dotproduct) and pod type/size but not raw HNSW parameters. The tradeoff is operational simplicity at the cost of fine-grained tuning. For teams without a dedicated ML infrastructure engineer, this is often the right call.

    Milvus exposes both HNSW and IVFFlat as first-class options along with more exotic indexes like DISKANN (for data that exceeds RAM), IVF_SQ8 (scalar quantization of IVFFlat), and HNSW_SQ. For very large datasets (>100M vectors) that cannot fit in RAM, DISKANN becomes the relevant comparison point — but that's beyond the scope of this chapter.

    Production Tuning Playbook

    Understanding the algorithms is necessary but not sufficient. Here is how experienced practitioners actually set parameters in production.

    Step 1: Establish your recall floor

    Before touching index parameters, decide what recall is acceptable for your application. Run exact search on a representative query sample and benchmark baseline latency. Then set a target: "We need 0.95 recall at under 20ms p99 at 100 QPS."

    Step 2: Size your index

    For IVFFlat: lists = sqrt(row_count) is a reliable starting point up to 1M rows. For HNSW: start with m=16, ef_construction=64 — these are conservative defaults that work well across most workloads.

    Step 3: Tune probes or ef_search against recall

    Run the recall measurement loop from the earlier Python example against your actual query distribution. Plot recall vs. latency as you sweep the parameter. The curve will be steep initially (large recall gains per unit of latency) and then flatten (diminishing returns). Pick the knee of the curve.

    # Python
# Recall-latency sweep for IVFFlat probes tuning
import psycopg2
import numpy as np
import time
from pgvector.psycopg2 import register_vector

conn = psycopg2.connect("dbname=vectordb user=postgres")
register_vector(conn)
cur = conn.cursor()

def benchmark_ivfflat(query_vectors, k=10, probes_range=None):
    if probes_range is None:
        probes_range = [1, 2, 5, 10, 20, 50, 100]
    
    results = []
    
    # Precompute exact results for recall calculation
    cur.execute("SET enable_indexscan = off")
    exact_results = {}
    for i, qv in enumerate(query_vectors):
        cur.execute(
            "SELECT id FROM documents ORDER BY embedding <=> %s LIMIT %s",
            (qv, k)
        )
        exact_results[i] = set(r[0] for r in cur.fetchall())
    
    cur.execute("SET enable_indexscan = on")
    
    for probes in probes_range:
        cur.execute(f"SET ivfflat.probes = {probes}")
        
        latencies = []
        recalls = []
        
        for i, qv in enumerate(query_vectors):
            t0 = time.perf_counter()
            cur.execute(
                "SELECT id FROM documents ORDER BY embedding <=> %s LIMIT %s",
                (qv, k)
            )
            ann_ids = set(r[0] for r in cur.fetchall())
            latencies.append((time.perf_counter() - t0) * 1000)  # ms
            recalls.append(len(exact_results[i] & ann_ids) / k)
        
        results.append({
            "probes": probes,
            "mean_recall": np.mean(recalls),
            "p99_latency_ms": np.percentile(latencies, 99),
            "mean_lat_ms": np.mean(latencies),
        })
        print(f"probes={probes:4d} | recall={np.mean(recalls):.3f} | "
              f"p99={np.percentile(latencies, 99):.1f}ms | "
              f"mean={np.mean(latencies):.1f}ms")
    
    return results

def benchmark_hnsw(query_vectors, k=10, ef_range=None):
    if ef_range is None:
        ef_range = [10, 20, 40, 64, 100, 200, 400]
    
    results = []
    
    cur.execute("SET enable_indexscan = off")
    exact_results = {}
    for i, qv in enumerate(query_vectors):
        cur.execute(
            "SELECT id FROM documents ORDER BY embedding <=> %s LIMIT %s",
            (qv, k)
        )
        exact_results[i] = set(r[0] for r in cur.fetchall())
    
    cur.execute("SET enable_indexscan = on")
    
    for ef in ef_range:
        cur.execute(f"SET hnsw.ef_search = {ef}")
        
        latencies = []
        recalls = []
        
        for i, qv in enumerate(query_vectors):
            t0 = time.perf_counter()
            cur.execute(
                "SELECT id FROM documents ORDER BY embedding <=> %s LIMIT %s",
                (qv, k)
            )
            ann_ids = set(r[0] for r in cur.fetchall())
            latencies.append((time.perf_counter() - t0) * 1000)
            recalls.append(len(exact_results[i] & ann_ids) / k)
        
        results.append({
            "ef_search": ef,
            "mean_recall": np.mean(recalls),
            "p99_latency_ms": np.percentile(latencies, 99),
            "mean_lat_ms": np.mean(latencies),
        })
        print(f"ef_search={ef:4d} | recall={np.mean(recalls):.3f} | "

rng = np.random.default_rng(0)
query_sample = [rng.standard_normal(1536).astype(np.float32) for _ in range(200)]

print("\n=== HNSW Sweep ===")

    Step 4: Validate on your actual query distribution

    Synthetic random vectors have a different nearest-neighbor structure than real embeddings from text, images, or tabular data. Real embeddings cluster around semantic topics. This means recall numbers measured on random vectors are often pessimistic for IVFFlat (your real queries are more likely to stay within a cluster) and can be either optimistic or pessimistic for HNSW depending on cluster density. Always validate with a sample of production queries before finalizing parameters.

    Step 5: Monitor recall in production

    Recall is not static. It drifts as your data grows, as your embedding model changes, and as query patterns evolve. The cheapest ongoing measurement strategy is shadow exact search: periodically route a small fraction of queries (e.g., 0.1%) through a sequential scan and compare results against the index-served response. When measured recall drops below your floor, rebuild the index.

    -- PostgreSQL
-- Simple recall monitoring using a dedicated test query table
-- Store known exact results, then re-run through the index periodically

CREATE TABLE recall_probes (
    probe_id    BIGSERIAL PRIMARY KEY,
    query_vec   vector(1536),
    exact_ids   BIGINT[],       -- precomputed exact top-10 ids
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- Stored procedure to measure current recall on stored probes
CREATE OR REPLACE FUNCTION measure_index_recall(k INT DEFAULT 10)
RETURNS TABLE(probe_id BIGINT, recall FLOAT)
LANGUAGE plpgsql AS $$
DECLARE
    rec RECORD;
    ann_ids BIGINT[];
    overlap INT;
BEGIN
    FOR rec IN SELECT * FROM recall_probes LOOP
        -- ANN search using the current index
        SELECT ARRAY(
            SELECT id FROM documents
            ORDER BY embedding <=> rec.query_vec
            LIMIT k
        ) INTO ann_ids;

        -- Compute intersection size
        SELECT COUNT(*) INTO overlap
        FROM UNNEST(rec.exact_ids) e
        JOIN UNNEST(ann_ids) a ON e = a;

        probe_id := rec.probe_id;
        recall   := overlap::FLOAT / k;
        RETURN NEXT;
    END LOOP;
END;
$$;

-- Run recall check
SELECT
    AVG(recall)    AS mean_recall,
    MIN(recall)    AS min_recall,
    PERCENTILE_CONT(0.05) WITHIN GROUP (ORDER BY recall) AS p5_recall
FROM measure_index_recall(10);

    Filtering and the ANN Problem

    A dimension of performance that benchmark tables frequently omit: what happens when you combine vector search with scalar filters?

    Consider a query like "find the 10 most similar documents to this query vector, but only among documents owned by tenant_id = 42." This is pre-filtering in database terms — restricting the candidate set before ranking.

    IVFFlat with pre-filtering: pgvector applies the WHERE clause first via a sequential scan or regular index, then computes vector distances only for qualifying rows. This is accurate — exact search on the filtered subset — but slow when the filter is selective enough to defeat the vector index.

    HNSW with pre-filtering: pgvector uses a similar approach. For very selective filters (tiny candidate sets), both indexes abandon ANN and fall back to exact search, which is actually the right behavior.

    The failure mode is a moderately selective filter — say, WHERE tenant_id = 42 returns 50,000 of your 1,000,000 rows. Now you want ANN search on those 50,000, but your index was built on all 1,000,000. The planner must choose between:

  • → Sequential scan of all 50,000 qualifying rows (exact but potentially slow)
  • → ANN search with probes/ef_search high enough to cover the filtered subset
    • -- PostgreSQL / pgvector
-- Pre-filtered vector search
-- Add a btree index on the filter column for efficient candidate selection
CREATE INDEX ON documents (tenant_id);

-- For HNSW: pgvector will use the HNSW index and apply the filter post-scan
-- If the filter is very selective, the planner may choose a sequential scan
SET hnsw.ef_search = 200;   -- raise ef_search to compensate for filtering

SELECT id, content, 1 - (embedding <=> '[...]'::vector) AS similarity
FROM documents

    Managed vector databases handle this differently. Weaviate and Qdrant implement post-filtering (ANN search then apply filter, may return fewer than k results) and pre-filtering (filter candidates then ANN search within the subset, accurate but requires a different index structure). Qdrant's approach uses a filterable HNSW where payload indexes interact with the graph traversal — you get accurate filtered results without a full sequential scan.

    For multi-tenant workloads with strict per-tenant isolation, the practical solution in pgvector is per-tenant tables or partitioning, so each tenant's vectors get their own index. This is standard database partitioning logic applied to the vector dimension.

    Choosing Between Indexes: A Decision Framework

    Rather than a simple rule, apply this checklist:

    Choose HNSW when:

  • → Query latency at low-to-moderate concurrency is the primary constraint
  • → Your dataset grows continuously via inserts (not bulk rebuilds)
  • → You need consistent recall across diverse query types
  • → Memory is available (budget roughly 1.5–2x raw vector size for the full working set)
  • → Build time is acceptable (plan for hours at multi-million-row scale)

    • Choose IVFFlat when:

  • → Build time is constrained (nightly rebuilds, CI pipelines, frequent schema changes)
  • → Memory is limited and you cannot afford the HNSW graph overhead
  • → Your dataset is relatively static (infrequent inserts, bulk-loaded)
  • → You need to tune recall precisely per query by varying `probes` at runtime
  • → Dataset size is under 500K vectors, where the build time gap shrinks substantially

    • Choose exact search (no ANN index) when:

  • → Dataset is under roughly 50K vectors — brute force at this size is fast enough for interactive applications
  • → Recall must be 1.0 (e.g., compliance or audit contexts where missing a result is unacceptable)
  • → Index maintenance cost is not justified for the query volume
    • -- PostgreSQL / pgvector

    SQL Server Context: What the Ecosystem Looks Like

    SQL Server does not ship with native vector index support as of this writing. Microsoft's vector search path runs through:

    1. Azure Cognitive Search — managed service that handles vector indexing separately from SQL Server, using HNSW internally

    2. Azure SQL / SQL Server with JSON + CLR — storing vectors as JSON or binary, computing distances via T-SQL or CLR extensions (brute force, no ANN)

    3. SQL Server 2022 + external integrations — offloading vector search to a sidecar service (Qdrant, Weaviate, or Pinecone) and joining results back via application code

    The implication for SQL Server shops is architectural: vector search currently lives outside the database engine, which means you're managing data consistency between SQL Server (your source of truth) and a separate vector store. The dual-write pattern discussed in earlier chapters applies directly here.

    -- SQL Server
-- Brute-force vector similarity using T-SQL (no ANN index available)
-- Vectors stored as comma-separated strings, decoded in application layer
-- This approach does not scale beyond ~100K rows at interactive latency

-- Alternatively, store as VARBINARY and decode in CLR
-- The pattern below uses a precomputed similarity cache for known query vectors

CREATE TABLE vector_similarity_cache (
    query_hash      CHAR(64)        NOT NULL,   -- SHA256 of query vector bytes
    document_id     BIGINT          NOT NULL,
    similarity      FLOAT           NOT NULL,
    computed_at     DATETIME2       NOT NULL DEFAULT SYSUTCDATETIME(),
    CONSTRAINT PK_sim_cache PRIMARY KEY (query_hash, document_id)
);

CREATE INDEX IX_sim_cache_query_score
    ON vector_similarity_cache (query_hash, similarity DESC)
    INCLUDE (document_id);

-- Application pattern:
-- 1. Hash the incoming query vector
-- 2. Check cache (valid for N minutes)
-- 3. On cache miss: call external vector search service, populate cache
-- 4. JOIN cache results with SQL Server document table for metadata enrichment

-- This pattern allows SQL Server to remain authoritative for business data
-- while delegating vector search to a purpose-built system

    The SQL Server ecosystem is moving quickly in this area; future versions and Azure SQL updates are likely to close this gap. Teams building on SQL Server today should design their vector search layer as a separable concern so that native support can be adopted when available.

    Key Takeaways

  • → **HNSW and IVFFlat solve the same ANN problem through opposite strategies**: HNSW builds a navigable graph for efficient traversal; IVFFlat partitions the vector space into clusters for scoped brute-force search. Neither is universally superior — workload characteristics determine the right choice.
  • → **The dominant tradeoff is build time vs. query performance**: HNSW delivers lower latency and better recall consistency but requires hours to build at million-row scale. IVFFlat builds in minutes but degrades recall when data distribution shifts and cannot recover without a rebuild.
  • → **Both algorithms expose a single runtime dial that controls the recall-latency tradeoff** — `probes` for IVFFlat, `ef_search` for HNSW. Benchmark this dial against your actual query distribution before finalizing, and monitor recall drift in production over time.
  • → **Pre-filtering (WHERE clause + vector search) requires extra care**: ANN indexes are built on the full dataset, not filtered subsets. Highly selective filters can defeat the index and force exact search; moderately selective filters can silently reduce recall. Raise `ef_search`/`probes` or restructure data (per-tenant tables, partitioning) when filtering is a core access pattern.
  • → **SQL Server teams must treat vector search as an external service today**: Without native ANN index support in the engine, the pragmatic path is a sidecar vector database with a dual-write consistency pattern, designed so that future native support can be adopted by replacing the sidecar rather than rearchitecting the application.
