Chapter 20: How AI Agents Use Databases as Tools

AI agents don't just query databases — they use them as instruments for reasoning, memory, state management, and coordination. Where a traditional application executes a fixed query on behalf of a user, an agent decides at runtime which database operations to perform, in what order, and with what parameters. PostgreSQL, with its rich feature set spanning structured queries, vector similarity, full-text search, JSON document storage, and procedural logic, is unusually well-suited to serve as the operational backbone for agent systems. This chapter covers how to design PostgreSQL schemas and Python applications so that agents can treat your database as a first-class tool — reading context, writing state, searching knowledge, and coordinating with other systems.

---

What It Means for an Agent to Use a Database

Classical applications treat databases as passive storage: the code decides what to do, then persists or retrieves data. Agents invert this relationship. The agent is given a toolkit of available operations and decides — at inference time — which tools to invoke, with what arguments, and how to chain them together to complete a goal.

A database tool from an agent's perspective is a callable function with a defined schema: it takes structured inputs, performs a well-bounded operation, and returns structured outputs the agent can reason about. The agent doesn't know your internal schema; it knows the tool's interface. PostgreSQL's capabilities map naturally onto agent tools:

| Agent capability | PostgreSQL feature |

|---|---|

| Long-term memory | Persistent tables with structured recall |

| Semantic search | pgvector + cosine_distance |

| Fact lookup | Indexed relational tables |

| State tracking | JSONB columns with partial updates |

| Event signaling | pg_notify / LISTEN |

| Audit trail | Append-only log tables |

| Multi-agent coordination | Row-level locking, status columns |

The architecture of an agent using PostgreSQL as tooling has three layers:

1. Tool definitions — Python functions registered with the LLM framework as callable tools

2. Tool implementations — the actual database operations, query logic, and result formatting

3. PostgreSQL schema — the tables, indexes, functions, and constraints that make the operations safe and fast

Everything flows through this stack. The LLM sees tool names and JSON schemas; your Python code translates those into SQL; PostgreSQL executes and returns results that get fed back into the model context window.

---

Designing the Agent State Schema

Before writing any agent logic, the database schema needs to support agent workflows. An agent must be able to track its own execution context: what task is it working on, what has it already tried, what did it learn, and what decisions did it make? This is distinct from application user data — it's metadata about agent runs themselves.

-- Core agent infrastructure schema
-- Run this migration to set up agent state tracking

CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS vector;

-- Agent runs: one row per invocation of an agent
CREATE TABLE agent_runs (
    run_id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    agent_type      TEXT NOT NULL,               -- 'research', 'sql_gen', 'support', etc.
    user_id         UUID REFERENCES users(id),
    session_id      UUID NOT NULL,
    status          TEXT NOT NULL DEFAULT 'running'
                    CHECK (status IN ('running', 'paused', 'completed', 'failed', 'cancelled')),
    goal            TEXT NOT NULL,               -- the original task description
    context         JSONB NOT NULL DEFAULT '{}', -- arbitrary agent-specific context
    tool_budget     INTEGER NOT NULL DEFAULT 20, -- max tool calls allowed
    tools_used      INTEGER NOT NULL DEFAULT 0,
    started_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    completed_at    TIMESTAMPTZ,
    final_answer    TEXT,
    error_message   TEXT,
    model_used      TEXT NOT NULL DEFAULT 'claude-opus-4-5',
    total_tokens    INTEGER,
    metadata        JSONB NOT NULL DEFAULT '{}'
);

CREATE INDEX idx_agent_runs_session ON agent_runs (session_id);
CREATE INDEX idx_agent_runs_status ON agent_runs (status) WHERE status = 'running';
CREATE INDEX idx_agent_runs_user ON agent_runs (user_id, started_at DESC);

-- Individual tool calls made during an agent run
CREATE TABLE agent_tool_calls (
    call_id         UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    run_id          UUID NOT NULL REFERENCES agent_runs(run_id) ON DELETE CASCADE,
    tool_name       TEXT NOT NULL,
    sequence_num    INTEGER NOT NULL,            -- order within the run
    input_args      JSONB NOT NULL,
    raw_result      JSONB,
    error           TEXT,
    duration_ms     INTEGER,
    called_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (run_id, sequence_num)
);

CREATE INDEX idx_tool_calls_run ON agent_tool_calls (run_id, sequence_num);
CREATE INDEX idx_tool_calls_name ON agent_tool_calls (tool_name, called_at DESC);

-- Agent memory: facts the agent discovered and wants to retain across runs
CREATE TABLE agent_memory (
    memory_id       UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    agent_type      TEXT NOT NULL,
    user_id         UUID REFERENCES users(id),
    memory_type     TEXT NOT NULL               -- 'fact', 'preference', 'failed_approach', 'entity'
                    CHECK (memory_type IN ('fact', 'preference', 'failed_approach', 'entity', 'summary')),
    content         TEXT NOT NULL,
    content_vec     VECTOR(1536),               -- embedding for semantic retrieval
    source_run_id   UUID REFERENCES agent_runs(run_id),
    confidence      FLOAT NOT NULL DEFAULT 1.0 CHECK (confidence BETWEEN 0 AND 1),
    access_count    INTEGER NOT NULL DEFAULT 0,
    last_accessed   TIMESTAMPTZ,
    expires_at      TIMESTAMPTZ,               -- NULL = permanent
    metadata        JSONB NOT NULL DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_agent_memory_user_type ON agent_memory (user_id, agent_type, memory_type);
CREATE INDEX idx_agent_memory_vec ON agent_memory
    USING hnsw (content_vec vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
CREATE INDEX idx_agent_memory_expiry ON agent_memory (expires_at)
    WHERE expires_at IS NOT NULL;

-- Shared agent workspace: structured data agents produce or consume
CREATE TABLE agent_artifacts (
    artifact_id     UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    run_id          UUID REFERENCES agent_runs(run_id) ON DELETE CASCADE,
    artifact_type   TEXT NOT NULL,              -- 'sql_query', 'report', 'data_extract', 'plan'
    name            TEXT NOT NULL,
    content         TEXT NOT NULL,
    content_json    JSONB,                      -- structured version when available
    embedding       VECTOR(1536),
    is_final        BOOLEAN NOT NULL DEFAULT FALSE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_artifacts_run ON agent_artifacts (run_id, artifact_type);

This schema gives you end-to-end observability over agent behavior — what did it try, in what order, for how long, and what did it conclude? The agent_memory table with its vector index allows agents to retrieve relevant past knowledge using semantic search rather than exact key lookups.

The tool_budget column is worth highlighting: uncontrolled agents can spiral into loops. Tracking tools_used and enforcing a hard budget at the database level (via a trigger, shown below) prevents runaway executions from consuming resources.

-- Trigger to enforce tool budget and auto-update run stats
CREATE OR REPLACE FUNCTION enforce_agent_tool_budget()
RETURNS TRIGGER AS $$
DECLARE
    v_budget        INTEGER;
    v_used          INTEGER;
    v_status        TEXT;
BEGIN
    SELECT tool_budget, tools_used, status
    INTO v_budget, v_used, v_status
    FROM agent_runs
    WHERE run_id = NEW.run_id
    FOR UPDATE;

    IF v_status != 'running' THEN
        RAISE EXCEPTION 'Cannot add tool call to run % with status %',
            NEW.run_id, v_status;
    END IF;

    IF v_used >= v_budget THEN
        UPDATE agent_runs
        SET status = 'failed',
            error_message = 'Tool budget exhausted after ' || v_used || ' calls',
            completed_at = NOW()
        WHERE run_id = NEW.run_id;

        RAISE EXCEPTION 'Agent run % exceeded tool budget of %',
            NEW.run_id, v_budget;
    END IF;

    -- Increment counter atomically
    UPDATE agent_runs
    SET tools_used = tools_used + 1
    WHERE run_id = NEW.run_id;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_enforce_tool_budget
    BEFORE INSERT ON agent_tool_calls
    FOR EACH ROW
    EXECUTE FUNCTION enforce_agent_tool_budget();

Implementing PostgreSQL Tools for Agents

With the state schema in place, you can build the tool functions that agents actually call. These are Python functions wrapped with the tool-calling interface of your LLM SDK. Each tool function should do exactly one coherent thing, return clean structured data, and log its execution to agent_tool_calls.

# tools.py — PostgreSQL-backed tools for AI agents
# Uses: asyncpg, anthropic, pgvector, and a connection pool

import asyncio
import json
import re
import time
import uuid
from datetime import datetime
from typing import Any, Optional
from dataclasses import dataclass, field

import asyncpg
import anthropic
import numpy as np
from openai import AsyncOpenAI

# ── Connection pool (set up in application startup) ──────────────────────────
_pool: asyncpg.Pool | None = None

async def get_pool() -> asyncpg.Pool:
    global _pool
    if _pool is None:
        _pool = await asyncpg.create_pool(
            dsn="postgresql://app_user:password@localhost/agentdb",
            min_size=5,
            max_size=20,
            command_timeout=30,
        )
    return _pool

# ── Embedding helper ──────────────────────────────────────────────────────────
openai_client = AsyncOpenAI()

async def embed_text(text: str) -> list[float]:
    response = await openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=text,
    )
    return response.data[0].embedding

# ── Tool call logger ──────────────────────────────────────────────────────────
async def log_tool_call(
    run_id: str,
    tool_name: str,
    sequence_num: int,
    input_args: dict,
    result: Any = None,
    error: str | None = None,
    duration_ms: int = 0,
) -> None:
    pool = await get_pool()
    async with pool.acquire() as conn:
        await conn.execute(
            """
            INSERT INTO agent_tool_calls
                (run_id, tool_name, sequence_num, input_args, raw_result, error, duration_ms)
            VALUES ($1, $2, $3, $4, $5, $6, $7)
            """,
            uuid.UUID(run_id),
            tool_name,
            sequence_num,
            json.dumps(input_args),
            json.dumps(result) if result is not None else None,
            error,
            duration_ms,
        )

# ── Tool: semantic search over knowledge base ─────────────────────────────────
async def search_knowledge_base(
    run_id: str,
    sequence_num: int,
    query: str,
    top_k: int = 5,
    min_similarity: float = 0.75,
    filters: dict | None = None,
) -> dict:
    """
    Semantic search over the knowledge base using pgvector.
    Returns ranked chunks with metadata. The agent uses this to
    retrieve relevant context before answering questions.
    """
    start = time.monotonic()
    input_args = {
        "query": query,
        "top_k": top_k,
        "min_similarity": min_similarity,
        "filters": filters,
    }

    try:
        embedding = await embed_text(query)
        embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

        pool = await get_pool()
        async with pool.acquire() as conn:
            # Build filter clause from optional structured filters
            filter_clause = ""
            filter_params = []
            param_idx = 3  # $1=embedding, $2=min_similarity, $3=top_k

            if filters:
                conditions = []
                if "source_type" in filters:
                    param_idx += 1
                    conditions.append(f"dc.source_type = ${param_idx}")
                    filter_params.append(filters["source_type"])
                if "date_after" in filters:
                    param_idx += 1
                    conditions.append(f"dc.created_at > ${param_idx}")
                    filter_params.append(filters["date_after"])
                if conditions:
                    filter_clause = "AND " + " AND ".join(conditions)

            rows = await conn.fetch(
                f"""
                SELECT
                    dc.chunk_id,
                    dc.document_id,
                    dc.content,
                    dc.source_type,
                    dc.metadata,
                    1 - (dc.embedding <=> $1::vector) AS similarity
                FROM document_chunks dc
                WHERE 1 - (dc.embedding <=> $1::vector) >= $2
                {filter_clause}
                ORDER BY dc.embedding <=> $1::vector
                LIMIT $3
                """,
                embedding_str,
                min_similarity,
                top_k,
                *filter_params,
            )

        results = [
            {
                "chunk_id": str(row["chunk_id"]),
                "document_id": str(row["document_id"]),
                "content": row["content"],
                "source_type": row["source_type"],
                "similarity": round(float(row["similarity"]), 4),
                "metadata": json.loads(row["metadata"]) if row["metadata"] else {},
            }
            for row in rows
        ]

        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "search_knowledge_base", sequence_num,
                            input_args, {"results": results, "count": len(results)},
                            duration_ms=duration_ms)

        return {"results": results, "count": len(results), "query": query}

    except Exception as e:
        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "search_knowledge_base", sequence_num,
                            input_args, error=str(e), duration_ms=duration_ms)
        return {"error": str(e), "results": [], "count": 0}


# ── Tool: execute read-only SQL ───────────────────────────────────────────────
async def execute_readonly_sql(
    run_id: str,
    sequence_num: int,
    sql: str,
    params: list | None = None,
    row_limit: int = 100,
) -> dict:
    """
    Execute a read-only SQL query against allowed tables.
    The agent generates SQL to answer analytical questions.
    Row limit is enforced server-side to prevent large result sets.
    """
    start = time.monotonic()
    input_args = {"sql": sql, "params": params, "row_limit": row_limit}

    # Whitelist check — only SELECT statements
    normalized = sql.strip().upper()
    if not normalized.startswith("SELECT") and not normalized.startswith("WITH"):
        error = "Only SELECT and WITH (CTE) statements are permitted"
        await log_tool_call(run_id, "execute_readonly_sql", sequence_num,
                            input_args, error=error)
        return {"error": error, "rows": [], "row_count": 0}

    try:
        pool = await get_pool()
        async with pool.acquire() as conn:
            # Force read-only transaction and statement timeout
            await conn.execute("SET LOCAL transaction_read_only = on")
            await conn.execute("SET LOCAL statement_timeout = '10s'")

            # Inject LIMIT if not present
            if "LIMIT" not in normalized:
                limited_sql = f"SELECT * FROM ({sql}) _agent_query LIMIT {row_limit}"
            else:
                limited_sql = sql

            rows = await conn.fetch(limited_sql, *(params or []))

        result_rows = [dict(row) for row in rows]
        # Serialize any non-JSON-native types
        for row in result_rows:
            for k, v in row.items():
                if isinstance(v, (datetime, uuid.UUID)):
                    row[k] = str(v)

        duration_ms = int((time.monotonic() - start) * 1000)
        result = {"rows": result_rows, "row_count": len(result_rows)}
        await log_tool_call(run_id, "execute_readonly_sql", sequence_num,
                            input_args, result, duration_ms=duration_ms)

        return result

    except asyncpg.PostgresError as e:
        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "execute_readonly_sql", sequence_num,
                            input_args, error=str(e), duration_ms=duration_ms)
        return {"error": f"Database error: {e}", "rows": [], "row_count": 0}


# ── Tool: recall agent memory ─────────────────────────────────────────────────
async def recall_memory(
    run_id: str,
    sequence_num: int,
    query: str,
    memory_type: str | None = None,
    user_id: str | None = None,
    agent_type: str = "default",
    top_k: int = 5,
) -> dict:
    """
    Retrieve relevant memories from past agent runs using semantic similarity.
    The agent uses this to avoid repeating mistakes and to leverage prior context.
    """
    start = time.monotonic()
    input_args = {
        "query": query, "memory_type": memory_type,
        "user_id": user_id, "top_k": top_k
    }

    try:
        embedding = await embed_text(query)
        embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

        pool = await get_pool()
        async with pool.acquire() as conn:
            rows = await conn.fetch(
                """
                SELECT
                    memory_id,
                    memory_type,
                    content,
                    confidence,
                    access_count,
                    created_at,
                    1 - (content_vec <=> $1::vector) AS relevance
                FROM agent_memory
                WHERE agent_type = $2
                  AND ($3::TEXT IS NULL OR user_id = $3::UUID)
                  AND ($4::TEXT IS NULL OR memory_type = $4)
                  AND (expires_at IS NULL OR expires_at > NOW())
                  AND 1 - (content_vec <=> $1::vector) > 0.7
                ORDER BY content_vec <=> $1::vector
                LIMIT $5
                """,
                embedding_str,
                agent_type,
                user_id,
                memory_type,
                top_k,
            )

            # Update access statistics
            if rows:
                memory_ids = [row["memory_id"] for row in rows]
                await conn.execute(
                    """
                    UPDATE agent_memory
                    SET access_count = access_count + 1,
                        last_accessed = NOW()
                    WHERE memory_id = ANY($1)
                    """,
                    memory_ids,
                )

        memories = [
            {
                "memory_id": str(row["memory_id"]),
                "type": row["memory_type"],
                "content": row["content"],
                "confidence": row["confidence"],
                "relevance": round(float(row["relevance"]), 4),
                "age_days": (datetime.utcnow() - row["created_at"].replace(tzinfo=None)).days,
            }
            for row in rows
        ]

        duration_ms = int((time.monotonic() - start) * 1000)
        result = {"memories": memories, "count": len(memories)}
        await log_tool_call(run_id, "recall_memory", sequence_num,
                            input_args, result, duration_ms=duration_ms)
        return result

    except Exception as e:
        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "recall_memory", sequence_num,
                            input_args, error=str(e), duration_ms=duration_ms)
        return {"error": str(e), "memories": [], "count": 0}


# ── Tool: store memory ────────────────────────────────────────────────────────
async def store_memory(
    run_id: str,
    sequence_num: int,
    content: str,
    memory_type: str,
    user_id: str | None = None,
    agent_type: str = "default",
    confidence: float = 1.0,
    expires_days: int | None = None,
) -> dict:
    """
    Persist a new memory for future agent runs. Used when the agent learns
    something worth retaining: a user preference, a failed approach to avoid,
    or a resolved factual question.
    """
    start = time.monotonic()
    input_args = {
        "content": content, "memory_type": memory_type,
        "confidence": confidence
    }

    try:
        embedding = await embed_text(content)
        embedding_str = "[" + ",".join(str(x) for x in embedding) + "]"

        expires_at = None
        if expires_days:
            from datetime import timedelta
            expires_at = datetime.utcnow() + timedelta(days=expires_days)

        pool = await get_pool()
        async with pool.acquire() as conn:
            memory_id = await conn.fetchval(
                """
                INSERT INTO agent_memory
                    (agent_type, user_id, memory_type, content, content_vec,
                     source_run_id, confidence, expires_at)
                VALUES ($1, $2::UUID, $3, $4, $5::vector, $6::UUID, $7, $8)
                RETURNING memory_id
                """,
                agent_type,
                user_id,
                memory_type,
                content,
                embedding_str,
                run_id,
                confidence,
                expires_at,
            )

        duration_ms = int((time.monotonic() - start) * 1000)
        result = {"memory_id": str(memory_id), "stored": True}
        await log_tool_call(run_id, "store_memory", sequence_num,
                            input_args, result, duration_ms=duration_ms)
        return result

    except Exception as e:
        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "store_memory", sequence_num,
                            input_args, error=str(e), duration_ms=duration_ms)
        return {"error": str(e), "stored": False}


# ── Tool: lookup structured entity ───────────────────────────────────────────
async def lookup_entity(
    run_id: str,
    sequence_num: int,
    entity_type: str,
    identifier: str,
    fields: list[str] | None = None,
) -> dict:
    """
    Look up a specific entity by type and identifier. Supports customers,
    products, orders, and other registered entity types. Returns only the
    requested fields (or all fields if none specified).
    """
    start = time.monotonic()
    input_args = {"entity_type": entity_type, "identifier": identifier, "fields": fields}

    ENTITY_TABLES = {
        "customer":  ("customers",  "customer_id"),
        "product":   ("products",   "product_id"),
        "order":     ("orders",     "order_id"),
        "ticket":    ("support_tickets", "ticket_id"),
    }

    if entity_type not in ENTITY_TABLES:
        error = f"Unknown entity type '{entity_type}'. Valid: {list(ENTITY_TABLES)}"
        await log_tool_call(run_id, "lookup_entity", sequence_num, input_args, error=error)
        return {"error": error, "entity": None}

    table, id_col = ENTITY_TABLES[entity_type]

    # Since `fields` comes from the LLM's tool call, never interpolate it into
    # SQL unvalidated — restrict to safe column-name identifiers to prevent
    # SQL injection via a crafted fields list.
    _IDENTIFIER_RE = re.compile(r"^[a-zA-Z_][a-zA-Z0-9_]*$")
    if fields:
        invalid = [f for f in fields if not _IDENTIFIER_RE.match(f)]
        if invalid:
            error = f"Invalid field name(s): {invalid}"
            await log_tool_call(run_id, "lookup_entity", sequence_num, input_args, error=error)
            return {"error": error, "entity": None}
        field_list = ", ".join(fields)
    else:
        field_list = "*"

    try:
        pool = await get_pool()
        async with pool.acquire() as conn:
            row = await conn.fetchrow(
                f"SELECT {field_list} FROM {table} WHERE {id_col} = $1",
                identifier,
            )

        entity = None
        if row:
            entity = dict(row)
            for k, v in entity.items():
                if isinstance(v, (datetime, uuid.UUID)):
                    entity[k] = str(v)

        duration_ms = int((time.monotonic() - start) * 1000)
        result = {"entity": entity, "found": entity is not None}
        await log_tool_call(run_id, "lookup_entity", sequence_num,
                            input_args, result, duration_ms=duration_ms)
        return result

    except Exception as e:
        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "lookup_entity", sequence_num,
                            input_args, error=str(e), duration_ms=duration_ms)
        return {"error": str(e), "entity": None}


# ── Tool: write structured update ────────────────────────────────────────────
async def write_structured_update(
    run_id: str,
    sequence_num: int,
    entity_type: str,
    identifier: str,
    updates: dict,
    reason: str,
) -> dict:
    """
    Apply a controlled write to a whitelisted set of mutable fields on a
    registered entity. All writes are audit-logged automatically. The agent
    must supply a reason string for every write.
    """
    start = time.monotonic()
    input_args = {
        "entity_type": entity_type,
        "identifier": identifier,
        "updates": updates,
        "reason": reason,
    }

    # Which tables and which fields are agent-writable
    WRITE_PERMISSIONS: dict[str, tuple[str, str, set[str]]] = {
        "ticket": ("support_tickets", "ticket_id",
                   {"status", "priority", "assigned_to", "resolution_notes"}),
        "order":  ("orders", "order_id",
                   {"status", "fulfillment_notes"}),
    }

    if entity_type not in WRITE_PERMISSIONS:
        error = f"Entity type '{entity_type}' is not writable by agents"
        await log_tool_call(run_id, "write_structured_update", sequence_num,
                            input_args, error=error)
        return {"error": error, "updated": False}

    table, id_col, allowed_fields = WRITE_PERMISSIONS[entity_type]

    # Reject any field not in the whitelist
    disallowed = set(updates.keys()) - allowed_fields
    if disallowed:
        error = f"Fields not writable by agents: {disallowed}. Allowed: {allowed_fields}"
        await log_tool_call(run_id, "write_structured_update", sequence_num,
                            input_args, error=error)
        return {"error": error, "updated": False}

    if not updates:
        return {"error": "No fields to update", "updated": False}

    try:
        pool = await get_pool()
        async with pool.acquire() as conn:
            async with conn.transaction():
                # Build SET clause
                set_parts = []
                values = []
                for i, (col, val) in enumerate(updates.items(), start=1):
                    set_parts.append(f"{col} = ${i}")
                    values.append(val)

                set_clause = ", ".join(set_parts)
                id_param = f"${len(values) + 1}"
                values.append(identifier)

                result = await conn.execute(
                    f"UPDATE {table} SET {set_clause}, updated_at = NOW() "
                    f"WHERE {id_col} = {id_param}",
                    *values,
                )

                rows_updated = int(result.split()[-1])

                # Audit log
                await conn.execute(
                    """
                    INSERT INTO agent_audit_log
                        (run_id, entity_type, entity_id, action, changes, reason)
                    VALUES ($1::UUID, $2, $3, 'update', $4, $5)
                    """,
                    run_id, entity_type, identifier,
                    json.dumps(updates), reason,
                )

        duration_ms = int((time.monotonic() - start) * 1000)
        result_data = {"updated": rows_updated > 0, "rows_affected": rows_updated}
        await log_tool_call(run_id, "write_structured_update", sequence_num,
                            input_args, result_data, duration_ms=duration_ms)
        return result_data

    except Exception as e:
        duration_ms = int((time.monotonic() - start) * 1000)
        await log_tool_call(run_id, "write_structured_update", sequence_num,
                            input_args, error=str(e), duration_ms=duration_ms)
        return {"error": str(e), "updated": False}

    entity_id       TEXT NOT NULL,

The principle in the write tool is minimum necessary authority: the agent can update only a predefined set of fields on a predefined set of tables, every change is attributed to a run and a stated reason, and nothing executes outside a transaction. This keeps agent writes auditable and reversible.

async def dispatch_tool(

    tool_input: dict,
    run_id: str,
    sequence_num: int,
    user_id: str | None,
    agent_type: str,
) -> Any:

# ── Main agent loop ────────────────────────────────────────────────────────────

async def run_agent(
    goal: str,
    agent_type: str = "support",
    user_id: str | None = None,
    session_id: str | None = None,
    tool_budget: int = 20,
    system_prompt: str | None = None,
) -> dict:
    """
    Run a single agent session to completion.
    Returns the final answer and run metadata.
    """
    run_id = str(uuid.uuid4())
    session_id = session_id or str(uuid.uuid4())

    # Create the run record
    pool = await get_pool()
    async with pool.acquire() as conn:
        await conn.execute(
            """
            INSERT INTO agent_runs
                (run_id, agent_type, user_id, session_id, goal, tool_budget)
            VALUES ($1::UUID, $2, $3::UUID, $4::UUID, $5, $6)
            """,
            run_id, agent_type, user_id, session_id, goal, tool_budget,
        )

    client = anthropic.AsyncAnthropic()

    system = system_prompt or (
        f"You are a {agent_type} agent with access to a set of database tools. "
        "Use tools to gather information before answering. Always recall relevant "
        "memories at the start of a session. Store important discoveries before finishing. "
        "Be concise in tool calls; do not search for the same thing twice."
    )

    messages: list[dict] = [{"role": "user", "content": goal}]
    sequence_num = 0
    final_answer = None

    try:
        while True:
            response = await client.messages.create(
                model="claude-opus-4-5",
                max_tokens=4096,
                system=system,
                tools=TOOL_DEFINITIONS,
                messages=messages,
            )

            # Append assistant message to history
            messages.append({"role": "assistant", "content": response.content})

            if response.stop_reason == "end_turn":
                # Extract text content as final answer
                for block in response.content:
                    if hasattr(block, "text"):
                        final_answer = block.text
                        break
                break

            if response.stop_reason != "tool_use":
                # Unexpected stop reason — surface it
                final_answer = f"Agent stopped unexpectedly: {response.stop_reason}"
                break

            # Process all tool calls in this response turn
            tool_results = []
            for block in response.content:
                if block.type != "tool_use":
                    continue

                sequence_num += 1
                tool_result = await dispatch_tool(
                    tool_name=block.name,
                    tool_input=block.input,
                    run_id=run_id,
                    sequence_num=sequence_num,
                    user_id=user_id,
                    agent_type=agent_type,
                )

                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(tool_result),
                })

            # Feed all results back in a single user turn
            messages.append({"role": "user", "content": tool_results})

    except Exception as e:
        # Mark run as failed
        async with pool.acquire() as conn:
            await conn.execute(
                """
                UPDATE agent_runs
                SET status = 'failed',
                    error_message = $1,
                    completed_at = NOW()
                WHERE run_id = $2::UUID
                """,
                str(e), run_id,
            )
        raise

    # Mark run as completed
    async with pool.acquire() as conn:
        await conn.execute(
            """
            UPDATE agent_runs
            SET status = 'completed',
                final_answer = $1,
                completed_at = NOW(),
                total_tokens = $2
            WHERE run_id = $3::UUID
            """,
            final_answer,
            response.usage.input_tokens + response.usage.output_tokens,
            run_id,
        )

    return {
        "run_id": run_id,
        "final_answer": final_answer,
        "tools_used": sequence_num,
        "session_id": session_id,
    }

The agent loop is deliberately simple — it drives the model until stop_reason is "end_turn", dispatching every tool call along the way. All state lives in PostgreSQL: you can inspect any run's full history by querying agent_tool_calls joined to agent_runs, resume a paused run by replaying its message history, or analyze patterns across thousands of runs with standard SQL.

graph TD
    A[agent_runs row created] --> B[Claude call with TOOL_DEFINITIONS]
    B --> C{stop_reason}
    C -->|end_turn| D[Extract final_answer]
    C -->|tool_use| E[dispatch_tool per block]
    E --> F[(PostgreSQL: search_knowledge_base / recall_memory / lookup_entity / execute_readonly_sql / write_structured_update)]
    F --> G[log_tool_call -> agent_tool_calls]
    G --> H[trg_enforce_tool_budget checks tools_used vs tool_budget]
    H -->|under budget| I[Append tool_result to messages]
    H -->|exhausted| J[Mark run failed, raise]
    I --> B
    D --> K[agent_runs marked completed]

*Each turn either ends the run or dispatches tool calls back into PostgreSQL, with a database trigger — not application code — enforcing the hard stop on runaway loops.*

Multi-Agent Coordination Through PostgreSQL

Single agents solve single tasks. Larger workflows require multiple agents — a planner, several specialists, and a synthesizer — working concurrently without trampling each other's state. PostgreSQL's row-level locking and notification system provide the coordination primitives.

-- Task queue for multi-agent coordination
CREATE TABLE agent_tasks (
    task_id         UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    priority        INTEGER NOT NULL DEFAULT 5,
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending', 'claimed', 'running', 'done', 'failed')),
    input_data      JSONB NOT NULL,
    output_data     JSONB,
    claimed_by      TEXT,               -- agent instance identifier
    claimed_at      TIMESTAMPTZ,
    completed_at    TIMESTAMPTZ,
    error           TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_tasks_pending ON agent_tasks (priority DESC, created_at ASC)
    WHERE status = 'pending';
CREATE INDEX idx_tasks_parent ON agent_tasks (parent_run_id);
# coordination.py — claim/complete task primitives for multi-agent systems

async def claim_next_task(
    agent_id: str,
    task_types: list[str],
) -> dict | None:
    """
    Atomically claim the next available task of the given types.
    Uses SELECT ... FOR UPDATE SKIP LOCKED for contention-free queue pop.
    """
    pool = await get_pool()
    async with pool.acquire() as conn:
        async with conn.transaction():
            row = await conn.fetchrow(
                """
                SELECT task_id, task_type, input_data
                FROM agent_tasks
                WHERE status = 'pending'
                  AND task_type = ANY($1)
                ORDER BY priority DESC, created_at ASC
                LIMIT 1
                FOR UPDATE SKIP LOCKED
                """,
                task_types,
            )

            if row is None:
                return None

            await conn.execute(
                """
                UPDATE agent_tasks
                SET status = 'claimed',
                    claimed_by = $1,
                    claimed_at = NOW()
                WHERE task_id = $2
                """,
                agent_id,
                row["task_id"],
            )

            return {
                "task_id": str(row["task_id"]),
                "task_type": row["task_type"],
                "input_data": dict(row["input_data"]),
            }


async def complete_task(
    task_id: str,
    output_data: dict,
    parent_run_id: str | None = None,
) -> None:
    """Mark a task complete and notify any waiting coordinator."""
    pool = await get_pool()
    async with pool.acquire() as conn:
        await conn.execute(
            """
            UPDATE agent_tasks
            SET status = 'done',
                output_data = $1,
                completed_at = NOW()
            WHERE task_id = $2::UUID
            """,
            json.dumps(output_data),
            task_id,
        )

        # Signal the parent run that a subtask finished
        if parent_run_id:
            await conn.execute(
                "SELECT pg_notify($1, $2)",
                f"agent_run_{parent_run_id}",
                json.dumps({"task_id": task_id, "event": "task_complete"}),
            )


async def wait_for_subtasks(
    parent_run_id: str,
    expected_count: int,
    timeout_seconds: float = 120.0,
) -> list[dict]:
    """
    Coordinator blocks here until all subtasks for a run are complete,
    using PostgreSQL LISTEN for efficient wake-up.
    """
    channel = f"agent_run_{parent_run_id}"
    completed: list[dict] = []

    pool = await get_pool()
    async with pool.acquire() as conn:
        # Keep a reference to the callback — remove_listener() matches on the
        # exact callback object, so a freshly created lambda at cleanup time
        # would silently fail to unregister the original one.
        def _on_notify(con, pid, chan, payload):
            completed.append(json.loads(payload))

        await conn.add_listener(channel, _on_notify)

        try:
            deadline = asyncio.get_event_loop().time() + timeout_seconds
            while len(completed) < expected_count:
                remaining = deadline - asyncio.get_event_loop().time()
                if remaining <= 0:
                    raise TimeoutError(
                        f"Subtasks did not complete within {timeout_seconds}s"
                    )
                await asyncio.sleep(min(0.25, remaining))
        finally:
            await conn.remove_listener(channel, _on_notify)

    # Fetch the full output for all completed tasks
    async with pool.acquire() as conn:
        rows = await conn.fetch(
            """
            SELECT task_id, task_type, output_data, completed_at
            FROM agent_tasks
            WHERE parent_run_id = $1::UUID
              AND status = 'done'
            ORDER BY completed_at
            """,
            parent_run_id,
        )

    return [
        {
            "task_id": str(r["task_id"]),
            "task_type": r["task_type"],
            "output": dict(r["output_data"]),
        }
        for r in rows
    ]

SELECT ... FOR UPDATE SKIP LOCKED is the key idiom here. Multiple agent workers can call claim_next_task simultaneously; PostgreSQL ensures only one of them acquires each row, and others move on to the next pending task without blocking. This is a well-established queue pattern that scales well for moderate task volumes without requiring an external queue service.

Querying Agent Behavior in PostgreSQL

One of the practical advantages of storing all agent state in PostgreSQL is that you can analyze it with ordinary SQL. The following queries illustrate operational monitoring patterns.

-- Which tools are most frequently used, and how fast are they?
SELECT
    tool_name,
    COUNT(*)                              AS total_calls,
    COUNT(*) FILTER (WHERE error IS NULL) AS successful_calls,
    ROUND(AVG(duration_ms))               AS avg_ms,
    PERCENTILE_CONT(0.95) WITHIN GROUP
        (ORDER BY duration_ms)            AS p95_ms,
    ROUND(100.0 * COUNT(*) FILTER (WHERE error IS NOT NULL)
          / COUNT(*), 1)                  AS error_pct
FROM agent_tool_calls
WHERE called_at > NOW() - INTERVAL '7 days'
GROUP BY tool_name
ORDER BY total_calls DESC;

-- Runs that exhausted their tool budget (likely looping)
SELECT
    r.run_id,
    r.agent_type,
    r.goal,
    r.tools_used,
    r.tool_budget,
    r.error_message,
    r.started_at,
    EXTRACT(EPOCH FROM (r.completed_at - r.started_at)) AS duration_sec
FROM agent_runs r
WHERE r.status = 'failed'
  AND r.error_message LIKE 'Tool budget exhausted%'
  AND r.started_at > NOW() - INTERVAL '30 days'
ORDER BY r.started_at DESC;

-- Tool call sequences for a specific run (debugging replay)
SELECT
    tc.sequence_num,
    tc.tool_name,
    tc.input_args,
    tc.raw_result,
    tc.error,
    tc.duration_ms,
    tc.called_at
FROM agent_tool_calls tc
WHERE tc.run_id = 'your-run-id-here'::UUID
ORDER BY tc.sequence_num;

-- Memory access patterns: which memories are being reused most?
SELECT
    memory_type,
    LEFT(content, 80)    AS content_preview,
    access_count,
    confidence,
    created_at::DATE     AS stored_date
FROM agent_memory
WHERE user_id IS NULL   -- shared memories
ORDER BY access_count DESC
LIMIT 20;

-- Slowest tool calls in the past 24 hours (performance hotspots)
SELECT
    tc.tool_name,
    tc.duration_ms,
    LEFT(tc.input_args::TEXT, 120) AS input_preview,
    r.agent_type,
    tc.called_at
FROM agent_tool_calls tc
JOIN agent_runs r USING (run_id)
WHERE tc.called_at > NOW() - INTERVAL '24 hours'
  AND tc.error IS NULL
ORDER BY tc.duration_ms DESC
LIMIT 25;

These queries don't require any external observability platform — a psql session or a lightweight dashboard backed by these tables gives you a complete view of your agents' operational behavior.

The SQL Server Parallel

All of the patterns above translate directly to SQL Server, with syntactic adaptations. The schema is equivalent; the key idioms differ in a few places.

Agent task queue — SQL Server edition:

-- agent_tasks equivalent on SQL Server
CREATE TABLE agent_tasks (
    task_id         UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    parent_run_id   UNIQUEIDENTIFIER NULL,
    task_type       NVARCHAR(100) NOT NULL,
    priority        INT NOT NULL DEFAULT 5,
    status          NVARCHAR(20) NOT NULL DEFAULT 'pending'
                    CONSTRAINT chk_task_status
                    CHECK (status IN ('pending','claimed','running','done','failed')),
    input_data      NVARCHAR(MAX) NOT NULL,   -- JSON stored as NVARCHAR
    output_data     NVARCHAR(MAX) NULL,
    claimed_by      NVARCHAR(200) NULL,
    claimed_at      DATETIMEOFFSET NULL,
    completed_at    DATETIMEOFFSET NULL,
    error           NVARCHAR(MAX) NULL,
    created_at      DATETIMEOFFSET NOT NULL DEFAULT SYSDATETIMEOFFSET()
);

CREATE INDEX idx_tasks_pending
    ON agent_tasks (priority DESC, created_at ASC)
    WHERE status = 'pending';
-- Atomic task claim on SQL Server using UPDLOCK + READPAST
-- (equivalent to SELECT FOR UPDATE SKIP LOCKED)
BEGIN TRANSACTION;

    DECLARE @claimed_id UNIQUEIDENTIFIER;

    SELECT TOP 1 @claimed_id = task_id
    FROM agent_tasks WITH (UPDLOCK, READPAST)
    WHERE status = 'pending'
      AND task_type IN ('research', 'summarize')   -- parameterize as needed
    ORDER BY priority DESC, created_at ASC;

    IF @claimed_id IS NOT NULL
    BEGIN
        UPDATE agent_tasks
        SET status     = 'claimed',
            claimed_by = 'agent-worker-01',          -- parameterize
            claimed_at = SYSDATETIMEOFFSET()
        WHERE task_id = @claimed_id;

        SELECT task_id, task_type, input_data
        FROM agent_tasks
        WHERE task_id = @claimed_id;
    END

COMMIT TRANSACTION;

Agent notifications — SQL Server edition:

PostgreSQL's pg_notify/LISTEN has no direct equivalent in SQL Server. The closest built-in mechanism is Service Broker, which provides reliable asynchronous messaging within the database engine.

-- Service Broker setup for agent task notifications
-- Run once per database

ALTER DATABASE AgentDB SET ENABLE_BROKER;

CREATE MESSAGE TYPE [AgentTaskComplete]
    VALIDATION = NONE;

CREATE CONTRACT [AgentCoordination]
    ([AgentTaskComplete] SENT BY INITIATOR);

CREATE QUEUE AgentNotificationQueue;

CREATE SERVICE [AgentNotificationService]
    ON QUEUE AgentNotificationQueue
    ([AgentCoordination]);
-- Sending a task-complete notification (from worker)
DECLARE @dialog UNIQUEIDENTIFIER;
DECLARE @payload NVARCHAR(MAX) = N'{"task_id":"' + CAST(@task_id AS NVARCHAR(36)) + N'","event":"task_complete"}';

BEGIN DIALOG CONVERSATION @dialog
    FROM SERVICE [AgentNotificationService]
    TO SERVICE 'AgentNotificationService'
    ON CONTRACT [AgentCoordination]
    WITH ENCRYPTION = OFF;

SEND ON CONVERSATION @dialog
    MESSAGE TYPE [AgentTaskComplete]
    (CAST(@payload AS VARBINARY(MAX)));

END CONVERSATION @dialog WITH CLEANUP;

In practice, many SQL Server shops use a polling approach for coordinator agents rather than Service Broker, since Service Broker configuration adds operational overhead. A coordinator polling agent_tasks on a short interval (WAITFOR DELAY '00:00:01') with READPAST is simpler and entirely adequate for workloads where sub-second notification latency isn't required.

SELECT
    tool_name,
    COUNT(*)                                            AS total_calls,
    SUM(CASE WHEN error IS NULL THEN 1 ELSE 0 END)     AS successful_calls,
    ROUND(AVG(CAST(duration_ms AS FLOAT)), 0)          AS avg_ms,
    MAX(duration_ms)                                   AS max_ms,
    ROUND(100.0 * SUM(CASE WHEN error IS NOT NULL THEN 1 ELSE 0 END)
          / COUNT(*), 1)                               AS error_pct
FROM agent_tool_calls
WHERE called_at > DATEADD(DAY, -7, SYSDATETIMEOFFSET())
GROUP BY tool_name
ORDER BY total_calls DESC;

-- Budget-exhausted runs (SQL Server)
SELECT TOP 50
    r.run_id,
    r.agent_type,
    r.goal,
    r.tools_used,
    r.tool_budget,
    r.error_message,
    r.started_at,
    DATEDIFF(SECOND, r.started_at, r.completed_at) AS duration_sec
FROM agent_runs r
WHERE r.status = 'failed'
  AND r.error_message LIKE 'Tool budget exhausted%'
  AND r.started_at > DATEADD(DAY, -30, SYSDATETIMEOFFSET())
ORDER BY r.started_at DESC;

The structural differences between the two platforms are surface-level: JSONB becomes NVARCHAR(MAX) with JSON path functions (JSON_VALUE, JSON_QUERY, OPENJSON), pgvector has no direct SQL Server equivalent without an extension (Azure SQL's native vector support is available in preview as of this writing), and pg_notify maps to Service Broker or a polling loop. The schema design and agent logic patterns are identical.

Hardening Agent Tools for Production

Several production concerns apply specifically to database-backed agent tools that don't arise in simpler API integrations.

Connection pool saturation. An agent loop that issues many sequential tool calls holds a pool connection for the entire round-trip between tool calls — including the time the LLM is generating a response. With long model latencies, a modest number of concurrent agents can exhaust a naive connection pool. The fix is to acquire connections only for the duration of each database operation, not for the lifetime of the agent run. The asyncpg pool's async context manager (async with pool.acquire() as conn) already does this correctly when used per-operation rather than held open across the entire agent loop.

Statement timeouts per tool. Different tools warrant different timeout budgets. A semantic search that normally runs in 80ms should be killed at 5 seconds; an analytical SQL query might legitimately take 30 seconds. Set timeouts at the session level within each tool function rather than relying on a single global setting:

async def execute_readonly_sql(run_id, sequence_num, sql, row_limit=50):
    pool = await get_pool()
    async with pool.acquire() as conn:
        # Scoped timeout: this connection only, this operation only
        await conn.execute("SET LOCAL statement_timeout = '30s'")
        await conn.execute("SET LOCAL lock_timeout = '5s'")
        rows = await conn.fetch(...)

Idempotent tool calls. If an agent loop crashes mid-turn after some tool calls have executed but before their results were fed back to the model, restarting the agent means those operations will be called again. For read-only tools this is harmless. For write tools (write_structured_update, store_memory), make them idempotent by checking for existing state before writing, or by using the sequence number as a deduplication key:

-- Idempotent memory insert: skip if an identical memory
-- from the same run already exists
INSERT INTO agent_memory
    (agent_type, user_id, memory_type, content, content_vec, source_run_id, confidence)
SELECT $1, $2::UUID, $3, $4, $5::vector, $6::UUID, $7
WHERE NOT EXISTS (
    SELECT 1 FROM agent_memory
    WHERE source_run_id = $6::UUID
      AND content = $4
);

Defense against prompt injection via retrieved content. When the agent calls search_knowledge_base or execute_readonly_sql, the content returned from the database goes directly into the model's context. If any of that content contains instructions disguised as data ("Ignore previous instructions and..."), the model may follow them. Mitigations at the database layer include:

  • → Storing retrieved chunks in a structured JSON envelope so the model receives them framed as tool results rather than inline text
  • → Adding a content moderation step over retrieved chunks before injecting them into messages
  • → Keeping write tools separate from read tools so that even a compromised read result can't directly trigger a write

    • The framing already used in the tool result format ("type": "tool_result", "content": json.dumps(result)) helps — the model receives the retrieved text as data within a tool result, not as a continuation of conversational text.

    Expiry and garbage collection. Agent run tables grow indefinitely. A background maintenance job is essential:

    -- Purge completed runs older than 90 days
-- (tool_calls and artifacts cascade-delete via FK)
DELETE FROM agent_runs
WHERE status IN ('completed', 'failed', 'cancelled')
  AND completed_at < NOW() - INTERVAL '90 days';

-- Purge expired memories
DELETE FROM agent_memory
WHERE expires_at IS NOT NULL
  AND expires_at < NOW();

-- Summarize old runs into compressed audit records before deletion
-- (run this before the DELETE above in a scheduled job)
INSERT INTO agent_run_summaries
    (agent_type, period_start, period_end, run_count, avg_tools_used,
     success_rate, common_tool_names)
SELECT
    agent_type,
    DATE_TRUNC('day', started_at)      AS period_start,
    DATE_TRUNC('day', started_at) + INTERVAL '1 day' AS period_end,
    COUNT(*)                           AS run_count,
    ROUND(AVG(tools_used), 1)          AS avg_tools_used,
    ROUND(AVG(CASE WHEN status = 'completed' THEN 1.0 ELSE 0.0 END), 3) AS success_rate,
    ARRAY_AGG(DISTINCT tc.tool_name)   AS common_tool_names
FROM agent_runs r
JOIN agent_tool_calls tc USING (run_id)
WHERE r.completed_at < NOW() - INTERVAL '90 days'
GROUP BY agent_type, DATE_TRUNC('day', started_at);

    Schedule this as a pg_cron job or an external cron task running nightly.

    Designing Tool Descriptions for Reliable Agent Behavior

    The quality of the agent's tool selection depends as much on how tools are described as on how they are implemented. Poorly described tools produce agents that call the wrong tool, pass the wrong arguments, or fail to use available tools at all.

    Effective tool descriptions follow several principles:

    Describe when to use the tool, not just what it does. Compare:

  • → Weak: *"Searches the knowledge base."*
  • → Strong: *"Semantic search over the company knowledge base. Use this to find relevant documentation, policies, FAQs, or product information before answering questions that require company-specific context."*

    • The stronger version tells the model the *trigger condition* — when this tool is the right choice.

    Describe what the tool cannot do. If execute_readonly_sql only has access to certain tables, say so. If search_knowledge_base doesn't cover real-time data, say so. This prevents the agent from issuing a tool call expecting information the tool can't provide.

    Use the JSON schema to guide inputs precisely. Enum constraints ("enum": ["ticket", "order"]) are enforced by the SDK and prevent the model from inventing values. Description strings on each property steer argument formatting.

    Keep each tool's responsibility narrow. An agent with ten narrowly scoped tools performs more reliably than one with three multi-purpose tools. The model can reason about what each tool does when the boundary is clear.

    Key Takeaways

  • → **PostgreSQL as agent tooling** means treating the database not as passive storage but as an active participant in agent reasoning — providing semantic search, structured fact lookup, state tracking, and write operations, all through callable Python functions.
  • → **Schema design for agents** requires dedicated tables for runs, tool calls, memories, and artifacts, so that agent behavior is fully observable, queryable, and auditable using ordinary SQL.
  • → **Tool safety requires defense in depth**: whitelist which entity types and fields are writable, enforce tool budgets with database triggers, scope every tool call's timeout and transaction, and audit all writes with run attribution and stated reasons.
  • → **Multi-agent coordination** can be built on PostgreSQL primitives — `SELECT FOR UPDATE SKIP LOCKED` for contention-free task queuing and `pg_notify`/`LISTEN` for lightweight event signaling — without requiring a separate message broker for moderate workloads.
  • → **Operational visibility into agent behavior** comes for free when state lives in PostgreSQL: tool performance statistics, budget exhaustion patterns, memory reuse rates, and full tool call replay are all available through standard SQL queries against the agent state tables.
