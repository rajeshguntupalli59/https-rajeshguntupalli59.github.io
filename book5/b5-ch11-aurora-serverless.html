Chapter 11: Aurora Serverless v2: Auto-Scaling in Practice

Aurora Serverless v2 represents one of the more significant architectural departures from traditional database capacity planning. Where you once sized an instance, benchmarked it, added 30% headroom, and hoped your estimates held through the next fiscal year, Aurora Serverless v2 lets the database scale compute capacity up and down in near real-time — in increments as small as 0.5 ACUs (Aurora Capacity Units) — without dropping connections or requiring a restart. For a DBA who has spent years managing instance fleets, over-provisioning for peak loads, and scheduling maintenance windows for vertical scaling, this requires a genuine shift in how you think about capacity. This chapter covers how ACUs work, how to configure scaling bounds, how the system behaves under real production load, what the billing model means for your architecture decisions, and where the gotchas live — particularly around connection behavior, writer/reader asymmetry, and the interactions between Serverless v2 and Aurora Global Database.

---

11.1 Aurora Capacity Units: What You're Actually Scaling

Before configuring anything, you need a clear mental model of what an Aurora Capacity Unit is. AWS defines 1 ACU as approximately 2 GiB of memory, with a proportional allocation of CPU and networking. This is not an exact ratio — Aurora does not expose the raw vCPU count the way an EC2 instance does — but as a working approximation, a 64 ACU instance is roughly equivalent to a db.r6g.16xlarge in CPU and memory terms, and a 0.5 ACU instance is a tiny slice suitable only for near-idle workloads.

The scaling range you configure is expressed as a minimum and maximum ACU value. The minimum can be as low as 0.5 ACUs (though there are practical implications to setting it this low, covered in §11.3). The maximum can be as high as 256 ACUs as of the current service limits, though that ceiling has been raised several times and you should check the AWS documentation for the current value.

What makes Serverless v2 categorically different from Serverless v1 is that scaling is continuous and fine-grained. v1 scaled in discrete steps and could take 15–30 seconds to respond, during which queries would queue or time out. v2 scales in sub-second increments. In practice this means that a sudden spike — a batch job firing, a marketing email going out, an end-of-day report — gets absorbed without the application seeing a degraded response time curve typical of traditional vertical scaling events.

One thing experienced DBAs sometimes misunderstand early on: ACU scaling only applies to compute. Aurora storage is always decoupled from the compute tier. The Aurora distributed storage layer scales automatically regardless of your ACU configuration, handles up to 128 TiB per cluster, and you are billed for storage separately. This matches the Aurora architecture you learned in Chapter 9 — the storage layer is shared across all instances in the cluster.

The relationship between ACUs and what you can observe in CloudWatch is through the ServerlessDatabaseCapacity metric, which reports the current ACU level. Pair this with CPUUtilization, DatabaseConnections, and FreeableMemory to build a complete picture of scaling behavior.

-- Run this against Aurora PostgreSQL to correlate what you observe
-- in CloudWatch with what the database is actually doing
SELECT 
    now()                                        AS sample_time,
    pg_postmaster_start_time()                   AS db_start_time,
    (SELECT count(*) FROM pg_stat_activity)      AS total_connections,
    (SELECT count(*) FROM pg_stat_activity 
     WHERE state = 'active')                     AS active_connections,
    (SELECT count(*) FROM pg_stat_activity 
     WHERE wait_event_type IS NOT NULL)          AS waiting_connections,
    pg_size_pretty(pg_database_size(current_database())) AS db_size;

This query, run periodically from a monitoring process, establishes the connection load baseline you'll use to validate that your ACU minimum is sized appropriately for your idle-state connection overhead.

11.2 Provisioning Aurora Serverless v2 with the AWS CLI and Terraform

Creating a Serverless v2 cluster is a two-step process: you create the Aurora cluster, then you add instances to it with a serverless scaling configuration. This is different from Aurora Serverless v1, where the cluster itself was serverless. In v2, the cluster is a standard Aurora cluster and the serverless behavior is a property of the individual DB instances within it.

Creating the cluster via AWS CLI:

# Step 1: Create the Aurora cluster (MySQL-compatible shown first, 
# then PostgreSQL pattern below)
aws rds create-db-cluster \
  --db-cluster-identifier prod-serverless-v2 \
  --engine aurora-postgresql \
  --engine-version 15.4 \
  --master-username dbadmin \
  --master-user-password "${DB_MASTER_PASSWORD}" \
  --vpc-security-group-ids sg-0abc123def456789a \
  --db-subnet-group-name prod-aurora-subnet-group \
  --backup-retention-period 7 \
  --preferred-backup-window "03:00-04:00" \
  --preferred-maintenance-window "sun:05:00-sun:06:00" \
  --storage-encrypted \
  --kms-key-id arn:aws:kms:us-east-1:123456789012:key/mrk-abc123 \
  --enable-cloudwatch-logs-exports '["postgresql"]' \
  --deletion-protection \
  --region us-east-1

# Step 2: Add the writer instance with Serverless v2 scaling configuration
aws rds create-db-instance \
  --db-instance-identifier prod-serverless-v2-writer \
  --db-cluster-identifier prod-serverless-v2 \
  --db-instance-class db.serverless \
  --engine aurora-postgresql \
  --region us-east-1

# Step 3: Modify the cluster's scaling configuration
# MinCapacity: 2 ACUs (never go below this — rationale in §11.3)
# MaxCapacity: 64 ACUs (size to your known peak, not theoretical maximum)
aws rds modify-db-cluster \
  --db-cluster-identifier prod-serverless-v2 \
  --serverless-v2-scaling-configuration MinCapacity=2,MaxCapacity=64 \
  --apply-immediately \
  --region us-east-1

One point worth noting: db.serverless is the instance class you specify — it is not a size within a family like db.r6g.xlarge. The ACU range you set on the cluster governs the actual compute allocation. This means you can have a writer and multiple readers that each independently scale within the same ACU bounds. The writer and readers do not share an ACU budget; each instance scales individually.

11.3 Scaling Behavior: What Triggers It, How Fast It Responds

Understanding the scaling triggers prevents you from being surprised by billing spikes and helps you tune the min/max bounds correctly. Aurora Serverless v2 monitors several signals to decide when to scale:

  • → **CPU utilization** relative to current capacity
  • → **Memory pressure** (buffer pool fill rate, swap activity)
  • → **Connection count** relative to the `max_connections` value for the current ACU level
  • → **Database load** as reported by the Performance Insights average active sessions metric

    • When any of these signals indicates the current ACU level is insufficient, the service scales up. Scale-up is aggressive by design — it happens in small increments but very quickly, typically completing within 1–2 seconds. Scale-down is deliberate and slow. AWS does not want a brief lull between query bursts to trigger a scale-down that then requires a scale-up moments later. In practice, expect scale-down to lag behind reduced load by several minutes.

    The minimum ACU floor matters more than people expect. At 0.5 ACUs, max_connections on Aurora PostgreSQL is approximately 90. That sounds fine until you realize that PgBouncer or RDS Proxy pools often open tens of connections just for health checks and pool maintenance, and your application likely has connection pools of its own. Setting MinCapacity=0.5 on a production cluster will result in connection failures whenever the cluster is at its minimum — usually late at night when you don't notice until your monitoring alerts on a failed 3 AM backup job.

    A practical minimum for production PostgreSQL workloads is 2 ACUs (approximately 4 GiB RAM, ~450 max connections). For MySQL-compatible Aurora, the connection scaling is more favorable at low ACU counts, but the same principle applies: never set your minimum to a value that makes the idle-state connection budget uncomfortably tight.

    The max_connections formula for Aurora PostgreSQL Serverless v2 is:

    LEAST({DBInstanceClassMemory/9531392}, 5000)

    where DBInstanceClassMemory is in bytes. At 2 ACUs (≈4 GiB), this yields approximately 450 connections. At 8 ACUs (≈16 GiB), approximately 1800. At 32 ACUs (≈64 GiB) the uncapped formula would exceed 5000, so the hard cap of 5000 applies.

    You can verify what your cluster is currently using:

    -- Aurora PostgreSQL: check current connection limit and usage
SELECT 
    current_setting('max_connections')::int          AS max_connections,
    count(*)                                          AS current_connections,
    count(*) FILTER (WHERE state = 'idle')           AS idle_connections,
    count(*) FILTER (WHERE state = 'active')         AS active_connections,
    count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_txn,
    round(
        count(*)::numeric / 
        current_setting('max_connections')::numeric * 100, 
    1)                                               AS pct_utilized
FROM pg_stat_activity
WHERE pid <> pg_backend_pid();

    If pct_utilized regularly exceeds 70% at your minimum ACU level, your minimum is too low. A scale-up event that is triggered by memory or CPU pressure will also increase the connection limit headroom — but the scale-up takes 1–2 seconds, and in that window, new connection attempts against a fully saturated connection limit will fail immediately.

    11.4 RDS Proxy Integration and the Connection Management Layer

    For Serverless v2, RDS Proxy is not optional — it is the architectural pattern that makes the auto-scaling behavior compatible with application-level connection pooling. Here is why.

    When Aurora Serverless v2 scales its ACU level, the database endpoint does not change, connections are not dropped, and there is no TCP-level interruption. This is the advertised behavior, and it holds true in steady-state scaling. However, at the extremes — when the cluster scales to its minimum and stays there for an extended idle period, or when you change the ACU bounds via a modify-db-cluster call — brief disruptions are possible. RDS Proxy absorbs these by maintaining its own connection pool to the backend and presenting a stable connection surface to applications.

    Beyond that protective function, RDS Proxy serves the standard purpose of multiplexing many application connections onto fewer database connections — a pattern you would traditionally implement with PgBouncer or pgpool-II on-premises. RDS Proxy uses IAM authentication and Secrets Manager to rotate credentials without connection disruption, which maps to what you previously handled manually in pg_hba.conf and password rotation scripts.

    # Create RDS Proxy for the Serverless v2 cluster
aws rds create-db-proxy \
  --db-proxy-name prod-serverless-v2-proxy \
  --engine-family POSTGRESQL \
  --auth '[
    {
      "AuthScheme": "SECRETS",
      "SecretArn": "arn:aws:secretsmanager:us-east-1:123456789012:secret:prod/aurora/dbadmin",
      "IAMAuth": "REQUIRED"
    }
  ]' \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-0abc123 subnet-0def456 subnet-0ghi789 \
  --vpc-security-group-ids sg-0abc123def456789a \
  --require-tls \
  --idle-client-timeout 1800 \
  --debug-logging false \
  --region us-east-1

# Register the Aurora cluster as the proxy target
aws rds register-db-proxy-targets \
  --db-proxy-name prod-serverless-v2-proxy \
  --db-cluster-identifiers prod-serverless-v2 \
  --region us-east-1

# Create a reader endpoint proxy target group for read scaling
aws rds create-db-proxy-endpoint \
  --db-proxy-name prod-serverless-v2-proxy \
  --db-proxy-endpoint-name prod-serverless-v2-proxy-reader \
  --vpc-subnet-ids subnet-0abc123 subnet-0def456 subnet-0ghi789 \
  --vpc-security-group-ids sg-0abc123def456789a \
  --target-role READ_ONLY \
  --region us-east-1

    IAM authentication through RDS Proxy replaces the traditional pg_hba.conf + password authentication model. Your application no longer stores a database password in its configuration. Instead, it generates a short-lived authentication token using the AWS SDK:

    # Python: Generate RDS IAM auth token and connect through RDS Proxy
# Requires boto3 and psycopg2

import boto3
import psycopg2
import os
from botocore.exceptions import ClientError

def get_rds_auth_token(
    hostname: str,
    port: int,
    username: str,
    region: str
) -> str:
    """
    Generate a 15-minute IAM authentication token for RDS/RDS Proxy.
    The EC2 instance or Lambda function must have an IAM role with
    rds-db:connect permission on the target resource.
    """
    client = boto3.client("rds", region_name=region)
    token = client.generate_db_auth_token(
        DBHostname=hostname,
        Port=port,
        DBUsername=username,
        Region=region
    )
    return token


def get_connection(read_only: bool = False) -> psycopg2.extensions.connection:
    """
    Return a psycopg2 connection through RDS Proxy.
    Uses IAM auth — no password stored in environment or config files.
    """
    region = os.environ["AWS_REGION"]
    
    if read_only:
        host = os.environ["RDS_PROXY_READER_ENDPOINT"]
    else:
        host = os.environ["RDS_PROXY_WRITER_ENDPOINT"]
    
    port = int(os.environ.get("DB_PORT", "5432"))
    username = os.environ["DB_USERNAME"]
    dbname = os.environ["DB_NAME"]

    token = get_rds_auth_token(host, port, username, region)

    conn = psycopg2.connect(
        host=host,
        port=port,
        user=username,
        password=token,       # IAM token used as password
        dbname=dbname,
        sslmode="verify-full",
        sslrootcert="/etc/ssl/certs/rds-combined-ca-bundle.pem",
        connect_timeout=10
    )

    # For read-only connections, enforce at the session level
    # as a defensive measure even though the proxy endpoint is read-only
    if read_only:
        conn.set_session(readonly=True)

    return conn


def execute_query(query: str, params: tuple = None, read_only: bool = False):
    """
    Execute a query and return results. Demonstrates connection reuse pattern
    appropriate for Lambda or short-lived application processes.
    For long-lived services, use a connection pool (e.g., psycopg2.pool or
    SQLAlchemy) with a max_overflow sized to your ACU minimum's connection budget.
    """
    conn = None
    try:
        conn = get_connection(read_only=read_only)
        with conn.cursor() as cur:
            cur.execute(query, params)
            if cur.description:  # SELECT
                return cur.fetchall()
            conn.commit()
            return cur.rowcount
    except psycopg2.OperationalError as e:
        # Log and re-raise — let the caller decide on retry strategy
        # Common causes: proxy is rotating target, ACU scale event in progress
        raise RuntimeError(f"Database connection failed: {e}") from e
    finally:
        if conn and not conn.closed:
            conn.close()

    One behavioral difference from on-premises PgBouncer that catches DBAs off guard: RDS Proxy operates in transaction pooling mode for MySQL and session pooling mode for PostgreSQL by default. Session pooling means that a proxy connection is pinned to a specific backend connection for the life of the session — it does not multiplex at the transaction level the way PgBouncer does in transaction mode. This limits the connection compression ratio for PostgreSQL workloads. The practical implication is that you should not expect RDS Proxy to reduce your backend connection count by 10:1 for a PostgreSQL Serverless v2 cluster the way it might for MySQL. Budget for a proxy-to-backend ratio closer to 3:1 or 4:1 for PostgreSQL.

    11.5 Monitoring, Alerting, and Cost Governance

    Aurora Serverless v2 billing is straightforward to understand but easy to mismanage. You are billed per ACU-hour, plus storage, plus I/O (unless you use Aurora I/O-Optimized storage) — check the current AWS pricing page for your region for the ACU-hour rate. A cluster that runs at a fixed ACU level continuously will cost roughly the same as a provisioned instance sized to match that capacity, since Serverless v2's per-second billing offers no discount for steady-state usage — you're paying for the compute you use either way. The economic argument for Serverless v2 is workloads that are spiky rather than flat, where peak capacity would otherwise sit idle most of the time on a fixed provisioned instance.

    CloudWatch provides the ServerlessDatabaseCapacity metric, which you should track alongside CPUUtilization and FreeableMemory to build a scaling profile. The following CloudWatch alarm setup uses the AWS CLI to alert when the cluster is approaching its maximum ACU ceiling:

    # CloudWatch alarm: writer approaching MaxCapacity
# Fires when the cluster sustains >= 90% of MaxCapacity for 5 consecutive minutes
# Adjust threshold (57.6 = 90% of 64 ACU max) and dimensions for your cluster

aws cloudwatch put-metric-alarm \
  --alarm-name "aurora-serverless-approaching-max-capacity" \
  --alarm-description "Writer ACU >= 90% of MaxCapacity for 5 minutes — review scaling bounds" \
  --namespace "AWS/RDS" \
  --metric-name "ServerlessDatabaseCapacity" \
  --dimensions Name=DBClusterIdentifier,Value=prod-serverless-v2 \
  --statistic Average \
  --period 60 \
  --evaluation-periods 5 \
  --threshold 57.6 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:dba-alerts \
  --ok-actions arn:aws:sns:us-east-1:123456789012:dba-alerts \
  --region us-east-1

# Complementary alarm: sustained high CPU suggesting compute is the bottleneck
aws cloudwatch put-metric-alarm \
  --alarm-name "aurora-serverless-high-cpu" \
  --alarm-description "CPU > 80% for 10 minutes while at or near MaxCapacity" \
  --namespace "AWS/RDS" \
  --metric-name "CPUUtilization" \
  --dimensions Name=DBClusterIdentifier,Value=prod-serverless-v2 \
  --statistic Average \
  --period 60 \
  --evaluation-periods 10 \
  --threshold 80 \
  --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:us-east-1:123456789012:dba-alerts \
  --region us-east-1

# Cost governance: set a monthly budget alert for the Aurora cluster
# Uses AWS Budgets, not CloudWatch — catches cost overruns before month-end
aws budgets create-budget \
  --account-id 123456789012 \
  --budget '{
    "BudgetName": "aurora-serverless-monthly",
    "BudgetLimit": {"Amount": "1500", "Unit": "USD"},
    "TimeUnit": "MONTHLY",
    "BudgetType": "COST",
    "CostFilters": {
      "Service": ["Amazon Relational Database Service"]
    }
  }' \
  --notifications-with-subscribers '[
    {
      "Notification": {
        "NotificationType": "ACTUAL",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 80,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {
          "SubscriptionType": "SNS",
          "Address": "arn:aws:sns:us-east-1:123456789012:dba-alerts"
        }
      ]
    },
    {
      "Notification": {
        "NotificationType": "FORECASTED",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 100,
        "ThresholdType": "PERCENTAGE"
      },
      "Subscribers": [
        {
          "SubscriptionType": "SNS",
          "Address": "arn:aws:sns:us-east-1:123456789012:dba-alerts"
        }
      ]
    }
  ]' \
  --region us-east-1

    The two-alert pattern — one on ServerlessDatabaseCapacity approaching MaxCapacity, one on forecasted budget overage — covers both the operational signal (the database is compute-constrained) and the financial signal (your ACU consumption is trending above plan). These serve different audiences: the capacity alarm goes to the on-call DBA, the budget alert goes to engineering management.

    Building a capacity utilization dashboard. Performance Insights is the most useful single tool for understanding whether your ACU bounds are correctly sized. The key metric to track is Database Load — the average number of active sessions divided by the number of vCPUs (or the ACU-normalized equivalent). When Database Load consistently exceeds your normalized ACU level, you are compute-bound and queries are queuing. When it is a small fraction of your MinCapacity, your minimum is over-provisioned.

    A practical SQL query to track load patterns directly from the database, useful for historical analysis or during a troubleshooting session:

    -- Aurora PostgreSQL: Identify top wait events contributing to load
-- Run this repeatedly during a high-load period to build a wait profile
SELECT
    wait_event_type,
    wait_event,
    state,
    count(*)                              AS session_count,
    round(count(*) * 100.0 / 
        NULLIF(SUM(count(*)) OVER (), 0), 
    1)                                    AS pct_of_total
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
  AND state <> 'idle'
GROUP BY wait_event_type, wait_event, state
ORDER BY session_count DESC
LIMIT 20;

    When wait_event_type = 'CPU' dominates this output, the cluster is compute-bound and you should consider raising MaxCapacity. When lock waits (wait_event_type = 'Lock') or ClientRead dominate, the issue is query design or application behavior, and raising ACU limits will not help. This distinction is the same analysis you would perform on any PostgreSQL instance — Serverless v2 does not change the diagnostic methodology, only the remediation path for compute-bound cases.

    11.6 Writer/Reader Asymmetry and Failover Behavior

    A subtlety in Serverless v2 that has tripped up production deployments: the writer and each reader instance scale independently. This is largely a benefit — a read-heavy reporting workload on a reader can scale to 32 ACUs without affecting the writer's billing or performance — but it introduces asymmetry that you need to account for in failover design.

    When a failover occurs (a writer instance failure, a blue/green deployment promotion, or an failover-db-cluster call), Aurora promotes one of the readers to writer. The promoted reader was scaling based on read traffic patterns. Immediately post-promotion, it must handle write traffic, which typically has a different CPU and memory profile. If your readers are sized with a lower MaxCapacity than the writer — which is tempting since reader workloads are often lighter — the newly promoted writer may scale up rapidly, potentially hitting the MaxCapacity ceiling before you have a chance to raise it.

    The operationally conservative configuration is to set the same ACU bounds on all instances in the cluster during initial deployment. You can differentiate later once you have a clear empirical profile of reader versus writer load, but launching with asymmetric bounds introduces risk in the failover scenario.

    You can test failover behavior explicitly in a maintenance window using the AWS CLI:

    # Initiate a manual failover to observe post-failover scaling behavior
# The --target-db-instance-identifier specifies which reader to promote
aws rds failover-db-cluster \
  --db-cluster-identifier prod-serverless-v2 \
  --target-db-instance-identifier prod-serverless-v2-reader-0 \
  --region us-east-1

# Poll cluster status until failover completes
# Typical duration for Aurora PostgreSQL: 20–40 seconds
watch -n 5 'aws rds describe-db-clusters \
  --db-cluster-identifier prod-serverless-v2 \
  --query "DBClusters[0].{Status:Status,Writer:DBClusterMembers[?IsClusterWriter==\`true\`].DBInstanceIdentifier|[0]}" \
  --output table \
  --region us-east-1'

    While the failover is in progress, monitor ServerlessDatabaseCapacity for both the newly promoted writer and the old writer (now a reader) to observe how quickly the scaling profile adjusts. What you will typically see: the new writer's ACU count climbs within the first 30–60 seconds as it absorbs write traffic, then stabilizes. The old writer, now a reader, may scale down if read traffic is lighter than write traffic was.

    Aurora Global Database and Serverless v2. If you have deployed a Global Database for cross-region disaster recovery (covered in Chapter 12), each regional cluster has its own ACU configuration. The secondary region cluster handles only read traffic (Global Database secondary clusters are read-only), so you might configure a lower MaxCapacity there. However, the same failover asymmetry concern applies at the Global Database level: a regional failover promotes the secondary to a primary, and it must now handle write traffic with whatever ACU bounds you configured for a read-only workload. The recommendation is the same: match the ACU bounds between primary and secondary regions, or accept the operational burden of adjusting bounds immediately post-failover.

    11.7 Practical Capacity Sizing: From Workload Profile to ACU Bounds

    Given everything covered in this chapter, you need a concrete method for translating your workload characteristics into initial ACU min/max values. The following framework is not a formula — Aurora scaling behavior depends on too many workload-specific factors for a formula to be reliable — but it provides a structured starting point.

    Step 1: Establish your peak compute requirement.

    If you are migrating from a provisioned Aurora or RDS instance, your starting point is the instance class you are currently running. Map that to an approximate ACU equivalent:

    | Provisioned Instance | Approx ACU Equivalent |

    |---------------------|----------------------|

    | db.t3.medium | 1–2 ACUs |

    | db.r6g.large | 2–4 ACUs |

    | db.r6g.xlarge | 4–8 ACUs |

    | db.r6g.2xlarge | 8–16 ACUs |

    | db.r6g.4xlarge | 16–32 ACUs |

    | db.r6g.8xlarge | 32–64 ACUs |

    | db.r6g.16xlarge | 64–128 ACUs |

    Your MaxCapacity should be set at or above the ACU equivalent of your current instance class. If your current instance runs at 60–70% CPU utilization at peak, you have headroom and your MaxCapacity could be set to the equivalent of your current instance. If your current instance regularly hits 80–90%, set MaxCapacity one step above.

    Step 2: Profile your idle state.

    The minimum ACU determines what you pay during off-peak hours and sets the connection budget floor. Run the connection utilization query from §11.3 during your quietest maintenance window:

    -- Aurora PostgreSQL: Idle-state connection profile
-- Run during off-peak hours to establish minimum connection requirements
SELECT
    application_name,
    state,
    count(*)          AS connection_count
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
GROUP BY application_name, state
ORDER BY connection_count DESC;

    Sum up the connections from monitoring agents, connection pools, and application idle pools. That total is your idle-state connection floor. Work backwards through the max_connections formula: if your idle state holds 200 connections, you need at least 2 ACUs (which yields ~450 max_connections). If your monitoring infrastructure alone holds 50 connections and your app pools another 100, 2 ACUs gives you adequate headroom.

    Step 3: Review the ACU utilization history post-launch.

    After running for two to four weeks, pull ServerlessDatabaseCapacity from CloudWatch and build a percentile distribution. The P99 value over that period is a strong candidate for your MaxCapacity. If the P99 is well below your configured maximum, consider lowering it — not because a higher maximum costs more at idle (it does not), but because a hard ceiling prevents runaway queries from consuming unbounded resources. A rogue cartesian join at 3 AM should not be allowed to scale your cluster to 256 ACUs.

    # Pull ServerlessDatabaseCapacity statistics for the last 14 days
# This gives you the distribution of actual ACU consumption
aws cloudwatch get-metric-statistics \
  --namespace "AWS/RDS" \
  --metric-name "ServerlessDatabaseCapacity" \
  --dimensions Name=DBClusterIdentifier,Value=prod-serverless-v2 \
  --start-time "$(date -u -d '14 days ago' '+%Y-%m-%dT%H:%M:%SZ')" \
  --end-time "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
  --period 3600 \
  --statistics Average Maximum \
  --query 'sort_by(Datapoints, &Timestamp)[*].{Time:Timestamp,Avg:Average,Max:Maximum}' \
  --output table \
  --region us-east-1

    Use the Maximum statistic across all hourly periods to find your observed peak ACU level. Use the Average to understand your typical billing rate. The ratio of Average to Maximum is a good indicator of how spiky your workload is — a high ratio (close to 1.0) means your workload is relatively flat and Serverless v2 may not be the most cost-effective choice compared to Reserved Instance pricing on a provisioned cluster. A low ratio (0.2–0.4) means you are getting real economic benefit from the auto-scaling.

    11.8 Limitations and When Serverless v2 Is Not the Right Choice

    Serverless v2 is compelling for many workloads, but there are cases where you should stay with provisioned instances or at least mix serverless and provisioned within the same cluster.

    I/O-intensive workloads and storage throughput. ACU scaling governs compute — it does not change the underlying storage I/O throughput in the same way a larger provisioned instance would. Very high I/O workloads (bulk data loads, intensive VACUUM operations, high-throughput analytics) may find that compute scales fine but storage I/O becomes the bottleneck. In these cases, the VolumeReadIOPs and VolumeWriteIOPs CloudWatch metrics will plateau while CPUUtilization remains moderate — a signature that compute auto-scaling is not addressing the actual constraint.

    Latency-sensitive workloads during cold starts. If you set MinCapacity to 0.5 ACUs and your cluster sits truly idle overnight, the first queries of the morning will experience elevated latency as the cluster scales from its minimum. This is not the dramatic cold start of Serverless v1 (which could be 10–30 seconds), but there is a ramp period of a few seconds where response times are higher than steady-state. For applications where consistent sub-10ms query response is required across all hours, a minimum of 2 ACUs or higher effectively eliminates this behavior.

    Aurora Parallel Query. As of the current service version, Aurora Parallel Query (which pushes query processing down to the storage layer for large table scans) is not available on Serverless v2 instances. If your workload depends on Parallel Query for analytics performance, you need to run those queries against a provisioned reader in the same cluster, rather than a serverless reader.

    Cross-engine compatibility. Serverless v2 is available for both Aurora MySQL and Aurora PostgreSQL, but the specific minor version support changes with each engine release. Always verify that the engine version you need is available in the db.serverless instance class before committing to the architecture:

    # Check which Aurora PostgreSQL versions support Serverless v2
aws rds describe-orderable-db-instance-options \
  --engine aurora-postgresql \
  --db-instance-class db.serverless \
  --query 'OrderableDBInstanceOptions[*].{Version:EngineVersion,MultiAZ:MultiAZCapable}' \
  --output table \
  --region us-east-1

    RDS Proxy limitations with prepared statements. If your application uses named prepared statements that persist across transactions (common in some ORM frameworks and PostgreSQL-specific drivers), RDS Proxy session pinning behavior will hold a backend connection open for the life of the client session, effectively eliminating the multiplexing benefit. In these cases, the proxy adds latency overhead without reducing backend connection pressure. Profile your application's prepared statement behavior before deploying RDS Proxy in front of Serverless v2.

    ---

    Key Takeaways

  • → **ACUs are compute abstractions, not instance sizes.** One ACU maps to approximately 2 GiB of memory with proportional CPU. The `db.serverless` instance class takes its actual compute allocation from the cluster's `serverless_v2_scaling_configuration` min/max bounds, and each instance in the cluster scales independently within those bounds.
  • → **Set your minimum ACU floor based on connection budget, not cost minimization.** The `max_connections` limit scales with ACU level. A 0.5 ACU minimum leaves fewer than 100 connections available — insufficient for most production workloads including monitoring agents and idle connection pools. A 2 ACU minimum is a more defensible floor for PostgreSQL clusters.
  • → **RDS Proxy is the recommended connection layer for Serverless v2, but understand its PostgreSQL session pooling behavior.** Unlike MySQL (which supports transaction pooling), RDS Proxy uses session pooling for PostgreSQL, meaning backend connections are pinned per client session. Plan for a 3:1 to 4:1 proxy-to-backend ratio rather than the higher compression ratios achievable with PgBouncer in transaction mode.
  • → **Writer and reader instances scale independently — account for failover asymmetry.** If readers are configured with lower `MaxCapacity` than the writer and a failover promotes a reader to writer, the new writer may rapidly approach its ACU ceiling under write traffic. Start with symmetric ACU bounds across all instances and differentiate only after empirical profiling.
  • → **Use the ratio of average to peak `ServerlessDatabaseCapacity` to evaluate fit.** A flat workload (high average-to-peak ratio) derives little economic benefit from Serverless v2 compared to Reserved Instance pricing on a provisioned cluster. A spiky workload (low average-to-peak ratio) is where Serverless v2's billing model pays dividends. Build this analysis from two to four weeks of CloudWatch data before committing to the architecture long-term.
