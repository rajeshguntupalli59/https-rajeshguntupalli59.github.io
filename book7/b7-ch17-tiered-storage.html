Chapter 17: Tiered Storage: Moving Cold Data Cheaply

Organizations that audit their cloud database storage seriously almost always find the same thing: 60–80% of the data sitting on expensive SSD-backed block storage has not been touched in months. That data costs the same per gigabyte as the hot rows your application reads thousands of times per second. Moving cold data to cheaper storage tiers—S3, Azure Blob, GCS, or archival-class object storage—routinely reduces total database storage costs by 40–70%, and on multi-terabyte databases that translates directly to $8,000–$50,000 per year in avoided spend. This chapter walks through how to identify cold data, classify it systematically, move it to the right storage tier, and automate the entire lifecycle so it keeps paying dividends without manual intervention every quarter.

---

17.1 Understanding the Storage Cost Stack

Before moving anything, you need to understand what you are paying for and why the pricing spread across tiers is so dramatic.

AWS RDS storage pricing (us-east-1, 2024):

| Storage Type | Cost per GB-month |

|---|---|

| gp2 SSD | $0.115 |

| gp3 SSD | $0.092 |

| io1 / io2 SSD | $0.125–$0.138 |

| S3 Standard | $0.023 |

| S3 Standard-IA | $0.0125 |

| S3 Glacier Instant | $0.004 |

| S3 Glacier Deep Archive | $0.00099 |

The math is straightforward. A 1 TB volume on gp2 costs $117.76/month. That same 1 TB on S3 Glacier Deep Archive costs $1.01/month. The gap is 116x. Even moving to S3 Standard-IA costs 10x less than gp2.

Azure SQL / Blob pricing (East US, 2024):

| Storage Type | Cost per GB-month |

|---|---|

| Azure SQL Premium (P-series) | $0.114 |

| Azure SQL General Purpose | $0.115 |

| Azure Blob Hot | $0.018 |

| Azure Blob Cool | $0.01 |

| Azure Blob Archive | $0.00099 |

Google Cloud (us-central1, 2024):

| Storage Type | Cost per GB-month |

|---|---|

| Cloud SQL SSD | $0.17 |

| Cloud SQL HDD | $0.09 |

| GCS Standard | $0.020 |

| GCS Nearline | $0.010 |

| GCS Coldline | $0.004 |

| GCS Archive | $0.0012 |

The pricing structure across all three clouds tells the same story: object storage is an order of magnitude cheaper than block storage attached to your database instances. The technical challenge is not the pricing—it is designing the data movement pipeline so that cold data moves gracefully and retrieval remains possible when needed.

Worked example: 10 TB audit log table on AWS RDS (gp3)

Current: 10,000 GB × $0.092 = $920/month = $11,040/year
After archiving 8 TB to S3 Glacier Instant:
  Hot tier (2 TB on gp3):  2,000 × $0.092 =  $184/month
  Cold tier (8 TB on Glacier Instant): 8,000 × $0.004 = $32/month
  Total: $216/month = $2,592/year
Annual savings: $8,448 (76% reduction)

17.2 Diagnosing Cold Data: Finding What You Can Archive

You cannot archive what you cannot identify. The first step is building a clear picture of data age, access patterns, and business rules for retention.

Identifying table-level age distribution in PostgreSQL:

-- Find tables with the oldest average tuple age
-- Run on each RDS PostgreSQL / Aurora PostgreSQL instance
SELECT
    schemaname,
    relname AS table_name,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || relname)) AS total_size,
    pg_total_relation_size(schemaname || '.' || relname) AS total_bytes,
    n_live_tup AS live_rows,
    n_dead_tup AS dead_rows,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    -- Estimate staleness: tables not analyzed in 90 days are candidates
    CASE
        WHEN COALESCE(last_autoanalyze, last_analyze) < NOW() - INTERVAL '90 days'
          OR COALESCE(last_autoanalyze, last_analyze) IS NULL
        THEN 'Cold candidate'
        WHEN COALESCE(last_autoanalyze, last_analyze) < NOW() - INTERVAL '30 days'
        THEN 'Warm - monitor'
        ELSE 'Active'
    END AS access_classification
FROM
    pg_stat_user_tables
ORDER BY
    total_bytes DESC;
-- Find the date range of data in each table that has a created_at column
-- This query generates dynamic SQL for inspection
SELECT
    'SELECT '''
    || table_schema || '.' || table_name
    || ''' AS tbl, MIN(' || column_name || ') AS oldest_row, '
    || 'MAX(' || column_name || ') AS newest_row, '
    || 'COUNT(*) AS total_rows '
    || 'FROM ' || table_schema || '.' || table_name || ';' AS inspection_sql
FROM
    information_schema.columns
WHERE
    column_name IN ('created_at', 'created_date', 'inserted_at', 'event_time', 'timestamp')
    AND table_schema NOT IN ('pg_catalog', 'information_schema')
ORDER BY
    table_schema, table_name;
-- For SQL Server / Azure SQL: find table age distribution
-- using sys.dm_db_index_usage_stats
SELECT
    OBJECT_NAME(i.object_id) AS table_name,
    i.name AS index_name,
    ius.user_seeks,
    ius.user_scans,
    ius.user_lookups,
    ius.user_updates,
    ius.last_user_seek,
    ius.last_user_scan,
    ius.last_user_lookup,
    -- Total read activity
    (ius.user_seeks + ius.user_scans + ius.user_lookups) AS total_reads,
    CASE
        WHEN ius.last_user_seek < GETDATE() - 90
          OR ius.last_user_seek IS NULL
        THEN 'Archive candidate'
        WHEN ius.last_user_seek < GETDATE() - 30
        THEN 'Monitor'
        ELSE 'Active'
    END AS recommendation
FROM
    sys.indexes i
    LEFT JOIN sys.dm_db_index_usage_stats ius
        ON i.object_id = ius.object_id
        AND i.index_id = ius.index_id
        AND ius.database_id = DB_ID()
WHERE
    OBJECTPROPERTY(i.object_id, 'IsUserTable') = 1
ORDER BY
    total_reads ASC,
    table_name;

Beyond table-level statistics, you need CloudWatch or Azure Monitor metrics to confirm that the storage IOPS consumption is actually coming from a small subset of tables. A table that shows up as large in pg_stat_user_tables but consumes zero IOPS is a clean archival candidate. A large table with high IOPS is not—even if most rows are old.

Pulling CloudWatch RDS storage and IOPS metrics via AWS CLI:

#!/bin/bash
# Pull RDS IOPS and storage metrics for the last 30 days
# to identify instances with underutilized storage capacity

DB_INSTANCE="prod-postgres-01"
START_DATE=$(date -u -d '30 days ago' +%Y-%m-%dT%H:%M:%SZ)
END_DATE=$(date -u +%Y-%m-%dT%H:%M:%SZ)
REGION="us-east-1"

echo "=== Read IOPS (avg over 30 days) ==="
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ReadIOPS \
  --dimensions Name=DBInstanceIdentifier,Value=$DB_INSTANCE \
  --start-time $START_DATE \
  --end-time $END_DATE \
  --period 86400 \
  --statistics Average \
  --region $REGION \
  --output table \
  --query 'sort_by(Datapoints, &Timestamp)[*].{Date:Timestamp,AvgReadIOPS:Average}'

echo ""
echo "=== Write IOPS (avg over 30 days) ==="
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name WriteIOPS \
  --dimensions Name=DBInstanceIdentifier,Value=$DB_INSTANCE \
  --start-time $START_DATE \
  --end-time $END_DATE \
  --period 86400 \
  --statistics Average \
  --region $REGION \
  --output table \
  --query 'sort_by(Datapoints, &Timestamp)[*].{Date:Timestamp,AvgWriteIOPS:Average}'

echo ""
echo "=== Free Storage Space (min over 30 days) ==="
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name FreeStorageSpace \
  --dimensions Name=DBInstanceIdentifier,Value=$DB_INSTANCE \
  --start-time $START_DATE \
  --end-time $END_DATE \
  --period 86400 \
  --statistics Minimum \
  --region $REGION \
  --output table \
  --query 'sort_by(Datapoints, &Timestamp)[*].{Date:Timestamp,FreeGB:Minimum}' \
  | awk '{if ($0 ~ /[0-9]/) {split($0,a,"|"); printf "%-25s %10.2f GB\n", a[2], a[3]/1073741824} else print}'

17.3 Classifying and Partitioning Data for Tiered Movement

The most reliable pattern for tiered storage is range partitioning by time. Once you know which tables have archivable data, you restructure them so that cold partitions can be detached and exported cleanly without touching active data.

Creating a partitioned table in PostgreSQL for future tiering:

-- Convert an existing unpartitioned table to a partitioned structure
-- This example handles an audit_events table with 3 years of history

-- Step 1: Create the new partitioned parent table
CREATE TABLE audit_events_partitioned (
    id          BIGSERIAL,
    user_id     BIGINT       NOT NULL,
    event_type  VARCHAR(100) NOT NULL,
    event_data  JSONB,
    ip_address  INET,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- Step 2: Create partitions for each quarter going back 2 years
-- Current quarter stays hot; older quarters become archive candidates
DO $$
DECLARE
    start_date DATE := DATE_TRUNC('quarter', NOW() - INTERVAL '2 years');
    end_date   DATE;
    part_name  TEXT;
BEGIN
    WHILE start_date < DATE_TRUNC('quarter', NOW()) LOOP
        end_date  := start_date + INTERVAL '3 months';
        part_name := 'audit_events_'
                     || TO_CHAR(start_date, 'YYYY_Q"Q"');

        EXECUTE FORMAT(
            'CREATE TABLE IF NOT EXISTS %I
             PARTITION OF audit_events_partitioned
             FOR VALUES FROM (%L) TO (%L)',
            part_name,
            start_date,
            end_date
        );

        RAISE NOTICE 'Created partition: % covering % to %',
                     part_name, start_date, end_date;

        start_date := end_date;
    END LOOP;
END $$;

-- Step 3: Create the current active partition
CREATE TABLE audit_events_current
    PARTITION OF audit_events_partitioned
    FOR VALUES FROM (DATE_TRUNC('quarter', NOW()))
               TO   (DATE_TRUNC('quarter', NOW()) + INTERVAL '3 months');

-- Step 4: Create a default partition for future inserts outside expected range
CREATE TABLE audit_events_future
    PARTITION OF audit_events_partitioned
    DEFAULT;

-- Step 5: View partition sizes to understand archival opportunity
SELECT
    child.relname                                             AS partition_name,
    pg_size_pretty(pg_total_relation_size(child.oid))        AS total_size,
    pg_total_relation_size(child.oid)                        AS bytes,
    parent.relname                                            AS parent_table
FROM
    pg_inherits
    JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
    JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
WHERE
    parent.relname = 'audit_events_partitioned'
ORDER BY
    child.relname;

Once partitions exist, the archival workflow is clean: detach a partition, export it to S3/GCS/Blob as Parquet or CSV, verify the export, then drop the partition. The table keeps serving queries with no downtime.

Detach, export, and verify workflow for PostgreSQL on AWS RDS:

-- Step 1: Detach the oldest partition (run during maintenance window or off-peak)
-- Detached partition remains queryable as a standalone table
ALTER TABLE audit_events_partitioned
    DETACH PARTITION audit_events_2022_q1;

-- Step 2: Confirm row counts match before export
SELECT COUNT(*) FROM audit_events_2022_q1;
-- Save this number for post-export validation

-- Step 3: Export the detached partition via COPY to S3
-- (Use aws_s3 extension on RDS PostgreSQL)
SELECT aws_s3.query_export_to_s3(
    'SELECT * FROM audit_events_2022_q1',
    aws_commons.create_s3_uri(
        'your-archive-bucket',
        'database-archive/audit_events/2022/Q1/audit_events_2022_q1.csv',
        'us-east-1'
    ),
    options := 'FORMAT CSV, HEADER true'
);

-- Step 4: Verify export row count by querying S3 via Athena (run separately)
-- SELECT COUNT(*) FROM archive_audit_events WHERE year=2022 AND quarter=1;

-- Step 5: After verification, drop the partition
-- Only run after confirming S3 export matches row count
DROP TABLE audit_events_2022_q1;

-- Step 6: Record the archival in your metadata tracking table
INSERT INTO archive_metadata (
    original_table,
    partition_name,
    archive_path,
    row_count,
    archived_at,
    archived_by,
    verified
) VALUES (
    'audit_events_partitioned',
    'audit_events_2022_q1',
    's3://your-archive-bucket/database-archive/audit_events/2022/Q1/',
    (SELECT COUNT(*) FROM audit_events_2022_q1),  -- captured before DROP
    NOW(),
    CURRENT_USER,
    false  -- set to true after Athena validation
);

17.4 Automated Tiering with S3 Lifecycle Policies and AWS Glue

Manual archival runs once. Automation runs forever. The goal is a pipeline that identifies cold partitions on a schedule, exports them, validates the export, and transitions the objects through S3 storage classes automatically as they age further.

S3 lifecycle policy to transition archived database exports through storage tiers:

#!/bin/bash
# Apply a lifecycle policy to the database archive bucket
# Transitions: Standard → Standard-IA (30d) → Glacier Instant (90d) → Deep Archive (365d)

BUCKET="your-archive-bucket"

cat > /tmp/lifecycle-policy.json << 'EOF'
{
  "Rules": [
    {
      "ID": "DatabaseArchiveTiering",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "database-archive/"
      },
      "Transitions": [
        {
          "Days": 30,
          "StorageClass": "STANDARD_IA"
        },
        {
          "Days": 90,
          "StorageClass": "GLACIER_IR"
        },
        {
          "Days": 365,
          "StorageClass": "DEEP_ARCHIVE"
        }
      ],
      "NoncurrentVersionTransitions": [
        {
          "NoncurrentDays": 7,
          "StorageClass": "STANDARD_IA"
        }
      ],
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 90
      }
    },
    {
      "ID": "DeleteExpiredArchives",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "database-archive/audit_events/"
      },
      "Expiration": {
        "Days": 2555
      }
    }
  ]
}
EOF

aws s3api put-bucket-lifecycle-configuration \
  --bucket $BUCKET \
  --lifecycle-configuration file:///tmp/lifecycle-policy.json

echo "Lifecycle policy applied to s3://$BUCKET"

# Verify the policy was applied
aws s3api get-bucket-lifecycle-configuration \
  --bucket $BUCKET \
  --output json | jq '.Rules[] | {ID: .ID, Status: .Status, Transitions: .Transitions}'
