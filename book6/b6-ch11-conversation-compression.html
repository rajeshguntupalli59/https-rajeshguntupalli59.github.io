Chapter 11: Conversation Summarization and Compression in the Database

Every production chatbot eventually runs into the same wall: context windows are finite, tokens are expensive, and users have long memories. A customer who started a support conversation three weeks ago expects your AI to remember the resolution — but storing every message verbatim and replaying the full transcript on each request is neither scalable nor economical. Conversation summarization solves this by compressing older turns into dense representations while keeping recent turns verbatim, giving the model enough context without burning your token budget. This chapter shows how to design, implement, and operate a conversation compression pipeline entirely within PostgreSQL, with async summarization jobs, rolling summaries, embedding-based retrieval for relevant history, and production-grade monitoring. PostgreSQL is the right place to build this — it gives you transactional consistency between raw messages and their summaries, trigger-driven automation, JSONB for metadata, and pgvector for semantic recall, all in one system rather than five.

---

11.1 The Context Window Problem and Why Compression Belongs in the Database

A language model doesn't read your database. It reads a prompt. Everything your application knows about a user's conversation history has to be squeezed into that prompt before the model ever sees it. This creates a hard engineering constraint: the prompt must be short enough to fit the context window, recent enough to feel coherent, and complete enough to be useful. Most teams handle this badly — they either truncate blindly (losing critical information), replay everything (burning tokens), or move to an external vector store (losing transactional consistency).

The database-centric approach treats conversation memory as a first-class data problem. Messages are rows. Summaries are rows. Embeddings are columns. The rules for when to summarize, what to include, and how to retrieve relevant history are queries. Every operation is transactional, auditable, and indexable.

The strategy has three tiers:

Tier 1 — Verbatim recent history: the last N turns, always included in full. N is typically 4–10 depending on average turn length.

Tier 2 — Rolling summary: a periodically regenerated compressed narrative of older turns, included as a paragraph-length summary.

Tier 3 — Semantic recall: embeddings of older turns, queried at retrieval time to pull back turns that are semantically similar to the current user message, even if they happened long ago.

graph TD
    Q[Current user message] --> P[Assembled prompt]
    T1[Tier 1: last N turns, verbatim] --> P
    T2[Tier 2: rolling summary of older turns] --> P
    T3["Tier 3: pgvector search over old turns, semantic match to Q"] --> P

*All three tiers land in the same prompt; only Tier 3 depends on the current message, which is why it's computed at retrieval time rather than kept rolling like Tier 2.*

-- Complete schema for a three-tier conversation memory system

CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;  -- for fuzzy search on text content

-- Core conversation and session tracking
CREATE TABLE conversations (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id             BIGINT NOT NULL,
    channel             TEXT NOT NULL DEFAULT 'web',   -- web, slack, api, mobile
    title               TEXT,                           -- auto-generated or user-set
    status              TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'archived', 'deleted')),
    metadata            JSONB NOT NULL DEFAULT '{}',
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_active_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    message_count       INT NOT NULL DEFAULT 0,
    total_tokens_used   BIGINT NOT NULL DEFAULT 0
);

CREATE INDEX idx_conversations_user_active
    ON conversations (user_id, last_active_at DESC)
    WHERE status = 'active';

-- Raw message store — the source of truth
CREATE TABLE messages (
    id              BIGSERIAL PRIMARY KEY,
    conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    turn_number     INT NOT NULL,           -- sequential within conversation
    role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool')),
    content         TEXT NOT NULL,
    content_tokens  INT,                    -- populated by application layer
    model_used      TEXT,                   -- which model generated this (for assistant turns)
    metadata        JSONB NOT NULL DEFAULT '{}',  -- tool calls, citations, latency, etc.
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    summarized      BOOLEAN NOT NULL DEFAULT FALSE,  -- has this turn been rolled into a summary?
    UNIQUE (conversation_id, turn_number)
);

CREATE INDEX idx_messages_conversation_turn
    ON messages (conversation_id, turn_number DESC);

CREATE INDEX idx_messages_unsummarized
    ON messages (conversation_id, turn_number)
    WHERE summarized = FALSE;

-- Rolling summaries — one or more per conversation
CREATE TABLE conversation_summaries (
    id                  BIGSERIAL PRIMARY KEY,
    conversation_id     UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    summary_version     INT NOT NULL DEFAULT 1,  -- increments on each regeneration
    turn_range_start    INT NOT NULL,            -- first turn number covered
    turn_range_end      INT NOT NULL,            -- last turn number covered
    content             TEXT NOT NULL,           -- the summary text
    content_tokens      INT,
    model_used          TEXT NOT NULL,
    generation_latency_ms INT,
    is_current          BOOLEAN NOT NULL DEFAULT TRUE,
    embedding           VECTOR(1536),            -- embed the summary for semantic retrieval
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (conversation_id, summary_version)
);

CREATE INDEX idx_summaries_conversation_current
    ON conversation_summaries (conversation_id, summary_version DESC)
    WHERE is_current = TRUE;

CREATE INDEX idx_summaries_embedding
    ON conversation_summaries USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

-- Per-message embeddings for semantic recall (Tier 3)
CREATE TABLE message_embeddings (
    message_id      BIGINT PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
    embedding       VECTOR(1536) NOT NULL,
    model_used      TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_message_embeddings_vec
    ON message_embeddings USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

-- Compression job queue — tracks summarization work
CREATE TABLE summarization_jobs (
    id                  BIGSERIAL PRIMARY KEY,
    conversation_id     UUID NOT NULL REFERENCES conversations(id),
    status              TEXT NOT NULL DEFAULT 'pending'
                        CHECK (status IN ('pending', 'running', 'completed', 'failed')),
    trigger_reason      TEXT NOT NULL,  -- 'turn_count', 'token_budget', 'manual', 'scheduled'
    turns_to_summarize  INT[],          -- array of turn numbers to compress
    attempt_count       INT NOT NULL DEFAULT 0,
    last_error          TEXT,
    scheduled_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at          TIMESTAMPTZ,
    completed_at        TIMESTAMPTZ,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_summarization_jobs_pending
    ON summarization_jobs (scheduled_at)
    WHERE status = 'pending';

This schema is intentionally normalized. Summaries are rows, not JSONB fields buried inside a conversation record. That gives you version history, allows multiple granularities of summary (chapter-level, session-level), and makes it straightforward to query which turns have and haven't been compressed.

11.2 Trigger-Driven Compression Scheduling

The best compression pipelines are invisible to application code. When a message is inserted, a database trigger evaluates whether compression is needed and enqueues a job if so. The application doesn't make that decision — the database does, consistently, every time.

-- Function to count unsummarized tokens and decide whether to enqueue compression
CREATE OR REPLACE FUNCTION estimate_message_tokens(content TEXT)
RETURNS INT
LANGUAGE sql
IMMUTABLE
AS $$
    -- Rough approximation: 1 token ≈ 4 characters for English
    -- Replace with a more precise calculation if needed
    SELECT greatest(1, length(content) / 4);
$$;

CREATE OR REPLACE FUNCTION update_conversation_stats()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE conversations
    SET
        message_count      = message_count + 1,
        last_active_at     = now(),
        total_tokens_used  = total_tokens_used + COALESCE(NEW.content_tokens, estimate_message_tokens(NEW.content))
    WHERE id = NEW.conversation_id;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_update_conversation_stats
    AFTER INSERT ON messages
    FOR EACH ROW
    EXECUTE FUNCTION update_conversation_stats();

-- Core compression scheduler: enqueues a job when unsummarized turns exceed threshold
CREATE OR REPLACE FUNCTION maybe_schedule_summarization()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_unsummarized_count    INT;
    v_unsummarized_tokens   BIGINT;
    v_turn_threshold        INT     := 15;   -- summarize after 15 unsummarized turns
    v_token_threshold       INT     := 6000; -- or after ~6k unsummarized tokens
    v_keep_verbatim         INT     := 6;    -- always keep last 6 turns verbatim
    v_turns_to_summarize    INT[];
    v_pending_exists        BOOLEAN;
BEGIN
    -- Don't schedule if there's already a pending job for this conversation
    SELECT EXISTS (
        SELECT 1 FROM summarization_jobs
        WHERE conversation_id = NEW.conversation_id
          AND status IN ('pending', 'running')
    ) INTO v_pending_exists;

    IF v_pending_exists THEN
        RETURN NEW;
    END IF;

    -- Count unsummarized turns, excluding the most recent ones we want to keep verbatim
    SELECT
        COUNT(*),
        COALESCE(SUM(COALESCE(content_tokens, estimate_message_tokens(content))), 0)
    INTO v_unsummarized_count, v_unsummarized_tokens
    FROM messages m
    WHERE m.conversation_id = NEW.conversation_id
      AND m.summarized = FALSE
      AND m.turn_number < (
          SELECT turn_number
          FROM messages
          WHERE conversation_id = NEW.conversation_id
          ORDER BY turn_number DESC
          LIMIT 1 OFFSET (v_keep_verbatim - 1)
      );

    -- Check if we've crossed either threshold
    IF v_unsummarized_count >= v_turn_threshold OR v_unsummarized_tokens >= v_token_threshold THEN

        -- Collect the turn numbers that need summarizing
        SELECT array_agg(turn_number ORDER BY turn_number)
        INTO v_turns_to_summarize
        FROM messages m
        WHERE m.conversation_id = NEW.conversation_id
          AND m.summarized = FALSE
          AND m.turn_number < (
              SELECT turn_number
              FROM messages
              WHERE conversation_id = NEW.conversation_id
              ORDER BY turn_number DESC
              LIMIT 1 OFFSET (v_keep_verbatim - 1)
          );

        INSERT INTO summarization_jobs (
            conversation_id,
            trigger_reason,
            turns_to_summarize
        ) VALUES (
            NEW.conversation_id,
            CASE
                WHEN v_unsummarized_tokens >= v_token_threshold THEN 'token_budget'
                ELSE 'turn_count'
            END,
            v_turns_to_summarize
        );

        -- Notify the async worker via pg_notify
        PERFORM pg_notify(
            'summarization_needed',
            json_build_object(
                'conversation_id', NEW.conversation_id,
                'turn_count',      v_unsummarized_count,
                'token_estimate',  v_unsummarized_tokens
            )::text
        );
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_maybe_schedule_summarization
    AFTER INSERT ON messages
    FOR EACH ROW
    WHEN (NEW.role IN ('assistant', 'user'))  -- don't trigger on system/tool messages
    EXECUTE FUNCTION maybe_schedule_summarization();

-- Helper view: what context should be assembled for a given conversation?
CREATE OR REPLACE VIEW conversation_context AS
SELECT
    c.id AS conversation_id,
    c.user_id,
    -- Current summary (if any)
    cs.content           AS summary_text,
    cs.turn_range_start  AS summary_covers_from,
    cs.turn_range_end    AS summary_covers_to,
    -- Recent verbatim turns
    (
        SELECT json_agg(
            json_build_object(
                'role',       m.role,
                'content',    m.content,
                'turn',       m.turn_number,
                'created_at', m.created_at
            )
            ORDER BY m.turn_number
        )
        FROM messages m
        WHERE m.conversation_id = c.id
          AND m.summarized = FALSE
    ) AS recent_turns,
    c.message_count,
    c.last_active_at
FROM conversations c
LEFT JOIN conversation_summaries cs
    ON cs.conversation_id = c.id
    AND cs.is_current = TRUE;

The pg_notify call at the end of the trigger is what connects the database event to your async Python worker. The trigger does the decision-making; the worker does the expensive LLM call. This separation means your INSERT latency is unaffected by summarization time.

11.3 The Summarization Worker

The async worker listens on the PostgreSQL notification channel and processes jobs when they appear. It uses Celery for retry logic and Claude or GPT-4o for the actual summarization, then writes the result back and marks messages as summarized — atomically.

# summarization_worker.py
# Celery worker that listens for pg_notify events and runs summarization jobs

import asyncio
import json
import logging
import time
from datetime import datetime
from typing import Optional

import asyncpg
import tiktoken
from anthropic import Anthropic
from celery import Celery
from openai import OpenAI

from config import settings

logger = logging.getLogger(__name__)

# --- Celery app setup ---
celery_app = Celery(
    "summarization",
    broker=settings.REDIS_URL,
    backend=settings.REDIS_URL,
)

celery_app.conf.update(
    task_serializer="json",
    result_expires=3600,
    task_acks_late=True,           # ack only after successful completion
    worker_prefetch_multiplier=1,  # process one job at a time per worker
    task_max_retries=3,
)

# --- LLM clients ---
anthropic_client = Anthropic(api_key=settings.ANTHROPIC_API_KEY)
openai_client = OpenAI(api_key=settings.OPENAI_API_KEY)
tokenizer = tiktoken.encoding_for_model("gpt-4o")


SUMMARIZATION_SYSTEM_PROMPT = """You are a conversation summarizer for an AI assistant application.
Your task is to compress a conversation segment into a concise summary that preserves:
- Key facts, decisions, and outcomes
- User's goals and any unresolved questions
- Important context that would affect future responses
- Any commitments or follow-up items

Write in third person. Be specific, not general. Preserve technical details and numbers.
Keep the summary under 200 words unless the conversation contains unusually dense information.
Output only the summary text — no preamble, no labels."""


def count_tokens(text: str) -> int:
    """Count tokens using tiktoken (GPT-compatible approximation)."""
    return len(tokenizer.encode(text))


def format_turns_for_summary(turns: list[dict]) -> str:
    """Format message rows into a readable transcript for the LLM."""
    lines = []
    for turn in turns:
        role_label = {
            "user": "User",
            "assistant": "Assistant",
            "tool": "Tool Result",
            "system": "System",
        }.get(turn["role"], turn["role"].title())
        lines.append(f"{role_label}: {turn['content']}")
    return "\n\n".join(lines)


async def fetch_job_and_turns(
    conn: asyncpg.Connection, job_id: int
) -> Optional[dict]:
    """Load the job and the message turns it covers."""
    job = await conn.fetchrow(
        """
        SELECT j.id, j.conversation_id, j.turns_to_summarize, j.trigger_reason,
               cs.content AS existing_summary,
               cs.turn_range_end AS existing_summary_end
        FROM summarization_jobs j
        LEFT JOIN conversation_summaries cs
            ON cs.conversation_id = j.conversation_id
            AND cs.is_current = TRUE
        WHERE j.id = $1 AND j.status = 'pending'
        FOR UPDATE OF j SKIP LOCKED
        """,
        job_id,
    )

    if not job:
        return None

    turns = await conn.fetch(
        """
        SELECT turn_number, role, content, content_tokens, created_at
        FROM messages
        WHERE conversation_id = $1
          AND turn_number = ANY($2::int[])
        ORDER BY turn_number
        """,
        job["conversation_id"],
        job["turns_to_summarize"],
    )

    return {"job": dict(job), "turns": [dict(t) for t in turns]}


def build_summarization_prompt(
    turns: list[dict],
    existing_summary: Optional[str],
) -> list[dict]:
    """Build the messages array for the LLM call."""
    transcript = format_turns_for_summary(turns)

    if existing_summary:
        user_content = (
            f"Here is an existing summary of earlier parts of this conversation:\n\n"
            f"{existing_summary}\n\n"
            f"---\n\n"
            f"Now summarize the following continuation, incorporating the earlier summary "
            f"context where relevant:\n\n"
            f"{transcript}"
        )
    else:
        user_content = (
            f"Summarize the following conversation segment:\n\n{transcript}"
        )

    return [{"role": "user", "content": user_content}]


def call_claude_for_summary(messages: list[dict]) -> tuple[str, int, int]:
    """
    Call Claude to generate the summary.
    Returns (summary_text, input_tokens, output_tokens).
    """
    start = time.time()
    response = anthropic_client.messages.create(
        model="claude-opus-4-5",
        max_tokens=512,
        system=SUMMARIZATION_SYSTEM_PROMPT,
        messages=messages,
    )
    latency_ms = int((time.time() - start) * 1000)
    summary_text = response.content[0].text.strip()
    return summary_text, response.usage.input_tokens, latency_ms


def generate_summary_embedding(text: str) -> list[float]:
    """Embed the summary for semantic retrieval later."""
    response = openai_client.embeddings.create(
        model="text-embedding-3-small",
        input=text,
    )
    return response.data[0].embedding


async def write_summary_result(
    conn: asyncpg.Connection,
    job: dict,
    turns: list[dict],
    summary_text: str,
    latency_ms: int,
) -> None:
    """
    Atomically:
    1. Mark old summaries as not current
    2. Insert the new summary with its embedding
    3. Mark covered messages as summarized
    4. Mark job as completed
    """
    turn_numbers = [t["turn_number"] for t in turns]
    turn_range_start = min(turn_numbers)
    turn_range_end = max(turn_numbers)

    # If there's an existing summary, the new one covers from its start
    if job.get("existing_summary") and job.get("existing_summary_end"):
        # The prior summary already handled earlier turns; the combined summary
        # conceptually covers from turn 1, but we record the new range start
        # as the beginning of what we just compressed (existing summary is baked in)
        effective_start = 1  # summary now covers the whole compressed history
    else:
        effective_start = turn_range_start

    embedding = generate_summary_embedding(summary_text)
    summary_tokens = count_tokens(summary_text)

    async with conn.transaction():
        # Get next version number
        version = await conn.fetchval(
            """
            SELECT COALESCE(MAX(summary_version), 0) + 1
            FROM conversation_summaries
            WHERE conversation_id = $1
            """,
            job["conversation_id"],
        )

        # Retire old summaries
        await conn.execute(
            """
            UPDATE conversation_summaries
            SET is_current = FALSE
            WHERE conversation_id = $1 AND is_current = TRUE
            """,
            job["conversation_id"],
        )

        # Insert new summary
        await conn.execute(
            """
            INSERT INTO conversation_summaries (
                conversation_id, summary_version, turn_range_start, turn_range_end,
                content, content_tokens, model_used, generation_latency_ms,
                is_current, embedding
            ) VALUES ($1, $2, $3, $4, $5, $6, $7, $8, TRUE, $9::vector)
            """,
            job["conversation_id"],
            version,
            effective_start,
            turn_range_end,
            summary_text,
            summary_tokens,
            "claude-opus-4-5",
            latency_ms,
            embedding,
        )

        # Mark messages as summarized
        await conn.execute(
            """
            UPDATE messages
            SET summarized = TRUE
            WHERE conversation_id = $1
              AND turn_number = ANY($2::int[])
            """,
            job["conversation_id"],
            turn_numbers,
        )

        # Complete the job
        await conn.execute(
            """
            UPDATE summarization_jobs
            SET status = 'completed', completed_at = now()
            WHERE id = $1
            """,
            job["id"],
        )

    logger.info(
        "Summarization complete",
        extra={
            "conversation_id": str(job["conversation_id"]),
            "turns_compressed": len(turn_numbers),
            "summary_tokens": summary_tokens,
            "latency_ms": latency_ms,
            "version": version,
        },
    )


@celery_app.task(
    bind=True,
    max_retries=3,
    default_retry_delay=30,
    name="summarization.process_job",
)
def process_summarization_job(self, job_id: int) -> dict:
    """
    Celery task: fetch a summarization job, call the LLM, write results.
    Idempotent — safe to retry.
    """
    return asyncio.run(_async_process_job(self, job_id))


async def _async_process_job(task, job_id: int) -> dict:
    conn = await asyncpg.connect(settings.DATABASE_URL)
    try:
        # Mark job as running
        updated = await conn.execute(
            """
            UPDATE summarization_jobs
            SET status = 'running', started_at = now(), attempt_count = attempt_count + 1
            WHERE id = $1 AND status = 'pending'
            """,
            job_id,
        )

        if updated == "UPDATE 0":
            logger.info(f"Job {job_id} already picked up by another worker, skipping")
            return {"skipped": True}

        data = await fetch_job_and_turns(conn, job_id)
        if not data:
            logger.warning(f"Job {job_id} not found or not pending")
            return {"skipped": True}

        job, turns = data["job"], data["turns"]

        if not turns:
            logger.warning(f"Job {job_id} has no turns to summarize")
            await conn.execute(
                "UPDATE summarization_jobs SET status = 'completed', completed_at = now() WHERE id = $1",
                job_id,
            )
            return {"skipped": True, "reason": "no_turns"}

        messages = build_summarization_prompt(turns, job.get("existing_summary"))
        summary_text, _input_tokens, latency_ms = call_claude_for_summary(messages)

        await write_summary_result(conn, job, turns, summary_text, latency_ms)

        return {
            "job_id": job_id,
            "conversation_id": str(job["conversation_id"]),
            "turns_compressed": len(turns),
            "latency_ms": latency_ms,
        }

    except Exception as exc:
        # Mark job as failed with error details
        await conn.execute(
            """
            UPDATE summarization_jobs
            SET status = 'failed', last_error = $2
            WHERE id = $1
            """,
            job_id,
            str(exc),
        )
        logger.exception(f"Summarization job {job_id} failed: {exc}")
        raise task.retry(exc=exc)

    finally:
        await conn.close()


# --- pg_notify listener: bridges database events to Celery tasks ---

async def listen_for_summarization_events():
    """
    Long-running coroutine that listens on the PostgreSQL
    'summarization_needed' channel and dispatches Celery tasks.
    """
    conn = await asyncpg.connect(settings.DATABASE_URL)

    async def handle_notification(connection, pid, channel, payload):
        try:
            data = json.loads(payload)
            conversation_id = data["conversation_id"]

            # Find the pending job for this conversation
            job_id = await connection.fetchval(
                """
                SELECT id FROM summarization_jobs
                WHERE conversation_id = $1 AND status = 'pending'
                ORDER BY created_at DESC
                LIMIT 1
                """,
                conversation_id,
            )

            if job_id:
                process_summarization_job.delay(job_id)
                logger.info(
                    f"Dispatched summarization job {job_id} for conversation {conversation_id}"
                )
        except Exception as e:
            logger.exception(f"Error handling notification: {e}")

    await conn.add_listener("summarization_needed", handle_notification)
    logger.info("Listening for summarization_needed notifications...")

    try:
        while True:
            await asyncio.sleep(60)   # keep the event loop alive
    finally:
        await conn.remove_listener("summarization_needed", handle_notification)
        await conn.close()


if __name__ == "__main__":
    asyncio.run(listen_for_summarization_events())

The listener process is typically run as a separate long-lived service alongside your Celery workers. The Celery workers do the actual LLM work; the listener just bridges pg_notify events to the task queue. This is a deliberate split: the listener is stateless and restartable, while Celery handles retry logic and concurrency.

11.4 Assembling Context at Query Time

When a user sends a new message, your application needs to assemble the right context before calling the LLM. The context assembly function pulls the three tiers together: the rolling summary, verbatim recent turns, and optionally a set of semantically retrieved turns from further back.

# context_assembler.py
# Assembles the three-tier context for a conversation at query time

from dataclasses import dataclass
from typing import Optional
import asyncpg
from openai import OpenAI

openai_client = OpenAI(api_key=settings.OPENAI_API_KEY)


@dataclass
class ConversationContext:
    conversation_id: str
    summary: Optional[str]
    summary_covers_turns: Optional[tuple[int, int]]
    recent_turns: list[dict]
    semantic_recall_turns: list[dict]
    total_estimated_tokens: int

    def to_prompt_messages(self) -> list[dict]:
        """
        Convert the assembled context into an ordered list of prompt messages.
        The order is: system context preamble, summary (if any),
        semantically recalled turns (if any), then recent verbatim turns.
        """
        messages = []

        # Tier 2: rolling summary as a system message
        if self.summary:
            messages.append({
                "role": "system",
                "content": (
                    f"The following is a summary of earlier parts of this conversation:\n\n"
                    f"{self.summary}"
                ),
            })

        # Tier 3: semantically retrieved older turns
        if self.semantic_recall_turns:
            recalled_text = "\n\n".join(
                f"{t['role'].title()}: {t['content']}"
                for t in self.semantic_recall_turns
            )
            messages.append({
                "role": "system",
                "content": (
                    f"The following older turns are relevant to the current question:\n\n"
                    f"{recalled_text}"
                ),
            })

        # Tier 1: verbatim recent turns
        for turn in self.recent_turns:
            messages.append({
                "role": turn["role"],
                "content": turn["content"],
            })

        return messages


async def assemble_context(
    conn: asyncpg.Connection,
    conversation_id: str,
    current_user_message: str,
    verbatim_turns: int = 6,
    semantic_recall_count: int = 3,
    max_total_tokens: int = 8000,
) -> ConversationContext:
    """
    Assemble the three-tier context for a conversation.

    Args:
        conn: asyncpg connection
        conversation_id: the conversation to load
        current_user_message: the new message (used to drive semantic recall)
        verbatim_turns: how many recent turns to include verbatim
        semantic_recall_count: how many semantically relevant older turns to retrieve
        max_total_tokens: soft budget; reduces verbatim count if exceeded
    """

    # --- Tier 2: get current rolling summary ---
    summary_row = await conn.fetchrow(
        """
        SELECT content, turn_range_start, turn_range_end
        FROM conversation_summaries
        WHERE conversation_id = $1 AND is_current = TRUE
        """,
        conversation_id,
    )

    summary_text = summary_row["content"] if summary_row else None
    summary_range = (
        (summary_row["turn_range_start"], summary_row["turn_range_end"])
        if summary_row else None
    )

    # --- Tier 1: verbatim recent turns ---
    recent_rows = await conn.fetch(
        """
        SELECT turn_number, role, content, content_tokens, created_at
        FROM messages
        WHERE conversation_id = $1
          AND summarized = FALSE
        ORDER BY turn_number DESC
        LIMIT $2
        """,
        conversation_id,
        verbatim_turns,
    )
    # Reverse so they're in chronological order
    recent_turns = list(reversed([dict(r) for r in recent_rows]))

    # --- Tier 3: semantic recall for older, summarized turns ---
    semantic_turns = []
    if semantic_recall_count > 0:
        # Only bother with semantic recall if there are summarized turns
        has_summarized = await conn.fetchval(
            "SELECT EXISTS(SELECT 1 FROM messages WHERE conversation_id = $1 AND summarized = TRUE)",
            conversation_id,
        )

        if has_summarized:
            # Embed the current user message
            embedding_response = openai_client.embeddings.create(
                model="text-embedding-3-small",
                input=current_user_message,
            )
            query_embedding = embedding_response.data[0].embedding

            # Find the most semantically relevant summarized turns
            semantic_rows = await conn.fetch(
                """
                SELECT m.turn_number, m.role, m.content, m.created_at,
                       1 - (me.embedding <=> $1::vector) AS similarity
                FROM message_embeddings me
                JOIN messages m ON m.id = me.message_id
                WHERE m.conversation_id = $2
                  AND m.summarized = TRUE
                  AND m.role IN ('user', 'assistant')
                ORDER BY me.embedding <=> $1::vector
                LIMIT $3
                """,
                query_embedding,
                conversation_id,
                semantic_recall_count,
            )

            # Only include turns that are above a similarity threshold
            semantic_turns = [
                dict(r) for r in semantic_rows
                if r["similarity"] > 0.75
            ]

    # --- Token budget enforcement ---
    # Estimate total tokens and trim if needed
    summary_tokens = len(summary_text.split()) * 1.3 if summary_text else 0
    recent_tokens = sum(
        t.get("content_tokens") or len(t["content"]) // 4
        for t in recent_turns
    )
    semantic_tokens = sum(
        len(t["content"]) // 4 for t in semantic_turns
    )
    total_estimated = int(summary_tokens + recent_tokens + semantic_tokens)

    # If we're over budget, trim semantic recall first, then reduce verbatim turns
    if total_estimated > max_total_tokens and semantic_turns:
        semantic_turns = []
        total_estimated = int(summary_tokens + recent_tokens)

    if total_estimated > max_total_tokens and len(recent_turns) > 4:
        # Keep at least 4 verbatim turns no matter what
        while total_estimated > max_total_tokens and len(recent_turns) > 4:
            dropped = recent_turns.pop(0)  # drop oldest verbatim turn
            total_estimated -= dropped.get("content_tokens") or len(dropped["content"]) // 4

    return ConversationContext(
        conversation_id=conversation_id,
        summary=summary_text,
        summary_covers_turns=summary_range,
        recent_turns=recent_turns,
        semantic_recall_turns=semantic_turns,
        total_estimated_tokens=total_estimated,
    )

The token budget enforcement at the end is a graceful degradation strategy. Semantic recall is dropped first because it's the least critical tier — the summary and verbatim turns carry the essential context. Verbatim turns are trimmed only as a last resort, and never below four turns, which preserves the immediate conversational flow.

11.5 Per-Message Embedding Pipeline

Semantic recall only works if message embeddings exist. These are generated asynchronously — you don't want to call an embedding API on every INSERT — using a second, lightweight worker that processes the message_embeddings backfill queue.

-- Track which messages need embeddings (populated by trigger)
CREATE TABLE embedding_queue (
    message_id      BIGINT PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
    conversation_id UUID NOT NULL,
    queued_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    attempt_count   INT NOT NULL DEFAULT 0,
    last_error      TEXT
);

CREATE INDEX idx_embedding_queue_queued
    ON embedding_queue (queued_at)
    WHERE attempt_count < 3;

-- Trigger to enqueue messages for embedding when inserted
CREATE OR REPLACE FUNCTION enqueue_message_for_embedding()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    -- Only embed user and assistant turns; tool and system messages are less useful for recall
    IF NEW.role IN ('user', 'assistant') THEN
        INSERT INTO embedding_queue (message_id, conversation_id)
        VALUES (NEW.id, NEW.conversation_id)
        ON CONFLICT (message_id) DO NOTHING;
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_enqueue_embedding
    AFTER INSERT ON messages
    FOR EACH ROW
    EXECUTE FUNCTION enqueue_message_for_embedding();
# embedding_worker.py
# Batch-processes the embedding queue with rate-limit awareness

import asyncio
import logging
import time
from typing import Optional

import asyncpg
from openai import OpenAI, RateLimitError

from config import settings

logger = logging.getLogger(__name__)
openai_client = OpenAI(api_key=settings.OPENAI_API_KEY)

BATCH_SIZE = 50          # embed up to 50 messages per batch call
POLL_INTERVAL_SECS = 5   # check queue every 5 seconds when idle
MAX_RETRIES = 3


async def process_embedding_batch(conn: asyncpg.Connection) -> int:
    """
    Pull a batch of messages from the queue and embed them.
    Returns the number of messages processed.
    """
    rows = await conn.fetch(
        """
        SELECT eq.message_id, eq.conversation_id, m.content, m.role
        FROM embedding_queue eq
        JOIN messages m ON m.id = eq.message_id
        WHERE eq.attempt_count < $1
        ORDER BY eq.queued_at
        LIMIT $2
        FOR UPDATE OF eq SKIP LOCKED
        """,
        MAX_RETRIES,
        BATCH_SIZE,
    )

    if not rows:
        return 0

    message_ids = [r["message_id"] for r in rows]
    texts = [r["content"] for r in rows]

    try:
        response = openai_client.embeddings.create(
            model="text-embedding-3-small",
            input=texts,
        )
    except RateLimitError:
        logger.warning("Embedding rate limit hit, backing off 30 seconds")
        await asyncio.sleep(30)
        return 0
    except Exception as e:
        # Increment attempt count on all rows in this batch
        await conn.execute(
            """
            UPDATE embedding_queue
            SET attempt_count = attempt_count + 1, last_error = $2
            WHERE message_id = ANY($1::bigint[])
            """,
            message_ids,
            str(e),
        )
        logger.exception(f"Embedding batch failed: {e}")
        return 0

    embeddings = [item.embedding for item in response.data]

    async with conn.transaction():
        # Bulk insert embeddings
        await conn.executemany(
            """
            INSERT INTO message_embeddings (message_id, embedding, model_used)
            VALUES ($1, $2::vector, 'text-embedding-3-small')
            ON CONFLICT (message_id) DO UPDATE
                SET embedding = EXCLUDED.embedding,
                    model_used = EXCLUDED.model_used
            """,
            [(message_ids[i], embeddings[i]) for i in range(len(message_ids))],
        )

        # Remove processed messages from the queue
        await conn.execute(
            "DELETE FROM embedding_queue WHERE message_id = ANY($1::bigint[])",
            message_ids,
        )

    logger.info(f"Embedded {len(message_ids)} messages")
    return len(message_ids)


async def run_embedding_worker():
    """Main loop for the embedding worker."""
    conn = await asyncpg.connect(settings.DATABASE_URL)
    logger.info("Embedding worker started")

    try:
        while True:
            processed = await process_embedding_batch(conn)
            if processed == 0:
                await asyncio.sleep(POLL_INTERVAL_SECS)
    except asyncio.CancelledError:
        logger.info("Embedding worker shutting down")
    finally:
        await conn.close()


if __name__ == "__main__":
    asyncio.run(run_embedding_worker())

Batching the embedding calls is important both for throughput and cost. The OpenAI embedding API bills per token, not per call, so batching 50 messages into one request has the same cost as 50 individual calls but far lower latency and fewer round-trips. The SKIP LOCKED clause ensures multiple embedding workers can run in parallel without double-processing.

11.6 Rolling Summary Quality and Prompt Engineering

The quality of your summaries determines how much context fidelity you retain after compression. Poor summaries lose critical details; good summaries are almost lossless for the facts that matter. Several prompt engineering patterns improve summary quality significantly.

Incremental summarization beats batch summarization. Rather than summarizing 20 turns at once, summarize each 10-turn window incrementally, passing the prior summary as context. The model is better at extending a coherent narrative than at compressing a large transcript from scratch.

Chain-of-thought extraction improves recall. Ask the model to first list the key facts, decisions, and questions before writing the summary. The intermediate extraction step reduces the chance of dropping important details.

# Improved summarization prompt with chain-of-thought extraction
EXTRACTION_SYSTEM_PROMPT = """You are a conversation analyst preparing a summary for an AI assistant.

Step 1 - Extract: List the key elements from this conversation segment:
  • Facts established (names, numbers, decisions, outcomes)
  • User's goals and current status (resolved/unresolved)
  • Technical details that would affect future responses
  • Any commitments, deadlines, or follow-up items

Step 2 - Compress: Write a 100-200 word narrative summary that incorporates all extracted elements.

Format your response as:
KEY_ELEMENTS:
[bulleted list]

SUMMARY:
[narrative paragraph]"""


def call_claude_with_extraction(
    messages: list[dict],
    existing_summary: Optional[str] = None,
) -> tuple[str, str]:
    """
    Returns (extracted_elements, summary_text).
    Extracts the structured key elements alongside the narrative summary.
    """
    response = anthropic_client.messages.create(
        model="claude-opus-4-5",
        max_tokens=768,
        system=EXTRACTION_SYSTEM_PROMPT,
        messages=messages,
    )
    raw = response.content[0].text.strip()

    # Parse the structured response
    if "SUMMARY:" in raw:
        parts = raw.split("SUMMARY:", 1)
        elements = parts[0].replace("KEY_ELEMENTS:", "").strip()
        summary = parts[1].strip()
    else:
        # Fallback: treat the whole response as the summary
        elements = ""
        summary = raw

    return elements, summary

Domain-specific prompt variants improve precision for known use cases. A customer support bot should emphasize ticket IDs, error codes, and resolution steps. A coding assistant should preserve function signatures and file paths. A financial advisor bot should preserve amounts, dates, and instrument names. Store the prompt variant in the conversation's metadata field and select it at summarization time.

DOMAIN_SUMMARY_PROMPTS = {
    "customer_support": """
Summarize this customer support conversation. Preserve:
- Ticket or case IDs
- Error messages and codes
- Steps already attempted
- Resolution status (resolved/pending/escalated)
- Any promised callbacks or follow-up dates
""",
    "coding_assistant": """
Summarize this coding session. Preserve:
- Files and functions modified
- Bugs found and their root causes
- Solutions implemented (with key code details)
- Outstanding issues or TODOs
- Technology stack and version constraints
""",
    "general": SUMMARIZATION_SYSTEM_PROMPT,
}


def get_domain_prompt(metadata: dict) -> str:
    domain = metadata.get("domain", "general")
    return DOMAIN_SUMMARY_PROMPTS.get(domain, DOMAIN_SUMMARY_PROMPTS["general"])

11.7 Summary Versioning and Rollback

Summaries are lossy by nature. If a bug in your prompt causes a bad batch of summaries, you need to be able to roll back without losing the source messages — which is why the raw messages table is the permanent record and the conversation_summaries table is a derived view. The is_current flag and summary_version column give you a full audit trail and a one-query rollback.

-- View the full summary version history for a conversation
SELECT
    id,
    summary_version,
    turn_range_start,
    turn_range_end,
    is_current,
    content_tokens,
    model_used,
    generation_latency_ms,
    created_at,
    left(content, 120) AS preview
FROM conversation_summaries
WHERE conversation_id = 'your-conversation-id-here'
ORDER BY summary_version DESC;

-- Roll back to the previous summary version
WITH ranked AS (
    SELECT id, summary_version,
           ROW_NUMBER() OVER (ORDER BY summary_version DESC) AS rn
    FROM conversation_summaries
    WHERE conversation_id = 'your-conversation-id-here'
)
UPDATE conversation_summaries cs
SET is_current = (r.rn = 2)   -- version 2 becomes current, version 1 gets retired
FROM ranked r
WHERE cs.id = r.id;

-- Find conversations whose summaries were generated by a specific model version
-- (useful for targeted re-summarization after a prompt change)
SELECT DISTINCT conversation_id, model_used, COUNT(*) AS summary_count
FROM conversation_summaries
WHERE is_current = TRUE
  AND model_used = 'claude-opus-4-5'
  AND created_at < '2025-01-01'
GROUP BY conversation_id, model_used
ORDER BY summary_count DESC;

-- Re-queue summarization for all conversations that had summaries
-- generated before a known bad prompt deployment
INSERT INTO summarization_jobs (conversation_id, trigger_reason, turns_to_summarize)
SELECT
    cs.conversation_id,
    'manual',
    ARRAY(
        SELECT turn_number FROM messages m
        WHERE m.conversation_id = cs.conversation_id
          AND m.turn_number BETWEEN cs.turn_range_start AND cs.turn_range_end
        ORDER BY turn_number
    )
FROM conversation_summaries cs
WHERE cs.is_current = TRUE
  AND cs.created_at BETWEEN '2025-01-15' AND '2025-01-17'  -- bad deployment window
ON CONFLICT DO NOTHING;

The ability to re-summarize from source messages is one of the strongest arguments for keeping raw turns in the database rather than discarding them after compression. Storage is cheap; conversations are not reproducible.

11.8 Monitoring and Observability

A summarization pipeline has three things that can go wrong silently: jobs can pile up faster than workers process them, summaries can degrade in quality without raising errors, and the token savings can be less than expected if conversations are short. Instrument all three.

-- Operational dashboard: pipeline health at a glance
CREATE OR REPLACE VIEW summarization_pipeline_health AS
WITH job_stats AS (
    SELECT
        status,
        COUNT(*) AS cnt,
        AVG(EXTRACT(EPOCH FROM (COALESCE(completed_at, now()) - created_at))) AS avg_age_secs,
        MAX(EXTRACT(EPOCH FROM (COALESCE(completed_at, now()) - created_at))) AS max_age_secs
    FROM summarization_jobs
    WHERE created_at > now() - INTERVAL '24 hours'
    GROUP BY status
),
embedding_lag AS (
    SELECT
        COUNT(*) AS pending_embeddings,
        MIN(queued_at) AS oldest_queued
    FROM embedding_queue
    WHERE attempt_count < 3
),
summary_quality AS (
    SELECT
        AVG(content_tokens) AS avg_summary_tokens,
        PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY generation_latency_ms) AS p95_latency_ms,
        COUNT(*) FILTER (WHERE generation_latency_ms > 10000) AS slow_summaries
    FROM conversation_summaries
    WHERE created_at > now() - INTERVAL '24 hours'
)
SELECT
    js.status,
    js.cnt AS job_count,
    ROUND(js.avg_age_secs::numeric, 1) AS avg_age_seconds,
    ROUND(js.max_age_secs::numeric, 1) AS max_age_seconds,
    el.pending_embeddings,
    el.oldest_queued,
    sq.avg_summary_tokens,
    sq.p95_latency_ms,
    sq.slow_summaries
FROM job_stats js
CROSS JOIN embedding_lag el
CROSS JOIN summary_quality sq;

-- Token compression ratio: how much are we actually saving?
CREATE OR REPLACE VIEW compression_efficiency AS
SELECT
    DATE_TRUNC('day', cs.created_at) AS day,
    COUNT(*) AS summaries_created,
    AVG(cs.content_tokens) AS avg_summary_tokens,
    AVG(
        (SELECT SUM(COALESCE(m.content_tokens, estimate_message_tokens(m.content)))
         FROM messages m
         WHERE m.conversation_id = cs.conversation_id
           AND m.turn_number BETWEEN cs.turn_range_start AND cs.turn_range_end)
    ) AS avg_raw_tokens_compressed,
    AVG(
        cs.content_tokens::float /
        NULLIF(
            (SELECT SUM(COALESCE(m.content_tokens, estimate_message_tokens(m.content)))
             FROM messages m
             WHERE m.conversation_id = cs.conversation_id
               AND m.turn_number BETWEEN cs.turn_range_start AND cs.turn_range_end),
            0
        )
    ) AS avg_compression_ratio   -- lower is better; 0.1 means 90% token reduction
FROM conversation_summaries cs
WHERE cs.created_at > now() - INTERVAL '7 days'
GROUP BY DATE_TRUNC('day', cs.created_at)
ORDER BY day DESC;

-- Alert query: jobs stuck in running state (worker crash scenario)
SELECT
    id,
    conversation_id,
    started_at,
    EXTRACT(EPOCH FROM (now() - started_at)) / 60 AS minutes_running,
    attempt_count
FROM summarization_jobs
WHERE status = 'running'
  AND started_at < now() - INTERVAL '10 minutes'
ORDER BY started_at;

-- Recovery: reset stuck jobs for re-processing
UPDATE summarization_jobs
SET status = 'pending', started_at = NULL
WHERE status = 'running'
  AND started_at < now() - INTERVAL '10 minutes';

The compression ratio metric is particularly useful for tuning your thresholds. If conversations are compressing to less than 10% of their original token count, your summaries are probably too aggressive and losing fidelity. A compression ratio between 15% and 30% typically indicates a good balance between compression and retention.

For alerting, configure three thresholds in your monitoring system:

  • → **Queue depth > 100 pending jobs**: workers are falling behind; scale horizontally.
  • → **Max age of pending job > 5 minutes**: worker may be down; check Celery health.
  • → **Compression ratio < 0.10**: summaries may be too short; review prompt and model outputs manually.

-- SQL Server triggers fire per-statement, not per-row;
-- use a CURSOR or set-based approach for multi-row inserts

CREATE OR ALTER TRIGGER trg_maybe_schedule_summarization
ON messages
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @v_turn_threshold INT = 15;
    DECLARE @v_token_threshold INT = 6000;
    DECLARE @v_keep_verbatim INT = 6;

    -- Process each affected conversation from the inserted set
    INSERT INTO summarization_jobs (conversation_id, trigger_reason, turns_to_summarize)
    SELECT
        i.conversation_id,
        CASE
            WHEN SUM(COALESCE(m.content_tokens, LEN(m.content) / 4)) >= @v_token_threshold
                THEN 'token_budget'
            ELSE 'turn_count'
        END,
        -- Build JSON array of turn numbers to summarize
        (
            SELECT STRING_AGG(CAST(m2.turn_number AS NVARCHAR), ',')
            FROM messages m2
            WHERE m2.conversation_id = i.conversation_id
              AND m2.summarized = 0
              AND m2.turn_number < (
                  SELECT turn_number
                  FROM (
                      SELECT turn_number,
                             ROW_NUMBER() OVER (ORDER BY turn_number DESC) AS rn
                      FROM messages
                      WHERE conversation_id = i.conversation_id
                  ) ranked
                  WHERE rn = @v_keep_verbatim
              )
        )
    FROM inserted i
    JOIN messages m ON m.conversation_id = i.conversation_id
                    AND m.summarized = 0
                    AND m.role IN ('user', 'assistant')
    WHERE i.role IN ('user', 'assistant')
      -- No pending job already exists
      AND NOT EXISTS (
          SELECT 1 FROM summarization_jobs sj
          WHERE sj.conversation_id = i.conversation_id
            AND sj.status IN ('pending', 'running')
      )
    GROUP BY i.conversation_id
    HAVING
        COUNT(*) >= @v_turn_threshold
        OR SUM(COALESCE(m.content_tokens, LEN(m.content) / 4)) >= @v_token_threshold;
END;
GO
    -- SQL Server: polling query for the worker (replaces pg_notify)
-- Workers poll this view on a configurable interval (typically 5-10 seconds)

CREATE OR ALTER PROCEDURE dbo.ClaimSummarizationJob
    @worker_id NVARCHAR(100)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @job_id BIGINT;

    -- Claim one pending job atomically using UPDLOCK + READPAST
    -- to avoid blocking between competing workers
    WITH next_job AS (
        SELECT TOP 1 id
        FROM summarization_jobs WITH (UPDLOCK, READPAST)
        WHERE status = 'pending'
          AND scheduled_at <= SYSDATETIMEOFFSET()
        ORDER BY scheduled_at
    )
    UPDATE summarization_jobs
    SET status = 'running',
        started_at = SYSDATETIMEOFFSET(),
        attempt_count = attempt_count + 1
    OUTPUT INSERTED.id INTO @job_id
    FROM summarization_jobs sj
    JOIN next_job nj ON sj.id = nj.id;

    -- Return the claimed job with its turns
    IF @job_id IS NOT NULL
    BEGIN
        SELECT
            sj.id,
            sj.conversation_id,
            sj.turns_to_summarize,
            sj.trigger_reason,
            cs.content AS existing_summary,
            cs.turn_range_end AS existing_summary_end
        FROM summarization_jobs sj
        LEFT JOIN conversation_summaries cs
            ON cs.conversation_id = sj.conversation_id
            AND cs.is_current = 1
        WHERE sj.id = @job_id;
    END
END;
GO

-- SQL Server: reset stuck running jobs (run periodically via SQL Agent)
UPDATE summarization_jobs
SET status = 'pending', started_at = NULL
WHERE status = 'running'
  AND started_at < DATEADD(MINUTE, -10, SYSDATETIMEOFFSET());
GO

    The SQL Server polling approach using UPDLOCK and READPAST is the standard pattern for queue-style workloads in SQL Server — it avoids lock contention between workers without needing a dedicated queue technology. You'd typically call ClaimSummarizationJob from a Python worker on a tight polling loop, sleeping when no job is returned.

    For vector storage in SQL Server, the options depend on your version and extensions. SQL Server 2025 introduces native vector support; for earlier versions, teams commonly store embeddings as JSON arrays in NVARCHAR(MAX) and perform similarity search in the application layer, or offload vector retrieval to Azure Cognitive Search while keeping the conversation data in SQL Server.

    11.10 End-to-End Integration: Putting It Together

    The pieces described in this chapter fit together as a pipeline with clearly defined responsibilities:

    User sends message
      │
      ▼
Application layer
  ├── Insert message into messages table
  │     ├── Trigger: update conversation stats
  │     ├── Trigger: enqueue message for embedding
  │     └── Trigger: maybe schedule summarization
  │
  ├── Assemble context (assemble_context())
  │     ├── Fetch current rolling summary (Tier 2)
  │     ├── Fetch recent verbatim turns (Tier 1)
  │     └── Semantic recall via pgvector (Tier 3)
  │
  └── Call LLM with assembled context
        └── Insert assistant response into messages table

Background workers (async)
  ├── Embedding worker: processes embedding_queue in batches
  └── Summarization worker: listens on pg_notify,
        calls Claude, writes new summary version
    # main_chat_handler.py
# Simplified end-to-end handler showing how the pieces connect

import asyncpg
from openai import OpenAI
from context_assembler import assemble_context

openai_client = OpenAI(api_key=settings.OPENAI_API_KEY)


async def handle_user_message(
    pool: asyncpg.Pool,
    conversation_id: str,
    user_content: str,
) -> str:
    """
    Core chat handler:
    1. Persist the user message
    2. Assemble context
    3. Call the LLM
    4. Persist the assistant response
    5. Return the response text
    """
    async with pool.acquire() as conn:
        async with conn.transaction():
            # Get the next turn number
            next_turn = await conn.fetchval(
                """
                SELECT COALESCE(MAX(turn_number), 0) + 1
                FROM messages WHERE conversation_id = $1
                """,
                conversation_id,
            )

            # Persist user message
            await conn.execute(
                """
                INSERT INTO messages (conversation_id, turn_number, role, content)
                VALUES ($1, $2, 'user', $3)
                """,
                conversation_id,
                next_turn,
                user_content,
            )

        # Assemble context (outside the transaction — reads are fine here)
        ctx = await assemble_context(
            conn=conn,
            conversation_id=conversation_id,
            current_user_message=user_content,
            verbatim_turns=6,
            semantic_recall_count=3,
        )

    # Build the prompt messages
    prompt_messages = ctx.to_prompt_messages()
    # The last message in recent_turns is the user message we just inserted;
    # it's already included via assemble_context, so no need to append again

    # Call the LLM
    response = openai_client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": "You are a helpful assistant."},
            *prompt_messages,
        ],
        temperature=0.7,
        max_tokens=1024,
    )

    assistant_content = response.choices[0].message.content
    completion_tokens = response.usage.completion_tokens

    # Persist assistant response
    async with pool.acquire() as conn:
        async with conn.transaction():
            next_turn_assistant = await conn.fetchval(
                """
                SELECT COALESCE(MAX(turn_number), 0) + 1
                FROM messages WHERE conversation_id = $1
                """,
                conversation_id,
            )

            await conn.execute(
                """
                INSERT INTO messages (
                    conversation_id, turn_number, role, content,
                    content_tokens, model_used
                ) VALUES ($1, $2, 'assistant', $3, $4, 'gpt-4o')
                """,
                conversation_id,
                next_turn_assistant,
                assistant_content,
                completion_tokens,
            )

    return assistant_content

    A few design notes on this integration:

    Two separate connections/transactions for insert and LLM call. The user message is committed before the LLM call starts, so even if the LLM request times out or fails, the user's message is durably stored. This also means the embedding trigger fires immediately, and embeddings start being generated while the LLM is thinking.

    Context assembly reads from committed data. The assemble_context call happens after the user message is committed, so it will include the message just inserted if it falls within the verbatim window. This is correct behavior — the user message is part of the context the LLM should see.

    Turn numbers are assigned inside transactions. Both user and assistant messages use MAX(turn_number) + 1 inside a transaction to avoid gaps or collisions under concurrent requests. For very high-throughput systems, a SEQUENCE per conversation or a serial column is more scalable; for most chatbot workloads, the transactional MAX approach is sufficient.

    11.11 Tuning Thresholds for Your Workload

    The thresholds in this chapter — 15 turns, 6,000 tokens, 6 verbatim turns — are starting points, not universal constants. The right values depend on your conversation characteristics and cost tolerance.

    Turn count threshold (15): Use a lower threshold for high-value, dense conversations (customer support, legal, medical) where every detail matters. Use a higher threshold for casual or exploratory conversations where context matters less. Monitor the compression ratio view; if you're consistently seeing high compression ratios, your threshold is probably too high (you're accumulating too much before compressing).

    Token threshold (6,000): This should be set to roughly 30–40% of your target context window size. If you're targeting an 8k-token context window for your LLM call, a 3,200-token trigger makes sense. If you're on a model with a 128k context window and cost isn't a concern, you might never need to summarize at all.

    Verbatim turn count (6): This is the number of recent turns the model always sees in full. Six turns gives you three user/assistant exchanges, which is usually enough for the model to understand the immediate conversational thread. Increase this if your users tend to reference things they said 7–10 turns ago within a single session.

    -- Per-conversation threshold overrides stored in conversation metadata
-- Allows different settings for different customer tiers or channels

-- Example: premium customers get more verbatim turns
UPDATE conversations
SET metadata = metadata || '{"summarization": {"verbatim_turns": 12, "turn_threshold": 25}}'::jsonb
WHERE user_id IN (SELECT user_id FROM premium_users);

-- Query: what are the effective thresholds for a given conversation?
SELECT
    id,
    COALESCE((metadata->'summarization'->>'verbatim_turns')::int, 6) AS verbatim_turns,
    COALESCE((metadata->'summarization'->>'turn_threshold')::int, 15) AS turn_threshold,
    COALESCE((metadata->'summarization'->>'token_threshold')::int, 6000) AS token_threshold
FROM conversations
WHERE id = 'your-conversation-id-here';

    Update the maybe_schedule_summarization trigger function to read these per-conversation overrides if you implement this pattern. The JSONB extraction cost is negligible compared to the overall trigger overhead.

    Key Takeaways

  • → **Conversation memory is a three-tier architecture**: verbatim recent turns for immediacy, a rolling summary for compressed history, and semantic recall for relevant older context — all assembled at query time from PostgreSQL.
  • → **The database owns the scheduling logic**: triggers evaluate compression thresholds on every INSERT, enqueue jobs idempotently, and fire `pg_notify` to wake workers — keeping application code free of memory-management concerns.
  • → **Raw messages are the permanent record**: summaries are a derived, versioned view that can be rolled back or regenerated from source at any time, making the system resilient to prompt changes or model upgrades.
  • → **Async workers decouple latency from cost**: embedding generation and LLM summarization happen in background processes, so user-facing INSERT and context-assembly paths remain fast regardless of summarization workload.
  • → **Thresholds and prompts are configuration, not code**: token budgets, verbatim turn counts, and domain-specific prompt variants live in the database and metadata, allowing tuning without redeployment.
