Chapter 23: AlloyDB Omni: Running Google's Database On-Premises

AlloyDB Omni brings Google's columnar engine, adaptive query optimization, and PostgreSQL-compatible runtime to hardware you control — your on-premises servers, your colocation cage, or your edge deployment. For DBAs who have spent years tuning PostgreSQL instances but need the performance headroom of AlloyDB without migrating workloads into Google Cloud, Omni represents a genuinely different proposition: a managed-engine experience running in a container on your own infrastructure. This chapter covers deploying AlloyDB Omni from scratch, understanding what the columnar engine actually does under the hood, connecting Omni to Google Cloud services for observability and management, and building production patterns that keep the deployment maintainable over time. If you have worked with AlloyDB in Google Cloud (covered in Chapter 22), Omni will feel familiar in its SQL layer but distinctly different in its operational model.

---

23.1 What AlloyDB Omni Actually Is — and What It Is Not

Before deploying anything, you need a clear mental model of what Omni provides versus what you get from a self-compiled PostgreSQL binary or a full AlloyDB instance in Google Cloud.

The core architecture

AlloyDB Omni ships as a container image (gcr.io/alloydb-omni/alloydb-omni) that wraps a modified PostgreSQL 15 engine. The modifications include three components that differentiate it from vanilla Postgres:

1. The columnar engine — an in-memory columnar store that automatically populates based on query patterns. Google's documentation calls this the "columnar cache." It stores frequently accessed column data in a compressed, vectorized format alongside the standard row-based heap. You do not manage this explicitly; the engine decides what to populate based on workload.

2. The adaptive query optimizer — an overlay on top of the standard PostgreSQL planner that uses statistics and runtime feedback to choose between row and columnar execution paths. Unlike a traditional hint-based approach, this happens automatically per query.

3. The AlloyDB AI extensions — google_ml_integration and pgvector, pre-installed and configured for embedding generation calls that can reach out to Vertex AI endpoints if you configure a service account.

What Omni is not

Omni is not a fully managed service. You own the container runtime, the host OS, the storage subsystem, backup scheduling, and HA failover. Google does not patch it for you. You pull new container images when updates release, test them, and roll them out on your own schedule. This is the fundamental trade-off: you get the engine, not the platform.

Omni also does not replicate the AlloyDB storage layer from Google Cloud. In GCP, AlloyDB uses a distributed, disaggregated storage system that durably replicates across multiple zones within a region — consult current AlloyDB documentation for the exact replica topology. In Omni, you get standard PostgreSQL WAL-based storage on whatever block device you mount into the container. The columnar engine still works, but the durability model is your problem to design.

Comparing Omni to PostgreSQL

| Feature | Vanilla PostgreSQL 15 | AlloyDB Omni |

|---|---|---|

| Row storage | ✓ | ✓ |

| Columnar engine | ✗ | ✓ (automatic) |

| pgvector extension | Manual install | Pre-installed |

| google_ml_integration | ✗ | ✓ |

| GCP Observability integration | Manual | Built-in agent |

| License | PostgreSQL License | Google ToS |

| Patching | Your binary | Pull new container |

| Max column store memory | N/A | Configurable, default 1 GB |

The PostgreSQL ToS difference matters for production legal review. Omni is licensed under Google's terms, not the PostgreSQL License. Run that past your legal team before deploying in regulated environments.

23.2 Deploying AlloyDB Omni on Bare Metal and Virtual Machines

Omni runs on any container runtime that supports Docker or Podman. In practice, most production deployments use either Docker Engine on Linux or Kubernetes with the AlloyDB Omni Operator. This section covers both paths.

Prerequisites

Minimum host specifications for a production deployment:

  • → 8 vCPUs (16 recommended for OLAP workloads using the columnar engine)
  • → 32 GB RAM (the columnar engine uses a configurable slice of this)
  • → Local NVMe or SAN storage with at least 3,000 IOPS sustained
  • → Linux kernel 5.4 or newer (tested on RHEL 8/9, Ubuntu 20.04/22.04)
  • → Docker Engine 20.10+ or Podman 4.0+

    • Standalone container deployment

    # Pull the AlloyDB Omni image
# You need to authenticate with Google Container Registry first
gcloud auth configure-docker gcr.io

docker pull gcr.io/alloydb-omni/alloydb-omni:latest

# Create persistent storage directories on the host
# Use a dedicated mount point backed by your fastest storage
mkdir -p /alloydb/data /alloydb/logs /alloydb/tmp

# Deploy the container with production settings
# POSTGRES_PASSWORD sets the initial superuser password
# ALLOYDB_ENABLE_COLUMNAR_ENGINE enables the in-memory columnar cache
docker run -d \
  --name alloydb-omni \
  --restart unless-stopped \
  -e POSTGRES_PASSWORD='YourSecureP@ssword123' \
  -e ALLOYDB_ENABLE_COLUMNAR_ENGINE=true \
  -e ALLOYDB_COLUMNAR_MEMORY_SIZE_MB=8192 \
  -p 5432:5432 \
  -v /alloydb/data:/var/lib/postgresql/data \
  -v /alloydb/logs:/var/log/postgresql \
  --shm-size=2g \
  --cpus=16 \
  --memory=64g \
  gcr.io/alloydb-omni/alloydb-omni:latest

# Verify the container started cleanly
docker logs alloydb-omni | tail -30

# Connect and confirm AlloyDB extensions are present
docker exec -it alloydb-omni psql -U postgres -c "\dx"

    The --shm-size parameter is easy to forget and causes immediate performance problems. PostgreSQL uses shared memory for the buffer pool and inter-process communication. If you leave it at the Docker default of 64 MB, you will see errors in the PostgreSQL log about shared memory allocation failing when you try to set shared_buffers to a reasonable value.

    Configuring the columnar engine

    Once the container is running, you control the columnar engine through GUC parameters that AlloyDB Omni adds to the standard PostgreSQL parameter namespace:

    -- Connect as postgres superuser and check columnar engine status
SELECT name, setting, unit, short_desc
FROM pg_settings
WHERE name LIKE 'alloydb%'
ORDER BY name;

-- Key parameters to understand:
-- alloydb.enable_columnar_engine          (on/off)
-- alloydb.columnar_memory_size_mb         (default: 1024)
-- alloydb.auto_columnar_scan_threshold    (rows, default: 10000)
-- alloydb.columnar_engine_mode            (auto, manual)

-- Check what the columnar engine has populated
-- This view shows which relations have columnar data
SELECT
    schemaname,
    tablename,
    pg_size_pretty(columnar_size_bytes) AS columnar_size,
    columnar_row_count,
    last_refresh_time
FROM alloydb_columnar_info
ORDER BY columnar_size_bytes DESC;

-- Force a specific table into the columnar cache explicitly
-- Useful during initial load before query patterns establish themselves
ALTER TABLE order_line_items SET (columnar = on);

-- Check actual query execution to see if columnar path was chosen
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    product_id,
    SUM(quantity) AS total_qty,
    SUM(unit_price * quantity) AS revenue
FROM order_line_items
WHERE order_date >= '2024-01-01'
GROUP BY product_id;
-- Look for "Columnar Scan" nodes in the plan output
-- If you see "Seq Scan" instead, the table may not yet be in the columnar cache
-- or the row count is below the threshold

    The auto_columnar_scan_threshold parameter is the one most DBAs misconfigure. If a table has fewer rows than this threshold, the planner will not consider the columnar path even if the table is marked for columnar storage. Set it too high and small-but-wide analytical tables miss out. Set it too low and you waste columnar memory on tables too small to benefit. A starting value of 50,000 rows works well for most mixed OLTP/OLAP environments.

    Kubernetes deployment with the AlloyDB Omni Operator

    For environments running Kubernetes on-premises (OpenShift, Rancher, vanilla kubeadm clusters), Google provides the AlloyDB Omni Operator, which adds CRDs for DBCluster resources:

    23.3 Connecting AlloyDB Omni to Google Cloud Services

    Running Omni on-premises does not mean operating in isolation. Google designed Omni to optionally connect back to Google Cloud for observability, AI feature access, and fleet management through the AlloyDB Omni management API. This section covers those integrations and when to use them.

    graph TD
    App[Application] --> Omni[AlloyDB Omni container
    on-prem / edge]
    Omni -->|metrics + logs| CM[Cloud Monitoring /
    Cloud Logging]
    Omni -->|WAL archive_command| GCS[(Cloud Storage
    WAL + base backups)]
    Omni -->|google_ml_integration| Vertex[Vertex AI
    embedding / model endpoints]
    Omni -.optional.-> LogRep[Logical replication
    to central AlloyDB/Omni]

    *Omni owns its own storage and HA on-premises; the connections back to Google Cloud are opt-in integrations for observability, backup, and ML inference — each crosses the network boundary and should be evaluated against data-residency requirements before enabling.*

    Google Cloud Observability integration

    Omni can ship logs and metrics to Cloud Logging and Cloud Monitoring through the built-in observability agent. This is the fastest way to get production-grade monitoring without building a Prometheus stack from scratch.

    # Create a Google Cloud service account for the Omni observability agent
# Run this from a machine with gcloud access to your GCP project
gcloud iam service-accounts create alloydb-omni-agent \
  --project=your-project-id \
  --description="AlloyDB Omni observability and ML integration agent" \
  --display-name="AlloyDB Omni Agent"

# Grant the minimum required roles
gcloud projects add-iam-policy-binding your-project-id \
  --member="serviceAccount:alloydb-omni-agent@your-project-id.iam.gserviceaccount.com" \
  --role="roles/monitoring.metricWriter"

gcloud projects add-iam-policy-binding your-project-id \
  --member="serviceAccount:alloydb-omni-agent@your-project-id.iam.gserviceaccount.com" \
  --role="roles/logging.logWriter"

gcloud projects add-iam-policy-binding your-project-id \
  --member="serviceAccount:alloydb-omni-agent@your-project-id.iam.gserviceaccount.com" \
  --role="roles/aiplatform.user"

# Create and download a JSON key for the service account
# Store this securely — treat it like a root password
gcloud iam service-accounts keys create /etc/alloydb/gcp-credentials.json \
  --iam-account=alloydb-omni-agent@your-project-id.iam.gserviceaccount.com

chmod 600 /etc/alloydb/gcp-credentials.json
    # Redeploy the container with GCP credentials mounted
# The GOOGLE_APPLICATION_CREDENTIALS env var activates the observability agent
docker stop alloydb-omni && docker rm alloydb-omni

docker run -d \
  --name alloydb-omni \
  --restart unless-stopped \
  -e POSTGRES_PASSWORD='YourSecureP@ssword123' \
  -e ALLOYDB_ENABLE_COLUMNAR_ENGINE=true \
  -e ALLOYDB_COLUMNAR_MEMORY_SIZE_MB=8192 \
  -e GOOGLE_APPLICATION_CREDENTIALS=/etc/alloydb/gcp-credentials.json \
  -e GOOGLE_CLOUD_PROJECT=your-project-id \
  -e ALLOYDB_OBSERVABILITY_ENABLED=true \
  -p 5432:5432 \
  -v /alloydb/data:/var/lib/postgresql/data \
  -v /alloydb/logs:/var/log/postgresql \
  -v /etc/alloydb:/etc/alloydb:ro \
  --shm-size=2g \
  --cpus=16 \
  --memory=64g \
  gcr.io/alloydb-omni/alloydb-omni:latest

# After 2-3 minutes, verify metrics appear in Cloud Monitoring
gcloud monitoring metrics list \
  --filter="metric.type=starts_with(\"alloydb.googleapis.com\")" \
  --project=your-project-id | head -30

    Once connected, you can build Cloud Monitoring dashboards that show AlloyDB Omni metrics — active connections, cache hit ratios, columnar engine memory usage, transaction throughput — alongside metrics from your Cloud SQL and AlloyDB instances in GCP. This unified view is one of the practical reasons to wire Omni back to Google Cloud even when you prefer keeping data on-premises.

    Vertex AI integration for embedding generation

    The google_ml_integration extension in Omni can call Vertex AI to generate text embeddings from inside SQL queries. This is the same capability available in AlloyDB in GCP, now runnable from your on-premises database. The service account you created above needs the roles/aiplatform.user role for this to work.

    -- Enable the ML integration extension
CREATE EXTENSION IF NOT EXISTS google_ml_integration;

-- Configure the Vertex AI endpoint
-- Replace the region and model with your Vertex AI configuration
SELECT google_ml.create_model(
    model_id => 'text-embedding-005',
    model_provider => 'google',
    model_type => 'text_embedding',
    model_endpoint =>
        'https://us-central1-aiplatform.googleapis.com/v1/projects/your-project-id/locations/us-central1/publishers/google/models/text-embedding-005',
    model_qualified_name => 'publishers/google/models/text-embedding-005'
);

-- Test embedding generation
-- This call goes from your on-premises Omni instance to Vertex AI over HTTPS
SELECT google_ml.embedding(
    'text-embedding-005',
    'AlloyDB Omni columnar engine performance benchmark'
)::vector(768);

-- Practical use: generate embeddings for a product catalog
-- and store them for similarity search
ALTER TABLE product_catalog
ADD COLUMN IF NOT EXISTS description_embedding vector(768);

UPDATE product_catalog
SET description_embedding = google_ml.embedding(
    'text-embedding-005',
    product_description
)::vector(768)
WHERE description_embedding IS NULL
  AND product_description IS NOT NULL;

-- Create an IVFFlat index for approximate nearest neighbor search
CREATE INDEX idx_product_embeddings
ON product_catalog
USING ivfflat (description_embedding vector_cosine_ops)
WITH (lists = 100);

    The network path here matters for latency and for compliance. Every embedding call in a SQL query exits your on-premises network and reaches Google's API endpoints. If your data classification policy prohibits row data leaving the facility, passing product descriptions to Vertex AI may trigger a compliance review. Know what data you are embedding before you build this into production query patterns.

    23.4 Backup, HA, and the Operational Gap

    This is where the honest conversation about Omni needs to happen. In AlloyDB in GCP, Google handles backup, point-in-time recovery, HA failover, and storage durability automatically. In Omni, none of that is included. You are running a PostgreSQL-compatible engine in a container, and backup and HA are entirely your design responsibility.

    Backup strategy

    For Omni deployments, you have three practical backup approaches:

    1. pg_basebackup — same as vanilla PostgreSQL, works reliably

    2. WAL archiving to Cloud Storage — gives you PITR with Google Cloud as the archive destination

    3. Volume snapshots — snapshot the underlying block device at the host level

    WAL archiving to Cloud Storage is the approach that best preserves the Google Cloud integration story:

    # Create a Cloud Storage bucket for WAL archiving
gsutil mb -l us-central1 gs://your-company-alloydb-omni-wal

# Set lifecycle policy to expire old WAL segments after 30 days
cat > /tmp/wal-lifecycle.json << 'EOF'
{
  "lifecycle": {
    "rule": [
      {
        "action": {"type": "Delete"},
        "condition": {"age": 30}
      }
    ]
  }
}
EOF

gsutil lifecycle set /tmp/wal-lifecycle.json \
  gs://your-company-alloydb-omni-wal

# Inside the container, configure postgresql.conf for WAL archiving
# AlloyDB Omni respects all standard PostgreSQL archive parameters
docker exec -it alloydb-omni psql -U postgres << 'EOF'
ALTER SYSTEM SET wal_level = 'replica';
ALTER SYSTEM SET archive_mode = 'on';
ALTER SYSTEM SET archive_command =
  'gcloud storage cp %p gs://your-company-alloydb-omni-wal/%f';
ALTER SYSTEM SET archive_timeout = '300';
SELECT pg_reload_conf();
EOF

# Restart required for wal_level and archive_mode changes
docker restart alloydb-omni

# Take a base backup to Cloud Storage to anchor your PITR chain
docker exec alloydb-omni pg_basebackup \
  -U postgres \
  -D /tmp/basebackup \
  -Ft \
  -z \
  --checkpoint=fast \
  --wal-method=stream

# Upload the base backup
tar czf - /tmp/basebackup | \
  gcloud storage cp - \
    gs://your-company-alloydb-omni-wal/basebackups/$(date +%Y%m%d-%H%M%S).tar.gz

    High availability with Patroni

    The most production-proven HA approach for Omni is running Patroni to orchestrate multiple container instances. You already know how Patroni works with vanilla PostgreSQL; the configuration for Omni is identical at the Patroni level because Omni exposes the same replication API as PostgreSQL.

    # /etc/patroni/patroni.yml for AlloyDB Omni primary node
scope: alloydb-omni-cluster
namespace: /db/
name: omni-node-01

restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.0.1.10:8008

etcd3:
  hosts:
    - 10.0.1.20:2379
    - 10.0.1.21:2379
    - 10.0.1.22:2379

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576  # 1 MB — adjust for your RPO tolerance
  initdb:
    - encoding: UTF8
    - data-checksums

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.1.10:5432
  data_dir: /alloydb/data
  bin_dir: /usr/lib/postgresql/15/bin
  parameters:
    max_connections: 500
    shared_buffers: 16GB
    work_mem: 64MB
    wal_level: replica
    max_wal_senders: 10
    max_replication_slots: 10
    hot_standby: on
    # AlloyDB Omni specific
    alloydb.enable_columnar_engine: on
    alloydb.columnar_memory_size_mb: 8192

tags:
  nofailover: false
  noloadbalance: false
  clonefrom: false
  nosync: false

    One thing to verify before committing to this architecture: the columnar engine state is not replicated. The columnar cache on the primary gets rebuilt from scratch on a standby that promotes to primary. The first 15–30 minutes after a failover will have degraded analytical query performance until the new primary repopulates the columnar cache from query traffic. This is acceptable in most cases but needs to be communicated to application teams as expected post-failover behavior.

    23.5 Performance Tuning the Columnar Engine

    The columnar engine in AlloyDB Omni is the feature that most DBAs want to exploit first, and the place where the most time gets wasted chasing configuration parameters that do not move the needle as much as query and schema design.

    What the columnar engine actually accelerates

    The columnar engine provides meaningful speedup for queries that:

  • → Scan a large number of rows but access only a subset of columns
  • → Perform aggregations (SUM, AVG, COUNT) over wide tables
  • → Filter on low-cardinality columns where column statistics enable fast skipping

    • It provides minimal or no benefit for:

  • → Point lookups by primary key (these use the row store via index)
  • → Heavy write workloads (columnar cache is read-optimized)
  • → Queries on tables with fewer than 50,000 rows (below the default threshold)
  • → Joins where both sides are small and fit in `work_mem`

    • Diagnosing columnar engine utilization

    -- Check if the columnar engine is being used for your analytical queries
-- Run this after the workload has been running for at least 30 minutes
-- to allow the columnar cache to warm up

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    c.customer_region,
    p.product_category,
    DATE_TRUNC('month', o.order_date) AS order_month,
    COUNT(*) AS order_count,
    SUM(ol.quantity * ol.unit_price) AS total_revenue,
    AVG(ol.unit_price) AS avg_unit_price
FROM orders o
JOIN order_line_items ol ON o.order_id = ol.order_id
JOIN customers c ON o.customer_id = c.customer_id
JOIN products p ON ol.product_id = p.product_id
WHERE o.order_date >= '2023-01-01'
  AND o.order_date < '2024-01-01'
GROUP BY 1, 2, 3
ORDER BY 1, 2, 3;

-- In the plan output, look for nodes like:
--   "Columnar Scan on order_line_items"
--   "Columnar Scan on orders"
-- If you see "Seq Scan" on large tables, the columnar cache has not
-- yet populated those tables or the threshold is preventing columnar access

-- Check current columnar cache contents
SELECT
    schemaname,
    tablename,
    pg_size_pretty(columnar_size_bytes) AS columnar_size,
    columnar_row_count,
    to_char(last_refresh_time, 'YYYY-MM-DD HH24:MI:SS') AS last_refresh
FROM alloydb_columnar_info
WHERE columnar_row_count > 0
ORDER BY columnar_size_bytes DESC;

-- Check columnar engine memory utilization
SELECT
    name,
    setting,
    unit
FROM pg_settings
WHERE name IN (
    'alloydb.columnar_memory_size_mb',
    'alloydb.enable_columnar_engine',
    'alloydb.auto_columnar_scan_threshold',
    'alloydb.columnar_engine_mode'
);

-- Force specific columns' tables into the columnar cache
-- when automatic population is too slow for your testing cadence
SELECT alloydb_columnar_refresh('public.order_line_items');
SELECT alloydb_columnar_refresh('public.orders');

    Tuning memory allocation

    The columnar engine competes with shared_buffers for RAM. The right split depends heavily on your workload ratio. A useful starting heuristic:

  • → **Primarily OLTP (< 20% analytical queries):** `shared_buffers` = 25% of RAM, columnar memory = 5–10% of RAM
  • → **Mixed OLTP/OLAP (20–60% analytical queries):** `shared_buffers` = 20% of RAM, columnar memory = 15–20% of RAM
  • → **Primarily OLAP (> 60% analytical queries):** `shared_buffers` = 15% of RAM, columnar memory = 25–30% of RAM

    • These are starting points, not rules. Use the query timing before and after adjustments to validate whether moving memory between the two caches improves your actual workload.

    -- On a 64 GB host with a mixed OLTP/OLAP workload
-- Adjust shared_buffers and columnar memory simultaneously
-- Note: shared_buffers requires a restart; columnar memory does not

ALTER SYSTEM SET shared_buffers = '12GB';
-- Restart container after this change

-- Columnar memory can be adjusted without restart
ALTER SYSTEM SET alloydb.columnar_memory_size_mb = 12288;  -- 12 GB
SELECT pg_reload_conf();

-- After workload runs for 30+ minutes, measure hit rates
-- Columnar reads vs total analytical scans
SELECT
    SUM(columnar_rows_read) AS columnar_rows,
    SUM(heap_rows_read) AS heap_rows,
    ROUND(
        SUM(columnar_rows_read)::numeric /
        NULLIF(SUM(columnar_rows_read) + SUM(heap_rows_read), 0) * 100,
        2
    ) AS columnar_pct
FROM alloydb_columnar_query_stats;

    Schema design patterns that maximize columnar benefit

    The columnar engine rewards the same schema design choices that help any columnar store — wide, flat tables with fewer joins. If you have a heavily normalized schema designed for OLTP efficiency, you will get less columnar benefit than someone running a star schema. This does not mean you should denormalize your OLTP tables; it means you should consider whether Omni is the right home for your most analytical workloads, or whether you should push aggregated data into dedicated wide tables that the columnar engine can work through efficiently.

    -- PATTERN: Create a materialized summary table optimized for columnar access
-- Refresh this periodically from the normalized OLTP tables

CREATE TABLE sales_summary_columnar (
    summary_date        DATE NOT NULL,
    customer_region     TEXT NOT NULL,
    product_category    TEXT NOT NULL,
    product_subcategory TEXT NOT NULL,
    sales_channel       TEXT NOT NULL,
    order_count         INTEGER NOT NULL,
    unit_count          INTEGER NOT NULL,
    gross_revenue       NUMERIC(18, 4) NOT NULL,
    discount_amount     NUMERIC(18, 4) NOT NULL,
    net_revenue         NUMERIC(18, 4) NOT NULL,
    return_count        INTEGER NOT NULL DEFAULT 0,
    return_amount       NUMERIC(18, 4) NOT NULL DEFAULT 0
)
-- Partition by month to improve columnar segment pruning
PARTITION BY RANGE (summary_date);

-- Create monthly partitions
CREATE TABLE sales_summary_columnar_2024_01
    PARTITION OF sales_summary_columnar
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

CREATE TABLE sales_summary_columnar_2024_02
    PARTITION OF sales_summary_columnar
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

-- Force the summary table into the columnar cache immediately
-- rather than waiting for query pattern detection
ALTER TABLE sales_summary_columnar SET (columnar = on);

    Partitioning interacts with the columnar engine in an important way: the columnar cache tracks data at the partition level. A query that filters on the partition key can skip entire partitions before the columnar engine even evaluates individual rows. Combine partition pruning with columnar scanning and you get compounding performance improvements on date-range analytical queries — the most common pattern in reporting workloads.

    23.6 Upgrading AlloyDB Omni Without Downtime

    Omni updates release as new container image tags. You control when to apply them, but letting upgrades accumulate creates larger, riskier jumps. A rolling upgrade process for standalone container deployments and Kubernetes deployments looks different but shares the same validation structure.

    Standalone container upgrade procedure

    #!/bin/bash
# alloydb_omni_upgrade.sh
# Safe upgrade procedure for a standalone AlloyDB Omni deployment
# Prerequisites: Patroni or application-level connection retry in place

set -euo pipefail

NEW_IMAGE="gcr.io/alloydb-omni/alloydb-omni:15.6.0"
CONTAINER_NAME="alloydb-omni"
DATA_DIR="/alloydb/data"
LOG_DIR="/alloydb/logs"
CREDS_DIR="/etc/alloydb"
POSTGRES_PASSWORD="YourSecureP@ssword123"
GCP_PROJECT="your-project-id"
COLUMNAR_MB=8192

echo "=== AlloyDB Omni Upgrade ==="
echo "Target image: ${NEW_IMAGE}"
echo "Start time: $(date)"

# Step 1: Pull the new image while the current container is still running
echo "[1/7] Pulling new image..."
docker pull "${NEW_IMAGE}"

# Step 2: Verify current cluster health before touching anything
echo "[2/7] Checking cluster health..."
docker exec "${CONTAINER_NAME}" psql -U postgres -c "SELECT version();" || {
    echo "ERROR: Current instance not healthy. Aborting upgrade."
    exit 1
}

# Step 3: Capture current configuration for comparison after upgrade
echo "[3/7] Capturing current configuration snapshot..."
docker exec "${CONTAINER_NAME}" psql -U postgres -t -c \
    "SELECT name || '=' || setting FROM pg_settings
     WHERE source = 'configuration file'
     ORDER BY name;" > /tmp/pre_upgrade_config.txt

# Step 4: Checkpoint and graceful shutdown
echo "[4/7] Initiating checkpoint and graceful shutdown..."
docker exec "${CONTAINER_NAME}" psql -U postgres -c "CHECKPOINT;"
docker stop "${CONTAINER_NAME}"

# Step 5: Rename the old container (preserve it for rollback)
echo "[5/7] Archiving old container..."
docker rename "${CONTAINER_NAME}" "${CONTAINER_NAME}-prev-$(date +%Y%m%d%H%M%S)"

# Step 6: Start the new container on the same data directory
echo "[6/7] Starting new container version..."
docker run -d \
  --name "${CONTAINER_NAME}" \
  --restart unless-stopped \
  -e POSTGRES_PASSWORD="${POSTGRES_PASSWORD}" \
  -e ALLOYDB_ENABLE_COLUMNAR_ENGINE=true \
  -e ALLOYDB_COLUMNAR_MEMORY_SIZE_MB="${COLUMNAR_MB}" \
  -e GOOGLE_APPLICATION_CREDENTIALS=/etc/alloydb/gcp-credentials.json \
  -e GOOGLE_CLOUD_PROJECT="${GCP_PROJECT}" \
  -e ALLOYDB_OBSERVABILITY_ENABLED=true \
  -p 5432:5432 \
  -v "${DATA_DIR}:/var/lib/postgresql/data" \
  -v "${LOG_DIR}:/var/log/postgresql" \
  -v "${CREDS_DIR}:/etc/alloydb:ro" \
  --shm-size=2g \
  --cpus=16 \
  --memory=64g \
  "${NEW_IMAGE}"

# Step 7: Validate the new instance
echo "[7/7] Validating new instance..."
sleep 10  # Allow PostgreSQL to finish startup

docker exec "${CONTAINER_NAME}" psql -U postgres -c "SELECT version();" && \
docker exec "${CONTAINER_NAME}" psql -U postgres -c \
    "SELECT count(*) FROM pg_settings WHERE name LIKE 'alloydb%';" && \
echo "Upgrade complete. New version running." || {
    echo "ERROR: Post-upgrade validation failed."
    echo "To rollback, stop the new container and start the -prev container."
    exit 1
}

echo "Upgrade complete at: $(date)"
echo "Previous container preserved as: ${CONTAINER_NAME}-prev-*"
echo "Once satisfied with stability, remove old container with:"
echo "  docker rm \$(docker ps -a --filter name=${CONTAINER_NAME}-prev -q)"

    Kubernetes rolling upgrade

    With the AlloyDB Omni Operator, upgrades are handled by patching the DBCluster resource with the new version. The Operator coordinates a rolling restart that respects the primary/standby topology:

    # Check available versions
kubectl describe dbcluster prod-analytics-cluster -n database | grep -i version

# Patch the databaseVersion field to trigger a rolling upgrade
kubectl patch dbcluster prod-analytics-cluster \
  -n database \
  --type merge \
  -p '{"spec":{"databaseVersion":"15.6.0"}}'

# Watch the Operator coordinate the upgrade
kubectl get dbcluster prod-analytics-cluster -n database -w

# The Operator upgrades standbys first, then performs a controlled
# switchover before upgrading the original primary.
# This produces a brief connection interruption at switchover time —
# typically a few seconds if your application handles connection retries.

# Verify post-upgrade
kubectl exec -n database \
  $(kubectl get pods -n database -l dbcluster=prod-analytics-cluster \
    -o jsonpath='{.items[0].metadata.name}') \
  -- psql -U postgres -c "SELECT version();"

    23.7 Edge Deployment Patterns

    One use case that AlloyDB Omni enables and cloud-only AlloyDB cannot is edge deployment: running a full AlloyDB-compatible engine at a location with intermittent or constrained connectivity to Google Cloud. Factory floors, retail point-of-sale systems, ships, remote mining sites — anywhere that needs analytical query capability locally but cannot tolerate cloud round-trip latency or potential connectivity loss.

    Design principles for edge deployments

    Edge deployments require a different set of trade-offs than datacenter deployments:

  • → **Resource constraints are real.** An edge device may have 8 GB of RAM and a 4-core industrial CPU. The columnar engine's default memory allocation of 1 GB may be more than you can spare. Be aggressive about setting `alloydb.columnar_memory_size_mb` to a value that leaves adequate headroom for OS and application processes.
  • → **Connectivity is intermittent by definition.** Design your backup and observability pipeline to tolerate periods without Cloud Storage or Cloud Monitoring access. The WAL archiving `archive_command` should fail gracefully and queue locally rather than crashing the database when the WAN link is down.
  • → **Data sync is a separate problem.** Omni does not solve bidirectional sync between edge and central. You need to design replication flows explicitly — whether that is logical replication from edge to a central AlloyDB instance, a change-data-capture pipeline, or periodic bulk export.
    • # Edge deployment: resource-constrained container configuration
# Assumes 16 GB RAM host, 8 vCPUs, local SSD storage

docker run -d \
  --name alloydb-omni-edge \
  --restart unless-stopped \
  -e POSTGRES_PASSWORD='EdgeSecurePass456' \
  -e ALLOYDB_ENABLE_COLUMNAR_ENGINE=true \
  -e ALLOYDB_COLUMNAR_MEMORY_SIZE_MB=1024 \
  -e ALLOYDB_OBSERVABILITY_ENABLED=false \
  -p 5432:5432 \
  -v /alloydb/data:/var/lib/postgresql/data \
  -v /alloydb/wal-archive:/var/lib/postgresql/wal-archive \
  --shm-size=512m \
  --cpus=6 \
  --memory=12g \
  gcr.io/alloydb-omni/alloydb-omni:latest

# Configure archiving to local directory when cloud is unavailable
# A separate sync process uploads to Cloud Storage when connectivity resumes
docker exec alloydb-omni-edge psql -U postgres << 'EOF'
ALTER SYSTEM SET archive_mode = 'on';
ALTER SYSTEM SET archive_command =
    'test ! -f /var/lib/postgresql/wal-archive/%f &&
     cp %p /var/lib/postgresql/wal-archive/%f';
ALTER SYSTEM SET archive_timeout = '600';
SELECT pg_reload_conf();
EOF
    # Sync script to upload locally archived WAL to Cloud Storage
# Run this as a cron job — it handles intermittent connectivity gracefully
#!/bin/bash
# edge_wal_sync.sh

WAL_ARCHIVE_DIR="/alloydb/wal-archive"
GCS_BUCKET="gs://your-company-edge-wal-archive"
SITE_ID="factory-floor-01"

# Attempt upload — gsutil exits 0 on success, non-zero on network failure
# The loop ensures already-uploaded files are skipped (gsutil -n flag)
gsutil -m cp -n \
  "${WAL_ARCHIVE_DIR}"/*.* \
  "${GCS_BUCKET}/${SITE_ID}/" 2>/var/log/edge_wal_sync.log

if [ $? -eq 0 ]; then
    # Clean up local WAL files older than 7 days after successful upload
    find "${WAL_ARCHIVE_DIR}" -name "*.gz" -mtime +7 -delete
    echo "$(date): WAL sync completed successfully" >> /var/log/edge_wal_sync.log
else
    echo "$(date): WAL sync failed — will retry next cycle" >> /var/log/edge_wal_sync.log
fi

    Logical replication from edge to central AlloyDB

    If you need near-real-time data flow from edge Omni instances to a central AlloyDB cluster in GCP (or to another Omni instance in your datacenter), logical replication is the right mechanism. AlloyDB Omni supports PostgreSQL logical replication as both publisher and subscriber.

    -- On the edge AlloyDB Omni instance (publisher side)
-- Requires wal_level = logical, which we set in the earlier configuration

-- Create a publication for the tables you want to replicate centrally
CREATE PUBLICATION edge_to_central_pub
FOR TABLE
    sensor_readings,
    production_events,
    quality_inspection_results
WITH (publish = 'insert, update, delete');

-- Create a replication user with minimal privileges
CREATE ROLE replication_user
  LOGIN REPLICATION PASSWORD 'ReplPass789!';

GRANT SELECT ON
    sensor_readings,
    production_events,
    quality_inspection_results
TO replication_user;

-- Verify publication
SELECT pubname, pubtables FROM pg_publication_tables
WHERE pubname = 'edge_to_central_pub';
    -- On the central AlloyDB instance (subscriber side)
-- This runs on either AlloyDB in GCP or another AlloyDB Omni instance

-- The target tables must already exist with compatible schemas
-- Create the subscription pointing to the edge Omni instance
CREATE SUBSCRIPTION central_from_edge_sub
CONNECTION 'host=edge-site-01.internal
            port=5432
            dbname=production
            user=replication_user
            password=ReplPass789!
            sslmode=require'
PUBLICATION edge_to_central_pub
WITH (
    connect = true,
    enabled = true,
    create_slot = true,
    copy_data = true,
    synchronous_commit = 'off'  -- async is appropriate for edge replication
);

-- Monitor replication lag
SELECT
    subname,
    pid,
    received_lsn,
    latest_end_lsn,
    latest_end_time
FROM pg_stat_subscription;

    One operational concern with logical replication from edge sites: if the edge site loses connectivity for an extended period, the replication slot on the publisher holds WAL on disk until the subscriber reconnects. On a space-constrained edge device, this can fill the data volume. Set a max_slot_wal_keep_size parameter to bound WAL retention, accepting that a subscriber that falls too far behind will need a full re-sync rather than catching up through replication:

    -- On the edge Omni instance: limit WAL held for replication slots
ALTER SYSTEM SET max_slot_wal_keep_size = '10GB';
SELECT pg_reload_conf();

-- Monitor slot WAL retention
SELECT
    slot_name,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained,
    active
FROM pg_replication_slots;

    23.8 Security Hardening for Production Omni Deployments

    Running a database in a container introduces security considerations beyond what you face with a binary installed directly on a host. Container security, network isolation, credential management, and PostgreSQL-level access controls all need attention.

    Container security baseline

    # Run the container as a non-root user where the image supports it
# AlloyDB Omni's image runs the PostgreSQL process as uid 999 internally
# but the container itself should not be started as root on the host

# Verify the process user inside the container
docker exec alloydb-omni ps aux | grep postgres

# Restrict container capabilities — PostgreSQL does not need most Linux capabilities
docker stop alloydb-omni && docker rm alloydb-omni

docker run -d \
  --name alloydb-omni \
  --restart unless-stopped \
  --security-opt no-new-privileges:true \
  --cap-drop ALL \
  --cap-add CHOWN \
  --cap-add SETUID \
  --cap-add SETGID \
  --cap-add DAC_OVERRIDE \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=512m \
  --tmpfs /run:rw,noexec,nosuid,size=64m \
  -e POSTGRES_PASSWORD='YourSecureP@ssword123' \
  -e ALLOYDB_ENABLE_COLUMNAR_ENGINE=true \
  -e ALLOYDB_COLUMNAR_MEMORY_SIZE_MB=8192 \
  -e GOOGLE_APPLICATION_CREDENTIALS=/etc/alloydb/gcp-credentials.json \
  -e GOOGLE_CLOUD_PROJECT=your-project-id \
  -p 127.0.0.1:5432:5432 \
  -v /alloydb/data:/var/lib/postgresql/data \
  -v /alloydb/logs:/var/log/postgresql \
  -v /etc/alloydb:/etc/alloydb:ro \
  --shm-size=2g \
  --cpus=16 \
  --memory=64g \
  gcr.io/alloydb-omni/alloydb-omni:latest

    Note the -p 127.0.0.1:5432:5432 binding. Binding the port to loopback rather than 0.0.0.0 means PostgreSQL is only reachable from the host itself. Applications connect through a reverse proxy or pgBouncer that handles TLS termination and connection pooling. This is preferable to exposing the PostgreSQL port directly to the network.

    PostgreSQL-level access controls

    -- Harden the pg_hba.conf defaults
-- AlloyDB Omni ships with permissive defaults for developer convenience
-- Replace them with production-appropriate rules

-- View current HBA configuration
SELECT line_number, type, database, user_name, address, auth_method
FROM pg_hba_file_rules
ORDER BY line_number;

-- Remove the 'trust' auth method for local connections
-- Edit pg_hba.conf inside the data volume and reload
-- (Do this through a volume-mounted config file in production,
--  not by editing inside the container)

-- Create role hierarchy for application access
-- Never allow applications to connect as postgres superuser

CREATE ROLE app_readonly NOLOGIN;
CREATE ROLE app_readwrite NOLOGIN;
CREATE ROLE app_user LOGIN PASSWORD 'AppUserPass321!'
  IN ROLE app_readwrite;
CREATE ROLE reporting_user LOGIN PASSWORD 'ReportingPass654!'
  IN ROLE app_readonly;

-- Grant schema-level privileges rather than table-by-table
GRANT USAGE ON SCHEMA public TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO app_readonly;

GRANT USAGE ON SCHEMA public TO app_readwrite;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public
    TO app_readwrite;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_readwrite;

-- Audit who has superuser access
SELECT usename, usesuper, usecreatedb, usecreaterole
FROM pg_user
WHERE usesuper = true;

    TLS configuration

    AlloyDB Omni will use the certificates you place in the data directory. Generate a proper certificate for production rather than relying on the self-signed certificate the engine creates on first startup:

    # Generate a certificate signing request on the host
openssl req -new -newkey rsa:4096 \
  -keyout /alloydb/tls/server.key \
  -out /alloydb/tls/server.csr \
  -nodes \
  -subj "/CN=alloydb-omni.internal/O=YourCompany/C=US"

# Have your CA sign it (or use a self-signed cert for internal networks)
# Copy the signed cert to the data directory where PostgreSQL expects it
cp /alloydb/tls/server.crt /alloydb/data/server.crt
cp /alloydb/tls/server.key /alloydb/data/server.key
chmod 600 /alloydb/data/server.key

# Configure PostgreSQL to require TLS
docker exec alloydb-omni psql -U postgres << 'EOF'
ALTER SYSTEM SET ssl = 'on';
ALTER SYSTEM SET ssl_cert_file = 'server.crt';
ALTER SYSTEM SET ssl_key_file = 'server.key';
ALTER SYSTEM SET ssl_min_protocol_version = 'TLSv1.2';
SELECT pg_reload_conf();
EOF

    Key Takeaways

  • → **AlloyDB Omni delivers the columnar engine and AI extensions on your hardware**, but it does not replicate the managed-service durability model from GCP. Backup, HA, and patching are your complete responsibility; plan the operational model before deploying in production.
  • → **The columnar cache is automatic but not instantaneous.** New deployments and post-failover primaries start with a cold columnar cache. Use `ALTER TABLE ... SET (columnar = on)` and `alloydb_columnar_refresh()` to seed the cache proactively for your most important analytical tables rather than waiting for query-pattern detection to populate it.
  • → **Connecting Omni to Google Cloud is optional but valuable.** WAL archiving to Cloud Storage, metrics shipping to Cloud Monitoring, and Vertex AI embedding calls are all available through the service account integration. Each requires evaluating the data-egress and compliance implications before enabling in regulated environments.
  • → **Edge deployments are a genuine use case**, but they require explicit design for intermittent connectivity. Use `max_slot_wal_keep_size` to prevent replication slots from filling edge storage, and design your WAL archive sync to tolerate WAN outages gracefully rather than failing hard.
  • → **The columnar engine rewards query and schema design choices, not just memory tuning.** Wide, flat tables with date-range partitioning extract more benefit from the columnar path than heavily normalized schemas. Materialized summary tables populated from OLTP data are often the fastest path to realizing columnar performance gains without restructuring your transactional schema.
